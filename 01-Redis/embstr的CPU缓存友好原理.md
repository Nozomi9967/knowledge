## 一句话概括

**embstr 将 redisObject 和 SDS 分配在同一块连续内存中，利用 CPU 缓存行（Cache Line）的空间局部性（Spatial Locality），实现"一次内存加载，两个结构同时命中缓存"，避免了 raw 编码因内存碎片化导致的额外 Cache Miss。**

---

## 1. 核心概念：CPU 缓存行（Cache Line）

CPU 从内存读数据时，**不是按需只读一个字节**，而是以 **缓存行** 为单位整块加载：

| 层级  | 典型大小     | 延迟（大约） |
| ----- | ------------ | ------------ |
| L1 d-cache | 32 KB，每行 64 B | ~1 ns        |
| L2 cache    | 256 KB，每行 64 B | ~4 ns        |
| L3 cache    | 8–32 MB，每行 64 B | ~12 ns       |
| **主内存**（Cache Miss） | —            | **~60–100 ns** |

> **一次 Cache Miss 的时间，CPU 理论上可以执行几百条指令。**

### 空间局部性（Spatial Locality）

当 CPU 访问某个内存地址时，**它附近的数据大概率马上也会被访问**。因此 CPU 会把目标地址周围的整块数据（一个缓存行）都加载到缓存中。

## 2. embstr vs raw 的内存布局对比

### embstr（连续分配）

```
一次 malloc，一块连续内存：

┌─────────────── 一个缓存行 (64 字节) ───────────────┐
│  RedisObject (16字节)  │     SDS 结构体 + 数据      │
│  ┌─────┬─────┬───┬───┐│  ┌───┬───┬───┬──────────┐ │
│  │type │enc. │ptr│…  ││  │len│cap│flg│ buf[]    │ │
│  └─────┴─────┴───┴───┘│  └───┴───┴───┴──────────┘ │
└──────────────────────────────────────────────────────┘
  ^── 访问 redisObject ──→ CPU 加载 64 字节到缓存
                          → SDS 数据也在这个范围内
                          → **一次内存访问，全部命中**
```

### raw（分开分配）

```
两次 malloc，两块不相邻的内存：

地址 0x1000:   ┌──────────────────┐
               │   RedisObject    │  ← 第1次加载到缓存
               └──────────────────┘

地址 0x8000:   ┌──────────────────┐   ← 不在此缓存行中
               │      SDS 数据     │  → **Cache Miss，必须重新加载**
               └──────────────────┘
```

## 3. 分步详解：访问字符串时发生了什么

假设 Redis 要执行 `GET key` 读取一个 embstr 编码的字符串：

```
步骤1：访问 redisObject
         → CPU 查 L1 → Miss → 从主存加载 64 字节缓存行
         → 这 64 字节同时包含了紧邻的 SDS 数据

步骤2：紧接着访问 SDS 中的 len / buf[]
         → CPU 查 L1 → **Hit！**数据已经在缓存行里了
         → 无需再次访问主存
```

如果是 raw 编码：

```
步骤1：访问 redisObject
         → 加载一个缓存行（地址 0x1000 附近）

步骤2：通过 ptr 跳转到 SDS（地址 0x8000）
         → CPU 查 L1 → **Miss！** 不在缓存中
         → 必须再次访问主存，加载另一个缓存行

代价：多了一次 ~60-100ns 的主存访问
```

---

## 4. 在 Redis 单线程模型下，影响被放大

Redis 是 **单线程事件循环**：

- 所有请求串行排队处理
- 每个请求内部的数据访问路径越短越好
- 如果每次字符串访问都多一次 Cache Miss，**千万级 QPS 下，累积的延迟非常可观**
- `embstr` 省去的不仅是 1 次 `malloc/free`，更是 **高频率路径上的 Cache Miss 开销**

## 5. EMSTR 的边界条件

| 版本           | embstr 最大长度 | 原因                         |
| -------------- | --------------- | ---------------------------- |
| Redis 2.+      | 32 字节         | redisObject(16) + SDS(16)    |
| Redis 3.0–4.0  | 39 字节         | SDS header 结构调整          |
| **Redis 5.0**  | **44 字节**     | SDS 去掉旧 flags，对齐更紧凑 |
| Redis 7.0+     | 仍为 44 字节     | 使用新的 SDS 布局但边界不变  |

> 44 字节的来源：
> - 一个缓存行 = 64 字节
> - redisObject 占用 16 字节 → 留给 SDS 的数据空间 = 64 - 16 = 48 字节
> - SDS header（sdshdr8）占用 4 字节（len + alloc + flags + 终止符 '\0'）
> - 实际可用字符串长度 = 48 - 4 = **44 字节**

## 6. Redis 中其他利用缓存局部性的优化

不只是 embstr，Redis 的多个数据结构都利用了这一思想：

| 数据结构     | 缓存友好策略                         |
| ------------ | ------------------------------------ |
| **ziplist**  | 所有元素连续存储，遍历时顺序命中缓存行 |
| **listpack** | ziplist 的改进版，同样连续存储         |
| **intset**   | 整数数组连续存储，二分查找时缓存命中率高 |
| **quicklist** | 由多个 ziplist/listpack 节点组成，每个节点内连续 |

## 7. 面试回答模板

> **问：为什么 embstr 对 CPU 缓存友好？**
>
> 回答要点：
> 1. CPU 以 **缓存行（64 字节）** 为单位加载数据
> 2. embstr 的 redisObject 和 SDS **在同一块连续内存**
> 3. 访问 redisObject 时，CPU 把**相邻的 SDS 数据也一并加载到缓存行中**
> 4. 紧接着访问 SDS 时，直接**缓存命中**，无需再次访问主存
> 5. raw 编码两段内存**相隔很远**，访问 SDS 必然触发 **Cache Miss**（~60-100ns 延迟）
> 6. Redis 单线程高并发下，每次 Cache Miss 的累积效应非常显著
