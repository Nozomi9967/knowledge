# 第 1 章 · 内核基础：用户态与内核态

## 1.1 知识

**直觉：用户态是"普通住户"，内核态是"物业+供电局"。改电表要交工单（系统调用），工单本身有成本。**

- CPU 有特权级（x86 Ring 0~3，Linux 只用 0 和 3）。**特权指令**（改页表基址寄存器、操作 IO 端口、关中断）只能在内核态执行。

[[OS-IO篇#**什么是 IO 端口**]]

### 陷入内核（Trap）的三条路

| 入口 | 性质 | 例子 |
|---|---|---|
| 系统调用 | 主动，程序请求内核服务 | `read` / `write` / `futex` |
| 异常 | 被动，同步，指令执行出错 | 缺页、除零、非法地址 |
| 中断 | 被动，异步，外部设备/时钟触发 | 时钟中断、网卡收包 |

>同步和异步的区别在于：事件是否由 CPU 当前正在执行的那条指令引起。同步由当前指令引起，异步与当前指令无关。​


- 陷入内核 = 系统调用 ∪ 异常 ∪ 中断。三条路都要付模式切换代价，但只有系统调用是"我要求内核帮我做事"。
- 两个高频坑：① 时钟中断每秒上百次都陷入内核，但那只是调度器计时，不是系统调用；② **vDSO** 让 `gettimeofday` / `clock_gettime` 等"系统调用"根本不陷入内核（内核把代码映射进用户空间直接读）。
- ==可优化的只有系统调用部分：批量（`writev`）、复用（epoll）、避免拷贝（sendfile）、vDSO。异常只能靠锁页/大页/预读缓解，中断不可控。==

### 一次切换贵在哪

- 系统调用：保存用户态寄存器现场 → 切内核栈 → 参数校验 → 执行 → 恢复现场 → 切回。开销 ≈ **1μs 量级**（比函数调用贵两三个数量级；KPTI 内核页表隔离后更贵）。
- **精度区分**：模式切换（用户⇄内核）只换栈，**不换页表**；**进程上下文切换才换页表**（改 CR3 → TLB 全刷 → 缓存失效）。KPTI 是唯一例外（模式切换也多一次页表切换）。
- **线程切换不换页表**（同进程共用 CR3），只换栈和寄存器，所以比进程切换便宜一截。缓存也大部分保留：同进程代码段、堆、全局区物理地址没变，只有私有栈、ThreadLocal、切换点附近指令流是冷的。注意：线程切到另一个核时 L1/L2 带不过去（只有 L3 共享）。
- **IO 密集场景线程开太多反而变慢的根因**：不是线程本身重，是切换时丢缓存重。

## 1.2 排障

- `%sy` 比 `%us` 高 → 内核态开销大：上下文切换频繁、系统调用密、大量软中断。优化方向：批量、复用、减少锁竞争。
- 中断耗时体现在 `top` 的 `%si`（软中断）。

> 完整话术见第 11 章 Q1（进程 vs 线程切换）、Q7（中断 vs 异常）。

# 第 2 章 · 进程与线程

## 2.1 知识

**直觉：进程是独门独院的一户人家，线程是同院里共用厨房的几个人，协程是这些人约好自觉轮换、不惊动物业。**

### 2.1.1 三层对比（必背）

| 维度 | 进程 | 线程 | 协程 |
|---|---|---|---|
| 定位 | 资源分配的最小单位 | CPU 调度的最小单位 | 用户态轻量执行单元，运行时调度 |
| 地址空间 | 独立（各有页表） | 同进程内共享 | 同一线程内共享 |
| 私有部分 | — | 栈、程序计数器、寄存器组 | 自己的栈（可放堆上）、寄存器上下文 |
| 切换成本 | 最贵：换页表 + TLB 刷 + 缓存失效 | 中等：换栈和寄存器，不换页表 | 最轻：用户态保存少量上下文，不进内核 |
| 谁调度 | 内核 | 内核 | 用户态（运行时/库） |
| 崩溃影响 | 互不影响 | 一个线程崩可能整进程完 | 取决于实现：Go 的 goroutine panic 默认整进程崩；Java 虚拟线程的未捕获异常只死自己 |
| 数量级 | 几十~几百 | 几百~几千 | 几万~百万 |

**线程切换比进程便宜的本质（一句话）**：同进程线程共用一张页表，切换时 CR3 不动、TLB 一条不清，缓存大部分是热的；进程切换是地址空间全换、TLB 全刷、工作集缓存全丢。细节见第 1 章。

### 2.1.2 PCB（进程控制块）

- 内核里描述和管理进程的数据结构，常驻内核空间；Linux 实现是 `struct task_struct`。
- 装什么：PID、处理机现场（寄存器/PC/栈指针）、调度信息（状态、优先级、vruntime、时间片）、内存管理信息（页表基址、`mm_struct`）、文件描述符表、信号与 IPC 资源、CPU 记账。
- 三个关键点：① **PCB 是进程存在的唯一标志**——代码数据可共享换出，只要 PCB 在进程就存在；② 状态位都是 PCB 字段：新建 = PCB 建好没进就绪队列；僵尸 Z = 资源都释放只剩 PCB 等父进程 `wait()`；③ **进程切换 = 换 PCB**（保存/恢复寄存器就是存进/取出 PCB）。
- Linux 里进程和线程都是 `task_struct`，区别只在 `clone` 要不要共享地址空间。Java 平台线程 ≈ 一个 task_struct（1:1）；**虚拟线程没有自己的 PCB**。

### 2.1.3 进程状态

```
        调度            等待资源/事件        资源就绪/事件完成（唤醒）
  就绪 ─────▶ 运行 ─────────▶ 阻塞 ────────────────────▶ 就绪
    ▲          │
    └─时间片用完┘
               │ exit（终止）
               ▼
              僵尸 Z ──父进程 wait() 收尸──▶ 消亡
```

- 教科书五态模型：新建 → 就绪 → 运行 → 阻塞 → 终止。僵尸不是独立第五态，是终止态的滞留。
- Linux 状态位与经典模型对码：

| 经典模型 | Linux | 说明 |
|---|---|---|
| 就绪 + 运行 | **R** | top 里 R = 两者合集 |
| 阻塞 | **S**（可中断）/ **D**（不可中断） | 区别只在能不能被信号唤醒；D 等磁盘/NFS，`kill -9` 都杀不掉，**计入 Load** |
| 停止 | **T** | SIGSTOP / 调试 |
| 僵尸 | **Z** | 已退，父进程没 wait() 收尸 |
| 消亡 | **X** | 只存在一瞬间 |

- D 和 S 醒来后去向相同（都进 R），区别只在等待期间 D 听不见信号。

### 2.1.4 进程创建与生命周期（fork / exec / wait）

- **fork**：创建子进程。**复制页表而不复制数据**（写时复制 COW，见第 5 章），返回两次：父进程得到子进程 PID，子进程得到 0。
- **exec**：用新程序替换当前进程的地址空间，PID 不变。shell 执行命令 = fork + exec。
- **wait**：父进程回收子进程的退出状态。不回收就成僵尸。
- **孤儿进程 vs 僵尸进程**：孤儿 = 父先退、子被 init(PID 1) 收养，**无害**；僵尸 = 子已退、父没回收，**有害**（占 PID 和 PCB）。
- **守护进程**：脱离终端后台运行，传统做法 fork 两次 + `setsid`；现代多交 systemd/容器管理。

### 2.1.5 线程模型（1:1 / M:1 / M:N）

| 模型 | 说明 | 例子 |
|---|---|---|
| 1:1 | 用户线程直接对应内核线程 | Linux、Java 平台线程 |
| M:1 | 多个用户线程复用一个内核线程；一个阻塞全阻塞 | 早期绿色线程 |
| M:N | M 个用户线程调度到 N 个内核线程上 | Go goroutine、**Java 虚拟线程** |

### 2.1.6 线程共享了什么、Java 里怎么体现

- 共享：堆（Java 对象）、方法区/元空间、文件描述符表
- 私有：虚拟机栈 + 本地栈、程序计数器、寄存器

这解释了 ThreadLocal 为什么存在——堆是共享的，想要私有变量就得自己造 per-thread 映射表（`Thread.threadLocals`）。OS 层"共享堆 + 私有栈"是 Java 并发一半问题的物理来源。

### 2.2 协程：把调度权抢回用户态

- **为什么线程不够用**：线程是内核对象，创建要 `clone()` 系统调用、栈默认 8MB（虚拟内存，`ulimit -s` 可改），数量受内核调度限制。扛 10 万连接用"一连接一线程"就是 10 万 × 8MB + 内核调度崩溃。
- **协程做法**：把"阻塞时让出、就绪时恢复"从内核搬到用户态——挂起的只是栈上几个字节的状态，切换不进内核。

**Java 虚拟线程（JDK 21 / Loom）**：

- 挂载在**载体线程**（Carrier Thread，ForkJoinPool 平台线程）上；阻塞 IO 时把栈帧**卸载（unmount）**成堆上的 continuation，载体线程立刻跑别的虚拟线程。
- 百万虚拟线程 ≠ 百万内核线程；内核只看到那几十个平台线程。
- **调度是协作式不是抢占式**：JVM 不会主动打断正在跑的虚拟线程，只在它自己走到卸载点（阻塞 IO、`park`、`sleep`、队列 take）时挂起。内核抢占载体线程也没用——跑的仍是同一个没卸载的虚拟线程。
- **后果不是"没用"，是"饿死别人"**：全 JVM 一个共享调度器，载体数默认 = CPU 核数，没法给 CPU 任务单独开池做隔离；载体被不阻塞的虚拟线程占满后，IO 任务恢复时挂不上载体，表现是 CPU 满、请求全卡。
- **判据（别背成"CPU 密集不能用"）**：要避开的是"长跑 + 全程不阻塞"的组合。短促 CPU 突发算完就退、混合负载阻塞段照样卸载，都 ✅；只有长时间纯算不阻塞 ❌。

| 场景 | 适合虚拟线程吗 | 原因 |
|---|:---:|---|
| 阻塞式 IO（RPC / DB） | ✅ | 主战场，阻塞点就是卸载点 |
| 短促 CPU 突发 | ✅ | 很快退出归还载体 |
| CPU 与 IO 混合 | ✅ | 阻塞段照样卸载 |
| 长时间跑 + 全程不阻塞 | ❌ | 占着载体白跑，饿死 IO 任务 |
| pinning：synchronized 块中阻塞 / 大量本地方法 | ⚠ | JDK 21 卸不掉退化成重量级线程；**JDK 24 起 JEP 491 已消除 synchronized 的 pinning**，只剩 Native 方法 |

- 单线程事件循环型协程（asyncio/Node）的代价是放弃多核并行 + 一个死循环饿死全线程；Java 虚拟线程是 M:N 能吃满多核，代价是没有内核抢占时间片。

## 2.3 排障

- 一堆 D 状态 → 查磁盘/存储/NFS；一堆 Z 状态 → 修父进程没 `wait()`。
- 僵尸为什么 `kill -9` 杀不掉：已无可执行实体，剩下一张等认领的档案卡，信号没有送达对象。

# 第 3 章 · CPU 调度与 Load

## 3.1 知识

### 调度算法

| 算法 | 思路 | 缺陷 |
|---|---|---|
| FCFS 先来先服务 | 队列顺序执行 | 护航效应：长作业后面所有短作业跟着等 |
| SJF 短作业优先 | 最短先到 | 要预知时长（做不到），长作业饥饿 |
| 高响应比优先 | 响应比 =（等待+预估运行）/ 预估运行 | 等越久响应比越高，缓解饥饿，但仍要估时长 |
| 时间片轮转 RR | 每人一个时间片 | 太小切换开销占比高；太大退化成 FCFS |
| 多级反馈队列 | 多优先级队列，跑不完降级、排队久升级 | Linux 实际采用的思路 |

**CFS（完全公平调度器）**：没有固定时间片，维护每个任务的**加权虚拟运行时间 `vruntime`**，红黑树排序，永远挑最小的跑——权重（nice 值）大的 vruntime 涨得慢，分到更多 CPU。加分项：Linux 6.6 起被 **EEVDF** 取代（同样基于虚拟时间，额外按最早虚拟截止期挑选）。

**优先级反转**（补充）：低优先级持锁 → 高优先级等锁 → 中优先级抢占低优先级 → 高优先级被间接阻塞。解法：**优先级继承**（临时把持锁者提到等待者的优先级）。火星探路者事故的经典案例。

### Load Average

- 统计 **R 状态（运行+可运行）+ D 状态（不可中断睡眠）** 的任务数，1/5/15 分钟指数衰减移动平均。
- 判断标准看核数：4 核 Load=4 满载，>4 排队，8 重度堆积。经验：单核 Load ≈ 0.7 告警。
- **Load 高但 CPU 不高** = 大量进程卡 D 状态等 IO（磁盘慢、NFS 挂、大量换页）。加 CPU 没用，看 `iostat`、`vmstat` 的 `bi/bo`、`wa`。

## 3.2 排障

`vmstat 1`：`r` 大 = 真缺 CPU；`wa` 大 = 存储瓶颈。两种处理方向完全相反。

## 3.3 面试

> "Load 不是 CPU 指标，是**任务堆积**指标——在跑的 + 排队等 CPU 的 + 等 IO 醒不过来的。判断机器压力大不大，先看 Load 除以核数，再看 vmstat 的 r 列和 wa 列。"（见第 11 章）

# 第 4 章 · 并发同步（含死锁）

## 4.1 知识

**直觉：多个执行流要安全共享资源，核心问题是"拿不到时怎么等"——是原地转圈（自旋），还是去睡觉（阻塞）。**

### 同步原语对比

| 原语 | 拿不到时的行为 | 适用 | Java 对应 |
|---|---|---|---|
| 互斥锁 mutex | 睡眠，让出 CPU | 临界区较长 | `ReentrantLock`、重量级 `synchronized` |
| 自旋锁 spinlock | 忙等，不睡眠 | 临界区极短、多核 | CAS 自旋、`synchronized` 轻量级阶段 |
| 读写锁 | 读读并行，写独占 | 读多写少 | `ReentrantReadWriteLock` |
| 条件变量 | 等某条件成立，配 mutex 用 | 生产者-消费者 | `Condition`、`wait/notify` |
| 信号量 | 计数，P/V 原语 | 限流、资源池 | `Semaphore` |

- **自旋和睡眠的取舍**：睡眠要付两次上下文切换的代价；临界区短于这个代价时自旋更划算。**单核上自旋毫无意义**——持锁者没机会运行，白烧 CPU。
- **futex（Fast Userspace muTEX）**：无竞争时只在用户态用原子指令改一个整数，不进内核；有竞争时才走系统调用睡眠/唤醒。所以大部分加锁不付陷入内核代价——和 JVM 锁优化（偏向/轻量级锁）是同一思路。
- **优先级反转**：见第 3 章。

### 死锁

**四个必要条件（缺一不可）**：

| 条件 | 含义 |
|---|---|
| 互斥 | 资源一次只能被一个线程持有（锁的本质属性，去不掉） |
| 请求并持有 | 拿到 A 再申请 B |
| 不可剥夺 | 已持有的不能被强抢，只能自己释放 |
| 循环等待 | 形成首尾相接的等待环：T1→T2→T1 |

**四种处理策略**：

| 策略 | 做法 | 现实 |
|---|---|---|
| 预防（静态） | 破坏任一条件：一次性申请全部资源 / **按固定顺序加锁**（最实用）/ 申请失败主动释放 / 更细粒度或无锁结构 | 工程可落地 |
| 避免（动态） | **银行家算法**：分配前检查安全序列 | 教科书爱考，生产没人用（要预知最大需求） |
| 检测 | 允许发生，定期用等待图找环 | Java `jstack`、`ThreadMXBean.findDeadlockedThreads()` |
| 忽略 | 不管 | **Linux 和 Java 实际都选这个** |

**值钱的一句话**：操作系统和 JVM 都没真正防死锁——选了检测/忽略。死锁在生产上是**编码规范问题**（保证加锁顺序全局一致），不是内核问题。

**死锁 vs 活锁 vs 饥饿**：死锁 = 都在等对方，都不动；活锁 = 都在动（互相谦让重试）但没进展，典型是两个 CAS 冲突后同时退避又同时撞上；饥饿 = 单个线程一直抢不到（优先级低、或写锁把读线程饿住）。

## 4.2 排障（Java 死锁现场，应届生说出这套就赢）

1. `top -H -p <pid>` 找高 CPU 线程号 → `printf '%x\n' <tid>` 转十六进制
2. `jstack <pid>`，搜 `deadlock`（jstack 自带检测："Found one Java-level deadlock"）
3. 看两个线程各持哪把锁、各等哪把锁 → 定位加锁顺序不一致
4. 修复：统一加锁顺序，或 `ReentrantLock.tryLock(timeout)` 拿不到就退避重来

# 第 5 章 · 内存管理

## 5.1 知识

### 分页 vs 分段 vs 段页式

| | 分页 | 分段 | 段页式 |
|---|---|---|---|
| 划分依据 | 固定大小页，对程序员透明 | 按逻辑（代码/数据/栈），大小可变 | 先分段，段内再分页 |
| 碎片 | 内部碎片 | 外部碎片 | 兼顾，但翻译要查两次 |

- **内部碎片**：分配块比需要的大，浪费在块内；**外部碎片**：空闲总量够但不连续，凑不出一块大的。

### 虚拟内存：为什么要有

三个动机，按重要性排：

1. **隔离与安全**——每个进程独立地址空间，越界直接段错误；否则一个野指针搞崩整机。
2. **连续内存假象**——物理内存是碎的，虚拟地址让程序以为自己有连续大块，链接加载才能简化。
3. **按需分配 + 可换出**——页不在物理内存也能"存在"（缺页再要/换回），才有 swap、内存超配、fork 的写时复制。

**代价**：每次访存多一层地址翻译。兜住代价的是 TLB。

### 地址翻译链路（画图题）

```
执行访存指令，CPU 发出虚拟地址
  │  地址翻译由 MMU 完成；页内偏移不变，只翻译页号
  ▼
分段（Linux 已"平坦化"，几乎不做实际变换）
  ▼
分页：虚拟页号 ──▶ 查页表（内存里，多级）──▶ 物理页框号 + 偏移 = 物理地址
        ▲
        └─ TLB（页表缓存，MMU 硬件）命中就跳过查表
```

- 页大小 x86_64 默认 **4KB**；页表多级（x86 是 4/5 级），目的是每级表正好装进一页，稀疏映射省内存。
- TLB 命中是常态（局部性原理）。一次访存：TLB 命中 ≈ 1 周期；miss 走多级页表可能几十上百周期。
- 进程切换刷 TLB；现代 CPU 有 **ASID/PCID** 标签（给 TLB 表项打地址空间编号）避免全刷——进程切换差距没教科书说的那么夸张的原因。
- 32 位寻址 4GB（内核还占 1GB，用户空间 3G）；64 位真实只用 48 位虚拟地址（LA57 后 57 位）。

**大页（Huge Page）**：页从 4KB 到 2MB，一个 TLB 表项覆盖更多地址，减少 miss，适合大内存数据库和 JVM（`-XX:+UseLargePages`）。**透明大页（THP）**有时引发延迟抖动，Redis 官方建议关闭。

### 缺页异常三种

| 类型 | 场景 | 是否读盘 |
|---|---|---|
| 非法访问 | 段错误 | 否，直接 SIGSEGV |
| 硬缺页 | 页合法但不在物理内存（swap in / mmap 首次访问） | **是** |
| 软缺页 | 页在内存只是没建映射（fork 写时复制） | 否 |

### 用户态堆：brk 与 mmap

| 方式 | 用途 | 特点 |
|---|---|---|
| `brk`/`sbrk` | 小块分配 | 移动堆顶指针；free 后不能立刻归还内核（有空洞要先整理） |
| `mmap` | 大块分配（glibc 默认阈值 **128KB**） | 单独开一段 VMA；`munmap` 立刻归还内核 |

- `brk` = **break**（program break，堆顶指针）；堆伸缩 = 拖这条线移动。
- **三层归属（边界感加分点）**：堆的两种增长方式 = 通用机制；brk/mmap 系统调用 = Unix/Linux（POSIX 已标 brk legacy，Windows 用 VirtualAlloc）；128KB 阈值、空闲链表 = glibc 实现细节（musl/jemalloc/tcmalloc 不同）。
- **考法**：为什么 free 了很多内存 `top` 里 RES 不降？→ 小块走 brk，glibc 把释放的块留在空闲链表复用，堆顶不下移。真归还要么整理成功（`malloc_trim()`），要么本来就是 mmap 来的。

### 内核物理内存分配：伙伴系统与 slab

- **伙伴系统（Buddy System）**：内核管理物理页框，按 2 的幂次成块，释放时合并相邻"伙伴"块，对抗**外部碎片**。
- **slab**：在伙伴系统之上为内核小对象（task_struct 等）建对象缓存，复用已初始化对象，减少碎片和初始化开销。

### 内存不够：swap 与 OOM Killer

求生线三步：

1. 先回收：页缓存、slab 可回收部分（几乎免费）
2. 不够就 **swap 换出匿名页**（生产上很多中间件主动 `swapoff`，因为换出后 RT 抖动巨大）
3. 还不行 → **OOM Killer** 按 `oom_score`（与匿名内存正相关）挑最大进程 SIGKILL，退出码 **137 = 128+9**

要点：

- oom_score 主要由**匿名内存**决定——页缓存不扛分（随时可回收）。"占内存最多的最容易被杀"的精确版是"**占匿名内存最多的**"。
- 保护：`oom_score_adj`（-1000 免死金牌，+1000 优先送死，默认 0）。实战给 **sshd、监控 agent** 设 -1000——否则机器快挂时连登都登不上。
- **"加 -Xmx 反而死得更快"**：机器已告急，调大堆让匿名内存更多、oom_score 更高，从候选升级成首选。正确反应是看 `dmesg` 的 `anon-rss`，确认是不是堆外/线程栈吃掉了内存。
- K8s `OOMKilled` 同一套机制，范围缩到容器 cgroup 配额内（见第 9 章）。

### 两种 OOM 对照表

| | 内核 oom-kill | JVM 抛 OutOfMemoryError |
|---|---|---|
| 谁动的手 | 内核，SIGKILL | JVM，堆分配失败 |
| 原因 | 整机内存 + swap 真没了 | 堆内 GC 后仍不够，撞了 -Xmx |
| 发现 | `dmesg | grep -i oom`，退出码 137 | 异常栈 + GC 日志，进程一般还活着 |
| 元凶 | **可能在堆外**：DirectByteBuffer、线程栈、别的进程 | 就在堆内：泄漏或配置不合理 |
| 加 -Xmx | **死得更快** | 机器有余量时可能真管用 |

### 页面置换算法

| 算法 | 思路 | 现实 |
|---|---|---|
| OPT | 换掉未来最久不用的 | 要预知未来，理论下界 |
| **LRU** | 换掉最久没被访问的 | 效果好，但精确实现每次访问都要移动节点，开销大 |
| FIFO | 换最先进来的 | 有 **Belady 异常**（内存变大缺页反而变多），不用 |
| **Clock / 二次机会** | 环形链表 + 引用位，指到 1 清 0 跳过 | LRU 的工程近似，O(1) 摊还，OS 实际多用 |
| LFU | 换访问次数最少的 | 历史高光赖着不走，需老化机制 |

**LRU 精确实现**：哈希表 + 双向链表（哈希 O(1) 定位，双向链表维护顺序、头插淘汰尾）。算法题高频手撕。

**工程联系**：Redis `allkeys-lru` 实际是采样近似 LRU（随机取 5 个 key 淘汰最久未用）；Caffeine 用 W-TinyLFU——都是"精确 LRU 太贵，用近似"同一条取舍。

### 写时复制（COW）

- fork 只复制页表，父子共享物理页并全部标只读；任何一方**写**时才触发缺页、内核才复制那一页。
- fork 的开销是**页表**开销，不是数据量开销。
- Redis BGSAVE 靠这个：fork 子进程写 RDB，父进程正常服务；代价是内存最坏翻倍，大实例 fork 卡顿、写密集可能 OOM。

## 5.2 排障

- `free -h` 看 **available**（free + 可回收 cache），别看 free 列——cache 可回收不是真占用。
- Java 进程被 Killed 无异常日志 → `dmesg | grep -i oom` 查 oom-kill，退出码 137。
- `vmstat` 的 `si/so` 非零 = 在换页 = 内存不够。

# 第 6 章 · 文件系统与磁盘（全新）

## 6.1 知识

**直觉：文件名是书的书脊标签，inode 是书的内容和目录卡片——丢了书脊不影响内容，丢了卡片书就真没了。**

### 目录项（dentry）

- **目录本身是一种文件**：它的"数据"就是一张表，每条记录是 `文件名 → inode 号` 的映射，这条记录就叫目录项（directory entry，Linux 内核里叫 dentry）。
- 所以**文件名不属于 inode，属于目录项**。同一个 inode 可以被多个目录项（不同目录、不同文件名）指向——这就是硬链接的本质。
- **路径解析（path lookup）是逐级的**：打开 `/a/b/c`，内核从根 inode 读根目录的目录项找到 `a` 的 inode，再读 `a` 目录找 `b`……一层层走。路径越深，要读的目录块越多，这也是 dentry 缓存存在的理由。
- **dentry cache（dcache）**：内核把目录项缓存在内存里加速路径解析，否则每次 open 都要一级级读磁盘目录块。和 inode cache、page cache 一样占的是可回收内存。
- **rm / mv 的真相**：`rm` 实际是 `unlink`——删目录项、inode 链接计数减 1，减到 0 且无进程打开才真正回收数据块；同文件系统内 `mv` 只改目录项（改名/换目录），inode 和数据块原地不动，所以 mv 快、也不改 mtime（见下文软硬链接表）。

### inode

- 存文件元数据（大小、权限、时间戳、数据块位置），**不含文件名**。文件名在目录项里，目录项 → inode → 数据块。
- 所以每个文件系统 inode 数量有限，可能出现"磁盘没满但 inode 用尽"。

### 硬链接 vs 软链接

**先建立画面**（接着上面「目录项 → inode」那套模型看）：

- **硬链接**：给同一个 inode 再起一个文件名——就是在目录里多加一条目录项，指向原来那个 inode。两个名字完全平等，没有"原件/副本"之分，inode 的链接计数 +1。
- **软链接（符号链接）**：一个全新的小文件，有它自己独立的 inode；它的"数据"就是一行字符串——目标的路径。访问它时内核读出这行路径、再跳过去找目标，相当于 Windows 的"快捷方式"。

一句话抓本质：**硬链接指向 inode（底层那个对象），软链接指向路径（一串文件名）**。下表每一行差异，都是从这一句推出来的：

|       | 硬链接                        | 软链接（符号链接）                     |
| ----- | -------------------------- | ----------------------------- |
| 本质    | 同一 inode 的另一个名字，多一条目录项     | 独立小文件，内容是一行目标路径               |
| inode | 与源**共用同一个**（`ls -i` 看号码相同） | **自己独立的 inode**（`ls -i` 号码不同） |
| 创建命令  | `ln 源 链接`                  | `ln -s 源 链接`                  |
| 删掉源文件 | 照样能读（inode 计数未归零，不算真删）     | **失效**，变悬空链接（它指的路径没了）         |
| 跨文件系统 | ❌ inode 号只在本文件系统内唯一        | ✅ 存的只是路径字符串，无所谓               |
| 指向目录  | ❌ 一般禁止（会成环、破坏树形结构）         | ✅ 允许                          |

- **为什么删了源文件、硬链接还活着**：删文件（`rm` 即 `unlink`）删的只是目录项、把 inode 链接计数减 1；只要还有别的硬链接指着它、计数没减到 0，数据块就不回收。而软链接指的是路径，源的目录项一没，它就指了个空——这就是悬空链接。
- 也解释了「`mv` 不改文件 mtime」：同文件系统内 mv 只是改目录项（改名/换目录），inode 和数据块都没动，所以修改时间不变。

### 页缓存（Page Cache）

- 内核用空闲内存缓存文件内容。读先查缓存，写先写缓存再**异步回写**（脏页）。
- `free` 里的 cache/buff 就是它，可回收，不算真占用。

### write ≠ 落盘

- `write` 只写到页缓存；`fsync` 强制脏页和元数据落盘，`fdatasync` 只保证数据。
- MySQL `innodb_flush_log_at_trx_commit`（1 = 每事务 fsync 最安全）、Kafka flush 策略，都是同一取舍：**安全性和吞吐对立**。断电丢的是内核页缓存里没回写的脏页。
- **Direct IO（`O_DIRECT`）**：绕过页缓存，应用自己管缓存。InnoDB 常用，避免双重缓存。
- **顺序写为什么快**：减少寻道（机械盘）、利于预读与合并写、页缓存回写高效——Kafka 顺序写的底层依据。

## 6.2 排障

- `df -i` 看 inode 使用率；`df -h` 看空间。两个都可能先满。
- `iostat -x 1`：`%util` 接近 100% 说明盘打满（SSD 多队列不可靠，看 `await`）；`await` 是平均等待时长。

# 第 7 章 · I/O 模型与零拷贝

## 7.1 知识

### 五种 I/O 模型（POSIX）

一次网络读分两阶段：① 等数据到内核缓冲区 → ② 拷到用户空间。**前四种差别全在①**；② 是同步/异步分界——只有 AIO 例外。

```
阻塞 IO      ：①等  ②拷            （线程全挂住）
非阻塞 IO    ：①轮询轮询轮询 ②拷    （CPU 白烧）
IO 多路复用  ：①一个线程等多个 fd，就绪后 ②拷
信号驱动 IO  ：①内核就绪时发 SIGIO ②拷
异步 IO AIO  ：①②全由内核做完再通知  （唯一真异步）
```

⚠ 说准：前四种都是**同步 I/O**——"数据从内核拷到用户态"由发起线程同步完成。说反是硬伤。

### select → poll → epoll

| 维度 | select | poll | epoll |
|---|---|---|---|
| fd 上限 | **1024**（FD_SETSIZE，改要重编译） | 无理论上限 | 无上限（受 file-max、ulimit -n 约束） |
| fd 集合传递 | **每次全量用户↔内核拷贝** | 同样全量 | `epoll_ctl` 注册一次，`epoll_wait` 不重复拷 |
| 内核找就绪 fd | 线性遍历 O(n) | 线性遍历 O(n) | **就绪双向链表**，O(就绪数) |
| 数据结构 | 三个 bitmap | pollfd 数组 | 红黑树存全量 + 就绪链表 |

**select 的位图怎么"知道"你要监听谁**：

- `fd_set` 是 1024 位位图，**下标 = fd 号，值 = 要不要监听**。"监听谁"编码在位置里，解码的唯一办法是遍历。
- 第一个参数 `nfds` = 最大 fd + 1，是划边界。传小了后面 fd 静默漏掉；传对了也慢——**select 开销 ∝ 最大 fd 号，不是 ∝ 监听个数**。
- ⚠ select 连一万个连接都放不下（位图只有 1024 位），"大量连接"是 poll/epoll 的场景。
- epoll 表达方式相反：fd 作为参数直接传进红黑树，是真集合，不用边界参数，不受 fd 编号影响。

**epoll 快的三层因果（别只说"没上限"）**：

1. **注册与等待分离**：fd 常驻内核红黑树，省掉拷贝 + 重建集合的固定开销
2. **回调取代轮询**：数据到达 → 软中断 → 回调把 fd 挂进就绪链表，`epoll_wait` 只返回真就绪的
3. 所以**活跃连接占比低时优势巨大**（C10K）；几乎所有 fd 都活跃时不比 select 快多少（红黑树有成本）

**LT vs ET**：

- LT（默认）：缓冲区还有数据就一直通知，编程简单
- ET：只在状态变化时通知一次，必须**循环读到 EAGAIN** 且配非阻塞 fd。省通知次数，Nginx 用 ET

### 零拷贝

**问题**：经典"读文件发网络" = `read()` + `write()`，数据走 硬盘 → 页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡，其中**内核↔用户的两次拷贝纯属浪费**（数据用户态根本不看）。

| 方案 | 系统调用 | 模式切换 | 数据拷贝 |
|---|---|---|---|
| 传统 read + write | 2 | 4 | **4 次**：2 DMA + 2 CPU |
| mmap + write | 2 | 4 | **3 次**：2 DMA + 1 CPU |
| sendfile | 1 | 2 | **3 次**：2 DMA + 1 CPU |
| sendfile + **SG-DMA** | 1 | 2 | **2 次**：2 DMA + **0 CPU** |

- ⚠ 这列是**模式切换**（一次 syscall 一进一出），不是上下文切换——不换页表不刷 TLB。
- **为什么 sendfile 还剩 1 次 CPU**：传统网卡 DMA 只从 socket 缓冲区搬数据，页缓存必须先 CPU 拷进 socket 缓冲区——根因是"网卡只从 socket 缓冲区取货"。
- **scatter-gather**：DMA 能把分散数据拼成报文，socket 缓冲区只放描述符，CPU 拷贝彻底归零。

**工程落点**：

- Kafka 高吞吐四板斧：零拷贝（`FileChannel.transferTo` → sendfile）+ 顺序写 + 页缓存 + 批量压缩
- Netty：`FileRegion`；`CompositeByteBuf` 用逻辑组合代替物理拷贝（用户态版零拷贝）
- Nginx 静态文件走 sendfile
- Redis `fork + COW` 是**内存层面**避免拷贝，同一思想家族

## 7.2 排障

`ss -antp` 看连接状态堆积（TIME_WAIT、CLOSE_WAIT）；`lsof -p <pid>` 看 fd 泄漏。

# 第 8 章 · IPC 进程间通信

## 8.1 知识

| 方式 | 方向 | 速度 | 关键点 |
|---|---|---|---|
| 管道 pipe | 半双工、仅亲缘进程 | 中 | 内核环形缓冲区默认 64KB；读端关闭写会收到 **SIGPIPE** |
| 命名管道 FIFO | 半双工，无亲缘可用 | 中 | 文件系统里有个名字（类型 `p`），数据在内核缓冲不落盘 |
| 信号 signal | 异步通知 | 快但信息量极小 | 只传编号不传数据；SIGKILL(9)/SIGSTOP(19) 不可捕获忽略 |
| 信号量 semaphore | — | — | **不传数据，是同步计数器**（P/V），常配共享内存 |
| 共享内存 shm | 双向 | **最快** | 一次映射零拷贝不走内核；无同步能力，要配信号量/锁 |
| 消息队列 | 双向 | 较慢 | 有格式、按类型取，有拷贝开销 |
| Socket / Unix 域套接字 | 双向 | Unix 域较快 | **唯一能跨机** |

- **为什么管道只给亲缘进程**：管道靠读端/写端两个 **fd** 访问，fd 是进程私有的；无亲缘进程拿不到，除非 fork 继承或 Unix 域套接字 `SCM_RIGHTS` 显式传 fd。**FIFO 补的正是这个入口**：给个文件系统名字，任何进程 open 就能拿 fd。一句话：**管道靠"继承"，FIFO / Unix 域套接字靠"名字"**。
- **FIFO 的坑**：size 恒为 0，写的数据全在内核缓冲不落盘；默认 `open` 是同步点（只读端阻塞到有写端 open，反之亦然）；写 ≤ PIPE_BUF 4KB 才保证原子。
- **SIGKILL/SIGSTOP 为什么不可捕获**：内核强留的管理员兜底手段，否则进程全忽略信号就赖着不死。**优雅停机用 15 不用 9**：SIGTERM 可捕获，先关连接刷盘再退；SIGKILL 直接撕，没有 shutdown hook。退出码 137 = 128+9，143 = 128+15。K8s 停服默认发 15、超时补 9。
- **为什么共享内存最快**：其他方式都要"用户态 → 内核 → 用户态"两次拷贝；共享内存是两个进程把同一物理页映射进各自地址空间，数据一次不动。和零拷贝同一思想：**消除用户态和内核态的无谓搬运**。

# 第 9 章 · 容器与隔离（全新）

## 9.1 知识

**直觉：namespace 决定容器里"看得见什么"，cgroup 决定"能用多少"。**

- **namespace**：隔离视图——PID（容器内自己是 PID 1）、Network（独立网络栈）、Mount、UTS（主机名）、IPC、User。容器 ≠ 轻量虚拟机：**没有独立内核**，共享宿主机内核。
- **cgroup**：资源限额——CPU（配额/权重）、内存、IO。超内存限额 → 该 cgroup 内 OOM Killer → K8s `OOMKilled`（退出码 137，同一套机制，范围缩到 cgroup 配额）。

**Java 容器化高频坑**：

- 老版本 JVM 读不到 cgroup 限制，按宿主机内存算堆 → 容器被 OOMKilled。JDK 8u191+/10+ 默认容器感知（`UseContainerSupport`）。
- 堆外还有元空间、线程栈、DirectByteBuffer、Code Cache——都算进 cgroup 限额。**-Xmx 不能设成限额 100%**，一般留 25% 左右余量。
- CPU 配额同理：cgroup 的 CPU quota 会影响 JVM 可见核数，进而影响 GC 线程数、ForkJoinPool 并行度（虚拟线程载体数默认 = 可见核数）。

## 9.2 排障

- `docker stats` / `kubectl top pod` 看限额使用。
- 退出码 137 且有容器环境 → 十有八九 cgroup 超限，不是 JVM 堆问题；看 `-Xmx` 没用，看容器 limit。

# 第 10 章 · Linux 常用排障命令

| 想看什么 | 命令 | 关键字段 |
|---|---|---|
| CPU / Load / 单线程 | `top`（`1` 每核、`H` 线程） | `%wa` 高=IO 瓶颈；`%sy` 高=内核态开销大 |
| 整体 CPU、切换、运行队列 | `vmstat 1` | `r`（等 CPU）、`cs`（每秒切换）、`si/so`（换页=内存不够）、`wa` |
| 磁盘 | `iostat -x 1` | `%util` 打满（SSD 不可靠看 `await`） |
| 内存 | `free -h`、`/proc/meminfo` | 看 **available**，别看 free |
| 进程打开了什么 | `lsof -p <pid>`、`ss -antp` | fd 泄漏、连接堆积 |
| 文件系统 | `df -h`、`df -i` | 空间 vs inode 双检查 |
| Java 线程/死锁 | `jstack <pid>`、`jstat -gcutil` | 见第 4 章死锁排查 |

**面试常问三条**：

1. **available 和 free 的区别**：available = free + 可回收 cache。"内存只剩 200MB"先看 available。
2. **kill -9 杀不掉怎么办**：先看 ps 状态列——D 状态在等 IO，信号要等它从内核态回来才处理，查存储或重启；Z 状态已死等收尸，kill 无意义，修父进程。
3. **%sy 比 %us 高说明什么**：内核态开销过大——切换频繁、系统调用密、软中断多。

# 第 11 章 · 面试问答库

所有答题话术集中于此。每题格式：一句话答案 → 展开要点。

### Q1：进程切换和线程切换到底差在哪一步？
一句话：进程切换要换页表（改 CR3 → TLB 失效 → 缓存重建），线程共用页表只换栈和寄存器。
> "贵不是贵在那几条指令，是贵在**切换之后缓存和 TLB 的重建**。现代 CPU 有 PCID/ASID 缓解全刷，所以差距没教科书说的那么夸张。"

### Q2：为什么 32 位系统最多用 4G 内存？64 位呢？
一句话：寻址范围由虚拟地址位数决定。
> "32 位 = 4GB，内核还占 1GB，用户空间 3G——JVM 在 32 位机器堆开不大的原因。64 位真实只用 48 位虚拟地址；另外 Linux 默认栈大小、glibc arena 数随核数增长，是 64 位机器线程一多内存就爆的原因之一。"

### Q3：fork 之后父子进程内存是复制了一份吗？
一句话：写时复制 COW。
> "fork 只复制页表，父子共享物理页标只读，写时才触发缺页真复制。fork 开销是页表开销不是数据量开销。Redis BGSAVE 就靠这个；代价是内存最坏翻倍，大实例 fork 卡顿。"

### Q4：mmap 和 read/write 有什么区别，什么时候用 mmap？
> "mmap 把文件映射进地址空间，省掉'内核→用户'那次拷贝，小文件随机访问划算。三个前提：页缓存本身很快，mmap 不一定更快；随机跳访问疯狂缺页反而慢；mmap 期间文件被截断会 SIGBUS。大文件顺序传输用 sendfile，随机访问、想内核管刷盘的用 mmap，比如 ES 索引。"

### Q5：一个程序崩溃，可能的原因有哪些？
四类：
1. 非法内存访问（野指针、越界、栈溢出 → SIGSEGV / StackOverflowError）
2. 主动 abort（断言失败、raise）
3. 资源耗尽（OOM Killer、fd 用尽、线程数超限）
4. 被信号杀（kill -9、运维脚本、容器 OOM）
> "Java 里退出码 137 = 128+9，基本是被 SIGKILL 杀的；容器环境十有八九是 cgroup 内存超限，看 -Xmx 没用，得看容器 limit。"

### Q6：为什么进程比线程"重"？
三处：创建要建页表/地址空间/fd 表；切换要换页表刷 TLB；通信不能直接共享变量要走 IPC。共享内存是例外——把"重"的部分预先做掉一次。

### Q7：中断和异常有什么区别？
> "中断是外部来的、和当前指令无关，异步；异常是当前指令出错，同步。系统调用是故意触发的异常。网卡收包走硬中断 + 软中断两级：硬中断只做最少的事，耗时协议栈丢给软中断——%si 指标的由来。"

### Q8：并发和并行的理解？
> "并发是一个 CPU 时间片内交替推进，靠切换制造'同时在跑'的假象；并行是多核真的同时跑。单核加线程不会变快只增加切换开销；超过一个核线程才带来真实吞吐。IO 密集时线程大部分在阻塞态不占核，才允许开更多。"

### Q9：Load 高但 CPU 不高说明什么？
> "Load 不是 CPU 指标，是任务堆积指标。Load 高 CPU 不高 = 大量任务卡 D 状态等 IO。加 CPU 没用，看 vmstat 的 r 列（真缺 CPU）和 wa 列（存储瓶颈），方向完全相反。"

### Q10：虚拟线程的本质和适用场景？
> "虚拟线程本质是 JVM 实现的协程（M:N），解决的不是'并发不够'而是'阻塞 IO 浪费内核线程'。它在阻塞点把上下文挂起还回载体线程。它的本事就一条——扛阻塞 IO；长跑不阻塞的任务占着载体饿死别人。JDK 21 的 synchronized pinning 在 JDK 24（JEP 491）已消除。"

### Q11：为什么自旋锁和互斥锁要分场景？
> "睡眠锁要付两次上下文切换代价；临界区短于这个代价时自旋划算。单核上自旋毫无意义。futex 是折中：无竞争纯用户态，有竞争才进内核睡眠。"

### Q12：MySQL 的 flush 参数在 OS 层面对应什么？
> "write 只写到内核页缓存，fsync 才强制落盘。innodb_flush_log_at_trx_commit=1 是每事务 fsync 最安全；断电丢的是页缓存里没回写的脏页。安全性和吞吐就是在这里对立的。"

### Q13：容器里 Java 进程被 OOMKilled，为什么调 -Xmx 可能没用？
> "cgroup 限额算的是整个容器的内存：堆 + 元空间 + 线程栈 + DirectByteBuffer。-Xmx 调小到限额以内也可能被堆外吃掉触发 OOMKilled（退出码 137）。要留 25% 余量，并用 NativeMemoryTracking / NMT 看 JVM 全景。"

# 附录 A · 文件权限与 chmod

**`ls -l` 前 10 字符**：第 1 位是文件类型（`-`普通/`d`目录/`l`软链接/`c`字符设备/`b`块设备/`s`socket/`p`管道），**chmod 改不了**；后 9 位是三段 rwx（所有者/组/其他）。

r=4, w=2, x=1。`rwx`=7，`r-x`=5，`rw-`=6。

| 数字 | 典型用途 |
|---|---|
| 400 | 证书私钥只读 |
| 600 | SSH 私钥（否则 ssh 拒绝使用） |
| 644 | 普通文件 |
| 700 | 私有目录 |
| 755 | 可执行文件、目录最常用 |
| 777 | 生产别用 |

**文件 vs 目录权限含义不同**：

| 权限位 | 对文件 | 对目录 |
|---|---|---|
| r | 读内容 | 列出文件名 |
| w | 改内容 | 新建/删除文件 |
| x | 执行 | 进入目录/访问元信息 |

经典坑：目录只有 r 没有 x，`ls` 能列名但详情全是 `?`，打不开里面的文件。

**特殊权限位**：SUID（4xxx，临时获得属主权限，`/usr/bin/passwd`）、SGID（2xxx，目录上新建文件继承属组）、Sticky（1xxx，目录内只有属主能删自己的文件，/tmp 是 1777）。

**umask**：新建文件扣掉的权限，默认 022 → 文件 644、目录 755。

# 附录 B · 易混 Linux 概念（选择题）

原题（答案 **A**）：
A. 线性访问内存非法时，当前线程会进入信号处理函数 ✅（但措辞不严谨：需该信号可捕获且已安装 handler，否则默认动作终止，可能生成 core dump）
B. mv 移动文件 mtime 会变 ❌ —— 同一文件系统内 mv 只改目录项，mtime 不变；改的是**目录的 mtime**
C. `ulimit -c` 是函数调用栈 ❌ —— **-c 是 core dump 大小上限**；**-s 才是栈大小**；-n 是最大 fd 数；-u 是最大进程/线程数
D. malloc 是 OS 最底层申请内存接口 ❌ —— malloc 是 **glibc 库函数**，底层才是 brk/mmap 系统调用

**core dump**：进程异常终止时的状态快照（内存、寄存器、栈），用于事后 gdb 调试；生成与否受 `ulimit -c` 影响。
