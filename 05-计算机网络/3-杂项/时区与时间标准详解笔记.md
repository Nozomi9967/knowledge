## 1. 先建立直觉：为什么需要"时区"

地球是个自转的球体，太阳每天只会在某一条经线上空达到最高点。如果全世界共用同一个钟点，就会出现北京中午 12 点太阳最高、伦敦同一刻却是凌晨 4 点的情况。这显然不合理，所以人们把地球按经度切成 24 个竖条，每个竖条使用各自的"当地钟点"，这就是**时区**。

- **经线（子午线）**：连接南北两极的竖线，用来标记东西方向的位置。
- **经度**：某地所在经线的编号，范围是东经 0° 到 180° 和西经 0° 到 180°。
- **本初子午线**：人为规定的 0° 经线，穿过英国伦敦的格林尼治天文台。
- 地球 24 小时自转 360°，所以每小时转 15°。**每隔 15° 经度，钟点差 1 小时**。

## 2. GMT：格林尼治标准时间

**GMT = Greenwich Mean Time**，字面意思是"格林尼治平均太阳时"。

- 它以本初子午线上的太阳位置为准：太阳每天经过格林尼治正上方的时刻，定为 12:00。
- **时区**：GMT 对应的时区就是"零时区"，写作 UTC+0 或 GMT+0。
- **北京时间**：位于东八区，即 GMT+8。GMT 12:00 时，北京是 20:00。

### 为什么叫"平均（Mean）"

太阳真正过正上方的时刻，一年里会前后波动约 ±16 分钟。原因有两个：

1. 地球绕太阳的轨道是椭圆，不是正圆，所以公转速度时快时慢。
2. 地球自转轴是倾斜的（约 23.4°）。

如果直接用"真太阳时"，每天的长度会忽长忽短。于是人们取全年平均，得到一个均匀的"平太阳时"，这就是 Mean。

## 3. UTC：协调世界时

**UTC = Coordinated Universal Time**，是今天的国际时间标准。

### 为什么要有 UTC

GMT 依据地球自转来定义，而地球自转并不均匀：潮汐摩擦会让它缓慢变慢，地震、洋流、冰川融化也会造成微小抖动。对精密的计算机、通信和卫星系统来说，这种不稳定是不能接受的。

### UTC 怎么定义

- **原子钟**：利用原子（如铯原子）振荡频率来计时的钟，极其稳定，几千万年才差 1 秒。
- **TAI（国际原子时）**：纯粹由原子钟累计出来的时间，不考虑地球自转。
- **UT1**：根据地球实际自转观测得到的时间。
- **UTC**：以 TAI 的节奏走时，再通过**闰秒**让它与 UT1 的差距保持在 0.9 秒以内。

### 闰秒

当原子时与地球自转差距快超过 0.9 秒时，国际机构会宣布在某年 6 月底或 12 月底多加（或减去）1 秒，例如出现 23:59:60 这个时刻。它是造成很多系统故障的来源之一，所以近年国际上已讨论在 2035 年前后取消闰秒。

### 关键时间线

| 年份 | 事件 |
|---|---|
| 1884 | 华盛顿国际子午线会议，确定格林尼治为本初子午线，GMT 成为国际标准 |
| 1960 年代 | 原子钟普及，开始采用原子时 |
| 1972 | UTC 正式启用 |

### GMT 与 UTC 对比

| | GMT | UTC |
|---|---|---|
| 依据 | 地球自转（天文观测） | 原子钟加闰秒修正 |
| 性质 | 历史上的标准，也是一个时区名 | 现行的国际标准 |
| 数值差异 | 与 UTC 相差不到 1 秒 | 基准 |

**工程上的结论**：两者差异小于 1 秒，缓存、日志、定时任务都可以当同一个东西。日常约定是：存储和计算用 UTC，HTTP 头里写 GMT。

> 小趣闻：英文是 Coordinated Universal Time，法文是 Temps Universel Coordonné，缩写本应分别是 CUT 和 TUC。双方各让一步，最后选了谁都不对应的 UTC。

## 4. 时区的表示方法

| 写法 | 含义 | 例子 |
|---|---|---|
| UTC+8 / GMT+8 | 比 UTC 快 8 小时 | 北京时间 |
| +08:00 | ISO 8601 标准里的偏移量写法 | 2026-10-22T17:00:00+08:00 |
| Z | 代表 UTC+0，读作 Zulu | 2026-10-22T09:00:00Z |
| Asia/Shanghai | IANA 时区名（时区数据库里的"地区名"） | 推荐编程时使用 |

### 偏移量与时区名的区别

- **偏移量**（如 +08:00）只表示"和 UTC 差多少"，是一个固定数字。
- **时区名**（如 America/New_York）包含一整套规则，包括历史变更和**夏令时**。
- **夏令时（DST）**：夏天把时钟拨快 1 小时以多利用日照的制度。美国纽约冬天是 UTC-5，夏天是 UTC-4。中国目前不实行夏令时。

因此，涉及夏令时的地区必须用时区名，不能写死偏移量。

## 5. 时间戳：计算机最爱用的时间

**Unix 时间戳**：从 **1970-01-01 00:00:00 UTC** 起经过的秒数（有的系统用毫秒）。

- 它**没有时区概念**，全球同一时刻的时间戳完全相同。
- 只有展示给人看时，才根据用户所在时区转换成"年月日时分秒"。
- 最佳实践：**存储用时间戳或 UTC，展示时才转换成本地时间**。

例如，时间戳 0 在北京显示为 1970-01-01 08:00:00，在纽约显示为 1969-12-31 19:00:00。

## 6. HTTP 为什么规定用 GMT

HTTP（浏览器和服务器之间通信的协议）里有一批头字段携带日期，例如：

- `Date`：响应生成的时间
- `Expires`：缓存过期的绝对时刻
- `Last-Modified`：资源最后修改时间
- `If-Modified-Since`：客户端询问"这个时间之后改过吗"

这些头要被世界各地的浏览器、CDN（内容分发网络）、代理服务器读取，所以必须有一个**无歧义的统一参照**，规范选择了 GMT。

### 标准格式（IMF-fixdate）

```
Wed, 21 Oct 2015 07:28:00 GMT
```

结构为：`星期缩写, 日 月份缩写 年 时:分:秒 GMT`。规则：

- 末尾必须是字面量 `GMT`，不能写 `+0800`、`CST`。
- 星期和月份必须用英文缩写。
- 服务端必须先把时间换算成 GMT 再输出。

### 另外两种旧格式

解析时需要兼容，生成时不要使用：

| 格式 | 样子 |
|---|---|
| RFC 850（废弃） | `Wednesday, 21-Oct-15 07:28:00 GMT` |
| asctime（废弃） | `Wed Oct 21 07:28:00 2015` |

## 7. 经典事故：忘记转换时区

### 事故一：把本地时间当 GMT 输出

北京服务器本地时间 15:28，对应的 GMT 是 07:28。如果直接输出 `15:28:00 GMT`，客户端会认为过期时刻比真实值晚 8 小时，缓存多留 8 小时。

### 事故二：用 CST 缩写

`CST` 有歧义，可能指：

- China Standard Time（UTC+8）
- Central Standard Time（美国中部，UTC-6）
- Cuba Standard Time（UTC-5）

不同客户端解析结果不同，bug 只在部分用户身上出现，很难排查。

### Java 正确写法

```java
// 错误：使用服务器默认时区，可能输出 CST
SimpleDateFormat bad = new SimpleDateFormat("EEE, dd MMM yyyy HH:mm:ss z", Locale.US);

// 正确（旧 API）：显式指定 GMT
SimpleDateFormat sdf = new SimpleDateFormat("EEE, dd MMM yyyy HH:mm:ss 'GMT'", Locale.US);
sdf.setTimeZone(TimeZone.getTimeZone("GMT"));

// 推荐（新 API，线程安全）
String expires = ZonedDateTime.now(ZoneOffset.UTC)
        .plusHours(1)
        .format(DateTimeFormatter.RFC_1123_DATE_TIME);
```

- `SimpleDateFormat` 不是线程安全的，多线程共用会出错。
- `RFC_1123_DATE_TIME` 与 HTTP 日期格式基本一致。
- 新旧 API 的完整用法对照（`Date`/`Calendar`/`SimpleDateFormat` vs `java.time`、格式符陷阱、`withZoneSameInstant` vs `withZoneSameLocal`、新旧互转）见 [[新旧时间 API 基本用法对照]]。

## 8. 常见陷阱

**陷阱一：`Etc/GMT-8` 的符号是反的。** 这是 IANA 时区库沿用 POSIX 约定的结果：`Etc/GMT-8` 实际是 UTC+8，`Etc/GMT+5` 实际是 UTC-5。建议不要使用，直接用 `Asia/Shanghai` 或 `UTC`。

**陷阱二：本地时钟不准。** 用户手机或电脑的时间可能被手动改过，依赖客户端时钟判断的逻辑（如 `Expires`）就会失效。

**陷阱三：夏令时。** 在夏令时切换日，一天可能是 23 或 25 小时，"加 24 小时"不等于"明天同一时刻"。

>夏令时是一种在夏季把时钟拨快一小时的制度，用来更充分地利用白天日照。​

**陷阱四：数据库时区。** 数据库、应用服务器、JVM 三处时区设置不一致，会造成时间差几小时。统一用 UTC 存储可避免。

## 9. 对原笔记的订正

- 原文写"CST 六义性"，但列出的只有三种含义，应改为"多义性"。实际上 CST 还可指其他时区（如台北标准时间），所以"多义"更准确。
- 原文提到"1960 年起国际时间局改用原子时"，更严谨的说法是：原子钟在 1950 至 1960 年代逐步投入使用，UTC 在 1960 年代开始试行，1972 年才形成现行体系，具体年份细节建议以权威资料为准。
- 原文把 GMT 描述为"本质就是一个时区"，这是工程上的简化。严格来说，GMT 既是历史上的天文时间标准，也是英国冬季使用的时区名称（夏季英国用 BST，即 UTC+1）。

## 10. 与缓存的关系：为什么 Expires 不可靠

`Expires` 用绝对时刻表示过期，存在三个问题：

1. **依赖客户端本地时钟**：用户的时钟快慢直接影响缓存是否过期。
2. **时区和格式有歧义**：服务端漏转 GMT 或输出 CST，会导致解析错误。
3. **多级缓存不友好**：浏览器、CDN、代理层层缓存时，下游必须靠 `Date` 和 `Age` 头反推剩余时间，任何一环出错都会失效。

`Cache-Control: max-age=3600` 是相对秒数，从收到响应时开始计时，和时区、本地时钟、格式都无关，所以优先级高于 `Expires`。

- **max-age**：缓存的有效秒数。
- **Age**：响应在代理缓存中已存放的秒数。


>**关于第三点的解释**

**具体来说，下游缓存要自己算"还剩多久"，而这个计算要依赖多个头字段，每一步都可能算错。**

### 单层缓存的计算方式

源站（原始服务器）返回的响应里通常有两个时间：

- `Date`：源站生成这条响应的时刻。
- `Expires`：缓存失效的绝对时刻。

缓存拿到响应后，先算出这条响应的"新鲜期"：`Expires - Date`。如果只有一层缓存，它直接从收到响应的那一刻开始计时，剩余时间比较好算。

### 多层缓存的问题

实际链路往往是这样的：

```
源站 → CDN 边缘节点 → 公司代理 → 浏览器
```

每一层都会保存这份响应，并在把它转发给下游时，告诉下游"这份内容在我这里已经放了多久"。这个数字就是 `Age` 头，单位是秒。下游收到后要计算：

- 剩余新鲜时间 = 新鲜期 − `Age` − 本层自己收到响应后经过的时间

每一层都要正确地累加 `Age`，下游才能得到准确的剩余时间。

### 一个具体的例子

源站在 07:00（GMT）生成响应，`Date: 07:00:00`，`Expires: 08:00:00`，新鲜期为 1 小时。

1. **CDN 在 07:00 收到并缓存**。
2. **浏览器在 07:30 向 CDN 请求**。CDN 应返回 `Age: 1800`，表示这份内容已在它那里放了 30 分钟。
3. **浏览器计算剩余时间**：3600 − 1800 = 1800 秒，即最多还能使用到 08:00。

如果中间任何一环出错，结果就不对了：

- **CDN 忘记返回 `Age`**：浏览器认为内容是刚生成的，会一直用到 08:30，多用了 30 分钟的过期内容。
- **CDN 或代理修改了 `Date`**：新鲜期的计算基准被破坏，失效时间随之错误。
- **某一层的时钟不准**：本层记录"收到响应的时刻"时用的是本地时钟。时钟快慢会直接影响它算出的经过时间。
- **旧代理不支持 `Age`**：整条链路的累加就断了，下游只能按错误的数据判断。

### 为什么 max-age 能避开这些问题

`Cache-Control: max-age=3600` 只给出一个相对秒数，每一层收到后各自从收到的那一刻开始计时，不需要比较两台机器上的绝对时刻。各层只需要扣除自己的停留时间，不必依赖其他层准确累加 `Age`，所以出错的环节少得多。

需要说明的是，`max-age` 并非完全不依赖时间。RFC 9111 规定，缓存在计算停留时间时仍会用到本地时钟，只是不再受 `Expires` 的绝对时刻和时区格式影响。因此它的优势主要在于计算链条更短、对格式和时区歧义免疫，而不是完全脱离时钟。


**CDN 是内容分发网络，把网站的静态资源缓存到离用户更近的服务器上，让访问更快。**

CDN 的全称是 Content Delivery Network，中文通常叫内容分发网络。它由分布在世界各地的大量节点服务器组成，这些节点常被称为边缘节点（Edge Node）。网站把图片、视频、JavaScript、CSS 等内容交给 CDN 托管后，用户访问时不必每次都跨越半个地球去请求源站，而是由离自己最近的节点直接返回。

**CDN 的工作方式**

以访问一张图片为例，流程大致如下：

1. 用户在上海打开网站，浏览器请求图片的域名。
2. DNS 解析把请求导向离上海较近的 CDN 边缘节点。
3. 如果节点已经缓存了这张图片，就直接返回；如果没有，节点会向源站拉取一份，保存下来，再返回给用户。

第二次有人再访问时，节点就能直接命中缓存，无需再次回源。

**为什么它和缓存头有关**

CDN 本身就是一层缓存，所以前面讲的 `Date`、`Expires`、`Age` 和 `max-age` 在这里都会用到。CDN 收到源站响应后，要根据这些头判断内容能保存多久；转发给下游时，又要通过 `Age` 告诉对方这份内容已经放了多久。

常见的 CDN 服务商包括阿里云、腾讯云、Cloudflare、Akamai 等。它们提供的功能除了缓存，还包括 HTTPS 加速、流量调度、防攻击等，但对于理解缓存问题，只需要记住它是一个分布在各地、会替源站保存内容的中间层即可。

## 11. 速记卡

- GMT 是零时区，北京时间是 GMT+8。
- UTC 是现行标准，由原子钟加闰秒维持，工程上与 GMT 视为同一个。
- 存储用 UTC 或时间戳，展示才转本地时区。
- HTTP 日期末尾必须是 `GMT`，服务端要先转换再输出。
- 不要使用 CST 这类有歧义的缩写。
- 编程时优先使用 `Asia/Shanghai` 这类时区名，避免 `Etc/GMT±N`。
- 夏令时地区不能写死偏移量。

## 12. 面试话术

> GMT 是格林尼治标准时间，本质就是零时区，北京时间等于 GMT 加 8 小时。它现在已经被原子钟定义的 UTC 取代，UTC 通过闰秒保持与地球自转接近，两者相差不到 1 秒，工程上可以当同义词。
>
> HTTP 规定日期头一律用 GMT 格式，因为这些头要被全世界各个时区的客户端和代理读取，必须有统一参照。服务端必须先把本地时间转成 GMT 再输出，否则北京服务器会让缓存多留 8 小时。另外别用 CST 这种有歧义的缩写。Java 里可以用 `DateTimeFormatter.RFC_1123_DATE_TIME`。
>
> 这也解释了 Expires 为什么不可靠：它是绝对时刻，依赖客户端时钟，有时区和格式歧义，多级缓存下还要靠 Date 和 Age 反推。max-age 是相对秒数，从收到响应起算，天然避开这些问题。
