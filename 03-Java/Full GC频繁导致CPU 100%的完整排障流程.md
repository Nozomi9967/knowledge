

这是一个典型的"先用工具定位现象，再用dump分析根因"的排障思路，按时间顺序完整走一遍。

### 第一步：top确认整体资源消耗

```bash
top
```

先确认是哪个Java进程占用CPU异常，记下PID。同时观察系统层面的内存、负载、IO情况，排除是否有其他进程或者宿主机资源争抢的干扰因素（比如同台机器部署了别的服务抢资源），确保问题确实出在这个JVM进程本身。

### 第二步：top -Hp定位具体线程

```bash
top -Hp <PID>
```

`-H`参数显示进程内的所有线程，能看到哪些具体线程在消耗CPU。这一步已经确认是GC线程（通常显示为`GC task thread`），说明CPU打满不是业务逻辑死循环，而是JVM在频繁地做垃圾回收，记下这个高CPU线程的LWP（线程ID，十进制）。

### 第三步：将线程ID转换为16进制

```bash
printf "%x\n" <LWP_PID>
```

因为jstack输出的线程栈里，nid字段是用16进制表示的，需要做一次进制转换，方便后面在jstack输出里搜索对应的线程。不过这一步对于"GC线程占用CPU"这种场景其实意义不大（GC线程本身不在常规的Java线程栈里能完整体现，它是JVM内部线程），更多是用来确认"这确实是个GC相关的内部线程，而不是某个业务线程在死循环"，做个交叉验证。

### 第四步：jstat确认GC频率与详情

```bash
jstat -gcutil <PID> 1000 10
```

每隔1秒打印一次，连续打印10次，重点看几列：

`FGC`（Full GC次数）和`FGCT`（Full GC总耗时）这两列变化速度，结合题目描述的"每分钟5次"，说明平均12秒一次Full GC，这是一个非常危险的频率，正常健康的JVM可能几小时甚至几天才一次Full GC。

同时看`O`（老年代使用率）这一列，如果Full GC之后老年代使用率依然居高不下（比如回收完还有90%以上），说明存在大量无法被回收的"存活"对象，这通常指向内存泄漏；如果回收后使用率能降下来，但很快又涨回阈值触发下一次Full GC，可能是对象创建速率过高、或者新生代设置过小导致大量对象直接晋升到老年代。

`YGC`和`YGCT`这两列也要看，如果Young GC也异常频繁，结合新生代大小（可以用`jstat -gc`看Eden区S0/S1区大小），可能是新生代空间设置不合理，对象来不及在新生代消亡就被晋升到老年代，加剧了老年代压力。

### 第五步：jmap生成堆快照

确认了Full GC频繁且老年代回收效果差之后，需要抓一份堆内存快照来分析具体是什么对象占用了大量内存。

```bash
jmap -dump:live,format=b,file=heap.hprof <PID>
```

这里有几个注意点。第一，`live`参数会先触发一次Full GC再dump（只dump存活对象），能让分析结果更聚焦在"真正占内存的存活对象"上，但代价是这次dump本身会让本就紧张的现场雪上加霜，多卡顿一会儿，所以这一步最好在业务低峰期操作，或者提前和业务方报备会有短暂停顿。第二，dump出来的hprof文件可能很大（取决于堆大小，可能几个G甚至更大），生成过程中要确保磁盘空间足够，生成期间这个JVM进程基本会处于STW（Stop The World）暂停状态，这点也要提前评估对业务的影响。

如果担心dump期间的影响太大，也可以先用`jmap -histo:live <PID> | head -50`快速查看一下存活对象的类直方图（不生成完整dump文件，相对开销小一些），按实例占用空间排序，初步判断一下是哪个类的对象在大量堆积，再决定是否要进一步做完整dump。

### 第六步：用MAT分析dump文件

把生成的hprof文件下载到本地，用Eclipse MAT（Memory Analyzer Tool）打开分析，几个核心动作：

**Histogram视图**：按类排序展示每个类的实例数量和占用内存，第一眼看哪个类的Shallow Heap或Retained Heap异常的大，初步定位可疑类型（比如某个业务对象、某个集合类，如HashMap、ArrayList异常膨胀）。

**Leak Suspects报告**：MAT会自动分析并给出"疑似内存泄漏"的报告，列出占用内存最大的几个对象集群，并展示它们的GC Roots到这些对象的引用链，这是最高效的入口，通常能直接告诉你"是哪个对象树占了80%以上的堆内存"。

**Dominator Tree（支配树）**：从GC Roots出发，按Retained Size（这个对象被回收后能真正释放多少内存，包括它独占引用的子对象）排序，能精确找到内存占用的"罪魁祸首"对象，而不是被一些表面上很大但实际是被多处共享引用、不会真正被回收的对象误导。

**Path to GC Roots**：选中某个可疑对象，右键查看"到GC Root的引用路径"，并选择排除弱引用/软引用（because these would naturally be collected），这一步能直接定位到底是谁在持有这些对象不放，常见的根因包括：静态集合类持续添加对象却没有清理机制（比如全局Map缓存没有设置过期淘汰策略）、监听器/回调注册了但忘记注销、ThreadLocal用完没有remove导致线程池复用时持续累积、第三方连接池或客户端没有正确关闭资源。

### 第七步：结合代码定位与验证

MAT分析出可疑的引用链之后，回到代码里找到对应的逻辑，常见的修复方向包括：给静态缓存加上LRU淘汰策略或者改用WeakHashMap、检查ThreadLocal的使用是否成对出现remove、检查长生命周期对象（比如单例、静态字段）是否意外持有了短生命周期对象的引用、审查最近上线的变更是否引入了新的缓存逻辑或者集合类使用不当。

修复后还需要回归验证，可以在测试环境用同样的流量复现场景，再用jstat观察Full GC频率和老年代使用率是否恢复正常，确认问题真正得到解决，而不只是表面上"这次dump看到的问题解决了"，因为内存泄漏经常是渐进累积的，需要观察足够长的时间窗口才能确认彻底修复。

### 补充：紧急止血手段

如果是线上紧急故障，排查分析需要时间，但业务又扛不住持续的Full GC卡顿，可以考虑先做应急处理：比如重启该实例的JVM进程释放内存（治标不治本，但能快速恢复服务，注意确保有其他实例承接流量，避免单点重启导致服务整体不可用）、或者临时调大堆内存/调整GC参数缓解症状争取分析时间，但根本问题依然需要靠上面的dump分析流程定位并在代码层面修复，否则内存泄漏会再次积累复现。
