### **8G 堆 dump 拉本地不现实,思路是"不下载 dump,直接在服务器上用轻量命令拿类维度的直方图和对象分布",三个工具各有分工:`jmap -histo:live` 单次快照最简单、`jcmd GC.class_histogram` 更安全推荐用它、`arthas` 交互式排查最强**

  

---

  

### **一、为什么不下载 dump**

  

先讲清楚背景。堆 dump(`jmap -dump:live,format=b,file=xxx.hprof`)是**把整个堆的对象图完整序列化**,8G 堆的 dump 文件通常就是 8G 左右,拉到本地面临几个问题:

  

- **网络传输慢**:跨机房、云上带宽有限,几十分钟到几小时。

- **本地 MAT / VisualVM 打不开**:MAT 分析 8G dump 至少需要 12G 内存 + 一段索引构建时间,笔记本吃不消。

- **合规问题**:dump 里可能有用户敏感数据(密码、token、身份证号),不能随便下载。

- **生产影响**:`jmap -dump` 会 STW 整个 JVM,8G 堆可能停几十秒,业务直接超时。

  

所以线上排查的正确姿势是:**先用轻量工具拿类直方图(每个类有多少实例、占多少字节),定位可疑类;再用交互式工具深挖对象引用链**。全量 dump 只在轻量分析找不到线索时才做,而且做完直接在服务器上用 `jhat` 或者启动个临时 MAT 分析,不下载。

  

---

  

### **二、`jmap -histo:live`——最基础的类直方图**

  

**用法**:

  

```bash

jmap -histo:live <pid> | head -50

# 或者输出到文件

jmap -histo:live <pid> > histo.txt

```

  

`:live` 参数很关键——它会**先触发一次 Full GC**,只统计存活对象。不加 `:live` 的话统计的是所有对象(包括即将被 GC 的垃圾),数据没参考价值。

  

**输出样例**:

  

```

num #instances #bytes class name

----------------------------------------------

1: 1234567 2000000000 [B # byte[]

2: 890123 800000000 java.lang.String

3: 456789 400000000 com.xxx.User

4: 234567 200000000 java.util.HashMap$Node

...

```

  

三列含义:实例数、总字节、类名。`[B` 是 `byte[]`,`[C` 是 `char[]`,`[L类名;` 是对象数组。

  

**排查思路**:

  

- 看**前 20 名**,如果某个业务类实例数明显异常(比如 `com.xxx.User` 有几百万个),就是嫌疑对象。

- `byte[]` / `char[]` 常年霸榜第一很正常(String 底层),但如果字节数占堆一半以上,可能是缓存或 DirectByteBuffer 泄漏。

- `HashMap$Node`、`ConcurrentHashMap$Node`、`LinkedList$Node` 数量爆炸,说明有集合类没清理。

  

**代价和注意**:

  

- **触发 Full GC**——这是硬性 STW,8G 堆停几秒到十几秒,业务感知明显。**生产慎用,最好在低峰期或者容忍度高的实例上跑**。

- 输出是文本,几 MB 到几十 MB,`grep` / `sort` / `head` 直接分析。

- 只能拿到**类维度**信息,拿不到"谁引用了这些对象"、"具体某个 User 对象的字段值",要深挖得靠 arthas 或 dump。

### **三、`jcmd <pid> GC.class_histogram`——推荐首选**

  

**用法**:

  

```bash

jcmd <pid> GC.class_histogram | head -50

# 或加 live 过滤

jcmd <pid> GC.class_histogram -all=false # 默认就是 live,只统计存活对象

```

  

输出格式和 `jmap -histo` **几乎一样**,但底层实现更现代:

  

- **JDK 9+ 官方推荐用 jcmd 替代 jmap**,jmap 未来可能被废弃。

- **同样会触发 GC**(默认统计存活对象),但内部实现比 jmap 更稳定,遇到坏堆时不容易挂掉 JVM。jmap 历史上有过因为 attach 失败导致目标 JVM 卡死甚至崩溃的 bug。

- jcmd 是**通过本地 socket attach 到目标 JVM**,对同一台机器上的进程零依赖,比 jmap 走 SA(Serviceability Agent)机制更轻。

  

**jcmd 其他好用的堆相关子命令**:

  

```bash

jcmd <pid> GC.heap_info # 堆整体使用情况,Young/Old/Metaspace 各多少

jcmd <pid> GC.heap_dump /tmp/heap.hprof # 生成 dump(等价 jmap -dump)

jcmd <pid> VM.native_memory summary # NMT 堆外内存分析(要启动加 NativeMemoryTracking)

jcmd <pid> Thread.print # 线程栈,替代 jstack

jcmd <pid> VM.classloader_stats # ClassLoader 统计,查类加载泄漏

jcmd <pid> VM.system_properties # 看 JVM 系统属性

jcmd <pid> VM.flags # 看当前生效的 JVM 参数

```

  

**实战流程**:

  

```bash

# 第一步:看堆整体

jcmd <pid> GC.heap_info

  

# 第二步:拿类直方图

jcmd <pid> GC.class_histogram > histo.txt

  

# 第三步:按字节数排序,看 Top 20

head -30 histo.txt

  

# 第四步:搜业务类

grep "com.mycompany" histo.txt | head -20

```

  

**为什么推荐 jcmd 优先**:同样功能、更安全、JDK 官方主推、还能顺手拿到堆整体、线程、ClassLoader 等信息,是**服务器上无 dump 排查的瑞士军刀**。

### **四、Arthas——交互式深度排查神器**

  

前面两个命令拿到的是**静态快照**,只能看类维度。真正的深挖靠 Arthas。

  

**接入**:

  

```bash

# 一键启动,自动 attach

curl -O [https://arthas.aliyun.com/arthas-boot.jar](https://arthas.aliyun.com/arthas-boot.jar)

java -jar arthas-boot.jar

# 选择目标 PID,进入交互式命令行

```

  

Arthas **不需要重启业务、不改代码、极低侵入**,attach 后就能用几十个命令。堆内存分析相关的核心命令:

  

**1. `dashboard`——总览**

  

进入 arthas 直接敲 `dashboard`,实时刷新显示:

  

- 每个线程 CPU / 内存占用

- 堆各代使用率、GC 次数和耗时

- 运行时环境信息

  

一屏看清 JVM 全局状态,发现异常再往下钻。

  

**2. `heapdump`——比 jmap 更安全的 dump**

  

```

heapdump --live /tmp/heap.hprof

```

  

功能等价 `jmap -dump:live`,但 arthas 的实现更稳。可以配合 `--live` 只 dump 存活对象,文件小一半。

  

**3. `vmtool`——直接查询堆里的对象(核心武器)**

  

```

# 查询堆里所有 User 实例

vmtool --action getInstances --className com.xxx.User --limit 10

  

# 拿到实例后可以直接看字段值

vmtool --action getInstances --className com.xxx.User --limit 5 --express 'instances[0].name'

  

# 统计某个类的实例数

vmtool --action getInstances --className com.xxx.User --express 'instances.length'

  

# 强制 GC

vmtool --action forceGc

```

  

**这个命令是 arthas 的杀手锏**——直接从运行中的 JVM 里捞对象,能看字段、能调方法。比如怀疑某个缓存 Map 没清理,直接 `vmtool` 把它捞出来看 `size()`。

  

**4. `ognl`——执行任意表达式**

  

```

# 查看静态字段

ognl '@com.xxx.CacheManager@INSTANCE.cache.size()'

  

# 调用方法

ognl '@com.xxx.CacheManager@INSTANCE.clear()'

  

# 查系统属性

ognl '@java.lang.System@getProperty("java.version")'

```

  

OGNL 表达式能访问任意静态字段、调用任意方法,查看单例缓存、连接池状态、配置对象都很方便。**生产用要小心,别乱调方法改状态**。

  

**5. `sc` / `sm`——查类和方法**

  

```

sc -d com.xxx.User # 查看类详情,包括 ClassLoader

sc -d *.MyService # 通配符搜类

sm com.xxx.User * # 列出所有方法

```

  

排查 **ClassLoader 泄漏**(比如热部署导致同一个类被加载多次)特别有用,`sc` 能看到有几个 ClassLoader 加载了同名类。

  

**6. `classloader`——ClassLoader 分析**

  

```

classloader # 列出所有 ClassLoader

classloader -t # 树形展示

classloader -c <hash> # 查看某个 ClassLoader 加载的所有类

```

  

**Metaspace 泄漏**排查必备——热部署、动态代理滥用会导致 ClassLoader 无法被回收,类不停堆积。

  

**7. `profiler`——CPU / 内存火焰图(基于 async-profiler)**

  

```

profiler start --event alloc # 开始采集内存分配

# ... 等一会儿

profiler stop --file /tmp/alloc.html # 生成火焰图

```

  

`--event alloc` 是**内存分配火焰图**,能看到"哪些代码路径在疯狂分配对象"。堆增长快但不知道谁在分配时,这个能一秒定位到具体方法调用栈。CPU 火焰图用 `--event cpu`。

  

**8. `watch` / `trace`——方法监控**

  

```

# 监控方法返回值和耗时

watch com.xxx.UserService getUser '{params, returnObj, throwExp}' -x 3

  

# 追踪方法内部调用链和耗时

trace com.xxx.UserService getUser

```

  

怀疑某个方法在创建大量对象,可以 `watch` 看它返回的对象大小,或者 `trace` 看它调用了哪些下游。

### **五、三个工具的选择策略**

  

| 场景 | 首选工具 | 理由 |

|---|---|---|

| 快速看堆里有啥类、哪个类占内存最多 | `jcmd GC.class_histogram` | 一条命令、无依赖、比 jmap 安全 |

| 想拿类直方图但 JDK 太老没 jcmd | `jmap -histo:live` | 老 JDK 兼容 |

| 需要看对象具体字段、调用方法验证 | Arthas `vmtool` + `ognl` | 唯一能实时查对象内部 |

| 想知道谁在疯狂分配对象 | Arthas `profiler --event alloc` | 分配火焰图直接定位 |

| Metaspace 泄漏、ClassLoader 问题 | Arthas `classloader` + `sc` | 类加载视角唯一选择 |

| 堆整体状态、GC 情况 | `jcmd GC.heap_info` + Arthas `dashboard` | 一目了然 |

| 一定要 dump 但不下载 | Arthas `heapdump` + 服务器上 MAT | 本地传不动就服务器分析 |

### **六、完整排查 SOP**

  

假设线上告警"堆一直涨,快 OOM 了",8G 堆 dump 拉不下来,我会这么做:

  

**第 1 步:确定堆状态(30 秒)**

  

```bash

jcmd <pid> GC.heap_info

```

  

看 Young / Old / Metaspace 各自占比,判断是**老年代涨**(内存泄漏嫌疑大)还是 **Metaspace 涨**(ClassLoader / 动态类问题)。

  

**第 2 步:类直方图定位嫌疑(1 分钟)**

  

```bash

jcmd <pid> GC.class_histogram | head -50 > /tmp/histo.txt

grep "com.mycompany" /tmp/histo.txt

```

  

按字节数看 Top 20,重点关注:业务类实例数异常、集合类 Node 爆炸、byte[] 占比过大。

  

**第 3 步:Arthas 深挖嫌疑类(5 分钟)**

  

```

# 接入 arthas

java -jar arthas-boot.jar

  

# 假设怀疑 UserCache 泄漏

vmtool --action getInstances --className com.xxx.UserCache --limit 1 --express 'instances[0].cache.size()'

# 看缓存 Map 大小是不是异常

  

# 或者查静态字段

ognl '@com.xxx.CacheManager@INSTANCE.userMap.size()'

```

  

**第 4 步:如果还找不到,用分配火焰图**

  

```

profiler start --event alloc

# 等 30 秒

profiler stop --file /tmp/alloc.html

```

  

拿到火焰图后 `scp` 一个几百 KB 的 HTML 文件到本地看,直接定位分配热点。**这个文件小,能拉**。

  

**第 5 步:实在需要 dump 才 dump**

  

```

heapdump --live /tmp/heap.hprof

```

  

然后在服务器上用命令行 MAT(`ParseHeapDump.sh`)或者启动个临时容器分析,不下载。

### **七、一些实战经验**

  

- **`jmap -histo:live` 和 `jcmd GC.class_histogram` 都会 STW**,别在业务高峰跑,能选低峰实例就选低峰。

- **不加 `:live` 也可以**,不触发 GC,数据里混着垃圾但速度快,如果只是粗看趋势够用。

- **Arthas 用完记得 `stop`**,虽然侵入低但长期挂着有额外开销。

- **生产权限管好**——arthas 的 `vmtool` 和 `ognl` 能读到任何对象包括敏感数据,操作要留审计日志。

- **多实例负载均衡场景**,可以先把一个实例摘流量再排查,避免影响业务。

- **JDK 版本很重要**:JDK 8 老版本某些 arthas 命令不支持;JDK 11+ 才有完整的 jcmd 子命令集;JDK 17+ 上 `profiler` 更稳。

  

---

  

一句话总结:**8G dump 拉本地是错的思路,正解是"服务器上做轻量分析,只把小体积结果拉回来"**。三件套的分工是——**jcmd 拿类直方图定嫌疑**(替代 jmap,更安全)、**arthas vmtool / ognl 实时查对象内部**、**arthas profiler --event alloc 生成分配火焰图定位热点**。整个过程只有几百 KB 到几 MB 的文本和 HTML 需要拉,零网络压力零合规风险。**dump 是最后手段,而且做了也在服务器上分析,永远不下载**。
