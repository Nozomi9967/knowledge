# Redis fork 全量同步优化案例

## 面试话术（STAR）

### Situation（背景）

之前负责一个电商促销活动系统，大促期间 Redis 主节点内存达到 12GB 左右，存储了大量商品维表数据和秒杀库存 Key。

### Task（任务）

活动期间突然出现 Redis 间歇性耗时毛刺，部分请求超时。排查发现主节点频繁发生 fork 操作，每次耗时 1~3 秒，期间阻塞主线程，导致客户端超时。

### Action（行动）

**第一步，定位 root cause。**

查 `info stats` 发现 `latest_fork_usec` 达到 2000+ us，同时从节点因为网络抖动间歇性断连，重连时主节点发现 `repl_backlog_buffer` 太小（默认仅 1MB），需要的偏移量已经被新数据覆盖，只能走全量重同步——fork 子进程生成 RDB 发送给从节点。12GB 的页表复制加上后续写时复制（COW），导致主线程阻塞好几秒。

**第二步，对症下药。** 做了两个优化：

1. **调大 `repl-backlog-size`**。按主节点每秒写入量和可接受的断连时长（比如 5 分钟）估算，从默认的 1MB 调到 64MB。这样从节点短时间断连后，偏移量还在 buffer 内，走增量同步，不再触发 fork。
2. **拆分实例，降低单实例内存**。把商品维表数据拆出一个独立的 Redis 实例，主节点内存从 12GB 降到 6GB 左右，fork 耗时也明显缩短。

至于关闭 AOF 的方案，因为业务要求数据不丢，所以没有采用。

### Result（结果）

优化后 `latest_fork_usec` 从 2000+ us 降到 300~500 us，全量同步触发频率从每天几十次降到接近零，活动期间 Redis 毛刺消失，接口 P99 延迟下降了约 40%。

## 要点提炼

| 知识点 | 说明 |
|--------|------|
| `fork()` 阻塞原因 | 复制父进程页表（耗时长与内存量正相关） + 后续写时复制（COW）拷贝物理内存 |
| `repl_backlog_buffer` | 主节点上的环形缓冲区，缓存最近写命令，用于增量同步 |
| 全量同步触发条件 | 从节点断连重连时，所需偏移量已被 buffer 覆盖 |
| 优化手段 | 调大 `repl-backlog-size`、拆分实例降低单实例内存 |
| 面试亮点 | 体现排查链路（从现象→指标→根因→方案→效果），展示权衡思维（为何不关 AOF） |
