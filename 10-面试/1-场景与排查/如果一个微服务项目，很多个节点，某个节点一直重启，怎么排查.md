### **面试回答的核心是先定位退出原因，再区分是应用、资源、依赖还是配置问题，最后给出修复和预防措施。**

面试官问这个问题，主要想看三点：排查思路是否有条理，对容器运行机制是否熟悉，以及能否把排查经验沉淀为预防方案。下面是一份可以直接口述的回答思路。

#### **一、先确认重启现象和退出原因**

我会先用 `docker ps -a` 确认容器状态和重启次数，再用 `docker inspect` 读取 `State.ExitCode`、`State.OOMKilled`、`RestartCount` 和 `State.Error`。退出码是第一个判断依据：137 通常是被 SIGKILL 杀死，最常见的是内存超限被 OOM Killer 杀掉；1 或其他非零值一般是应用自身异常；139 是段错误；126 和 127 说明启动命令不可执行或找不到，多半是 ENTRYPOINT 写错或脚本格式问题。同时，我会用 `docker events` 查看 die、oom、restart 事件的精确时间，方便和应用日志对齐。

#### **二、再看日志，确认是不是应用本身的问题**

我会用 `docker logs --tail` 查看重启前后的日志，重点找启动阶段的异常堆栈，例如配置缺失、环境变量未设置、端口占用、数据库或 Redis 连接失败等。如果容器启动几秒就退出，问题通常在启动阶段暴露得最明显。如果日志在某个时刻突然中断而没有任何报错，就要怀疑是被外部 kill，转向资源和宿主机层面排查。

#### **三、排查资源限制**

内存是单机 Docker 最常见的原因。我会检查容器是否设置了 `--memory` 限制，以及 JVM、Node 等运行时的内存参数是否超过了这个限制。对于 JVM 应用，我会建议使用 `-XX:+UseContainerSupport` 和 `-XX:MaxRAMPercentage`，而不是写死 `-Xmx`，否则容器内的堆可能超过 cgroup 限制而被杀。CPU 和 PIDs 限制也要看，线程数过多或 CPU 被长期限流，会让健康检查超时。宿主机上还要执行 `dmesg -T | grep -i kill` 确认内核是否杀过进程，并用 `df -h` 检查磁盘是否写满，因为磁盘满会导致日志和临时文件写入失败，进而引发退出。

#### **四、检查依赖、健康检查和重启策略**

很多"一直重启"其实是重启策略放大了问题。如果配置了 `restart: always`，即使应用是正常退出也会被拉起，所以排查时我会临时改为 `on-failure` 或 `no`，让容器停在退出状态保留现场。依赖方面，`depends_on` 只保证启动顺序，不保证依赖服务就绪，应用可能因数据库尚未可用而连接失败退出，然后又被重启，形成循环。解决方式是在应用中加入带退避的重试逻辑，并为依赖服务配置健康检查，配合 `condition: service_healthy` 使用。此外，Docker 本身不会因为 unhealthy 状态重启容器，除非有 autoheal 之类的工具介入，所以要确认是谁触发了重启。

#### **五、复现和修复**

定位后，我会用同一镜像以交互方式复现，例如 `docker run -it --entrypoint sh <镜像>`，手动执行启动命令观察失败点。如果是发布引起的问题，会对比新旧镜像的依赖版本、配置文件和启动脚本的差异，必要时回滚。

#### **六、预防措施**

我会从几个方面做预防：为容器设置合理的内存和 CPU 限制，并让运行时参数跟随容器限制；为日志配置轮转，例如 `--log-opt max-size` 和 `max-file`；区分存活检查与启动检查，存活检查只判断进程是否存活，不把下游依赖作为判断条件；为应用的依赖连接增加重试和超时；并在监控中关注容器重启次数、OOM 事件和内存曲线，设置告警。

如果面试官追问具体场景，我还可以结合某次实际排查经历，按照"现象、定位过程、根因、修复和复盘"的结构展开，这样说服力会更强。
