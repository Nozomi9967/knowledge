# RocketMQ — 分布式消息中间件详解

## 一句话定义

> **RocketMQ** 是阿里巴巴开源的**分布式消息中间件**，基于**发布/订阅**模型，以「**高吞吐、低延迟、强可靠**」著称，Java 编写，支持**顺序消息、延迟消息、事务消息**三大特色能力，是国内电商场景的事实标准。

---

## 核心架构：四大角色

| 角色 | 职责 | 关键点 |
|------|------|--------|
| **Producer** | 发送消息 | 从 NameServer 拉取路由，与 Broker 建立连接 |
| **Consumer** | 消费消息 | 集群消费 / 广播消费两种模式 |
| **Broker** | 存储 + 转发消息 | 消息的真正载体，主从架构保证高可用 |
| **NameServer** | 注册中心 | 维护 Broker 的路由信息，**无状态**，可水平扩展 |

### 为什么用 NameServer 而不是 ZooKeeper？

| 对比 | NameServer ✅ | ZooKeeper |
|------|--------------|-----------|
| 状态 | 无状态，各自独立 | 有状态，需选举 |
| 一致性 | 最终一致即可（路由信息短暂不一致无影响） | 强一致（Paxos/Zab） |
| 部署 | 简单，每台独立 | 复杂，3 节点起步 |
| 通信 | Broker 每 30s 心跳上报 | 长连接 + watch |

> **面试话术**："RocketMQ 的注册中心是 NameServer 而不是 ZK。原因是路由信息**允许短暂不一致**——Producer 拿到的 Broker 地址稍微旧一点没关系，重试就能纠正。NameServer 无状态、不选举，部署和运维都简单得多。Kafka 用 ZK 是因为它要管理 Controller 选举（分区领导者选举），RocketMQ 的 Broker 主从选举也不依赖 ZK。"

### 一条消息的完整旅程

```
Producer → NameServer（拿路由） → Broker Master（存 CommitLog）
                                      │
                         ┌────────────┴────────────┐
                   同步/异步复制              消费者
                         ▼                         ▼
                   Broker Slave              拉取消息（长轮询）
```

## 存储设计：为什么 RocketMQ 这么快（重点考点）

### 三层文件结构

```
Broker 磁盘
├── CommitLog/          # 所有消息顺序写入的单一日志文件（每个 Broker 一个）
├── ConsumeQueue/       # 消费队列：每 topic×queue 一个，记录消息在 CommitLog 的偏移量
└── IndexFile/          # 索引文件：按 key（如订单号）快速查消息
```

| 文件 | 存什么 | 作用 |
|------|--------|------|
| **CommitLog** | 消息的完整内容 | **顺序写**，落盘最快 |
| **ConsumeQueue** | 消息的物理偏移量（20 字节定长条目） | 逻辑队列，消费时**顺序读**，一跳定位 |
| **IndexFile** | 消息 key → 偏移量的索引 | 按 key 查询消息（如按订单号排查） |

### 快的原因一：顺序写磁盘

- 所有消息**只追加**到同一个 CommitLog 文件，没有随机 IO
- 机械盘顺序写也能到几百 MB/s，SSD 更不用说了

### 快的原因二：页缓存 + 零拷贝（mmap）

| 技术 | 说明 |
|------|------|
| **Page Cache** | 写消息先写 OS 页缓存，由内核异步刷盘，读写命中率高 |
| **mmap 映射** | CommitLog 用 mmap 映射到用户态，避免用户态/内核态数据拷贝 |
| **FileRegion（sendfile）** | 消费者拉消息走 sendfile，**零拷贝**直接从内核发到网卡 |

> **面试话术**："RocketMQ 快是因为存储设计：① 所有消息顺序写一个 CommitLog，没有随机 IO；② 借助 Page Cache，读写基本在内存里完成；③ 消费走 mmap 甚至 sendfile 零拷贝，数据不经过用户态。所以单 Broker 轻松扛几十万 TPS 写入。"

### 刷盘策略

| 策略 | 行为 | 风险 | 场景 |
|------|------|------|------|
| **异步刷盘**（默认） | 先写页缓存就返回 | 机器断电丢最近消息 | 高吞吐、允许少量丢失 |
| **同步刷盘** | 落盘成功才返回 | 吞吐下降 | 支付、订单等关键消息 |

### 主从复制

| 模式 | 行为 | 风险 |
|------|------|------|
| **异步复制**（默认） | Master 写完就返回 | 主挂，Slave 可能少消息 |
| **同步复制** | Slave 确认才返回 | 吞吐下降 |

> **组合拳（不丢消息）**：**同步刷盘 + 同步复制** = 消息最保险（但吞吐最低）；生产上一般**异步刷盘 + 异步复制**，靠业务幂等兜底。

## 消费模型

### 集群消费 vs 广播消费

| 模式 | 语义 | 进度存储 | 场景 |
|------|------|---------|------|
| **集群消费**（默认） | 一条消息只被一个实例消费，天然负载均衡 | 存 Broker | 任务分配（如订单处理） |
| **广播消费** | 每个实例都消费全量 | 存消费者本地 | 本地缓存刷新、配置同步 |

### Push 模式的本质：长轮询

- RocketMQ 的 Push **不是真推送**，而是**长轮询（Long Polling）**：
  - Consumer 发拉取请求给 Broker
  - Broker 有消息 → 立即返回
  - Broker 没消息 → **挂起请求最多 15s**，有消息到达或超时才返回

> **为什么不用真推送**："真推送的难点是 Broker 不知道消费者处理能力，容易把消费者压垮。长轮询兼顾了实时性（消息到就返回）和背压（消费者自己控制拉取节奏），是 Pull 和 Push 的折中。"

> [!question]- 「Push」到底是谁在推？—— Broker 没推，但框架在往你的回调里推
> **整条链路一半拉、一半推，PushConsumer 的名字描述的是后半段**：
>
> ```
> Broker ──①长轮询（Consumer 发起）──▶ 框架内部线程 ──②回调（框架发起）──▶ 你的 onMessage()
>              拉取                                      推送
> ```
>
> - `DefaultMQPushConsumer` 只是 API 命名：框架后台拉取线程主动向 Broker 发 pull 请求，拉到消息后回调你
> - **请求方向永远是 Consumer → Broker**，TCP 连接也是 Consumer 建的；Broker 只应答、从不主动发起数据发送（未经请求主动发数据才叫推送）
> - 长轮询"挂起 15s"返回的仍是**对你请求的应答**，不是推送；主动权始终在 Consumer
> - **推是存在的，推在最后一跳**：Pull 消费者要自己写 `while(true) poll()` 循环、消息是自己伸手拿的；Push 消费者的业务代码全程被动——框架调你的 `onMessage` 把消息**作为参数塞进来**，你的代码里不存在"取消息"这个动作。对 Broker 是拉，对你的业务代码是推
> - **为啥敢叫 Push**：命名沿袭 JMS 传统——`onMessage()` 回调式 = 推、`receive()` 轮询式 = 拉，说的是 **API 风格**，不是网线方向。真正的分界线是「**谁驱动消费循环**」
> - **真推的参照物（RabbitMQ）**：订阅后 Broker 异步主动投递，消费者可能被压垮，要靠 prefetch 限流自保；RocketMQ 长轮询拉取天然自带背压，不需要 prefetch
> - **面试话术**："RocketMQ 的 Push 是'假推真拉'——框架对 Broker 是长轮询拉取，拉到后回调我的 listener，等于把消息推进我的业务代码。Broker 不主动推，这正是背压的来源：消费多快、拉多快，所以也不需要 RabbitMQ 那样的 prefetch 限流。"

### 负载均衡与重平衡

- 集群模式下，Broker 的 Topic 下多个 MessageQueue 会**分给多个消费者实例**（如 8 个队列 2 个实例，各分 4 个）
- 消费者实例增减（上线/宕机/扩容）时触发**重平衡**，队列重新分配
- ⚠ 重平衡期间可能造成**短暂重复消费**——消费端幂等又派上用场了

### 消费失败怎么办：重试 + 死信

```
消费失败 → 重试队列（延迟递增，共 16 次：1s 2s 4s 8s ... 2h）
     ├─ 成功 → 结束
     └─ 仍失败 → 死信队列（%DLQ%topic），人工介入/对账补偿
```

- 顺序消息消费失败会**挂起当前队列**（block 后续消息），保证顺序不被乱
- 死信队列详见 [[死信队列]]

## 消息类型：四大类

| 类型 | 特点 | 面试高频点 |
|------|------|-----------|
| **普通消息** | 无顺序要求 | 基础 |
| **顺序消息** | 全局顺序 / 分区顺序 | 如何保证？见下 |
| **延迟消息** | 延迟 N 秒投递 | 18 个固定级别 |
| **事务消息** | 本地事务 + 消息原子 | 详见 [[RocketMQ事务消息详解]] |

### 顺序消息怎么保证？

| 粒度           | 做法                                                                   | 代价              |
| ------------ | -------------------------------------------------------------------- | --------------- |
| **全局顺序**     | 整个 Topic 只建 1 个队列                                                    | 吞吐降到单队列，基本不用于生产 |
| **分区顺序**（主流） | 用 `MessageQueueSelector` 按业务 key（如 orderId）**取模选队列**，同一 key 的消息进同一队列 | 单队列内串行消费，不同订单并行 |

> **面试话术**："顺序消息的核心是**队列维度**——RocketMQ 的队列是 FIFO 的，只要同一订单的消息都进**同一个队列**，消费端按队列顺序消费就是有序的。实现上用 `MessageQueueSelector` 按订单号 hash 选队列；消费端注意：顺序消息消费失败会**阻塞当前队列**，所以消费者要保证单条消息最终能处理成功（配合重试）。注意顺序消息**重试会阻塞**，事务消息不能顺序——这是 RocketMQ 的两个限制。"

### 延迟消息：18 个固定级别

- RocketMQ 的延迟消息**不是任意秒数**，而是固定 18 级：
  `1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h`
- 实现：消息带延迟级别 → Broker 放入对应延迟队列 → 定时任务到期后**重新投递**到真实队列
- 场景：30 分钟未支付自动关单（但 30m 恰好是内置级别，超过 2h 的自定义延迟需要改造或用时间轮）

### 经典对比：30 分钟未支付自动关单 —— 延迟消息 vs 定时任务轮询

**方案 A：RocketMQ 延迟消息（事件驱动）**

下单成功 → 发一条延迟 30m 的消息（`setDelayTimeLevel(16)`，第 16 级正好 30m）→ 30m 后消息投递回消费者 → 检查订单：仍未支付则关单，已支付则忽略。

```
下单 ──▶ 发延迟消息(30m) ──▶ [Broker 暂存 30 分钟] ──▶ 投递 ──▶ 查订单状态
                                                              ├─ 未支付 → 关单
                                                              └─ 已支付 → 忽略
```

**方案 B：定时任务轮询（Elastic-Job / XXL-Job / @Scheduled）**

定时任务每 N 分钟扫一次订单表：`SELECT * FROM orders WHERE status='待支付' AND create_time < now()-30min` → 批量关单。

| 维度     | 延迟消息 ✅                                            | 定时任务轮询                                            |
| ------ | ------------------------------------------------- | ------------------------------------------------- |
| 触发精度   | **精确到秒**（下单后正好 30m）                               | 取决于轮询周期——每 5 分钟扫一次，关单最多**晚 5 分钟**                 |
| 空转开销   | **零空转**——每笔订单一条消息，处理完即焚                           | **大量空扫**——绝大多数订单 30 分钟内就支付了，每轮扫出的"待关单"常为 0 条，扫表白跑 |
| DB 压力  | 不扫库                                               | 每轮全表/索引扫描，订单量大时慢查询拖垮 DB（可加 `create_time` 索引缓解）    |
| 可靠性    | ⚠ 消息可能丢（Broker 故障），关单漏掉需兜底                        | ✅ 到点必扫，天然不漏（幂等可重跑）                                |
| 延迟级别限制 | 只能 18 级选一，且**要和支付超时时间强绑定**——运营把超时改成 25 分钟就得改代码改级别 | 改配置即可，灵活                                          |
| 积压放大   | 下单峰值 = 30m 后关单消费峰值（双 11 削峰变成延迟削峰）                 | 扫描压力恒定                                            |

**两方案真正的分工（面试标准答法）**：不是二选一，是**互为兜底**——主链路用延迟消息保证精度和零空转，再配一个**低频轮询（如每小时一次）扫漏网的未支付订单**，防止消息丢失导致订单永挂。这正好复用"消息不丢三环节"的思路：MQ 负责快，轮询负责"最终一定发生"。

> [!warning] 延迟消息的三个面试坑
> ① **级别写错静默不报错**——`setDelayTimeLevel(17)` 是 1h 不是 30m，硬编码数字不如用常量；② **延迟消息不保证不丢**——同步刷盘+同步复制只防单点故障，防不住双节点同灭（机房级故障）；且更现实的丢法是**消息没丢、关单动作丢了**：投递成功但消费失败重试 16 次进死信无人处理，订单照样永挂。所以必须配轮询兜底——它以数据库状态为事实源，完全绕开消息链路，是**结果层面**的保证；③ **RocketMQ 5.x 已支持任意时间延迟**（基于时间轮的 TimerWheel），答题时可主动提，体现知识时效性。
>
> ⚠ 勘误（2026-09-05）：本条初版把「回查」写进了延迟消息的丢失路径——**回查是事务消息（half 消息）专属机制**，延迟消息发出去后 Producer 与 Broker 无任何交互，没有回查环节，两者不可混。

### 消费端幂等：为什么必然重复 + 三层去重方案

**先说根因——重复消费是 MQ 的固有属性，防不住只能兜：**

- at-least-once 语义：Broker 投递后**没收到 ACK 就重投**——你消费成功了但 ACK 在网络上丢了，Broker 认为你没消费，再投一次
- 生产端重试：同一消息发两次（网络抖动，Producer 不知道第一次成功没）
- 重平衡：队列重新分配的瞬间，旧消费者 offset 未提交，新消费者从头拉一遍

> 结论：**RocketMQ 只承诺"不丢"，不承诺"不重"**。想恰好一次（exactly-once）在分布式系统里基本不可达，工程上永远是"至少一次投递 + 消费端幂等" = 业务上的恰好一次。

**三层幂等方案（从重到轻）：**

| 层级 | 方案 | 做法 | 适用 |
|------|------|------|------|
| ① DB 层 | **唯一索引** | 订单号/流水号建唯一索引，重复插入直接报 `DuplicateKeyException`，捕获后当成功处理 | 插入类消息，**最硬的一道防线，零额外代码** |
| ② 去重表 | **消息消费记录表** | 消费前先 `INSERT` 消息 ID（msgId/业务唯一键）进去重表——同一事务里"插记录 + 处理业务"，插入冲突说明消费过 | 通用，可审计 |
| ③ 缓存层 | **Redis SETNX** | `SET mq:dedup:{msgId} 1 NX EX 86400`，设置成功才处理 | 高频轻量场景，⚠ **Redis 不可靠（宕机/过期）**，只能挡"短时间内的重复"，必须配合 ①② 而不能替代 |

**⚠ 状态机校验（容易被追问的第四种）**：有状态流转的业务不用额外去重表——`UPDATE orders SET status='已发货' WHERE order_id=? AND status='已支付'`，affected rows = 0 就是重复消息，天然幂等。**能用状态机就不要另建去重表**。

> [!info]- 幂等三方案的分工：唯一索引 / 去重表 / 状态机
> **唯一索引 vs 状态机：分工关系，二选一**——各管一类操作，对同一个写操作非此即彼，都是完整方案：
> - **唯一索引**防重复**插入**（第二次 INSERT 撞约束报错）——但防不了 UPDATE
> - **状态机**防重复**更新**（第二次 UPDATE 时前置状态已不满足，WHERE 匹配不到）——但没有插入动作时它也无从校验
> - 同时出现的唯一场合：一次消费含多步（如支付消息 = INSERT pay_log 撞唯一索引 + UPDATE 订单状态撞状态机）——各守各的步骤，不是对同一动作双重保护
>
> **唯一索引 vs 去重表：同一机制、不同位置**——都是「唯一约束撞墙 = 已处理」、都捕获 `DuplicateKeyException` 当重复，区别只在唯一性挂在谁的表上：
> - 业务本身就是 INSERT 且有天然业务键（订单号/流水号）→ **挂业务表**（唯一索引，零额外成本）
> - 三种情况被迫**另建门**（去重表）：① 消费动作不是 INSERT（外部 HTTP/RPC，没有"业务自身的记录"可撞）② 一条消息触发多步、"只执行一次"是整体（单个索引覆盖不了）③ 需要审计哪些消息消费过（唯一索引拒绝时不留痕）
> - 代价：去重表每次消费多一次写 + 定期清理；INSERT 去重记录与业务操作必须在**同一事务**（否则业务失败但记录已存在，消息被永久跳过）
>
> 统一原则——幂等就是让"第二次执行"：唯一索引 = **进不去**，状态机 = **匹配不上**，去重表 = **有账可查**（把唯一约束的门另挂一扇）。
>
> ⚠ **实践坑 1**：affected rows = 0 分不出「重复消息」还是「前置状态本来就不对」，两种都返回成功 ACK，但 0 行要**打日志**——否则真实脏数据异常会被幂等逻辑静默吞掉。
> ⚠ **实践坑 2（去重表的天花板）**：同事务只能捆住**本地 DB 操作**，外部 HTTP 调用不跟事务回滚——"记录已提交但外部调用前挂掉"（少调）或"外部调成功但事务回滚"（多调）是必然的双写缺口。要对外部调用逼近 exactly-once，得上**本地消息表 / Transactional Outbox**（先落"待调用"记录与业务同事务 → 提交后调外部 + 更新 → 定时补偿扫卡住的），参见 [[RocketMQ事务消息详解]] Q2 的对比。

**面试话术**：

> "RocketMQ 是 at-least-once，重复消费防不住，只能在消费端幂等。我的做法分两层：第一道用**数据库唯一索引**兜底——重复消息插入直接冲突，零成本；业务上再配合**状态机校验**，UPDATE 带 `WHERE status='前置状态'`，affected rows 为 0 就说明处理过了，直接返回成功让 Broker 停止重投。高频场景前置一层 **Redis SETNX** 快速挡掉大部分重复，但它不可靠，只当加速，真正的正确性靠 DB 层。"

**⚠ 两个细节坑：**
- 判重键用**业务唯一键**（订单号），不要用 `msgId`——生产端重试会产生两条 msgId 不同但业务相同的消息，按 msgId 去重会漏
- 去重逻辑要和业务处理**在同一个事务里**——"先记去重表再处理业务"两步分开写，第二步失败时记录已存在，消息被永久跳过

## 消息可靠性：三层防丢失

| 环节 | 手段 | 丢失风险 |
|------|------|---------|
| **生产端** | 同步发送 + 失败重试（默认 2 次）；确认返回才算成功 | 低 |
| **Broker** | 异步刷盘（断电丢）/ 同步刷盘 + 同步复制（不丢） | 可控 |
| **消费端** | 消费成功才 ACK；失败进重试队列（16 次）→ 死信 | 低 |

> **面试话术**："消息不丢失要三个环节一起看。生产端我用同步发送，失败重试并告警；Broker 端关键消息配同步刷盘；消费端消费成功才 ACK，失败进重试队列，重试 16 次还失败进死信队列，定时任务扫死信做补偿。**丢失**和**重复**是硬币两面——RocketMQ 是 at-least-once 语义，保证不丢但可能重复，所以消费端幂等是必须的。"

## 消息堆积怎么办（线上高频）

| 场景 | 排查 | 处理 |
|------|------|------|
| 消费速度跟不上 | 看消费组 lag（`mqadmin consumerProgress`） | 扩容消费者实例（队列数 ≥ 实例数才有效） |
| 单条消费太慢（慢 SQL/远程调用） | 查消费者日志耗时 | 批量消费（一次拉 N 条）、异步化、优化单条逻辑 |
| 瞬时洪峰（秒杀） | 堆积是**设计预期** | 削峰填谷——本来就是要让它慢慢消化 |
| 积压 100 万级 | 短时间消化不完 | 临时把消息转存（如落 HDFS/库），业务侧直接查结果 |

> 关键认知：**堆积 ≠ 故障**，只要积压消息在 TTL 内能消化完就没事；真正危险的是**消费端雪崩**（堆着堆着消费端也挂了）。

## 面试高频追问与话术

### Q1: RocketMQ vs Kafka 怎么选？

| 维度 | RocketMQ ✅ | Kafka |
|------|------------|-------|
| 吞吐 | 高（十万级/秒） | 更高（百万级/秒） |
| 事务消息 | ✅ 原生支持 | ⚠ 需外部协调 |
| 延迟消息 | ✅ 18 级内置 | ❌ 需自研 |
| 顺序消息 | ✅ 队列维度 | ✅ 分区维度 |
| 消费失败重试 | ✅ 重试队列 + 死信 | ⚠ 靠 offset 手动控制 |
| 语言 | Java | Scala |

> **面试话术**："选型看场景。Kafka 吞吐极限更高、生态强（流处理），但消息可靠性机制弱一些——消费失败靠手动管理 offset，延迟消息要自研。RocketMQ 是 Java 写的，事务消息、延迟消息、死信重试开箱即用，正好匹配电商的支付、关单、订单流转场景。我们项目选 RocketMQ 就是看中它**事务消息 + 延迟消息 + 顺序消息**三件套。"

### Q2: 如何保证消息不丢失？（三层答案见上）

### Q3: 如何保证消息不重复消费？

> **面试话术**："RocketMQ 是 at-least-once 语义，重复消费靠**业务幂等**兜底：① 消费前查**去重表**（订单号唯一键）；② 或依赖数据库**唯一索引**，重复插入直接冲突忽略；③ 轻量场景用 Redis SETNX 判重。不能指望 MQ 帮你去重。"

> 📖 完整版（重复根因 + 三层方案 + 状态机校验 + 去重键选择）见上方「消费端幂等」小节。

### Q4: 顺序消息为什么不能配合事务消息使用？

> 事务消息 commit 前消息不可见，而顺序消息要求队列内严格有序——两者的语义冲突。RocketMQ 官方不支持事务消息 + 顺序消息组合。如果需要「有序 + 事务」，一般拆成：本地事务落库 + 顺序消息通知，靠业务状态机兜底。

### Q5: 为什么 RocketMQ 吞吐高？（存储设计答案见上）

### Q6: 堆积的消息会过期吗？过期怎么办？

- 消息默认保存 **48 小时**（`fileReservedTime` 可配），过期删除
- 如果 48h 内消化不完，用「临时转存」方案，别硬扛

### Q7: 重平衡导致的重复消费怎么避免？

> "重平衡瞬间队列重新分配，旧消费者还没提交 offset、新消费者又拉了一遍，必然产生重复。没有银弹，消费端幂等是唯一解。"

## 常见踩坑清单

| 坑 | 现象 | 解决 |
|----|------|------|
| 消费组内实例数 > 队列数 | 部分实例空闲 | 扩容前先加队列（Topic 创建时规划够） |
| 顺序消息消费失败一直重试 | 队列卡死，后续消息全堵 | 重试次数内保证成功；或拆队列隔离 |
| 异步发送不检查结果 | 静默丢消息 | 回调里校验 SendResult，失败告警 |
| 消费端不幂等 | 重复扣库存/重复发积分 | 唯一键去重表 |
| 消息 48h 过期 | 大堆积时消息被删 | 提前转存方案 |
| 广播消费进度存本地 | 实例重启从最早开始消费 | 确认模式再使用，别混用 |

## 通俗理解

> **通俗理解**：RocketMQ 像一个**大型物流中转站**。
>
> **NameServer** 是「地址簿」——你寄快递前先查哪个站点收件；**Broker** 是「仓库」——所有包裹按到达顺序码放整齐（CommitLog 顺序写），每面墙上贴着「货架索引」（ConsumeQueue），找包裹不用翻仓库，看索引一步到位；**Consumer** 是「收货人」——它不去仓库门口蹲守（真推送），而是打电话问「有我的货吗？没有我就先挂机 15 分钟再打」（长轮询）。**顺序消息**是「同一收件人的包裹必须按寄出顺序送达」——放进同一条传送带（队列）；**延迟消息**是「加急件到了先放暂存区，到点再送」。万一包裹送错了（消费失败），退回重试 16 次，还不行就进「问题件仓库」（死信队列）等人处理。
