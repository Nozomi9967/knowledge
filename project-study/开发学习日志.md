### /proc

Linux 中 `/proc` 是一个**虚拟文件系统**，内核为每一个正在运行的进程都创建了一个以 **PID 命名的目录**，实时反映该进程的状态。

```
/proc/
├── 1/          # systemd 进程
├── 1776/       # mysqld 进程
├── 59599/      # nacos java 进程
├── 78144/      # 你的 nacos 进程
│   ├── cwd     # 工作目录（软链接）
│   ├── exe     # 可执行文件路径（软链接）
│   ├── cmdline # 完整启动命令
│   ├── fd/     # 打开的所有文件描述符
│   ├── maps    # 内存映射
│   └── status  # 进程状态、内存占用等
└── ...
```

**Nginx 请求处理流程（简化版）**

```
Rewrite 阶段：处理 rewrite 指令，重写 URL。

Access 阶段：执行你的 access_by_lua_file。（Redis 逻辑在这里运行）

如果 Lua 直接 ngx.say 并 ngx.exit，流程在此终止。

Content 阶段：

第一步：缓存检查。Nginx 检查 proxy_cache 区域是否有匹配的缓存。

第二步：命中或回源。

如果 命中：直接从磁盘/内存读取缓存返回。

如果 未命中：执行 proxy_pass 请求后端服务器，获取数据后更新缓存并返回。
```

`rewrite_by_lua`：重写阶段，执行完**不会自动进入代理**

`access_by_lua`：访问控制阶段，执行完**自动继续走 proxy_pass**

```nginx
#门户发布
server {
    listen       80;
    server_name  www.gpshopvip.com;

    #推广产品查询
    location /sku/aditems/type {
        
        access_by_lua_file /usr/local/openresty/nginx/lua/aditem.lua;
        #第二个proxy_cache是缓存区域名称，第一个是命令
        proxy_cache proxy_cache;
        #针对指定请求缓存
        #proxy_cache_methods GET;
        #哪些状态码的响应要缓存、缓存多久。
        proxy_cache_valid 200 304 60s;
        #最少请求1次才会缓存
        proxy_cache_min_uses 1;
        #如果并发请求，只有第1个请求会去服务器获取数据
        #proxy_cache_lock on;
        #给每个不同的请求，生成一个独一无二的缓存文件名，避免缓存错乱。
        proxy_cache_key $host$uri$is_args$args;
        #动态代理
        proxy_pass http://192.168.172.100:8081;
    }


    #其他所有请求
    location / {
        root   /usr/local/nozomi-mall/web/static/front;
    }
}
```





```nginx
#清理缓存
location ~ /purge(/.*) {
    #清理缓存
    proxy_cache_purge proxy_cache $host$1$is_args$args;
}
# ~: 表示开启 区分大小写 的正则匹配。
```

**正则表达式拆解：`~ /purge(/.*)`**

- **`~`**: 表示开启 **区分大小写** 的正则匹配。
- **`/purge`**: 这是固定的前缀。意味着只有请求以 `/purge` 开头的 URL 才会命中这个 `location`。
- **`(/.\*)`**: 这是一个 **捕获组（Capture Group）**：
  - `(` `)`：圆括号表示将匹配到的内容保存到一个临时变量中。在 Nginx 中，第一个圆括号捕获的内容会被赋值给变量 **`$1`**。
  - `/.*`：匹配斜杠 `/` 后面跟着的任意数量（`*`）的任意字符（`.`）（包括/）。

```lua
http {
    lua_shared_dict cache_dict 100m;

    server {
        listen 80;

        location /api/ {

            content_by_lua_block {
                local redis = require "resty.redis"
                local red = redis:new()
                red:set_timeout(100)

                -- 连接 Redis
                local ok, err = red:connect("127.0.0.1", 6379)
                if not ok then
                    ngx.say("Redis连接失败")
                    return
                end

                local uri = ngx.var.request_uri

                -- 获取版本号
                local version_key = "cache:version:" .. uri
                local version = red:get(version_key)

                if version == ngx.null then
                    version = "1"
                end

                -- 拼接缓存key
                local cache_key = "cache:data:" .. uri .. ":v" .. version

                -- 查缓存
                local cache = red:get(cache_key)

                if cache ~= ngx.null then
                    ngx.say(cache)
                    return
                end

                -- ====== 未命中，访问后端 ======
                local res = ngx.location.capture("/backend" .. uri)

                if res.status ~= 200 then
                    ngx.status = res.status
                    ngx.say("后端错误")
                    return
                end

                local data = res.body

                -- 写缓存（带过期时间）
                red:setex(cache_key, 300, data)

                ngx.say(data)
            }
        }

        # 后端接口（示例）
        location /backend/ {
            proxy_pass http://127.0.0.1:8080/;
        }
    }
}
```

## rocketMQ



### 部署

以下是使用 Docker Compose 安装 RocketMQ 5.x 的完整教程：---

#### 一、准备工作

确认已安装 Docker 和 Docker Compose：

```bash
docker --version
docker compose version
```

------

#### 二、创建目录结构

```bash
mkdir -p rocketmq/{nameserver/logs,broker/logs,broker/data,broker/conf,dashboard}
cd rocketmq
```

------

#### 三、Broker 配置文件

创建 `broker/conf/broker.conf`：

```properties
brokerClusterName = DefaultCluster
brokerName = broker-a
brokerId = 0

# 关键：填写你宿主机的实际 IP（不能用 127.0.0.1）
brokerIP1 = 192.168.1.100

namesrvAddr = namesrv:9876
defaultTopicQueueNums = 4
autoCreateTopicEnable = true
autoCreateSubscriptionGroup = true

listenPort = 10911
deleteWhen = 04
fileReservedTime = 48
mapedFileSizeCommitLog = 1073741824
mapedFileSizeConsumeQueue = 300000
destroyMapedFileIntervalForcibly = 120000
deleteCommitLogFilesInterval = 100
deleteConsumeQueueFilesInterval = 100

diskMaxUsedSpaceRatio = 88
storePathRootDir = /home/rocketmq/store
storePathCommitLog = /home/rocketmq/store/commitlog

flushDiskType = ASYNC_FLUSH
```

> ⚠️ `brokerIP1` 必须是你宿主机的局域网 IP，用 `ip addr` 查询。

------

#### 四、docker-compose.yml

```yaml
version: '3.8'

services:
  namesrv:
    image: apache/rocketmq:5.3.1
    container_name: rocketmq-namesrv
    ports:
      - "9876:9876"
    environment:
      - JAVA_OPT_EXT=-Xms512m -Xmx512m
    command: sh mqnamesrv
    volumes:
      - ./nameserver/logs:/home/rocketmq/logs
    networks:
      - rocketmq-net
    restart: unless-stopped

  broker:
    image: apache/rocketmq:5.3.1
    container_name: rocketmq-broker
    ports:
      - "10909:10909"
      - "10911:10911"
    environment:
      - JAVA_OPT_EXT=-Xms1g -Xmx1g
    command: sh mqbroker -c /home/rocketmq/conf/broker.conf
    volumes:
      - ./broker/logs:/home/rocketmq/logs
      - ./broker/data:/home/rocketmq/store
      - ./broker/conf/broker.conf:/home/rocketmq/conf/broker.conf
    depends_on:
      - namesrv
    networks:
      - rocketmq-net
    restart: unless-stopped

  dashboard:
    image: apacherocketmq/rocketmq-dashboard:latest
    container_name: rocketmq-dashboard
    ports:
      - "8080:8080"
    environment:
      - JAVA_OPTS=-Drocketmq.namesrv.addr=namesrv:9876
    depends_on:
      - namesrv
      - broker
    networks:
      - rocketmq-net
    restart: unless-stopped

networks:
  rocketmq-net:
    driver: bridge
```

#### 常见问题

| 问题                                                         | 原因                                                         | 解决                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| broker 注册失败                                              | `brokerIP1` 填了 127.0.0.1                                   | 改为宿主机真实 IP                                            |
| 内存不足启动失败                                             | JVM 默认堆较大                                               | 调小 `JAVA_OPT_EXT` 中的 `-Xmx`                              |

| 消息发送超时                                                 | 防火墙拦截 10911 端口                                        | 开放端口或检查 `brokerIP1`                                   |
| `ScheduleMessageService.configFilePath` 在尝试访问 store 目录时拿到了 null， | 说明容器内的 `/home/rocketmq/store` 路径无法写入，通常是宿主机挂载目录权限不对。 | \# 在 docker-compose.yml 所在目录执行 chmod -R 777 broker/data chmod -R 777 broker/logs chmod -R 777 nameserver/logs |

**更新语句**

```sql
> db.item.update({_id:"No1"},{$inc:{price:1}})
WriteResult({ "nMatched" : 1, "nUpserted" : 0, "nModified" : 1 })

> db.item.update({_id:"No1"},{$set:{name:"华为P40 Pro"}})

-- {_id:"No1"}（查询条件）：告诉 MongoDB 寻找 _id 为 "No1" 的那条文档。

-- $inc（修改器）：这是 increase 的缩写，是 MongoDB 的内置操作符，专门用于数字的加减。

-- {price: 1}（操作内容）：指定对 price 字段进行操作，增加 1。如果要降价，只需写成 -1。

-- WriteResult 是数据库给你的回执，告诉你这次操作的结果：

-- "nMatched" : 1：匹配到了 1 条数据。说明数据库里确实存在 _id:"No1" 的商品。

-- "nUpserted" : 0：没有进行 Upsert 操作。Upsert 是指“如果不存在就插入”，这里因为匹配到了，所以不需要插入。

-- "nModified" : 1：实际修改了 1 条数据。
```







## 用bootstrap.yml还是application.yml?

看你的项目有没有接 **Nacos 配置中心**。

文档里 `mall-cart-service` 的配置写了：

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: 192.168.100.130:8848
```

这说明它要从 Nacos 拉取配置，**就必须用 `bootstrap.yml`**，因为 Nacos 配置需要在 Spring 容器启动之前加载，而 `application.yml` 加载时机太晚。

------

**结论：**

- 你的 `mall-cart-service` 和 `mall-order-service` 都连了 Nacos → 用 **`bootstrap.yml`**
- 同时确保依赖里有：

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
```

没有这个依赖，Spring Boot 3.x 默认不识别 `bootstrap.yml`，Nacos 配置就不会生效。



当 `bootstrap.yml` 和 `application.yml` 同时存在时，它们并不是简单的“谁听谁的”竞争关系，而是**加载顺序**和**优先级**的差别。

简单来说：**它们会合并，但如果配置冲突，`bootstrap.yml` 的优先级更高（在大多数 Spring Cloud 场景下）。**

------

### 1. 加载顺序：谁先启动？

`bootstrap.yml` 由父 Spring `ApplicationContext` 加载。

- **`bootstrap.yml` 先加载**：它用于应用程序上下文的引导阶段。主要用于从外部配置中心（如 Nacos、Config Server）读取配置，或者解密属性。
- **`application.yml` 后加载**：它是常规的应用程序配置，在引导完成后加载。

------

### 2. 优先级：谁说了算？

在默认的 Spring Cloud 行为中，配置的优先级如下（从高到低）：

1. **命令行参数** (例如 `--server.port=8081`)
2. **`bootstrap.yml`** (远程配置中心获取的配置通常映射到这里)
3. **`application.yml`**

**这意味着：**

如果你在 `bootstrap.yml` 中写了 `port: 8083`，而在 `application.yml` 中写了 `port: 8080`，程序最终会运行在 **8083** 端口。

------

### 3. 它们各自的分工（最佳实践）

为了避免混乱，开发者通常会按照以下逻辑分配配置：

| **配置类型**                             | **建议存放位置**  | **理由**                                |
| ---------------------------------------- | ----------------- | --------------------------------------- |
| **Nacos/远程配置中心地址**               | `bootstrap.yml`   | 必须在应用启动前就知道去哪取配置。      |
| **应用名称 (`spring.application.name`)** | `bootstrap.yml`   | 作为获取远程配置的索引 ID。             |
| **解密/加密密钥**                        | `bootstrap.yml`   | 在处理常规配置前需要完成解密。          |
| **业务逻辑配置**                         | `application.yml` | 属于应用内部的常规逻辑设置。            |
| **数据库/Redis 本地连接**                | `application.yml` | 除非这些连接信息是从 Nacos 动态获取的。 |

------

### 4. 特别注意：Spring Boot 3.x 的变化

如果你使用的是 **Spring Boot 3.x**（或较新的 2.4+ 版本），官方默认**禁用了** `bootstrap` 机制。

- 如果你发现 `bootstrap.yml` 完全不生效，那是因为新版本推荐使用 `spring.config.import` 来引入远程配置。

- 若想恢复 `bootstrap` 的行为，你需要手动添加以下依赖：

  XML

  ```
  <dependency>
      <groupId>org.springframework.cloud</groupId>
      <artifactId>spring-cloud-starter-bootstrap</artifactId>
  </dependency>
  ```

**一句话总结：**

`bootstrap` 是“先行官”，定基调（连接配置中心）；`application` 是“指挥官”，管细节。如果两人命令冲突，**先行官（bootstrap）** 往往拥有更早的决策权且不轻易被后者覆盖。
