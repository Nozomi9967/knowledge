### **"先写库再删缓存"是工程上最推荐的默认方案，延迟双删是它的补丁，订阅 binlog 是最终一致性的最优解，"先删缓存再写库"因并发脏读风险最大不推荐。**

下面按面试口述节奏展开。

---

**第一部分：先讲清楚不一致的根源**

缓存和数据库是**两个独立存储**，任何"写 DB + 写/删缓存"的操作都不是原子的。中间任何一步失败、任何一次并发读写交错，都会导致缓存里存的和 DB 里存的不一致。所有方案本质都在回答两个问题：

1. **先操作哪个？** —— 决定并发下"脏读窗口"有多大；
2. **不一致发生后怎么修复？** —— 决定最终一致的时间上限。

另外一个前提共识：**"更新缓存"比"删除缓存"更容易出错**（并发写会覆盖、复杂对象要重新计算），所以业界主流是**"删除缓存"策略 (Cache-Aside)**，而不是"更新缓存"。下面四种方案都基于这个前提。

---

**第二部分：四种方案逐一拆解**

**方案一：先删缓存，再写数据库**

```
1. DEL cache
2. UPDATE db
```

**并发下的问题**（最经典的脏数据场景）：

```
线程 A: 删缓存 → (还没写库)
线程 B: 读缓存 miss → 读 DB 读到旧值 → 回写缓存旧值
线程 A: 写 DB 新值
结果：缓存是旧值，DB 是新值 → 长时间不一致，直到 TTL
```

问题的根本：**删缓存和写库之间有一个"读窗口"**，只要期间有读请求，就会把旧值刷回缓存。

**评价**：**不推荐**。虽然直觉上"先清缓存再写库"看着合理，但并发下脏数据窗口最大、最持久（要等 TTL 或下一次写才能修复）。

**方案二：先写数据库，再删缓存（Cache-Aside 标准做法）**

```
1. UPDATE db
2. DEL cache
```

**并发下的理论问题**：

```
线程 A (读): 读缓存 miss → 读 DB 旧值 (还没回写)
线程 B (写): 写 DB 新值 → 删缓存
线程 A (读): 回写缓存旧值
结果：缓存是旧值
```

看起来也会脏读？但**这个场景要成立的前提非常苛刻**：读线程 A 必须"读到旧值"发生在写线程 B 的"写库"之前，同时"回写缓存"发生在 B 的"删缓存"之后——也就是**读操作必须比写操作慢**。而现实中读通常是"查缓存 miss → 查 DB → 回写"，DB 查询和回写加起来通常远快于一次写事务，**概率极低**。

**主要问题反而是"删缓存失败"**：写 DB 成功了，DEL cache 因为 Redis 抖动失败，缓存里就是旧值。解决方式：

1. 引入**重试机制**（MQ 兜底重试删除）；
2. 配合**兜底 TTL**（缓存过期后自然恢复一致）。

**评价**：**工程上首选方案**。并发脏读概率极低，删缓存失败可以通过重试和 TTL 兜底，实现简单，绝大多数业务够用。Facebook 的经典论文 *Scaling Memcache at Facebook* 采用的就是这个策略。

**方案三：延迟双删**

```
1. DEL cache
2. UPDATE db
3. sleep N ms
4. DEL cache   ← 再删一次
```

**核心动机**：解决方案一"读线程回写旧值"的脏数据窗口——即使中间有读线程把旧值刷回来了，**sleep 一段时间后再删一次**，把旧值清掉，缓存最多短暂不一致。

**关键参数是 sleep 时长 N**：

- 必须**大于一次读操作（读 DB + 回写缓存）的耗时**，才能保证第二次删除时脏数据已经被写进来；
- 也要**大于主从延迟**（如果读的是 MySQL 从库）；
- 但太长会阻塞写线程，影响写入 TPS；
- 生产实践通常 **500ms \~ 1s**，具体要压测。

**改进版**：把第二次删除**丢到 MQ 或延迟队列**里异步执行，写线程不阻塞：

```
1. DEL cache
2. UPDATE db
3. 发消息 → 延迟 1s 消费 → DEL cache
```

**评价**：**方案一的补丁**，能显著降低不一致概率但**不能根治**（sleep 时间无法精确匹配所有读耗时，极端场景仍有窗口）。适合对一致性要求较高、又不愿意上 binlog 订阅的中间态方案。

**方案四：订阅 binlog（最终一致性最优解）**

```
应用层: UPDATE db (只管写库，不管缓存)
Canal / Debezium: 订阅 MySQL binlog → 解析变更 → 发 MQ
消费者:接收变更 → DEL / UPDATE cache
```

**核心优势**：

1. **业务代码只写库**，缓存维护完全下沉到中间件，业务代码干净、不用关心一致性；
2. **binlog 是有序的、可回放的**，MQ 保证 at-least-once，缓存操作可以做幂等，天然容错；
3. **失败可重试**：消费失败 MQ 重投，直到删缓存成功；
4. **可扩展性强**：一份 binlog 可以同时驱动 Redis 缓存、ES 索引、数据仓库等多个下游。

**代价**：

1. **架构复杂**：多引入 Canal / Debezium + MQ + 消费者服务，运维成本高；
2. **延迟增加**：从 DB 写入到缓存更新有几十毫秒到几百毫秒的延迟，属于最终一致而非强一致；
3. **顺序性挑战**：同一个 key 的多次变更必须**串行处理**（MQ 按 key 分区），否则可能出现"旧变更覆盖新变更"；
4. **重复消费**：MQ 至少一次投递，删缓存操作必须幂等（DEL 天然幂等，UPDATE 就要小心）。

**评价**：**大厂标准解**。业务解耦、可靠性高、可扩展，缺点是复杂度高，适合体量大、对一致性有要求的核心系统（订单、商品、库存）。

---

**第三部分：四种方案对比表**

| 方案 | 并发脏读概率 | 修复窗口 | 实现复杂度 | 适用场景 |
|---|---|---|---|---|
| 先删缓存再写库 | 高 | 直到 TTL | 简单 | 不推荐 |
| 先写库再删缓存 | 极低 | 直到 TTL 或重试成功 | 简单 | 通用默认方案 |
| 延迟双删 | 低 | 秒级 | 中等 | 方案二不够用时的补丁 |
| 订阅 binlog | 极低 | 百毫秒级 | 高 | 核心业务、多下游同步 |

---

**第四部分：几个容易被追问的细节**

**1. 为什么普遍选"删缓存"而不是"更新缓存"？**

- 更新缓存需要**重新计算 value**（可能涉及多表 JOIN、复杂对象），代价大；
- 并发写下**两次更新的顺序无法保证**（B 后写的却先到缓存），会出现"覆盖倒挂"；
- 删缓存是**懒加载**，下次读时按需回源，避免了"写了但没人读"的无效计算。

只有**读远多于写、value 计算便宜**的场景才考虑主动更新缓存。

**2. 删缓存失败怎么办？**

三层兜底：

- **同步重试**（有限次数、指数退避）；
- **异步 MQ 重试**（写库成功后发消息，消费者删缓存，失败重投）；
- **TTL 兜底**（缓存都要设过期时间，比如 5\~30 分钟，即使前两层都失败也能自愈）。

**3. 强一致场景怎么办？**

四种方案都是**最终一致**，不是强一致。如果业务真的要求"写完立刻读到最新值"：

- 读**强制走 DB**，绕过缓存；
- 或者**加分布式锁**（读写都要拿锁，性能损失大）；
- 或者用 **2PC / 分布式事务**（几乎没人这么干，代价过大）。

**现实中的正确姿势是：接受最终一致，业务上做补偿**——用户看到旧数据几百毫秒无感，真正强一致需求交给数据库事务本身。

**4. 主从架构下的额外坑**

如果读走 MySQL 从库、写走主库，方案二的"读线程读旧值回写缓存"窗口会被**主从延迟放大**。解法：

- 关键路径读走主库；
- 或者用 binlog 订阅方案（binlog 本身就是从库同步的源，天然对齐）；
- 延迟双删的 sleep 时间要**大于主从延迟上限**。

---

**面试收尾一句话：**

四种方案的选型本质是**"一致性 vs 复杂度"的权衡**：先写库再删缓存是 80% 场景的最优解，简单可靠；延迟双删是它的补丁；binlog 订阅是核心业务的终极方案，把一致性维护下沉到中间件层。**没有绝对一致的缓存方案，只有"业务能容忍多长时间不一致"的选择**——记住这个前提，就不会在面试里被"如何做到强一致"这种伪命题带偏。
