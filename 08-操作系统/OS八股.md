## 一、用户态与内核态

### 1.1 为什么要分两级

CPU 有特权级（x86 的 Ring 0~3，Linux 只用 Ring 0 和 Ring 3）。**特权指令**（改页表基址寄存器、操作 IO 端口、关中断）只能在内核态执行，否则任何一个用户程序都能把别人内存占了、把网卡关了。

```
用户态 ──系统调用/异常/中断──▶ 内核态
        （int 0x80 走软中断、syscall 是专用快速指令，硬件自动切栈 + 切特权级）
```

> 通俗理解：用户态是"普通住户"，内核态是"物业+供电局"。你要改电表（IO、内存映射）不能自己动手，得提交工单（系统调用），物业来操作。工单本身是有成本的。

> [!info]- 陷入内核 — Trap into Kernel Mode
> **是什么**：指 CPU 从 Ring 3 掉进 Ring 0，是个**上位概念**；入口有**三条路**，不止系统调用一条。
> - **系统调用**：程序**主动**请求内核服务（`read` / `write` / `futex`），有明确意图和参数，也叫「陷阱（trap）」。
> - **异常**：指令执行**出错**触发的**同步**事件（缺页、除零、非法地址），是被动的。
> - **中断**：外部设备或时钟触发的**异步**事件（时钟中断、网卡收包），与当前指令无关。
> 所以关系是：**陷入内核 = 系统调用 ∪ 异常 ∪ 中断**。三条路都要付模式切换的代价，但只有系统调用是「我要求内核帮我做事」。
> **两个高频坑**：① 时钟中断每秒上百次、每次都陷入内核，但那只是**调度器在计时**，没有任何进程调过系统调用——**别把「陷入内核」一律读成「系统调用」**；② 反过来，**`vDSO` 让部分「系统调用」根本不陷入内核**（`gettimeofday` / `clock_gettime` 由内核把代码和数据页映射进用户空间，直接读共享内存就拿得到），所以「系统调用 API」和「真的陷入内核」也不等价。
> **面试落点**：Q5 追问「减少陷入内核的次数」，你能优化的其实只有**系统调用**那一部分——批量、复用、避免拷贝、vDSO；异常（缺页）只能靠锁页 / 大页 / 预读缓解；中断基本不可控（**网卡收包的中断两级处理见 [[网卡收包流程详解#一、为什么必须拆成两级]]**）——上面两句高频坑与这份优化清单的逐点展开见 [[OS-IO篇]]。

### 1.2 一次切换贵在哪

从用户态进内核要做：**保存用户态寄存器现场 → 切到内核栈 → 参数校验 → 执行 → 恢复现场 → 切回**。所以：

- 一次系统调用的开销 ≈ **1μs 量级**（比一次普通函数调用贵两三个数量级；spectre 缓解措施、**KPTI**（内核页表隔离，Meltdown 缓解，让每次陷入/返回多切一次页表）之后更贵）
- **上下文切换**比系统调用更贵：**进程切换要换页表**，随之带来 **TLB 失效 + CPU 缓存命中率下降**；**线程切换不换页表**（同进程内共用 CR3），只换栈和寄存器，所以比进程切换便宜一截（模式切换 vs 上下文切换的完整区分 → [[模式切换与上下文切换详解#二、三层区分（核心表）]]）

**这就是"为什么 IO 密集场景线程开太多反而变慢"的根因**：不是线程本身重，是**切换时丢缓存**重。这条因果能直接把 OS 和线程池那页串起来。

### 1.3 高频考法：系统调用一定慢吗

不一定慢，但**一定比普通函数调用贵**。所以高性能框架的核心优化思路之一就是**减少陷入内核的次数**：批量（`writev` 一次写多块）、复用（epoll 一次等待多个 fd）、避免拷贝（sendfile）、缓存（页缓存、连接池）。

**面试话术**："用户态到内核态的切换贵在三件事——保存恢复现场、换栈换页表、参数校验。所以你看 Netty、Kafka、Redis 这些高并发组件的优化方向基本都是同一个思路：**把多次陷入内核合并成一次**，或者干脆**让数据不用进用户态**，零拷贝就是后一种思路的极致。"

> ⚠ 上句「换栈换页表」不严谨：**模式切换只换栈**（用户栈 → 内核栈），**换页表是进程上下文切换才有的动作**（KPTI 是唯一例外，见 [[模式切换与上下文切换详解#七、精度问题：KPTI 之后，模式切换也要换页表了]]）。

> [!info]- 展开：「切内核栈」和「参数校验」到底在做什么
> **内核栈**：内核为**每个线程**单独分配的小栈（x86-64 上通常 16KB，32 位时代 8KB，**不能像用户栈那样自动增长**），进入内核后的函数调用、局部变量、返回地址都放这里。为什么不能继续用用户栈？① 用户栈内容**不可信**——栈指针可能被恶意设成非法值、栈上可能是攻击数据；② 内核栈上会放内核数据，不能让用户可读写；③ 用户栈可能没有足够映射，在内核里触发缺页很危险。所以进入内核第一件事就是**把栈指针切到本线程的内核栈**；系统调用入口把用户态寄存器（`rip`、标志位、用户栈指针等）压在栈顶形成 `pt_regs`，返回时从这里恢复。
> **参数校验**：内核**不信任用户态传进来的任何东西**。查五类：① 系统调用号是否越界（否则 `ENOSYS`）；② **用户指针**——是否落在用户空间（`access_ok`）、有没有指向内核地址（提权企图）、会不会越界；而且**不能直接解引用**，必须经 `copy_from_user` / `get_user` 访问，途中触发缺页由异常修复表安全返回 `EFAULT`；③ fd 是否存在、打开模式是否匹配（`EBADF`）；④ 数值与标志位是否合法（`EINVAL`，如 `writev` 的 iovec 数不超 `IOV_MAX`）；⑤ 权限（`EPERM` / `EACCES`）。还要防 **TOCTOU**（检查通过后、使用前，用户另一线程把内存改了）——所以参数通常**先拷进内核再用**。检查本身很快，但多次拷贝有成本——这正是 `writev` 这类批量调用能摊薄的部分。

## 二、进程 / 线程 / 协程

### 2.1 三层对比（必背）

| 维度   | 进程                    | 线程                | 协程                     |
| ---- | --------------------- | ----------------- | ---------------------- |
| 定位   | **资源分配**的最小单位         | **CPU 调度**的最小单位   | 用户态的轻量执行单元，由程序/运行时调度   |
| 地址空间 | 独立（各有页表）              | 同进程内共享（代码段、堆、全局区） | 同一线程内共享                |
| 私有部分 | —                     | 栈、程序计数器、寄存器组      | 自己的栈（可放堆上）、寄存器上下文      |
| 切换成本 | 最贵：换页表 + TLB 刷 + 缓存失效 | 中等：换栈和寄存器，不换页表    | 最轻：用户态保存少量上下文，**不进内核** |
| 谁调度  | 内核                    | 内核                | 用户态（运行时/库）             |
| 崩溃影响 | 进程互不影响                | 一个线程崩可能整进程完       | 取决于实现：Go 的 goroutine panic 默认整个进程崩；Java 虚拟线程的未捕获异常只死自己 |
| 数量级  | 几十~几百                 | 几百~几千             | 几万~百万                  |

**因果链要说出来**：线程之所以切换比进程便宜，**关键只有一条——同一个进程内的线程共用页表，切换时不需要切 CR3、不需要刷新 TLB，缓存命中也能部分保留**。其余（栈、寄存器）本来就要换。

**展开**：CR3 是页目录基址寄存器，CPU 靠它定位当前进程的页表。TLB（快表）是「虚拟地址→物理地址」映射的缓存，其条目都是"在当前 CR3 指向的页表下翻译出来的"——所以 x86 上**写 CR3 本身就触发 TLB 整条刷空**，换页表和刷 TLB 是同一件事的两面。

- **切 CR3**：换地址空间；线程共用一张页表，CR3 不动
- **刷 TLB**：映射没变，线程 1 留下的翻译条目线程 2 直接能用，一条都不用清
- **缓存部分保留**：Cache（L1/L2/L3）按物理地址存代码和数据本体。同进程内代码段、堆、全局区物理地址没变 → 缓存行直接接着用（热）；只有**线程私有栈、ThreadLocal、切换点附近的指令流**是冷的。进程切换则是地址空间全换，整个工作集的缓存全丢，代价最大

> 追问补充：线程被调度到**另一个 CPU 核**时，L1/L2 带不过去（只有 L3 共享）——这也是"部分保留"而非"完全保留"的一层原因；线程亲和性绑核优化正是为了守缓存温度。另注意：线程切换仍要走完整的用户态→内核态→调度→回用户态，省掉的只是地址空间侧的开销，不是切换本身。

**面试话术**："进程内线程共用一张页表，切线程时 CR3 不用动、TLB 一条不清，地址翻译成本整个归零；缓存也大部分是热的——代码、堆、全局数据都共享，上个线程留下的缓存下个线程接着用，只有栈和线程局部变量会冷。进程切换是地址空间全换、TLB 全刷、整个工作集缓存全丢，这就是线程比进程便宜的本质。"

### 2.2 线程共享了什么、Java 里怎么体现

- 共享：**堆（Java 对象都在堆上）**、方法区/元空间、文件描述符表
- 私有：虚拟机栈 + 本地栈、程序计数器、寄存器

这直接解释了 [[ThreadLocal 深度解析与内存泄露笔记#一、核心概念：ThreadLocal 是什么？|ThreadLocal]] 为什么存在——**因为堆是共享的，想让变量私有就得自己造一份 per-thread 的映射表**（`Thread.threadLocals`）。OS 层的"共享堆 + 私有栈"是 Java 并发一半问题的物理来源。

### 2.3 协程：把调度权抢回用户态

**为什么线程不够用**：线程是内核对象，创建要 `clone()` 系统调用、栈默认 **8MB**（`ulimit -s`，可改）、可运行的线程数受内核调度能力限制。要扛 10 万并发连接，用"一连接一线程"就是 10 万 × 8MB 栈 + 内核调度崩溃。（8MB 是**虚拟内存**，物理 RSS 按实际触页算——但虚拟地址空间和内核对象的开销是实打实的，仍绕不开。）

**协程的做法**：把「阻塞时让出、就绪时恢复」这个动作从内核搬到用户态——挂起的只是栈上几个字节的状态，切换不需要陷入内核。

**和 Java 的关系（这是最好的加分点）**：JDK 21 的**虚拟线程（Virtual Thread / Loom）**就是协程的工程化落地——

- 虚拟线程挂载在**载体线程（Carrier Thread，即 ForkJoinPool 里的平台线程）**上
- 遇到阻塞 IO 时，把栈帧**卸载（unmount）**成堆上的 continuation 对象，载体线程立刻去跑别的虚拟线程
- 所以「百万虚拟线程」不是百万内核线程，**内核看到的还是那几十个平台线程**

**话术**："虚拟线程本质就是 JVM 实现的协程：它解决的不是'并发不够'，而是'阻塞 IO 浪费内核线程'。以前一个请求一个线程，下游慢 200ms 这个内核线程就白等 200ms；虚拟线程在阻塞点把上下文挂起还回载体线程，等于把'等待'和'占着线程'解耦了。说白了它的本事就一条——**扛阻塞 IO**：任务里阻塞占比越高它越赚，纯计算的长任务塞进来，等于把它的特长废掉，占着载体白跑、还可能把别的 IO 任务饿死。另一个要提的坑是 pinning：JDK 21 里在 `synchronized` 块中阻塞、或者大量本地方法调用，会让虚拟线程想卸载却卸不掉，只能一直占着一个载体线程，**退化成一个占满内核线程的重量级线程**——**JDK 24 起经 JEP 491 已经消除了 synchronized 的 pinning**，只剩 Native 方法调用还会卡住载体。"

⚠ **别只说"协程更快"**——代价要分模型说清：**单线程事件循环型协程**（asyncio/Node）用「放弃多核并行 + 用户态协作调度」换轻量，一个协程跑死循环会把同线程所有协程饿死；**Java 虚拟线程是 M:N 调度**，能摊在多个载体线程上吃满多核，它的真实代价是**没有内核抢占时间片**——CPU 密集的虚拟线程会一直占着载体线程，直到自己主动阻塞才让出。

**代价的机制——协作式调度，不是抢占式**：内核调度平台线程是**抢占式**，时间片一到强行走人、线程配不配合都得下 CPU；虚拟线程的调度在用户态，是**协作式**——JVM 调度器**不会**主动打断正在跑的虚拟线程，只在它**自己走到卸载点**（阻塞 IO、`park`、`sleep`、队列 `take`…）时才挂起。纯算不阻塞的代码没有卸载点，就会一直占着载体线程；**内核抢占载体线程也没用**——抢下来再恢复，跑的仍是同一个虚拟线程（它压根没卸载），排队的其他虚拟线程照样上不来。

**后果不是"没用"，是"饿死别人"**：

- 全 JVM 只有**一个**共享的虚拟线程调度器，载体数默认 = CPU 核数（`jdk.virtualThreadScheduler.parallelism`）——**没法像平台线程池那样给 CPU 任务单独开一个池做隔离**
- 载体有限，被不阻塞的虚拟线程占满后，IO 虚拟线程**从等待中恢复时挂载不上载体**，表现是整个服务卡住
- 所以混合负载下它可能是**负收益**：`top` 里 CPU 是满的，请求却全卡住

**判据（别背成"CPU 密集不能用"）**：真正要避开的是「**长跑 + 全程不阻塞**」这个组合，不是"CPU 密集"两个词本身。短促的 CPU 突发算完就退出、很快把载体还回去，几乎没有危害；任务里只要有不可忽略的阻塞占比，虚拟线程就赚。

| 场景 | 适合虚拟线程吗 | 原因 |
|------|:---:|------|
| 阻塞式 IO（含下游 RPC / DB 调用） | ✅ | 主战场，阻塞点就是卸载点 |
| 短促 CPU 突发（算几毫秒就结束） | ✅ | 很快退出、归还载体 |
| CPU 与 IO 混合 | ✅ | 阻塞段照样卸载 |
| **长时间跑 + 全程不阻塞** | ❌ | 占着载体白跑，还可能饿死 IO 任务 |

> 通俗理解：内核调度平台线程像**车间班长强制轮岗**——时间一到，不管你干到哪，抢下工具换人干；虚拟线程像**员工自觉交接**——你必须自己喊一声"我卡住了，先让别人上"班长才换人。你闷头一直干、从不吭声，排队的同事就只能干等。

**收益别说得太绝**：CPU 密集任务跑虚拟线程，**失去的只是"拿它扛 IO 并发"这个特长**，不是全部收益——编程模型统一（不用写响应式）、内存占用小（栈在堆上、按需增长，不预留 8MB）、创建成本低、不用调池，这些照样还在。所以准确的说法是「**长跑不阻塞才是要避开的**」，而不是「CPU 密集就不能用」。

### ==2.4 进程有哪几种状态==

```
        调度            等待资源/事件        资源就绪/事件完成（唤醒）
  就绪 ─────▶ 运行 ─────────▶ 阻塞 ────────────────────▶ 就绪
    ▲          │
    └─时间片用完┘
               │ exit（终止）
               ▼
              僵尸 Z ──父进程 wait() 收尸──▶ 消亡
```

补充一句状态名单：教科书的**五态模型**是 **新建 → 就绪 → 运行 → 阻塞 → 终止**；上图为了讲流转省掉了「新建」，并把「终止」到「消亡」之间**父进程还没收尸**的那一段单独标成**僵尸 Z**——所以僵尸不是独立的第五态，而是**终止态的滞留**。

> [!info]- PCB 解析 — Process Control Block（进程控制块）
> **是什么**：内核里描述和管理一个进程的数据结构，常驻内核空间。进程在教材里的定义就是「程序 + 数据 + **PCB**」，Linux 里 PCB 的具体实现是 `struct task_struct`。
> **装什么**：PID 等标识、**处理机现场**（通用寄存器 / PC / 栈指针）、调度信息（状态位、优先级、nice、vruntime、时间片）、内存管理信息（页表基址、`mm_struct`）、打开的文件描述符表、信号与 IPC 资源、CPU 使用记账。
> **三个关键点**：① 教材原话是「**PCB 是进程存在的唯一标志**」——代码和数据可以共享、换出、甚至不在内存里，只要 PCB 还在，这个进程就还「存在」；PCB 一释放，进程才算真正消亡。② 上面那串状态位，本质都是 **PCB 里的字段**：**新建** = PCB 刚建好、还没挂进就绪队列；**僵尸 Z** = 地址空间和打开的文件都释放了，只剩 PCB 里的退出状态等父进程 `wait()` 读走；**消亡 X** = 父进程读完、PCB 也被释放。③ **进程切换 = 换 PCB**：把当前现场存进它自己的 PCB，再换上下一进程的 PCB、从里面恢复现场——所以 Q1 说的「保存 / 恢复寄存器」，保存到的就是 PCB。
> **两个加分延伸**：Linux 里进程和线程都是 `task_struct`，区别只在 `clone` 要不要共享地址空间，所以内核最小的调度单位其实是 PCB；Java 平台线程 ≈ 一个 `task_struct`（1:1），而**虚拟线程没有自己的 PCB**，只有挂到载体线程上时才临时借用。
> **面试坑**：僵尸进程为什么 `kill -9` 杀不掉？因为它已经没有可执行实体了，剩下的是内核里一张等父进程认领的「档案卡」，信号没有送达对象。

- **R**（可运行，含正在跑 + 在运行队列等）
- **S**（可中断睡眠，等事件，能被信号唤醒）
- **D**（**不可中断**睡眠，通常是在等磁盘/NFS IO，`kill -9` 都杀不掉；D 和 R 一样计入 Load，**一堆 D 会把 Load 顶起来**——但根因是它背后卡住的存储 IO，不是 D 本身）
- **T**（停止，调试或 SIGSTOP）、**Z**（僵尸：进程已退，父进程没 `wait()` 回收，只剩 PCB 里的退出状态；为什么杀不掉、怎么收 → [[wait 与僵尸进程回收详解#一、问题的起点：内核为什么不自己清理]]）、**X**（已退出、PCB 即将释放，即图中「消亡」，只存在一瞬间）

**排障高频**：`top` 里一堆 D 状态 → 查磁盘/存储/NFS；一堆 Z 状态 → 父进程代码有问题（没回收子进程）。

**为什么上面图（经典状态模型）和下面列表（Linux 状态位）长得不一样——两套体系对码表**：

| 图上（经典状态模型） | Linux（top/ps 里看到的） | 对码说明 |
|---------------|----------------------|------|
| 就绪 + 运行 | **R** | Linux 把「排队等 CPU」和「正在跑」合并成一个字母，`top` 里 R = 这两种的合集 |
| 阻塞 | **S**（可中断睡眠）/ **D**（不可中断睡眠） | 图上的大「阻塞」在 Linux 里拆成两种——区别只在**能不能被信号/kill 唤醒**；D 就是「杀不掉、只能等磁盘/NFS」的那个 |
| 停止（图上没画） | **T** | 不是正常流转态，是 SIGSTOP / 调试打断出来的，图里省略是约定俗成 |
| 僵尸 | **Z** | 两边都有：exit 后父进程没 `wait()` 收尸 |
| 消亡（图上终点） | **X**（已退出，PCB 释放） | `wait()` 收尸后进程彻底消失，X 只存在一瞬间 |

看图的新姿势：图里「阻塞 → 就绪」那条**唤醒**边，换成 Linux 就是 **D/S → R**——D 和 S 醒来后的去向完全相同，只是 D 在等待期间连信号都听不见，只能干等 I/O 完成。

## 三、CPU 调度与 Load Average

### 3.1 常见调度算法

| 算法 | 思路 | 缺陷 |
|------|------|------|
| FCFS 先来先服务 | 队列顺序执行 | **护航效应**：长作业后面所有短作业跟着等，平均等待时间长 |
| SJF 短作业优先 | 最短的先到 | 需要**预知运行时长**（做不到），且长作业**饥饿** |
| 高响应比优先 | 响应比 =（等待时间+预估运行时间）/ 预估运行时间，比值大的优先 | 折中方案：等越久响应比越高，缓解了饥饿，但仍要估时长 |
| 时间片轮转 RR | 每人跑一个时间片，公平 | 时间片太小 → 切换开销占比高；太大 → 退化成 FCFS |
| **多级反馈队列** | 多个优先级队列，跑不完降级、排队久升级 | Linux 实际采用的思路（CFS 又不同，见下） |

Linux 经典调度器是 **CFS（完全公平调度器）**：没有**固定**时间片，而是维护每个任务的**加权虚拟运行时间 `vruntime`**，红黑树按 vruntime 排序，永远挑最小的那个跑——**权重（nice 值）大的任务 vruntime 涨得慢，从而分到更多 CPU**。（加分项：Linux 6.6 起 CFS 已被 **EEVDF** 取代——同样基于虚拟时间，额外按「最早虚拟截止期」挑选，对延迟敏感任务更友好。）CFS 的完整机制（vruntime 折算公式、红黑树选最左、min granularity 托底、睡眠归一化、EEVDF）→ [[CFS 完全公平调度器详解]]

### 3.2 Load Average：它统计的不只是"在跑"的任务

Linux 的 Load 统计的是**处于 R 状态（运行+可运行）+ D 状态（不可中断睡眠）的任务数**，是按指数衰减算的 1/5/15 分钟移动平均。

- **判断标准**：Load 是否健康要看**核数**。4 核机器 Load=4 是满载，超过 4 就开始排队（过载），到 8 是重度堆积。粗略经验：**单核 Load 接近 0.7 就该告警**。
- **高频考法**：*"Load 很高但 CPU 使用率不高，说明什么？"*
  → 说明大量进程卡在 **D 状态等 IO**（磁盘慢、NFS 挂、大量缺页换页）。CPU 空转不是因为闲，是因为**没人 runnable，都在等**。这时候加 CPU 完全没用，要去看 `iostat`、`vmstat` 的 `bi/bo`、`wa`（IO wait）指标。

**话术**："Load 不是 CPU 指标，是**任务堆积**指标——它算的是在跑的加上排队等 CPU 的，再加上等 IO 醒不过来的。所以我判断机器压不压力大，先看 Load 除以核数，再看 `vmstat` 里 `r` 列和 `wa` 列：`r` 大是真缺 CPU，`wa` 大是存储瓶颈，这两种处理方向完全相反。"

## 四、内存管理

### ==4.1 为什么要有虚拟内存==

三个动机，按重要性排：

1. **隔离与安全**——每个进程一套自己的地址空间，A 进程访问 `0x1000` 碰不到 B 的，越界直接段错误。没有它，一个野指针就能搞崩整机。
2. **连续内存假象**——物理内存是碎的、多个进程交错分配、还会被换出。虚拟地址让程序以为自己有一大块连续空间，链接和加载才能简化。
3. **按需分配 + 可换出**——页不在物理内存也能"存在"（缺页时再要/再换回来），这才有了 swap、内存超配、`fork` 的写时复制。

**代价**：每次访存多一层地址翻译，慢。兜住这个代价的东西叫 TLB。

### 4.2 地址翻译链路（画图题）

```
执行访存指令，CPU 发出虚拟地址（逻辑地址）
  │  地址翻译由 MMU 完成；页内偏移不变，只翻译页号
  ▼
分段（Linux 已基本"平坦化"，几乎不做实际变换）
  ▼
分页：虚拟页号 ──▶ 查页表（在内存里，多级）──▶ 物理页框号 + 偏移 = 物理地址
        ▲
        └─ TLB（页表缓存，MMU 硬件里）命中就跳过查表，未命中才 walk 多级页表
```

**关键细节**：

- 页大小 x86_64 Linux 默认 **4KB**；页表设计成**多级**（x86 是 4/5 级），目的就是让每级表正好装进一页 4KB，稀疏映射时能省内存
- **TLB 命中是常态**，局部性原理决定的；进程切换刷 TLB（现代 CPU 有 **ASID/PCID** 标签——给 TLB 表项打上地址空间编号，避免切换时全刷）——这也是"进程切换比线程切换贵"的又一层原因
- 一次访存平均耗时：TLB 命中 ≈ 1 周期，TLB miss 走多级页表可能要**几十上百个周期**

> **通俗理解**：虚拟内存像公司的"工位编号"，物理内存是"实际的楼"。每个人只知道自己工牌号，查一次表才知道坐在哪栋楼哪层。前台手上那份"工牌→座位"便签（TLB）就是让绝大多数人不查台账直接找到座位。

### 4.3 用户态的堆：brk 与 mmap

| 方式 | 用途 | 特点 |
|------|------|------|
| `brk`/`sbrk` | **小块**分配 | 移动堆顶指针，连续一大片；**free 后不能立刻归还内核**（中间有空洞，要先整理） |
| `mmap` | **大块**分配（glibc 默认阈值 **128KB**，`MMAP_THRESHOLD`） | 在进程地址空间单独开一段 **VMA**（Virtual Memory Area，虚拟内存区域，描述一段连续虚拟地址的映射）；`munmap` 直接销毁，**立刻归还内核** |

**名字来历**：`brk` 不是缩写，就是 **break**（去元音的 Unix 老式起名，同 `tty` 一路），指的是 **program break（程序断点）**——数据段 + BSS 之后的"结束标记"地址，即俗称的**堆顶指针**（BSS = Block Started by Symbol，未初始化全局变量段）。`brk(addr)` = 把 break 设到绝对地址；`sbrk(增量)` 是它的相对版（s 一般释作 set），挪多少返旧值。堆伸缩 = 拖着这条 break 线上下移动。

**别把 glibc 行为背成 OS 定律——三层归属**：

| 层面 | 归属 |
|------|------|
| 堆的两种增长方式（原地延伸 vs 另起一块）、小块 free 不立刻还 OS | **通用机制**，任何 OS 都有 |
| `brk`/`sbrk`/`mmap` 这套系统调用 | **Unix/POSIX/Linux**（POSIX 已把 brk/sbrk 标 legacy；**Windows 无此调用**，对应物是 `VirtualAlloc`/`HeapAlloc`） |
| 128KB 阈值、空闲链表、`malloc_trim()` | **glibc 的实现细节**，musl/jemalloc/tcmalloc 策略各异、阈值可配 |

面试口径：先答通用层（两种方式），再报 Linux 的名字（brk/mmap），最后点一句"128KB 是 glibc 的数，换分配器不一样"——这半句是边界感加分点。

**考法**：*"为什么程序 free 了很多内存，`top` 里 RES 不降？"*
→ 因为小块内存走 brk，glibc 的 malloc 把释放的块留在自己的空闲链表里复用，堆顶不会轻易下移（存在"内存空洞"挡着）。真归还要么整理成功（`malloc_trim()`），要么这块本来就是 mmap 来的。（VIRT/RES/SHR 怎么看、M_TRIM_THRESHOLD 自动收缩、Java 侧落点 → [[进程内存指标与 glibc 分配详解]]）

**缺页异常（Page Fault）三种**：① 非法访问（段错误）；② **硬缺页**——页合法但不在物理内存，要读盘（swap in / mmap 首次访问读文件）；③ **软缺页**——页其实已经在内存，只是没建映射（`fork` 后的写时复制就是典型，不读盘）。软硬全场景、匿名页首触、minflt/majflt 怎么看 → [[缺页异常详解]]

### 4.4 页面置换算法

内存不够时把哪个页换出去：

| 算法 | 思路 | 现实 |
|------|------|------|
| OPT 最优 | 换掉**未来最久不用**的 | 要预知未来，理论下界，只用来证明别人更差 |
| **LRU** | 换掉**最久没被访问**的 | 效果好，但精确实现要在每次访问时移动链表节点，硬件/软件开销大 |
| FIFO | 换最先进来的 | 有 **Belady 异常**（内存变大缺页反而变多），不用。反例演算与"为什么只有它有" → [[Belady 异常与页面置换算法详解]]
| **Clock / 二次机会** | 环形链表 + 引用位，指到 1 就清 0 跳过 | LRU 的**工程近似**，开销 O(1) 摊还，操作系统实际多用这类 |
| LFU | 换掉访问次数最少的 | 有"历史高光赖着不走"问题，需老化机制 |

**LRU 的精确实现（也是算法题 TOPK 常用）**：**哈希表 + 双向链表**——哈希查 O(1) 定位节点，双向链表维护访问顺序、头插 + 淘汰尾。这题 `算法题/` 里有手撕版本，面试很可能"讲完原理就让写"。

**和你熟的东西挂上**：[[Caffeine详解#W-TinyLFU 淘汰算法]] 的 **W-TinyLFU**、[[Redis 过期删除策略和内存淘汰策略有什么区别？#内存淘汰策略|Redis 的 allkeys-lru]] 实际是**采样近似 LRU**（默认随机取 5 个 key 里最久未用的淘汰）——都是"精确 LRU 太贵，所以用近似"这同一条工程取舍。说出这个联系，比单纯背算法强得多。

### 4.5 内存不够会怎样：swap 与 OOM Killer

> 本页反复出现的内存名词（页缓存、slab、匿名页、MMU/TLB/CR3、PCID、VMA、mmap、大页、errno…）在 [[OS 名词解释速查]] 有「一句话 + 详细」两档定义，卡壳先查那页。

1. 先回收：页缓存、**slab**（内核对象缓存分配器，用于分配小对象；可回收的部分先收回）
2. 不够就 **swap 换出匿名页**（生产上很多中间件会主动 `swapoff`，因为换出后 RT 抖动巨大）
3. 还不行 → **OOM Killer** 挑一个进程杀掉，依据是 **`oom_score`**（跟内存占用量正相关，可用 `oom_score_adj` 调整保护级别）

**排障话术**："Java 进程被 OOM Killer 杀掉，`dmesg | grep -i oom` 能看到内核日志。这时要分两件事：**进程是被内核杀的（oom-kill）还是自己抛 OutOfMemoryError 的**——前者说明整个机器内存真没了（这时候 JVM 堆之外，比如堆外内存、大量线程栈、页缓存都可能是元凶），后者是 JVM 自己管不住堆。前者加 `-Xmx` 反而死得更快。"（呼应 [[DirectByteBuffer与堆外内存回收#为什么堆外内存不足会触发 Full GC？]]、[[StackOverflowError与OutOfMemoryError（虚拟机栈）#OutOfMemoryError（OOM）— 无法创建线程]]）

> [!info]- OOM Killer 深解 — 内核的"最后手段"：一条命保住整台机器
> 面试记四句：**什么时候触发、杀谁、怎么保护、怎么和 JVM 自己的 OOM 区分**。
>
> **① 什么时候触发：第三级台阶**。上面 1-2-3 就是一条求生线——页缓存丢完（几乎免费）、匿名页也换完（慢但能活）、回收也腾不出一页，内核放弃救所有人，开始杀人。触发条件是**物理内存 + swap 都被榨干**。
>
> **② 杀谁：按 oom_score 挑最大冤种**。规则朴素：**谁占的不可回收内存多谁先死**，分数看 `/proc/<pid>/oom_score`（0~1000），主要由**匿名内存**决定——页缓存占再多不扛分（随时可回收，不构成威胁），所以"占内存最多的最容易被杀"的精确版是"**占匿名内存最多的**"。被选中后内核发 **SIGKILL（9）**：不可捕获不可忽略，没有 shutdown hook、来不及 dump 堆，死得毫无动静，退出码 **137（128+9）**。
>
> **③ 怎么保护：`oom_score_adj`（-1000~+1000）**。-1000 免死金牌（内核直接跳过），+1000 优先送死，默认 0。实战几乎只用负值，且**方向常被搞反**：要给 **sshd、监控 agent** 这类"排障入口"设 -1000——否则机器快挂时你连登都登不上。K8s 里的 `OOMKilled` 本质同一套机制，只是范围缩到容器 cgroup 配额内。
>
> **④ 两种 OOM 不是一个东西**（面试最该答对的一点）：内核 oom-kill 是"整机 + swap 真没了、SIGKILL 无痛无栈、元凶常在堆外、加 -Xmx 死更快"；JVM 抛 OutOfMemoryError 是"堆内 GC 后仍不够撞了 -Xmx、有异常栈和 GC 日志、进程一般还活着、机器有余量时加 -Xmx 真管用"。对照表见下（标注内不放表格）。
>
> **"加 -Xmx 反而死得更快"**要会解释：机器已告急，调大堆只会让本进程的匿名内存更多、oom_score 更高，从"候选"升级成"首选"。正确反应是看 `dmesg` 那行的 **`anon-rss`**，确认是不是堆外/线程栈吃掉了内存，而不是急着调参数。
>
> **答题模板（可直接背）**："内存不够时内核分三步走：先回收页缓存和 slab 这类能丢的；不够就把匿名页换到 swap——生产上很多中间件宁可 `swapoff`，因为换出后 RT 抖动很大；还不行就 OOM Killer 按 oom_score 挑进程杀掉。排障时先看 `dmesg` 判断是内核杀的还是 JVM 抛 OutOfMemoryError，前者说明整机内存真没了、元凶常在堆外，这时候加 -Xmx 反而更快被杀。"
>
> ⚠ 按这个长度准备就够了；细节（水位线、直接回收、NUMA）面试基本不挖，追问再展开。swap/匿名页的名词层见 [[OS 名词解释速查#swap / 换入换出（Swap In / Swap Out）]]。

**两种 OOM 对照表**：

| | 内核 oom-kill | JVM 抛 OutOfMemoryError |
|---|---|---|
| 谁动的手 | 内核，直接 SIGKILL | JVM，堆分配失败 |
| 什么原因 | 整机内存 + swap 真没了 | 堆内 GC 后仍不够，撞了 -Xmx |
| 怎么发现 | `dmesg \| grep -i oom`，退出码 137 | 有异常栈和 GC 日志，进程一般还活着 |
| 元凶在哪 | **可能在堆外**：DirectByteBuffer、线程栈、别的进程 | 就在堆内：泄漏或配置不合理 |
| 加 -Xmx | **死得更快** | 机器有余量的话可能真管用 |

> 追问链深解（cgroup 配额与 cgroup OOM、dmesg 读法、退出码 137、swapoff / swap 区操作、防 OOMKilled checklist）见 [[OOM Killer 与容器内存详解]]。

## 五、死锁

### 5.1 四个必要条件（缺一不可）

| 条件 | 含义 |
|------|------|
| **互斥** | 资源一次只能被一个线程持有（锁的本质属性，去不掉） |
| **请求并持有** | 拿到 A 之后再去申请 B |
| **不可剥夺** | 已持有的资源不能被别人强抢，只能自己释放 |
| **循环等待** | 形成首尾相接的等待环：T1→T2→T1 |

### 5.2 预防 / 避免 / 检测 / 忽略

- **预防**（破坏任一条件，静态策略）：
 - 破坏「请求并持有」→ **一次性申请全部资源**（或 tryLock 拿不到就全放开）
 - 破坏「循环等待」→ **按固定顺序加锁**（最常用、最实用，工程里就是"全局锁序"）
 - 破坏「不可剥夺」→ 申请新锁失败时**主动释放已有锁**
 - 破坏「互斥」→ 不现实，资源本身要求互斥；但可以用**更细粒度/无锁结构**（CAS、读写分离）绕开
- **避免**（动态）：**银行家算法**——分配前先假设分配，看系统是否还存在**安全序列**，没有就不分配。教科书爱考，生产几乎没人用（要预知最大资源需求）。
- **检测**：允许死锁发生，定期用**资源分配图 / 等待图**找环（Java 里 `jstack`、`ThreadMXBean.findDeadlockedThreads()` 就是这个思路）。
- **忽略**：**Linux 和 Java 实际都选这个**——宁可让你出现死锁再排查，也不为不可能发生的场景付检测成本。

**这句话很值钱**："死锁的四种处理策略里，操作系统和 JVM 其实都没真正防——它们选择了**检测/忽略**。所以死锁在生产上是个**编码规范问题**而不是内核问题，我能做的是保证加锁顺序全局一致。"

### 5.3 Java 现场排查（应届生能说出这套就赢）

1. `top -H -p <pid>` 找到高 CPU 的线程号 → `printf '%x\n' <tid>` 转十六进制
2. `jstack <pid> > dump.txt`，搜 **`deadlock`** 关键字（jstack 自己会检测并打印 "Found one Java-level deadlock"）
3. 看两个线程各持有哪把锁、各等哪把锁 → 定位代码里的加锁顺序不一致
4. 修复：**统一加锁顺序**，或改 `ReentrantLock.tryLock(timeout)` 拿不到就退避重来

### 5.4 死锁 vs 活锁 vs 饥饿

- **死锁**：都在等对方，谁都不动
- **活锁**：都在动（互相谦让重试），但**状态没进展**，典型是两个 CAS 冲突后同时退避又同时重试撞上
- **饥饿**：单个线程一直抢不到资源（优先级低、或 `synchronized` 不公平 + 写锁把读线程饿住）

## 六、IPC 进程间通信

| 方式                     | 传输方向             | 速度            | 关键点                                                                                                  |
| ---------------------- | ---------------- | ------------- | ---------------------------------------------------------------------------------------------------- |
| **管道 pipe**            | 半双工、仅限**亲缘**进程   | 中             | 内核环形缓冲区，默认 64KB（16 页，fcntl F_SETPIPE_SZ 可调，上限 sysctl `fs/pipe-max-size` 默认 1MB）；读端关闭写会收到 **SIGPIPE** |
| **命名管道 FIFO**          | 半双工，**无亲缘关系也可用** | 中             | 在文件系统里有个名字，本质还是内核缓冲                                                                                  |
| **信号 signal**          | 异步通知             | 快但信息量极小       | 只能传"哪个信号"，不传数据；**SIGKILL(9)/SIGSTOP(19) 不能被捕获或忽略**，SIGTERM(15) 可以（所以优雅停机要用 15 不要用 9）                 |
| **信号量 semaphore**      | ——               | ——            | **它不传数据，是同步计数器**（P/V 原语），常配共享内存用                                                                     |
| **共享内存 shm**           | 双向               | **最快**        | 一次映射、之后**零拷贝**，不走内核；缺点是没有同步能力，必须自己配信号量/锁                                                             |
| **消息队列**               | 双向               | 较慢            | 有格式、按类型取，但有大小限制和拷贝开销                                                                                 |
| **Socket / Unix 域套接字** | 双向               | 网络栈慢，Unix 域较快 | **唯一能跨机**的方式                                                                                         |

**为什么管道只给亲缘进程用（因果）**：**「亲缘进程」不是 OS 正式术语，指靠 `fork` 繁衍出血缘关系的进程（父子/祖孙/兄弟）**。管道只能用在这一类进程之间，根因在 **fd**——管道的本质是内核里一块环形缓冲区，但用户态要通过**读端/写端两个 fd** 才能访问它，而 **fd 是进程私有的**，只存在于创建管道那个进程自己的 fd 表里。别的进程想拿到这对 fd，唯一途径是 `fork` 时**继承**父进程的 fd 表副本，于是父子进程持有同一对 fd、指向同一块内核 buffer，管道才通。因果链：**fd 私有 → 只能靠 fork 继承 → 只有亲缘进程拿得到同一对 fd → 管道天生限定亲缘进程**。无亲缘的进程即使知道对方有管道也拿不到 fd（fd 不能凭空跨越进程传递，除非走 Unix 域套接字的 `SCM_RIGHTS` 显式传 fd——那已绕开"亲缘"这条路）。对比之下 **FIFO 补上的正是这个入口**：给它一个文件系统里的**名字**，任何进程 `open` 就能拿到 fd，所以无亲缘也能用。一句话记：**管道靠"继承"，FIFO / Unix 域套接字靠"名字/路径"**——分水岭就在能不能靠继承拿到 fd。

**命名管道 FIFO 的机制与坑**：FIFO 一句话就是——**给管道起一个文件系统里的名字**。`mkfifo /tmp/myfifo` 后用 `ls -l` 看，它的文件类型是 `p`（pipe），任何进程（不管有没有亲缘）只要 `open("/tmp/myfifo")` 就能拿到 fd，于是双方**通过"名字"汇聚到同一块内核缓冲区**——它把管道「靠 fork 继承 fd」换成了「靠路径 open 拿 fd」。⚠ **最大的坑：FIFO ≠ 普通文件**——名字虽然挂在文件系统上，但它只是个**入口（inode）**，`ls -l` 显示 **size 恒为 0**，写进去的数据**全在内核缓冲区、不落盘**，读走就没了，无进程打开时数据不保留。面试爱问这个，别以为写 FIFO 等于写文件。第二个高频点是 **`open` 的阻塞语义**——默认（阻塞）方式 `open` 时，**只读端会阻塞到有写端 open、只写端会阻塞到有读端 open**（加 `O_NONBLOCK` 才不阻塞），这是 FIFO 特有的"打开即同步点"。其余性质和匿名管道完全一样：半双工、字节流无消息边界、有 64KB 内核缓冲做背压（写 ≤ `PIPE_BUF` 4KB 才保证原子性）。**典型用途**：毫无亲缘关系的两个进程/脚本之间搭管道，shell 里常拿 `mkfifo` 当"命名中转站"串数据。

> [!abstract]- 信号 Signal（软中断通知）
> **定义**：进程间**异步通知**机制，只传「信号编号」、不传数据——本质是内核或另一个进程给目标进程「戳一下」，业务数据得靠管道/共享内存另送。
> **三种处置**：① 默认动作（内核预设，多数是终止进程）② 忽略（注册 `SIG_IGN`）③ 捕获（注册 handler 自行处理）。
> **SIGKILL(9) / SIGSTOP(19) 为何不可捕获、不可忽略、不可阻塞**：它们是内核强留的**两个「管理员兜底手段」**——否则进程把信号全忽略就能赖着不死、彻底无法管理。`9` 无条件杀死、`19` 无条件暂停（`SIGCONT(18)` 恢复）。
> **优雅停机为什么用 15 不用 9**：`SIGTERM(15)` 是「**请求**你退出」，进程可捕获 → 先关连接、刷盘、存状态再自己退；`SIGKILL(9)` 是内核**直接撕**，**没有 shutdown hook、来不及 dump 堆**。故容器/K8s 停服默认发 15、超时才补发 9。
> ⚠ **面试坑**：`kill` 命令名有误导——它只是「**发信号**」，`kill -9` 不是「更强地 kill」。退出码 **137 = 128+9**（被 SIGKILL 杀，见 [[#4.5 内存不够会怎样：swap 与 OOM Killer]] OOM Killer）、**143 = 128+15**（被 SIGTERM 杀）。Java 的 `Runtime.addShutdownHook` 能被 15 触发、被 9 无效。

**为什么共享内存最快（因果）**：其他方式都要「A 进程用户态 → 内核缓冲区 → B 进程用户态」两次拷贝 + 多次系统调用；共享内存是**两个进程把同一段物理页映射进各自的虚拟地址空间**，写完对方直接可见——数据一次都不动。这正是 [[#七、I/O 模型与零拷贝]] 里"零拷贝"的同一种思想：**消除用户态和内核态之间的无谓搬运**。

**挂到 Java**：进程间共享内存 ≈ `MappedByteBuffer`（mmap 文件）、`Unsafe`；Redis 持久化 RDB 的 fork 能便宜是因为 [[#4.2 地址翻译链路（画图题）]] 的写时复制。

## 七、I/O 模型与零拷贝

### 7.1 五种 I/O 模型（POSIX）

一次网络读分两阶段：**① 等数据到内核缓冲区（wait for data）→ ② 把数据从内核拷到用户空间（copy）**。**前四种模型之间的差别全在①**（等待策略不同）；**② 是同步/异步的分界**——前四种都逃不掉（发起线程同步拷到用户缓冲），只有 **AIO** 例外（内核后台代拷、完成后通知）。

```
阻塞 IO      ：①等  ②拷            （线程全挂住）
非阻塞 IO    ：①轮询轮询轮询 ②拷    （CPU 白烧）
IO 多路复用  ：①一个线程等多个 fd，就绪后 ②拷   （select/poll/epoll）
信号驱动 IO  ：①内核就绪时发 SIGIO 通知 ②拷
异步 IO AIO  ：①②全由内核做完，做完通知我    （唯一真异步）
```

⚠ **必须说准的一句**：前四种都是**同步 I/O**——因为「数据从内核拷到用户态」这一步是**发起 I/O 的那个线程在自己的 CPU 时间上**同步完成的。**只有 AIO 是异步**。这个点说反是硬伤。

### 7.2 IO 多路复用：select → poll → epoll

| 维度       | select                                     | poll        | epoll                                        |
| -------- | ------------------------------------------ | ----------- | -------------------------------------------- |
| fd 上限    | **1024**（`FD_SETSIZE`，要改得重编译）              | 无理论上限（链表）   | 无上限（受系统 `file-max`、`ulimit -n` 约束）           |
| fd 集合传递  | **每次调用都把整个 fd 集合用户↔内核整体拷一遍**（拷贝量 ∝ 总 fd 数） | 同样全量拷贝      | `epoll_ctl` **注册一次**，`epoll_wait` 不重复拷贝      |
| 内核找就绪 fd | **线性遍历 O(n)**                              | 线性遍历 O(n)   | 内核维护**就绪双向链表**，`epoll_wait` 直接返回它，**O(就绪数)** |
| 数据结构     | 三个 bitmap（读/写/异常）                          | `pollfd` 数组 | **红黑树**存全量 fd + **就绪链表**存已就绪 fd              |

**select 的位图设计：它到底怎么"知道"你要监听谁**（说清这个才叫真懂 select）

- **编码方式**：`fd_set` 是 1024 位的位图，**下标 = fd 号，这一位的值 = 要不要监听它**。所以"要监听谁"是靠"哪几位是 1"表达的——`FD_SET(3, &readfds)` 就是把第 3 位置 1
- **第一个参数 `nfds` 是划边界**：位图永远是 1024 位那么长，内核不知道你填到了哪一位，所以必须传 **最大 fd + 1**
- **两个坑都从这儿来**：
  - **传小了** → 后面的 fd 内核根本不检查，**静默漏掉**，怎么等都等不到（很典型的事故）
  - **传对了也慢** → 就算只监听 fd 1000 这一个，`nfds` 也得传 1001，内核要从第 0 位一路扫到第 1000 位
- **代价模型**：**select 的开销 ∝ 最大 fd 号，不是 ∝ 监听的个数**。十个监控项散在 fd 0~1000 之间、和十个挤在连续低位，内核扫描量能差一百倍；这也是「连接反复开关、fd 号越涨越大」的程序用 select 会越来越慢的原因
- ⚠ **别拿"一万个连接"举例**：select 连一万个都放不下（位图只有 1024 位），"大量连接"是 **poll / epoll** 的场景。select 的问题是**密而全**，不是多

**为什么它非得逐位扫**：因为信息被编码进了**位置**，解码的唯一办法就是遍历——内核手上是一张位图，想找出哪些位是 1，除了从头看到尾没有别的办法；它甚至没法只检查你关心的那几个（"0"既是"不监听"，也和"空位"长得一样）。

**epoll 是怎么"知道"的**：`epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event)` —— **fd 就是一个普通整数，直接当参数传进去**，内核把它当节点插进红黑树。这是真正的**集合**，不是编码：

| | select | epoll |
|------|--------|-------|
| 怎么表达"监听谁" | 编码进**位图位置** | fd 作为**参数直接给** |
| 要不要边界参数 | 要（`nfds`，传错就漏） | 不要 |
| 受 fd 编号大小影响吗 | **受**（代价 ∝ 最大 fd 号） | 不受 |
| 怎么找就绪的 | 逐位扫 | 看**就绪链表** |

> 通俗理解：select 像**在花名册上打钩**——册子只有 1024 格，你只能勾、不能写名字，想知道勾了谁只能**从头翻到尾**；epoll 像**把名字直接登记进成员簿**——你是谁就写谁，不用占位置，也就不用翻整本。

**epoll 为什么快（三层因果，别只说"没有上限"）**：

1. **注册与等待分离**：fd 用红黑树常驻内核，不用每次传一遍——省掉「拷贝 + 重建集合」的固定开销；
2. **回调机制取代轮询**：网卡数据到达 → 软中断 → 回调把该 fd 挂进就绪链表，`epoll_wait` 只返回**真正就绪的**那几个；10 万连接里只有 100 个活跃时，代价只和 100 成正比，而 select 是 10 万；
3. 所以**活跃连接占比低时 epoll 优势巨大**（C10K 场景）；如果几乎所有 fd 都活跃，epoll 反而不比 select 快多少——红黑树插入删除是有成本的。

**水平触发 LT vs 边缘触发 ET**：

- **LT（默认）**：只要缓冲区还有数据就一直通知。**编程简单**，不必一次读完
- **ET**：只在**状态变化时**通知一次。**必须循环读到 `EAGAIN`**（errno，表示「此刻没数据了、稍后再试」），且必须配非阻塞 fd（否则读到没数据时会把线程卡死）。**省通知次数、更快**，Nginx 用 ET

**话术**："select 到 epoll 的改进，本质是三件事：**fd 列表不用每次从用户态拷进内核**、**内核不用线性扫全部 fd 才知道谁就绪了**、**没有 1024 个的坑**。实现上是红黑树存注册表、就绪链表存结果，靠中断回调把 fd 塞进就绪链表。这也解释了一个反直觉的点：如果你的连接基本都很活跃，epoll 相对 select 就没那么大优势，它赢在'大量连接、少数活跃'这种真实互联网场景。"（Redis 侧细节见 [[Redis IO多路复用详解#底层：select / epoll 对比]]；底层机制的完整拆解见 [[select 与 epoll 机制详解]]）

### 7.3 零拷贝

**要解决的问题**：经典「读文件发网络」= `read()` + `write()`，数据要 **硬盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡**，其中**内核 ↔ 用户态这两次拷贝纯属浪费**——数据用户态根本不看。

| 方案                                  | 系统调用 | 模式切换（用户⇄内核） | 数据拷贝                                                                         |
| ----------------------------------- | ---- | ----------- | ---------------------------------------------------------------------------- |
| 传统 `read + write`                   | 2    | 4           | **4 次**：2 次 DMA + 2 次 CPU                                                    |
| `mmap + write`                      | 2    | 4           | **3 次**：2 次 DMA + 1 次 CPU（省掉"页缓存→用户缓冲区"那次 CPU 拷贝，write 时直接从页缓存拷进 socket 缓冲区） |
| `sendfile`                          | 1    | 2           | **3 次**：2 次 DMA + 1 次 CPU（数据完全不进用户态，剩下的 CPU 拷贝是"页缓存→socket 缓冲区"）             |
| `sendfile` + **scatter-gather DMA** | 1    | 2           | **2 次**：2 次 DMA + **0 次 CPU**（最优；socket 缓冲区只放描述符，网卡直接从页缓存 DMA 拼包）            |

> ⚠ **术语精度**：这列严格说是**模式切换（用户态 ⇄ 内核态）**，不是「上下文切换」——一次系统调用 = **一进一出 2 次模式切换**，只换栈、**不换页表、不刷 TLB**（见 [[模式切换与上下文切换详解#二、三层区分（核心表）]]）。零拷贝的经典图多沿用了"上下文切换"这个习惯说法，本页统一按**模式切换**口径。`read+write` 的 4 次 = 两次 syscall 各一进一出；`sendfile` 的 2 次 = 合成一次 syscall，一进一出。

- **DMA 拷贝**：网卡/磁盘控制器自己搬，不占 CPU
- **CPU 拷贝**：内核软件复制，才是真正要省的那部分
- **为什么 `sendfile` 还剩 1 次 CPU**：传统网卡的 DMA **只肯从 socket 缓冲区搬数据**，所以页缓存里的数据必须先 CPU 拷贝进 socket 缓冲区——这次省不掉，根因是"网卡只从 socket 缓冲区取货"
- **scatter-gather**：DMA 能把「分散在多处的数据」拼成一个报文发送，所以 socket 缓冲区里只放描述符、不放数据体，就彻底不用 CPU 拷贝（**正好消掉上面那次**——网卡按描述符直接从页缓存 gather 拼包）

**工程落点（面试必提）**：

- **Kafka 高吞吐的四板斧**里就有零拷贝（`FileChannel.transferTo` → sendfile）+ 顺序写 + 页缓存 + 批量压缩
- **Netty** 的 `FileRegion`、以及它把"ByteBuf 合并"用**逻辑组合代替物理拷贝**（`CompositeByteBuf`）——这是用户态版的零拷贝思想
- **Nginx** 静态文件走 sendfile
- **Redis** 的 `fork + 写时复制`（[[Redis fork 全量同步优化案例#要点提炼]]）是**内存层面**的避免拷贝，同一个思想家族

**话术**："零拷贝省的不是'硬盘到内存'，那是必须的 DMA；它省的是**CPU 拷贝**——像'读文件发网络'这种场景用户态压根不看数据：mmap+write 省掉'内核→用户'那一次，sendfile 更彻底，数据根本不进用户态、两次 CPU 拷贝全省。Kafka 快就快在这儿：`sendfile` 配 scatter-gather DMA，让数据从页缓存直接被网卡搬走，CPU 一次都不用碰，这才扛得住它那种吞吐。"

**面试常问的三条**：
1. **`available` 和 `free` 的区别** → free 是彻底没用过的内存，available = free + 可回收的 cache。看到"内存只剩 200MB"先别慌，看 available。
2. **`kill -9` 杀不掉进程怎么办** → 先看 `ps` 状态列：**D 状态**是在等 IO，信号要等它从内核态回来才处理，只能查 IO（磁盘/网络存储）或重启；**Z 状态**是已经死了等父进程收尸，`kill -9` 无意义，该修的是父进程没 `wait()`。
3. **`%sy` 比 `%us` 高说明什么** → 内核态开销过大，通常是**上下文切换太频繁、系统调用太密、或大量软中断**，优化方向是批量、复用、减少锁竞争。（呼应 [[解释为何CPU不是redis的瓶颈以及单线程为何还这么快？#二、 既然用单线程，Redis 凭什么这么快？]]）

### 附：文件权限与 chmod（ls -l 十字符拆解）

**`ls -l` 输出的前 10 个字符**：

```
-rwxr-xr--  1 user group 1024 Jan 1 12:00 myfile
↑└─┬─┘└─┬─┘└─┬─┘
│  │    │    └── 第 8-10 位：其他用户（others）的权限
│  │    └─────── 第 5-7 位：属组用户（group）的权限
│  └──────────── 第 2-4 位：文件所有者（owner/user）的权限
└─────────────── 第 1 位：**文件类型**（`-` 普通文件 / `d` 目录 / `l` 软链接 / `c` 字符设备 / `b` 块设备 / `s` socket / `p` 管道）
```

⚠ **第 1 位是文件类型，`chmod` 改不了它**——`chmod` 只管后 9 位（三段 `rwx`）。

**r / w / x 的数值来源**：三个位置各占 1 个二进制位，按 `rwx` 顺序正好是 `100 / 010 / 001`：

| 字符 | 含义 | 二进制 | 十进制 |
|------|------|--------|--------|
| `r` | 可读（read） | 100 | **4** |
| `w` | 可写（write） | 010 | **2** |
| `x` | 可执行（execute） | 001 | **1** |
| `-` | 无权限 | 000 | 0 |

所以一段权限就是三个数的和：`rwx` = 4+2+1 = **7**，`r-x` = 4+0+1 = **5**，`r--` = **4**，`rw-` = **6**。**三段按「所有者 / 组 / 其他」拼起来**，就是那个三位八进制数。

**数字法 vs 符号法**：

```bash
chmod 400 myfile          # 数字法：所有者只读，组和其他无权限（r--------）
chmod u=r,go= myfile      # 符号法，完全等价（u=user, g=group, o=others, a=all）
chmod u+x script.sh       # 给所有者加执行权限
chmod -R 755 dir          # 递归改目录及其内容
```

**常见数字对应场景**：

| 数字 | 展开 | 典型用途 |
|------|------|---------|
| `400` | `r--------` | **只读、仅自己可读**（证书私钥、`~/.ssh/id_rsa.pub` 等） |
| `600` | `rw-------` | 私密文件（**SSH 私钥 `id_rsa` 必须是 600，否则 ssh 直接拒绝使用**） |
| `644` | `rw-r--r--` | 普通文件：自己可读写，别人只读 |
| `700` | `rwx------` | 私有目录 / 脚本，仅自己可进 |
| `755` | `rwxr-xr-x` | 可执行文件、目录（**目录最常用**） |
| `777` | `rwxrwxrwx` | 所有人可读写执行（**生产别用**，只配临时排障） |

**文件 vs 目录，权限含义完全不同**（面试爱考）：

| 权限位 | 对文件 | 对目录 |
|--------|--------|--------|
| `r` | 读取文件内容 | **列出目录里的文件名**（`ls`） |
| `w` | 修改文件内容 | **在目录内新建 / 删除文件** |
| `x` | 执行该文件 | **进入该目录**（`cd`）/ 访问其中文件的元信息 |

⚠ 经典坑：**目录只有 `r` 没有 `x`** 时，`ls` 能列出文件名，但看不到任何详情（大小、权限、属主全是 `?`），也打不开里面的文件——因为访问文件的元信息也要目录的 `x`。

**其它相关命令**：

| 命令 | 作用 |
|------|------|
| `chown user:group file` | 改属主 / 属组（`-R` 递归） |
| `chgrp group file` | 只改属组 |
| `umask` | **新建文件时"要扣掉"的权限**：默认 022 → 新建文件 644、新建目录 755 |
| `ls -ld dir` | 看目录**本身**的权限（不加 `-d` 看到的是目录里的内容） |

**特殊权限位（多出来的那一位，了解即可）**：

| 位 | 出现在 | 含义 |
|----|--------|------|
| SUID（`s`，4xxx） | 文件的 owner 位 | 执行时**临时获得文件属主的权限**（`/usr/bin/passwd` 靠它改 `/etc/shadow`） |
| SGID（`s`，2xxx） | 文件的 group 位 | 执行时获得属组权限；**放在目录上**表示"新建文件继承目录的属组" |
| Sticky Bit（`t`，1xxx） | 目录的 others 位 | 目录内**只有文件属主才能删自己的文件**（`/tmp` 就是 `1777`） |

**回到面试**：[[针对实习的追问]] 里问「Shell 脚本里为什么要用 `chmod`」——完整答法是：脚本下载/拷进来时通常没有执行位（常见是 `644`），要 `chmod +x`（给三类用户都加 `x`）才能用 `./script.sh` 跑起来；而 `chmod` 改的只是后 9 个权限位，第 1 位的文件类型它管不着。

### 附二：几个易混的 Linux 概念（信号 / mtime / ulimit / malloc 底层）

出自一道选择题（正确答案 **A**）。

**原题**：对于 Linux 说法，下列说法正确的是（）
A. 线性访问内存非法时，当前线程会进入信号处理函数
B. 用 `mv` 命令移动文件时，文件的修改时间会发生变化
C. `ulimit -c` 设置的是函数调用栈的大小
D. `malloc` 函数是操作系统最底层申请内存的接口

**A（对，但措辞不严谨）—— 非法内存访问 → SIGSEGV**

- 访问非法线性地址时，MMU 触发**硬件异常**（本质是一次缺页异常），内核判定该访问非法后，向**出错的线程**发送信号 **SIGSEGV**（段错误）；部分场景是 SIGBUS。
- 进程若**注册了该信号的处理函数**，内核就转去执行它；**没注册则按默认动作终止进程**（可能生成 core dump）。
- ⚠ 严格说法要加条件：**"该信号可捕获、且已安装处理函数"**时才进处理函数。展开见 [[缺页异常详解]]。

**B（错）—— `mv` 在同一文件系统内不改 mtime**

- 同一文件系统内 `mv`：只改**目录项**的指向，文件的 inode 和内容都没动 → **mtime 不变**。
- 跨文件系统：`mv` 退化成"复制 + 删除源"，复制时通常会保留时间戳（视工具 / 选项而定）。
- 补充：`mv` 改变的是**目录的 mtime**（目录项变了），不是文件本身的。

**C（错）—— `ulimit -c` 是 core dump 大小，不是栈**

| 选项 | 管什么 |
|------|-------|
| `ulimit -c` | **core dump 文件大小上限**（`0` = 不生成） |
| `ulimit -s` | **栈大小**（进程栈 / 函数调用栈） |
| `ulimit -n` | 能打开的最大 fd 数（默认 1024 的由来，见 [[select 与 epoll 机制详解#二、先搞清 fd：后面全靠它]]） |
| `ulimit -u` | 最大进程 / 线程数 |
| `ulimit -a` | 全部列出 |

**D（错）—— `malloc` 是 glibc 库函数，底层是 `brk` / `mmap` 系统调用**

- `malloc` 是 **C 运行库（glibc）里的库函数**，不是系统调用，更不是"内核最底层接口"。
- 它管理**进程的堆**，需要更多内存时通过系统调用向内核申请：
  - **`brk/sbrk`**：调整堆顶（program break）——小块分配走这条；
  - **`mmap`**：映射一块匿名内存——大块分配（默认 ≥ 128 KB，阈值 `M_MMAP_THRESHOLD`）走这条，`free` 时直接 `munmap` 还给内核。
- 所以"内核提供的接口"是 **`brk` / `mmap` 这些系统调用**，`malloc` 是它们之上的**用户态封装**（还自己管空闲链表、tcache 等）。详见 [[进程内存指标与 glibc 分配详解]]。

**顺带：core dump 是什么**

- 进程异常终止时，系统保存的一份**进程当时状态的快照**，含内存内容、寄存器、线程状态、调用栈等。
- 用途是**事后调试**（`gdb ./prog core`）定位崩溃原因——它不是"函数调用栈文件"，而是进程多个内存区域的转储。
- 是否生成、生成到哪、多大，受系统配置与 `ulimit -c` 影响。

## 高频追问与话术

### Q1：进程切换和线程切换到底差在哪一步？
> "就一处关键差别：**进程切换要换页表**（改 CR3），换了页表就意味着 TLB 大部分要失效、CPU 里的缓存数据也不再可信，等于把工作集清空重来；线程在同一进程内**共用页表**，只需要保存恢复栈和寄存器。所以贵不是贵在那几条指令，是贵在**切换之后缓存和 TLB 的重建**。现代 CPU 有 PCID/ASID 给 TLB 表项打上进程标签，能缓解全刷，这也是为什么这个差距在近些年的机器上没有教科书说的那么夸张。"

### Q2：为什么 32 位系统最多用 4G 内存？64 位呢？
> "地址总线决定物理上限，但**进程能直接寻址的范围由虚拟地址位数决定**：32 位 = 2^32 = 4GB，而且内核还要占走 1GB（默认 3G/1G 划分），用户空间只有 3G，这也是 JVM 在 32 位机器上堆开不大的原因。64 位理论上限极大，但真实硬件只用 48 位虚拟地址（开 5 级页表 LA57 后到 57 位），而且**Linux 的默认栈大小、glibc malloc 的 arena 数会随核数增长**，这也是 64 位机器上'线程一多内存就爆'的原因之一。"

### Q3：fork 之后父子进程内存是复制了一份吗？
> "没有，**写时复制（COW）**。fork 只复制页表，父子共享同一批物理页并全部标成只读；任何一方**写**时才触发缺页异常，内核此时才真复制那一页。所以 fork 的开销是**页表**开销，不是数据量开销。Redis 的 BGSAVE 就是靠这个：fork 出子进程去写 RDB，期间父进程正常服务，只有被改到的页才产生复制——代价是**内存最坏情况会翻倍**，也是为什么大内存 Redis 实例 fork 时会卡顿、写密集时可能 OOM。"（→ [[Redis fork 全量同步优化案例#要点提炼]]）

### Q4：mmap 和 read/write 有什么区别，什么时候该用 mmap？
> "mmap 把文件直接映射进虚拟地址空间，访问它就像访问内存，缺页时由内核把对应页读进来。省掉了「内核缓冲区 → 用户缓冲区」那次 CPU 拷贝，所以小文件反复随机访问很划算。但三个前提：**页缓存本身已经很快，mmap 不一定更快**；访问模式是随机跳的话会疯狂触发缺页，比顺序 read 还慢；以及 **mmap 期间文件被截断或删除会拿到 SIGBUS**。所以大文件顺序传输用 sendfile（连用户态都不用进），需要随机访问、想让内核管刷盘节奏的用 mmap，比如 ES 的索引文件。"

### Q5：一个程序崩溃，可能的原因有哪些？
> "按类型分四类：**① 非法内存访问**（野指针、数组越界、栈溢出 → SIGSEGV / StackOverflowError）；**② 主动 abort**（断言失败、`raise`）；**③ 资源耗尽**（内存 → OOM Killer、文件描述符用尽 → `Too many open files`、线程数超限、pid 用完）；**④ 被信号杀**（`kill -9`、运维脚本、容器 OOM）。Java 里还要加一条：**退出码 137 = 128+9，基本就是被 SIGKILL 杀的**，容器环境里十有八九是 cgroup 内存超限，不是 JVM 自己的堆问题——这时候看 `-Xmx` 没用，得看容器 limit。"

### Q6：为什么进程比线程"重"？
> "三处：**创建**要新建页表、地址空间、文件描述符表（虽然 fork 用了 COW 但结构还是要建）；**切换**要换页表并连带刷 TLB；**通信**没法直接共享变量，得走 IPC 拷贝。共享内存之所以是例外，就是把'重'的部分预先做掉一次，之后大家直接读写同一批物理页。"

### Q7：中断和异常有什么区别？
> "**中断是外部来的、和当前指令无关**（时钟中断、网卡收包完成），叫异步事件；**异常是当前指令执行时出问题的**（缺页、除零、系统调用），叫同步事件。系统调用是**故意触发的异常**（软中断 / `syscall` 指令），这也是它被称为"陷入内核"的原因。网卡收包走的是**硬中断 + 软中断（softirq）**两级：硬中断里只做最少的事（确认 + 通知），耗时的协议栈处理丢给软中断，避免长时间关中断影响系统响应——这也是 `%si` 这个指标的由来。"

### Q8：说说你对「并发」和「并行」的理解，用 OS 的话讲
> "并发是**一个 CPU 时间片内交替推进多个任务**，靠调度切换制造"同时在跑"的假象；并行是**多个核真的同一时刻各跑一条指令流**。OS 层的意义在于：单核下加线程不会变快，只会增加切换开销；**只有超过一个核，线程数增加才带来真实吞吐**。所以判断线程该开多少，第一看核数，第二看任务是 CPU 密集还是 IO 密集——IO 密集时线程大部分时间在阻塞态、不占核，才允许开更多。"（→ [[线程池#九、为什么 IO 密集型任务线程数可以多些]]）
