# N+1 查询问题（ORM 经典陷阱）

## 一句话定义

> 执行 **1 条查询获取 N 条主数据**，再**循环 N 次查询获取每条数据的关联数据**，共执行 **N+1 条 SQL** — 这就是 N+1 查询问题。

---

## 问题场景

假设有两个表：`user`（用户）和 `order`（订单），一个用户有多个订单。

**业务需求**：列出所有用户及其订单列表。

### ❌ 错误写法（N+1 问题）

```java
// 1 条 SQL：查询所有用户
List<User> users = userMapper.selectList(null);

// 循环中 N 条 SQL：每个用户查一次订单
for (User user : users) {
    // 每次都执行一条 SQL
    List<Order> orders = orderMapper.selectByUserId(user.getId());
    user.setOrders(orders);
}
```

**执行 SQL 数量**：`1（查用户） + N（查订单） = N+1 条`

| 用户数 | SQL 条数 | 耗时（估算） |
|--------|---------|------------|
| 10     | 11      | ~10ms     |
| 100    | 101     | ~100ms    |
| 10000  | 10001   | ~10s+     |

数据量越大，性能越差！

---

## 为什么会发生？

### 1. ORM 懒加载（Lazy Loading）

```java
// User 实体中配置懒加载
@OneToMany(fetch = FetchType.LAZY)
private List<Order> orders;

// 遍历时触发 N 次查询
users.forEach(user -> user.getOrders().size()); // 第一次访问时触发 SQL
```

> [!info] 为什么默认懒加载？
> JPA 对 `@OneToMany` / `@ManyToMany` 默认 `FetchType.LAZY`：查 User 时**不**关联查子表，第一次访问 `user.getOrders()` 才发 SQL。循环里访问 N 个用户的订单 → 追加 N 条 SQL，这就是 N+1 的直接来源。
> MyBatis 对应机制：`lazyLoadingEnabled=true` + `<collection select="...">` 嵌套查询（见 [[MyBatis ResultMap 关联映射详解]]）。

### 2. 循环中查询数据库

```java
// 常见于 MyBatis <collection> 标签 + 循环查询
for (Long id : ids) {
    Order order = orderMapper.selectById(id); // 每次都查 DB
}
```

---

## ✅ 解决方案

### 方案一：JOIN 一次查（推荐）

```sql
SELECT u.*, o.*
FROM user u
LEFT JOIN `order` o ON u.id = o.user_id
WHERE u.id IN (1, 2, 3, ...);
```

```java
// MyBatis-Plus 多表联查
@Select("SELECT u.*, o.* FROM user u LEFT JOIN `order` o ON u.id = o.user_id WHERE u.id IN ${ids}")
List<UserOrderVO> selectUserWithOrders(@Param("ids") String ids);
```

> [!warning] 注意 `IN ${ids}` 是字符串拼接，存在 SQL 注入风险
> 生产环境应改用 `<foreach>` 标签拼接参数（见 [[MyBatis详解]]），或让 MP 封装的分页/自定义 SQL 处理。

**结果**：1 条 SQL 搞定，无论多少用户。

### 方案二：IN 查询 + 内存组装（最常用）

```java
// 第 1 步：查所有用户（1 条 SQL）
List<User> users = userMapper.selectList(null);
List<Long> userIds = users.stream().map(User::getId).toList();

// 第 2 步：批量查订单（1 条 SQL）
List<Order> orders = orderMapper.selectByUserIds(userIds);  // WHERE user_id IN (...)

// 第 3 步：内存中组装（0 条 SQL）
Map<Long, List<Order>> orderMap = orders.stream()
    .collect(Collectors.groupingBy(Order::getUserId));

users.forEach(user -> user.setOrders(orderMap.getOrDefault(user.getId(), List.of())));
```

**结果**：**2 条 SQL**，不再 N+1。

### 方案三：MyBatis-Plus 批量查询

```java
// 使用 MyBatis-Plus 的 batch 方法
List<User> users = userService.list();
List<Order> orders = orderService.lambdaQuery()
    .in(Order::getUserId, users.stream().map(User::getId).toList())
    .list();
// 内存组装同上
```

本质同方案二（IN 查询 + 内存组装），只是换成了 MP 的 LambdaQuery 写法。

### 方案四：MyBatis `<collection>` — 嵌套查询 vs 嵌套结果

两个 `resultMap` 长得很像，区别全在 `<collection>` 上：

| 写法 | `<collection>` 特征 | 查询次数 |
|------|--------------------|---------|
| 嵌套查询（反例） | 带 `select` 属性，指向另一个查询 | N + 1 次 ❌ |
| 嵌套结果（正例） | 直接内联子表字段映射，无 `select` | 1 次 JOIN ✅ |

```xml
<!-- ❌ 反例：嵌套查询（select 属性），N+1 的典型写法 -->
<resultMap id="userOrderMap" type="User">
    <id property="id" column="id"/>
    <!-- select：每个 User 额外执行一次 selectOrdersByUserId -->
    <!-- column：把当前行的 id 作为参数传给子查询 -->
    <collection property="orders" ofType="Order"
                select="selectOrdersByUserId"
                column="id">
        <!-- 注意：这里是嵌套查询，仍然是 N+1！ -->
    </collection>
</resultMap>

<!-- ✅ 正确做法：使用 JOIN + 嵌套结果（resultMap id 必须唯一，不能与上面重复） -->
<resultMap id="userOrderJoinMap" type="User">
    <id property="id" column="id"/>
    <collection property="orders" ofType="Order">
        <id property="id" column="order_id"/>
        <result property="amount" column="amount"/>
    </collection>
</resultMap>

<select id="selectUserWithOrders" resultMap="userOrderJoinMap">
    SELECT u.*, o.id AS order_id, o.amount
    FROM user u
    LEFT JOIN `order` o ON u.id = o.user_id
</select>
```

## JPA / Hibernate 场景：fetch join 与 @EntityGraph

> [!abstract] JPA 方案 — Java Persistence API（Java 持久层 API）
> 面试话术中常提的 `@EntityGraph` / `fetch join` 是 JPA（Hibernate）侧的解决方案。MyBatis 没有对应注解，只能用 JOIN SQL / 嵌套结果实现（见 [[MyBatis ResultMap 关联映射详解]]）。

### 方案五：JPQL fetch join（1 条 SQL）

```java
// 一次 JOIN 查出 User + orders，杜绝懒加载触发
@Query("select u from User u join fetch u.orders")
List<User> findAllWithOrders();
```

### 方案六：@EntityGraph（声明式指定抓取路径）

```java
@EntityGraph(attributePaths = "orders")   // 等价于 fetch join，但不用写 JPQL
@Query("select u from User u")
List<User> findAllWithOrders();
```

**对比**：

| 方式 | 写法 | 说明 |
|------|------|------|
| `join fetch` | JPQL 中手写 | 本质生成 JOIN SQL，1 条查询 |
| `@EntityGraph` | 注解声明属性路径 | 同上，免手写 JPQL，可叠加 `@Query` |
| `FetchType.EAGER` | 实体注解 | ⚠ 全局急加载，任何查 User 都带出 orders，**不推荐** |

> [!warning] fetch join 两个坑
> 1. **不能分页**：`join fetch` 一对多时，Hibernate 会拒绝 `setFirstResult/setMaxResults`（返回行被 JOIN 放大，分页结果错误）
> 2. **重复对象**：JOIN 一对多会产生重复主表行，Hibernate 已自动去重（内存去重，量大会占内存；MyBatis 靠 `<id>` 去重）

## 常见坑点

### 1. IN 列表过长

IN 参数过多（如几千个 id）会导致 SQL 超长、索引失效、数据库解析变慢。建议**分批**：每批 500~1000 个 id，内存中合并结果。

### 2. 空 IN 列表

`userIds` 为空时拼接出 `WHERE user_id IN ()` 直接 SQL 语法错误。查空集时应**短路返回**，不再执行第 2 步查询。

```java
if (userIds.isEmpty()) {
    return;  // 或直接返回空结果
}
```

### 3. 懒加载 + 事务关闭 = LazyInitializationException

```java
// ❌ 事务提交后访问懒加载属性 → 抛异常（JPA 场景高频面试点）
@Transactional
public List<User> list() {
    List<User> users = userRepository.findAll();  // 事务内查询
    return users;                                  // 事务提交，Session 关闭
}
// 之后调用 user.getOrders() → LazyInitializationException
```

解决：事务内提前访问 / `join fetch` / 改用 DTO 投影。这也是为什么很多项目干脆禁用懒加载或统一用 DTO。

### 4. 只查部分字段也用 JOIN *

方案一、五都按 `*` 全字段查出，只展示两个字段时可只 SELECT 需要的列，减少网络传输和内存占用（见 [[MyBatis复杂SQL性能优化经验]]）。

## 面试话术

> **面试官**：ORM 的 N+1 查询问题是什么？怎么解决？

**回答要点**：
1. **定义**：1 条主查询 + N 条关联查询，共 N+1 条 SQL
2. **原因**：ORM 懒加载机制 / 循环中查数据库
3. **危害**：数据量大时性能急剧下降，1000 条数据就是 1001 条 SQL
4. **解决方案**：
   - JOIN 一次查出（1 条 SQL）
   - IN 批量查询 + 内存组装（2 条 SQL）
   - JPA 用 `@EntityGraph` / `fetch join` 声明式解决
   - MyBatis 用嵌套结果 `<collection>` 代替嵌套查询
5. **加分点**（主动抛出，展示深度）：
   - 区分 MyBatis 的嵌套查询 vs 嵌套结果：`select` 属性触发 N+1，JOIN 合并行只查 1 次
   - 提到 IN 分批、空 IN 短路等边界处理
   - 提到懒加载出事务的 `LazyInitializationException`

**一句话总结**：N+1 的本质是**查询次数随数据量线性增长**，优化方向永远是**把 N+1 条 SQL 压成 1~2 条**。
