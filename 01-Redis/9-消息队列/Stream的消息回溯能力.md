## Stream 的消息回溯能力（XRANGE）

### List 为什么做不到？

List 的元素通过下标（index）访问，比如 `LINDEX list 0`、`LRANGE list 0 10`。但作为消息队列时，有两个致命问题：

1. **消费过的消息会被删除**（`LPOP`/`RPOP`），一旦 pop 出去就没了，不可能回溯
2. **即使不删，也分不清哪些是新消息、哪些是历史消息**——List 没有"消息 ID"这个概念，只有下标，而下标在并发生产消费时是不断变化的

```
# List 的困境
LPUSH queue msgA msgB msgC
RPOP queue  → 消费 msgC（删掉了）
RPOP queue  → 消费 msgB（删掉了）
# msgA 和 msgB 去哪了？没了，查不到
```

### Stream 是怎么做到的？

Stream 的每条消息有一个**全局唯一、单调递增的消息 ID**，格式为 `时间戳-序号`：

```
1526919030474-0  第一条消息
1526919030474-1  第二条消息
1526919030532-0  第三条消息
...
```

`XRANGE` 就是按照这个 ID 范围来查的：

```
# 查所有消息（从头到尾）
XRANGE mystream - +

# 查某个时间范围内的消息
XRANGE mystream 1526919030474-0 1526919030532-0

# 查指定数量
XRANGE mystream - + COUNT 10
```

### 关键对比

| | List | Stream |
|---|---|---|
| **消息标识** | 只有下标，pop 后下标变 | 每个消息有**唯一固定 ID** |
| **消费后数据** | 默认删除（LPOP/RPOP） | 数据默认**保留在内存中** |
| **回溯方式** | 无法回溯 | `XRANGE` + ID 范围，想查哪段查哪段 |
| **典型场景** | 一次性的任务队列 | 需要重放、审计、延迟处理的场景 |

### 什么时候用得上回溯？

- **新消费者加入**：想从头开始处理所有历史消息 → `XRANGE stream - +`
- **排查问题**：怀疑某条消息处理错了，查它当时的内容 → `XRANGE stream <时间戳-序号> <时间戳-序号>`
- **重新处理**：某段时间的数据需要重算 → 查到那段消息重新消费

# 🎯 面试题 · 2026-07-28 16:30（基于《Stream的消息回溯能力》）

> [!question]- 面试题 1：Redis List 为什么不支持消息回溯，与 Stream 相比有哪些本质区别？
> Redis List 之所以无法像 Stream 那样实现消息回溯，核心在于它的数据结构和访问机制存在两个致命缺陷。首先是消费行为的问题，List 通常配合 LPOP 或 RPOP 命令使用，这些操作在消费消息的同时会直接删除数据，一旦消息被弹出，物理上就不存在了，自然无法回头再查。其次是标识问题，List 依赖下标来定位元素，但在高并发场景下，生产者和消费者同时操作会导致下标频繁变动，即使不删除消息，也无法区分哪些是新到的、哪些是历史遗留的，缺乏稳定的消息唯一标识，所以无法精准定位到某条特定消息进行重放或审计。相比之下，Stream 拥有固定的消息 ID 且消费后默认保留数据，从而解决了这两个问题。

>

> [!question]- 面试题 3：在实际业务中，Stream 的消息回溯能力主要应用在哪些场景？
> 消息回溯能力在实际业务中有三个典型应用场景。第一是新消费者加入时，如果希望从头开始处理所有积压的历史消息，可以直接查询整个流的数据。第二是在排查线上问题时，如果怀疑某条特定消息处理逻辑有误，可以通过该消息的时间戳或 ID 范围快速定位并检查当时的原始内容。第三是数据需要重新计算的场景，比如某个时间段的统计逻辑变更，可以回溯查到那段时间产生的消息，重新投递给消费者进行二次处理，保证数据的一致性。
