### **给 `(user_id, create_time DESC)` 建联合索引即可把查询压到毫秒级,再配合覆盖索引消除回表、ICP 做二次过滤,是这类"等值 + 排序 + 取 TopN"场景的标准解法。**

面试口述的话,我会按这个逻辑讲:

---

**先分析为什么慢。** 8000 万行、`user_id` 等值 + `create_time` 排序 + `LIMIT 10`,慢到 3 秒基本可以断定是走了**单列索引 `user_id`** 或者干脆全表扫。假设 `user_id` 上有普通索引,那流程是:先通过索引拿到该用户所有订单的主键(可能几万几十万条),回表捞出所有行,再在内存里按 `create_time` 排序,最后取 10 条。回表 + filesort 是慢的根源。

---

**第一步:联合索引顺序。**

建 `idx_user_time (user_id, create_time)`。顺序不能反,原则是**等值列在前、排序/范围列在后**。原因是 B+ 树的有序性——`user_id` 相等的记录在索引里天然按 `create_time` 有序排列,查询就变成:

1. 定位到 `user_id=?` 对应的索引区间（B+ 树跳转到该用户记录所在的叶子节点区域）
2. 根据排序方向，从区间**末尾**（`create_time` 最大端）开始扫 10 条就结束

完全没有 filesort,也没有额外的排序开销。

至于要不要写成 `create_time DESC`,MySQL 8.0 之前索引都是升序存储的,反向扫描优化器会自动做,写不写 DESC 无所谓;8.0 之后支持真正的降序索引,如果几乎所有查询都是倒序取新数据,可以显式建 `(user_id ASC, create_time DESC)`,让降序扫描更高效。

---

**第二步:覆盖索引消除回表。**

上面那个索引虽然排序解决了,但 `SELECT *` 还是要**回表**——用主键去聚簇索引里拿完整行。10 条回表看似不多,但如果 `SELECT *` 里字段很多、行很大,或者 LIMIT 变成 1000,回表就是随机 I/O,还是会拖慢。

优化有两条路:

**方式一:改 SQL,别用 `SELECT *`**,只查真正需要的列。比如列表页只需要 `order_id, amount, status, create_time`,那就建覆盖索引 `(user_id, create_time, order_id, amount, status)`,查询直接在二级索引上跑完,`Extra` 里会看到 `Using index`,零回表。

**方式二:延迟关联(deferred join)**,尤其适合深分页:

```sql
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders 
      WHERE user_id=? ORDER BY create_time DESC LIMIT 10) t
ON o.id = t.id;
```

子查询在二级索引上完成过滤和排序,只拿 10 个主键,外层再回表 10 次。相比在外层直接 `LIMIT 100000, 10` 那种,效率天差地别。

---

**第三步:ICP(Index Condition Pushdown,索引下推)。**

这个考察点面试官很爱问。ICP 是 MySQL 5.6 引入的优化,作用是**把 WHERE 里能用索引列判断的条件,下推到存储引擎层,在扫索引时就过滤掉,不用回表再判断**。

放到这道题的扩展场景:如果 SQL 变成

```sql
WHERE user_id=? AND status=1 ORDER BY create_time DESC LIMIT 10
```

索引是 `(user_id, create_time, status)`。没有 ICP 时,server 层要先回表拿到 `status` 再过滤;有 ICP 时,`status` 判断直接下推到 InnoDB,在遍历二级索引时就做掉,不满足的记录压根不回表。可以在 `EXPLAIN` 的 `Extra` 里看到 `Using index condition`。

需要注意:**ICP 只能推能用二级索引列表达的条件**,而且 `status` 放在索引末尾即可参与下推;如果条件是函数、类型隐式转换,或者字段根本不在索引里,就用不上 ICP,只能回表后由 server 层过滤。

---

**最后串一下完整的落地方案**,让面试官看到工程闭环:

1. **索引**:`CREATE INDEX idx_user_ctime ON orders(user_id, create_time DESC)`,如果字段固定,进一步做覆盖索引。
2. **SQL**:去掉 `SELECT *`,只查必要字段;深分页用延迟关联或者游标(基于 `create_time < ?` 的 keyset pagination)代替 `LIMIT offset, n`。
3. **验证**:`EXPLAIN` 看到 `type=ref`、`key=idx_user_ctime`、`Extra=Using index` 或 `Using index condition`,`rows` 估算接近 LIMIT 数量就 OK。
4. **兜底**:8000 万行如果单表还在膨胀,考虑按 `user_id` 分库分表或按时间做冷热分离,索引只是延缓单表瓶颈,不是无限解药。
5. **注意点**:联合索引会占空间和拖慢写入,`orders` 是高写入表,索引数量要克制;`create_time` 如果精度到毫秒且分布均匀,选择性很好,联合索引效率会非常高。

这套讲下来能覆盖"索引原理 + SQL 改写 + 执行计划验证 + 架构演进"四个层次,基本就是这道题的满分答案。
