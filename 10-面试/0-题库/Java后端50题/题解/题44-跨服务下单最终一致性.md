### **跨服务下单要的是最终一致，不是强一致：2PC 性能与可用性代价太大基本不用；TCC 适合资金类、要求中间态可见可补偿的场景；Saga 适合长流程、每步都有逆向操作；**本地消息表是绝大多数业务的最优解**——把「业务落库」和「消息落库」放进同一个本地事务，再靠异步投递 + 重试 + 消费幂等达成最终一致，成本最低、可控性最好。**

下面按面试口述节奏展开，先讲清楚四种方案的本质差异，再落到下单场景。

---

**第一部分：先明确"一致性"在这个场景里指什么**

下单要跨三个服务：订单服务建单、库存服务扣减、积分服务加积分。它们各有独立数据库，你不可能用一个本地事务包住——这就是分布式事务要解决的问题。

但要注意，"保证一致性"有两种强度：

- **强一致**：任何时刻三个库的数据都必须同时正确。代价是必须同步协调、必须阻塞，性能和可用性都会打折
- **最终一致**：允许中间有窗口期（比如订单已建、库存在几秒后才扣），但最终一定收敛到正确状态

下单这种业务，绝大多数公司选的是最终一致。因为"几秒钟内库存还没扣"用户感知不到，但"下单接口要 500ms 变 2 秒"用户立刻能感知。

---

**第二部分：四种方案的对比**

**2PC（两阶段提交）**

准备阶段：协调者让所有参与者执行事务但不提交，各自锁住资源；提交阶段：全部 ok 就一起提交，有一个失败就全部回滚。

问题很致命：一是**同步阻塞**，准备阶段所有参与者都占着资源锁，协调者一挂参与者全卡死；二是**协调者单点**；三是阶段之间崩溃会有数据不一致，需要人工介入。所以互联网业务基本不用 2PC，它更多出现在传统企业的 XA 场景。

**TCC（Try-Confirm-Cancel）**

Try 阶段做资源预留（比如冻结库存而不是直接扣），Confirm 真正扣减，Cancel 释放预留。

本质是**把"锁"从数据库层搬到了业务层**，所以没有 2PC 的数据库锁阻塞问题，性能好很多。代价是**业务改造成本极高**：每个参与方都要写三个方法，还要处理"空回滚""悬挂""幂等"三个经典问题——Try 没到、Cancel 先到了怎么办（空回滚）；Cancel 重复调用怎么办（幂等）；Try 超时后被取消、然后又到了怎么办（悬挂）。

适合：资金、支付、库存这种**强业务约束、中间态必须可见可补偿**的场景。

**Saga**

把长流程拆成一串本地事务，每个都有对应的补偿操作，某步失败就反向依次补偿。

优点是适合**长流程、跨多个服务**（比如旅行预订：机票 + 酒店 + 租车）；缺点是**没有隔离性**，中间状态对外可见（订单已建但库存还没扣，别人能看到这个订单），而且补偿逻辑不一定总能写出来（比如"已经发出的短信"无法撤回）。

**本地消息表（最常用）**

做法是在业务库里加一张消息表，把"改业务数据"和"插一条待发送消息"放进**同一个本地事务**：

```sql
BEGIN;
UPDATE t_stock SET qty = qty - 1 WHERE sku_id = ? AND qty >= 1;
INSERT INTO t_local_msg (msg_id, topic, payload, status)
VALUES (?, 'order-created', ?, 'PENDING');
COMMIT;
```

然后一个定时任务扫 `status = PENDING` 的记录去投递 MQ，投递成功后改成 SENT，失败就重试（配最大重试次数 + 告警）。

它的好处是**不依赖 MQ 的可靠性**——MQ 挂了也没关系，消息还在表里，恢复后接着投；缺点是**有延迟**（靠定时扫，秒级到分钟级），且**多一次表写**。

---

**第三部分：落地下单场景的具体设计**

我会这么做：

**主链路用本地消息表**。订单服务建单 + 写消息表在一个事务里；库存服务和积分服务作为消费者，各自消费、各自幂等（用 orderId 做唯一键），失败重试，重试耗尽进死信队列人工处理。

**为什么不选 TCC**：库存扣减确实适合 TCC（冻结 → 扣减），但积分加不加其实不影响下单成败，没必要为它付出 TCC 的改造成本。**按业务重要性分级**——核心的库存可以做预扣（本质是 TCC 的 Try），非核心的积分走异步消息就够了。

**关键补两个东西**：

1. **对账兜底**。每天跑一次对账任务，比对"订单表里有但库存没扣"的差异单，自动补偿或告警。最终一致靠消息，但消息可能丢、消费可能永久失败，对账是最后一道网
2. **补偿接口**。给运营一个"手动重推消息"的入口，出了问题能立刻修，不用等开发

---

**第四部分：面试时容易被追问的点**

**"消息表和业务表在同一个库吗"**：是。这正是它成立的前提——同一个本地事务才能保证"业务成功则消息一定在"。如果分库了就用不了，得换事务消息。

**"定时扫表会不会扫到重复的"**：会。所以要靠消费端幂等（orderId 唯一）来消化，这也是为什么最终一致方案里"幂等"是不可省的。

**"和 RocketMQ 事务消息比呢"**：本质相同（都是"本地事务 + 可靠投递"），事务消息把消息表换成了 broker 的半消息，省了扫表但绑死了 MQ。项目用 RocketMQ 就用事务消息，要通用性就用本地消息表。

**"为什么不用 Seata AT"**：AT 模式靠全局锁 + undo 日志，本质还是接近 2PC 的同步协调，高并发下全局锁会成为瓶颈；而且它对 SQL 有要求（不支持复杂 SQL）。中小流量可以用，大促场景不合适。
