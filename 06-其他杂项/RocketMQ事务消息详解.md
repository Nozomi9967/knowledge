# RocketMQ 事务消息 — 保证「本地事务 + 消息发送」原子性

## 一句话定义

> **事务消息**是 RocketMQ 提供的**分布式最终一致性**方案：通过 **half 消息（半消息）** + **本地事务** + **回查（checkLocalTransaction）** 三个机制，解决「先发消息还是先写库」的原子性问题——让**本地事务成功 ⟺ 消息发送成功**，二者要么都发生，要么都不发生。

---

## 要解决的问题：为什么需要事务消息

经典场景：**支付成功 → 通知订单服务更新状态**。

如果只是「发消息 + 写库」两步，无论顺序如何都有漏洞：

| 顺序       | 失败场景             | 后果                       |
| -------- | ---------------- | ------------------------ |
| 先写库，再发消息 | 写库成功，发消息时网络超时/宕机 | 支付日志有了，订单服务永远不知道 → 两边不一致 |
| 先发消息，再写库 | 消息发出，本地事务回滚      | 消费者处理了一个**不存在的订单** → 脏数据 |

> 本质矛盾：消息发送（网络操作）和本地事务（数据库操作）是两个独立资源，无法用同一个 ACID 事务包住。事务消息用「两阶段 + 回查」绕开了这个矛盾。

---

## 核心原理：half 消息的两阶段流程

### 第一阶段：发半消息 + 执行本地事务

```
Producer                     Broker                       Consumer
   │                           │                             │
   ├─ ① 发送 half 消息 ──────► │                             │
   │         （投递到 RMQ_SYS_TRANS_HALF_TOPIC，消费者不可见）  │
   │ ◄────── 确认收到 ────────┤                             │
   │                           │                             │
   ├─ ② 执行本地事务            │                             │
   │    （如：INSERT pay_log）  │                             │
   │                           │                             │
   ├─ ③a commit ─────────────► │─ ④ 消息转入真实 topic ────► │─ 消费
   ├─ ③b rollback ───────────► │─ 消息直接丢弃                 │
```

- **① 发送 half 消息**：Producer 先发一条半消息，Broker 把它投递到专门的 `RMQ_SYS_TRANS_HALF_TOPIC`，此时**对消费者不可见**（也查不到）
- **② 执行本地事务**：Producer 执行真正的业务事务（如插入支付日志）
- **③ 提交/回滚**：本地事务成功 → 返回 **commit**，Broker 把消息从 half topic 转移（复制）到真实 topic，消费者可见；本地事务失败 → 返回 **rollback**，消息直接丢弃

### 第二阶段：回查（事务状态未知时的兜底）

```
Producer                      Broker
   │                             │
   │ ◄── 长时间没收到 commit/rollback（进程挂、超时）────┤
   │                             │
   ├─ ④ 被回调 checkLocalTransaction() ──►  查本地事务状态
   │       （如查 pay_log 里有没有这条记录）
   ├─ ⑤ 返回 COMMIT / ROLLBACK / UNKNOWN ─►  按结果处理
   │
   │  （UNKNOWN → Broker 过一会再次回查）
```

- **触发条件**：步骤 ③ 之前 Producer 挂了、或响应超时，Broker 收不到 commit/rollback
- **回查机制**：Broker 主动回调 Producer 的 `checkLocalTransaction(msg, halfMsg)` 方法，Producer 查本地事务状态后返回结论
- **默认参数**：回查次数默认 **15 次**，间隔递增（最早 1s 起步，逐次拉长），超过次数仍查不到则丢弃消息

---

## 为什么 half 消息对消费者不可见？

- half 消息**不进入真实 topic**，而是进入内部的 `RMQ_SYS_TRANS_HALF_TOPIC`
- 只有 commit 之后，RocketMQ 才把消息**转移到真实 topic**，此时消费者才能拉到
- 这样消费者永远不会提前看到「事务还没提交」的消息 —— 这就是「本地事务 + 消息发送」原子性的关键

---

## 幂等性：最终一致的最后一块拼图

> ⚠ 事务消息只保证**「发送」和「本地事务」原子**，**不保证**消费者只收到一次。

重复消费的可能来源：Broker 重试投递、消费端处理成功但 ACK 丢失、消费者重启后重新拉取。消费端**必须幂等**：

| 方案 | 做法 | 适用 |
|------|------|------|
| 业务唯一键 + 去重表 | 消费时先查去重表，已处理过直接跳过 | 最通用，推荐 |
| 数据库唯一索引 | 订单号建唯一索引，重复插入直接冲突忽略 | 插入类消息 |
| Redis SETNX | `SETNX order:123 processed` 成功才处理 | 高频轻量场景 |

**面试话术**："事务消息解决的是生产端的原子性，消费端的重复消费要靠业务幂等兜底——我们用订单号做唯一键去重，重复消息直接丢弃。"

## 本项目应用（支付模块）

- **链路**：微信支付回调 → 支付服务发送 half 消息 → 执行本地事务（`INSERT pay_log`）→ commit → 订单服务 `@RocketMQMessageListener` 消费 → 更新订单状态 → 发放积分
- **为什么不用本地消息表**：RocketMQ 自带回查机制，业务代码少一个「定时扫表 + 重发」的轮询任务，复杂度更低
- **状态流转**：支付日志（本地库，强一致）→ 订单状态（MQ 异步，最终一致）

## 面试高频追问与话术

### Q1: 事务消息完整流程画一遍？（必考）

> **面试话术**：
> "① Producer 发 half 消息，Broker 放进 `RMQ_SYS_TRANS_HALF_TOPIC`，消费者不可见；② Producer 执行本地事务；③ 本地事务成功返回 commit，Broker 把消息转移到真实 topic，消费者可见；失败返回 rollback，消息丢弃；④ 如果 Producer 在 ③ 之前挂了或超时，Broker 会主动回查——回调 `checkLocalTransaction`，我查本地事务状态返回结论，默认回查 15 次、间隔递增。"

### Q2: 为什么不用本地消息表？

> **面试话术**：
> "本地消息表思路是：业务表 + 消息表同一个事务写入，然后定时任务扫消息表发消息、改状态。它能解决问题，但每接入一个业务就要维护一张消息表和一个轮询任务，代码侵入大。RocketMQ 事务消息把回查内建到 Broker 里，业务只需要实现一个 `checkLocalTransaction` 回调，代码更少。选型上：如果公司已经用了 RocketMQ，直接上事务消息；如果没有 MQ 只有 MySQL，本地消息表 + 定时任务也能凑合。"

### Q3: 回查具体怎么实现？要注意什么？

> **面试话术**：
> "实现 `TransactionListener#checkLocalTransaction`，根据消息里的业务标识（如订单号）查本地库，查到说明本地事务提交了，返回 COMMIT；查不到返回 ROLLBACK；如果库暂时不可查，返回 UNKNOWN 让 Broker 稍后再查。注意：① 回调里不能做重操作（查库要快）；② 回查本身必须幂等——多次回查结论要一致；③ 回查次数是有限的，事务状态要能快速确认，不能依赖长时间的人工处理。"

### Q4: 事务消息、本地消息表、Seata AT 怎么选？

| 方案 | 侵入性 | 适合场景 |
|------|--------|---------|
| 本地消息表 | 中（表 + 定时任务） | 无 MQ 或 MQ 不支持事务 |
| RocketMQ 事务消息 | 低（一个回调） | 异步通知、状态同步，最终一致即可 |
| Seata AT | 低（一个注解） | 需要**强一致**（如扣库存 + 建订单同时成功/失败） |

> **面试话术**：
> "事务消息和 Seata 解决的是不同粒度的问题。事务消息是**最终一致**——支付成功后订单状态晚几秒更新完全可接受；Seata 是**强一致**——下单 5 步操作必须同时成功或回滚。我项目里两个都用：跨服务强一致走 Seata AT（下单链路），跨服务异步通知走事务消息（支付 → 订单）。"

### Q5: 事务消息有什么坑？

> **面试话术**：
> "① **半消息不可见**——消费者看不到 half 消息，测试时容易误以为消息丢了；② **回查要快且幂等**——默认只回查 15 次，回调里查库太久会耗尽次数导致消息丢失；③ **commit 后消息才可见，但消费端仍要幂等**——事务消息不管消费端重复；④ **事务消息不解决顺序问题**——同一个订单的状态流转还要配合顺序消息（MessageQueue 选择器）使用。"

### Q6: 事务消息 vs 延迟消息（顺带一提）

- 事务消息：保证「本地事务 ⟺ 消息发送」原子性
- 延迟消息：消息发出后延迟 N 秒才投递给消费者（如 30 分钟未支付自动关单）
- 两者用途完全不同，别混为一谈

## 常见踩坑清单

| 坑 | 现象 | 解决 |
|----|------|------|
| `checkLocalTransaction` 返回 UNKNOWN 过多次数 | 消息被丢弃，订单状态不更新 | 回查逻辑查库要快，避免依赖外部系统 |
| 回查里查错事务状态 | 消息提前 commit / 误 rollback | 用业务唯一键定位，状态确认要准 |
| 消费端不幂等 | 重复发放积分、重复关单 | 订单号唯一索引 / 去重表 |
| 回调实现里做远程调用 | 回查超时拖垮 Broker 线程 | 回调只查本地库，不调远程 |
| 事务消息 topic 配置错 | half 消息一直堆积在 `RMQ_SYS_TRANS_HALF_TOPIC` | 确认 producer group 和 topic 配置一致 |

## 通俗理解

> **通俗理解**：事务消息像「先交定金，后付尾款」的网购。
>
> 你（Producer）先在商家（Broker）那里**交定金**（发 half 消息）——定金商品**还不发货**（消费者不可见）；然后你去银行办手续（执行本地事务），办成了说「付尾款发货」（commit），办砸了说「退定金不买了」（rollback）。要是商家一直等不到你的消息（进程挂了），它会**打电话来问**（回查）：你手续办得怎么样了？你说办好了就发货，没办就退款，不确定就过会儿再打。整个过程保证：**手续成功 = 一定发货，手续失败 = 一定不发货**——这就是「本地事务 + 消息发送」的原子性。
