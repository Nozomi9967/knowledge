### **全链路灰度的本质是三件事：入口按规则给请求打上「灰度标签」、标签要沿着调用链一路透传下去、每一跳的负载均衡都要按标签挑实例。落地靠 Nacos 给实例打 metadata、Feign 拦截器透传 header + ThreadLocal 传递、自定义 Ribbon 的 `IRule` 做标签优先匹配。最容易翻车的地方是异步线程池和 MQ —— ThreadLocal 到那里就断了。**

下面按面试口述节奏展开，按"打标 → 透传 → 选实例"三段讲。

---

**第一部分：先讲清楚灰度的目标和基本模型**

需求是：指定一批用户走新版本（灰度组），其余用户走稳定版，两批用户的请求各自闭环、互不串。

模型上有三个角色：

- **灰度规则**：谁算灰度用户？常见是 userId 白名单、userId 取模、请求 header 里的特定值、或者按比例随机
- **灰度实例**：新版本部署时给这些实例打上 `version=gray` 的元数据，稳定版打 `version=stable`
- **流量路由**：请求进来先判定标签，然后整条链路上每个调用都优先找"同标签"的实例

关键认知：**灰度不是入口一层的事，是全链路的事**。如果入口路由到灰度实例，但它调用下游时随机选到了稳定版，那这次请求就"半灰不灰"，很容易出数据不一致。

---

**第二部分：打标——标签从哪来**

三种常见来源，按优先级：

**用户维度（最常用）**：登录态里的 userId 做规则匹配，比如 `userId % 100 < 10` 就是 10% 灰度，或者维护一份白名单。

**请求维度**：header 里的 `X-Gray: true`，适合内部测试、运营验收。

**会话维度**：cookie 里带标记，避免同一个用户一会儿灰一会儿稳（体验不一致）。

打标的实现在网关层（Spring Cloud Gateway 的 GlobalFilter）：

```java
@Component
public class GrayFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String userId = exchange.getRequest().getHeaders().getFirst("X-User-Id");
        String tag = grayRule.match(userId) ? "gray" : "stable";
        ServerHttpRequest req = exchange.getRequest().mutate()
                .header("X-Gray-Tag", tag).build();
        return chain.filter(exchange.mutate().request(req).build());
    }
    @Override public int getOrder() { return -100; }   // 要早于路由
}
```

**注意一个坑**：标签要"粘住"。如果规则是按比例随机，同一个用户两次请求可能一次灰一次稳，业务上会很怪（比如购物车一会儿有新功能一会儿没有）。所以按比例灰度也要用 `userId 哈希` 做稳定映射，而不是每次 `Random`。

**第三部分：透传——三层机制缺一不可**

**第一层，HTTP 调用要带上 header。** 用 Feign 的 `RequestInterceptor` 把当前线程的标签塞进下游请求：

```java
@Component
public class GrayFeignInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        String tag = GrayContext.get();     // 从 ThreadLocal 取
        if (tag != null) template.header("X-Gray-Tag", tag);
    }
}
```

**第二层，服务内部跨线程要传递。** 进来的请求把标签写进 ThreadLocal，业务里开线程池异步处理时 ThreadLocal 就丢了——这是最常见的翻车点，必须用 `TransmittableThreadLocal`（阿里 TTL）或者手动包装 Runnable：

```java
public class GrayContext {
    private static final TransmittableThreadLocal<String> TAG = new TransmittableThreadLocal<>();
    public static void set(String t) { TAG.set(t); }
    public static String get() { return TAG.get(); }
    public static void clear() { TAG.remove(); }
}
// 线程池要用 TtlExecutors.getTtlExecutorService(...) 包装
```

**第三层，MQ 消息要带标签。** 发消息时把 tag 写进消息 header，消费端读出来重新 set 到 ThreadLocal。注意消费端如果是灰度实例消费了稳定消息、或者反过来，行为会不一致——所以要么按 tag 分 topic/队列，要么在消费逻辑里判断版本兼容性。

**第四部分：选实例——自定义 Ribbon 负载均衡**

Nacos 注册时可以带 metadata：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        metadata:
          version: gray    # 灰度实例配 gray，稳定版配 stable
```

然后用自定义 `IRule` 做标签优先匹配：

```java
public class GrayRule extends AbstractLoadBalancerRule {
    @Override
    public Server choose(Object key) {
        String tag = GrayContext.get();
        List<Server> all = getLoadBalancer().getReachableServers();
        if (tag == null) {
            // 无标签：只走 stable，避免误打到灰度
            return pick(all.stream().filter(s -> !"gray".equals(meta(s, "version"))).toList());
        }
        // 有标签：优先同标签，找不到再回退（视降级策略）
        List<Server> same = all.stream()
                .filter(s -> tag.equals(meta(s, "version"))).toList();
        return pick(same.isEmpty() ? all : same);
    }
}
```

**"找不到同标签实例怎么办"是个要明确的设计决策**：灰度实例挂了，灰度用户的请求要不要回退到稳定版？我的做法是**核心链路回退**（保证可用性），**非核心链路直接失败**（保证灰度的隔离性不被污染）。

---

**第五部分：这套方案的边界，必须主动说出来**

**异步和定时任务不受控**。`@Async`、`@Scheduled`、MQ 消费者这些没有 HTTP 入口的场景，标签从哪来是个问题。做法是定时任务按实例 metadata 决定跑不跑（灰度实例不执行定时任务，避免重复执行），MQ 消费端从消息 header 取标签。

**数据库和缓存的灰度最难**。应用可以灰度，但库表结构变更、缓存 key 变更没法灰度——所以 DDL 要向前兼容（先加字段不删旧字段），缓存 key 变更要双写过渡。这是全链路灰度真正的难点，应用层反而是最容易的。

**线程池隔离要彻底**。灰度实例和稳定版实例如果共用一个下游资源池（比如同一个 Redis 集群、同一个连接池），灰度出问题会影响到稳定版，隔离就失效了。

---

**面试话术收口**

我会这么说：全链路灰度分三段——网关按用户或 header 打标，Feign 拦截器 + TransmittableThreadLocal + MQ header 三层透传，负载均衡按 Nacos metadata 优先选同版本实例。难点不在应用层，在异步场景的标签传递和数据库/缓存的兼容性上，所以 DDL 必须向前兼容、缓存 key 要双写过渡。灰度实例的定时任务要关掉，避免重复执行。
