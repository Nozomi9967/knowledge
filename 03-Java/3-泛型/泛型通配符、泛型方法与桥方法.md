# 泛型通配符、泛型方法与桥方法

> 本文是 [[泛型擦除]] 的延伸。擦除那篇讲的是「**为什么会擦、擦成什么样**」；本文讲擦完之后，写代码时你会撞到的三类问题——① 通配符 `?` 到底怎么用（PECS）；② 泛型方法里 `<T>` 写在哪儿、什么时候必须传 `Class<T>`；③ 擦除与多态之间那道转接头——**桥方法**。最后补一个经常被问到的「常量池」辨析。

---

## 一、类型参数 T 与通配符 ? 的区别

这两个东西长得像，但身份完全不同，是很多困惑的根源。

- **`T` 是一个有名字的类型**：先给它起名（声明），后面可以在这个类 / 方法里反复使用它。
- **`?` 是一个没名字的类型**：只表示"某种类型"，但你不知道它具体是哪一种，也**不能把它当类型名用**。

```java
// T 是「有名字的类型参数」：先声明，之后可当类型用
<T extends Number> T doubleIt(T value) { ... }

// ? 是「通配符」：某种未知的 Number 子类型，不能当类型名用
List<? extends Number> numbers = ...;
```

| 写法 | 名称 | 出现位置 | 能否当类型名用 |
|------|------|---------|--------------|
| `<T extends Number>` | 类型参数（有名字） | 类 / 方法**声明**处 | ✅ 声明后 `T` 可当类型用 |
| `<? extends Number>` | 通配符（无名字） | 只在**使用**处（变量 / 参数类型） | ❌ 只表示某种未知类型 |

> 记忆：**`T` 是"我给它起了名"，`?` 是"我不知道它是谁"。** 起名了才能反复用；不知道是谁，就只能表达"它能满足什么约束"。

## 二、通配符与 PECS 原则

### 2.1 为什么需要通配符：泛型是不变的

`String` 是 `Object` 的子类，但 `List<String>` **不是** `List<Object>` 的子类型——这叫**泛型不变（invariant）**。所以下面这行编译不过：

```java
List<String> strings = List.of("A");
// List<Object> objects = strings;  // 编译错误
```

如果允许，就能通过 `objects` 往一个"只该装字符串"的列表里塞 `Integer`，破坏类型安全。

但我们又常常需要"接受一堆不同泛型实参"的方法。通配符就是用来表达这种**受限的协变 / 逆变**的。详细的不变 vs 协变推导见 [[泛型擦除#协变与不变（Covariance & Invariance）]]。

### 2.2 `? extends T`——读安全

```java
List<? extends Number> numbers;  // 可能是 List<Integer>、List<Double>...
Number n = numbers.get(0);       // ✅ 读出来一定是 Number，安全
numbers.add(1);                  // ❌ 编译错误
```

**读为什么安全？** 不管实际是 `List<Integer>` 还是 `List<Double>`，取出的元素都**一定是 `Number`**（或其子类），所以可以用 `Number` 接收。

**写为什么不安全？** 如果往里放 `Integer`，可它实际是个 `List<Double>`，或反之——放进去的类型和真实元素类型对不上。编译器无法保证安全，于是禁止写入（`null` 除外，因为 `null` 适配任何引用类型）。

### 2.3 `? super T`——写安全

```java
List<? super Integer> numbers;  // 可能是 List<Integer>、List<Number>、List<Object>
numbers.add(1);                 // ✅ 写 Integer 一定安全
Object value = numbers.get(0);  // 读出来只敢当 Object
```

**写为什么安全？** 这三种列表（`Integer` / `Number` / `Object`）**都能接收** `Integer`。

**读为什么不确定？** 取出的可能是 `Integer`，也可能是别的 `Number` 或 `Object`，编译器只知道至少是 `Object`，所以只能先当 `Object`。

### 2.4「安全」到底指什么

一句话：**安全 = 编译器能保证这个操作不会破坏类型约束。**
不管通配符背后实际是哪个"符合约束的列表"，这些读取 / 写入操作都不会引入运行时类型错误。

所以"只能读 / 只能写"是便于记忆的口语；更准确的说法是**哪些操作能保证类型安全**——`extends` 里读安全、`super` 里写安全。

### 2.5 PECS：生产 / 消费是相对**方法**而言，不是相对容器

**PECS = Producer Extends, Consumer Super。**

```java
static <T> void copy(List<? extends T> source,
                     List<? super T> destination) {
    for (T item : source) {
        destination.add(item);
    }
}
```

把方法想成**中间人**：

- `source` 把元素**提供给方法**，方法从它那里**读** → 它是**生产者（Producer）** → 用 `? extends T`。
- `destination` **接收方法写入**的元素，方法往里**写** → 它是**消费者（Consumer）** → 用 `? super T`。

> ✅ 关键：**"生产 / 消费"是站在方法的角度看的**，方向是「方法从列表读 → `extends`」「方法往列表写 → `super`」。不是站在容器角度（容器自己不会"生产"东西）。标准库的 `Collections.copy(List<? super T> dest, List<? extends T> src)` 就是这个签名。

## 三、泛型方法

### 3.1 返回值前的 `<T>` 是「声明类型变量」，不是修饰返回值

```java
static <T> boolean isType(Object obj, Class<T> type)
```

按顺序拆开看：

- `static` —— 静态方法
- `<T>` —— **声明类型变量 `T`**（这一步不加，后面就没得用）
- `boolean` —— 返回值类型
- `isType(...)` —— 方法名和参数

因为 `<T>` 先声明了类型变量，参数里才能写 `Class<T> type`。调用时传入 `String.class`，编译器就**推断**出 `T` 是 `String`：

```java
isType("hello", String.class);  // T 被推断为 String
```

注意：这里**方法返回的是 `boolean`，不是 `T`**。`<T>` 不在"修饰返回值"，而是在方法签名里先声明类型变量，供后面的参数、返回值等位置使用。如果真想让返回值是 `T`，得这样写：

```java
static <T> T first(T value) { return value; }
String s = first("hello");   // 这里 T 才是返回值类型
```

### 3.2 泛型方法**不一定**要放 `Class<T>`

```java
static <T> T first(T value) { return value; }  // 不需要 Class<T>，照样是泛型方法
```

只有**方法需要在运行时用到 `T` 的具体类型**时，才常要额外传 `Class<T>` 当"类型令牌"。判断标准就一句话：

> **方法是否需要运行时的具体类型信息？** 不需要 → 不传；需要 → 传 `Class<T>`。

## 四、类型变量 `T` 的三大运行时限制（都是类型擦除惹的祸）

因为擦除，`T` **不会在运行时保留成可检查的具体类型**，于是这三种写法都编译不过：

### 4.1 不能 `new T()`——不知道构造器

```java
static <T> T create() {
    return new T();  // ❌ 编译错误
}
```

`new T()` 要求知道两件事：① 具体创建哪个类；② 调哪个构造器。但 `T` 在不同调用里可能是 `String`、`Integer`……运行时无从确定；而且泛型约束也**不能说明 `T` 一定有某个可调用的构造器**。常见替代是让调用方把"创建动作"传进来：

```java
static <T> T create(Supplier<T> factory) {
    return factory.get();
}
String text = create(() -> new String("hello"));
```

### 4.2 不能 `obj instanceof T`——类型被擦掉了

```java
static <T> boolean isT(Object obj) {
    return obj instanceof T;  // ❌ 编译错误
}
```

即使写成 `isT<String>("hello")` 也没用：`T` 在运行时仍被擦除，JVM 无法判断 `obj` 是不是 `T`。（`instanceof` 的类型操作数必须是 **可具体化 reifiable** 的，而类型变量不是。）

替代方案：把运行时类型信息**以参数形式传进来**——

```java
static <T> boolean isType(Object obj, Class<T> type) {
    return type.isInstance(obj);
}
isType("hello", String.class);  // true
```

顺带：`obj instanceof List<String>` 同样不允许（运行时区分不出元素类型）；但 `obj instanceof List<?>` 可以，因为它只检查"是不是某种 `List`"，不关心元素泛型。

> ⚠️ 注意 `isT` 与 `isType` 的区别：原来的 `isT(Object obj)` **形参里没有 `Class<T>`**，所以它拿不到运行时类型，压根编译不过；`Class<T>` 是后来改写时**新加的**参数，不是原来藏着的。

### 4.3 不能 `new T[]`——数组必须在运行时知道组件类型

```java
static <T> T[] makeArray() {
    return new T[10];  // ❌ 编译错误
}
```

**为什么数组一定要知道运行时类型？** 因为 Java 数组在运行时会**记住自己的实际元素类型**，并在每次写入时检查：

```java
String[] strings = new String[1];
Object[] objects = strings;   // 数组协变：允许
objects[0] = 123;             // 运行时抛 ArrayStoreException
```

虽然变量 `objects` 的静态类型是 `Object[]`，它指向的数组实际是 `String[]`；JVM 知道这一点，所以拦下了往 `String[]` 里写 `Integer`。

而泛型方法运行时并不知道 `T` 是 `String` 还是 `Integer`，**造不出真正的 `String[]` / `Integer[]`**；可数组又必须明确自己的运行时类型才能做上述写入检查。两下冲突 → 只能借反射：

```java
import java.lang.reflect.Array;

static <T> T[] makeArray(Class<T> type, int length) {
    @SuppressWarnings("unchecked")
    T[] result = (T[]) Array.newInstance(type, length);
    return result;
}
String[] names = makeArray(String.class, 10);
```

`@SuppressWarnings` 是因为编译器无法验证这个泛型转换；正确性依赖传入的 `Class<T>` 与 `T` 保持一致。

> 📌 这和 [[泛型擦除#类型擦除带来的限制]] 里讲的"不能创建 `List<String>[]`"是**同一根因的两种表现**：一个是"泛型实参被擦"（`List<String>` vs `List<Integer>` 运行时分不出），一个是"类型变量被擦"（`T` 到底是啥不知道）。归根结底都是**数组要运行时类型，泛型没有**。

### 4.4 统一解法：`Class<T>` 类型令牌

上述三个限制，绕法都是同一个——**把 `Class<T>` 当参数传进来**，让运行时拿得到具体类型：

| 限制 | 根因 | 替代写法 |
|------|------|---------|
| 不能 `new T()` | 运行时不知道具体类 / 构造器 | 传 `Supplier<T>` 或工厂、`Class<T>` |
| 不能 `obj instanceof T` | `T` 被擦除，不可具体化 | 传 `Class<T>`，用 `type.isInstance(obj)` |
| 不能 `new T[]` | 数组要运行时组件类型 | 传 `Class<T>`，用 `Array.newInstance` 反射创建 |

## 五、桥方法（Bridge Method）

这是擦除最容易被忽略、也最常被追问的后果。

### 5.1 问题从哪来

```java
class Parent<T> {
    T get() { return null; }
}

class Child extends Parent<String> {
    @Override
    String get() { return "hello"; }
}
```

**从源码看**，`Child.get()` 返回 `String`，它重写了父类针对 `Parent<String>` 的 `get()`——天经地义，JVM 应该动态分派到它。

**但擦除之后呢？** 父类的 `T` 被擦成 `Object`，父类方法在**字节码层面**近似变成：

```java
Object get()   // 描述符 ()Ljava/lang/Object;（无参）
```

而子类真正写出的是：

```java
String get()   // 描述符 ()Ljava/lang/String;
```

**致命点**：JVM 匹配方法（vtable 重写判定、`invokevirtual` 解析）依据的是**方法名 + 描述符**，而**返回类型也进描述符**。于是擦除后的父类签名 `()Ljava/lang/Object;` 和子类的 `()Ljava/lang/String;` **在字节码层面根本不是同一个签名** → 子类那个方法**无法覆盖**父类的擦除版本。

### 5.2 桥方法补上这个签名

编译器于是在 `Child` 里**额外生成一个方法**（写源码时你看不到），概念上等价于：

```java
// 编译器生成，源码里不写
Object get() {          // 描述符与父类擦除版一致
    return get();       // 转发到真正返回 String 的那个 get()
}
```

调用点：`Parent<String> p = new Child(); p.get();`

- 调用方的字节码是**按静态类型 `Parent` 编译**的，调用签名落在擦除后的 `get()Ljava/lang/Object;` 上；
- 运行时找到 `Child` 里的**桥方法**（签名对得上父类）；
- 桥方法再转发到子类真正的 `String get()`。

最终执行的仍是子类实现，经由父类引用（`Parent<String> p`）的多态分发照旧成立。

### 5.3 用 `javap` 亲眼看一下

```bash
javap -c -v Child
```

你会看到 `Child` 里有**两个** `get`：

```text
String get();
  descriptor: ()Ljava/lang/String;
  Code:
    ldc           #7      // String "hello"
    areturn

Object get();
  descriptor: ()Ljava/lang/Object;       // ← 与父类擦除后的签名一致
  flags: ACC_BRIDGE, ACC_SYNTHETIC       // ← 编译器合成
  Code:
    aload_0
    invokevirtual #5      // Method get:()Ljava/lang/String;  ← 转发到真身
    areturn
```

`ACC_BRIDGE`（桥）/ `ACC_SYNTHETIC`（合成）两个标志就是它的身份证——它**由编译器生成，真实源码里并不存在**。

### 5.4 回答那个疑问：「我感觉不用写桥方法也能正确动态分派啊？」

**你的直觉从"源码视角"看是对的**，但从"字节码视角"看不对——关键差别在这：

> **动态分派（看对象实际类型决定调哪个）没错，但它得先"有一个签名能对上的方法入口"。** 桥方法不是替动态分派做决定，而是**让擦除后的父类签名在子类里有一个可匹配的入口**。

拆开说：

1. 源码里 `Parent<String>.get()` 逻辑上就是返回 `String`——所以你在源码层面觉得"直接覆盖就行了"。
2. 但 JVM 不跑源码，跑的是**擦除后的描述符**。调用点是按 `Parent` 的擦除签名 `()Ljava/lang/Object;` 编译的。
3. 若子类**只有** `()Ljava/lang/String;`，这次调用在 `Child` 里**找不到签名匹配的方法** → 重写失效、分派落空。
4. 所以编译器必须补一个 `()Ljava/lang/Object;` 的桥方法，把"擦除后的父类签名"接住，再转发到真身。

一句话收口：**桥方法负责"签名对齐"，动态分派负责"选谁执行"，两者配合，缺一不可。**

### 5.5 setter 版：桥方法里还带 `checkcast`

不只是返回类型，**参数类型**进描述符同样会引发桥方法——而且这时桥方法里会有一次**强制转换**：

```java
class Parent<T> {
    void set(T t) { }
}

class Child extends Parent<String> {
    @Override
    void set(String s) { }
}
```

`Child` 里会生成：

```java
// 编译器生成的桥方法
void set(Object o) {
    set((String) o);   // ← checkcast 在这里！
}
```

因为父类擦除后是 `set(Object)`，子类是 `set(String)`；桥方法接到 `Object` 后得先转成 `String` 才能调真身。**这也解释了为什么泛型是"编译期检查"**：真正的类型转换动作，一部分就藏在编译期生成的桥方法里。

> 无泛型的**协变返回**也一样会生成桥方法，例如 `Object clone()` 被子类重写为 `Foo clone()`——同样是"擦除/更宽签名 vs 更窄签名"对不上的老问题。

## 六、.class 文件常量池 vs 运行时常量池

这是顺带被问到的辨析，容易混。

| | `.class` 文件常量池 | 运行时常量池（Runtime Constant Pool） |
|---|---|---|
| 是什么 | 编译产物里的**静态表**，`javap -v` 显示的 `Constant pool:` | 类加载后，JVM 在**方法区**为这个类建立的**运行时结构** |
| 内容 | 字面量、类名 / 方法名 / 字段名、类型描述符、符号引用 | 以 class 文件常量池为**蓝本**，另可含运行时生成的内容（如 `String.intern()` 驻留、`invokedynamic` 引导） |
| 所在 | 磁盘上的 `.class` 文件里 | 方法区（JDK 8 起为**元空间**，堆外） |

要点：

- **概念上可近似理解成"同一个东西的静态版 / 运行时版"**：运行时常量池就是 `.class` 常量池在类加载后的"运行时映像"。
- **严格说两者不完全相同**：运行时常量池会**额外**加入运行期产生的内容，所以不是 `.class` 里那张表的逐字复制。

> ⚠️ 别和**字符串常量池（String Table）**搞混：那是**另一个**东西，JDK 7 起已从方法区挪到了**堆**里（`String.intern()` 指向它）。一句话区分——运行时常量池是"每个类一份、放方法区"，字符串常量池是"全局一份、在堆里"。

## 面试话术（口述版）

**问：`<T extends Number>` 和 `<? extends Number>` 有什么区别？**

> 这俩一个是**类型参数**、一个是**通配符**。`<T extends Number>` 是在声明处给类型起个名 `T`，限定它必须是 `Number` 的子类，声明之后 `T` 就能当类型名用，参数、返回值都能引用它。而 `<? extends Number>` 是通配符，只表示"某种未知的 `Number` 子类型"，出现在使用处，不能当类型名用。它们配合的就是 PECS 原则——`? extends` 只保证读安全（生产者用 extends），`? super` 只保证写安全（消费者用超级通配符），而 `T` 则是"我要在这个方法 / 类里反复引用这个类型"时才用。

**问：泛型擦除带来了哪些限制？为什么会有桥方法？**

> 擦除之后，类型变量 `T` 在运行时就不存在了，所以围绕 `T` 的操作都做不了三件事：不能 `new T()`，因为运行时不知道要创建哪个类、调哪个构造器；不能 `obj instanceof T`，因为 `T` 被擦成上界、不可具体化，做不到运行时判断；不能 `new T[]`，因为数组必须在运行时知道自己的组件类型，泛型给不了。这三个绕法都一样——把 `Class<T>` 当"类型令牌"传进来，用 `type.isInstance()` 判断、`Array.newInstance()` 建数组。至于**桥方法**，它是擦除和多态打架的产物：子类 `Child extends Parent<String>` 重写了返回 `String` 的 `get`，但父类擦除后签名是返回 `Object`，返回类型也是描述符的一部分，两个签名对不上，子类方法就覆盖不了父类。编译器于是在子类里合成一个返回 `Object` 的桥方法，转发到真正的方法，让 JVM 的虚方法分派能在擦除后的签名上找得到入口。用 `javap -v` 能看到它带着 `ACC_BRIDGE` 和 `ACC_SYNTHETIC` 两个标志。说白了——**桥方法负责签名对齐，动态分派负责选谁执行**。
