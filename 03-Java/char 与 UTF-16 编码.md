# char 与 UTF-16 编码

> Java 的 `char` 用的是 **UTF-16** 编码，占 **2 个字节（16 位）**。但要注意：**`char` 不是一个字符，而是一个「UTF-16 代码单元（code unit）」**——超出基本多文种平面的字符（部分生僻字、emoji）要用**两个 `char`** 表示。

---

## 一、`char` 的基本事实

- `char` 是**无符号 16 位整数**，取值范围 `0` ~ `65535`（`'\u0000'` ~ `'￿'`）。
- 它表示一个 **UTF-16 代码单元**，不是"一个 Unicode 字符"。
- 选择题里问 Java `char` 的编码，答案通常是 **Unicode（UTF-16）**。

> 注意区分：UTF-16 是 **Java 内部**（`String` / `char`）的表示；文件存储、网络传输用的通常是 **UTF-8**。两者是不同层面的事——`"中文".getBytes("UTF-8")` 转成字节数组时才涉及具体编码。

---

## 二、一个 `char` ≠ 一个字符（关键）

Unicode 把所有字符划成若干"平面"：

| 平面 | 码点范围 | 一个字符需要几个 `char` |
|------|---------|:---:|
| **基本多文种平面（BMP）** | `U+0000` ~ `U+FFFF` | **1 个**（常见汉字、字母、标点都在这里） |
| **补充平面** | `U+10000` 以上 | **2 个**（代理对） |

**代理对（surrogate pair）**：超出 BMP 的字符，用两个 `char` 拼出来，一个来自高代理区、一个来自低代理区。例如 emoji `😀`（`U+1F600`）需要两个 `char`：

```java
System.out.println("😀".length());          // 2  ← 两个代码单元
System.out.println("😀".codePointCount(0, 2)); // 1  ← 一个码点
```

`String.length()` 返回的是**代码单元个数（char 数）**，不是字符个数——这就是 emoji 的 `length()` 为 2 的原因。

**正确计数用 `codePointCount`**；遍历含代理对的字符串时，用 `codePoints()` 而不是逐个 `char`。

---

## 三、和 `String` 的关系（顺带记住）

- JDK 8：`String` 内部就是 `char[]`，每字符固定 2 字节（UTF-16）。
- JDK 9+：引入 **Compact Strings**，若字符串只含 Latin-1 范围字符，内部改用 `byte[]`（1 字节/字符），否则仍用 UTF-16（2 字节）。这只影响**内存占用**，不影响 `char` = UTF-16 的语义。详见 [[循环内字符串拼接性能分析（JDK 8 vs JDK 17）]]。

## 四、面试话术（口述版）

**问：Java 的 `char` 用什么编码？占几个字节？**

> `char` 用 **UTF-16** 编码，占 **2 个字节、16 位**，取值范围 0 到 65535。但要强调一点：`char` 表示的是一个 **UTF-16 代码单元**，不是"一个字符"。对于基本多文种平面里的字符，一个 `char` 就是一个字符；但超出这个范围的字符，比如某些生僻汉字和 emoji，需要**两个 `char` 组成的代理对**来表示，所以 `"😀".length()` 是 **2**，而 `codePointCount` 才是真正的字符个数 1。另外，UTF-16 是 Java 内部 `String` 的表示方式，文件存储和网络传输一般用 UTF-8，这是两个层面。

## 五、从源码到运行：三种编码的全链路（答疑沉淀）

**题目**：`char foo = '中'`，源文件以 GB2312 存储、用 `javac -encoding GB2312` 编译——这个语句正确吗？（答案：**正确**）有人会问：`char` 不是 UTF-16 吗，怎么又冒出来 GB2312？——因为「编码」发生在**三个不同环节**，各管一段：

| 环节 | 编码 | 作用 |
|------|------|------|
| 源文件（.java） | GB2312（题目设定，也可以 UTF-8） | 磁盘上保存你写的代码文本 |
| 字节码（.class） | **修改版 UTF-8** | 常量池里保存字符 / 字符串常量 |
| JVM 运行时内存 | **UTF-16** | `char` / `String` 的内部表示 |

以"中"为例走一遍：源文件里是 GB2312 字节 `D6 D0` → `javac -encoding GB2312` 解码成 Unicode 码点 U+4E2D → 写入 `.class` 时转成修改版 UTF-8 字节 `E4 B8 AD` → JVM 加载后，`char` 里是 UTF-16 代码单元 `0x4E2D`。

- **只要第一步解码用对编码**（`-encoding` 与源文件一致），后面两种编码都由 Java 自动处理。编码指定错（源文件 GB2312 却按 UTF-8 读）会解码出乱码，`'中'` 甚至可能报"未结束的字符文字"之类的错误。
- 顺带修正一个常见的不严谨说法："char 是 16 位 Unicode 字符"——严格说是"**16 位 UTF-16 代码单元**"（见本文第二节：一个 `char` ≠ 一个字符；BMP 内汉字一个 `char` 装得下，超出 BMP 的字符不能写成单个 `char` 常量）。

### 修改版 UTF-8（Modified UTF-8）是什么

Java 在标准 UTF-8 基础上做了**两处改动**，用于 `.class` 常量池（`CONSTANT_Utf8_info`）、`DataOutputStream.writeUTF()` 与 JNI 的 `GetStringUTFChars`：

1. **`\u0000` 用两字节 `C0 80` 表示**（标准 UTF-8 是单字节 `00`）——让编码结果里不出现 `00`，C 语言风格的字符串函数（以 `00` 作结束符）也能安全处理。
2. **增补字符按代理对分别编码**：超出 BMP 的字符（如 `😀` U+1F600），标准 UTF-8 是 4 字节 `F0 9F 98 80`；修改版先拆成 UTF-16 的两个代理项、各按 3 字节编码，共 **6 字节**（`ED A0 BD ED B8 80`）——与"JVM 内部 char 是 UTF-16 代码单元"的设计保持一致。

BMP 内、且不是 `\u0000` 的字符（含绝大多数汉字，"中"的 `E4 B8 AD` 两种编码一致）没有差异。注意：**修改版 UTF-8 不是合法的标准 UTF-8**，用标准解码器直接读含空字符或 emoji 的内容可能出错。
