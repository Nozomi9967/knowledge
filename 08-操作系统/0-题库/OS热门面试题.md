## 一、进程 / 线程 / 协程（4 题）

### 1. 进程和线程的区别？为什么线程切换比进程切换便宜？【高频】

**参考答案：**

进程是**资源分配**的最小单位，线程是 **CPU 调度**的最小单位。进程之间地址空间相互独立，每个进程有自己的页表；同一个进程内的线程共用同一套地址空间——代码段、堆、全局区全共享，线程私有的只有自己的栈、程序计数器和寄存器组。

线程切换比进程切换便宜的关键就一条：**同进程内的线程共用一张页表，切换时不用换 CR3（页表基址寄存器）、TLB 一条都不用清**，CPU 缓存也大部分是热的——代码、堆、全局数据物理地址没变，上条线程留的缓存下条线程接着用；进程切换是地址空间整个换掉，TLB 全刷、整个工作集缓存全丢，代价最大。

> **知识点跳转：** [[OS八股#二、进程 / 线程 / 协程]] · [[线程池#一、为什么用线程池]]

**追问：** 线程共享了什么？Java 里怎么体现？

线程共享堆（Java 对象都在堆上）、方法区/元空间、文件描述符表；私有的是虚拟机栈、程序计数器、寄存器。说白了，**堆是共享的，想让变量私有就得自己造一份 per-thread 的映射表**——这正是 [[ThreadLocal 深度解析与内存泄露笔记#一、核心概念：ThreadLocal 是什么？|ThreadLocal]] 存在的原因，OS 层的「共享堆 + 私有栈」是 Java 并发一半问题的物理来源。

### 2. 为什么有了线程还要协程？JDK 21 的虚拟线程了解吗？【中频】

**参考答案：**

线程不够用的根子在**数量**：线程是内核对象，创建要走 `clone()` 系统调用，一个线程栈默认就 **8MB 虚拟内存**，可运行线程数受内核调度能力限制。要扛 10 万并发连接，用「一连接一线程」就是 10 万 × 8MB 栈 + 内核调度直接崩溃。

协程的做法是把「阻塞时让出、就绪时恢复」这个动作**从内核搬回用户态**——挂起的只是栈上几个字节的状态，切换不需要陷入内核，栈可以很小，所以能开到几万到百万级别。

JDK 21 的**虚拟线程（Loom）**就是协程的工程化落地：虚拟线程挂载在**载体线程**（ForkJoinPool 里的平台线程）上，遇到阻塞 IO 时把栈帧**卸载**成堆上的 continuation 对象，载体线程立刻去跑别的虚拟线程。所以「百万虚拟线程」不是百万内核线程，内核看到的还是那几十个平台线程。

> **知识点跳转：** [[OS八股#2.3 协程：把调度权抢回用户态]] · [[线程池#一、为什么用线程池]]

**追问：** 虚拟线程有没有代价？

有代价，但要分清是哪种。第一，它的调度是**协作式**，而不是内核那种**抢占式**——JVM 不会主动打断一个正在跑的虚拟线程，只有在它自己走到卸载点、也就是阻塞的那一刻才会挂起它。所以一段代码如果**长时间跑、而且全程不阻塞**，比如一个大循环或者大数组排序，它就会一直占着载体线程不放；**这时候内核就算把载体线程抢下来也没用**，恢复之后跑的仍然是同一个虚拟线程，因为它压根没卸载。

问题出在载体是稀缺资源：整个 JVM 只有一个共享的虚拟线程调度器，载体数就等于 CPU 核数，你没法像给平台线程池那样单开一个池把它隔离出去。几个这样的长任务把载体占满，其他 IO 虚拟线程从等待中恢复时挂不上载体，整个服务就卡住了——**所以混合负载下这可能是负收益，`top` 里 CPU 是满的，请求却全卡住**。

第二是 pinning：JDK 21 里在 `synchronized` 块中阻塞会钉住载体线程、想卸载卸不掉，结果就是它一直占着一个载体线程不动，**退化成一个占满内核线程的重量级线程**；**JDK 24 起经 JEP 491 已经消除了 synchronized 的 pinning**，只剩调用 Native 方法还会卡住载体。

所以我的判断标准是：**要避开的不是「CPU 密集」，而是「长跑 + 全程不阻塞」这个组合**。短促的 CPU 突发算完就退出，很快把载体还回去，几乎没什么危害；任务里只要有不可忽略的阻塞占比，虚拟线程就赚。说白了，它本来就是为**阻塞式 IO** 设计的，你硬塞纯计算的长任务进去，失去的只是「拿它扛 IO 并发」这个特长——收益不是零，但风险明显盖过收益。

### 3. 进程有哪些状态？互相之间怎么转换？【高频】

**参考答案：**

进程的状态，经典模型是**五态**：**新建、就绪、运行、阻塞、终止**。新建态是内核刚把 PCB，也就是进程控制块，建好、还没挂进就绪队列；就绪被调度器选中就进入运行；运行的时间片用完，会被打回就绪；运行期间等资源、等事件就进入阻塞，阻塞等到资源就绪或者事件完成，再被唤醒回就绪——**就绪、运行、阻塞这三个来回转，是整个模型的核心循环**，也常单独叫**三态模型**。运行结束调 `exit`，进入**终止态**，父进程 `wait()` 回收之后，进程才彻底消亡。

有个细节要注意：终止之后不一定马上消失。父进程及时 `wait()` 收尸，进程就立刻消亡；**父进程不来回收，它才会滞留在僵尸 Z**——僵尸只剩一个 PCB 里的退出状态，已经没有可执行实体了。所以严格讲，**僵尸不是每个进程都要经过的一站，它是终止了但没人收尸的遗留状态**。

对应到 Linux，`top`/`ps` 里的状态字母和经典模型是对得上的：**R** 是就绪和运行的合并，排队等 CPU 和正在跑都算 R；**S** 是可中断睡眠，等事件、能被信号唤醒；**D** 是不可中断睡眠，通常是在等磁盘或 NFS 的 IO，`kill -9` 都杀不掉——而且 D 和 R 一样计入 Load，一堆 D 会把 Load 顶起来，但根因不是 D 本身，是它背后卡住的存储 IO；**T** 是停止，SIGSTOP 或者调试打断出来的；**Z** 就是僵尸，进程已经退出、父进程没回收，只剩 PCB 里的退出状态；另外还有个 **X**，表示已退出、PCB 马上要释放，对应经典模型里的消亡，只存在一瞬间，日常基本看不到。

排障的时候记住这个：一堆 **D** 就查磁盘/存储/NFS；一堆 **Z** 就是父进程没回收子进程。

> **知识点跳转：** [[OS八股#二、进程 / 线程 / 协程]] · [[wait 与僵尸进程回收详解#一、问题的起点：内核为什么不自己清理]]

**追问：** 僵尸进程怎么处理？

僵尸进程杀不掉，因为它已经死了——信号是发给活进程的，僵尸没有可执行实体，`kill -9` 对它没有意义。所以要处理的是**父进程的回收逻辑**：正规做法是父进程调 `wait()` 或 `waitpid()` 收尸，工程上一般挂在 **SIGCHLD 信号处理**里，子进程一退出就去收；Linux 下还有个更省事的办法，把 `SIGCHLD` 显式设成 `SIG_IGN`，子进程退出会由内核直接回收，根本不会产生僵尸；不想让父进程操心的话，也可以用**两次 fork**，让孙子进程变成孤儿、由 init 收养。

要是父进程长期不回收，先查它为什么漏了 wait；实在改不动，才考虑让父进程退出，孤儿进程会被重新挂到 init（PID 1）或者最近的 subreaper 下面，由它接管回收。**这里要注意一点：容器里的 PID 1 未必会回收**——容器里的 PID 1 就是你自己的主进程，它通常不 wait，所以 Docker 要加 `--init`（tini）兜底，不然僵尸会在容器里越堆越多。

### 4. 并发和并行的区别？【低频·加分】

**参考答案：**

并发是**一段时间内交替推进多个任务**，靠调度切换制造「同时在跑」的假象；并行是**多个核真的在同一时刻各跑一条指令流**。OS 层的意义在于：单核下加线程不会变快，只会增加切换开销；**只有超过一个核，线程数增加才带来真实吞吐**。所以判断线程该开多少，第一看核数，第二看任务是 CPU 密集还是 IO 密集——IO 密集时线程大部分时间在阻塞态、不占核，才允许开更多。

> **知识点跳转：** [[OS八股#七、I/O 模型与零拷贝]] · [[线程池#九、为什么 IO 密集型任务线程数可以多些]]

**追问：** 单核机器上开多线程还有意义吗？

看任务类型。CPU 密集任务在单核上开多线程只会互相抢时间片、白白增加切换开销，没有收益；但 **IO 密集任务有意义**——线程在等 IO 时让出 CPU，其他线程可以继续算，相当于**用并发掩盖 IO 延迟**。另外 Java 里多线程的意义不只是加速，还有异步解耦、共享资源并发控制等目的。

## 二、用户态与内核态（2 题）

### 5. 为什么要区分用户态和内核态？一次切换贵在哪？【中频】

**参考答案：**

CPU 有特权级（x86 的 Ring 0~3，Linux 只用 Ring 0 和 Ring 3）。**特权指令**——改页表基址寄存器、操作 IO 端口、关中断——只能在内核态执行，否则任何用户程序都能把别人的内存占了、把网卡关了。

一次从用户态进内核要做：**保存用户态寄存器现场 → 切到内核栈 → 参数校验 → 执行 → 恢复现场 → 切回**。一次系统调用 ≈ **1μs 量级**，比普通函数调用贵两三个数量级。**上下文切换比系统调用更贵**：进程切换要换页表，连带 **TLB 失效 + CPU 缓存命中率下降**。

这就是「**IO 密集场景线程开太多反而变慢**」的根因——不是线程本身重，是切换时丢缓存重。这条因果能把 OS 和线程池那页直接串起来。

> **知识点跳转：** [[OS八股#一、用户态与内核态]] · [[线程池#一、为什么用线程池]] · [[模式切换与上下文切换详解#六、贵的到底在哪：直接开销 vs 间接开销]]

**追问：** 高并发框架为什么都在「减少陷入内核的次数」？

因为系统调用一定比普通函数调用贵。优化方向就三类：**批量**——`writev` 一次写多块，比如一个 HTTP 响应天然是「状态行 + headers + body」三段不连续内存，本来要三次 write，现在一次搞定；再往前一步就是 `io_uring`，提交队列和完成队列在用户态、内核间共享，一批操作一次提交，极端模式下甚至能做到零系统调用。**复用**——epoll 一次等多个 fd，让一个线程用**一次**系统调用等 N 个连接，这是 C10K 的基石。**避免拷贝**——sendfile 让数据完全不进用户态。这里有个容易被忽略的点：**sendfile 这类零拷贝顺带也省了一半模式切换**——`read` + `write` 要四次陷入内核，`sendfile` 只需要两次。所以 Netty、Kafka、Redis 的优化都是同一个思路：**把多次陷入内核合并成一次，或者让数据不用进用户态**。

### 6. 系统调用、中断、异常有什么区别？【低频·加分】

**参考答案：**

**中断是外部来的、和当前指令无关的异步事件**（时钟中断、网卡收包完成）；**异常是当前指令执行时出问题的同步事件**（缺页、除零）；**系统调用是故意触发的异常**（x86 的 `int 0x80` 软中断，或专用 `syscall` 指令），所以也叫「陷入内核」。

网卡收包走的是**硬中断 + 软中断（softirq）两级**：硬中断里只做最少的事（确认 + 通知），耗时的协议栈处理丢给软中断，避免长时间关中断影响系统响应——这就是 `%si` 指标的由来。

> **知识点跳转：** [[OS八股#一、用户态与内核态]] · [[网卡收包流程详解#一、为什么必须拆成两级]]

**追问：** 为什么系统调用也叫「陷入内核」？

因为它确实是「主动掉进内核态」的动作：执行 `int 0x80` 或 `syscall` 指令时，硬件自动切换特权级和栈，从 Ring 3 跳到 Ring 0，就像程序「陷」进了内核的执行流。它和被动的错误（除零、缺页）不同——系统调用是程序**故意触发**、有明确的调用意图和参数，本质是一种「软件的、可控的异常」。

## 三、CPU 调度与 Load Average（2 题）

### 7. 常见调度算法有哪些？Linux 用的是什么？【中频】

**参考答案：**

先来先服务 FCFS——队列顺序执行，问题是**护航效应**，长作业后面所有短作业跟着等；短作业优先 SJF——最短的先跑，但要**预知运行时长**（做不到），长作业还会**饥饿**；时间片轮转 RR——每人跑一个时间片，时间片太小切换开销占比高、太大又退化成 FCFS；**多级反馈队列**——多个优先级队列，跑不完降级、排队久升级，这是实操中比较好的思路。

Linux 的经典调度器是 **CFS（完全公平调度器）**：没有固定时间片，维护每个任务的加权虚拟运行时间 **vruntime**，红黑树按 vruntime 排序、永远挑最小的跑——**权重（nice 值）大的任务 vruntime 涨得慢，从而分到更多 CPU**。这里可以再补一句：Linux 6.6 起 CFS 已经被 **EEVDF** 取代，同样是基于虚拟时间，额外按「最早虚拟截止期」来挑任务，对延迟敏感的任务更友好。

> **知识点跳转：** [[OS八股#3.1 常见调度算法]] · [[CFS 完全公平调度器详解#二、核心机制：vruntime 与权重]]

> 护航效应就是 FCFS 里一个长作业占着 CPU，后面短作业全被推迟开始——平均等待被领头一个拖爆（总时长不变，炸的是等待的分布）

**追问：** 为什么 CFS 不用固定时间片？

固定时间片是「一刀切」：对 IO 密集任务太长（它要的不多），对 CPU 密集任务又不够。CFS 的思路是**按任务权重分配 CPU 占比**，每个任务维护 vruntime，谁的虚拟运行时间最少就调度谁——权重大的 vruntime 涨得慢、自然拿到更多 CPU，公平且无固定时间片。

### 8. Load Average 是什么？Load 很高但 CPU 不高说明什么？【高频】

**参考答案：**

Load **不是 CPU 指标，是任务堆积指标**——统计的是处于 **R 状态（运行 + 可运行）+ D 状态（不可中断睡眠）**的任务数，按指数衰减算的 1/5/15 分钟移动平均。判断标准要看**核数**：4 核机器 Load=4 是满载，超过 4 开始排队过载，到 8 是重度堆积；粗略经验：单核 Load 接近 **0.7** 就该告警。

Load 很高但 CPU 使用率不高，说明**大量进程卡在 D 状态等 IO**——磁盘慢、NFS 挂住、大量缺页换页。CPU 空转不是因为闲，是因为没人 runnable、都在等。这时候**加 CPU 完全没用**，要去看 `iostat`、`vmstat` 的 `bi/bo` 和 **`wa`（IO wait）**指标。

> **知识点跳转：** [[OS八股#3.2 Load Average：它统计的不只是"在跑"的任务]] · [[磁盘 IO 瓶颈排查详解#五、完整排查链路（面试报三板就报这个）]]

>NFS（Network File System）网络文件系统
>**NFS 就是把别的机器上的磁盘，挂载到本机来用，就好像本地磁盘一样。**


**追问：** 怎么判断一台机器是真缺 CPU 还是存储瓶颈？

看 `vmstat` 的 **`r` 列和 `wa` 列**：`r` 大是真缺 CPU（运行队列排长队），`wa` 大是存储瓶颈（CPU 在等 IO）。这两种处理方向完全相反——前者加核/优化计算，后者查磁盘吞吐、换 SSD、查慢 IO。

## 四、内存管理（5 题）

### 9. 为什么要有虚拟内存？【高频】

**参考答案：**

三个动机，按重要性排。第一是**隔离与安全**：每个进程一套自己的地址空间，进程 A 访问 `0x1000` 碰不到进程 B 的，越界直接段错误——没有它一个野指针就能搞崩整机。第二是**连续内存假象**：物理内存是碎的、多进程交错分配还被换出，虚拟地址让程序以为自己有一大块连续空间，链接和加载才能简化。第三是**按需分配 + 可换出**：页不在物理内存也能「存在」，缺页时再要、再换回来——这才有 swap、内存超配、`fork` 的写时复制。

代价是**每次访存多一层地址翻译、变慢**。兜住这个代价的东西叫 **TLB**。

> **知识点跳转：** [[OS八股#四、内存管理]]

**追问：** 32 位系统为什么最多用 4G 内存？64 位呢？

进程能直接寻址的范围由**虚拟地址位数**决定：32 位 = 2^32 = 4GB，内核还要占走 1GB（默认 3G/1G 划分），用户空间只剩 3G——这也是 JVM 在 32 位机器上堆开不大的原因。64 位理论上限极大，但真实硬件只用 48 位虚拟地址（开 5 级页表 LA57 后到 57 位）。

---

### 10. 地址翻译的过程？TLB 是什么？为什么要多级页表？【中频】

**参考答案：**

执行一条访存指令时，CPU 发出的本来就是虚拟地址（也叫逻辑地址），把它翻译成物理地址是 **MMU** 干的活。翻译规则一句话：**页内偏移不动，只翻译页号**：虚拟页号 → 查页表（在内存里、多级）→ 得到物理页框号，加上偏移就是物理地址。**TLB 是页表缓存**，在 MMU 硬件里，命中就跳过查表，未命中才去 walk 多级页表。x86_64 Linux 默认页大小 **4KB**；页表设计成多级（x86 是 4 级，后续 5 级），目的是**让每级表正好装进一页 4KB**，稀疏映射时省内存。一次访存：TLB 命中 ≈ **1 周期**，miss 走多级页表可能要**几十上百个周期**。

进程切换会刷 TLB——现代 CPU 有 **ASID/PCID 标签**（给 TLB 表项打上地址空间编号）可以避免全刷，这也是「进程切换比线程切换贵」的又一层原因。

> **知识点跳转：** [[OS八股#4.2 地址翻译链路（画图题）]]

>**MMU = Memory Management Unit（内存管理单元）**——CPU 芯片里一块**专门做地址翻译的硬件**。



**追问：** TLB miss 会怎样？

去查多级页表，每读一级都要访存，还可能触发缺页异常——如果目标页不在内存里，要读盘（swap in 或 mmap 首次访问读文件），那是几十万甚至上百万个周期的代价。正常情况靠**局部性原理**保证 TLB 命中是常态。

### 11. malloc 分配内存：brk 和 mmap 的区别？free 了很多内存 RES 为什么不降？【中频】

**参考答案：**

用户态堆两种分配方式：**`brk`/`sbrk` 用于小块分配**——移动堆顶指针、连续一大片，但 free 后不能立刻归还内核（中间有空洞、要先整理）；**`mmap` 用于大块分配**——glibc 默认阈值 **128KB**（`MMAP_THRESHOLD`），在进程地址空间单独开一段 **VMA**（虚拟内存区域），`munmap` 直接销毁、**立刻归还内核**。

「free 了很多内存但 `top` 里 RES 不降」：因为小块走 brk，glibc 的 malloc 把释放的块留在自己的**空闲链表里复用**，堆顶不会轻易下移，存在内存空洞挡着。真归还要么 `malloc_trim()` 整理，要么这块本来就是 mmap 来的。

> **知识点跳转：** [[OS八股#4.3 用户态的堆：brk 与 mmap]] · [[进程内存指标与 glibc 分配详解#四、free 之后发生了什么：为什么 RES 纹丝不动]] · [[缺页异常详解#五、判断总表]]

**追问：** 缺页异常有哪几种？

三种。① **非法访问**——地址不合法，段错误；② **硬缺页**——页合法但不在物理内存，必须读盘（swap in、mmap 首次访问读文件）；③ **软缺页**——页其实已经在内存里，只是没建好映射关系，`fork` 后的写时复制就是典型，**不读盘**。

### 12. 页面置换算法有哪些？LRU 怎么实现？【高频】

**参考答案：**

内存不够要把某个页换出去。**OPT 最优**——换未来最久不用的，要预知未来、只用来证明别人更差；**LRU**——换最久没被访问的，效果好但精确实现要每次访问都移动链表节点，开销大；**FIFO**——换最先进来的，有 **Belady 异常**（内存变大缺页反而变多）；**Clock / 二次机会**——环形链表 + 引用位，指到 1 就清 0 跳过，是 **LRU 的工程近似**，摊还 O(1)；**LFU**——换访问次数最少的，有「历史高光赖着不走」问题。

LRU 的精确实现就是常说的**「哈希表 + 双向链表」**：哈希 O(1) 定位节点，双向链表维护访问顺序、头插、淘汰尾——这也是算法题 LRU Cache 的手撕模板。

> **知识点跳转：** [[OS八股#4.4 页面置换算法]] · [[Belady 异常与页面置换算法详解#三、为什么只有 FIFO 会这样：栈包含性质]] · [[Caffeine详解#W-TinyLFU 淘汰算法]]


>Clock摊还O(1)的意思

**摊还**就是：单次操作可能很慢，但**平均下来**每次操作是 O(1)

```
极端情况：所有页引用位都是1
→ 指针要转一整圈，清掉所有1，才找到可换的页
→ 这一次操作是 O(n)

但是：
→ 这一圈清掉了所有1
→ 下一次换页，很快就能找到0
→ 不会再转一整圈了
```

把这些操作**平摊**到每一页上：

```
n 个页，转一圈做了 n 次清零
这 n 次清零的工作，分摊给后续 n 次换页操作
→ 每次换页平均花费 O(1)
```



**追问：** Redis 的 allkeys-lru 是精确 LRU 吗？

不是。它是**采样近似 LRU**——不是全内存找最久未用的，而是默认随机取 5 个 key、在样本里淘汰最久未用的。Caffeine 的 **W-TinyLFU** 同样是近似思路。它们和 OS 用 Clock 是**同一条工程取舍：精确 LRU 太贵，所以近似**。

### 13. 内存不够时操作系统会怎么做？Java 进程被 OOM Killer 杀了怎么办？【中频】

**参考答案：**

顺序三步。**第一步先回收**：页缓存、**slab**（内核小对象缓存）里可回收的部分；**第二步 swap 换出匿名页**——所以生产上很多中间件会主动 `swapoff`，因为换出后 RT 抖动巨大；**第三步 OOM Killer**：按 `oom_score` 挑一个进程杀掉，`oom_score` 与内存占用量正相关，可用 `oom_score_adj` 调整保护级别。

Java 进程被 OOM Killer 杀掉，`dmesg | grep -i oom` 能看到内核日志。关键是分两件事：**进程是被内核杀的（oom-kill）还是自己抛 OutOfMemoryError 的**——前者说明整个机器内存真没了，堆外内存、大量线程栈、页缓存都可能是元凶，**加 `-Xmx` 反而死得更快**；后者是 JVM 自己管不住堆。容器环境里退出码 **137（=128+9）**基本就是被 SIGKILL 杀的，十有八九是 **cgroup 内存超限**，不是 JVM 自己的堆问题。

> **知识点跳转：** [OS八股 > 4.5 内存不够会怎样：swap 与 OOM Killer](http://localhost/OS%E5%85%AB%E8%82%A1#4.5%20%E5%86%85%E5%AD%98%E4%B8%8D%E5%A4%9F%E4%BC%9A%E6%80%8E%E6%A0%B7%EF%BC%9Aswap%20%E4%B8%8E%20OOM%20Killer) · [DirectByteBuffer与堆外内存回收 > 为什么堆外内存不足会触发 Full GC？](http://localhost/DirectByteBuffer%E4%B8%8E%E5%A0%86%E5%A4%96%E5%86%85%E5%AD%98%E5%9B%9E%E6%94%B6#%E4%B8%BA%E4%BB%80%E4%B9%88%E5%A0%86%E5%A4%96%E5%86%85%E5%AD%98%E4%B8%8D%E8%B6%B3%E4%BC%9A%E8%A7%A6%E5%8F%91%20Full%20GC%EF%BC%9F)

**追问：** 为什么容器里的 Java 进程特别容易触发 OOM Killer？

容器有 **cgroup 内存限制**，而 JVM 的 `-Xmx` 默认按宿主机内存算，堆可能比容器配额还大；再加上元空间、线程栈、堆外内存全占配额，一旦超过 cgroup limit 内核直接杀进程，JVM 来不及抛异常。解决：显式配 `-Xmx` 和容器配额匹配（JDK 10+ 默认开 `UseContainerSupport`），并留意堆外内存。

## 五、死锁（3 题）

### 14. 死锁的四个必要条件是什么？【高频】

**参考答案：**

四个必要条件**缺一不可**：**互斥**——资源一次只能被一个线程持有，这是锁的本质属性、去不掉；**请求并持有**——拿到 A 之后再去申请 B；**不可剥夺**——已持有的资源不能被人强抢，只能自己释放；**循环等待**——形成首尾相接的等待环，T1 等 T2、T2 等 T1。

工程上最常破坏的是**循环等待**：全局固定加锁顺序，所有人都按同一顺序申请锁，就不会成环。互斥那个条件基本去不掉，但可以用**无锁结构**（CAS、读写分离）绕开。

> **知识点跳转：** [[OS八股#5.1 四个必要条件（缺一不可）]] · [[ReentrantLock详解#二、四大核心特性详解]]

**追问：** 怎么破坏「请求并持有」和「不可剥夺」？

破坏请求并持有：**一次性申请全部资源**，或者 `tryLock` 拿不到就全部放开；破坏不可剥夺：申请新锁失败时**主动释放已有锁**，退避后重试。

---

### 15. 死锁的预防、避免、检测、忽略分别是什么？【中频】

**参考答案：**

**预防**是静态策略，破坏四个条件中的任意一个（破坏请求并持有 = 一次性申请全部资源；破坏循环等待 = 按固定顺序加锁，最常用；破坏不可剥夺 = 申请失败主动释放已有锁）。**避免**是动态策略：**银行家算法**——分配前先假设分配、检查系统是否还存在安全序列，没有就不分配——教科书爱考、生产几乎没人用，因为要预知进程最大资源需求。**检测**：允许死锁发生，定期用资源分配图/等待图找环，Java 里 `jstack`、`ThreadMXBean.findDeadlockedThreads()` 就是这个思路。**忽略**：Linux 和 Java 实际都选这个——宁可出现死锁再排查，不为不可能发生的场景付检测成本。

最后收一句：**操作系统和 JVM 其实都没有真正去防死锁，它们选的是检测或者忽略。所以死锁在生产上其实是个编码规范问题，不是内核问题，我能做的就是保证加锁顺序全局一致。**

> **知识点跳转：** [[OS八股#5.2 预防 / 避免 / 检测 / 忽略]]

**追问：** Java 现场排查死锁的完整步骤？

① `top -H -p <pid>` 找到高 CPU 的线程号，`printf '%x\n' <tid>` 转十六进制；② `jstack <pid>` 导线程 dump，搜 **`deadlock`** 关键字——jstack 自己会检测并打印 "Found one Java-level deadlock"；③ 看两个线程各持有哪把锁、各等哪把锁，定位代码里加锁顺序不一致；④ 修复：**统一加锁顺序**，或改 `ReentrantLock.tryLock(timeout)` 拿不到就退避重来。

### 16. 死锁、活锁、饥饿的区别？【低频·加分】

**参考答案：**

**死锁**：都在等对方、谁都不动——等资源互等成环。**活锁**：都在动（互相谦让重试），但**状态没进展**——典型是两个 CAS 冲突后同时退避又同时重试撞上。**饥饿**：单个线程一直抢不到资源——优先级低，或 `synchronized` 不公平 + 写锁把读线程饿住。

> **知识点跳转：** [[OS八股#5.4 死锁 vs 活锁 vs 饥饿]]

**追问：** 活锁和死锁怎么区分？怎么避免活锁？

死锁的特征是**「静止」**——都在等、谁也不动；活锁的特征是**「动态的僵局」**——都在重试、CPU 在烧，就是没进展。避免活锁的办法是给重试加**随机退避**，让两个线程的退避时间错开、不再同时撞上。

## 六、IPC 进程间通信（2 题）

### 17. 进程间通信有哪些方式？【高频】

**参考答案：**

主要六种。**管道 pipe**——半双工、仅限**亲缘**进程，内核环形缓冲区默认 64KB，读端关闭时写会收到 **SIGPIPE**；**命名管道 FIFO**——半双工但无亲缘关系也能用，文件系统里有名字，本质还是内核缓冲；**信号 signal**——异步通知，只传「哪个信号」不传数据，**SIGKILL(9)/SIGSTOP(19) 不能被捕获或忽略**，SIGTERM(15) 可以，所以优雅停机用 15 不要用 9；**信号量 semaphore**——不传数据，是**同步计数器**（P/V 原语），常配共享内存用；**共享内存 shm**——双向、**最快**，一次映射之后零拷贝、不走内核，缺点是没有同步能力必须自己配信号量或锁；**消息队列**——有格式、按类型取，但有大小限制和拷贝开销；**Socket / Unix 域套接字**——**唯一能跨机的方式**，Unix 域比走网络栈快。

> **知识点跳转：** [[OS八股#六、IPC 进程间通信]] · [[Semaphore详解#什么是 Semaphore]]

**追问：** 为什么共享内存最快？

其他方式都要「A 进程用户态 → 内核缓冲区 → B 进程用户态」**两次拷贝 + 多次系统调用**；共享内存是让两个进程**把同一段物理页映射进各自的虚拟地址空间**，A 写完 B 直接可见、数据一次都不动。这是和零拷贝**同一种思想：消除用户态和内核态之间的无谓搬运**。

### 18. 往已关闭读端的管道写数据会发生什么？【低频·加分】

**参考答案：**

管道是内核里的环形缓冲区，默认 **64KB（16 页）**，可用 `fcntl` 的 `F_SETPIPE_SZ` 调整，上限是 sysctl `fs/pipe-max-size`（默认 1MB）。写端往管道写数据时，如果**读端已经关闭**，内核会向写进程发送 **SIGPIPE 信号**，默认动作是终止进程——所以往断开的管道或者 TCP 连接上写，本质上都会碰到这个信号。Java 里表现为 broken pipe 异常；Go 的 runtime 对标准输出以外的 fd 会忽略这个信号、让 write 直接返回 EPIPE 错误，只有写 stdout/stderr 才会真被 SIGPIPE 杀掉。

> **知识点跳转：** [[OS八股#六、IPC 进程间通信]]

**追问：** 管道和 Socket 有什么本质区别？

你说的 Socket 要先分两种：**Unix 域套接字**和**网络套接字**。Unix 域套接字和管道都是内核缓冲区，区别在——管道**单向（半双工）、而且通常只给亲缘进程用**（靠 fork 继承 fd）；Unix 域套接字**全双工、任意进程都能用**，走 socket 那套 API（socket/bind/listen/accept），但不经过网络协议栈、没有 IP 层开销，所以它比走网络的 TCP Socket 快得多；而**网络套接字是唯一能跨机的方式**，代价是要走完整协议栈。要更本质一点说，不同 IPC 的抽象层次不同：管道传字节流、信号只传编号、共享内存传数据本身（共享同一批物理页）。

## 七、I/O 模型与零拷贝（3 题）

### 19. 五种 I/O 模型有哪些？为什么只有异步 I/O 是真异步？【高频】

**参考答案：**

一次网络读分两个阶段：**① 等数据到内核缓冲区 → ② 把数据从内核拷到用户空间**。五个模型的差别全在①，②除了异步 I/O 都逃不掉。**阻塞 IO**——线程在等数据时整个挂住；**非阻塞 IO**——反复轮询、CPU 白烧；**IO 多路复用**——一个线程等多个 fd、就绪后再拷（select/poll/epoll）；**信号驱动 IO**——内核就绪时发 SIGIO 通知、再拷；**异步 IO（AIO）**——等数据和拷贝全由内核做完、做完通知我，唯一真正的异步。

关键在于，**前四种本质上都是同步 I/O**——因为「数据从内核拷到用户态」这一步始终是 CPU 或者线程在参与，这一步不省掉，就谈不上真正的异步。

> **知识点跳转：** [[OS八股#7.1 五种 I/O 模型（POSIX）]] · [[Redis IO多路复用详解#架构：Reactor 模式]]

**追问：** Java NIO 是异步的吗？

不是。Java NIO 用的是**IO 多路复用**（Selector + epoll/kqueue），属于同步非阻塞——只是「多个 fd 一起等」，数据拷贝阶段还是有线程参与。Java 真正的 AIO 是 NIO.2 的 `AsynchronousSocketChannel`（Windows 走 IOCP、Linux 上是 epoll 模拟），生产用得少，Netty 主流还是多路复用模型。

### 20. select、poll、epoll 的区别？epoll 为什么快？【高频】

**参考答案：**

三个维度对比。**fd 上限**：select 是 **1024**（`FD_SETSIZE`，要改得重编译）、poll 无理论上限（链表）、epoll 无上限（受 `file-max` 和 `ulimit -n` 约束）。**fd 集合传递**：select/poll 每次调用都**全量拷贝**用户态↔内核态，epoll 是 `epoll_ctl` **注册一次**、`epoll_wait` 不重复拷贝。**内核找就绪 fd**：select/poll **线性遍历 O(n)**，epoll 内核维护**就绪双向链表**、`epoll_wait` 直接返回就绪那几个，**O(就绪数)**。

epoll 为什么快，三层因果：第一，**注册与等待分离**——fd 用红黑树常驻内核，省掉拷贝和重建集合的固定开销；第二，**回调机制取代轮询**——网卡数据到达 → 软中断 → 回调把该 fd 挂进就绪链表，代价只和就绪数成正比；第三，所以**活跃连接占比低时优势巨大**（C10K 场景）——10 万连接里只有 100 个活跃，代价只和 100 成正比，select 是 10 万。反过来，如果几乎所有 fd 都活跃，epoll 优势就不明显，红黑树插入删除也有成本。

> **知识点跳转：** [[OS八股#7.2 IO 多路复用：select → poll → epoll]] · [[Redis IO多路复用详解#底层：select / epoll 对比]]

**追问：** 水平触发 LT 和边缘触发 ET 的区别？

**LT（默认）**：只要缓冲区还有数据就一直通知，编程简单、不必一次读完。**ET**：只在**状态变化时通知一次**，必须循环读到 **`EAGAIN`**（errno，表示「暂时没数据、稍后再试」），而且必须配**非阻塞 fd**（否则读不到数据时卡死线程）。ET 省通知次数、更快，**Nginx 用 ET**。

### 21. 什么是零拷贝？传统 read+write 有几次拷贝？【高频】

**参考答案：**

经典「读文件发网络」用 `read()` + `write()`，数据要经过 **硬盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡**，共 **4 次拷贝**：2 次 **DMA 拷贝**（硬盘→页缓存、socket 缓冲→网卡，设备自己搬、不占 CPU）+ 2 次 **CPU 拷贝**（页缓存→用户缓冲区、用户缓冲区→socket 缓冲区）。**零拷贝省的就是 CPU 拷贝**——用户态压根不看数据。

演进：`mmap + write` 省掉「页缓存→用户缓冲区」那次 CPU 拷贝 → 3 次；`sendfile` 数据完全不进用户态 → 3 次但只有 1 次 CPU 拷贝；`sendfile + scatter-gather DMA` 让 socket 缓冲区只放描述符、网卡直接从页缓存 DMA 拼包 → **2 次 DMA + 0 次 CPU 拷贝**，这是最优。

> **知识点跳转：** [[OS八股#7.3 零拷贝]] · [[Redis fork 全量同步优化案例#要点提炼]]

**追问：** Kafka、Netty、Nginx 分别怎么用零拷贝？

**Kafka** 靠 `FileChannel.transferTo` 走 sendfile + scatter-gather DMA，数据从页缓存被网卡直接搬走；**Netty** 的 `FileRegion` 是 sendfile 的封装，`CompositeByteBuf` 把「ByteBuf 合并」用逻辑组合代替物理拷贝，是用户态版零拷贝思想；**Nginx** 静态文件走 sendfile。**Redis** 的 fork + 写时复制是**内存层面**的避免拷贝，同一个思想家族。

## 八、Linux 排障（2 题）

### 22. `free` 的 available 和 free 有什么区别？【中频】

**参考答案：**

`free` 是彻底没用过的内存；**available = free + 可回收的 cache**（页缓存、可回收的 slab）。Linux 会尽量用内存做页缓存，所以看到「内存只剩 200MB」先别慌，看 available——**cache 能回收，不是真占用**。这就是为什么看 `free -h` / `cat /proc/meminfo` 时不要盯 free 列、要看 available。

> **知识点跳转：** [[OS八股#八、Linux 常用排障命令（应届生要能报出三板）]]

**追问：** Swap 高说明什么？

`vmstat` 的 **si/so（swap in/out）非零**说明物理内存真不够了，内核在把匿名页换到磁盘又换回来——**RT 抖动巨大**。生产上很多中间件会主动 `swapoff` 或调低 `swappiness`，宁可用 OOM 也不要 swap，因为换页导致的延迟抖动比杀进程还难排查。

### 23. `kill -9` 杀不掉进程怎么办？`%sy` 比 `%us` 高说明什么？【中频】

**参考答案：**

`kill -9` 杀不掉，先看 `ps` 的状态列：如果是 **D 状态**，说明进程在等 IO，信号只能等它从内核态回来后才能处理——要查的是磁盘/网络存储/大量换页；如果是 **Z 状态**，说明它已经死了、只是等父进程收尸，`kill -9` 毫无意义，要修的是父进程没 `wait()` 的代码。排除完这些才考虑内核不可中断的极端情况。

`%sy` 比 `%us` 高说明**内核态开销过大**——通常是上下文切换太频繁、系统调用太密、或大量软中断。优化方向是**批量、复用、减少锁竞争**：把多次系统调用合并、用 epoll 复用等待、减少线程切换。

> **知识点跳转：** [[OS八股#八、Linux 常用排障命令（应届生要能报出三板）]] · [[解释为何CPU不是redis的瓶颈以及单线程为何还这么快？#二、 既然用单线程，Redis 凭什么这么快？]]

**追问：** 为什么「上下文切换频繁」会导致 `%sy` 偏高？

上下文切换的活**全在内核态干**：保存恢复寄存器、换栈、调度器选下一个进程、可能还要换页表刷 TLB——这些 CPU 时间都记到系统态（`%sy`）里。所以 `%sy` 高 + `vmstat` 的 `cs`（每秒上下文切换）数值大，说明系统把大量时间花在把线程/进程换来换去，而不是真正干活——这就是高并发框架要控制线程数、用批量系统调用的原因。
