## 方案 0：`synchronized` 整方法（基线）

```java
public synchronized boolean seckill(Long skuId, Long userId) {
    // 查库存 → 扣减 → 写订单  全部串行
}
```

所有线程争同一把对象锁，JVM 层面完全串行，QPS ≈ 200。

---

## 方案 1：分段锁

把库存拆成 N 段，用 `skuId % N` 决定落在哪段，每段一把锁，并发度提升 N 倍。

```java
private static final int SEGMENTS = 16;
private final Object[] locks = new Object[SEGMENTS];

public boolean seckill(Long skuId, Long userId) {
    int idx = (int)(skuId % SEGMENTS);
    synchronized (locks[idx]) {
        // 只锁当前 sku 对应的分段
        int stock = stockMap.get(skuId);
        if (stock <= 0) return false;
        stockMap.put(skuId, stock - 1);
        orderService.createOrder(skuId, userId);
        return true;
    }
}
```

**优点**：纯 JVM 内实现，无网络开销，改造简单。**缺点**：多节点部署时无效（各节点分段独立），且热点 sku 仍会打到同一把锁。

---

## 方案 2：`ReentrantLock` + `tryLock` 快速失败

获锁失败立即返回，而非阻塞排队，主动控制线程堆积。

```java
private final ReentrantLock lock = new ReentrantLock(false); // 非公平，吞吐更高

public Result seckill(Long skuId, Long userId) {
    if (!lock.tryLock()) {          // 0 等待，立即返回
        return Result.busy();       // 前端可提示"稍后重试"
    }
    try {
        // 扣减逻辑
    } finally {
        lock.unlock();
    }
}
```

也可加限时等待：`tryLock(50, TimeUnit.MILLISECONDS)`，在允许少量等待的场景下提升成功率。**适合**：请求量波动大、希望快速降级的场景。**缺点**：同样是单节点锁。

---

## 方案 3：Redis 分布式锁 + Lua 原子扣减

适合多节点部署。关键点：SET NX 加锁、Lua 脚本扣减保原子性、解锁也用 Lua 防误删。

```java
// 加锁
String token = UUID.randomUUID().toString();
Boolean locked = redis.set("seckill:lock:" + skuId, token,
    SetArgs.Builder.nx().px(300));          // 300ms 自动过期，防死锁
if (!Boolean.TRUE.equals(locked)) {
    return Result.busy();
}

// Lua 原子扣减库存（查+改一步完成，避免 ABA）
String lua = """
    local stock = tonumber(redis.call('get', KEYS[1]))
    if stock and stock > 0 then
        redis.call('decr', KEYS[1])
        return 1
    end
    return 0
    """;
Long ok = redis.eval(lua, ScriptOutputType.INTEGER,
    new String[]{"seckill:stock:" + skuId});

// 解锁（Lua 防误删）
String delLua = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    end
    return 0
    """;
redis.eval(delLua, ScriptOutputType.INTEGER,
    new String[]{"seckill:lock:" + skuId}, token);
```

**优点**：天然支持集群，Redis 单线程命令串行保证原子性。**缺点**：每次秒杀多 2 次网络 RTT；Redis 宕机需要 Redlock 或降级策略。

## 方案 4：本地库存预扣 + MQ 异步落库（最高性能）

请求打到内存 `AtomicInteger` 扣减，成功后发 MQ，消费者异步写 DB。核心逻辑无锁等待，QPS 可达万级。

```java
// 启动时从 DB/Redis 加载库存到内存
private final ConcurrentHashMap<Long, AtomicInteger> localStock = new ConcurrentHashMap<>();

public Result seckill(Long skuId, Long userId) {
    AtomicInteger stock = localStock.get(skuId);
    if (stock == null) return Result.notFound();

    // CAS 自旋扣减，库存不足时立即失败
    int cur;
    do {
        cur = stock.get();
        if (cur <= 0) return Result.soldOut();
    } while (!stock.compareAndSet(cur, cur - 1));

    // 异步发 MQ，消费者落库 + 创建订单
    mqProducer.send(new SeckillMessage(skuId, userId));
    return Result.success();
}
```

**关键保障**：

- **超卖兜底**：消费者写 DB 前再次校验，MQ 消费幂等（唯一键约束）。
- **节点一致**：多节点本地库存之和 = 总库存（提前按节点分配），或统一从 Redis `DECR` 拿令牌后再走异步。
- **重启恢复**：消费者消费失败走死信队列，重启时从 DB 读已扣数量初始化 `AtomicInteger`。

## 为什么要 Lua？

### 问题根源：Redis 命令非原子

不用 Lua 时，"查库存 → 扣减"是两条独立命令：

```
GET seckill:stock:1   → 返回 1
DECR seckill:stock:1  → 返回 0
```

两条命令之间有时间窗口，多个线程可以同时读到 `1`，然后各自执行 `DECR`，库存变成负数——**超卖**。

Lua 脚本在 Redis 服务端作为**单个原子操作**执行，执行期间不会被其他命令插入：

```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if stock and stock > 0 then
    redis.call('decr', KEYS[1])
    return 1
end
return 0
```

Redis 单线程处理命令，Lua 执行中不切换，所以"读+判断+改"三步对外表现为一个不可分割的操作。

## 为什么解锁要对比 token 再删？

### 问题场景：锁被误删

假设不校验 token，直接 `DEL lock`：

```
时间线：
T1  线程 A 加锁，SET lock "A的token" PX 300
T2  线程 A 业务逻辑执行中...
T3  300ms 到期，锁自动过期释放       ← 网络抖动 / GC 暂停
T4  线程 B 加锁成功，SET lock "B的token"
T5  线程 A 业务执行完，执行 DEL lock  ← 删掉的是 B 的锁！
T6  线程 C 加锁成功...               ← A、B、C 同时持锁，互斥失效
```

### 解法：加锁时写入唯一 token，解锁时先比对

```java
// 加锁
String token = UUID.randomUUID().toString();
redis.set("lock:" + skuId, token, SetArgs.Builder.nx().px(300));

// 解锁 Lua：compare-and-delete 原子执行
String lua = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    end
    return 0
    """;
redis.eval(lua, ..., new String[]{"lock:" + skuId}, token);
```

**为什么解锁也要 Lua？** 因为"比对 + 删除"同样是两步操作，如果用：

```java
if (token.equals(redis.get(key))) {  // ← GET
    redis.del(key);                   // ← DEL，中间可能锁已过期被别人拿走
}
```

GET 和 DEL 之间仍有窗口，还是会误删。Lua 把 compare-and-delete 压成一个原子操作才真正安全。

---

## 一句话总结

|问题|根因|解法|
|---|---|---|
|超卖|GET + DECR 非原子|Lua 合并为单个操作|
|误删他人锁|DEL 前锁已过期被别人拿走|Lua 的 compare-and-delete|

两个场景本质上是同一个道理：**Redis 的互斥保证只在单条命令粒度成立，跨命令的"读-改-写"必须用 Lua 封装成一个原子单元。**
