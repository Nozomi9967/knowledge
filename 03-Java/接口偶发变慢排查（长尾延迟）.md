# 接口偶发变慢排查（长尾延迟）

> 面试题：`某接口响应时间偶尔突增 300ms，CPU 不高、GC 正常、数据库慢查没报警，怎么系统性定位？`
> 这道题考的不是"你知道哪些工具"，而是**有没有一套可复用的排查路线**：CPU/GC/慢 SQL 都正常，只说明"常见原因暂无证据"——线程等待、网络、连接池排队、锁竞争、长尾延迟仍是嫌疑。

## 一、先懂"分位数"，别只看平均

把一段时间内所有请求的响应时间**从快到慢（从小到大）排序**，看排在某个比例位置的值：

| 指标 | 含义 | 读法 |
|:---:|:---|:---|
| **P50** | 约 50% 的请求不超过它 | 典型耗时（中位数） |
| **P95** | 约 95% 请求不超过它，最慢 5% 比它更慢 | 少数慢请求 |
| **P99** | 约 99% 请求不超过它，最慢 1% 比它更慢 | 长尾/尾延迟 |

- 例：`P50=50ms，P95=120ms，P99=400ms` → 大多数很快，但有极少数很慢。**只看平均值会把这个尖峰抹平**。
- 排查"偶发变慢"要盯 **P99 / max**，再看 P99 在突增时段是否抬高，按时间、实例、请求类型缩小范围。

> [!warning] 排序方向别记反
> 是从**快→慢**（小→大）排。**P95 = 95% 的请求 ≤ 这个耗时**，剩下的 **5% 比它更慢**。别记成"95 个超过它"。

## 二、四步排查路线

### 第 1 步：量化 + 缩小范围
看延迟的 **分位数**（P50/P95/P99/max）、时间点、频率、影响实例、请求特征；对照**发布、流量、定时任务、下游波动**。确认是不是某台机器、某类参数、某条业务分支触发。先核对**计时口径**：是服务端处理时间，还是含网关/网络/客户端耗时？

### 第 2 步：用链路追踪拆分耗时
按 **Trace ID** 找完整调用链，分解入口处理、线程池排队、缓存、DB、RPC/HTTP 各段耗时，看**哪一段突然多出 300ms**，是否集中在某下游/实例/连接池。
- 工具：SkyWalking、Zipkin、Jaeger、OpenTelemetry（分布式追踪）；Micrometer + Prometheus + Grafana（指标）。
- 埋点太粗就在可疑调用前后补耗时记录并带上 Trace ID，别只凭总耗时猜。

### 第 3 步：耗时不在外部调用 → 查线程和等待
CPU 不高，线程更可能在**等待**而非计算。看线程池活跃数、队列长度、拒绝数；用 **jstack / JFR** 看线程是否阻塞在：锁、连接池等待、队列排队、网络读写。
- 锁竞争 → 线程栈 + JFR 锁事件；
- 线程池排队 → 分清"排队时间"与"执行时间"，看是否被少数慢任务拖住。

### 第 4 步：补齐易漏的等待点 + 用证据验证
- 数据库**连接池获取连接**是否偶尔等（池耗尽≠必有慢 SQL）；
- 下游 HTTP/RPC 的**连接建立、连接池排队、读超时、重试、DNS**；
- 缓存未命中/节点抖动；文件/日志/MQ 的 I/O 阻塞；
- JVM 安全点、类加载、JIT 编译等短时因素。
- 网络问题可用 `tcpdump`/Wireshark 看重传、握手、延迟（注意抓敏感数据的规范）。

**先找证据再改配置**：对比"慢 vs 正常"请求（同参不同实例 / 同实例不同时间 / 有无重试）；难以复现就开一段低开销 **JFR**，事后分析，必要时 `jcmd`/`jstack`。避免无依据地频繁抓栈、开高开销日志。

## 三、一句话压轴

> 先按**时间、实例、请求特征**确认范围，再用 **Trace 拆耗时**；若不在外部调用，就查**线程排队、锁、连接池等待**，最后用 **JFR / 线程栈 / 网络抓包**验证假设。
