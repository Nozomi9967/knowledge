### **凌晨三点的告警，第一原则是「先止血、后定位」——先判断是不是刚发布导致的，是就立刻回滚；回滚完再按「看板 → 链路 → 日志 → 资源 → 代码」五步往下钻。顺序不能反，因为用户在等你恢复，不是在等你找到根因。**

下面按面试口述节奏展开，这题考的是"有没有真处理过线上问题"。

---

**第一部分：第一分钟，先做三件事**

**第一，确认影响面。** 全站还是单接口？所有用户还是部分用户？只影响写还是读写都影响？打开监控看板（Grafana / 公司自建），先看错误率曲线和 P99 曲线**从什么时刻开始拐**。

**第二，对齐时间点。** 拐点时间往前推 10 分钟，问一句"这个点有没有发布、有没有配置变更、有没有 DDL、有没有运营活动"。**80% 的线上故障和变更有关**，这条线索的价值最高。

**第三，判断能否回滚。** 如果确认是发布导致的，**立刻回滚**，不要先分析为什么——分析可以等恢复之后做。回滚是最快的止血手段，K8s 一条 `kubectl rollout undo` 或者流水线点一下，一分钟内能恢复到上一版本。

如果拐点没有对应的变更，那就进入下面的排查。

---

**第二部分：第二步，看板看什么**

监控看板要按"黄金三指标"看：**流量、错误、延迟**。

| 指标 | 看什么 | 异常含义 |
|---|---|---|
| QPS | 是否突增或骤降 | 突增可能是攻击/爬虫；骤降可能是上游熔断或前端挂了 |
| 错误率 | 5xx / 4xx 分别多少 | 5xx 是服务端问题，4xx 暴涨多半是上游传参变了 |
| P99 / P95 | 分接口看，别只看全局 | 全局 P99 被单个接口拉高时，要下钻到接口维度 |

**关键动作是下钻**：全局 P99 从 100ms 到 5s，不能就此停住，要看是**所有接口都慢**还是**某个接口慢**。

- 所有接口都慢 → 怀疑公共资源：数据库、Redis、线程池、GC、机器
- 单个接口慢 → 怀疑这个接口的外部依赖或代码逻辑

题里说"错误率 30%"，说明不完全是慢，还有实打实的失败，那更要看错误码分布。

---

**第三部分：第三步，链路追踪定位慢在哪一段**

打开 SkyWalking / Zipkin / 鹰眼，找一条慢请求的完整 trace，看耗时分布：

```
[API] /order/create        5023ms
  ├─ [MySQL] select user     12ms
  ├─ [Redis] get stock       3ms
  ├─ [HTTP] invoke inventory 4980ms   ← 慢在这里
  └─ [HTTP] invoke points    8ms
```

**这一段能把范围从"整个系统"缩到"一个下游"**，是排查里性价比最高的一步。

几种典型形态对应不同根因：

- **耗时全在某个 RPC/HTTP 调用**：下游慢或超时，去看下游自己的看板
- **耗时全在 SQL**：慢查询或锁等待，去 DB 看 `SHOW PROCESSLIST` 和慢日志
- **耗时分布很均匀、每段都略慢**：机器资源问题（CPU 被抢、GC 频繁、网络抖动）
- **trace 里有大段空白（span 空洞）**：可能是线程排队、GC 停顿、或者安全点停顿，这类问题 trace 看不出来，要结合 jstack

---

**第四部分：第四步，日志看具体报错**

按 traceId 捞日志，重点看三样：

**异常堆栈**。`TimeoutException`、`Connection refused`、`Pool exhausted`、`RejectedExecutionException` 这几个关键词直接指向不同的根因——超时是下游慢，refused 是下游挂了，pool exhausted 是连接池不够，rejected 是线程池满了。

**错误日志的集中度**。如果是同一个错误刷屏，说明是系统性问题；如果是零散的不同错误，可能是数据问题。

**业务日志的时间分布**。看某个关键步骤的耗时日志，能不能和 trace 对上。

---

**第五部分：第五步，资源层面排查**

到这一步是"确认是不是自己这边的问题"：

**JVM**：
```bash
jstat -gcutil <pid> 1000      # GC 频率和耗时，看 FGC 是否暴涨
jstack <pid> > stack.txt      # 线程栈，看有没有大量 BLOCKED / WAITING
jmap -histo:live <pid> | head # 对象分布，看有没有异常大类
```

- 大量线程卡在同一个锁 → 锁竞争或死锁
- 大量线程在 `WAITING` 于连接池 → 连接池耗尽
- FGC 频繁且耗时长 → 内存问题（可能是有大对象或泄漏）

**数据库**：
```sql
SHOW PROCESSLIST;             -- 有没有大量 Sleep 或 Locked 的连接
SHOW ENGINE INNODB STATUS;    -- 最近一次死锁详情
```
看慢查询日志、看连接数是否打满、看主从延迟。

**Redis**：`INFO stats` 看 ops 和命中率、`SLOWLOG GET` 看慢命令、看有没有大 key 导致阻塞。

**机器**：`top`、`vmstat 1`、`iostat -x 1`——CPU 是被用户态吃满还是被 iowait 吃满？内存有没有 swap？

---

**第六部分：常见根因对照表（这部分最显功力）**

| 现象 | 最可能的原因 |
|---|---|
| P99 慢但 P50 正常 | 少量请求遇到慢路径：锁等待、GC 停顿、个别机器异常 |
| P99 和 P50 一起慢 | 全局资源不足：DB 慢、网络带宽、下游整体变慢 |
| 错误率突然 30% | 某个下游挂了；或连接池/线程池打满开始拒绝 |
| 每隔几分钟周期性抖动 | 定时任务、缓存集中过期、GC |
| 只有部分机器慢 | 单机问题：磁盘、网卡、宿主机资源争抢、GC |
| 流量没变但 CPU 涨 | 死循环、正则回溯、序列化问题、日志打了太多 |

---

**第七部分：止血手段的清单**

排查的同时，手上要有几个"立刻能做"的动作：

1. **回滚**（最优先）
2. **扩容**：加实例扛流量，但如果瓶颈在 DB 就没用
3. **限流**：把非核心流量挡掉，保住核心接口
4. **降级**：关掉非核心功能（推荐、评论），把资源让给主链路
5. **切流**：多机房/多集群切换
6. **改配置**：调大连接池、调大超时（治标但快）

---

**面试话术收口**

我会这么说：凌晨告警第一件事不是查代码，是确认影响面和时间点，看拐点前有没有发布——有就立刻回滚，这是最快止血。回滚后再按"看板 → trace → 日志 → 资源 → 代码"往下钻：看板按黄金三指标下钻到接口维度，trace 定位到具体 span，日志看异常类型，资源层看 JVM/DB/Redis/机器的具体指标。同时准备限流、降级、扩容这些止血手段。

**最后补一句体现经验的话**：真正难的不是找到根因，是在高压下保持顺序——很多事故是被"边查边改"搞大的，回滚和排查同时进行，越改越乱。所以我习惯先拉一个群、明确一个人指挥，回滚和排查分两条线走。
