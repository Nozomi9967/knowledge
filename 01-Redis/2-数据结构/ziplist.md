## ziplist（压缩列表）是什么

ziplist 是 Redis 自己实现的一种**紧凑型顺序数据结构**，把一串元素**连续、紧凑地**放在一块连续内存里。目的是节省内存——相比双向链表每个节点要存 prev/next 指针（各 8 字节），ziplist 完全不存指针。

### 内存布局

```
每个 ziplist 整体长这样（连续内存块）：

zlbytes | zltail | zllen | entry1 | entry2 | ... | entryN | zlend
```

| 字段          | 大小  | 作用                          |
| ----------- | --- | --------------------------- |
| **zlbytes** | 4B  | 整个 ziplist 占用的总字节数          |
| **zltail**  | 4B  | 最后一个元素的偏移量（方便从尾部倒序遍历）       |
| **zllen**   | 2B  | 元素个数（> 65535 时需要遍历才能知道实际个数） |
| **entryX**  | 不定  | 每个元素                        |
| **zlend**   | 1B  | 结束标记 `0xFF`                 |


### 每个 entry 的结构

```
每个 entry 长这样：

prevlen | encoding | data
```

|字段|作用|
|---|---|
|**prevlen**|前一个 entry 的总字节数（往前回溯用）|
|**encoding**|当前 entry 的数据类型和长度|
|**data**|实际存储的数据（字符串或整数的二进制）|

`prevlen` 有两种编码：

- 如果前一个 entry 长度 **< 254B**，prevlen 只用 **1 字节**
- 如果前一个 entry 长度 **≥ 254B**，prevlen 用 **5 字节**（第 1 字节 = `0xFE` 标记，后 4 字节存长度）

## 连锁更新（cascade update）—— ziplist 的致命伤

这就是 ziplist 最终被放弃的根本原因。

### 触发场景

假设你的 ziplist 里有一串 entry，每个 entry 长度都在 **250~253 字节**之间：

```
entry1(250B) → entry2(253B) → entry3(251B) → entry4(252B) → ...
         ↑              ↑              ↑              ↑
      prevlen=1B    prevlen=1B      prevlen=1B      prevlen=1B
```

现在你在 entry1 后面**插入了一个新元素**，这个新元素很大，占了 **300 字节**：

```
entry1(250B) → NEW(300B) → entry2(253B) → entry3(251B) → entry4(252B) → ...
                              ↑
                         问题来了：NEW 的长度 ≥ 254B
                         所以 entry2 的 prevlen 需要从 1B 扩容到 5B
```

### 连锁反应

1. **entry2 的 prevlen 从 1B → 5B**，导致 entry2 的整体长度增加了 4 字节（253 → 257）
2. entry2 现在 ≥ 254B 了，那 **entry3 的 prevlen 也得从 1B 扩容到 5B**
3. entry3 长度增加 4 字节（251 → 255），又 ≥ 254B
4. **entry4 的 prevlen 也得扩容**
5. ...一直传导下去，像多米诺骨牌

这就是**连锁更新（cascade update）**——最坏情况下，插入一个元素要往后更新 N 个 entry，**时间复杂度 O(n²)**。

### 概率问题

> 实际生产中，连锁更新并不常见。因为需要：
> 
> 1. 每个 entry 长度恰好落在 [250, 253] 这个狭窄区间
> 2. 连续多个 entry 都这样
> 
> 概率低，但一旦触发，延迟会瞬间飙升。

这就是 Redis 团队仍然要换掉它的原因——哪怕概率低，**作为基础设施不能有这种 O(n²) 的隐患**。

# 🎯 面试题 · 2026-07-21 16:11（基于《ziplist》）

> [!question]- 面试题 1：什么是 ziplist？它相比 Redis 双向链表在内存节省上的核心设计思路是什么？
> ziplist 是 Redis 自行实现的一种紧凑型顺序数据结构，核心设计目标就是节省内存。它会将一串元素连续、紧凑地存放在一块连续的内存块中，完全摒弃了双向链表每个节点必须存储的 prev/next 指针（各占8字节），而是依靠内存本身的连续性来表示元素的顺序，同时通过每个 entry 中存储的「前一个 entry 的长度」来实现从后往前回溯，从根源上省去了指针占用的额外内存，内存利用率远高于双向链表。

> [!question]- 面试题 2：请描述 ziplist 的整体内存布局，以及单个 entry 的结构和 prevlen 字段的编码规则。
> ziplist 的整体内存是连续块，布局从首地址到末地址依次为几个固定字段加元素区：首先是4字节的 zlbytes，存储整个 ziplist 占用的总字节数；其次是4字节的 zltail，存储最后一个元素的偏移量，方便从尾部开始倒序遍历；然后是2字节的 zllen，存储元素个数，当元素个数超过 65535 时，这个字段存不下实际值，必须遍历整个 ziplist 才能拿到真实元素个数；之后是 N 个变长的 entry 元素；最后是1字节的 zlend，作为结束标记，固定值为 0xFF。
> 单个 entry 的结构分为三部分：prevlen 字段存储前一个 entry 的总字节数，作用是从当前 entry 往前回溯到上一个 entry；encoding 字段存储当前 entry 的数据类型和长度信息；data 字段存储实际的数据，可以是字符串的二进制形式，也可以是整数的二进制形式。
> 其中 prevlen 有两种编码规则：如果前一个 entry 的总长度小于 254 字节，prevlen 只需要1字节就足够存储；如果前一个 entry 的总长度大于等于 254 字节，prevlen 会扩容到5字节，第1字节固定为 0xFE 作为标记，剩余4字节存储实际的长度值。

> [!question]- 面试题 3：什么是 ziplist 的连锁更新（cascade update）？它为什么是 ziplist 最终被 Redis 放弃的根本原因？
> ziplist 的连锁更新也叫 cascade update，是它最终被 Redis 放弃的根本原因，本质是插入元素时引发的多个 entry 的 prevlen 字段连续扩容的连锁反应。
> 它的典型触发场景是：ziplist 中连续多个 entry 的长度都落在 250~253 字节这个狭窄区间，此时这些 entry 的 prevlen 都只用1字节存储。如果我们在某个 entry 后面插入一个长度大于等于 254 字节的新元素，那么紧跟在它后面的下一个 entry 的 prevlen 就需要从1字节扩容到5字节，导致这个 entry 的整体长度增加4字节，刚好超过 254 字节的阈值，那么再下一个 entry 的 prevlen 也需要执行同样的扩容操作，这种效应会像多米诺骨牌一样一直向后传导。
> 最坏情况下，插入一个元素需要向后更新全部 N 个 entry，时间复杂度直接退化成 O(n²)，会引发瞬间的延迟飙升。虽然实际生产中触发概率很低，因为需要连续多个 entry 都恰好落在 250~253 字节的区间，但作为 Redis 这种核心基础设施，不能容忍存在这种极端场景下性能出现致命隐患的设计，因此 Redis 最终选择废弃 ziplist 这种实现，避免这种 O(n²) 的风险。
