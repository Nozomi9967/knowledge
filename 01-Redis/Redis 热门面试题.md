## 一、认识 Redis（2 题）

### 1. 什么是 Redis？为什么选择 Redis 作为 MySQL 的缓存？请从「高性能」和「高并发」两个角度展开说明。

> **知识点跳转：** [[redis八股]] · [[解释为何CPU不是redis的瓶颈以及单线程为何还这么快？]]

Redis是一个高性能高并发的内存数据库

因为它操作数据都在内存中，比mysql读写数据快几个数量级，而且它单机QPS轻松上万，能用于高并发场景

**追问：** 既然要高性能高并发，为什么不用本地缓存 Caffeine 或进程内缓存？Redis 作为独立的中间件带来了哪些额外价值（如多进程共享）？

---

**批改分析区：**

**评分：5/10**

- ❌ **硬伤：QPS 严重低估**——"轻松上万"应为"轻松破 **10w**"，差一个数量级
- ❌ **两个维度没展开**——"高性能高并发"只是定性，没说 O(1)/O(logN)、对比 MySQL 受限、三大底层设计
- ❌ 追问（本地缓存 vs Redis）没答

**参考答案 ✅**

**① 什么是 Redis？**

Redis 是一种**基于内存的键值数据库**，对数据的读写操作都在内存中完成，因此读写速度特别快，常用于**缓存、消息队列、分布式锁**等场景。

**② 为什么选择 Redis 作为 MySQL 的缓存？——一句话概括**

因为 Redis **高性能**且**高并发**：全内存 + O(1)/O(logN) 数据结构，实现微秒级的内存访问；单机 QPS 轻松破 10w，能在内存层消化绝大多数热点请求，防止海量流量直接冲击 MySQL。在架构中扮演**蓄水池 / 护城河**的角色。

**③ 从「高性能」角度展开**

- Redis 是**全内存架构**，数据读写都在内存中完成
- 核心数据结构（哈希表、跳跃表等）经过极致优化，大多数常用操作时间复杂度 **O(1) 或 O(logN)**
- 业务收益：MySQL 的复杂查询（解析 / 索引扫描 / 磁盘 I/O）被内存命中替代，**接口时延（RT）大幅降低**

**④ 从「高并发」角度展开**

- 先对比 MySQL 为什么受限：MySQL 受限于**进程/线程模型 + 文件系统锁机制**，并发到数千时线程上下文切换和连接池瓶颈凸显，容易连接数爆满甚至宕机
- Redis 单机 **QPS 轻松破 10w**，靠三大底层设计，且环环相扣：
  1. **全内存操作**——每条命令微秒级完成，**所以单线程处理也绝不会阻塞事件循环**
  2. **单线程执行命令模型**——**正因单线程，天然没有多线程上下文切换的 CPU 损耗，也没有锁竞争**
  3. **非阻塞 I/O 多路复用**（基于 epoll）——让单线程也能同时监听成千上万个网络连接

**⑤ 角色定位（加分点）**

Redis 是系统的"**蓄水池 / 护城河**"——缓存热点数据，在内存层消化绝大多数请求，防止海量流量直接冲击下游 MySQL。

> **追问参考答：为什么不用 Caffeine / 进程内缓存？**
> 本地缓存存在 **JVM 进程内**，每个服务实例各有一份——多实例之间**不共享、必然不一致**，进程重启缓存直接丢失。Redis 是**独立的共享中间件**，所有服务实例访问同一份缓存，天然保证多实例一致；而且自带 TTL、持久化、分布式锁等能力。所以**分布式场景下必须用独立缓存，本地缓存只能做二级缓存**。

|------|-------|-----------|
| 数据类型 | 支持 **String、Hash、List、Set、ZSet** 等丰富类型 | 只支持最简单的 key-value |
| 持久化 | 支持，重启可恢复数据 | 无持久化，重启/挂掉数据全丢 |

**批改分析区：**

**评分：6/10**

- ✅ 说对了「简单动态字符串」、O(1) 获取长度、操作安全不溢出
- ❌ 漏了**二进制安全**（SDS 三大核心优点之一）

**参考答案 ✅**

**① 底层实现：** String 的底层是 **SDS（Simple Dynamic String，简单动态字符串）**

**② 相比 C 字符串解决了三个问题：**

- **O(1) 获取长度**：C 字符串要遍历到 `\0`（O(N)），SDS 用专门字段存 len，直接读取

> **追问参考答：**
> ① O(1) 长度——专门字段存 len；
> ② 二进制安全——靠 len 判断边界，不依赖 `\0`；
> ③ 不溢出——free 字段 + 拼接前扩容检查。

### 8. ZSet 为什么使用「跳表 + 哈希表」的组合？为什么不用红黑树或平衡树？

> **知识点跳转：** [[跳表（Skip List）详解]] · [[Redis底层编码标准答案]]

不了解，笔记里好像没写

---

**批改分析区：**

**评分：1/10**

- ❌ **空着**，说"笔记里好像没写"——违反批卷准则「不会的题不要空着，展示思考过程」；且笔记里有（[[Redis底层编码标准答案]]）
- ⚠️ 推理路径：ZSet 要"有序 + 能查分数" → 有序需排序树/跳表；要范围取 TopN → 跳表最顺手；不用红黑树 → 实现复杂是致命伤

**参考答案 ✅**

**① 为什么跳表 + 哈希表组合：**

- **哈希表**：O(1) 精确定位 member → score（如 ZSCORE）
- **跳表**：有序结构，支撑范围查询（ZRANGE、ZRANGEBYSCORE，排行榜取 TopN）

**② 为什么不用红黑树 / 平衡树：**

1. **范围查询**：跳表找到起点后顺着 forward 指针遍历区间即可；红黑树范围查询要走中序遍历，实现复杂
2. **实现简单**：跳表本质是多层有序链表，插入/删除只改局部指针，没有旋转、染色调整
3. **平衡方式**：跳表靠概率决定层高，天然近似平衡
4. **取舍**：跳表多耗内存（多层指针），但排行榜场景范围操作是核心，值得

> 知识位置：[[Redis底层编码标准答案]] ZSet 部分 + 速记口诀「ZSet 小用 listpack（128），大则跳」。跳表结构/操作/与红黑树对比的详细原理 → [[跳表（Skip List）详解]]

### 9. 什么是 ziplist 的「连锁更新」问题？Redis 7.0 的 listpack 是如何解决这个问题的？

**① 什么是连锁更新：**

- ziplist 的每个 entry 头部有 **prevlen 字段**，记录**前一个 entry 的长度**
- prevlen 本身大小可变：前一 entry 长度 < **254B** 时用 **1 字节**，≥ 254B 时用 **5 字节**
- 连锁更新：若某个 entry 变大、跨过 254B 临界点，它后面的 entry 需要把 prevlen 从 1 字节扩成 5 字节 → 自身也变大 → 继续影响更后面的 entry → 级联扩容

**② listpack 怎么解决（追问参考答）：**

- listpack 的 entry **只存自身的长度，不再引用前一个 entry 的长度**
- 单个 entry 变大只影响自己，不会级联影响其它 entry，从根上消除连锁更新
- **本质区别**：ziplist 是"记录**前一个**的长度"（引用前面，变长会扩散）；listpack 是"记录**自己**的长度"（自包含，变长不扩散）---

### 14. Redis 如何实现数据不丢失？三种持久化方式分别是什么？各有什么特点？

AOF日志是把每个数据操作日志记录下来，恢复时直接回放命令日志
	优点是不容易丢数据，缺点是恢复速度慢，需要一条一条回放

	优点是恢复数据速度快，把RDB文件加载进数据库就行，缺点是把握不好RDB快照的频率，太快影响性能，太慢掉电了容易丢很多数据
混合持久化是AOF和RDB混合使用
	结合了AOF和RDB的特点，在保证恢复速度的同时保证了不会丢很多数据

**批改分析区：**

**评分：8.5/10**

- ✅ 三种方式全对，优缺点因果清晰
- ✅ AOF 恢复慢、RDB 恢复快、混合折中——主线正确
- ⚠️ 可更精确：RDB 缺点是"最后一次快照之后的数据会丢"（丢多少取决于频率）；混合持久化的触发时机在 **AOF 重写过程**

**参考答案 ✅**

**① AOF 日志：** 每执行一条写操作命令，把命令追加记录到 AOF 文件；恢复时逐条回放命令。优点丢数据少（取决于写回策略），缺点恢复慢（一条条回放）。

**③ 混合持久化（Redis 4.0）：** 在 AOF 重写时，前半段 RDB 全量 + 后半段 AOF 增量，既保证恢复速度又降低丢失风险。

### 17. AOF 文件越来越大怎么办？AOF 重写机制是怎么工作的？为什么要使用子进程而不是子线程？

> **知识点跳转：** [[AOF 持久化是怎么实现的？]]

AOF文件过大时会触发AOF重写机制

AOF重写会将数据库中的每一个键值转换为对应的一条写命令，写入到新的AOF文件中
因为子线程和父线程共享内存空间操作数据时，会加锁，影响性能
而子进程和父进程虽然共用内存，但发生读写冲突时会发生写时复制，保证父子之间互不影响

**批改分析区：**

**评分：8.5/10**

- ✅ 重写机制核心对（键值对转命令写入新文件）
- ✅ 子进程 vs 子线程：共享内存加锁影响性能 + 写时复制，两点都对

**① 触发：** AOF 文件超过阈值 → 由后台子进程 `bgrewriteaof` 执行重写。

**② 重写原理：** 读取当前数据库所有键值对，**每个键值对用一条命令**记录到新的 AOF 文件，全部完成后替换旧文件。本质是"数据快照"，不是日志追加，所以能压缩文件。

**③ 为什么用子进程而不是子线程（两个好处）：**

- **避免阻塞主进程**：重写期间主进程可以继续处理命令请求
- **无需加锁**：子进程与父进程共享内存（只读），一方修改触发**写时复制（COW）**，父子各持独立数据副本；若用线程则必须加锁，降低性能

**评分：9/10**

### 21. 为什么会有混合持久化？它解决了什么问题？有什么缺点？

> **知识点跳转：** [[混合持久化与MP-AOF对比]]

它解决了纯AOF恢复太慢重写太慢，纯RDB丢数据多频率不好把握的问题

缺点是文件混杂了RDB和AOF两种文件格式，且没有向下兼容

**评分：8.5/10**

- ✅ 优缺点对（可读性差 + 不向下兼容）
- ⚠️ 小瑕疵："纯 AOF **重写太慢**"表述不准确——AOF 的核心痛点是**恢复慢**（逐条回放），重写慢不是主因

**① 背景：** RDB 恢复快但丢数据多、频率难把握；AOF 丢数据少但恢复慢。混合持久化取两者之长。

**② 原理：** AOF 重写时，fork 出的子进程先把共享内存数据以 **RDB 格式**写入 AOF 文件，重写缓冲区的增量命令再以 **AOF 格式**追加 → 文件**前半段 RDB 全量、后半段 AOF 增量**。

## 五、过期删除与内存淘汰（5 题）

### 23. Redis 的过期删除策略是什么？为什么选择「惰性删除 + 定期删除」组合？

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

是惰性删除和定期删除组合的方式
惰性删除不会主动删除过期键，只有过期后对应数据再次被访问时才会删除
它对内存不是很友好，因为长期不会被访问的过期数据就会一直滞留在内存
对CPU友好
定期删除是每隔一段时间就随机挑一批检查是否过期，进行删除
它对CPU不友好，对内存优化

redis采用组合的方式是在CPU和内存之间的权衡选择

**批改分析区：**

**评分：8/10**

- ✅ 惰性/定期机制对，CPU/内存权衡主线对
- ✅ 追问内容其实都答了（惰性 CPU 友好内存不友好、定期反之、组合是权衡）
- ❌ 追问答"**上面答了**"——面试不能甩这句，每道追问要独立重新组织

**参考答案 ✅**

**① 惰性删除：** 每次访问 key 时检测是否过期，过期则删除。优点**对 CPU 友好**（只用很少资源）；缺点过期 key 不被访问就一直在内存里，**对内存不友好**。

**② 定期删除：** 每隔一段时间**随机抽 20 个 key** 检查并删除过期 key；若本轮过期比例 **> 25%（超过 5 个）** 则继续下一轮，最多持续 **25ms**。优点主动清理释放内存；缺点频率难把握——太频繁伤 CPU，太少又和惰性一样。

**③ 组合原因：** 惰性删除保 CPU，定期删除保内存，在**合理使用 CPU 时间和避免内存浪费**之间取得平衡。

> **追问参考答：** 惰性删除对 **CPU 友好**、**内存不友好**；定期删除对 **CPU 不友好**（额外扫描开销）、**内存友好**（主动释放）。两者互补，形成 CPU/内存的权衡。

redis的近似lru是根据redis对象结构体中lru字段实现的，该字段存储了对应数据上次的访问时间戳，淘汰时redis会随机抽取一批数据，淘汰里面lru字段最小的

**批改分析区：**

**评分：7/10**

- ✅ LRU/LFU 核心思想对、近似 LRU 机制对（lru 字段存时间戳 + 随机采样淘汰最小）
- ✅ **追问答得好**：缓存污染问题讲清楚了
- ⚠️ 传统 LRU 两个问题只答了一个（移动耗时），漏了「用链表管理所有数据带来的额外空间开销」

**参考答案 ✅**

**① 核心思想：**
- **LRU**（Least Recently Used）：按**最后访问时间**淘汰最久未使用的数据
- **LFU**（Least Frequently Used）：按**访问频次**淘汰最少被访问的数据

**② 传统 LRU 的两个问题：**
- 需要用链表管理所有缓存数据 → **额外空间开销**
- 数据被访问时要移动到链表头 → 大量访问时**链表移动操作耗时**，降低性能

**③ Redis 近似 LRU：** 对象结构体用 24 bit `lru` 字段记录**最后一次访问时间戳**；淘汰时**随机取 5 个**（可配置），淘汰其中 lru 最小的。优点：不用维护大链表（省空间）、不用每次访问移动链表项（提性能）。

### 27. Redis 的 LFU 是怎么实现的？对象头的 24 bits 字段在 LRU 和 LFU 模式下如何复用？

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

lfu复用了lru字段，它用低八位存logc对数计数器，高16位存访问时间戳

**追问：** LFU 的低 8bit 计数器最大只有 255，为什么够用？「访问次数越多、增长概率越低」是怎么实现的？长时间不被访问的 key 频次会怎样变化？

低八位的计数器是对数计数器，不是单纯的+1-1，随着访问次数增加，它的增长会越来越慢，而且他还会随着时间自动衰减

---

**批改分析区：**

**评分：8.5/10**

- ✅ 主问对：24 bits 复用（低 8 bit logc + 高 16 bit ldt）
- ✅ **追问答得好**：对数计数器 + 时间衰减，核心机制全对
- ⚠️ 可补精确的增长概率表：0-5 次 100% 涨、6-50 次约 10%、50+ 次约 1%

**参考答案 ✅**

**① 24 bits 复用：**
- **LRU 模式**：24 bits 全部存最后一次访问时间戳
- **LFU 模式**：高 **16 bit** 存 ldt（Last Decrement Time，访问时间戳，用于时间衰减），低 **8 bit** 存 logc（对数计数器，记录访问频次）

**② 8 bit 计数器为什么够用（不会溢出）：** 用的是**对数计数器（Logistic Counter）**，增长是**概率性**的：

| 当前 cnt | 每次访问增长概率 |
|:--------:|:--------------:|
| 0-5 | 100% |
| 6-50 | 约 10% |
| 50+ | 约 1% |

> 访问次数越多，后续增长越难。被访问 100 万次的 key 计数器可能也就 40 多，根本不会溢出。

**③ 时间衰减：** ldt（高 16 bit）记录上次衰减时间；key 长时间不被访问，logc 会**自动减半**（每过一个 `lfu-decay-time` 周期衰减一次），让 LFU 能"遗忘"过去的热度，响应访问模式变化。

> ⚠️ 面试中不要说"8 bit 溢出了指向别的内存地址"——这是错的。

## 六、缓存设计（5 题）

### 28. 缓存雪崩、缓存击穿、缓存穿透分别是什么？三者本质区别是什么？各自的解决方案？

> **知识点跳转：** [[什么是缓存雪崩、击穿、穿透？]]

缓存雪崩是同一时间大量的缓存过期，导致大量请求缓存miss后直接落到数据库，导致数据库压力骤增
解决方案可以是打乱缓存过期时间，不设置过期时间由后台线程异步更新缓存

缓存击穿是某个热点缓存数据过期，大量并发请求同时打过来缓存miss后直接落到数据库，n个请求同时请求数据库缓存重建，导致系统压力骤增
解决方案：不设置过期时间由后台线程异步更新缓存，重建缓存时设置分布式锁保证只有一个线程重建其他返回默认值或null值

缓存穿透是指用户请求的数据既不在缓存又不在数据库，每次请求都miss缓存然后请求数据库，可数据库里也没有，无法建立缓存
解决方案：这种一般是业务误操作或黑客恶意攻击，可以在请求参数那里做校验，恶意请求直接拦截、或者把数据存布隆过滤器，请求打来时先检查布隆过滤器有没有、或者直接在缓存对该数据建立默认值或空值

**追问：** 布隆过滤器有什么缺点？能不能 100% 拦截？Redis 原生支持布隆过滤器吗？

布隆过滤器它存在在应用层，走的仍然是进程线程模型，有连接池限制和上下文开销
相比代理层效率不是很高

---

**批改分析区：**

**评分：6.5/10**

- ✅ 三个问题定义都对，区分清楚（雪崩=大量 key 同时过期、击穿=单热点过期+并发重建、穿透=库也没有）
- ✅ 解决方案全（打散过期 / 异步更新 / 互斥锁 / 参数拦截 / 布隆 / 空值）
- ❌ **追问答偏**：问的是布隆过滤器缺点 / 能否 100% / Redis 原生是否支持，你答的是"部署在应用层有连接池开销"——三问都没答到点上

**参考答案 ✅**

| 场景 | 缓存有吗 | 数据库有吗 | 核心问题 |
|:---:|:---:|:---:|------|
| 雪崩 | 有，但大量同时过期 | 有 | 大量不同 key 同时过期 |

- **雪崩方案**：过期时间打散（加随机值）、缓存不过期后台异步更新
- **击穿方案**：互斥锁（SETNX 只允许一个线程重建）、热点数据不过期异步更新
- **穿透方案**：参数校验拦截、缓存空值（短过期）、布隆过滤器

> **追问参考答：** 布隆过滤器缺点——**有误判率**（说"不存在"一定不存在，说"存在"可能不存在=假阳性）、**不支持删除**、需额外维护；**不能 100% 拦截**，通常配合空值缓存兜底；**Redis 原生不支持**，需加载 RedisBloom 模块。

### 29. Cache Aside（旁路缓存）策略的写操作，为什么推荐「先更新数据库，再删除缓存」？反过来先删缓存会有什么问题？

> **知识点跳转：** [[Cache Aside 写策略满分拆解]] · [[数据库和缓存如何保证一致性？]]

主要是时间窗口大小的问题，先更新数据库后删除缓存，这之间的时间窗口是微秒级，也就是说只有在我更新数据库后，删除缓存前的窗口内，完成写缓存，才有可能出现数据不一致，但删除缓存微秒级，极快，几乎不可能出现不一致

而先删缓存后更新，时间窗口是毫秒级，在此窗口内完成查数据库，更新缓存这一流程的可能性大大增加

**追问：** 「先更新 DB 再删缓存」理论上还有不一致的窗口吗？这个窗口为什么实际几乎不会命中？

理论上是有的，但此窗口极小，几乎不可能

---

**批改分析区：**

**评分：8/10**

- ✅ 时间窗口分析到位：先更 DB 再删缓存窗口微秒级、先删后更窗口毫秒级
- ✅ 追问核心对：理论上有一致性窗口但几乎不可能命中
- ⚠️ 可更精确描述窗口：不一致发生在"读请求读完 DB 后、写缓存前"的瞬间，另一请求须在其中完成"更新 DB（毫秒级磁盘 IO）+ 删缓存"——要求 B 的 DB 更新比 A 的 DB 读取返回还快，几乎不可能

**参考答案 ✅**

**① 先删缓存再更 DB 为什么不安全：**

```
请求A（写）： 删缓存     →          更新DB（慢，毫秒级）
请求B（读）：            读缓存miss → 读DB(旧值) → 写缓存(旧值)
```

删缓存后、更 DB 前的毫秒级窗口里，读请求会把旧值写回缓存 → 缓存永久留旧值。

**② 先更 DB 再删缓存为什么更安全：**

```
请求A（写）：            更新DB（慢）→ 删缓存（极快，微秒级）
请求B（读）： 读缓存miss → 读DB(新值) → 写缓存(新值)
```

不一致窗口 = 读请求"读完 DB 后、写缓存前"的微秒级瞬间，另一请求要在此窗口内完成"更新 DB + 删缓存"。删缓存/写缓存是内存操作（微秒级），更新 DB 是磁盘 IO（毫秒级）——B 的 DB 更新要比 A 的 DB 读取返回还快，几乎不可能命中。

**③ 即使发生了也不怕：** 若写缓存发生在删缓存之前，删除操作会把旧值清掉，下次读 miss 读 DB 拿新值，不一致自动修复。

### 30. 除了 Cache Aside，数据库和缓存一致性还有哪些保证方案？「延迟双删」是怎么做的？有什么局限？

> **知识点跳转：** [[数据库和缓存如何保证一致性？]]

读穿/写穿、写回

延迟双删是先删缓存，再更新数据库，过一段时间后，再删一次缓存

---

**批改分析区：**

**评分：5/10**

- ✅ 延迟双删步骤对（先删缓存 → 更新 DB → 延迟 → 再删）
- ⚠️ 首问没答到点："读穿/写穿/写回"是**缓存更新策略**，不是 DB 缓存**一致性保证方案**——一致性方案主要是延迟双删、binlog 订阅异步更新、短过期兜底、加锁更新
- ❌ 局限没答

**参考答案 ✅**

**① 除 Cache Aside 外的一致性保证方案：**

- **延迟双删**（Cache Aside 的加强版）
- **异步更新缓存**：订阅 binlog（如 Canal）增量同步到缓存，不依赖业务代码删缓存
- **缓存设短过期时间兜底**：即使短暂不一致，过期后自动刷新
- **更新时加分布式锁**：同一时间只允许一个线程更新缓存

**② 延迟双删怎么做：** 先删缓存 → 更新数据库 → **延迟几百 ms** → 再删一次缓存。

**③ 为什么加延迟：** 等"读请求把旧值写回缓存"的窗口过去，第二次删除把残留旧值清掉。

**④ 局限：** 延迟时间难设（太短没兜住窗口、太长影响缓存命中率）；极端并发下仍可能不一致；**第二次删除可能失败**，需配合删除重试机制兜底。

### 33. 主从复制是怎么实现的？全量同步和增量同步分别发生在什么阶段？

> **知识点跳转：** [[主从复制是怎么实现的？]] · [[replication buffer 与 repl_backlog_buffer 对比]]

通过binlog实现
主节点每执行一次写操作后，都会把命令追加到binlog日志中，然后再返回结果给客户端，而从节点会读取主节点的binlog回放，从而保证主从节点数据一致

全量同步发生在从节点第一次同步主节点数据时
后续都走增量同步

**追问：** 主从命令复制是同步还是异步？为什么无法保证强一致性？

异步，主节点写完binlog日志就会返回响应给客户端，后续同步binlog是异步的，所以redis主从复制是最终一致

---

**批改分析区：**

- ✅ 全量同步时机对（首次）、异步复制 + 最终一致对
- ❌ **致命概念混淆：Redis 主从复制没有 binlog！** binlog 是 **MySQL** 的日志；Redis 用的是「RDB 快照全量同步 + 命令传播增量同步 + repl_backlog_buffer」——把两个数据库的机制搞混，面试会一票否决
- ⚠️ "后续都走增量同步"不准确：断线重连后如果复制积压缓冲区不够，会**重新全量同步**

**参考答案 ✅**

**① 主从复制机制（Redis 没有 binlog）：**

- **全量同步**（首次 / 断线后 repl_backlog 不够）：从节点发 psync → 主节点 fork 子进程生成 **RDB 快照**发送 → 从节点清空并加载 RDB → 期间的增量命令经 **replication buffer** 补发
- **增量同步（命令传播）**：正常运行期，主节点执行写命令后把命令发给从节点执行，依赖 **repl_backlog_buffer**

**② 全量 vs 增量时机：**

- 全量：从节点**首次连接**、或断线重连后复制积压缓冲区不足
- 增量：正常运行时的命令传播阶段

> ⚠️ 记忆锚点：Redis 复制 = **RDB 快照 + 命令传播 + repl_backlog**，**没有 binlog**（那是 MySQL 的概念）。

> **追问参考答：** 主从命令复制是**异步**的——主节点本地执行完命令就返回客户端，**不等待从节点确认**，所以无法保证强一致性，只能做到最终一致。

### 34. replication buffer 和 repl_backlog_buffer 有什么区别？它们分别在什么场景下发挥作用？

> **知识点跳转：** [[replication buffer 与 repl_backlog_buffer 对比]] · [[主从复制是怎么实现的？]]

**批改分析区：**

- ❌ **空着**——但这是主从复制的高频追问（面试官爱问"断线重连走全量还是增量"），至少要答出：一个服务全量同步、一个服务增量同步

**参考答案 ✅**

| 对比 | replication buffer | repl_backlog_buffer |
|------|------|------|
| **作用** | 全量同步期间，缓存主节点新增的写命令，发给正在做全量同步的从节点 | 环形缓冲区，记录主节点所有写命令，供**断线**从节点增量同步 |
| **生命周期** | 从节点全量同步期间存在，同步完成即释放 | **常驻**，大小固定（`repl-backlog-size`，默认 1MB） |
| **归属** | 每个从节点一个 | 全局一个，所有从节点共享 |
| **满了** | 可能阻塞主节点（受 `client-output-buffer-limit` 限制） | 环形**覆盖旧命令**，从节点追不上就要全量重同步 |

> 记忆锚点：replication buffer = **全量同步专用**；repl_backlog = **增量同步（断线续传）专用**。

### 35. 为什么需要哨兵（Sentinel）模式？哨兵如何判定主节点故障？「主观下线」和「客观下线」的区别？

> **知识点跳转：** [[为什么要有哨兵？]]

当有一个哨兵在规定时间内没有收到主节点发来的PING后，会将该主节点标记为主管下线，当有一般以上的哨兵都主观认为它下线，就定为客观下线

**追问：** 哨兵是怎么选举出新的主节点的？主从切换后旧主节点怎么办？

旧主节点会向新主节点同步数据

---

**批改分析区：**

- ✅ 主观/客观下线核心概念对（单哨兵判定 → 多数哨兵一致确认）
- ⚠️ 错别字："主管下线"应为**主观下线**、"一般以上"应为**一半以上（quorum）**
- ⚠️ 漏了哨兵解决的**核心问题**（主从无法自动容灾恢复 → 哨兵提供自动故障转移）
- ⚠️ 追问答得太简略：缺"旧主被**降级为从**、向新主做**全量同步清空数据**"的完整链条

**参考答案 ✅**

**① 哨兵解决什么：** 主从架构中主节点宕机后**无法自动容灾恢复** → 哨兵提供**监控 + 自动故障转移**。

**② 主观下线（sdown）：** 单个哨兵在 `down-after-milliseconds` 内没收到主节点的 PONG（心跳），**自己判定**主节点不可达。

**③ 客观下线（odown）：** 多个哨兵（达到 **quorum**，通常为半数以上）通过 `is-master-down-by-addr` 通信，**都认为**该主节点主观下线，才确认客观下线。

**④ 故障转移（两个"领导"别混淆）：**

- **哨兵 leader**：主节点客观下线后，哨兵集群投票（过半）选出一个**哨兵进程**当 leader，负责执行故障转移——它是"**指挥官**"，不亲自上阵
- **新主节点**：leader 从从节点中**筛选+打分**（优先级 slave-priority、数据最新 offset、runid）挑出一个从库升为新主——这是"**新将军**"
- leader 最后通知其它从节点切换主从关系、通知客户端新主地址

> 面试话术：主节点客观下线后，哨兵集群先**选出哨兵 leader**（投票过半），由它执行故障转移——从从节点里筛选+打分挑出新主，通知其它从节点切换主从关系，再通知客户端新主地址。旧主恢复后被降级为从节点，向新主做全量同步。

> **追问参考答：** 旧主节点恢复后被**降级为从节点**，向新主节点发起**全量同步**——因为首次/断线同步是全量，会先**清空本地数据**再做全量同步。

因为单个物理机能存放的数据是有限的，有时需要进行横向扩展，redis cluster就排上用场了

会先对key进行CRC16运算得到16bit

**追问：** 为什么用 CRC16 对 16384 取模？扩容时数据如何迁移？

---

**批改分析区：**

- ✅ 引入原因对（数据量大到单机放不下 → 横向扩展）、CRC16 算 16bit 对

### 37. 集群「脑裂」是什么？会导致什么后果？如何用配置参数避免脑裂导致的数据丢失？

> **知识点跳转：** [[为什么要有哨兵？]] · [[主从复制是怎么实现的？]]

脑裂是指，主节点和从节点以及哨兵的网络不好，导致哨兵认为主节点下线，实际上主节点没挂，只是跟哨兵的网络不好，哨兵认为主节点下线后选举出了新主节点，而旧主节点仍然在处理客户端发来的请求，这时脑裂就出现了，一个集群有了两个主节点，主节点和从节点以及哨兵之间的网络恢复后，旧主节点变为了从节点，它需要向新主节点全量同步数据，之前处理的客户端数据请求就丢失了

可以通过配置参数来避免数据丢失
min-slaves-to-write n:主节点需要至少和n个节点保持连接，否则拒绝处理请求
min-slaves-max-lag n:主节点与从节点之间的响应延迟需要小于n，否则拒绝处理请求

**追问：** min-slaves-to-write 和 min-slaves-max-lag 组合后具体是怎么生效的？

---

**批改分析区：**

- ✅ **这题答得很好**：脑裂成因、数据丢失过程、两个配置参数的作用全对——高可用板块里唯一的高分
- ⚠️ 两个参数名没写全格式（应写成 `min-slaves-to-write N`、`min-slaves-max-lag T`）
- ❌ 追问空着：两个参数**组合**生效的完整逻辑没答

**参考答案 ✅**

**① 脑裂是什么：** 主节点与从节点/哨兵之间网络异常，哨兵判定主节点下线并选举出新主节点，但**旧主节点仍正常接收客户端写请求** → 集群同时出现两个主节点。

**② 为什么丢数据：** 网络恢复后，旧主节点被降级为从节点，向新主节点做**全量同步**（首次同步会清空本地数据）→ 脑裂期间客户端写入旧主的数据**全部丢失**。

**③ 如何避免（两个参数组合）：**

- `min-slaves-to-write N`：主节点必须至少与 **N** 个从节点保持连接，否则**拒绝写请求**
- `min-slaves-max-lag T`：主从复制的 ACK 延迟不能超过 **T 秒**，否则**拒绝写请求**

> **追问参考答：** 两个条件**同时满足才允许写**——主库连接的从库至少 N 个，且复制 ACK 延迟不超过 T 秒。脑裂时旧主是"假故障"，它无法响应哨兵心跳、也无法与从库完成 ACK，条件不满足 → **被限制接收写请求** → 新主上线后只有新主能写，数据不再丢失。
>
> 例：`min-slaves-to-write 1` + `min-slaves-max-lag 12s` + 哨兵 `down-after-milliseconds 10s`——主库卡住 15s 时，哨兵判定客观下线开始切换；同时旧主没有从库能在 12s 内完成复制 ACK，也被禁止接收写请求 → 切换后只有新主能写，无脑裂丢数据。

### 41. Redlock 是怎么工作的？加锁成功的两个条件是什么？它有什么争议？

redlock下，客户端需要向多个节点申请加锁，每个节点都是独立的，只有成功加锁半数以上的节点，才算成功加锁，并且需要判断加锁所花费时间是否小于申请的时间，否则也加锁不成功

有一个时钟抖动争议，说的是如果某一个节点时钟动荡，会导致重复加锁的问题

> **知识点跳转：** [[多节点争抢资源， Redis 分布式锁是怎么实现的？]] · [[Redisson详解]]

**追问：** Martin Kleppmann 对 Redlock 的主要批评是什么？Antirez 如何反驳？Redisson 现在对 RedLock 是什么态度？

Antirez说redlock只是业务上的高可用，而不是理论上的绝对可用，而且时钟抖动问题其他强一致系统也有这种问题

redisson默认不用redlock

---

**批改分析区：**

**评分：7/10**

- ✅ 主问全对：多个独立节点、半数以上成功、总耗时 < 过期时间——两个条件都答了
- ✅ 时钟漂移争议答对；追问答对"Redisson 默认不用 RedLock"
- ⚠️ 追问缺 Martin 的**第二点批评：进程暂停（GC）**，只答了时钟漂移
- ⚠️ Antirez 反驳表述不准："业务上的高可用"应为"**工程上的足够安全**（时钟跳跃生产极少发生、NTP 配成微调可避免）"

**参考答案 ✅**

**① Redlock 思路：** 向多个**相互独立的 master 节点**依次申请加锁（官方建议 5 个），每个加锁操作 `SET NX PX` + 唯一标识 + 给加锁操作设超时（远小于锁 TTL，几十毫秒）。

**② 加锁成功两个条件（同时满足）：**

- **超过半数**（≥ N/2+1）节点加锁成功
- **总耗时（t2 - t1）< 锁过期时间**

加锁成功后重新计算有效时间 = 锁 TTL - 加锁总耗时。

**③ 争议（两大阵营）：**

- **Martin Kleppmann 批评**：① **时钟漂移**——某节点时钟跳跃导致锁提前过期，两个客户端同时持锁；② **进程暂停**——客户端 GC 暂停期间锁过期，恢复后仍以为自己持锁 → 提出 **fencing token**（递增令牌，操作资源时校验，拒绝过期请求）
- **Antirez 反驳**：时钟跳跃生产环境极少发生、NTP 配成微调即可避免；Redlock 追求的是**工程上的"足够安全"**而非理论绝对安全；进程暂停是任何锁服务都面临的问题，不是 Redlock 特有
- **现状**：Redisson 已把 **RedLock 标记为废弃**，默认用单点 Redis 锁 + 看门狗续约

> **追问参考答：** Martin 批评两点——时钟漂移 + 进程暂停（GC），核心方案是 fencing token；Antirez 反驳时钟跳跃极少且可配 NTP 避免、Redlock 是工程足够安全、暂停问题非特有；Redisson 已废弃 RedLock，默认单点 + 看门狗。

**③ EXEC 之后报错（运行时类型错误）：**

```
MULTI
SET name "redis"
LPUSH age "abc"  ← 运行时报错（age 是 String）
SET city "bj"
EXEC             ← SET name 和 SET city 正常执行，LPUSH 单独报错
```

正确的命令照常执行，Redis **不回滚**已执行命令、**不中断**后续命令。

> **追问参考答：** "未执行的命令会被 discard" 是**错的**——EXEC 一旦发出，所有已入队的正确命令**逐一执行**，运行时错误不影响其他命令。DISCARD 是主动清空队列**放弃事务**，对已 EXEC 的命令没有影响。

### 47. Redis 如何实现延迟队列？用什么数据结构？核心命令是什么？有什么问题？



> **知识点跳转：** [[redis八股]] · [[Redis 常见数据类型和应用场景]]

**批改分析区：**

**评分：0/10**

- ❌ **空着**——但这是实战高频题（订单超时取消、延迟消息都靠它），面试十有八九会问

**参考答案 ✅**

**① 数据结构：** 用 **ZSet**，score 存**延迟执行的时间戳**（到期时间）。

**② 核心命令：**

- 生产：`zadd delay_queue <到期时间戳> <任务ID>`
- 消费：`zrangebyscore delay_queue -inf <当前时间戳>` 取出所有已到期任务
- 处理后：`zrem delay_queue <任务ID>` 删除

**③ 问题：** 轮询精度（间隔决定延迟精度，太短费 Redis、太长延迟大）；**消息丢失**（取出后、ZREM 前崩溃，重启后 score 已过期不会再取出）；**重复消费**（多消费者同时取到同一任务）；无原生 ACK 机制。

### 48. SCAN 命令相比 KEYS 命令有什么优势？SCAN 的游标原理是怎样的？

SCAN命令是分批间隔返回，它不会一直阻塞主线程，而KEYS是ON级别的，它会一直扫描完，如果扫描的数据量大会阻塞主线程相当久

> **知识点跳转：** [[SCAN 命令原理详解]] · [[SCAN命令查找大key详解]]

**追问：** SCAN 在遍历过程中如果集合发生 rehash，还能保证不遗漏吗？返回的游标可能为 0 但还没遍历完吗？

---

**批改分析区：**

**评分：5/10**

- ✅ 核心对：SCAN 分批不阻塞 vs KEYS 一次性 O(N) 阻塞
- ⚠️ "ON级别"应为 **O(N) 级别**
- ⚠️ 只答了"不阻塞"这一面，漏了**游标原理**（逆二进制游标、rehash 兼容）
- ❌ 追问空着

**参考答案 ✅**

**① SCAN vs KEYS：**

- **KEYS**：一次性全库遍历，O(N)，数据量大时**阻塞主线程**很久
- **SCAN**：**增量式迭代**，每次返回游标 + 一批 key，分批扫描**不阻塞主线程**

**② 游标原理：** 基于哈希桶索引的**逆二进制游标**（反掩码递增），每次 SCAN 传入上次返回的游标，**游标返回 0 表示遍历结束**。遍历开始后新增的 key 不保证被访问（但保证遍历开始前存在的 key 最终都能被访问到）。

> **追问参考答：** SCAN 通过游标的**高位递增设计**兼容 rehash——扩容/缩容时用低位掩码 + 游标高位保证**已开始的桶不遗漏**，所以**能保证不遗漏**（但可能重复返回）；**游标为 0 即遍历结束**，不存在"游标为 0 但还没遍历完"的情况（可能出现游标非 0 但某批返回空集）。

## 十、消息队列（3 题）

### 49. 用 List 实现消息队列有什么缺陷？Stream 是怎么解决这些问题的？

用List实现消息队列有几个缺陷，一个是没有消息持久化，POP后消息就彻底消失了，无法回溯查看，而Stream天然保证了消息持久化，可以随时拉出来看。还有就是无法以消费者组的形式消费数据，Stream通过XREADGROUP实现。还有一个问题就是如果消息分配给一个消费者处理，它还没处理完就宕机了，这个消息就彻底消失了，而Stream有一个Pending Entry List，消息处理完才会ACK，未被确认的消息不会退出PEL


> **知识点跳转：** [[List与Stream消息队列对比]] · [[Stream消息队列]]

**追问：** List 能实现「消费者组」消费吗？不能的话是为什么？

---

**批改分析区：**

**评分：8/10**

- ✅ **答得很好**：持久化/回溯、消费者组、PEL+ACK 防丢失三点全对，还点出了"宕机消息消失"的场景
- ❌ 追问空着（List 为什么不能消费者组）
- ⚠️ 可补 List 的另一个缺陷：生产者需**自行实现全局唯一 ID**

**参考答案 ✅**

**① List 做消息队列的缺陷：**

- **无消息持久化**：`POP` 后消息立即消失，无法回溯
- **无法消费者组消费**：`BRPOP` 是竞争消费，一个消息只能被一个消费者拿到
- **生产者需自行实现全局唯一 ID**（Stream 自动生成"时间戳-序号"ID）

**② Stream 的解决方案：**

| List 缺陷 | Stream 怎么解决 |
|-----------|----------------|
| 无持久化 | 追加式日志结构，消息持久化可回溯 |
| 无消费者组 | `XREADGROUP` + 消费组（last-delivered-id 分配） |
| 消息丢失 | **PEL + ACK**，未 ACK 的消息不消失，可 XCLAIM 重试 |
| ID 不自增 | 消息 ID 自动生成（时间戳-序号，全局唯一有序） |

> **追问参考答：** List **不能**实现消费者组——`BRPOP` 只能竞争消费（谁先抢到谁拿，消息 POP 即消失），无法实现"组内多消费者分工 + 消息可回溯/可重试"。Stream 用 `XREADGROUP` 按组内 `last-delivered-id` 分配，每个消息只给一个消费者。

### 50. Stream 的消费者组是怎么工作的？ACK 机制和 PendingList 分别是什么？

当消费者通过XREADGROUP申请消费消息时，redis会根据对应的group的last-delivered-id分配消息给消费者，在正常情况下，一个消息只会被一个消费者处理，redis stream是基于PEL的最少交付一次语义，当一个消息被分配后，如果未被ACK那么它将会一直存在在PEL中，其他消费者可以通过XCLAIM认领他重新消费

> **知识点跳转：** [[Stream消息队列]] · [[Stream的ACK与PendingList]]

**追问：** 消费者消费了消息但不 ACK，消息会一直留在 PendingList 吗？重复消费怎么处理？

---
当使用XREADGROUP消费消息，消息投递之后进入当前消费者组的PEL待确认列表。
只有调用XACK，消息才从PEL移除，标记消费成功，注意Stream原始消息不会被删除。
如果消费者拿到消息未ACK就宕机，消息会滞留在PEL，Redis不会自动重发。我们需要独立定时任务，通过XPENDING扫描PEL中超时消息，使用XCLAIM将消息重新认领，交给其他消费者处理。我们还可以根据认领次数delivery‑count，把多次失败消息投递到死信。
**批改分析区：**

**评分：8/10**

- ✅ **主问全对**：last-delivered-id 分配、单消费者处理、PEL at-least-once、XCLAIM 认领——机制讲得很清楚
- ❌ 追问空着

**参考答案 ✅**

**① 消费者组工作：** `XREADGROUP` 按组的 **`last-delivered-id`** 把新消息分配给组内消费者，**每条消息只分配给一个消费者**（组内负载均衡）。

**② ACK 机制 / PEL：**

- 消费者收到的消息会进入该消费者的 **PEL（Pending Entries List，待处理列表）**
- 处理完调用 **`XACK`** 才会从 PEL 移除
- 这是 **at-least-once（至少一次交付）** 语义——**未 ACK 的消息一直留在 PEL**，不会丢

**③ 失败重试：** 其他消费者可用 **`XCLAIM`** 认领超时未 ACK 的消息重新消费。

> **追问参考答：** 不 ACK 消息**会一直留在 PendingList（PEL）**——这是 at-least-once 语义，保证消息不丢。重复消费处理：`XCLAIM` / `XAUTOCLAIM` 让其他消费者认领超时未 ACK 的消息；业务侧做好**幂等**（消息有唯一 ID）。

### 51. XREADGROUP 的三种读取模式（`>`、`$`、`0`）分别代表什么含义？

 `>`是拉取还未被认领过的消息
 `0`是拉取已被自己认领但未ACK的消息
 `$`是拉取发出XREADGROUP后的最新消息

> **知识点跳转：** [[Stream的XREADGROUP三种模式]] · [[Stream的消息回溯能力]]

**追问：** 用 `0` 模式读取能实现什么能力？这和 Stream 的消息回溯有什么关系？

实现故障后恢复，如果消费者A宕机了，回来后就可以用0来重新处理自己之前的消息

---

**批改分析区：**

**评分：8.5/10**

- ✅ **三种模式全对，追问也答了**（故障恢复 + 回溯）——本板块最佳
- ⚠️ `$` 可更准确："从流末尾开始，只读之后到达的新消息，**不读历史**"

**参考答案 ✅**

| 模式      | 含义                                        |
| ------- | ----------------------------------------- |
| **`>`** | 读取**还没被分配给任何消费者**的新消息（新消息）                |
| **`0`** | 读取当前消费者，在所属消费组PEL列表里自己认领、尚未ACK的消息，用于故障恢复。 |
| **`$`** | 从**流的末尾**开始，只读取之后到达的新消息，**不读历史**（常配合阻塞等待） |

> **追问参考答：** `0` 模式读取自己 PendingList 里未 ACK 的消息——用于**故障恢复**（消费者宕机回来重处理未完成消息）和**消息回溯**（查历史处理情况）。这正是 Stream 可回溯能力的体现：消息持久化在流里，任意消费者都能按 ID 区间重读。
