# 虚拟线程详解

## 定义

虚拟线程（Virtual Thread，又称协程 / 纤程）是 Java 21 正式发布（JEP 444）的一种**轻量级线程**，由 JVM 管理而非操作系统。它解决了传统平台线程（Platform Thread）"**一个请求一个线程**"模型下线程数量受限、上下文切换开销大的问题。

→ **通俗理解**：以前一个线程就是一条"操作系统级别的车道"，开多了就堵；虚拟线程是 JVM 在一条操作系统车道上虚拟出的**无数条"微车道"**，轻量到可以轻松创建上百万条。

---

## 核心原理

### 传统平台线程（Platform Thread）

```
┌─────────────────────────────────────────┐
│  Java 线程      ←→      OS 线程          │
│  1:1 映射                              │
│  栈空间 ~1MB（固定分配）                   │
│  创建 / 切换都走内核态（昂贵）               │
└─────────────────────────────────────────┘
```

- 每个平台线程对应一个 OS 线程，栈空间创建时就固定分配了
- 线程切换由 OS 内核调度 = **用户态→内核态→用户态**，开销大
- 一台机器通常只能创建几千个平台线程

### 虚拟线程（Virtual Thread）

**执行流程**：
1. 虚拟线程被调度 → 找空闲载体线程 → 将其 StackChunk（堆上）的栈帧**拷贝到**载体线程原生栈 → 执行
2. 遇到阻塞 I/O（yield）→ 载体线程原生栈上该虚拟线程的帧**拷回**堆上的 StackChunk → 载体线程原生栈清空 → 变为空闲状态，可被其他虚拟线程复用
3. I/O 就绪 → 找任意空闲载体线程 → StackChunk 帧再次拷贝到该载体线程原生栈 → 继续执行

> **关键**：虚拟线程自己的栈**一直在堆上**（StackChunk 对象），载体线程的原生栈只是**临时执行场地**。拷贝上去跑，跑完拷回堆。载体线程的栈不会被销毁，只清空复用。

```
┌─────────────────────────────────────────┐
│  虚拟线程（N:M 模型）                     │
│                                         │
│  栈在堆上动态分配（轻量）                   │
│  挂起时栈卸载到堆 → 归还载体线程            │
│  恢复时从堆加载回载体线程                   │
│                                         │
│  载体线程（平台线程池）                     │
│  ┌──┬──┬──┬──┬──┐                       │
│  │P1│P2│P3│P4│..│  ← 少量（通常 CPU 核数）│
│  └──┴──┴──┴──┴──┘                       │
│      ↕ 挂载 / 卸载（纯用户态）             │
│  虚拟线程（数量巨大）                       │
│  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐       │
│  │V1│V2│V3│V4│V5│V6│V7│..│..│..│       │
│  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘       │
│  可创建数百万个                            │
└─────────────────────────────────────────┘
```

关键点：

|       | 平台线程          | 虚拟线程                     |
| ----- | ------------- | ------------------------ |
| 映射关系  | 1:1 映射到 OS 线程 | N:M（大量虚拟线程挂载到少量载体线程）     |
| 栈空间   | 固定分配 ~1MB     | 堆上动态分配，挂起时回收             |
| 创建开销  | 微秒级，但受 OS 限制  | 纳秒级，可创建数百万               |
| 上下文切换 | 内核态调度（昂贵）     | 用户态调度（轻量）                |
| 适用场景  | CPU 密集型       | **I/O 密集型**（等待时自动让出载体线程） |

**为什么虚拟线程适合 I/O 密集型？**

I/O 操作的特点是"大量等待，少量计算"。平台线程在等待 I/O（如数据库查询、RPC 调用）时，整个 OS 线程被阻塞挂起，无法干任何其他事——资源白白浪费。

虚拟线程在遇到阻塞 I/O 时会**自动 yield**：
1. 将栈帧从载体线程原生栈拷回堆上的 StackChunk
2. 载体线程恢复空闲，立即挂载另一个虚拟线程执行
3. I/O 就绪后，虚拟线程找任意空闲载体线程重新挂载继续执行

结果是：**载体线程不再空等**，有限的平台线程轮番执行海量虚拟线程的计算部分，大幅提升吞吐量。

## 使用方式

### 方式一：静态方法

```java
Thread vt = Thread.startVirtualThread(() -> {
    System.out.println("虚拟线程执行: " + Thread.currentThread());
});
vt.join();
```

### 方式二：Thread.ofVirtual() 构建器

```java
Thread vt = Thread.ofVirtual()
    .name("my-vt")
    .unstarted(() -> {
        System.out.println("Hello from virtual!");
    });
vt.start();
```

### 方式三：ExecutorService

```java
// 虚拟线程的线程池
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> {
            // 每个任务自动分配一个虚拟线程
            Thread.sleep(1000);  // sleep 时不阻塞载体线程
            return "done";
        });
    }
}  // try-with-resource 自动等待所有任务完成
```

## 虚拟线程怎么"让出"载体线程

核心机制：**当虚拟线程执行阻塞 I/O 操作时，自动从载体线程上卸载（yield），载体线程转去执行其他虚拟线程。**

```java
// 传统平台线程：sleep(1000) 会阻塞整个 OS 线程
// 虚拟线程：sleep(1000) 时，虚拟线程的栈被卸载到堆
//           载体线程被释放去执行别的虚拟线程
//           1000ms 后，虚拟线程重新挂载到某个载体线程继续执行
```

这是**自动**发生的，不需要写任何特殊代码。对开发者透明，看起来就像普通线程一样。

## 适用场景

### ✅ 适合：I/O 密集型应用

- Web 服务器（Tomcat、Spring Boot）：每个请求一个虚拟线程
- 数据库访问（JDBC、Redis、RPC）：等待 I/O 时不占载体线程
- 微服务间调用链：大量等待时间被充分利用

### ❌ 不适合：CPU 密集型计算

- 视频编码、加解密、大数据计算等持续占用 CPU 的任务
- 虚拟线程在 CPU 计算时不会主动 yield，用平台线程反而更合适

## 注意事项

| 注意点                      | 说明                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| **不要池化虚拟线程**             | 虚拟线程很轻量，每次创建新线程比==池化复用==更高效，`Executors.newVirtualThreadPerTaskExecutor()` 就是这么设计的        |
| **synchronized 会钉住载体线程** | 虚拟线程进入 `synchronized` 块时会被"钉住"在载体线程上，不会 yield。大量虚拟线程抢同一个锁可能导致性能退化。建议用 `ReentrantLock` 替代 |
| **ThreadLocal 慎用**       | 虚拟线程数量巨大，ThreadLocal 会占用大量内存。且虚拟线程可能在不同载体线程间迁移，ThreadLocal 语义受影响                         |
| **不要用线程优先级**             | 虚拟线程不支持 `setPriority()`，会被忽略                                                             |

> [!warning] 「建议用 ReentrantLock 替代」仅适用于 JDK 21~23
> 上面 synchronized 钉住载体线程的结论，在 **JDK 24（2025-03，[JEP 491](https://openjdk.org/jeps/491)）已被修复**：虚拟线程在 `synchronized` 块内阻塞也能正常从载体线程上卸下，不再 pin。JDK 24+ 上 `synchronized` 与 `ReentrantLock` 在「钉不钉住」这点上**没有区别**。仅 `native` 方法 / FFI（JNI、Foreign Function）调用等少数底层路径仍会发生剩余 pinning。

### 为什么 ReentrantLock 不钉住（JDK 21~23 的原理）

- **synchronized 钉住的根因**：monitor 在 JVM 底层（C++ 层）实现，锁的归属关系挂在 native 栈帧上，绑定到**操作系统线程**。虚拟线程进入 synchronized 块后若发生阻塞，调度器无法把它从载体线程上卸下来，于是被 pinned，载体线程也跟着被占用，吃不到虚拟线程「廉价阻塞」的好处。
- **ReentrantLock 不钉住的原因**：它是**纯 Java 实现**，底层靠 `AQS`（AbstractQueuedSynchronizer）+ `LockSupport.park()`。`park` 是调度器能感知的挂起点——线程一 park，调度器就能把虚拟线程从载体线程卸下，载体线程转去执行其他虚拟线程。

## 面试话术

> "虚拟线程是 Java 21 推出的轻量级线程，采用 N:M 模型——大量虚拟线程挂载到少量平台线程（载体线程）上执行。它的栈在堆上动态分配，执行阻塞 I/O 时自动卸载到堆，释放载体线程去执行其他虚拟线程，整个过程是纯用户态切换，远比平台线程的内核态切换轻量。这使得我们可以创建上百万个虚拟线程，大幅提升 I/O 密集型应用的吞吐量。但注意 CPU 密集任务不适合，且要避免 synchronized 钉住载体线程的问题。"
