# 一、JVM 内存模型（共 3 题）

## 第 1 题｜7/10

请画出 JVM 运行时数据区的结构，列出五个核心区域，分别说明每个区域的**作用、是否线程私有、以及可能抛出的异常**。

### 我的答案

虚拟机栈，堆，程序计数器，本地方法栈，元空间

- 虚拟机栈：每个线程一个虚拟机栈，生命周期与线程一致，当调用方法时会创建栈帧并压入其中，会出现堆溢出和栈溢出
  - 栈帧包括：局部变量表、操作数栈、动态链接、方法返回值
- 堆：存放对象实例，虚拟机启动时被创建，被所有线程共享，会出现堆溢出
- 程序计数器：每个线程私有的，存放当前线程下一个要执行的字节码指令地址，是唯一一个不会出现堆溢出和栈溢出的内存区域
- 本地方法栈：和虚拟机栈类似，主要用于存放本地方法的栈帧，会出现堆溢出和栈溢出
- 元空间：用于存放类的元数据信息、运行时常量池、JIT生成的代码缓存等，会出现堆溢出

### 批改

**✅ 答对的核心内容**

五个区域全部列出，线程私有/共享判断正确，异常类型有提及，程序计数器无异常也答对了。

**🔴 知识硬伤**

1. **异常类型名称混用**："堆溢出/栈溢出"是口语说法，面试中必须用正确名称：
   - 虚拟机栈/本地方法栈：栈深度超限 → `StackOverflowError`；动态扩展失败 → `OutOfMemoryError`
   - 堆：`OutOfMemoryError: Java heap space`
   - 元空间：`OutOfMemoryError: Metaspace`

2. **元空间作用描述有误**："JIT生成的代码缓存"实际放在 **Code Cache**，不在元空间。元空间主要存放类的结构信息（字段、方法、接口、常量池引用等）。

**🎯 面试追问点**

- "程序计数器为什么是唯一不会OOM的区域？" → 只存一个指针大小的数据，不动态分配
- "虚拟机栈什么时候是 OOM，什么时候是 StackOverflow？" → 见 [[StackOverflowError与OutOfMemoryError（虚拟机栈）]] 详解
- "元空间相比永久代有什么优势？" → 使用本地内存，上限由系统内存决定；GC 触发条件也不同

## 第 2 题｜6/10

请说明**运行时常量池**和**字符串常量池**的区别。它们在 JDK 6、JDK 7、JDK 8+ 三个版本中各位于 JVM 的哪个区域？为什么说两者是"包含关系"但又相互独立？

### 我的答案

- 运行时常量池存放方法的符号引用
- 字符串常量池存放字符串字面量和intern生成的字符串对象

- JDK6中，它们都存在于永久代
- JDK7中，字符串常量池被转移到堆中，运行时常量池在永久代
- JDK8中，字符串常量池仍然在堆中，运行时常量池在元空间中

包含指的是运行时常量池中的字符串的符号引用指向字符串常量池中的字符串字面量；
独立指的是从JDK7后，它们存在在不同的内存空间中，独立互不影响

### 批改

**✅ 答对的核心内容**

三个版本的位置变迁说对了，JDK6→7→8 的迁移路径清晰，"包含"和"独立"都有作答。

**🔴 知识硬伤**

1. **运行时常量池描述过窄**：只说"方法的符号引用"不够完整。运行时常量池存放的是 `.class` 文件常量池的运行时版本，包括：**字面量（数字、字符串字面量引用）、符号引用（类名、字段名、方法名）、以及解析后的直接引用**。

2. **"包含关系"解释方向偏了**：你说的是"引用关系"，不是"包含关系"。真正的"包含"是指：JDK6 及之前，字符串常量池**本身就是**运行时常量池的一部分，物理上在永久代同一块区域。JDK7 之后才分离出去，所以说"曾经是包含，现在是独立"更准确。

**🎯 面试追问点**

- "为什么 JDK7 要把字符串常量池移到堆里？" → 永久代空间有限且不好调整，字符串滥用容易 OOM；移到堆里可以被 GC 正常管理
- "`String s = new String("abc")` 创建了几个对象？" → 常量池里没有 "abc" 时：2个；有则：1个
- "`s.intern()` 在 JDK6 和 JDK7 行为有什么区别？" → JDK6 在永久代复制一份新对象；JDK7+ 在堆中保存引用，不复制

## 第 3 题｜6/10

Java 堆被分为哪几个部分？Eden : Survivor 的默认比例为什么是 8:1:1？假如 Minor GC 后 Survivor 装不下存活对象，JVM 会怎么处理？请完整描述**空间分配担保机制**的执行流程。

### 我的答案

堆被分为两个部分：年轻代和老年代。
因为大部分对象都是朝生夕死的，在MinorGC后存活下来的极少。
如果装不下，JVM会直接将该对象放到老年代中。

每次进行MinorGC后，JVM会判断当前老年代的最大连续空间是否大于年轻代的所有对象占用内存总和，还会判断是否开启了担保机制以及当前老年代的最大连续空间是否大于以往晋升的大对象平均内存占用，如果有以上任意一个不符合，就会触发MajorGC

### 批改

**✅ 答对的核心内容**

年轻代/老年代划分、8:1:1 的理由（朝生夕死）、担保机制的主要判断条件基本到位。

**🔴 知识硬伤**

1. **8:1:1 解释不完整**：没有说明为什么两个 Survivor 各占 1 份。每次 Minor GC 时，Eden + From Survivor 存活对象复制到 To Survivor，始终保持一个 Survivor 为空。两个 Survivor 等大是为了交替使用，**总有效利用率 90%（8+1），浪费 1 份**，这是设计的折中点。

2. **担保机制的触发时机错误（硬伤）**：担保检查发生在 **Minor GC 之前**，不是之后。正确流程：
   - Minor GC **前**：检查老年代最大连续空间 ≥ 年轻代所有对象总大小 → 满足则直接做 Minor GC
   - 不满足：检查是否允许担保失败（`HandlePromotionFailure`，JDK7 后默认开启）
   - 允许担保失败：再检查老年代最大连续空间 ≥ 历次晋升平均大小 → 满足则冒险 Minor GC，不满足则触发 Full GC

**🎯 面试追问点**

- "担保机制失败了会怎样？" → 触发 Full GC；Full GC 后还放不下则 OOM
- "大对象为什么直接进老年代？" → 复制算法代价太高，大对象复制成本很大
- =="什么叫动态年龄判定？" → Survivor 中同年龄对象总大小 > Survivor 一半时，该年龄及以上的对象直接晋升老年代==

# 二、类加载机制（共 3 题）

## 第 4 题｜7/10

类加载过程有哪七个阶段？重点说明**准备（Preparation）**和**初始化（Initialization）**两个阶段各做了什么。`static final int MAX = 100` 和 `static final int MAX = getValue()` 在准备阶段的行为有什么不同？为什么？

### 我的答案

- 加载：将字节码字节流的静态存储结构转化为运行时Class对象
- 验证：检验字节码字节流是否符合JVM规范
- 准备：为静态变量分配内存并赋初值
- 解析：将符号引用转换为直接引用
- 初始化：执行clinit方法
- 使用
- 卸载

`static final int MAX = 100` 是编译时常量，在准备阶段进行赋值；
`static final int MAX = getValue()` 是运行时常量，在初始化阶段进行赋值

### 批改

**✅ 答对的核心内容**

七个阶段全部列出，顺序正确。编译时常量 vs 运行时常量的区分答对了，这是本题核心考点。

**🔴 知识硬伤**

1. **"加载"阶段描述不准确**：加载阶段做三件事：①通过全限定名获取二进制字节流；②将字节流的静态结构转为方法区的运行时数据结构；③在**堆中生成对应的 `Class` 对象**作为方法区数据的访问入口。你的描述缺少了"在堆生成 Class 对象"这个关键步骤。

2. **"准备阶段赋初值"没说清楚初值是什么**：初值是**零值**（`int` → 0，`boolean` → false，引用 → null），不是程序员写的赋值值。`static int x = 5` 在准备阶段 x=0，初始化阶段才变成 5。没说清楚这点，面试追问时容易答错。

3. **`<clinit>` 描述过简**：`<clinit>` 由编译器自动收集**所有静态变量的赋值动作和静态代码块**合并生成，执行顺序按源码顺序。

**🎯 面试追问点**

- "准备阶段的初值是什么？" → 零值，不是程序员写的赋值
- "`<clinit>` 和 `<init>` 有什么区别？" → `<clinit>` 是类构造器（静态初始化）；`<init>` 是实例构造器
- "类初始化的主动引用有哪些触发时机？" → 见 [[类初始化的主动引用与被动引用]] 详解（含 5 种主动引用 + 6 种被动引用陷阱）

## 第 5 题｜5/10

什么是双亲委派模型？它的工作流程是怎样的？为什么需要这种设计？请举一个**需要打破双亲委派模型**的实际场景，并说明如何实现。

### 我的答案

一个类加载器在收到类加载请求时，先不会自己处理，而是委托给他的父类加载器进行加载，如果父类加载器不能加载，自己才会去尝试加载

- 可以防止类的重复加载，使得类加载器之间的层级关系更加清晰，还可以防止用户自定义类对系统类库篡改，保证了安全性

### 批改

**✅ 答对的核心内容**

双亲委派的基本流程描述正确，三条好处（防重复加载、层级清晰、安全性）是对的。

**🔴 知识硬伤**

1. **三层类加载器结构完全没提**：双亲委派必须配合层次结构讲才完整，否则"委托给父类加载器"是在委托给谁？
   - 见 [[三层类加载器与classpath]] 详解（Bootstrap / Extension / Application 三个加载器 + classpath 详解）

2. **"打破双亲委派"的场景完全没答**：这是题目明确要求的，直接失分。常见场景：
   - **JDBC/SPI 机制**：`java.sql.Driver` 由 [[三层类加载器与classpath|Bootstrap ClassLoader]] 加载，但 MySQL 驱动实现类在 classpath，Bootstrap 加载不到，所以用**[[线程上下文类加载器（TCCL）]]**反向委托给 AppClassLoader
   - **Tomcat**：每个 Web 应用有独立的 `WebappClassLoader`，优先加载自己的类，隔离不同应用的依赖版本
   - **实现方式**：继承 `ClassLoader`，重写 `loadClass()` 方法（见 [[重写loadClass与findClass的区别]]：重写 findClass 不破坏双亲委派 vs 重写 loadClass 才是真正破坏）

**🎯 面试追问点**

- "为什么重写 `findClass` 不是破坏双亲委派，重写 `loadClass` 才是？" → `loadClass` 里实现了委派逻辑；`findClass` 只是委派失败后的兜底方法
- "Tomcat 为什么要打破双亲委派？" → 不同 WebApp 可能依赖同一个库的不同版本，必须隔离
- "Bootstrap ClassLoader 为什么不是 Java 对象？" → C++ 实现，是 JVM 的一部分

# 三、垃圾回收（共 4 题）

## 第 7 题｜7/10

请分别说明 **Minor GC**、**Major GC**、**Full GC** 的作用范围和触发条件。其中 Full GC 的触发条件有哪些？**空间分配担保失败**和**元空间不足**分别是怎么导致 Full GC 的？

### 我的答案

当Eden区内存空间不足时，会触发Minor GC，Minor GC会对年轻代中的Eden区和两个Survivor区进行清理，存活下来的对象会轮流放S0/S1；
当老年代内存空间不足时，会触发Major GC，Major GC会对老年代进行垃圾回收；
当年轻代和老年代都空间不足时，会触发Full GC，Full GC会对整个堆进行垃圾回收。

触发条件有：
- 内存担保失败：当Minor GC执行后，JVM会判断老年代的最大连续空闲内存是否大于等于目前年轻代所有内存占用总和，以及判断是否通过参数开启了内存担保机制和判断老年代的最大连续空闲内存是否大于历代晋升的大对象的平均内存占用，如果以上任意一条不满足，则会触发Full GC
- 当经过Minor GC、Major GC后，仍找不到足够大的内存空间来进行实例化，就会触发Full GC
- 元空间不足一般是由于加载的类过多，Full GC会对不再引用的类加载器、类的元数据进行回收

### 批改

**✅ 答对的核心内容**

三种 GC 的作用范围和主要触发条件基本正确，担保失败和元空间不足两个触发点都答到了。

**🔴 知识硬伤**

1. **担保机制触发时机仍然写错**（同第 3 题）：判断在 **Minor GC 之前**，不是之后。面试官听到"之后判断"会直接追问。

2. **Full GC 触发条件不完整**，还有：
   - `System.gc()` 显式调用（通常会触发）
   - **堆外内存（Direct Memory）不足**：NIO 的 `DirectByteBuffer` 分配失败时会触发 Full GC 尝试回收（见 [[DirectByteBuffer与堆外内存回收]]：Full GC 不回收堆外内存，但回收堆内的 DirectByteBuffer 对象会触发 cleaner 释放堆外内存）

**🎯 面试追问点**

- "Full GC 一定会 STW 吗？" → 取决于 GC 器，CMS 并发阶段不 STW，但 Final Remark 阶段会；G1 的 Mixed GC 也有短暂 STW
- "老年代空间不足为什么先尝试 Major GC 而不是直接 Full GC？" → CMS 等 GC 器有独立的老年代并发回收阶段，先并发回收，回收后还不够才升级 Full GC

## 第 8 题｜7/10

为什么说 G1 垃圾回收器**弱化了分代的概念**？G1 适合大内存堆的核心原因是什么（从 Region 分块、可预测停顿、碎片控制、增量整理四个角度说明）？

### 我的答案

G1垃圾回收器推出了分区的概念，它将堆划分为若干数量的大小均等的Region（1-32M）。
G1每次垃圾回收不是对整个堆所有Region进行，而是对部分Region，由于G1垃圾回收器可以搭建可预测停顿的模型，它会挑选回收效益最大的Region进行回收，这使得它在面对Region很多——也就是大内存堆时，反而更加容易控制响应时间。
不仅如此，G1采用的是复制&整理算法，这两种算法都不容易产生内存碎片。

### 批改

**✅ 答对的核心内容**

Region 分块讲清楚了，可预测停顿 + 回收效益优先的逻辑是对的，复制+整理算法减少碎片也答到了。

**🔴 知识硬伤**

1. **"弱化分代"没有解释清楚**：G1 分代**逻辑上仍然存在**（Eden Region、Survivor Region、Old Region），但物理上不再是连续两块内存，Region 可以动态切换角色。没有解释这一点，面试官会说"你没真正理解弱化的含义"。另外 **[[G1 Humongous Region（大对象区）]]**（大对象区，超过 Region 一半的对象）没有提到。

2. **增量整理角度完全没答**：题目明确要求从四个角度说明，增量整理是空的。G1 的增量整理是指：不必每次整理整个堆，每次只回收部分 Region，配合 **Remembered Set** 追踪跨 Region 引用，这才是 G1 能控制停顿时间的底层机制。

3. **Remembered Set 没提**：G1 为每个 Region 维护 RSet 记录哪些其他 Region 引用了自己，是实现增量回收的关键数据结构。

**🎯 面试追问点**

- "G1 的 Remembered Set 是干什么的，有什么代价？" → 追踪跨 Region 引用；代价是写屏障（Write Barrier）和额外内存开销（约 10-20%）
- "Humongous 对象有什么特殊处理？" → 直接进 Old Region 的连续空间，不走 Eden，GC 时单独处理
- "G1 的 Mixed GC 和 Full GC 有什么区别？" → Mixed GC 回收所有 Young Region + 部分 Old Region，并发+增量；Full GC 是 STW 兜底（JDK10 后改为并行）

1. **初始标记（Initial Mark）**：STW，标记 GC Roots 直接关联的对象，极快
2. **并发标记（Concurrent Mark）**：与用户线程并发，从 GC Roots 遍历整个老年代，耗时最长
3. **重新标记（Remark）**：STW，修正并发标记期间用户线程导致的引用变动（增量更新），比初始标记慢但比并发标记快
4. **并发清除（Concurrent Sweep）**：与用户线程并发，清除死亡对象

**CMS 优缺点**

- 优点：STW 时间短，主要阶段并发执行
- 缺点：
  - **内存碎片**：标记-清除算法，不整理内存，长时间运行后大对象分配失败触发 Full GC
  - **浮动垃圾**：并发清除时产生的新垃圾只能等下次 GC
  - **并发模式失败（Concurrent Mode Failure）**：并发清除期间老年代满了，退化为 Serial Old（单线程 STW Full GC），停顿可能达到秒级，这是 CMS 最大的痛点
  - CPU 资源与用户线程竞争

**CMS vs G1 对比**

| 维度     | CMS          | G1                           |
| ------ | ------------ | ---------------------------- |
| 算法     | 标记-清除        | 复制+整理                        |
| 内存碎片   | 有，长时间运行后严重   | 无，每次回收都整理                    |
| 停顿可预测性 | 弱，大堆扫描时间不可控  | 强，可设置 `-XX:MaxGCPauseMillis` |
| 大堆表现   | 老年代越大扫描越慢    | 增量回收，停顿不随堆增大线性恶化             |
| 适用场景   | 4G 以下堆，追求低延迟 | 6G 以上大堆，需要可预测停顿              |

**CMS 在大内存堆下为什么不如 G1：** CMS 并发标记需要扫描整个老年代，堆越大扫描越慢；加上碎片问题在大堆长期运行后积累，最终引发 Concurrent Mode Failure 退化为单线程 STW Full GC，停顿不可控。

## 第 10 题｜6/10

请完整描述一个对象从 `new` 创建到最终被 GC 回收的整个生命周期，包括它经过的内存区域、每个区域的触发条件、以及 GC 在不同阶段的角色。

### 我的答案

1. 如果该对象不是大对象的话，它会被分配到Eden区；否则它会被直接分配到老年代
2. 接着，Eden区内存不足，会触发Minor GC，如果该对象仍然被强引用着，它还会被转移到Survivor区
3. 在经过多次Minor GC后，它如果仍然存活，会被转移到老年代

### 批改

**✅ 答对的核心内容**

大对象直接进老年代、Eden 不足触发 Minor GC、多次 GC 后晋升老年代，这条主线是对的。

**🔴 知识硬伤**

1. **TLAB 没有提**：对象创建的第一步不是直接分配到 Eden，而是先尝试在 **[[TLAB详解|TLAB（Thread-Local Allocation Buffer）]]** 中分配。TLAB 是 Eden 中每个线程的私有缓冲区，避免多线程竞争 Eden 分配指针。这是面试高频点，几乎一定会被追问。

2. **晋升老年代的条件只说了两个**，完整应有四个：
   - 大对象（`-XX:PretenureSizeThreshold`）直接进老年代 ✅
   - Survivor 空间不足，直接晋升 ✅
   - 年龄达到阈值（默认 15 次，`-XX:MaxTenuringThreshold`）❌ 未提
   - 动态年龄判定：Survivor 中同年龄对象总大小 > Survivor 一半，该年龄及以上直接晋升 ❌ 未提

3. **GC 回收的判定过程完全没答**：题目问"最终被 GC 回收"的过程，需要说明：
   - **可达性分析**：GC Roots 不可达 → 第一次标记
   - **`finalize()` 机制**：第一次标记后若覆盖了 `finalize()` 且未执行过，放入 F-Queue 执行；执行后仍不可达才真正回收（JDK18 已废弃，提一句即可）

**🎯 面试追问点**

- "TLAB 满了怎么办？" → 重新申请 TLAB；若 Eden 也放不下，触发 Minor GC；还不行则直接在 Eden 用 CAS 分配
- "GC Roots 包含哪些？" → 虚拟机栈引用的对象、方法区静态属性/常量引用的对象、本地方法栈 JNI 引用的对象、JVM 内部引用（Class 对象、常驻异常对象）、被同步锁持有的对象
- "对象一定在堆上分配吗？" → 不一定，JIT 的**逃逸分析**可以将不逃逸的对象**栈上分配**，方法结束后随栈帧销毁，完全不经过 GC
