## 第一部分：项目概览与架构设计

### Q1：请简单介绍一下你的 Nozomi-Mall 项目，以及你在其中的角色？

**口述回答：**

"这是一个基于 Spring Cloud Alibaba 微服务架构的 B2C 电商平台。我主要负责核心链路的设计与开发，包括**秒杀系统、商品搜索、分布式事务**以及**多级缓存架构**的落地。

项目拆分了 **14 个微服务**，涵盖了从商品管理、搜索、订单、支付到秒杀的全流程。在这个项目中，我解决了两个核心问题：

1. **高并发下的系统稳定性**：通过 6 层漏斗架构支撑了峰值 5,000+ QPS 的秒杀流量。
2. **数据一致性与解耦**：利用 Canal CDC 实现了 MySQL 到 ES 的毫秒级同步，利用 Seata 和 RocketMQ 保证了分布式事务的最终一致性。

这不仅仅是一个课程实训，我是按照生产级标准来设计它的，特别是针对**缓存一致性**和**防超卖**做了深入的工程实践。"

### Q2：为什么选择 Spring Cloud Alibaba 而不是 Spring Cloud Netflix？为什么技术栈里选了 Nacos？

**口述回答：**

"主要考虑的是**生态成熟度**和**社区活跃度**。Spring Cloud Netflix 的核心组件如 Eureka、Hystrix 等都已经进入维护模式，不再推荐用于新系统。而 Spring Cloud Alibaba 贴合国内业务场景，比如 Nacos、Sentinel 都是阿里经过双十一验证的开源产品。

具体到 **Nacos**，它最大的优势是**注册中心与配置中心二合一**。相比于 Eureka + Config 的组合，Nacos 减少了维护成本，而且它支持动态 DNS 服务和 DNS 协议，对于 K8s 等云原生环境支持更好。在我们的项目中，Nacos 统一管理了 14 个微服务的服务发现和配置热更新，运维效率很高。"

## 第二部分：高并发与秒杀系统（核心亮点）

### Q3：你的秒杀系统设计了"6 层漏斗架构"，请详细讲讲每一层的作用，为什么要这样设计？

**口述回答：**

“秒杀的核心矛盾是**瞬间巨大的流量**和**有限的库存**。我的设计思想是**成本梯度**——在最外层用最低成本挡掉最多的流量，让越深层的资源越少被浪费。

这 **7 层**防护分别是：

1. **Nginx/OpenResty 层**：这是最外层的物理防线。利用 Lua 脚本和 Redis 做 IP 限流、UA 黑名单拦截。这是 C 语言层面的操作，开销微乎其微，能在网络边缘直接挡掉恶意脚本和爬虫。
2. **网关 BloomFilter 层**：针对**非法商品 ID**（比如黑客随机生成的、不存在的 SKU）进行拦截。布隆过滤器基于位图，内存占用极低且速度极快，直接防止这些请求穿透到数据库（缓存穿透防护）。
3. **JWT + IP 绑定校验**：我们在 Token 里加密了用户登录时的 IP Hash。如果请求 IP 和 Token 不一致，说明可能被盗用或异地刷单，直接在网关层拦截，保护账号安全。
4. **RBAC 权限校验**（*补充*）：**这是业务逻辑的第一道关卡**。有些秒杀商品是“会员专享”的。我们在网关解析 Token 里的用户角色，如果商品要求 VIP 但用户是普通用户，直接返回“无权限”，避免无效请求占用下游库存资源。
5. **Redis 预扣库存**：这是**最核心的流量筛选层**。我们把库存预热到 Redis，利用 `DECR` 原子操作扣减。如果返回值小于 0，直接返回“已售罄”。实测这一层能挡掉 **90% 以上** 的无效请求，真正能抢到资格的请求极少。
6. **RocketMQ 异步削峰**：只有 Redis 扣减成功的请求才会发送消息到 MQ。订单服务按照自己的处理能力去消费，把瞬时的并发洪峰变成了平滑的流量，保护后端数据库不崩。
7. **Redisson 分布式锁 + 数据库乐观锁**：这是**最后一道兜底防线**。在真正写数据库扣减库存时，利用分布式锁和 SQL 的 `WHERE stock > 0` 条件，保证数据强一致性和零超卖。但因为走到这的流量已经很少了，锁竞争非常小，不会成为性能瓶颈。”

### Q4：Redis 扣减了库存后，如何保证数据库的库存也是准确的？如果 Redis 挂了怎么办？

**口述回答：**

"首先是**数据同步策略**。Redis 的扣减是"实时强一致"的，而数据库的更新是"异步最终一致"的。当 Redis 扣减成功后，我们发送 MQ 消息，消费者去执行 `UPDATE stock SET num = num - 1 WHERE id = ? AND num > 0`。如果 SQL 执行失败（比如数据库库存不足），会触发补偿机制，回滚 Redis 的库存并发送告警。

关于**Redis 挂了**的风险，我们有两层保障：

1. **Redis 集群高可用**：我们采用的是 Redis Cluster 模式（3 主 3 从），具备自动故障转移能力，单点挂掉不影响整体。
2. **降级预案**：如果发生极端情况整个 Redis 集群不可用，我们会快速降级，暂停秒杀服务或在数据库层面做限流保护，保证系统不雪崩，虽然牺牲了用户体验，但保住了数据安全。"

### Q5：秒杀场景下如何解决"超卖"问题？

**口述回答：**

"我是三管齐下：

1. **Redis 原子性**：使用 `DECR` 命令，保证并发扣减时不会有并发安全问题。
2. **数据库乐观锁**：在 SQL 层面加条件 `AND num > 0`，确保数据库不会扣成负数。
3. **分布式锁**：虽然前面两层已经能防住 99.9% 的情况，但在事务提交前，我还是用 Redisson 锁住了商品 ID，防止极端的竞态条件。

这三个组合拳下来，实测多次压测，库存准确率 100%。"


这两层防护是**“业务逻辑层”**和**“数据持久层”**的最后一道防线。虽然看起来有点重复，但它们防守的维度完全不同。
简单来说：
*   **数据库乐观锁（SQL 层）**：是**底线**，保证数据绝对不会错（物理层面）。
*   **分布式锁**：是**秩序**，保证并发过程不混乱（逻辑层面），同时保护数据库不被打挂。
下面我为您详细拆解这两层的原理和它们之间的配合关系。
---
### 第一层详解：数据库乐观锁（SQL 层面的“守门员”）
#### 1. 核心原理：利用数据库行锁的原子性
所谓的“乐观锁”在这里并不是指加 `version` 字段，而是利用 **SQL 的 `WHERE` 条件判断**。
我们执行的 SQL 不是简单的减法，而是带条件的更新：
```sql
UPDATE sku_stock 
SET num = num - 1 
WHERE sku_id = 1001 AND num > 0;
```
#### 2. 场景推演（为什么这样能防超卖？）
假设库存 `num = 1`，此时有两个线程（请求）同时到达数据库：
*   **线程 A** 和 **线程 B** 同时读取到 `num = 1`（快照读）。
*   **线程 A** 先抢到数据库的**行锁**，执行更新。
    *   SQL 判断：`1 > 0` 成立。
    *   执行：`num` 变为 **0**。
    *   线程 A 提交事务，释放行锁。
*   **线程 B** 拿到行锁，开始执行更新。
    *   SQL 判断：此时数据库里的 `num` 已经是 **0** 了。
    *   条件 `0 > 0` **不成立**。
    *   **更新失败**，`affected_rows = 0`。
#### 3. 这一层的作用
它利用数据库底层的 ACID 特性，**强制保证库存永远不会变成负数**。即使前面的 Redis 出了 Bug（比如 Redis 里扣减成功，但数据库里其实不够了），这一层 SQL 也会报错，拦截住非法修改。
**它的代价**：在高并发下，大量请求会拿着错误的旧数据去更新数据库，导致大量请求“白跑一趟”（更新失败），浪费数据库的 CPU 和 I/O 资源。
---
### 第二层详解：Redisson 分布式锁（业务逻辑层的“疏导员”）
既然 SQL 已经能防住超卖了，为什么还需要 Redisson 锁？这不是多此一举吗？**并不是。**
#### 1. 核心作用 1：保护“业务逻辑”的一致性
秒杀不仅仅是一个“减库存”的动作，它通常是一段**复杂的业务代码**，包含：
1.  校验订单状态（是否重复购买）。
2.  计算价格（优惠券抵扣）。
3.  **扣减库存**。
4.  **创建订单**。
如果不加锁，可能会出现这种**“诡异”**的竞态条件：
*   线程 A 扣减库存成功（`num` 变 0）。
*   线程 B 扣减库存失败（SQL 返回 0）。
*   **但是**，线程 B 可能在扣减库存**之前**就已经创建了订单（如果代码写法不当，或者事务隔离级别问题）。
*   结果：库存没扣，但订单生成了（或者库存扣了但订单没生成），导致**订单与库存数据不一致**。
**Redisson 锁的作用**：把这一坨代码锁住，变成**原子操作**。要么全做，要么全不做。保证“查库存-扣库存-写订单”这一系列动作在并发时是串行执行的，不会出现“步调不一致”。
#### 2. 核心作用 2：减少数据库“无效碰撞”（保护 DB 性能）
回到上面的 SQL 场景。如果有 100 个请求通过了 Redis 的预扣减（假设 Redis 还有 100 个库存），但数据库里其实只剩 1 个了。
*   **没有 Redisson 锁**：
    100 个请求同时打到数据库。数据库处理 1 个成功的，99 个都在抢行锁，然后 99 个全部执行 `WHERE num > 0` 判定失败。
    **后果**：数据库忙活了一阵子，结果 99% 的工作都是无效的，CPU 飙升，响应变慢。
*   **有 Redisson 锁**：
    100 个请求在 Java 层排队。第 1 个拿到锁的进去，扣减成功，释放锁。第 2 个进去，发现 SQL 返回失败（`affected_rows=0`），直接结束，不再重试。
    **后果**：数据库没有并发争抢，一个个顺序处理，压力极小。
#### 3. Redisson 的“看门狗”机制
这里用 Redisson 而不是 `SETNX`，还有一个重要原因：**业务耗时不固定**。
如果创建订单、调用第三方支付接口耗时很长（比如 30 秒），普通的锁（过期时间 10 秒）早就过期释放了。这时第二个请求拿到锁，进入业务，会导致并发安全问题。
**Redisson 的看门狗** 会自动给锁“续命”，只要业务线程没死，锁就不会过期，绝对安全。
---
### 🔄 总结：它们是如何打配合的？
可以把这两层比作**银行的柜台业务**：
1.  **Redis 预扣减**：是**门口的保安**。没号的人直接挡回去，主要挡流量。
2.  **Redisson 分布式锁**：是**叫号机**。控制一次只有一个人能进柜台办业务，保证里面不乱，防止两个人同时抢一个窗口。
3.  **数据库乐观锁**：是**柜员系统**。即使叫号机坏了（极端情况），两个人挤进窗口，柜员系统（`WHERE num > 0`）也会检查余额，余额不够直接拒绝办理，绝对不让账户变负。
**面试口述建议：**
> “我们在代码层加了 Redisson 锁，在 SQL 层加了乐观锁，这是**双重保障**。
>
> **Redisson 锁**主要是为了**保业务逻辑的完整性**和**保数据库性能**。它确保了‘校验-扣库存-建订单’这一长串操作是串行的，不会出现订单创建成功但库存没扣的中间状态，也避免了大量无效请求并发冲击数据库造成死锁或 CPU 飙升。
>
> 而 **SQL 里的 `AND num > 0`** 是最后一道**物理防线**。这是利用数据库行锁的原子性，即使上面的 Redis 锁失效了，或者 Redis 数据与 DB 不一致，数据库也绝对不会允许库存变成负数。这是防止超卖的底线。”

## 第三部分：数据一致性与分布式事务

### Q6：项目中用到了 Seata 做分布式事务，为什么选 AT 模式而不是 TCC？AT 模式的原理是什么？

**口述回答：**

"选 AT 模式主要是**开发成本**和**业务侵入性**的考量。TCC 模式需要每个业务接口写三个方法（Try、Confirm、Cancel），开发量是 AT 的 3 倍，而且业务逻辑容易写错。我们的下单场景虽然并发高，但还没达到极致秒杀那种需要 TCC 来提升性能的程度，AT 模式完全够用。

关于 **AT 模式原理**，简单说就是"两阶段提交"：

*   **一阶段**：Seata 会拦截业务 SQL，解析出元数据，生成**前镜像**（修改前的数据）和**后镜像**（修改后的数据），组成 Undo Log，连同业务 SQL 一起提交。此时本地事务提交成功，但全局事务状态还没定。
*   **二阶段**：
    *   如果所有分支都成功，TC（事务协调器）通知异步删除 Undo Log。
    *   如果有分支失败，TC 通知回滚。Seata 会读取 Undo Log，生成反向 SQL（比如原来是 `+1`，反向就是 `-1`），把数据恢复到原状。

这就保证了跨服务的 ACID 特性。"

### Q7：支付模块是如何保证支付状态与订单状态最终一致的？

**口述回答：**

"支付是强依赖外部系统的（微信/支付宝），回调可能会丢包或延迟。我们采用了 **RocketMQ 事务消息**：

流程是：支付服务先发一条**半消息**（Half Message）给 MQ，这条消息对下游订单服务不可见。然后执行本地事务（插入支付日志）。如果本地事务成功，就向 MQ 发送 Commit 指令，订单服务就能消费消息更新订单状态。

如果 MQ 一直没收到 Commit/Rollback（比如支付服务挂了），RocketMQ 会回调我们的**回查接口**，我们去查数据库的支付日志状态，反过来告诉 MQ 是提交还是回滚。

这套机制保证了**本地事务**与**消息发送**的原子性，从而保证了支付与订单的最终一致。"

## 第四部分：搜索、缓存与数据同步（CDC）

### Q8：为什么用 Canal 而不是直接在业务代码里写 ES？Canal 的原理是什么？

**口述回答：**

"主要是为了**解耦**。如果业务代码里既要写 MySQL 又要写 ES，代码耦合度太高，而且如果 ES 更新失败，可能导致整个业务回滚，性能也很差。

**Canal 的原理**是模拟 MySQL 的 Slave 节点。它伪装成 MySQL 的从库，向 Master 发送 dump 协议，Master 会推送 binlog 给 Canal。Canal 解析 binlog（必须是 ROW 模式），提取出变更的数据，然后通过 Feign 调用搜索服务更新 ES。

这种方式下，商品服务只管写 MySQL，数据同步完全异步化，**代码侵入性为零**，而且保证了最终一致性。"

### Q9：你的多级缓存（Nginx + Redis + JVM）是如何设计的？缓存一致性问题怎么解决？

**口述回答：**

"我们设计了三级缓存来抗压：

1. **Nginx 本地缓存**：缓存静态资源和热点数据的 JSON 响应，请求根本打不到 Java 层。
2. **Redis 分布式缓存**：存热点商品数据，速度快且共享。
3. **JVM 本地缓存（Caffeine）**：存配置项或极高频的数据，避免网络开销。

**一致性问题**是个挑战。我们的方案是结合 **Canal**。当 MySQL 数据变更时，Canal 监听到 binlog，除了同步 ES，还会调用缓存接口**删除 Redis** 对应的 Key（而不是修改，避免并发脏写）。如果 Nginx 层有缓存，我们会通过 Lua 脚本主动 purge 掉。虽然有短暂的延迟（毫秒级），但我们通过**设置较短的 TTL（比如 60 秒）**作为兜底，保证最终一致。"

### Q10：为什么购物车选 MongoDB？搜索选 ES？分析选 Druid？

**口述回答：**

"这就是 **Polyglot Persistence（混合持久化）** 的思想，选型取决于数据特点：

*   **购物车 → MongoDB**：因为购物车数据结构不固定，有的用户存了很多自定义字段，MongoDB 的无 Schema 特性非常灵活，且它支持持久化，不像 Redis 怕丢数据。
*   **搜索 → Elasticsearch**：商品搜索需要全文检索、分词、高亮、复杂的聚合筛选。MySQL 的 `LIKE` 在百万级数据下性能极差，而 ES 基于**倒排索引**，毫秒级响应。
*   **分析 → Apache Druid**：我们要分析用户行为日志，数据量是亿级的，且需要实时聚合（比如算过去 1 分钟的热门商品）。Druid 是列式存储，天然适合 OLAP 场景，查询速度比 MySQL 快几个数量级。"

## 第五部分：系统运维与工程实践

### Q11：项目中提到了"热点发现"，具体是怎么实现的？为什么要这么做？

**口述回答：**

"这是为了应对**突发流量**。有时普通商品突然爆火，没有运营配置秒杀活动，系统可能会被打挂。

我们用 **Druid + ElasticJob** 实现了一个自动闭环：

1. 用户的行为日志（点击、浏览）实时灌入 Druid。
2. ElasticJob 定时（每 30 秒）去查询 Druid，聚合过去 1 分钟访问量突增的商品。
3. 如果超过阈值（比如 5000 次/分），系统自动判定为"热点商品"。
4. 自动将这些商品推送到 Redis 秒杀隔离池预热，并更新网关限流规则。

整个过程**无需人工干预**，体现了数据驱动的自动化运维能力。"

### Q12：如果面试官追问：Canal 挂了怎么办？或者 Canal 消费太慢导致积压怎么办？

**口述回答：**

"这也是我考虑过的风险点。

对于 **Canal 挂了**：我们部署了 Canal HA（高可用）集群，基于 ZooKeeper 选举。一台挂了另一台自动接管，且断点会记录在 ZooKeeper 上，恢复后从断点续传，不会丢数据。

对于 **消费积压**：

1. 我们在 Canal Client 和搜索服务之间加了**RocketMQ 做缓冲**。Canal 只管把 binlog 快速发到 MQ，不阻塞自己。
2. 搜索服务可以动态增加消费者实例数量进行扩容。
3. 如果积压严重，我们会临时**降级**，暂停非核心索引的更新，优先保证商品主索引的同步。"

### Q13：文件存储为什么选 FastDFS 而不是 MinIO 或直接用 OSS？

**口述回答：**

"主要是考虑**私有化部署**和**中小文件优化**。

MinIO 虽然现在很火，但 S3 兼容协议在某些老系统对接时可能有坑。而 OSS 是云服务，不仅贵，而且数据在云上，有些项目要求内网私有部署。

**FastDFS** 专攻 4KB 到 500MB 的文件（如图片、文档），架构非常轻量（Tracker + Storage）。它对文件名的处理、HTTP 访问的集成都很成熟。

我们的实现是：Java 客户端上传文件到 FastDFS，拿到 `group1/M00/...` 的路径，然后配合 Nginx 的 `fastdfs-nginx-module` 模块，直接通过 HTTP 访问文件，性能非常高。"

## 第六部分：行为面试与软技能

### Q14：在这个项目中，你遇到的最大技术难题是什么？你是怎么解决的？

**口述回答：**

"最大的难题是**Canal 同步 ES 的延迟问题**。

初期我们发现，运营修改商品价格后，前端搜索页要过好几秒甚至更久才能刷新出来。排查发现，当 Canal 捕获到大批量 binlog（比如运营批量导入商品）时，Feign 同步调用搜索服务的 HTTP 请求变成了瓶颈，导致消费积压。

**我的解决思路**是：

1. **引入 MQ**：将同步链路改为 `Canal -> RocketMQ -> Search Service`，利用 MQ 的缓冲能力削峰。
2. **批量写入**：搜索服务消费时，不是来一条写一条，而是聚合成一批（比如 50 条）再 Bulk Write 到 ES，大幅提升了 ES 的写入吞吐。
3. **监控告警**：对接了 Prometheus，如果同步延迟超过 1 秒立刻报警。

优化后，P99 延迟从 5 秒降到了 500 毫秒以内，解决了业务痛点。"

### Q15：如果这个项目要上线，你还会做哪些改进？

**口述回答：**

"目前是原型阶段，如果要真上线，我会重点关注**可观测性**和**容灾**：

1. **全链路追踪**：引入 SkyWalking 或 Jaeger，现在虽然有日志，但跨服务的调用链路如果不清晰，排查问题很慢。
2. **数据库限流与熔断**：虽然应用层有限流，但我会给数据库加 proxy（如 ShardingSphere 或 Vitess），防止慢 SQL 把数据库拖挂。
3. **容灾演练**：引入 Chaos Blad（混沌工程），定期杀掉容器或模拟网络延迟，测试系统的自愈能力。
4. **静态资源 CDN**：秒杀页面的静态资源全部推到 CDN，把流量留在边缘节点，减轻源站压力。"
