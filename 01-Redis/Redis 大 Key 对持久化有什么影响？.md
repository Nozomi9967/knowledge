大家好，我是小林。

上周有位读者字节一二面时，被问到： **Redis 的大 Key 对持久化有什么影响？**

![·](https://cdn.xiaolincoding.com//mysql/other/2ae06f60d9614da0be4729944b2a317c.png)

Redis 的持久化方式有两种：AOF 日志和 RDB 快照。

所以接下来，针对这两种持久化方式具体分析分析。

## 大 Key 对 AOF 日志的影响

> 先说说 AOF 日志三种写回磁盘的策略

Redis 提供了 3 种 AOF 日志写回硬盘的策略，分别是：

- Always，这个单词的意思是「总是」，所以它的意思是每次写操作命令执行完后，同步将 AOF 日志数据写回硬盘；
- Everysec，这个单词的意思是「每秒」，所以它的意思是每次写操作命令执行完后，先将命令写入到 AOF 文件的内核缓冲区，然后每隔一秒将缓冲区里的内容写回到硬盘；
- No，意味着不由 Redis 控制写回硬盘的时机，转交给操作系统控制写回的时机，也就是每次写操作命令执行完后，先将命令写入到 AOF 文件的内核缓冲区，再由操作系统决定何时将缓冲区内容写回硬盘。

这三种策略只是在控制 fsync() 函数的调用时机。

当应用程序向文件写入数据时，内核通常先将数据复制到内核缓冲区中，然后排入队列，然后由内核决定何时写入硬盘。

![](https://cdn.xiaolincoding.com//mysql/other/def7d5328829470c9f3cfd15bbcc6814.png)

如果想要应用程序向文件写入数据后，能立马将数据同步到硬盘，就可以调用 fsync() 函数，这样内核就会将内核缓冲区的数据直接写入到硬盘，等到硬盘写操作完成后，该函数才会返回。

- Always 策略就是每次写入 AOF 文件数据后，就执行 fsync() 函数；
- Everysec 策略就会创建一个异步任务来执行 fsync() 函数；
- No 策略就是永不执行 fsync() 函数;

> 分别说说这三种策略，在持久化大 Key 的时候，会影响什么？

在使用 Always 策略的时候，主线程在执行完命令后，会把数据写入到 AOF 日志文件，然后会调用 fsync() 函数，将内核缓冲区的数据直接写入到硬盘，等到硬盘写操作完成后，该函数才会返回。

**当使用 Always 策略的时候，如果写入是一个大 Key，主线程在执行 fsync() 函数的时候，阻塞的时间会比较久，因为当写入的数据量很大的时候，数据同步到硬盘这个过程是很耗时的** 。

当使用 Everysec 策略的时候，由于 `fsync()` 是由后台 BIO 线程异步执行的，所以相比 Always 策略，大 Key 持久化对主线程的影响 **会显著减轻** 。但需要注意的是，==主线程仍然要同步执行 `write()` 把 AOF 缓冲区的数据拷贝到内核缓冲区，写入大 Key 时 `write()` 本身的耗时也会随之变大；并且如果上一次后台 `fsync()` 还未结束，主线程的 `write()` 会被强制等待，此时大 Key 依然可能对主线程造成阻塞。

当使用 No 策略的时候，虽然永不执行 fsync() 函数，但主线程仍然需要同步执行 `write()` 将 AOF 缓冲区的数据拷贝到内核缓冲区。因此与 Everysec 策略一样，写入大 Key 时 `write()` 本身的耗时也会随之变大，大 Key 的持久化过程仍然会对主线程产生影响。

## 大 Key 对 AOF 重写和 RDB 的影响

当 AOF 日志写入了很多的大 Key，AOF 日志文件的大小会很大，那么很快就会触发 **AOF 重写机制** 。

AOF 重写机制和 RDB 快照（bgsave 命令）的过程，都会分别通过 `fork()` 函数创建一个子进程来处理任务。

在创建子进程的过程中，操作系统会把父进程的「页表」复制一份给子进程，这个页表记录着虚拟地址和物理地址映射关系，而不会复制物理内存，也就是说，两者的虚拟空间不同，但其对应的物理空间是同一个。

![](https://cdn.xiaolincoding.com//mysql/other/06657cb93ffa4a24b8fc5b3069cb29bf.png) 这样一来，子进程就共享了父进程的物理内存数据了，这样能够节约物理内存资源，页表对应的页表项的属性会标记该物理内存的权限为 **只读** 。

Redis 占用的总内存越大，对应的页表也就越大（页表大小取决于虚拟地址空间的映射范围，与内存是分布在大 Key 中还是小 Key 中无关）。

> [!warning] 常见误区
> 小林coding 原文将「大 Key → 占用内存多 → 页表大 → fork 阻塞」串联为因果链，这是**逻辑误导**。fork 阻塞与"大 Key"这个**概念**无关，只与 Redis 进程占用的**总虚拟内存量**有关。同样的总数据量，无论存在一个 1 GB 的大 Key 还是十万个 10 KB 的小 Key，页表大小基本一致，fork 耗时也基本一致。页表项的数量取决于被映射的物理页数量（≈总内存 / 页大小），与单个 Key 的大小无关。一个 1 GB 的大 Hash 和 1024 个 1 MB 的小 Key，在页表层面映射的页数是一样的。

在通过 `fork()` 函数创建子进程的时候，虽然不会复制父进程的物理内存，但是 **内核会把父进程的页表复制一份给子进程，如果页表很大，那么这个复制过程是会很耗时的，那么在执行 fork 函数的时候就会发生阻塞现象** 。

而且，fork 函数是由 Redis 主线程调用的，如果 fork 函数发生阻塞，那么意味着就会阻塞 Redis 主线程。由于 Redis 执行命令是在主线程处理的，所以当 Redis 主线程发生阻塞，就无法处理后续客户端发来的命令。

我们可以执行 `info` 命令获取到 latest\_fork\_usec 指标，表示 Redis 最近一次 fork 操作耗时。

```sql
# 最近一次 fork 操作耗时
latest_fork_usec:315
```

如果 fork 耗时很大，比如超过1秒，则需要做出优化调整：

- 单个实例的内存占用控制在 10 GB 以下，这样 fork 函数就能很快返回。
- 如果 Redis 只是当作纯缓存使用，不关心 Redis 数据安全性问题，可以考虑关闭 AOF 和 AOF 重写，这样就不会调用 fork 函数了。
- 在主从架构中，要适当调大 `repl-backlog-size`。`repl_backlog_buffer` 是主节点上的一个环形缓冲区，用于缓存最近执行的写命令。当从节点断连后重连时，主节点会检查从节点需要的偏移量数据是否仍在 buffer 中：如果在，则进行**部分重同步（增量同步）**，无需 fork；如果已被新数据覆盖，则必须进行**全量重同步**，这会触发 fork 子进程生成 RDB 文件，导致主线程阻塞。调大该 buffer 能容纳更长时间的写命令，从而减少全量同步的频率，也就是减少了 fork 的调用次数。

> **面试参考**：可结合 [[01-Redis/Redis fork 全量同步优化案例]] 中的业务场景，用 STAR 法则讲述该优化实践。

> 那什么时候会发生物理内存的复制呢？

当父进程或者子进程在向共享内存发起写操作时，CPU 就会触发 **写保护中断** ，这个「写保护中断」是由于违反权限导致的，然后操作系统会在「写保护中断处理函数」里进行物理内存的复制，并重新设置其内存映射关系，将父子进程的内存读写权限设置为可读写，最后才会对内存进行写操作，这个过程被称为「 **写时复制(Copy On Write)** 」。

![](https://cdn.xiaolincoding.com//mysql/other/451024fe10374431aff6f93a8fed4638.png)

写时复制顾名思义，在发生写操作的时候，操作系统才会去复制物理内存，这样是为了防止 fork 创建子进程时，由于物理内存数据的复制时间过长而导致父进程长时间阻塞的问题。

> [!warning] 修正原文表述
> 原文说"父进程对共享内存中的大 Key 进行了修改，那么内核就会发生写时复制"——这个表述容易让人以为只有修改大 Key 才会触发 COW。实际上，**父进程修改任何共享页（无论属于大 Key 还是小 Key）都会触发 COW**。大 Key 的特别之处在于：如果父进程在重写/快照期间修改了大 Key，COW 需要拷贝大 Key 占用的物理页（可能数十 MB 甚至 GB 级别），这个拷贝发生在主线程的 page fault 处理中，会阻塞主线程。而小 Key 的 COW 拷贝量小，阻塞时间也短。

如果创建完子进程后， **父进程对共享内存中的大 Key 进行了修改，那么内核就会发生写时复制，会把物理内存复制一份，由于大 Key 占用的物理内存是比较大的，那么在复制物理内存这一过程中，也是比较耗时的，于是父进程（主线程）就会发生阻塞** 。

所以，有两个阶段会导致阻塞父进程：

- 创建子进程的途中，由于要复制父进程的页表等数据结构，阻塞的时间跟页表的大小有关，页表越大，阻塞的时间也越长；
- 创建完子进程后，如果子进程或者父进程修改了共享数据，就会发生写时复制，这期间会拷贝物理内存，如果内存越大，自然阻塞的时间也越长；

这里额外提一下， 如果 **Linux 开启了内存大页，会影响 Redis 的性能的** 。

Linux 内核从 2.6.38 开始支持内存大页机制，该机制支持 2MB 大小的内存页分配，而常规的内存页分配是按 4KB 的粒度来执行的。

如果采用了内存大页，那么即使客户端请求只修改 100B 的数据，在发生写时复制后，Redis 也需要拷贝 2MB 的大页。相反，如果是常规内存页机制，只用拷贝 4KB。

两者相比，你可以看到，每次写命令引起的 **复制内存页单位放大了 512 倍，会拖慢写操作的执行时间，最终导致 Redis 性能变慢** 。

那该怎么办呢？很简单，关闭内存大页（默认是关闭的）。

禁用方法如下：

```shell
echo never >  /sys/kernel/mm/transparent_hugepage/enabled
```

> [!info] 大 Key 影响持久化的完整路径
>
> 大 Key 对持久化的影响并非只存在于"修改大 Key"这一种场景，有以下几条独立路径：
>
> | 阶段 | 是否涉及大 Key | 是否阻塞主线程 | 说明 |
> |------|:---:|:---:|------|
> | AOF 日志写入（Always 策略） | 是 | **是** | 写入大 Key 后 `fsync()` 同步刷盘，数据量大则耗时长 |
> | AOF 日志增长触发重写 | 是（间接） | 否 | 大 Key 使 AOF 文件增长更快，更频繁触发重写 |
> | `fork()` 复制页表 | **否** | **是** | 耗时取决于总内存量，与大 Key 无关 |
> | 子进程序列化大 Key + 写盘 | 是 | **否** | 子进程处理大 Key 耗时更长，延长 COW 窗口 |
> | 父进程修改大 Key 触发 COW | 是 | **是** | 拷贝大 Key 物理页，阻塞主线程 |
>
> **关键结论：fork 阶段的阻塞与"大 Key"无关，只与总内存量有关。** 但大 Key 确实通过"AOF 膨胀 → 重写频率升高"、"fsync 阻塞"、"COW 拷贝量增大"、"子进程耗时延长"等多条路径影响持久化。

## 总结

当 AOF 写回策略配置了 Always 策略，如果写入是一个大 Key，主线程在执行 fsync() 函数的时候，阻塞的时间会比较久，因为当写入的数据量很大的时候，数据同步到硬盘这个过程是很耗时的。

> [!warning] fork 阻塞与大 Key 无关
> fork 阶段的阻塞与"大 Key"这个概念无关，只与 Redis 进程占用的**总虚拟内存量**有关。同样的数据量，无论分布在大 Key 还是小 Key 中，页表大小和 fork 耗时基本一致。

AOF 重写机制和 RDB 快照（bgsave 命令）的过程，都会分别通过 `fork()` 函数创建一个子进程来处理任务。会有两个阶段会导致阻塞父进程（主线程）：

- 创建子进程的途中，由于要复制父进程的页表等数据结构，阻塞的时间跟页表的大小有关，页表越大，阻塞的时间也越长；（**注意：此阶段与大 Key 无关，只取决于总内存量**）
- 创建完子进程后，如果父进程修改了共享数据中的大 Key，就会发生写时复制，这期间会拷贝大 Key 占用的物理内存，由于大 Key 占用的物理内存会很大，那么在复制物理内存这一过程，就会比较耗时，所以有可能会阻塞父进程。

此外，大 Key 对持久化还有以下独立影响路径：

- **AOF 日志膨胀 → 重写频率升高**：大 Key 的写命令让 AOF 文件增长更快，更频繁触发重写（每次重写都需一次 fork）。
- **子进程序列化耗时延长**：RDB 快照和 AOF 重写期间，子进程序列化大 Key 的 I/O 耗时长，延长 COW 时间窗口，增加父进程触发 COW 的概率。

> 大 key 除了会影响持久化之外，还会有以下的影响：

- 客户端超时阻塞。由于 Redis 执行命令是单线程处理，然后在操作大 key 时会比较耗时，那么就会阻塞 Redis，从客户端这一视角看，就是很久很久都没有响应。
- 引发网络阻塞。每次获取大 key 产生的网络流量较大，如果一个 key 的大小是 1 MB，每秒访问量为 1000，那么每秒会产生 1000MB 的流量，这对于普通千兆网卡的服务器来说是灾难性的。
- 阻塞工作线程。如果使用 del 删除大 key 时，会阻塞工作线程，这样就没办法处理后续的命令。
- 内存分布不均。集群模型在 slot 分片均匀情况下，会出现数据和查询倾斜情况，部分有大 key 的 Redis 节点占用内存多。

> 如何避免大 Key 呢？

最好在设计阶段，就把大 key 拆分成一个一个小 key。或者，定时检查 Redis 是否存在大 key ，如果该大 key 是可以删除的，不要使用 DEL 命令删除，因为该命令删除过程会阻塞主线程，而是用 unlink 命令（Redis 4.0+）删除大 key，因为该命令的删除过程是异步的，不会阻塞主线程。

# 🎯 面试题 · 2026-07-26 17:37（基于《Redis 大 Key 对持久化有什么影响？》）

> [!question]- 面试题 1：大 Key 对 AOF 日志持久化有什么影响？请结合 AOF 的三种写回策略具体说明。
> 大 Key 对 AOF 持久化的影响主要体现在增加主线程阻塞的风险上，具体表现和三种写回策略密切相关：首先是 Always 策略，该策略要求每次写命令执行完成后，主线程立刻同步调用 fsync() 把内核缓冲区的 AOF 数据刷到硬盘，如果写入的是大 Key，数据量大会导致 fsync() 的耗时显著拉长，直接阻塞主线程，影响后续命令的处理。然后是 Everysec 策略，fsync() 操作由后台 BIO 线程异步执行，相比 Always 策略主线程的阻塞风险大幅降低，但主线程仍然需要同步执行 write() 把 AOF 缓冲区的数据拷贝到内核缓冲区，写入大 Key 时 write() 本身的耗时会明显变大；而且如果上一次后台的 fsync() 还没执行完成，主线程的 write() 会被强制等待，此时大 Key 依然可能造成主线程阻塞。最后是 No 策略，该策略不主动调用 fsync()，刷盘时机完全交给操作系统控制，但主线程同样需要同步执行 write() 完成数据拷贝，因此和 Everysec 策略类似，大 Key 的写入会拉长 write() 的耗时，依然会对主线程造成阻塞影响。

> [!question]- 面试题 2：有观点认为大 Key 会导致 fork 子进程时阻塞 Redis 主线程，这个说法正确吗？请结合原理说明你的判断。
> 这个说法不正确，fork 阶段的阻塞和大 Key 这个概念本身没有直接因果关系。AOF 重写和 RDB 快照都会通过 fork() 创建子进程来处理持久化任务，fork 过程中内核只会复制父进程的页表给子进程，不会复制物理内存；而页表的大小取决于 Redis 进程占用的总虚拟内存的映射范围，和 Key 是单个大 Key 还是多个小 Key 无关——同样的总数据量，无论是存储在 1 个 1GB 的大 Key 还是十万个 10KB 的小 Key 中，页表大小和 fork 耗时基本一致，因此 fork 本身的阻塞只和 Redis 总内存占用有关，和大 Key 无关。
> 不过大 Key 确实会通过其他路径和 fork 产生关联：一方面大 Key 的写命令会让 AOF 日志文件增长更快，更频繁触发 AOF 重写，从而增加 fork 的调用次数，间接提升主线程阻塞的概率；另一方面子进程生成后，需要将内存数据序列化写入目标文件，大 Key 的序列化和磁盘 I/O 耗时长，会延长写时复制（COW）的时间窗口，增加父进程修改共享内存时触发 COW 的概率。而如果父进程在子进程运行期间修改了大 Key，会触发 COW 机制拷贝大 Key 占用的物理内存页，这个拷贝过程发生在主线程的异常处理中，会阻塞主线程，但这属于 fork 之后的阶段，不是 fork 本身阻塞的原因。我们可以通过 info 命令获取 latest_fork_usec 指标，查看最近一次 fork 操作的耗时，如果超过 1 秒就需要考虑优化。

> [!question]- 面试题 3：Redis 的 RDB 快照和 AOF 重写过程中，大 Key 会产生哪些影响？有哪些对应的优化思路？
> 首先需要明确，RDB 快照和 AOF 重写都会调用 fork() 创建子进程，这个阶段的阻塞只和 Redis 总内存占用有关，和大 Key 无关。大 Key 对这两个过程的影响主要体现在后续阶段：第一，子进程生成后需要将内存数据序列化后写入 RDB 文件或重写后的 AOF 文件，大 Key 占用的内存大，序列化和磁盘 I/O 的耗时会显著更长，会延长子进程的运行时间，进而延长写时复制（COW）的时间窗口，增加父进程触发 COW 的概率。第二，如果父进程在子进程运行期间修改了大 Key，会触发 COW 机制，内核需要拷贝大 Key 占用的物理内存页，这个拷贝过程会阻塞主线程；如果 Linux 开启了内存大页，哪怕只修改大 Key 中的少量数据，也需要拷贝 2MB 的大页，相比常规 4KB 内存页的拷贝量放大 512 倍，会进一步加剧阻塞。第三，如果配置了 AOF 持久化，大 Key 的写命令会让 AOF 日志文件增长更快，更频繁触发 AOF 重写，从而增加 fork 操作的频率，间接提升主线程阻塞的概率。
> 对应的优化思路可以参考：一是将单实例内存占用控制在 10GB 以内，缩短 fork 的耗时；二是如果 Redis 仅作为纯缓存使用、不关心数据持久化，可以关闭 AOF 和 AOF 重写，避免触发 fork 操作；三是在主从架构中适当调大 repl-backlog-size，减少主从全量同步的频率，降低 fork 的触发次数；四是避免在子进程运行期间执行修改大 Key 的命令，或者提前将大 Key 拆分为多个小 Key，降低 COW 的拷贝量。
