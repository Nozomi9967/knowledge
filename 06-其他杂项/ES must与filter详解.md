# ES Must 与 Filter 详解

> 本文件是 [[06-其他杂项/ES详解]] 中 `must` vs `filter` 的独立详解延伸。主文件在性能优化表格中提到"Filter 代替 Must"，本文展开完整对比。

---

## 一句话结论

**`must` 和 `filter` 都是"必须匹配"（AND 逻辑），核心区别在于：`must` 参与评分，`filter` 不参与评分且结果可缓存。**

面试时直接说这句就够了。

---

## 对比表格

| 特性 | `must` | `filter` |
|------|--------|---------|
| **逻辑** | 必须匹配（AND） | 必须匹配（AND） |
| **是否计算 _score** | ✅ 是 | ❌ 否 |
| **结果缓存** | 不缓存 | ✅ 可缓存 |
| **性能** | 较慢（评分耗 CPU） | 更快（跳过评分 + 缓存） |
| **适用场景** | 全文检索、需要相关性排序 | 精确值过滤、范围过滤、状态筛选 |

---

## 本质原因：背后是两种上下文

`must` 和 `filter` 的区别根子在于它们分别落在 ES 的两种执行上下文中：

| 上下文 | 核心问题 | 是否算 _score | 结果缓存 |
|--------|---------|:------------:|:-------:|
| **查询上下文**（Query Context） | "有多匹配？" | ✅ 是 | ❌ |
| **过滤上下文**（Filter Context） | "是否匹配？" | ❌ 否 | ✅ |

- `must` 落在**查询上下文**——关心"文档匹配程度"，所以算分
- `filter` 落在**过滤上下文**——只做"是/否"二值判断，所以不算分且可缓存

**面试时如果需要展开说，可以提一句"背后是查询上下文和过滤上下文的区别"——但结论永远是：要评分用 must，不要评分用 filter。**

---

## 实际使用：混合搭配

全文搜索需要评分，但过滤条件不需要——两者组合使用：

```json
{
  "query": {
    "bool": {
      "must": {
        "match": { "title": "elasticsearch" }       // 要评分：按匹配度排序
      },
      "filter": {
        "range": { "publish_date": { "gte": "2023-01-01" } },  // 不要评分：只做过滤
        "term":   { "status": "published" }
      }
    }
  }
}
```

**原则**：不需要参与排序的条件，一律放 `filter`。

---

## bool 查询四子句速查

| 子句 | 是否评分 | 逻辑 | 对应上下文 |
|------|:--------:|------|----------|
| `must` | ✅ | AND | 查询上下文 |
| `should` | ✅ | OR | 查询上下文 |
| `filter` | ❌ | AND | 过滤上下文 |
| `must_not` | ❌ | NOT | 过滤上下文 |

重点：`must` 和 `filter` 逻辑一样（都是 AND），区别只在于**评不评分**。

---

## 面试话术

> "must 和 filter 的口诀我记的是：**要评分用 must，不要评分用 filter**。两者都是 AND，但 must 在查询上下文中会计算 _score，filter 在过滤上下文中不做评分且可缓存。所以只要是不需要排序的条件——分类、品牌、价格区间、状态——全部应该放 filter，既能提升查询性能，又能利用缓存。"
