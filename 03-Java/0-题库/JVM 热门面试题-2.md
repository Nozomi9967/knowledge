## 五、类加载机制（5 题）

### 13. 类加载器有哪些？三层结构分别加载什么路径下的类？

> **知识点跳转：** [[jvm八股]] · [[三层类加载器与classpath]]

**参考答案**

四个层级：启动类加载器、扩展类加载器、应用类加载器，再加上自定义类加载器。启动类加载器在最顶层，加载核心类库，JDK 8 是 rt.jar，JDK 9 模块化之后变成了 jmods 目录下的 java.base 这些核心模块，一个 jmod 就是一个模块，不再是一个大罐子全装了。扩展类加载器在 JDK 8 加载 JAVA_HOME 下面 lib 里 ext 目录的扩展类库，JDK 9 之后改名叫平台类加载器，ext 目录已经没有了。应用类加载器也叫系统类加载器，加载 classpath 下的类，就是我们自己写的业务代码。自定义类加载器继承 ClassLoader，一般覆写 findClass，用于热部署、加密解密这些场景。

**追问参考答**

启动类加载器不是 Java 写的，是 C/C++ 实现的，内嵌在 JVM 里，JVM 一启动它就已经存在了，所以它没有父加载器，这也是双亲委派到它这里就到头的原因。它加载的是核心类库：JDK 8 是 rt.jar，JDK 9 以后是 jmods 下的核心模块。另外 jmod 不能直接放 classpath 用，它主要给 JDK 内部和 jlink 裁剪运行时用的，日常开发依赖的还是 jar。

### 14. 双亲委派模型是什么？它解决了什么问题？

> **知识点跳转：** [[jvm八股]] · [[三层类加载器与classpath]]

**参考答案**

双亲委派是说类加载器收到加载请求时，不自己先加载，而是先委派给父加载器，逐级往上一直到启动类加载器；父加载器能加载就由父加载，父加载不了才轮到自己试。加载之前还会先查一下这个类是不是已经被加载过了，加载过就直接返回。它解决三个问题：一是安全性，核心类库只能由启动类加载器加载，防止有人自定义一个 java.lang.String 把核心类篡改掉；二是唯一性，同一个类只会被加载一次，不会出现多个不同版本的类；三是层次清晰，加载顺序按父到子，结构规整。

**追问参考答**

打破双亲委派的经典场景有两个，方向正好相反。Tomcat 是下层打破：每个 webapp 要优先加载自己 WEB-INF/lib 里的依赖，可能和父加载器的版本冲突，所以 WebappClassLoader 反过来先自己找再委派父，代价是同名类可以在不同 webapp 共存、类只加载一次的约束被破坏。JDBC 是上层打破：DriverManager 在核心库里由启动类加载器加载，但驱动实现在 classpath 里它够不着，于是用线程上下文类加载器反向拿到 AppClassLoader 去加载驱动。细节见 [[打破双亲委派的经典场景]]。

### 15. 类的生命周期有哪几个阶段？加载 → 验证 → 准备 → 解析 → 初始化各做了什么？

> **知识点跳转：** [[jvm八股]]

**参考答案**

五个阶段：加载、验证、准备、解析、初始化，其中验证准备解析合起来叫链接，之后是使用和卸载。加载是通过类的全限定名获取二进制字节流，把静态存储结构转成方法区的运行时数据结构，并生成 Class 对象。验证是校验字节流的合法性，保证安全。准备是给静态变量分配内存并赋零值，注意如果是 static final 而且是编译期就能确定的常量，会直接赋实际值。解析是把常量池里的符号引用替换成直接引用。初始化是执行 clinit 方法，这个方法由编译器按源码顺序收集静态变量赋值语句和静态代码块生成。

**追问参考答**

准备阶段分配的是静态变量也就是类变量，赋的是零值，0、false、null 这种。static final 常量分两种：编译期就能确定值的，准备阶段直接赋实际值；依赖运行时计算的，比如调了个方法取随机数，那还是得等到初始化阶段走 clinit。卸载要三个条件同时满足：该类没有存活实例、类的 Class 对象没有被任何地方引用、加载它的 ClassLoader 已经被回收。顺序要记准，是 Class 对象引用着 ClassLoader，ClassLoader 被回收了类才可能卸载。

### 16. 类的初始化什么时候触发？主动引用和被动引用的区别？

> **知识点跳转：** [[类初始化的主动引用与被动引用]]

**参考答案**

只有主动引用才触发初始化，被动引用不触发。主动引用有五类：new 创建对象、读写非编译期常量的静态字段、调用静态方法；反射，包括 Class.forName 以及反射创建实例、读写字段、调用方法；初始化子类时如果父类还没初始化，先初始化父类；作为 JVM 启动的主类，也就是带 main 方法的那个类。被动引用要记住几种典型：通过子类引用父类的静态字段，只初始化父类不初始化子类；定义引用类型的数组，比如 new 一个 A 数组，只创建数组对象不触发 A 的初始化；访问编译期常量，编译时已经写进常量池了，不触发；用 ClassLoader.loadClass 只加载不初始化。但要注意 static final 的包装类型常量会触发，因为包装类赋值要调 valueOf，是运行时行为。

**追问参考答**

子类访问父类的静态字段只触发父类初始化。因为静态字段属于父类，字节码直接访问父类的字段，压根不涉及子类；子类会被加载、验证、准备，但不执行初始化。这是被动引用六种情形里最常考的一个，答题时把"只初始化父类、子类不初始化"这两句说死。

### 17. 线程上下文类加载器（TCCL）是什么？为什么 JDBC 驱动要打破双亲委派？

> **知识点跳转：** [[线程上下文类加载器（TCCL）]] · [[重写loadClass与findClass的区别]]

**参考答案**

线程上下文类加载器是 Thread 类里的一个字段，通过 getContextClassLoader 拿到。它的作用是让父加载器加载的代码，反过来去拿子加载器。为什么 JDBC 驱动要打破双亲委派：DriverManager 在核心库里、由启动类加载器加载，但 JDBC 驱动实现，比如 MySQL 的 Driver，在 classpath 里由应用类加载器加载。按双亲委派，启动类加载器往下委派也找不到驱动类，因为父加载器够不着子加载器的类。解法就是 DriverManager 在 ServiceLoader 加载驱动时，用当前线程的上下文类加载器拿到 AppClassLoader，让它去加载驱动，这就是反向打破双亲委派。

**追问参考答**

重写 findClass 和重写 loadClass 完全不是一回事。重写 findClass 不破坏双亲委派，因为 loadClass 的默认流程是"先委派父加载器，父加载不了才调 findClass"，覆写 findClass 只是提供自己加载的能力，委派逻辑原样保留，这是 JDK 推荐的做法。重写 loadClass 才是真正破坏，因为它直接改写了整条链的入口，跳过委派那一步，Tomcat 就是这么干的。一句话记：findClass 是在委派链末尾加自己的逻辑，属于安全扩展；loadClass 是重写链的入口，属于真正破坏。补一个常被追问的点：TCCL 的默认值不一定等于 AppClassLoader。线程创建时会从父线程继承 contextClassLoader，所以主线程是 AppClassLoader、它 new 出来的子线程也继承它；但框架可以主动换掉，比如 Tomcat 里每个 webapp 线程的 TCCL 是 WebappClassLoader，Spring 也有自己设置 TCCL 的逻辑。所以写框架代码时不能假设它是什么，拿不准就显式传。

## 六、垃圾回收（6 题）

### 18. 判断对象可回收有哪些方法？什么是 GC Roots？有哪些？

> **知识点跳转：** [[jvm八股]]

**参考答案**

两种方法：引用计数法和可达性分析。引用计数给每个对象加计数器，被引用加一、引用失效减一，归零就回收，缺点是无法处理循环引用。可达性分析是从 GC Roots 出发遍历引用链，任何一条链都到不了的对象就判定可回收，它解决了循环引用问题，JVM 用的是这个。GC Roots 有六类：虚拟机栈里局部变量表引用的对象、静态变量引用的对象、方法区常量引用的对象、本地方法栈 JNI 引用的对象、活跃的线程对象、被 synchronized 锁持有的对象，另外 Class 对象本身也算一类。

**追问参考答**

不用引用计数是因为循环引用。A 引用 B、B 引用 A，两者互相指着，如果没有外部引用，它们其实都该回收，但引用计数法里 A 的计数是 1、B 的计数也是 1，永远到不了零，就漏掉了，内存泄漏。可达性分析从根出发根本找不到它们，直接一起回收，这就是 JVM 选它的核心原因。答的时候把"计数不为零"点出来，比只说"看起来有用"更清楚。

### 19. 垃圾回收算法有哪些？各自的优缺点？为什么分代采用不同算法？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

三种。标记清除是先标记垃圾再直接清掉，优点是实现简单、不用移动对象，缺点是产生内存碎片，大对象可能找不到连续空间。标记复制是把存活对象复制到另一块空闲区，优点是没有碎片、分配高效，缺点是浪费一半空间，存活率高的时候复制开销很大。标记整理是标记完把存活对象往一端挪，再清理边界之外的内存，优点是没有碎片、空间利用率高，缺点是移动对象成本高、需要 STW。为什么分代用不同算法：新生代对象存活率极低，绝大多数朝生夕灭，用标记复制最划算，浪费一半空间可以接受，要复制的对象也少；老年代存活率高，没有额外空间做复制，只能用标记清除或者标记整理，避免反复搬大对象。

**追问参考答**

三个追问一句话各答一句：标记清除的缺点是内存碎片；标记复制的代价是空间利用率只有一半；标记整理最适合老年代，因为存活率高、又需要避免碎片。补一句容易漏的：标记清除说"效率高"要限定为"不需要移动对象"，它其实有标记和清除两次扫描的成本。

### 20. Minor GC、Major GC、Full GC 的区别？什么时候触发 Full GC？

> **知识点跳转：** [[jvm八股]] · [[Full GC频繁导致CPU 100%的完整排障流程]]

**参考答案**

Minor GC 也叫 Young GC，只回收新生代，Eden 区满了就触发。Major GC 只回收老年代，概念上是这样，实际多数收集器回收老年代时会连带整堆。Full GC 回收整个堆，包括新生代、老年代、元空间，STW 最长、代价最高，生产上要极力避免。Full GC 的触发条件有五个：老年代空间不足，Minor GC 后存活对象要晋升但放不下；空间分配担保失败，Minor GC 前会检查老年代有没有连续空间能容纳新生代全部存活对象，不够又不允许担保失败就 Full GC；元空间不足；显式调用 System.gc；CMS 的 Concurrent Mode Failure，并发清理时老年代又被填满，退化成 Serial Old。

**追问参考答**

频繁 Full GC 的排查按顺序走。先用 top 和 top -Hp 确认哪个进程、哪个线程 CPU 高，再用 printf 把线程号转成十六进制、jstack 查线程栈，看清是 GC 线程高还是业务线程高。接着 jstat -gcutil 每秒看一次各代使用率，重点看 Eden、老年代、元空间的使用率和 FGC 次数，判断到底是老年代被撑满还是元空间在涨。如果是老年代满就 jmap dump 出堆快照，用 MAT 看 Dominator Tree 谁占内存最多、Path to GC Roots 看被谁引用。定位到代码层面，通常是大对象、内存泄漏、集合没清理、缓存无限膨胀这几类。最后结合业务验证是不是周期性大流量。核心思路就一句：先确认谁占满，再 dump，再 MAT，最后回归代码。

### 21. 对象从新生代晋升到老年代的条件有哪些？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

四个条件。第一是年龄阈值，对象每熬过一次 Minor GC 年龄加一，默认到 15 就晋升，可以用 -XX:MaxTenuringThreshold 调。第二是动态年龄判断，Minor GC 后 Survivor 里同龄对象大小之和超过 Survivor 空间的一半，这批对象就提前晋升，不用等到 15，目的是防止 Survivor 被撑爆。第三是大对象直接进老年代，超过阈值的大对象一开始就分配在老年代，Serial 和 ParNew 下由 -XX:PretenureSizeThreshold 控制，G1 用 Humongous Region。第四是 Survivor 放不下，Minor GC 后存活对象塞不进 Survivor，通过分配担保直接进老年代。

**追问参考答**

一个口诀能把这四种串起来：正常熬到 15、Survivor 装不下、同龄对象太多提前走、一上来就太大。注意动态年龄判断的分母是"单个 Survivor 区的一半"，不是整个新生代的一半，这个细节说错容易被抓。

### 22. 垃圾回收器有哪些？CMS 和 G1 的核心区别？G1 的 Region 和 RSet 是什么？

> **知识点跳转：** [[jvm八股]] · [[G1]] · [[ZGC]]

**参考答案**

收集器按代分：新生代有 Serial、ParNew、Parallel Scavenge；老年代有 Serial Old、Parallel Old、CMS；整堆的有 G1 和 ZGC。Serial 是单线程复制算法，客户端默认；ParNew 是 Serial 的多线程版，配合 CMS 用；Parallel Scavenge 是吞吐量优先；Parallel Old 配它做老年代。CMS 是老年代的并发收集器，用标记清除，所以有内存碎片。G1 面向全堆、用复制加整理，没有碎片，适合大堆。ZGC 用染色指针，几乎不 STW。CMS 和 G1 的核心区别可以归纳成一句：CMS 只管老年代、标记清除、有碎片、停顿不可控；G1 管全堆、Region 分区、复制整理、无碎片、停顿可预测，G1 用分区加增量回收解决了 CMS 的碎片和停顿不可控两个问题。

**追问参考答**

G1 有两个核心概念必须说。Region 是把堆切成 1 到 32MB 的均等块，每个 Region 动态扮演 Eden、Survivor、Old 或者 Humongous，回收以 Region 为单位，不用扫全堆。RSet 是记忆集，记录其他 Region 指向本 Region 的引用，靠写屏障维护；回收某个 Region 时通过它的 RSet 就知道有哪些外部引用指向它，从而避免全堆扫描，代价是额外空间和写屏障开销。至于为什么能做到可预测停顿，是因为 G1 跟踪每个 Region 的回收收益也就是垃圾占比，按收益排序，在 -XX:MaxGCPauseMillis 设定的目标停顿时间内优先回收收益最高的那批 Region，属于量入为出的增量回收。

### 23. 什么是 STW？为什么需要 STW？各收集器的 STW 策略？

> **知识点跳转：** [[jvm八股]] · [[ZGC]]

**参考答案**

STW 是 Stop The World，GC 执行时把所有业务线程暂停，只让 GC 线程工作，暂停时间越长系统延迟越高。为什么需要它：可达性分析要求引用关系在一个稳定的快照上。如果业务线程一边跑一边改引用，GC 标出来的结果就不一致，可能刚标完又被改成垃圾，也可能漏标了本该存活的对象。STW 保证标记期间引用链不被修改，结果才准确。各收集器的策略：Serial 和 Parallel 是全程 STW；CMS 是初始标记 STW、并发标记不停、重新标记 STW、并发清除不停，两次短暂停顿；G1 类似但配合可预测停顿控制时长；ZGC 几乎所有阶段都并发，只剩三次极短的 STW，而且这个时间和堆大小无关。

**追问参考答**

ZGC 靠两个东西做到几乎不停。染色指针是把 GC 标记信息直接编码进引用本身的高几位，标记状态、重映射状态都挂在指针上，读引用时零成本拿到对象的 GC 状态，不用访问对象头。读屏障是每次从引用读对象时插一道检查，如果对象正在被移动或者等着重映射，读屏障立刻把指针修正到新地址再返回。因为修正在"读"这一刻发生，业务线程和 GC 线程并发搬对象也不会读到旧地址。结果就是标记、转移、重映射全部能并发完成，STW 被压到极短。传统收集器必须停下来更新大量引用，ZGC 把这部分工作分摊到了 GC 并发搬迁和应用线程实际读引用时完成。
