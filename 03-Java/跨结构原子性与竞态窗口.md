# 跨结构原子性与竞态窗口

> 两个在并发编程中常被混淆的关键概念，本质都是"原子性边界"的问题，但视角不同。

---

## 跨结构原子性

### 定义

**跨结构原子性**：一个逻辑操作涉及**两个或以上独立的数据结构**时，无法保证它们的状态同时更新成功或同时回滚，导致出现"一个变了另一个没变"的不一致状态。

### 核心问题

每个并发安全容器（如 `ConcurrentHashMap`、`ConcurrentLinkedDeque`）只保证**自身内部操作**的原子性，管不到其他结构。多个结构之间的操作组合在一起时，原子性就失效了。

### 典型场景

```java
ConcurrentHashMap<Long, Boolean> map = new ConcurrentHashMap<>();
Deque<Long> deque = new ConcurrentLinkedDeque<>();

public void access(long userId) {
    if (map.putIfAbsent(userId, true) == null) {  // map 写成功
        deque.addLast(userId);                     // ❌ 这里抛异常 → map 变了，deque 没变
    }
}
```

- `putIfAbsent` 在 map 里插入成功
- 下一行 `deque.addLast` 抛异常 → map 已经变了，deque 没变，两个结构**不一致**
- 没有一把"跨结构的锁"来保证这两个操作同时成功或同时回滚

### 解决方案

| 方案 | 做法 | 代价 |
|------|------|------|
| **全局锁** | 用 `synchronized` 或 `ReentrantLock` 把整个操作包起来 | 回到串行，并发度归零 |
| **统一数据结构** | 改用自带 LRU 语义的 `LinkedHashMap` + Collections.synchronizedMap | 同上 |
| **成熟方案** | 使用 [[Caffeine详解\|Caffeine]]、Guava Cache 等专业缓存库 | 外部依赖，但正确性和性能都有保障 |

## 竞态窗口

### 定义

**竞态窗口（Race Window）**：两行（或更多）代码之间没有原子性保护，其他线程可以插进来执行的**那段时间空隙**。

### 核心问题

每一行代码本身是原子的（从 CPU 指令角度），但两行之间没有锁保护，线程调度可以在任意时刻切换——这就给其他线程留下了"见缝插针"的机会。

### 典型场景

```java
// 淘汰逻辑
Long evicted = deque.pollFirst();  // ① 从队头取出 userId=1
map.remove(evicted);               // ② 从 map 中删除
```

```
时间轴 →
线程A:  pollFirst() → 拿到 1  →   map.remove(1)   ← 把线程B的也删了！
线程B:                       →  put(1) 插入新数据
```

1. 线程 A 执行 `pollFirst()` 从 deque 头部拿到 `userId=1`，准备从 map 中删除
2. 在线程 A 执行 `map.remove(1)` **之前**，线程 B 插进来给 map 插入了一个新用户 `userId=1`
3. 线程 A 继续执行 `map.remove(1)` → **把线程 B 刚插入的新数据误删了**

> [!warning] 竞态窗口 vs 跨结构原子性
> **竞态窗口**关注的是"时间上的空隙"——两行代码之间线程插进来的那段时间。
> **跨结构原子性**关注的是"空间上的跨度"——操作涉及多个数据结构。
> 两者经常同时出现：`pollFirst` + `map.remove` 既有竞态窗口（两行之间有空隙），又是跨结构操作（涉及 deque 和 map）。

### 如何消除

加锁或使用原子操作把多步操作合并成一步：

```java
// 方式一：加锁
synchronized (lock) {
    Long evicted = deque.pollFirst();
    map.remove(evicted);
}

// 方式二：改用统一数据结构（如 LinkedHashMap），一次回调搞定淘汰和删除
```
