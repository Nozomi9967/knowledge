## 六、缓存设计（5 题）

### 28. 缓存雪崩、缓存击穿、缓存穿透分别是什么？三者本质区别是什么？各自的解决方案？

> **知识点跳转：** [[什么是缓存雪崩、击穿、穿透？]]

**参考答案**

这三个词经常被混着说，区分点其实就两个，缓存里有没有这个 key，数据库里有没有这个 key。雪崩是缓存里有、但大量 key 在同一时间集体过期，请求全部砸到数据库上；击穿是缓存里有、但单个热点 key 过期了，同一瞬间几十上百个并发请求一起进来重建缓存；穿透是缓存里没有、数据库里也没有，压根建不了缓存，每个请求都直接打穿到库上。方案对应着来：雪崩把过期时间打散、加随机值，核心数据干脆不设过期靠后台异步更新；击穿用互斥锁，只放一个线程去重建，其他线程等一下或者返回旧值，热点数据同样可以不设过期；穿透要三层防线，先做参数校验拦掉明显非法的请求，再缓存空值给个短过期兜底，最外面用布隆过滤器把一定不存在的 key 挡掉。

**追问参考答**

布隆过滤器的缺点主要是四个：它有误判率，说不存在的一定不存在，说存在可能其实不存在，这叫假阳性；它不支持删除元素，要删只能换 Counting Bloom；它做不到百分之百拦截，所以通常还得配空值缓存兜底；Redis 原生也不支持，得额外装 RedisBloom 模块。生产上一般把它放在最前面做粗筛，真正的可靠性还是靠空值缓存和参数校验。

### 29. Cache Aside（旁路缓存）策略的写操作，为什么推荐「先更新数据库，再删除缓存」？反过来先删缓存会有什么问题？

> **知识点跳转：** [[Cache Aside 写策略满分拆解]] · [[数据库和缓存如何保证一致性？]]

**参考答案**

核心就是时间窗口的大小。反过来先删缓存再更新数据库，删完到数据库真正更新完成之间有一个毫秒级的窗口，这期间读请求进来，缓存 miss 了去读库，读到的还是旧值，然后它把这个旧值写回缓存，缓存就永久脏了，后面一直读旧值。而先更新数据库再删缓存，不一致窗口被压到微秒级：写请求先更新库，这是毫秒级的磁盘操作，然后立刻删缓存，删缓存是内存操作，微秒级就完了；读请求要造成脏数据，必须恰好在删缓存之前读到旧值并写回，而且要求它读库返回比写请求更新库还快，实际上几乎不可能发生。所以工程上默认推荐这个顺序。

**追问参考答**

理论上确实还有窗口，但概率极低，而且就算真发生了也不致命：如果写缓存发生在删缓存之前，那次删除正好把旧值清掉，下一次读 miss 就会拿到新值，不一致就自动修复了。这也是为什么它被当作默认方案，而不是追求理论上的零窗口。

### 30. 除了 Cache Aside，数据库和缓存一致性还有哪些保证方案？「延迟双删」是怎么做的？有什么局限？

> **知识点跳转：** [[数据库和缓存如何保证一致性？]]

**参考答案**

除了 Cache Aside，还有四条思路。第一条是延迟双删，算是 Cache Aside 的加强版；第二条是订阅 binlog 异步更新缓存，比如用 Canal 把数据库变更同步到缓存里，业务代码完全不用管删缓存，最终一致；第三条是给缓存设个短过期时间兜底，就算短暂不一致，过期后也能自动刷新；第四条是更新的时候加分布式锁，保证同一时刻只有一个线程在更新缓存。延迟双删的做法是先删缓存、再更新数据库、然后延迟几百毫秒再删一次缓存，延迟的目的就是等那个读请求把旧值写回缓存的窗口过去，第二次删除把残留的旧值清干净。它的局限有三个：延迟时间不好定，太短兜不住窗口、太长影响命中率；极端并发下仍然可能不一致；第二次删除可能失败，得配上删除重试机制兜底。

**追问参考答**

有人会把读写穿透、写回当一致性方案答，这里要分清：那三个是缓存更新策略，解决的是缓存和数据库的读写分工，不是一致性问题。一致性方案是围绕"怎么让缓存和库最终对齐"来的，延迟双删、binlog 订阅、短过期兜底、加锁更新都属于这一类。

### 31. 如何设计一个「动态缓存热点数据」的策略？以电商 Top1000 热门商品为例说明，用哪些 Redis 命令实现？

> **知识点跳转：** [[redis八股]] · [[Redis 常见数据类型和应用场景]]

**参考答案**

用 ZSet 做一个按访问时间排序的队列。member 存商品 ID，score 存访问时间戳，越近访问的分数越大、排名越靠前。每次请求进来，用 zadd 更新这个商品的 score；然后后台定期用 zrange 把排名最后的两百个淘汰掉，同时从数据库里随机读两百个商品 zadd 回队列，保证队列里始终有一批候选；请求先查队列，拿到商品 ID 之后再从另一个缓存结构里取详情返回。核心思想就是按最新访问时间排名，定期淘汰冷数据、回填新候选，队列里自然留下的就是最近最热的那些商品，既不用全量统计，也不会被历史数据撑爆。

**追问参考答**

为什么淘汰之后一定要回填，因为队列里如果只有淘汰没有补充，跑一段时间就空了，热点会越跑越少。回填用随机读而不是按销量取，是为了让候选池保持多样性，避免热点固化。另外 ZSet 的 score 用时间戳而不是访问次数，是为了让"最近"这个维度生效，访问次数高但很久没访问的应该被换掉。

### 32. Read/Write Through 和 Write Back 这两种缓存策略为什么在 Redis + MySQL 的场景下很少用？它们各自适合什么场景？

> **知识点跳转：** [[Read Through Write Through Write Back 深度拆解]]

**参考答案**

Read Through 和 Write Through 的思路是应用只跟缓存打交道，由缓存组件代理数据库的读写，读不到缓存自己回库加载，写的时候缓存同步写库。这套东西 Redis 干不了，因为它是纯 KV 存储，没有内置的数据库加载和写入能力，要做得自己在业务层实现，那就不叫这个模式了，所以基本用不上。Write Back 是写只写缓存、标脏、立即返回，数据库异步批量写，它的优势是写入吞吐极高，适合写多的场景，但它给不了强一致，而且缓存本身是内存，掉电脏数据全丢，所以不适合拿来给 Redis 当缓存策略用。

**追问参考答**

为什么 CPU 缓存和文件系统能接受这个风险，Redis 不行，因为前者有硬件层面的保障，比如电池保护、NVDIMM、内核会强制刷盘，掉电也有兜底；Redis 是应用层的纯内存，进程一挂或者机器一断电就是真丢了，没有任何机制能救，所以同一个策略在硬件层能用、在应用层不能照搬。

## 七、高可用（5 题）

### 33. 主从复制是怎么实现的？全量同步和增量同步分别发生在什么阶段？

> **知识点跳转：** [[主从复制是怎么实现的？]] · [[replication buffer 与 repl_backlog_buffer 对比]]

**参考答案**

先纠正一个高频错误，Redis 主从复制没有 binlog，binlog 是 MySQL 的东西，这个说错面试基本就废了。Redis 复制靠三样东西：RDB 快照做全量、命令传播做增量、repl_backlog_buffer 支撑断线续传。全量同步发生在从节点第一次连上来，或者断线重连后积压缓冲区里缺的数据已经被覆盖了：从节点发 psync，主节点 fork 子进程生成 RDB 发过去，从节点清空本地数据加载 RDB，这期间主节点新产生的写命令通过 replication buffer 补给从节点。增量同步就是正常运行时的命令传播，主节点执行完写命令就把命令发给从节点执行，靠 repl_backlog_buffer 记着最近一段命令。

**追问参考答**

复制是异步的，主节点本地执行完就返回给客户端，不等从节点确认，所以只能做到最终一致，保证不了强一致。这也是脑裂会丢数据的根源：主节点在没同步出去的时候就挂了，那批数据只有旧主有。

### 34. replication buffer 和 repl_backlog_buffer 有什么区别？它们分别在什么场景下发挥作用？

> **知识点跳转：** [[replication buffer 与 repl_backlog_buffer 对比]] · [[主从复制是怎么实现的？]]

**参考答案**

这两个缓冲区最容易混，其实服务的是两件事。replication buffer 是给全量同步用的：从节点正在加载 RDB 的时候，主节点新产生的写命令放在这里，等从节点加载完再补发过去。它是每个从节点各有一个，从节点同步完成就释放。repl_backlog_buffer 是给增量同步用的：它是一个常驻内存的环形缓冲区，全局只有一个，所有从节点共享，记录主节点最近的所有写命令。从节点断线重连后，如果要的偏移量还在这个环里，就把缺的命令补给它是增量；如果已经被覆盖了，就只能重新做一次全量同步。它的大小由 repl-backlog-size 控制，默认 1MB。

**追问参考答**

记忆点就一句话，replication buffer 管全量同步期间的增量，repl_backlog 管断线续传。还有一个容易忽略的差异：replication buffer 满了会受 client-output-buffer-limit 限制，极端情况可能导致主节点断开这个从节点；repl_backlog 满了是环形覆盖旧命令，不会报错，只是从节点追不上就得全量。

### 35. 为什么需要哨兵（Sentinel）模式？哨兵如何判定主节点故障？「主观下线」和「客观下线」的区别？

> **知识点跳转：** [[为什么要有哨兵？]]

**参考答案**

哨兵解决的是主从架构的一个硬伤，主节点挂了之后没法自动恢复。主从只能保证数据有副本，但选谁当新主、怎么通知客户端切换，全靠人工，哨兵就是来做自动故障转移的。故障判定分两级：主观下线是单个哨兵在 down-after-milliseconds 时间内没收到主节点的心跳，它自己认为主节点挂了；客观下线是多个哨兵通过 is-master-down-by-addr 互相通信确认，票数达到 quorum 也就是通常的半数以上，才正式判定客观下线。之后进入故障转移，这里有两个"领导"容易混：先是哨兵集群投票选出一个哨兵 leader 负责执行这次转移，它是指挥官不亲自上阵；再由这个 leader 从从节点里按优先级、复制偏移量、runid 打分，挑一个升为新主，然后通知其他从节点改主从关系、通知客户端新地址。

**追问参考答**

旧主恢复之后不会自动变回主，它被降级为从节点，向新主做全量同步，而全量同步会先清空本地数据再做，所以脑裂期间写进旧主的那部分数据就彻底没了。这也解释了为什么光有哨兵还不够，还得配 min-slaves 系列参数来限制旧主接收写请求。

### 36. 为什么需要 Redis Cluster？哈希槽是怎么计算的？16384 个哈希槽如何分配到节点上？

> **知识点跳转：** [[为什么要有 Redis Cluster 集群？]]

**参考答案**

单机内存有限，数据量大到一台机器放不下就得做切片集群，Redis Cluster 就是为了横向扩展，同时降低对单一主节点的依赖。槽的计算分两步：先对 key 做 CRC16 运算得到一个 16 位的值，再用这个值对 16384 取模，得到 0 到 16383 之间的槽编号，这个槽落在哪个节点上，key 就存在哪个节点。槽的分配有两种方式，cluster create 建集群时会自动把 16384 个槽平均分到各节点；也可以 cluster meet 先让节点互相握手认识，再用 cluster addslots 手动指定每个节点负责哪些槽。要特别注意，16384 个槽必须全部分配完，只要有一个槽没分配，整个集群就是不可用状态。

**追问参考答**

为什么是 16384 而不是更大，这是迁移开销和分布均匀度之间的权衡：槽太多，节点间心跳包要携带的位图就大、迁移时碎块也多；槽太少又容易分布不均。扩容时把一部分槽从原节点迁到新节点，用 MIGRATE 搬槽里的 key，迁移过程中访问这些槽的请求会收到 MOVED 重定向，正在迁移的那个槽会返回 ASK 重定向，客户端跟着跳过去就行。

### 37. 集群「脑裂」是什么？会导致什么后果？如何用配置参数避免脑裂导致的数据丢失？

> **知识点跳转：** [[为什么要有哨兵？]] · [[主从复制是怎么实现的？]]

**参考答案**

脑裂是网络分区造成的。主节点和从节点、哨兵之间的网络断了，哨兵认为主节点挂了，选举出新主，可旧主其实活得好好的，还在接客户端的写请求，于是集群里同时存在两个主节点。等网络恢复，旧主被降级成从节点，要向新主做全量同步，而全量同步会先清空本地数据，所以脑裂期间写进旧主的数据全部丢失。避免的办法是两个参数配合：min-slaves-to-write N 要求主节点至少和 N 个从节点保持连接，min-slaves-max-lag T 要求主从复制的 ACK 延迟不超过 T 秒，两个条件同时满足才允许写，否则直接拒绝写请求。

**追问参考答**

脑裂时旧主是假故障，它既响应不了哨兵心跳，也没法和从库完成 ACK，两个条件双双不满足，于是被限制接收写请求，写不进去自然就不丢数据。举个典型配法：min-slaves-to-write 设 1、min-slaves-max-lag 设 12 秒、哨兵 down-after-milliseconds 设 10 秒，主库卡住 15 秒时哨兵开始切换，同时旧主也没有从库能在 12 秒内完成 ACK，写请求被拒，切换完成后只有新主能写。

## 八、分布式锁（4 题）

### 38. 如何用 Redis 实现分布式锁？加锁需要满足哪三个条件？请写出核心命令。

> **知识点跳转：** [[多节点争抢资源， Redis 分布式锁是怎么实现的？]]

**参考答案**

加锁要同时满足三个条件。第一是原子性，检查锁存不存在和设置值必须一步完成，所以用 SET 的 NX 参数，别用 SETNX 加 EXPIRE 两条命令拼，中间客户端一宕机就成了永久死锁。第二是必须带过期时间，防止客户端异常退出后锁永远占着，用 PX 或者 EX 都行。第三是锁的值必须是客户端的唯一标识，解锁的时候要判断这把锁是不是自己加的，防止误删别人的。命令就是 SET lock_key 唯一值 NX PX 10000 这么一条。

**追问参考答**

NX 的含义是 key 不存在才设置，正好对上锁空闲就获取、锁被持有就放弃的语义。EX 单位是秒，PX 单位是毫秒，现在一般用 PX，因为业务执行时间常常是毫秒级的，用秒不够精细。唯一值的作用在解锁那一刻体现：A 的锁到期自动释放后被 B 拿到，A 恢复后想解锁，拿自己那个值一比对不相等，就不会把 B 的锁删掉。

### 39. 为什么解锁必须用 Lua 脚本？「判断值 + 删除」为什么不能拆成两步？

> **知识点跳转：** [[多节点争抢资源， Redis 分布式锁是怎么实现的？]]

**参考答案**

因为解锁其实是两个动作，先判断这把锁是不是自己加的，再删除它，这两个动作必须原子完成，拆开就留出了竞态窗口。具体场景是这样：A 判断值确实是自己之后、还没来得及执行删除，这时候锁到期自动释放了，B 抢到了锁；A 恢复执行删除，删掉的其实是 B 的锁。锁就这么失效了，后面可能一堆客户端同时持锁在跑。所以要写成一段 Lua，先 get 出来跟 ARGV 里的值比较，相等才 del，不相等返回 0。Redis 执行 Lua 是原子的，中间插不进别的命令，竞态窗口就被堵死了。

**追问参考答**

有人会问既然 Redis 单线程，为什么两条命令还会被打断，因为单线程只保证单条命令原子，两条命令之间可以有别的客户端的命令插进来，这不是多线程问题，是命令之间没有隔离。Lua 脚本的原子性正好补上这一层。

### 40. 基于 Redis 的分布式锁有什么缺点？锁的超时时间怎么设置比较合理？「看门狗（Watchdog）」续约是怎么工作的？

> **知识点跳转：** [[如何保证 Redis 分布式锁的高可用和高性能？]] · [[Redisson详解]]

**参考答案**

主要有两个缺点。一是超时时间难设，设短了业务还没跑完锁就失效、别人进来并发执行；设长了持锁的客户端一旦挂掉，其他人要干等很久。二是主从异步复制带来的不可靠，主节点加锁成功但还没同步给从节点就宕机了，从节点升为新主后这把锁根本不存在，其他客户端可以在新主上再次加锁成功，同一把锁就被两个客户端同时持有，互斥性直接破了。超时的合理设置是略大于业务执行时间，再配合看门狗续约兜底。看门狗就是 Redisson 里的守护线程，默认锁有效期 30 秒，每 10 秒检查一次，业务还没执行完就自动续回 30 秒；业务执行完释放锁，守护线程也跟着销毁。

**追问参考答**

主从那个问题正是 Redlock 想解决的场景，但它自己的代价和争议也不小。另外要注意看门狗的生效前提是客户端进程还活着，如果整个 JVM 被 GC 卡住或者进程被杀，守护线程也停了，锁照样会到期，这种场景只能靠 fencing token 在资源侧做最后一道校验。

### 41. Redlock 是怎么工作的？加锁成功的两个条件是什么？它有什么争议？

> **知识点跳转：** [[多节点争抢资源， Redis 分布式锁是怎么实现的？]] · [[Redisson详解]]

**参考答案**

Redlock 的思路是向多个相互独立的 master 节点依次申请加锁，官方建议五个。加锁成功要同时满足两个条件：一是在超过半数节点上加锁成功，二是整个加锁过程的总耗时小于锁的过期时间。成功之后锁的有效期要重新算，等于原 TTL 减去加锁花掉的时间。争议来自两个方向。Martin Kleppmann 批了两点：一是时钟漂移，某个节点时钟跳一下锁可能提前过期，两个客户端同时持锁；二是进程暂停，客户端 GC 卡住的时候锁过期了，恢复后它还以为自己持有锁。他的解法是 fencing token，用一个单调递增的令牌，操作资源时校验，过期的请求一律拒绝。Antirez 反驳说时钟跳跃在生产环境极少发生，NTP 配成微调就能避免，Redlock 追求的是工程上足够安全而不是理论上的绝对安全，而且进程暂停是所有分布式锁服务都要面对的问题，不是 Redlock 独有。现状是 Redisson 已经把 RedLock 标记为废弃，默认用单点 Redis 锁加看门狗续约。

**追问参考答**

要补一句，Martin 的批评里"进程暂停"比"时钟漂移"更致命，因为它跟时钟无关，任何依赖锁超时的方案都有这个洞，所以真正的解法不在锁本身，是在资源侧做版本号或者 fencing token 校验。

## 九、实战技巧（6 题）

### 42. 什么是 Redis 大 key？大 key 会带来哪些问题？

> **知识点跳转：** [[Redis 大 Key 对持久化有什么影响？]] · [[redis八股]]

**参考答案**

大 key 的判定标准分两类：String 类型的值超过 10KB 就算大 key；Hash、List、Set、ZSet 这类集合，元素个数超过 5000 就算。这两个数字是业界常用的判断线，不是 Redis 的硬性规定。它带来四个问题。一是客户端超时阻塞，单线程处理大 key 本身就慢，客户端长时间收不到响应。二是网络阻塞，一个 1MB 的 key 按 1000 QPS 算就是每秒 1000MB 的流量，千兆网卡直接被冲爆。三是阻塞工作线程，del 一个大 key 的时候主线程同步释放内存，卡顿非常明显。四是内存分布不均，集群里槽是分均匀了，但数据和访问量会倾斜，个别节点内存高、QPS 也高，成了木桶的短板。

**追问参考答**

为什么大 key 在集群里更麻烦，因为槽是按 key 数量分的，不是按内存分的，一个 500MB 的 key 和一个 1KB 的 key 各占一个槽位，但给节点带来的压力完全不是一个量级，扩容时迁移它也要花很久，还会阻塞 migtate 的连接。

### 43. 如何查找大 key？请至少说出三种方法，并说明各自的优缺点。

> **知识点跳转：** [[SCAN命令查找大key详解]] · [[SCAN 命令原理详解]]

**参考答案**

常用三种。第一种是 redis-cli --bigkeys，扫一遍返回每种类型最大的那个 key，快是快，但局限明显，它只给每种类型最大的一个、拿不到前 N 名，而且对集合类型只按元素个数算，不看元素实际占多少内存。第二种是 SCAN 遍历加命令估算，扫出 key 之后用 TYPE 判断类型，集合用 LLEN、HLEN、SCARD、ZCARD 看个数，想知道真实内存就用 MEMORY USAGE 直接查，这个方法可控也能做前 N 名排名，缺点是要自己写脚本。第三种是 RdbTools 这类工具，离线解析 RDB 文件按内存排序输出，完全不碰线上，缺点是要能拿到 RDB 文件，实时性差。

**追问参考答**

为什么推荐在从节点或者业务低峰期执行，因为扫描本身就消耗资源，--bigkeys 会遍历整个键空间，主节点上跑会跟线上请求抢 CPU 和内存带宽。另外 MEMORY USAGE 虽然更准，但它内部要遍历整个 key，对超大 key 本身就是个重操作，别在大 key 上反复调。

### 44. 如何安全删除大 key？分批次删除和异步删除分别怎么做？

> **知识点跳转：** [[Redis 大 Key 对持久化有什么影响？]] · [[redis八股]]

**参考答案**

两种思路。第一种是分批删，按类型用不同命令：大 Hash 用 hscan 每次取 100 个字段再 hdel，大 List 用 ltrim 每次裁掉一小段，大 Set 用 sscan 扫 100 个再 srem，大 ZSet 用 zremrangebyrank 每次删排名前一百的。核心是把一次大操作拆成很多次小操作，让主线程每删一小批就有机会去处理别的请求。第二种是异步删，直接用 unlink。unlink 的时候主线程只把 key 从全局哈希表里摘掉，这个动作微秒级，真正的内存释放交给后台的 lazyfree 线程去做，主线程完全不卡。

**追问参考答**

lazyfree 有四个配置项，默认都是关的。lazyfree-lazy-eviction 控制内存淘汰时异步释放，lazyfree-lazy-expire 控制过期键删除时异步释放，lazyfree-lazy-server-del 控制隐式删除时异步释放，比如 rename 覆盖目标键时得先删目标键，slave-lazy-flush 控制从库全量同步前清空数据时异步释放。这几个打开能明显降低大 key 和批量过期场景的卡顿。

### 45. Pipeline 解决了什么问题？它是客户端功能还是服务端功能？使用时要注意什么？

> **知识点跳转：** [[Pipeline 批量处理减少 RTT]] · [[Redis6.0多线程IO的限制]]

**参考答案**

Pipeline 是把一批命令打包一次性发给服务端，服务端全部处理完再统一返回，这样 N 条命令只花一次网络往返，省掉的是 RTT。它是客户端的功能，不是服务端功能，本质是客户端库把命令攒起来批量发出去，服务端那边还是逐条执行，只是不用每条都等一轮网络。使用时注意两点：一是别打包太多太大，几万个命令塞一个包，服务端要一次性分配很大的接收缓冲区，网络也容易拥塞；二是会有队头阻塞，一批里只要有一条慢命令，后面的响应全得等它。

**追问参考答**

Pipeline 和事务能一起用，但它们解决的不是一件事。Pipeline 解决的是网络传输效率，事务解决的是原子性。可以把 MULTI 和 EXEC 放进 Pipeline 里发出去，不过要清楚 Pipeline 本身不保证原子性，这批命令中间完全可能插进其他客户端的命令。

### 46. Redis 事务支持回滚吗？「EXEC 之前报错」和「EXEC 之后报错」的行为有什么区别？

> **知识点跳转：** [[redis八股]]

**参考答案**

Redis 事务不支持回滚，这是它和关系型数据库最大的区别，DISCARD 只是主动放弃事务、清空命令队列，那也不叫回滚。要分两种错误看。第一种是 EXEC 之前就报错，也就是命令入队的时候就有语法错误或者命令根本不存在，这时候整个事务会被拒绝执行，一条都不跑，返回 EXECABORT。第二种是 EXEC 之后报错，命令都入队成功了，执行时才发现类型不对，比如对一个 String 键执行 LPUSH，这时候报错的那条单独失败，其他命令照常执行，既不回滚已执行的，也不中断后面的。

**追问参考答**

所以那句"未执行的命令会被 discard"是错的。EXEC 一旦发出，所有入队的正确命令都会逐条执行，运行时错误影响不了别人；DISCARD 是主动清空队列放弃事务，对已经 EXEC 过的命令没有任何作用。Redis 这么设计的原因是不想在运行时维护 undo 日志，它假设入队阶段的语法错误能提前拦住，运行时错误属于程序员自己的 bug，不替人兜底。

### 47. Redis 如何实现延迟队列？用什么数据结构？核心命令是什么？有什么问题？

> **知识点跳转：** [[redis八股]] · [[Redis 常见数据类型和应用场景]]

**参考答案**

用 ZSet 做，score 存任务的到期时间戳。生产用 zadd delay_queue 到期时间戳 任务ID；消费用 zrangebyscore 把 score 小于等于当前时间的任务取出来；处理完再用 zrem 删掉。问题有四个。一是精度靠轮询，轮询间隔决定延迟精度，间隔短了费 Redis，长了延迟大。二是可能丢消息，取出来之后、zrem 之前进程崩了，重启后这条的 score 已经过期会被再取一次，状态就很尴尬。三是重复消费，多个消费者同时轮询会取到同一批任务，得靠 zrem 的返回值或者额外的锁去重。四是它没有原生 ACK，不像 Stream 有 PEL 兜底，可靠性全靠业务自己保证。

**追问参考答**

生产上如果要更可靠，一般会把这套逻辑换成 Stream 加消费者组，或者直接用 RocketMQ 的延迟消息、时间轮方案。用 ZSet 的场合多半是延迟精度要求不高、量也不大的场景，比如订单超时关闭做个兜底扫描。

### 48. SCAN 命令相比 KEYS 命令有什么优势？SCAN 的游标原理是怎样的？

> **知识点跳转：** [[SCAN 命令原理详解]] · [[SCAN命令查找大key详解]]

**参考答案**

KEYS 是一次性扫全库，复杂度 O(N)，几百万个 key 的时候主线程会被卡住好几秒，线上绝对不能用。SCAN 是增量式迭代，每次返回一个游标加一批 key，你拿着游标继续下一批，把一次大扫描拆成很多次小扫描，主线程每次只花很少时间，不会长时间阻塞。游标的原理是基于哈希桶索引的逆二进制游标，它不是简单加一递增，而是高位优先、反向进位，好处是哈希表扩容或缩容时已经扫过的桶不会因为元素重新分配而漏掉。游标返回 0 就表示遍历结束。

**追问参考答**

遍历过程中发生 rehash 还能不能保证不遗漏，能，靠的就是这个高位递增的设计，扩容缩容时已开始的桶不会漏，代价是可能重复返回一些 key，所以下游要能去重。另外，游标为 0 就意味着结束，不存在游标是 0 却还没扫完的情况；反过来游标不为 0 但这一批返回空集是有可能的，那是正常的，继续传游标就行。

## 十、消息队列（4 题）

### 49. 用 List 实现消息队列有什么缺陷？Stream 是怎么解决这些问题的？

> **知识点跳转：** [[List与Stream消息队列对比]] · [[Stream消息队列]]

**参考答案**

List 做消息队列有三个缺陷。一是没有持久化语义，pop 出来消息就从队列里消失了，没法回溯也没法重放。二是没法做消费者组，brpop 是竞争消费，一条消息只能被一个消费者抢到，没法组内分工又保证每条都被处理。三是生产者得自己生成全局唯一 ID，List 本身不提供。Stream 对应解决：它本质是追加式日志，消息持久化在流里，可以按 ID 区间回溯；用 XREADGROUP 加消费者组，按 last-delivered-id 分配，一条消息只给组内一个消费者；有 PEL 加 ACK 机制，没确认的消息不消失，可以 XCLAIM 让别人接手；消息 ID 自动生成，是时间戳加序号，全局唯一且有序。

**追问参考答**

List 不能实现消费者组，根子在于 brpop 的语义就是抢到即出队，消息一 pop 就没了，既没法记录谁在处理，也没法重试。要实现类似效果只能在应用层自己加锁、自己维护处理中列表，那等于在业务代码里重造一遍 Stream 的 PEL，不如直接用 Stream。

### 50. Stream 的消费者组是怎么工作的？ACK 机制和 PendingList 分别是什么？

> **知识点跳转：** [[Stream消息队列]] · [[Stream的ACK与PendingList]]

**参考答案**

XREADGROUP 消费时，Redis 按这个组的 last-delivered-id 把新消息分配给组内消费者，正常情况下一条消息只给一个消费者，实现组内负载均衡。消息投递出去后会进入这个消费者的 PEL，也就是待处理列表，只有调用 XACK 才从 PEL 里移除，才算消费成功。注意 Stream 里原始的消息并不会被删掉，删的只是 PEL 里那条待确认记录，这也是它能回溯的原因。这套机制给的是至少一次交付的语义：没 ACK 的消息一直留在 PEL 里不会丢，但可能被重复投递。

**追问参考答**

消费了不 ACK 会一直留在 PendingList 里，而且 Redis 不会自动重发。要有独立的定时任务用 XPENDING 扫 PEL 里的超时消息，再用 XCLAIM 或者 XAUTOCLAIM 把它们重新分配给别的消费者；还可以看 delivery-count，认领次数过多的消息扔进死信队列人工处理。重复消费的根治办法还是业务幂等，消息 ID 是唯一的，拿它当去重键最合适。

### 51. XREADGROUP 的三种读取模式（`>`、`0`、`$`）分别代表什么含义？

> **知识点跳转：** [[Stream的XREADGROUP三种模式]] · [[Stream的消息回溯能力]]

**参考答案**

这三个符号要分清。大于号读的是还没被分配给任何消费者的新消息，也就是正常消费模式。0 读的是当前消费者自己在 PEL 里认领了但还没 ACK 的消息，用于故障恢复或者回溯自己没处理完的。美元符是从流的末尾开始，只读之后到达的新消息，历史的一条都不读，通常配合阻塞等待一起用。

**追问参考答**

0 模式实现的就是故障恢复。比如消费者 A 处理到一半宕机了，重启回来后用 0 就能把自己之前没 ACK 的那些消息重新捞出来接着处理，不用等着别人来认领。这也是 Stream 可回溯能力的一部分，消息一直躺在流里，只要知道 ID 区间，任何消费者都能重读。
