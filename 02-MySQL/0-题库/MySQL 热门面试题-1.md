## 一、索引（6 题）

### 1. 什么是索引？索引有哪些分类？

> **知识点跳转：** [[MySQL索引]]

**参考答案**

索引本质是一种帮助存储引擎快速定位数据的数据结构，它把全表扫描变成按索引结构定向查找。分类要从四个维度讲。按数据结构分，有 B+Tree 索引、Hash 索引和全文索引，InnoDB 默认用 B+Tree，因为只有它既支持等值又支持范围。按物理存储分，有聚簇索引和二级索引，聚簇索引就是主键索引，叶子节点存的是整行数据；二级索引也叫辅助索引，叶子节点存的是主键值，拿到主键还要再查一次聚簇索引，这就是回表。按字段特性分，有主键索引、唯一索引、普通索引和前缀索引四种。按字段个数分，有单列索引和联合索引。面试里有个小坑，"非聚簇索引"这个说法不规范，标准术语是二级索引，说错容易被追问。

**追问参考答**

四个维度就是数据结构、物理存储、字段特性、字段个数，每个维度下面的具体分类要能一口气说完。补一句，前缀索引是对字符串字段的前 N 个字符建索引，目的是减少索引体积，代价是区分度下降，所以 N 要选到区分度足够的位置。

### 2. 为什么 InnoDB 用 B+Tree 作为索引结构，而不用 B 树、二叉搜索树或哈希表？

> **知识点跳转：** [[MySQL索引]]

**参考答案**

核心原因是 B+Tree 能把磁盘 IO 次数压到最低，而且范围查询友好。跟 B 树比，B+Tree 的非叶子节点只存索引不存数据，一个 16KB 的页能放更多 key，扇出更大，树高就更矮，定位一条记录需要读的页更少。同时 B+Tree 的数据全部集中在叶子层，叶子之间还用双向链表串起来，范围查询找到起点之后顺着链表走就行，不用像 B 树那样回溯父节点。跟二叉树和二叉搜索树比，B+Tree 是多叉树，树高是 log 以 m 为底，远低于二叉树的 log2，而且二叉搜索树在有序插入时会退化成链表、查询退化成 O(n)，B+Tree 靠节点分裂保证树高稳定。跟哈希表比，哈希表等值查询是 O(1)，但它无序，既不支持范围查询也不支持排序，所以只能做等值场景的补充。

**追问参考答**

范围查询快是因为叶子层的双向链表，一次遍历到底；不退化成链表是因为多叉树加上节点分裂机制，插入再有序也只是页内有序、树高不变。这两个是不同问题，别混答。

### 3. 什么是「回表」？什么是「覆盖索引」？如何利用覆盖索引避免回表？

> **知识点跳转：** [[MySQL索引]]

**参考答案**

回表是二级索引查询多出来的一次索引查找。二级索引的叶子节点只存主键值，所以按非主键条件查完整行的时候，先在二级索引 B+Tree 上定位到主键，再拿这个主键去聚簇索引 B+Tree 里找整行数据，两次索引查找就叫回表。覆盖索引是指查询需要的字段全部都在二级索引的叶子节点上，一次索引扫描就能拿到结果，不需要回表。要用好它，做法有三个：一是把高频查询的列组合成联合索引，让索引覆盖查询列；二是严格控制查询列，别写 SELECT 星号，因为星号要所有列、必然超出索引范围；三是用 EXPLAIN 看 Extra 列，出现 Using index 说明覆盖索引生效了。

**追问参考答**

规范里禁 SELECT 星号跟覆盖索引直接相关：只要查询列是索引列的子集，就不回表；星号把不属于索引的列也带上，索引覆盖立刻失效，只能回表。注意 Using index 是覆盖索引，Using index condition 是索引下推，两个别混。

### 4. 联合索引的最左匹配原则是什么？为什么 `>`、`<` 会中断匹配，而 `>=`、`<=`、`BETWEEN`、`LIKE 前缀`不会？

> **知识点跳转：** [[MySQL索引]] · [[最左前缀匹配范围查询不停止的原因]]

**参考答案**

要讲清楚这题得先说数据在 B+Tree 里怎么排。联合索引 a、b、c 是按 a 排序、a 相同时再按 b 排、b 也相同再按 c 排，所以 a 是全局有序的，b 和 c 都只是局部有序。最左匹配就是利用这个特性：只有从 a 开始等值匹配，才能靠二分定位到确定的区间，再在里面用 b、c。跳列不行，直接从 b 查，b 在整个索引里无序，只能全扫。至于范围查询，大于和小于这种开区间，在区间内部 b 是无序的，所以后面的列用不上索引，匹配在这里中断；而大于等于、小于等于、BETWEEN、LIKE 前缀这几种都含等值边界点，在边界那个点上 b 是有序的，可以继续用，所以不中断。

**追问参考答**

联合索引 a、b、c，条件写 a 大于 1 且 b 等于 2，b 用不上，因为在 a 大于 1 的那批记录里 b 是无序的。反过来说 a 等于 1 且 b 大于 2，b 能用上、c 用不上，因为 b 的范围里 c 无序。规律就一句：范围条件之后，后面的列一律失效，只是 >= 这种带等值点的能把边界那一条也用上。

### 5. 什么是索引下推（ICP）？EXPLAIN 里怎么判断有没有用到？

> **知识点跳转：** [[MySQL索引]]

**参考答案**

索引下推是把联合索引上能筛的条件，从 Server 层下推到存储引擎层，在遍历索引的时候就过滤掉不满足的记录，从而减少回表的行数。没有它的时候，存储引擎按索引条件把记录一条条捞出来，全部回表取整行，再交给 Server 层判断剩余条件，回表量很大。有了它，那些只靠索引列就能判断的条件在引擎层就筛掉了，回表次数直接下降。判断方法看 EXPLAIN 的 Extra 列，出现 Using index condition 就是用了索引下推。

**追问参考答**

下推的层是从 Server 层到存储引擎层，减少的是回表的行数和随之而来的 IO 开销。这里有个容易写错的地方：下推的不是"整个非聚簇索引查询"，而是联合索引里可筛选的那些条件，而且只能下推索引列上的条件，非索引列的条件照样得回表之后再判断。

### 6. 索引在什么情况下会失效？什么时候不需要创建索引？

> **知识点跳转：** [[MySQL索引]]

**参考答案**

失效场景主要有四类。第一类是模糊匹配方向不对，LIKE 百分号在左边或者两边都有，比如百分号 abc 或者百分号 abc 百分号，索引直接失效，只有 abc 百分号这种前缀匹配能用。第二类是在索引列上做函数运算、表达式计算或者隐式类型转换，比如 where id 加 1 等于 10，或者字符串列传了数字，索引就用不上。第三类是联合索引不满足最左匹配，跳列或者从中间列开始查。第四类是 or 连接的两个条件，一个有索引一个没有，整个条件退化成全表扫描。至于什么时候不该建索引：字段在 where、order by、group by 里都用不到；表数据量太小，全表扫比走索引还快；字段区分度低，比如性别只有两三个值；字段更新特别频繁，维护 B+Tree 的有序性开销比查询收益还大。

**追问参考答**

主键为什么要自增，是因为自增插入永远追加在最后一页，不会动已有数据；非自增主键可能插到中间某页，页满了就触发页分裂，要挪动数据、产生内存碎片，索引结构也不紧凑。索引列为什么建议 NOT NULL，一是 NULL 本身占存储空间，二是 NULL 会让优化器在做索引选择时更复杂，统计信息不准，可能选错执行计划。

## 二、事务与隔离级别（6 题）

### 7. 事务的四大特性（ACID）是什么？分别靠什么机制保证？

> **知识点跳转：** [[MySQL事务与隔离级别]]

**参考答案**

原子性是指事务里的操作要么全部成功、要么全部回滚，靠 undo log 保证，回滚的时候按 undo log 逆向执行。一致性是指事务执行前后数据库都要满足完整性约束，这条比较特殊，它没有专属的实现机制，是原子性、隔离性、持久性共同保证的结果，所以说一致性是最终目标，另外三个都是为它服务的手段。隔离性是指并发事务之间互不干扰，要分两种读法：快照读靠 MVCC 加 undo log 版本链，当前读靠 Next-key Lock 加锁。持久性是指事务提交后修改永久生效，靠 redo log 保证，崩溃之后重放 redo 就能恢复到提交状态。

**追问参考答**

原子性靠 undo log，持久性靠 redo log，隔离性分两条路径：快照读走 MVCC 加 undo log，当前读走 Next-key Lock。补一句常被追问的：为什么一致性不能单独靠某个机制，因为它是个业务语义要求，数据库只能通过 A、I、D 三个手段把你送到一致状态，具体什么是"一致"得由约束和业务逻辑定义。

### 8. 并发事务会引发哪三个问题？它们的严重程度排序？

> **知识点跳转：** [[MySQL事务与隔离级别]]

**参考答案**

三个问题是脏读、不可重复读、幻读。脏读是读到了别的事务还没提交的修改，如果对方回滚了，你读到的数据根本不存在。不可重复读是同一个事务里两次读同一行，结果不一样，因为中间别的事务改了并提交了。幻读是同一个事务里两次按同一个范围查，行数变了，因为中间别的事务插入或者删除了记录。严重程度排序是脏读最严重、不可重复读居中、幻读最轻，因为脏读读到的是根本不存在的数据，会直接导致错误的业务决策；不可重复读只是前后不一致，数据本身真实存在；幻读影响的是范围统计，危害相对最小。

**追问参考答**

区分三者的关键看"改的是什么"：脏读是读未提交；不可重复读是同一行被改了；幻读是同一范围内的行数变了。一句话记法：脏读读的是假数据，不可重复读是同一行变了两次，幻读是同一批数据多出来或少了几条。

### 9. 事务的四大隔离级别分别是什么？InnoDB 的默认隔离级别是哪个？

> **知识点跳转：** [[MySQL事务与隔离级别]]

**参考答案**

四个隔离级别从低到高是读未提交、读提交、可重复读、串行化。读未提交什么都能看到，脏读、不可重复读、幻读一个都挡不住。读提交只能挡住脏读，因为它是每条语句开始前才创建 Read View，所以能看到别的事务新提交的数据，不可重复读和幻读都还在。可重复读是 InnoDB 的默认级别，它在事务第一个快照读时创建 Read View 并在整个事务里复用，所以挡住了脏读和不可重复读；幻读理论上有，但 InnoDB 用两套机制基本压住了，快照读靠 MVCC 让行集保持恒定，当前读靠 Next-key Lock 锁住范围不让插入。串行化全部挡住，代价是并发度最低。

**追问参考答**

InnoDB 的 RR 解决幻读是两条腿走路：快照读走 MVCC，因为 Read View 复用、看的一直是同一个版本集合；当前读走 Next-key Lock，锁住扫描区间和间隙，从物理上禁止插入。要注意这两条腿各管各的，一旦在同一个事务里混用，就还有漏网的可能，这也是后面那道"MVCC 为什么防不住幻读"要讲的点。

### 10. 快照读和当前读有什么区别？InnoDB 在可重复读下如何分别解决幻读？

> **知识点跳转：** [[MySQL事务与隔离级别]] · [[为什么MVCC无法完全避免幻读现象]]

**参考答案**

快照读就是普通的 SELECT，不加任何锁，读的是 Read View 建立那一刻的快照。当前读是 SELECT FOR UPDATE、SELECT LOCK IN SHARE MODE，以及 UPDATE、DELETE、INSERT 这类写操作里面的读，它读的是最新已提交的数据，而且要加锁。RR 下解决幻读是分两条路径的：快照读走 MVCC，事务内 Read View 复用，所以无论别的事务怎么插入，你看到的行集始终不变；当前读走 Next-key Lock，它是记录锁加间隙锁的组合，既锁记录本身也锁记录前面的间隙，别的事务想往这个范围里插就被挡住。

**追问参考答**

普通 SELECT 走 MVCC 的版本链快照，不加锁；SELECT FOR UPDATE 走 Next-key Lock，是加锁读。这里不要说成"间隙锁解决当前读幻读"，间隙锁只是一半，真正起作用的是 Next-key Lock，记录锁负责挡住已存在行的修改，间隙锁负责挡住新行插入，缺一个都不完整，面试官很爱追这一句。

### 11. MVCC 是什么？Read View 的四个字段是什么？可见性判断规则？

> **知识点跳转：** [[MySQL事务与隔离级别]] · [[快照读时undo log和read view的具体作用]]

**参考答案**

MVCC 是多版本并发控制，核心思想是修改记录时不覆盖旧值，而是把旧版本挂到 undo log 的版本链上，快照读的时候靠 Read View 沿版本链往回找，找到第一个对自己可见的版本，这样读不加锁、写不阻塞读。Read View 有四个字段：creator_trx_id 是创建这个视图的事务 id；m_ids 是创建那一刻所有活跃且未提交的事务 id 列表；min_trx_id 是 m_ids 里最小的那个；max_trx_id 是下一个待分配的事务 id。可见性判断是拿记录隐藏列 trx_id 去比：小于 min_trx_id 说明改它的事务早就提交了，可见；大于等于 max_trx_id 说明改它的事务是在视图创建之后才启动的，不可见；夹在中间的就去 m_ids 里查，在列表里说明还活跃着、不可见，不在列表说明已提交、可见。

**追问参考答**

两个隐藏列是 trx_id 和 roll_pointer，trx_id 记录最后一次修改这行事务的 id，roll_pointer 指向 undo log 里上一个版本，顺着它就能把版本链串起来。这里有个高频错误要说清：min_trx_id 是"活跃未提交事务里最小的那个"，不是"已提交事务里最小的"，说反了整条判断逻辑就崩了。

### 12. Read Committed 和 Repeatable Read 的 Read View 创建时机有什么区别？事务真正启动是什么时候？

> **知识点跳转：** [[MySQL事务与隔离级别]]

**参考答案**

区别就一句话：读提交是每条 SELECT 执行前都新建一个 Read View，所以每条语句都能看到别的事务最新提交的数据，这就是不可重复读的根源；可重复读是在事务的第一个快照读时创建一次，然后整个事务生命周期都复用这一个视图，所以后面怎么查都是同一份数据。事务真正启动的时机也要说清：begin 或者 start transaction 只是开了个标记，执行第一条语句的时候才算真正启动；而 start transaction with consistent snapshot 会立即启动并马上创建一致性快照。

**追问参考答**

begin 不是立即启动，第一条语句执行时才真正启动，这一点在算"事务持续了多久"的时候很关键，长事务往往就是这么被忽略的。with consistent snapshot 则是立即开启并建快照，适合明确要读一致快照的场景。补一句精确表述：RR 的 Read View 是第一个快照读时创建，不是事务 begin 的瞬间创建。

## 三、锁机制（7 题）

### 13. MySQL 有哪些锁？哪些是 InnoDB 特有的？

> **知识点跳转：** [[MySQL锁机制]]

**参考答案**

按粒度分三类：全局锁、表级锁、行级锁。表级锁里有表锁也就是 LOCK TABLES 那种、MDL 元数据锁、意向锁、AUTO-INC 自增锁。行级锁里有记录锁、间隙锁、Next-key Lock 和插入意向锁。这题真正的考点是分清哪些是 InnoDB 特有的：全局锁、表锁、MDL、AUTO-INC 锁这些是 Server 层或者通用能力，MyISAM 也有；而意向锁、记录锁、间隙锁、Next-key Lock、插入意向锁全部是 InnoDB 才有的，因为只有 InnoDB 支持行级锁和事务。所以被问"MyISAM 有没有行锁"要能立刻答没有，MyISAM 只有表级锁。

**追问参考答**

MyISAM 没有行级锁，只有表锁，所以它并发写的能力很差。意向锁、间隙锁、Next-key Lock、插入意向锁都是 InnoDB 特有的，判断标准也简单：凡是依赖"行级锁"这个概念的，就只可能在支持行锁的 InnoDB 里存在。

### 14. 全局锁怎么用？应用场景是什么？如何避免全局锁阻塞业务？

> **知识点跳转：** [[MySQL锁机制]]

**参考答案**

加锁命令是 FLUSH TABLES WITH READ LOCK，执行后整个库进入只读状态，所有写操作都被阻塞，释放用 UNLOCK TABLES，或者会话断开自动释放。它的应用场景就是全库逻辑备份，要保证备份期间数据不被改动。缺点是整个库不能写，业务直接停摆，所以线上很少直接用。避免阻塞的做法是备份前开启一个事务，利用可重复读的 Read View 拿到一致性快照，这样备份读到的数据是同一时刻的，同时又不会阻塞其他事务的正常读写，工具层面就是 mysqldump 的 single-transaction 参数。

**追问参考答**

single-transaction 的原理就是备份前开事务、用 Read View 做快照，整个备份过程不锁表。它的限制是只适用于支持可重复读的存储引擎，InnoDB 可以，MyISAM 不行，因为 MyISAM 没有事务和 MVCC，拿不到一致性快照，只能退回去用全局锁。另外这条命令容易写错，是 FLUSH TABLES WITH READ LOCK，不是 flush db 什么的，命令名说错在面试里是硬伤。

### 15. MDL 锁是什么？为什么一个未提交的长查询会让整张表的 DDL 和后续 DML 全部阻塞？

> **知识点跳转：** [[MySQL锁机制]] · [[怎么查MDL锁]]

**参考答案**

MDL 是元数据锁，由 MySQL Server 层自动加，不是存储引擎层，所有存储引擎共享。规则是：增删改查这些操作自动加 MDL 读锁，改表结构这类 DDL 自动加 MDL 写锁，锁在事务提交后才释放。阻塞链是这么形成的：事务 A 做了个普通查询拿了 MDL 读锁但一直没提交，事务 B 要改表结构申请 MDL 写锁，读写互斥所以 B 阻塞排队；关键在于事务 C 再来做普通查询申请读锁，它也得排在 B 后面，因为 MySQL 为了保证写锁不被饿死，会让后来的读锁排在等待中的写锁之后。于是一个长查询把整张表的读写全卡住了。

**追问参考答**

排查主要看 performance_schema 里的 metadata_locks 表，看 lock_type、lock_status 和 owner_thread_id，找到状态是 GRANTED 的那个读锁会话，把它 KILL 掉，DDL 才能继续。生产上的预防手段是控制事务长度、DDL 走低峰期、给 DDL 设 lock_wait_timeout，别让它在队列里无限等。

### 16. 意向锁是什么？为什么需要意向锁？

> **知识点跳转：** [[MySQL锁机制]] · [[MySQL 意向锁详解]]

**参考答案**

意向锁是 InnoDB 的表级锁，在给记录加行锁之前，先在表级别打个标记：要加行共享锁就先加 IS，要加行排他锁就先加 IX。它的唯一目的是让表级锁的申请能快速判断冲突。比如事务 A 给某几行加了行级排他锁，事务 B 想 LOCK TABLES 加独占表锁，如果没有意向锁，B 得遍历整张表去检查有没有行被锁，百万行级别的表直接废掉；有了意向锁，B 只看表上有没有 IX 标记，有就阻塞，一步判断。冲突关系记住三句：意向锁之间永远不冲突，意向锁不和行锁直接冲突，意向锁只和手动加的表级 S 锁、X 锁冲突，其中 IX 和表级 S 冲突，IS 和表级 S 兼容，X 表锁则和所有意向锁冲突。

**追问参考答**

意向锁和行锁不冲突，因为一个是表级一个是行级，粒度不同没法直接比；意向锁之间也不冲突，IS 和 IS、IS 和 IX、IX 和 IX 都能共存。没有意向锁的后果就是加表锁必须遍历所有行锁，O(n) 的代价在线上根本不可接受。完整的冲突矩阵、插入意向锁为什么能防活锁，见 [[MySQL 意向锁详解]]。

### 17. 行级锁有哪几种？Record Lock、Gap Lock、Next-key Lock 的区别？

> **知识点跳转：** [[MySQL锁机制]]

**参考答案**

行级锁的核心是三种。Record Lock 是记录锁，锁住单条索引记录本身。Gap Lock 是间隙锁，锁的是两条记录之间的开区间，不包含记录本身，作用是阻止别人往这个间隙里插入。Next-key Lock 是临键锁，等于记录锁加间隙锁，锁的是左开右闭区间，既锁记录也锁它前面的间隙。InnoDB 加行锁的基本单位就是 Next-key Lock，能退化的时候才退成前两种。插入意向锁容易被误当成第四种，它其实不是独立的锁类型，而是插入操作在等待间隙时产生的一种标记，声明"我想往这个间隙插"，见前一题的详解页。

**追问参考答**

Next-key Lock 是左开右闭，比如索引值是 3 和 5，那么 (3,5] 这个区间被锁住，包含 5 但不包含 3。Gap Lock 是左开右开，(3,5) 两个端点都不锁。间隙锁彼此之间是兼容的，两个事务可以同时持有同一个间隙的间隙锁，这也是后面死锁题的伏笔，因为真正的互斥发生在间隙锁和插入意向锁之间。

### 18. Next-key Lock 什么时候会退化为记录锁或间隙锁？

> **知识点跳转：** [[MySQL锁机制]]

**参考答案**

退化原则一句话：当记录锁或者间隙锁本身就足够避免幻读时，Next-key Lock 就退化，不需要锁更大的范围。最典型的是唯一索引的等值查询，分两种情况。记录存在的时候退化为记录锁，因为唯一约束本身已经保证不会插进重复值，间隙锁是多余的。记录不存在的时候退化为间隙锁，锁住第一条大于该值的记录前面的那个间隙，比如表里只有 id 等于 1 和 id 等于 5，你要查 id 等于 2，就退化成 (1,5) 这个间隙锁，阻止别人插入 2、3、4。

**追问参考答**

这里有个容易说错的细节：记录不存在时锁的不是"前后两端点"，而是"第一条大于该记录的记录之前的那段间隙"，方向是单边的。另外退化还出现在非唯一索引的边界值上，扫描到的最后一条记录如果不是等值命中，也可能退成间隙锁，具体要看加锁规则那几节。

### 19. 间隙锁为什么无法完全解决幻读？什么情况下会失效？

> **知识点跳转：** [[为什么MVCC无法完全避免幻读现象]] · [[间隙锁防幻读的边缘场景]]

**参考答案**

根子在于 RR 下有两套时间基准：快照读走 MVCC，看的是 Read View 冻结的版本；当前读走 Next-key Lock，看的是最新已提交数据。两者一旦在同一个事务里混用，就会出现缝隙。典型时序是：事务 A 先做普通查询，快照读看到符合条件的 3 条记录；事务 B 插入一条并提交；事务 A 再用 SELECT FOR UPDATE 做当前读，绕过 Read View 直接读最新数据，看到 4 条，幻读就发生了。更关键的局限是，间隙锁是当前读语句执行的那一刻才按需加的，不是事务一开始就铺满，它只能挡住加锁之后的插入，挡不住加锁之前已经提交的那些。

**追问参考答**

要彻底杜绝，办法是让整个临界区都用当前读，事务一开头就用 SELECT FOR UPDATE 把范围锁住，让间隙锁贯穿始终。但代价是并发度大幅下降，所以生产上更常见的是接受 RR 下这个极小的缝隙，或者业务层面用唯一约束、用乐观锁版本号兜底，而不是真去全程当前读。间隙锁失效还有别的场景，比如查询没走索引、范围条件被优化器改写、LIMIT 截断扫描，这些在边缘场景那篇里有完整清单。
