# 缺页异常详解（软/硬之分与三大场景）

> **缺页不是一个错误，是虚拟内存的"按需供货"机制**：页不在内存也能"存在"，真去访问了才让内核来补。补的方式分两种——**要不要读磁盘**，这一条分界线决定了软硬、也决定了万倍的性能差。用户原稿为主，⚠ 标注处是本次补充。

---

## 一、先理解缺页中断

```
进程访问一个地址 → CPU 查页表 → 发现"没有映射" → 触发缺页中断
                                                        ↓
                                              操作系统来处理
```

⚠ **精确一点**：MMU 抛缺页的触发条件不止"没有映射"一种——**存在位=0（真没映射）** 和 **权限不符（有映射但不让你干这事）** 都会进缺页处理程序。软缺页的两大场景正好各占一种：匿名页/mmap 首次访问是"没映射"，COW 写触发是"有映射但只读"——**内核在 handler 里看一眼现场才定性**：是合法请求就当场办掉（软），需要读盘就排队（硬），真非法就 SIGSEGV。这就是 §五 说的"三岔口"。

缺页中断分两种，区别只有一个：**需不需要读磁盘**。

```
硬缺页（Major）：数据不在内存，必须去磁盘读  ← 慢（毫秒级，几十万~百万周期）
软缺页（Minor）：不需要读磁盘，在内存里解决  ← 快（微秒级）
```

⚠ 量级记法：**硬缺页 ≈ 一次 SSD 随机读的代价（几十微秒~毫秒），软缺页 ≈ 几十次到百来次内存访问**。所以 `time -v` 里maj/min 差几个数量级是正常体感。

⚠ **怎么数缺页**：`/proc/<pid>/stat` 第 10/12 个字段就是 **minflt / majflt**（累计值），`ps -o min_flt,maj_flt -p <pid>` 直接可看；`perf stat` / `getrusage` 同源。JVM 进程启动阶段 minflt 大量集中出现（堆页逐页首触），是正常现象。

## 二、软缺页最纯粹的例子：mmap 共享

```
进程A 通过 mmap 读了一个文件，数据页已经在内存物理页帧 #42

进程B 也 mmap 同一个文件，第一次访问这个地址：
    ↓
触发缺页中断
    ↓
操作系统检查：数据在内存里吗？在！#42 就有
    ↓
只需要在进程B的页表里建一条映射：虚拟地址 → #42
    ↓
完成，全程没碰磁盘
```

这就是"页已经在内存里，只是没建好映射关系"的最直接含义。

⚠ 前提要说死：**"A 先读过"才软**。若文件页压根不在页缓存里，第一次 mmap 访问就是**硬缺页**（要读盘）；mmap 共享映射的软硬之分，本质是**页缓存命中率**的问题。另外这只对 MAP_SHARED 最干净；MAP_PRIVATE 首读共享页缓存也走软路径，但**一写就落进 COW**（§三）。

⚠ 顺带一句同源知识：两个进程 mmap 同一文件，**映射的是同一批页缓存物理页**——这正是 [[OS八股#六、IPC 进程间通信]] 里"共享内存最快"的实现底座。

## 三、fork 写时复制：也是软缺页，但稍复杂

### fork 之后

操作系统不立刻复制内存，而是让父子进程先共享：

```
父进程页表：  虚拟地址 0x1000 → 物理页帧 #42  [只读]
                                      ↑ 共享
子进程页表：  虚拟地址 0x1000 → 物理页帧 #42  [只读]
```

### 子进程写入时

```c
x = 200; // 子进程写 0x1000
```

```
CPU 查页表：有映射，但标记只读 → 触发缺页中断
    ↓
操作系统处理：
    需要读磁盘吗？不需要，数据就在 #42
    ↓
    在内存内部：把 #42 内容复制到新页帧 #99
    更新子进程页表：0x1000 → #99 [可读写]
    ↓
完成，全程没碰磁盘
```

### 最终

```
父进程： 0x1000 → #42（原数据不变）
子进程： 0x1000 → #99（新修改的数据）
```

这里虽然分配了新页帧，但数据来源是内存里的 #42，不是磁盘，所以仍然是软缺页。

⚠ **COW 是"权限型缺页"转正的样板**：CPU 视角这是一次合法的写撞上了只读页，先当保护错误进内核；内核发现"哦，这是 COW 页"，就地复制、改映射、返回重执行指令——**全程不惊动磁盘**。若内核查明不是合法场景（真往只读段写），同样的入口就改判 SIGSEGV——**同一条异常通道，三种命运**。

⚠ 代价分布要说准：Redis BGSAVE 场景里 **fork 那一刀只复制页表**（快，页表开销），**真正的贵是在写密集期间父子各自的 COW 软缺页连发**——内存最坏翻倍说的就是这段时间。

## 四、第三大软缺页来源：匿名页首触（⚠ 原稿未提，补上）

`malloc` 拿到一大块、或 `mmap(MAP_ANONYMOUS)` 之后**第一次读写**它：

```
glibc/内核早把 VMA 建好了（记账完成），但页表项还没建
    ↓
首次访问 → 存在位=0 → 缺页
    ↓
内核：这是匿名内存，没有文件可读 → 分配一个页框、 memset 清零、建映射
    ↓
完成，不读盘 → 软缺页
```

这是日常程序里**数量最大**的一类软缺页（进程一生对每页内存基本都触发一次）。两个工程推论：

- **`malloc` 便宜的原因**：大 arena 里只是指针挪动，页的"真身"推迟到首触才结账——**分配和占用分离**，和 [[进程内存指标与 glibc 分配详解]] 的 VIRT/RES 分界同源
- **JVM `-XX:+AlwaysPreTouch`**：启动时把堆页逐页预触一遍，把分散在请求路径上的软缺页**集中到启动期还债**——追求 RT 稳定性的服务常开，代价是启动变慢

## 五、判断总表

**软缺页的判断标准只有一个：有没有磁盘 IO。**

```
没有 → 软缺页
有   → 硬缺页
```

| 场景 | 需要磁盘IO | 类型 |
|------|:---:|------|
| mmap 共享页已在页缓存，只需建映射 | ❌ | 软缺页 |
| fork 后写时复制 | ❌ | 软缺页 |
| 匿名页首次触碰（malloc/mmap 后首访问） | ❌（清零即可） | 软缺页（⚠补） |
| 第一次访问文件 / 数据不在内存 | ✅ | 硬缺页 |
| swap 换入（页被换出去了） | ✅ | 硬缺页 |
| 地址非法 | —— | 不是缺页"补"的范畴，SIGSEGV |

> ⚠ **一个考试级边角**：swap 换入**永远是硬缺页**——即使当初换出前它是热页；"页曾经来过内存再回来"不改变"这次要读盘"的事实。软硬的分界看**这一次处理动作**，不看历史。

## 面试话术

> "缺页分软硬，分界线只有一条：**这次处理要不要读磁盘**。要读盘的是硬缺页——比如 mmap 的页还不在页缓存、或者 swap 换出又用回来了，毫秒级；不需要读盘的都在内存里就地解决，是软缺页。软缺页三大来源：mmap 同一个文件、页缓存里已经有的，只需在我页表里建条映射；fork 后的写时复制——写撞上只读共享页，内核现场复制个新页框、改写映射，数据源是内存不是磁盘；还有一个数量最大的，匿名页首次触碰，malloc 拿到的内存第一次用，内核才给分配页框并清零，所以 malloc 便宜、贵的是首触。另外入口其实有个三岔口：存在位为 0 和权限不符都走同一条缺页异常，内核查明是合法场景就软硬缺一办掉，查明确实非法就是段错误。排查时用 minflt/majflt 就能看到区别——JVM 开 AlwaysPreTouch 就是为了把堆页那批软缺页集中到启动期还掉，别让它散在每个请求里。"
