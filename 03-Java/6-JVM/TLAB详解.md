# TLAB — Thread-Local Allocation Buffer（线程本地分配缓冲区）

## 一句话

TLAB 是 Eden 区中**每个线程独享的一小块空间**。对象创建时，**先**尝试在自己的 TLAB 中分配，TLAB 不够了才去竞争 Eden 的公共分配指针。

> 目的：**避免多线程在堆上分配对象时的锁竞争**，提升分配性能。

---

## 为什么需要 TLAB？

### 没有 TLAB 时的问题

Eden 是一个**所有线程共享**的区域。当多个线程同时 `new` 对象时，它们都要修改同一个指针——Eden 的**分配指针（Bump The Pointer）**：

```
Eden 区
┌──────────────────────────────────────────────┐
│ 已经分配的对象                      ↑         │
│                                    分配指针    │
│                                    指向这里    │
└──────────────────────────────────────────────┘
      线程 A 说："我要分配！"        ← 需要加锁保证线程安全
      线程 B 说："我也要分配！"        ← CAS 或锁，竞争激烈
```

如果是 `new` 一个非常小的对象（几字节），**分配锁的开销可能比对象本身还大**。

### TLAB 的解决方案

```
Eden 区（堆）
┌─────────────────────────────────────────────────┐
│  ┌─ TLAB A ─┐ ┌─ TLAB B ─┐ ┌─ TLAB C ─┐        │
│  │ obj1 obj2 │ │ obj3 obj4 │ │ obj5     │ ...    │
│  │ obj7      │ │           │ │          │        │
│  └───────────┘ └───────────┘ └───────────┘        │
│                                     ↑             │
│                                  全局分配指针       │
│                                  （几乎不动了）      │
└─────────────────────────────────────────────────┘
```

每个线程在 Eden 内**划一块私有的小空间**（TLAB），分配对象时在自己的 TLAB 里改自己的指针，**完全不需要锁**。TLAB 用完了才需要新的 TLAB 分配（这时才需要竞争全局指针）。

---

## 对象分配完整链路

```
new 一个对象
    ↓
① 检查 TLAB 是否有足够空间？
    ├─ 是 → 在 TLAB 中分配（无锁，极快）
    └─ 否 → ② 是否需要新 TLAB？
              ├─ 是 → 从 Eden 分配新 TLAB（需要 CAS 竞争）
              │        然后在新 TLAB 中分配对象
              └─ 否 → ③ 直接在 Eden 中分配（绕过 TLAB，需要锁）
                        ↓
                       ④ 如果 Eden 也不够 → Minor GC
```

> 第②步的"是否需要新 TLAB"判断依据：如果当前对象太大，直接分配新 TLAB 也装不下，不如直接在 Eden 分配，避免浪费 TLAB 空间。

## 相关参数

| 参数 | 说明 |
|------|------|
| `-XX:+UseTLAB` | 启用 TLAB（JDK 8 默认开启） |
| `-XX:-UseTLAB` | 禁用 TLAB |
| `-XX:TLABSize` | 手动设置 TLAB 大小（默认由 JVM 动态调整） |
| `-XX:+ResizeTLAB` | 是否动态调整 TLAB 大小（默认开启） |
| `-XX:TLABRefillWasteFraction` | TLAB 空间浪费比例，默认 64，即 1/64 的可浪费空间 |

---

## JVM 调优中的 TLAB

### TLAB 大小如何确定？

JVM 会根据线程数量、分配速率、Eden 大小**动态调整** TLAB 大小：

```
理想 TLAB 大小 ≈ Eden 大小 / 线程数
```

但不会无限小，有下限（默认 1KB）。

### TLAB 浪费问题

TLAB 是"预分配"的，线程实际可能只用了一部分。比如：
```
线程 A 的 TLAB：         ┌───────┬───────┐
实际用了 60%：           │ 已使用 │ 浪费  │
                         └───────┴───────┘
这些浪费的空间在 Minor GC 之前是无法被其他线程使用的。
```

但这仍然是**划算的**——TLAB 带来的分配吞吐量提升远大于浪费的空间。
`TLABRefillWasteFraction` 参数控制允许的浪费比例，超过此比例时不再分配新 TLAB，而是直接走 Eden 分配。

### 大对象会直接在 TLAB 分配吗？

不会。大对象（超过 TLAB 剩余空间且超过直接分配阈值）会**绕过 TLAB**，直接在 Eden 分配（甚至直接在老年代分配）。这与 `` 的 Humongous Object 是不同的判定逻辑。

## 面试话术

> **问：TLAB 是什么？为什么要用它？**
>
> 答：TLAB（Thread-Local Allocation Buffer）是 JVM 在 Eden 区为每个线程划分的一块私有缓冲区。对象创建时优先在自己的 TLAB 中分配，不需要加锁，避免了多线程竞争 Eden 分配指针的开销。
>
> 没有 TLAB 的情况下，每次 `new` 对象都要通过 CAS 或锁来竞争 Eden 区的分配指针，即使分配一个很小的对象也要付出同步代价。TLAB 让大部分对象分配变成无锁操作，显著提升分配吞吐量。TLAB 空间用完后，线程才需要竞争新的 TLAB 空间。

> **问：TLAB 会不会浪费空间？**
>
> 答：会。TLAB 是预分配的，线程可能只用了一部分，剩下的空间就浪费了。但 JVM 会动态调整 TLAB 大小，并通过 `TLABRefillWasteFraction` 参数控制允许的浪费比例。整体上 TLAB 带来的分配性能提升远大于浪费的空间成本。
