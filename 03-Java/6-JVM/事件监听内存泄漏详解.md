# 事件监听内存泄漏详解

> 事件监听（Event Listener）是 Java 中常用的观察者模式实现。当短生命周期对象注册为监听器后，若未及时取消注册，长生命周期的事件源会持续持有该对象引用，导致 GC 无法回收，造成内存泄漏。

---

## 一、什么是事件监听？

**专业定义：** 事件监听是观察者模式的一种实现。一个对象（**事件源 / EventSource**）维护一个监听器列表，当特定事件发生时，遍历列表回调所有已注册的监听器。监听器通过 `register` 方法注册，通过 `unregister` 方法取消注册。

**通俗理解：** 想象一个公众号（事件源），你（监听器）关注了它。只要你不取关，它每次发文章都会推送给你。如果你的号已经注销了（对象被销毁），但公众号那边没清理你的关注关系（未取消注册），它还是会尝试往你这里推送——这就占着资源。

---

## 二、内存泄漏的根因：生命周期不匹配

事件监听本身不会泄漏，泄漏发生在**监听器对象的生命周期 < 事件源的生命周期**，且注册后未取消注册时。

```
┌─────────────────────────────────────────────┐
│ 事件源（长生命周期，如单例 / Spring Bean）       │
│  └── Listeners: [A, B, C]                   │
│       ↑                                     │
│       │ 引用                                 │
│       │                                     │
│  ┌────┴────┐                                │
│  │ A (短生命周期)  ← 请求结束后本应被 GC 回收    │
│  │ 但事件源仍持有引用 → GC roots 可达 → 无法回收  │
│  └─────────┘                                │
└─────────────────────────────────────────────┘

每次请求泄漏一个 A 对象 → 堆内存逐渐耗尽 → OOM
```

**关键点：** 泄漏的本质不是"注册了监听器"，而是**事件源（作为 GC roots 的一部分）持有监听器的强引用**，导致监听器即使不再使用也无法被回收。

> [!info] 明确泄漏链路：不只是"监听器"本身被钉住
> 最常见的描述只停在"监听器被事件源钉住"，其实完整链路是：
>
> **长生命周期事件源 →（强引用）监听器 →（闭包 / 匿名内部类捕获）短生命周期对象**
>
> 监听器（尤其是 Lambda、匿名内部类）往往**捕获了外部对象**（比如当前请求的 `order`、`request`、大数组）。即使监听器"看起来"很小，只要它被事件源钉住，**它捕获的那些本应短命的对象也一起被钉住**——泄漏的"体积"是整条捕获链，不只是监听器本身。
>
> 所以关键**不是"监听器短命"**，而是**"注册后没有注销"**：监听器生命周期 > 事件源生命周期时，注册就等于给事件源装了一根不会断的强引用；而生命周期是否匹配，是调用方自己保证的，框架不会替你清理。

## 三、Java 后端中的典型场景

### 场景 1：单例持有请求级对象（最常见）

```java
// 长生命周期：应用级别的单例
@Component
public class EventManager {
    // 静态集合，生命周期 = 应用生命周期
    private static final List<DataChangeListener> listeners = new ArrayList<>();

    public static void register(DataChangeListener l) {
        listeners.add(l);  // 强引用，不会自动清除
    }

    public static void unregister(DataChangeListener l) {
        listeners.remove(l);
    }
}

// 短生命周期：每次请求创建一个
@Service
public class OrderService {
    public void processOrder() {
        OrderEventListener listener = new OrderEventListener(order);
        EventManager.register(listener);  // ✅ 注册了
        // ... 处理订单 ...
        // ❌ 忘记调用 EventManager.unregister(listener)
        // 请求结束 → listener 本应被回收 → 但 EventManager 静态列表持有强引用 → 泄漏
    }
}
```

### 场景 2：Spring Bean 作用域不匹配

```java
// Request 作用域的 Bean 注册到 Singleton Bean 上
@RequestScope
@Component
public class RequestContext {
    @Autowired
    public void init(EventPublisher publisher) {
        // this 是 Request 级别，publisher 是 Singleton 级别
        publisher.addListener(this);  // 注册了
        // 请求结束后，publisher 仍持有 this 的引用 → 泄漏
    }
}
```

### 场景 3：JDK 原生 Observer/Observable（已废弃但仍有人用）

```java
// Observable 是一个类（不是接口），维护 Vector<Observer> 观察者列表
public class DataModel extends Observable {
    public void updateData() {
        setChanged();
        notifyObservers(data);  // 通知所有观察者
    }
}
// 调用方 addObserver(this) 后未 deleteObserver → 泄漏
```

## 四、三种修复策略

| 策略 | 原理 | 适用场景 |
|------|------|---------|
| **手动取消注册** | `unregister` 后移除强引用，GC 可回收 | 所有场景，最直接 |
| **弱引用持有** | `WeakReference<Listener>` 包装，GC 不受强引用约束 | 无法控制注册/注销时机的场景 |
| ** WeakHashMap** | key 是弱引用，listener 被 GC 后条目自动清除 | 批量管理监听器 |

### 策略 1：手动取消注册（推荐）

```java
// 在 finally 块中确保取消注册
public void processOrder() {
    OrderEventListener listener = new OrderEventListener(order);
    EventManager.register(listener);
    try {
        // 业务逻辑
    } finally {
        EventManager.unregister(listener);  // 保证一定执行
    }
}
```

### 策略 2：弱引用

```java
public class EventManager {
    // 用 WeakReference 包装，GC 可回收 listener 本体
    private static final List<WeakReference<DataChangeListener>> listeners =
            new ArrayList<>();

    public static void register(DataChangeListener l) {
        listeners.add(new WeakReference<>(l));
    }
}
// 无需手动 unregister，GC 回收 listener 后，WeakReference.get() 返回 null，条目自动失效
```

> [!warning] 弱引用不会误杀长生命周期监听器
> 弱引用只在对象**没有其他任何强引用**时才允许 GC 回收。如果长生命周期监听器（如 Spring 单例 Bean）同时被容器强引用，WeakReference 列表中的引用不会导致它被回收。**弱引用区分"该不该回收"的方式是：看这个对象还有没有别的强引用，跟监听器的意图无关。**
>
> 但如果监听器**只**被 WeakReference 持有、没有其他强引用，那不管它是长生命周期还是短生命周期，都会被 GC——这时需要手动在别处保持强引用。

### 策略 3：WeakHashMap

```java
public class EventManager {
    // key 是 listener（弱引用），listener 被 GC 后条目自动移除
    private static final WeakHashMap<DataChangeListener, Boolean> listeners =
            new WeakHashMap<>();
}
```

> [!warning] WeakHashMap 的坑
> WeakHashMap 的 value 必须是强引用对象（如 Boolean.TRUE），不能用 `null` 作为 value，否则 key 也会被立即回收。

## 五、面试话术

> 事件监听导致内存泄漏，根因是**生命周期不匹配**：短生命周期的对象（比如请求级别的对象）注册到了长生命周期的事件源（比如单例）上，事件源以强引用持有监听器列表，请求结束后监听器对象本应被 GC 回收，但因为事件源的强引用还在，GC roots 可达，所以无法回收。每次请求都泄漏一份，堆内存逐渐耗尽，最终 OOM。
>
> 解决思路有三种：最直接的是**手动取消注册**，在 `finally` 块里确保 `unregister`；如果无法控制注册时机，可以用 **`WeakReference`** 包装监听器，让 GC 可以自动回收；也可以用 **`WeakHashMap`** 代替普通 `List` 来管理监听器。
