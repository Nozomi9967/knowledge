# 云商城压测方案（成果数字怎么跑出来）

> 目标：把 [[云商城（nozomi-mall）一页纸]] 成果栏里的 4 个 ⚠️ 待填 换成**你自己机器上真跑出来的数字**。
> 面试时数字被追问的三连是固定的：**「什么环境？」「多少并发？」「P99 还是平均？」**。这份方案的每一步都是为了让你这三问都能答上。

---

## 零、先把「环境」写死（这一步最重要）

单机压测不丢人，**谎报环境才丢人**。开压之前先把下面这张表填掉，之后所有数字都必须带着这张表一起说。

| 项 | 你的值 |
|------|------|
| CPU / 内存 | ⚠️ 填（`wmic cpu get name` / 任务管理器） |
| 部署方式 | 压测机与被压服务**同机**（本地 IDEA 启动） |
| MySQL / Redis / ES | 均为单机，跑在 VMware 虚拟机 `192.168.172.100` |
| JVM 参数 | ⚠️ 填（默认还是指定了 -Xmx？） |
| 数据量 | sku ⚠️ 条 / seckill_goods 12,605 条 / ES 索引 ⚠️ 条 |

**面试话术模板**：
> 「我是在本地单机压的，压测机和服务同机、中间件在同一台虚拟机上，所以绝对值不代表生产能力。我关注的是**同一环境下优化前后的相对提升**，这个比值是可信的。」

这句话一说，面试官基本不会再纠数字大小 —— 因为你已经先一步把边界划清了，这反而是加分项。

## 一、工具

| 场景 | 工具 | 理由 |
|------|------|------|
| 单接口纯压 | `hey` 或 `wrk` | 一行命令出 P50/P95/P99，装完就能用 |
| 多步骤场景（登录拿 token → 下单） | JMeter **非 GUI 模式** | 需要参数化和串联；GUI 模式自己就是瓶颈，必须 `-n` |

```bash
# hey（Windows 直接下 exe，最省事）
hey -z 60s -c 100 -H "Authorization: Bearer <token>" "http://localhost:8081/sku/aditems/type?id=1"

# JMeter 命令行（-n 非 GUI，-l 结果，-e -o 生成 HTML 报告）
jmeter -n -t seckill.jmx -l result.jtl -e -o report/
```

接口的准确路径别猜，项目里有 SpringDoc，启动服务后开 `http://localhost:<端口>/swagger-ui.html` 照着抄。

## 二、四组实验

### 实验 1｜Redis 注解缓存的真实收益（最容易出漂亮数字）

项目里 `SkuServiceImpl` 已经有 `@Cacheable(cacheNames="ad_items_skus", key="#id")`，TTL 12 小时。**控制变量就一个**：把 `@Cacheable` 注释掉重启（走 DB），对比不注释（走 Redis）。

| 步骤 | 操作 |
|:--:|------|
| 1 | 起 goods-service，`FLUSHDB` 清空 Redis |
| 2 | **组 A（无缓存）**：注释掉 `@Cacheable` 重启，`hey -z 60s -c 50` 压 `/sku/aditems/type?id=1` |
| 3 | **组 B（有缓存）**：恢复注解重启，先手动请求 1 次预热把缓存灌进去，再同样压 60s |
| 4 | 并发梯度各跑一遍：`-c 10` / `-c 50` / `-c 100` / `-c 200` |

**记录**：QPS、P99、错误率。**别记平均值** —— 面试官问 P99 你答平均，等于承认没压过。

**顺带能观察到的现象**（讲出来很值钱）：组 A 在 `-c 200` 时 QPS 会**掉头下降**而不是持平，因为 DB 连接池打满后请求开始排队。能说出这个拐点，说明你真看着图跑过。

### 实验 2｜ES 搜索接口

直接压搜索接口，重点不是和谁对比，而是**摸清当前数据量下的 P99**，以及带筛选/聚合/高亮时的额外开销。

| 组 | 请求 |
|:--:|------|
| A | 只带关键词（`must(match name)`） |
| B | 关键词 + 分类/品牌 term 过滤（走 filter 上下文） |
| C | B + 规格属性聚合 + 高亮 |

A → B 理论上**不会明显变慢甚至更快**（filter 不打分、可被 filter cache 复用），B → C 会明显变慢（`attrmaps` 聚合的 size 开到了 10000）。跑出来如果符合预期，你就有了一条实测支撑的话术，见 [[ES must与filter详解]]。

### 实验 3｜秒杀链路（这组数字最值钱，也最需要正确性校验）

这一组要同时产出**两个**结论：吞吐提升 + 零超卖。

**对比两条路径**：

- **路径 A（同步）**：绕过网关，直接压 seckill-service 的同步下单
- **路径 B（异步）**：走网关 → INCR 去重准入 → RocketMQ → 监听器落单

**必须用不同用户压**，否则网关的 `OrderQueue:{username}:{id}` 去重会把你的压测请求全挡掉。JMeter 用 CSV Data Set Config 灌 1000 个用户名 + 对应 token。

**正确性校验（比吞吐数字更重要）**——压完立刻执行：

```sql
-- 1. 卖出总量 是否等于 库存减少量（不等就是超卖或少卖）
SELECT
  (SELECT IFNULL(SUM(num),0) FROM seckill_order WHERE goods_id = 1) AS sold,
  (SELECT store_count FROM seckill_goods WHERE id = 1)               AS remain;

-- 2. 有没有人下了两单（幂等是否失守）
SELECT username, goods_id, COUNT(*) c
FROM seckill_order GROUP BY username, goods_id HAVING c > 1;

-- 3. Redis 里的剩余库存 与 MySQL 是否一致
--    HGET HotSeckillGoods 1
```

第 2 条查询**大概率会查出结果** —— 因为 `seckill_order` 目前没有唯一索引（见 [[云商城已知硬伤与追问预案]] #3）。这不是坏事：**先压出重复单，加上唯一索引再压一遍，重复数归零** —— 这就是一个完整的、有前后对比的、你自己发现并修掉的问题。这种叙述在面试里的分量远超任何 QPS 数字。

### 实验 4｜Canal 同步延迟（不用压测工具，脚本量最小，性价比最高）

改一条 SKU，量「多久后 ES 能搜到 / 静态页文件被重写」。这个数字是你难点 2 的直接证据。

```bash
# 1. 记下开始时间，改库
mysql -h192.168.172.100 -uroot -p -e \
  "UPDATE shop_goods.sku SET name = CONCAT(name,'_t',UNIX_TIMESTAMP()) WHERE id = <某个id>;"

# 2. 轮询 ES 直到查到新值，记下耗时
while true; do
  curl -s "http://192.168.172.100:9200/shop-search/_doc/<某个id>" | grep -q "_t" && date +%s%3N && break
  sleep 0.05
done

# 3. 静态页：看文件 mtime 变化（路径见 PageServiceImpl 的 pagepath 配置）
```

重复 10 次取 P99，别只测一次。同时观察 **canal-service 的日志有没有报错** —— 注意 `CanalNativeClient.java:142` 有开发期硬编码过滤（只放行 id 末位为 1 且 price 小于 20 的数据），**测之前先把这段过滤去掉**，否则你会以为同步坏了。

## 四、数字填好后，简历这样写

把上面的实测值代进去（示例里的数字是**占位**，不要照抄）：

> · 商品详情接口引入 Redis 注解缓存，100 并发下 QPS 由 **A** 提升至 **B**（P99 从 **C** ms 降至 **D** ms）
> · 秒杀链路由同步下单重构为「网关去重准入 + RocketMQ 异步落单」，200 并发下吞吐由 **E** 提升至 **F**；压测中发现 `seckill_order` 缺唯一索引导致 **N** 条重复订单，补索引后归零
> · Canal 增量同步链路端到端延迟 P99 **G** ms（商品改价 → ES 可搜索）

**三条纪律**：

1. 只写**相对提升**（倍数 / 百分比），慎写绝对 QPS —— 绝对值一定会被问环境
2. 一定带 **P99**，不写平均
3. 「压测中发现问题 → 修复 → 再压验证」这个叙述结构，比任何单个数字都值钱。它证明的不是你的机器快，是**你会用数据驱动优化**
