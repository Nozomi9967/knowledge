### **`SETNX + EXPIRE` 两条命令非原子，中间宕机会导致锁永不过期；Redisson 用 `SET NX PX` 原子加锁 + 看门狗后台续期解决"业务未完但锁已过期"问题；RedLock 争议核心是 Martin Kleppmann 质疑其在时钟漂移和 GC 停顿下无法提供真正的安全性。**

下面按面试口述节奏展开。

---

**第一部分：先讲清楚 `SETNX + EXPIRE` 为什么会锁丢失**

经典的错误写法：

```
SETNX lock_key uuid       # 加锁
EXPIRE lock_key 30        # 设过期
# ... 业务逻辑 ...
DEL lock_key              # 释放锁
```

这里至少有**三个坑**：

**坑一：SETNX 和 EXPIRE 不是原子的**

如果 `SETNX` 成功后、`EXPIRE` 执行前**客户端崩溃或网络断开**，这个 key 就变成**永久锁**，后续所有客户端都拿不到，整个业务卡死。

解法很简单：用 Redis 2.6.12+ 的 **原子命令**：

```
SET lock_key uuid NX PX 30000
```

一条命令搞定加锁 + 过期，不再有中间态。

**坑二：释放锁不校验持有者，误删别人的锁**

场景：A 拿到锁，业务执行超过 30 秒，锁自动过期；B 拿到锁开始执行；A 业务完成后执行 `DEL lock_key`，**把 B 的锁删了**。

解法：加锁时 value 存一个**唯一标识（UUID / 线程ID）**，释放时用 **Lua 脚本**保证"判断 + 删除"原子性：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**坑三：业务执行时间超过锁 TTL**

即使前两个问题都解决了，只要业务耗时 > TTL，锁就会提前释放，多个客户端并发进入临界区。**这个坑无法用"设置更长的 TTL"根治**——设太长，客户端崩溃后其他人要等很久；设太短，正常业务容易超时。真正的解法就是**看门狗自动续期**。

---

**第二部分：Redisson 看门狗机制（Watch Dog）**

Redisson 是 Redis 官方推荐的 Java 客户端，它把上面这些坑都封装好了。核心亮点就是**看门狗**。

**触发条件**：调用 `lock.lock()` 时**不传 leaseTime**（或传 -1），才会启用看门狗。如果显式 `lock.lock(30, TimeUnit.SECONDS)`，看门狗不生效——因为你已经明确指定了持锁时间。

**默认 TTL**：`lockWatchdogTimeout = 30000ms`（30 秒），可通过配置修改。

**续期原理**：

1. 加锁成功后，Redisson 在客户端启动一个**定时任务 (Netty TimerTask)**；
2. 每隔 `lockWatchdogTimeout / 3`（默认 10 秒）执行一次续期；
3. 续期通过 Lua 脚本判断"锁还是我持有的吗"，是则 `PEXPIRE` 重置 TTL 回 30 秒；
4. 直到 `unlock()` 被调用，或客户端进程消失（定时任务停止，锁自然过期）。

Lua 续期脚本大致是：

```lua
if redis.call('hexists', KEYS[1], ARGV[2]) == 1 then
    redis.call('pexpire', KEYS[1], ARGV[1])
    return 1
end
return 0
```

**好处**：

- **业务执行多久锁就续多久**，永远不会中途过期；
- **客户端崩溃时**定时任务停止，锁到 30 秒自动释放，不会永久死锁；
- **可重入**：Redisson 用 Hash 结构存 `{threadId: 重入次数}`，同线程重入 +1，unlock -1，为 0 才真删。

**一句话总结看门狗价值**：**"业务活着，锁就活着；业务死了，锁最多 30 秒后自动死"**。这是 `SETNX + EXPIRE` 手写方案很难做到的。

**注意几个坑**：

1. 看门狗是**JVM 本地定时任务**，如果这个 JVM 发生**长时间 STW GC**（比如 Full GC 停 40 秒），定时任务无法执行，锁到期被别人拿走，业务恢复后还以为自己持有锁——这就是下面 RedLock 争议的核心场景；
2. 看门狗只对**未显式指定 leaseTime** 的 lock 生效，很多人一开始不知道，传了 leaseTime 后发现根本没续期；
3. Redisson 的连接池要够大，否则续期任务打不出去也会失败。

**第三部分：RedLock 及其争议**

**RedLock 的动机**：单点 Redis（或主从 Redis）做分布式锁不安全——主库宕机时，如果锁刚写入主库但未同步到从库，从库切成主后**锁就丢了**，两个客户端可能同时拿到锁。

**RedLock 算法** (Redis 作者 antirez 提出)：

1. 部署 **N 个独立的 Redis 节点**（推荐 5 个），彼此**没有主从关系**；
2. 客户端**顺序向 N 个节点请求加锁**，每个请求带一个较小的超时（比如 50ms）；
3. 如果在**多数节点 (N/2+1)** 上成功加锁，且**总耗时 < 锁 TTL**，则加锁成功；
4. 否则向所有节点发送释放请求，加锁失败；
5. 锁的实际有效时间 = 初始 TTL - 加锁总耗时 - 时钟漂移补偿。

**Martin Kleppmann 的经典质疑**（2016 年那场著名论战）：

Martin（《Designing Data-Intensive Applications》作者）写了一篇文章 *"How to do distributed locking"*，核心论点是 **RedLock 既不够快也不够安全**。他提出两类攻击场景：

**场景一：进程停顿（GC / 调度延迟）**

```
1. 客户端 A 从 5 个节点获得锁，TTL = 10s
2. A 开始业务，此时发生 15s 的 Full GC 停顿
3. TTL 过期，锁在所有 Redis 节点上被释放
4. 客户端 B 顺利拿到锁，开始写数据
5. A 的 GC 结束，以为自己还持有锁，继续写数据
6. → A 和 B 同时写，锁失效
```

Martin 指出：**任何基于 TTL 的锁都无法防御长时间停顿**，不只是 RedLock，Redisson 看门狗也有同样问题（GC 期间续期任务没执行）。真正安全的分布式锁必须依赖**Fencing Token**（单调递增的版本号），下游存储在写入前校验 token，拒绝旧 token 的写入。RedLock 无法提供这样的 token。

**场景二：时钟漂移**

RedLock 的正确性依赖各节点的**本地时钟不能剧烈跳变**。如果某个 Redis 节点的系统时间被 NTP 或运维手动**大幅前调**，其上的锁会**提前过期**，可能破坏"多数派持有"的假设，导致两个客户端同时认为自己拿到了锁。

Martin 结论：**RedLock 试图在异步网络模型下实现同步共识，理论上不可能安全。要么用 Zookeeper/etcd 这类基于共识协议且提供 fencing token 的服务，要么承认锁只是"性能优化"而非"正确性保证"**。

**antirez 的反驳**：

- GC 停顿在任何锁方案里都是问题，不是 RedLock 独有；
- 时钟漂移在实践中可控，可以通过监控、禁止跳变式 NTP 缓解；
- 对**效率型场景**（避免重复工作），RedLock 已经够用；对**正确性型场景**（避免数据损坏），本来就该用共识系统 + fencing token。

**这场争论没有胜负**，但达成了业界共识：

1. **锁的用途要分清**：
   - **效率锁**（避免重复计算、防止重复发消息）：Redis / Redisson 够用；
   - **正确性锁**（金融记账、库存扣减）：需要 fencing token 或幂等设计兜底，别指望锁本身；
2. **RedLock 在实践中较少使用**，大多数团队要么用单点 Redis + 看门狗（承认极端情况下可能失效），要么直接上 Zookeeper / etcd；
3. **fencing token 才是终极方案**：锁服务返回一个单调递增 ID，下游存储在写入前比较，只有大于等于当前 token 的写入才被接受。

---

**第四部分：生产实践建议**

**1. 锁只是第一道防线，不是唯一防线**

真正的资金、库存操作，**数据库唯一索引 + 乐观锁 (version) + 幂等 key** 才是最终保障。Redis 锁的作用是**削峰**，不是**兜底**。

**2. 选型建议**

| 场景 | 推荐方案 |
|---|---|
| 一般去重、防重复提交 | Redisson (`SET NX PX` + 看门狗) |
| 严格正确性、可容忍性能 | Zookeeper / etcd |
| 金融资损场景 | 锁 + fencing token + DB 幂等三重防护 |

**3. 参数建议**

- 看门狗 TTL 别设太长（默认 30s 通常够用），设太长会让客户端崩溃后释放变慢；
- 业务方法上加**熔断超时**，避免持锁线程无限执行导致锁一直续期；
- 监控**锁等待时间、加锁失败率、续期失败告警**，Redisson 的续期失败一定要有报警。

---

**面试收尾一句话：**

`SETNX + EXPIRE` 出问题本质是**非原子 + 无续期 + 无持有者校验**三个坑叠加，Redisson 用 **`SET NX PX` 原子加锁 + Lua 释放校验 + 看门狗续期**基本解决了工程侧的问题；但 RedLock 之争告诉我们：**任何基于 TTL 的分布式锁在 GC 停顿和时钟漂移下都不是绝对安全的**，要正确性就必须靠 fencing token 或共识系统兜底。生产上判断"这把锁到底要多安全"，比选哪个组件更重要——**锁只是优化，幂等才是根本**。
