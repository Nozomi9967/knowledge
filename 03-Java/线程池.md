## Java 线程池核心知识

### 一、为什么用线程池

频繁创建/销毁线程开销大，线程池通过**复用线程**解决：降低资源消耗、提高响应速度、便于统一管理。

------

### 二、ThreadPoolExecutor 七大核心参数

```java
new ThreadPoolExecutor(
    int corePoolSize,      // 核心线程数，常驻不销毁
    int maximumPoolSize,   // 最大线程数
    long keepAliveTime,    // 非核心线程空闲存活时间
    TimeUnit unit,         // 时间单位
    BlockingQueue workQueue,       // 任务队列
    ThreadFactory threadFactory,   // 线程工厂（命名、优先级）
    RejectedExecutionHandler handler // 拒绝策略
);
```

**任务提交流程：**

```
提交任务
  → 核心线程数未满？→ 创建核心线程执行
  → 队列未满？      → 入队等待
  → 最大线程数未满？→ 创建非核心线程执行
  → 执行拒绝策略
```

------

### 三、四种拒绝策略

| 策略                  | 行为                               |
| --------------------- | ---------------------------------- |
| `AbortPolicy`（默认） | 抛出 `RejectedExecutionException`  |
| `CallerRunsPolicy`    | 由调用者线程直接执行，起到降速作用 |
| `DiscardPolicy`       | 静默丢弃任务                       |
| `DiscardOldestPolicy` | 丢弃队列头部最老任务，重新提交     |

------

### 四、Executors 工厂方法（及其问题）

| 方法                        | 本质                                     | 风险                  |
| --------------------------- | ---------------------------------------- | --------------------- |
| `newFixedThreadPool(n)`     | 固定核心=最大线程，`LinkedBlockingQueue` | 队列无界，**OOM**     |
| `newCachedThreadPool()`     | 核心=0，最大=Integer.MAX_VALUE           | 线程数无上限，**OOM** |
| `newSingleThreadExecutor()` | 单线程，`LinkedBlockingQueue`            | 队列无界，**OOM**     |
| `newScheduledThreadPool(n)` | 支持定时/周期任务                        | 最大线程数无上限      |

> **阿里规范**：生产环境禁用 `Executors`，必须手动 `new ThreadPoolExecutor` 并明确参数。



> ## LinkedBlockingQueue 详解
>
> ### 一、本质
>
> 基于**单向链表**实现的**有界阻塞队列**（不指定容量时默认 `Integer.MAX_VALUE`，即近似无界）。
>
> ------
>
> ### 二、核心结构
>
> ```java
> public class LinkedBlockingQueue<E> extends AbstractQueue<E>
>         implements BlockingQueue<E> {
> 
>     // 容量上限
>     private final int capacity;
>     // 当前元素数（AtomicInteger，线程安全）
>     private final AtomicInteger count = new AtomicInteger();
> 
>     // 链表头尾节点
>     transient Node<E> head;  // head.item == null（哨兵节点）
>     private transient Node<E> last;
> 
>     // 两把锁！！！
>     private final ReentrantLock takeLock = new ReentrantLock();
>     private final Condition notEmpty = takeLock.newCondition();
> 
>     private final ReentrantLock putLock = new ReentrantLock();
>     private final Condition notFull = putLock.newCondition();
> }
> ```
>
> > **关键设计**：读写分离用**两把锁**，`put` 和 `take` 可以并发执行，吞吐量高于 `ArrayBlockingQueue`（只有一把锁）。
>
> ------
>
> ### 三、四类核心方法
>
> 队列满/空时，不同方法的**处理方式不同**，分四种：
>
> | 操作 | 抛异常     | 返回特殊值 | 阻塞等待 | 超时等待               |
> | ---- | ---------- | ---------- | -------- | ---------------------- |
> | 入队 | `add()`    | `offer()`  | `put()`  | `offer(e, time, unit)` |
> | 出队 | `remove()` | `poll()`   | `take()` | `poll(time, unit)`     |
>
> **最常用的两个：**
>
> ```java
> // 队列满时阻塞，直到有空间
> queue.put(element);
> 
> // 队列空时阻塞，直到有元素
> E e = queue.take();
> ```
>
> ------
>
> ### 四、put() 源码逻辑
>
> ```java
> public void put(E e) throws InterruptedException {
>     int c = -1;
>     Node<E> node = new Node<E>(e);
>     final ReentrantLock putLock = this.putLock;
>     final AtomicInteger count = this.count;
>     
>     putLock.lockInterruptibly();  // 获取 putLock
>     try {
>         while (count.get() == capacity) {
>             notFull.await();      // 队列满 → 阻塞在 notFull 条件上
>         }
>         enqueue(node);            // 入队
>         c = count.getAndIncrement();
>         if (c + 1 < capacity)
>             notFull.signal();     // 还有空位，唤醒其他 put 线程
>     } finally {
>         putLock.unlock();
>     }
>     if (c == 0)
>         signalNotEmpty();         // 之前队列为空，唤醒 take 线程
> }
> ```
>
> ------
>
> ### 五、与 ArrayBlockingQueue 对比
>
> | 对比项   | `LinkedBlockingQueue`    | `ArrayBlockingQueue`       |
> | -------- | ------------------------ | -------------------------- |
> | 底层结构 | 链表                     | 数组                       |
> | 锁数量   | **两把锁**（读写分离）   | **一把锁**                 |
> | 吞吐量   | 更高                     | 较低                       |
> | 内存     | 每个节点额外有 next 指针 | 预分配连续内存，无额外开销 |
> | 容量     | 默认近似无界（OOM 风险） | **必须指定**，强制有界     |
> | 公平性   | 不支持公平模式           | 支持公平/非公平            |
>
> ------
>
> ### 六、典型使用场景
>
> **生产者-消费者模型：**
>
> ```java
> BlockingQueue<Task> queue = new LinkedBlockingQueue<>(1000); // 务必指定容量
> 
> // 生产者线程
> new Thread(() -> {
>     while (true) {
>         queue.put(generateTask());   // 满了就阻塞
>     }
> }).start();
> 
> // 消费者线程
> new Thread(() -> {
>     while (true) {
>         Task t = queue.take();       // 空了就阻塞
>         process(t);
>     }
> }).start();
> ```
>
> ------
>
> ### 七、面试高频追问
>
> **Q：为什么用两把锁而不是一把？** `put` 操作链表尾部，`take` 操作链表头部，两者操作的节点**天然不冲突**，用两把锁可以真正并发，提升吞吐量。
>
> **Q：count 为什么用 AtomicInteger 而不是普通 int？** `put` 和 `take` 持有不同的锁，两者同时执行时都需要修改 count，AtomicInteger 保证跨锁的可见性和原子性。
>
> **Q：生产上用 LinkedBlockingQueue 要注意什么？** **必须指定容量**，默认 `Integer.MAX_VALUE` 近似无界，任务堆积会导致 OOM。

### 五、常用阻塞队列

| 队列                    | 特点                 | 适用场景            |
| ----------------------- | -------------------- | ------------------- |
| `LinkedBlockingQueue`   | 默认无界（慎用）     | FixedThreadPool     |
| `ArrayBlockingQueue`    | 有界，推荐生产使用   | 自定义线程池        |
| `SynchronousQueue`      | 不存储任务，直接交接 | CachedThreadPool    |
| `DelayedWorkQueue`      | 按延迟时间排序       | ScheduledThreadPool |
| `PriorityBlockingQueue` | 按优先级排序         | 有优先级差异的任务  |

### 六、线程池参数如何设置

```
CPU 密集型：corePoolSize = CPU核心数 + 1
IO  密集型：corePoolSize = CPU核心数 × 2（或更高，视阻塞系数而定）
```

更精确公式：`线程数 = CPU核心数 × (1 + 平均等待时间/平均计算时间)`

------

### 七、线程池状态机

```
RUNNING → SHUTDOWN（调用shutdown()，不接新任务，处理完队列）
RUNNING → STOP    （调用shutdownNow()，中断所有线程）
SHUTDOWN/STOP → TIDYING → TERMINATED
```

### 八、高频追问

**Q：execute() vs submit() 区别？**

- `execute()`：无返回值，异常直接抛出
- `submit()`：返回 `Future`，异常被封装，调用 `get()` 时才抛出

**Q：核心线程会销毁吗？** 默认不会；设置 `allowCoreThreadTimeOut(true)` 后，超过 keepAliveTime 也会销毁。

**Q：如何优雅关闭线程池？**

```java
executor.shutdown();                          // 停止接新任务
executor.awaitTermination(60, TimeUnit.SECONDS); // 等待任务完成
if (!executor.isTerminated()) {
    executor.shutdownNow();                   // 强制中断
}

### 九、为什么 IO 密集型任务线程数可以多些

#### 核心原因：线程大部分时间在"等待"

IO 密集型任务（网络请求、数据库查询、文件读写）的特点是：线程发起 IO 操作后，**会被阻塞挂起**，CPU 转去执行其他线程。

```
CPU密集型线程生命周期：
[计算][计算][计算][计算][计算]  → CPU始终繁忙

IO密集型线程生命周期：
[计算][等待IO...........][计算][等待IO...........][计算]
         ↑ 这段时间CPU空闲，可以跑别的线程
```

所以更多线程 = 更多任务可以"同时"在等待 IO，CPU 利用率更高。

#### ThreadPoolExecutor 的线程数公式

**CPU 密集型：**

```
线程数 = CPU核心数 + 1
```

+1 是为了防止某个线程偶发性暂停（缺页中断等）时，有备用线程顶上。

**IO 密集型：**

```
线程数 = CPU核心数 × (1 + 等待时间/计算时间)
```

比如一个任务 90% 时间在等 IO，10% 在计算：

```
线程数 = 8核 × (1 + 0.9/0.1) = 8 × 10 = 80
```

实践中常用的经验值：`CPU核心数 × 2` 或直接用 `CPU核心数 × 2 + 1`。

#### ThreadPoolExecutor 参数对应关系

```java
new ThreadPoolExecutor(
    corePoolSize,      // 常驻线程数
    maximumPoolSize,   // 最大线程数（IO密集型这里设大）
    keepAliveTime,     // 超出core的线程空闲多久销毁
    TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100),   // 任务队列
    new ThreadFactory(),
    new CallerRunsPolicy()            // 拒绝策略
);

// IO密集型示例（8核机器）
int cpuCores = Runtime.getRuntime().availableProcessors(); // 8
new ThreadPoolExecutor(
    cpuCores * 2,      // corePoolSize = 16
    cpuCores * 2,      // maximumPoolSize = 16（队列无界时max意义不大）
    60L,
    TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(200)
);
```

#### 面试一句话总结

> IO 密集型任务线程大部分时间阻塞在 IO 等待，CPU 是空闲的，增加线程数可以让 CPU 在等待期间切换去处理其他请求，提高吞吐量。上限取决于**内存**和**线程切换开销**，而非 CPU 核心数。

### 十、线程池是懒加载的，核心线程不会"提前备好"

很多人误以为 `new ThreadPoolExecutor(5, 10, ...)` 一执行就会有 5 个核心线程——其实**默认是懒加载**。

#### 懒加载过程（`corePoolSize=5`）

```
初始状态：线程池 [ 空 ]   ← 一个线程都没有
提交第 1 个任务：线程池 [ T1(running) ]
提交第 2 个任务：线程池 [ T1, T2 ]
...
提交第 5 个任务：核心线程数已满
提交第 6 个任务：核心线程已满 → 任务进等待队列（不创建新线程）
```

"核心线程"的"核心"体现在**一旦创建就不会因为空闲而销毁**（默认行为；除非设置 `allowCoreThreadTimeOut(true)`），而不是"提前创建好"。

#### 如果想预热（手动提前创建）

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(5, 10, 60L,
    TimeUnit.SECONDS, new LinkedBlockingQueue<>());

pool.prestartAllCoreThreads();  // 创建全部 5 个核心线程
// 或
pool.prestartCoreThread();      // 只创建 1 个
```

适用场景：对**冷启动 RT 敏感**的服务（如支付下单、抢购），希望第一个请求到来时不用等线程创建。

#### 完整提交流程（带懒加载 + 预热分支）

```
提交任务
   ↓
当前线程数 < corePoolSize？
   ↓ 是                        ↓ 否
创建新核心线程执行         任务进等待队列
                                ↓
                          队列满了？
                         ↓ 是        ↓ 否
               线程数 < maxPoolSize？  在队列等待
                ↓ 是      ↓ 否
             创建非核心   执行拒绝策略
             线程执行
```

> 线程池的"池"是**线程复用**（任务执行完线程不销毁，等下一个任务），不是**线程预热**。面试被问"线程池创建后就有线程吗？"不要踩坑。

```
