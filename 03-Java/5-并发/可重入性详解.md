# 可重入性（Reentrancy）详解

> [[Java并发编程面试题]] 中可重入题仅给出一句话答案（"避免递归调用 / 子方法调用时自己锁自己"），本页展开**因果链、典型触发场景、计数器方案、三阶段实现**。
>
> 反向引用：[[Java并发编程面试题]] · [[synchronized 关键字详解]] · [[ReentrantLock详解]] · [[AQS 详解]]

---

## 一句话回答

**可重入**：同一线程对同一把锁可以多次 `monitorenter` 而不会死锁。

**为什么需要**：避免"递归调用 / 子方法调用"时自己锁自己——**同一线程再次申请已被自己持有的锁时不被挂起**，否则递归/子方法调用会自己等自己，永远释放不了锁，直接死锁。

---

## 一、问题展开：为什么"不可重入"会死锁

假如锁**不可重入**，那"同一线程第二次拿同一把锁"时，JVM 会认为"锁被占用了"→ 当前线程被**挂起**等待。

**因果链**：

1. 线程 A 已经是锁的持有者（`_owner == 线程A`）
2. 线程 A 在临界区内**递归调用**或**调用另一个同步方法**，再次申请同一把锁
3. JVM 发现"锁被占用"，**把线程 A 自己挂起**（因为它也走不进 `_entryList`——`_entryList` 是给"其他线程"用的，但 A 已经是 owner，A 在重入会进入等待）
4. 线程 A 已经**阻塞在"第二次拿锁"那行代码**上 → **永远不会退出临界区** → 永远不会释放锁
5. 死锁形成，且**任何其他线程也拿不到这把锁**——它被一个永远不醒的"幽灵持有者"占着

**本质矛盾**：「申请锁的线程」和「释放锁的线程」是**同一个线程**，但这个线程被自己挂起了，导致"释放动作"永远不会发生。

## 二、典型触发场景

### 2.1 子方法调用（最常见）

```java
class OrderService {
    public synchronized void createOrder() {   // ① 第一次加锁：拿到 this
        // ... 业务代码（校验、扣库存等）
        sendNotification();                     // 调用另一个同步方法
    }

    public synchronized void sendNotification() {  // ② 第二次加锁：拿同一个 this
        // 发短信 / 推消息
    }
}
```

线程 A 调用 `createOrder()` 拿到 `this` 锁 → 进入 `sendNotification()` 再次申请 `this` 锁：

- ✅ **可重入**：计数器 1 → 2，方法正常返回，计数器 2 → 1 → 0，锁释放
- ❌ **不可重入**：线程 A 在 `sendNotification()` 入口处被自己挂起 → 永远阻塞

**为什么这是"最常见"**：业务方法之间天然有调用关系，拆分方法（单一职责）是好习惯，但拆分后**多个方法需要锁住同一对象的同一段状态**，就会触发重入。

### 2.2 递归调用

```java
class TreeProcessor {
    public synchronized void traverse(Node node) {  // 每次递归都加同一把锁
        if (node == null) return;
        processNode(node);
        for (Node child : node.children) {
            traverse(child);   // 递归
        }
    }
}
```

- ✅ **可重入**：从根节点一路递归到叶子，锁计数器累加到 N，回溯时 N→0 后才真正释放
- ❌ **不可重入**：第一次递归调用 `traverse(child)` 就死锁

**为什么"树遍历 + synchronized"看起来不合理**——因为 synchronized 会把整个树锁住，**不可重入机制下根本无法用 synchronized 实现树遍历**。可重入性让"递归 + 锁"成为可能。

### 2.3 多态 / 继承场景

```java
class Parent {
    public synchronized void doWork() {
        // 父类核心逻辑
    }
}

class Child extends Parent {
    @Override
    public synchronized void doWork() {   // 子类重写时也加了锁
        preProcess();                      // 子类前置处理
        super.doWork();                    // ① 调用父类 → 同一线程再次加 this 锁
    }
}
```

- ✅ **可重入**：进入 `Child.doWork` 时计数器 0→1 → 调用 `super.doWork()` 时 1→2 → 父类返回时 2→1 → 子类返回时 1→0
- ❌ **不可重入**：`super.doWork()` 时线程被自己挂起

**这个场景最容易踩坑**——开发者重写方法时加了锁，**很容易忘记父类方法也加了锁**，因为父类的 synchronized 在方法签名上**不可见**（不像 `@Override` 有编译器提醒）。

### 2.4 回调 / 框架内部调用

```java
class TaskProcessor {
    public synchronized void process(List<Task> tasks) {   // 第一次加锁
        for (Task t : tasks) {
            t.run();      // Task.run() 内部又调用了 this 的某个 synchronized 方法
        }
    }
}
```

回调 / 模板方法 / 观察者模式中，业务对象在持锁状态下被框架回调，回调逻辑里再次申请同一把锁——可重入性保证这条链路不爆炸。

## 三、解决方案：计数器

可重入的本质是**用计数器记录"同一线程加锁的次数"**——

| 阶段 | 动作 | 计数器变化 |
|------|------|-----------|
| **第一次加锁** | 线程拿到锁 | 0 → 1 |
| **同一线程再申请** | JVM 看到"持有者是自己"→ **不阻塞** | N → N+1 |
| **每次 `monitorexit`** | 计数器 -1 | N → N-1 |
| **计数器减到 0** | **真正释放锁**给其他线程 | 0 |

**关键点**：

- **"同一线程"的判断依据**：synchronized 看 ObjectMonitor 的 `_owner` 字段；ReentrantLock 看 AQS 的 `exclusiveOwnerThread` 字段
- **"不阻塞"而不是"立即成功"**：synchronized 在重量级阶段，"同一线程"不需要走 `_entryList` 排队；轻量级阶段走 LockRecord 链；偏向锁阶段连 CAS 都不需要（直接比对 ThreadID）
- **"真正释放"的定义**：只有计数器归 0 才**唤醒等待队列**的下一个线程；中途的 monitorexit 只减计数，不唤醒

---

## 四、不同锁阶段的可重入实现

| 锁阶段 | 重入计数存哪 | 机制 |
|--------|-------------|------|
| **偏向锁** | Mark Word 里存的是 ThreadID，**无需计数器** | 线程 ID 一致就放行，每次进入都重置偏向 |
| **轻量级锁** | 线程栈上 **LockRecord 链**（每次重入压入一个新 LockRecord） | 每次重入压一个 LockRecord，displaced mark word 为空表示是重入 |
| **重量级锁** | ObjectMonitor 的 **`_count` 字段** | 每次 `monitorenter` +1，`monitorexit` -1；减到 0 才真正释放 |

**面试话术**：synchronized 任何阶段都是可重入的，区别只在于"重入计数存在哪"——**轻量级靠 LockRecord 链，重量级靠 ObjectMonitor._count**，偏向锁最简单（不需要计数器，比 ThreadID 即可）。

---

## 五、synchronized vs ReentrantLock 的可重入实现对比

| 实现位置 | synchronized | ReentrantLock |
|----------|--------------|---------------|
| **持有线程** | ObjectMonitor._owner | AQS.exclusiveOwnerThread |
| **重入计数** | ObjectMonitor._count | AQS.state |
| **判断逻辑** | 进入时：CAS 抢锁；已是 owner → 计数器 +1 | tryAcquire：state=0 时 CAS；已是 owner → state++ |
| **释放逻辑** | 计数器 -1，归 0 才唤醒等待队列 | tryRelease：state -1，归 0 才 setExclusiveOwnerThread(null) |

**共同点**：本质都是"持有线程 + 计数器"二元组。

**不同点**：
- synchronized 是 JVM 内置（ObjectMonitor，C++ 实现），计数器**自动维护、自动释放**
- ReentrantLock 是 JDK 层（AQS + Sync），计数器**手动维护、手动释放**（必须 `try-finally`）

## 六、面试话术模板

> "可重入是指同一线程对同一把锁可以多次加锁而不会死锁。需要可重入的根本原因是**避免递归调用 / 子方法调用时自己锁自己**——假如不可重入，线程在第二次申请自己已持有的锁时会被挂起，但释放动作也在这个线程里，线程被挂起了就永远不会释放，形成死锁。最典型的三个场景：子方法调用、递归调用、多态继承中的 `super.method()`。Java 锁通过'持有线程 + 计数器'实现可重入：第一次加锁计数器 0→1，同一线程再申请计数器 +1，释放时 -1，减到 0 才真正释放并唤醒其他线程。synchronized 在偏向锁阶段不用计数器（直接比 ThreadID），轻量级阶段用 LockRecord 链，重量级阶段用 ObjectMonitor._count。"
