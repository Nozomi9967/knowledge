### **这三个机制解决的是三个不同问题，不能混着说：舱壁隔离限制「单个下游最多占用多少资源」，防止一个慢调用吃光所有线程；熔断在下游持续失败时「快速失败」，不再继续打过去；降级是熔断或超时后「给一个兜底返回」，保证主流程能走完。顺序是隔离 → 熔断 → 降级，一层比一层靠后。**

下面按面试口述节奏展开，先用 A→B→C 的链路把问题讲透。

---

**第一部分：先还原 C 超时怎么把 A 拖死**

链路是 A 调 B、B 调 C。C 偶发超时（比如 3 秒才返回），B 的线程池被这些慢调用占满，B 无法响应 A；A 等 B 超时（比如 2 秒），A 的 Tomcat 工作线程也被占满，A 对所有请求都无响应。

**关键点在于：线程是有限资源，慢调用会"传染"**。一台 4 核机器 Tomcat 默认 200 个工作线程，只要 200 个请求卡在等下游，整个服务就假死了——哪怕 CPU 使用率只有 5%，因为它全在等 IO。

所以三板斧要解决的是：**不让单个下游把所有线程占满（隔离）→ 下游明显挂了就别再打了（熔断）→ 打不通时给个兜底（降级）**。

---

**第二部分：舱壁隔离——把线程资源切成舱**

"舱壁"这个名字来自轮船：船体分成多个隔水舱，一个舱进水不会沉船。技术上是把资源池按下游切分，A 调 B 用 20 个线程、调 C 用 20 个线程，C 慢了最多占满自己那 20 个，不影响调 B。

两种实现方式，区别很重要：

**线程池隔离**（Hystrix 默认）：每个下游一个独立线程池，调用在独立线程里执行。好处是**支持超时中断**（能真的把线程掐掉），坏处是**线程切换开销大**，而且线程数一多内存压力大。适合耗时长、可能卡死的调用。

**信号量隔离**（Sentinel 默认）：不换线程，只用一个信号量计数限制并发数（比如最多 20 个并发）。好处是**没有线程切换开销**，坏处是**不支持主动超时中断**（只能等调用自己返回）。适合耗时短、调用量大的场景。

Sentinel 里配起来是这样：

```java
// 给下游 C 单独设一个资源名，限制并发 20
FlowRule rule = new FlowRule("callServiceC");
rule.setGrade(RuleConstant.FLOW_GRADE_THREAD);   // 线程数模式，等价于信号量隔离
rule.setCount(20);
FlowRuleManager.loadRules(Collections.singletonList(rule));
```

**这个数字怎么定**：按"下游能承受的 QPS × 平均 RT"估，或者按"总线程数的 10~20%"给每个下游分。宁可给小一点，让小部分请求快速失败，也别让一个下游吃光全部。

---

**第三部分：熔断——从"一直重试"到"直接不打"**

隔离解决了"占用上限"，但如果下游已经完全挂了，每次都等到超时再失败，那 20 个线程会一直处于"打过去—等超时—失败"的循环，吞吐极低且用户等很久。熔断就是在检测到高失败率时**直接短路**，不再发起调用。

标准的三态模型：

- **Closed（关闭）**：正常放行，同时统计失败率
- **Open（打开）**：失败率超过阈值（比如 10 秒内 50% 失败且请求数 ≥ 20），进入打开状态，**所有调用直接失败**，不再打向下游
- **Half-Open（半开）**：打开状态持续一段时间（比如 5 秒）后，放少量请求过去试探。成功率达到阈值就回到 Closed，否则退回 Open

```java
DegradeRule degrade = new DegradeRule("callServiceC")
    .setGrade(CircuitBreakerStrategy.ERROR_RATIO.getType())  // 按异常比例
    .setCount(0.5)              // 50% 失败率触发
    .setMinRequestAmount(20)    // 至少 20 个请求才统计，避免样本太小误判
    .setStatIntervalMs(10000)   // 统计窗口 10 秒
    .setTimeWindow(5);          // 熔断 5 秒后半开试探
```

**参数怎么讲**：`minRequestAmount` 很关键，没有它的话"1 个请求失败 1 个"就是 100% 失败率，一启动就熔断。`timeWindow` 别设太长（比如 60 秒），下游恢复了也得等一分钟才能用。

---

**第四部分：降级——给用户一个能接受的答案**

熔断只是让调用快速失败，**失败之后返回什么**是降级要解决的。降级分两种粒度：

**自动降级**：熔断/超时触发后走 fallback 方法。

```java
@SentinelResource(value = "callServiceC", fallback = "fallbackC")
public Result callC(Long id) { ... }

public Result fallbackC(Long id, Throwable t) {
    // 返回缓存快照、默认值、或"稍后重试"的提示
    return Result.of(cacheService.getSnapshot(id));
}
```

**手动降级**：大促前把非核心功能（推荐、评价、积分展示）的开关关掉，直接返回兜底数据，把资源让给下单主链路。这是**预案级别**的降级，比自动降级更可控。

降级的关键原则是**分级**：核心链路（下单、支付）不允许降级到不可用，只能降级到"简化版"；非核心链路（推荐、评论）可以直接关掉。所以要先有一张"业务分级表"，不然出事时不知道该关谁。

---

**第五部分：完整链路的串讲**

我会这么说：A→B→C 的超时会传染，因为线程是有限资源。第一层用舱壁隔离给每个下游分配独立的并发额度，Sentinel 默认信号量模式、Hystrix 默认线程池模式，选哪个看调用是否需要强制超时中断。第二层用熔断，失败率超阈值就短路，避免继续打已经挂掉的下游，半开状态用来探测恢复。第三层是降级，熔断后返回缓存或默认值，同时支持大促前手动关掉非核心功能。

**三层之外还要补两个**：一是超时时间必须逐层递减（A 调 B 的超时要大于 B 调 C 的超时加上 B 自己的处理时间），否则内层还没结果外层已经超时了；二是要有重试的克制——重试会放大流量，熔断状态下不该重试。
