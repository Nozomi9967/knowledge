# 网卡收包流程详解

> 网卡收包是**设备主动通知 CPU** 的场景，天然用中断。但中断处理有个硬约束：**处理期间 CPU 要屏蔽中断**，做久了就丢包、影响系统响应。
>
> 所以内核把收包劈成两半：**上半部（硬中断）只负责"报告有包了"，下半部（软中断）才真正走协议栈**。这份笔记讲清整条链路，以及三个绕不开的工程问题——**中断风暴、中断只打一个核、以及怎么排查收包瓶颈**。

---

## 一、为什么必须拆成两级

| 环节 | 约束 |
|------|------|
| **硬中断里** | CPU 在这个核上**屏蔽中断**——待得越久，丢包和延迟风险越大 |
| **协议栈处理** | 解析以太网头、查路由、TCP 状态机查找 socket……**很耗时**，绝不能放在硬中断里 |

**结论**：硬中断必须**极短**，所以它只做"通报"，把重活丢给下半部。

---

## 二、完整流程

### ① DMA 把帧写进 ring buffer（不占 CPU）

驱动初始化时就为每个 RX 队列预分配一块**环形缓冲区**（`rx_ring`），里面是一圈缓冲区描述符，各自指向一块数据缓冲区。

网卡收到帧后，由 **DMA 引擎**直接把帧数据写进 ring 的下一个空闲槽——**这一路完全不经过 CPU**。

> ⚠ 关键点：**收包的第一次"拷贝"是 DMA 做的，不消耗 CPU**。这也是零拷贝链路能成立的前提。

### ② 网卡发硬中断

DMA 写完，网卡拉高中断线，经中断控制器投递给**某一个 CPU**。

⚠ **"某一个"是后面所有麻烦的根源**——默认情况下所有包的中断都打给同一个核。

### ③ 硬中断处理（上半部）——只做最少的事

1. **确认中断**（ack）——不 ack 网卡不会再次中断
2. **触发软中断**：给 `NET_RX_SOFTIRQ` 打个待处理标记（`napi_schedule`）
3. **关掉这张网卡的硬中断** ← 这是 NAPI 的入口，见 §四
4. 立刻返回

**它不碰协议栈，一个包都不解析。**

### ④ 软中断处理（下半部）

**执行时机有两个**：

- **硬中断返回的那一刻**——最常见。`irq_exit()` 里发现有 pending 软中断，顺手就跑
- **交给 `ksoftirqd/<CPU>` 内核线程**——软中断太重、或需要被调度时

**干的事**：

1. **NAPI 轮询**，从 ring 里**批量取包**（不是一包一次中断）
2. 逐包走协议栈：
   - **L2** 解析以太网头
   - **L3** `ip_rcv` → 路由 / 分片重组
   - **L4** `tcp_v4_rcv` / `udp_rcv` → 找到对应的 socket
3. 数据挂到 **socket 的接收队列**，然后调用 `sk_data_ready()` **唤醒**阻塞在 `recv` / epoll 上的进程
4. **有预算限制**：`net.core.netdev_budget` 默认 **300 个包 / 2 jiffies**，跑超了就退出、剩下的交给 `ksoftirqd`

**为什么要有预算**：不加限制的话，软中断会一直占着 CPU 把**用户态饿死**（表现为系统 load 高、但业务就是不动）。

### ⑤ 用户态被唤醒

`read` / `recvfrom` 把数据从 socket 接收队列**拷进你的 buffer**——**这才是收包路径上第一次消耗 CPU 的拷贝**。

## 三、上下半部分工对照

| | **上半部（硬中断）** | **下半部（软中断）** |
|---|---|---|
| 上下文 | 中断上下文，**屏蔽中断** | 内核态，但**可被中断** |
| 时间要求 | **越短越好** | 可长，但**有预算** |
| 干什么 | ack + 触发下半部 + 关网卡中断 | 协议栈处理 + 交给 socket |
| 谁执行 | 中断向量 | 中断返回时 / `ksoftirqd/CPU` |

> **通俗理解**：上半部像**前台按一下铃**——"有快递了"，按完立刻走，绝不在前台拆箱；下半部像**后台分拣员**——拿到通知后慢慢把一堆箱子拆开、分类、送到对应工位。

## 四、NAPI：中断 + 轮询的混合

### 要解决的问题：中断风暴

**纯中断模式下**，包速率一高就出事：

```
每来一个包 → 一次硬中断 → CPU 全在处理中断 → 没空处理包
   ↓
ring 越堆越满 → 包被丢 → 对端重传 → 包更多 → 中断更多
   ↓
★ 活锁（livelock）：CPU 100% 忙，却一个包也处理不完 ★
```

**关键特征**：机器看着很忙，但吞吐反而崩了。这是"忙而不出活"的典型。

### NAPI 的解法

```
第一个包到达 → 硬中断 → ★ 关掉这张网卡的硬中断 ★
                            ↓
                  改成主动轮询，一次把 ring 里的包全取走
                            ↓
                     取干净了 → 重新开启硬中断
```

所以它是**混合模式**：

| 负载 | 模式 | 理由 |
|------|------|------|
| 低 | **中断** | 省 CPU（没包就别空转） |
| 高 | **轮询** | 防中断风暴 |

回到 §二 第 ③ 步那个"关硬中断"——**那就是 NAPI 的入口**。

## 五、RSS / RPS / RFS：解决"中断只打一个核"

默认一张网卡的硬中断**只投给一个 CPU**，结果那个核 `%si` 打满、其他核闲着。解法分两层：

| 机制 | 层次 | 做法 |
|------|:---:|------|
| **RSS**（Receive Side Scaling） | **硬件** | 网卡按四元组哈希把不同流分到**多个 RX 队列**，每队列独立中断 |
| **RPS**（Receive Packet Steering） | **软件** | 没有多队列硬件时，用软件模拟分流（写 `/sys/class/net/eth0/queues/rx-0/rps_cpus`） |
| **RFS**（Receive Flow Steering） | **软件** | 进一步让包在**应用所在的那个 CPU** 上处理，提高 CPU 缓存命中 |

再配合：

- **中断亲和性**（`/proc/irq/<n>/smp_affinity`）——手动把各队列中断绑到不同核
- **`irqbalance`** 守护进程——自动分配

**这才是"收包打满一个核"的正解**：不是去优化协议栈，而是**把中断摊开**。

> **通俗理解**：一个分拣口扛不住 → **RSS 是多开几个分拣口**（硬件扩），**RPS 是人工把包裹分给几个人**（软件补），**RFS 是干脆把包裹直接送到那个收货人所在的工位**（省一趟搬运）。

## 六、接收侧合并：GRO

**GRO（Generic Receive Offload）**：在软中断里把**同一流的多个小包合并成一个大包**，再送协议栈——**协议栈调用次数大幅减少**。

发包方向对应的是 **GSO / TSO**（交给网卡分段）。

这和 `writev` / `epoll` 是同一个思路：**把多次处理合并成一次**（见 [[模式切换与上下文切换详解]]）。

**另一个相关优化**：**中断合并（interrupt coalescing）**——`ethtool -C eth0`，让网卡"攒几个包再发一次中断"，用一点延迟换中断次数。极端低延迟场景反过来用 **`SO_BUSY_POLL`**（干脆不靠中断，应用自己轮询 ring）。

## 七、可观测指标与故障排查

| 指标 | 怎么看 | 含义 |
|------|--------|------|
| **`%si`** | `top` | **软中断占 CPU 比例** ← Q6 那句「`%si` 的由来」 |
| `ksoftirqd/CPU` | `top -H` | 软中断内核线程，它忙 = 软中断压力大 |
| `rx_dropped` | `ethtool -S eth0` | **ring buffer 满**，丢包 |
| `rx_missed_errors` | 同上 | 网卡没来得及把包 DMA 进来 |
| `netdev_budget` | `sysctl net.core.netdev_budget` | 一次软中断最多处理多少包（默认 300） |
| `netdev_max_backlog` | `sysctl` | 每 CPU backlog 队列上限 |

**两条典型故障链**：

| 现象 | 根因 | 处理 |
|------|------|------|
| **`%si` 高 + `ksoftirqd` 忙** | 收包量大，或中断挤在一个核 | 上**多队列 + RSS**，中断绑核（§五） |
| **`rx_dropped` 一直涨** | ring 太小，或软中断处理不过来 | `ethtool -G eth0 rx 4096` 扩大 ring；查上方 `%si` |

⚠ **别把 `%si` 和 `%sy` 搞混**：`%si` 是**软中断**（收发包、定时器等），`%sy` 是**系统调用 / 上下文切换**的开销（见 [[OS热门面试题]] Q23）。

## 八、和 epoll / 零拷贝的接点

这条链路正好把前面几个话题接上了：

```
DMA 写 ring（不占 CPU）
    ↓ 硬中断（上半部：只通报）
    ↓
软中断 → 走协议栈 → socket 就绪
    ↓
内核调用 ep_poll_callback() → 把 fd 挂进【就绪链表】   ← epoll 那条回调路径的上游
    ↓
epoll_wait 醒来 → 你 read 到数据
```

- **epoll 回路的起点就在这儿**——[[select 与 epoll 机制详解]] §5.3 那条 `ep_poll_callback` 路径，**上游正是"软中断里 socket 就绪"**
- **零拷贝**：DMA 写 ring 天然省掉了"设备 → 内核"的 CPU 拷贝；`sendfile` 省的是后面"内核内部 + 内核 → 用户"那几次（见 [[OS八股]] §7.3）
- **中断 / 异常 / 系统调用**的三分法见 [[OS八股]] §1.1 的「陷入内核」标注

## 面试话术

> "网卡收包要分两级，根子在**中断上下文不能久留**——硬中断期间 CPU 屏蔽中断，做久了既丢包又影响响应。所以内核把收包拆成上半部和下半部。
>
> 完整流程是这样：驱动预先在内存里给网卡准备一圈 ring buffer，网卡收到帧之后由 **DMA 直接写进去，这一步不占 CPU**；写完了网卡发一个硬中断；硬中断处理程序只做三件事——确认中断、给软中断打个标记、然后**把这张网卡的硬中断关掉**，立刻返回。**关中断这一步是 NAPI 的入口**——因为纯中断在高包速率下会出'中断风暴'，CPU 全在处理中断、没空处理包，ring 越堆越满，形成**活锁**，看着 100% 但吞吐崩了。所以 NAPI 改成混合模式：低负载用中断省 CPU，高负载自动切轮询批量取包。
>
> 真正干活的软中断分两个时机执行：硬中断返回时顺手跑，或者交给 `ksoftirqd` 内核线程。它从 ring 里批量取包、走完 L2/L3/L4 协议栈、把数据挂到 socket 接收队列，然后**唤醒阻塞的进程**。这里有预算限制，默认 300 个包，超了就退出，**防止软中断把用户态饿死**。
>
> 工程上最常见的问题是**中断只打一个核**——那个核 `%si` 打满、其他核闲着。解法是硬件层的 **RSS 多队列**、软件层的 **RPS/RFS**，再加中断亲和性绑核。排查就看 `%si`、`ksoftirqd` 忙不忙、还有 `ethtool -S` 的 `rx_dropped`。"
