### **G1（Garbage First）是 JDK 9 之后的默认 GC，核心是"Region 化堆布局 + 并发标记 + 可预测停顿模型"，用增量回收把 CMS 时代动辄几百 ms 的停顿压到几十 ms,是当前中等堆场景（4G~64G）的生产标杆**

  

---

  

### **一、G1 要解决什么问题**

  

在 G1 之前主流是 **CMS（Concurrent Mark Sweep）**,思路是"老年代并发标记 + 并发清除"降低停顿。但 CMS 有三个致命伤:

  

- **内存碎片**:标记-清除算法不整理内存,老年代碎片化后大对象分配失败,最终退化成 **Serial Old 单线程 Full GC**（切换到能整理内存的收集器：Serial Old）,几十秒起步。

- **Concurrent Mode Failure**:并发标记期间如果老年代满了,同样退化到 Full GC。

- **停顿仍然随堆增长**:堆到 8G 以上 CMS 就控制不住了。

  

G1 的设计目标:

  

- **可预测停顿**:用户给一个目标(比如 50ms),GC 尽量满足。

- **不产生碎片**:整体是"标记-复制"算法,回收即整理。

- **支持大堆**:几 G 到几十 G 都稳定。

- **兼顾吞吐**:相比 Parallel GC 损失控制在 10% 以内。

  

它的核心思路是**把堆切成小块(Region),每次只回收一部分收益最高的 Region**,这就是名字"Garbage First"的由来——优先回收垃圾最多的 Region。

  

---

  

### **二、Region 化堆布局**

  

G1 把堆划分成 **2048 个左右的 Region**(不严格,大致这个量级),每个 Region 大小是 2 的幂:1M/2M/4M/8M/16M/32M,默认根据堆大小自动算(32G 堆默认 8M)。

  

Region 有五种角色,**动态分配**,不像传统 GC 里 Young/Old 是固定的一大块内存:

  

- **Eden Region**:新对象分配在这里。

- **Survivor Region**:Young GC 后存活的对象晋升到这。

- **Old Region**:多次 GC 后仍存活的对象。

- **Humongous Region**:存放大对象(> Region 一半的对象),可能横跨多个连续 Region,**逻辑上归属 Old**。

- **Free Region**:空闲,待分配。

  

**为什么这么设计**:

  

- **灵活性**:Young / Old 比例根据 GC 反馈动态调整,不像传统分代要 `-Xmn` 锁死。

- **增量回收**:每次 GC 挑选一部分 Region 组成 **CSet(Collection Set)**回收,停顿可控。

- **无碎片**:回收时把存活对象拷贝到新 Region,旧 Region 整体释放,天然整理。

  

**Humongous 对象是重点**:一旦对象大小 > Region 的 50%,就直接分配到 Humongous Region,**跳过 Young 区、直接进 Old**。这样做的问题是:

  

- Humongous Region 只能存这一个大对象,剩余空间浪费。

- 大对象只能靠并发标记周期回收,回收慢。

- 频繁分配大对象会导致 Old 区快速涨满,触发 Full GC。

  

调优时如果监控到大量 Humongous 分配,首选**调大 `G1HeapRegionSize`** 让大对象降级成普通对象。

  

---

  

### **三、Remembered Set(RSet)与 Card Table**

  

G1 要做**部分回收**,就必须知道"要回收的 Region 里,哪些对象被其他 Region 引用了",否则会误回收。

  

**RSet 是每个 Region 一个的反向引用表**——记录"有哪些其他 Region 的对象引用了我"。这样回收某个 Region 时,只需要扫它自己的 RSet 就知道所有跨 Region 的引用来源,不用扫全堆。

  

维护 RSet 靠 **Card Table + 写屏障**:

  

- 堆被切成 512 字节的 **Card**,Card Table 是个 byte 数组记录每张 Card 是否"脏"。

- 业务代码执行 `obj.field = other` 时,JIT 插入的**写屏障**代码检查:如果 `other` 和 `obj` 在不同 Region 且 `other` 在 Old 区,就把对应 Card 标记为脏。

- 后台的 **Refinement 线程**异步把脏 Card 里的引用信息更新到目标 Region 的 RSet 里。

**RSet 只记录回收范围之外的引用**:同一 Region 内是"铁板一块"一起回收;Young→Young 因为 Young GC 全量扫,引用自然被发现;这两种都不需要 RSet。

| 场景 | 引用方 | 被引用方 | 需要 RSet | 原因 |
|------|--------|----------|:---:|------|
| 同一 Region | 同 Region | 同 Region | ❌ | 回收时整 Region 一起处理 |
| Young→Young | Young | Young | ❌ | Young GC 全量扫，自然发现 |
| Old→Young | Old | Young | ✅ | Old 不参与 Young GC，需 RSet 告知"Old 引用了 Young" |
| Young→Old | Young | Old | ✅ | Mixed GC 收 Old 时，需 RSet 告知"Young 引用了 Old" |
| Old→Old | Old A | Old B | ✅ | Mixed GC 收 Region B 时，需 RSet 告知"Region A 引用了它" |



**代价**:

  

- 写屏障有 CPU 开销(每次引用赋值多几条指令)。

- RSet 本身占内存,大堆下能占到堆的 5~20%(极端情况),这也是 G1 内存开销比 Parallel GC 大的原因。

- Refinement 线程也吃 CPU。

  

对比 ZGC:ZGC 完全没有 RSet(靠染色指针 + 读屏障),这是 ZGC 大堆下更省内存的原因;但 G1 的写屏障比 ZGC 的读屏障轻,业务代码"读多写少"时 G1 反而占优——**这也是 G1 吞吐比 ZGC 好的技术根源**。

### **四、GC 流程:Young GC / Mixed GC / Full GC**

  

**Young GC(STW)**

  

触发条件:Eden 满了。

  

流程:

  

1. 停止所有业务线程。

2. 扫 GC Roots + 所有 Young Region 的 RSet(找出被 Old 引用的 Young 对象)。

3. 把存活对象**拷贝**到 Survivor 或晋升到 Old(拷贝算法,无碎片)。

4. 清空原 Eden / Survivor Region。

5. 恢复业务线程。

  

Young GC 是纯 STW 的,但停顿由 CSet 大小决定,G1 会根据 `MaxGCPauseMillis` 动态调整 Young 区大小控制停顿。

  

**并发标记周期(Concurrent Marking Cycle)**

 %% 它不是一个 GC，而是 Mixed GC的前置工作 %%
  

触发条件:老年代占比达到 **IHOP**(默认 45%)。

  

分五个阶段:

  

1. **Initial Mark(STW)**:标记 GC Roots 直接可达的对象。**这一步搭 Young GC 的顺风车做**——反正 Young GC 已经 STW 了,顺便标一下 Root,零额外成本。

2. **Root Region Scan(并发)**:扫 Survivor Region,找出 Survivor 引用的 Old 对象作为标记起点。

3. **Concurrent Mark(并发)**:业务线程继续跑,GC 线程遍历对象图完成标记。用 **SATB(Snapshot At The Beginning)**算法保证并发标记的正确性——标记开始时给堆拍个"快照",标记期间新产生的引用变化通过写屏障记录在 SATB Buffer 里,最后处理。

4. **Remark(STW)**:处理 SATB Buffer 里的增量变化,完成最终标记。

5. **Cleanup(部分 STW)**:统计每个 Region 的存活率,把**完全没有存活对象的 Region 直接回收**(不用拷贝),并排序 Region 为后续 Mixed GC 做准备。

  

**并发标记周期本身不回收对象(除了 Cleanup 里完全空的 Region),它的产物是"哪些 Old Region 值得回收"的名单**。

  

**Mixed GC(STW)**

  

触发条件:并发标记周期完成后,老年代占比仍然高。

  

**这是 G1 回收老年代的主要方式**——注意名字叫"Mixed",意思是它同时回收 Young Region + 部分 Old Region,不是只回收 Old。

  

- 从并发标记选出的候选 Old Region 里挑存活率最低的加入 CSet。

- 拷贝存活对象,整体释放 Region。

- 一次并发标记周期后通常触发 **8 次左右**的 Mixed GC(`G1MixedGCCountTarget=8`),分批把老年代回收干净。

  

Mixed GC 的停顿由 CSet 里 Old Region 数量决定,可以通过 `G1OldCSetRegionThresholdPercent` 控制单次回收多少。

  

**Full GC(STW,灾难)**

  

触发条件:

  

- 并发标记还没跑完老年代就满了(**Concurrent Mode Failure**)。

- Humongous 分配时没有连续空间。

- Metaspace 满。

- 显式 `System.gc()`。

  

**JDK 10 之前 G1 的 Full GC 是单线程 Serial**,几十秒起步。JDK 10 之后改成**并行 Full GC**,快多了但仍然是 STW 大停顿,几百 ms 到几秒。

  

**生产环境目标:永远不出现 Full GC**。一旦监控到就必须查,通常是 IHOP 设太高、Humongous 太多、或者内存泄漏。

### **五、可预测停顿模型**

  

`MaxGCPauseMillis` 之所以能"预测",靠的是 G1 的**统计反馈机制**:

  

- G1 会记录每次 GC 每个 Region 的**回收耗时**(拷贝 N 个对象花多少 ms)。

- 下次 GC 时根据历史数据估算:"我要在 40ms 内回收完,大概能装下多少个 Region"。

- 挑选 CSet 时按"回收收益 / 耗时"排序,优先选存活率低(垃圾多)的 Region——**这就是 Garbage First 的字面含义**。

  

**关键理解**:

  

- **`MaxGCPauseMillis` 是软目标,不是硬保证**。设 10ms 不代表真能 10ms 达成,G1 只是尽力接近。

- 设得太小副作用严重:CSet = Young + Old Region 的总和,目标停顿越短,CSet 能装的 Region 越少 → Young 区被迫缩小 → Eden 很快满 → Young GC 更频繁 → 对象来不及在 Young 区"熬死"就被晋升到 Old → Old 区快速膨胀 → Mixed GC 收不过来 → **最终 Full GC**。

- 经验值 **50~200ms** 之间,先设 100 观察再往下压。

### **六、参数体系完整梳理**

  

**基础参数**

  

```

-XX:+UseG1GC

-Xms32g -Xmx32g # 堆固定,避免动态扩缩抖动

-XX:MaxGCPauseMillis=50 # 目标停顿

-XX:G1HeapRegionSize=16m # Region 大小,2 的幂

-XX:+AlwaysPreTouch # 启动预分配物理内存

```

  

**并发与并行线程**

  

```

-XX:ParallelGCThreads=8 # STW 阶段线程数,一般等于 CPU 核数(核数 > 8 用 8 + (N-8)*5/8)

-XX:ConcGCThreads=2 # 并发标记线程,一般是 ParallelGCThreads 的 1/4

```

  

`ParallelGCThreads` 影响 Young GC 和 Mixed GC 停顿——**核数越多单次 GC 越快,但超过物理核数后并行线程之间互相抢 CPU, diminishing returns 明显**(一般等于 CPU 核数即可)。容器环境要注意 JVM 是否正确识别到 cgroup 的 CPU 限额(JDK 8u191+ 才支持)。真正与业务线程抢 CPU 的是 `ConcGCThreads`（并发阶段运行的线程）。

  

**IHOP 与并发标记**

  

```

-XX:InitiatingHeapOccupancyPercent=45 # 老年代占比阈值,达到就启动并发标记

-XX:-G1UseAdaptiveIHOP # JDK 9+ 默认自适应,一般不用关

```

  

**IHOP 设置的核心逻辑**:并发标记周期需要时间跑完,期间业务线程还在往 Old 区塞东西。**如果 IHOP 太高,并发标记还没结束 Old 就满了 → Concurrent Mode Failure → Full GC**。

  

- 老年代增长快(短命对象多、晋升频繁)→ IHOP 调低(35~40)。

- 老年代增长慢(缓存类应用)→ IHOP 可以高(50~55)。

- **JDK 9+ 默认开启自适应 IHOP,会根据历史数据动态调**,除非监控到问题否则别手动改。

  

**Mixed GC 调优**

  

```

-XX:G1MixedGCLiveThresholdPercent=85 # Region 存活率 <85% 才纳入 Mixed GC

-XX:G1MixedGCCountTarget=8 # 一个周期后分几次 Mixed GC

-XX:G1OldCSetRegionThresholdPercent=10 # 单次 Mixed GC 最多回收 Old Region 的百分比

-XX:G1HeapWastePercent=5 # 堆浪费阈值,空闲（Free）Region 占比低于此值不再 Mixed GC

```

  

调优思路:

  

- **Mixed GC 单次停顿超标** → 调小 `G1OldCSetRegionThresholdPercent`(比如 5),每次少回收点。

- **Mixed GC 回收不干净、Old 涨得快** → 调大 `G1MixedGCLiveThresholdPercent`(比如 90),让更多 Region 有资格被回收;或增加 `G1MixedGCCountTarget` 分更多次回收。

  

**Mixed GC 参数精要**:
- `G1MixedGCLiveThresholdPercent`：Region 存活率门槛。G1 是"拷贝"算法——如果一个 Region 里 95% 的对象还活着,拷贝 95MB 只省 5MB,浪费 STW 时间,干脆不碰。只有垃圾足够多的 Region 才值得收,体现"Garbage First"的哲学。
- `G1MixedGCCountTarget`：一次并发标记周期后分几次 Mixed GC。默认 8 次,分批把老年代回收干净。
- `G1OldCSetRegionThresholdPercent`：单次 Mixed GC 最多放多少 Old Region 进 CSet。控制单次停顿上限。
- `G1HeapWastePercent`：堆里空闲 Region 占比低于此值就不再 Mixed GC,避免过度清理浪费停顿时间。

**Young 区大小(通常别手动设)**

  

```

-XX:G1NewSizePercent=5 # Young 最小占堆比,默认 5%

-XX:G1MaxNewSizePercent=60 # Young 最大占堆比,默认 60%

```

  

G1 会根据 `MaxGCPauseMillis` **自动调整 Young 大小**。**千万别用 `-Xmn` 锁死**——这会禁用自适应,让 G1 的可预测停顿模型失效,是最常见的错误调参。

  

**其他实用参数**

  

```

-XX:+ParallelRefProcEnabled # 并行处理 Reference,加速 Final/Weak/Soft 引用清理

-XX:+ExplicitGCInvokesConcurrent # 让 System.gc() 走并发标记而不是 Full GC

-XX:+UseStringDeduplication # 字符串去重,能省 5~10% 内存

-XX:G1ReservePercent=10 # 预留堆空间应对晋升失败,默认 10%

```

  

`G1ReservePercent` 是"保险丝"——晋升到 Old 时如果 Old 满了会触发 Full GC,预留一部分空间应对突发。默认 10% 一般够,晋升失败频繁可以调到 15~20。

### **七、监控与调优实战**

  

**GC 日志(JDK 9+ 统一日志)**

  

```

-Xlog:gc*,gc+heap=debug,gc+age=trace,gc+ergo=trace:file=/log/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=100M

```

  

`gc+ergo=trace` 会打出 G1 的**决策过程**——为什么选这些 Region、预测停顿多少、实际停顿多少,对深度调优非常有用。

  

**关键指标**

  

- **Pause Time P99 / P999**:是不是稳定在目标以下,有没有毛刺。

- **Throughput**:业务运行时间 / 总时间,健康值 > 95%。

- **Young GC 频率**:太频繁说明 Eden 太小(可能 `MaxGCPauseMillis` 设太严)。

- **Mixed GC 是否正常触发**:观察并发标记周期后是否跟着一串 Mixed GC。

- **Full GC 次数**:必须是 0,出现即事故。

- **Humongous 分配次数**:GC 日志里有 `humongous` 关键字,频繁出现要调大 Region。

- **To-space Exhausted**:晋升失败,预留空间不够,是 Full GC 前兆。

  

**分析工具**

  

- **GCViewer / GCEasy**:GC 日志离线分析,最常用。

- **JFR + JMC**:低开销持续采集,能看到每次 GC 的详细信息。

- **Arthas dashboard**:线上实时看 GC 情况。

- **Prometheus + Grafana**:微服务标配,`jvm_gc_pause_seconds` 打监控面板。

  

**常见问题排查决策树**

  

- **停顿超标** → 看是 Young GC 还是 Mixed GC 超标 → Young 超标调低 `MaxGCPauseMillis` 或增加 `ParallelGCThreads`;Mixed 超标调小 `G1OldCSetRegionThresholdPercent`。

- **频繁 Full GC** → 看是 Concurrent Mode Failure(IHOP 太高)、Humongous(Region 太小)、还是 Metaspace 满。

- **老年代涨得快回收不下去** → 检查内存泄漏、调低 IHOP、调大 `G1MixedGCLiveThresholdPercent`。

- **吞吐低** → `MaxGCPauseMillis` 是不是设太小、`ConcGCThreads` 是不是太多抢 CPU。

### **八、G1 vs CMS vs Parallel vs ZGC**

  

| 维度 | Parallel GC | CMS(已废弃)| G1 | ZGC(分代)|

|---|---|---|---|---|

| 定位 | 吞吐优先 | 低延迟(过时)| 平衡 | 极致低延迟 |

| 停顿 | 秒级 | 百 ms 级 | 几十 ms | < 1ms |

| 停顿与堆大小 | 强正相关 | 正相关 | 弱正相关 | 无关 |

| 吞吐损失 | 基准 | ~5% | ~10% | ~15% |

| 内存开销 | 低 | 中(碎片) | 中高(RSet)| 高(染色映射) |

| 碎片问题 | 无 | 严重 | 无(拷贝) | 无 |

| 堆 sweet spot | 任意 | 4~8G | 4G~64G | 32G~TB |

| 状态 | 存在 | JDK 14 移除 | JDK 9+ 默认 | JDK 15+,21 成熟 |

  

**选择决策**:

  

- 批处理、离线计算 → **Parallel GC**(吞吐第一)。

- **在线服务、微服务、大部分业务 → G1**(默认就是最优解)。

- 大堆 + 极致低延迟 → **ZGC**。

- CMS **别再用了**,JDK 14 已经删除。

  

---

  

一句话总结 G1:**它用 Region 化堆布局 + RSet 跨引用管理 + 并发标记 + 增量 Mixed GC,把 CMS 时代的"停顿失控 + 内存碎片 + Full GC 灾难"三大问题一起解决了**。核心心智模型是**"垃圾多的 Region 优先回收,单次只回收放得下 `MaxGCPauseMillis` 的量"**。生产调优的黄金法则:**固定 Xms=Xmx、别锁 Xmn、`MaxGCPauseMillis` 从 100ms 起调、盯紧 IHOP 别让并发标记来不及、Humongous 多就调大 Region、任何 Full GC 都是事故**。掌握这些,G1 能覆盖 90% 的 Java 生产场景。
