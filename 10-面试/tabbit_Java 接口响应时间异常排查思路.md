“我们有个服务上线后，发现某接口的响应时间偶尔突增 300ms，监控显示 CPU 不高、GC 正常、数据库慢查也没报警。你作为 Java 工程师，会怎么系统性地定位这个问题？请说说你的排查思路和关键工具。”

### **先把"偶发 300ms 突增"拆成可验证的假设，用证据逐层收敛：先定位慢在哪一段，再找为什么慢。**

CPU、GC、慢查都正常，说明问题大概率不在"算得慢"，而在"等得久"：等锁、等连接、等网络、等下游、等调度或等 IO。

### **1. 先把现象量化**

- **看分布，不看平均值**：看 P99、P999 和最大值，别只看 avg。
- **找规律**：突增是否周期性（比如每 30s、每整点）？是否集中在某台实例、某个机房，或某类参数的请求？
- **周期性往往指向定时任务**：例如定时刷新缓存、日志滚动、连接池的 keepalive 或 evict、DNS TTL 过期、注册中心心跳。
- **和 300ms 这个数字对号入座**：很多默认值恰好在这个量级，比如重试间隔、TCP 重传（最小 RTO 约 200ms）、Nagle 加延迟 ACK（约 40ms 到 200ms）、连接池获取超时。

### **2. 用链路追踪切分耗时**

- 用 SkyWalking、Pinpoint、Zipkin 或 Jaeger 抓出慢请求的 trace，看 300ms 落在哪个 span：本服务内部、数据库、Redis、RPC 下游还是 MQ。
- 如果没有 trace，就在入口、出口和关键步骤临时加分段耗时日志，或用 Arthas 的 `trace` 命令动态查看方法调用链的耗时，不用重启。
- 如果 span 之间有空洞，说明时间花在排队：线程池队列、Tomcat 或 Netty 的 worker 排队、连接池等待。

### **3. 按"等待类型"逐项排查**

**线程与锁**
- 用 `jstack` 或 Arthas 的 `thread -b` 连续抓多次。偶发问题可以写脚本，在 RT 超阈值时自动抓栈。
- 重点看 BLOCKED 状态、`synchronized` 竞争、`ReentrantLock` 等待，以及日志框架同步输出（Logback 同步 appender 在磁盘抖动时会阻塞业务线程）。
- 看线程池是否打满、队列是否堆积。用 `thread -n` 查看线程状态，或查看 Micrometer 暴露的线程池指标。

**连接池与下游**
- HikariCP、Druid、HttpClient 和 Redis 连接池，看 pending 或 waiting 数、创建连接的耗时。连接被回收后重建（握手加 TLS）很容易产生几百毫秒的抖动。
- 检查连接 `maxLifetime`、`idleTimeout` 与服务端或防火墙的超时设置是否匹配。
- 下游的 P99 本身是否抖动，是否有超时后的重试。

**JVM 层面（GC 正常不等于 JVM 没问题）**
- **安全点停顿**：GC 日志里看不到，但会让所有线程停住。用 `-Xlog:safepoint`（JDK 9+）或 `-XX:+PrintSafepointStatistics` 排查。常见诱因有偏向锁撤销、JIT 去优化、大量 `jstack` 或 `jmap` 触发。
- **JIT 编译与类加载**：刚上线或冷路径首次调用会慢，可用 `-XX:+PrintCompilation` 和类加载日志确认。
- **Metaspace 或 CodeCache** 是否频繁扩容或被填满。
- **GC 日志要细看**：不只看 Young 和 Full GC 次数，还要看单次 pause、`Allocation Failure` 以及 GC 线程等待的时间。要关注 `user`、`sys`、`real` 的差异：real 大于 user+sys 通常说明 IO 或调度问题。
- 用 JFR（Java Flight Recorder）持续录制是最推荐的方式，开销低（约 1% 到 2%）。它可以查看锁竞争、Socket 读写、文件 IO、安全点和线程停顿事件，然后用 JMC 分析。

**操作系统与容器**
- **CPU 不高不代表没被限流**：在 K8s 里看 cgroup 的 `cpu.stat` 中的 `nr_throttled` 和 `throttled_time`。CFS quota 限流经常产生几十到上百毫秒的抖动，而平均 CPU 使用率看起来很低。
- 用 `vmstat`、`pidstat -w` 看上下文切换。用 `iostat` 看磁盘 await。用 `sar -n` 和 `ss -ti` 看网络重传。
- **内存**：是否发生 swap、透明大页（THP）导致的停顿、宿主机内存紧张。
- **宿主机噪声邻居**：同机其他容器抢资源、虚拟机 CPU steal（`top` 里的 `st`）。

**网络与 DNS**
- 用 `tcpdump` 或 Wireshark 抓包，看是否有重传、握手延迟、RST。
- DNS 解析：JVM 的 DNS 缓存策略、解析超时。应用里 `InetAddress.getByName` 偶尔卡顿很常见。
- 负载均衡、网关或 Service Mesh（Sidecar）本身的排队。

**数据库侧的隐性问题（慢查没报警不等于 DB 没问题）**
- 慢查询阈值可能设得太高，而且慢日志只记录执行时间，不包含等锁、等连接和网络往返。
- 检查行锁等待、元数据锁、主从延迟、连接数打满、事务未及时提交。用 `SHOW ENGINE INNODB STATUS` 和 `performance_schema` 查看。

### **4. 工具组合**

| 目的 | 工具 |
|---|---|
| 链路耗时拆分 | SkyWalking、Zipkin、Arthas `trace` |
| 线程与锁 | jstack、Arthas `thread`、async-profiler（lock 模式） |
| 持续低开销诊断 | JFR + JMC |
| 火焰图 | async-profiler（cpu、wall、lock 模式） |
| 系统和网络 | pidstat、iostat、sar、ss、tcpdump |
| 容器限流 | cgroup `cpu.stat`、Prometheus 的 `container_cpu_cfs_throttled_*` |

这里的关键是 **async-profiler 的 wall-clock 模式**：它采样的是墙钟时间而不是 CPU 时间，所以能抓到"在等什么"，这正是 CPU 型分析看不到的部分。

### **5. 复现与验证**

1. 先找到共性，比如特定实例、特定时间点或特定参数，缩小范围。
2. 定位到疑点后做对照实验：调大连接池，调整线程池，关闭偏向锁，放宽 CPU limit，或把日志改成异步。每次只改一个变量。
3. 改动后对比 P99 和最大值是否消失，而不只看平均值。
4. 最后补上防护：给关键环节加耗时指标和告警（连接池等待、线程池队列、限流次数、安全点时间），避免下次再无从下手。

### **我的优先级建议**

如果要给一个"最先看什么"的排序，我会先查 **容器 CPU 限流**、**连接池和线程池排队**、**安全点停顿**、**同步日志阻塞** 和 **DNS 或连接重建**。这几项最符合"CPU 低、GC 正常、慢查无报警、偶发突增"的特征，而且用 JFR 加 trace 通常一两轮就能确认。

什么叫span之间有空洞

### **"Span 之间有空洞"，指的是在 trace 的时间轴上，父 span 的总耗时比所有子 span 耗时加起来多出一大截。这段没有被任何 span 记录的时间，就是"空洞"。**

### **先说 span 和 trace**

一次请求在链路追踪里是一个 trace。trace 由多个 span 组成，每个 span 代表一段有开始和结束时间的操作，比如"处理 HTTP 请求"、"查 MySQL"、"调用 Redis"、"RPC 调下游"。span 之间有父子关系，形成一棵树。

### **一个具体例子**

假设接口总耗时 400ms，trace 如下：

```
[ 父 span：/order/create  0ms ──────────────────────── 400ms ]
   [ 子 span：查 MySQL   0ms ─ 20ms ]
        (空洞：20ms ~ 320ms，没有任何 span)
                                   [ 子 span：调用 Redis  320ms ─ 340ms ]
                                        [ 子 span：RPC 下游  340ms ─ 390ms ]
```

子 span 实际耗时只有 20 + 20 + 50 = 90ms，但父 span 花了 400ms。20ms 到 320ms 之间的 300ms 没有任何 span 覆盖，这就是"空洞"。

### **为什么空洞说明在排队或等待**

追踪框架只给"被埋点的操作"生成 span，比如 JDBC、HTTP Client、Redis 客户端。空洞里的时间，说明代码既没有在执行被埋点的操作，也没有出现在任何子调用里。常见原因有：

- **线程池排队**：请求已经进入系统，任务提交到线程池后在队列里等线程，真正开始执行前的时间没有 span。
- **Web 容器排队**：Tomcat 或 Netty 的 worker 线程都忙，请求在 accept 队列或任务队列里等。
- **连接池等待**：拿数据库或 Redis 连接时阻塞，而 span 往往从拿到连接、真正发送请求才开始计时。
- **锁等待**：`synchronized` 或 `ReentrantLock` 竞争，同样不会生成 span。
- **未埋点的本地代码**：比如同步日志、序列化、一段没被插桩的业务逻辑。
- **安全点停顿或 CPU 限流**：线程被整体挂起，也表现为一段空白。

### **怎么用它定位问题**

1. 先找到慢请求的 trace，对比父 span 总时长和子 span 之和。
2. 如果子 span 本身很慢，说明问题在那个下游，直接去查对应组件。
3. 如果出现空洞，说明慢在本服务内部的"等待"，再用 `jstack`、JFR、async-profiler 的 wall 模式，或者给线程池和连接池加指标，确认到底卡在哪种等待上。

另外要注意，空洞也可能是**埋点缺失**造成的，比如某个框架没被 agent 插桩。排查时可以先确认空洞前后的代码做了什么，再判断是"真的在等"还是"没埋点"。

这里是什么的重试间隔

### **这里的"重试间隔"指的是应用层或客户端组件在请求失败/超时后、发起下一次重试之前的等待时间。它是我举的一类例子,并不特指某一个组件。**

我当时写得比较笼统,容易让人误解。具体来说,它是指各类客户端或中间件框架里"失败后自动重试"的退避间隔。如果某个请求第一次失败(连接被重置、超时、下游返回错误),等待一个固定间隔后再试一次,这段等待就会直接叠加到接口响应时间上。偶发的一次重试,就会表现为"偶尔突增一截"。

### **常见的会产生这类间隔的地方**

- **RPC 框架的重试**:Dubbo、gRPC、Feign/Ribbon、Spring Retry 等,失败后会按配置重试,间隔和次数都可以设置。有的默认立即重试,有的带退避(例如 100ms、200ms 递增)。
- **HTTP 客户端的重试**:Apache HttpClient、OkHttp 的重试策略。典型场景是复用了一个已被服务端关闭的"死连接",第一次发送失败后自动换新连接重试,多出一次建连甚至握手的耗时。
- **数据库和缓存客户端**:连接断开后的重连与重试,比如 Redis 客户端(Lettuce、Jedis)重连退避、JDBC 连接池校验失败后重新获取连接。
- **消息和注册中心客户端**:Kafka 的 `retry.backoff.ms` 默认就是 100ms,一些配置中心和注册中心的重连间隔也在百毫秒级。

### **为什么说它和"300ms"有关**

这些重试间隔的默认值或常用配置,很多落在 100ms 到 500ms 之间。如果你看到的突增稳定在接近某个固定值(比如一直是约 300ms,或 100ms 的整数倍),就很可能是"一次失败加一次固定间隔的重试"。

### **怎么验证**

1. 检查各客户端的重试配置(重试次数、间隔、是否开启),看是否有值与突增量吻合。
2. 在日志或 trace 里找慢请求对应的 warn/error、重试日志或同一下游的多个重复 span。
3. 查下游和网络是否偶发超时、连接被重置,因为重试只是"症状",根因往往是连接失效或下游抖动。

需要说明的是,TCP 重传、Nagle 加延迟 ACK 则属于操作系统网络层的机制,不属于应用层重试,这一点和前面的"重试间隔"是不同层面的。

线程池指的是tomcat线程池吗？Tomcat的worker排队是？连接池又是？

### **不完全是。"线程池"在这里是泛指,Tomcat 线程池只是其中最常见的一种;Tomcat 的 worker 排队、连接池则是另外两个不同位置的"等待点"。**

一个请求从进入到返回,会依次经过好几个"池子",每个池子满了都会让请求排队,而这些排队时间通常不会生成 span,所以在 trace 里表现为空洞。

### **1. 线程池:泛指应用里所有的线程池**

它包括三类:

- **Web 容器的请求线程池**:也就是 Tomcat 的线程池,下面单独讲。
- **业务自己创建的线程池**:比如用 `ThreadPoolExecutor`、`@Async`、`CompletableFuture` 提交任务的线程池。任务提交后,如果核心线程都忙,就会进入队列等待,队列里的等待时间就是空洞。
- **框架内部的线程池**:比如 Dubbo 的服务端线程池、Feign/异步 HttpClient 的 IO 线程池、`parallelStream` 用的公共 ForkJoinPool。

所以我说的"线程池队列",重点是指任务在"队列里等线程"这件事,不限于 Tomcat。

### **2. Tomcat 的 worker 排队**

Tomcat 处理请求的大致流程如下:

```mermaid
flowchart LR
A[客户端连接] --> B[操作系统 accept 队列]
B --> C[Acceptor 线程接收连接]
C --> D[Poller 线程监听读写事件]
D --> E[Worker 线程池 处理业务]
E --> F[返回响应]
```

- **Worker 线程**:就是真正执行你的 Controller 代码的线程,数量由 `server.tomcat.threads.max` 控制(Spring Boot 默认 200)。
- **排队发生的地方**:当 200 个 worker 都在忙,新请求无法立刻被处理,会在 Tomcat 的任务队列里等待。连接数也有上限(`max-connections`,默认约 8192),超出后连接会进入操作系统的 accept 队列(由 `accept-count` 控制,默认 100)。
- **为什么没有 span**:追踪 agent 通常在 worker 线程开始执行请求时才创建入口 span,排队的那段时间请求还没被 worker 拿起来,所以没被记录。从客户端视角看响应慢了,但服务端 trace 里看不出来。

Netty 同理,只是它的角色叫 EventLoop/worker 线程(比如 Spring WebFlux、gRPC、Dubbo 底层),如果 EventLoop 被阻塞的业务代码占住,其他请求就得等。

### **3. 连接池:对下游资源的连接复用池**

连接池不是处理"进来的请求",而是管理"你主动发出去的连接",比如:

- 数据库连接池:HikariCP、Druid。
- Redis 连接池:Lettuce、Jedis。
- HTTP 客户端连接池:Apache HttpClient、OkHttp。

池里的连接数是有限的(比如 HikariCP 默认 10)。如果所有连接都被占用,你的线程调用 `getConnection()` 时就会阻塞等待,直到有连接归还或超时(HikariCP 的 `connectionTimeout` 默认 30 秒)。这段等待时间同样发生在"真正发起 SQL 之前",而 JDBC 的 span 往往从 SQL 发送才开始计时,所以也是空洞。

### **三者的关系**

可以这样理解一个请求的生命周期:先在 Tomcat 队列里等 worker(排队点一),拿到 worker 后执行业务,可能把部分任务丢给业务线程池(排队点二),执行过程中要查库或调下游,又要向连接池借连接(排队点三)。三处任何一个繁忙,都会造成"偶发 300ms"却没有明显 CPU 压力的现象。

### **怎么观察它们**

- Tomcat:通过 Micrometer 查看 `tomcat.threads.busy`、`tomcat.threads.current` 等指标,busy 接近 max 就说明在排队。
- 业务线程池:监控 `getQueue().size()`、`getActiveCount()`。
- 连接池:HikariCP 的 `hikaricp.connections.pending`(正在等待连接的线程数)、`hikaricp.connections.acquire`(获取连接耗时)。

这里是啥意思

这句话的意思是：**请求偶尔变慢时，趁它正在变慢，查看 Java 进程里各线程当时在做什么；多抓几次，判断它是在等锁、等连接，还是卡在某段代码上。**

- **`jstack`**：JDK 自带的命令行工具，用来打印 Java 进程中所有线程的堆栈和状态。堆栈可以看到线程当时执行到哪些方法，以及是在运行、等待还是阻塞。
- **Arthas 的 `thread -b`**：Arthas 是 Java 诊断工具；`thread -b` 用于查看当前阻塞其他线程的线程，帮助定位锁竞争。它不是所有“慢请求”的通用捕获命令，只有怀疑锁阻塞时才特别有用。
- **“连续抓多次”**：例如间隔几百毫秒到 1 秒抓几次。单次堆栈只是瞬时快照，可能刚好没抓到问题；多次结果若反复显示线程卡在同一把锁、同一个网络读写或连接获取位置，就更有参考价值。注意，线程快照本身不能直接证明请求耗时，最好结合请求日志或 trace 的时间戳。
- **“RT 超阈值时自动抓栈”**：RT 是响应时间。可以在监控或应用代码发现某次请求耗时超过设定值（例如 500ms）时，自动保存当时的线程快照，方便事后分析偶发问题。

要谨慎使用：`jstack` 会短暂影响进程，生产环境应控制抓取频率；也不要在每个慢请求上都抓，宜设冷却时间并限制文件数量。

RT全拼？

RT 是 **Response Time** 的缩写，意思是“响应时间”，也就是从发出请求到收到响应所经过的时间。

pending和waiting是？为什么创建连接会耗时很多？连接被回收后为啥要重建？为啥重建耗时

### **`pending` / `waiting` 通常表示正在等连接池分配连接的请求或线程。连接重建耗时，是因为客户端要重新和服务器建立一条可用连接；若还要做 TLS 加密握手、DNS 查询或跨网络建连，就可能明显变慢。**

**`pending` 和 `waiting` 是什么？**  
不同连接池的指标命名不完全一样，含义通常相近：连接池里的连接都被占用或暂时不可用时，等待借连接的线程数。比如 5 个请求同时要查数据库，但池中连接都被其他请求占着，后来的请求会等；这时 pending/waiting 可能增加。它们表示“有人在等”，不是等待时长。要判断影响，应同时看获取连接的耗时、连接池使用数和等待数；个别框架中 `pending` 也可能指等待中的连接创建任务，需以对应组件文档为准。

**为什么创建连接会耗时？**  
以访问数据库为例，建立连接通常不只是分配一个对象，还可能包含：

1. DNS 查询，把数据库域名解析成 IP。
2. TCP 建连，与服务器完成网络握手。
3. TLS 握手（如果启用了加密），协商加密参数并验证证书。
4. 数据库协议认证、会话初始化，以及连接池配置的校验或初始化 SQL。

这些步骤需要网络往返；跨机房、网络抖动、DNS 慢或服务器繁忙都会拉长耗时。TLS 和认证等具体步骤取决于客户端与服务端的配置。

**连接为什么会被回收？**  
连接池会按配置关闭或替换连接，例如连接空闲过久、达到最大存活时间、服务端或防火墙关闭了闲置连接，或者连接被检测为失效。池会在合适时机补充连接；某个请求借到失效连接时，客户端也可能先发现连接不可用，再尝试换新连接。这里的“回收”通常是**关闭旧连接**，不是把连接放回池里；正常使用完的连接一般是归还池中复用。

**怎么确认是不是这个原因？**  
看慢请求对应时刻的连接获取耗时，以及池的总连接数、空闲连接数、使用中连接数和等待数；再结合连接池日志、数据库或 Redis 服务端日志、DNS/网络指标，确认是否发生了连接创建、验证失败或重试。还要区分“等池里现有连接”和“新建连接慢”：前者看等待时间，后者看连接创建耗时。

为啥要特别指出是P99

### **因为平均值容易掩盖少数慢请求，而 P99 专门反映慢请求尾部的表现。**

P99 是“第 99 百分位响应时间”：把一段时间内的请求按耗时从短到长排序，99% 的请求不超过这个值，最慢的约 1% 会高于它。

比如 10,000 个请求中，9,900 个在 20ms 内完成，100 个要 300ms。平均值可能仍然看起来不错，但 P99 会接近 300ms，能把这类偶发抖动凸显出来。

因此排查时看下游 P99，是为了判断：**慢请求是否也发生在下游的尾部**。如果接口 P99 突增时，下游 P99 也同时突增，下游抖动就值得重点排查；如果下游 P99 正常，则应继续检查本服务里的排队、连接池等待或未埋点耗时。

这里的命令会打印出什么？JIT去优化是啥

`-Xlog:safepoint` 会在 JVM 日志中记录**安全点相关事件和耗时**，不是打印 Java 线程的完整堆栈。具体格式会随 JDK 版本和日志配置略有差异，常见信息包括：

- 为了让所有相关线程到达安全点，JVM 等了多久（`Reaching safepoint`）。
- 线程停在安全点期间，JVM 做了什么、花了多久（`At safepoint`）。
- 离开安全点、线程恢复运行的耗时。

例如可能看到类似 `Reaching safepoint: ...`、`At safepoint: ...` 的记录。若“到达安全点”的耗时很长，说明有线程迟迟没能停到安全点；若安全点内耗时很长，则要进一步看当时执行的 JVM 操作。要把日志写入文件，通常还需配合 `-Xlog:safepoint:file=...` 等日志选项。旧版参数 `-XX:+PrintSafepointStatistics` 适用于较早的 JDK；较新的 JDK 通常使用统一日志 `-Xlog:safepoint`。

**JIT 去优化（deoptimization）**是指：JVM 发现某段已经由 JIT 编译成机器码的代码，依赖的假设不再成立，于是让执行从优化后的机器码退回解释执行，或转到重新编译后的代码。比如 JIT 根据运行时情况做了某种优化，后来程序行为变了，原有优化不再安全，JVM 就可能撤销它。

它有时会涉及安全点，但**并不意味着每次去优化都会造成明显停顿，更不能仅凭出现去优化就断定它导致了 300ms 延迟**。实际排查时要把安全点日志中的停顿时间与慢请求的时间戳对齐，并结合 JFR 事件或 JIT 编译日志确认。

这里为什么会导致300ms

**Metaspace 或 CodeCache 本身扩容、接近满，不会必然导致 300ms；它们只是值得检查的线索。**可能造成延迟的是扩容或空间不足时触发的后续工作，而不是“空间变大”这个动作一定很慢。

- **Metaspace** 存放类的元数据。加载大量新类、Metaspace 不足时，JVM 可能需要申请更多本地内存；若触发类卸载或相关 GC，可能出现停顿。不过，Metaspace 扩容通常不等于一次全线程停顿，也不应直接假定会造成 300ms。
- **CodeCache** 存放 JIT 编译后的机器码。空间不足时，JVM 可能停止或限制 JIT 编译，或清理不再使用的编译代码。之后热点方法可能暂时由解释器执行，性能变差；但这通常表现为一段时间内变慢，不一定是单次、固定的 300ms 尖峰。

排查时把事件时间与慢请求对齐：查看 JFR、GC/安全点日志、类加载与 JIT 编译日志，以及 `jcmd <pid> VM.metaspace`、`jcmd <pid> Compiler.codecache` 的状态。若只是容量接近上限，却没有对应的停顿、编译受限或慢请求时间关联，就不应把它当成根因。

单次pause是啥？分配失败不就是强关联着FullGC次数吗？GC线程等待谁？user、sys、real是啥

这里说的 **pause** 是一次 GC 让应用线程暂停的时间，也叫停顿时间。比如日志显示一次 Young GC 的 `Pause` 为 15ms，就表示这次 GC 期间，受影响的应用线程大约停了 15ms。具体是否所有线程都暂停、停顿如何统计，要看所用的垃圾收集器和日志格式。

**“分配失败”和 Full GC 有关联，但不是一回事。**`Allocation Failure` 通常表示线程申请内存时，当前区域无法满足分配，JVM 因而触发一次回收尝试。它可能通过 Young GC 解决，不一定直接 Full GC；若回收后仍无法满足分配、老年代空间不足等，才可能进一步触发 Full GC。要结合前后 GC 记录看它触发了哪种回收、是否升级到 Full GC，以及各自的停顿时间。

**“GC 线程等待”要看具体语境。**GC 线程可能等应用线程到达安全点，也可能等待其他 GC 工作线程、锁或操作系统调度；应用线程也可能在 GC 期间等待恢复。不能只凭“等待时间”这个词判断是在等谁，要看 GC 日志、JFR 的事件类型和安全点日志中的阶段耗时。

GC 日志里的 `user`、`sys`、`real` 通常是这次 GC 相关任务的 CPU 时间和墙钟时间：

- `user`：CPU 在用户态执行这些任务所花的时间。
- `sys`：CPU 在内核态为这些任务执行所花的时间。
- `real`：从开始到结束的实际经过时间，也就是墙钟时间。

GC 使用多个线程并行工作时，`user + sys` 是各线程 CPU 时间的合计，可能大于 `real`。如果 `real` 明显大于 `user + sys`，说明任务整体耗时中有较多时间没有消耗在这些线程的 CPU 执行上，可能是线程等待、调度延迟或资源等待；这只是线索，不足以单独证明是 IO 或调度问题。GC 类型、线程数和 JVM 版本都会影响这些数字的解释。

CPU 不高不代表没被限流：在 K8s 里看 cgroup 的 cpu.stat 中的 nr_throttled 和 throttled_time。CFS quota 限流经常产生几十到上百毫秒的抖动，而平均 CPU 使用率看起来很低。

这里每一个名词都是什么意思

这句话是在说：**容器的 CPU 使用率平均看起来不高，也可能因为短时间触到 CPU 配额而被暂停执行，导致请求延迟突然升高。**可以拆开理解：

- **K8s（Kubernetes）**：容器编排平台。它可以给容器设置 CPU 资源请求和上限。
- **CPU limit（CPU 上限）**：容器在一段时间内最多能使用多少 CPU 时间。达到上限后，Linux 可能暂时限制该容器继续使用 CPU。
- **CFS**：Linux 的 Completely Fair Scheduler（完全公平调度器），负责安排进程或线程何时使用 CPU。
- **CFS quota（CFS 配额）**：Linux 用来限制进程组 CPU 使用量的机制。可以理解为“每个调度周期内，这个容器最多能用多少 CPU 时间”。达到配额后，容器中的线程会被暂时 throttled，等下一个周期再继续运行。
- **限流 / throttling**：这里不是接口请求限流，而是 **CPU 限流**。线程因为用完 CPU 配额，暂时不能运行。
- **`cpu.stat`**：Linux cgroup 提供的 CPU 统计文件。在容器或对应的 cgroup 中查看它，可看到 CPU 使用和限流相关计数。不同 cgroup 版本的文件路径和字段略有差异。
- **`nr_throttled`**：发生过 CPU 限流的次数，或发生限流的调度周期数；更准确的定义取决于 cgroup 版本。
- **`throttled_time`**：线程组因 CPU 配额被限制运行所累计的时间。单位及字段名称也可能随 cgroup 版本不同。
- **平均 CPU 使用率**：一段时间内 CPU 使用量的平均值。平均值会掩盖短时间的限流：例如某个请求执行期间短暂用满配额，随后又空闲，整体平均值仍可能不高。
- **“几十到上百毫秒的抖动”**：指请求偶尔比平时慢几十到上百毫秒。它是可能出现的现象，不是固定值；实际延迟取决于配额、调度周期、线程数量和负载。

排查时，不要只看 `nr_throttled` 或 `throttled_time` 的累计值；应观察它们在**慢请求发生的同一时间窗口内是否增加**，并结合容器的 CPU limit、CPU 使用率和请求延迟判断。

cgroup是啥

**cgroup** 是 Linux 的 **control group（控制组）**机制，用来把一组进程归到一起，并对它们的资源使用进行统计和限制，例如 CPU、内存和 I/O。

在 Kubernetes 里，容器通常运行在 cgroup 管理之下。因此，容器的 CPU 限额、内存限额，以及是否被 CPU 限流等信息，都可以从对应的 cgroup 统计中查看。可以把它理解为：**Linux 给一组进程划出的资源“账本”和“限额规则”**。

例如，容器达到 CPU 配额时，cgroup 会记录相关限流统计；运维人员据此判断，是否存在“平均 CPU 看起来不高，但请求执行时短暂被限制”的情况。

vmstat、pidstat -w、sar -n、ss -ti
每一个的含义作用
以及对应字母单词的含义

### **它们都是 Linux 上用于观察系统或进程状态的命令。简单说：`vmstat` 看系统整体，`pidstat -w` 看进程的上下文切换，`sar -n` 看网络统计，`ss -ti` 看 TCP 连接细节。**

| 命令 | 名称含义 | 主要作用 |
|---|---|---|
| `vmstat` | **Virtual Memory Statistics**，虚拟内存统计 | 查看系统整体的进程、内存、交换空间、磁盘 I/O、CPU 等情况。排查时重点看 `r`（等待运行的进程数）、`b`（不可中断睡眠的进程数）、`si/so`（交换进出）和 `wa`（CPU 等待 I/O 的比例）。 |
| `pidstat -w` | **Process ID Statistics**，进程 ID 统计；`-w` 表示显示任务切换统计 | 按进程或线程查看上下文切换。重点字段通常是 `cswch/s`（主动上下文切换）和 `nvcswch/s`（被动上下文切换）。 |
| `sar -n` | **System Activity Reporter**，系统活动报告程序；`-n` 表示查看网络统计 | 按时间间隔查看网络流量、包数、错误和丢包等。常见用法如 `sar -n DEV 1` 看网卡流量，`sar -n TCP,ETCP 1` 看 TCP 活动及错误统计。 |
| `ss -ti` | `ss` 是 **Socket Statistics**，套接字统计；`-t` 表示 TCP，`-i` 表示显示 TCP 内部信息 | 查看 TCP 连接及其详细状态，例如重传、往返时延（RTT）、拥塞窗口等。适合观察连接是否存在重传、时延升高或拥塞迹象。 |

### **几个术语**

**上下文切换（context switch）**：CPU 暂停运行一个线程，保存它的状态，再切换去运行另一个线程。切换是正常现象；如果数量异常高，可能说明线程频繁被唤醒、阻塞或争抢 CPU，但不能单凭这个数字判定根因。

`pidstat -w` 中的两类切换通常是：

- **主动切换**（`cswch/s`）：线程主动让出 CPU，常见于等待锁、I/O 或条件变量。
- **被动切换**（`nvcswch/s`）：线程被操作系统抢占，常见于时间片用完或 CPU 竞争。

**TCP 重传**：发送方没有及时收到确认，就再次发送数据包。少量重传可能偶尔发生；若与慢请求同时增加，可能提示网络丢包、拥塞或链路异常。`ss -ti` 展示的是单条连接信息，`sar -n` 则更偏向一段时间内的系统网络统计。

这些命令的字段会因 Linux 发行版和 `sysstat` 版本略有差异；生产环境排查时，最好按秒采样，并把采样时间与慢请求的时间戳对齐。

### **THP 是 Transparent Huge Pages（透明大页），是 Linux 自动把多个小内存页合并成较大的内存页的一种机制。**

普通内存页常见大小是 4 KB；开启 THP 后，Linux 可能使用 2 MB 等更大的页。这样可以减少页表数量和地址转换开销，对某些内存密集型负载有帮助。

但在对延迟敏感的服务中，THP 可能带来偶发卡顿：内核需要合并、拆分或整理内存页时，可能产生额外开销。是否真是延迟根因，要看慢请求发生时是否同时出现相关内核活动；不能只因为开启了 THP 就认定它有问题。

这是啥

### **JVM 的 DNS 缓存策略，是 Java 决定“域名解析成 IP 后缓存多久、失败结果缓存多久”的规则。**

比如程序访问 `api.example.com`，JVM 会通过 DNS 把域名解析成 IP。解析成功后，JVM 可能暂时复用这个结果，而不每次都重新查询 DNS；解析失败时，也可能把失败结果缓存一段时间。

它可能影响连接行为：如果缓存的 IP 已失效，连接可能失败或变慢；如果缓存时间过长，DNS 已切换到新 IP，应用也可能继续连旧地址。排查这类问题时，可检查 JVM 的 DNS 缓存配置、域名解析耗时，以及慢请求是否恰好发生在新建连接或 DNS 缓存过期时。

这里是？

这里是指：**请求到达你的 Java 服务之前，或从 Java 服务发往下游的途中，经过的代理组件也可能排队，增加延迟。**

- **负载均衡器（Load Balancer）**：把请求分发到不同服务实例的组件。请求可能在等待转发，或因为后端实例繁忙而延迟。
- **网关（Gateway）**：统一接收和转发请求的入口，常做认证、路由、限流等处理。网关自身繁忙时，请求可能排队。
- **Service Mesh（服务网格）**：管理服务间通信的一层基础设施，通常由控制组件和每个服务旁边的代理组成。
- **Sidecar（边车代理）**：部署在应用容器旁的代理进程，例如 Envoy。应用发出的请求可能先经过它，再到下游；它也可能在转发、限流、重试或等待连接时增加耗时。

排查时可以对比各段耗时：客户端到网关、网关到服务、服务到 Sidecar、Sidecar 到下游。如果入口侧耗时已经很高，而 Java 服务收到请求后的处理时间正常，问题可能在网关或网络路径上；若 Java 的 trace 显示调用下游耗时高，再查看 Sidecar 和下游的指标、日志。

这慢查询阈值是啥？啥玩意还会报警？没听说

这里的**慢查询阈值**，是数据库或监控系统用来判断“这条 SQL 算不算慢”的时间门槛。例如阈值设为 1 秒，执行 200ms 的 SQL 通常不会被记作慢查询；执行超过 1 秒的才会被记录或触发告警。

它**不一定默认会报警**。常见有几种情况：

- 数据库开启了慢查询日志：超过阈值的 SQL 被写入日志，方便之后分析，但未必发告警。
- 监控平台采集了慢查询日志或数据库指标：再按规则发送告警，例如慢查询数量突然增加。
- DBA 或团队配置了数据库告警：达到设定条件时通知相关人员。
- 没有开启日志或告警：那就不会自动提醒，可能只能从应用耗时、数据库监控或事后排查中发现。

“慢查询”通常是按 **SQL 在数据库侧执行多久**来判定的。它不一定包含应用等待数据库连接、网络传输或结果读取的全部时间；具体记录哪些阶段要看数据库、驱动和监控方式。因此，接口慢了而数据库慢查询日志没有记录，并不能完全排除数据库链路的问题。

JMC是啥

**JMC** 是 **Java Mission Control** 的缩写，是一款用于分析和诊断 Java 应用的工具。它可以打开 **JFR（Java Flight Recorder）录制文件**，查看线程、锁竞争、GC、安全点、网络和文件 I/O 等事件，帮助分析应用在某段时间内发生了什么。

简单说：**JFR 负责记录运行事件，JMC 负责查看和分析记录结果。**

火焰图是啥

### **火焰图是把程序运行时的调用栈汇总成一张图，用来快速看哪些函数最“占地方”。**

横向表示采样样本数量，通常可近似理解为某类活动所占比例；**越宽，说明该函数及其调用路径在样本中出现得越多**。纵向表示调用层级：最底层通常是入口或调用者，往上是被调用的方法。图形像一簇火焰，所以叫火焰图。

在 Java 性能排查中，常用 profiler 定期采样线程堆栈，再生成火焰图。不同采样模式回答的问题不同：

- **CPU 火焰图**：线程在采样时主要执行哪些代码？适合找 CPU 热点。
- **Wall-clock 火焰图**：线程的墙钟时间主要花在哪些调用栈上，包括等待、阻塞等情况；适合查“CPU 不高但请求慢”。
- **锁相关火焰图**：哪些调用路径花了较多时间等待锁？是否支持取决于 profiler 和配置。

注意，火焰图通常是**采样结果，不是每次请求的精确耗时账单**。看图时应结合采样类型、慢请求的时间段和 trace 一起判断；“最宽”表示样本占比高，不一定就是根因。

这是啥

**async-profiler 是 Java 性能分析工具。**它以采样方式记录程序运行时的调用栈，通常开销较低，可生成火焰图，帮助判断时间花在 CPU 运算、锁竞争、内存分配，还是等待网络、磁盘等操作上。 [async-profiler](https://github.com/async-profiler/async-profiler)

它的名字容易让人以为只分析异步代码；其实它也能分析普通 Java 应用。排查接口慢时，常见模式包括：

- **CPU 模式**：看哪些方法消耗了较多 CPU。
- **Wall-clock 模式**：看线程的实际经过时间花在哪里，包括等待和阻塞；适合 CPU 不高但响应慢的情况。

请求、线程和调用栈是三个不同层次的东西：

- **请求**：一次业务操作，例如客户端调用“查询订单”接口。

常见原因包括：

- **算法或数据规模问题**：例如本来近似线性处理的数据量突然增大，或低效查询结果在应用侧被大量处理。
- **线程竞争与忙等**：锁竞争、CAS 自旋、死循环、频繁重试，线程一直消耗 CPU，却没有有效推进请求。

- **异常处理或日志开销**：大量异常堆栈、同步日志、日志格式化也可能消耗明显 CPU。

### **GC 异常：分配过多、堆压力大或对象留存过久**

常见原因包括：

- **短命对象分配速率过高**：频繁创建临时对象、集合、字符串、序列化对象，会让 Young GC 变频繁。
- **内存泄漏或缓存无界增长**：对象长期被引用，老年代持续变大，可能引发 Old/Full GC。
- **大对象或大结果集**：接口一次读取、组装或返回大量数据，增加分配压力，甚至造成晋升或 Full GC。
- **堆太小或 GC 参数不合适**：负载稍有增加就出现频繁回收。
- **引用链或类加载器未释放**：对象、缓存、线程本地变量或动态生成的类没有及时释放。

查看 GC 日志中的频率、停顿时间、回收前后堆占用和对象晋升情况。若 GC 后堆占用仍持续升高，重点查对象留存；若回收后下降明显但很快又涨，可能是分配速率过高。

常见原因包括：

- **执行计划不佳**：索引缺失或未命中、索引选择性差、隐式类型转换、对索引列做函数处理。
- **扫描或返回数据过多**：缺少合适过滤条件、分页方式低效、一次查出大量行。
- **锁等待**：事务时间过长、热点行更新、锁冲突；SQL 执行时间之外的等待也可能拖慢请求。
- **数据库资源不足**：连接数、CPU、磁盘 I/O 或缓存压力，导致查询排队。
- **参数分布变化**：同一条 SQL 在不同参数下，数据量和执行计划可能差异很大。
