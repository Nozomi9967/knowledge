# 磁盘 IO 瓶颈排查详解（vmstat · wa · iostat · iotop）

> 当 **Load 高但 CPU 使用率不高** 时，第一怀疑是 IO 问题（大量进程卡在 D 状态，见 [[OS热门面试题#8. Load Average 是什么？Load 很高但 CPU 不高说明什么？【高频】]]）。这份笔记给出确认它、并定位到**具体磁盘、具体进程**的三个核心工具/指标。

---

## 一、`vmstat` 的 `bi` / `bo`

`vmstat 1` 每秒刷新一次，看系统整体状态：

```
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2  5      0 123456  78900 456789    0    0  1024  2048  500 1000  5  3 12 80  0
```

| 指标 | 含义 | 怎么看 |
|------|------|--------|
| **`bi`** | Blocks In，每秒从磁盘读入的数据块 | 数值大 = 大量读磁盘 |
| **`bo`** | Blocks Out，每秒写到磁盘的数据块 | 数值大 = 大量写磁盘 |
| `b` | 处于 **D 状态**（等 IO）的进程数 | 这个大 = 进程堆积在等 IO |
| `wa` | IO wait（见下节） | CPU 花在等 IO 的比例 |

> 记忆：**b**lock **i**n / **b**lock **o**ut，就是磁盘读写量。

两个精度补充（被追问时用得上）：

- **`bi` 不含页缓存命中的读**——数据在 cache 里就不产生块设备流量。所以"缓存命中高的应用 bi 反而低"，bi 高 = 真在敲磁盘
- **`bo` 主要是脏页回写**——不是应用 `write()` 的那一刻（那只是写进页缓存），而是内核回写线程刷盘时才计入。所以"写多 bi/bo 就高"要隔一层看

---

## 二、`wa`（IO wait）—— 最关键指标

`wa` 出现在 `top`、`vmstat`、`iostat` 里，代表：

> **CPU 空闲着，但在等磁盘 IO 完成的时间占比**

### 怎么理解

```
CPU 时间去哪了？
├── us（user）    用户程序占用      → 正常干活
├── sy（system）  内核占用          → 正常干活
├── id（idle）    纯空闲            → 真的没事干
└── wa（iowait）  空闲但在等磁盘 ← 干不了活，被磁盘拖住了
```

### 关键判断

```
CPU 使用率低（us+sy 低）
   +
wa 很高（比如 80%）
   ↓
说明：CPU 不是闲，是被慢磁盘卡住了！
   ↓
问题在磁盘/IO，加 CPU 没用！
```

这正对上 Load 那题的因果：**一堆 D 进程把 Load 顶起来，根因是它们背后的存储 IO**（[[OS八股#3.2 Load Average：它统计的不只是"在跑"的任务]]）。

> ⚠ **`wa` 高只是"有 CPU 闲着且有人在等 IO"的信号**，它不告诉你谁在等、等哪块盘——所以要往下走 `iostat`。另外极端情况（所有核都在忙别的）wa 可能不高但 IO 依然堵，别只盯 wa 一个数。

---

## 三、`iostat` —— 定位到具体磁盘

`iostat -x 1` 看每块磁盘的详细情况：

```
$ iostat -x 1
Device  r/s    w/s    rkB/s   wkB/s  await  %util
sda     10.0   200.0  1024.0  8192.0  50.0   98.5
nvme0   5.0    50.0   512.0   2048.0  0.5    12.0
```

| 指标 | 含义 | 报警信号 |
|------|------|----------|
| `r/s` `w/s` | 每秒读/写次数（IOPS） | — |
| `await` | **IO 平均等待时间（毫秒）**，含排队 + 服务 | 机械盘 &gt; 20ms、SSD &gt; 5ms 就慢 |
| **`%util`** | **磁盘繁忙程度** | **接近 100% = 磁盘打满了！** |

> `%util = 98.5%` 意味着这块磁盘几乎没有空闲时间，已经是瓶颈。

> ⚠ **`%util` 对 SSD / NVMe 这类多队列设备不可靠**：它的定义是"设备 busy 的时间占比"，机械盘一次只能处理一个请求，98% ≈ 饱和；但 NVMe 能并行处理几十个 IO，**%util 打满 ≠ 真饱和，甚至可能永远不到 100% 就已到极限**。所以**判断 SSD 瓶颈以 `await` 为主、%util 只作机械盘的参考**。

---

## 四、`iotop` / `pidstat` —— 定位到具体进程

找到盘之后，最后一环是**谁在读写的这张盘**：

```
iotop -oPa       # -o 只显示正在产生 IO 的进程；-P 显示进程而非线程；-a 累计量
pidstat -d 1     # sysstat 包，没有 iotop 时的替代，能看到每个进程的读/写 KB/s
```

拿到 pid 之后接 Java 侧套路：`/proc/<pid>/io` 看累计量、`lsof -p <pid>` 看它打开了哪些文件、`jstack <pid>` 看哪些线程卡在文件/网络 IO 上。

---

## 五、完整排查链路（面试报三板就报这个）

```
① top / uptime  → 发现 Load 高，但 CPU 使用率低
        ↓
② top 看 wa     → wa 很高（如 80%）→ 确认是 IO 问题
        ↓
③ vmstat 1      → 看 b 列（D状态进程多）+ bi/bo（读写量大）
        ↓
④ iostat -x 1   → 找到 %util 接近 100%（机械盘）或 await 飙高 的那块盘
        ↓
⑤ iotop         → 找到具体是哪个进程在疯狂读写
        ↓
      定位完成：处理问题进程 / 换更快的盘 / 优化 IO 模式
```

**NFS 场景补一刀**：如果 `iostat` 里本地盘都不忙、但 D 进程一堆，查挂载——`mount | grep nfs`、`dmesg | tail` 看有没有 `nfs server not responding`。NFS 挂住时 IO 不进任何本地设备的统计，**只有 D 和 wa 会诚实反映**。

## 六、一句话总结

| 指标 | 一句话 |
|------|--------|
| `bi/bo` | 磁盘每秒读/写了多少数据 |
| `wa` | CPU 有多少时间在**干等磁盘** |
| `await` | 每次 IO 要等多久 |
| `%util` | 磁盘忙到什么程度（机械盘接近 100% 就是瓶颈；SSD 别信它，看 await）|

> 核心逻辑：**Load 高 + CPU 低 → 看 wa → wa 高就是 IO 问题 → 用 iostat 找到打满的磁盘 → 用 iotop 找到罪魁进程**。

---

## 面试话术

> "Load 高但 CPU 不高，我的判断是大量进程卡在 D 状态等 IO，确认分三步。先 `vmstat 1` 看全局：`b` 列是 D 状态进程数，`bi`/`bo` 是磁盘每秒的读入写出量，两个一起大就是实锤在敲盘；再看 `wa`，它的含义是 CPU 闲着但在等磁盘——wa 高说明 CPU 不是没活干，是活被磁盘卡住了，这时候加核完全没用。然后 `iostat -x 1` 下钻到具体设备，机械盘看 `%util`，接近 100% 就是盘打满了，`await` 超过 20 毫秒就是慢；不过 NVMe 这种多队列盘 `%util` 不可靠，得看 `await`。最后 `iotop` 找到是哪个进程在疯狂读写，再看它的代码路径——是日志刷盘、大文件读写，还是换页。整套就是三板斧：top 定性、iostat 定位到盘、iotop 定位到进程。"
