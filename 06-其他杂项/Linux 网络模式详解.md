# Linux 网络模式详解（虚拟机三模式 + Docker 五模式 + 内核网桥）

> [!abstract] Linux 网络模式 — Network Modes（虚拟机 / 容器 / 内核三层的网络接入方式）
> 一句话：**虚拟机和容器怎么接入网络**，本质都是同一套事——**造一张虚拟网卡 → 接进一个虚拟交换机 → 决定谁做 NAT**。
> 三种语境，同一套机制：
> - **虚拟机三模式**：桥接 / NAT / 仅主机（VMware 的 VMnet0 / 8 / 1）
> - **Docker 五模式**：bridge / host / none / container / overlay
> - **内核底层四件套**：network namespace + veth pair + Linux bridge + iptables NAT
> 记住底层那套，"虚拟机连不上网怎么排查""容器为什么能上外网"都是它的推论。

---

## 一、底层原理：Linux 网络虚拟化四件套

任何"虚拟网络"都是这四样东西搭出来的。先吃透它们，后面虚拟机、Docker、K8s 全是套用。

### ① network namespace（网络命名空间）

- 隔离一整套**网络栈**——所谓"网络栈"就是下面这五样，它们合起来 = **一台机器在网络世界里的全部家当**，隔离它们就等于凭空造出一台"网络身份独立"的机器：

| 东西                     | 一句话          | 具体干嘛                                                      | 怎么看                  |
| ---------------------- | ------------ | --------------------------------------------------------- | -------------------- |
| **网卡**（interface）      | 机器的"网口"      | 数据包进出的地方；每张卡挂着 IP / MAC / 状态（up/down）/ MTU，**IP 是配在网卡上的** | `ip addr`            |
| **路由表**（routing table） | 出门的"导航"      | 决定一个包**从哪张网卡发、下一跳给谁**；没有匹配项就报 `Network is unreachable`    | `ip route`           |
| **iptables 规则**        | "门卫 + 地址伪装员" | 放行/拦截包，以及**改写地址**（DNAT 端口映射、SNAT/MASQUERADE 伪装出网）         | `iptables -t nat -L` |
| **ARP 表**              | 同局域网的"通讯录"   | **IP → MAC 缓存**；二层发帧靠 MAC，发前先查它，表项会老化重问                   | `ip neigh`           |
| **socket 端口空间**        | 进程的"门牌号"     | 0~65535 的端口占用范围；谁监听 8080，发到 8080 的包就归谁                    | `ss -lntp`           |

- **"独立"的含义**：上面每一样，**每个 ns 各有一份、互不干扰**。所以**容器里能监听 80、宿主机也能监听 80，不冲突**（同一个 ns 里做不到）；`ip netns exec ns1 bash` 进去后，看到的 `ip addr` / `ip route` / `iptables -L` 全是"那台机器"的，跟宿主无关。
- **边界**：netns 隔的是 **L3/L4 及以下 + 规则**，**不管应用层**，也不管 DNS 配置（`/etc/resolv.conf` 是普通文件，要靠 mount namespace 才能一起隔掉）。
- **新建的 ns 只有一张 `lo`，而且是 down 的**——所以容器刚起来必须给它配网卡、配路由。
- 典型落点：一个 Docker 容器 = 一个 network namespace（所以容器里有独立的 IP 和端口，和宿主机端口不冲突）。

```bash
ip netns add ns1                 # 建一个网络命名空间
ip netns exec ns1 ip addr       # 进去看，只有 lo
```

### ② veth pair（虚拟网线）

- 一对**成对出现**的虚拟网卡，一根网线的两端：**从一端进去的帧，一定从另一端出来**。
- 典型接法：一端放进容器/虚拟机的 ns（容器里改名 `eth0`），另一端插在宿主机的虚拟网桥上。

**心智模型**：把 veth pair 想成一根"虚拟网线"，**两头各有一张虚拟网卡**：

```
容器里的 eth0  ←──── 虚拟网线 ────→  宿主机上的 veth1
（容器 netns）                        （宿主 netns）
```

容器往 `eth0` 发出的数据，会从宿主机那一端的 `veth1` 收到；反过来也一样。**两端通常分别放在不同的 network namespace 里**，所以容器能像真的接了一张网卡一样通信。

```bash
ip link add veth0 type veth peer name veth1   # 造一根网线
```

**命令拆解**：

| 片段 | 含义 |
|------|------|
| `ip link add veth0` | 创建一张虚拟网卡，命名为 `veth0` |
| `type veth` | 类型是 veth（虚拟以太网） |
| `peer name veth1` | **给它的配对端（peer）命名为 `veth1`** |

- `peer name` 就是**给"另一端"起名**——veth 天生成对，创建一端时会**顺带把另一端也造出来并命名**。所以这一条命令实际创建了**两张**网卡：`veth0` 和 `veth1`，就像一根网线的两头。
- **刚创建时两端都在当前网络命名空间**；之后典型的两步：把一端**移进**容器的 netns（`ip link set veth1 netns &lt;容器ns&gt;`，进去后常改名 `eth0`），另一端**接到**宿主机的网桥上（`ip link set veth0 master docker0`）。
- **口诀**：veth pair = 一根虚拟网线的两头；发到一头的数据，从另一头出来。

### ③ Linux bridge（虚拟网桥 = 二层交换机）

- 本质是**二层交换机**：按 MAC 地址学习、转发帧。**不路由**（除非给它配上 IP 当网关）。
- `docker0` 就是一个 bridge，默认 `172.17.0.1/16`；自定义网络会再建一个 `br-xxxx`。
- 插上去的 veth 就是它的"端口"，**同一个网桥内的设备能二层直接互通**，跨网段才需要过网关。

```bash
brctl show                       # 或 ip link show type bridge
```

**"给它配上 IP 当网关"是什么意思**：网桥本身只做二层转发，但如果给网桥配一个 IP，容器就能把它当作**出口网关**：

```
容器：    172.17.0.2
docker0： 172.17.0.1   ← 容器把出网的包先交给它
```

容器要访问外网时，先把包交给 `172.17.0.1`，再由宿主机转发出去（就像电脑把包交给家里的路由器）。⚠ 但这个 IP **只是网关地址**——要真能出网，宿主机还得开转发（`ip_forward`）并配好 NAT 规则。

### ④ iptables / nftables（NAT 与转发开关）

一句话总览：**NAT 负责改地址，`ip_forward` 负责允许包通过。**

- **出方向**（容器/虚拟机 → 外网）：`MASQUERADE`（一种 SNAT），把源 IP 改写为宿主机 IP。
- **入方向**（外网 → 容器）：`DNAT`，把目的 IP:port 改写为容器 IP:port（这就是 `-p` 端口映射）。
- 中间还受内核开关 `net.ipv4.ip_forward=1` 控制是否允许转发。

**为什么非改地址不可**：容器拿的是**内网 IP**（如 `172.17.0.2`），这个地址在外网**不可路由**——外网压根不知道往哪儿送回复。

**先说 NAT 是什么**：`NAT` = **N**etwork **A**ddress **T**ranslation（**网络地址转换**）——转发数据包时，把包里的地址（有时连端口）改写一下。按"改哪一端"分成两种，记法就在首字母：

| 类型 | 改哪一端 | 用处 | 记法 |
|------|---------|------|------|
| **SNAT** | **来源**地址 | 内网出外网，伪装成网关 | **S** = **S**ource（来源） |
| **DNAT** | **目的**地址 | 端口映射，把外部流量转给内部 | **D** = **D**estination（目的） |

`MASQUERADE` 就是 **SNAT 的一种特殊形式**（源地址不写死，动态取出口网卡的地址）。

**① 容器访问外网：MASQUERADE（改来源地址）**

```
容器 172.17.0.2  →  宿主机改写来源地址  →  外网看到的是宿主机 IP
```

宿主机把包的**来源地址**改成自己的外网 IP，这叫 `MASQUERADE`（本质是一种 SNAT），理解成「**代替容器对外通信**」。外网回包发给宿主机，宿主机再转回容器。

> **单词记忆**：`masquerade` 本义是**化装舞会 / 伪装、冒充**——让内网机器"套上"网关的 IP 出门，正是这个意思。比死记缩写好记得多。

**② 外网访问容器：DNAT（改目的地址）**

```
访问 宿主机IP:8080  →  改写目的地址  →  容器IP:80
```

把包的**目的地址和端口**改写为容器的地址和端口，这叫 `DNAT`。Docker 的 `-p 8080:80` 配的就是这套。

**③ 转发开关：`ip_forward`**

即使 NAT 规则写好了，Linux 还得**允许自己把包从一张网卡转发到另一张网卡**——这是 `net.ipv4.ip_forward` 管的事。为 `1` 才允许转发；为 `0` 时宿主机根本不会替容器转发这些包，NAT 规则形同虚设。

```bash
sysctl -w net.ipv4.ip_forward=1      # 临时打开
cat /proc/sys/net/ipv4/ip_forward    # 或直接读这个文件
```

**通俗理解：宿主机是个"中转员"**

把 Linux 主机想成一位**中转员**，`ip_forward` 就是"**他愿不愿意帮忙转发**"的开关：

```
          容器 172.17.0.2
                │ ① 发出请求
                ▼
┌────────────────────────────────┐
│   Linux 主机（中转员）           │
│   ip_forward = 1 ？             │  ← 关着就到此为止，包被丢掉
│   conntrack 记下这次转换         │
└────────────────────────────────┘
                │ ② 转发
                ▼
              网站
```

- **`ip_forward = 1`**：允许主机转发经过自己的包 → 容器能出网；
- **`ip_forward = 0`**：包到了主机就此打住 → 容器出不去，**哪怕 NAT 规则配得好好的**。

所以务必分清：**NAT 负责改地址，`ip_forward` 负责允许转发**——两者缺一不可，也完全不是一回事。

**回复包怎么知道该回哪个容器？——conntrack「对照表」**

容器用的是内网地址，网站没法把回复直接发回来。所以主机做 NAT 时，除了改源地址，还会在 **conntrack（连接跟踪表）** 里记一笔：**这条连接原来来自哪个容器、被改成了什么地址**。

```
去：容器  →  主机改写来源地址  →  网站
回：容器  ←  主机改写目标地址  ←  网站回复
```

主机收到网站的回包，查这张"对照表"把目标地址改回容器地址，再转发给容器。

- **一次"记一笔"、一次"查表"**——所以容器**不需要知道任何 NAT 细节**，就像真的直连外网一样。
- 也正因如此，`MASQUERADE` 是**有状态**的：它天生依赖 conntrack，不是无脑改写。`conntrack -L` 可查看当前连接表。

**和 `-p 8080:80` 的区别**：上面讲的是**容器主动访问外网**（改**源**地址，靠 conntrack 自动回程）；`-p` 是**另一个方向**——外部访问主机的 8080 被转给容器的 80（改**目的**地址的 DNAT）。两者都涉及转发，但规则和数据流不同。

- 这里是**概念层**；`-p 8080:80` 对应的**具体 iptables 规则和数据流**见**第五节**；**iptables 本身是什么（五条链 / 四张表 / 规则怎么读）见第二节**。

### 串起来：一个容器是怎么"接上网"的

```
               宿主机（root namespace）
   ┌──────────────────────────────────────────────┐
   │   eth0 (物理网卡, 192.168.1.10)                │
   │      │                                        │
   │   docker0 (网桥 172.17.0.1/16)                 │
   │      │  ◄── veth 的宿主机端                    │
   └──────┼────────────────────────────────────────┘
          │ (veth pair = 一根网线)
   ┌──────┴───────── 容器 A（独立 netns）──────────┐
   │   eth0 (172.17.0.2/16, 网关 172.17.0.1)        │
   └───────────────────────────────────────────────┘
```

- 容器 = 一个 netns；Docker 给它造一对 veth，一端进容器 ns（改名 eth0），一端插到 docker0。
- 容器访问外网 → 宿主机开 `ip_forward` + iptables `MASQUERADE`。
- 外部访问容器 → iptables `DNAT`（即 `-p`）。

> **关键洞察**：**VMware 的 NAT 模式和 Docker 的 bridge 模式是同一个东西**——都是「虚拟网卡 → 虚拟交换机 → 宿主机做 NAT」，只是「容器」换成了「完整虚拟机」。理解了这句，三套"网络模式"就合并成一套了。

### 补充：路由表条目怎么读（`default via … dev …`）

```
default via 192.168.1.1 dev eth0
```

三个部分：

| 片段 | 含义 |
|------|------|
| `default` | **兜底规则**：前面所有更具体的路由都没匹配上时，用这条 |
| `via 192.168.1.1` | **下一跳**（nexthop）交给谁——通常是路由器 / 网关 |
| `dev eth0` | 从哪张**网卡**发出去（`dev` 是 **dev**ice 的缩写；网卡也可能叫 `wlan0`、`ens33` 等） |

连起来读：**"目的地不在我直连网段里的包，统统从 `eth0` 发出去、交给网关 `192.168.1.1`。"**

结合上面那张"五样对照表"看：**路由表 = 出门的导航**，这条就是导航里最兜底的一行。容器出网靠的也是它——把包交给 `docker0` 的网关（`172.17.0.1`）。

## 二、iptables 基础（表 / 链 / 数据包走向）

**一句话**：iptables 是 **Linux 内核的包过滤 + 地址改写框架**（用户态命令 + 内核的 netfilter 钩子），决定"**每个经过的包，在哪个时机、满足什么条件、做什么动作**"。它**不是 Docker 的东西**——Docker 只是自动往它里面插规则而已。

### ① 五条链 = 数据包经过的五个"关卡"

| 链（chain） | 时机 |
|------------|------|
| `PREROUTING` | 包刚进网卡、**还没决定发给谁**（路由决策之前） |
| `INPUT` | 已确认是发给**本机**的 |
| `FORWARD` | 已确认是**路过本机**、要转发出去的 |
| `OUTPUT` | 本机自己**发出**的包 |
| `POSTROUTING` | 包**即将离开网卡**（路由决策之后） |

一句话记忆：**进来的先过 PREROUTING；"给本机还是路过"在路由时决定；出去前过 POSTROUTING。**

```
                        进包
                          │
                     PREROUTING
                          │
                    [路由决策] ──┬──→ INPUT ──→ 本机进程
                          │      │
                          │      └──→ FORWARD ──┐
                          │                     │
        （DNAT 在这一步改目的地址）                │
                                                ▼
                            本机进程 ──→ OUTPUT ──────────┐
                                                          ▼
                                                   POSTROUTING
                                                          │
                              （MASQUERADE / SNAT 在这一步改源地址）
                                                          ▼
                                                        出包
```

### ② 四张表 = 同一个关卡上"管不同事"的规则集

| 表（table）   | 管什么                                | 常用链                               |
| ---------- | ---------------------------------- | --------------------------------- |
| **filter** | 放行 / 拦截（防火墙本职）                     | INPUT / FORWARD / OUTPUT          |
| **nat**    | **改写地址**（DNAT / SNAT / MASQUERADE） | PREROUTING / OUTPUT / POSTROUTING |
| mangle     | 改包的元信息（TTL、TOS 等）                  | 五条链都有                             |
| raw        | 连接跟踪之前的处理（极少用）                     | PREROUTING / OUTPUT               |

⚠ **`nat` 表不能用在 `INPUT` / `FORWARD` 链上**——这正是为什么端口映射的 **DNAT 一定挂在 `PREROUTING`**、出网的 **MASQUERADE 一定挂在 `POSTROUTING`**。

### ③ 规则怎么读

```
-A         DOCKER      -p tcp   --dport 8080   -j DNAT   --to-destination 172.17.0.2:80
│          │           │        │             │         │
│          │           │        │             │         └─ target 的参数（改成谁）
│          │           │        │             └─────────── target（做什么动作）
│          │           │        └───────────────────────── 匹配条件：目的端口 8080
│          │           └────────────────────────────────── 匹配条件：协议 tcp
│          └────────────────────────────────────────────── 挂到哪条链（DOCKER 是自定义链）
└───────────────────────────────────────────────────────── 追加一条规则（-A = append）
```

- **规则自上而下匹配，一旦匹配就执行 target 并结束这条链**（除非 target 是 `RETURN` 或跳到自定义链）。
- ⚠ **参数永远"紧跟在它所属的选项后面"——别按第几个词去数**：`-A` 后面**永远只有链名**（本例是 `DOCKER`，一个地址都没有），地址在最后的 `--to-destination` 后面。对照一句更眼熟的：`-A INPUT -s 1.2.3.4 -j DROP` —— `1.2.3.4` 看着在 `-A INPUT` 后面，其实它是 **`-s`**（source）的参数。
- **地址只会出现在两个地方**：① 匹配条件里 `-s 源地址` / `-d 目的地址`（"看这个包是谁发的 / 发给谁"）；② target 的参数里 `--to-destination` / `--to-source`（"把地址改成什么"）。
- 常用 target：`ACCEPT`（放行）、`DROP`（静默丢弃）、`REJECT`（拒绝并回一个错误）、`DNAT` / `SNAT` / `MASQUERADE`（改地址）、`RETURN`（返回上层链）。

### ④ 怎么看

```bash
iptables -t nat -L -n -v                 # 看 nat 表所有链和规则（-n 不解析域名，-v 带计数）
iptables -t nat -L DOCKER -n --line-numbers
```

Docker 会在 `nat` 表里插一条自己的 **`DOCKER` 自定义链**，由 `PREROUTING` / `OUTPUT` 跳进去——第五节那两条规则就在里面。

### ⑤ 和 nftables 的关系

`nftables` 是新一代框架（`nft` 命令），正在取代 iptables；多数发行版上 `iptables` 命令已经变成 nftables 的兼容前端。但**表 / 链 / 规则这套概念一脉相承**，面试说 iptables 就够了。

## 三、虚拟机三种网络模式

| 维度 | 桥接（Bridged） | NAT | 仅主机（Host-Only） |
|------|----------------|-----|--------------------|
| 虚拟交换机 | VMnet0（直接桥到物理网卡） | VMnet8 | VMnet1 |
| 谁发 IP | 物理局域网的 DHCP | VMware 虚拟 DHCP | VMware 虚拟 DHCP |
| 虚拟机 IP | 与宿主机**同网段**的局域网 IP | 私有网段（如 192.168.x.x） | 仅 VMnet1 私有网段 |
| 访问外网 | ✅ 直接走物理网卡 | ✅ 经宿主机 NAT | ❌ 不能 |
| 局域网其他机器访问 VM | ✅ | ❌（除非端口映射） | ❌ |
| 宿主机访问 VM | ✅ | ✅ | ✅ |
| 占用局域网 IP | 是（**可能冲突**） | 否 | 否 |
| 典型用途 | 要把 VM 当局域网里一台独立服务器 | 日常上网、**最常用** | 隔离实验 / 攻击靶机 |

### 桥接（Bridged）

- VM 通过虚拟网桥**直接接到宿主机物理网卡所在的物理网络**，在局域网里表现得像一台独立主机。
- IP 由**局域网 DHCP** 分配，和宿主机同网段。局域网里其他机器能直接访问它，它也能被 ping 到。
- 坑：**会占用局域网 IP**，公司/学校网络里可能没权限，或者撞 IP 冲突。

### NAT

- VMware 造 VMnet8（虚拟交换机）+ **虚拟 NAT 设备** + 虚拟 DHCP。
- VM 待在私有网段，宿主机扮演路由器做 NAT，所以 **VM 能上外网，但外网主动连不进来**（除非配端口映射）。
- 不占局域网 IP，宿主机 ↔ VM 双向可通，是最常用的模式。

### 仅主机（Host-Only）

- VMnet1，只有宿主机和 VM，**没有 NAT 设备 → 上不了外网**。
- 用于做纯隔离环境（实验、恶意样本分析、靶场）。

### 「虚拟机连不上网」怎么排查

1. **先看模式**：仅主机本来就上不了外网，别白排查。
2. **桥接**：`ip addr` 看有没有拿到**同网段** IP；没拿到查局域网 DHCP / IP 是否冲突。
3. **NAT**：查宿主机两个服务是否在跑——`VMware DHCP Service` 和 `VMware NAT Service`；再确认宿主机自身能上网、VMnet8 网卡没被禁用。
4. **DNS**：能 ping 通 IP 但打不开网页 → 十有八九是 DNS 没配好。

**第 2 条具体在查什么（桥接）**

桥接就是让虚拟机像一台新电脑插进同一个局域网。比如局域网是 `192.168.1.x`、网关 `192.168.1.1`，那虚拟机正常应该拿到 `192.168.1.25` 这种**同网段**地址（`ip addr` 里显示 `inet 192.168.1.25/24`，`/24` 表示属于 `192.168.1.0/24` 这个网段）。拿不到地址通常是：

- **DHCP 没分配成功**：路由器（DHCP 服务器）没响应，或该网段地址池用完了；
- 网桥、网卡或 DHCP 配置有误；
- **IP 冲突**：手动配的静态 IP 和局域网里另一台设备撞了。

所以"查 DHCP / IP 是否冲突"= 先确认路由器有没有成功发地址；若是手动配的 IP，再确认这个地址没被别的设备占用。

**第 3 条那两个服务分别干嘛**

| 服务 | 作用 | 它挂了会怎样 |
|------|------|------------|
| `VMware DHCP Service` | 给 VMnet8 里的虚拟机**自动分配 IP / 网关**等网络信息 | 虚拟机**拿不到 IP** |
| `VMware NAT Service` | 把虚拟机发往外网的数据**经宿主机转出去并做地址转换** | 虚拟机**有 IP，但上不了外网** |

路径大致是：`虚拟机 →（DHCP 分配虚拟 IP）→ VMnet8 虚拟网络 →（NAT 转发）→ 宿主机网络 → 外网`。

**Docker 的 bridge 模式，不就相当于虚拟机的 NAT 模式吗？**

**效果上很像**——两者常见的路径都是 `容器/虚拟机 → 私有虚拟网络 → NAT → 宿主机网络 → 外网`，而且要让外部访问里面的服务都得配端口映射（Docker 的 `-p` / VMware 的端口转发）。

但**不是同一个东西**，区别在**实现和管理者**：Docker bridge 由 Docker + Linux 网络功能管理；VMware NAT 由 VMware 的虚拟网络组件管理。

## 四、Docker 五种网络模式

| 模式 | 启动方式 | 独立 netns | 独立 IP | 能上外网 | 端口映射 `-p` | 性能 | 典型场景 |
|------|---------|-----------|---------|---------|--------------|------|---------|
| bridge（默认） | `--network bridge` | ✅ | ✅ 172.17.x.x | ✅（靠 SNAT） | ✅ 有效 | 中（多一层 NAT） | 单机多容器 |
| host | `--network host` | ❌ 共享宿主 | ❌ 用宿主 IP | ✅ | ❌ 无效（会警告） | 最高 | 高性能 / 需要大量端口 |
| none | `--network none` | ✅ | ❌ 只有 lo | ❌ | ❌ | — | 完全隔离 / 自定义网络底座 |
| container | `--network container:&lt;名字&gt;` | ❌ 共享指定容器 | ❌ 共享 | 跟随被共享容器 | ❌ | 高 | K8s Pod（pause 容器） |
| overlay | `--network &lt;overlay网络&gt;` | ✅ | ✅ | ✅（跨主机） | 集群管理 | 低（VXLAN 封装） | Swarm / 跨主机通信 |

### bridge（默认模式）

- 每个容器**一对 veth** 接到 `docker0`（一端在容器里叫 `eth0`，另一端在宿主机上），有独立 netns、独立 IP（`172.17.0.0/16`）。
- **同网桥容器可互通**（默认能互相 ping 通 IP），出外网靠 iptables `MASQUERADE`。
- ⚠ **默认的 `docker0` 不支持用容器名互相解析**；用 `docker network create` 自建 bridge 才有内嵌 DNS（`127.0.0.11`），容器名可以直接当域名互通。

**纠正一个常见口误**：说"每个容器一张 veth"是省略说法。veth 是**成对**的，准确说是**一对**——一端在容器里（`eth0`），一端在宿主机上接到网桥。容器里看不到宿主机那一端。

**为什么叫 bridge（桥）？**
不是说"把容器直接桥接到真实局域网"，而是因为 Docker 先在宿主机里建了一个**虚拟二层交换机**、把容器的网卡接到一起——这才是 "bridge" 指的那部分：

```
容器网卡 ─┐
          ├─ bridge（虚拟交换机，容器之间二层互通）
容器网卡 ─┘
             │
        宿主机转发 / NAT   ← 这是另外做的出网处理，不属于 bridge
             │
            外网
```

**"自建 bridge 才有内嵌 DNS"具体是什么意思**：默认 `docker0` 里容器之间**只能用 IP 通信**（如 `172.17.0.3`），Docker 不会把容器名 `web` 解析成这个 IP；自建网络里 Docker 提供内嵌 DNS（地址 `127.0.0.11`，**注意这是 DNS 服务本身的地址，不是别的容器的 IP**），于是可以直接用容器名。

```bash
docker network create mynet
docker run -d --name web --network mynet nginx
docker run --rm --network mynet busybox ping web   # 直接用名字 web 就能通
```

### host

- 容器**共享宿主机的 network namespace**，不分配 IP，直接用宿主机网卡。
- 性能最好（省掉网桥转发 + NAT），但**没有网络隔离、端口直接和宿主机抢**。
- 副作用：`-p` 会失效（Docker 会打警告，因为根本不需要映射）。
- **"宿主机"是谁，取决于 Docker 装在哪**：Docker 装在物理机上 → 容器直接用物理机网络；**Docker 装在虚拟机里 → 容器直接用的就是那台虚拟机的网络**。而虚拟机自己本来还是要靠桥接 / NAT 接入网络的——host 模式只是让容器**跳过 Docker 自己的 bridge/NAT**，直接共用所在机器的网络栈。
  - 例：Docker 跑在一台 IP 为 `192.168.1.50` 的虚拟机里，容器用 host 模式监听 8080 → 访问 `192.168.1.50:8080`。至于外部能不能访问到，还要看那台虚拟机自己是桥接（像局域网内一台设备、有自己的 IP）还是 NAT（要配端口转发）。

### none

- 容器里只有 `lo`，完全没网——需要自己接网络（常用作自定义网络的底层）。

### container

- **共享另一个已存在容器的 netns**：两个容器共用 IP 和端口空间，彼此用 `localhost` 就能通。
- **K8s 里 Pod 内多容器共享一个 IP，底层就是这个模式**（每个 Pod 一个 pause 容器持有网络）。
- **Pod 是什么**：K8s 里**最小的部署和调度单位**，可以理解成"共同住同一间网络小屋"的容器组——组内多容器**共用一个 IP**、用 `localhost` 互访，但**不能监听同一个端口**（会冲突）。Pod 由 K8s 创建和管理，里面的容器一起被调度到同一台机器上。

### overlay

- **跨主机**通信，用 VXLAN 把二层帧封装进 UDP 里传。
- 底层每个宿主机上仍然是一个 bridge，overlay 只是把多个宿主机上的 bridge 连成一个虚拟大二层网。
- **VXLAN 是什么**（Virtual Extensible LAN）：把**二层以太网帧整个"打包"进 UDP/IP 包里**，穿过现有 IP 网络运到对端宿主机再拆开——相当于"一条穿过 IP 网络的虚拟网线"。两台宿主机上的容器隔着普通 IP 网络，也能像连在同一个二层网络里一样通信。外层 IP 用来找到对端宿主机，内层仍保留原来的虚拟网络数据。

## 五、`-p 8080:80` 到底发生了什么（数据流）

> iptables 的表 / 链 / 规则怎么读见**第二节**。

### 方向一：外部 → 容器（DNAT）

```
外网/宿主机 → 宿主 eth0:8080
            → iptables PREROUTING → nat 表 DOCKER 链（DNAT 改写目的地址）
            → 经 docker0 转发
            → 容器 172.17.0.2:80
```

对应规则（目的地址被改写）：

```
-A DOCKER -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
```

**里面那个 `DOCKER` 链是什么**：它是 Docker 在 `nat` 表里建的**一组自己的规则清单**（不是网卡、也不是网线），专门用来处理容器网络和端口映射。`PREROUTING` 是"入口分流处"，`DOCKER` 链是 Docker 写在那里的分流规则；`-p 8080:80` 一配，规则就出现在这条链里。Docker 版本 / 防火墙后端不同，具体规则会有差异。

### 方向二：容器 → 外网（SNAT / MASQUERADE）

```
容器 → docker0 网关 172.17.0.1 → 宿主转发
     → iptables POSTROUTING（MASQUERADE 改写源地址为宿主 IP）
     → 宿主 eth0 → 外网
```

对应规则（源地址被改写为宿主 IP）：

```
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
```

### 方向三：容器 → 宿主机上的服务

- 容器里的 `127.0.0.1` 是**容器自己**，不是宿主机——这是最常见的坑。
- Mac / Windows 上 Docker Desktop 提供 `host.docker.internal` 指代宿主机。
- **Linux 原生 Docker 默认没有**，要加 `--add-host=host.docker.internal:host-gateway`（Docker 20.10+）。
- 或者直接用 `docker0` 网关 IP（`172.17.0.1`）去访问宿主机监听在 `0.0.0.0` 的服务。

## 六、面试话术 & 高频坑

**Q：容器为什么能上外网？**
→ 宿主机开了 `net.ipv4.ip_forward=1` 允许转发，出方向在 `POSTROUTING` 上挂了 `MASQUERADE` 规则，把容器的源 IP 换成宿主机 IP 再发出。**说白了就是宿主机当了一台 NAT 路由器。**

**Q：容器之间怎么通信？**
→ 同一个 bridge 上，两张 veth 插在同一台虚拟交换机上，二层直连就能通（同一网段）；不同网络之间要走网关路由。**必须用容器名解析时，要用自定义网络的 127.0.0.11 内嵌 DNS**，默认 docker0 只有 IP 没有名字。

**Q：bridge 和 host 网络哪个快？为什么？**
→ host 快。bridge 要经过「veth → docker0 网桥 → iptables NAT」好几跳，host 直接复用宿主机协议栈，省掉了这一整套虚拟化和 NAT 的开销；代价是没有网络隔离、端口会冲突。

**Q：K8s 里一个 Pod 的多个容器为什么共享一个 IP？**
→ Pod 内有一个 `pause` 容器先占住 network namespace，其他容器用 Docker 的 `container` 模式共享它的 netns，所以整个 Pod 共用一个 IP 和端口空间，容器间用 `localhost` 互访。

**Q：为什么我在容器里 ping 不通宿主机的服务？**
→ 先确认你访问的是 `127.0.0.1` 还是宿主机真实 IP。容器里的 loopback 是容器自己的，指向不了宿主机；要访问宿主得用 `172.17.0.1`（docker0 网关）或 `host.docker.internal`，而且宿主的服务必须监听在 `0.0.0.0` 而不是 `127.0.0.1`。

**Q：VMware 的 NAT 和 Docker 的 bridge 有什么区别？**
→ 机制上没区别，都是「虚拟网卡 → 虚拟交换机 → 宿主机 NAT」。区别只在被虚拟化的对象：一个是完整的虚拟机，一个是轻量容器；以及 Docker 的默认 bridge 额外提供端口映射和（自定义网络的）服务名解析。

**Q：一台机器能有多个公网 IP 吗？**
→ 能，服务器上很常见。三种形态：① **一张网卡绑多个公网 IP**（IDC 卖你一段 `/29`，全 `ip addr add` 到 `eth0` 上，就是"多 IP 服务器"）；② 多张网卡各绑一个（BGP 多线机房）。③ **云主机要特别注意**：ECS 的公网 IP（EIP）**通常不配在网卡上**，而是云平台网关设备上的一对一 **NAT 映射**——所以云主机里 `ip addr` 只看得到私网 IP，公网是"映射"上去的（就是第五节那个 DNAT）。多个出口 IP 时要指定"哪类流量走哪个源 IP"，靠**策略路由** `ip rule`。⚠ 但**反方向的常态才是多数**：一个公网 IP 靠**端口**承载多个服务、靠 **Host 头 / SNI** 承载多个域名；多台机器共用一个公网 IP 就是 **NAT**。
