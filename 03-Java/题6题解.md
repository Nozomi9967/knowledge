
### **用 `groupingBy` + 下游 `collectingAndThen` 排序截断即可；但百万级数据下 Stream 的装箱、比较器开销和全量排序会成为瓶颈，应改为分组内"Top-K 堆"或直接走数据库。**

  

## **Stream API 写法**

  

```java

Map<Long, List<Order>> top3PerUser = orders.stream()
    .collect(Collectors.groupingBy(
        Order::getUserId,
        Collectors.collectingAndThen(
            Collectors.toList(),
            list -> list.stream()
                .sorted(Comparator.comparing(Order::getCreateTime).reversed())
                .limit(3)
                .collect(Collectors.toList())
        )
    ));


```

  

要点：

- `groupingBy` 的下游用 `collectingAndThen(toList, …)`,先收齐同组再排序截断,逻辑清晰。

- 排序键 `createTime` 若可能为 `null`,用 `Comparator.comparing(Order::getCreateTime, Comparator.nullsLast(Comparator.naturalOrder())).reversed()` 防 NPE。

- 想要稳定有序的分组结果（如按 userId 排序），把外层 `groupingBy` 换成 `groupingBy(…, TreeMap::new, …)`。

  

一个更"Stream 味"的等价写法是用 `Collectors.toMap` + 合并函数，但可读性反而下降，不推荐。

  

## **百万级数据下的性能问题**

  

**1. 全量排序是最大开销。** 上面写法是"先分组、再对每组整体排序、再截断"。如果某个大 V 用户名下有 50 万条订单，仅为了取 3 条就排完整 50 万,时间复杂度 $O(n \log n)$,排序产生的临时数组和比较器调用都很贵。**正确做法是 Top-K**：维护一个容量为 3 的小顶堆（按 `createTime` 升序的 `PriorityQueue`），遍历一遍即可,复杂度降到 $O(n \log k)$,k=3 几乎等于 $O(n)$。

  

```java

Map<Long, List<Order>> top3 = orders.stream().collect(Collectors.groupingBy(
    Order::getUserId,
    Collector.of(
        () -> new PriorityQueue<Order>(3, Comparator.comparing(Order::getCreateTime)),
        (pq, o) -> {
            if (pq.size() < 3) pq.offer(o);
            else if (o.getCreateTime().compareTo(pq.peek().getCreateTime()) > 0) {
                pq.poll(); pq.offer(o);
            }
        },
        (a, b) -> { b.forEach(o -> {                       // 合并器(并行用)
            if (a.size() < 3) a.offer(o);
            else if (o.getCreateTime().compareTo(a.peek().getCreateTime()) > 0) {
                a.poll(); a.offer(o);
            }
        }); return a; },
        pq -> pq.stream()
                .sorted(Comparator.comparing(Order::getCreateTime).reversed())
                .collect(Collectors.toList())
    )
));


```


### 解析



百万订单、十万用户量级，这个写法实测能比 `sorted().limit(3)` 快一个数量级。

  

**2. 装箱与对象分配。** `Comparator.comparing(Order::getCreateTime)` 每次比较都会调用 getter,如果 `createTime` 是 `LocalDateTime`/`Date`,比较本身就比 `long` 慢得多。**优化**：把时间戳冗余成 `long createTimeMillis`,用 `Comparator.comparingLong(Order::getCreateTimeMillis).reversed()`,避免装箱、避免对象比较。

  

**3. `groupingBy` 默认走 `HashMap`,扩容成本不小。** 已知 userId 基数时，可以用三参数版本预分配：

  

```java

Collectors.groupingBy(Order::getUserId,

() -> new HashMap<>(expectedUsers * 4 / 3 + 1),

downstream);

```

  

**4. 并行流要慎用。** `orders.parallelStream()` 在分组场景下，下游 collector 必须是 `CONCURRENT` 且 `UNORDERED` 才真的能并行收集,上面的写法不是 `CONCURRENT`,实际是"并行切分 → 串行合并",合并阶段反而成瓶颈。如果一定要并行，用 `groupingByConcurrent` + `ConcurrentHashMap`,且只在 CPU 密集（比较代价高、数据量 ≥ 几百万）时才有正收益,IO 拿到的数据通常不值得开并行。

  

**5. 内存压力。** 百万 Order 全量装进 `List<Order>` 再 Stream,堆内存峰值很高,加上 `groupingBy` 中间还要再持有一份分组结果。若每个 Order 200B,百万就是 ~200MB,加上中间结构很容易触发 Full GC。

  

**6. 终极方案是不在 JVM 里做。** 这种"分组 Top-N"在数据库侧用窗口函数一句 SQL 就能搞定，且能利用 `(user_id, create_time desc)` 联合索引：

  

```sql

SELECT * FROM (

SELECT o.*, ROW_NUMBER() OVER (

PARTITION BY user_id ORDER BY create_time DESC

) AS rn

FROM orders o

) t WHERE rn <= 3;

```

  

百万行数据走索引扫描，比拉到应用层再 Stream 快几十倍，网络传输量也小得多。**经验法则**：能用 SQL/OLAP 解决的分组聚合，不要拉到 JVM 用 Stream 做,Stream API 的优势在表达力，不在大数据吞吐。

  

## **小结对照**

  

| 方案 | 复杂度 | 适用规模 | 备注 |

|---|---|---|---|

| `sorted().limit(3)` | $O(n \log n)$ /组 | < 10 万 | 写法最直观 |

| `PriorityQueue` Top-K | $O(n \log k)$ | 10 万 \~ 百万 | 一次遍历，省内存 |

| `parallelStream` + 并发 Collector | 取决于核数与比较代价 | 百万级 CPU 密集 | 慎用，需 benchmark |

| SQL `ROW_NUMBER()` 窗口函数 | 走索引 | 百万 \~ 亿级 | **首选**，下推到 DB |

  

如果你的 `Order` 已经在内存里（比如来自一次缓存批量加载），用 Top-K 堆的版本足够；如果是从 DB 查出再分组，那直接写 SQL 才是正解。
