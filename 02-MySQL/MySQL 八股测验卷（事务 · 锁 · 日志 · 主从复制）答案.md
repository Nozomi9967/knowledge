## MySQL 八股测验卷批卷结果

### 一、事务（共 3 题）

**第 1 题（ACID 保证机制）** — **6/10**

- ✅ 原子性→undo log、持久性→redo log 正确
- ⚠️ **隔离性只说 MVCC 不完整**：MySQL 的隔离性是由**锁 + MVCC 共同保证**的，没有提到锁机制
- ❌ **未回答核心问题**：题目专门问"为什么说一致性是最终目标，其他三个是为它服务的"，你的回答完全没有触及这一点。一致性的正确理解是：一致性本身没有专门的机制，而是通过原子性（事务不中断）、隔离性（不互相干扰）、持久性（修改不丢失）**共同约束**来保证业务层面的数据完整约束

**第 2 题（并行事务三大问题）** — **8/10**

- ✅ 三个问题的定义基本正确
- ⚠️ "严重程度排序"：你说从上到下越来越低（脏读>不可重复读>幻读），这个排序可以接受但建议补充一句理由——脏读读到的是未提交的脏数据，可能导致业务决策基于错误信息；不可重复读只是前后不一致但数据是已提交的；幻读影响行数统计但对单行数据本身无影响
- ❌ **用词不规范**："从上到下"指代不清晰，应该直接写结论

**第 3 题（隔离级别 + 幻读解决）** — **4/10**

- ✅ 四个隔离级别及其解决的问题基本正确
- ✅ 默认是可重复读，正确
- ❌ **说"可重复读解决不了幻读"是错误的**：InnoDB 的可重复读通过 MVCC 快照读 + Next-Key Lock，在**大部分场景**下是能解决幻读的，只有特定场景（快照读和当前读交替使用）才可能出现幻读，这也是为什么 InnoDB 敢把可重复读设为默认级别
[[为啥MVCC快照读也是解决幻读的方式？]]
- ❌ **"通过可重复读和间隙锁来解决问题（不确定）"**：这等于没说清楚。正确的答案是：
    - 方式一：**MVCC 快照读**——在 RR 下，整个事务使用同一个 Read View，快照读始终看到一致的数据快照
    - 方式二：**Next-Key Lock（临键锁）**——在当前读（SELECT...FOR UPDATE / UPDATE / DELETE）时，通过间隙锁锁定范围内不存在的记录，防止幻影行插入

### 二、MVCC 与 Read View（共 3 题）

**第 4 题（Read View 四个字段 + 隐藏列）** — **7/10**

- ✅ 四个字段的说明基本正确
- ⚠️ ==**第一个字段不叫 trx_id**，Read View 中对应的应该是 `creator_trx_id`（创建该 Read View 的事务 ID），你说的是"当前事务的事务 id"，意思对但专业名称不规范==
- ✅ 隐藏列 trx_id 和 roll_pointer 正确
- ✅ 可见性判断规则的三种情况描述正确

**第 5 题（Read View 创建时机）** — **3/10**

- ❌ 第一句"上一题已回答"——题目明确问的是创建时机的不同，上一题问的是字段含义，根本不是同一题，不能这样蒙混
- ✅ 读提交：每次执行 SQL 前创建，正确
- ⚠️ 可重复读：==你说"开启事务前"——**不准确**，应该是**事务中第一次执行查询时创建**，而不是"开启事务前"==
- ❌ "这个还真不太了解清晰"——这种话在考试中拿不到分，题目明确问"这个不同如何导致了它们的行为差异"，需要回答：==RC 每次查询都重新生成 Read View → 前后查询可能看到不同结果（不可重复读）；RR 整个事务用同一个 Read View → 前后查询结果一致==

**第 6 题（MVCC 为何不能完全避免幻读）** — **5/10**

==更准确的因果关系是：MVCC 给每个事务一个一致性快照，快照读永远看到同一个版本的数据，**在纯快照读的场景下 MVCC 其实避免了幻读**（RR 级别中两次 `SELECT` 的行数是一致的）。但当前读（`SELECT...FOR UPDATE`、`UPDATE`、`DELETE`）不走快照，走最新已提交版本，所以当前读天然绕过了 MVCC 的保护——**不是因为 MVCC"没加锁"而有漏洞，而是当前读的语义决定了 MVCC 管不到它**。==

> 事务A：select count(1) from stu where age>18 -- 记录数=3  
> 事务B：insert stu(id=1,age=19) -- 记录数=4  
> 事务A：select * from stu where age > 18 for update set gender = 男 -- 记录数=4 不一致

SQL 示例本身概念是对的，不过有一个细节问题：`SELECT ... FOR UPDATE SET gender = 男` 这不是合法 SQL 写法——`FOR UPDATE` 后面不能接 `SET`。应该拆成 `SELECT ... FOR UPDATE` 得到 4 行，再用 `UPDATE` 去改。虽然这不影响你对幻读现象的理解，但作为批卷来看写法上不够严谨。

### 三、锁机制（共 4 题）

- ❌ **未回答限制条件**：==此方式要求所有表都是支持事务的 InnoDB 引擎，MyISAM 等非事务表不能用此方式==

**第 8 题（表级锁）** — **4/10**

- ✅ 列出了四种表级锁，正确
- ❌ **共享表锁描述有严重错误**：你说"其它所有会话都不能对该表读写"——这是错误的！`LOCK TABLES ... READ`（共享表锁）时，**其他会话可以读但不能写**，只有当前会话也不能写。你的描述实际上是独占锁的行为
- ✅ MDL 读锁/写锁触发场景正确，阻塞链式反应正确
- ⚠️ **意向锁冲突关系错误**：==你说"意向锁和行级锁表级锁都是读读共享、读写冲突、写写冲突"——不准确。意向锁（IS/IX）彼此之间**不冲突**，但 IX 与 S（表级共享锁）冲突、IX 与 X（表级排他锁）冲突。实际上意向锁的兼容性矩阵是：==
    - ==IS 与任何锁都兼容（IS 只表示"我要对某行加共享锁"）==
    - ==IX 与 IS/IX 兼容，但与 S/X 不兼容==

[[意向锁与行级锁的冲突关系]]

**第 9 题（行级锁类型）** — **7/10**

- ✅ Record Lock、Gap Lock、Next-Key Lock 特点正确
- ⚠️ 插入意向锁：说到作用是"告知别人我要往这里插入记录了"——不够严谨。**插入意向锁是一种特殊的间隙锁**，在 INSERT 操作前生成，多个插入意向锁可以共存（不互斥），它解决的是插入并发问题而不是"告知"这么简单

## 总体评价与复习建议

**掌握较好的部分：**
