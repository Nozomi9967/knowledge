
[[答案-Java并发-多线程#4. 指令重排序]]

这里其实是两个层面的事情：synchronized 怎么从"机制上"保证有序性，以及 happens-before 规则怎么从"规范层面"把这种保证描述出来。

**1. 机制层面：内存屏障**

当线程进入 `synchronized` 块时执行的是 `monitorenter`，退出时执行 `monitorexit`（对应字节码层面的指令，底层会调用到操作系统的 mutex 锁）。JVM 在这两个操作前后会插入**内存屏障（Memory Barrier）**：

- 进入同步块（获取锁）时，相当于插入一个"读屏障"：会强制清空线程的工作内存中关于共享变量的缓存，之后的读操作都要重新从主内存加载——保证看到的是最新数据。
- 退出同步块（释放锁）时，相当于插入一个"写屏障"：会把这期间对共享变量的所有修改强制刷回主内存——保证修改对其他线程可见。

同时，内存屏障还会限制编译器和 CPU 的重排序：**屏障前面的指令不能被重排到屏障后面，屏障后面的指令不能被重排到屏障前面**。所以同步块内的代码，相对于"进入"和"退出"这两个点是不能跨越的，整体上对外表现为一个不可分割、按顺序执行的整体。

**2. 规则层面：happens-before**

happens-before 是 JMM 用来描述"什么时候一个线程的写操作对另一个线程的读操作一定可见、且顺序确定"的一套规则。其中和 synchronized 相关的是**监视器锁规则（Monitor Lock Rule）**：

> 对同一个锁，一个线程的 `unlock` 操作，happens-before 于后续另一个线程对这把锁的 `lock` 操作。

也就是说：

```
线程A：
synchronized(lock) {
    x = 1;        // 这里的写操作
}                 // unlock，触发写屏障，x=1 刷回主内存

线程B：
synchronized(lock) {  // lock，触发读屏障，重新从主内存读取
    System.out.println(x); // 一定能看到 x = 1
}
```

只要线程 A 的 `unlock` 在线程 B 的 `lock` 之前发生，那么 A 在同步块内的所有操作，对 B 来说都是"先发生"的——既保证了可见性（A 写的值 B 能看到），也保证了有序性（B 不会看到 A 同步块内代码被重排序后的"中间状态"，因为整个同步块对 B 来说是一个原子的整体）。

**简单总结一下因果关系**：

- 内存屏障是"硬件/JVM 层的具体手段"——靠它真正阻止了重排序、强制了缓存刷新；
- happens-before 是"语言规范层的描述"——告诉你只要满足"同一把锁的 unlock-lock"关系，就可以放心地认为前面线程的写对后面线程可见、且顺序有保证，不需要你关心底层屏障具体怎么插的。

所以可以理解为：synchronized 通过加锁/解锁触发底层的内存屏障，实现了"同步块内的代码对外表现为整体"的效果，而 happens-before 的监视器锁规则正是对这个效果的形式化描述，让你在写代码时有一个可以依赖的、可预测的顺序保证。
