## 一、线程基础（11 题）

### 1. Java 创建线程有哪几种方式？各有什么优缺点？

> **知识点跳转：** [[Java并发编程面试题]] · [[线程池]]

**参考答案**

常见四种。第一种继承 Thread 类，重写 run 方法，new 出来直接 start；第二种实现 Runnable 接口，把任务体交给 Thread 执行；第三种实现 Callable 接口，配合 FutureTask 使用，它能带返回值、能抛受检异常；第四种是交给线程池提交任务，生产上只用这一种。优缺点上，继承 Thread 的硬伤是 Java 单继承，继承了 Thread 就不能再继承别的类，而且任务和线程耦合在一起；实现 Runnable 没有这个限制，任务可以复用、可以提交给任意线程池，所以是标准写法；Callable 比 Runnable 多了返回值和异常处理能力；线程池则把线程的创建销毁复用起来，避免频繁创建的性能开销，还能统一管控并发数。

**追问参考答**

如果追问"为什么生产不用 new Thread"，答三点：每次 new 都要走内核创建线程，开销大；线程数无法控制，高并发时会把机器打满；无法统一管理生命周期和异常。所以要么用线程池，要么在 Java 21 之后用虚拟线程。

### 2. 实现 Runnable 接口和继承 Thread 类，在多个线程共享同一份资源时有什么区别？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

共享资源的场景下实现 Runnable 明显更好。因为 Runnable 定义的是任务，可以被多个 Thread 共享同一份状态：比如卖票，new 一个 Runnable 实例传给十个 Thread，这十个线程操作的是同一个 ticket 变量，天然共享，扣减是同一份数据。而继承 Thread 时，每个 Thread 子类实例自己就是线程，实例字段各有一份，要共享资源只能把资源声明成 static、或者靠外部传同一个对象进去，否则十个实例各卖各的票，一定超卖。所以只要涉及共享状态，实现 Runnable 是标准做法。

**追问参考答**

严格说共享资源的关键不在写法，而在于"多个线程是否拿到同一个对象引用"。Runnable 天然满足这一点，Thread 子类需要额外处理。另外不管哪种写法，共享变量的并发修改都得加锁或者用原子类，写法本身不解决线程安全问题。

### 3. Java 线程有哪几种状态？分别什么含义？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

六种。NEW 是创建了还没调 start；RUNNABLE 是调了 start 之后的状态，JVM 把操作系统的就绪和运行合并成这一种，所以看到 RUNNABLE 不代表一定在跑，可能在等 CPU；BLOCKED 是在等 synchronized 的锁；WAITING 是调用 wait、join、park 之后无限期等待，必须别人唤醒；TIMED_WAITING 是带超时的等待，比如 sleep、带时间的 wait 和 join；TERMINATED 是 run 方法跑完或者异常退出。这里有个容易错的点：BLOCKED 只对应 synchronized 的锁竞争，Lock 接口的等待走的是 park，属于 WAITING 或者 TIMED_WAITING，不算 BLOCKED。

**追问参考答**

线上排查时线程状态很关键：大量 BLOCKED 说明锁竞争严重，去看 jstack 里"waiting to lock"指向哪个对象；大量 WAITING 可能是线程池空闲，也可能是死锁或者误用 wait；大量 RUNNABLE 但 CPU 不高，说明在等 IO 或者被阻塞在 native 调用。

### 4. 如何安全地停止一个线程？Thread.stop() 为什么不推荐？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

三种主流做法。第一种设一个 volatile 的停止标志位，线程主循环里检查它，为 true 就优雅退出，这是最推荐的；第二种调 interrupt 中断，配合 isInterrupted 判断或者捕获 InterruptedException；第三种交给线程池，用 shutdown 等任务跑完，或者 shutdownNow 中断工作线程。stop 废弃是因为太暴力：它直接终止线程并释放该线程持有的所有锁，可能让对象停在中间状态，别的线程接着用这个对象就出错；而且它不保证 finally 块执行完，清理逻辑可能被跳过，资源泄漏。同理 suspend 和 resume 也废弃了，suspend 挂起时不释放锁，极容易死锁。

**追问参考答**

标志位写法的关键在于标志位要 volatile，否则主线程改了值、工作线程可能看不到，一直循环。interrupt 写法的关键在于捕获 InterruptedException 后要恢复中断标志或者直接退出，别吞掉异常继续跑。

### 5. 调用 interrupt() 后会发生什么？请分情况说明。

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

interrupt 本身只是把线程的中断标志位置为 true，具体效果取决于线程当时在干什么。第一种，线程阻塞在 sleep、wait、join 上，会立刻抛 InterruptedException，同时中断标志位被清除，所以得在 catch 里决定是退出还是恢复标志；第二种，线程阻塞在 NIO 的 InterruptibleChannel 上，通道被关闭、标志位被置位，抛 ClosedByInterruptException；第三种，线程阻塞在 Selector 的 select 上，select 立即返回；第四种，线程正在正常运行，标志位只是被置为 true，代码得自己用 isInterrupted 检查，不然什么都不会发生。另外，对一个已经终止的线程调 interrupt 没有任何效果。

**追问参考答**

isInterrupted 和 Thread.interrupted 的区别常被追问：前者是实例方法，只读标志位；后者是静态方法，读完之后会把标志位清掉。所以 catch 到 InterruptedException 后如果还想让上层知道被中断了，要手动再调一次 Thread.currentThread().interrupt() 恢复标志。

### 6. sleep() 和 wait() 有什么区别？sleep 会释放 CPU 吗？会释放锁吗？

> **知识点跳转：** [[Java并发编程面试题]] · [[Condition 详解]]

**参考答案**

区别要抓六点：sleep 属于 Thread 类，wait 属于 Object；sleep 不释放锁，抱着锁睡，wait 会释放锁；sleep 在任何地方都能调，wait 必须在 synchronized 块里；sleep 到点自己醒，wait 要靠 notify 或者超时；用途上 sleep 只是暂停一会儿，wait 是线程间协作的手段。关于释放资源，sleep 会释放 CPU 但绝不会释放锁，所以它只是把 CPU 让给别的就绪线程，拿着锁的线程照样进不来；wait 是既释放 CPU 又释放锁，别人才能进来改条件、发通知。这个区别是二者最本质的地方。

**追问参考答**

为什么 sleep 不释放锁？因为它的语义只是"我歇一会儿"，不涉及对象监视器的让出；而 wait 的语义是"我在等一个条件成立，让别人来改"，所以必须先让出锁，否则别人进不来、条件永远不变，就死锁了。

### 7. BLOCKED 和 WAITING 状态有什么区别？为什么这两种状态都不消耗 CPU？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

区别在成因和唤醒方式。BLOCKED 是在等 synchronized 的锁，锁一释放由 JVM 自动把你转入锁竞争，不需要别人显式叫你；WAITING 是主动调用 wait、join、park 之后的无限期等待，必须等别人 notify、unpark 或者目标线程结束才能醒。都不消耗 CPU 的原因是它们已经从操作系统的就绪队列里出去了，进入等待队列，调度器根本不会给它们分配时间片；CPU 只在就绪态的线程之间轮转，阻塞态的线程是被挂起的，等事件发生了内核才把它唤醒放回就绪队列。所以一个线程再多，只要都阻塞着，CPU 占用也可以接近零。

**追问参考答**

这条能延伸出一个常见面试题：为什么大量线程阻塞不影响性能？因为阻塞的线程不占 CPU，占的是内存里的栈。真正怕的是大量线程频繁唤醒和切换，那种上下文切换开销才吃得厉害。所以"线程多"和"CPU 高"不是一回事，得看它们处于什么状态。

### 8. notify() 和 notifyAll() 有什么区别？为什么推荐用 notifyAll？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

notify 随机唤醒一个在该对象上等待的线程，具体叫醒哪个由 JVM 实现决定，程序员控制不了；notifyAll 唤醒所有等待线程，让它们一起去竞争锁。生产代码推荐 notifyAll，原因是唤醒错人会死锁：生产者消费者模型里，队列满了可能有多个生产者在 wait，消费者取走一个后调 notify，有可能叫醒的还是个生产者，它一看队列还是满的又 wait 回去，而消费者也在等新数据，结果所有人都睡着，程序卡死。notifyAll 让所有等待者都参与竞争，谁的条件满足谁往下走，安全但有一次全唤醒的开销。要既精确又高效，就用 Condition，一个锁上开多个条件队列。

**追问参考答**

notify 什么时候能用？只有一个等待者、或者所有等待者的条件完全相同时才勉强安全，比如单生产单消费。但即便如此，代码演进后加了线程就容易踩坑，所以工程上默认写 notifyAll，需要精确唤醒就上 Condition。

### 9. 线程间通信有哪些方式？请至少列举四种。

> **知识点跳转：** [[Java并发编程面试题]] · [[阻塞队列详解]]

**参考答案**

四种常用。第一种 wait/notify 配合 synchronized，最基础的对象监视器方式，靠等待队列传递信号；第二种 Condition 配合 ReentrantLock，一个锁能开多个条件队列，可以精确唤醒某一类等待者；第三种阻塞队列 BlockingQueue，生产者 put、消费者 take，队列满和空时的等待唤醒都封装好了，是生产消费模型最省事的写法；第四种是 CountDownLatch、CyclicBarrier、Semaphore 这些同步工具，它们做的是线程间协调而不是传数据，比如等一批任务完成、让一批线程同时出发、控制同时访问的线程数。另外还有 volatile 共享标志位、管道流 PipedInputStream，但用得少。

**追问参考答**

面试常追问"哪种最好"，答案看场景：传数据用阻塞队列；等任务完成用 CountDownLatch；需要精确唤醒（比如生产者只叫消费者）用 Condition；最基础的教学演示用 wait/notify。别一上来就说 wait/notify 最好，那是底层原语，封装好的工具更不容易写错。

### 10. wait() 为什么必须在 synchronized 块中调用？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

两个层面的原因。表层原因是 wait 的语义就是"释放当前持有的监视器锁并进入等待"，前提是你得先持有这把锁，没有锁可释放就没有意义，JVM 会直接抛 IllegalMonitorStateException。深层原因是避免丢失通知的竞态：如果检查条件和调用 wait 之间有间隙，别的线程可能正好在这个间隙里改变了条件并发出了 notify，这时候你还没进入等待，通知就丢了，等你真正 wait 下去就再也没人叫醒你。把条件判断和 wait 放进同一个 synchronized 块，检查条件和进入等待是原子的，通知不会丢。

**追问参考答**

这也是"为什么用 while 而不是 if"的同一个逻辑起点：wait 醒来之后条件可能又被别人改了，所以必须重新检查；而检查和等待必须原子，所以都在锁内。两题连着问的情况很常见，答案要能串起来。

### 11. Java 21 的虚拟线程是什么？它和平台线程、Go 的 goroutine 有什么区别？

> **知识点跳转：** [[Java并发编程面试题]] · [[线程池]]

**参考答案**

平台线程就是传统 Java 线程，和操作系统线程一一对应，创建销毁都要内核态介入，每个线程栈大概占 1MB，几千个就到极限了。虚拟线程是 Java 21 正式引入的，由 JVM 调度而不是操作系统，本质是用户态的轻量级线程，一个载体线程上能挂载成千上万个虚拟线程。关键机制是虚拟线程遇到阻塞 IO 时会把载体线程让出来，自己挂起在堆里，等 IO 就绪再被调度回去，所以它的"阻塞"几乎不占资源，特别适合 IO 密集型的高并发，比如每请求一线程的模型。和 goroutine 比，两者调度模型相似，都是 M 比 N 的用户态调度；区别是 goroutine 用语言内置的 channel 通信、栈可动态伸缩，虚拟线程完全兼容现有 Thread API、老代码可以直接跑，但虚拟线程不适合 CPU 密集型任务，也不该用线程池去池化它。

**追问参考答**

虚拟线程为什么不能池化？因为它本身就极轻量，创建成本接近 new 一个对象，池化反而增加了排队和管理开销，官方明确建议直接 new。另外要注意虚拟线程里调用 synchronized 包住的阻塞操作会钉住载体线程，影响吞吐，JDK 21 之后的版本在逐步优化这一点。

## 二、JMM 与可见性（4 题）

### 12. JMM（Java 内存模型）是什么？并发编程的三大特性是哪三个？

> **知识点跳转：** [[Java并发编程面试题]] · [[内存屏障和happens-before]]

**参考答案**

JMM 就是 Java 内存模型，是官方定的一套规范，用来约束多线程共享变量的读写，保证并发安全。它规定了两层结构：所有共享变量都住在主内存里，每个线程操作的是自己工作内存里的副本，不能直接改主内存。并发编程的三大特性是原子性、可见性、有序性。原子性是同一时刻只能有一个线程改这个数据，靠锁或者 CAS 保证；可见性是线程改完的数据要及时刷回主内存让其他线程看到，靠 volatile、synchronized、Lock 保证；有序性是禁止指令重排序，代码写在前面的不能被编译器或 CPU 乱序执行，靠 happens-before 规则和内存屏障保证。

**追问参考答**

有序性的定义最容易说错，它不是"观察到其他线程按顺序执行"，而是"禁止编译器和 CPU 对本线程内的指令重排"。另外要补一句：工作内存是 JMM 的抽象概念，CPU 缓存是物理实现，两者是抽象与实现的关系，说"工作内存约等于 CPU 缓存"可以，但要清楚这只是简化类比。

### 13. 什么是缓存一致性？为什么会出现可见性问题？

> **知识点跳转：** [[Java并发编程面试题]]

**参考答案**

缓存一致性指的是主内存的数据和各个线程工作内存里的副本不一致的问题。为什么会出现？因为 JMM 规定线程不能直接操作主内存，必须先把共享变量读进自己的工作内存，改完先写回工作内存，什么时候刷回主内存是不确定的。这就产生了一个窗口：线程 A 改了变量但还没刷回主内存，线程 B 去主内存读，拿到的还是旧值，这就是可见性问题。volatile 的作用就是强制读写直通主内存，配合缓存一致性协议和内存屏障把这个窗口关掉。

**追问参考答**

追问"底层硬件怎么保证"就答缓存一致性协议，比如 MESI，它靠总线嗅探和缓存行状态机让各核的缓存保持同步；JMM 的内存屏障则是在指令层面约束重排序，两者一个管硬件同步、一个管编译器优化，是两层保障。

### 14. happens-before 规则有哪些？它解决什么问题？

> **知识点跳转：** [[内存屏障和happens-before]]

**参考答案**

happens-before 是 JMM 里两个操作之间的偏序关系，解决的是"没有锁的时候，多线程怎么保证有序性和可见性"这个问题。含义是：如果 A happens-before B，那 A 的执行结果对 B 可见，而且 A 不能被重排到 B 后面。要强调这是逻辑保证，不是物理时间的先后，本质是禁止编译器、CPU 重排序。核心规则有四条：程序顺序规则，同一个线程内前面的代码 happens-before 后面的；volatile 规则，对 volatile 变量的写 happens-before 后面所有对它的读；锁规则，解锁 happens-before 后面再进来的加锁；传递性，A 先于 B、B 先于 C，则 A 先于 C。

**追问参考答**

面试常拿它解释一个现象：为什么一个线程把对象赋值给 volatile 变量后，另一个线程读到这个引用就能看到对象内部的所有字段？因为 volatile 写之前的普通写 happens-before 这次写，这次写又 happens-before 后续的读，靠传递性把内部的普通字段也一起保证了可见性。这就是 DCL 单例要加 volatile 的理论依据。

### 15. 内存屏障是什么？有哪几类？volatile 的读写分别插入什么屏障？

> **知识点跳转：** [[内存屏障和happens-before]] · [[volatile 关键字详解]]

**参考答案**

内存屏障是 CPU 或编译器提供的一种约束指令，作用是禁止屏障前后的指令越过它乱序执行，本质是拦重排序。一共有四类：LoadLoad、StoreStore、LoadStore、StoreLoad，命名规则就是"什么操作不能被重排到什么操作后面"，比如 LoadLoad 就是屏障前的读不能重排到屏障后的读之后。volatile 的语义就靠它：volatile 写的时候，前面插 StoreStore、后面插 StoreLoad；volatile 读的时候，后面插 LoadLoad 和 LoadStore。效果就是写之前把该写的普通写都写完，写之后的操作不能跑到写前面去；读之后的操作不能跑到读前面去，读到的必须是最新值。

**追问参考答**

四类里 StoreLoad 最重，因为它要同时挡住写和读两个方向，通常用全屏障或者 lock 前缀指令实现，开销最大。所以 volatile 写的成本比读高，只读不改的共享变量用 volatile 相对便宜，频繁写的场景要谨慎。

## 三、synchronized（5 题）

### 16. synchronized 有哪几种用法？锁的对象分别是谁？

> **知识点跳转：** [[synchronized 关键字详解]]

**参考答案**

三种用法。第一种修饰实例方法，锁的是当前实例对象也就是 this；第二种修饰静态方法，锁的是当前类的 Class 对象，因为静态资源属于类级别、所有实例共享；第三种修饰代码块，锁的是括号里指定的那个对象，可以是任意对象，不限于实例或 Class。第三种最灵活，也是缩小锁粒度、控制并发范围的主要手段，比如只锁住需要保护的那一小段，而不是整个方法。

**追问参考答**

有个常见陷阱：synchronized 修饰静态方法和修饰实例方法用的是两把不同的锁，前者是 Class 对象、后者是 this。所以一个静态同步方法和一个实例同步方法可以同时执行，互不影响，很多人以为"加了 synchronized 就互斥"是错的。

### 17. synchronized 的底层原理是什么？

> **知识点跳转：** [[synchronized 关键字详解]]

**参考答案**

底层是 Monitor，也就是监视器锁，由 JVM 的 ObjectMonitor 实现。同步代码块编译成字节码后，前后会有 monitorenter 和 monitorexit 两条指令。每个对象都关联一个 Monitor，它记录着当前是哪个线程持有锁、重入了几次、还有哪些线程在等待。加锁流程是这样：monitorenter 时如果 Monitor 的计数器是 0，当前线程拿到锁、计数变 1；如果锁已经被自己持有，计数加一，这就是可重入；如果被别的线程占着，就进阻塞队列等待。monitorexit 时计数减一，减到 0 才真正释放并唤醒等待的线程。要注意为了保证异常时也能释放，编译器会生成两个 monitorexit，一个正常路径、一个异常路径。

**追问参考答**

Monitor 底层依赖操作系统的 mutex，所以重量级锁的加解锁要陷入内核态，开销大。JDK 1.6 之后引入锁升级就是为了让大部分无竞争和轻竞争的场合绕开这个内核调用。

### 18. synchronized 的锁升级过程是怎样的？

> **知识点跳转：** [[synchronized 关键字详解]]

**参考答案**

JDK 1.6 之前 synchronized 只有重量级锁，一上来就挂起线程走系统调用，性能很差。1.6 之后引入锁升级，链路是无锁、偏向锁、轻量级锁、重量级锁，越往后越重。触发条件是这样：对象刚 new 出来是无锁状态；第一个线程进入同步块时升级为偏向锁，对象头 Mark Word 里记这个线程 ID，它重入时直接判断 ID 是不是自己，不需要 CAS 也不需要加锁；第二个线程来竞争时，偏向锁撤销、升级为轻量级锁，线程在自己栈帧里建锁记录 Lock Record，然后 CAS 把对象头 Mark Word 指向这个锁记录，成功就拿锁，失败就自旋重试；自旋到一定次数还拿不到，说明竞争激烈，升级为重量级锁，挂起线程走操作系统 mutex。

**追问参考答**

两个细节容易错：一是偏向锁重入是直接比较线程 ID，不用 CAS，CAS 是轻量级锁阶段的事；二是对象头的字段叫 Mark Word，不是 Mark Work。升级是单向的，重量级锁不会退回轻量级，偏向锁撤销后也不会再偏回去。

### 19. JDK 15 为什么默认废弃偏向锁？

> **知识点跳转：** [[synchronized 关键字详解]]

**参考答案**

偏向锁优化的场景是"同一个线程反复进入、完全没有竞争"，靠把线程 ID 写进对象头，省掉后续每次的 CAS。但它有代价：撤销偏向锁必须等到安全点做 STW，暂停所有线程、检查对象头的偏向记录才能改，这个成本不低。JDK 15 默认禁用（JEP 374）的原因是，现代应用的锁竞争比早年想象中普遍，偏向锁省下的那点开销收益越来越小，反而要承担撤销时的 STW 开销；同时偏向锁让 HotSpot 里的锁实现变得非常复杂，维护成本高。禁掉之后 synchronized 直接从轻量级锁起步。

**追问参考答**

禁用不代表锁升级链路没了，轻量级锁到重量级锁的路径还在。如果确认自己的应用是单线程反复进同步块、几乎无竞争，可以手动开回来，但收益通常不值那个复杂度，官方也建议别开。

### 20. synchronized 和 ReentrantLock 有什么区别？

> **知识点跳转：** [[synchronized 关键字详解]] · [[ReentrantLock详解]]

**参考答案**

从底层和功能两个维度说。底层上，synchronized 是 JVM 的内置锁，靠 Monitor 实现，编译成 monitorenter 和 monitorexit；ReentrantLock 是 Java 层面基于 AQS 实现的，用 CAS 加一个双向队列管理等待线程。功能上，两者都是可重入的，这点要强调，可重入不是 ReentrantLock 独有；但 ReentrantLock 多了几个能力：可中断，lockInterruptibly 能响应中断；可超时，tryLock 可以限时等锁；可公平，构造时传 fair 为 true 就排队；多条件变量，一个锁上能开多个 Condition 队列，比 synchronized 单一的 wait/notify 队列灵活；锁的范围也更自由，可以跨方法 lock 再 unlock。代价是必须手动 unlock，而且一定要放 finally，否则容易死锁。所以原则是能用 synchronized 就用，确实需要那些高级特性才换。

**追问参考答**

追问"公平性"：synchronized 只有非公平；ReentrantLock 默认也是非公平，构造传 true 才公平。追问"性能"：现在两者性能差距不大，synchronized 有锁升级，除非是高竞争或者需要高级特性，否则没必要为了性能换。

## 四、volatile（2 题）

### 21. volatile 能保证什么？不能保证什么？为什么不能保证原子性？

> **知识点跳转：** [[volatile 关键字详解]]

**参考答案**

volatile 能保证可见性和有序性，不能保证原子性。可见性是线程改了 volatile 变量会立刻写回主内存，其他线程立刻能看到；有序性是用内存屏障禁止指令重排序。为什么不能保证原子性？因为 volatile 只提供读写屏障，它不提供互斥，像 count++ 这种操作本质是读、加、写三步，volatile 只保证每一步各自可见，不保证这三步连续。两个线程可能同时读到旧值，各自加一再写回，后写的把先写的覆盖掉，就丢了更新。

**追问参考答**

要让 count++ 原子，得用 AtomicInteger 的 CAS，或者加锁。另外有个常见误区：volatile 不能保证原子性不是因为它"只能修饰变量"，而是因为它不建立互斥关系——这两者是不同层面的原因，说错会被追着问。

### 22. volatile 的底层实现是什么？

> **知识点跳转：** [[volatile 关键字详解]] · [[内存屏障和happens-before]]

**参考答案**

底层靠内存屏障。volatile 写的时候，在前插一个 StoreStore 屏障、在后插一个 StoreLoad 屏障；volatile 读的时候，在后面插 LoadLoad 和 LoadStore 屏障。作用是禁止屏障前后的指令越过它重排。概括一下：volatile 写，保证写之前该写的普通写都完成了，写之后的所有操作不能重排到这个写之前；volatile 读，保证读之后的所有操作不能重排到这个读之前，读到的都是最新值。另外在汇编层面，x86 上 volatile 写会生成带 lock 前缀的指令，它会锁总线或者锁缓存行，强制把写缓冲刷出去并让其他核的缓存失效，这是可见性的硬件保障。

**追问参考答**

为什么读比写便宜？因为写的屏障里包含 StoreLoad 这个最重的全屏障，而读只需要 LoadLoad 和 LoadStore。所以一个只被读、很少被写的共享变量用 volatile 成本很低，反过来频繁写的场景就要斟酌，可能要换成别的方案。
