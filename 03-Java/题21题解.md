### **`@Async` 本质是 Spring AOP 把方法调用丢到 `TaskExecutor` 的另一个线程去执行，因此主线程拿到的只是一个"发射后不管"的返回值，异常和 ThreadLocal 都留在了子线程里，必须靠 `Future`/`CompletableFuture` 或 `AsyncUncaughtExceptionHandler` 显式承接。**

  

## **实现原理**

  

`@Async` 的能力来自 `@EnableAsync`，它会注册一个 `AsyncAnnotationBeanPostProcessor`，扫描到带 `@Async` 的 Bean 后，用 AOP 给它生成一个代理。核心拦截器是 `AsyncExecutionInterceptor`，它的 `invoke` 逻辑非常简单：**拿到目标方法调用，包装成一个 `Callable`，提交给 `TaskExecutor`（默认是 `SimpleAsyncTaskExecutor`，也可以配 `ThreadPoolTaskExecutor`），然后立即返回**。

  

这就带来了两个关键后果：

  

**第一，调用线程和执行线程完全是两个线程。** 主线程走到 `@Async` 方法那一刻，实际上只是往线程池里丢了个任务，然后拿着返回值（`void`、`Future`、`CompletableFuture`）继续往下走。真正的业务逻辑在池里的工作线程执行。

  

**第二，异常和 ThreadLocal 都是线程私有的。** ThreadLocal 底层是 `Thread.threadLocals`，换了线程当然拿不到；异常抛出后是在子线程栈上，主线程的 `try-catch` 根本捕获不到——它捕获的只是"提交任务"这个动作，而不是任务本身的执行。

  

还有一个和上一题类似的坑：`@Async` 也是基于代理的，**同类自调用同样失效**，因为 `this.xxx()` 绕过了 `AsyncExecutionInterceptor`。

  

## **ThreadLocal 不共享的问题**

  

主线程里塞进 `ThreadLocal` 的东西（比如 `RequestContextHolder` 里的请求上下文、`SecurityContextHolder` 里的登录信息、MDC 里的 traceId），子线程默认全都拿不到。常见的解决方案有三种：

  

一是用 `TransmittableThreadLocal`（阿里 TTL）替换普通 `ThreadLocal`，它专门解决线程池场景下的上下文传递。二是配置 `TaskDecorator`，在提交任务前把主线程的上下文抓一份快照，在子线程执行前 restore 进去：

  

```java

executor.setTaskDecorator(runnable -> {

RequestAttributes ctx = RequestContextHolder.getRequestAttributes();

Map<String, String> mdc = MDC.getCopyOfContextMap();

return () -> {

try {

RequestContextHolder.setRequestAttributes(ctx);

if (mdc != null) MDC.setContextMap(mdc);

runnable.run();

} finally {

RequestContextHolder.resetRequestAttributes();

MDC.clear();

}

};

});

```

  

三是针对 Spring Security，开启 `MODE_INHERITABLETHREADLOCAL`，但这个只对"新建线程"生效，对复用线程的线程池并不可靠。

  

## **正确的异常处理方式**

  

**方式一：返回值用 `Future` 或 `CompletableFuture`，让调用方主动 `get()`。**

  

如果 `@Async` 方法返回 `void`，异常抛出后直接被吞掉，主线程无从感知。改成返回 `CompletableFuture<T>`：

  

```java

@Async

public CompletableFuture<Order> loadOrder(Long id) {

// ...可能抛异常

return CompletableFuture.completedFuture(order);

}

```

  

调用方通过 `future.get()` 会抛出 `ExecutionException`，里面包着真正的业务异常；或者用 `whenComplete`、`exceptionally` 异步处理。这是**返回值型异步方法**的标准做法。

  

**方式二：`void` 方法通过 `AsyncUncaughtExceptionHandler` 兜底。**

  

`void` 返回类型没有 `Future` 可拿，Spring 提供了专门的处理钩子。实现 `AsyncConfigurer`：

  

```java

@Configuration

@EnableAsync

public class AsyncConfig implements AsyncConfigurer {

  

@Override

public Executor getAsyncExecutor() {

ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();

// 参数配置...

executor.initialize();

return executor;

}

  

@Override

public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {

return (ex, method, params) -> {

log.error("异步方法 {} 执行异常，参数 {}", method.getName(), params, ex);

// 告警、落库、发消息等

};

}

}

```

  

**注意**：`AsyncUncaughtExceptionHandler` **只对返回 `void` 的方法生效**，对返回 `Future` 的方法不会调用（因为异常已经被塞进 `Future` 里了，Spring 认为你自己会处理）。

  

**方式三：在异步方法内部自己 `try-catch` 兜底。**

  

最朴素但也最可控的方式：既然主线程接不住，那就在 `@Async` 方法里把该记的日志记了、该发的告警发了、该做的补偿做了，别让异常裸奔到线程池。适合那种"通知类"、"日志类"的轻量异步任务。

  

## **面试口述要点**

  

面试口述时可以按这个顺序讲：**先讲 `@Async` 的原理——AOP 代理 + 线程池提交，说清楚"提交-返回"和"实际执行"是两个线程；然后自然引出两个副作用——异常和 ThreadLocal 都是线程私有的；接着分返回值型（`CompletableFuture`）和 void 型（`AsyncUncaughtExceptionHandler`）两种情况给出异常处理方案；最后补一句坑：自调用失效、`void` 方法 handler 才生效、线程池 ThreadLocal 要用 TTL 或 TaskDecorator 传递。** 这样答基本能覆盖考官想听的所有点。
