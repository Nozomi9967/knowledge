### 1. JMM 是什么？它要解决多线程下的哪三个问题？这三个问题为什么也是「Java 线程安全」的三个方面？

> **问题描述**
> 面试高频基础题，常作为并发开场。
>
> 建议回答顺序：先一句话定义 JMM → 再分点讲三问题（可见性、原子性、有序性） → 最后点出"三问题 = 线程安全三要素"的关系。

> [!abstract]- 参考答案
> JMM（Java Memory Model）是规定多线程环境下线程如何访问共享变量的一套规则，核心解决三个问题（也是 Java 线程安全的三个方面）：
>
> - **可见性**：一个线程修改了共享变量，其他线程能不能立刻看到。由于 CPU 缓存的存在，线程先把主内存变量读到工作内存（缓存），修改后可能没及时写回主内存，导致别的线程读到旧值。`volatile` 保证写后立即刷回主内存，并使其他线程缓存失效；`synchronized` 也能保证可见性（释放锁时会把修改刷回主内存）。
> - **原子性**：同一时刻只能有一个线程对数据进行操作，互斥访问。一个操作要么全部执行完，要么完全不执行，中间不会被打断。例如 `i++` 实际是"读-改-写"三步，多线程下会出错。Java 中用 `atomic` 包（如 AtomicInteger，基于 CAS）和 `synchronized` 关键字保证。
> - **有序性**：观察其他线程的指令执行顺序时，由于指令重排序（编译器/CPU 优化重排、CPU 指令级并行重排、内存系统重排），结果一般是杂乱无序的。代码执行顺序可能因编译器/CPU 重排序而和编写顺序不一致。单线程不影响结果，但多线程下可能导致另一个线程看到"半初始化"的对象（典型的"指令重排+发布对象"问题）。`volatile` 通过内存屏障禁止不合理的重排序；`synchronized` 通过加锁使临界区内代码对外表现为一个整体，结合 happens-before 规则保证有序性。Java 通过 **happens-before 原则**来约束和保证有序性。

### 2. 什么是可见性问题？现代 CPU 多级缓存为什么会造成可见性问题？`volatile` 是如何解决可见性的？

> **问题描述**
> 第 1 题"可见性"的展开追问，常和 volatile 一起考察。
>
> 建议回答顺序：举一个"线程 A 改了 flag，线程 B 看不到"的例子 → 解释 CPU 缓存层级（工作内存 ↔ 主内存）→ 讲 volatile 的两条机制（写后立即刷主内存 + 缓存行失效）。

> [!abstract]- 参考答案
> 可见性问题：线程 A 修改了共享变量后，线程 B 不能立刻看到最新值，看到的还是旧值。
>
> 原因：现代 CPU 都有多级缓存，线程操作变量时会先把主内存的值读到自己的工作内存（CPU 缓存）中进行操作，修改后不一定立刻写回主内存，导致其他线程读到的还是主内存中的旧值。
>
> volatile 的解决方式：被 volatile 修饰的变量，写操作会立即刷新到主内存，同时会让其他线程缓存了该变量的缓存行失效，强制其他线程必须重新从主内存读取最新值，从而保证可见性。

### 3. 为什么 `i++` 不是原子操作？在多线程下不加锁会出什么问题？有哪些解决方式？

> **问题描述**
> 经典原子性反例题，常用卖票、`HashMap.size()` 累加等场景做引子。
>
> 建议回答顺序：拆三步（读 → 改 → 写）→ 用"丢失更新"举例（A、B 都读到 10，都写 11）→ 给两种方案：synchronized/Lock vs AtomicInteger(CAS)。

> [!abstract]- 参考答案
> `i++` 实际上分为三步：① 读取 i 的当前值；② 将该值加 1；③ 把结果写回 i。
>
> 在多线程下，假设线程 A 读到 i=10，还没写回时线程 B 也读到 i=10 并写回 11，接着线程 A 继续执行加 1 并写回 11，最终结果应该是 12，实际却是 11，出现了结果丢失。
>
> 解决方式：用 `synchronized` 或 `Lock` 把"读-改-写"三步包裹成一个临界区，保证同一时刻只有一个线程能完整执行这三步，不会被其他线程打断；也可以用 `AtomicInteger` 等 CAS 操作来保证原子性。

### 4. 什么是指令重排序？是谁在重排？多线程下会出什么典型问题？Java 中有哪些手段禁止重排序？

> **问题描述**
> 进阶题，常和 DCL 单例（双重检查锁）一起考。
>
> 建议回答顺序：定义 + 三层重排（编译器、CPU 指令级并行、内存系统）→ 举"对象半初始化"例子 → 给两层手段：volatile 内存屏障、synchronized + happens-before。

> [!abstract]- 参考答案
> 指令重排序是指编译器或 CPU 为了提升执行效率，在不改变单线程程序最终结果的前提下，对代码指令的执行顺序进行调整。
>
> 发生原因：编译器优化重排、CPU 指令级并行的重排、内存系统的重排（写缓冲区等）。
>
> 多线程下的问题：单线程内重排序不影响最终结果，但在多线程下，一个线程看到的指令执行顺序可能与代码顺序不一致。典型例子：线程 A 先创建对象再赋值引用，可能被重排成先赋值引用、再初始化对象；线程 B 拿到引用后直接使用该对象，可能因为对象还未初始化完成而出错（典型的"指令重排+发布对象"问题）。
>
> 禁止重排序的方式：volatile 变量的读写会插入内存屏障，禁止该屏障前后的特定重排序；synchronized 通过加锁，使临界区内的代码对外表现为一个整体，结合 happens-before 规则保证有序性。

### 5. 实际开发中写多线程代码，有哪些"必须时刻警惕"的注意事项？

> **问题描述**
> 经验型开放题，考察工程意识，没有标准答案。
>
> 建议回答顺序：先列三方面（线程安全、通信、生命周期成本）→ 每点配一个真实场景（共享计数、生产消费、线程池）。

> [!abstract]- 参考答案
> 主要有三方面：
>
> 1. **线程安全问题**：多个线程同时操作共享数据可能导致数据错乱（如多线程同时给一个变量加 1，结果可能少加）。需要用 `synchronized`、`Lock` 等手段保证同一时间只有一个线程操作共享数据。
> 2. **线程间通信**：当多个线程需要协作（如生产者-消费者）时，需要通过 `wait()`/`notify()`、`Condition`、阻塞队列等机制进行同步，避免一方未准备好另一方就操作，导致数据错误或无限等待。
> 3. **线程创建和销毁成本**：频繁创建、销毁线程会消耗系统资源、影响性能，应使用线程池来复用线程、减少开销。

### 6. Java 线程和操作系统线程到底是什么关系？1:1 还是 M:N？虚拟线程出现后这个关系变了吗？

> **问题描述**
> 高频进阶题。JDK 21 后常追"虚拟线程是不是协程"。
>
> 建议回答顺序：先按"平台线程 vs 虚拟线程"分两段 → 各讲对应模型（1:1 / M:N）和调度方（内核 / ForkJoinPool）→ 用一句话收尾：Java 21 之前是 1:1，21 之后可以做到 M:N。

> [!abstract]- 参考答案
> 分两种情况：
>
> - **平台线程（Platform Thread）**：Java 长期以来默认的线程实现，JVM 在 Linux 上通过 `pthread_create` 创建，一个 Java 平台线程严格对应一个操作系统线程，是 **1:1 模型**。线程的调度、上下文切换都由操作系统内核负责，开销大，默认栈空间约 1MB，因此不能无限创建。
> - **虚拟线程（Virtual Thread）**：Java 21 正式发布（JEP 444），是 JVM 在用户态自行调度的轻量级线程，采用 **M:N 模型**——大量虚拟线程映射到少量载体平台线程（Carrier Thread）上执行，由 `ForkJoinPool` 调度。创建成本极低（几百字节，栈可动态扩缩），单 JVM 可轻松运行上百万个虚拟线程，特别适合 IO 密集型高并发场景。
>
> 所以"Java 线程=操作系统线程"只适用于 JDK 21 之前或只用平台线程的场景；用了虚拟线程后，Java 并发模型已接近 Go 的 M:N 协程调度。

#### 解释

**JVM 是什么**

JVM（Java Virtual Machine）是一个**运行在操作系统之上的程序**（一个进程）。你写的 `.java` 文件编译成 `.class` 字节码后，由 JVM 这个程序来加载、解释/编译执行。JVM 本身是用 C/C++ 写的一个软件（比如 HotSpot），它要运行，就得先跑在某个真实的操作系统上（Linux、Windows、macOS 都行）。

所以层级关系是：

```
你的 Java 代码
    ↓
JVM（一个运行在操作系统上的进程，比如 java 命令启动的那个进程）
    ↓
操作系统（Linux / Windows...）
    ↓
硬件（CPU）
```

**"JVM 在 Linux 上通过 pthread_create 创建"是什么意思**

当你在 Java 代码里 `new Thread().start()` 时，JVM 自己并不能凭空"造出"一个线程——它需要向操作系统申请。具体做法是：JVM（这个 C++ 程序）内部调用了 Linux 提供的系统调用/库函数 `pthread_create()`，这是 Linux 创建线程的标准方式。

==JVM 创建平台线程的本质是："JVM 调用所在操作系统提供的线程创建 API"，至于具体调的是哪个函数，取决于 JVM 跑在什么操作系统上：==

也就是说，JVM 创建一个 Java 线程的过程，本质上是 **JVM 这个进程，调用操作系统API，让操作系统帮它创建了一个真正的"操作系统线程"**。这个操作系统线程归属于 JVM 这个进程，但调度、上下文切换这些都是 Linux 内核管的，JVM 管不着。

类比一下：JVM 像是一个"中间商"——你（Java代码）跟 JVM 说"我要一个线程"，JVM 转头跟操作系统说"帮我整一个 pthread"，操作系统给了一个真正的线程，JVM 把这个线程包装成一个 `Thread` 对象交给你用。

**能不能说"平台线程 = 操作系统线程"**

**严格来说不完全对，但在大多数语境下这么理解也没问题，关键看你怎么定义"="。**

- 如果说的是**1:1 的对应关系、调度方式、开销大小**——这个说法是对的：一个平台线程对象背后，确实就唯一对应着一个由操作系统内核调度的真实线程，没有额外的"用户态调度层"，所以它的行为（创建开销、调度方式、栈大小限制等）几乎等同于操作系统线程的行为。

- 但如果抠字眼说"完全相等"——也不完全准确：`Thread` 对象本身是 JVM 里的一个**Java对象**，它内部封装/持有了对那个底层 pthread 的引用，并附加了一些 JVM 层面的东西（比如 Java 层面的线程状态、线程名、TID等元信息、与 JVM GC/安全点机制的配合等）。所以严格说，"平台线程"是"JVM 对一个操作系统线程的封装和暴露"，而不是"操作系统线程本身"。

回答面试问题时，说法可以是：

> "平台线程和操作系统线程是 1:1 的关系——每个 Java 平台线程对象背后都对应一个真实的操作系统线程，由内核负责调度和上下文切换，行为特征（如开销、栈大小）基本等同于操作系统线程；只是 Java 在上面包了一层 `Thread` 对象方便我们使用。这和虚拟线程的 M:N 模型形成对比，虚拟线程不是直接对应一个操作系统线程，而是被 JVM 动态调度到少量载体线程上。"

这样既体现了"1:1 对应"这个核心特征，又不会因为说得太绝对而显得不严谨。

### 7. 虚拟线程（Virtual Thread）有哪些核心特点？和 Go 的 goroutine 在模型、栈、调度上有什么异同？

> **问题描述**
> Java 21 之后的高频热点题，建议和第 6 题连着问。
>
> 建议回答顺序：先列虚拟线程 4-5 个核心特点 → 再和 goroutine 比"相同点（都 M:N、都用户态调度）"和"不同点（GMP vs ForkJoinPool、2KB vs 几百字节、channel vs synchronized）"。

> [!abstract]- 参考答案
> **虚拟线程特点**：
> - JEP 444，Java 21 正式发布；
> - JVM 用户态调度，M:N 模型，由 `ForkJoinPool` 承载；
> - 创建成本极低（几百字节起步，栈可动态扩缩），可创建上百万个；
> - 遇到 IO 阻塞时，JVM 会自动将其从载体线程上"摘下"，让载体线程去执行其他虚拟线程，从而不阻塞操作系统线程。
> - 创建方式简洁：`Thread.startVirtualThread(...)` 或 `Executors.newVirtualThreadPerTaskExecutor()`。
>
> **与 goroutine 的相同点**：都是用户态调度、M:N 模型、轻量级、遇到阻塞自动让出底层线程，适合高并发 IO 场景。
>
> **不同点**：goroutine 是 Go 运行时 GMP 模型调度，初始栈仅 2KB；虚拟线程依赖 `ForkJoinPool`，仍运行在 JVM 之上，并要兼容已有的同步原语（如 synchronized 在某些版本中会"钉住"载体线程）。整体来看 Java 21+ 后两者在高并发 IO 场景下差距已大幅缩小，但 Go 的并发语法（go 关键字 + channel）更简洁。

### 8. 多线程下保证"数据一致性"有哪些常见方案？它们各自的适用场景是什么？

> **问题描述**
> 偏实战题，常和"超卖""重复下单"等业务问题一起出现。
>
> 建议回答顺序：先列三类方案（数据库事务、锁、版本号/乐观锁）→ 各讲一句"什么时候用、有什么代价"。

> [!abstract]- 参考答案
> - **事务管理**：使用数据库事务，通过 ACID（原子性、一致性、隔离性、持久性）特性，保证一组数据库操作要么全部提交，要么全部回滚。
> - **锁机制**：使用锁实现对共享资源的互斥访问，如 `synchronized`、`ReentrantLock`，控制并发访问，避免并发操作导致数据不一致。
> - **版本控制（乐观锁）**：更新数据时记录版本号，更新时校验版本是否变化，避免多个线程同时修改同一数据导致覆盖问题，从而保证一致性。

### 9. Java 中线程有哪几种创建方式？它们的优缺点分别是什么？实际开发优先选哪种？

> **问题描述**
> 基础必考题，重点在"为什么推荐实现 Runnable/Callable"和"线程池的代价"。
>
> 建议回答顺序：四种方式依次讲（继承 Thread、实现 Runnable、实现 Callable+FutureTask、线程池）→ 每种讲优缺点 → 收尾"实际开发几乎只用线程池"。

> [!abstract]- 参考答案
> 1. **继承 Thread 类**：重写 `run()` 方法，调用 `start()` 启动。优点：编写简单，访问当前线程可直接用 `this`；缺点：已经继承了 Thread，不能再继承其他父类。
> 2. **实现 Runnable 接口**：重写 `run()`，将 Runnable 对象传给 Thread 构造器。优点：可以再继承其他类，且多个线程可以共享同一个 Runnable 对象，体现面向对象思想；缺点：访问当前线程要用 `Thread.currentThread()`，编程稍复杂。
> 3. **实现 Callable 接口 + FutureTask**：`call()` 方法可以有返回值并抛出异常，需要包装进 `FutureTask`（实现了 Runnable）才能交给 Thread 执行。优点：仍可继承其他类，且能拿到异步执行结果；缺点：编程相对复杂，访问当前线程也要用 `Thread.currentThread()`。
> 4. **使用线程池（Executor 框架）**：通过 `ExecutorService`/`Executors` 创建线程池，提交 Runnable/Callable 任务。优点：复用线程，避免频繁创建销毁的开销，能控制并发线程数量，防止资源耗尽；缺点：增加了系统复杂度，参数配置不当可能导致死锁、资源耗尽等问题，排查较复杂。

### 10. 为什么实现 Runnable 接口的方式天然适合"多线程共享同一份资源"？卖票超卖问题是怎么产生的？怎么修？

> **问题描述**
> 经典场景题，常作为线程安全入门案例。
>
> 建议回答顺序：先讲 Runnable 共享实例的特点 → 再讲 `tickets--` 非原子导致的超卖 → 给出 synchronized 包裹"判断+自减+打印"的标准修法 → 顺便提一句为什么 sleep 而不用 yield。

> [!abstract]- 参考答案
> 实现 Runnable 接口时，多个 Thread 可以共用**同一个 Runnable 对象实例**（如卖票的 `TicketTask`），这样多个线程操作的是同一份数据，天然适合抢票、秒杀这类多个相同线程处理同一份资源的场景；而继承 Thread 的方式每个线程都是独立对象，各自维护数据，无法直接共享状态。
>
> 超卖问题原因：`tickets--` 不是原子操作，实际是"读 tickets、减 1、写回"三步。多个线程可能同时读到相同的 `tickets` 值，导致多次减成同一个值，出现票数卖出超过库存或变成负数。
>
> 解决方式：用 `synchronized` 把"判断 + 自减 + 打印"包裹成临界区，保证同一时刻只有一个线程能完整执行这组操作，避免出现两个线程读到同一个 tickets 值的情况。同时可以配合 `Thread.sleep()` 让线程主动让出 CPU，给其他线程获取锁的机会（用 `yield()` 不行，因为它只是"建议"调度器让出 CPU，不保证真正切换）。

### 11. 如何"安全"地停止一个线程？常见的几种方式分别适合什么场景？为什么 `Thread.stop()` 被废弃了？

> **问题描述**
> 实战工程题，面试官重点看有没有踩过 stop() 的坑。
>
> 建议回答顺序：先列四种安全方案（标志位、interrupt、Future.cancel、关资源）→ 各讲适用场景 → 最后用 stop() 暴力释放锁的反例收尾。

> [!abstract]- 参考答案
> 常见的安全停止方式：
>
> 1. **共享标志位**：定义一个 `volatile boolean running`，工作线程循环检测该标志，主线程通过修改标志位通知线程退出循环。
> 2. **线程中断机制**：调用 `interrupt()` 设置中断状态，线程内通过 `Thread.currentThread().isInterrupted()` 检测中断状态来决定是否退出（注意不要用静态方法 `Thread.interrupted()`，它会清除中断标志）；如果线程处于 `sleep`/`wait`/`join` 等阻塞状态，会抛出 `InterruptedException` 并清除中断状态。
>    - **简单场景**（自己写的业务方法，没人会再调你）：catch 到 `InterruptedException` 后直接 `return`/`break` 退出即可。
>    - **线程池 / 上层调用栈场景**（任务可能被 `Future.get()`、`invokeAny()` 等调用方等待）：catch 后应当 `Thread.currentThread().interrupt()` **重新设置中断标志**再退出，否则中断状态被异常清掉，上层调用方拿不到"任务被中断过"的信号。
>    ```java
>    // 简单场景：直接退出
>    try { Thread.sleep(1000); } catch (InterruptedException e) { return; }
>
>    // 线程池场景：恢复中断标志，让上层知道
>    try { Thread.sleep(1000); } catch (InterruptedException e) {
>        Thread.currentThread().interrupt();
>        return;
>    }
>    ```
> 3. **Future.cancel()**：通过线程池提交任务得到 Future，调用 `future.cancel(true)`，底层依赖中断机制来终止任务线程。
> 4. **关闭资源**：对于不可中断的阻塞操作（如 `ServerSocket.accept()`），通过关闭底层资源（如 `serverSocket.close()`）使阻塞调用抛出异常，从而结束线程。
>
> `Thread.stop()` 已被弃用，因为它是暴力终止，会立即释放线程持有的所有锁且不给线程任何清理资源、完成必要收尾工作的机会，可能导致共享数据处于不一致状态、资源未正确释放等问题。`suspend()`/`resume()` 也已废弃，容易导致死锁。

### 12. `interrupt()` 到底做了什么？线程在"阻塞中"和"运行中"分别会有什么不同表现？

> **问题描述**
> 紧接第 11 题的深入追问，必须分清两种状态。
>
> 建议回答顺序：先说 interrupt() 是"修改中断标志位" → 分两种情况（正在 sleep/wait/join、正常运行）讲表现 → 强调"正常运行中不会抛异常，也不会自动停止"。

> [!abstract]- 参考答案
> 每个线程都有一个布尔属性表示其中断状态，初始值为 false。调用某线程的 `interrupt()` 方法后，根据该线程当前状态有不同表现：
>
> - 如果线程正在执行**低级别可中断方法**（如 `Thread.sleep()`、`Thread.join()`、`Object.wait()`）而处于阻塞状态，会**立即解除阻塞**，并抛出 `InterruptedException` 异常，同时中断状态会被清除。
> - 如果线程**没有处于上述阻塞状态**（正常运行中），`interrupt()` 只是把该线程的中断状态设置为 true，不会立即产生任何效果，线程需要自己在合适的位置通过 `isInterrupted()` 轮询中断状态，来决定是否要停止当前任务。

### 13. Java 线程有哪几种状态（`Thread.State`）？每种状态分别在什么场景下进入？

> **问题描述**
> 基础题，但 6 种状态容易记混，建议和"BLOCKED 和 WAITING 区别"连考。
>
> 建议回答顺序：直接列六种状态（NEW / RUNNABLE / BLOCKED / WAITING / TIMED_WAITING / TERMINATED）→ 各讲进入条件 → 强调"没有 RUNNING，RUNNABLE 包了 ready+running"。

> [!abstract]- 参考答案
> `java.lang.Thread.State` 枚举定义了六种状态：
>
> | 状态 | 含义 |
> |------|------|
> | NEW | 线程已创建但还未调用 `start()` |
> | RUNNABLE | 包括"就绪"（已调用 start，等待调度）和"正在运行"两种子状态 |
> | BLOCKED | 等待获取监视器锁（如进入 synchronized 块时锁被占用） |

> | TIMED_WAITING | 有指定等待时间的等待状态（如 `sleep(time)`、`wait(time)`） |
> | TERMINATED | 线程执行完毕，终止状态 |

> 可通过 `Thread.getState()` 获取当前线程状态。注意：枚举中没有单独的 RUNNING 状态，RUNNABLE 包含了操作系统层面的 ready 和 running 两个子状态。

### 14. `sleep()` 和 `wait()` 有什么区别？从所属类、是否释放锁、唤醒方式三方面对比。

> [!abstract]- 参考答案

### 15. `sleep()` 会释放 CPU 吗？会释放锁吗？为什么这两个问题要分开看？

> **问题描述**
> 紧接第 14 题的常见追问。
>
> 建议回答顺序：开门见山"会释放 CPU，不会释放锁" → 解释 CPU 让出（→ TIMED_WAITING 状态） → 解释锁不释放（synchronized 退出前锁不释放） → 一句话总结"两个动作是独立的"。

> [!abstract]- 参考答案
> sleep() **会释放 CPU，但不会释放锁**。
>
> 调用 `Thread.sleep()` 后，线程主动让出 CPU 时间片，进入 `TIMED_WAITING` 状态，操作系统会把 CPU 分配给其他就绪线程执行。
>
> 但 sleep() 不会释放线程已经持有的任何锁（如 `synchronized` 同步块/方法中获取的锁）。所以如果其他线程在等待同一把锁，它们仍然会被阻塞，直到当前线程退出同步代码块、真正释放锁为止。

### 16. BLOCKED 和 WAITING 状态有什么区别？分别是怎么进入、怎么恢复的？

> **问题描述**
> 高频易错题，关键是"被动 vs 主动"和"自动 vs 显式唤醒"。
>
> 建议回答顺序：先讲进入条件（BLOCKED=抢锁失败，WAITING=主动调方法）→ 再讲恢复方式（BLOCKED=自动重抢，WAITING=必须被显式唤醒）→ 收尾"被动/自动 vs 主动/显式"。

> [!abstract]- 参考答案
> - **触发条件**：
>   - BLOCKED：线程尝试获取某对象的监视器锁（如进入 `synchronized` 块/方法）时，该锁已被其他线程持有，于是被阻塞，等待锁释放。
>   - WAITING：线程主动调用 `Object.wait()`、`Thread.join()`、`LockSupport.park()` 等方法，等待另一个线程执行某些操作（如 notify、线程结束、unpark）。
>
> - **唤醒机制**：
>   - BLOCKED：当持有锁的线程释放锁后，等待锁的线程会**自动**有机会重新竞争该锁，竞争成功则变为 RUNNABLE。
>   - WAITING：必须**被其他线程显式唤醒**（如 `notify()`/`notifyAll()`、`join` 的目标线程结束、`unpark()`），不会自动恢复。
>
> 总结：BLOCKED 是锁竞争失败后**被动**触发的状态，WAITING 是线程**主动**调用相关方法进入的状态；BLOCKED 的恢复是自动的，WAITING 的恢复必须靠特定方法主动唤醒。

### 17. 为什么处于 WAITING / BLOCKED 状态的线程不消耗 CPU？这和自旋锁"空转烧 CPU"有什么本质区别？

> **问题描述**
> 原理题，回答时一定要落到"操作系统调度器的运行队列"上。
>
> 建议回答顺序：先给结论"不消耗" → 讲两层原因（JVM 让出 + OS 调度器从 run queue 摘掉）→ 用自旋锁做反面对比 → 收尾"竞争激烈时重量级锁反而更优"。

> [!abstract]- 参考答案
> 原因分两层：
>
> 1. **JVM 层主动让出**：线程调用 `wait()`、`park()`、`sleep()` 或竞争重量级锁失败时，HotSpot 底层通过 `pthread_cond_wait`、`pthread_mutex_lock` 等系统调用向操作系统声明该线程当前无需占用 CPU 资源。
> 2. **操作系统调度器层（本质原因）**：处于 WAITING/BLOCKED 状态的线程对操作系统调度器来说是"不可运行（not runnable）"的。调度器维护一个运行队列（run queue），只从队列中选线程分配 CPU 时间片。WAITING/BLOCKED 的线程不在运行队列中，调度器不会为它做上下文切换，也不分配任何 CPU 时间片，因此 CPU 占用为 0%。
>
> **对比自旋锁**：自旋锁获取失败时线程仍保持 RUNNABLE 状态，仍驻留在运行队列中，持续被调度器分配 CPU 时间片执行空循环（PAUSE 指令），造成 CPU 资源空耗。而处于 WAITING/BLOCKED 状态的线程已被内核从运行队列中移出，CPU 可转而执行其他可运行线程——这也是在高竞争场景下，重量级锁往往优于忙等待自旋锁的原因。

### 18. `notify()` 和 `notifyAll()` 有什么区别？`notify()` 选择唤醒哪个线程是确定的吗？单生产者-单消费者能不能用 `notify()`？

> **问题描述**
> wait/notify 高频题，重点是"notify 随机性"和"为什么生产消费模式更推荐 notifyAll"。
>
> 建议回答顺序：先讲共同点（都唤醒等同一把锁的线程）→ 分开讲 notify(1 个) vs notifyAll(全部) → 提一句 HotSpot FIFO 实现 → 提一句"单生产者单消费者可以 notify，其他场景推荐 notifyAll"。

> [!abstract]- 参考答案
> 两者相同点：都是唤醒在该对象监视器上等待的线程，唤醒后这些线程要重新竞争锁，最终最多只有一个线程能获得锁继续执行，且都无法控制具体哪个线程能获得锁。
>
> 区别：
> - `notify()`：只唤醒**一个**等待中的线程，其余线程继续处于等待状态。如果被唤醒的线程执行结束后没有再调用 `notify()`，其他等待线程将永远没人唤醒，只能等待超时或被中断。
> - `notifyAll()`：唤醒**所有**等待中的线程，它们会一起去竞争锁，只有一个能抢到并执行；执行完后释放锁，剩下的线程再竞争，依次循环。
>
> `notify()` 选择唤醒哪个线程是任意的，依赖具体 JVM 实现；在 HotSpot 中实际是按"先进先出（FIFO）"的顺序唤醒。
>
> **单生产者-单消费者能否使用 `notify()`**：可以使用。由于只有两类线程（生产者、消费者各一个），`notify()` 唤醒的必然是对方角色线程，不存在"唤醒同类型线程导致信号丢失"的问题。但前提是必须在 `while` 循环中判断条件（防止虚假唤醒），并保证两类线程使用**同一个对象的同一个等待队列**。在多生产者/多消费者场景下则必须使用 `notifyAll()`，否则可能出现"唤醒的是同类线程，对方线程永远等不到信号"导致的死等问题。
>
> **示例代码**（单生产者-单消费者使用 `notify()`）：
> ```java
> public class SinglePC {
>     private final Object lock = new Object();
>     private Integer data = null; // null 表示缓冲区为空
>
>     // 生产者
>     public void produce(int value) throws InterruptedException {
>         synchronized (lock) {
>             // 用 while 而非 if：防止虚假唤醒 + 条件仍满足时继续 wait
>             while (data != null) {
>                 lock.wait();
>             }
>             data = value;
>             System.out.println("生产: " + value);
>             lock.notify(); // 唤醒唯一的消费者
>         }
>     }
>
>     // 消费者
>     public Integer consume() throws InterruptedException {
>         synchronized (lock) {
>             while (data == null) {
>                 lock.wait();
>             }
>             int v = data;
>             data = null;
>             System.out.println("消费: " + v);
>             lock.notify(); // 唤醒唯一的生产者
>             return v;
>         }
>     }
> }
> ```
> 该例中只有 1 个生产线程、1 个消费线程，共享 `lock` 对象的同一等待队列：生产者 `notify()` 唤醒的必然是消费者，消费者 `notify()` 唤醒的必然是生产者，因此不会丢信号。
>
> **反例**（多生产者-多消费者如果误用 `notify()` 会出问题）：
> ```java
> // 假设 2 个生产者 P1、P2，2 个消费者 C1、C2 共享同一个 lock
> // P1 刚生产完调用 notify()，唤醒了 P2（同类线程）而不是 C1/C2
> // P2 醒来后 while(data != null) 条件不满足（缓冲区已满），继续 wait
> // 此时 C1/C2 仍在 wait，缓冲区已满、P2 已 wait、P1 也可能已 wait
> // → 所有线程都卡住，程序无法继续
> ```

### 19. Java 中线程间通信（协作）有哪些常见方式？分别适合什么场景？

> **问题描述**
> 综合性题，建议按"共享内存 vs 同步原语 vs 并发工具类"分层讲。
>
> 建议回答顺序：先讲最朴素的 volatile 标志位 → 再讲 wait/notify → 再讲 Lock+Condition → 最后讲并发工具类（CountDownLatch、CyclicBarrier、Semaphore、BlockingQueue）各适合什么场景。

> [!abstract]- 参考答案
> 主要有以下几种：
>
> 1. **共享变量 + volatile**：多个线程访问同一个 volatile 变量，写操作立即可见，常用于简单的状态标志通信。
> 2. **wait()/notify()/notifyAll()**：基于对象监视器（锁）的等待/通知机制，`wait()` 释放锁并进入等待，`notify()`/`notifyAll()` 唤醒等待线程，典型用于生产者-消费者模式。
> 3. **Lock + Condition**：`ReentrantLock` 配合 `Condition`，`await()`/`signal()`/`signalAll()` 分别对应 `wait()`/`notify()`/`notifyAll()`，提供比 synchronized 更灵活的等待/通知机制（可以创建多个条件队列）。
> 4. **CountDownLatch**：构造时指定计数值，调用 `countDown()` 递减计数，`await()` 的线程会一直阻塞直到计数变为 0，常用于"一个或多个线程等待若干线程完成任务"的场景。
> 5. **CyclicBarrier**：让一组线程在屏障点互相等待，所有线程都到达后才能继续执行，且屏障可以重复使用（cyclic）。
> 6. **Semaphore**：计数信号量，`acquire()` 获取许可（无许可则阻塞），`release()` 释放许可，用于控制同时访问某资源的线程数量。
> 7. **BlockingQueue**：线程安全的队列，`put()` 在队列满时阻塞，`take()` 在队列空时阻塞，常用于生产者-消费者模式。

### 20. `wait()` 为什么必须在 `synchronized` 块中调用？判断条件为什么推荐用 `while` 而不是 `if`？

> **问题描述**
> wait/notify 原理题，两个子问题都是经典坑点。
>
> 建议回答顺序：先讲 wait 必须持锁的语义（"释放锁+等待"是组合操作）→ 不持锁会抛 IllegalMonitorStateException → 再讲 while 而不用 if 的两个原因（虚假唤醒 + 多消费者条件已变）。

> [!abstract]- 参考答案
> **为什么 wait() 必须在 synchronized 块中调用**：
> `wait()` 是 `Object` 的方法，它的语义是"释放当前持有的对象监视器锁，并让线程进入等待队列"。如果调用 `wait()` 前线程没有持有该对象的锁，就没有锁可释放，JVM 无法保证"释放锁+进入等待"这一组合操作的原子性，因此规定必须在 `synchronized` 块/方法中（即持有锁的前提下）调用 `wait()`，否则会抛出 `IllegalMonitorStateException`。
>
> **为什么用 while 而不是 if 判断条件**：
> 1. **虚假唤醒（spurious wakeup）**：线程可能在没有被 `notify()` 的情况下从 `wait()` 中返回（JVM 规范允许），用 while 可以在被唤醒后重新检查条件是否真正满足。
> 2. **多消费者/多生产者竞争**：当使用 `notifyAll()` 唤醒多个线程时，被唤醒的线程需要重新竞争锁，竞争到锁后条件可能已经被其他线程改变（例如盘子里的面包已经被别的消费者吃掉），用 while 循环可以重新判断条件，条件不满足则继续 `wait()`，避免出现重复消费/重复生产等错误。
>
> **正例（用 while）**：
> ```java
> synchronized (lock) {
>     while (data == null) {  // 唤醒后重新检查，防止虚假唤醒 + 条件已被其他线程改变
>         lock.wait();
>     }
>     int v = data;
>     data = null;
>     lock.notifyAll();
> }
> ```
>
> **反例（误用 if 会出问题）**：
> ```java
> synchronized (lock) {
>     if (data == null) {  // 错误：被唤醒后不再检查，可能消费空数据
>         lock.wait();
>     }
>     int v = data;        // 虚假唤醒后 data 仍为 null，抛 NullPointerException
>     data = null;
>     lock.notifyAll();
> }
> ```
> 在多消费者场景下问题更严重：消费者 C1 被唤醒后从 wait 返回，若用 if 会直接往下执行消费；但此时消费者 C2 可能已经先抢到锁并把唯一一份数据消费完，等 C1 拿到锁时 data 已是 null，再执行 `data` 读取就会 NPE，或出现"重复消费同一份数据"的逻辑错误。
>
> **虚假唤醒的具体场景**：
> 1. **JVM 规范允许**：`Object.wait()` 的 Javadoc 明确指出，线程可能在没有被 `notify()`、`notifyAll()`、中断或超时的情况下"虚假唤醒"（spurious wakeup），这是底层 pthread_cond_wait 实现为了应对竞态而保留的行为，Java 规范要求程序必须自行防御。
> 2. **典型场景（生产者-消费者）**：
>    - 时间线：消费者 C 调用 `lock.wait()` 进入等待队列（data 为 null）→ **无人调用 notify** → 几毫秒后 C 自动从 wait 中"虚假"返回。
>    - 此时用 `if`：C 直接往下读 `data`，NPE。
>    - 此时用 `while`：C 重新检查 `data == null`，发现条件不满足，继续 `wait()`，正确阻塞。
> 3. **debug 时的常见表现**：本地/测试环境几乎必现（特别是压力测试、循环跑生产者-消费者），线上偶发，表现为"明明没有 notify 通知，线程却自己跑起来消费了一个空值/重复值"。把 `if` 改成 `while` 后问题消失。

### 21. `CountDownLatch` 和 `CyclicBarrier` 有什么区别？分别用一句话讲清楚它们各自解决什么问题？

> **问题描述**
> 并发工具类对比题。
>
> 建议回答顺序：先分别讲构造、关键方法、是否可重用、典型场景 → 最后用一句话对比（"等待别人"vs"互相等待"）。

> [!abstract]- 参考答案
> - **CountDownLatch**：
>   - 构造时指定一个计数值，`countDown()` 使计数减 1，`await()` 的线程会阻塞直到计数变为 0。
>   - 是**一次性**的，计数到 0 后不能重置（重新使用）。
>   - 典型场景：主线程等待多个子线程都执行完某个初始化任务后再继续（如等待若干服务都启动完成）。
>
> - **CyclicBarrier**：
>   - 构造时指定参与线程数（parties），可选地指定所有线程到达屏障点后要执行的回调任务。
>   - 所有参与线程都调用 `await()` 到达屏障点后，才能一起继续往下执行，且屏障可以**重复使用（cyclic）**，到达后自动重置计数。
>   - 典型场景：多线程分阶段计算，每个阶段所有线程都要互相等待，等全部到齐再进入下一阶段。
>
> 简单说：CountDownLatch 是"一个或多个线程等待其他线程完成"，是单向、一次性的；CyclicBarrier 是"一组线程互相等待，集合后一起出发"，可循环使用。

### 22. `Semaphore` 有什么用？`acquire()` 和 `release()` 是什么语义？典型应用场景是什么？

> **问题描述**
> 工具类基础题，难度不高但常作为限流方案的引子。
>
> 建议回答顺序：先讲用途（控制并发数）→ 再讲构造许可数 → 再讲 acquire/release 阻塞/唤醒 → 收尾典型场景（限流、连接池）。

> [!abstract]- 参考答案
> `Semaphore`（信号量）用于控制同时访问某个资源/临界区的线程数量。
>
> - 构造时指定许可（permit）数量，表示同时最多允许多少个线程进入。
> - `acquire()`：获取一个许可，如果当前没有可用许可，则线程阻塞等待，直到有许可被释放。
> - `release()`：释放一个许可，归还给信号量，可能会唤醒正在 `acquire()` 阻塞等待的其他线程。
>
> 典型应用场景：限流（如同时只允许 N 个线程访问某资源/数据库连接池）、控制并发数。

### 23. Go 的 goroutine 和 Java 线程（平台线程 + 虚拟线程）相比，在调度模型、资源消耗、通信方式上有什么核心差异？

> **问题描述**
> 对比型开放题，Java 21 之后是热点。
>
> 建议回答顺序：分四个维度（调度模型、资源消耗、通信机制、使用方式）逐项对比 → 每项先讲 Java 现状（含虚拟线程补丁）→ 再讲 Go 的做法 → 收尾不绝对化。

> [!abstract]- 参考答案
> - **调度模型**：Java 平台线程是 1:1 模型，一个 Java 线程对应一个操作系统线程，由内核调度，调度涉及用户态/内核态切换，开销较大；Go 的 goroutine 是用户态调度（GMP 模型：G=goroutine，M=操作系统线程，P=逻辑处理器），多个 goroutine 映射到少量操作系统线程上，调度在用户态完成，开销小。（注：Java 21 引入虚拟线程后，已经是 M:N 模型，和 Go 思路接近。）
>
> - **资源消耗**：Java 平台线程默认栈空间约 1MB，创建/销毁需要系统调用，开销大，不能无限创建，因此需要线程池；goroutine 初始栈仅 2KB 且可动态伸缩，创建成千上万甚至几十万个都很轻松。
>
> - **通信机制**：Java 线程间主要通过共享内存通信，配合 `synchronized`/`Lock` 等同步机制，容易出现死锁、竞态条件等问题；Go 提倡"不要通过共享内存来通信，而要通过通信来共享内存"，主要用 channel 来传递数据，代码更清晰，不容易出现并发问题（虽然 Go 也支持共享内存+锁）。
>
> - **使用方式**：Go 创建协程只需 `go funcName()`，语法极简；Java 创建线程相对繁琐，需要 new Thread/实现 Runnable/Callable 或借助线程池。
