# 模式切换与上下文切换详解

> **用户态 ↔ 内核态的切换叫「模式切换（mode switch）」，它和「上下文切换（context switch）」是两件不同的事，但常被混成一句「切换开销大」。**
>
> 一句话区分：**模式切换是「同一个任务换了个身份进内核」**——特权级变了，任务没变；**上下文切换是「换一个任务来跑」**——任务变了。
>
> 两者正交：**模式切换可以单独发生**（系统调用不切任务）；但**上下文切换必然包含模式切换**（要让出 CPU 得先进内核）。

---

## 一、两个词的定义

| 概念 | 换的是 | 触发者 |
|------|--------|--------|
| **模式切换**（mode switch） | **特权级**：Ring 3 ↔ Ring 0，同一线程 | 系统调用、中断、异常 |
| **上下文切换**（context switch） | **执行的任务**：线程 / 进程 | 调度器（自愿让出或时间片到） |

**关键**：上下文切换是**调度层面**的动作，模式切换是**特权级层面**的动作。**它们的维度不同。**

---

## 二、三层区分（核心表）

| 动作 | 换任务了吗 | 特权级变了吗 | 换页表 CR3 吗 | 典型直接开销 |
|------|:---:|:---:|:---:|---|
| **模式切换**（syscall / 中断 / 异常） | ❌ 同一个线程 | ✅ Ring3 ↔ Ring0 | 传统上不换（KPTI 后要换，见 §七） | 几十 ns ~ 1μs |
| **线程上下文切换**（同进程） | ✅ 换线程 | 中间必经内核 | ❌ 不换（共用 CR3） | ~1–3μs |
| **进程上下文切换** | ✅ 换进程 | 中间必经内核 | ✅ 换 + TLB 失效 | 更贵，间接代价可达十几 μs |
| **协程 / 虚拟线程切换** | ✅ 换协程 | ❌ **完全不进内核** | ❌ | 几十 ns |

最后一行的意义在 §十。

---

## 三、为什么「上下文切换必然包含模式切换」

因为**调度器住在内核里**。一个线程要让出 CPU，不管是自愿还是被迫，都**必须先陷入内核**：

```
自愿让出：调 read() / futex / park → 需要等待 → 陷入内核（模式切换）→ schedule() 选下一个
被迫让出：时钟中断打到 CPU        → 陷入内核（模式切换）→ schedule() 选下一个
```

所以一次完整的上下文切换是**三段**：

```
用户态 ──模式切换──▶ 内核态 ──任务切换（换栈 / 换寄存器）──▶ 内核态 ──模式切换──▶ 用户态（换了个线程）
```

而**系统调用只有首尾两段、没有中间那段**（除非它阻塞了）。**这就是两者的分界线。**

---

## 四、最干净的证明：中断

**时钟中断**每次都会触发模式切换（CPU 被硬件强制拉进内核），但**处理完可能直接返回原任务**。这时候：

- 模式切换：**发生了 2 次**（进 / 出）
- 上下文切换：**0 次**

**只有模式切换、没有上下文切换**——直接证明两者不是同一件事。

| 事件 | 模式切换 | 上下文切换 |
|------|:---:|:---:|
| 系统调用（非阻塞，如 `getpid`） | ✅ | ❌ |
| 时钟中断（未触发抢占） | ✅ | ❌ |
| 缺页异常（页换回来即可） | ✅ | ❌ |
| 系统调用阻塞 / 时间片用完 | ✅ | ✅ |
| 线程或进程主动让出 | ✅ | ✅ |
| **协程 / 虚拟线程挂起** | ❌ | ✅（用户态） |

---

## 五、各自保存了什么

| | 模式切换 | 上下文切换 |
|---|---|---|
| 保存用户寄存器 | ✅ | ✅ |
| 换栈 | 用户栈 → **本线程的内核栈** | 换到**另一个任务的内核栈** |
| 保存 PC / SP / 线程私有数据 | 部分 | ✅ **完整** |
| 选出下一个任务 | ❌ | ✅ `schedule()` 的活 |
| 换页表 + 刷 TLB | ❌（KPTI 例外） | ✅（仅进程切换） |

**模式切换只保存「用户态现场」**——因为同一个线程等会儿还要回来；**上下文切换要保存「整个任务上下文」**——因为回来的是别人。

---

## 六、贵的到底在哪：直接开销 vs 间接开销

这是最反直觉的一点：

| 开销 | 量级 | 说明 |
|------|:---:|------|
| **直接**：保存 / 恢复寄存器 | 几百 ns | 就这么点活，其实不贵 |
| **间接**：TLB 失效 + **缓存变冷** | **几 μs ~ 十几 μs** | **真正贵的是这个** |

切换回来后，前一个任务留下的 L1/L2 缓存全成了废物，得重新从内存捞。所以「**不是线程本身重，是切换时丢缓存重**」。

**成本排序**：

```
协程切换（不进内核） ≪ 系统调用（1 次模式切换） < 线程切换（不换页表） < 进程切换（换页表 + 缓存全冷）
```

---

## 七、精度问题：KPTI 之后，模式切换也要换页表了

Meltdown 缓解的 **KPTI（页表隔离）** 把内核页表从用户态可见范围里拆出来，于是**每次陷入 / 返回内核都要切一次 CR3**（用户页表 ↔ 内核页表）。所以现代机器上一次 `syscall` **比以前贵**。

但要分清性质，**同名不同命**：

| | 换的是什么 | TLB 后果 |
|---|---|---|
| **KPTI 的换页表** | **同一任务**的用户页表 ↔ 内核页表，大部分映射共享 | 有 **PCID** 标签可避免 TLB 全刷 |
| **进程切换的换页表** | **另一个任务**的页表，映射几乎完全不同 | TLB 条目几乎全废 |

所以别把这两个「换页表」当成一回事——**一个是同任务的视图切换，一个是跨任务的地址空间切换。**

---

## 八、怎么减少模式切换：批量 / 复用 / 避免拷贝

高性能框架的优化方向基本都是同一个：**把多次陷入内核合并成一次，或者干脆让数据不进内核。** 三招各有各的 API。

### 8.1 批量：一次 syscall 搬多块数据

**`writev` / `readv`（scatter-gather IO）**——一次系统调用传多个 buffer：

```c
struct iovec iov[3];
iov[0].iov_base = status_line; iov[0].iov_len = len0;
iov[1].iov_base = headers;     iov[1].iov_len = len1;
iov[2].iov_base = body;        iov[2].iov_len = len2;

writev(fd, iov, 3);   /* 3 次 write → 1 次 syscall */
```

典型场景：一个 HTTP 响应天然是「状态行 + headers + body」三段**不连续内存**。传统要 3 次 `write`（3 次模式切换），`writev` 一次搞定。

**同类**：

| API | 作用 |
|-----|------|
| `writev` / `readv` | 一次搬多块 buffer |
| `sendmmsg` / `recvmmsg` | 一次收发多个报文（UDP 高吞吐） |
| `io_uring` | 批量推到极致——见下 |

**`io_uring`（Linux 5.1+）** 是批量的终极形态：它把「提交请求」和「获取结果」两件事都变成了**共享内存读写**，一次 `io_uring_enter` 提交**一批**操作。

两个队列是它的核心，都在**用户态与内核共享**的一块内存里：

| 队列 | 全称 | 谁写 | 谁读 | 装什么 |
|------|------|:---:|:---:|------|
| **SQ** | Submission Queue（提交队列） | 用户态 | 内核 | 请求（SQE：操作类型、fd、buffer、`user_data`） |
| **CQ** | Completion Queue（完成队列） | 内核 | 用户态 | 结果（CQE：返回值 / errno + 原样带回的 `user_data`） |

**关键就一条**：CQ 在**你自己的地址空间**里，内核把结果写进去、你直接读——**「取结果」完全不需要系统调用**。这正是 io_uring 比 epoll 省的地方：epoll 拿就绪列表仍要一次 `epoll_wait`。

更狠的 **SQPOLL 模式**（`IORING_SETUP_SQPOLL`）让内核线程主动轮询 SQ，应用连 `io_uring_enter` 都省了。⚠ 但那是**稳态**的零 syscall——轮询线程 idle 超时后会去睡觉（否则白烧一个核），这时仍需要一次 `io_uring_enter` 把它唤醒。

> 通俗理解：**SQ 是餐厅的点单夹**——你把订单夹上去（写 SQE）、夹子一推（更新 tail），厨房就知道有新单；**CQ 是出餐台**——厨师做好往台上一放，你**直接去台上拿**，不用每次都跑进厨房问「我的好了没」（省掉的就是那个 syscall）；**SQPOLL** 则是厨房专门派个人盯着点单夹，你夹完他立刻拿走——连通知都省了，但他一直站着费人力（烧一个核），没人点单时会去歇会儿，这时得喊一声把他叫醒。

⚠ **别把「应用层批量」和「减少 syscall」混了**：Redis pipeline、批量 `MGET` 减少的主要是 **RTT**（网络往返次数），顺带才摊薄了 `read`/`write` 的次数；而 `writev` 减少的是 **syscall 次数本身**。两者目标不同，但都往「少陷入内核」这个方向使劲。

### 8.2 复用：一次 syscall 等多个 fd

| 机制 | 一次调用的代价 | 问题 |
|------|------|------|
| `select` / `poll` | **每次调用**都要全量传 fd 集合、内核**线性遍历 O(n)** | 连接数一大就崩 |
| **`epoll`** | `epoll_ctl` **注册一次**，`epoll_wait` 一次返回**多个就绪 fd**，代价只和**就绪数**成正比 | C10K 的基石 |

**核心价值**：**一个线程用一次 syscall 等 N 个连接**——把 N 次「陷入内核」压成 1 次。这也是 Redis 单线程能扛高并发的原因之一。

再加 `epoll_wait` 的超时参数，可以让「等待」和「拿到就绪列表」在同一次调用里完成。

### 8.3 避免拷贝：让数据不进用户态

传统「读文件发网络」用 `read` + `write`，代价是 **4 次拷贝 + 4 次模式切换**（`read` 进出 + `write` 进出）：

```
硬盘 →(DMA)→ 页缓存 →(CPU)→ 用户缓冲区 →(CPU)→ socket 缓冲区 →(DMA)→ 网卡
```

| 方案 | 拷贝次数 | 模式切换次数 | 说明 |
|------|:---:|:---:|------|
| `read` + `write` | 2 DMA + 2 CPU | **4** | 基线 |
| `mmap` + `write` | 2 DMA + 1 CPU | 4 | 省掉「页缓存→用户缓冲区」那次 CPU 拷贝 |
| **`sendfile`** | 2 DMA + 1 CPU | **2** | 数据完全不进用户态 |
| `sendfile` + scatter-gather DMA | **2 DMA + 0 CPU** | 2 | socket 缓冲区只放描述符，网卡直接从页缓存 DMA 拼包——最优 |
| `splice` | 0 CPU | 2 | 在两个 fd 间搬数据（至少一个是管道），不经用户态 |

★ **一个很少被提到的点**：`sendfile` 相对 `read+write` 的收益，**不只是「少一次 CPU 拷贝」，还有「模式切换从 4 次降到 2 次」**——因为整个搬运只用一次系统调用的进出。**「避免拷贝」和「减少模式切换」在这里是同一件事的两面。**

### 8.4 落点表：谁用了哪招

| 组件 | 用哪招 | 具体做法 |
|------|--------|----------|
| **Nginx** | 避免拷贝 | 静态文件走 `sendfile` |
| **Kafka** | 避免拷贝 | `FileChannel.transferTo` → `sendfile` + scatter-gather DMA，数据从页缓存被网卡直接搬走 |
| **Netty** | 批量 + 避免拷贝 | 内部用 `writev` 批量写；`FileRegion` 封装 `sendfile`；`CompositeByteBuf` 用**逻辑组合**代替物理拷贝（用户态版零拷贝） |
| **Redis** | 复用 | 单线程 + `epoll` 一次等多连接；6.0 起多线程 IO 进一步分摊 |
| **通用中间件** | 批量 / 复用 | 连接池、页缓存、批量提交——都是「把多次陷入内核合并成一次」 |

### 8.5 极端手段：干脆不走内核

- **DPDK / 用户态协议栈**：网卡驱动搬到用户态、轮询收包，**完全不陷入内核**——代价是独占 CPU 核
- **RDMA**：网卡直接读写对端内存，绕过双方内核

这是「减少模式切换」的极致：**把模式切换降到 0。**

## 九、开销量级速查表

| 操作 | 量级 | 备注 |
|------|:---:|------|
| 普通函数调用 | 几 ns | 基线 |
| **系统调用（模式切换）** | **~0.1–1μs** | 比函数调用贵 2~3 个数量级；KPTI 后更贵 |
| 线程上下文切换（同进程） | ~1–3μs | 不换页表 |
| 进程上下文切换 | 十几 μs 起 | 换页表 + TLB 失效 + 缓存全冷 |
| 协程 / 虚拟线程切换 | 几十 ns | 不进内核 |

**注意**：上下文切换的「贵」主要不在保存寄存器（几百 ns），而在 **TLB 失效 + 缓存变冷**（几 μs~十几 μs）这部分**间接开销**。

## 十、落到 Java

| 现象 | 归因 |
|------|------|
| Redis 单线程还这么快 | **免掉**了线程上下文切换 |
| 线程池不是越多越好 | 上下文切换吃 `%sy` |
| Netty / Kafka 减少系统调用 | 省的是**模式切换**（`writev` / `epoll` / `sendfile`） |
| IO 密集场景「加线程反而慢」 | 线程切换的缓存 / TLB 间接开销 > 多线程带来的并行收益 |
| **虚拟线程为什么能开到百万级** | 它把「阻塞时让出」**从内核态搬回用户态**——挂起只在 JVM 里做，**不陷入内核、没有模式切换**，也没有内核调度 |

**虚拟线程那一条正好把两者串起来**：它不是「让切换变快」，而是**把切换整个搬出了内核**——这才是它比平台线程便宜的本质。

⚠ 但注意边界：**虚拟线程只在阻塞点卸载**，纯计算的长任务没有卸载点，会一直占着载体线程（详见 [[OS八股]] §2.3 与 [[OS热门面试题]] Q2 追问）。

## 面试话术

> "很多人把这两个混着说，其实是两件事。**用户态和内核态的切换叫模式切换**——同一个线程进了内核，特权级变了、任务没变，开销大约 0.1 到 1 微秒。**上下文切换是换一个任务来跑**，它必然包含模式切换，因为调度器住在内核里，要让出 CPU 就得先陷入内核。
>
> 最好的区分例子是**时钟中断**：它每次都触发模式切换，但如果没有抢占发生，处理完直接回原任务——**模式切换发生了两次，上下文切换零次**。这就说明两者是正交的。
>
> 真正贵的地方也不在保存恢复寄存器，那只有几百纳秒；贵在**间接开销**——进程切换要换页表、TLB 失效、CPU 缓存全冷，几微秒到十几微秒。所以进程切换比线程切换贵，线程切换比模式切换贵。
>
> 顺着这个逻辑，高并发框架的优化方向就清楚了：**要么减少模式切换，要么减少上下文切换**。减少模式切换就是**批量、复用、避免拷贝**——`writev` 一次写多块、`epoll` 一次等多个 fd、`sendfile` 让数据不进用户态，io_uring 更是把批量做到极致。而减少上下文切换就是**控制线程数**，Redis 干脆用单线程绕过。虚拟线程是第三条路：把切换从内核态搬到用户态，连接都不断，自然就便宜了。"
