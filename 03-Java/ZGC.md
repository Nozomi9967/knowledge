### **ZGC 是 JDK 11 引入、15 转正的低延迟垃圾回收器，核心是"染色指针 + 读屏障 + 全并发"，能做到 TB 级堆下 STW 稳定 < 1ms，代价是牺牲 5~15% 吞吐**

  

---

  

### **一、ZGC 要解决的问题**

  

在 ZGC 之前，G1 已经把停顿压到几十毫秒级，但**停顿时间和堆大小仍然正相关**——堆越大，Young GC 拷贝对象越多、Remembered Set 扫描越慢、Mixed GC 越难收敛。到了 100G 以上的堆，G1 的 P99 停顿经常突破 200ms。

  

ZGC 的设计目标很激进:

  

- **停顿时间 < 10ms**（实测通常 < 1ms）

- **停顿时间与堆大小无关**：4G 和 4TB 停顿一样

- **支持 TB 级堆**：理论上限 16TB（JDK 15），JDK 21 已经到 16TB

- **代价可控**：吞吐损失控制在 15% 以内

  

它的做法是把"能并发做的全并发做"——**只有 root scan 阶段 STW**，标记、转移、重定位全部和业务线程并发执行。

  

---

  

### **二、核心技术：染色指针（Colored Pointers）**

  

这是 ZGC 最精妙的地方。

  

在 64 位系统上，一个指针虽然是 64 位，但实际用不满。ZGC 借用其中**几位存元数据**（JDK 15 之前用高 42~45 位，JDK 15 之后用低 3 位做多映射）：

  

```

63 46 45 44 43 42 0

+-----------+--+--+--+--+------------------------------------+

| unused |Fi|Re|M1|M0| object address |

+-----------+--+--+--+--+------------------------------------+

| | | |

| | | +-- Marked0: 标记周期 0

| | +----- Marked1: 标记周期 1

| +-------- Remapped: 已重映射

+----------- Finalizable: finalizer 可达

```

  

**为什么这么设计**：传统 GC 要判断一个对象"是否被标记"、"是否被移动"，得读**对象头**（对象在堆里的某个字段）。这就要求先加载对象到 cache，慢且需要额外内存。ZGC 把这些状态直接**编码进指针**，CPU 读指针的同时就知道对象状态，零内存访问开销。

  

配合的操作系统技巧是 **多重内存映射（Multi-Mapping）**：同一段物理内存被映射到不同虚拟地址，Marked0 / Marked1 / Remapped 三个视图对应同一份数据，指针的不同"颜色"访问的是同一物理页——**这就是为什么 ZGC 早期 RSS 看起来是实际堆的 3 倍**（`top` 里的数字虚高，实际物理内存只用一份）。JDK 15 之后用 4 位地址压缩，缓解了这个问题。

### **三、读屏障（Load Barrier）**

  

染色指针需要**读屏障**配合。业务代码每次从堆里读一个引用字段，JVM 会插入一小段机器码检查：

  

```

// 伪代码

Object obj = someField; // 业务代码

// JIT 插入的读屏障:

if (指针颜色 != 当前GC期望的颜色) {

obj = slow_path_fix(obj); // 更新指针,可能触发重映射

someField = obj; // 自愈:回写修正后的指针

}

```

  

**关键点**：

  

- **读屏障不是 STW**，是每个业务线程自己执行的一小段代码（大概 4~8 条汇编指令）。

- **自愈（self-healing）**：一旦一个引用被修正，下次再读同一字段就直接命中，不会再走 slow path。所以稳态下屏障开销很低。

- **吞吐损失就来自这里**：每次读引用多几条指令，累积起来 5~15%。写操作反而没有屏障（G1 有 SATB 写屏障，ZGC 靠读屏障统一处理）。

  

对比 G1：G1 用**写屏障**维护 Remembered Set（跨 Region 引用表），ZGC 完全不需要 RSet，因此没有 RSet 维护的 CPU 和内存开销——这是 ZGC 能大堆低延迟的另一关键。

### **四、GC 流程（分三个并发阶段 + 三次极短 STW）**

  

ZGC 的一个回收周期：

  

**1. Pause Mark Start（STW，< 1ms）**

只扫 GC Roots（线程栈、静态变量），把根引用染成"Marked"色。这里 STW 时间只和线程数、根数量相关，**和堆大小完全无关**——这就是 ZGC 停顿恒定的核心原因。

  

**2. Concurrent Mark（并发）**

业务线程继续跑，GC 线程遍历对象图完成标记。读屏障保证并发过程中新加载的引用也被正确染色。

  

**3. Pause Mark End（STW，< 1ms）**

处理并发标记期间的边界情况，确认标记完成。

  

**4. Concurrent Prepare for Relocate（并发）**

选择要回收的 Region（ZGC 也是 Region 化的，叫 ZPage，分 Small/Medium/Large 三种），建立**转移表（Forwarding Table）**。

  

**5. Pause Relocate Start（STW，< 1ms）**

转移根引用指向的对象。

  

**6. Concurrent Relocate（并发）**

并发拷贝对象到新 Region。业务线程读到旧地址的对象时，**读屏障触发**，走 slow path 完成转移或修正指针（自愈）。转移完的旧 Region 立刻释放，物理内存归还操作系统。

  

**关键差异**：G1 是"标记 + 拷贝"分两个 GC 周期做（并发标记周期决定回收哪些 Region，然后靠若干次 STW 的 Mixed GC 拷贝），ZGC 是**拷贝也并发**。

### **五、分代 ZGC（JDK 21，重大升级）**

  

早期 ZGC 是**单代**的——不区分 Young / Old，每次都扫全堆。这在有大量短命对象的业务（Web 服务、微服务几乎都是）下**吞吐和内存效率都远差于 G1**：短命对象本该在 Young 区快速回收，单代 ZGC 却要把它们和长命对象一起管理，浪费严重。

  

**JDK 21 的分代 ZGC（`-XX:+ZGenerational`）**引入 Young / Old 分代:

  

- Young 区独立回收，短命对象快速释放

- Old 区回收频率大幅降低

- **吞吐提升 10%+，Young GC 频率也降下来了**

  

JDK 23 开始，非分代 ZGC 被废弃，JDK 24 移除。**现在选 ZGC = 分代 ZGC，没别的选**。

### **六、参数调优**

  

ZGC 的哲学是"少调参"，大部分场景开箱即用：

  

```

-XX:+UseZGC

-XX:+ZGenerational # JDK 21+, 强烈建议开

-Xms32g -Xmx32g # 固定堆大小

-XX:SoftMaxHeapSize=28g # 软上限,提前触发 GC 防止逼近硬顶

-XX:ConcGCThreads=2 # 并发 GC 线程,默认约 CPU 核数的 1/8

-XX:ParallelGCThreads=8 # STW 阶段线程,一般对齐核数

-XX:+AlwaysPreTouch # 启动预分配,避免运行时 page fault

-XX:-ZUncommit # 关闭内存归还,减少抖动(内存充裕时)

-XX:ZCollectionInterval=60 # 强制 GC 间隔上限(秒),防止长期不触发

-Xlog:gc*:file=/log/zgc.log

```

  

**核心思路**：

  

- `SoftMaxHeapSize` 是 ZGC 特有的软上限，堆用到这个值就积极 GC，避免撞硬顶导致 Allocation Stall（分配失速，是 ZGC 唯一会引发的"停顿"）。

- `ZUncommit` 默认开，会把空闲堆内存归还给 OS，对 K8s 环境省内存但可能带来抖动，稳态服务可以关。

>**抖动 = 堆空闲时还内存给 OS，下次需要时再要回来，这个"还→要"的过程触发 page fault 和 TLB 失效，带来延迟尖刺和内存曲线震荡。**

- ZGC 没有 `MaxGCPauseMillis`——不需要，停顿本来就 < 1ms。

- ZGC 没有 IHOP、Region Size 这些 G1 参数，触发策略是自适应的。

  

**监控要看什么**：

  

- **Allocation Stall**：分配速度超过 GC 速度时业务线程会被"暂停等内存"，日志里会打 `Allocation Stall`。一旦出现说明 GC 跟不上，需要增大堆或增加 `ConcGCThreads`。

- **GC 频率**：分代 ZGC 里 Young GC 应该占多数，Old GC 稀疏。

- **堆使用曲线**：应该是锯齿状且稳定，不应该有单调上升。

### **七、ZGC 的坑和适用边界**

  

**它的短板**：

  

- **吞吐 5~15% 损失**：读屏障是常态开销，无法消除。CPU 密集型（大数据计算、批处理）用 ZGC 亏。

- **内存占用高**：染色指针的多重映射 + Forwarding Table，实际 RSS 比 G1 高 10~20%。

- **CPU 占用高**：并发 GC 线程持续工作，云上按核收费的场景要算账。

- **不支持压缩指针（`-XX:+UseCompressedOops`）**：堆 ≤ 32G 时 G1 能用压缩指针省一半引用内存，ZGC 不行，实际可用堆更小。

  

**真正适合 ZGC 的场景**：

  

1. **堆 ≥ 64G 甚至 TB 级**：大缓存服务（本地缓存 Caffeine、Ehcache）、图数据库、搜索引擎节点。

2. **延迟敏感的核心业务**：高频交易撮合、实时风控、广告竞价、游戏战斗服。

3. **P99 / P999 是硬 SLA**：金融、支付类系统，宁可损失吞吐也要保停顿。

4. **JDK 21+ 环境**：能用分代 ZGC，才发挥出实力。

  

**不适合的**：中小堆（< 32G）、吞吐优先的批处理、CPU 已经打满的高负载服务、还在 JDK 8/11 的老系统（用不上分代 ZGC）。

### **八、和 G1 / Shenandoah 的对比**

  

| 维度 | G1 | ZGC（分代） | Shenandoah |
|-----|-----|-----|-----|
| STW 停顿 | 几十 ms | < 1 ms | < 10 ms |
| 停顿与堆大小 | 正相关 | 无关 | 无关 |
| 吞吐损失 | ~5% | ~10% | ~10% |
| 屏障类型 | 写屏障（SATB + RSet） | 读屏障（染色指针） | 读写屏障（Brooks 指针） |
| 堆大小 sweet spot | 4G~64G | 32G~16TB | 类似 ZGC |
| 成熟度 | 生产标杆 | JDK 21 后成熟 | Red Hat 主推，OpenJDK 有 |
| 压缩指针 | 支持 | 不支持 | 支持 |

  

Shenandoah 和 ZGC 思路类似但技术选型不同（Brooks 指针 vs 染色指针），国内用得少，主要在 Red Hat 生态和 OpenJDK 部分发行版里。

  

---

  

一句话总结 ZGC：**用"染色指针 + 读屏障 + 全并发"换来了"停顿恒定 < 1ms 且与堆大小无关"的能力，代价是 5~15% 吞吐和额外内存**。**JDK 21 之后的分代 ZGC 才是生产可用形态**，选它的判断标准就三个：**堆够大（≥64G）、延迟够苛刻（P99 < 10ms 是硬指标）、能容忍吞吐损失**——三个都满足才上，否则老老实实用 G1。


> 5~15% 吞吐和额外内存的原因？

- **Load Barrier（最大头）**
    - 每次读取对象引用，都可能经过读屏障。
    - JIT 会优化掉大量无意义的屏障，但热点代码里仍然会保留不少。
    - 这是 ZGC 最独特、也是最持续的运行时开销。
- **并发标记、并发重定位**
    - GC 线程一直和业务线程抢 CPU。
    - 如果机器 CPU 核数不多，这部分影响会更明显。
    - 即使没有任何读屏障，并发 GC 本身也会消耗算力。
- **对象重定位与引用修正**
    - 搬迁对象需要复制数据。
    - Load Barrier 发现旧引用时，需要查询 Forwarding 信息并修正引用。
    - 虽然不是每次读取都会发生，但 GC 周期内会持续存在。
- **缓存、TLB 等微架构影响**
    - 额外的屏障逻辑会增加指令数量。
    - 有时会影响 CPU 的分支预测、缓存命中等。
    - 这部分通常比较小，但也是吞吐损失的一部分。

### **补充：传统收集器 vs ZGC 的"引用更新"方式**

同样是"对象搬迁（移动 / 压缩）"，传统收集器与 ZGC 处理**搬迁后旧引用**的方式截然不同，这是 ZGC 停顿恒定的关键。

**传统收集器（Serial / Parallel / G1 / CMS 的整理阶段）**：搬迁对象后，必须**暂停应用线程，集中把所有指向旧地址的引用一次性改写成新地址**。这一步必须 STW——因为"一边搬、一边还有业务线程按旧地址读"会读到错误数据。堆越大、需要修正的引用越多，这段 STW 越长。**"停顿与堆大小正相关"的根源之一就在这里。**

**ZGC**：把"对象搬迁"和"引用修正"都**打散到并发阶段**——

- 搬迁（Concurrent Relocate）由 GC 线程**并发**完成；
- 旧引用**不集中修正**，而是靠**应用线程自己的读屏障**在**下次读到该引用时**顺手修正（**自愈 self-healing**）：读到染色不对的指针 → 查 Forwarding Table → 改写为新地址并回写字段。谁读到、谁修正，把一次大 STW 拆成无数次几纳秒的"顺手活"。

所以 ZGC 的停顿里**不含"集中更新引用"这一步**，只剩根扫描等极少几处，且这几处**只与线程数 / 根数量相关，与堆大小无关**——这才是"停顿恒定 < 1ms"的机制来源。

> 别理解成"ZGC 完全无 STW"：Pause Mark Start / Mark End / Relocate Start 仍是 STW，只是都极短（< 1ms）。ZGC 是**把停顿压到极短且与堆解耦**，不是消灭停顿。
