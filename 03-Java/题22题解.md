### **Spring 通过三级缓存"提前暴露半成品 Bean"来解决单例 Setter 循环依赖，但构造器注入在 Bean 实例化那一步就要求依赖已经存在，此时半成品都还没生成、放不进缓存，所以循环无法打破，直接抛 `BeanCurrentlyInCreationException`。**

  

## **三级缓存是什么**

  

Spring 的 `DefaultSingletonBeanRegistry` 里维护着三个 Map，就是常说的三级缓存：

  

| 缓存 | 字段名 | 存放内容 | 阶段 |

|---|---|---|---|

| 一级 | `singletonObjects` | 完全初始化好的成品 Bean | 最终态 |

| 二级 | `earlySingletonObjects` | 已经暴露出去的半成品 Bean（属性未填充） | 中间态 |

| 三级 | `singletonFactories` | 生产 Bean 早期引用的 `ObjectFactory`（工厂） | 起始态 |

  

获取 Bean 时，`getSingleton` 会按 **一级 → 二级 → 三级** 的顺序查：一级有就直接返回；一级没有就查二级；二级也没有就从三级拿工厂，调用 `getObject()` 生成早期引用，**升级到二级**，同时把三级里的工厂移除。

  

## **循环依赖的执行流程**

  

假设 A 依赖 B，B 又依赖 A，两个都是 Setter 注入。

  

**第一步：创建 A。** Spring 调用 `createBean(A)`，先通过构造器 `new` 出 A 的实例（此时属性还没填充，是个"半成品"）。紧接着 Spring 把一个能返回 A 早期引用的 `ObjectFactory` 放进**三级缓存** `singletonFactories`。这一步叫 **"提前暴露"**。

  

**第二步：填充 A 的属性，发现要注入 B。** 于是递归去 `getBean(B)`。

  

**第三步：创建 B。** 同样先 `new` 出 B 实例，也把它的工厂放进三级缓存。然后填充 B 的属性，发现要注入 A。

  

**第四步：B 反过来 `getBean(A)`。** 这次一级缓存里没有 A（A 还没初始化完），但**三级缓存里有 A 的工厂**！于是调用工厂拿到 A 的早期引用，把它升级到二级缓存，然后注入给 B。B 就这样"用半成品 A"完成了属性填充，走完初始化，成品放入一级缓存。

  

**第五步：回到 A。** B 已经成品了，注入给 A，A 也完成初始化，进入一级缓存。循环依赖破解完成。

  

## **为什么需要三级而不是二级**

  

很多人会问：既然半成品能解决问题，为什么不直接用二级缓存放早期引用，非要多一层工厂？

  

答案是 **AOP 代理**。如果 A 需要被 AOP 增强（比如加了 `@Transactional`），那么真正要注入给 B 的应该是**代理对象**，不是原始对象。三级缓存里放的 `ObjectFactory` 里封装了这段逻辑：

  

```java

addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));

```

  

`getEarlyBeanReference` 会调用 `SmartInstantiationAwareBeanPostProcessor`（比如 `AbstractAutoProxyCreator`），在这里判断是否需要提前生成代理。**只有真正被别人循环引用时，工厂才会被调用一次生成代理，然后把代理对象升级到二级缓存，保证同一个 Bean 无论被谁拿到都是同一个代理引用**。如果没有循环依赖，工厂根本不会执行，代理会在正常的 `initializeBean` 阶段生成。三级缓存本质上是一个 **"延迟决策 + 唯一性保证"** 的设计。

  

## **为什么构造器注入解决不了**

  

关键在于**"提前暴露"这个动作发生在实例化之后、属性填充之前**。看一下 `doCreateBean` 的核心流程：

  

```

1. createBeanInstance(...) ← 调用构造器，new 出实例

2. addSingletonFactory(...) ← 放进三级缓存，提前暴露

3. populateBean(...) ← 填充属性（@Autowired 字段/setter）

4. initializeBean(...) ← 初始化回调、AOP 增强

```

  

**构造器注入的依赖，是在第 1 步 `createBeanInstance` 里就要解析并传入构造函数的**。也就是说，当 Spring 想 `new A(B b)` 时，它必须先 `getBean(B)`；而 B 又要 `new B(A a)`，反过来 `getBean(A)`——此时 A 连 `new` 都还没完成，**根本没走到第 2 步"暴露到三级缓存"那里**，三级缓存里查不到 A 的工厂。Spring 发现 A 正在创建中（`singletonsCurrentlyInCreation` 里有 A），却又要再次创建 A，直接抛 `BeanCurrentlyInCreationException`。

  

一句话总结：**Setter/字段注入是"先有壳，后填肉"，可以把壳先暴露出去；构造器注入是"壳和肉一起浇筑"，没法拆开，所以循环破不了。**

  

## **额外几个易被追问的点**

  

- **`@Async` 修饰的 Bean 循环依赖也会失败。** 因为 `@Async` 的代理是通过 `AsyncAnnotationBeanPostProcessor` 在 `postProcessAfterInitialization`（初始化之后）生成的，而不是走 `getEarlyBeanReference`，所以三级缓存暴露的还是原始对象，最后一级缓存里放的却是代理对象——Spring 会检测到"你早期暴露的引用和最终引用不一致"，抛 `BeanCurrentlyInCreationException` 并提示 `has been injected into other beans […] in its raw version`。

  

- **Spring Boot 2.6 之后默认禁用循环依赖。** `spring.main.allow-circular-references=false` 是默认值，遇到循环依赖直接启动失败，官方鼓励用户从设计上消除。想临时救急可以设为 `true`，但不推荐。

  

- **`@Lazy` 是构造器循环依赖的救命稻草。** 在构造器参数上加 `@Lazy`，Spring 会注入一个代理，真正调用方法时才去解析目标 Bean，从而绕过循环。但这只是缓解，最好还是重构代码。

  

- **Prototype 作用域的循环依赖 Spring 不管。** 因为原型 Bean 每次都新建，没有"单例缓存"这个概念，直接抛异常。

  

## **面试口述要点**

  

口述时可以按这个骨架讲：**先描述现象——启动报 `BeanCurrentlyInCreationException`；然后引出三级缓存 `singletonObjects`、`earlySingletonObjects`、`singletonFactories`，用 A/B 例子说清楚"提前暴露半成品"如何打破循环；接着解释三级的必要性——为 AOP 代理保留延迟决策的空间；重点讲构造器为什么不行——`createBeanInstance` 阶段就要拿到依赖，此时还没来得及 `addSingletonFactory`，缓存里查不到；最后补几个加分点：Spring Boot 2.6 默认禁用、`@Lazy` 救急、`@Async` 循环依赖坑、字段/Setter 注入才能触发三级缓存机制。** 讲到这个程度，基本可以判定是深入读过源码的候选人。
