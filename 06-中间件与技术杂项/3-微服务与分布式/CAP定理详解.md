# CAP 定理详解 — Consistency · Availability · Partition Tolerance

> [!abstract] CAP 定理 — Consistency、Availability、Partition Tolerance（一致性、可用性、分区容错）
> 分布式系统在网络分区发生时，只能在一致性（C）和可用性（A）之间二选一。
> 面试高频：Eureka/Zookeeper/Nacos 选型、Redis Cluster 丢数据、注册中心为什么选 AP。

## 一句话定义

> 分布式系统在网络**分区**（P）发生时，只能在**一致性**（C）和**可用性**（A）之间二选一。P 无法避免，所以实际是「**P 必选，C/A 二选一**」。


>网络分区：**集群里节点之间的网络断了，整个系统被切成几块互相联系不上的"孤岛"**。

## 三个字母的含义

| 字母 | 含义 | 大白话 |
|------|------|--------|
| **C** Consistency | 一致性 | 所有节点同一时刻看到同一份数据 |
| **A** Availability | 可用性 | 任何请求都能得到响应（不保证是最新的） |
| **P** Partition tolerance | 分区容错 | 节点间网络断了，系统还能继续工作 |

## 为什么是「三选二」，而不是「三选一」

**核心逻辑链**：

1. 网络分区**一定会发生**（机房断电、交换机故障、网络抖动），P 无法避免，**必须选 P**。
2. 一旦分区发生，数据就分裂在两边的节点上，C 和 A 只能保一个：
   - 选 **C**：两边数据对不上，就拒绝服务等网络恢复 → **牺牲可用性**
   - 选 **A**：两边各自继续响应，但数据可能不一致 → **牺牲一致性**

> [!warning] 常见误解
> CAP 的取舍只在**发生分区时**生效，不是平时就缺一个字母。
> 分区没发生时，系统可以同时做到 C 和 A。
> 严格说法是「**AP 系统 / CP 系统**」，不是「缺 C 或缺 A 的系统」。

## 分布式一致性的演进：BASE 理论

CAP 的 C 是**强一致性**，现实中很难做到，于是演化出 **BASE**（Basically Available 基本可用 + Soft state 软状态 + Eventually consistent 最终一致）：

- **基本可用**：核心功能保得住，非核心可以降级（比如双十一砍掉推荐位）
- **软状态**：允许中间状态存在（数据同步有延迟）
- **最终一致**：经过一段时间，数据最终收敛到一致

> BASE 本质上是 CAP 中 AP 方案的延伸——牺牲强一致，换可用性 + 最终一致。

**典型应用**：MySQL 主从复制（延迟几毫秒~几秒最终一致）、Redis 主从、消息队列削峰。

## 面试话术

> **面试官**：网络分区发生时，为什么一致性和可用性会产生冲突？

**回答**：

网络分区是指集群节点之间的通信中断，这是分布式系统中无法避免的客观现象。

当分区发生时，假设节点 A 和节点 B 之间网络断开：

- 此时客户端向 A 写入了新数据，B 还是旧数据
- 这时候系统面临一个二选一的问题

**选择保一致性**：B 发现自己和 A 失联，无法确认数据是否最新，就拒绝响应请求，等网络恢复后再同步。服务不可用，但数据一定是准确的。典型如 Zookeeper，选举期间拒绝服务，大概 30~120 秒。

**选择保可用性**：B 继续响应请求，但返回的可能是旧数据。服务一直可用，但数据存在短暂不一致。典型如 Eureka，网络分区期间仍然返回注册信息，但可能是几分钟前的旧数据。

两边数据已经不同步，你又必须立刻决定怎么处理请求，所以 C 和 A 只能取其一，这就是冲突的根源。

**补充一点**：CAP 的冲突只在分区期间成立，正常情况下 C 和 A 是可以同时满足的。所以不是"三者永远不可兼得"，而是"分区发生时，C 和 A 必须做取舍"。

> **面试官**：注册中心为什么一般选 AP？

**回答要点**：服务注册信息短暂不一致可以接受（拿到的地址可能旧一点，但调用方重试/负载均衡可以兜底），但服务发现整体不可用是致命的（新服务找不到、调用全部失败）。所以 Eureka、Nacos 注册中心都偏 AP；而 Zookeeper 做分布式锁、配置中心这类强一致场景是 CP。

**为什么「旧信息」能接受、「没信息」不能接受**：
- **拿错地址可自愈**：A 调 B1 失败 → 负载均衡/重试自动换 B2 → 成功，代价只是一次重试
- **拿不到地址不可自愈**：没有可重试的目标，依赖该服务的调用全部失败 → 连锁雪崩
