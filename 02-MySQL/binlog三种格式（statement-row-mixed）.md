# binlog 三种格式（statement / row / mixed）

binlog 记录的是**逻辑日志**（区别于 redo log 的物理日志），但「怎么记这条逻辑」有三种格式，由参数 `binlog_format` 控制。这三者的取舍是主从复制、数据恢复、自增锁一致性等一系列问题的根子，面试里被反复引用（见 [[如何设置 innodb_autoinc_lock_mode]]、[[题29题解]] gh-ost 选型、[[题33题解]]），所以单独讲清。

---

## 三种格式一句话定性

| 格式 | 记录的是什么 | binlog 体积 | 主从一致性 |
|------|-------------|:----------:|:---------:|
| **STATEMENT** | 原始 SQL 语句本身 | 小 | 不安全（有不确定函数就出问题） |
| **ROW** | 每一行被修改后的**具体数据**（前后镜像） | 大 | 安全（记的是结果，不重放逻辑） |
| **MIXED** | 默认走 statement，遇到不安全语句自动切 row | 中 | 安全（两者折中） |

MySQL **5.7 及之前默认 STATEMENT**，**8.0 起默认 ROW**——这个默认值变更是很多连锁结论的前提（比如 8.0 才敢把 `innodb_autoinc_lock_mode` 默认改成 2）。

---

## STATEMENT：记语句

binlog 里存的就是执行过的原始 SQL，比如 `UPDATE t SET c=c+1 WHERE id<100`。从库把这条语句**重新执行一遍**来复现数据。

**优点：**
- 日志量小，一条语句改一万行也只记一行 SQL
- 可读性好，`mysqlbinlog` 出来就是 SQL

**致命缺陷——语句里含"不确定因素"时主从会不一致：**
- `NOW()`、`SYSDATE()`、`RAND()`、`UUID()` 这类**非确定函数**，主库和从库执行的时刻/随机种子不同，算出的值就不同
- `LIMIT` 不带 `ORDER BY`、或依赖存储引擎返回顺序的语句，主从命中的行可能不一样
- `INSERT ... SELECT` 配合自增列，在 `innodb_autoinc_lock_mode=2`（交错分配）下，从库重放时算出的自增序列可能和主库不同 → **主从数据不一致**（这正是自增锁那道题的因果链，详见 [[如何设置 innodb_autoinc_lock_mode]]）

## ROW：记行

binlog 里存的是**被改动的每一行的实际数据**——UPDATE 会同时记录改动前的镜像（before image）和改动后的镜像（after image），DELETE 记被删行的完整内容，INSERT 记新插入行的完整内容。从库直接**按行覆盖**，不重放任何 SQL 逻辑。

**优点：**
- **绝对安全**——记的是"结果长什么样"，不存在"重放逻辑算出不同值"的问题，任何函数、任何顺序都一致
- 数据恢复、CDC 增量订阅（[[CDC（Canal）详解]]）、gh-ost 在线改表都强依赖它——它们要的就是"每一行到底变成了什么"

**代价：**
- **日志量大**：一条 `UPDATE t SET c=c+1`（不带 WHERE）改一万行，statement 记 1 行 SQL，row 要记一万行的前后镜像
- 大事务/大批量操作会让 binlog 暴涨，也放大主从延迟

> [!tip] binlog_row_image 可以瘦身
> ROW 格式下 `binlog_row_image` 控制记多少列：`FULL`（默认，记全部列）、`MINIMAL`（只记主键 + 被改的列）、`NOBLOB`。生产上大表可用 `MINIMAL` 显著压缩 binlog 体积。

## MIXED：混合

默认用 STATEMENT，**MySQL 自动判断**：一旦语句里出现前面说的不确定因素（`UUID()`、`NOW()` 在某些场景、涉及 UDF、`INSERT ... SELECT` 等），就**自动切成 ROW** 记这一条。

**定位：** 想要 statement 的小体积，又要 row 的安全性，让引擎自己挑。但"什么时候切"是引擎判断的，行为不如 ROW 那样可预测，所以现代生产环境（尤其 8.0）大多**直接上 ROW**，图个确定性和对 CDC/恢复的友好。

---

## 为什么现在生产普遍用 ROW（面试话术）

面试问"你们线上 binlog 用什么格式"，标准回答的因果链是这样的：

先说 statement 为什么被淘汰——它记的是 SQL 语句，主从复制时从库要**重新执行**，只要语句里有 `NOW()`、`RAND()`、不带 `ORDER BY` 的 `LIMIT`、或者自增交错分配这类不确定因素，主从算出来的结果就可能不一样，直接导致数据不一致。这个坑太隐蔽，排查成本极高。

再说 ROW 强在哪——它不记逻辑、只记"每一行最后变成了什么样"，从库按行覆盖，天然不存在重放偏差，怎么都一致。而且现在我们普遍用 Canal、gh-ost 这些工具做增量同步和在线改表，它们本质都是订阅 binlog 拿"行级变更明细"，**必须 row 格式**才能拿到每行数据。

最后落到取舍——ROW 唯一的代价是日志体积大，但这个可以用 `binlog_row_image=MINIMAL` 缓解，而且现在磁盘和网络都不是瓶颈了。所以从 8.0 开始默认就是 ROW，我们线上也统一 ROW。说白了就是：**用可控的体积成本，换主从一致性的确定性和对生态工具的兼容**。
