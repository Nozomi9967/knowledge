## T1 · Redisson 分布式锁的实现原理？看门狗是怎么工作的？

### 面试官想听什么

三层都要点到，缺一层就是"用过但没懂"：**① 加锁为什么是原子的（Lua）→ ② 为什么用 Hash 不用 String（可重入）→ ③ 过期时间和业务时长怎么调和（看门狗）**。

### 参考答案（口述版）

> "Redisson 的锁我理解它是把三件事包在一起的。
>
> 第一件是**原子加锁**。它不把加锁拆成 SETNX 再 EXPIRE 两步，而是整段用 Lua 脚本发给 Redis 执行，Redis 单线程处理脚本，所以"判断锁存不存在 + 写入 + 设过期时间"这个序列在别的客户端看来是一瞬间完成的，不会有加完锁还没来得及设 TTL 就宕机导致死锁的情况。
>
> 第二件是**用 Hash 结构存锁**，这是很多人漏掉的点。它不是 `SET lock uuid`，加锁 Lua 里做的是：锁不存在就 `HINCRBY lockKey 线程标识 1`（新建时 Hash field 自动从 0 变 1）+ `PEXPIRE` 设 TTL；同一个线程再进来，`HEXISTS` 命中就再 `HINCRBY` 加一。所以 field 存"客户端 ID + 线程 ID"用来标识持有者，value 存重入次数，**一个结构同时解决了"这锁是谁的"和"他重入了几次"两件事**。解锁时 count 减一，减到 0 才真删 key，没减到 0 只刷新过期时间。
>
> 第三件就是**看门狗**。先说清一件事：我调无参 `lock()` 时，Redis 里这把锁的 TTL **就是实打实的 30 秒**，不是什么"不设过期"或者"-1"——底层 Lua 收到的 `pexpire` 参数就是 30000 毫秒。看门狗做的事是：加锁成功后，客户端在自己 JVM 里注册一个续期任务，每隔 `lockWatchdogTimeout / 3` 也就是 10 秒触发一次，触发时跑一段 Lua 去问 Redis"这把锁还在不在我手里"，在的话就把 TTL 重新推回 30 秒，然后把自己排到下一个 10 秒之后。所以业务只要没做完，锁的剩余时间会一直在 20 到 30 秒之间滚动，永远掉不到 0；一旦 `unlock()`，续期任务被取消，锁正常释放，等待者通过订阅解锁消息被唤醒。
>
> 有个坑我踩过：**看门狗只在没传 leaseTime 的时候启动**。源码里就一个分支——`if (leaseTime > 0) 把 internalLockLeaseTime 记成用户给的值 else 才 scheduleExpirationRenewal`。所以写成 `lock(10, TimeUnit.SECONDS)` 意思是"我明确告诉你这锁最多持有 10 秒"，Redisson 就不续了，10 秒一到锁直接消失。**而且它照样是无限阻塞地等锁**——那个 10 秒是持有时间不是等待时间，想控等待只能用三参的 `tryLock(waitTime, leaseTime, unit)`。这点很致命：秒杀里 `lock(10, SECONDS)` 拿到锁的人 10 秒后被强制释放，没拿到的人还在无限等。"

### 关键数字（说错会扣分）

| 项 | 值 | 记忆点 |
|---|---|---|
| `lockWatchdogTimeout` | **30 秒** | 默认锁 TTL |
| 续期间隔 | **10 秒** = 30 / 3 | 不是"每 30 秒"、不是"每 5 秒" |
| 每次续期后 TTL | 重置回 **30 秒** | TTL 在 [20s, 30s] 滚动 |
| 锁的数据结构 | **Hash**，field=客户端+线程 ID，value=重入计数 | 说 String 就丢可重入这一分 |
| 加锁/解锁/续期 | **都是一段 Lua 脚本** | 原子性的唯一来源 |
| 无参 lock() 时 Redis 里的 TTL | **30 秒**（❌ 不是 -1、不是"不设过期"） | `-1` 只在 Java 方法内部当哨兵，进 Lua 前已被换成 30000 |

> [!note] 上面这张表的 30s / 10s / 30÷3 与「TTL 不是 -1」三条，已核对 Redisson master 源码（`Config.java:82`、`RenewalTask.java:68`、`RedissonLock.java:173-178 / 214-224`）与官方 Javadoc。完整勘误记录见 [[Redisson详解]] 的「源码勘误」标注块。

### 可能的追问 & 一句话答

- **"为什么不用 `SET lock uuid EX 30` 就够了？"** → 那样只能记"谁持有"，记不了"持有几次"，可重入就得自己在客户端维护计数，Redis 侧没有单一事实来源。
- **"看门狗线程在哪个进程里？Redis 那边有它的东西吗？"** → 在**客户端 JVM** 里，是 Redisson 的 Netty 定时任务；Redis 侧只有那把 Hash 锁和它的 TTL，服务端没有任何"看门狗"。
- **"Redis 是单线程，Lua 脚本里的 HINCRBY 会阻塞别人吗？"** → 会，Lua 执行期间整个实例不处理别的命令，所以脚本要短，这也是它原子性的代价。
- **"锁被别的进程误删怎么办？"** → 释放走 Lua：先 `HEXISTS` 校验持有者再减计数，身份对不上直接返回，不会删别人的锁。

## T2 · 如果业务执行时间超过了锁的过期时间，会出什么问题？怎么解决？

### 面试官想听什么

这题不看你背方案，看你**能不能把事故链讲清楚**。华为很吃"推演"这一套——能把 A 线程 35 秒、B 线程 30 秒交错讲明白，比列四条措施强得多。

### 参考答案（口述版）

> "先讲会怎么坏。假设锁 TTL 30 秒，线程 A 拿到锁，但因为一次 Full GC 或者一条慢 SQL，业务实际跑了 35 秒。第 30 秒 Redis 里这把锁自然过期，等待者 B 立刻加锁成功开始写。到第 35 秒 A 醒过来，它自己是不知道自己已经"过期"了的，会继续往下写，也可能在最后无条件 `unlock()`——如果不管证，它会把 B 的锁删掉，于是 B 的临界区又对 C 敞开。所以这个问题最狠的地方不是"两个线程同时写"一次，而是**失效会沿着锁往下传染**，互斥性被连续打破，数据直接错乱。
>
> 我的处理分三层。
>
> 第一层是**根本不解法——让锁别过期**，也就是用无参 `lock()` 交给看门狗。只要我的客户端进程还活着、业务还在跑，每 10 秒就把 TTL 推回 30 秒，理论上不存在"业务没做完锁先掉"。但要说清它的边界：**看门狗是客户端侧的**，如果持有锁的那个 JVM 整个被 kill 掉，续期任务就停了，锁最多 30 秒后自动释放，不会永久死锁——这恰恰是它设计得好的地方。
>
> 第二层是**主动设一个够用的 leaseTime**。秒杀这种我知道最长路径大概多少毫秒的业务，我更倾向 `tryLock(3, 30, TimeUnit.SECONDS)`，等最多 3 秒、拿到最多持 30 秒，过期时间按业务 **P999 耗时再留 50%～100% 缓冲**估。这里是个明确的取舍：用固定 leaseTime 就放弃了看门狗保护，换来的是"最坏情况有上界"，不会出现某个进程卡死就一直占着锁。我选上界可控。
>
> 第三层是**不把锁当唯一防线**。锁只保证同一时刻一个进程在操作，它管不了"这个进程是不是已经被判死刑了还在写"。所以数据库那一层我一定留 `UPDATE sku SET num = num - #{num} WHERE id = #{id} AND num >= #{num}` 这种带条件的原子写，靠影响行数判断成败。就算锁失效、两个请求同时冲进来，数据库自己不会把库存扣成负数——锁管效率，SQL 管正确性。"

### 失分提醒

- ❌ 只答"用看门狗续期"就结束 → 这是 T1 的答案，面试官问的是**过期之后**，你没接住。
- ❌ 漏掉"解锁会误删别人的锁"这一层 → 讲不出传染链，说明没真想过。
- ⚠️ 别说"Redis 分布式锁能保证绝对互斥" → 严格说不能（T2 的 GC 停顿、T3 之后的主从切换都是反例），要落到"锁 + 数据库条件更新"双保险。这条**说出来是加分**，说明你知道边界。

## T3 · 你这把锁的粒度是什么？两个不同商品的秒杀会互相阻塞吗？加锁不就退化成单线程了，性能怎么保证？

### 面试官想听什么

表面问粒度，实际问三件事：**你项目里到底是怎么写的**、**你知不知道锁在整条链路的第几层**、**你有没有"锁是最贵的兜底不是最便宜的防线"这个意识**。

### 参考答案（口述版 · 含坦白话术）

> ⚠️ 真实代码是全局单锁，**先坦白、再讲你会怎么改**，比背"我用了商品维度"安全得多——面试官会让你讲代码或者追问一句就穿帮。

> "先说实话：我现在这版实现里锁 key 是个固定字符串 `seckill-order-lock`，所以不同商品**会**互相阻塞，等于把整个秒杀串行化了。这是我项目里我自己列在最高优先级要修的问题之一，原因有两个。
>
> 第一，粒度错了。锁的目标是保护"某个商品的库存"这个共享资源，那锁的 key 就应该带上商品维度，写成 `seckill-order-lock:{goodsId}`。改完之后不同商品的请求落在不同 key 上，Redis 集群里 16384 个哈希槽是按 key 做 CRC16 算槽位的，不同商品的锁天然散在不同节点上，既保持了同商品互斥，又把压力摊开了。反过来，全局 key 会把所有流量钉在一个槽、一个主节点上，那个节点自己就成了热点。
>
> 第二，更进一步的话，这把锁其实**可以不要**。我原来之所以加锁，是因为我把"查库存"和"扣库存"写成了两步——`HGET` 判断够不够，再 `HINCRBY` 扣，这两步之间有竞态窗口，两个线程可能同时读到还有货。正确的做法是把"判断 + 扣减"合成一段 Lua 脚本让 Redis 原子执行，或者干脆只用 `DECR` 的返回值判断：扣完小于 0 就是卖完了，再 `INCR` 回滚回去。Redis 单线程执行命令，这个判断本身就不需要外部互斥。**从"我加了把锁"升级成"我发现锁粒度错了、并且用原子操作把锁消掉了"**，这是我做完这个项目最大的收获之一。
>
> 至于"加锁不就成单线程了吗"——即使保持加锁，锁也不该是性能瓶颈，因为它在我整个链路的**最里面一层**。外面有几层在挡流量：网关的布隆过滤器先挡掉不存在的商品 ID，然后是 JWT 鉴权和 RBAC 校验，再到 Redis 预扣库存——这一层就能把九成以上抢不到货的无效请求直接返回"已售罄"，过了这关的才发 RocketMQ 排队，订单服务按自己的消费能力拉取。所以真正落到数据库这把锁上的并发量**基本等于库存数**，几十个请求抢 100 件货，锁竞争几乎没有。**锁是最后一道兜底，不是第一道防线**，前面每多挡一层，最后一层就可以做得越重、越安全。"

### 三种粒度对照（被追问时用）

| 粒度 | key 形态 | 并发度 | 结论 |
|---|---|:---:|---|
| 全局单锁 | `seckill-order-lock` | ❌ 极低 | ⚠️ **你现在代码里的状态**，必须知道是错的 |
| 商品维度 | `seckill-order-lock:{goodsId}` | ✅ 高 | 及格答案：同商品互斥、异商品并行 |
| 无锁（Lua 原子） | 不需要 key | ✅ 最高 | 满分答案：把"查+扣"压进一次原子操作 |
| 用户维度 | `lock:user:{userId}` | — | ❌ **答错了**：防的是同一用户重复请求（幂等），跟库存超卖无关 |

> "用户维度"是这题最常见的失分点——用户维度的锁不解决超卖，因为超卖的竞争方是**不同用户对同一个商品**。要说清楚这点，反而是加分。

### 可能的追问 & 一句话答

- **"那幂等呢？同一个人连点两次？"** → 靠用户 + 商品维度的去重 key（网关 `INCR` + TTL）判重，我目前缺的是 `seckill_order` 表上 `(username, goods_id)` 唯一索引兜底——Redis 抖一次幂等就漏了，这是我能想到的下一个风险点。
- **"锁多了会不会把 Redis 压垮？"** → 锁操作就是普通 Redis 命令，量级跟库存数走不是跟流量走；真正要防的是热点 key，用商品维度打散 + 本地缓存兜一层。

## 延伸四题（有余力再看，按出现概率排序）

| 题 | 一句话答 | 出处 |
|---|---|---|
| 为什么用 Redisson 不用手写 SETNX？ | 手写要自己解决三件事：Lua 原子性、续期、可重入；Redisson 内置，而且我同时还用了它的 `RBloomFilter` 做网关 URI 校验，一套客户端解决两个问题 | [[Redisson详解]] §场景一 |
| 主从异步复制下锁会丢，RedLock 你怎么看？ | Master 加锁成功但没同步就宕机，新 Master 上没有这把锁，第二个人又能加——互斥破了。RedLock 用 5 个独立节点、过半成功才算持锁来缓解，但它依赖系统时钟，Kleppmann 指出时钟跳跃和 GC 停顿仍能击穿。所以资金级用 ZK/etcd，防重限流用单节点 Redisson 够了 | [[Redisson详解]] §RedLock |
| Redisson 和 Jedis / Lettuce 什么区别？ | 定位不同：Jedis/Lettuce 是"把 Redis 命令递过去"的客户端，Redisson 是建在 Redis 上的内存数据网格，把 `RLock`/`RMap`/`RSemaphore` 做成 `java.util.concurrent` 风格的高阶抽象 | [[Redisson详解]] §Q4 |
| `tryLock` 和 `lock` 什么时候用哪个？ | `lock()` 无限阻塞且不响应中断，适合必须拿到的场景；秒杀要用 `tryLock(waitTime, leaseTime, unit)`，等 3 秒拿不到就返回"人多稍后再试"，**快速失败比排队更重要**，因为排队只会让后面所有人 RT 一起烂 | [[Redisson详解]] §三种锁 API |

## 背诵优先级

1. **T1 看门狗的数字**（30s / 10s / 30÷3）——错了直接判"没读过源码也没真用过"。
2. **T2 事故链的完整推演**（A 35 秒、B 第 30 秒进场、A 醒来误删 B 的锁）——这是"讲因果链不罗列要点"的标准练习。
3. **T3 的坦白话术**——提前想好"我代码里这里是错的，我是这么发现和怎么打算改的"，比硬撑安全。**华为面试很吃"知道自己不知道什么"**。

> [!note] 与你的历史失分模式对照
> 你的 Redis 卷 Q38/Q39/Q40（分布式锁板块）均分 **7.3**，是全卷较强的板块；但整卷高频硬伤之一是**追问作答率低**（Q6/Q12/Q20/Q21/Q23 追问空着）。这三题是按"一题带两三个追问"的形式排的，练的时候**必须把追问一起开口说出来**，只答主干等于没练。
