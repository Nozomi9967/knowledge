### **核心原因：这四种操作符的边界值构成了「单点区间」，在该点上后续列依然保持 B+ 树的有序性**

`>=`、`<=`、`BETWEEN`、`LIKE` 前缀匹配之所以不会中断最左匹配，是因为它们都包含**边界等值点**——即条件中隐含了一个 `= 边界值` 的情况。在联合索引的 B+ 树中，当前导列取某个确定值（等值）时，后续列是**有序的**，因此优化器可以继续利用后续列的索引进行区间定位。而 `>` 和 `<` 是严格不等式，不存在任何等值边界点，后续列在整个范围内都是无序的，所以匹配中断。 [博客园](https://www.cnblogs.com/lyn8100/p/18237491) [JavaGuide](https://javaguide.cn/database/mysql/mysql-index.html)

### 联合索引 B+ 树的排序规则

要理解这个问题，首先需要看清联合索引在 B+ 树叶子节点中的实际排列方式。以联合索引 `(a, b, c)` 为例，假设有如下数据，它们在叶子节点中按联合键值排列：

| 序号 | a | b | c |
|:---:|:---:|:---:|:---:|
| 1 | 1 | 1 | 1 |
| 2 | 1 | 2 | 3 |
| 3 | 1 | 2 | 5 |
| 4 | 2 | 1 | 2 |
| 5 | 2 | 3 | 1 |
| 6 | 3 | 1 | 4 |
| 7 | 3 | 2 | 2 |

从中可以观察到三个层次的有序性：

- **a 列全局有序**：1, 1, 1, 2, 2, 3, 3 — 从左到右递增。
- **b 列局部有序**：仅在 a 值相同时才有序。例如 a=1 时 b 为 1, 2, 2（递增）；但整体看 b 是 1, 2, 2, 1, 3, 1, 2 — **全局无序**。
- **c 列更局部有序**：仅在 a 和 b 都相同时才有序。例如 (a=1, b=2) 时 c 为 3, 5（递增）。

这就是最左匹配原则的物理基础：只有当前导列被**固定为等值**时，后续列才具备二分查找所需的有序性。 [腾讯云](https://cloud.tencent.com/developer/article/1774781) [博客园](https://www.cnblogs.com/ibigboy/p/18803885)

### 为什么 `>` 和 `<` 会中断匹配

以 `WHERE a > 1 AND b = 2` 为例：

`a > 1` 是严格大于，取值范围是 a=2 和 a=3（在这个数据集中）。跨不同的 a 值看 b 列的排列：

```
a=2 → b: 1, 3
a=3 → b: 1, 2
整体 → b: 1, 3, 1, 2  ← 无序
```

b 列在整个 `a > 1` 的范围内是**全局无序**的，优化器无法通过二分查找定位 `b = 2`，只能对 a 做范围扫描后逐条过滤 b。因此 b 列无法用于索引区间定位，最左匹配在 a 处中断。 [掘金](https://juejin.cn/post/7283832557502693413)

关键在于：`>` 是**开区间**，不包含任何等值边界点，不存在"a 固定为某个值"的情况，后续列永远处于无序状态。

### 为什么 `>=` 和 `<=` 不会中断匹配

以 `WHERE a >= 2 AND b = 3` 为例：

`a >= 2` 可以分解为两部分：

- **`a = 2`（等值边界，单点区间）**：此时 b 列是**有序的**（1, 3），优化器可以直接利用 `b = 3` 在 a=2 的子范围内做二分定位。
- **`a > 2`（严格范围部分）**：此时 b 列跨不同 a 值仍然无序，无法用于定位。

优化器据此构造出多个扫描区间：

| 区间 | 下界 | 上界 | 使用的索引列 |
|:---:|:---:|:---:|:---:|
| 区间 1（边界等值部分） | (2, 3, -∞) | (2, 3, +∞) | a 和 b |
| 区间 2（严格范围部分） | (2, +∞, +∞) | (+∞, +∞, +∞) | 仅 a |

区间 1 利用了 `a = 2` 这个单点区间内 b 列的有序性，把 `b = 3` 纳入了索引区间构造。虽然区间 2 只用了 a，但整体上 b 列确实被索引使用了（`EXPLAIN` 的 `key_len` 会反映出 b 列的长度），所以最左匹配**没有中断**。 [博客园](https://www.cnblogs.com/lyn8100/p/18237491)

`<=` 的原理完全对称：`a <= 2` 包含 `a = 2` 这个等值边界点，在该点上后续列有序，可继续匹配。

这就是 `>` 和 `>=` 本质上的区别——**多了一个等号，就多了一个单点区间**。

### 为什么 `BETWEEN` 不会中断匹配

`a BETWEEN 5 AND 10` 等价于 `a >= 5 AND a <= 10`，两端都是**闭区间**，包含两个等值边界点：

- `a = 5`：后续列有序 → 可继续匹配
- `a = 10`：后续列有序 → 可继续匹配
- `5 < a < 10`：后续列无序 → 无法用于定位，但通过边界等值部分已将后续列纳入索引

所以 `BETWEEN` 不会中断最左匹配。本质上，`BETWEEN` 就是两个 `>=`/`<=` 的组合，天然携带双侧的等值边界。 [JavaGuide](https://javaguide.cn/database/mysql/mysql-index.html)

### 为什么 `LIKE 'prefix%'` 前缀匹配不会中断匹配

`LIKE 'abc%'` 在 B+ 树中实际上定义了一个**词法范围**。所有以 `abc` 开头的字符串在排序时是连续的，等价于：

```sql
a >= 'abc' AND a < 'abd'
```

这里下界 `'abc'` 是**包含的**（闭区间），上界 `'abd'` 是不包含的（开区间）。关键在于下界包含等值边界点 `a = 'abc'`：

- `a = 'abc'`（精确匹配前缀，单点区间）：后续列有序 → 可继续匹配
- `a > 'abc'`（如 `a = 'abc1'`、`a = 'abcd'` 等）：后续列跨不同值无序 → 无法用于定位

由于下界是闭区间，存在等值边界点，优化器可以像处理 `>=` 一样在该点利用后续列的有序性。因此前缀 LIKE 不会中断最左匹配。 [MySQL 官方文档](https://dev.mysql.com/doc/en/range-optimization.html)

需要注意的是，只有**前缀匹配**（`LIKE 'abc%'`，通配符在后）才具有这种性质。如果是 `LIKE '%abc'`（后缀匹配）或 `LIKE '%abc%'`（中间匹配），通配符在前面，无法确定范围的起始点，完全无法利用索引有序性，属于另一种索引失效场景。

### 统一原则总结

上述四种操作符不中断最左匹配的根本原因可以归结为一条统一规则：

> **只要范围条件包含等值边界点（即闭区间端点），该边界点就构成一个单点区间，在这个单点区间内后续列保持 B+ 树的有序性，优化器可以继续利用后续列进行索引区间定位。**

| 操作符 | 等值边界点 | 后续列在边界处有序 | 是否中断匹配 |
|:---:|:---:|:---:|:---:|
| `> value` | 无 | — | 中断 |
| `< value` | 无 | — | 中断 |
| `>= value` | 有（`= value`） | 是 | 不中断 |
| `<= value` | 有（`= value`） | 是 | 不中断 |
| `BETWEEN x AND y` | 有两个（`= x` 和 `= y`） | 是 | 不中断 |
| `LIKE 'prefix%'` | 有（`= 'prefix'`） | 是 | 不中断 |

从 B+ 树的物理结构来看，这一切都源于联合索引的排序规则：**先按第一列排序，第一列相同时按第二列排序，依此类推**。等值条件锁定了前导列的具体值，从而"解锁"了后续列在该子范围内的有序性；而严格不等式（`>`、`<`）没有任何等值锁定点，后续列始终处于全局无序状态，二分查找无从下手，匹配就此中断。
