
### **Spring WebFlux 是基于 Reactor 的响应式 Web 框架，采用非阻塞 I/O 与事件循环模型,适合高并发、I/O 密集型场景**

  

下面按面试高频考点串讲,每个知识点都配上面试题与答题要点,帮你在面试中系统输出。

  

---

  

### **一、基础认知类**

  

#### **Q1:什么是 Spring WebFlux?它和 Spring MVC 有什么区别?**

  

Spring WebFlux 是 Spring 5 引入的响应式 Web 框架,基于 **Reactor** 库(实现了 Reactive Streams 规范),运行在 Netty、Undertow 或 Servlet 3.1+ 容器上,采用**非阻塞 I/O + 少量事件循环线程**处理请求。

  

核心区别可以从下表看出:

  

| 维度 | Spring MVC | Spring WebFlux |

|------|-----------|----------------|

| 编程模型 | 命令式、同步阻塞 | 响应式、异步非阻塞 |

| 线程模型 | 一请求一线程(Thread-per-Request) | 事件循环(Event Loop) |

| 底层 API | Servlet API | Reactive Streams / Netty |

| 返回类型 | `Object`、`ResponseEntity` | `Mono<T>`、`Flux<T>` |

| 默认容器 | Tomcat | Netty |

| 适用场景 | CPU 密集、传统 CRUD | 高并发、I/O 密集、流式 |

  

**答题加分点**:两者不是取代关系,Spring 官方明确"如果现有 MVC 应用运行良好,不必迁移"。

### **二、响应式编程与 Reactor 类**

  

#### **Q2:Mono 和 Flux 有什么区别?**

  

- **Mono<T>**:发布 0 或 1 个元素的异步序列,类似 `Optional` 的响应式版本,常用于单个结果(如 `findById`)。

- **Flux<T>**:发布 0 到 N 个元素的异步序列,类似 `Stream`,常用于列表、事件流、SSE 推送。

  

两者都实现了 `Publisher<T>`,遵循 Reactive Streams 的 `onSubscribe / onNext / onError / onComplete` 信号语义。

  

#### **Q3:什么是 Reactive Streams?它有哪四个核心接口?**

  

Reactive Streams 是**异步流处理 + 非阻塞背压**的标准规范,四个核心接口:

  

- `Publisher<T>`:数据发布者

- `Subscriber<T>`:数据订阅者

- `Subscription`:连接两者,控制 `request(n)` 和 `cancel()`

- `Processor<T,R>`:同时是 Publisher 和 Subscriber

  

#### **Q4:什么是背压(Backpressure)?WebFlux 如何实现?**

  

背压指**下游消费者根据自身处理能力,通知上游生产者控制发送速率**,防止内存溢出。

  

WebFlux 通过 `Subscription.request(n)` 实现:Subscriber 主动 pull,而不是 Publisher 无限 push。Reactor 提供 `onBackpressureBuffer / Drop / Latest` 等策略处理超载。

### **三、线程模型类(核心难点)**

  

#### **Q5:WebFlux 的线程模型是怎样的?为什么少量线程能扛高并发?**

  

Netty 默认启动 **CPU 核数 × 2** 个事件循环线程(`reactor-http-nio-*`)。每个线程通过 **Selector** 轮询多个 Channel:

  

- 请求到达 → 事件循环线程读取 → 交给业务处理链

- 遇到 I/O(数据库、下游 HTTP)→ **注册回调,线程立刻释放**去处理其他请求

- I/O 完成 → 回调触发,继续下游算子

  

因此**线程不会因等待 I/O 而阻塞**,少量线程即可支撑数万并发连接。

  

#### **Q6:在 WebFlux 里为什么绝对不能调用阻塞代码?**

  

事件循环线程一旦被阻塞(如 JDBC、`Thread.sleep`、同步 HTTP 调用),**这个线程负责的所有连接都会卡住**,吞吐骤降。

  

**解决方案**:

- 优先使用响应式驱动:R2DBC、Reactive Mongo、WebClient

- 不得已的阻塞调用用 `publishOn(Schedulers.boundedElastic())` 切到弹性线程池

- 用 `BlockHound` 在测试期检测阻塞调用

### **四、编程模型类**

  

#### **Q7:WebFlux 支持哪两种编程模型?**

  

1. **注解式(Annotated Controllers)**:与 MVC 几乎一致,`@RestController` + `@GetMapping`,只是返回 `Mono/Flux`。

  

```java

@GetMapping("/users/{id}")

public Mono<User> getUser(@PathVariable String id) {

return userRepository.findById(id);

}

```

  

2. **函数式(Functional Endpoints)**:用 `RouterFunction` + `HandlerFunction` 声明路由,更函数式、更适合 lambda 组合。

  

```java

@Bean

RouterFunction<ServerResponse> routes(UserHandler h) {

return route(GET("/users/{id}"), h::get)

.andRoute(POST("/users"), h::create);

}

```

### **五、组件与生态类**

  

#### **Q8:WebClient 和 RestTemplate 的区别?**

  

`RestTemplate` 同步阻塞,官方已进入维护模式;`WebClient` 是 WebFlux 提供的**非阻塞、响应式 HTTP 客户端**,支持流式、SSE、背压,可在 MVC 项目中单独使用。

  

```java

webClient.get().uri("/api/x")

.retrieve()

.bodyToFlux(Item.class)

.timeout(Duration.ofSeconds(3))

.retry(2);

```

  

#### **Q9:响应式数据库怎么办?**

  

JDBC 本身是阻塞的,响应式栈需要用:

- **R2DBC**:响应式关系数据库连接规范(MySQL、PostgreSQL、H2)

- **Reactive MongoDB / Redis / Cassandra**:官方 starter 都提供响应式版本

- 若必须用 JPA/JDBC,用 `Schedulers.boundedElastic()` 隔离

### **六、进阶与踩坑类**

  

#### **Q10:常用的 Reactor 操作符有哪些?`map` 和 `flatMap` 区别?**

  

- **转换**:`map`(同步 1→1)、`flatMap`(异步 1→N,会订阅返回的 Publisher 并合并)

- **过滤**:`filter`、`take`、`skip`

- **合并**:`zip`(等所有源发出配对)、`merge`(交错合并)、`concat`(顺序拼接)

- **错误处理**:`onErrorReturn`、`onErrorResume`、`retry`、`retryWhen`

- **调度**:`subscribeOn`(影响源头执行线程)、`publishOn`(切换下游线程)

  

关键差异:`map` 用于同步转换,`flatMap` 用于**返回 Mono/Flux 的异步调用**(如链式 DB 查询)。

  

#### **Q11:`subscribeOn` 和 `publishOn` 有什么区别?**

  

- `subscribeOn`:**只影响订阅链的起点**,无论放在链路哪里,决定源头在哪个线程执行,只生效一次(第一个)。

- `publishOn`:**从此处往下切换线程**,可多次使用,后续算子在新线程执行。

  

#### **Q12:WebFlux 里如何做异常处理?**

  

- 算子层面:`onErrorResume`、`onErrorMap`、`doOnError`

- 全局层面:`@ExceptionHandler` 仍可用;函数式路由用 `WebExceptionHandler` 或自定义 `ErrorWebExceptionHandler`

- 状态码:抛 `ResponseStatusException` 或用 `ServerResponse.status(...)`

  

#### **Q13:WebFlux 支持 SSE / 流式响应吗?**

  

支持。返回 `Flux<T>` 并将 `produces = MediaType.TEXT_EVENT_STREAM_VALUE`,即可推送 Server-Sent Events;也可用 `application/x-ndjson` 实现 JSON 流。这是 WebFlux 相较 MVC 的天然优势。

### **七、选型与总结类**

  

#### **Q14:什么场景该用 WebFlux?什么场景不该用?**

  

**适合**:

- 高并发、长连接(网关、BFF、聊天、推送、SSE)

- I/O 密集型(大量下游 HTTP / NoSQL 调用)

- 流式数据处理

  

**不适合**:

- 团队不熟悉响应式,调试与排错成本高

- 依赖大量阻塞库(旧版 JDBC、老中间件 SDK)

- 简单 CRUD、低并发业务,MVC 更直观

  

#### **Q15:WebFlux 的调试为什么难?怎么办?**

  

因为异步链路让传统堆栈信息断裂。应对:

- 开启 `Hooks.onOperatorDebug()`(开发环境)或用 `checkpoint()` 定位

- 使用 **Reactor Debug Agent**(生产可用,开销更小)

- 上下文透传用 `Context` / `contextWrite`,不能依赖 `ThreadLocal`(MDC 需借助 `ContextPropagation`)

  

---

  

**一句话收尾**:WebFlux 的本质是**用少量线程 + 事件驱动 + 背压**,在 I/O 密集场景换取更高吞吐;掌握它的关键在于理解 Reactor 的**装配期 vs 订阅期**、**线程调度**和**永不阻塞事件循环**这三件事,面试基本围绕它们展开。
