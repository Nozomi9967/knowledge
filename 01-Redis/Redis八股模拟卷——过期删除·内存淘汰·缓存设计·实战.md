## 一、过期删除策略

### 1. Redis 为什么选择「惰性删除 + 定期删除」这种组合？分别说一下这两种策略是怎么工作的，以及它们各自解决了对方的什么问题。

**你的回答：**
- 惰性删除是如果键过期了，只有客户端再次去访问它，它才会被删，否则一直存在
- 定期删除是每隔一段时间，主线程就会随机抽取一部分键，将其中的过期键删掉，如果过期键的比例大于25%，继续随机抽取，重复上述过程，直到整个过程超过25ms或某轮比例小于25%
- 惰性删除只有客户端访问才会删，对CPU友好，但如果客户端一直不去访问过期键，过期键就会一直存在在内存中，所以它对内存不友好
- 定期删除如果频率过高，会影响CPU性能，但如果频率过低，又会出现惰性删除的那种情况
- Redis选择这种组合是为了实现CPU和内存的效率最大化

**追问：** 定期删除每次抽多少个 key？判断要不要继续下一轮的条件是什么？
→ 回答："这俩问题我在上面回答过了"

---

**参考答案 ✅**

**惰性删除：**
- 工作方式：每次从数据库访问 key 时，检测 key 是否过期，如果过期则删除该 key
- 优点：只在实际访问时才检查，**对 CPU 最友好**
- 缺点：过期 key 一直不被访问，就一直占用内存，**对内存不友好**

**定期删除：**
- 工作方式：每隔一段时间，**随机抽取 20 个 key** 进行检查，删除其中的过期 key
- 判断条件：如果本轮已过期 key > **5 个**（即比例 > 25%），则继续下一轮，最多持续 **25ms**
- 优点：主动清理过期 key 释放内存
- 缺点：执行频率难把握，频率高伤 CPU，频率低又和惰性删除一样

**选型理由：** 两者互补。惰性删除保 CPU，定期删除保内存。面试中完整说法——"**Redis 在合理使用 CPU 时间和避免内存浪费之间取得了平衡**"。

⚠️ **面试注意：** 追问的问题需要**独立重新组织回答**，不能甩一句"上面回答过了"。正确回答："定期删除每次随机抽 **20 个 key**，如果过期比例超过 **25%（即超过 5 个）** 就继续下一轮，整个过程不超过 **25ms**。"

### 2. 假设现在 Redis 的主服务器宕机了，重启后载入 RDB 文件，过期键会怎么处理？如果是从服务器载入 RDB，处理方式有什么不同？

**你的回答：**
- 主服务器重启后载入RDB：检查键是否过期，过期则不导入 → ✅
- 从服务器载入RDB：不会对过期键进行处理，客户端访问从服务器正常响应 → ✅

**追问：** AOF 写入阶段 vs AOF 重写阶段的不同？
→ AOF 写入：正常写入，过期键被删除时追加 DEL；AOF 重写：跳过过期键
→ 为什么 AOF 重写过滤而普通写入不过滤？"我猜跟主从数据一致性有关，具体不知道"

---

**参考答案 ✅**

**RDB 阶段：**
- **RDB 生成阶段**：过期的键不会保存到新的 RDB 文件
- **RDB 加载阶段（主服务器）**：过期键不会被载入 → ✅
- **RDB 加载阶段（从服务器）**：不论是否过期都载入。但从服务器在后续主从同步时数据会被清空，所以实际无影响

**AOF 阶段：**
- **AOF 写入阶段**：过期键还在时正常写入 AOF；过期后被删除时，Redis 会追加一条 DEL 命令到 AOF
- **AOF 重写阶段**：跳过过期键，不写入新 AOF 文件

**为什么 AOF 重写过滤而普通写入不过滤？**
AOF 重写本质是**重新构造一份数据库快照**，过期键是无效数据，没必要写入浪费空间。而普通 AOF 是**逐条追加日志**，必须完整记录每一条写操作命令，才能在恢复时精确重现执行顺序——跳过写入阶段的过期键反而会破坏恢复的完整性。不是主从数据一致性的问题。

### 3. Redis 主从架构中，过期键的删除是谁来负责的？从库为什么不能自己主动删除过期键？这种设计有什么潜在问题吗？

**你的回答：**
- 过期键删除由主库负责 → ✅
- 从库为什么不能主动删除？→ **不知道**

---

**参考答案 ✅**

**谁来负责：** 主库。主库在 key 到期时，会在 AOF 文件里追加一条 DEL 指令，同步到所有从库执行。

**从库为什么不能自己主动删除？**
从库可能因为**主从复制延迟**导致本地时间与主库不一致。如果从库自行判断过期时间并删除，可能出现数据不一致——比如主库认为还没过期的 key，从库自己删了；或者主库已经删了，从库还留着。

**潜在问题：**
如果**主库宕机**，从库晋升为主库前，从库中的过期键会一直被客户端读到（因为从库被动删除，没有收到主库的 DEL 指令），直到新主库建立后通过后续同步来清理。

> **面试官会追问：** 那如果你做主从切换，升主那一刻从库里的过期键怎么处理？
> → 可以手动执行一次 `SCAN` + `TTL` 批量清理，或者在业务层容忍短暂的不一致。

## 二、内存淘汰

### 4. Redis 的 8 种内存淘汰策略可以分为哪几类？请完整列举。如果现在让你给一个社交 Feed 流系统选淘汰策略，你会选哪个？为什么？

**你的回答：**
- 不进行淘汰（noeviction）→ 到达 maxmemory 返回错误
- 在过期键中淘汰：random、ttl、lru、lfu
- 在所有键中淘汰：random、lru、lfu
- 选 LFU

**追问：** noeviction 返回什么错误？→ 没答
**追问：** volatile-ttl 的局限？→ "随机抽取一部分，淘汰最快过期的"（不完整）

---

**参考答案 ✅**

**8 种策略分 3 大类：**
1. **不进行数据淘汰**：`noeviction`——内存超限直接返回错误`(error) OOM command not allowed when used memory > 'maxmemory'`
2. **在过期键中淘汰**：`volatile-random`、`volatile-ttl`、`volatile-lru`、`volatile-lfu`
3. **在所有键中淘汰**：`allkeys-random`、`allkeys-lru`、`allkeys-lfu`

**volatile-ttl 的局限：**
它的实现也是**随机抽样**，在抽到的样本中选最快过期的，不是全局扫描所有过期 key 找最快过期的。所以如果样本集中没有真正最快过期的那个 key，淘汰结果就不精确。

**Feed 流选型：**
选 `allkeys-lfu`。Feed 流有明显的热点分布——少数热门帖子被高频访问，大量冷门帖子几乎无人问津。LFU 天然契合这个模式，能保留常访问的热帖。LRU 容易被突发流量污染缓存（比如某个帖子突然冲上热搜被大量读取一次，之后热度消退却长期占据缓存）。

---

### 5. 解释一下 LRU 和 LFU 的核心思想。LRU 有什么缺陷？LFU 是怎么解决的？

**你的回答：**
- LRU：淘汰最近最早被使用的键
- 缺陷：某一次访问大量只会被访问一次的键，这些键会长期占用内存
- LFU：根据访问次数淘汰，解决了一次性访问的问题
- 传统 LRU 链表方案：额外内存开销 + 频繁移动
- Redis 近似 LRU：24bit lru 字段存时间戳 + 随机采样 5 个

**追问：** LFU 的 8 bit 计数器够用吗？如果溢出怎么办？
→ **"不够用，如果溢出这 8bit 会存放指向其它内存空间的地址"** ❌ **严重错误！**

---

**参考答案 ✅**

**LRU 核心：** 淘汰最近最少使用的数据。（按最后访问时间排序）

**LRU 缺陷：** 缓存污染——一次性读取大量数据，这些数据只访问一次，但会长期滞留缓存。

**LFU 核心：** 淘汰最少被访问的数据。（按访问频次排序）

**24 bits 字段复用：**
- LRU 模式：24 bits 全部存最后一次访问的时间戳
- LFU 模式：**高 16bit 存 ldt（访问时间戳）**，**低 8bit 存 logc（对数计数器）**

**⚠️ LFU 的 8bit 计数器为什么够用？（不要答"溢出存地址"——这是错的）**

Redis 用的是**对数计数器（Logistic Counter）**，增长是概率性的：

| 当前 cnt | 每次访问时增长概率 |
|:--------:|:----------------:|
|   0-5    |     100%        |
|   6-50   |     ~10%        |
|   50+    |      ~1%        |

也就是说一个 key 被访问 100 万次，计数器可能也就 40 多，根本不会溢出。同时配合**时间衰减机制（ldt）**——key 长时间不被访问，logc 自动减半，LRU 模式下无此机制。

## 三、缓存设计

### 6. 请分别说明缓存雪崩、缓存击穿、缓存穿透各是什么场景，它们之间的本质区别是什么？针对每一种，你会怎么解决？

**你的回答：**
- 雪崩：大量缓存同一时间过期 → 打乱过期时间 / 异步更新 ✅
- 击穿：热点数据过期 → 设永不过期 / 异步更新 / 互斥锁 ✅
- 穿透：缓存和数据库都不存在的请求 → 参数拦截 / 布隆过滤器 / 空值缓存 ✅

**追问：** 布隆过滤器有什么缺点？能不能 100% 拦截？→ **没答**

---

**参考答案 ✅**

**雪崩 vs 击穿 vs 穿透的本质区别：**

| 场景 | 缓存有吗 | 数据库有吗 | 核心问题 |
|:----:|:--------:|:--------:|---------|
| 雪崩 | 有，但大量同时过期 | 有 | 大量 key 同时过期 |
| 击穿 | 有，但单个热点过期 | 有 | 单个热点 key 过期 + 高并发 |
| 穿透 | 没有 | **也没有** | 数据库也查不到，缓存无法重建 |

**布隆过滤器的缺点：**
- **有误判率**：说"不存在"一定不存在，说"存在"可能不存在（假阳性）
- **不支持删除元素**：一旦写入无法撤销
- **需要额外维护**：数据变化时需要同步更新布隆过滤器
- 不能 100% 拦截，所以通常会**配合空值缓存兜底**

### 7. 旁路缓存（Cache Aside）策略的写操作，为什么推荐「先更新数据库，再删除缓存」？如果反过来会有什么问题？

**你的回答：**
- 时间线画了，结论正确 ✅
- 改进思路：写 DB 后重建缓存 + 互斥锁 / 短过期时间 ✅

**不足：** "修改数据库比操作缓存慢得多"——可以更精确

---

**参考答案 ✅**

**先删缓存再更新 DB 为什么不安全：**
```
请求A（写）： 删缓存          →         更新DB（慢）
请求B（读）：             读缓存 miss → 读DB（旧值）→ 写缓存（旧值）
```
缓存中永久留下旧值。

**先更新 DB 再删缓存为什么更安全：**
```
请求A（写）：              更新DB（慢）  →  删缓存（极快）
请求B（读）： 读缓存命中（正常） / 缓存 miss → 读DB（新值）→ 写缓存（新值）
```
不一致窗口：B 读了旧 DB 后、写缓存前，A 完成删缓存。但这个窗口是**微秒级**（写缓存纯内存操作），比先删后更新的**毫秒级窗口**（更新 DB 磁盘 IO）短得多。

**时间量级：** 删除缓存是**内存操作（微秒级，μs）**，更新数据库是**磁盘 IO（毫秒级，ms）**，相差 3-4 个数量级。所以"先更新 DB 再删缓存"的窗口极小，实际几乎不会触发。

### 8. Read/Write Through 和 Write Back 这两种缓存策略，为什么在 Redis + MySQL 的场景下很少用？它们各自适合什么样的场景？

**你的回答：**
- Read/Write Through：由缓存组件与数据库交互 → Redis 没有相应功能，所以少用 ✅
- Write Back：修改后标记脏页立即返回 → 一致性太差，很少用；适合写多的场景 ✅

**追问：** 如何让 Redis 具备 Write Through 能力？
→ "添加后台线程定时写盘" ❌——你答的是 Write Back 的方案，不是 Write Through

---

**参考答案 ✅**

**Read Through：** 应用程序只跟缓存交互，缓存组件负责从数据库加载数据
**Write Through：** 写入缓存的同时，缓存组件**同步**写入数据库，写操作完成后才返回

**为什么 Redis 少用？**
Redis 没有内置的数据库写入和自动加载功能，这两种策略需要**缓存层代理数据库操作**，而 Redis 只是一个缓存/KV 存储，不负责与数据库交互。

**Write Back 的风险：**
- 数据非强一致——只写缓存就返回，DB 可能还没写
- 缓存（内存）掉电 → 脏数据全部丢失
- ==CPU 缓存和文件系统有硬件保障（NVDIMM、电池保护、内核强制刷盘），Redis 是应用层纯内存，没有这些保护==

**Write Back 适合：** 写多的场景，能大幅提升写入性能

**如果非要让 Redis 具备 Write Through 能力：**
需要**业务层自己实现**——在写入缓存后同步写数据库，写入成功才返回。这不是 Redis 的配置能解决的，需要应用层代码介入。

## 四、实战

### 9. Redis 如何用 ZSet 实现延迟队列？有没有什么问题？

**你的回答：**
"用 zadd 和 zrangebyrank" —— **只有 9 个字，严重缺失**

---

**参考答案 ✅**

**实现方案：**
1. 用 **ZSet 的 score 存储延迟执行的时间戳**（如到期时的 Unix 毫秒时间戳）
2. **轮询**：消费者用 `ZRANGEBYSCORE key -inf <当前时间戳>` 取出所有已到期的任务
3. 处理任务后通过 **ZREM** 从 ZSet 中删除

**存在的问题：**
- **精度问题**：轮询间隔决定了延迟精度。间隔太短增加 Redis 压力，间隔太长任务可能延迟执行
- **消息丢失**：取出任务后、处理完成前如果进程崩溃，已取出的任务还没 ZREM，重新启动后因为 score 已过期不会再被取出 → **丢失**
- **重复消费**：取出任务后、ZREM 前如果另一个消费者也取到了同一个任务 → **重复执行**
- **多消费者竞争**：没有原生的 ACK 机制，需要业务层自己解决（比如用 `ZPOPMIN` + Lua 脚本保证原子性）

### 10. 什么是 Redis 大 key？大 key 会造成哪些问题？如何排查和安全删除？

**你的回答：**
- String > 10KB ✅
- 集合类型元素个数 > **50000** ❌ **（实为 5000，差 10 倍）**
- 三个问题描述 ✅

- 删除方法（分批 + 异步）✅

---

**参考答案 ✅**

**大 key 定义：**
- String 类型值 > **10KB**
- Hash、List、Set、ZSet 元素个数 > **5000 个** ⚠️ 不是 50000

**unlink 为什么不阻塞：**
主线程只做两件事（微秒级）：
1. 从**全局哈希表**中移除 key 的引用（客户端立刻查不到了）
2. 把真正的内存释放操作丢给后台 **lazyfree 线程**

不是"存入过期字典"——过期字典（expires dict）是存过期时间的，跟 unlink 的异步删除是两码事。

**lazyfree 配置建议开启：**
- `lazyfree-lazy-eviction` → 内存淘汰时异步释放
- `lazyfree-lazy-expire` → 过期键删除时异步释放
- `lazyfree-lazy-server-del` → 隐式删除（如 rename）时异步释放
- `slave-lazy-flush` → 从库清空数据时异步释放

面试中**记不清全名**可以说功能，不要直接说"忘了"。

### 11. Redis 事务为什么不支持回滚？如果一组操作中某条命令执行失败了，其他命令会怎样？

**你的回答：**
- 创始人理念：回滚多是业务问题，Redis 更注重效率 ✅
- **"未执行的会被 discard"** ❌ **严重错误！**

---

**参考答案 ✅**

**EXEC 之前报错（语法错误）：**
```
MULTI
SET name "redis"
SET age           ← 入队时语法错误
EXEC              ← 整个事务被拒绝，一条不执行
```
入队阶段就检测到语法错误 → Redis 在 EXEC 前直接拒绝整个事务

**EXEC 之后报错（运行期错误）：**
```
MULTI
SET name "redis"
LPUSH age "abc"   ← age 是 String，LPUSH 运行时报错
SET city "bj"
EXEC              ← SET name 和 SET city 正常执行，LPUSH 单独报错
```
**正确的命令照常执行**，Redis **不回滚**已执行的命令，**不中断**后续命令。

**所以"未执行的会被 discard"是错的。** 正确的理解是：**EXEC 一旦发出，所有已入队的正确命令都会逐一执行，运行时报错不影响其他命令的执行。**

**DISCARD 不是回滚：** 它只是**主动放弃当前事务队列**，清空暂存区。对于已 EXEC 执行的命令没有任何影响。

### 12. 基于 Redis 单节点实现分布式锁，需要考虑哪些问题？请写出加锁和解锁的核心逻辑。

**你的回答：**
- 加锁：`SET lock unique_id NX PX 10` ✅
- NX / PX 解释 ✅
- 锁超时问题 ✅
- 续约方案 ✅

**追问：** 解锁为什么要用 Lua 脚本？→ **没答**
**缺：** 解锁的 Lua 脚本没有给出

---

**参考答案 ✅**

**三个关键条件：**
1. **原子操作**：`SET NX`——检查存在 + 设置值一步完成
2. **过期时间**：`PX`——防止客户端异常死锁
3. **唯一标识**：`unique_value`——防止误释放其他客户端的锁

**加锁命令：**
```
SET lock_key unique_value NX PX 10000
```

**过期时间怎么设：**
- 设短了 → 业务还没执行完锁就过期了，其他线程抢进来
- 设长了 → 持有锁的线程挂了，其他线程要等很久才能拿到锁
- 面试回答"设长了影响业务执行效率"不准确，应该说是**增加了其他线程等待锁的时间**

**续约方案：** 启动一个守护线程，在锁快过期时自动续约（Redisson 的 Watchdog 机制）

**解锁必须用 Lua 脚本（保证原子性）：**
```
// "比较+删除"两步合一，原子执行
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**为什么不能直接用 DEL？**
因为判断 `unique_value` 和 `DEL` 是两个操作，非原子。如果判断完值正确但还没执行 DEL 时，锁恰好过期了，另一个线程拿到了锁，此时 DEL 就会误删别人的锁。

### 13. Redlock 解决了什么问题？它的加锁成功条件是什么？有什么争议？

**你的回答：**
- 解决了主从异步复制下的锁同步问题 ✅
- 半数以上节点成功 + 总耗时小于阈值 ✅
- 剩余时间不足则释放锁 ✅

**不足：** 争议没答，加锁操作的**超时时间**没提

---

**参考答案 ✅**

**解决的问题：**
==主从复制是异步的。如果主节点加锁成功但还没同步到从节点就宕机了，新主节点没有锁数据，其他客户端可以再次加锁，破坏互斥性。==

**加锁成功的两个必要条件：**
1. 从 **超过半数（≥ N/2+1）** 的独立 Redis 节点上成功获取到锁
2. 加锁 **总耗时 < 锁的过期时间**

**细节：** 给每个节点的加锁操作要设置**超时时间（几十毫秒）**，远远小于锁的过期时间。防止某个节点挂了导致客户端一直等待。

**Redlock 争议：**
- **Martin Kleppmann** 批评 Redlock 依赖"时钟假设"——==如果某个节点的系统时钟发生跳跃（如 NTP 步进），锁的过期时间计算会出错，可能导致两个客户端同时拿到锁==
- **Antirez（Redlock 作者）** 回应：时钟跳跃在生产环境中极少发生，即使发生也可以通过配置 NTP 为"微调"（slew）而不是"步进"（step）来避免；==Redlock 追求的是工程上的"足够安全"，不是理论上的绝对安全==

> 面试被问到时说明双方观点即可，不需要站队。关键是**知道有这场争论**。

### 14. 你了解 Redis 的管道（Pipeline）吗？它解决了什么问题？用的时候要注意什么？

**你的回答：**
- 客户端命令批处理机制 ✅
- 解决 RTT 问题 ✅
- 提高吞吐量 ✅

**追问：** Pipeline 是客户端还是服务端功能？→ 没答
**追问：** Pipeline 和事务能一起用吗？→ 没答
**追问：** 一次性塞太多命令的后果？→ 没答

---

**参考答案 ✅**

**Pipeline 是客户端的功能，不是 Redis 服务器端的功能。**
它把多个命令在客户端**打包一次性发送**给服务器，服务器处理完再**一次性返回**所有响应，减少了网络 RTT。

**Pipeline 和事务可以一起用：**
- Pipeline 解决的是**网络传输效率**问题
- 事务解决的是**原子性**问题
- 两者可以组合使用（在 Pipeline 中发送 MULTI/EXEC），但注意 Pipeline 不会保证命令的原子性

**一次性塞太多命令的后果：**
- ==客户端输出缓冲区被打满==
- ==网络阻塞，响应延迟飙升==
- ==如果其中某个命令执行慢，所有命令的响应都要等它执行完才能返回（队列头阻塞）==

**建议：** 控制 Pipeline 中的命令数量（几百到几千为宜），根据业务场景分批次发送。
