## 一、索引

### 什么是索引？

索引是一种帮助存储引擎快速查找数据的数据结构

### 索引的分类？

按**数据结构**分类：B+Tree索引、Hash索引、Full-text索引
按**物理存储**分类：聚簇索引(主键索引),二级索引(辅助索引)
按**字段特性**分类：主键索引、唯一索引、普通索引、前缀索引
按**字段个数**分类：单列索引、联合索引

### EXPLAIN 执行计划

`explain` + `sql` → 返回一份**执行计划报告**

**key**字段为null则表示没有使用索引

**type**字段描述了找到所需数据时使用的**扫描方式**是什么

**执行效率从低到高**

| 扫描方式 | type值 |
|----------------------------------|--------|
| 全表扫描 | All |
| 全索引扫描 | index |
| 索引范围扫描 | range |
| 非唯一索引扫描 | ref |
| 唯一索引扫描 | eq_ref |
| 结果只有一条的主键或者唯一索引扫描 | const |

**const：**

当查询条件是**主键（PRIMARY KEY）**或**唯一索引（UNIQUE KEY）**，并且查询条件是精确匹配（如 `WHERE id = 123`）时，数据库能确定最多只会返回一条记录（或没有记录）。这种情况下，查询效率极高（常量扫描），`type` 字段就会显示为 `const`。

### B+Tree 数据结构

B+Tree 是一种**多叉树**，**叶子节点才存放数据，非叶子节点只存放索引**，而且每个节点里的数据是按主键顺序存放的。每一层父节点的索引值都会出现在下层子节点的索引值中，因此在叶子节点中，包括了所有的索引值信息，并且每一个叶子节点都有两个指针，分别指向下一个叶子节点和上一个叶子节点，形成一个**双向链表**。

B+Tree 相比 B 树和二叉树查询效率更高，核心是其**非叶子节点仅存索引、叶子节点链式相连且数据仅存于叶子层**，既大幅降低磁盘 IO 次数，又让范围查询无需回溯，同时规避了二叉树易退化为链表的单路查询低效问题。

**非叶子节点仅存索引 + 数据仅存叶子层**，能最大化单个节点的存储密度，直接让树的层数剧减，大幅减少磁盘 IO 次数；叶子节点链式相连，让范围查询无需回溯父节点，一次遍历即可完成，彻底解决 B 树范围查询的低效问题。

#### 非叶子节点（索引节点）的指针：区间路由指针

非叶子节点里面存放的是：**【Key 的列表】** 和 **【指向子节点的指针列表】**。 这些指针不是简单的左右，而是“夹在 Key 之间”的区间指针。

用我们刚才图里的根节点（Root Node）来举例，它里面有 `K10`、`K30`、`K50`：

Plaintext

```
  [ P1 | K10 | P2 | K30 | P3 | K50 | P4 ]  <-- 这是一个非叶子节点
    |         |         |         |
    v         v         v         v
 子节点1    子节点2    子节点3    子节点4
 (Key<10)  (10≤Key<30) (30≤Key<50) (Key≥50)
```

- **`P1`** 指向所有主键 **小于 10** 的子节点。
    
- **`P2`** 指向所有主键 **在 10 到 30 之间** 的子节点。
    
- **`P3`** 指向所有主键 **在 30 到 50 之间** 的子节点。
    
- **`P4`** 指向所有主键 **大于等于 50** 的子节点。
    

所以，它不是 `Left` 和 `Right`，而是 `Pointer[0]`, `Pointer[1]`, `Pointer[2]`... 这样一组指针，数量通常是 **`Key 的数量 + 1`**（或者在某些实现中数量相等）。

### 回表

通过非主键索引的B+树找到叶子节点中的**主键值**，再用该主键值去主键索引的B+树逐层定位，找到对应叶子节点的**完整行数据**，这两次索引查询过程就叫做**回表**

### 覆盖索引

非主键索引的B+树叶子节点直接存储查询所需的**全部字段值**，无需回表查询主键索引即可得到结果，这就是**覆盖索引**。

### 联合索引

1. 需要遵循**最左匹配原则**，也就是按照最左优先的方式进行索引的匹配

2. 如果有联合索引（a,b,c）
   那么b和c全局无序，局部有序
3. 并不是查询过程用到了联合索引，就代表联合索引中的所有字段都用到了联合索引进行索引查询
4. 联合索引的最左匹配原则，在遇到范围查询（如 >、<）的时候，就会停止匹配，也就是范围查询的字段可以用到联合索引，但是在范围查询字段的后面的字段无法用到联合索引。**注意**，对于 **>=、<=、BETWEEN、like 前缀匹配**的范围查询，并不会停止匹配。详见 [[最左前缀匹配范围查询不停止的原因]]

### 索引下推

索引下推是 MySQL 将联合索引中可筛选的**非主键条件**下推至存储引擎层，在索引遍历阶段提前过滤数据，减少回表的行数和 IO 开销。

**Extra：`Using index condition`** 表示用到了索引下推

### 索引区分度

索引区分度是指索引列中唯一值的占比，占比越高区分度越好，能让数据库通过索引快速缩小查询范围、减少扫描行数。

### 什么时候适合用索引？

1. 有唯一性限制的字段
2. 经常用于where、order by和group by条件查询的字段

### 什么时候不需要创建索引？

1. where、order by和group by条件里用不到的字段，因为索引的价值是快速定位，如果起不到定位的价值就不需要创建索引，索引也是会占用物理空间的
2. 表中数据过少
3. 表中存在大量重复数据
4. 经常更新的字段不用创建索引，索引字段被频繁修改，由于要维护B+Tree的有序性，那么就需要频繁的重建索引，这会影响数据库性能

### 有什么优化索引的方法？

#### 前缀索引优化

前缀索引就是使用字段的前几个字符建立索引，可以减小索引项的大小，从而增加一个索引页中存放的索引值数量，提高索引的查询效率

#### 覆盖索引优化

覆盖索引就是在非主键索引B+树的叶子节点中直接存储查询所需的所有字段值，无需回表查询主键索引即可得到结果

```
1. 核心核心：设计"宽"联合索引
实现覆盖索引最直接的手段是根据查询需求，将原本不在索引中的字段，加入到联合索引中。

做法： 如果业务经常执行 SELECT a, b FROM table WHERE c = 10，那么不要只给 c 加索引，而是建立 (c, a, b) 的联合索引。

原理： 此时非主键索引的叶子节点已经包含了 a 和 b 的值，MySQL 发现索引树里的信息够用了，就不会再去主键索引（聚簇索引）里找整行数据了。

2. 严控查询字段（拒绝 SELECT *）
开发规范中强调"禁止 SELECT * "的本质原因之一就是为了配合覆盖索引。

做法： 只查询必要的字段。即使你建立了 (name, age) 的联合索引，但如果你写了 SELECT *，由于索引里没有 address 等其他字段，数据库被迫必须回表。

话术： "我会要求开发团队在编写 SQL 时精准匹配索引字段，确保查询列是索引列的子集。"

3. 利用执行计划确认（EXPLAIN）
空谈优化没用，必须通过工具验证。

做法： 使用 EXPLAIN 查看 SQL 的执行计划。

关键指标： 观察 Extra 列。如果显示 Using index，说明覆盖索引已生效；如果显示 Using index condition，说明只用到了索引过滤但仍需回表。
```

#### 主键索引最好是自增的

- 如果我们使用**自增主键**，那么每次插入一条新纪录，都是追加操作，不需要移动数据，这种插入数据的方法效率很高
- 如果我们不使用自增主键，就有可能会插入到数据页中间的某个位置，如果当前页满，就会不得不移动其他数据，甚至需要从一个页面复制数据到另一个页面，这种情况就叫做**页分裂**。页分裂还有可能会造成大量的内存碎片，导致索引结构不紧凑，从而影响查询效率

#### 索引最好设置为NOT NULL

1. 索引列存在NULL会导致优化器在索引优化的时候更加复杂，更加难以优化
2. NULL值是一个没有意义的值，但他会占用物理空间，所以会带来存储空间的问题

#### 防止索引失效

- 使用左或者左右模糊匹配时
- 在查询条件中对索引列进行了计算、函数或类型转换操作
- 联合索引没有遵循最左匹配原则
- where子句中or前的条件列是索引列，or后的条件列不是索引列

## 二、执行SELECT语句的流程

### 连接器

先连接Mysql服务

1. 与客户端进行**TCP三次握手**建立连接
2. 校验**用户名和密码**
3. 如果校验通过，则读取该用户的**权限**，后面有关的权限逻辑判断都会基于此时读取到的权限

### 查询缓存

连接器的工作完成后，客户端就可以向Mysql服务发送SQL语句了，Mysql收到语句后，会解析出语句的第一个字段，看看是不是SELECT，是的话就会查询缓存

*MySQL8.0将查询缓存删掉了*

*关闭查询缓存：`query_cache_type`设置为`DEMAND`*

### 解析SQL

在正式执行SQL查询语句之前，Mysql会先对SQL语句进行解析，这个工作由**解析器**完成

解析器会做两件事情，一个是**词法分析**，另一个是**语法分析**

*词法分析：根据输入的字符串解析出关键字出来*

*语法分析：语法分析器根据词法分析的结果和语法规则，判断sql语句是否符合sql语法规范，符合则构建sql语法树*

### 执行SQL

每条SELECT查询语句流程都可以分为以下三个阶段

**prepare**阶段、**optimize**阶段、**execute**阶段

#### prepare阶段

- 检查表和字段是否存在
- 将`*`符号换成表中所有字段

#### optimize阶段

优化器为sql查询语句制定一个**执行计划**

*例如执行时选择哪个索引*

#### execute阶段

根据执行计划执行SQL查询语句，从存储引擎读取记录，返回给客户端

## 三、事务

### 事务有哪些特性？

- **原子性（Atomicity）**
  - 一个事务中的所有操作，要么全部完成，要么全部不完成
  - 通过 **undo log（回滚日志）** 来保证的
- **一致性（Consistency）**
  - 事务操作前和操作后，数据满足完整性约束，数据库保持一致性状态
  - 通过 原子性、隔离性和持久性来保证的
- **隔离性（Isolation）**
  - 数据库允许多个并发事务同时对数据进行读写
  - 通过 **MVCC（多版本并发控制）** 或**锁机制**来保证的
- **持久性（Durability）**
  - 事务处理结束后，对数据的修改是永久的，即使系统故障也不会丢失
  - 通过 **redo log（重做日志）** 来保证的

>一致性的含义

无论数据库怎么折腾（并发、挂机、报错），数据都必须符合预设的“业务规则”和“物理约束”，不能出现违背现实逻辑的脏数据。

### 并行事务会引发什么问题？

- **脏读**
  - 一个事务读到了另一个**未提交**事务修改过的数据
- **不可重复读**
  - 一个事务多次读取**同一个数据**，出现了前后数据不一致的情况
- **幻读**
  - 一个事务内多次查询**符合同一查询条件的记录数量**，出现前后记录数量不一致的情况

*脏读最严重，往下依次递减*

### 事务的隔离级别有哪些？

隔离级别越高，性能效率越低

- **读未提交（READ UNCOMMITTED）**
  - 一个事务未提交时，它所做的变更就可以被其他事务看见
  - 脏读、不可重复读、幻读
- **读提交（READ COMMITTED）**
  - 一个事务提交了，它所做的变更才能被其他事务看见
  - 不可重复读、幻读
- **可重复读（REPEATABLE READ）**
  - 一个事务执行过程中所看到的数据，与它事务开始时看见的数据是一致的
  - 是 **InnoDB 引擎默认的隔离级别**
  - 幻读
- **串行化（SERIALIZABLE）**
  - 会对记录加上读写锁，当多个事务对同一个记录进行读写操作时，如果发生了读写冲突，后一个事务需要等前一个事务执行完成

InnoDB的默认隔离级别虽然是可重复读，但它可以**很大程度上避免幻读现象**，解决方案有两种：

- 针对**快照读**（普通 SELECT），是通过 **MVCC** 来解决幻读问题的
- 针对**当前读**（SELECT ... FOR UPDATE），是通过 **next-key lock（记录锁+间隙锁）** 来解决的，当执行SELECT ... FOR UPDATE 时，会加上 next-key lock 锁，如果其他事务在next-key lock锁范围内插入了一条数据，那么这个插入语句会被阻塞

---

>优化前

MVCC也就是多版本并发控制，它通过将一份数据分为多个版本来保证多线程并发访问时的数据安全性，具体是，当一个事务访问数据时，会根据当前事务的事务ID与该数据的事务ID进行比较，并顺着bin log的版本链找到一个符合当前事务可见性的版本数据，从而实现线程之间各自操作数据互不影响

>优化后

**MVCC（多版本并发控制）** 是一种用来解决“读-写”冲突的无锁并发控制机制。

它的核心原理是：当一条记录被修改时，MySQL 不会直接覆盖旧数据，而是会将旧数据写入 **`undo log`**，并通过隐藏的回滚指针（`roll_pointer`）将这些历史版本串联成一条**版本链**。

当一个事务进行“快照读”时，系统会为该事务生成一个 **Read View（一致性视图）**。事务会顺着 `undo log` 的版本链，将数据最新的事务 ID（`trx_id`）与 Read View 中的事务活跃情况进行**可见性算法比对**，直到找到第一个对自己可见的历史版本。从而实现了并发读写时，线程之间互不影响的高效访问。

---

### 四种隔离级别具体是如何实现的？

- **读未提交**，就是直接读取最新数据
- **串行化**，是通过加读写锁来避免并行访问
- **读提交**和**可重复读**，都是通过**Read View**来实现的，只是创建Read View的时机不同
  - 读提交的是在**每个语句执行前**创建
  - 可重复读是在**启动事务时**创建

Mysql有两种开始事务的命令：

- `begin` / `start transaction`
  - 执行该命令后，执行了第一条select语句，才算事务真正启动
- `start transaction with consistent snapshot`
  - 执行该命令后，立刻启动

## 四、MVCC 与 Read View

### Read View 中的四个字段

Read View中有四个字段

- `creator_trx_id`：创建该Read View的事务的事务id
- `m_ids`：创建Read View时，数据库处于活跃且暂未提交状态的事务id列表
- `min_trx_id`：创建Read View时，处于活跃且暂未提交状态的事务中的最小事务id
- `max_trx_id`：创建Read View时，数据库分配给下一个事务的事务id

### 聚簇索引记录中的两个隐藏列

- `trx_id`：当事务对聚簇索引记录进行修改时，就会把该事务id记录在trx_id隐藏列中
- `roll_pointer`：每次对聚簇索引记录进行改动时，都会把旧版本的记录写入undo日志中，roll_pointer就是一个指向该旧版本记录的指针

### 可见性判断规则

**当一个事务访问记录时，会有以下三种情况：**

- 访问的记录的`trx_id` **小于** `min_trx_id`，表示这个版本的记录是在创建Read View之前已提交的事务生成的，该版本记录对当前事务**可见**
- 访问的记录的`trx_id` **大于等于** `max_trx_id`，表示这个版本的记录是创建Read View之后才启动的事务生成的，该版本记录对当前事务**不可见**
- 访问的记录的`trx_id` **在 `min_trx_id` 和 `max_trx_id` 之间**，需要查看`trx_id`是否在`m_ids`列表中
  - 在列表中，表示生成该版本记录的事务仍然活跃着，该版本记录对该事务**不可见**
  - 否则表示生成该版本记录的事务已提交，**可见**

> 详细可见性判断流程及示例可参考：[快照读时undo log和read view的具体作用](快照读时undo log和read view的具体作用.md)

**MVCC多版本并发控制就是通过版本链来控制并发事务对同一个记录的访问**

### 关于幻读的补充说明

> 以下内容整合自 [为什么MVCC无法完全避免幻读现象.md](为什么MVCC无法完全避免幻读现象.md)

#### 先明确概念

- **不可重复读**：同一事务里，两次读**同一行**，结果不同（被其他事务修改了）
- **幻读**：同一事务里，两次查询**同一范围**，第二次多出了（或少了）几行

可重复读（RR）通过 **MVCC** 解决了不可重复读，但幻读没完全解决。

## 五、锁机制

### Mysql有哪些锁？

- **全局锁**
- **表级锁**
- **行级锁**

### 全局锁

#### 全局锁怎么用？

**使用全局锁**

```mysql
flush tables with read lock
```

数据库将处于**只读状态**

**释放全局锁**

```mysql
unlock tables
```

会话断开也会释放

>不需要你手动输入 `unlock tables`，只要你当前执行加锁的那个数据库连接（会话）断开了，MySQL 会自动帮你把全局锁给释放掉。

#### 应用场景

全库逻辑备份

#### 缺点

业务停滞

#### 既然备份数据库时使用全局锁会影响业务，有什么方法可以避免吗？

如果数据库的存储引擎支持**可重复读**的隔离级别，可以在备份前**开启事务**，其他事务可以正常进行，备份事务期间都使用Read View，备份数据不会改变

*备份数据库的工具是mysqldump，在使用mysqldump时加上 `--single-transaction`，就可以实现备份数据前开启事务*

*这种方法只适用于支持可重复读隔离级别的存储引擎，InnoDB可以，MyISAM不行*

### 表级锁

#### 表级锁有哪些？

- **表锁**
- **元数据锁（MDL）**
- **意向锁**
- **AUTO-INC锁**

#### 表锁


**标记共享锁**
当前会话和其他会话可以对该表读，不能写
*当前会话不能访问其他表*

```sql
lock tables student read   -- 表级共享锁
```

**表级排他锁**
当前会话可以对该表进行读写，其他会话读写都不可

*当前会话不能访问其他表*

```sql
lock tables student write   -- 表级排他锁
```

> 其他会话写该表是**阻塞等待**，不是直接报错。

> [!当前会话不能访问其他表的原因]
>
> `LOCK TABLES` 执行时会**隐式释放之前持有的所有表锁**，并且在锁定期间当前会话只能访问已锁定的表，访问未锁定表会直接报错：
>
> ```
> ERROR 1100: Table 'xxx' was not locked with LOCK TABLES
> ```

解锁

```sql
unlock tables
```

#### 元数据锁（MDL）

当我们对数据库表操作时，会自动加元数据锁

- **增删查改** → 元数据读锁
- **对表结构进行修改** → 元数据写锁

>MDL不需要显示调用，那它什么时候被释放？

**事务提交后会释放**


1. 如果有一个select事务，长时间不提交，MDL读锁一直没被释放
2. 其他select事务不影响，读读不冲突
3. 此时修改表结构，MDL写锁阻塞
4. 其他select事务会阻塞，读写冲突

所以，在修改表结构前，需要查看是否有事务加上了MDL读锁，如果有，最好kill掉再修改

> 详细参考：[怎么查MDL锁](怎么查MDL锁.md)

```sql
-- 查看 MDL 锁
SELECT 
    object_type,
    object_schema,
    object_name,
    lock_type,
    lock_duration,
    lock_status,
    owner_thread_id
FROM performance_schema.metadata_locks
WHERE object_type = 'TABLE';

-- 关键字段说明
-- lock_type: SHARED_READ（读锁）/ EXCLUSIVE（写锁）
-- lock_status: GRANTED（已持有）/ PENDING（阻塞等待中）
-- owner_thread_id: 持有锁的线程 ID

-- 找到对应的会话并 kill
SELECT 
    t.processlist_id,
    t.processlist_user,
    t.processlist_time,
    t.processlist_info,
    m.lock_type,
    m.lock_status
FROM performance_schema.metadata_locks m
JOIN performance_schema.threads t ON m.owner_thread_id = t.thread_id
WHERE m.object_type = 'TABLE'
  AND m.lock_status = 'GRANTED';

-- 找到长时间持有读锁的事务后
KILL <processlist_id>;
```

**MDL阻塞场景说明：**

```
事务A: SELECT (MDL读锁，长时间未提交)
                    ↓
事务B: ALTER TABLE (申请MDL写锁，阻塞 PENDING)
                    ↓
事务C: SELECT (申请MDL读锁，也阻塞！)  ← 容易被忽视
```

事务C 被阻塞的原因是：写锁在队列里等待，后续读锁排在写锁后面，**防止写锁饥饿**。这也是为什么一个未提交的长事务可能导致整张表查询全部卡住，影响非常大。

#### 意向锁

在使用 InnoDB 引擎的表里对某些记录加上「共享锁」之前，需要先在表级别加上一个「**意向共享锁**」；

在使用 InnoDB 引擎的表里对某些纪录加上「独占锁」之前，需要先在表级别加上一个「**意向独占锁**」；

> 这里指的共享锁和独占锁是**行级锁**中的两种，详细参考：[此处共享锁和独占锁指的是？](此处共享锁和独占锁指的是？.md)

**意向锁的逻辑说明：**

> 详细参考：[此处逻辑是？](此处逻辑是？.md)

意向共享锁和意向独占锁是表级锁，不会和行级的共享锁和独占锁发生冲突，而且意向锁之间也不会发生冲突，只会和共享表锁（`lock tables ... read`）和独占表锁（`lock tables ... write`）发生冲突。

表锁和行锁是满足**读读共享、读写互斥、写写互斥**的。

如果没有「意向锁」，那么加「独占表锁」时，就需要遍历表里所有记录，查看是否有记录存在独占锁，这样效率会很慢。那么有了「意向锁」，由于在对记录加独占锁前，先会加上表级别的意向独占锁，那么在加「独占表锁」时，直接查该表是否有意向独占锁，如果有就意味着表里已经有记录被加了独占锁，这样就不用去遍历表里的记录。

所以，**意向锁的目的是为了快速判断表里是否有记录被加锁**

#### AUTO-INC锁

数据库会自动给主键赋值递增的值，这主要是通过 AUTO-INC 锁实现的。

AUTO-INC 锁是特殊的表锁机制，锁不是在事务提交后才释放，而是在**执行完插入语句后就会立即释放**。

在插入数据时，会加一个表级别的 AUTO-INC 锁，然后为被 AUTO_INCREMENT 修饰的字段赋值递增的值，等插入语句执行完成后，才会把 AUTO-INC 锁释放掉。

那么，一个事务在持有 AUTO-INC 锁的过程中，其他事务的如果要向该表插入语句都会被阻塞，从而保证插入数据时，被 AUTO_INCREMENT 修饰的字段的值是连续递增的。但是，AUTO-INC 锁在对大量数据进行插入的时候，会影响插入性能，因为另一个事务中的插入会被阻塞。

因此，在 **MySQL 5.1.22 版本**开始，InnoDB 存储引擎提供了一种**轻量级的锁**来实现自增。一样也是在插入数据的时候，会为被 AUTO_INCREMENT 修饰的字段加上轻量级锁，然后给该字段赋值一个自增的值，就把这个轻量级锁释放了，而不需要等待整个插入语句执行完后才释放锁。

InnoDB 存储引擎提供了个 `innodb_autoinc_lock_mode` 的系统变量，是用来控制选择用 AUTO-INC 锁，还是轻量级的锁。

- 当 `innodb_autoinc_lock_mode = 0`，就采用 AUTO-INC 锁，语句执行结束后才释放锁；
- 当 `innodb_autoinc_lock_mode = 2`，就采用轻量级锁，申请自增主键后就释放锁，并不需要等语句执行后才释放。
- 当 `innodb_autoinc_lock_mode = 1`：普通 INSERT 语句，自增锁在申请之后就马上释放；类似 INSERT ... SELECT 这样的批量插入数据的语句，自增锁还是要等语句结束后才被释放；

当 `innodb_autoinc_lock_mode = 2` 是性能最高的方式，但是当搭配 binlog 的日志格式是 statement 一起使用的时候，在**主从复制的场景**中会发生数据不一致的问题

> 详细设置参考：[[如何设置 innodb_autoinc_lock_mode]]
>
> 注意：该参数**不支持运行时动态修改**，必须重启才能生效。
>
> 查看当前值：`SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode';`

| 值 | 模式 | 说明 |
|---|---|---|
| `0` | 传统模式 | 每次 INSERT 都加表级 AUTO-INC 锁，并发差 |
| `1` | 连续模式 | 普通 INSERT 用轻量锁，批量 INSERT 用表锁，MySQL 8.0 前默认 |
| `2` | 交错模式 | 完全不用表锁，并发最好，MySQL 8.0 后默认，但 binlog 需用 row 格式 |

### 行级锁

**InnoDB支持行级锁，MyISAM不支持**

- **快照读**（普通的SELECT语句）是不会对记录加锁的
- **锁定读**（当前读），需要用下面这两个方式，且用的时候需要在同一个事务中

```sql
SELECT ... LOCK IN SHARE MODE
SELECT ... FOR UPDATE
```

#### 行级锁的类型

- **Record Lock**：记录锁，只锁定一条记录
- **Gap Lock**：间隙锁，锁定一个范围，不含记录本身
- **Next-key Lock**：记录锁和间隙锁的组合，锁定一个范围，并锁定记录本身

#### Record Lock（记录锁）

分为**S型记录锁**和**X型记录锁**

- 一个事务对一条记录加S锁后，其他事务可以对他加S锁，不可以加X锁
- 一个事务对一条记录加X锁后，其他事务不可以加S、X锁
	
#### Gap Lock（间隙锁）

间隙锁，存在于**可重复读的隔离级别和串行化的隔离级别**，目的是解决可重复读出现的幻读现象

例如，范围为（3,5）的间隙锁，不能插入id为4的记录

间隙锁也有S和X锁，但没啥区别，**间隙锁之间是兼容的**，也就是说不同事务可以同时持有相同范围的间隙锁

> 关于间隙锁为何无法完全解决幻读，参考：[为什么MVCC无法完全避免幻读现象](为什么MVCC无法完全避免幻读现象.md)

#### Next-Key Lock（临键锁）

例如，范围为（3,5] 的临键锁，不能插入4和5

#### 插入意向锁

一个事务在执行插入事务前，会先查看插入的位置是否被加了间隙锁，如果存在间隙锁，当前事务阻塞并生成一个**插入意向锁**，表示有事务想在区间内插入数据，但目前处于等待状态

[[插入意向锁的意义]]

### 什么SQL语句会加行级锁？

```sql
SELECT ... LOCK IN SHARE MODE    -- 共享锁
SELECT ... FOR UPDATE             -- 独占锁
UPDATE 和 DELETE                  -- 独占锁
```

### Mysql是怎么加行级锁的？

加锁的对象是**索引**，加锁的基本单位是**next-key lock**

- 临键锁是**左开右闭**区间
- 间隙锁是**左开右开**区间

### 什么情况下next-key lock 会退化为记录锁或间隙锁？

**在使用记录锁或者间隙锁就能避免幻读现象的情况下，就会退化**

#### 唯一索引（主键索引）等值查询

*默认是当前读*

当我们用唯一索引进行等值查询的时候，查询的记录存不存在，加锁的规则也会不同：

- 当查询的记录是**「存在」的**，在索引树上定位到这一条记录后，将该记录的索引中的 next-key lock 会退化成**「记录锁」**。
- 当查询的记录是**「不存在」的**，在索引树找到第一条大于该查询记录的记录后，将该记录的索引中的 next-key lock 会退化成**「间隙锁」**
  - 假如查 id=2，不存在，此时表中有 id=1、id=5……，next-key lock 会退化为 (1, 5) 的间隙锁，防止其他事务插入 id=2、3、4 的记录产生幻读。

## 六、日志系统

### Mysql有哪几种日志？

- **undo log**（回滚日志）：是 **InnoDB** 存储引擎层生成的日志，实现了事务的**原子性**，主要用于事务回滚和 MVCC
- **redo log**（重做日志）：是 **InnoDB** 存储引擎层生成的日志，实现了事务的**持久性**，主要用于掉电等故障恢复
- **binlog**（归档日志）：是 **Server** 层生成的日志，主要用于**数据备份**和**主从复制**

### undo log

#### 为什么需要undo log？

当我们增删改时，Mysql会隐性的开启事务，执行完一条语句是否提交事务，是由参数 `autocommit` 决定的，默认是开启的

如果一个事务运行过程中，Mysql发生了崩溃，事务还未提交，怎么回滚到事务开启前的数据呢？

如果我们在事务执行过程中，记录回滚时需要用到的信息到日志中，实现这一机制的就是**undo log**

- 当插入记录时，将记录的主键值记录下来，回滚时删除对应主键值的记录即可
- 当删除记录时，将记录的完整信息记录下来，回滚时新增记录即可
- 当修改记录时，将被更新列的旧值记录下来，回滚时更新回去即可

#### undo log 两大作用

1. **实现事务回滚**，保障事务的原子性。事务处理过程中，如果出现了错误或者用户执行了 ROLLBACK 语句，MySQL 可以利用 undo log 中的历史数据将数据恢复到事务开始之前的状态。
2. **实现 MVCC（多版本并发控制）关键因素之一**。MVCC 是通过 ReadView + undo log 实现的。undo log 为每条记录保存多份历史数据，MySQL 在执行快照读（普通 SELECT 语句）的时候，会根据事务的 Read View 里的信息，顺着 undo log 的版本链找到满足其可见性的记录

> 详细参考：[快照读时undo log和read view的具体作用](快照读时undo log和read view的具体作用.md)

### Buffer Pool

#### 为什么需要Buffer Pool？


> MySQL 的数据最终是保存在**磁盘**上的。如果每次读写数据都直接去跟磁盘打交道，那么磁盘的 I/O 瓶颈会直接把整个数据库的性能拉垮。
> 
> 为了解决这个问题，MySQL InnoDB 引擎在启动时，会向操作系统申请一块**连续的内存空间**，这块内存就是 **Buffer Pool**。

Mysql的数据都是存在磁盘中的，当我们需要更新数据时，先要把磁盘中的数据拿出来，放到内存中，再将内存中的数据修改，修改后的数据是直接写回磁盘好呢？还是放在内存好呢？

放在内存好，下次要查询此数据直接从内存拿即可

**为此，InnoDB专门设计了一个缓冲池（Buffer Pool），来提高数据库的性能**

有了Buffer Pool之后：

- 当需要查数据时，数据如果存在缓冲池，直接读缓冲池就可
- 当需要改数据时，如果数据在缓冲池，将缓冲池中的**数据所对应的数据页**修改，并标记为**脏页**即可，以后再挑选一个合适的时机由**后台线程**写回

#### 数据页是什么

MySQL InnoDB 以**页（Page）**为单位管理数据，默认每页 **16KB**，数据页就是存放表中行记录的基本单位。

```
磁盘
└── 表空间文件（.ibd）
    └── 数据页 Page（16KB）
        └── 行记录 row
```

#### Buffer Pool 和数据页的关系

```
磁盘上的数据页  ──读入──▶  Buffer Pool（内存）
                                 ↓ 修改
                            脏页（dirty page）
                                 ↓ 刷盘
                          磁盘上的数据页（更新）
```

Buffer Pool 是**内存缓冲区**，缓存的内容就是从磁盘读进来的数据页。对数据的修改先在 Buffer Pool 里的数据页上进行，这时候内存里的页和磁盘上的页不一致，称为**脏页**。

### redo log

#### 为什么需要redo log？

因为Buffer Pool是基于内存的，一旦断电，数据就会丢失

为了防止这种情况，当一条记录需要更新时，InnoDB会先更新内存，再将此数据页的修改信息写入redo log中

#### 为什么不直接将脏页写回？

事务提交时，脏页刷回磁盘（随机IO，很慢），但 写redo log（顺序IO，很快）。

```
事务提交
  ↓
redo log 写入磁盘 ✅（顺序IO，快）
  ↓
Buffer Pool 脏页之后慢慢刷盘（随机IO，异步）

如果中间崩溃 → 用 redo log 重放，恢复数据页
```

这就是 **WAL（Write-Ahead Logging）预写日志**机制。

#### 什么是redo log？

redo log是**物理日志**，记录了某个数据页做了什么修改

事务提交时，只需要将redo log持久化到磁盘即可

#### redo log 记录的是什么

```
redo log："对第X号数据页，偏移量Y处，写入了Z字节的数据"
```

==是磁盘上真实数据页的物理修改记录，不是 Buffer Pool 本身。==

#### 被修改 Undo 页面，需要记录对应 redo log 吗？

**需要的。** 开启事务后，InnoDB 层更新记录前，首先要记录相应的 undo log，如果是更新操作，需要把被更新的列的旧值记下来，也就是要生成一条 undo log，undo log 会写入 Buffer Pool 中的 Undo 页面。不过，在内存修改该 Undo 页面后，也是需要记录对应的 redo log，因为 undo log 也要实现持久性的保护

#### redo log 和 undo log 区别在哪？

这两种日志是属于 InnoDB 存储引擎的日志，它们的区别在于：

- **redo log** 记录了此次事务「修改后」的数据状态，记录的是更新之后的值，主要用于事务**崩溃恢复**，保证事务的**持久性**。
- **undo log** 记录了此次事务「修改前」的数据状态，记录的是更新之前的值，主要用于事务**回滚**，保证事务的**原子性**。

所以有了 redo log，再通过 WAL 技术，InnoDB 就可以保证即使数据库发生异常重启，之前已提交的记录都不会丢失，这个能力称为 **crash-safe（崩溃恢复）**。可以看出来，redo log 保证了事务四大特性中的持久性

#### redo log 要写到磁盘，数据也要写磁盘，为什么要多此一举？

写入 redo log 的方式使用了**追加操作**，所以磁盘操作是**顺序写**，而写入数据需要先找到写入位置，然后才写到磁盘，所以磁盘操作是**随机写**。

磁盘的「顺序写」比「随机写」高效的多，因此 redo log 写入磁盘的开销更小

#### 产生的 redo log 是直接写入磁盘的吗？

**不是的。** 实际上，执行一个事务的过程中，产生的 redo log 也不是直接写入磁盘的，因为这样会产生大量的 I/O 操作，而且磁盘的运行速度远慢于内存。

所以，redo log 也有自己的缓存——**redo log buffer**，每当产生一条 redo log 时，会先写入到 redo log buffer

#### redo log什么时候刷盘？

> 以下内容提取自图片 `images/image-20260206181927386.png`（来源：小林coding/MySQL教程）

redo log buffer 中的日志写入 redo log 文件（即刷盘），有以下几种触发场景：

**1. MySQL 后台线程每秒轮询**
- InnoDB 有一个后台线程，每隔 **1 秒** 执行一次 write + fsync
- 即使事务未提交，redo log buffer 中的日志也会被写入磁盘
- 这意味着**未提交事务的 redo log 也可能被持久化**

**2. redo log buffer 达到一半容量**
- 当 redo log buffer 占用空间达到 `innodb_log_buffer_size` 的 **50%** 时
- 后台线程会主动触发 write（写入 Page Cache），但不会 fsync（因为事务未提交）

**3. 事务提交时（`innodb_flush_log_at_trx_commit=1`）**
- 每次 COMMIT 都会触发 fsync
- 这是最频繁的刷盘场景，也是高并发下 IO 压力的主要来源

**4. 并发事务的“捎带”刷盘（也会触发组提交优化）**

redo log buffer 是连续写入的。当事务 B 提交并触发强制刷盘（`innodb_flush_log_at_trx_commit=1`）时，会将当前 buffer 中直到 B 为止的所有日志全部刷入磁盘。此时，若有并发事务 A 尚未提交，其产生的 redo log 只要已经写入 buffer，就会被 B **顺带/捎带** 刷入磁盘。

*(注：多事务同时提交时，MySQL 会通过**组提交（Group Commit）*_机制将这些并发提交合并为一次 `fsync`，从而提升整体捎带效率。)_

**5. 正常关闭 MySQL 时**
- MySQL 关闭时会触发一次完整的 redo log 刷盘（包括 checkpoint）

#### innodb_flush_log_at_trx_commit 参数

> 以下内容提取自图片 `images/image-20260206182024310.png`

| 值 | 行为 | 数据安全性 | 性能 |
|---|---|---|---|
| **0** | 事务提交时只留在 redo log buffer，不写入磁盘，**每秒**由后台线程刷盘 | 崩溃可能丢 1 秒数据 | 最高 |
| **1**（默认） | 每次事务提交时**直接 fsync 刷盘**到磁盘文件 | 事务持久性有保障，不丢数据 | 最低（IO 开销最大） |
| **2** | 每次事务提交时只写入 OS 的 **Page Cache**，由 OS 异步刷盘 | MySQL 进程崩溃不丢，但 OS 崩溃可能丢数据 | 较高 |

**关键区别：**

- **值为 0**：redo log 只留在 redo log buffer，不进行 write，依赖后台线程每秒一次的刷盘。此时如果 MySQL 崩溃，会丢失 1 秒的数据。
- **值为 2**：redo log 写入 Page Cache（write），但不进行 fsync。如果 MySQL 崩溃，Page Cache 还在，数据不会丢；如果操作系统崩溃，Page Cache 丢失，数据会丢。
- **值为 1**：redo log 写入 Page Cache 后立即 fsync，保证数据不丢。

#### redo log 文件写满了怎么办？

> 以下内容提取自图片 `images/image-20260206184605075.png`、`image-20260206184615669.png`、`image-20260206184622704.png`

**redo log 的文件结构：**

redo log 是**固定大小、循环写入**的。InnoDB 默认配置一组 redo log 文件（称为 redo log Group），通常包含 2 个文件：`ib_logfile0` 和 `ib_logfile1`。

```
ib_logfile0    ib_logfile1
```

每个 redo log File 的大小是固定的（默认为 48MB，建议生产环境设置为 1GB ~ 2GB 每个）。

**写入机制：**

redo log 有两个关键指针：
- **write pos**：当前写入的位置，一边写一边往后移
- **checkpoint**：当前擦除的位置，擦除后往后移

```
redo log buffer
    ↓
┌────────────────────────────────────────┐
│  ib_logfile0  │  ib_logfile1          │
│  [checkpoint → write pos → 循环...]   │
└────────────────────────────────────────┘
```

当 `write pos` 追上了 `checkpoint`，表示 redo log 已经写满，此时 **InnoDB 必须强制刷脏页**，将 checkpoint 往前推进，释放空间。

**写满的后果：**
- 系统**不能再接受新的更新请求**，所有更新操作会被阻塞
- 这会导致 **QPS 暴跌**
- 建议：redo log 不要设置太小。如果是几 TB 的磁盘，建议直接设置 **4 个文件、每个文件 1GB**。太小会导致频繁强制刷盘，WAL 机制的优势就发挥不出来了。

### binlog

#### binlog是什么？
	
binlog是 **Server层** 生成的二进制日志

它记录了所有数据库表结构变更和表数据修改的日志

#### redo log和binlog的区别

1. **适用对象不同**
   - redo log 只适用于 **InnoDB**
   - binlog 适用于所有存储引擎，因为它是在 Server 层

2. **文件格式不同**

3. **写入方式不同**
   - redo log 是**循环写**，写满就重头写
   - binlog 是**追加写**，写满就创建新的文件

   > 你的质疑是对的，但需要区分一下"追加写"的含义。
   >
   > redo log 的写入方式确实不是纯粹的追加写，而是**循环覆盖写**。它有固定大小的日志文件组（比如两个文件 ib_logfile0、ib_logfile1），写满之后会回到头部覆盖旧数据，所以不能无限保留历史记录。
   >
   > 你可能觉得它是"追加写"，是因为在**单次写入行为**上，redo log 确实是顺序往后追加的，不是随机写。但这只是物理 I/O 层面的特性，跟 binlog 那种"写满就新建文件、历史永久保留"的追加语义是不同的。
   >
   > 所以原文的表述没有错，关键在于：
   >
   > - redo log：固定空间，循环覆盖，旧数据会被淘汰
   > - binlog：无限扩展，追加新文件，历史完整保留
   >
   > 这也正好解释了用途的差异——redo log 只需要保留"还没刷盘的脏页"对应的日志，够崩溃恢复用就行；binlog 需要完整历史，才能支持主从复制和按时间点还原。

4. **用途不同**
   - redo log 用于**断电故障恢复**
   - binlog 用于**备份恢复**和**主从复制**

> 以下内容提取自图片 `images/image-20260206201022973.png`
>
> 该图对比了 redo log 与 binlog 在写入方式、适用对象、持久化策略以及用途上的差异，为上述文字的图形化总结。

#### binlog什么时候刷盘？

**事务执行时，先把日志写到 `binlog cache` 中，事务提交时，再把 binlog cache 写到 binlog 文件中**

*binlog cache 每个线程都有一份*

**binlog文件是操作系统文件缓存，还需要持久化到磁盘**

Mysql提供 `sync_binlog` 来控制binlog持久化到磁盘上的频率

- `sync_binlog=0`：每次事务提交都只 **write**（binlog cache写到binlog文件），什么时候 **fsync**（binlog文件持久化到磁盘）由操作系统决定
- `sync_binlog=1`：每次事务提交先write，然后马上fsync
- `sync_binlog=N`（N>1）：每次事务提交都write，累计N个事务后fsync

一般设置为 100 ~ 1000 中的某个数值

### 两阶段提交

#### 为什么需要两阶段提交？

> 以下内容提取自图片 `images/image-20260206215051245.png`

两阶段提交是为了解决 **redo log**（InnoDB 引擎日志）和 **binlog**（Server 层日志）之间的**逻辑一致性问题**。

**反证法说明：**

| 场景 | 先写 redo log 后写 binlog | 先写 binlog 后写 redo log |
|---|---|---|
| 崩溃发生在中间 | redo log 已写但 binlog 没写完 → 主库恢复后数据正确（因为 redo log 能恢复），但从库用 binlog 恢复时会**缺失这次更新** | binlog 已写但 redo log 没写完 → 主库认为事务无效，但从库用 binlog 恢复时会**多出一次更新** |
| **结果** | **主备数据不一致** | **主备数据不一致** |

两阶段提交让"所有人都说 ok 了，再一起提交"，保证了 redo log 和 binlog 的一致性。

#### 两阶段提交的过程

> 以下内容提取自图片 `![[images/image-20260206220117584.png]]`、`![[images/image-20260206220126370.png]]`

两阶段提交将 redo log 的写入拆成 **Prepare** 和 **Commit** 两个步骤，中间插入 binlog 的写入：

![[images/image-20260206220117584.png]]
![[images/image-20260206220126370.png]]

```
1. 执行器调用 InnoDB 引擎，修改内存中的数据
2. 写入 redo log（Prepare 阶段）✅
3. 写入 binlog ✅
4. 写入 redo log（Commit 阶段）✅
```

具体流程：

1. **Prepare 阶段**：InnoDB 将修改记录写入 redo log，并将 redo log 状态设置为 Prepare
2. **写 binlog**：Server 层将修改记录写入 binlog，并完成刷盘
3. **Commit 阶段**：InnoDB 将 redo log 状态设置为 Commit，表示事务已提交

#### 异常重启会出现什么情况？

> 以下内容提取自图片 `![[images/image-20260206220416207.png]]`、`![[images/image-20260206220428303.png]]`

![[images/image-20260206220416207.png]]
![[images/image-20260206220428303.png]]

崩溃恢复时，MySQL 会扫描 redo log，按以下规则判断：

| redo log 状态 | binlog 情况 | 恢复行为 |
|---|---|---|
| 有 **Prepare** + 有 **Commit** 标识 | — | ✅ **直接提交事务** |
| 只有 **Prepare**（无 Commit） | binlog **存在且完整** | ✅ **提交事务** |
| 只有 **Prepare**（无 Commit） | binlog **不存在或不完整** | ❌ **回滚事务** |

**时刻 A**（redo log Prepare 后、binlog 写入前崩溃）：
- binlog 还没写 → 事务**回滚**
- binlog 不会传到备库，主备一致

**时刻 B**（binlog 写完、redo log Commit 前崩溃）：
- redo log 只有 Prepare，但 binlog 已写完且完整
- 按规则**提交事务**
- 原因：binlog 已经写入了，之后会被从库使用，主库也必须提交才能保持主备一致

**为什么 `Prepare` 状态的 redo log 加上完整的 binlog 也要提交？**

- **逻辑一致性**：因为 binlog 一旦写完并落盘，它就会被从库（Slave）读取并执行。
- **必须提交**：如果此时主库重启后因为 redo log 是 `Prepare` 就选择回滚，那么主库就没有这笔数据，而从库却有了。
- **结论**：为了保证主从数据绝对一致，只要 binlog 写入成功了，主库重启后就必须把对应的 `Prepare` 事务提交掉。

## 七、主从复制

### 主从复制是如何实现的？

主从复制是依赖 **binlog** 实现的，也就是将数据库上发生的所有变化以二进制的形式保存到磁盘，复制也就是将binlog的数据从主库传输到从库上

这个复制过程是**异步**的，也就是说主库上的事务不会阻塞等待复制binlog的线程同步完成

**主从复制的流程如下：**

主库写入binlog → 从库创建一个专门的 **IO线程** 连接主库的 **log dump线程** → 接收binlog并写入 **relay log（中继日志）** 中 → 从库再创建一个 **SQL线程** 从 relay log 中读取binlog来回放

### 从库是不是越多越好？

**不是**，从库越多，从库连接上来的IO线程越多，主库也需要提供相同数量的log dump线程，对主库资源消耗较高

### Mysql主从复制还有哪些模型？

- **同步复制**：提交事务的线程需要等待**所有从库**的复制成功响应，才能返回客户端结果
- **异步复制**：不需要等待从库复制成功，直接返回客户端结果
- **半同步复制**：事务线程不用等待所有从库复制成功，只需**一半**从库复制成功，就可以返回客户端结果
