# 2064.分配给商店的最多商品的最小值（二分答案 + 上取整贪心）

> [!abstract] 题目
> 给定整数 `n`（零售商店数量）和长度为 `m` 的数组 `quantities`，`quantities[i]` 是第 `i` 种商品的数量。分配规则：
> - **所有**商品必须分配完；
> - 每家商店**最多只能分到一种**商品（可以分到 0 件）；
> - 同一种商品可以拆开分给多家商店。
>
> 设分配后单个商店拿到的商品数量的最大值为 x，返回 x 的**最小**可能值。

| 参数 | 范围 |
|------|------|
| m == quantities.length | 1 ~ 10⁵ |
| n | m ~ 10⁵（保证 m ≤ n） |
| quantities[i] | 1 ~ 10⁵ |
| 难度/标签 | 中等 · 二分查找、数组 |

**示例 1：**
```
输入：n = 6, quantities = [11,6]
输出：3
解释：11 拆成 3+3+3+2 占 4 家店，6 拆成 3+3 占 2 家店，共 6 家，最大值为 3。
```

**示例 2：**
```
输入：n = 7, quantities = [15,10,10]
输出：5
解释：15 拆成 5+5+5 占 3 家，两个 10 各拆成 5+5 占 4 家，共 7 家，最大值为 5。
```

## 核心思路：正着分难，反过来「猜答案 + 验证」

直接构造分配方案很难：拆多少份、给哪家店，组合爆炸。但**把答案当成已知量**，问题立刻变简单——

> 假设允许「单店最多拿 x 件」，那么这 n 家店够不够用？

这就是**二分答案**的套路：答案本身不好求，但「给定答案，判定可行性」很容易。

### 单调性（能二分的前提）

x 越大，每种商品需要拆的份数越少，需要的商店数越少。所以可行性关于 x 是**单调**的：

| x | 需要的商店数 | 可行？ |
|---|---|---|
| 小 | 多 | 否 |
| … 分界点（答案） | = n 附近 | 是 |
| 大 | 少 | 是 |

一旦 x 可行，所有更大的 x 都可行 → 判定函数是 `false…false | true…true` 的阶梯，二分找第一个 true。

### check(x)：为什么可以按商品种类独立求和

关键在题目那句「每家商店最多只能分到一种商品」——**不同种类的商品不共享商店**，所以各类之间互不干扰，可以分开算再相加：

- 第 i 种有 `q` 件，每店最多 x 件 → 至少需要 `⌈q / x⌉` 家店（这就是最优的，装满一家再开下一家，贪心）；
- 总需求 `cnt = Σ ⌈quantities[i] / x⌉`；
- `cnt ≤ n` 即可行（商店可以空着，用不完不影响）。

上取整用整数写法 `(q + x - 1) / x`，恒等式与坑见 [[机试]]「上取整恒等式」小节（**别用 `Math.ceil` 浮点**）。

## 代码（灵神·开区间二分）

```java
class Solution {
    public int minimizedMaximum(int n, int[] quantities) {
        int mx = 0;
        for (int q : quantities) {
            mx = Math.max(mx, q);
        }

        int left = 0;          // 恒为「不可行」的一侧（哨兵，永不参与 check）
        int right = mx;        // 恒为「可行」的一侧（哨兵，无需验证）
        while (left + 1 < right) {
            int mid = (left + right) >>> 1;
            if (check(mid, n, quantities)) {
                right = mid;   // mid 可行 → 答案在左半（含 mid）
            } else {
                left = mid;    // mid 不可行 → 答案严格在右半
            }
        }
        return right;          // 第一个可行的 x
    }

    private boolean check(int mx, int n, int[] quantities) {
        int cnt = 0;
        for (int q : quantities) {
            cnt += (q + mx - 1) / mx;   // ⌈q / mx⌉
        }
        return cnt <= n;
    }
}
```

**复杂度**：时间 O(m log U)，U = max(quantities) ≤ 10⁵（约 17 次迭代）；空间 O(1)。

## 开区间写法的四个细节（这题的精髓）

灵神用的是**开区间** `(left, right)`：循环不变量是「left 一定不可行，right 一定可行」，答案就是 right。

### 1. `left = 0` 是哨兵，顺手规避了除零

x = 0 显然分不完任何商品（`quantities[i] ≥ 1`），天然满足「left 不可行」。而开区间的循环条件 `left + 1 < right` 保证 `mid ≥ left + 1 ≥ 1`，**0 永远不会被传进 check**，所以 `(q + mx - 1) / mx` 不会除零。

换成闭区间 `l = 1` 也对，但开区间省掉了「验证下界」这一步。

### 2. `right = mx` 是哨兵，不需要验证就知道可行

取 x = max(quantities) 时，每种商品都能被一家店全吃下 → 需要 m 家店，而题目保证 **m ≤ n**，必然可行。所以 right 天生满足「一定可行」，直接当上界，二分区间从不越界。

也因此**答案上界就是 mx**，不用取 10⁵ 这种保守值。

### 3. `>>>` 而不是 `>>`

`(left + right) >>> 1` 是无符号右移：即使 `left + right` 溢出成负数，无符号移位仍能得到正确的中点。本题 mx ≤ 10⁵ 不会溢出，但这是**值域二分的肌肉记忆**——换成 `Integer.MAX_VALUE` 附近的值域时 `(l + r) / 2` 会崩，而 `>>> 1` 不会。

### 4. check 里的 `cnt` 为什么用 int 不溢出

粗看很危险：`Σ quantities[i]` 最大 10⁵ × 10⁵ = 10¹⁰，早就爆 int。但被 check 的 mid **永远不会小到那个程度**：

- 上取整满足 `⌈q/x⌉ ≤ 2·⌈q/2x⌉`，即 x 减半，份数最多翻倍；
- 每次调用 check(mid) 时，右端点 right（≈ 2·mid 量级或是哨兵 mx）都是**已知可行**的，即 `cnt(right) ≤ n`；
- 所以 `cnt(mid) ≤ 2·cnt(right) ≤ 2n ≤ 2×10⁵`，稳稳在 int 内。

想省心也可以直接写 `long cnt`，或在循环里 `if (cnt > n) return false;` 提前剪枝。

## 等价的闭区间写法（对照记忆）

```java
int l = 1, r = mx;
while (l <= r) {
    int mid = l + (r - l) / 2;
    if (check(mid, n, quantities)) r = mid - 1;   // 可行，试更小
    else l = mid + 1;
}
return l;   // l 收敛到第一个可行值
```

两种写法只差「哨兵是否参与循环」：闭区间的 `l = 1` 必须自己保证不除零；开区间用 `left = 0` 把非法值挡在循环外。

## 面试话术

1. **一句话思路**：正向构造分配方案组合太多，但「限定单店上限 x，判断 n 家店够不够」很容易算，可行性对 x 单调，于是二分答案，找第一个可行的 x。
2. **check 为什么能贪心**：因为每家店只能放一种商品，不同种类不抢商店，彼此独立。那么第 i 种 q 件在上限 x 下最少要 `⌈q/x⌉` 家店——装满一家再开下一家，不可能更省。把所有种类加起来和 n 比即可。
3. **上下界怎么定**：下界取 0 作哨兵（x=0 必然不可行，也避免除零）；上界取 max(quantities)，因为此时每种商品一家店装完，用掉 m 家，题目保证 m ≤ n，所以必然可行——上界不用瞎猜。
4. **为什么写 `>>> 1`**：无符号右移防止 `left + right` 溢出，值域二分的通用习惯。
5. **溢出风险**：`cnt` 理论上界看似 10¹⁰，但被测试的 mid 至少是某个已知可行值的一半量级，所以 cnt 不超过 2n；保险起见可以用 long 或提前剪枝。
6. **复杂度**：O(m log max(quantities))，约 10⁵ × 17 次基本运算。
