# 项目面试考前速览卡（20 题）

> **用法**：面试前 20 分钟扫一遍。每题只给「**开口第一句**（怎么起头）+ **必须说到**（漏了就没分）+ **关键数字**」。
> **配套**：完整答案见 [[项目八股热门面试题]]；本文是它的**索引和触发器**，不是替代品。
> **纪律**：① 数字必须精确；② 先说结论再展开；③ 讲不出的别硬编——**不知道就说不知道，但要给出「正确做法应该是什么」**。

## 一、项目总纲（3 题）

### ① 用 30 秒介绍你的项目 —— 对应 Q1

**开口第一句：**
> 「这是一个基于 JDK 17 + Spring Boot 3.2.5 + Spring Cloud Alibaba 2023.0.1.0 的微服务电商系统，14 个可独立部署的服务，覆盖商品、搜索、购物车、订单、支付、秒杀全链路。」

**必须说到：** 三条链路 —— **Canal 订阅 binlog 驱动 ES 索引 + 静态页** / **Seata AT 兜住跨 3 服务的下单事务** / **热点发现 → 隔离 → 网关去重准入 → MQ 异步下单的秒杀削峰**。

**关键数字：** 14 服务 · 17 张业务表 · 48 个 HTTP 接口 · 10 个 @FeignClient · 181 个 Java 文件 7358 行。

**红线：** 不要主动说「完全原创」。被问就实话说「基础骨架参考了公开的电商项目，热点发现链路、网关四层鉴权是我自己补的」。

### ② 项目里含金量最高的点是哪个 —— 对应 Q7

**开口第一句：**
> 「我选秒杀的热点发现 → 隔离 → 去重准入 → 异步下单这条闭环，因为它是全链路自建的。」

**必须说到（六步）：** ① 访问日志进 **Apache Druid**（事实表 `msitemlogs`）；② dw-service 查 Druid 做**时间窗口聚合** `group by uri having viewCount > threshold`；③ ElasticJob **每 30 秒**拉热点清单；④ **CAS 式 UPDATE** 隔离（`where id=x and is_lock=0 and store_count>0`，靠影响行数判成功）；⑤ 库存搬进 **Redis Hash `HotSeckillGoods`**，网关用 `OrderQueue:{username}:{id}` **INCR + 2 分钟 TTL** 做去重准入；⑥ 扔进 **RocketMQ `order-queue`** 异步落单。

**最关键的一句取舍：** 「**热点识别放在离线 OLAP 而不是在线统计**——因为在线埋点做 topN 本身就要抢锁、写 Redis，等于把热点问题又搬了一层。」

### ③ 面试官问「你的 QPS 是多少」怎么答 —— 对应 Q158

**开口第一句：**
> 「我是在**本地单机**压的——压测机和服务同机，中间件在同一台虚拟机上（192.168.172.100）。所以**绝对值不代表生产能力**，我关注的是**同一环境下优化前后的相对提升**。」

**必须说到：** 主动把边界划清（**环境 / 并发 / P99 还是均值** 这三连）；只报**倍数或百分比**。

**关键数字：** 压测记录的是 **P99 不是平均值**；商品详情对比「注释掉 @Cacheable」vs「恢复」；秒杀对比「同步下单」vs「网关去重准入 + MQ 异步」。

**加分：** 「**我压测中发现问题 → 修复 → 再压验证**」——这个闭环比任何数字都值钱。

## 二、秒杀链路（4 题 · 项目最独一份，优先讲）

### ④ 秒杀的技术难点有哪几个 —— 对应 Q140

**开口第一句：**
> 「我归纳成四个：**瞬时高并发、超卖、幂等、热点集中**。」

**必须说到（四个解法一一对应）：** 削峰用 **MQ** · 超卖用**原子操作** · 幂等用**唯一索引** · 热点用**隔离**。

**点睛句：** 「秒杀设计的精髓是**把「请求数」的压力，转化成「库存数」的压力**——最终打到 MySQL 的流量和商品库存是一个量级，而不是和请求数一个量级。」

---

### ⑤ 秒杀怎么防超卖 —— 对应 Q141

**开口第一句：**
> 「分两层：**Redis 层挡流量、数据库层兜正确性**。」

**必须说到：**
- **Redis 层**：`HGET` 判库存 + `HINCRBY` 扣减 —— **这两步不是原子的**，我现在套了 Redisson 锁兜住，但这是「用锁掩盖原子性问题」。
- **数据库层**：`UPDATE sku SET num = num - #{num} WHERE id = #{id} AND num >= #{num}`，靠 **InnoDB 行锁 + 条件更新** 保证原子，影响行数为 0 就是库存不足。

**关键数字 / 名词：** **`num >= #{num}` 是防超卖的核心** · 两层职责 = 性能层 + 正确性层。

**加分：** 「正确做法是用 **Lua 脚本**把判库存 + 扣库存合成原子操作，**锁就可以去掉**。」

### ⑥ 秒杀怎么保证幂等（一人一单）—— 对应 Q142

**开口第一句：**
> 「**我要先坦白，我目前只有一层，是不完整的。**」

**必须说到：**
- **现状**：网关 `OrderQueue:{username}:{id}` 做 **INCR + 2 分钟 TTL**，返回值 > 1 判重复。
- **漏洞**：Redis 重启 / 主从切换丢数据 / TTL 到期后重试 —— 都绕过去了；而且 `seckill_order` **没有 `(username, goods_id)` 唯一索引**，DB 层零兜底。
- **正确方案**：`ALTER TABLE seckill_order ADD UNIQUE KEY uk_user_goods (username, goods_id)`，插入时 catch `DuplicateKeyException` 当「已下单」返回。

**面试话术（背下来）：**
> 「**Redis 是性能层的挡板，挡掉 99% 的重复请求；唯一索引是正确性层的兜底，保证极端情况下也不会重。两层职责不同，不能只留一层。**」

### ⑦ 秒杀怎么削峰 / DB 最终承接多少流量 —— 对应 Q143

**开口第一句：**
> 「三层缓冲：**网关限流 + 去重准入 → Redis 扣减 → MQ 异步落单**。」

**必须说到：** 每层解决的问题不同 —— 网关限流解决「流量超过系统容量」· 去重准入解决「重复请求」· **Redis 扣减把竞争收敛到 Redis（DB 不参与竞争）** · MQ 解决「生产速度和消费速度不匹配」。

**关键数字：** 库存 100 件 → 最终落到 MySQL 的写操作是**几百次**（含订单 + 明细 + 状态），和「几万 QPS 的请求量」**差三个数量级**。

**加分：** 限流我用**快速失败（429）不是排队** —— 因为排队会占着连接不放，网关自己先被压垮。

## 三、数据一致与核心组件（8 题）

### ⑧ Canal 为什么用、链路是什么 —— 对应 Q56 + Q57

**开口第一句：**
> 「因为**手动双写会漏场景**——后台直接改库、批量脚本、其他服务改库、DBA 手工操作，这四类你根本没法保证它们都记得同步。」

**必须说到：** 链路是 **MySQL binlog → Canal 1.1.7 → canal-service(8083) → 下游 ES / 静态页**；订阅 **4 张表**（`shop_goods.sku`、`shop_goods.ad_items`、`shop_seckill.seckill_goods`、`shop_seckill.seckill_activity`）；一次 SKU 变更**同时驱动两件事**：更新 ES 索引 + 重建 Thymeleaf 静态页。

**关键细节：** 用 `getWithoutAck(100)` 批量拉 + 逐批 ack，**单条异常 catch 掉不中断主循环**；下游 Feign 调用放异步（因为 ES 写入和模板渲染都是重 IO，同步会拖慢 Canal 主循环导致 binlog 位点堆积）。

**主动坦白：** 「Canal 直连 Feign **缺一层 MQ 缓冲**，下游挂了只能 catch 丢弃、没有重试和堆积能力，标准做法是 **Canal → MQ → 消费者**。」

**可能被追问（必答）：** 「**静态化是什么？**」——把「模板 + 数据」提前渲染成完整 HTML 文件落盘，Nginx 直接发文件、不进 Java 服务。**关键是把动词分开**：ES 那条是「**同步**」（同一份数据的两种表示 → 一致性），静态页那条是「**重建**」（模板 + 多数据源的产物 → 只有「新不新」）。详见 **Q62**。

### ⑨ Seata AT 的两阶段 + undo_log —— 对应 Q46 + Q47

**开口第一句：**
> 「AT 的核心是**一阶段提交本地事务 + 二阶段补偿**，业务代码零侵入。」

**必须说到：**
- **一阶段**：拦截业务 SQL → 记录**前后镜像**写进 `undo_log` → 业务 SQL 和 undo_log **在同一个本地事务里一起提交** → 注册分支、申请全局锁。
- **二阶段提交**：只需**异步删除 undo_log**（因为数据已经提交了，很快）。
- **二阶段回滚**：用 **before image 生成反向 SQL** 恢复数据；改之前**校验两次** —— 当前值 == 前镜像 → 跳过（幂等）；当前值 == 后镜像 → 才回滚；**对不上就是被全局事务外的人改过 → 回滚失败抛 `Has dirty records when undo.`，不是硬覆盖**（防脏写放大）。

**关键数字 / 名词：** `tx-service-group: tx_shop` · Seata Server **2.0.0** · `data-source-proxy-mode: AT` · **AT 默认隔离级别是读未提交（RU）**，靠全局锁 + `@GlobalLock` 弥补。

**面试话术（区分「用过」和「配过」）：**
> 「**undo_log 必须建在业务库而不是 Seata 库，因为回滚要和业务写在同一个本地事务里**。」

### ⑩ 数据库和缓存的一致性怎么保证 —— 对应 Q84

**开口第一句：**
> 「我用 **Cache Aside（旁路缓存）**：读先查缓存、不命中查 DB 回写；写**先更新 DB、再删除缓存**。」

**必须说到：**
- **为什么是「删」不是「更新」**：① 更新缓存代价大（要重新组装，可能白算）；② **并发下更新缓存会永久不一致**（A 写 DB=1、B 写 DB=2，但缓存写入顺序反了，缓存留下 1）。删除最坏也只是「缓存没了」，下次读会重建正确值。
- **为什么「先更 DB 再删缓存」**：反过来（先删缓存再更 DB）窗口更大 —— 删完缓存、DB 还没更新时来个读请求，会把**旧值**写回缓存，之后一直留着。

**主动坦白：** 「我项目里商品缓存用 `@Cacheable` + **TTL 12 小时**，**实际上只有过期删除、没有主动删除**，所以有最长 12 小时的不一致窗口。改进方向是用 Canal 订阅 SKU 变更来主动删缓存。」

### ⑪ ES 的 must 和 filter 有什么区别 —— 对应 Q66

**开口第一句：**
> 「区别在于**要不要算相关性得分**：must 是查询上下文、要算 `_score`；filter 是过滤上下文、只判断匹配/不匹配。」

**必须说到（为什么 filter 更快，两条）：** ① **省掉打分计算**（TF-IDF/BM25 涉及浮点运算和统计）；② **结果可缓存**（二值结果稳定，ES 用 **bitset** 缓存命中文档，下次直接做位运算）。

**最佳实践：** 「**影响相关性的用 must，纯筛选的用 filter** —— 比如商品名搜索用 must，分类/品牌筛选用 filter。」

**项目落点：** 我用 `co.elastic.clients` + `NativeQuery`，`filter(term(categoryName/brandName))` 走过滤上下文；遍历 `attr_` 前缀参数动态拼 `attrMap.xxx.keyword` 实现任意规格筛选；三个 terms 聚合（`categoryList`/`brandList`/`attrmaps`）回填筛选面板。

**加分：** 「压测验证过 **A（仅关键词）→ B（+term 过滤）不会明显变慢甚至更快**，因为 filter 不打分、还能命中 filter cache。」

### ⑫ RocketMQ 事务消息 + 回查 —— 对应 Q76 + Q77

**开口第一句：**
> 「事务消息解决的是「**本地事务和发消息的原子性**」，原理是**两阶段提交 + 回查**。」

**必须说到：**
- **第一阶段**：Producer 先发 **half 消息**（存在 `RMQ_SYS_TRANS_HALF_TOPIC`，**消费者看不到**），Broker 确认后**才执行本地事务**。
- **第二阶段**：根据本地事务结果发 **commit / rollback**。
- **回查**：如果 Producer 发完 half 消息就挂了，Broker **主动回查** —— 默认 6 秒后触发第一次，之后每 60 秒一次、最多 15 次，**15 次都拿不到明确结果就默认回滚**。

**顺序不能反的原因：** 「**先发 half 消息再执行本地事务** —— 反过来（先执行事务再发消息）的话，事务成功了但发消息失败就丢了；先发 half 消息的话，即使确认没发出去，Broker 还能回查。」

**主动坦白（必答）：** 「我项目里 `TransactionListenerImpl.checkLocalTransaction` **无条件 return COMMIT** —— 等于回滚路径完全失效、half 消息永远被提交。**正确做法是去查本地事务表/支付状态，返回 COMMIT / ROLLBACK / UNKNOWN**。」

### ⑬ 秒杀库存为什么放 Redis Hash、怎么扣 —— 对应 Q92

**开口第一句：**
> 「因为秒杀库存扣减是**高频写同一个值** —— 打 MySQL 的话 `UPDATE ... WHERE num >= x` 会给这一行加行锁、所有并发串行排队；放 Redis 之后是内存操作、单线程，吞吐高几个数量级。」

**必须说到：** 用 **Hash** 是因为一个 key 下要放多个商品（`HotSeckillGoods` 的 field 是商品 id、value 是剩余库存），而且 **`HINCRBY` 支持原子自减**。

**必须指出问题：** `HGET` 判库存 + `HINCRBY` 扣减**是两条命令、不是原子的** —— 两个线程都读到「还有 1 个」就会都扣，库存变 -1。

**加分（这是我最想讲的迭代）：** 「正确做法是 **Lua 脚本** —— Redis 执行 Lua 期间不处理其他命令，所以脚本内多条命令是原子的，**锁就可以直接去掉**。我的改进路径是：**我加了锁 → 我发现锁粒度错了 → 我发现根本不需要锁（Lua 更好）**。」

### ⑭ Redisson 看门狗机制 —— 对应 Q91

**开口第一句：**
> 「看门狗解决的是「**锁提前过期、业务还没执行完**」的问题。」

**必须说到：** 不指定过期时间时（`lock()` 不传 leaseTime），Redisson 给锁设 **默认 30 秒**，然后起后台定时任务**每 10 秒**（过期时间的三分之一）检查一次，业务还在跑就把过期时间**重置回 30 秒**。

**关键坑（必说）：** 「**如果调用 `lock(leaseTime, unit)` 显式指定了过期时间，看门狗就不生效** —— 很多人为了『保险』传个 30 秒，结果业务跑 40 秒、锁提前过期了。**正确用法是 `lock()` 不传时间，让看门狗兜底**。」

**追问怎么答：** 「客户端进程被 kill 后，看门狗线程消失、停止续期，锁在 30 秒内自动过期 —— 这是**符合预期**的：进程都没了，锁该释放给别人。」

### ⑮ 网关为什么需要、承担什么 —— 对应 Q19

**开口第一句：**
> 「网关解决的是**横切关注点重复**的问题 —— 14 个服务各写一遍鉴权，一是重复，二是**漏一个就是后门**。」

**必须说到（四件事）：** ① **统一鉴权**（布隆过滤器 → JWT → IP 绑定 → RBAC 四层）；② **限流**（Sentinel，超了 429）；③ **秒杀去重准入**（命中 `/seckill/order` 走去重准入）；④ **路由转发**（Nacos 寻址）。

**关键数字：** `mall-api-gateway:9001` · `GlobalFilter` **order = 10001** · 布隆 `tryInit(1000000L, 0.0001)` · 幂等 key **2 分钟 TTL**。

**追问怎么答（网关会不会成为单点）：** 「网关本身设计成**无状态**、可以横向扩多个实例，前面用 Nginx 做负载均衡；而且网关**只做轻量操作（鉴权、路由），不做业务逻辑**，避免它自己变慢拖垮全局。」

## 四、硬伤（面试官必挖 · 5 题）

> 统一答法：**① 承认问题 → ② 说清后果 → ③ 给出正确做法 + 说明当前为什么没做。**

### ⑯ Seata 用的 AT，回滚怎么回滚？undo_log 建在哪个库 —— 对应 Q170

**开口第一句：**
> 「回滚靠 **undo_log** —— 一阶段记录前后镜像、和业务 SQL 在同一个本地事务提交；二阶段用 **before image 恢复数据**、改之前校验 after image 防脏写。」

**必须说到的坑：** 「undo_log **必须建在业务库**，因为**回滚要和业务写在同一个本地事务里** —— 如果它在另一个库，就变成跨库操作，会出现『数据改了但 undo_log 没写进去』。」

**主动坦白（必答）：** 「我项目 `sql/` 里**只有 Seata Server 端的 4 张表，唯独漏了业务库侧的 undo_log** —— 所以一阶段能提交、**一旦需要回滚就会直接报错**。修复方案是在 `shop_goods`、`shop_order` 各建一张，然后**真的跑一次失败回滚验证**。」

### ⑰ 你那把秒杀锁的粒度是什么 —— 对应 Q171

**开口第一句：**
> 「**我要坦白，我项目里这把锁的粒度是错的。**」

**必须说到：** 锁 key 是**固定字符串 `"seckill-order-lock"`** —— 意味着**所有商品、所有用户的秒杀请求竞争同一把锁**，商品 A 和商品 B 的秒杀**互相阻塞**，整个秒杀被做成**单线程队列**。

**正确做法：** key 改成 `seckill-order-lock:{goodsId}`（**锁的粒度要匹配它保护的资源粒度**）。

**加分：** 「**更进一步，这把锁根本不需要** —— 用 Lua 把「判库存 + 扣库存」做成原子操作就行。」

### ⑱ Redis 挂了，你的幂等还成立吗 —— 对应 Q172

**开口第一句：**
> 「**不成立。**」

**必须说到：** 我只有 Redis 一层（INCR + TTL），Redis 重启 / 主从切换丢数据 / TTL 到期后重试 —— 都会失守；`seckill_order` **没有唯一索引**、DB 层零兜底。

**面试话术（和 ⑥ 同一句，背下来）：**
> 「**Redis 是性能层的挡板，挡掉 99% 的重复请求；唯一索引是正确性层的兜底，保证极端情况下也不会重。两层职责不同，不能只留一层。**」

**深层一句：** 「这个问题的本质是**分布式幂等** —— 任何内存的、异步的组件都可能失效，所以**幂等的最终保证必须落在「有持久化 + 强约束」的地方**。」

### ⑲ 用户表里密码是怎么存的 —— 对应 Q174（红线）

**开口第一句：**
> 「**我要坦白，我项目里是明文存储 + 明文比对**（`UserInfoController.java:43` 直接 `equals`）。」

**必须说到：** 这是**常识性红线** —— 一次数据库泄露 = 全站密码泄露，而用户往往多站同密码，**影响会扩散**。

**正确做法：** **BCrypt**（引入 `spring-security-crypto`，**只引这一个包**，不用引整个 Spring Security），注册时 `encode()`、登录时 `matches()`。

**为什么不是 MD5 加盐：** 「**BCrypt 是慢哈希**（cost 参数，默认 10 即 2^10 次迭代，毫秒级），**MD5 是微秒级**，差三四个数量级；而且 **cost 可调（自适应）**、**内置盐**。**MD5 加盐只能防彩虹表，防不住针对单个盐的暴力枚举**。」

**态度：** 明文存密码**没有「取舍」，就是错的** —— 直接承认 + 给方案，不要辩解。

### ⑳ 服务雪崩怎么防？你项目里做了吗 —— 对应 Q177

**开口第一句：**
> 「**我先说现状：我项目里基本没做。** 全仓搜 `@SentinelResource` 是 **0 处** —— Sentinel 只在**网关层**做了限流，**服务之间的调用完全没有熔断降级保护**。」

**必须说到（雪崩怎么发生的）：** order 调 goods，goods 变慢 → order 的线程都在等、**线程池被占满** → order 也没法处理其他请求 → 调 order 的 cart 也开始堆积 → **故障沿调用链一路向上传导**。

**防雪崩的五个手段：** ① **熔断**（慢调用比例 / 异常比例 / 异常数）· ② **降级**（Feign 配 `fallbackFactory`）· ③ **隔离**（独立线程池或并发线程数）· ④ **超时调小**（Feign 默认 60 秒太长）· ⑤ **限流**（网关挡外部洪峰）。

**必须点出的关键判断：** 「**只做网关限流是不够的** —— 网关限流防的是「**外部流量洪峰**」，但雪崩是「**服务间传导**」的，这条链条上没有任何一层被保护。」

**面试话术（心态层）：** 「**对每个外部依赖都要假设它随时会挂** —— 这是微服务设计的核心心态。所以每个 Feign 客户端都要配齐三样：**超时（快速失败）+ fallback（降级）+ Sentinel 熔断规则**。」

**说明为什么没做：** 「坦白说是开发阶段没有意识到，而且**单机跑 14 个服务很难复现真实的故障传导**。但我认为这是**最高优先级**的改进之一，因为它直接关系到系统稳定性。」

## 六、如果只记住三句话

**① 分层思想** —— 「**性能层 + 正确性层**」：Redis 挡 99% + 唯一索引兜 1%；热点隔离是优化、Redis 预扣减 + 限流是兜底；调度层不重复是优化、业务层幂等是正确性保证。

**② 秒杀的本质** —— 「**把「请求数」的压力，转化成「库存数」的压力**」：几万 QPS 进来，限流后剩一万，去重准入后剩几千，Redis 扣减后真正落单的只有库存那么多。

**③ 面对硬伤的姿态** —— 「**承认问题 → 说清后果 → 给出正确做法 + 说明当前为什么没做**」。面试官对「知道自己不足」的评价，**远高于**「假装没问题」。
