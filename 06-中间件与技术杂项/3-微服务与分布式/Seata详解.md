# Seata — 分布式事务中间件详解

## 一句话定义

> **Seata**（Simple Extensible Autonomous Transaction Architecture）是阿里巴巴开源的**分布式事务中间件**，为微服务架构提供跨数据库/跨服务的强一致性事务能力。
>
> 发音：`/siːˈɑːtə/`（西-阿-塔），中文常读作 "西阿塔"

**本项目实现**：Seata AT 模式，覆盖下单链路（扣库存 → 创建订单 → 清购物车）共 5 步操作的分布式事务。

## 架构角色

Seata 采用 **TC → TM → RM** 三层模型：

```
                   ┌──────────────────┐
                   │   TC (Server)    │ ← 事务协调者，维护全局事务状态
                   │                  │
                   │   seata-server   │
                   └──────┬───────────┘
                          │
          ┌───────────────┼───────────────┐
          │               │               │
   ┌──────▼──────┐ ┌──────▼──────┐ ┌──────▼──────┐
   │   TM        │ │   RM        │ │   RM        │
   │ 事务管理器    │ │ 资源管理器    │ │ 资源管理器    │
   │             │ │             │ │             │
   │ 下单服务      │ │ 库存服务      │ │ 订单服务      │
   └─────────────┘ └─────────────┘ └─────────────┘
```

| 角色 | 全称 | 职责 |
|------|------|------|
| **TC** | Transaction Coordinator | 全局事务协调者，维护全局事务 ID 和分支事务状态 |
| **TM** | Transaction Manager | 定义全局事务边界（`@GlobalTransactional`），向 TC 发起 begin/commit/rollback 指令 |
| **RM** | Resource Manager | 管理分支事务的资源，向 TC 注册分支，报告状态 |

## 四种事务模式详解

### AT 模式（Automatic Transaction）— 自动补偿 ✅ 本项目使用

**特点**：对业务代码零侵入，自动生成回滚 SQL。

**前提条件**：
- 使用支持 ACID 的**关系型数据库**（MySQL、PostgreSQL 等）
- 使用 **JDBC** 数据源（Seata 代理数据源连接池）

>**AT 模式的核心机制依赖 JDBC 层的 SQL 拦截**

**一阶段流程**：

```
1. TM 向 TC 发起 begin，获取全局事务 XID
2. RM 执行业务 SQL（如 UPDATE sku SET num = num - 1 WHERE id = ?）
3. Seata 自动拦截该 SQL，生成：
   ┌─ 前镜像（Before Image）— SQL 执行前的数据快照
   └─ 后镜像（After Image） — SQL 执行后的数据快照
4. RM 将 undo log（前镜像 + 后镜像 + 事务信息）通过本地事务写入 undo_log 表
5. 向 TC 报告分支事务状态
```

**脏读问题**：

> [!warning] 一阶段提交后数据已对外可见
> 本地事务提交后，该分支的修改对其他事务**已经可见**。如果全局事务最终**回滚**，其他事务已经读到了"不应该存在"的数据 → 这就是**脏读**。
>
> **面试话术**：AT 模式不保证读隔离，只保证写隔离（通过全局锁）。如果需要避免脏读，可以升级到 TCC 或 XA 模式。

```
执行顺序示例：
  事务A（全局）一阶段：UPDATE sku SET num=9 WHERE id=1  → 本地提交，数据对外可见
                          ↓
  事务B读取：SELECT num FROM sku WHERE id=1  → 读到 9（脏数据）
                          ↓
  全局事务回滚：num 恢复为 10  → 但事务B已经读到了 9
```

---

**二阶段流程**：

```
TM 提交/回滚请求
       │
       ▼
TC 检查所有分支状态
       │
  ┌────┴────┐
  │         │
全成功      任一分支失败/超时
  │         │
  ▼         ▼
TC 通知 RM   TC 通知所有 RM 回滚
异步删 undo log   RM 查出当前行数据（SELECT ... FOR UPDATE）
  │
  ▼
  ① 校验：当前数据 == 前镜像？
        │
    ┌───┴───┐
   相等     不等
    │        │
    ▼        ▼
跳过反向 SQL  ② 校验：当前数据 == 后镜像？
（幂等保护）      │
             ┌───┴───┐
            相等     不等
             │        │
             ▼        ▼
      执行反向 SQL   回滚失败、抛异常
      （前镜像恢复）  Has dirty records when undo.
      + 删 undo log   undo_log 保留、需人工介入
```

**图解**：

```
              一阶段                       二阶段
  ┌─────────────────────┐        ┌──────────────────────┐
  │ 执行业务 SQL         │        │ 全部成功 → 删 undo log │
  │ 自动生成 undo log    │ ─────▶ │ 任一失败 → 反向回滚     │
  │ 提交本地事务（暂锁）   │        │ 释放全局锁             │
  └─────────────────────┘        └──────────────────────┘
```

**回滚前的两道数据校验**（对应上图 ①②，方法名 `dataValidationAndGoOn`）：回滚不是无脑拿前镜像覆盖，RM 会先 `SELECT ... FOR UPDATE` 把这一行**当前值**查出来，做两次比对——

- **① 当前值 vs 前镜像（before image）**：相等说明这行压根没被改过，或已经被回滚过一次 → **跳过反向 SQL，直接删 undo_log**。这一步是**幂等保护**，防止重复回滚把数据多减/多加一次。
- **② 当前值 vs 后镜像（after image）**：相等说明数据确实是本事务改完的样子 → **执行反向 SQL 恢复**；**不等**说明这行在「一阶段提交」到「二阶段回滚」之间被**全局事务之外**的力量改过了 → 抛异常 `Has dirty records when undo.`，**回滚失败、undo_log 保留、需人工介入**。

**为什么必须有 ②**：一阶段提交后数据库行锁就放了，只剩 TC 那把全局锁，而全局锁**只拦得住"也走 Seata、也要申请全局锁"的事务**——裸 JDBC 旧代码、DBA 手工 UPDATE、全局锁重试超时后放行，这三类都拦不住。此时若无脑用前镜像覆盖，就是**回滚动作自己制造了一次脏写**。所以 ② 防的不是"脏写发生"（那靠全局锁），而是"**回滚把脏写放大**"——宁可让回滚失败卡住等人处理，也不能悄悄覆盖掉正确数据。

> 开关：`client.undo.dataValidation=false` 可关闭校验，**生产绝不该关**。

**⚠ 二阶段"提交"是异步的**：新版 Seata Server 默认开启二阶段异步提交（`commit-mode: async`，可配回 `sync`），TC 收到分支的 PhaseTwo_Commit 回执即可，不必等所有 RM 真的删完 undo log 才给 TM 返回，所以 AT 的全局提交 RT 很短。**回滚默认仍是同步**——只有回滚才是必须真正执行补偿 SQL 的重活。（⚠ 这条按你们实际用的 Seata 版本核一下配置项再报细节；面试保守说法是"二阶段**提交**可以异步化、回滚必须同步执行完才给 TM 返回"，别硬报版本号。）

**⚠ 注意**：一阶段提交后 Seata 会持有**全局锁**（行级），这个锁是 **Seata TC 层面**的，不是数据库层面的行锁。其他事务要修改同一行数据时，需要向 TC 申请锁，TC 发现锁被持有就会等待。这是 AT 模式的性能瓶颈。

> [!warning] 全局锁防的是「脏写」（Dirty Write）
> **脏写**：两个全局事务并发改同一行，后提交的把先提交的成果直接覆盖，全局一致性被破坏——这是四种并发异常里最严重的一种，连 MySQL 的读未提交都要防它。
>
> **AT 的解法（按时间顺序）**：执行完业务 SQL、写完 undo log 之后，**本地事务提交之前**，RM 先向 TC 申请这一行的全局锁（按「表名 + 主键值」定位）；申请不到就重试等待。所以同一行的跨全局事务修改被强制串行化。本地提交后**数据库行锁立刻释放**，但**全局锁一直持有到二阶段结束**才放。
>
> **对照记**：全局锁只管**写**（防脏写），不管**读**——所以 AT 有脏读问题、没有脏写问题，一句话能记住两个坑。
>
> **面试话术**："全局锁防的是脏写。两个全局事务改同一行，没有全局锁就会互相覆盖。AT 在一阶段本地提交之前，必须先拿到这一行的全局锁，拿不到就重试等待，等于同一行的修改被串行化了。要注意这是 Seata TC 层面的逻辑锁，不是数据库行锁——数据库行锁本地一提交就放了，全局锁要到二阶段才释放。"

### TCC 模式（Try-Confirm-Cancel）

**特点**：业务代码需要手动实现三个阶段接口，侵入性高但灵活性最强。

| 阶段 | 操作 | 说明 |
|------|------|------|
| **Try** | 预留资源 | 如库存冻结、账户预扣 |
| **Confirm** | 确认执行 | 将预留资源真正扣减 |
| **Cancel** | 取消回滚 | 释放预留资源 |

**适用场景**：
- 高并发短事务（如秒杀扣库存）
- 对隔离性有严格要求

**面试坑点**：

> [!info] 先分清谁在发指令（下面 TC / TM 混用的原因）
> **Try 阶段**是普通业务 RPC：TM 所在的入口服务直接调下游服务的 Try 方法，TC 完全不参与，所以讲 Try 时说"TM 发起"。
> **Confirm / Cancel 是二阶段指令**：一律由 TC 下发给各 RM（TM 只负责向 TC 声明"全局提交"或"全局回滚"，不直接喊 RM 干活），所以讲重试、乱序、空回滚时说"TC"。
> 一句话：**Try 走业务调用链（TM 侧），Confirm/Cancel 走 TC 的控制链**——TM 决定方向，TC 负责下发和超时重试。

#### ① 幂等性

> [!warning] Confirm 和 Cancel 必须幂等（AT 模式自动保证，TCC 需要手动保证）

**问题**：TC 网络超时可能重试 Confirm/Cancel，导致同一操作被执行多次。

**举例**：Confirm 执行 `UPDATE account SET balance = balance - 100 WHERE user_id = 1`——这个操作本身**不幂等**（执行两次扣 200）。TC 重试时如果没有幂等控制，账户被多扣。

**面试话术**："TCC 的幂等分两种。① 自然幂等——操作本身满足 `f(f(x)) = f(x)`，比如 `SET balance = 100`（改成绝对值，几次都一样）；② 强制幂等——增量操作如 `balance = balance - 100` 本身不幂等，靠 XID 唯一键查重实现。扣余额走第二种，用全局事务 XID 做唯一键，扣减前先查这笔 XID 是否已处理过，已处理则直接返回，确保多次执行等于一次执行。"

#### ② 空回滚 → 悬挂（一对因果关系）

> [!warning] 网络乱序导致 Try 和 Cancel 顺序颠倒

**空回滚（第一步）**：Try 还没执行，Cancel 先到了。场景——下单服务（TM）依次调用 A、B 两个分支的 Try，B 失败 → TM 向 TC 发起全局回滚 → **TC 通知各 RM 执行 Cancel**；但 A 的 Try 请求网络慢了，Cancel 反而先到 A。A 还没预留资源，Cancel 却要"释放"——释放了不存在的资源。

**解决**：Cancel 执行前先判断 Try 是否执行过（查分支记录），没执行过就标记"已取消"（空回滚），等 Try 真正来时发现已取消，直接跳过。

**悬挂（第二步，空回滚的后续）**：Cancel 已经标记"已取消"了，但**慢的 Try 又在取消之后落下来**。如果 Try 不查状态，直接去预留资源，资源就被"挂"住了——全局事务已结束，没人再通知回滚，预留的资源永久泄漏。

**解决**：Try 执行前先判断分支是否已处于"已取消"状态，已取消则直接拒绝。

**总结**：空回滚和悬挂是同一个网络乱序问题的两步后果。靠**"执行前查状态"双向互查**解决——Cancel 查 Try 没执行（防空回滚），Try 查 Cancel 已取消（防悬挂）。

### Saga 模式

**特点**：基于状态机编排的**长事务**方案，每个节点提交本地事务，失败时通过**补偿事务**回滚。

```
下单 Saga 示例：
  下单 ──▶ 扣库存 ──▶ 支付 ──▶ 发货
                                  │
                          ┌───────┘
                          ▼
                    回滚：退款 → 加库存 → 取消订单
```

**适用场景**：
- 业务流程很长（几天到几周）
- 对隔离性要求低
- 不要求强一致性，最终一致即可

**⚠ 缺点**：无隔离性，中间状态对外可见，需要业务层处理脏读。

---

### XA 模式

**特点**：基于数据库本身的 XA 协议，Seata 只是协调者，由数据库完成两阶段提交。

```
阶段一：所有分支预提交（prepare）
阶段二：全部成功 → 真正提交（commit）
        任一失败 → 全部回滚（rollback）
```

**适用场景**：
- 使用支持 XA 的数据库（Oracle、MySQL InnoDB 等）
- 追求强一致性的短事务

**⚠ 缺点**：阻塞式协议，性能差；依赖数据库 XA 实现；MySQL XA 有 bug（某些版本）。

> [!tip] AT 和 XA 的根本区别 = 锁什么时候放（不是要不要 undo log）
> 两者都叫"两阶段"，但一阶段做的事完全不同：
>
> - **XA 一阶段只 prepare，不提交**。本地事务挂在那里，InnoDB 的行锁、MVCC 相关资源**全部持有到二阶段 commit 才释放**。协调要等所有分支都 prepare 完，一个慢分支拖住全部，这就是"阻塞式"三个字的来源——阻塞的不是网络，是**数据库锁**。
> - **AT 一阶段就是真正的本地事务提交**。提交瞬间数据库行锁就放掉了，Seata 只留一把**自己的全局锁**（TC 层面、行级、逻辑锁）在二阶段期间护着这一行。
>
> **面试话术**："AT 和 XA 都是一阶段准备、二阶段决定，但根本区别在锁的释放时机。XA 一阶段只 prepare 不提交，数据库自己的行锁要一直持有到二阶段才放，所以是阻塞式协议，并发一高吞吐就塌了。AT 一阶段直接提交本地事务，数据库锁当场释放，代价是要自己实现回滚——所以有了 undo log 和前镜像；同时它用 Seata 的全局锁在 TC 层面补回写隔离。一句话：XA 靠数据库自己的锁保证强一致，简单但慢；AT 用'提前提交 + 全局锁 + 反向补偿'换性能，代价是读隔离退化成读未提交。"

## 四模式选型对比

| 维度 | AT | TCC | Saga | XA |
|------|-----|-----|------|-----|
| 业务侵入 | 低（加注解） | 高（三接口） | 中（状态机） | 低 |
| 隔离性 | ✅ 全局锁保证 | ✅ 业务保证 | ❌ 无 | ✅ 隔离级别 |
| 一致性 | 强一致 | 强一致 | 最终一致 | 强一致 |
| 性能 | 中（全局锁开销） | 高（无锁） | 高 | 低（阻塞） |
| 典型场景 | 下单、支付 | 秒杀、扣减 | 长流程审批 | 银行转账 |

## 本项目：下单分布式事务

### 事务链路

```
@GlobalTransactional 开始 ─── 全局事务 XID 生成
    │
    ├── ① 扣库存（商品服务） ─── UPDATE sku SET num = num - #{num}
    ├── ② 创建订单（订单服务） ─── INSERT INTO order_info
    ├── ③ 清购物车（购物车服务） ─── DELETE FROM cart_items
    ├── ④ 更新日志                   
    └── ⑤ 其他后置操作
```

### 代码示例

```java
@Service
public class OrderService {

    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public Order createOrder(OrderDTO dto) {
        // 1. 扣库存（跨服务 Feign 调用）
        skuService.deductStock(dto.getSkuId(), dto.getNum());
        
        // 2. 创建订单（本地数据库操作）
        Order order = new Order();
        order.setUserId(dto.getUserId());
        order.setTotalAmount(dto.getTotal());
        orderMapper.insert(order);
        
        // 3. 清购物车（跨服务 Feign 调用）
        cartService.clearCart(dto.getUserId());
        
        return order;
        // 方法正常返回 → Seata 自动提交全局事务
        // 方法抛异常 → Seata 自动回滚所有分支
    }
}
```

## 面试高频追问与话术

### Q1: Seata AT 和 TCC 怎么选？
> **面试话术**：
> "AT 模式对业务零侵入，适合业务逻辑复杂但并发不太极端的场景，比如我们的下单链路。TCC 需要手写 Try/Confirm/Cancel 三接口，开发成本高，但性能更好、不用全局锁，适合秒杀这种短事务高并发场景。我们项目下单用 AT，秒杀用 Redisson 分布式锁而不是 Seata，因为全局锁在高并发下吞吐不够。"

### Q2: AT 模式的全局锁会不会成为性能瓶颈？
> **面试话术**：
> "会的。AT 模型在一阶段提交后持有全局锁，全局锁释放前其他分支事务要等待。并发量大的时候，这个等待时间会明显拖慢。所以 AT 适合并发不太极致的场景。如果面试官接着问怎么优化：可以缩短短事务执行时间、用 TCC 替代 AT、或者用数据库乐观锁 + 消息队列做最终一致性方案。"

### Q3: undo log 满了怎么办？undo_log 表会不会无限膨胀？
> **面试话术**：
> "undo_log 中的记录在**该分支的二阶段完成后**会被异步删除。只有在全局事务正在执行或异常恢复期间，undo_log 才会有数据。所以正常情况下不会无限膨胀——各分支的二阶段完成后各自清理，无需等其他分支。"

### Q4: AT 模式如何保证隔离性？
> **面试话术**：
> "AT 模式通过**全局写锁**（Global Lock）保证写隔离——一阶段提交后，其他事务要等待全局锁释放才能修改同一行数据。但 AT 不保证读隔离，也就是说一个分支事务一阶段提交后，它的修改对其它事务可见——这可能导致脏读。如果需要读隔离，可以用 TCC 或 XA。"
>
> ⚠ **被追问"那 AT 到底是什么隔离级别"时，要正面给名词，别绕**：**默认等价于 Read Uncommitted（读未提交）**。原因是全局事务的可见性由"一阶段本地提交"决定——本地一提交数据就对外可见，而这一刻全局事务还没定局。更关键的一点：**即使把本地 MySQL 设成 RC 甚至 RR，站在全局事务的视角仍然是 RU**，因为别的分支的一阶段提交在本地是"已提交"，在全局却可能马上被回滚。
>
> 想拿到全局 RC 有两条路：① 读的地方加 `@GlobalLock` + `SELECT ... FOR UPDATE`，让读操作也去 TC 排队拿全局锁（新版本 AT 支持全局读锁）；② 直接换模式，TCC 靠业务预留资源天然不暴露中间态、XA 靠数据库不提前提交天然有隔离。
>
> **面试话术（补这一段）**："隔离级别上 AT 默认是读未提交——一阶段本地事务一提交数据就对外可见，这时候全局事务还没决定，所以本质上就是脏读。而且这个不是调本地参数能解决的，MySQL 设成 RC 也没用，因为可见性是全局事务层面的事。要读已提交就得读的地方加 `@GlobalLock` 配 `FOR UPDATE` 去 TC 排队，或者干脆换 TCC、XA。这也是我们下单用 AT、但下单后的库存查询能接受短暂脏数据的原因——业务上读到的中间态没有副作用。"

### Q5: Seata 和消息队列（RocketMQ）事务消息的区别？
> **面试话术**：
> "Seata AT 是**强一致方案**，保证跨服务 ACID。RocketMQ 事务消息是**最终一致方案**。我们项目的原则是：下单这种需要强一致的用 Seata，支付状态同步这种可以接受最终一致的用 RocketMQ 事务消息。"

### Q6: 项目中有没有因为引入 Seata 踩过坑？
> **面试话术**：


① **undo_log 表要提前手动建好**，并且按官方 SQL 指定 utf8mb4 字符集。Seata 不会自动建这张表，如果手动建的时候漏了字符集，rollback_info 这类字段存取序列化内容时就容易出现乱码。

② **Feign 的超时时间要调长**。全局事务要协调多个分支事务，执行时间明显比本地事务长，而 Feign 默认超时偏短（旧版基于 Ribbon 时 connect 和 read 都是 1 秒），很容易在事务还没跑完时就被中断、触发全局回滚。生产上建议显式把 readTimeout 调到 5~10 秒。

③ **​@GlobalTransactional 要加在事务发起方的最外层入口方法上**，方法得是 public。关键是异常要能一路冒泡到这个注解，它感知到才会发起全局回滚。内部方法可以正常用本地 @Transactional，但不能反过来让本地事务把全局事务包住——那样会使得全局事务生命周期错乱从而导致空提交问题

④ **Seata 和 MyBatis-Plus 一起用，MP 的插件容易集体失效**（分页、自动填充、自定义 ID 生成器都中招）。根因不是多数据源，而是 Seata 代理了数据源之后，项目又手动配了一个 SqlSessionFactory，把 MP 自己装配的那个工厂顶掉了，导致插件链没注册上去。解决办法是别重复配 SqlSessionFactory，让代理后的 DataSource 加 @Primary 交给 MP 自动装配，插件就保住了。

> **通俗理解**：Seata 就像一个快递中转站。你发三个包裹（三步业务操作），中转站记录每个包裹发出前的样子和发出后的样子（undo log）。如果三个都成功签收，中转站就把记录销毁；如果有一个中途丢了，中转站按照"发之前的样子"重新发一遍（自动回滚）。你（业务代码）只需要把所有包裹交到前台（`@GlobalTransactional`），剩下的事中转站全包了。
