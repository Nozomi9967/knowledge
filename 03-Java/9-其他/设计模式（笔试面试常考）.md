# 设计模式（笔试面试常考）

> 面试最常考的不是背 23 个模式的定义，而是**会区分、会选型、能讲清利弊**。设计模式是针对常见软件设计问题总结出的可复用思路，不是现成代码、也不是必须套用的规范。经典 **GoF** 模式共 23 种，分创建型、结构型、行为型。
>
> **GoF（Gang of Four / 四人帮）** = Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides 四人合著的《设计模式：可复用面向对象软件的基础》。书中归纳 23 种模式，**不是说设计模式总共只有 23 种**。

## 一、创建型：对象怎么创建

| 模式 | 核心思路 | 常见场景 | 面试关键词 |
|:---|:---|:---|:---|
| **单例（Singleton）** | 一个类只提供一个共享实例 | 配置、缓存、线程池 | 线程安全、懒加载、生命周期 |
| **工厂方法（Factory Method）** | 把创建某产品的职责交给对应工厂 | 按类型创建不同实现 | 解耦调用方与具体类 |
| **抽象工厂（Abstract Factory）** | 创建一组相互配套的对象 | 多主题组件、多库产品族 | 产品族、一致性 |
| **建造者（Builder）** | 分步骤构造复杂对象 | 参数很多、不可变对象 | 分步构建、可读性 |
| **原型（Prototype）** | 复制已有对象创建新对象 | 创建成本高、结构复杂 | 浅拷贝、深拷贝 |

### 单例：重点掌握线程安全与生命周期
实现方式（详见 [[DCL（Double-Checked Locking）单例完整展开]]）：

- **饿汉式**：类加载时创建，线程安全；可能提前创建、浪费资源。
- **懒汉式加锁**：首次使用创建；每次访问有锁开销。
- **双重检查锁（DCL）**：缩小加锁范围，字段需 `volatile` 防指令重排序。
- **静态内部类**：利用类加载实现懒加载 + 线程安全，简洁。
- **枚举单例**：Java 能处理好序列化、反射破坏；但不能继承。

**面试常问：**
- 懒汉式为何要线程安全？两线程同时判空会各创建实例，需同步或借类加载机制保证只发布一个。
- DCL 为何要 `volatile`？防指令重排序导致其他线程看到未完全初始化的对象。
- **单例保证全系统唯一吗？** 一般指**单个类加载器范围内**唯一；多类加载器/多进程/多机各自可能有独立实例，**不等于分布式全局唯一**。
- **什么时候别用单例？** 对象需不同配置/不同用户独立状态、生命周期要明确管理、测试要替换实现时。依赖注入容器管理共享实例通常更可控。

> [!warning] 单例的"全局可访问状态 + 隐式依赖"
> 单例像"随处可用的全局变量"：调用方对它产生**隐式依赖**（`Config.getInstance()` 藏在方法内部，读代码看不出它依赖什么、测试也不易替换）。且任何地方修改它，别处读到的都会受影响——测试互相污染、改动要考虑所有调用方、多线程需明确谁保证线程安全、生命周期不清楚。
> **解法**：改成**显式传入依赖**（构造注入 `Config config`），测试时可注入测试/模拟对象，更易替换和独立测试。

### 工厂方法 vs 抽象工厂 vs 简单工厂（最易混）
- **简单工厂**：一个工厂集中 `if/else` 判断创建哪种产品。常用，但**不属于 GoF 23 种**。
- **工厂方法**：每种产品对应一个工厂，新增产品可新增工厂，减少改原工厂。
- **抽象工厂**：一次创建**一族**相关对象（如同一主题的按钮/输入框/菜单）。

| 对比 | 简单工厂 | 工厂方法 |
|:---|:---|:---|
| 工厂数量 | 通常一个 | 每种产品一个 |
| 怎么选产品 | 把类型交给工厂判断 | 调用方选对应工厂 |
| 新增产品 | 通常改工厂内分支 | 通常新增产品类 + 工厂类 |
| 复杂度 | 简单、类少 | 灵活但类更多 |

快速区分：**工厂方法偏向"一种产品"；抽象工厂偏向"一族产品"。**

### 建造者
适合**构造过程复杂/可选参数多**的对象（`User.builder().name("Lin").age(20).build()`）。和工厂区别：工厂回答**创建哪一种对象**；建造者回答**如何分步构造一个复杂对象**。

## 二、结构型：对象怎么组合

| 模式 | 核心思路 | 常见场景 | 面试关键词 |
|:---|:---|:---|:---|
| **代理（Proxy）** | 通过代理对象控制对真实对象的访问 | 权限、缓存、远程调用、AOP | 控制访问、增强功能 |
| **装饰器（Decorator）** | 包装对象，动态增加职责 | Java I/O、功能组合 | 同接口、可叠加、组合优于继承 |
| **适配器（Adapter）** | 转换接口，让不兼容对象能合作 | 旧系统接新接口、第三方库 | 接口转换 |
| **外观（Facade）** | 为复杂子系统提供统一入口 | SDK、服务层封装 | 简化调用、隐藏复杂性 |
| **组合（Composite）** | 统一处理单个对象和对象树 | 文件目录、组织结构 | 树形结构、递归处理 |
| **桥接（Bridge）** | 分离两个独立变化的维度 | 多平台、多种实现 | 抽象与实现分离 |
| **享元（Flyweight）** | 共享可复用的对象状态省内存 | 大量重复小对象 | 内部状态、外部状态 |

### 代理 / 装饰器 / 适配器：高频辨析
三者都可能"包一层"，但目的不同：**代理管访问，装饰器加功能，适配器改接口。**

- **代理**：控制访问（做权限校验/转发远程调用）。
- **装饰器**：增强功能（叠加日志/压缩/加密），通常保持同接口。
- **适配器**：转换接口（旧类接口 → 需要的 `Target` 接口）。

### 装饰器：为什么 + 真实例子
**为什么用装饰器？** 能在**不改原对象、也不必为每种功能组合写子类**的情况下逐层加功能。若用继承，"咖啡+牛奶""咖啡+糖""咖啡+牛奶+糖"要写很多子类；装饰器把功能做成**可叠加的包装层**，运行时组合更灵活。适合**功能像积木可单独添加组合、且不想改原对象**的情形；固定一种增强直接写类里更简单。

**Java I/O 流是最经典实际例子**：

```java
// 字节流：文件读取 + 缓冲
InputStream input = new BufferedInputStream(new FileInputStream("data.txt"));

// 字符流：文件读取 + 转字符 + 缓冲 + 按行
Reader reader = new BufferedReader(
        new InputStreamReader(new FileInputStream("data.txt"), StandardCharsets.UTF_8));
```

- `FileInputStream` 读字节；`BufferedInputStream` 包它加缓冲。两者都属 `InputStream`，可继续套。
- `InputStreamReader` 把字节流转字符流（其实更像**适配器**，转接口）；`BufferedReader` 加缓冲/按行读（**装饰器**）。

装饰器核心：**装饰器与被装饰对象实现相同接口，并持有被装饰对象；调用时先委托给它，再叠加自己的行为。**

### 代理模式与 AOP
AOP 常借**代理**实现横切关注点（日志/事务/权限）。常见：
- **静态代理**：代理类提前写好，直观但类多。
- **JDK 动态代理**：通常基于接口生成。
- **CGLIB 等子类代理**：通过生成目标类子类实现（受目标类/方法限制）。

别只说"动态代理就是 AOP"——**动态代理是实现手段，AOP 是组织横切逻辑的编程思想**。

## 三、行为型：对象怎么协作

| 模式 | 核心思路 | 常见场景 | 面试关键词 |
|:---|:---|:---|:---|
| **策略（Strategy）** | 将可替换算法封装起来 | 定价、排序、支付方式 | 消除条件分支、运行时切换 |
| **观察者（Observer）** | 一个对象变化时通知多个订阅者 | 事件通知、消息订阅 | 发布订阅、解耦 |
| **模板方法（Template Method）** | 固定算法骨架，部分步骤交给子类 | 导入/任务处理流程 | 流程复用、继承 |
| **责任链（Chain of Responsibility）** | 请求沿处理链传递 | 审批、过滤器、中间件 | 解耦发送者与处理者 |
| **命令（Command）** | 把请求封装成对象 | 队列、撤销、任务调度 | 请求对象化 |
| **状态（State）** | 状态相关行为封装在不同状态类 | 订单、工作流、连接状态 | 避免大量状态判断 |
| **迭代器（Iterator）** | 统一遍历集合元素 | 集合遍历 | 隐藏集合内部结构 |
| **备忘录（Memento）** | 保存和恢复对象状态 | 撤销、快照、编辑器历史 | 状态快照 |
| **中介者（Mediator）** | 集中协调多个对象交互 | 聊天室、复杂组件协作 | 减少网状依赖 |
| **访问者（Visitor）** | 不改元素结构添加操作 | 编译器语法树、操作多变 | 双分派、扩展操作 |
| **解释器（Interpreter）** | 定义并解释简单语言的语法 | 表达式、规则引擎 | 语法树、解释执行 |

### 策略 / 状态 / 模板方法 / 责任链：都常用于"流程或分支"
都能减少复杂 `if-else`，但解决不同问题：

- **策略**：多个算法可互换，调用方选哪个。例：不同优惠算法。
- **状态**：对象在不同状态时行为随状态变。例：订单待支付/已支付/已取消。
- **模板方法**：流程骨架固定，只允许部分步骤由子类实现。例：数据处理流程统一，读取格式不同。
- **责任链**：多个处理者按顺序尝试处理。例：认证→限流→业务处理。

判断口诀：**可替换算法选策略；行为取决于对象状态选状态；流程骨架固定选模板方法；多个处理节点串起来选责任链。**

### 观察者模式 vs 发布—订阅
- **观察者**：主题直接维护观察者列表，状态变化时通知它们。
- **发布—订阅**：多一个**消息代理/事件总线**，发布者与订阅者**不直接认识**，解耦程度通常更高。
两者叫法常被宽泛混用，回答时说明你指的结构即可。

## 四、综合问题

### 1. 为什么要用设计模式？
**管理变化、降低耦合、提高可测试性与复用性。** 但不是越多越好——简单问题套复杂模式会增加抽象层、阅读与维护成本。回答强调：**先识别变化点和实际痛点，再决定是否引入模式。**

> **"管理变化"是什么？** 把代码中常变动的部分隔离出来，避免需求一变就大改其他稳定代码。例：折扣算法从 `if-else` 抽成 `DiscountStrategy` 接口的多个实现，下单流程只调用折扣策略，不关心每种怎么算；以后新增折扣主要是**加实现**而不是反复改下单流程。**稳定的部分不动，变化的部分单独替换/扩展。** 规则很少且不常变时，直接写简单条件判断往往更清楚。

### 2. 如何选择设计模式？
先描述问题再选模式，别先挑模式硬套：
- 创建复杂/变化频繁 → 工厂、抽象工厂、建造者
- 控制访问 → 代理；动态叠加职责 → 装饰器；接口不兼容 → 适配器
- 算法互换 → 策略；事件通知 → 观察者；多步处理 → 责任链；状态分支膨胀 → 状态

### 3. 如何回答"举一个你用过的设计模式"？
用**问题—方案—收益—代价**组织。例：

> 原先不同支付方式都写在大量条件分支里，新增方式要改原逻辑。我把每种支付算法抽成**策略**，再用**工厂**按类型选策略。这样新增支付方式较少影响已有代码，也更容易单独测试。代价是多了一些策略类；若只有两三个稳定分支，可能没必要过度抽象。

比只说"用了策略模式，符合开闭原则"更有说服力。

## 五、快速记忆口诀
- **创建型**：单例控制唯一对象；工厂负责创建；建造者分步构建；原型复制对象。
- **结构型**：代理控访问；装饰器加职责；适配器转接口；外观简化入口；组合处理树；桥接拆变化；享元共享对象。
- **行为型**：策略换算法；观察者做通知；模板固定流程；责任链串处理；命令封装请求；状态封装状态行为。

**优先讲熟**：单例、工厂、建造者、代理、装饰器、适配器、策略、观察者、模板方法、责任链、状态——并能用真实项目场景说明为什么选、收益、代价。
