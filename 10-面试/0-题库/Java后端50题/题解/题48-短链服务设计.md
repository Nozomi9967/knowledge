### **短链服务的核心不是"生成一个短字符串"，而是「一个能扛 1 亿日请求的 KV 查询系统」：写少读多（读写比 1000:1 以上），所以存储选型、缓存层次、发号方式都围绕读性能设计。发号用「号段模式 + Base62」保证永不重复且有序，存储用 MySQL 分库分表扛写入、Redis 扛读，跳转用 302 而不是 301 以便统计点击。**

下面按面试口述节奏展开，先算容量再定方案。

---

**第一部分：先算容量，数字决定架构**

日均 1 亿次访问，按读写比 1000:1 估，每天新增短链约 10 万条，5 年累计约 **1.8 亿条**记录。

QPS：1 亿次访问 / 86400 秒 ≈ **1160 QPS 均值**，峰值按 5 倍算是 **6000 QPS**。这个量级单机 Redis 就扛得住（10 万 QPS），所以读不是瓶颈；真正的瓶颈在写入的 ID 生成和存储容量。

存储估算：每条记录存短码、原始 URL、创建时间、过期时间、创建者，平均 500 字节，1.8 亿条约 **90 GB**，单表放不下，必须分库分表。

**这几个数字面试时要主动报出来**，因为它直接决定了"要不要分库分表"这个结论。

---

**第二部分：发号器——怎么保证永不重复**

三种方案，按推荐度排序：

**方案一：号段模式 + Base62（推荐）**

用数据库自增或者 Redis INCR 预取一批号段（比如一次取 1000 个）缓存在内存，本地自增消耗，用完再取。拿到十进制 ID 后转成 62 进制（`0-9a-zA-Z`）作为短码。

62^7 ≈ 3.5 万亿，7 位就够用到天荒地老，一般用 6-7 位。

```java
private static final String CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
public static String toBase62(long id) {
    StringBuilder sb = new StringBuilder();
    while (id > 0) { sb.append(CHARS.charAt((int)(id % 62))); id /= 62; }
    return sb.reverse().toString();
}
```

好处是**绝对不会重复**（ID 唯一），且短码**趋势递增**（B+Tree 索引友好、缓存友好）。坏处是短码可被枚举（用户能推算下一个短码），需要配合访问控制；号段模式还要处理"服务重启浪费一段号码"的问题（无所谓，号码管够）。

**方案二：哈希取模（MD5 截断）**

对原始 URL 做 MD5 取前 7 位。问题是**会碰撞**，必须做"查库 → 碰撞了就加盐重算"的循环，写入路径变复杂，而且同一个 URL 多次提交会产生不同短码（除非额外维护 URL → 短码的反向索引）。

**方案三：预生成**

离线批量生成 1 亿个不重复短码存池子里，用完再生成。实现简单但要额外维护池子，且短码无序（对索引不友好）。

**我选号段 + Base62**，理由就一句：唯一性和有序性都拿到了，代价只是"可枚举"，而这个可以靠业务层解决。

---

**第三部分：存储选型——MySQL 还是 HBase**

| 维度 | MySQL 分库分表 | HBase |
|---|---|---|
| 写入 | 单机 3000-5000 TPS，需要分片 | 天然水平扩展，写入更强 |
| 读取 | 走主键索引很快，但要防热点 | 按 rowkey 查询快，适合海量 |
| 运维 | 成熟，团队都会 | 依赖 HDFS/ZK，运维重 |
| 成本 | 需要中间件（ShardingSphere） | 集群资源占用大 |

**结论：日增 10 万条这个量级，MySQL 分库分表完全够用**，不必上 HBase。分片键用短码（保证查询能直接定位到分片），按短码哈希分 16 库 64 表。

HBase 适合日增千万级以上的场景，这个需求用它是过度设计——面试时能说出"为什么不用"比说"我会用"更显判断力。

**表结构**：

```sql
CREATE TABLE t_short_url (
  id          BIGINT       NOT NULL,
  short_code  VARCHAR(8)   NOT NULL,
  origin_url  VARCHAR(2048) NOT NULL,
  create_time DATETIME     NOT NULL,
  expire_time DATETIME     NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_code (short_code)
) ENGINE=InnoDB;
```

`uk_code` 是最后一道唯一性保障，即使发号器出问题也能挡住重复。

**第四部分：读性能——多级缓存**

读路径是"短码 → 原始 URL"，典型的 KV 查询，用三级缓存：

**本地缓存（Caffeine）**：扛住热点短码（比如某个活动链接被疯狂点击），容量设 10 万条，TTL 5 分钟。本地缓存要注意**多实例不一致**，但对短链这种"基本不变"的数据可以接受。

**Redis**：主缓存，`GET short:xxx`，命中率目标 95% 以上。key 用短码，value 存原始 URL（可以只存 URL 不存整个对象，省内存）。

**MySQL**：缓存未命中回源，回源后**异步**回写 Redis（不要同步写，避免回源请求被写操作拖慢）。

**缓存穿透防护**：短码是外部可枚举的，攻击者可以随便编造短码刷库。两道防护——Redis 里对不存在的短码缓存空值（TTL 60 秒），以及入口做限流（按 IP 按短码维度）。

**缓存击穿防护**：如果某个超热短码的缓存刚好过期，大量请求同时回源。用 `SETNX` 互斥锁或者逻辑过期（value 里带过期时间，异步刷新）。

---

**第五部分：跳转细节——301 还是 302**

**用 302，不用 301。**

301 是永久重定向，浏览器会缓存，后续再访问这个短链**根本不会再请求你的服务**——你就统计不到点击量，也没法做风控和链接失效。

302 是临时重定向，每次都会回到服务端，能统计、能控制、能随时改指向。代价是多一次请求，但对"1 亿次日访问"这个业务来说，**统计能力比省那次请求重要得多**。

如果某些链接明确不需要统计（比如纯资源 CDN），可以给 301 作为优化选项。

**响应体的构造**：

```java
response.setStatus(302);
response.setHeader("Location", originUrl);
response.setHeader("Cache-Control", "no-cache");   // 防止中间层缓存
```

---

**第六部分：防刷与安全**

三个层面：

**生成接口防刷**：同一 IP 每分钟最多生成 10 条，超了返回 429。用 Redis 的滑动窗口或者 Sentinel 限流。

**跳转接口防刷**：按短码维度限流（防止某个链接被恶意刷），按 IP 维度限流（防止单 IP 扫库）。

**恶意 URL 检测**：接入黑名单（第三方安全库），生成前校验一遍，防止短链被用于钓鱼——这是短链服务最容易被忽视的合规风险。

**面试话术收口**

我会这么答：先算容量——日访问 1 亿对应 1160 QPS 均值、6000 峰值，5 年 1.8 亿条记录约 90 GB，所以读靠 Redis 完全够、存储必须分库分表。发号用号段模式 + Base62，保证唯一且趋势递增；存储选 MySQL 分 16 库 64 表，按短码哈希分片，不用 HBase 是因为量级不够；读走 Caffeine + Redis + MySQL 三级缓存，配空值缓存和互斥锁防穿透击穿；跳转用 302 保留统计能力。最后补一句防刷和恶意 URL 校验是合规底线。
