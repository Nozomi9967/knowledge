## 一、内存模型（6 题）

### 1. JVM 运行时内存分为哪几块？哪些是线程私有、哪些是线程共享？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

JVM 运行时内存分五块：程序计数器、虚拟机栈、本地方法栈、堆、方法区。按线程归属分两类，程序计数器、虚拟机栈、本地方法栈是线程私有的，每个线程各有一份，随线程创建和销毁；堆和方法区是线程共享的，整个进程就一份。方法区在 JDK 8 之后的实现叫元空间，已经挪到本机内存里了。还有一个容易混的概念是直接内存，它不算 JVM 运行时内存，属于堆外内存，走的是操作系统本地内存，NIO 的 DirectByteBuffer 用的就是它。所以线上会碰到一种情况：堆内存指标看着正常，进程却被 OOM Killer 杀掉，那就是堆外涨上去了。

**追问参考答**

直接内存不算 JVM 运行时内存，它属于堆外内存也叫本机内存，由操作系统分配管理，NIO 可以直接操作。它和堆的区别在于不受 GC 管理、不受 -Xmx 限制，但反过来泄漏了也很难发现，因为常规的堆监控看不到它。

### 2. 程序计数器是干什么的？为什么必须是线程私有？为什么它是唯一不会 OOM 的区域？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

程序计数器存的是当前线程正在执行的 Java 方法的字节码指令地址，相当于记着执行到哪一行。必须线程私有，是因为 JVM 的多线程是时间片轮转调度的，一个线程被切走之后要能恢复到原来执行的位置，所以每个线程得各自记自己的地址，不能共用。它还是唯一不会 OOM 的区域，原因很简单，它只存一个指令地址，内存大小固定、不需要动态分配，JVM 规范根本没给它分配动态内存，所以既不会 OOM 也不会栈溢出。

**追问参考答**

执行 native 方法的时候，程序计数器的值是 undefined。因为 native 方法由本地代码实现，压根不对应字节码，记字节码地址没有意义，所以规范直接把它定义成未定义值。这点常被拿来问，答"记的是本地方法地址"是错的。

### 3. 虚拟机栈里存什么？栈帧里包含哪些内容？栈深度由什么决定？

> **知识点跳转：** [[jvm八股]] · [[StackOverflowError与OutOfMemoryError（虚拟机栈）]]

**参考答案**

虚拟机栈存的是方法调用对应的栈帧，一个方法被调用就压一个栈帧，方法返回就弹出。栈帧里有四部分：局部变量表、操作数栈、动态链接、方法返回地址。局部变量表放方法参数和局部变量，操作数栈是字节码做运算时的工作区，动态链接指向运行时常量池里这个方法的符号引用，返回地址记着方法执行完该回到调用方的哪一条指令。栈深度由 -Xss 控制，它决定每个线程栈能有多大，栈帧越多就越深，超过就溢出。

**追问参考答**

这题最容易答错的是把栈的异常和堆的异常搞混。StackOverflowError 是栈深度超过 -Xss 上限，典型场景就是无限递归。栈的 OutOfMemoryError 是创建新线程时分配不出栈内存，典型场景是线程开得太多，每个线程的栈都要占一块内存，把机器内存耗光，报错是 unable to create new native thread。至于"Full GC 后找不到空间分配对象"，那是堆 OOM，和栈完全是两码事。

### 4. 堆是怎么分代的？JDK 8 下堆的完整结构？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

堆分新生代和老年代。新生代再细分成一个 Eden 加两个 Survivor，默认比例是 8 比 1 比 1，这两个 Survivor 一个叫 from 一个叫 to，复制算法就是在它们之间倒腾存活对象。老年代放熬过多次 GC 的对象。JDK 8 下堆的完整结构就是新生代的 Eden、S0、S1 加上老年代，注意方法区已经不在这里了，JDK 8 把它挪到元空间、放在本机内存。所以看堆结构图的时候别再画永久代。

**追问参考答**

大对象一般直接进老年代，因为新生代 Minor GC 非常频繁，用的又是复制算法，大对象在 Eden 和 Survivor 之间反复搬代价太高，直接放老年代省掉这些复制。不过要补一句限定条件：这只对 Serial、ParNew 这类收集器成立，G1 是用 Humongous Region 专门处理大对象的，不能一概而论。

### 5. 方法区（元空间）是什么？JDK 8 的元空间和永久代有什么区别？

> **知识点跳转：** [[jvm八股]]

**参考答案**

方法区是 JVM 规范里的逻辑概念，用来存类元数据、常量、静态变量、运行时常量池、JIT 编译后的代码缓存这些。元空间是 HotSpot 对这个逻辑概念的具体实现，JDK 8 开始取代永久代。区别主要在位置和 OOM 风险：永久代在 JVM 堆内，大小由 PermSize 限制，很容易 OOM；元空间挪到了本机内存，大小受本机内存限制，不容易 OOM。但"不容易"不等于"不会"，元空间照样能被打爆。

**追问参考答**

元空间 OOM 主要有三个原因：加载的类太多；类加载器泄漏，自定义 ClassLoader 一直不被回收，它加载的所有类就跟着都卸载不掉；动态代理生成的类太多，CGlib 和 JDK 代理都会产出大量类。类卸载要三个条件同时满足：这个类没有存活的实例、类的 Class 对象没有被任何地方引用、加载它的 ClassLoader 已经被回收。反过来说，启动类加载器加载的类永远不会卸载，因为它的 ClassLoader 永远不会被回收。

### 6. 直接内存是什么？为什么 NIO 要用堆外内存？它是怎么回收的？

> **知识点跳转：** [[jvm八股]] · [[DirectByteBuffer与堆外内存回收]]

**参考答案**

直接内存是堆外内存，通过 NIO 的 DirectByteBuffer 分配，绕过 JVM 堆直接使用操作系统的本地内存。NIO 要用它有两个原因：一是减少一次拷贝，普通堆内数据做 IO 时得先复制到堆外缓冲区再交给操作系统，用堆外内存直接省掉这次堆内到堆外的拷贝；二是不受堆 GC 影响，大块数据不会因为 GC 移动对象而被打断。回收机制是 DirectByteBuffer 关联了一个 Cleaner，Cleaner 本质上是虚引用，当 ByteBuffer 对象不可达时，Cleaner 被触发，调用 Unsafe 的 freeMemory 把堆外内存释放掉。

**追问参考答**

堆外内存泄漏特别隐蔽，因为 -Xmx 看堆是正常的，但本机内存被一点点吃光，最后进程被操作系统的 OOM Killer 杀掉，看日志只有一句 killed。排查手段是用 jcmd 的 VM.native_memory summary 看 native 内存分布，用 -XX:MaxDirectMemorySize 给堆外设上限，再回头查有没有创建了 ByteBuffer 却一直没释放的地方。

## 二、字符串与对象（2 题）

### 7. 栈中存的到底是指针还是对象？局部变量和方法参数存在哪？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

栈上存的是引用，不是对象本体。对象本体在堆里，栈帧的局部变量表里放的是指向堆对象的引用。但这题的关键是不能一刀切，要分类型说：基本类型是直接在栈上存值的，比如 int 就存那四个字节的数值本身；只有引用类型才在槽位里存引用。局部变量和方法参数都在当前栈帧的局部变量表里，方法参数在方法调用时按顺序压进局部变量表的起始槽位，本质上参数也是局部变量的一部分。

**追问参考答**

基本类型直接在局部变量表的槽位里存数值，引用类型的槽位存的是指向堆对象的引用，对象本身在堆上。所以同一句"栈存指针"对引用类型成立、对基本类型不成立，回答时把这两种情况分开讲，比笼统说一句更稳。

### 8. `String s1 = "abc"` 和 `String s2 = new String("abc")` 的区别？（创建了几个对象、内存位置、比较结果）

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

区别在对象个数、内存位置和比较结果三块。用字面量写 String s1 等于 abc，会先去字符串常量池找，有就直接返回那个引用、不创建新对象；没有就在常量池创建一个，所以是零个或一个对象。用 new String 加 abc，一定先在堆里创建一个对象，然后再去常量池看有没有 abc，没有的话池里也创建一个，所以常量池原本没有时一共创建两个对象，已经有了就只创建堆里那一个。内存位置上 s1 指向常量池，s2 指向堆。比较结果 s1 和 s2 用双等号是 false，因为引用不同；用 equals 是 true，因为内容相同。

**追问参考答**

intern 的作用是把字符串放进常量池并返回池里的引用。JDK 6 和 JDK 7 以后行为不一样：JDK 6 的常量池还在永久代，池里没有的话会把堆里的字符串拷贝一份到池里，返回的是新拷贝的引用，原来的堆对象和池对象是两个不同对象；JDK 7 以后常量池挪到了堆里，池里没有时直接把堆对象的引用登记进池子，不再拷贝，省一份内存。这个差异是 intern 最常考的点。

## 三、引用类型（1 题）

### 9. Java 有哪四种引用类型？分别什么强度？弱引用、虚引用各有什么应用场景？

> **知识点跳转：** [[jvm八股]] · [[jvm八股]]

**参考答案**

四种引用强度从高到低是强、软、弱、虚。强引用就是 new 出来的，只要还能顺着引用链找到就不回收，哪怕马上要 OOM 也不回收。软引用是内存充足时不回收，只有快要 OOM 之前才回收，适合做缓存，比如图片这种体积大、重建成本高但不是必需的数据。弱引用是只要发生 GC 就回收，不管内存够不够，典型场景是 ThreadLocal 的 key 和 WeakHashMap。虚引用最弱，随时可能被回收，而且 get 永远返回 null，你根本通过它拿不到对象，唯一作用是通过引用队列感知对象被回收了，典型场景是 DirectByteBuffer 的 Cleaner，用来监控堆外内存释放。所以弱引用和虚引用的关键区别不在回收时机，而在行为：弱引用回收前还能 get 到对象，虚引用永远 get 不到。

**追问参考答**

ThreadLocal 的 key 用弱引用是为了防泄漏。如果用强引用，栈上的引用断开后 ThreadLocal 对象还被 Entry 强引用挂着，ThreadLocal 和 value 会双重泄漏；用弱引用，ThreadLocal 能被回收，只剩 value 泄漏，而且还有被动清理的机会，细节见 [[ThreadLocal 深度解析与内存泄露笔记]]。WeakHashMap 的弱引用不会被"立刻"回收，只是"随时可能"，具体什么时候回收取决于 GC 什么时候发生，赋值那一刻不会触发回收，这是很常见的误区。

## 四、内存泄漏与溢出（3 题）

### 10. 内存泄漏和内存溢出的区别？内存泄漏一定会导致内存溢出吗？

> **知识点跳转：** [[jvm八股]] · [[静态集合内存泄漏与类卸载详解]]

**参考答案**

内存泄漏是对象已经不再使用了，但仍然被引用着，GC 回收不掉，可用内存一点点变少。内存溢出是分配对象时堆里没有足够空间，直接抛 OutOfMemoryError。泄漏不一定会导致溢出，但它会不断蚕食可用空间，让溢出更容易发生，泄漏量足够大时必然溢出。所以这两者是因果关系但不同步，泄漏是过程，溢出是结果。

**追问参考答**

静态集合为什么是 GC Root，要讲可达性链。JDK 8 下 static 字段本体挂在堆里的 Class 对象上，而 Class 对象被常驻的类加载器强引用着，整条链强可达，所以 static 变量就成了 GC Roots 的起点，它引用的任何对象都永远回收不掉。这里有个细节要分清：GC Root 是 static 变量本身，静态集合只是它指向的那个对象，说"静态集合是 GC Root"其实是简化说法，答的时候补这一句会显得真懂。

### 11. JVM 哪些区域会抛 OutOfMemoryError？各自的典型场景？

> **知识点跳转：** [[jvm八股]] · [[StackOverflowError与OutOfMemoryError（虚拟机栈）]]

**参考答案**

四个区域会 OOM，一个不会。堆 OOM 是对象实例堆积、内存泄漏把堆撑满，报错是 Java heap space。栈 OOM 是创建线程时分配不出栈内存，报 unable to create new native thread，注意这跟栈深度超限的 StackOverflowError 是两码事。元空间 OOM 是加载类太多或者类加载器泄漏，报 Metaspace。直接内存 OOM 是大量 allocateDirect 又不释放，堆内存指标正常但本机内存被吃光，进程被系统杀掉。程序计数器是唯一不会 OOM 的，因为它只存指令地址，大小固定，不动态分配。

**追问参考答**

元空间 OOM 的根本原因有三个：加载类过多、类加载器泄漏、动态代理生成的类爆炸。排查方向分四步：先用 jstat -class 看加载类数量是不是持续增长；再 jmap dump 出来用 MAT 查有没有自定义 ClassLoader 的实例残留，类加载器泄漏是元空间 OOM 的主因；接着检查 CGlib 和 JDK 动态代理的生成量；最后用 -XX:MaxMetaspaceSize 设上限并做监控告警。

### 12. 常见的内存泄漏案例有哪些？ThreadLocal 为什么会内存泄漏？怎么避免？

> **知识点跳转：** [[jvm八股]] · [[ThreadLocal 深度解析与内存泄露笔记]]

**参考答案**

常见泄漏案例有几类：静态集合一直往里放对象不清理；事件源绑定了短生命周期的监听器，事件源活着监听器就回收不掉；线程一直没停且持有对象引用；ThreadLocal 用完不 remove；流和数据库连接忘了关；缓存的 key 失效了但 value 还留着。ThreadLocal 泄漏的机制要讲清楚：ThreadLocalMap 的 Entry 是弱引用，key 指向 ThreadLocal 对象，value 是强引用。栈上的强引用断开后，ThreadLocal 对象会被 GC 回收，key 变成 null，但 value 还被 Entry 强引用着；而 Entry 又被 Thread 里的 ThreadLocalMap 强引用，只要这个线程活着，线程池场景线程几乎不死，这个 value 就永远回收不掉。避免办法就是在 finally 里显式调用 remove，线程池场景必须 remove，既防泄漏也防脏数据串到下一个任务。

**追问参考答**

未关闭的资源泄漏，本质是"堆内小对象加堆外大资源"错配。Connection 和流对象在堆里很小，但它持有底层句柄和堆外内存，GC 只回收堆内对象头，不 close 底层资源就永远不释放，最后句柄耗尽或者堆外内存耗尽。自定义 ClassLoader 导致元空间泄漏是这样一条链：每次热部署都 new 一个 ClassLoader，如果它的类实例还被引用着，比如被静态集合持有，这个 ClassLoader 就回收不掉，它加载的所有类也跟着卸载不掉，元空间只涨不降，最后 Metaspace OOM。
