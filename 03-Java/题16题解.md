
### **启动慢是因为 JVM 还在"热身"：JIT 没编译到 C2、类还在懒加载、连接池是空的，跑几分钟把这些冷启动成本摊掉后就稳了**

  

---

  

### **一、JIT 编译（C1 / C2）**

  

JVM 执行 Java 字节码有三种模式：**解释执行 → C1 编译 → C2 编译**，性能大概是 1 : 5 : 10 的量级。

  

刚启动时所有方法都是**解释执行**，也就是字节码一条条翻译成机器码跑，慢是必然的。JVM 内部有个计数器统计方法调用次数和循环回边次数，达到阈值后触发编译：

  

- **C1（Client Compiler）**：轻量优化，编译快，产出的机器码性能一般。阈值大概 1500 次调用。

- **C2（Server Compiler）**：重度优化，做逃辑分析、内联、循环展开、逃逸分析，编译慢但产出的代码接近 native 性能。阈值大概 10000 次。

- **分层编译（Tiered Compilation，JDK 8 之后默认开）**：先解释 → C1 → C2 逐级升温，热点方法最终稳定在 C2。

  

启动那几分钟，业务方法调用次数还没攒够，大量代码在解释或 C1，响应自然慢。等热点方法都被 C2 编译并缓存进 **CodeCache** 后，性能就上来了。

  

还有一个坑：**CodeCache 满了会停止 JIT**，之后一直解释执行，性能永远回不来。默认 240MB，微服务一般够，但类多的可以调大 `-XX:ReservedCodeCacheSize`。

  

---

  

### **二、类加载**

  

Java 的类是**懒加载**的——用到才加载。启动时 JVM 只加载了 main 和一部分核心类，业务链路上的类要等第一次请求触发才会：

  

**加载（读 class 文件） → 验证 → 准备 → 解析 → 初始化（跑 static 块）**

  

Spring 场景更明显：第一次请求走到某个 Controller，才会级联加载它依赖的 Service、Mapper、DTO、Jackson 的序列化器、AOP 代理类（CGLIB 动态生成）等等。每个类加载都要读文件、走 ClassLoader 双亲委派、可能还要从 jar 里解压，IO + CPU 都有开销。

  

再加上第一次跑的时候这些类的方法都是解释执行的，**类加载 + JIT 冷启动叠加**，前几百个请求特别慢。

  

---

  

### **三、连接池预热**

  

**数据库连接池**（HikariCP、Druid）、**HTTP 客户端池**（OkHttp、Apache HttpClient）、**Redis 连接池**（Lettuce、Jedis）、**RPC 连接**（Dubbo、gRPC）——这些池子启动时通常只建了 `minIdle` 个连接，甚至一个都没有（懒建）。

  

第一批请求进来会遇到：

  

- **建 TCP 连接**：三次握手 RTT。

- **TLS 握手**：如果是 HTTPS 或 MySQL SSL，还有证书交换、密钥协商，几十到几百 ms。

- **数据库鉴权**：MySQL 的 handshake、账号密码校验、字符集协商。

- **连接池扩容抖动**：并发上来后同时建多个连接，把 DB 也打慢。

  

还有 **DNS 解析**第一次也慢，JVM 默认还会缓存 DNS 结果（`networkaddress.cache.ttl`），第一次没缓存就得走完整解析。

  

---

  

### **预热方案**

  

**JIT 层面**：

  

- **JDK 11+ 可以用 AOT / JDK 17+ 用 CDS（Class Data Sharing）**，把类元数据和部分编译结果预先存盘，启动直接加载。`-XX:ArchiveClassesAtExit` 和 `-XX:SharedArchiveFile` 配合用。

- **JWarmup（阿里 Dragonwell）或 ReadyNow（Azul）**：把生产环境的 JIT 编译信息 dump 出来，下次启动直接编译到 C2，跳过升温过程。开源界类似方案是 GraalVM Native Image，直接编译成本地可执行文件，但有反射和动态代理的兼容成本。

- **应用层"打靶"预热**：启动完成后，在 `ApplicationReadyEvent` 里跑一段模拟流量，把核心接口的关键路径调用几千次，逼 JVM 编译到 C2。可以用录制的真实流量回放，或者写个内部预热接口。

  

**类加载层面**：

  

- **提前触发初始化**：在启动时主动 `Class.forName()` 或直接调用一遍核心链路的方法，把 Controller / Service / Mapper / Jackson 的 ObjectMapper / CGLIB 代理都加载好。

- **Spring 层面**把 lazy-init 关掉（`spring.main.lazy-initialization=false`，默认就是），并在启动完成后主动跑一次业务方法。

- 如果用了大量反射或动态代理，提前把代理类生成好。

  

**连接池层面**：

  

- **HikariCP**：把 `minimumIdle` 设成和 `maximumPoolSize` 一致，启动时就建满连接；或者用 `connectionInitSql` 确保连接建立后是可用状态。

- **Redis / HTTP 池**：启动后跑一次 `PING` 或健康检查接口，把每个连接都建起来。

- **Feign / OkHttp**：预先对下游服务发几个探测请求，把连接和 TLS 会话建好（TLS session 复用能省一次握手）。

- **DNS**：设置 `networkaddress.cache.ttl` 合理值，避免频繁解析；或启动时主动 `InetAddress.getByName()` 触发缓存。

  

**流量层面（最关键的兜底）**：

  

- **K8s 的 readinessProbe 延迟放流量**：健康检查里加一个"预热完成"标志，预热跑完才把 Pod 加进 Service Endpoint。

- **网关灰度放量 / 慢启动**：Nginx、Spring Cloud Gateway、Dubbo 都支持给新实例一个 slow start 权重曲线，前几分钟只分配 10% → 30% → 100% 流量，避免冷实例被打爆。

- **优雅上线**：结合服务注册中心（Nacos、Eureka）的权重能力，实例注册后先给低权重，预热完再调满。

  

---

  

一句话总结面试答法：**冷启动慢是"解释执行 + 懒加载 + 空连接池"三重叠加**，预热方案就是**在放流量之前，主动把这三样都"跑热"**——JIT 靠模拟流量或 JWarmup、类加载靠提前初始化、连接池靠 minIdle 拉满 + 健康探测，最后用 K8s readiness 或网关慢启动兜底不让冷实例接真实流量。
