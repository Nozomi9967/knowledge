# volatile 与内存屏障详解：双重检查锁（DCL）案例

## 番外：为什么屏障叫 StoreStore / StoreLoad —— 命名规律

> 这部分是"理解 4 种屏障名字"的额外补充，把抽象命名映射到代码结构上。

### 命名公式

JMM 屏障的名字是严格的"前后组合命名法"，公式：

```
[屏障前的操作] + [屏障后的操作]
```

底层概念：

- **Store** = 写（把寄存器里的数据"存"到缓存/主内存）
- **Load** = 读（把缓存/主内存里的数据"读"到寄存器）

### 四个屏障的"方位说明"

| 屏障 | 前面的操作 | 后面的操作 | 一句话大白话 |
|------|-----------|-----------|-------------|
| **StoreStore** | Store（写） | Store（写） | 前面的写不完，后面的写不准插队 |
| **StoreLoad** | Store（写） | Load（读） | 前面的写不刷主内存，后面的读不准开始 |
| **LoadLoad** | Load（读） | Load（读） | 前面的读不完，后面的读不准开始 |
| **LoadStore** | Load（读） | Store（写） | 前面的读不完，后面的写不准偷跑 |

### StoreStore 屏障代码还原

```java
a = 1;                  // Store1（普通写）
// ────────────────────
// 【StoreStore 屏障】
// ────────────────────
volatile_flag = true;   // Store2（volatile 写）
```

**潜台词**："前写、后写，老老实实，不准调换"。

### StoreLoad 屏障代码还原

```java
volatile_flag = true;   // Store（volatile 写）
// ────────────────────
// 【StoreLoad 屏障】
// ────────────────────
int b = a;              // Load（普通读）
```

**潜台词**："前面的写必须完事，后面的读才能开始"——StoreLoad 是开销最大的屏障，因为它既要**强制刷主内存**（让 Store 对其他线程可见），又要**禁止后续所有 Load/Store 跨越**。

### 一句话

> 别被名字唬住了——屏障的名字就是最老实的**"方位说明"**：左边是谁、右边是谁、中间切一刀，名字就叫"谁谁"。

---

## 一句话总结

volatile 不是用来"锁线程"的（那是 synchronized 的活），**它是用来"锁 CPU 指令顺序"的**——通过在写操作前后插入**内存屏障（硬隔离围栏）**，强行禁止编译器和 CPU 把屏障前后的指令重排序。

---

## 一、案例：看似完美的 DCL 单例

> 双重检查锁（Double-Checked Locking）是面试高频写法，也是理解 volatile 价值的最佳案例。

```java
public class Singleton {
    private static Singleton instance;   // ⚠️ 此时没有加 volatile！

    public static Singleton getInstance() {
        if (instance == null) {              // 第一次检查（无锁，快路径）
            synchronized (Singleton.class) {
                if (instance == null) {       // 第二次检查（持锁后）
                    instance = new Singleton();   // 💥 问题就出在这里！
                }
            }
        }
        return instance;
    }
}
```

**逻辑看似完美**：第一次无锁检查避免每次都进同步块，第二次持锁检查避免重复创建。**但实际上，这段代码在多线程下是错的**。

---

## 二、核心矛盾：`new Singleton()` 不是原子操作

在 Java 层面，`instance = new Singleton();` 是一行代码。但在 **CPU 眼里，它被拆成了 3 条指令**：

| 步骤 | 指令 | 实际干了什么 | 类比 |
|------|------|------------|------|
| **指令 1** | `memory = allocate()` | 在堆里分配一块内存空间 | 给房子打个地基、留个门牌号 |
| **指令 2** | `ctor(memory)` | 调用构造方法，初始化这块内存 | 把家具搬进房子、把墙刷好 |
| **指令 3** | `instance = memory` | 把 `instance` 引用指向这块内存 | 把钥匙交给 `instance` 变量 |

**关键问题**：这 3 条指令**不是原子的**，编译器/CPU 为了提速，**有权调整它们的执行顺序**。

---

## 三、灾难：CPU 的"偷跑"（指令重排序）

CPU 极其追求速度，它一看：

> "指令 2（装修）要花挺长时间，指令 3（给钥匙）只要一瞬间。反正最后 `instance` 都是指向这块内存，那我**先执行指令 3 吧**！"

于是执行顺序被重排成：**指令 1 → 指令 3 → 指令 2**。

### 3.1 致命邂逅：线程 A 和 线程 B

| 时间线 | 线程 A | 线程 B |
|--------|--------|--------|
| **T1** | 抢到锁，进入 `synchronized` 块 | — |
| **T2** | 执行 `new Singleton()`，触发指令重排 | — |
| **T3** | 执行**指令 1**：分配内存（堆里有了"毛坯房壳子"） | — |
| **T4** | **CPU 偷跑**执行**指令 3**：`instance` 指向内存 | — |
| **T5** | （此刻对象还没初始化，**房子是空的，家具还没进**） | 进入 `getInstance()` |
| **T6** | — | 第一层 `if (instance == null)`：`instance != null` ✅ |
| **T7** | — | 直接 `return instance` 🎉 |
| **T8** | — | 调用 `instance.doSomething()` → **NPE 爆炸 💥** |
| **T9** | 线程 A 终于慢吞吞执行**指令 2**：初始化对象 | （太晚了） |

**结果**：线程 B 拿到的 `instance` **对象存在（不是 null），但还没初始化完**——访问任何字段都是默认值，调用方法直接 NPE。

> **"半成品对象"是 DCL 的经典死穴**。第一次检查通过的前提是"对象可用"，但重排序让对象"看起来存在、实际未初始化"。

## 四、救星：volatile 怎么卡死 CPU

修法——给 `instance` 加 `volatile`：

```java
private static volatile Singleton instance;
```

JIT 编译器在编译 `instance = new Singleton()` 时，看到 `instance` 是 volatile 变量，会在**指令 3（volatile 写）前后**强行插入内存屏障：

```text
指令 1：memory = allocate()        ── 分配内存
指令 2：ctor(memory)                ── 初始化对象
─────────────────────────────────────────────────
【StoreStore 屏障】                 ── 硬隔离围栏①
─────────────────────────────────────────────────
指令 3：instance = memory          ── volatile 写（建立引用）
─────────────────────────────────────────────────
【StoreLoad 屏障】                  ── 硬隔离围栏②（开销最大）
─────────────────────────────────────────────────
```

### 4.1 屏障的"硬隔离"语义

JMM 对屏障的定义是绝对的、不可商量的：

- **屏障前面的指令**：CPU 绝对不能把它重排到屏障后面
- **屏障后面的指令**：CPU 绝对不能把它重排到屏障前面
- **屏障本身**：通常是一个**空操作 + 强制刷新**（x86 上是 `lock` 前缀指令）

### 4.2 StoreStore 屏障在这里的作用

> 「后面的指令 3，你给我站住！在指令 1 和指令 2 彻底干完活之前，你**绝对不准**重排到前面去！」

CPU 没办法，被这堵墙死死卡住。它只能乖乖地：

1. 先建房子（指令 1：分配内存）
2. 再把家具装修好（指令 2：初始化对象）
3. **跨过 StoreStore 屏障**
4. 最后才把钥匙交给 `instance`（指令 3：建立引用）

### 4.3 StoreLoad 屏障在这里的作用

> 「volatile 写必须刷主内存（可见性），且后续所有 Load/Store 不能重排到这次写之前」。

这一条既保证了**其他线程能立即看到 `instance` 的新值**，也保证了**其他线程看到 `instance` 时，背后的内存一定是初始化好的**——因为「建立引用」之前的所有写（指令 1、2）都被前面那个 StoreStore 屏障挡在后面了。

---

## 五、对比：如果不加 volatile 会怎样

| 步骤 | 不加 volatile | 加 volatile |
|------|--------------|-------------|
| 分配内存（指令 1） | ✅ 执行 | ✅ 执行 |
| 初始化对象（指令 2） | 可能被重排到指令 3 之后 | 必须在指令 3 之前 |
| 赋值引用（指令 3） | 可能在指令 2 之前执行 | 必须在指令 1、2 之后 |
| 线程 B 看到的 `instance` | **可能是半成品对象** 💥 | 一定是完整对象 ✅ |
| NPE 风险 | 高 | 0 |

## 六、DCL 之外的等价问题

DCL 是最经典案例，但**任何"先判断引用非空、再使用对象"的模式都可能有这个问题**：

- 单例模式的 holder / 枚举实现
- 缓存中的 lazy init（先 put 引用，再异步加载）
- `final` 字段的安全发布（必须确保构造完成后再让其他线程看到引用）

**统一修法**：让**"对象引用"**这个变量具备 volatile 语义，或者用 `final` 字段（被 JMM 保证安全发布）。

---

## 七、和 synchronized 屏障的区别

| 维度 | synchronized 屏障 | volatile 屏障 |
|------|-------------------|---------------|
| 作用范围 | 整个 monitorenter / monitorexit 之间 | 仅包裹 volatile 变量读写 |
| 触发时机 | 进入/退出同步块 | volatile 读/写前后 |
| 屏障类型 | 隐式（Lock 前缀） | 显式（4 种 JMM 屏障） |
| 阻塞线程 | ✅ 会阻塞 | ❌ 不阻塞 |
| 解决原子性 | ✅ 整个同步块原子 | ❌ 只保证单变量读写原子 |

> **synchronized 的屏障**管的是"一整块代码对外不可分割"（ACID 中的 A）；
> **volatile 的屏障**管的是"单变量的读写不被重排序 + 立即可见"（ACID 中的 V）。

---

## 八、面试话术模板

> "DCL 单例的 `instance` 必须加 volatile，根本原因是 `new Singleton()` 不是原子操作——它会被拆成分配内存、初始化对象、赋值引用三步，CPU 为了提速可能重排成 1→3→2，导致其他线程看到一个'半成品对象'，调用方法直接 NPE。volatile 在赋值引用这一步（volatile 写）前后插入 StoreStore + StoreLoad 屏障，强制指令 1、2 必须在指令 3 之前完成，CPU 没办法把'赋值引用'重排到'初始化'前面。volatile 不是锁线程的，是锁 CPU 指令顺序的——它通过内存屏障这种'硬隔离围栏'，让屏障前后的指令绝对不能换位。"
