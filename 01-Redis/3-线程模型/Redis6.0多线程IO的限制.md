## Redis 6.0 多线程 IO 的限制

### 一句话

> Redis 6.0 多线程 IO 是**单实例级别**的优化，解决的是**大量并发连接**下 read/write 系统调用的 CPU 开销，不能用于优化 pipeline 场景。

---

### 先搞清楚两个东西各自解决什么问题

**Redis 6.0 多线程 IO：**

```
之前：主线程  read(解析) → 执行命令 → write(回复)
6.0： IO线程 read+parse → 主线程 执行命令 → IO线程 write
```

优化的是**网络 IO 的吞吐量**——当每秒有成千上万个客户端连接发请求时，主线程花在 read/write 系统调用上的时间太多，分给 IO 线程来做，主线程专心执行命令。

**Pipeline（管道）：**

```
普通：    请求1 → 等回复 → 请求2 → 等回复 → 请求3 → 等回复
Pipeline：请求1、请求2、请求3 → 一次性发出 → 一次性收回复
```

优化的是**RTT（往返延迟）**——把多次网络交互合并成一次，减少网络开销。

---

### 为什么 pipeline 场景下多线程 IO 没用？

| 场景 | 瓶颈在哪 | 多线程 IO 有用吗 |
|------|---------|----------------|
| 1 万个独立连接各发 1 条请求 | 每次 read/write 都是独立系统调用，IO 开销大 | ✅ 有用，IO 线程分担 |
| 1 个连接用 pipeline 发 1 万条请求 | 一次 read 全读进来，只需一两次系统调用，IO 开销极小 | ❌ 没用，瓶颈在主线程执行命令的速度 |

pipeline 已经把多次网络交互合并了，IO 开销已经压到最低，再多 IO 线程也榨不出油水。

---

### 为什么"只能用于所有 clients 都在一个实例中"？

Redis 6.0 的多线程 IO 是**单实例级别**的优化：

- 每个 Redis 实例有自己独立的 IO 线程池
- 如果客户端分布在 Redis Cluster 的多个节点上
- 每个节点的 IO 线程只处理连接到它自己的客户端
- **多线程 IO 不能跨节点加速**

实际含义：这个特性就是个**本机优化**，不能指望它解决集群拓扑层面的性能问题。

---

### 对比总结

| | 多线程 IO（6.0） | Pipeline |
|---|---|---|
| **优化的瓶颈** | read/write 系统调用的 CPU 开销 | 网络 RTT（往返延迟） |
| **适用场景** | 大量并发连接，每个连接请求不多 | 单个连接发送大量请求 |
| **工作原理** | IO 线程并行处理网络读写 | 客户端批量发送、批量接收 |
| **能否叠加** | 能，但 pipeline 下收益极小 | — |
