# 云商城已知硬伤与追问预案

> 这不是给面试官看的，是给你自己看的。下面每一条都是**代码里真实存在**的问题，附带文件位置。
> 原则：**能修的先修，修不完的准备话术**。最怕的是你不知道它存在，面试官顺着你自己讲的技术点挖下去，第一铲就挖到。

---

## P0 —— 必须处理（不处理会当场翻车 / 或功能根本跑不通）

### 1. Seata AT 缺 `undo_log` 表，回滚根本执行不了

`sql/` 里只有 Seata Server 端的 4 张表（`global_table`、`branch_table`、`lock_table`、`distributed_lock`），**唯独没有业务库侧的 `undo_log`**。AT 模式第二阶段回滚，靠的就是各业务库自己的 `undo_log` 里存的前后镜像。缺这张表，一阶段能提交，回滚时会直接报错。

- **怎么问**：「你 Seata 用的 AT，那回滚具体是怎么回滚的？undo_log 建在哪个库？」
- **怎么修**：在 `shop_goods`、`shop_order` 两个参与库各建一张官方 `undo_log`（`branch_id` / `xid` / `context` / `rollback_info` / `log_status`），然后**真的跑一次失败回滚**验证。
- **顺带**：修完你就多了一个能讲的细节 ——「undo_log 必须建在业务库而不是 Seata 库，因为回滚要和业务写在同一个本地事务里」。这是区分"用过"和"配过"的分水岭。

### 2. 秒杀「先查后扣」两步非原子，全靠一把全局锁兜住

`SeckillOrderServiceImpl` 的逻辑是：`opsForHash().get` 判 `storage &lt; num` → 再 `opsForHash().increment(id, -num)`。这两步中间有窗口，本身会超卖。现在没出问题，是因为外面套了 Redisson 锁 —— 而这把锁的 key 是**固定字符串** `"seckill-order-lock"`，意味着**所有商品的所有秒杀请求全局串行**，秒杀被做成了单线程队列。

- **怎么问**：「你这把锁的粒度是什么？两个不同商品的秒杀会互相阻塞吗？」「不用锁能不能防超卖？」
- **怎么修（两步，都不难）**：
  1. 锁 key 改成 `seckill-order-lock:{goodsId}`，粒度降到商品维度
  2. 更进一步：把「判库存 + 扣库存」写成一段 Lua 脚本用 `DefaultRedisScript` 执行，Redis 单线程保证原子，锁就能直接去掉
- **改完的话术增益**：这正好是「[[多节点争抢资源， Redis 分布式锁是怎么实现的？]] → 为什么 Lua 比分布式锁更优」的现成案例，从"我加了锁"升级成"我发现锁粒度错了并用 Lua 消掉了锁"，这是面试官爱听的那种迭代。

### 3. 幂等只有 Redis 一层，没有数据库兜底

防重复下单靠网关的 `OrderQueue:{username}:{id}` INCR + 2 分钟 TTL，返回 &gt; 1 判重复。但 `seckill_order` 表**只有主键，没有 `(username, goods_id)` 唯一索引**，也没有防重表。Redis 一抖（重启、主从切换丢数据、TTL 到期后用户重试），同一个人就能下两单。

- **怎么问**：「Redis 挂了你的幂等还成立吗？」—— 这是幂等题的标准杀招，几乎必问。
- **怎么修**：`ALTER TABLE seckill_order ADD UNIQUE KEY uk_user_goods (username, goods_id)`，然后在插入处 catch `DuplicateKeyException` 当成"已下单"正常返回。
- **话术**：「Redis 是**性能层**的挡板，挡掉 99% 的重复请求；唯一索引是**正确性层**的兜底，保证极端情况下也不会重。两层职责不同，不能只留一层。」

### 4. JWT 过期时间写错了三个数量级

`mall-util/mall-common/.../util/JwtUtils.java`：`EXPIRE_MS = 10000 * 2 * 60 * 60 * 1000L`。注释写的是 2 小时，实际算出来约 **2283 年** —— 多乘了个 10000，等于签发的是永久 token。同一个文件里 **SECRET 硬编码在源码**。

- **怎么问**：「token 多久过期？过期了怎么续？密钥怎么管理？」
- **怎么修**：`EXPIRE_MS = 2 * 60 * 60 * 1000L`；SECRET 挪到 Nacos 配置中心（项目本来就有配置中心，不用额外引组件）。
- **附带**：代码里已有 `refreshIfNeeded`，修完过期时间它才有意义，正好接上"无感刷新"的话术。

### 5. 登录密码明文 `equals` 比对

`mall-user-service/.../controller/UserInfoController.java:43` 直接拿明文密码比。这条不改，一旦被问到"用户表怎么存密码"就是硬伤，而且属于面试官眼里的常识性红线。

- **怎么修**：`spring-security-crypto` 的 `BCryptPasswordEncoder`（只引这一个包，不用引整个 Security）。项目里已经有 `mall-common` 的 MD5/AES 工具，但 MD5 加盐也比明文强得多 —— 至少改成加盐哈希。

## 两个"身份"层面的坦白事项

### 关于「个人独立项目」这个说法

`doc/` 下的 7 个章节文件是**课程教程口吻**的资料（"本章我们将…"），配图约 230 张，文件时间集中在 2019–2020 年，明显是跟着课程做的电商项目。你选了简历上写「个人独立项目」，这本身没问题 —— 大部分候选人的项目都源自教程，面试官也心里有数。但要守住两条线：

1. **不要主动说"完全原创"**。被直接问「这个项目是跟着什么资料做的吗」，就实话说「基础骨架参考了公开的电商项目，热点发现链路、网关鉴权这些是我自己补的」。硬撑"全原创"一旦被追问某个设计的取舍，答不上来比承认参考更伤。
2. **把"我加的部分"讲清楚**。你的护城河不是"我从零写了 7000 行"，而是"我能说清每个组件为什么在这、换掉会怎样、当前实现有什么缺陷"。这一页纸的价值就在这。

### 仓库不是 git 仓库

`C:\Users\q1948\Desktop\project\nozomi-mall` **没有 `.git`**，没有任何提交历史。这意味着：

- 简历上**不要写工期**（"耗时 3 个月"之类无从佐证）
- 面试官要求看 GitHub 时你没有东西给。建议：`git init` + 补一个像样的 README（架构图 + 启动步骤 + 技术选型说明）+ 推上 GitHub。这件事收益比修任何一个 bug 都高，因为它是**唯一能让面试官在面试前就看到你项目**的途径。
