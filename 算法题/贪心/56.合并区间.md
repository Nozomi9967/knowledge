# 56.合并区间（排序 + 单调封闭扫描）

> [!abstract] 题目
> 以数组 `intervals` 表示若干个区间的集合，其中单个区间为 `intervals[i] = [start_i, end_i]`。
>
> 请你合并所有重叠的区间，并返回一个不重叠的区间数组，该数组需**恰好覆盖输入中的所有区间**。
>
> 注意：端点相接也算重叠，`[1,4]` 与 `[4,5]` 要合并为 `[1,5]`；输入不保证有序，`[[4,7],[1,4]]` 也要能处理。

| 参数 | 范围 |
|------|------|
| intervals.length | 1 ~ 10^4 |
| intervals[i].length | == 2 |
| start_i、end_i | 0 ~ 10^4，且 start_i ≤ end_i |

**示例 1：**
```
输入：intervals = [[1,3],[2,6],[8,10],[15,18]]
输出：[[1,6],[8,10],[15,18]]
解释：[1,3] 和 [2,6] 重叠，合并为 [1,6]
```

**示例 2：**
```
输入：intervals = [[1,4],[4,5]]
输出：[[1,5]]
解释：端点相接视为重叠
```

## 核心思路

三句话：**按左端点升序排序 → 遍历，拿当前区间的左端点和结果集末尾区间的右端点比 → 够不到就新开一组，够到就把末尾组的右端点扩成 max。**

真正的难点不在这三句，而在"只跟末尾那一组比"凭什么合法。

结果集里可能已经攒了好几组，比如 `[[1,6], [8,10]]`。理论上新来的区间跟这里面**任何**一组都可能重叠，严格做法是拿它跟每一组都比一遍。但代码只拿它跟末尾的 `[8,10]` 比，`[1,6]` 看都不看——这个偷懒的正确性，全靠排序提供的单调封闭性撑住。

## 为什么必须按左端点排（单调封闭性）

用示例 1 `[[1,3],[2,6],[8,10],[15,18]]` 走一遍。排序后左端点是 1, 2, 8, 15，**单调不减**。

处理到 `[8,10]` 时，末尾组是 `[1,6]`，判断 `8 > 6` 不重叠，于是封存 `[1,6]`、新开一组。这一刻的推理是三步：

1. 当前区间左端点是 8，末尾组右端点是 6，中间有一段真空 `(6, 8)`。
2. 因为已按左端点排序，**后面所有待处理区间的左端点都 ≥ 8**——这是排序直接给的，不需要额外验证。
3. 要跟 `[1,6]` 重叠，左端点必须 ≤ 6。但后面所有左端点都 ≥ 8 > 6，**一个都不可能**。

所以 `[1,6]` 永久封闭，不是"大概不会再被碰到"，是数学上不可能。整个扫描过程沿数轴单向推进、永不回头：

```
        1----6      8---10        15---18
        └封闭┘      ↑当前
                 后续区间的左端点只可能落在这条线的右边 →
                 永远够不到 6 左边的东西
```

### 附带好处：重叠只需判一边

两个区间 `[a,b]`、`[c,d]` 重叠的完整条件是 `a ≤ d && c ≤ b`，本该判两个方向。但排序后已知 `a ≤ c`（末尾组左端点一定不大于当前区间左端点），于是 `a ≤ d` 自动成立，只剩 `c ≤ b`。这就是代码里 `lastArr[1] < arr[0]` 只写一个比较的原因。

### 反例：按右端点排 + 正序遍历会错

如果排序键换成右端点，还按原方向扫，第 2 步的推理就断了——按右端点排只保证 right 单调，**left 是乱序的**。

反例 `[[5,6],[1,2],[0,10]]`，按右端点升序排完是 `[1,2] [5,6] [0,10]`，左端点依次是 1, 5, **0**：

```
排序后：  [1,2]   [5,6]   [0,10]
左端点：    1       5        0     ← 不单调，最后这个往回缩了
```

- `[1,2]` 入结果
- `[5,6]`：`5 > 2` 不重叠 → 新开一组，结果 `[1,2] [5,6]`
- `[0,10]`：`0 ≤ 6` 重叠 → 与末尾合并成 `[0,10]`，结果 `[[1,2],[0,10]]`

但 `[0,10]` 明明也盖住了 `[1,2]`，正确答案是 `[[0,10]]`。根因是那个"很早开始、很晚结束"的长区间被排到了最后，而单趟扫描不会回头查更早的分组。此时"只跟末尾比"不再合法，你必须回头检查所有分组，算法退化成 O(n²) 还要另写合并逻辑。

## 完整 Java 代码

```java
class Solution {
    public int[][] merge(int[][] intervals) {
        List<int[]> result=new LinkedList<>();
        Arrays.sort(intervals,new Comparator<int[]>(){
            public int compare(int[] a,int[] b){
                return a[0]-b[0];
            }
        });
        for(int[] arr:intervals){
            if(result.size()==0){
                 result.add(arr);
                 continue;
            }
            int[] lastArr=result.get(result.size()-1);
            if(lastArr[1]<arr[0]){
                result.add(arr);
            }else{
                lastArr[1]=Math.max(lastArr[1],arr[1]);
                result.set(result.size()-1,lastArr);
            }
        }
        int[][] mResult=new int[result.size()][2];
        for(int i=0;i<result.size();i++){
            mResult[i]=result.get(i);
        }
        return mResult;
    }
}
```

两处可以更干净（不影响 AC，原代码保留不动）：

- `result.set(result.size()-1, lastArr)` 可以删。`lastArr` 拿到的是同一个数组引用，改它就已经改了结果集里的对象，回写是多余的。
- `a[0]-b[0]` 在本题端点 ≤ 10^4 的约束下安全，但换成 `Integer.compare(a[0], b[0])` 是更稳的习惯，避免负数相减溢出。

## 变体：按右端点降序的镜像写法

上面说"按右端点排会错"，指的是排右端点却仍按左端点的方向扫。如果**排序方向和扫描方向配对**——按右端点升序排、然后倒着遍历（等价于按右端点降序处理）——是对的，但比较和合并逻辑必须一起镜像过来。

此时右端点单调不增，把封闭性推理照镜子：当前区间的右端点比末尾组的**左**端点还小 → 中间有真空 → 后面所有右端点都 ≤ 当前右端点 → 都够不到该组左端点 → 永久封闭。方向从"往右推进不回头"变成"往左推进不回头"。

数学上这就是数轴翻转 `x → -x`：区间 `[l, r]` 变成 `[-r, -l]`，"按右端点降序"就成了"按左端点升序"，合并操作在翻转下不变。所以它是原算法严格的镜像，正确性同源。

必须同步改的三处：

| 位置 | 左端点升序（原版） | 右端点降序（镜像版） |
|------|------------------|-------------------|
| 判不重叠 | 末尾.right 小于 当前.left | 当前.right 小于 末尾.left |
| 合并时更新 | 末尾.right = max(末尾.right, 当前.right) | 末尾.left = min(末尾.left, 当前.left) |
| 自动成立的那半边 | 末尾.left ≤ 当前.right | 当前.left ≤ 末尾.right |

直觉：原版是"组不断往右长"，维护右端点的 max；镜像版是"组不断往左长"，维护左端点的 min。反着遍历却还在更新右端点 max，就把组的生长方向搞错了。

```java
class Solution {
    public int[][] merge(int[][] intervals) {
        // 按右端点升序排，倒着遍历 == 按右端点降序处理
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));
        List<int[]> res = new ArrayList<>();
        for (int i = intervals.length - 1; i >= 0; i--) {
            int[] cur = intervals[i];
            if (res.isEmpty()) {
                res.add(new int[]{cur[0], cur[1]});
                continue;
            }
            int[] last = res.get(res.size() - 1);
            if (cur[1] < last[0]) {          // 够不到，真空成立 → 新开一组
                res.add(new int[]{cur[0], cur[1]});
            } else {                          // 重叠 → 往左扩
                last[0] = Math.min(last[0], cur[0]);
            }
        }
        Collections.reverse(res);             // 结果是降序的，翻回升序
        return res.toArray(new int[res.size()][]);
    }
}
```

同一个反例 `[[5,6],[1,2],[0,10]]` 验证：排序后 `[1,2] [5,6] [0,10]`，倒序处理 `[0,10] → [5,6] → [1,2]`。

- `[0,10]` 入组
- `[5,6]`：`6 < 0` 不成立 → 重叠，`min(0,5)=0`，组仍是 `[0,10]`
- `[1,2]`：`2 < 0` 不成立 → 重叠，`min(0,1)=0`，组仍是 `[0,10]`

结果 `[[0,10]]`，正确。差别在于长区间 `[0,10]` 被排到了**最前面**，先立住组，后面的短区间只能往里并；正序时它最后才出现，前面的组已经错误封闭了。

> [!warning] 两个反例是手推验证的，未在 LeetCode 实跑
> 镜像版结尾的 `Collections.reverse` 是为了输出升序。官方题解返回的是升序结果，判题是否顺序无关未确认，加上更保险。

**实践建议：** 这版能过但没人这么写——既然它本质是左端点升序的镜像，你多付一次 `reverse`、多一层"方向要反过来想"的心智负担，换不到任何收益。它的价值是把一件事讲透了：**排序方向和扫描方向必须配对，配对了才有单调封闭性。** 排右端点本身不错，错在排了右端点却按左端点的方向扫。

## 复杂度

- 时间：O(n log n)，瓶颈在排序，扫描是 O(n)
- 空间：O(n) 存结果（不计排序栈空间）

## 易错点

1. **必须按左端点排，不是右端点** → 右端点排序不保证左端点单调，长区间会排到后面往回吞掉已封闭的分组（反例 `[[5,6],[1,2],[0,10]]`）
2. **比较基准是结果集末尾的「已合并」区间，不是原数组里的前一个元素** → 反例 `[[1,10],[2,3],[4,5]]`：轮到 `[4,5]` 时拿原数组前一个 `[2,3]` 比会判成不重叠、多输出一段；拿结果末尾的 `[1,10]` 比才能正确吸收。合并会让右端点变大，基准必须是合并后的状态
3. **合并时右端点取 max，不能直接赋当前值** → 反例 `[[1,10],[2,6]]`：直接赋会把 10 缩成 6
4. **端点相接算重叠** → 判新开一组的条件是 `末尾.right < 当前.left`（严格小于），这样 `[1,4]` 与 `[4,5]` 会正确合并；写成 `<=` 就漏了
5. **不要在遍历中往结果集里塞输入数组的引用后又去改它**，除非明确接受修改入参（原代码 `result.add(arr)` 后 `lastArr[1]=...` 会改到 `intervals` 的子数组，本题无副作用，但换个上下文可能踩坑）

## 面试话术

1. **一句话讲思路？** → 先按左端点升序排序，然后一趟扫描：维护一个结果集，每来一个区间就看它的左端点能不能碰到结果集末尾那组的右端点，碰不到就说明中间断开了、新开一组，碰得到就把末尾组的右端点扩成两者的 max。整体是排序主导的 O(n log n)。
2. **为什么只跟末尾一组比就够了，不用跟前面所有组比？** → 这是排序换来的。因为左端点单调不减，一旦当前区间的左端点已经越过了末尾组的右端点，后面所有区间的左端点都只会更大，就更碰不到那一组了，所以那组可以永久封闭。这个单调封闭性把"可能和任意一组重叠"的二维问题压成了单向扫描。
3. **能不能按右端点排？** → 直接换排序键不行。按右端点排只保证右端点单调，左端点是乱序的，一个很早开始很晚结束的长区间会被排到最后，往回盖住已经封闭的分组。我可以举个反例：`[[5,6],[1,2],[0,10]]` 排完是 `[1,2] [5,6] [0,10]`，扫描时 `[1,2]` 已经被封掉了，但 `[0,10]` 其实盖住它，答案就错了。除非把扫描方向也反过来、改成比左端点、合并时取 min，那是原算法的镜像版本，能过但没必要。
4. **排序为什么能让重叠判断只写一个比较？** → 判两个区间重叠本来要 `a ≤ d && c ≤ b` 两个方向，排完序之后 `a ≤ c` 天然成立，其中一半就自动满足了，只剩一个比较。
5. **能不能不排序做到更快？** → 一般不行，合并区间的下界就卡在排序上。除非端点范围很小可以用桶/计数排序做到 O(n + C)，本题端点只到 10^4，理论上可以，但常数和空间不划算。
