## JVM的内存模型介绍一下？

根据 JDK 8（Java 1.8）规范，JVM运行时内存包括：虚拟机栈、本地方法栈、堆、元空间、程序计数器**五个部分**

> 还有直接内存，属于操作系统的本地内存，也是可以直接操作的

![img](https://cdn.xiaolincoding.com//picgo/1713516291293-ce6ee4e7-c5a6-4395-9ee7-4ec1c014b206.webp)



## 简单介绍一下程序计数器？

程序计数器存储着当前线程所执行Java方法的字节码指令地址，生命周期与线程一致

如果执行的是native方法，程序计数器为undefined

> 由于 Native 方法由本地代码实现、不对应字节码，因此当线程执行 Native 方法时，程序计数器的值为空

程序计数器也是唯一一块不会发生任何栈溢出和堆溢出的区域





## 简单介绍一下虚拟机栈？

每个线程都有自己独立的虚拟机栈，生命周期与线程一致

每个方法在被调用时都会创建一个栈帧压入当前线程的栈，栈帧用于存储局部变量表、操作数栈、动态链接、方法出口等信息。方法执行完毕后，对应的栈帧出栈销毁

会出现栈溢出和堆溢出



## 简单介绍一下本地方法机栈？

与虚拟机栈类似，主要为native方法服务

在hotspot虚拟机中与虚拟机栈合二为一

会出现栈溢出和堆溢出



## 简单介绍一下堆？

堆是JVM中最大的一块内存区域，被所有线程共享，在虚拟机启动时被创建，用于存放对象实例

从内存回收角度，堆被分为新生代和老年代，新生代又分为Eden区和两个Survivor区
**当堆中没有内存完成实例分配，并且堆也无法扩展时，就会抛出OOM异常**

### 堆分为哪几部分？

Java 堆（Heap）是 JVM 内存管理中最重要的区域，主要用于存放对象实例和数组。从 GC 管理的角度分为以下两部分：

- **新生代（Young Generation）**：分为 Eden Space 和 Survivor Space。Eden 区是新生代中最大的区域（默认 Eden:S0:S1 = 8:1:1），大多数新创建的对象首先存放在这里。当 Eden 区满时，会触发一次 Minor GC。Survivor Spaces 分为两个相等大小的区域（S0 和 S1），在每次 Minor GC 后，存活下来的对象会被移动到其中一个 Survivor 空间，两个区域轮流充当对象的中转站。
- **老年代（Old Generation）**：经过一次或多次 Minor GC 仍存活的对象会被移动到老年代。老年代中的对象生命周期较长，Major / Full GC 发生的频率相对较低，但执行时间通常比 Minor GC 长。

> [!note] 术语：新生代 = 年轻代
> 「新生代（Young Generation）」和「年轻代」是**同一个区域的不同译法**，本文统一用「新生代」。下文若出现「年轻代」，指的是同一个东西。

> **注意：** 
> 元空间（Metaspace）从 Java 8 起替代了永久代，但它使用**本地内存**，不属于 Java 堆。
> 大对象（Humongous Objects）在 G1 中虽然占用堆内的 Humongous Region，但在逻辑上归属于老年代，并非独立分区。

### 如果有个大对象一般是在哪个区域？

大对象通常会直接分配到老年代。

新生代主要用于存放生命周期较短的对象，内存空间相对较小。如果将大对象分配到新生代，会很快导致新生代空间不足，频繁触发 Minor GC。每次 Minor GC 都需要进行对象的复制和移动操作，带来额外的性能开销。

大对象通常需要连续的内存空间，如果在新生代中频繁分配和回收大对象，容易产生内存碎片。老年代的空间相对较大，更适合存储大对象，有助于减少内存碎片的产生。



## 简单介绍一下方法区（元空间）？

在 JDK 8（Java 1.8）及以后的版本，方法区被元空间所取代，**使用本地内存**

用于存储已被虚拟机加载的类的元数据信息、常量、静态变量等数据

> [!info] 版本注记
> 「方法区存静态变量」是经典说法。JDK 7 起 static 字段本体迁到堆，JDK 8+ 挂在堆里的 Class 对象上（元空间只存类元数据，不含 static 字段值），详见 [[静态集合内存泄漏与类卸载详解#static 字段的位置变迁（JDK 7 / JDK 8）]]。

虽然方法区被描述为堆的逻辑部分，但有**非堆**的别名

方法区可以选择不进行垃圾回收

内存不足时会抛出OOM



## 简单介绍一下运行时常量池？

是方法区的一部分，用于存储编译器生成的各种字面量和符号引用，运行时也可加入新的常量，具有动态性

内存不足时会抛出OOM



## 简单介绍一下直接内存？

不是JVM运行时数据区的一部分，通过NIO类引入，是一种堆外内存，可以显著提高IO性能

直接内存的使用受本机总内存的限制

会抛出OOM





## JVM 堆与栈的区别

### 核心对比

| 维度       | 堆（Heap）            | 栈（Stack）                                                                                                                                                                                       |
| -------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **存储内容** | 对象实例、数组            | **栈帧（Stack Frame）**。<br><br>  <br><br>每个栈帧内部包含：<br><br>  <br><br>1. **局部变量表**（基本数据类型、对象引用）<br><br>  <br><br>2. **操作数栈**（入栈出栈的临时计算）<br><br>  <br><br>3. **动态连接**<br><br>  <br><br>4. **方法返回地址** |
| **线程共享** | ✅ 所有线程共享           | ❌ 每个线程独立一份                                                                                                                                                                                     |
| **生命周期** | 与 JVM 进程一致（启动时分配，退出时释放）    | 与线程一致（栈帧随方法调用创建，返回销毁）                                                                                                                                                                          |
| **大小**   | 通常较大，可动态扩展         | 较小，固定或有上限                                                                                                                                                                                      |
| **分配速度** | 较慢（需要 GC 参与）       | 极快（移动栈顶指针）                                                                                                                                                                                     |
| **异常**   | `OutOfMemoryError` | `StackOverflowError`                                                                                                                                                                           |

------

### 堆（Heap）

存放所有 `new` 出来的对象，是 GC 的主战场：

```java
// person 对象本身存在堆上
Person person = new Person("Nozomi");
```

堆的内部结构（以 G1 之前的经典分代为例）：

```
┌─────────────────────────────────────────┐
│                  堆                      │
│  ┌──────────────────┐  ┌─────────────┐  │
│  │    新生代         │  │   老年代     │  │
│  │  Eden | S0 | S1  │  │             │  │
│  └──────────────────┘  └─────────────┘  │
└─────────────────────────────────────────┘
```

- **新生代**：新对象先分配在 Eden 区，Minor GC 后存活的晋升到 Survivor
- **老年代**：长期存活的对象，触发 Major GC / Full GC

------

### 栈（JVM Stack）

每个线程私有，由**栈帧（Stack Frame）**组成，每次方法调用压一帧：

```
┌──────────────────────────┐
│   栈帧：methodC()         │  ← 栈顶（当前执行）
├──────────────────────────┤
│   栈帧：methodB()         │
├──────────────────────────┤
│   栈帧：methodA()         │
├──────────────────────────┤
│   栈帧：main()            │  ← 栈底
└──────────────────────────┘
```

每个栈帧包含：

- **局部变量表**：基本类型值 + 对象引用（注意：引用在栈，对象在堆）
- **操作数栈**：执行字节码指令的临时工作区
- **动态链接**：指向运行时常量池的方法引用
- **返回地址**：方法执行完返回到哪里

------

### 一个例子看清两者关系

```java
public void process() {
    int count = 10;              // count 在栈上
    String name = "Nozomi";      // name 引用在栈，"Nozomi" 对象在堆
    Person p = new Person(name); // p 引用在栈，Person 对象在堆
}
栈                        堆
┌───────────────┐         ┌──────────────────┐
│ count = 10    │         │ String "Nozomi"   │
│ name ─────────┼────────▶│                  │
│ p ────────────┼──┐      └──────────────────┘
└───────────────┘  │      ┌──────────────────┐
                   └─────▶│ Person 对象       │
                          └──────────────────┘
```

### 常见面试延伸点

- **逃逸分析**：JIT 编译器分析对象是否"逃逸"出方法，若未逃逸可能直接在栈上分配（Stack Allocation），绕过堆，减少 GC 压力
- **-Xmx**（e**X**tended **M**emory **Ma**ximum）：最大堆内存
- **-Xms**（e**X**tended **M**emory **S**tart）：初始堆内存
- **-Xss**（e**X**tended **S**tack **S**ize）：每个线程栈大小
- **-Xmn**：**新生代**（Young / New）大小，n = new。设了它，老年代大小 = `-Xmx` − `-Xmn`
- **`-XX:SurvivorRatio=n`**：**Eden 与单个 Survivor 的比值**，即 `Eden : 单个 Survivor = n : 1`；而新生代 = Eden + S0 + S1
- 除了 JVM Stack，还有**本地方法栈（Native Method Stack）**，服务于 `native` 方法调用

> **Eden 大小计算（高频笔试题）**：设 `-Xmn500M -XX:SurvivorRatio=3`，则 `Eden : S0 : S1 = 3 : 1 : 1`，新生代共 5 份，每份 `500M ÷ 5 = 100M` → **Eden = 3 × 100M = 300M**，S0 = S1 = 100M。
> ⚠️ 常见错误：把 `SurvivorRatio=3` 当成"Eden : 两个 Survivor 之和"，实际是 Eden 与**单个** Survivor 之比。`-Xms` / `-Xmx` / `MaxPermSize` / GC 参数都**不影响**这个计算。





## 栈中存的到底是指针还是对象？

在VM内存模型中，栈（Stack）主要用于管理线程的局部变量和方法调用的上下文，而堆（Heap）则是用于存储所有类的实例和数组。
当我们在栈中讨论"存储"时，实际上指的是存储基本类型的数据（如int，double等）和对象的引用，而不是对象本身。
这里的关键点是，栈中存储的不是对象，而是对象的引用。也就是说，当你在方法中声明一个对象，比如Myobjectobj= newMyobject（）；，这里的obj实际上是一个存储在栈上的引用，指向堆中实际的对象实例。这个引用是一个固定大小的数据（例如在64位系统上是8字节），它指向堆中分配给对象的内存区域。





> [!faq]- Eden:Survivor是8:2，假如Eden满了，然后MinorGC，Survivor也装不下啊?
>
> 你直击了 Java 堆内存管理中**最核心、最经典**的一个矛盾点！
>
> 你的推导完全符合直觉：Eden 是 80%，两个 Survivor 各占 10%。如果 Eden（80%）全满了，而且里面**绝大多数对象都活着**，那哪怕把两个 Survivor 捏在一起（20%）也绝对装不下。
>
> JVM 团队当然也考虑到了这一点。为了解决这个“装不下”的问题，JVM 设计了两个非常核心的机制：**弱代假设（Weak Generational Hypothesis）** 和 **分配担保机制（Handle Promotion Failure）**。
>
> ### 1. 现实残酷但幸运：绝大多数对象“朝生夕死”
>
> JVM 的核心垃圾回收算法是建立在**弱代假设**之上的：**绝大多数对象存活的时间都极短（高达 98% 的对象在第一次 GC 时就会被回收）。**
>
> - **理想情况：** 别看 Eden 有 80%，当触发 Minor GC 时，往往只有不到 1%~2% 的对象还活着。这时候把它们复制到占比 10% 的 Survivor 区（比如 S1），空间是**绰绰有余**的。
> - **设计初衷：** 8:1:1 的比例不是一拍脑门定下来的，而是通过大量实际生产环境的对象生命周期数据测试出的黄金比例，目的是最大化 Eden 的吞吐量，同时不浪费太多内存给 Survivor。
>
> ### 2. 动真格的了：万一真的装不下怎么办？
>
> 你的担心在实际业务中一定会发生（比如突然来了个大并发请求，或者加载了一个大文件，导致 Eden 满的时候，大批对象都死不掉）。
>
> 这时候，JVM 会启动**分配担保机制（Garbage Collection Guarantee）**。
>
> 当 Minor GC 后，Survivor 区真的装不下那些好不容易活下来的对象时，它们**不会被强制挤在 Survivor 区**，而是会发生以下连锁反应：
>
> #### 方案 A：对象直接“跳级”到老年代（空间分配担保）
>
> 这是最常见的处理方式。Survivor 放不下的那部分对象，会直接被送进**老年代（Old Generation）**。老年代就像是一个“后备老大哥”，替新生代兜底。
>
> > **用一个通俗的比喻：**
> >
> > 新生代是**大学宿舍（Eden）**，毕业了（GC）大家都得搬出去。**S1 是租的单身公寓**。
> >
> > - **正常情况：** 毕业时大部分人都回老家了，只有少数几个人需要租房，S1 完全装得下。
> > - **特殊情况：** 今年大家都不想回老家，全想挤进 S1。S1 瞬间爆满，剩下的人没办法，只能直接去投奔已经在社会上立足的**父母家（老年代）**住。
>
> #### 方案 B：触发 Target Survivor Ratio（动态年龄判断）
>
> JVM 还有一个参数叫 `-XX:TargetSurvivorRatio`（默认 50%）。
>
> 如果在某次 GC 后，**同龄的对象**（或者从小到大累加的对象）体积超过了 Survivor 空间的 **50%**，那么为了防止 Survivor 彻底被挤爆，JVM 会把年龄大于或等于该年龄的对象**提前晋升到老年代**，主动给 Survivor 腾地方。
>
> ### 3. 如果连老年代也装不下呢？
>
> 如果新生代发生了 Minor GC，想把装不下的对象送往老年代，结果发现**老年代也满了，或者放不下这么多对象**，那就会触发终极手段：
>
> 1. **触发 Full GC**：JVM 会暂停一切（Stop The World），对整个堆内存（新生代 + 老年代）进行一次彻彻底底的大扫除，尝试释放老年代的空间。
> 2. **抛出 OOM（Out Of Memory Error）**：如果 Full GC 完之后，老年代还是没有足够的空间来接收这些从新生代挤过来的对象，JVM 就会彻底罢工，抛出著名的 `java.lang.OutOfMemoryError: Java heap space`。
>
> ### 总结
>
> - **常态下：** 因为 90% 以上的对象会死掉，10% 的 Survivor 足够用。
> - **极端下（装不下时）：** 触发**分配担保机制**，存活对象绕过 Survivor，直接进入老年代。
> - **老年代也装不下：** 触发 Full GC $\rightarrow$ 失败则 OOM。
>
> 你有遇到过因为这种大对象直接晋升老年代，导致老年代频繁触发 Full GC 的线上问题吗？





## 程序计数器的作用，为什么是私有的？

程序计数器的作用是记录当前线程下一条要执行的字节码指令地址，这样在线程切换后，线程还能从上次暂停的位置继续执行。
因为 Java 支持多线程，每个线程执行的代码位置都可能不同，所以程序计数器必须是线程私有的，避免线程之间互相影响。





## 方法区中的方法的执行过程？

当程序中对象或类直接调用某个方法时
首先，JVM会根据方法的符号引用找到实际的方法地址
接着，JVM会在当前线程的Java虚拟机栈中为该方法分配一个新的栈帧，用于存储局部变量表、操作数栈、动态链接、方法出口等信息

然后，执行方法中的字节码指令，方法执行结束后，可能会返回一个结果给调用者，并清理当前栈帧，恢复调用者的执行环境





## 方法区中有哪些东西？

**方法区用于存储已被虚拟机加载的类型信息、常量、静态变量、运行时常量池、即时编译器编译后的代码缓存等**



## 字符串常量池 vs 运行时常量池

### 关系图

```
方法区（JVM 的逻辑概念）
 ├── JDK 6 及之前：PermGen（永久代）
 │    └── 物理上：JVM 内部划出的独立内存（受 MaxPermSize 限制，易 OOM）
 │    └── 包含：运行时常量池、字符串常量池（都在里面）
 │
 ├── JDK 7：PermGen（仍在），但字符串常量池被提前移出 → 放入 JVM 堆
 │    └── 运行时常量池仍在 PermGen；字符串常量池独立于方法区，在堆中管理
 │
 └── JDK 8+：PermGen 被移除，改为 Metaspace（元空间）
      └── 物理上：直接使用操作系统的本地内存（Native Memory，受物理内存限制）
      └── 包含：运行时常量池（每个类一份，包含字面量、符号引用）

字符串常量池（全局共享）
 └── JDK 7 起已在 JVM 堆中（-XX:StringTableSize 可调，默认 60013），JDK 8+ 保持不变
```

> [!abstract] 方法区 vs 元空间的关系
> **方法区**是 JVM 规范定义的**逻辑概念**（接口），规定了它必须存储什么（类信息、运行时常量池、静态变量等），但不规定怎么实现。
>
> **PermGen（永久代）** 和 **Metaspace（元空间）** 都是 HotSpot JVM 对方法区的具体**物理实现**（实现类）：
> - JDK 7 及之前 → 实现类是 PermGen（JVM 堆内存中划出一块独立区域，受 `-XX:MaxPermSize` 限制）
> - JDK 8+ → 实现类换成 Metaspace（直接使用操作系统的本地内存，不再受 JVM 堆大小限制）
>
> 通俗理解：方法区是"需求文档"，PermGen 和 Metaspace 是"两版实现方案"——JDK 8 就是把旧方案（PermGen）下架，换上了新方案（Metaspace）。

两者是**包含关系**：字符串常量池是一个独立的全局结构，运行时常量池中的字符串字面量引用会指向它。


### 对比


#### 版本变迁对比

| 区域     | JDK 6 | JDK 7 | JDK 8+     |
| ------ | ----- | ----- | ---------- |
| 运行时常量池 | 永久代   | 永久代   | Metaspace  |
| 字符串常量池 | 永久代   | **堆**  | **堆**      |

|          | 运行时常量池（Runtime Constant Pool）    | 字符串常量池（String Table / String Pool） |
| -------- | -------------------------------- | ---------------------------------- |
| **作用域**  | 每个类一份                            | JVM 全局只有一份                         |
| **存储内容** | 类版本、字段/方法/接口信息、符号引用、字面量（含字符串字面量） | 纯字符串字面量 + `intern()` 存入的对象         |
| **所属关系** | 方法区的一部分（逻辑概念）                    | 运行时常量池中分离出来的区域                     |
| **位置变迁** | JDK6 在 PermGen → JDK8+ 在 Metaspace（本地内存） | JDK7 从 PermGen 迁到堆（独立管理）           |
| **主要用途** | 类加载时解析符号引用                       | 字符串复用，减少内存开销                       |

### 面试话术

> 运行时常量池是按类隔离的，每个类加载后都会生成一份；而字符串常量池是全局共享的，所有类共用一张 String Table。JDK7 之前字符串常量池在 PermGen 里，容易 OOM；JDK7 之后挪到了堆，**JDK8 移除了 PermGen 改为 Metaspace，但字符串常量池仍然留在堆中**，不受元空间大小限制。



---

### 位置变迁补充

- **运行时常量池**：JDK6 在 PermGen → JDK8+ 在 Metaspace（**本地内存**，不在堆）
- **字符串常量池**：JDK6 在 PermGen → JDK7 移到堆（`-XX:StringTableSize` 可调，默认 60013）→ JDK8+ 不变，仍在堆
- **类信息（元数据）**：JDK8+ 存在 Metaspace（本地内存），不再受 JVM 堆大小限制





## String s1="abc"和String s2=new String("abc")的区别

![images\image-20260222192252534](C:\Users\q1948\Desktop\八股\images\image-20260222192252534.png)


### **核心区别：创建对象的个数和内存位置不同**

`String s1 = "abc"` 只会在字符串常量池中创建（或复用）一个对象，而 `String s2 = new String("abc")` 会在堆内存中 new 出一个新对象，同时还会检查常量池中是否有 "abc"，没有则在常量池中也放一份。

---

### **详细对比**

**1. 内存位置不同**

- **`String s1 = "abc"`**：赋值号右边的是字符串字面量，JVM 会先去字符串常量池（String Pool）中查找是否已存在 "abc"。如果存在，直接返回该引用；如果不存在，则在常量池中创建一个对象并返回引用。所以 `s1` 指向的是常量池中的对象。
- **`String s2 = new String("abc")`**：`new` 关键字一定会在堆内存中创建一个新的 String 对象，`s2` 指向的是堆中这个新对象。同时，构造函数的参数 "abc" 也是字面量，JVM 同样会检查常量池——如果没有则放入常量池。

**2. 创建对象的个数不同**

这是面试官最常追问的点：

- `String s1 = "abc"`：如果常量池中已有 "abc"，创建 **0** 个新对象；如果没有，创建 **1** 个（在常量池中）。
- `String s2 = new String("abc")`：如果常量池中已有 "abc"，创建 **1** 个新对象（堆中）；如果没有，创建 **2** 个对象（1 个在常量池，1 个在堆）。

可以理解为：`new String("abc")` = 字面量 "abc" 的处理逻辑（可能 0 或 1 个对象）+ 堆中 new 出的 1 个对象。

**3. `==` 与 `equals()` 的结果不同**

```java
String s1 = "abc";
String s2 = new String("abc");

System.out.println(s1 == s2);        // false，引用不同（一个指向常量池，一个指向堆）
System.out.println(s1.equals(s2));  // true，内容相同
System.out.println(s1 == s2.intern()); // true，intern() 返回常量池中的引用
```

`==` 比较的是引用地址，`equals()` 比较的是字符串内容。`s1` 和 `s2` 是两个不同的对象，所以 `==` 为 false；但内容都是 "abc"，所以 `equals()` 为 true。

---

### **底层原理延伸：字符串常量池**

从 JDK 1.7 开始，字符串常量池从方法区（永久代）移到了堆内存中，但它的作用没有变——它是一个类似哈希表的结构，用于复用字符串字面量，避免相同内容的字符串重复创建，从而节省内存。

常量池中存的是字符串对象的引用（JDK 1.7+），而不是对象本身。当我们调用 `s2.intern()` 时，它会查找常量池中是否存在内容为 "abc" 的字符串，如果存在就返回该引用，如果不存在就把当前字符串加入常量池并返回引用。这也是为什么 `s1 == s2.intern()` 为 true。

---

### **面试加分回答建议**

如果面试官追问"为什么要有字符串常量池"，可以这样回答：

字符串在 Java 中是不可变对象，使用频率极高。常量池的设计是为了**复用相同内容的字符串对象，减少内存开销**。当多处使用 "abc" 时，它们共享同一个对象，而不是各自创建一份。这也是为什么不推荐用 `new String()` 创建字符串——它会破坏这种复用机制，额外消耗堆内存。

总结一句话：**字面量赋值走常量池复用，`new` 走堆内存新建，二者引用不同但内容相同。**

---

### **追问：常量池里的 "abc" 应该叫什么？字面量？字符串？**

准确的说法：**它叫"字符串常量池中的 String 对象"（被驻留的字符串，interned string）；而源码里写出的 `"abc"` 这种形式才叫"字面量"。** 三个层次不要混：

- **字面量（literal）**：源码里写出来的 `"abc"`，是语法层面的概念。
- **Class 文件常量池里的 `CONSTANT_String` / `CONSTANT_Utf8` 项**：编译后字节码里记录的符号信息——此时还**不是对象**。
- **字符串常量池（StringTable）里的对象**：类加载解析或执行 `ldc` 指令时，JVM 才创建（或查找）对应的 `String` 对象并登记进 StringTable——这个对象就是"被驻留（interned）的字符串"。

两个严谨点：

1. StringTable 本质是一张哈希表，**存的是对堆中 `String` 对象的引用**，对象本身在堆里（JDK 7 起；JDK 6 及以前在永久代）。所以"池里的对象"和"堆里的对象"不是两个区域——池中那个只是被 StringTable 引用、可复用；`new String("abc")` 创建的是另一个不在池里的对象。
2. 叫法建议：讲代码时说"字面量"；讲内存时说"字符串常量池中的 String 对象"或"驻留字符串（interned string）"；**不要说成"常量池里存的是字面量字符串本身"**——池里存的是引用，对象在堆中。

### 虚引用（PhantomReference）与 ReferenceQueue

四种引用里，虚引用要单独讲——因为它和另外三种的语义完全不同：**它的唯一作用是"通知"，拿不到对象本身**。

- `PhantomReference.get()` **永远返回 `null`**（设计如此，不给你拿到对象的机会）。
- 构造虚引用时**必须**传入一个 `ReferenceQueue`。当 GC 判定对象进入可回收流程时，JVM 会把这个 `PhantomReference` **入队（enqueue）**——程序从 `ReferenceQueue.poll()` / `remove()` 就能感知"某个对象即将 / 已被回收"。

| 对比项 | 弱引用 WeakReference | 虚引用 PhantomReference |
|--------|---------------------|------------------------|
| `get()` 返回 | 对象（未回收时）或 null | **永远 null** |
| 是否阻止回收 | 否 | 否 |
| 是否必须配 ReferenceQueue | 可选 | **必须** |
| 用途 | 缓存、WeakHashMap | **回收通知**（清理堆外资源等） |

**典型用途**：`DirectByteBuffer` 的 `Cleaner`（本质是 `PhantomReference` 的子类）就是靠它安排堆外内存释放——对象进入回收流程 → `Cleaner` 入队 → 由 `Reference Handler` 线程执行清理（`Unsafe.freeMemory`）。

> [!warning] "收到通知 ≠ 堆外内存此刻已释放"
> 虚引用给你的是**"对象进入回收流程"的通知**，不是"内存已经释放"的保证。清理动作（如 `freeMemory`）是**收到通知之后、由专门的 Reference Handler 线程异步执行**的，存在时间差。所以别把 `ReferenceQueue` 出队当成"内存已归还"的信号。（堆外回收细节见 [[DirectByteBuffer与堆外内存回收]]）






## **弱引用了解吗?举例说明在哪里可以用?**

Java中的弱引用是一种引用类型，它不会阻止一个对象被垃圾回收

 在Java中，弱引用是通过Java.lang.ref.WeakReference类实现的。弱引用的一个主要用途是创建非强制性的对象引用，这些引用可以在内存压力大时被垃圾回收器清理，从而避免内存泄露。 

弱引用的使用场景： 

- 缓存系统：弱引用常用于实现缓存，使用弱引用来维护缓存，可以让JVM在需要更多内存时自动清理这些缓存对象。

- 对象池：在对象池中，弱引用可以用来管理那些暂时不使用的对象。当对象不再被强引用时，它们可以被垃圾回收，释放内存。 

- 避免内存泄露：当一个对象不应该被长期引用时，使用弱引用可以防止该对象被意外地保留，从而避免潜在的内存泄露







## **内存泄漏和内存溢出的理解？ 

**内存泄露：内存泄漏是指程序在运行过程中不再使用的对象仍然被引用，而无法被垃圾收集器回收，从而导致可用内存逐渐减少。**

内存泄露常见原因： 

- 静态集合：使用静态数据结构（如HashMap或ArrayList）存储对象，且未清理。详见 [[静态集合内存泄漏与类卸载详解]]

- 事件监听：短生命周期对象注册了监听器，但销毁时未取消注册，长生命周期的事件源仍持有该对象引用，GC 无法回收。典型场景：一个请求级别的对象把自己注册到单例的事件管理器上，请求结束后忘记移除，单例的静态集合一直持有它。详见 [[事件监听内存泄漏详解]]

```java
// ❌ 泄漏：SingleManager 是单例（长生命周期），持有 ShortLived 对象的引用
public class SingleManager {
    private static List<EventListener> listeners = new ArrayList<>();
    public static void register(EventListener l) { listeners.add(l); }
}
// 请求进来时注册，请求结束后未移除 → SingleManager 静态集合一直持有 ShortLived 对象

// ✅ 修复：用弱引用持有，GC 可回收已无其他引用的监听器
// 长生命周期监听器（如单例 Bean）同时被 Spring 容器强引用，不会被 GC
// 短生命周期监听器（请求级对象）请求结束后无其他强引用，GC 可回收
private static List<WeakReference<EventListener>> listeners = new ArrayList<>();
```

- 线程：未停止的线程可能持有对象引用，无法被回收。 

**内存溢出：内存溢出是指Java虚拟机（JVM）在申请内存时，无法找到足够的内存，最终引发OutOfMemoryError。这通常发生在堆内存不足以存放新创建的对象时。 

内存溢出常见原因： 

- 大量对象创建：程序中不断创建大量对象，超出JVM堆的限制。 
- 持久引用：大型数据结构（如缓存、集合等）长时间持有对象引用，导致内存累积。 
- 递归调用：深度递归导致栈溢出。详见 [[栈溢出导致OOM的深层机制]]





## JVM内存结构有哪几种内存溢出的情况？

![images\image-20260222201336562](C:\Users\q1948\Desktop\八股\images\image-20260222201336562.png)

### ⭐ 元空间溢出（Metaspace OOM）

当 JVM 抛出 **`java.lang.OutOfMemoryError: Metaspace`** 时，说明元空间发生了内存溢出。

元空间主要用于存储类的元数据（如类结构、方法信息、常量池等）。
 如果系统中加载的类过多，或者类无法被回收，就可能导致元空间不断膨胀，最终发生溢出。

常见原因包括：

1. **系统加载的类数量过多**
    例如大型系统、微服务或使用了大量第三方框架，导致类元数据占用空间较大。
2. **动态生成类过多**
    比如使用 CGLIB、JDK 动态代理、ASM、ByteBuddy 等技术频繁生成代理类，如果这些类没有被卸载，就会持续占用元空间。
3. **类加载器泄漏（ClassLoader Leak）**
    某些应用（如 Web 容器热部署）中，如果旧的类加载器没有被正确回收，会导致对应加载的类元数据也无法释放，从而引发元空间 OOM。







### 各内存区域 → 错误类型 → 触发场景（汇总）

| 内存区域 | 错误类型 | 错误信息示例 | 触发场景 |
|----------|---------|-------------|---------|
| 堆（Heap） | OOM | `java.lang.OutOfMemoryError: Java heap space` | 对象过多 / 泄漏，GC 后仍放不下新对象 |
| 虚拟机栈（单线程） | StackOverflowError | `java.lang.StackOverflowError` | 递归过深 / 栈帧过大，超出 `-Xss` |
| 虚拟机栈（创建线程） | OOM | `...: unable to create new native thread` | 线程过多，native memory 不足以分配新线程栈 |
| 元空间（Metaspace） | OOM | `...: Metaspace` | 加载 / 动态生成类过多、ClassLoader 泄漏导致类无法卸载 |
| 直接内存（Direct Memory） | OOM | `...: Direct buffer memory` | `DirectByteBuffer` 分配超过 `-XX:MaxDirectMemorySize` |
| 程序计数器 | 永不 OOM / SOF | — | 唯一不会发生任何内存溢出的区域 |

> 记忆：**除了程序计数器"永不 OOM"，其余区域各有对应的 OOM / SOF**。栈有两种形态——单线程是 SOF（纵向越界），创建线程失败是 OOM（横向内存不足），别混。各区域细节见 [[StackOverflowError与OutOfMemoryError（虚拟机栈）]]、[[DirectByteBuffer与堆外内存回收]]。

## 有具体的内存泄漏和内存溢出的例子么请举例及解决方案?

### 1. 静态属性导致内存泄露

大量使用 static 静态变量会导致内存泄露。静态属性的生命周期通常伴随着应用整个生命周期（除非 ClassLoader 符合垃圾回收的条件）：

```java
public class StaticTest {
    public static List<Double> list = new ArrayList<>();
    public void populateList() {
        for (int i = 0; i < 10000000; i++) {
            list.add(Math.random());
        }
    }
    public static void main(String[] args) {
        new StaticTest().populateList();
        // list 是静态的，方法结束后仍不会被回收
    }
}
```

**解决**：减少静态变量；使用单例时尽量采用懒加载。

### 2. 未关闭的资源

创建数据库连接、输入流等资源后忘记关闭，会阻塞内存导致 GC 无法清理。特别是程序发生异常时没有在 finally 中进行资源关闭。

**解决**：始终在 finally 中关闭资源；Java 7+ 可使用 try-with-resources。

### 3. 使用 ThreadLocal 导致内存泄漏

> [!info] 详见 [[ThreadLocal 深度解析与内存泄露笔记]] — 完整分析：弱 Key 设计辩证、Value 为何不能弱引用、线程池脏数据、面试答题套路

ThreadLocalMap 使用 ThreadLocal 的弱引用作为 key，当 ThreadLocal 被回收后，key 变为 null，但 value 仍被 `Thread Ref → Thread → ThreadLocalMap → Entry → value` 这条强引用链持有，无法回收。

**解决**：使用 ThreadLocal 的 `remove()` 方法；最好在 finally 块中调用：

```java
try {
    threadLocal.set(value);
    // ... 业务处理
} finally {
    threadLocal.remove();
}
```

### 4. 内存溢出 — 堆溢出（解决思路）

堆溢出（`java.lang.OutOfMemoryError: Java heap space`）的排查与解决：

1. **捕获快照**：通过 JVM 参数 
	`-XX:+HeapDumpOnOutOfMemoryError 
	`-XX:HeapDumpPath=./heapdump.hprof`自动生成堆快照
2. **分析快照**：使用 MAT 或 JProfiler 分析哪些对象占用大量内存
3. **根据原因处理**：
   - 内存泄漏 → 梳理引用链，清理无用引用（如静态集合、未关闭资源）
   - 内存不足 → 调整 `-Xms -Xmx` 扩大堆内存；从代码层面优化（分批处理、设置缓存过期策略）

### 5. 栈溢出的情况

栈溢出（`java.lang.StackOverflowError`）的常见场景：

- **无限递归调用**：没有正确终止条件的递归，栈帧不断累积直至溢出
- **单方法栈帧过大**：方法定义了大量局部变量或大数组

**解决**：
1. 排查递归逻辑，添加终止条件或改为迭代
2. 通过 `-Xss` 参数增大栈内存（注意：栈越大，可创建的线程数越少）
3. 减少方法内局部变量数量


## 类加载机制

### 类加载器有哪些？

- **启动类加载器（Bootstrap Class Loader）**：最顶层，负责加载 Java 核心类库。Java 8 加载 `rt.jar`，Java 9+ 加载 `lib/modules` 模块化镜像。由 C++ 实现，Java 层面没有对应 ClassLoader 对象。
- **扩展类加载器（Extension Class Loader）**（Java 8）/ **平台类加载器（Platform Class Loader）**（Java 9+）：负责加载扩展目录或平台模块中的类。
- **应用程序类加载器（Application Class Loader）**：负责加载 ClassPath 上的类，开发者默认使用的加载器。
- **自定义类加载器（Custom Class Loader）**：开发者可定制类的加载方式（网络、数据库、加密文件等）。

### 双亲委派模型是什么？有什么作用？

**定义**：当一个类加载器收到类加载请求时，先委派给父加载器去尝试加载，只有父加载器加载不了时，自己才会去尝试加载。

**作用**：
1. **保证类的唯一性**：避免同一个类被不同加载器重复加载
2. **保证安全性**：防止恶意代码自定义 `java.lang.String` 等核心类替换 JDK 核心类
3. **支持隔离和层次划分**：不同层级的类加载器服务于不同需求，职责清晰
4. **简化加载流程**：减少每个加载器需要处理的类数量

### 类加载过程（七个阶段）

类从被加载到卸载，生命周期包括以下阶段：

|概念|含义|
|---|---|
|**字节码文件（.class 文件）**|磁盘上的静态二进制文件，是编译产物|
|**class 文件字节流**|加载阶段读取到的二进制数据流，来源不限于文件|

1. **加载（Loading）**：通过类的全限定名获取二进制字节流，将静态存储结构转化为方法区运行时数据结构，生成 `java.lang.Class` 对象
2. **验证（Verification）**：确保 class 文件字节流符合 JVM 规范，不会危害虚拟机安全
3. **准备（Preparation）**：为静态字段分配内存并设置默认初始值（`static final` 且在**编译期可确定的常量** → 直接赋实际值，跳过零值；若值依赖方法调用等运行时计算 → 仍赋零值，留到初始化阶段 `<clinit>()` 中赋值）
4. **解析（Resolution）**：将常量池中的符号引用替换为直接引用
5. **初始化（Initialization）**：JVM 执行编译器自动生成的 `<clinit>()` 方法。该方法由编译器将类中所有**静态变量的赋值语句**和**静态代码块**按照它们在源码中出现的**顺序**依次收集而成，是类生命周期中真正对静态变量赋予程序员指定值的阶段。
6. **使用（Using）**：使用类或创建对象
7. **卸载（Unloading）**：类被卸载需同时满足：所有实例被回收、ClassLoader 被回收、Class 对象无引用

### 创建对象的过程

1. **类加载检查**：检查 new 指令的参数能否在常量池中定位到类的符号引用，并检查该类是否已被加载、解析和初始化
2. **分配内存**：在类加载检查通过后，为新生对象分配内存（大小在类加载完成后即可确定）
3. **初始化零值**：将分配到的内存空间初始化为零值（不包括对象头）
4. **设置对象头**：设置对象是哪个类的实例、指向类元数据的指针、哈希码、GC 分代年龄等信息
5. **执行 init 方法**：执行构造函数，按程序员的意图初始化对象


首先会在常量池中寻找类的符号引用，
然后检查该类是否被加载、链接、初始化
检查通过后会为该对象分配内存，并初始化零值，
接着给对象设置对象头，对象头内容包括：对象所属类名、指向类元数据的指针、哈希码、GC分代年龄，
最后执行构造函数







## 什么是垃圾回收？

垃圾回收是一种自动管理内存的机制，它负责自动释放程序不再引用的对象所占内存




## 什么会触发垃圾回收？

在 Java 中，垃圾回收（GC）的触发主要由 JVM 的内存区域使用情况和运行时事件决定。以下是几种主要场景：

### 1. Minor GC（新生代 GC）

当 **Eden 区空间不足以分配新对象**时，JVM 会发起 Minor GC。这是最频繁的垃圾回收操作。其核心机制如下：

- 新对象默认分配在 Eden 区。当 Eden 区满时，触发 Minor GC。
- 存活的对象会被复制到 Survivor 区（From 区或 To 区）。
- 经过多次 Minor GC 仍然存活的对象（达到晋升年龄阈值，默认 15），会被晋升到老年代。
- Minor GC 过程中 Survivor 区空间不足时，部分对象会通过"动态年龄判断"提前晋升到老年代。

> 值得注意的是，由于复制算法的存在，Minor GC 会产生"Stop-The-World"（STW）暂停，但由于新生代通常较小，停顿时间一般很短。

> [!info] "动态年龄判断"的精确条件
> 原文只写了"50%"，说全应是：当**单个 Survivor 区**（S0 或 S1 之一，**不是两块 Survivor 之和**）中，从最小年龄开始累加各年龄对象的大小，累加到某年龄时**该年龄及以上的对象大小总和超过这个 Survivor 容量的 50%**，那么 ≥ 该年龄的对象就**直接晋升老年代**，不必等到默认年龄 15。
>
> 目的：避免 Survivor 被大量"半老不死"的对象撑爆，导致存活对象频繁在两个 Survivor 区之间来回拷贝。

### 2. **Major GC（老年代回收）​**

Major GC 指的是**只回收老年代**的垃圾回收动作。这是一个相对模糊的术语，在实际收集器中，单独只回收老年代而不动新生代的场景很少。最典型的例子是 CMS 收集器（`-XX:+UseConcMarkSweepGC`），它的并发回收周期主要针对老年代进行，新生代不在这次回收范围内，因此接近"真正的 Major GC"语义。

### 3. **Full GC（全堆回收）​**

Full GC 是对整个堆（包括新生代和老年代，通常还含 Metaspace）的全面回收，代价最高，STW 停顿时间最长，是生产环境中要极力避免的。触发条件更为复杂，主要包括以下几种：

- **老年代空间不足**：当晋升到老年代的对象总大小超过老年代的剩余空间时触发（更严谨地说：是**晋升需求 > 老年代可用空间**，且不同收集器会按**历史晋升量做预估**，预估放不下即提前触发）。
- **Metaspace（元空间）空间不足**：JDK 8 以后，永久代被 Metaspace 取代。当加载的类元数据超出 Metaspace 大小限制时，会触发 Full GC 进行类卸载。
- **空间分配担保失败**：Minor GC 前检查老年代连续可用空间是否足够容纳所有新生代对象。若不足且不允许担保失败，则触发 Full GC。
- **CMS GC 的 Concurrent Mode Failure**：在使用 CMS 收集器时，若老年代在并发清理阶段前就被填满，会退化为 Serial Old 收集器，触发 Full GC。

### 4. 手动调用 System.gc()

调用 `System.gc()` 或 `Runtime.getRuntime().gc()` 会向 JVM 发出一个建议性的 Full GC 请求。**注意，这只是一个建议，JVM 有权决定是否执行**。生产环境中应尽量避免手动调用，可通过参数 `-XX:+DisableExplicitGC` 来屏蔽此类请求。

### 5. RMI 系统的分布式 GC

Java RMI（Remote Method Invocation）系统会周期性触发 `System.gc()`，用于清理远程对象引用。默认间隔为 1 小时，可通过以下参数调整：

```bash
-Dsun.rmi.dgc.server.gcInterval=3600000
-Dsun.rmi.dgc.client.gcInterval=3600000
```

### 6. 堆内存自适应调整

当使用 `-XX:+UseAdaptiveSizePolicy`（默认开启）时，JVM 会根据运行时情况动态调整各内存区域大小。若调整过程中需要收缩堆内存或重新平衡各代大小，可能间接触发 GC。

### **Major GC 与 Full GC（老年代及全堆回收）​**

这里需要纠正之前的写法。Major GC 和 Full GC **不是同一个概念**，应当分开理解。两者的核心区别在于**回收范围**：Major GC 只针对老年代，Full GC 则回收整个堆（新生代 + 老年代，通常还包括 Metaspace）。由于在实际收集器实现中，很多收集器回收老年代时会一并回收整个堆，导致这两个词常被混用，但概念上应当区分。

### 对象不可达作为回收前提

以上所有触发条件的根本目的，都是为了回收**不可达对象**（即从 GC Roots 出发无法到达的对象）。GC Roots 包括：

- 虚拟机栈中的局部变量表引用的对象
- **堆中 Class 对象上的类静态属性引用的对象**（即 static 变量，JDK 8 起 static 字段本体挂在堆里的 Class 对象上，详见 [[静态集合内存泄漏与类卸载详解#static 字段的位置变迁（JDK 7 / JDK 8）]]）
- 方法区（元空间）中常量引用的对象
- 本地方法栈中 JNI 引用的对象
- 活跃线程、同步锁持有的对象等

GC 通过可达性分析算法（Reachability Analysis）从 GC Roots 出发遍历对象引用图，未被访问到的对象即为"垃圾"，可被回收。

---

综合来看，面试中回答这道题的关键，在于清晰区分 **Minor GC** 与 **Full GC** 的不同触发场景，并理解各类触发条件的本质——都是某块内存区域耗尽或需要回收不可达对象时的被动响应机制。掌握这些细节，不仅能展示对 JVM 内存模型的深入理解，也能体现对系统性能调优的实际经验。

## 什么是垃圾回收算法，解决什么问题？

垃圾回收算法是解决**如何识别不再使用的对象、如何高效回收其占用内存、同时尽量减少对应用程序停顿影响**的一套执行方案。

### 标记清除算法的缺点

标记-清除算法有两个主要缺点：
1. **效率问题**：标记和清除过程的效率都不高
2. **空间问题**：清除之后会产生大量不连续的内存碎片，导致后续分配大对象时可能因没有足够连续空间而提前触发另一次 GC

### 为什么复制算法"分配高效"？（指针碰撞 vs 空闲列表）

两种分配方式的根本差别：

| 分配方式 | 怎么做 | 场景 |
|---------|--------|------|
| **指针碰撞（Bump the Pointer）** | 维护一个指针指向空闲区起点，分配时指针直接后移（O(1)） | 标记-复制、Serial/ParNew 的新生代 |
| **空闲列表（Free List）** | 遍历空闲链表，找一块足够大的连续空间（可能 O(n)） | 标记-清除、CMS 的老年代 |

**复制算法为什么能用指针碰撞**：每次 GC 把存活对象**复制到另一块空闲区并紧凑排列**，剩下的是一整块连续空闲区——没有碎片，所以分配新对象只需"指针后移"一次，无需管理碎片。

```
GC 前：                 GC 后：
[已分配|   空闲区   ]    [存活对象（紧凑）|   空闲区   ]
        ↑                                 ↑
    分配指针                        分配指针重置到这
```

**对比标记-清除**：不做整理，内存变成 `[A|缝隙|B|缝隙|C]`，分配新对象得**遍历空闲列表**找合适缝隙——碎片严重时可能遍历多次，甚至总空间够但没连续空间 → 提前触发 Full GC。

> 一句话：**复制算法无碎片 → 指针碰撞 O(1)；清除算法有碎片 → 空闲列表可能 O(n) 且浪费空间。** 这就是"复制分配高效、清除分配低效"的根本原因。

## 垃圾回收器有哪些

| 垃圾回收器                | 类型         | 作用域     | 使用算法          | 特点             |
| ------------------------- | ------------ | ---------- | ----------------- | ---------------- |
| Serial                    | 串行回收     | 新生代     | 复制算法          | 响应速度优先     |
| Serial Old                | 串行回收     | 老年代     | 标记整理算法      | 响应速度优先     |
| ParNew                    | **并行回收** | 新生代     | 复制算法          | 响应速度优先     |
| Parallel Scavenge         | 并行回收     | 新生代     | 复制算法          | 吞吐量优先       |
| Parallel Old              | 并行回收     | 老年代     | 标记整理算法      | 吞吐量优先       |
| CMS-Concurrent Mark Sweep | 并发回收     | **老年代** | 标记清除算法      | **响应速度优先** |
| G1-Gargage first          | **并发并行** | **新老**   | 复制算法&标记整理 | **响应速度优先** |

> 总结：在 JDK21 的现代环境下，主流选择是G1（默认）／ZGC／Parallel／Shenandoah；CMS 和ParNew已经退出历史舞台，面试里若被问到CMS，要能说清它为什么被移除（维护复杂+G1/ZGC已经能取代其大部分使用场景)。

> [!note] 算法别名
> - **标记整理算法 = 标记压缩算法**（Mark-Compact）—— 把存活对象向一端移动、压缩成连续内存
> - **复制算法 = 标记复制算法**（Copying）—— 存活对象复制到空闲区后，原区整体清空

### Minor GC、Major GC、Full GC 的区别

**Minor GC (Young GC)**
- **作用范围**：只针对年轻代（Eden + Survivor）
- **触发条件**：Eden 区空间不足时触发
- **特点**：发生频繁，回收效率高，暂停时间较短

**Major GC**
- **作用范围**：仅回收老年代（如 CMS 的并发老年代 GC）
- **触发条件**：老年代空间不足，或年轻代对象晋升速度过快

**Full GC**
- **作用范围**：对整个 Java 堆（年轻代 + 老年代）回收，并可能卸载元空间中的无用类
- **触发条件**：
  - **老年代空间不足**：当晋升到老年代的对象总大小超过老年代的剩余空间时触发
  - **空间分配担保失败**：Minor GC 前检查老年代连续可用空间是否足够容纳所有新生代对象，若不足且不允许担保失败则触发 Full GC
  - **Metaspace 不足**：加载的类元数据超出 Metaspace 大小限制时，触发 Full GC 进行类卸载
  - **CMS 的 Concurrent Mode Failure**：并发清理阶段前老年代被填满，退化为 Serial Old 收集器触发 Full GC
- **特点**：最昂贵的 GC 操作，STW 时间长，应尽量减少触发

---

### **为什么卸载类要从堆入手？​**

很多人困惑的点在于：Metaspace 空间不足时触发 Full GC，为什么动作是"遍历堆中对象引用"？堆和 Metaspace 不是两块独立的内存吗？

答案是：**Metaspace 本身没有独立的 GC 机制，它必须"蹭"一次堆的 Full GC，借机判断哪些 ClassLoader 已经死亡，从而连带释放对应的类元数据。​**

### **三者之间的引用链**

理解的关键是理清下面这条引用链：
```
GC Roots
  ↓ 可达？
ClassLoader 对象        ← 活在堆里
  ↑ 持有引用
Class 对象              ← 也活在堆里（java.lang.Class 实例）
  ↓ 对应
Metaspace 中的类元数据   ← 方法字节码、常量池、字段定义等

```


GC 的判断逻辑是**自下而上反推**的——先判断 ClassLoader 是否还活着，再决定 Metaspace 里的东西要不要留。

### **GC 实际做了什么**

Full GC 遍历堆对象引用时，本质上在做一件事：**判断堆里的 ClassLoader 对象是否仍然从 GC Roots 可达。​**

- 如果某个 ClassLoader 对象仍然可达 → 说明还在用 → 它加载的类元数据必须保留。
- 如果某个 ClassLoader 对象已经不可达 → 说明没人再持有它 → 沿着引用链往下推，它加载的所有 Class 对象也不可达 → Metaspace 中对应的类元数据就失去了存在意义 → 可以释放。

> [!tip] 为什么 ClassLoader 不可达 ⟹ Class 对象也不可达？
> 关键不在"ClassLoader 是否引用着 Class 对象"，而在**每个 Class 对象都强引用着自己的定义类加载器**（`Class.classLoader` 字段）。
>
> 于是任何能到达 Class 对象的引用路径（实例的 `.getClass()`、`Class.forName()` 的结果、其他类静态字段缓存的 `Xxx.class`），都会顺着这个反向引用继续延伸到 ClassLoader——**只要还有一个 Class 对象活着，它的 ClassLoader 就被连带活着**。
>
> 取逆否命题：ClassLoader 不可达 ⟹ 不存在任何仍可达的 Class 对象。实例存活也救不了——实例对象头里的类指针 → Class 对象 → ClassLoader，实例活着同样会把 ClassLoader 拖住。
>
> 这正是 JVM 规范把"类可被卸载"定义成"其定义类加载器不可达"的原因：这是一个**完备判据**，不存在"Class 对象被别处强引用、但 ClassLoader 已经没了"的漏网情况。

举个典型场景：热部署时，旧的 `WebAppClassLoader` 被替换掉，没人再引用它。下一次 Full GC 发现这个 ClassLoader 不可达，于是连带卸载它加载的所有类元数据，Metaspace 空间得以回收。

### **一句话总结**

Metaspace 没有"自己的 GC"，它依赖堆的 Full GC 来判断 ClassLoader 的生死。堆里 ClassLoader 不可达，是 Metaspace 元数据被释放的前提条件，而非反过来。

---



## 垃圾回收中的 STW（Stop-The-World）阶段

不同 GC 算法的 STW 情况不同，以下以常见实现为例。先分清两个概念：

- **算法**：标记-清除、标记-整理、复制 —— 定义"怎么回收"
- **收集器**：CMS、G1、ZGC —— 算法的具体实现，决定"怎么调度执行"

### 三种基础算法（传统实现全程 STW）

Serial、Serial Old 等传统收集器，执行以下算法时都是全程 STW：

| 算法 | 做法 | 碎片 | 备注 |
|------|------|:---:|------|
| 标记-清除（Mark-Sweep） | 标记存活对象 → 清除垃圾对象 | ✅ 有 | 不整理，越用越碎 |
| 标记-整理（Mark-Compact） | 标记 → 存活对象向一端移动 → 清除边界外 | ❌ 无 | 移动对象开销大，Serial Old 用 |
| 复制（Copying） | 存活对象复制到空闲区 → 原区整体清空 | ❌ 无 | 需留空闲区，空间利用率低 |

> [!warning] 别把"算法"和"收集器"混为一谈
> 标记-清除 / 标记-整理 / 复制说的是**算法**；CMS、G1 是**收集器**，是算法的具体实现，会把算法拆成多个阶段、部分并发执行——所以 CMS 虽然是标记-清除，但并不是全程 STW。

### CMS（Concurrent Mark Sweep）—— 标记-清除的并发实现

CMS 实现的仍是标记-清除算法（名字 Mark **Sweep** 就是它），区别在**调度**：把最耗时的标记和清除并发执行，只留两个短暂 STW 窗口。

| 阶段                         | 是否 STW      |
| ---------------------------- | ------------- |
| 初始标记（Initial Mark）     | ✅ STW（短暂） |
| 并发标记（Concurrent Mark）  | ❌ 并发        |
| 重新标记（Remark）           | ✅ STW（较短） |
| 并发清除（Concurrent Sweep） | ❌ 并发        |

代价：仍是标记-清除，只清除不整理 → 碎片化严重，Concurrent Mode Failure 时回退 Serial Old 做一次全停顿的标记-整理兜底。

### G1（Garbage First）—— 整体标记-整理 + 局部复制

经典表述：**G1 从整体上看基于标记-整理，从局部（两个 Region 之间）基于复制算法**——两者都不产生碎片。

| 阶段                            | 是否 STW |
| ------------------------------- | -------- |
| 初始标记（Initial Mark）        | ✅ STW    |
| 并发标记（Concurrent Mark）     | ❌ 并发   |
| 最终标记（Final Mark / Remark） | ✅ STW    |
| 筛选回收（Evacuation）          | ✅ STW    |

- **整体（标记-整理）**：G1 维护全局标记信息（SATB + Remembered Set），回收后存活对象落到连续区域，整体效果等同一次全局整理，不会越用越碎。
- **局部（复制）**：Evacuation 阶段把存活对象从源 Region **复制**到空闲 Region，拷完清空源 Region——这一步就是复制算法，也是"整理"的落地机制。

### ZGC / Shenandoah

设计目标是极低 STW，大部分阶段并发执行：

| 阶段            | 是否 STW              |
| --------------- | --------------------- |
| 初始标记根集合  | ✅ STW（极短，毫秒级） |
| 并发标记        | ❌ 并发                |
| 再标记 / 根修复 | ✅ STW（极短）         |
| 并发转移/压缩   | ❌ 并发                |

### 总结规律

几乎所有 GC 算法都无法避免以下两类 STW：

1. **初始标记根对象**：==需要一致的GC Roots快照==，必须 STW
2. **重新标记（Remark）**：==修正并发标记期间的漏标==，必须 STW

优化方向就是让这两次 STW 尽可能短，其余阶段与应用线程并发执行。







## 什么情况使用CMS、G1？



CMS：

如果需要一个低延迟的老年代垃圾回收器，可以使用CMS



G1：

G1垃圾回收器适用于 对内存碎片比较敏感、需要比较平衡的性能且大内存堆的场景

> *G1在提供较低停顿时间的同时，也保持了相对较高的吞吐量。*

> [!info]- 为什么 G1 适合大内存堆？
>
> 1. **Region 分块机制**：堆划分为 1~32MB 的等大 Region，每次只收集**部分 Region**，不扫描整个堆；堆越大、Region 越多，选择空间越大，越容易满足停顿时间目标
> 2. **可预测停顿**：`-XX:MaxGCPauseMillis`（默认 200ms）控制每次 GC 时间，通过历史数据计算每个 Region 的回收成本，只选取收益最高的 Region 集合
> 3. **无碎片问题**：G1 用**复制-压缩**（Copy & Compact），避免大堆下 CMS 式的严重碎片化
> 4. **增量式整理**：Mixed GC 将年轻代和老年代中收益高的 Region 一起处理，**分摊全堆整理压力**
>
> > 作为对比：CMS 标记-清除不压缩，大堆极易碎片化 → 晋升失败 → Full GC；Parallel Scavenge 每次 Full GC 全量压缩，大堆 STW 过长





## G1垃圾回收器的特色？



**特点：**

- G1最大的特点是引入分区的思路，弱化了分代的概念。
- 合理利用垃圾收集各个周期的资源，解决了其他收集器、甚至 CMS 的众多缺陷

### GC只会对堆进行GC吗？

JVM 的垃圾回收器不仅仅会对堆进行垃圾回收，它还会对方法区进行垃圾回收。





## 为什么说G1引入分区的思路，弱化了分代的概念

> [!info]- 这句话切中了 G1 垃圾回收器的**灵魂设计**。
>
> 在它之前（比如 CMS、Parallel 垃圾回收器），JVM 的内存就像是**严格划分的“大省”**，而 G1 出来之后，直接打破了省界，把内存变成了“无数个对等的小社区”。
>
> 为了让你秒懂，我们用“圈地”和“乐高积木”来对比：
>
> ## 传统回收器： rigid 的“圈地运动”（强化分代）
>
> 在传统概念里，内存是一整块连续的大硬盘，直接切成三块大蛋糕：
>
> - 这一大块死活不能动，叫 **新生代**。
> - 那一大块死活不能动，叫 **老年代**。
> - 还有一小块叫 **永久代/元空间**
>
> ### 带来的致命问题：
>
> 因为边界是死死固定的，这就导致：
>
> 1. **尾大不掉**：老年代越攒越大。每次老年代满了要清理时（Full GC），垃圾回收器必须把这**一整块几十G的大蛋糕**从头到尾扫描一遍。内存越大，停顿（STW）时间越长。
> 2. **空间死板**：如果新生代满了，哪怕隔壁老年代空着大片地方，新生代也用不了，只能硬着头皮触发 GC。
>
> ## G1 回收器：灵活的“微型社区”（弱化分代）
>
> G1 直接把“大蛋糕”的切法给废了。它把整个堆内存平均分成了几千个大小相等的独立正方形小格子，每个小格子被称为一个 **Region（分区）**。
>
> ### 为什么说它“弱化了分代的概念”？
>
> 因为在 G1 里，**再也没有任何一个 Region 是生来就属于“年轻代”或“老年代”的。它们的身份是动态变化的！**
>
> - 此时此刻，格子 A 里面塞满了刚 new 出来的对象，那它现在就是 **Eden（年轻代）** 属性。
> - 几秒钟后，垃圾回收把格子 A 清空了，格子 A 就变成了 **Available（空闲状态）**。
> - 再过一会儿，程序里产生了一个存活很久的大对象，格子 A 被拿去装这个老对象，它就摇身一变，变成了 **Old（老年代）** 属性。
>
> 这就叫**弱化分代**：分代不再是物理上的“这一大块地归谁”，而仅仅是一个**逻辑上的标签**。格子们不再有固定的编制，哪里需要去哪里。
>
> ## 这样做，最大的好处是什么？
>
> 这就回到了它的名字：**G1（Garbage-First，垃圾优先）**。
>
> 正因为引入了分区，G1 回收内存时，再也不用像以前一样傻乎乎地去扫完整个几十 G 的老年代了。它可以玩“精准打击”。
>
> 想象一下：JVM 现在的内存是由 2000 个格子组成的。
>
> - 到了该回收的时候，G1 去清点了一下。
> - 发现格子 ① 号里面 95% 都是垃圾，回收它只要 1 毫秒。
> - 格子 ② 号里面 80% 都是活对象（垃圾只有 20%），回收它要花 50 毫秒。
>
> G1 就会根据用户设定的**最大停顿时间**（比如：我要求每次 GC 最多卡顿 10 毫秒），掐指一算：“时间有限，我这次**只收性价比最高、垃圾最多的格子 ① 号**，格子 ② 号先放着。”
>
> ### 总结
>
> - **以前的回收器**：要扫就得扫完整个老年代。内存越大，扫得越慢，程序员不敢给 JVM 分配太大的内存。
> - **G1 回收器**：通过**分区**，把大任务化整为零；通过**弱化分代**，让内存动态调配。它不管你是年轻代还是老年代，**谁的垃圾多、回收得快，我就先去薅谁的羊毛**。
>
> 这就是“引入分区思路，弱化分代概念”的真正含义——**化整为零，按需动态治理**。
