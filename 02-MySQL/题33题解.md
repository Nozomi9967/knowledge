### **`innodb_autoinc_lock_mode` 有 0（traditional）、1（consecutive）、2（interleaved）三种取值，控制自增锁的粒度，值越大并发越高但越容易跳号；`INSERT ... ON DUPLICATE KEY UPDATE` 在 mode=1/2 下会预分配自增值，冲突走 UPDATE 分支时预分配的 ID 直接作废，这是跳号的根因。**

下面按面试口述节奏展开。

---

**第一部分：先讲自增 ID 是怎么分配的**

InnoDB 里每张带 `AUTO_INCREMENT` 的表都有一个内存计数器，插入行时从这个计数器取值并 +1。为了保证并发安全，取值时需要加一把 **AUTO-INC 锁**。这把锁的加锁范围和持有时长，就由 `innodb_autoinc_lock_mode` 控制。

先分清两类 INSERT，因为不同 mode 对它们行为不一样：

- **Simple Insert**：能提前知道要插几行，比如 `INSERT INTO t VALUES (...)`、`INSERT ... VALUES (...), (...)`。**注意 `INSERT ... ON DUPLICATE KEY UPDATE` 不算 simple**，因为最终可能变成 UPDATE，无法预知；
- **Bulk Insert**：无法提前知道行数，比如 `INSERT ... SELECT`、`REPLACE ... SELECT`、`LOAD DATA`。

---

**第二部分：三种取值详解**

**mode = 0：Traditional（传统模式）**

- **加锁行为**：每条 INSERT 语句执行时申请 **AUTO-INC 表级锁**，一直持有到**语句结束**才释放；
- **优点**：自增 ID **严格连续**，主从复制（statement-based）也能保证顺序一致；
- **缺点**：并发度极低，同一张表的 INSERT 完全串行；
- **现状**：MySQL 5.1 之前的默认值，现在几乎不用。

**mode = 1：Consecutive（连续模式，MySQL 5.7 及之前默认）**

- **加锁行为**：
  - **Simple Insert**：语句开始时**一次性预分配 N 个连续 ID**（N = 要插入的行数），拿到后**立即释放锁**，不等语句结束。这样多条 simple insert 可以并发；
  - **Bulk Insert**：仍然按 mode=0 的方式，持有 AUTO-INC 锁到语句结束；
- **优点**：单语句内 ID 连续；simple insert 并发好；
- **缺点**：**跨语句会跳号**——批量 insert 预分配了 10 个 ID 只用了 3 个，剩下 7 个直接丢弃；`INSERT ... ON DUPLICATE KEY UPDATE` 场景下，即使走了 UPDATE 分支，预分配的 ID 也回收不了，这就是题目里跳号的直接原因。

**mode = 2：Interleaved（交错模式，MySQL 8.0 默认）**

- **加锁行为**：**完全不加 AUTO-INC 表级锁**，每次取值只加一个非常轻量的 mutex，取完立刻释放；
- **优点**：并发最高，多条 INSERT（包括 bulk insert）可以真正并行分配 ID；
- **缺点**：
  - 多条语句的 ID 会**交错分配**，比如事务 A 拿到 1、3、5，事务 B 拿到 2、4、6，单事务内的 ID **不再连续**；
  - **statement-based 复制不安全**（因为从库回放顺序可能和主库不一样，ID 分配结果会不同）。所以 mode=2 必须配合 **row-based 或 mixed binlog**；
- **8.0 改为默认 mode=2** 的前提，就是 8.0 把默认 binlog_format 改成了 ROW。

---

**第三部分：为什么 `ON DUPLICATE KEY UPDATE` 跳号严重**

回到题目场景，跳号的根因是**"先分配、后判断冲突"**：

1. `INSERT ... ON DUPLICATE KEY UPDATE` 执行时，MySQL **无法预知**这条到底会 INSERT 还是 UPDATE；
2. 但为了走 INSERT 分支，**必须先从自增计数器取一个 ID**；
3. 如果发现唯一键冲突，走 UPDATE 分支，**这个 ID 就作废了，计数器不会回退**；
4. 高并发下大量冲突 → 大量 ID 被"预支后作废" → 跳号严重。

举个例子：表里已有 `unique_key='A'` 的记录，ID 是 100。现在并发 1000 条 `INSERT ... ON DUPLICATE KEY UPDATE unique_key='A' ...`，MySQL 会分配 101\~1100 这 1000 个 ID，然后全部检测到冲突走 UPDATE，最终**表里那条记录 ID 还是 100，但自增计数器已经跳到 1101 了**。下一条真正的新记录 ID 就是 1101，中间的 1000 个全丢。

`INSERT IGNORE`、`REPLACE INTO` 也有类似问题。

---

**第四部分：怎么解**

**1. 换写法：先查后写 (SELECT + INSERT/UPDATE)**

用应用层 `SELECT` 判断是否存在，再决定 INSERT 还是 UPDATE。缺点是有 TOCTOU 竞态，需要配合唯一索引兜底或悲观锁。

**2. 换语句：INSERT ... SELECT ... WHERE NOT EXISTS**

只在不存在时才走 INSERT，冲突时不分配 ID。但仍需处理并发唯一冲突。

**3. 接受跳号，改用业务号或雪花 ID**

**最推荐的做法**：ID 本身不承担业务语义，只用来做主键。业务上真正需要连续、有序的字段（订单号、发票号），用**独立的发号器**（Redis INCR、雪花算法、号段模式）生成。这样 `AUTO_INCREMENT` 跳号也无所谓。

**4. 降低 mode（不推荐）**

设 `innodb_autoinc_lock_mode = 0` 确实能减少跳号，但会把并发彻底打死，得不偿失。

**5. 从业务侧削峰**

如果冲突集中在少数热点 key（比如"每日签到"这种），可以用 Redis 前置去重、消息队列合并，减少真正打到 DB 的 `ON DUPLICATE KEY` 请求量。

---

**第五部分：几个容易被追问的坑**

**1. 自增计数器不持久化（8.0 前）**

MySQL 8.0 之前，`AUTO_INCREMENT` 计数器只存在内存中，重启后靠 `SELECT MAX(id) + 1` 恢复。**这意味着重启后可能"回退"**：如果最大 ID 那条记录被删了，重启后计数器会退回。8.0 起把计数器持久化到 redo log，重启不再回退。

**2. 事务回滚也会跳号**

即使不是 `ON DUPLICATE KEY`，一个普通 `INSERT` 事务回滚了，分配出去的 ID 也不会退回。这是自增设计的本质决定的——**跳号是 feature，不是 bug**，别指望它连续。

**3. mode=2 + statement binlog 会导致主从数据不一致**，8.0 默认 ROW 之后才安全。老版本升 8.0 或调 mode 前一定要检查 `binlog_format`。

---

**面试收尾一句话：**

`innodb_autoinc_lock_mode` 的三种取值，本质是在**"ID 连续性 vs 并发度"**之间做权衡：0 完全串行、1 单语句内连续、2 完全并行但交错。`INSERT ... ON DUPLICATE KEY UPDATE` 跳号严重是因为**在冲突判定前就预分配了自增值，冲突后不回收**——这不是 lock mode 能治的，正确的思路是**接受主键跳号、把有业务语义的编号交给独立发号器**。记住一句话：**自增 ID 只保证唯一和递增，不保证连续**。
