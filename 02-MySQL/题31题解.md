### **把 uid 的末 4 位"基因"嵌入 orderId 的固定位，使得仅凭 orderId 就能反解出分库位，从而在不引入映射表的情况下同时支持按 uid 和按 orderId 路由到同一分片。**

下面按面试口述节奏展开。

---

**第一部分：先讲清楚问题本质**

分库分表的核心矛盾是：**分片键只能有一个**。

- 按 `uid` 分库，符合大部分业务查询（用户查自己订单），但 `按 orderId 查订单详情` 就没法直接定位分片，只能**全库扫描**或维护 `orderId → uid` 的**映射表**（多一次 IO，还有一致性问题）；
- 按 `orderId` 分库则反过来，用户查订单列表要扫全库。

基因法的巧思是：**让 orderId 自己"携带"uid 的分片信息**。这样 orderId 就变成了"自解释"的，用它算出来的分片位置和用 uid 算出来的完全一致，一份数据、两种查询路径都能命中同一个分片。

---

**第二部分：基因法方案设计**

**1. 分片规模假设**

假设分 16 库 × 16 表 = 256 分片。定位一个分片需要 `log₂(256) = 8 bit`。为了留扩容余量，我们取 **uid 的末 4 位十进制**（约等于 14 bit），叫做 **"基因位 (gene)"**。

```
gene = uid % 10000      // 取末 4 位十进制
```

后续路由用 gene 而不是完整 uid：

```
db_index    = gene % 16
table_index = (gene / 16) % 16
```

**2. orderId 的结构设计**

一个典型的 64 位 orderId，可以借鉴 Snowflake 的思路重新划分：

```
| 1 bit 符号位(0) | 41 bit 时间戳(ms) | 4 bit 机器号 | 4 bit 基因位(gene 的一部分) | 14 bit 自增序列 |
```

实际工程里更常见的是把基因位放到**低位或中间某段固定位置**，只要保证：

- **位数够表达所有分片**（比如 8 bit 表达 256 分片）；
- **位置固定**，方便反解；
- **不与其他字段冲突**。

一个更实用的版本：

```
orderId = timestamp(41) | machineId(5) | gene(14) | seq(4)
```

生成 orderId 时：

```java
long gene = uid % 10000;              // 拿到基因
long orderId = (timestamp << 23) 
             | (machineId << 18) 
             | (gene << 4) 
             | seq;
```

**3. 双路径路由**

**路径 A：按 uid 查（用户查自己的订单列表）**

```java
long gene = uid % 10000;
int db = (int)(gene % 16);
int tb = (int)((gene / 16) % 16);
```

**路径 B：按 orderId 查（订单详情页、支付回调）**

```java
long gene = (orderId >> 4) & 0x3FFF;   // 从固定位反解
int db = (int)(gene % 16);
int tb = (int)((gene / 16) % 16);
```

**两条路径算出的 (db, tb) 完全一致**，所以订单一定落在同一个分片，查询天然命中，不需要广播、不需要映射表。

---

**第三部分：几个关键细节**

**1. 基因位数选择**

基因位数决定了未来的**最大分片数**。取 4 bit 只能支持 16 分片，取 8 bit 支持 256 分片，取 14 bit 支持 16384 分片。**建议一开始就按未来 3\~5 年的容量上限预留**，比如现在 16 分片但预留 14 bit，扩容到 256 时算法完全不用改。

**2. 一致性保证**

生成 orderId 的服务必须**同时拿到 uid**，才能算出 gene 塞进去。所以 orderId 生成不能是"纯全局发号器"，而必须是**"带业务上下文的发号器"**——这是基因法的必要成本。

**3. 分片算法必须是"位运算"或"取模"能反解的**

基因法的前提是"用 gene 算 (db, tb)"这个函数可以在生成和查询两端得到一致结果。因此**分片算法必须是确定性的、无状态的**，比如取模、位与。如果用了一致性哈希 + 虚拟节点这种动态算法，基因法就失效了，因为 gene → 分片的映射会随节点增减而变。

**4. 扩容策略**

传统"按 uid 取模"扩容要迁移大量数据。基因法搭配**一致性倍增扩容**（比如从 16 库扩到 32 库，只需迁移一半数据）比较友好，因为 gene 是固定的，只要新的 `gene % 32` 落到新库上，迁移路径可预测。

**5. 非用户维度的查询怎么办**

基因法解决了 **uid 和 orderId 两个维度**，但如果还有"按商家 ID 查订单""按手机号查订单"这种需求，基因法救不了，还是要走**异构索引**（比如 ES、二级索引表、CDC 同步的宽表）。**基因法是双维度神器，不是万能钥匙**。

---

**第四部分：风险点与规避**

**1. uid 分布不均**

如果 uid 的末 4 位分布有偏（比如某些历史用户 ID 都是 0000 结尾），会导致**分片热点**。规避方式是先对 uid 做一次哈希打散再取基因：

```java
long gene = Hash(uid) & 0x3FFF;
```

**2. orderId 反解错误的兼容**

上线基因法之前生成的**存量 orderId 没有 gene 位**。方案是：

- 存量数据保留一张 `orderId → uid` 的小映射表兜底；
- 或在 orderId 里加一个**版本位**，反解时先看版本号决定走基因法还是查映射表。

**3. 泄露业务信息**

orderId 里带了 uid 的末 4 位，攻击者拿到大量 orderId 后可以做用户行为分析。敏感场景下**对外展示的 orderId 要加密或加签**，只在内部路由时用原始 orderId。

**4. 全局唯一性**

gene 只有 4 位十进制，多个用户会共享同一个 gene，所以 **orderId 全局唯一性靠 timestamp + machineId + seq 保证**，gene 只承担路由职责，不承担唯一性职责。这一点面试时要说清楚，不然容易被追问"末 4 位相同不会撞吗"。

---

**面试收尾一句话：**

基因法的核心思想是**把分片键的路由信息嵌入到另一个业务 ID 里**，用一份存储、一次查询同时支撑两个维度的等值查询，代价是 orderId 生成必须绑定 uid、分片算法必须可反解。它不是万能的，只解决"双维度精确查询"，多维度还是得靠异构索引兜底；但在电商订单、IM 消息这类"用户维度 + 业务实体维度"的场景里，是分库分表最优雅的解法之一。
