### **MyBatis-Plus 分页 total 与 records 不一致，根因几乎都在 Count SQL 的自动改写上——JOIN 会放大计数、GROUP BY 会被误当成单行、DISTINCT 会在 count(*) 里失效。**

MyBatis-Plus 的 `PaginationInnerInterceptor`(旧版 `PaginationInterceptor`) 会拦截原 SQL，并基于 JSqlParser 生成一条 Count SQL。它的目标是"尽量优化"——去 ORDER BY、去 LEFT JOIN、把 `select ...` 换成 `select count(*)`。这些优化在简单单表查询里没问题，但一旦你的业务 SQL 带 JOIN、GROUP BY 或 DISTINCT，就会踩到下面几个典型坑。

### **坑一：LEFT JOIN 被"智能优化"掉，导致 total 与 records 行数完全对不上**

`PaginationInnerInterceptor` 里有个 `optimizeJoin` 开关，**默认是 true**。它的逻辑是：如果 LEFT JOIN 的表没有出现在 where、group by、select 等位置，就把这段 JOIN 从 Count SQL 里砍掉，理由是"不影响主表行数"。

问题在于两点：

第一，判断并不总是准确。比如你在 `ON` 条件里写了过滤条件（`LEFT JOIN t2 ON t2.uid = t1.id AND t2.status = 1`），主查询靠这个 ON 条件筛掉了一部分数据，但因为 t2 没出现在 WHERE 里，Count SQL 会直接把 JOIN 删掉，count 出来的是"主表全量"，而 records 是"JOIN 过滤后的分页数据"，两者行数逻辑不同。

处理方式：

- 明确不需要 JOIN 参与计数：保留 `optimizeJoin=true`，但**把 ON 里的额外过滤条件挪到 WHERE**，让优化判断稳定。
- 需要 JOIN 参与计数但不想放大：给主键做 `COUNT(DISTINCT main.id)`，或者把 JOIN 改成子查询 / EXISTS。
- 一对多且必须 JOIN：**关掉自动 count**，手写 countSql。

### **坑二：GROUP BY 被当成普通查询，count(*) 数的是"分组前的行数"**

这是最经典的坑。假设业务 SQL 是：

```sql
select user_id, count(*) as cnt
from t_order
where create_time > '2026-01-01'
group by user_id
```

records 返回的是"按 user_id 聚合后的每一行"，比如 50 个用户就是 50 行。但 MyBatis-Plus 生成的 Count SQL 会变成：

```sql
select count(*) from t_order where create_time > '2026-01-01'
```

它**直接把 `group by` 忽略了**，数的是分组前的原始明细行数（比如 20 万条订单）。于是 total=200000，records 只有 50 条，翻页体验彻底崩溃。

正确的 Count SQL 应该是把整段查询作为子查询包一层：

```sql
select count(*) from (
  select user_id from t_order where create_time > '2026-01-01' group by user_id
) tmp
```

但 MyBatis-Plus 出于性能考虑**默认不会自动包子查询**。解决办法有三种：

- 在 XML 的 `<select>` 标签上通过 `resultMap` 对应的 `countMethod` / 手写 `xxxCount` 方法指定 Count SQL。最常用的做法是在 Mapper XML 中写一个与主查询同名但加 `_COUNT` 后缀的配套方法，框架分页时会自动识别并使用，跳过自动改写：

```xml
<!-- 主查询 -->
<select id="selectOrderPage" resultMap="orderResultMap">
    SELECT o.* FROM `order` o WHERE o.status = 1
</select>

<!-- 配套 Count SQL -->
<select id="selectOrderPage_COUNT" resultType="long">
    SELECT COUNT(*) FROM `order` o WHERE o.status = 1
</select>
```

- 使用 `Page` 对象的 `setOptimizeCountSql(false)`，让插件放弃优化、退化为外包一层 `select count(*) from (原SQL) t`；
- 更彻底的做法是关闭全局 count 优化，或用 `@InterceptorIgnore(illegalSql = "true")` 之类的开关，把 Count 交给自己写。

### **坑三：DISTINCT 在 count(*) 改写时被丢弃**

如果原 SQL 是 `select distinct user_id from ...`，插件会改写成 `select count(*) from ...`——**`distinct` 消失了**。原本 records 是去重后的 N 行，count 出来却是去重前的 M 行。

这里插件行为在不同版本不完全一致：较新的 MyBatis-Plus 会尝试识别 `SELECT DISTINCT` 并改写为 `select count(*) from (select distinct ...) t`，但一旦 distinct 出现在**列级函数**里（比如 `count(distinct col)`、`sum(distinct col)`），或者写成 `select distinct a, b, c from ...` 且伴随 JOIN，识别经常会失败，仍然退化成朴素的 `count(*)`。

判断方法很简单：开启 MyBatis 的 SQL 日志，看生成的 Count SQL 里还有没有 `distinct`。没有就必须自己接管。



### **规避这类问题的工程实践**

第一，**开发期强制开日志**，对每一个分页接口都看一眼生成的 Count SQL，不要等测试环境翻页出问题。第二，**约定复杂查询一律手写 countSql**——在 Mapper 的 XML 中定义与主查询同名并加 `_COUNT` 后缀的语句（如 `selectOrderPage_COUNT`），MyBatis-Plus 会自动识别并使用它，绕开自动改写。第三，对不得不用自动 count 的场景，用 `page.setOptimizeCountSql(false)` 让它退化为最保守的外包子查询方案，性能稍差但正确性最稳。第四，团队里做一次代码扫描：所有含 `group by`、`distinct`、`left join ... on ... and` 的分页方法，全部要求显式指定 countSql，把这条作为 Code Review 硬性规则。

一句话总结：MyBatis-Plus 的 Count SQL 自动生成本质上是"猜"，只要你的 SQL 稍微复杂一点，就别让它猜——**手写 countSql，或关掉 optimizeCountSql**，比事后排查数据不一致省事得多。
