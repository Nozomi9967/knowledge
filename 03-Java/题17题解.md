
### **这个场景选 G1 更合适：32G 堆不算大、STW < 50ms 是 G1 努努力能达到的目标、而且你明确"对吞吐敏感"——ZGC 停顿虽然更低但吞吐要牺牲 5~15%，属于用不上的过度设计**

  

---

  

### **一、先说选型判断**

  

先把两者的定位摆清楚：

  

**G1（Garbage First）**：JDK 9 默认，**Region 分代 + 并发标记 + 增量回收**。STW 主要发生在 Young GC 和 Mixed GC 的 evacuation 阶段，目标停顿可配。适合中等堆（4G~64G），吞吐损失小（相对 Parallel GC 大约 5~10%）。

  

**ZGC**：JDK 15 正式，JDK 21 有分代 ZGC。**染色指针 + 读屏障 + 并发一切**，STW 几乎只剩 root scan，通常 < 1ms，和堆大小无关。代价是读屏障有额外 CPU 开销，吞吐比 G1 低 5~15%，内存占用也更高（染色指针 + forwarding table）。

  

**回到题目场景**：

  

- **堆 32G**：G1 完全 hold 得住，ZGC 的"堆越大越有优势"体现不出来（ZGC 的杀手锏是 TB 级堆下依然亚毫秒停顿）。

- **STW < 50ms**：G1 调好参数一般能压到 30~50ms，够用。ZGC 能做到 < 1ms，但你不需要。

- **吞吐敏感**：这是决定性因素。ZGC 的读屏障是每次对象读取都要执行的，业务代码 CPU 会多花 5~15%，对高 QPS 服务就是白扔机器。

  

所以答案：**G1，除非 STW < 10ms 是硬指标**。

  

---

  

### **二、G1 关键参数调优**

  

**核心目标参数**

  

```

-XX:+UseG1GC

-XX:MaxGCPauseMillis=40 # 目标停顿，比 SLA 留 10ms 余量

-Xms32g -Xmx32g # 堆固定，避免动态扩缩

```

  

`MaxGCPauseMillis` 是**软目标**，不是硬保证。G1 会根据这个值反推 Young 区大小和每次回收的 Region 数量——**设得越小，Young 区越小，GC 越频繁，吞吐越差**。40ms 是经验值，别贪心设 10ms，会把吞吐打崩。

  

**Region 大小**

  

```

-XX:G1HeapRegionSize=16m

```

  

G1 把堆切成 Region，默认根据堆大小自动算（32G 堆默认 8M）。**大对象（Humongous Object）判定阈值 = Region 的一半**，超过就直接进 Old 区且占用整个 Region，容易造成碎片。

  

如果业务里有大数组、大 String（比如缓存 JSON、图片字节），把 Region 调到 16M 或 32M，减少 Humongous 分配。可选值必须是 2 的幂：1M/2M/4M/8M/16M/32M。

  

**并发线程 & 触发时机**

  

```

-XX:ConcGCThreads=4 # 并发标记线程，一般是 ParallelGCThreads 的 1/4

-XX:ParallelGCThreads=8 # STW 阶段的并行线程，通常等于 CPU 核数

-XX:InitiatingHeapOccupancyPercent=45 # IHOP,老年代占比达到就启动并发标记

```

  

**IHOP 是重点**：默认 45%，意思是老年代用到 45% 就启动并发标记周期，为 Mixed GC 做准备。设太高会来不及回收导致 **Full GC**（G1 的 Full GC 是 Serial 单线程，几十秒起步，灾难级），设太低则并发标记太频繁浪费 CPU。JDK 9+ 默认开自适应 IHOP，一般不用手动调，除非观察到频繁 Full GC 再往下压到 35。

  

**Mixed GC 调优**

  

```

-XX:G1MixedGCLiveThresholdPercent=85 # Region 存活率低于此值才纳入回收

-XX:G1MixedGCCountTarget=8 # 一次并发周期后分几次 Mixed GC 回收

-XX:G1OldCSetRegionThresholdPercent=10 # 每次 Mixed GC 最多回收多少 Old Region

```

  

Mixed GC 是 G1 回收老年代的方式，跟 Young GC 一起做部分老年代回收。这些参数决定"回收多狠"——回收越多单次停顿越长，回收越少老年代涨得快。默认值一般够用，只有观察到 Mixed GC 停顿超标或者老年代回收不下去才调。

  

**Young 区大小（一般别手动设）**

  

```

-XX:G1NewSizePercent=5 # Young 最小占比,默认 5%

-XX:G1MaxNewSizePercent=60 # Young 最大占比,默认 60%

```

  

G1 会根据 `MaxGCPauseMillis` 自动调整 Young 大小。**除非你确认自适应算法算错了，否则别锁死 `-Xmn`**（在 G1 下设 `-Xmn` 等于禁用了自适应，是常见误操作）。

  

**其他实用参数**

  

```

-XX:+ParallelRefProcEnabled # 并行处理 Reference,加速 Final/Weak/Soft 引用清理

-XX:+DisableExplicitGC # 或改成 -XX:+ExplicitGCInvokesConcurrent

-XX:+AlwaysPreTouch # 启动时把堆内存实际分配,避免运行时 page fault 抖动

-XX:+UseStringDeduplication # 字符串去重,能省不少内存

```

### **三、观测与验证**

  

调完必须验证，不能拍脑袋：

  

**GC 日志（JDK 9+ 统一日志）**：

  

```

-Xlog:gc*,gc+heap=debug,gc+age=trace:file=/log/gc.log:time,uptime,level,tags:filecount=10,filesize=100M

```

  

用 **GCViewer**、**GCEasy**（在线）或 **gceasy.io** 分析，重点看：

  

- **Pause Time 分布 P99 / P999**：是不是稳定在 50ms 以下。

- **Throughput**：应用运行时间占比，健康值 > 95%。

- **是否有 Full GC**：只要出现就是异常，必须查原因（大对象、Metaspace 满、System.gc() 调用、并发标记失败）。

- **Mixed GC 频率和回收效率**：老年代是否在稳定回收。

  

**运行时观测**：JFR（Java Flight Recorder）+ JMC 是首选，几乎零开销可以持续采集。Arthas 的 `dashboard` 命令看实时 GC 情况也很方便。

  

---

  

### **四、什么时候才该切 ZGC**

  

给个明确边界，避免"为新而新"：

  

- 堆 **≥ 64G**，G1 的 Mixed GC 已经压不住停顿。

- STW **< 10ms** 是业务硬指标（比如高频交易、实时风控、游戏服务器）。

- 业务能接受 **5~15% 吞吐损失**，或者机器成本相对停顿收益不敏感。

- **JDK 21+**：一定用**分代 ZGC**（`-XX:+UseZGC -XX:+ZGenerational`），非分代 ZGC 在有大量短命对象时表现远不如 G1。

  

ZGC 参数很少，主打"开箱即用"：`-XX:+UseZGC -Xmx32g -XX:SoftMaxHeapSize=28g`（软上限，让 ZGC 提前 GC 而不是逼近硬上限）。`ConcGCThreads` 一般不用调。

  

---

  

一句话面试答法：**32G 堆 + 50ms 停顿 + 吞吐敏感 → G1 就是最优解**。核心调参就四组：`MaxGCPauseMillis=40` 定目标、`G1HeapRegionSize=16m` 防 Humongous、`IHOP=45` 保证 Mixed GC 及时启动别退化成 Full GC、`ParallelGCThreads` 对齐 CPU 核数；配合 `AlwaysPreTouch` 和固定 Xms=Xmx 消除运行时抖动；上线后靠 GC 日志 + JFR 持续观测 P99 停顿。**只有堆超 64G 或 SLA 卡在 10ms 以内才考虑 ZGC，并且必须是分代版本**。
