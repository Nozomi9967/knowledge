### 二、MVCC 与 Read View（共 3 题）

当前读时，会将该记录的trx_id与readview中的值相比较

如果trx_id大于等于max_trx_id，代表修改该记录的事务是在创建当前事务之后才启动的，且未提交，不可以读当前版本的记录

**批改：** 字段含义理解正确，但字段名称不够规范。隐藏列回答正确。  
**修正答案：**

- **Read View 四个字段：**
    1. `m_ids`：生成 Read View 时当前系统中活跃的（未提交的）事务 ID 列表。
    2. `min_trx_id`：即 `m_ids` 中最小的事务 ID。
    3. `max_trx_id`：生成 Read View 时，系统应分配给下一个事务的 ID（即当前最大事务 ID + 1）。

**第 5 题**

请详细说明 Read View 的可见性判断规则（三种情况）。读提交和可重复读两种隔离级别在创建 Read View 的时机上有什么不同？这个不同如何导致了它们的行为差异？

**批改：** 可见性判断规则正确。创建时机描述有细微偏差。  
**修正答案：**

- **创建时机差异：**
    - **Read Committed (RC)：** 每次执行 **SELECT 语句** 时都会重新生成一个 Read View。
    - **Repeatable Read (RR)：** 只在 **事务第一次执行 SELECT 语句**（或开启事务时，取决于具体实现）生成一个 Read View，并在整个事务期间复用该 View。
- **行为差异：** 正是因为 RC 级别每次查询都生成新的 View，所以能看到其他事务已提交的修改（导致不可重复读）；而 RR 复用同一个 View，所以看不到后续事务的修改（实现了可重复读）。

**第 6 题**

MVCC 为什么无法完全避免幻读现象？请结合一个具体的 SQL 示例说明。InnoDB 通过什么机制来弥补这个缺陷？间隙锁是在什么时机加上的？

因为快照读是不会对记录加锁的，一个事务如果同时存在快照读和当前读，就可能发生幻读
事务A：select count(1) from stu where age>18   -- 记录数=3
事务B：insert stu(id=1,age=19)   -- 记录数=4
事务A：select * from stu where age > 18 for update set gender = 男  -- 记录数=4 不一致

额，弥补了吗？
我也不清楚

**批改：** 核心逻辑正确，但“弥补缺陷”的机制回答缺失。  
**修正答案：**

- **为什么无法完全避免：** MVCC 是快照读，无法阻止其他事务进行当前读（如 Insert）。如果一个事务先快照读，再当前读（如 `SELECT ... FOR UPDATE`），就会看到其他事务新插入的数据，产生幻读。
- **示例：** 事务 A 快照读查出 3 条；事务 B 插入第 4 条并提交；事务 A 进行 `UPDATE` 操作（当前读），会扫描到第 4 条记录并更新，此时再次快照读会发现多了一条记录（或者 UPDATE 成功了但 SELECT 看不到，取决于具体场景），打破了幻象。
- **弥补机制：** **Next-Key Lock（临键锁）**。在执行当前读（如 `SELECT ... FOR UPDATE`）时，InnoDB 会给相关记录和间隙加锁，阻止其他事务插入新数据，从而在锁层面彻底解决了幻读问题。

**第 20 题**

`IN` 和 `EXISTS` 有什么区别？各自的执行逻辑是怎样的？

IN是把结果都查出来再筛选
EXITSTS是查一个就筛一个，筛到了就停止

**批改：** 逻辑描述不够精准。  
**修正答案：**

- **IN：** 驱动表在外层，子查询只执行一次。适合**子查询表小，外层表大**的情况。
    - 逻辑：先查询子查询表得到结果集（去重），然后遍历外层表，判断外层表的值是否在结果集中。
- **EXISTS：** 驱动表在外层，子查询会执行多次（关联子查询）。适合**子查询表大，外层表小**的情况。
    - 逻辑：遍历外层表，将外层表的每一行数据代入子查询中执行，如果子查询有结果，则保留该行。
- **核心区别：** IN 是先查子表再过滤主表；EXISTS 是循环主表，每次触发子查询的查找。
