## 一、语言基础与变量（6 题）

### 1. 成员变量、局部变量、类变量的区别？默认值分别是什么？【高频】

> **知识点跳转：** [[Java变量分类与默认值]]

**追问：** 为什么成员变量有默认值，而局部变量没有？

---

**参考答案 ✅**

我分三条线说：归属、存放位置、默认值。**类变量**用 static 修饰，属于类、全类只有一份，随类加载初始化；**实例变量**不带 static，属于对象，每 new 一个对象就有一份；**局部变量**定义在方法或代码块里，每次方法调用各有一份。存放位置上，类变量跟着类元信息走（JDK 8 之后元信息在堆里），实例变量在堆上的对象里，局部变量在栈帧里。

最关键、也是笔试最爱考的区别在**默认值**：成员变量——也就是实例变量和类变量——JVM 会自动赋默认值：byte、short、int、long 是 0，float、double 是 0.0，char 是空字符，boolean 是 false，引用类型是 null；而**局部变量没有默认值**，用之前必须显式赋值，否则编译直接报错，根本跑不起来。

> **追问参考答：** 

成员变量有默认值，而局部变量没有，根本原因在于它们的生命周期和内存位置不同，JVM 对两者的保障责任也不同。

成员变量分为实例变量和静态变量，它们属于对象或类，创建对象或加载类时，JVM 会在分配内存后先把整块空间清零，所以 int 默认为 0，boolean 为 false，引用类型为 null。这一步由 JVM 统一完成，不依赖程序员，目的是保证每个对象和类在被使用之前都处于确定的状态，不会读到随机的内存内容。

局部变量则不同，它们存放在线程私有的虚拟机栈的栈帧中，随方法调用创建、方法结束销毁。栈空间会被反复复用，上一次方法调用留下的数据可能还残留在那块位置上。如果 JVM 也替局部变量兜底赋默认值，每次方法调用都要额外清零，会带来额外开销。因此 Java 选择由编译器做静态检查：只要局部变量在使用前没有被明确赋值，编译器就直接报错，从源头杜绝读到残留垃圾值的可能。

需要注意的是，这里的“没有默认值”指的是不会自动赋值，并不是说局部变量没有初始状态。另外，final 也是一个容易混淆的点，它不是与成员变量、局部变量并列的第三类变量，而只是一个修饰符，可以修饰成员变量，也可以修饰局部变量，作用是保证只能赋值一次。final 成员变量如果没有在声明处或构造器中赋值，编译器同样会报错，这也体现了 Java 在初始化问题上的严格要求。

### 2. Java 的访问权限修饰符有哪几个？protected 有什么特殊？【高频】

> **知识点跳转：** [[权限修饰符]]

**追问：** 什么时候用哪个？接口里的成员默认是什么权限？

---

**参考答案 ✅**

四个修饰符，从严到松是 **private、默认（包访问）、protected、public**。private 只有**本类**能访问；默认（不写修饰符）是**同包**可见；protected 是**同包可见、加子类可见 ；public 是**全局可见。

protected 有个经典坑要讲清楚：子类跨包时，可以访问**继承下来的** protected 成员——通过 this、通过子类自己的实例都行，但不能拿一个**父类引用**去访问。比如父类 Parent 有个 protected 字段 x，子类 Child 在另一个包里，`this.x`、`child.x` 都编译通过，但 `parent.x` 编译不过——因为 protected 跨包访问的前提是"这个成员是经子类继承而来的"。

使用原则就一条：**最小权限**。字段一律 private，方法按需要放开，对外 API 才用 public；protected 主要留给"设计上希望子类扩展"的钩子方法。

> **追问参考答：** 什么时候用哪个，按"暴露范围"定：只在类内用 private，同包协作但不对外用默认，给子类扩展留 protected，对外接口用 public。接口里的成员有特殊规则：接口方法默认就是 public abstract（也只能是 public），字段默认是 public static final 常量——这两点跟类的成员不一样，笔试题常在这里埋坑。再补一个高频混淆点：**Java 没有 internal 修饰符**——笔试题爱拿它当"假选项"。internal 是 **Kotlin**（表示模块内可见）和 **C#** 的概念，Java 的四个访问级别里没有它；如果有人把 Java 的"同包可见"那档叫成 internal，是不准确的（正名叫默认访问 / package-private）。

### 3. this 和 super 的区别？【高频】

> **知识点跳转：** [[super 与 this 详解]]

**追问：** 构造方法第一行的规则是什么？`super.getClass()` 返回父类还是运行时类？

---

**参考答案 ✅**

先纠一个最常见的误解：**this 是当前对象本身，而 super 不是一个对象**——它只是"在同一个对象里、去父类那部分找成员"的一种访问方式。内存里从头到尾只有一个对象，`new Child()` 创建的对象既是 Child 也是 Parent，不会额外再 new 一个父类对象出来。

用法上，this 有三种：一是区分同名的成员变量和参数（`this.name = name`）；二是调用本类其他构造方法（`this(...)`）；三是把当前对象传出去或返回自己（`return this`，链式调用的写法）。super 也有三种：访问父类被隐藏的字段（`super.name`）、调用父类被重写的方法（`super.hello()`，这是"复用父类逻辑再扩展"的标准写法）、调用父类构造方法（`super(...)`）。

构造方法有个硬性规则：**第一行要么是 super(...) 要么是 this(...)，二选一、不能同时出现**；什么都没写的时候，编译器自动补一个无参的 `super()`。所以子类构造无论怎么绕，最终一定先走父类构造——**父类一定先初始化**这条链条不会断。

> **追问参考答：** 第一行规则就是"super(...) 和 this(...) 只能选一个，不写默认补 super()"；用 this(...) 的那个构造方法自己不补 super()，但它转去调用的那个构造方法里会有。再看 `super.getClass()`——它返回的是**运行时类**，不是父类。因为 getClass() 是 Object 里的 final 方法，返回"当前对象实际是什么类"，而 super 并不会换对象，还是原来那个子类实例在调用，所以拿到的依然是子类。

### 4. Java 创建对象有哪几种方式？【高频】

> **知识点跳转：** [[Java基础面试题#java创建对象有哪些方式？]]

**追问：** clone 和反序列化为什么不走构造器？

---

**参考答案 ✅**

常规回答是五种。第一，**new**，最常用，直接调构造器。第二，**反射**——Class 对象上 newInstance()（这个方法 JDK 9 后废弃了），或者拿 Constructor 再 newInstance()，本质还是走构造器，只是把"创建哪个类"推迟到了运行时。第三，**clone()**，实现 Cloneable 接口后克隆一个已有对象。第四，**反序列化**，从字节流把对象还原出来。第五，**工厂方法或框架容器**——Spring 创建 Bean、各种工厂模式，看着是"容器帮你造对象"，但底层用的还是前面那几种手段，比如 Spring 默认就是反射调构造器。

面试里可以按"走不走构造器"给它们分两类，这是加分点：new、反射走构造器；clone 和反序列化**不走构造器**——对象的字段状态直接被赋予，构造器里的代码一行都不执行。

> **追问参考答：** clone 不走构造器，是因为它是 JVM 直接在内存层面复制对象——native 实现，按已有对象的内存布局拷一份，所以构造逻辑（包括构造器里的校验）都被跳过。反序列化也不走，对象是从字节流重建的，JVM 直接从流里恢复字段状态。这个特性带来的影响是：如果一个类对"实例创建过程"有约束——比如单例要求全流程只有一个实例——那反射、clone、反序列化都是要防的口子，这也是枚举单例天然安全的原因所在。

### 5. 数据类型转换有哪些方式？类型互转会出什么问题？【中频·高频】

> **知识点跳转：** [[Java基础面试题#数据类型转换方式你知道哪些？]] · [[Java基础面试题#类型互转会出现什么问题吗？]]

**追问：** long 转 float 是安全的吗？为什么？

---

**参考答案 ✅**

Java 中的类型转换分为自动转换（隐式）和强制转换（显式）两种。自动转换发生在小范围类型转大范围类型时，编译器认为安全，会直接完成，链条是 byte、short、int、long、float、double，其中 char 可以自动转为 int。强制转换则是大范围转小范围，需要手动加括号声明，编译器知道可能丢失数据，例如 (byte) 128 的结果是 -128，因为 byte 的范围是 -128 到 127，超出部分被截断。引用类型之间的转换对应向上转型和向下转型：子类对象赋给父类引用是向上转型，自动且安全；父类引用转回子类类型是向下转型，必须先用 instanceof 判断，否则运行时可能抛出 ClassCastException。

类型互转的风险可以概括为溢出、截断和丢失精度三类。整数从大类型转小类型会发生溢出截断；浮点数转整数会直接舍弃小数部分；字符与数字之间按 Unicode 码值互转，容易因为混淆字符 '0' 与数字 0 而出错。涉及金额或大整数计算时，应当使用 long 或 BigDecimal，避免在 int 和 float 之间反复转换。

long 转 float 不安全。虽然它是编译器允许的自动转换，不会报错，但 float 的尾数只有 23 位，加上隐含位共 24 位有效精度，而 long 最多有 63 位有效数值位，所以大数值转换时会丢失精度，例如 999999999999999999L 转为 float 后会变成近似值 1.0E18。这一点容易让人产生误解：float 的数值范围比 long 大得多，于是有人会以为它也能精确存下 long 的每个值，但能否无损，取决于尾数位数，而不是范围或字节数。同理，int 转 float 在超过 2 的 24 次方（16777216）之后也会丢失精度，而 int 转 double 则是安全的，因为 double 有 52 位尾数，足以精确表示所有 int 值。

### 6. i++ 和 ++i 的区别？&& 和 &、>> 和 >>> 的区别？【高频·笔试】

> **知识点跳转：** [[Java基础热门面试题-1#6. 什么是自动装箱/拆箱？为什么要用 BigDecimal 而不是 double？【中频】]]（拆箱相关坑）

**追问：** 三目运算符有什么拆箱的坑？循环里用包装类型累加有什么问题？

---

**参考答案 ✅**

i++ 和 ++i 的核心区别是**表达式的值取的时机**：i++ 是先取值、后自增，表达式值是旧值；++i 是先自增、后取值，表达式值是新值。单独写一行两者效果一样；但放表达式里就有差别——经典笔试题 `int a = 1; a = a++;` 最后 a 还是 1：右边 a++ 求出来是旧值 1，赋值发生在这个自增效果落定之前，把 1 又盖了回去。

&& 和 &、|| 和 | 的区别是**短路**：&& 左边为 false 就不算右边，& 两边都算。所以 `if (obj != null && obj.getX() > 0)` 必须用双与号做保护，用单个 & 照样空指针；反过来也可以用 || 做兜底默认值。&、| 另外还有位运算语义（按位与/或），双写符号只负责逻辑运算。

再说移位运算符。**算术右移 `>>` 左边补符号位**，负数移完还是负数；**逻辑右移 `>>>` 左边一律补 0**，负数移完会变成很大的正数。还有个隐藏坑：移位距离按类型取模（int 对 32、long 对 64 取模），所以 `1 << 32` 其实等于 1、不是 0。

> **追问参考答：** 三目运算符的坑是**自动拆箱 NPE**：只要表达式一侧是包装类型、另一侧是基本类型，整个条件表达式就会发生自动拆箱——`Integer i = null; int n = true ? i : 0;` 会直接空指针，哪怕 null 值不在被选中的分支上（条件表达式两个分支的类型要先统一，null 的 Integer 拆箱时就炸了）。循环里用包装类型累加的问题在**装箱开销**：`Long sum` 循环里每次 `sum += x` 都是"拆箱 → 相加 → 装箱"，几十万次循环就是几十万个临时对象，全压在 GC 上——所以循环累加用基本类型，数量大再考虑 long。

### 7. 类的初始化顺序是怎样的？静态代码块和实例代码块各执行几次？【高频】

> **知识点跳转：** [[super 与 this 详解]] · [[类初始化的主动引用与被动引用]]

**追问：** 什么情况会触发一个类的初始化？

---

**参考答案 ✅**

单个类内，静态变量的显式赋值和静态代码块是按源代码书写顺序从上到下执行的，并不是先统一执行所有静态变量再执行静态代码块。实例部分同理，实例变量赋值和实例代码块按书写顺序执行，并且都在构造方法体之前完成。静态部分只在类初始化时执行一次，实例部分每 new 一次执行一次。

父子类之间的顺序仍然成立：先执行父类静态部分，再执行子类静态部分，创建对象时先执行父类实例部分和父类构造方法，再执行子类实例部分和子类构造方法。这个顺序的根因是子类构造器第一行隐含的 super() 调用

有一个容易出错的地方需要单独说明。如果在静态块中读取后面才声明的静态变量，直接写变量名会编译报"非法前向引用"，但如果通过类名限定访问，比如 Demo.b，编译可以通过，此时读到的是尚未赋值的默认值 0。另外，编译期常量比如 static final int X = 1 这类值在编译时就已确定，会在准备阶段直接写入，因此即使声明在后面，读到的也是 1，而不是默认值。

关于静态代码块和实例代码块的用途，静态代码块常用于初始化静态资源，比如加载配置、注册 JDBC 驱动；实例代码块用得较少，一般用来抽取多个构造方法共用的初始化逻辑。

追问部分的回答基本准确：触发类初始化的主动引用包括 new 对象、访问非编译期常量的静态字段或调用静态方法、反射 Class.forName、初始化子类时先触发父类初始化；被动引用只加载不初始化，包括通过子类引用访问父类静态字段、定义数组对象、访问编译期常量。
### 8. 静态方法能被重写吗？静态绑定和动态绑定怎么理解？【高频】

> **知识点跳转：** [[Java基础面试题#解释Java中的静态变量和静态方法]] · [[super 与 this 详解]]

**追问：** 静态方法调用时看声明类型还是实际类型？

---

**参考答案 ✅**

静态方法不能被重写，只能被隐藏。重写是运行时多态，子类对象赋给父类引用后调用被重写的方法，JVM 会按对象的实际类型动态分派到子类版本。静态方法属于类而不属于对象，没有"实际类型"的概念，编译器在编译期只看引用变量的声明类型，声明是什么类就调哪个类的方法，这叫静态绑定。因此 Parent p = new Child(); p.staticMethod() 调用的是 Parent 中的静态方法，即使实际对象是 Child，这与实例方法的行为正好相反。子类如果写了同名同参的静态方法，只是方法隐藏，此时再加 @Override 会直接编译报错，这个注解正是用来提醒"这不是重写"。

静态绑定与动态绑定的区别在于目标方法何时确定。静态绑定发生在编译期，适用于 private 方法、static 方法、final 方法和构造器，这些方法都无法被子类重写，编译器可以直接确定调用目标。动态绑定发生在运行期，适用于可以被重写的普通实例方法，JVM 通过虚方法表，根据对象的实际类型找到应执行的方法版本，多态正是依靠动态绑定实现的。

追问一：静态方法调用看声明类型。把 Child 对象赋给 Parent 类型的引用，p.staticMethod() 调的是 Parent 的版本。如果想调用子类的静态方法，应把引用声明为 Child 类型，或者直接写 Child.staticMethod()。另外还要注意，静态方法中不能直接使用 this 和 super，也不能直接访问实例变量和实例方法，因为静态方法不依附于任何对象。

## 三、面向对象深入（5 题）

### 9. Java 有哪几种内部类？各自有什么特点？【高频】

> **知识点跳转：** [[Java内部类]]

**追问：** 局部内部类和匿名内部类为什么只能访问 effectively final 的局部变量？

---

**参考答案 ✅**


Java 有四种内部类，分别是成员内部类、静态内部类、局部内部类和匿名内部类。最关键的分界线是静态与非静态。非静态的成员内部类会持有外部类实例的引用，编译器会为它生成一个指向外部类的字段，通常叫 this$0，因此创建它之前必须先有外部类对象，它可以直接访问外部类的所有成员，包括私有成员，访问私有成员时编译器会生成合成的访问方法。静态内部类则不持有外部类引用，可以直接通过 new Outer.Inner() 独立创建，只能访问外部类的静态成员。实际开发中优先使用静态内部类，因为它少一层引用，也不会因为内部类对象仍被持有而导致外部类无法回收。局部内部类定义在方法或代码块里，作用域仅限于该方法内，可以访问方法中的局部变量，但这些变量必须是 final 或 effectively final。匿名内部类是没有类名的局部内部类，在声明处通过 new 接口或父类加花括号的方式一次性定义并实例化，它只能在声明处创建一次实例，对象本身可以反复使用，但不能再用类名创建第二个。

追问：局部内部类和匿名内部类只能访问 effectively final 的局部变量，根因在于生命周期不一致。局部变量存放在栈帧中，方法返回后就被销毁，而内部类对象位于堆上，可能比方法活得更久，例如作为回调被传递到其他地方。为了让内部类在方法结束后仍能使用这些值，编译器会把局部变量的值拷贝一份，作为内部类的字段保存。如果这个值之后还能被修改，内部类中的副本与外部的原变量就会不一致，行为无法预测，因此 Java 要求变量不可变。Java 8 之前必须显式加 final，从 Java 8 开始放宽为 effectively final，即变量在初始化后没有被再次赋值即可。Lambda 表达式捕获外部局部变量遵循同样的规则，可以对照理解。

### 10. 枚举（enum）是什么？它有哪些特性？【高频】

> **知识点跳转：** [[枚举]]

**追问：** 枚举和「public static final 常量」相比好在哪？

---

**参考答案 ✅**

枚举本质上是一个特殊的类，编译后继承自 java.lang.Enum 并且是 final 的，每个枚举常量都是这个类的一个 public static final 实例，因此枚举天生是单例的，而且类初始化时一次性创建所有常量，线程安全也由类加载机制保证。

枚举的特性主要有四点。第一，枚举可以定义字段、构造器和方法，构造器隐式为 private，不允许声明为 public 或 protected，可以把数据直接绑定在常量上，例如 EARTH(5.976e24, 6.378e6) 这种写法。第二，枚举可以声明抽象方法，让每个常量各自实现，这就是用枚举实现状态机或策略模式的常见写法，每个常量承载一段行为，可以替代大量 if-else。第三，枚举内置了一些方法：values() 返回所有常量组成的数组，valueOf() 根据名称查找常量，name() 返回名字，ordinal() 返回从 0 开始的序号。第四，枚举可以直接用于 switch，Java 14 之后还支持 switch 表达式，同时 JDK 提供了专为枚举设计的容器 EnumSet 和 EnumMap，底层基于位向量或数组实现，性能明显优于 HashSet 和 HashMap。实际开发中，枚举常用于订单状态、支付方式、性别这类取值有限的集合，也常被用作最安全的单例实现。

和 public static final 常量相比，枚举的优势主要在类型安全、信息承载、可遍历性和行为扩展四个方面。常量本质上是裸的 int 或 String，编译器无法限制传入的值是否合法，而枚举是独立的类型，只能传入已定义的常量，传错会在编译期被拦下。枚举还能把字段、方法和每个常量的行为都封装在一起，而常量只是一个值。values() 可以直接遍历，switch 可以直接匹配，IDE 也能提供补全和安全重构。最后，每个枚举常量可以重写方法给出不同实现，用多态替代分支判断。可以概括为：常量只是一个值，枚举则是值加类型约束加行为。

### 11. 为什么说「组合优于继承」？【中频】

> **知识点跳转：** [[设计模式（笔试面试常考）]] · [[Java基础面试题#面向对象的设计原则你知道有哪些吗]]

**追问：** 那什么时候还该用继承？

---

为什么说组合优于继承，核心在于继承是一种强耦合的 is-a 关系。子类在复用父类代码的同时，也把自己绑定到了父类的实现细节上，父类内部一旦调整，子类可能莫名其妙出错，这就是经典的脆弱基类问题。另外，继承会破坏封装，父类的 protected 成员对所有子类都是敞开的，而且继承关系在编译期就已经固定，运行时无法更换。

组合则是 has-a 关系，把能力做成对象持有在内部，通过委托调用，需要哪种能力就持有哪个对象，运行时也可以替换，父类实现细节不会暴露出去。最典型的例子是 Java IO 中的装饰器模式，比如 new BufferedInputStream(new FileInputStream(...))，一层层包装即可叠加缓冲、加密、解压等功能。如果改用继承去穷举"缓冲加加密""缓冲加解压"这些组合，子类数量会迅速爆炸。因此实践中的准则是默认优先使用组合，只有在真正满足 is-a 关系、并且父类是专门为扩展而设计的时候，才考虑继承，例如模板方法模式中留有明确 protected 钩子的场景。

追问：什么时候还该用继承？我认为需要同时满足三个条件。第一，确实是一脉相承的 is-a 关系，比如猫是动物；第二，父类明确为扩展设计过，留有 protected 钩子或文档说明了可覆写的点，模板方法模式就是标准范例；第三，团队能接受父类改动会传导到子类的耦合代价。三者都满足才用继承，否则应选择组合或接口。另外，Java 只支持单继承，这一限制也促使开发者用组合来组装能力。比如一个类既要具备飞行能力，又要具备游泳能力，用两个接口加组合持有的方式，比硬凑继承树要清晰得多。

### 12. 面向对象的设计原则有哪些？（SOLID）【中频】

> **知识点跳转：** [[Java基础面试题#面向对象的设计原则你知道有哪些吗]] · [[设计模式（笔试面试常考）]]

**追问：** 开闭原则在实际开发里怎么落地？

---


面向对象有五条主流设计原则，即 SOLID。S 是单一职责，一个类只负责一件事，只有一个变化的原因，职责过多时，修改一个功能容易误伤另一个功能。O 是开闭原则，对扩展开放，对修改关闭，新需求通过新增代码满足，而不是改动已有代码，策略模式、工厂模式等都是为它服务的。L 是里氏替换，子类必须能够替换父类出现的地方而不破坏程序正确性，本质上是子类不能违背父类约定的契约，比如父类约定不抛受检异常，子类就不应该抛出。I 是接口隔离，接口应当小而专，大而全的接口会迫使实现类编写用不上的方法，应拆分为多个小接口，实现哪个用哪个。D 是依赖倒置，高层模块和低层模块都应依赖抽象而不是具体实现，也就是面向接口编程，Spring 的依赖注入是这条原则的典型落地。可以简单记为：S 管类的粒度，O 管扩展方式，L 管子类契约，I 管接口粒度，D 管依赖方向。

追问：开闭原则在实际开发里怎么落地？通常采用抽象加多态加注册的套路。先把会变化的点抽象成接口，新功能只需新增一个实现类，再通过工厂或策略的注册机制让它自动接入，原有的调用代码无需改动。以支付模块为例，定义一个 PayService 接口，支付宝、微信各自实现它，之后要新增银行卡支付，只需新增一个实现类并注册到 Map 中，下单逻辑一行都不用改。在 Spring 中做法更简洁，给实现类加上 @Component 注解，容器会自动收集所有实现并以 List 或 Map 的形式注入，新增实现对已有代码几乎零侵入。需要注意的是，开闭原则不是要求一开始就把所有扩展点都设计好，而是在变化真正出现的地方抽象出扩展点，过度设计反而会增加复杂度。

### 13. 数组是「协变」的而泛型是「不变」的，怎么理解？【中频·加分】

> **知识点跳转：** [[泛型擦除]] · [[编译时类型和运行时类型可能不同]]

**追问：** ArrayStoreException 什么时候抛？

---

**参考答案 ✅**

先说定义。**数组是协变的**：String 是 Object 的子类型，那 `String[]` 就是 `Object[]` 的子类型——可以直接把 String 数组赋给 Object[] 引用。**泛型是不变的**：哪怕 String 是 Object 的子类型，`List<String>` 也不是 `List<Object>` 的子类型，互相赋值编译直接报错；想表达"某种未知类型的 List"要用通配符，比如 `List<? extends Object>`。

协变留下了一个著名的运行时漏洞：`Object[] arr = new String[3]; arr[0] = 123;`——编译完全通过（arr 的静态类型是 Object[]，存 Integer 语法合法），但运行时 JVM 会检查"数组的真实元素类型"，发现你要把 Integer 塞进 String 数组，直接抛 **ArrayStoreException**。也就是说，数组把类型检查**推迟到了运行时**。

泛型吸取了这个教训，选择**不变**——所有类型检查在编译期做完，换来的保证是"运行时绝不因为类型问题炸锅"。两组设计反映了两个时代的取舍：数组（Java 1.0）要兼容老代码、大量已有 API 依赖协变，只能背上运行时的锅；泛型（Java 5）是新加的，可以理直气壮地严格。

> **追问参考答：** 抛的时机：把"非 String 的元素"通过 Object[] 引用存进一个真实类型是 `String[]` 的数组时。要点两个：① 编译期只检查引用声明的静态类型——Object[] 存 Integer 语法合法，拦不住；② 运行期 JVM 才知道这块数组真实的元素类型是 String，于是抛 ArrayStoreException。这正是"协变数组不安全"的核心证据，也是泛型坚持不变的理由。

## 四、字符串与字符编码（2 题）

### 14. char 是几个字节？能存中文吗？为什么会乱码？【高频·笔试】

> **知识点跳转：** [[char 与 UTF-16 编码]]

**追问：** Unicode、UTF-8、UTF-16、GBK 之间是什么关系？

---

**参考答案 ✅**

char 是 2 字节，采用 UTF-16 编码。但需要先纠正一个概念：char 表示的是一个代码单元，并不总是一个完整字符。基本多文种平面（BMP）内的字符用一个 char 就能装下，而 emoji 和部分生僻字这类大码点字符，在 UTF-16 中需要两个 char 组成的代理对来表示，所以 "😀".length() 的结果是 2 而不是 1。String 的 length() 统计的也是 char 的个数，如果要按真正的字符个数计数，应使用 codePointCount。

中文可以存进 char 和 String。常用汉字都落在 BMP 中，一个 char 就能装下；少数扩展区的生僻字则需要两个 char。这里的"能存"是指 Unicode 层面，真正写入文件或通过网络传输时，还涉及编码转换，这一步处理不当才会出现乱码。

乱码的根本原因是编码和解码使用了不同的码表。写入时按某种编码把字符转成字节，读取时如果用另一种编码去解释这些字节，就会还原出错误的字符。例如 UTF-8 编码保存的中文，如果按 GBK 读取，就会出现"锟斤拷"这类典型乱码。因此原则是写和读必须使用同一种编码，跨系统传输数据时优先选择 UTF-8。

追问：Unicode、UTF-8、UTF-16、GBK 之间是什么关系？Unicode 是字符集，它为世界上每个字符分配一个唯一的码点编号；UTF-8、UTF-16、GBK 则是编码方式，负责把码点转换成字节的具体规则。UTF-8 是变长编码，每个字符占 1 到 4 个字节，并且完全兼容 ASCII，是互联网上的首选；UTF-16 以 2 或 4 个字节为单位，Java 中 char 的底层就是它；GBK 是面向中文环境的历史编码，占 1 到 2 个字节，不能覆盖其他语言的全部字符。同一个字符在不同编码下的字节形式完全不同，这正是编码不匹配就会乱码的根源。

### 15. 为什么密码建议用 char[] 而不是 String 来存？【中频·加分】

> **知识点跳转：** [[Java基础热门面试题-1#8. String 为什么设计成不可变的？不可变有什么好处？【高频】]] · [[Java基础面试题#String、StringBuffer、StringBuilder的区别和联系]]

**追问：** char[] 用完怎么处理？

---


密码用 char[] 存，核心是为了缩短明文在内存中的存在时间。String 是不可变对象，一旦创建，内容就固定了，而且 String 没有提供任何擦除内容的方法。密码放进 String 之后，这串明文会一直留在堆内存里，直到 GC 回收为止，而回收时机是不确定的。如果在这段时间内发生堆转储（heap dump），攻击者就能直接从内存中读到明文密码。

char[] 是可变数组，用完后可以逐个元素清零，比如 Arrays.fill(chars, '\0')，这样明文在内存中的停留窗口就从"等待 GC"变成了"主动擦除"。这也是 JDK 的做法，比如 JPasswordField.getPassword() 返回的就是 char[]，而不是 String。

需要说明的是，这种做法只是降低风险，并不能彻底消除。比如 JVM 在某些情况下可能复制数组内容，或者在 GC 时搬移对象，这些副本无法由程序控制。

>追问：char[] 用完怎么处理

用完之后应立即清零，即 Arrays.fill(password, '\0')，这样数组中就不再保留明文。同时要避免在处理过程中把它转成 String，因为一旦转换，String 就会另存一份明文，前面的清零就失去了意义。如果业务允许，更彻底的做法是根本不在内存中持有明文，例如客户端先对密码做加盐哈希再传输，服务端只保存和比对哈希值。

## 五、集合框架补充（4 题）

### 16. Java 集合框架的整体体系是怎样的？List、Set、Map 各自有什么特点？【高频】

> **知识点跳转：** [[Java基础面试题#java 容器都有哪些？]] · [[Deque 方法速记（栈 vs 队列）]]

**追问：** Queue 体系有哪些常见实现？

---

集合框架的顶层是两大接口，Collection 管理单列元素，Map 管理键值对，二者并不继承自同一个接口。Collection 下又分出 List、Set、Queue 三个分支。
List 有序、可重复、支持按索引访问，常用实现是 ArrayList，底层是动态数组，随机访问快，中间插入删除慢；LinkedList 是双向链表，两端操作快，随机访问慢；Vector 是历史遗留类，方法全部加锁，已基本淘汰。日常默认选 ArrayList。
Set 元素不重复，HashSet 底层就是 HashMap，靠 hashCode 定位、equals 判重；LinkedHashSet 在此基础上用双向链表保留插入顺序；TreeSet 底层是红黑树，元素按 Comparable 或 Comparator 排序。
Queue 用于队列与双端队列场景，ArrayDeque 是栈和队列的首选，性能优于 Stack 和 LinkedList；PriorityQueue 是基于堆的优先队列；BlockingQueue 一族用于并发阻塞场景，线程池的任务队列就是它。
Map 中，HashMap 最常用；LinkedHashMap 保留插入顺序，还能借助访问顺序实现 LRU；TreeMap 按 key 排序并支持范围查询；Hashtable 是历史遗留，整表加锁，已淘汰；ConcurrentHashMap 是并发场景的标准选择。

追问：Queue 体系有哪些常见实现？ArrayDeque 是双端队列，既能当队列也能当栈，它的方法分为 push、pop 这组栈风格和 offer、poll 这组队列风格，使用时注意不要混用。LinkedList 也实现了 Deque 接口，但性能不如 ArrayDeque。PriorityQueue 是小顶堆，出队顺序由优先级决定，常用于延时任务和 TopK 问题。BlockingQueue 家族包括 ArrayBlockingQueue、LinkedBlockingQueue、SynchronousQueue 等，带有阻塞语义，队列满或空时线程会等待，线程池的任务队列通常使用它们。

### 17. Comparable 和 Comparator 的区别？【高频】

> **知识点跳转：** [[Java基础面试题#有一个学生类，想按照分数排序，再按学号排序，应该怎么做？]]

**追问：** compareTo 返回 0 有什么坑？TreeSet/TreeMap 用什么排序？

---

**参考答案 ✅**

Comparable 和 Comparator 的区别在于排序逻辑的归属。Comparable 定义在类的内部，类通过实现它并重写 compareTo 方法，声明自己有一种天然的排序规则，例如 Integer 和 String 都实现了它。由于 Java 中一个类只能有一种自然排序，所以 Comparable 只适合表达唯一的、本身就可比较的顺序。Comparator 则定义在类的外部，是一个独立的比较器对象，通过重写 compare 方法实现，可以用匿名类或 Lambda 表达式来写，不侵入原有类，因此同一个类可以同时拥有多种排序规则。

两者的调用方式也不同。Collections.sort(list) 和数组的 Arrays.sort 默认使用 Comparable，而 list.sort(comparator) 以及 Stream 的 sorted(comparator) 则使用 Comparator。Lambda 让 Comparator 的组合变得非常简洁，比如要实现"分数降序、同分按学号升序"，可以写成 list.sort(Comparator.comparing(Student::getScore).reversed().thenComparing(Student::getId))。

选择时的原则是：如果类本身有唯一且稳定的自然顺序，比如时间、金额、学号这类本身可比较的值，就实现 Comparable；如果需要临时的排序、多种排序维度，或者不能修改原有类的源码，就使用 Comparator。同一个类要按不同维度排序时，Comparator 是唯一可行的方式。

关于 TreeSet 和 TreeMap 的排序，优先级是：构造时传入的 Comparator 最优先；未传入时使用元素的 Comparable 自然排序；两者都没有时，插入第一个元素就会抛出 ClassCastException。需要注意的是，TreeSet 和 TreeMap 判断两个元素是否相同，依据的是比较结果是否为 0，而不是 equals。如果比较器只比较了部分字段，比如只按分数比较，那么两个分数相同但学号不同的学生会被视为重复元素而被去掉一个，这是排序集合中很隐蔽的一个坑。解决办法是让比较口径能够区分不同的元素，例如分数相同时再比较学号，并尽量保持比较为 0 与 equals 相等的一致性。

> **补充：** 这里抛的不是"比较出错"，而是 TreeMap 的 put 在 root 为 null 时先做一次 `compare(key, key)` 自比较、把 key 强转成 Comparable 做类型检查，强转不成立。详见 [[ClassCastException 详解#场景 3：TreeMap / TreeSet 缺比较能力（最容易忽略的一个）]]。

另外，在实现比较逻辑时不要直接写 a - b，因为差值可能溢出，例如 Integer.MIN_VALUE 减去 1 会得到正数，导致排序结果反转，应当使用 Integer.compare(a, b) 或 Long.compare(a, b)。

### 18. LinkedHashMap 和 TreeMap 的底层是什么？怎么用 LinkedHashMap 实现 LRU？【中频】

> **知识点跳转：** [[HashMap Java 面试题完整详解（口述版）]]

**追问：** 手写 LRU 缓存的思路是什么？

---

LinkedHashMap 是在 HashMap 的基础上多维护了一条双向链表，把所有键值对按顺序串起来，因此既保留了哈希表 O(1) 的存取效率，又能有序遍历。链表的顺序有两种模式：默认是插入顺序；构造时传入 accessOrder 为 true，则变为访问顺序，每次 get 或 put 都会把对应节点移到链表尾部，这样链头自然就是最久没有被访问的节点。LRU（最近最少使用）缓存正是利用这一点实现的：继承 LinkedHashMap，构造时把 accessOrder 设为 true，再重写 removeEldestEntry 方法，在元素数量超过容量时返回 true，JVM 就会自动删除链头。十几行代码就能得到一个淘汰最久未使用项的缓存。

TreeMap 的底层是红黑树，增删查的时间复杂度都是 O(logN)，按 key 的自然顺序或 Comparator 排序。它的优势在于范围查询和有序操作，例如 firstKey、lastKey、headMap、tailMap、subMap，以及 ceilingEntry、floorEntry 等方法，这些都是 HashMap 无法直接提供的。

场景选择上，普通键值对使用 HashMap；需要保持插入顺序或实现 LRU 时使用 LinkedHashMap；需要按 key 排序或做范围查找时使用 TreeMap。

追问：手写 LRU 缓存的思路是什么？有两条路径。第一条是直接基于 LinkedHashMap 改造，设置 accessOrder 为 true 并重写 removeEldestEntry，这是面试中最快、最稳妥的写法。第二条是从零实现，用 HashMap 存储 key 到链表节点的映射，再自己维护一条双向链表：get 命中时把节点摘下并挂到链表头部；put 时新节点插入头部，若超出容量则删除尾部节点，尾部就是最久未使用的数据。无论哪种方式，核心动作都是每次访问都把节点移到头部。生产环境中做本地缓存时，通常会直接使用 Caffeine，它采用 W-TinyLFU 算法，命中率一般高于 LRU，在面试中提及这一点会是加分项。
### 19. Arrays.asList() 和 subList() 有哪些坑？【中频·加分】

> **知识点跳转：** [[Java基础面试题#如何实现数组和 List 之间的转换？]]

**追问：** 为什么 Arrays.asList 返回的 List 不能 add？

---

**参考答案 ✅**

这俩返回的都不是"正常集合"，而是**视图**——坑都从这儿来。

**Arrays.asList(array)**：返回的是 Arrays 内部的一个私有 List 实现，**大小固定**——可以 set 改元素，但 add、remove 直接抛 `UnsupportedOperationException`；而且它不是拷贝，是**原数组的视图**——改它也等于改原数组，反之亦然。要真正独立的、能增删的 List，包一层：`new ArrayList<>(Arrays.asList(...))`。

它还有个专门坑基本类型的大坑：`Arrays.asList(new int[]{1,2,3})` 得到的**不是**三个元素的列表，而是**只有一个元素**的 List——那个元素是整个 int[]。因为泛型不接受基本类型，int[] 被当成"一个 Object 元素"。用 Integer[] 或者先装箱才能得到期望结果。

**subList(from, to)**：返回原 List 某一段的**视图**（左闭右开）——对 subList 的修改会反映到原 List；反过来，原 List 一旦**结构性修改**（增删元素），再操作 subList 就抛 ConcurrentModificationException。要独立副本同样用 `new ArrayList<>(list.subList(...))` 拷出来。它的正经用法之一恰恰是"批量删一段"：`list.subList(a, b).clear()`——在视图上 clear，改的就是原 list。

> **追问参考答：** 因为 Arrays.asList 返回的 ArrayList **不是 java.util.ArrayList**，而是 Arrays 的内部类——它基于数组实现，只支持 set/get 这类"不改变大小"的操作；add/remove 走的是 AbstractList 的默认实现，直接抛 UnsupportedOperationException。所以"不能 add"不是 bug，是设计——它本来就承诺"映射到一个固定长度的数组"。要可变列表，`new ArrayList<>(Arrays.asList(...))`。

## 六、异常与资源（2 题）

### 20. try-with-resources 是什么？比 try-finally 好在哪？【中频·高频】

> **知识点跳转：** [[未关闭资源泄漏与元空间泄漏详解]]

**追问：** 多个资源关闭顺序？AutoCloseable 和 Closeable 的区别？

---

try-with-resources 是 Java 7 引入的语法，把需要释放的资源声明在 try 后面的括号里，代码块结束时无论正常结束还是抛出异常，都会自动调用资源的 close() 方法，不再需要手写 finally。使用前提是资源类实现 AutoCloseable 接口，或者实现它的子接口 Closeable。

它比 try-finally 好，主要体现在两点。第一是代码更简洁。手写 finally 时，每个资源都要在 try 外先声明变量并赋初值 null，finally 里逐个判空再调用 close，而 close 本身也可能抛异常，还要再包一层 try-catch。资源越多，嵌套越深，真正的业务逻辑反而被淹没。try-with-resources 把这些样板代码交给编译器生成，业务代码只剩资源声明和花括号里的逻辑。第二是异常不会丢失。手写 finally 的经典问题是：try 中业务抛出异常 A，finally 中 close 又抛出异常 B，B 会覆盖 A，最终只能看到 B，真正的原始问题被掩盖。try-with-resources 则会保留业务异常 A 原样抛出，close 抛出的异常 B 作为被压制异常附加在 A 上，通过 getSuppressed() 可以全部取到，原始问题不会丢失。

在外面 new，只要创建之后紧接着的代码不会抛异常，就不会有问题；但实际代码里创建之后往往还有可能抛异常的逻辑（比如第二个资源的创建、读写、初始化），这些逻辑如果不在保护范围内，前面已经打开的资源就关不掉。把 new 放进 try，本质上是让"创建"和"关闭的保护"在同一个作用域里同时生效，避免中间出现不受保护的空窗期。赋 null 则是为了让 finally 能访问变量并区分哪些资源已经创建成功。

从本质上说，try-with-resources 是语法糖，编译器会把它展开成包含 finally 和 addSuppressed 调用的等价代码。手写同样的逻辑当然也可以，但编译器生成的版本不会遗漏判空，也不会出现笔误。

关于多个资源的关闭顺序，资源按照声明的相反顺序关闭，即后声明的先关闭。比如 try (A a = ...; B b = ...) 会先关闭 b，再关闭 a，这与栈的后进先出一致，因为后创建的资源往往依赖先创建的资源，先释放依赖方才是安全的。

AutoCloseable 和 Closeable 的区别在于约束强度。Closeable 是 AutoCloseable 的子接口，它的 close() 声明抛出 IOException，并且约定重复调用 close 不产生副作用，即幂等。AutoCloseable 的 close() 声明抛出 Exception，范围更宽，也不要求幂等。任何需要释放的资源只要实现 AutoCloseable 就能用于 try-with-resources，而 Closeable 更多用于 I/O 相关的资源。
### 21. 异常处理有哪些最佳实践？什么时候 throws、什么时候 catch？【中频】

> **知识点跳转：** [[Java基础面试题#throws和try-catch如何选择？各自适用于什么场景？]]

**追问：** 什么是异常链？为什么要"包装异常"？

---

**参考答案 ✅**

我总结成几条。

第一，**选对异常类型**：调用方能恢复、属于预期内的外部失败（IO、网络、参数校验），用受检异常强制处理；程序 bug 类（空指针、状态非法），用运行时异常，靠修代码不是靠 catch。第二，**不要吞异常**——catch 块里什么都不做是最糟的写法，至少记日志或向上抛；吞掉异常等于把问题埋进坟墓。第三，**不要用异常控制流程**——能做 if 判断的别用"抛了再 catch"来实现，构造异常栈的开销大、可读性也差。第四，**try 块尽量小**——只包真正可能抛异常的语句，全裹进去会误捕、也难定位。第五，**早抛出、晚捕获**——第一现场发现问题就抛，留给能真正处理它的那层去 catch，中间层不掺和。第六，**资源释放交给 try-with-resources**，别在 finally 里 return 或抛异常（会覆盖原结果）。

throws 还是 catch：**能处理就 catch，处理不了就 throws**。本层能兜底（有降级方案、要转成业务异常、要记日志终止流程）就捕获；本层无能为力——比如工具方法查库失败，不知道上层要不要重试——就声明抛出，把决策权交给上层。中间层只是"路过"时别 catch 完再原样抛，那只会污染堆栈。

> **追问参考答：** **异常链**是把原始异常包在新异常里带着走：`throw new BizException("下单失败", e);`——把原因 e 作为 cause 传进去。上层看到的是"业务语义清晰的异常"，同时通过 `getCause()` 还能一路追到最底层的真实原因（比如某个 SocketTimeout）。为什么要包装：① **分层语义**——DAO 层抛 SQLException 太底层，Service 包装成业务异常，上层好理解好处理；② **保留现场**——堆栈链条完整，排查不难。反例是"不传 cause 就抛新异常"，排查时只见新异常、丢失底层真相。

## 七、IO 与文件（2 题）

### 22. Java 的流分为几种？字节流和字符流有什么区别？【高频】

> **知识点跳转：** [[Java基础面试题#Java 中流分为几种]]

**追问：** 缓冲流为什么快？flush 和 close 是什么关系？

---

**参考答案 ✅**

两个分类维度。按方向分**输入流/输出流**；按处理单位分**字节流和字符流**——这是重点。

**字节流**：InputStream/OutputStream 体系，以 byte（8 位）为单位读写，**什么文件都能处理**——图片、音频、视频、class 文件。**字符流**：Reader/Writer 体系，以 char（16 位）为单位读写，**专门处理文本**，内部负责字节与字符之间的编码转换。

为什么要有字符流？核心就是**编码**。字节流按字节读，一个中文在 UTF-8 里占 3 个字节，你得自己处理"读几个字节拼成一个字"的麻烦，还得知道编码是什么；字符流在桥接时可以**显式指定编码**，read() 出来直接是字符，转换交给它做。所以处理文本用字符流 + 明确指定编码；处理二进制必须字节流。经典模板：`new BufferedReader(new InputStreamReader(new FileInputStream(path), StandardCharsets.UTF_8))`——字节流读文件、转换流解编码、缓冲流加缓冲。

另一个维度是**节点流 vs 处理流**：节点流直接连数据源（FileInputStream、ByteArrayInputStream）；处理流包装别的流加能力（Buffered 系加缓冲、Data 系读写基本类型、Object 系做序列化、GZIP 系做压缩）。这就是**装饰器模式**在 Java IO 里的体现——一层层套、功能叠加，底层接口不变。

> **追问参考答：** 缓冲流快在**减少系统调用**：不带缓冲时每次 read 都是一次系统调用（可能触发磁盘 IO）、一次拿一个字节，开销巨大；BufferedInputStream 一次系统调用读进一整块（默认 8KB）放内存，之后你的 read 都从内存拿，系统调用次数从"字节数量级"降到"块数量级"，快几个量级。flush 和 close 的关系：flush 是把缓冲区里**还没写出去**的数据立刻推给底层；close 会**先 flush 再释放资源**。手动 flush 的场景是"写完一部分要让对方立刻收到"（网络对讲式交互）；忘了 flush 又直接断开，缓冲区数据就丢了。记住 close 之后流不可再用。

### 23. 什么是零拷贝？Java 里怎么用？【中频·加分】

> **知识点跳转：** [[OS-IO篇]] · [[DirectByteBuffer与堆外内存回收]]

**追问：** 为什么 Kafka 的读写性能这么高？

---

**参考答案 ✅**

先讲传统 IO 的成本。把文件发到网络（读文件再写 socket），传统方式要经历**四次拷贝、四次上下文切换**：磁盘 → 内核页缓存（DMA 拷贝）；内核页缓存 → 用户缓冲区（CPU 拷贝）；用户缓冲区 → socket 缓冲区（CPU 拷贝）；socket 缓冲区 → 网卡（DMA 拷贝）。中间两次 CPU 拷贝和用户/内核来回切换全是浪费——数据只是"路过"用户空间，用户态根本没碰它。

**零拷贝就是消掉这些冗余拷贝**，常见三层技术：① **mmap + write**——把内核页缓存映射进用户空间，用户态读它不发生复制，省掉"内核 → 用户"那次拷贝（拷贝 4 变 3），Java 对应 MappedByteBuffer；② **sendfile**——文件到 socket 全程留在内核里完成，不再经过用户空间（拷贝变 2 次），Java 对应 `FileChannel.transferTo/transferFrom`；③ **sendfile + 网卡 SG-DMA**（Linux 2.4+）——连"页缓存 → socket 缓冲区"那次拷贝都省了，网卡直接从页缓存取数、只传描述符，这才是严格意义的零拷贝（CPU 完全不碰数据）。

Java 的入口：FileChannel.transferTo（底层 sendfile，Kafka 消费端就靠它）、MappedByteBuffer（mmap）、DirectByteBuffer（堆外内存，避免堆内到堆外那次拷贝）。用得上的都是"大文件、高吞吐"场景：Kafka、RocketMQ 的消息投递、Netty 的文件传输、静态文件服务器。

> **追问参考答：** Kafka 快不只是零拷贝，是三件事叠加：① **顺序写**——消息追加到日志尾部，磁盘顺序写性能接近内存随机写；② **页缓存**——读写优先打在内核页缓存，避免随机磁盘 IO；③ **零拷贝**——消费端投递用 transferTo（sendfile），数据不出内核、没有用户态来回拷贝和上下文切换。所以答"Kafka 为什么快"，把"顺序写 + 页缓存 + 零拷贝 + 批量压缩"这套组合拳说出来才完整。

## 八、反射与代理（3 题）

### 24. JDK 动态代理的原理是什么？【高频】

> **知识点跳转：** [[Java基础面试题#代理模式和适配器模式有什么区别？]] · [[设计模式（笔试面试常考）#代理模式与 AOP]]

**追问：** 静态代理和动态代理的区别？MyBatis 的 Mapper 接口为什么不用写实现类？

---

**参考答案 ✅**

JDK 动态代理的核心是"**运行时生成代理类**"。入口是 `Proxy.newProxyInstance(classLoader, interfaces, handler)`——传三样：类加载器、要实现的接口数组、以及一个 **InvocationHandler**。返回的代理对象**实现了你指定的所有接口**。

关键在第三个参数。代理对象上的**每一次方法调用**，都会被统一转发到 `handler.invoke(proxy, method, args)`。你在这个 invoke 里可以做任何增强——方法前后打日志、开事务、鉴权——然后用 `method.invoke(target, args)` 反射调真实对象的对应方法。**所有方法的增强逻辑只写一处**，这是动态代理比静态代理的本质优势。

生成机制上，Proxy 内部会**动态生成字节码**（代理类实现目标接口、持有你的 handler），再加载成类、实例化——所以 debug 时会看到 `$Proxy0` 这样的类名。

限制只有一个：**只能代理接口**。因为动态生成的代理类已经继承了 Proxy 类（Java 单继承没得商量），没有位置再继承你的目标类——所以目标必须通过接口被代理。

> **追问参考答：** 静态代理类是**编译期手写**的——一个接口配一个代理类，接口一多、类一多，代理类数量爆炸，而且每个代理类里的增强代码还是重复的；动态代理在**运行时统一生成**，一套 InvocationHandler 处理所有方法，新增接口或方法不用改代理代码。MyBatis 的 Mapper 就是动态代理的经典应用：我们只写 `UserMapper` 接口、**不写实现类**，MyBatis 运行时用动态代理生成实现——任何方法调用都被转发进 MapperProxy 的 invoke，它按"接口全名 + 方法名"找到对应的 SQL 去执行。所以"只写接口就能查数据库"这个魔法，底层就是动态代理。

### 25. JDK 动态代理和 CGLIB 动态代理有什么区别？【高频】

> **知识点跳转：** [[Java基础面试题#代理模式和适配器模式有什么区别？]]

**追问：** Spring AOP 里怎么选？

---

**参考答案 ✅**

核心区别一句话：**JDK 动态代理基于接口，CGLIB 基于继承**。

JDK 的方案：`Proxy.newProxyInstance` 生成一个**实现目标接口**的代理类，通过 InvocationHandler 转发调用——**要求目标必须有接口**。CGLIB 的方案：**动态生成目标类的子类**、重写非 final 方法，通过 MethodInterceptor 拦截——**不需要接口**，普通类也能代理；但反过来**不能代理 final 类**（没法继承）、**拦不了 final/private 方法**（没法重写）。CGLIB 底层用 ASM 操作字节码，属于第三方库（Spring 内嵌了它）。

性能上现在的结论是"**差距不大、别背老结论**"：早期 CGLIB 调用快、JDK 创建快；JDK 8 之后 JDK 代理优化过，调用性能追上来了，日常业务里这点差异可以忽略。真正要背的取舍是：**有接口优先 JDK（标准库自带、规范）；没接口或必须对类代理用 CGLIB**。

> **追问参考答：** Spring AOP 的选择规则：目标类**实现了接口**默认用 **JDK 动态代理**；**没有接口**用 **CGLIB**（生成子类）。Spring Boot 2.x 之后默认改成**强制 CGLIB**（`spring.aop.proxy-target-class=true`）——目的是统一行为，避免"按接口注入时是 JDK 代理、按实现类注入又报错"这类兼容困惑；业务类写不写接口都能被切面拦到。总结成一句：**Spring 里默认"有接口 JDK、无接口 CGLIB"，Boot 2.x 起默认 CGLIB**——把这条演变讲出来就是亮点。

### 26. 怎么自定义一个注解？元注解有哪些？【中频】

> **知识点跳转：** [[注解原理详解]] · [[Java基础面试题#Java注解的作用域呢？]]

**追问：** 注解定义出来是怎么"生效"的？

---

**参考答案 ✅**

先讲定义。用 `@interface` 声明——本质是一个**继承了 java.lang.annotation.Annotation 的接口**。注解的"属性"写成方法形式、可以有默认值，比如：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    int permits() default 10;
    String key() default "";
}
```

使用时给属性赋值：`@RateLimit(permits = 5)`——属性名叫 value 时可以省略 `value=`、直接写值。

然后是**元注解**——"修饰注解的注解"，四个核心：**@Target** 管"能用在哪"（TYPE 类、METHOD 方法、FIELD 字段、PARAMETER 参数、CONSTRUCTOR 构造器……）；**@Retention** 管"活到什么时候"（SOURCE 只留源码、CLASS 编进字节码但反射不可见[默认]、RUNTIME 运行时保留——**要反射读就必须 RUNTIME**）；**@Documented** 进 javadoc；**@Inherited** 子类可继承（只对类注解生效）。Java 8 还加了 **@Repeatable**，支持同一处重复标注。

> **追问参考答：** 注解本身**什么都不做**——它只是"贴在代码上的标签"，真正干活的是"读标签的人"，共三种读法：① **运行时反射**——框架用 getAnnotation() 读，要求 RUNTIME（Spring 的 @Autowired、@Transactional）；② **编译期注解处理器 APT**——javac 编译时扫描、生成代码或报错（Lombok、MapStruct）；③ **字节码工具**——编译后或加载期改写。所以自定义注解要"生效"，通常要配一个处理它的组件——最常见的组合是"**自定义注解 + AOP 切面**"：切点匹配标注了注解的方法，切面里读出注解参数（比如限流阈值）、执行增强逻辑（比如按 key 限流）。@Transactional 就是这个套路——**注解负责"声明"，切面负责"实现"**。

## 九、新版本特性（2 题）

### 27. Java 8 之后有哪些重要新特性？（9 ~ 21）【中高频】

> **知识点跳转：** [[文本块（Text Blocks）]] · [[sealed class]] · [[Record类详解]] · [[Java基础面试题#Java 21 新特性知道哪些？]]

**追问：** record 和 Lombok 有什么区别？

---

**参考答案 ✅**

先说版本节奏：Java 8 之后改成**每半年一版**，其中 LTS（长期支持版）是 **11、17、21**——现在面试和项目主要盯 17 和 21。

按版本挑重点。**JDK 9**：模块化系统（JPMS）、接口可以有 private 方法、集合工厂（`List.of()`/`Map.of()`）、G1 成为默认 GC。**JDK 10**：**var** 局部变量类型推断。**JDK 11（LTS）**：HttpClient 转正（告别 HttpURLConnection）、String 新增 isBlank/strip/repeat 等方法。**JDK 14**：**switch 表达式**转正（箭头语法、可直接产出值）。**JDK 15**：**文本块**转正（`"""` 多行字符串）。**JDK 16**：**record** 转正、**instanceof 模式匹配**转正。**JDK 17（LTS）**：**sealed class**（密封类）转正。**JDK 21（LTS）**：**虚拟线程**转正、switch 模式匹配、记录模式（record 解构）、分代 ZGC。

挑几个语言层最常用的展开：**var**——编译器按右边推类型，省写但不牺牲类型安全（编译期就定死）；**record**——一行 `record Point(int x, int y) {}` 自动获得构造器、访问器、equals/hashCode/toString；**switch 表达式 + 模式匹配**——case 箭头直接返回值、还能按类型匹配（`case String s ->`）；**sealed**——用 permits 白名单限制"谁能继承我"，是构建封闭类型体系（配合穷尽性检查）的基础。

> **追问参考答：** record 和 Lombok 的区别：① **层级不同**——record 是**语言级**特性（javac 原生支持、IDE 无需插件），Lombok 是**第三方编译期插件**（注解处理器改语法树，属非标准做法）；② **能力不同**——record 只能做"不可变数据载体"（final 类、字段全 final、没有 setter、不能继承），Lombok 的 @Data 生成可变对象的 getter/setter、支持继承；③ **语义不同**——record 表达"一组不可变的值的集合"这个设计意图，还能配合模式匹配解构；Lombok 更多是"少写样板代码"的工具。结论：**"只读数据载体"优先 record；需要可变/继承/复杂行为的类才用 Lombok**。

### 28. 虚拟线程是什么？和平台线程有什么区别？【高频·新】

> **知识点跳转：** [[虚拟线程详解]]

**追问：** 为什么虚拟线程能提升吞吐？适合什么场景？

---

**参考答案 ✅**

虚拟线程是 **JDK 21 转正的轻量级线程**——由 JVM 调度，不再是"一个 Java 线程对一个操作系统线程"的 1:1 模型。

先看传统**平台线程**的问题：每个 Java 线程都绑定一个 OS 线程，栈 MB 级、创建销毁昂贵，线程数只能到几千；更亏的是线程**阻塞在 IO 上时**（等网络、等数据库），那个 OS 线程被占着**空等**——硬件线程全被"等待"浪费了。

虚拟线程的机制：栈在**堆上按需增长**（KB 级起步），可以创建**百万级**；运行时挂在**载体线程**（carrier，真正的平台线程）上执行——一遇到阻塞 IO，JVM 把虚拟线程**卸载（unmount）** 出去，载体立刻去跑别的虚拟线程，IO 就绪再调度回来。所以"阻塞"的成本从"占住一个 OS 线程"变成"换一个任务继续跑"——等待不再浪费内核线程。用法上不用池化：虚拟线程廉价、用完即弃，一个任务 new 一个，或 `Executors.newVirtualThreadPerTaskExecutor()`。

> **追问参考答：** 提升吞吐的本质是"**并行度不变、但等待不再浪费线程资源**"——CPU 核数没变、计算能力没变，变的是 IO 等待期的利用率：以前几千线程里大多数在阻塞等 IO，现在百万虚拟线程共享少量载体线程，把等待的空窗填满了。适合**IO 密集型**：Web 服务、RPC、数据库访问——用同步写法拿到接近异步的吞吐。**不适合 CPU 密集型**：纯计算不需要挂起/恢复，还是平台线程。两个坑：JDK 21~23 里 `synchronized` 块中阻塞会**钉住（pin）** 载体线程（JDK 24 已修复；官方建议热路径优先 `ReentrantLock`）；别把虚拟线程塞进线程池——池化的意义是复用昂贵资源，它不昂贵。

## 十、综合与加分（4 题）

### 29. SimpleDateFormat 为什么线程不安全？怎么替代？【中频】

> **知识点跳转：** [[Java 8 日期时间 API（java.time）]]

**追问：** DateTimeFormatter 为什么线程安全？

---

**参考答案 ✅**

根因：SimpleDateFormat 内部有一个 **Calendar 对象作为共享的可变状态**，parse 和 format 都在它上面干活——先 set、再读，中间步骤多。单线程没问题；**多线程并发用同一个实例**时，两个线程的 set/read 相互穿插，Calendar 里的数据被算乱：结果可能是错误日期、可能抛 NumberFormatException、也可能解析出离谱的值。JDK 文档明确写了它不是线程安全的、要求"每个线程用独立实例"。

经典事故场景：有人把 `static final SimpleDateFormat` 定义成工具类常量——看着省事，并发一上来就是定时炸弹。

替代方案四个：① **每次用就 new**——不会错，但频繁创建有小开销；② **加锁**——安全但并发差；③ **ThreadLocal 每线程一个实例**——Java 8 之前的经典解法；④ **换成 java.time 的 DateTimeFormatter**——**推荐**：不可变、天生线程安全，一次创建到处共享。

> **追问参考答：** DateTimeFormatter 线程安全的根因就是**不可变**——没有可变共享状态，所有字段 final，format/parse 都不修改自身，任何线程任何时刻读它都是稳定的，所以能放心做成静态常量。顺带把 java.time 的优点说全：① 不可变 + 线程安全（对比 Date 可变、SimpleDateFormat 不安全）；② 语义清晰——LocalDate 是日期、LocalDateTime 是无时区时间、Instant 是确定时刻、ZonedDateTime 带时区，不像 Date 把时间戳和语义混在一起；③ 链式 API（plusDays/withYear）；④ 月份从 1 开始（Date 从 0 开始，历史大坑）。新代码直接用 java.time，老 Date 只在遗留接口边界转换。

### 30. 方法引用有哪几种形式？和 Lambda 是什么关系？【中频】

> **知识点跳转：** [[Java基础面试题#方法引用]] · [[Java基础面试题#两种实例方法引用的区别]]

**追问：** `String::length` 和 `str::length` 有什么区别？

---

**参考答案 ✅**

方法引用是 Lambda 的**语法糖缩写**：当一个 Lambda 的"函数体"只是调用一个现成的方法时，直接引用方法名更简洁——`s -> System.out.println(s)` 等价于 `System.out::println`。和 Lambda 一样，必须在**函数式接口**的上下文里才能用。

四种形式：① **静态方法引用**——`Integer::parseInt`，等价 `s -> Integer.parseInt(s)`；② **实例方法引用（绑定具体对象）**——`System.out::println`、`str::length`，对象是固定的；③ **实例方法引用（未绑定，第一个参数当接收者）**——`String::length`，等价 `s -> s.length()`；④ **构造器引用**——`User::new`，等价 `(name, age) -> new User(name, age)`；另外还有数组构造器 `String[]::new`。

判断标准就一条：**Lambda 的参数和返回值签名能直接对上目标方法的签名**——对上就能换成方法引用。

> **追问参考答：** 两者是不同形式：`str::length` 是**绑定**的方法引用——str 是已存在的对象，调用者被写死，等价于无参方法 `() -> str.length()`；`String::length` 是**未绑定**的——自己没有对象，把"方法调用者"当第一个参数，签名是 `(String) -> int`。记忆法：**冒号左边是"类名"且方法是实例方法 → 未绑定（参数补位当调用者）；冒号左边是"变量/表达式" → 绑定（对象固定）**。这正是"两种实例方法引用的区别"的标准答案。

### 31. 如何设计一个不可变类？【高频】

> **知识点跳转：** [[Java基础热门面试题-1#8. String 为什么设计成不可变的？不可变有什么好处？【高频】]]

**追问：** 不可变对象有什么好处？

---

**参考答案 ✅**

不可变类就是"**实例创建后状态不能再变**"的类。设计要点五条：

① **类声明为 final**——防止子类加可变状态、或重写方法破坏不变性；② **所有字段 private final**——外部碰不到、只赋值一次；③ **不提供任何修改状态的方法**（没有 setter、没有"改自己"的操作）；④ **构造时对可变参数做深拷贝**——如果构造器接收数组、集合、Date 这类可变对象，不能直接存引用（外部改了它、我就跟着变），要拷一份进来；⑤ **对外返回可变字段时返回拷贝**——getter 不能直接把内部可变对象交出去，否则外部拿到就能改内部状态。

前三条保"我没法被改"，后两条堵"别人拿着我的内部引用去改"——五个洞全堵上才是严格不可变。典型例子：**String**（final 类 + private final 数组 + 无修改方法 + 构造时自建数组）、**包装类全家**、**java.time 全家**；还有 **record**——语言级快捷方式，字段 final、无 setter（但如果字段是可变对象，④⑤ 还得自己补）。

> **追问参考答：** 好处三条：① **线程安全**——状态不能变，天生没有并发问题，随便共享、无需加锁（最大的价值）；② **可安全共享和缓存**——适合当 Map 的 key（hashCode 永远稳定）、可做常量池/缓存；③ **可读可推理**——对象"长什么样"从创建起永远不变，读代码不用追"它中途被谁改了"。代价是"修改"必须创建新对象（String 拼接就是典型），所以适合值语义的类（金额、坐标、时间），不适合高频变更的状态载体。

### 32. SPI 是什么？原理是什么？【中频·加分】

> **知识点跳转：** [[SPI详解]]

**追问：** SPI 和类加载器有什么关系？

---

**参考答案 ✅**

SPI 是 Service Provider Interface——JDK 内置的**服务发现机制**：接口方定义规范、多个实现方各自提供实现、运行时自动发现加载。解决"**框架要用某个能力，但编译期不知道用哪个实现**"的问题——把"选实现"推迟到运行时，实现面向接口 + 插拔式扩展。

三要素：① **接口**（如 `java.sql.Driver`）；② **实现类**（MySQL 驱动、PG 驱动各一份）；③ **配置文件**——各自 jar 的 `META-INF/services/` 目录下，文件名是**接口的全限定名**，内容是实现类的全限定名（一行一个）。

加载流程：`ServiceLoader.load(接口.class)` 去**所有 classpath jar 里**找这个配置文件，读实现类名、反射实例化、返回可遍历的实现列表。调用方只依赖接口；加一个实现 jar 就多一份能力——**零改代码、即插即用**。最经典的例子是 **JDBC 驱动加载**：MySQL 驱动 jar 里就带着 `META-INF/services/java.sql.Driver`，DriverManager 启动时用 ServiceLoader 把驱动发现出来——所以你连 Class.forName 都不用写，驱动就在那儿了。

局限也要知道：Java 原生 SPI **一次性加载所有实现**（不能按需、没有优先级），Dubbo 为此实现了改进版 SPI（按名字按需加载 + wrapper 包装）——提这点是加分项。

> **追问参考答：** 关系在**类加载器**上，这是 SPI 的高阶考点：接口（java.sql.Driver）在 JDK 核心库里、由**启动类加载器**加载；实现类（MySQL 驱动）在**应用类路径**的第三方 jar 里——启动类加载器看不见这些 jar。按双亲委派，父加载器加载的类要引用子加载器才能看见的类，就"够不着"。SPI 的解法是 **ServiceLoader 默认用线程上下文类加载器（TCCL）** 去加载实现——TCCL 默认是应用类加载器、能看见所有业务 jar，相当于"父加载器借用子加载器的视野"，这就是"打破双亲委派"的经典场景之一。（TCCL 的完整机制在类加载专题展开，这里记结论：**SPI 靠 TCCL 拿到实现类**。）

### 33. AtomicLong 的底层原理是什么？为什么性能好？【高频·面试真题】

> **知识点跳转：** [[AtomicLong 底层原理与高性能原因]]

**追问：** AtomicLong 有什么缺点？高并发计数该用哪个？

---

**参考答案 ✅**

AtomicLong 的底层是 **volatile 值 + CAS 自旋**两件事拼起来的。它内部持有一个 `volatile long value`，volatile 负责可见性——一个线程改完别人立刻看得见；但 volatile 只管"看得见"、管不了"不重叠"，所以真正的原子性靠 CAS：调 `Unsafe` 的 native 方法 `compareAndSetLong`，往下是 CPU 的 `cmpxchg` 指令，由硬件保证"比较并交换"这一步不会被打断。所以 `incrementAndGet()` 就是个自旋循环：读出旧值、加一、CAS 写回；如果 CAS 失败，说明在我读和写之间被别的线程改过、旧值已经作废，那就重新读、重新算、再试一次。

它性能好，根因在于 **CAS 失败不阻塞线程**。加锁慢不在"加锁"这个动作本身，而在竞争失败之后线程要**挂起、等操作系统唤醒**——那是一次用户态到内核态的上下文切换，比自增本身的计算开销高几个数量级。CAS 全程留在用户态重试，不陷入内核、不依赖 OS 调度，也**天然不会死锁**（没有"持有锁"这回事）。所以**低到中等竞争、临界区极短**的场景，它明显优于锁。

代价这另一半也要说：① **高并发下大量 CAS 失败会自旋烧 CPU**——几百个线程抢同一个计数器，大部分 CAS 都失败，CPU 打满但业务没进展，这时候阻塞反而更优；② **只能原子一个变量**，多个变量一起改得用 `AtomicReference` 打包或加锁；③ **ABA 问题**——值 A→B→A，CAS 看不出中间变过，计数器场景无影响，但无锁栈这类依赖中间过程的结构会真的坏掉。

> **追问参考答：** 高并发计数要换 **LongAdder**。它维护一个 `base` 加一个 `Cell[]` 数组，写的时候线程按哈希落到自己那个 Cell 上做 CAS——不同线程大概率落在不同 Cell，等于把"一个热点"拆成"多个冷点"，冲突概率降到 1/N，竞争激烈时 Cell 数组还会扩容（上限约等于 CPU 核数）。读 `sum()` 时把 base 和所有 Cell 加起来。取舍是：**LongAdder 吞吐高，但 sum() 只是近似值**（求和时可能有线程正在改别的 Cell），而且**没有 compareAndSet 语义**。所以选型一句话——**要精确值、要做状态机用 AtomicLong；只要高并发累加的统计值（QPS 打点、监控计数）用 LongAdder**。顺带提一句：`ConcurrentHashMap` 1.8 的 `size()` 用的就是这套思想（详见 [[ConcurrentHashMap_1.7_vs_1.8]]）。
