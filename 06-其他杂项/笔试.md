![image-20260420101911706](C:\Users\q1948\Desktop\八股\images\image-20260420101911706.png)

正确答案是 **D. RK算法**。

在字符串匹配算法中，不同算法通过不同的策略来提高匹配效率。以下是各选项的简要分析：

### 1. RK 算法 (Rabin-Karp Algorithm)

这是本题的正确选项。**RK 算法的核心思想就是利用哈希（Hash）函数**。

- **原理**：它先计算模式串的哈希值，然后依次计算主串中每一个长度等于模式串的子串的哈希值。
- **优势**：通过比较哈希值而不是逐个字符比较，可以快速排除大部分不匹配的情况。只有当哈希值相同时，为了防止“哈希冲突”，才会进行逐个字符的精确匹配。

### 2. KMP 算法 (Knuth-Morris-Pratt Algorithm)

- **原理**：KMP 算法是基于**前缀函数（Next 数组）**实现的。
- **特点**：它利用已匹配的部分信息，通过预处理模式串来寻找“最长相等前后缀”，从而在不匹配时让模式串向后滑动尽可能远的距离，避免了主串指针的回溯。它并不依赖哈希。

### 3. BM 算法 (Boyer-Moore Algorithm)

- **原理**：BM 算法主要基于**坏字符规则（Bad Character Rule）\**和\**好后缀规则（Good Suffix Rule）**。
- **特点**：它通常从模式串的末尾开始向前匹配，是目前在实际文本编辑器中应用最广泛的高效算法之一，同样不涉及哈希计算。

### 4. BF 算法 (Brute Force)

- **原理**：即**暴力匹配算法**。
- **特点**：通过简单地将模式串与主串的每一位进行比对，没有任何复杂的预处理或数学优化。

------

**总结表：**

| **算法名称**         | **核心机制**         | **是否使用哈希** |
| -------------------- | -------------------- | ---------------- |
| **BF (Brute Force)** | 逐位比对             | 否               |
| **KMP**              | 前缀函数 (Next 数组) | 否               |
| **BM**               | 坏字符 + 好后缀规则  | 否               |
| **RK (Rabin-Karp)**  | **哈希指纹对比**     | **是**           |

正确答案是 **D. 原子性 (Atomicity)**。

在数据库管理系统中，事务（Transaction）具有四个基本特性，即 **ACID**。题目描述的正是其中“要么全做，要么全不做”的核心逻辑。

### 详细解析：

- **原子性 (Atomicity)**：
  - **定义**：事务被视为一个不可分割的最小工作单元。
  - **表现**：事务中的所有操作要么全部提交成功（All），要么全部失败回滚（None）。如果事务在执行过程中发生错误，会被恢复（Rollback）到事务开始前的状态，就像这些操作从未执行过一样。
  - **关键词**：所有操作完成、回滚恢复。

------

### 干扰项对比：

- **A. 持久性 (Durability)**：

  指事务一旦提交，它对数据库中数据的改变就应该是**永久性**的，即使系统发生故障（如断电、崩溃）也不会丢失。

- **B. 一致性 (Consistency)**：

  指事务执行前后，数据库都必须处于**一致性状态**。例如，在银行转账事务中，无论操作成功与否，两个账户的总额必须保持不变。它是事务追求的最终目标。

- **C. 隔离性 (Isolation)**：

  指多个事务并发执行时，一个事务的执行不应影响其他事务。每个事务都感觉不到系统中有其他事务在并发执行（通常通过**锁**或 **MVCC** 机制实现）。

------

### 总结对照表：

| **特性**       | **核心关注点**                 | **题目对应描述**                |
| -------------- | ------------------------------ | ------------------------------- |
| **原子性 (A)** | **完整性**：要么全有，要么全无 | "所有操作均已完成" / "回滚恢复" |
| **一致性 (C)** | **正确性**：符合预设逻辑和约束 | 状态转换的正确性                |
| **隔离性 (I)** | **独立性**：并发事务互不干扰   | 多个事务同时运行的相互影响      |
| **持久性 (D)** | **可靠性**：结果永久保存       | 故障后数据不丢失                |

> "为了防止多个处理器同时访问和修改同一块内存区域，可以采取**分页机制**"

- **分页机制** 的作用是：虚拟地址到物理地址的映射、内存隔离、实现虚拟内存。它解决的是**地址空间隔离**问题，而不是多核并发访问的同步问题。

分页机制根本不具备协调多核并发写入的能力，所以 **A 错误**。

这道题考查的是操作系统中**动态分区分配算法**（Dynamic Partitioning Allocation）的实现逻辑。

正确答案是 **A、D**。

这里的关键在于：算法在寻找空闲内存块时，是按照**什么顺序**去扫描空闲分区链（或表）的。

------

### 详细解析

#### A. 首次适应算法 (First Fit, FF) —— **符合题意**

- **排列方式**：空闲分区按**地址递增**的顺序链接。
- **逻辑**：分配内存时，从链首开始顺序查找，直到找到第一个大小能满足要求的空闲分区。
- **目的**：这种排列方式使得低地址部分被尽可能快地利用，保留了高地址部分的大空闲区。

#### D. 邻近适应算法 (Next Fit, NF) —— **符合题意**

- **排列方式**：同样要求空闲分区按**地址递增**的顺序排列（通常是一个循环链表）。
- **逻辑**：源自首次适应算法，不同之处在于它从**上次查找结束的位置**开始继续查找。
- **目的**：为了减少首次适应算法中频繁扫描低地址小分区的开销，使分区分配得更均匀。

------

### 为什么 B 和 C 是错误的？

这两个算法是按照**“大小”**而非“地址”排列的：

- **B. 最佳适应算法 (Best Fit, BF)**：
  - **排列方式**：空闲分区按**容量递增**的顺序排列。
  - **逻辑**：每次都寻找能满足要求的、且与请求大小最接近的最小分区，这能尽量减少内部碎片，但会产生很多难以利用的极小外部碎片。
- **C. 最坏适应算法 (Worst Fit, WF)**：
  - **排列方式**：空闲分区按**容量递减**的顺序排列。
  - **逻辑**：每次都直接查看链表第一个分区（即最大的空闲区），如果第一个都放不下，就说明分配失败。这样剩下的空闲区依然较大，但容易把大分区很快用光。

### 💡 记忆小贴士

- **按地址排**：为了“找得快”（FF）或“用得匀”（NF）。
- **按大小排**：为了“找得准”（BF）或“用得爽”（WF）。

看来你在动态分区这块容易把“地址顺序”和“大小顺序”记混，做题时可以先在脑子里画一个内存条，想象一下 FF 总是从顶端（低地址）往下找的情景。





## 5.BufferedReader和StringTokenizer

```java
import java.util.HashSet;
import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.util.StringTokenizer;

class Good {
    String name;
    int weight;
}

public class Main {

    public static void merge(Good[] arr, int left, int mid, int right, Good[] tem) {
        int i = left, j = mid + 1, t = 0;
        while (i <= mid && j <= right) {
            if (arr[i].weight >= arr[j].weight) tem[t++] = arr[i++];
            else tem[t++] = arr[j++];
        }
        while (i <= mid) tem[t++] = arr[i++];
        while (j <= right) tem[t++] = arr[j++];
        for (int index = left; index <= right; index++) arr[index] = tem[index - left];
    }

    public static void mSort(Good[] arr, int left, int right, Good[] tem) {
        if (left < right) {
            int mid = (right - left) / 2 + left;
            mSort(arr, left, mid, tem);
            mSort(arr, mid + 1, right, tem);
            merge(arr, left, mid, right, tem);
        }
    }

    public static void main(String[] args) throws Exception {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        StringTokenizer st = new StringTokenizer(br.readLine());
        int n = Integer.parseInt(st.nextToken());
        int q = Integer.parseInt(st.nextToken());

        HashSet<String> set = new HashSet<>();
        st = new StringTokenizer(br.readLine());
        for (int i = 0; i < q; i++) set.add(st.nextToken());

        Good[] gs = new Good[n];
        for (int i = 0; i < n; i++) {
            st = new StringTokenizer(br.readLine());
            Good g = new Good();
            g.name = st.nextToken();
            int m = Integer.parseInt(st.nextToken());

            st = new StringTokenizer(br.readLine());
            int wei = 0;
            for (int j = 0; j < m; j++)
                if (set.contains(st.nextToken())) wei++;
            g.weight = wei;
            gs[i] = g;
        }

        Good[] tem = new Good[n];
        mSort(gs, 0, n - 1, tem);

        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < n; i++) sb.append(gs[i].name).append('\n');
        System.out.print(sb);
    }
}
```

这道题目考察的是对 **HTTPS 协议特点**及其与 **HTTP 区别**的理解。

根据题目要求，我们需要选出 **“不属于”** HTTPS 劣势的选项。

### 选项详细分析

- **A. 性能开销和配置复杂性 (劣势)：**

  HTTPS 需要处理 SSL/TLS 握手，涉及非对称加密、对称加密及散列算法，计算量远大于纯文本的 HTTP。同时，配置 HTTPS 需要申请、购买、部署和更新 CA 证书，增加了维护成本。

- **B. 传输速度慢 (劣势)：**

  由于 HTTPS 在建立连接时需要额外的 TLS 握手过程（通常需要增加 1~2 个 RTT），且数据传输过程中需要加解密处理，因此在首包响应时间和整体吞吐速度上，HTTPS 通常会比 HTTP 稍慢一些。

- **D. 服务器负载高 (劣势)：**

  加解密操作是计算密集型任务，会对服务器的 CPU 造成显著压力。在高并发场景下，HTTPS 服务器需要比 HTTP 服务器消耗更多的硬件资源来维持相同的访问量。

------

### 为什么 C 是正确答案？

**C. 需要对传输数据进行压缩 (不是劣势)**

1. **非强制性：** 数据压缩（如 Gzip, Brotli）并不是 HTTPS 协议特有的要求或“劣势”。无论是传统的 HTTP 还是 HTTPS，为了节省带宽和提升加载速度，通常都会开启数据压缩。
2. **安全风险：** 事实上，在 HTTPS 中使用压缩有时反而会带来安全隐患（例如 **CRIME 攻击** 和 **BREACH 攻击**）。攻击者可以通过观察加密压缩包的大小变化，推测出加密数据中的敏感内容。因此，在某些高安全场景下，HTTPS 反而会选择**关闭**压缩。
3. **逻辑误区：** 压缩是为了优化传输效率，属于一种优化手段，而不应被视为 HTTPS 相比 HTTP 产生的“劣势”或额外负担。

------

### 总结

这道题你选 D 可能是因为考虑到加解密确实会增加负载，但题目问的是 **“不是”** 劣势的选项。D 确实是 HTTPS 的痛点之一，而 C 选项描述的内容既不是 HTTPS 的强制要求，也不是它带来的负面影响，因此它是干扰项，即本题的正确答案。

### 分析

四个选项的**内层逻辑完全相同**，区别只在最外层 `t3` 与 `user_profile t4` 的 JOIN 类型。

先明确 t3 的内容：t3 是"有重复的 university 中，id 最大的那条"，在本题中只有一行：

| university | id   |
| ---------- | ---- |
| 北京大学   | 3    |

------

#### 逐项分析最外层 JOIN

**A — `LEFT JOIN`**

以 t3 为左表，t4 为右表。t3 只有 `id=3` 这一行，`ON t3.id = t4.id` 能匹配到 t4 中 id=3 的记录。结果：**只返回 id=3 ✅ 符合预期**

**B — `INNER JOIN`**

只保留两边都能匹配的行。t3.id=3 能在 t4 中找到对应记录。结果：**只返回 id=3 ✅ 符合预期**

**C — `RIGHT JOIN`**

> **以 t4（user_profile 全表）为右表**，保留右表的所有行。

t4 共 5 行，无论 t3 能不能匹配，**右表全部输出**。对于 t3 中没有的 id（1、2、4、5），t3 那侧为 NULL，但 `SELECT t4.*` 照样把 t4 的数据输出。

结果：**返回全部 5 行 ❌ 不符合预期** → **答案是 C**

**D — 内层用 `LEFT JOIN`，外层用 `LEFT JOIN`**

内层：t1 LEFT JOIN t2。t1 是有重复的大学（北京大学），t2 是各大学最大 id，LEFT JOIN 在这里与 INNER JOIN 效果相同（因为每所大学在 t2 中必然存在），t3 结果不变，仍是 `{北京大学, id=3}`。外层 LEFT JOIN 结果同 A。**只返回 id=3 ✅ 符合预期**

------

#### 总结

| 选项  | 外层 JOIN      | 结果          | 是否符合预期 |
| ----- | -------------- | ------------- | ------------ |
| A     | LEFT JOIN      | 仅 id=3       | ✅            |
| B     | INNER JOIN     | 仅 id=3       | ✅            |
| **C** | **RIGHT JOIN** | **全表 5 行** | **❌**        |
| D     | LEFT JOIN      | 仅 id=3       | ✅            |

**答案是 C**，RIGHT JOIN 导致 t4 全表被保留输出，完全背离了"只查询重复中 id 最大的记录"的需求。

这道题考察的是 Java 中的**数据类型转换（Type Casting）\**和\**算术运算符**的底层机制。

题目问的是：下列语句**可运行有误**的是（即哪一行代码在编译时会报错）。

------

### 核心知识点：类型提升（Numeric Promotion）

在 Java 中，当进行算术运算（如 `+`）时，如果操作数的类型是 `byte`、`short` 或 `char`，它们会**自动提升为 `int` 类型**再进行计算。计算结果也是 `int` 型。

### 选项逐一拆解

#### **A. `short s = 2; s = s + 2;` （编译报错 ❌）**

- **过程：** `s` 是 `short` 型，`2` 是 `int` 型字面量。
- **提升：** 在执行 `s + 2` 时，`s` 会自动提升为 `int`。
- **结果：** `int + int` 的结果是 `int`。
- **错误点：** 试图将一个 `int` 类型的结果直接赋值给 `short` 类型的变量 `s`。由于存在精度丢失的风险，Java 编译器要求必须进行强制类型转换，否则报错。
- **修正：** `s = (short)(s + 2);`

#### **B. `short s = 2; s += 2;` （运行正常 ✅）**

- **原理：** `+=` 是 **复合赋值运算符**。
- **特殊性：** Java 语言规范规定，复合赋值运算符（如 `+=`, `-=`, `*=`）会自动包含一个**隐式的强制类型转换**。
- **等价于：** `s = (short)(s + 2);`
- **结论：** 编译器会自动帮你处理掉类型不匹配的问题，所以它是合法的。

#### **C. `short s = 2; s++;` （运行正常 ✅）**

- **原理：** 自增运算符 `++` 与 `+=` 类似，底层也包含了隐式的强制类型转换。
- **等价于：** `s = (short)(s + 1);`
- **结论：** 运行正常。

#### **D. `short s = 2; s = s + (short)2;` （编译报错 ❌）**

- **陷阱点：** 虽然你手动把 `2` 转成了 `short`，但在执行 `s + (short)2` 这一步时，**两个 `short` 相加，依然会先自动提升为 `int`**。
- **结果：** 结果依然是 `int`，再次尝试赋值给 `short s` 时，依然会报错（与 A 选项的原理一致）。

------

### 总结与答案

这道题的答案应该是 **A 和 D**。

> **注意：** 截图上方显示这是一个“多选题”。
>
> - **A** 报错是因为 `int` 不能直接赋给 `short`。
> - **D** 报错是因为两个 `short` 运算后的结果是 `int`，依然无法直接赋给 `short`。

这属于 Java 基础中的经典“坑”，记住一点：**除了复合赋值运算符（如 `+=`）有自动转换加持，其他的窄化转换（大转小）都必须手动强转。**

## 14. StringBuilder

在 Java 中，`StringBuilder` 是处理字符串的高效利器。与普通的 `String` 不同，它是**可变的**。这意味着当你修改字符串时，它不会创建一堆新的对象，而是在原有的内存缓冲区上直接操作，性能更强。

以下是 `StringBuilder` 的常用方法分类整理：

------

### 1. 核心增删改方法

这些是你在日常编码中最常用的操作，绝大多数支持**链式编程**（如 `sb.append("A").append("B")`）。

| **方法**                       | **说明**                                 | **示例**                  |
| ------------------------------ | ---------------------------------------- | ------------------------- |
| **`append(data)`**             | 在末尾追加数据（支持各种基本类型和对象） | `sb.append("Hello");`     |
| **`insert(offset, data)`**     | 在指定索引位置插入数据                   | `sb.insert(1, "Java");`   |
| **`delete(start, end)`**       | 删除从 `start` 到 `end-1` 的字符         | `sb.delete(0, 2);`        |
| **`deleteCharAt(index)`**      | 删除指定索引处的一个字符                 | `sb.deleteCharAt(5);`     |
| **`replace(start, end, str)`** | 用新字符串替换指定范围的内容             | `sb.replace(0, 2, "Hi");` |
| **`reverse()`**                | 将序列中的字符反转                       | `sb.reverse();`           |

------

### 2. 查找与获取方法

这些方法与 `String` 类中的用法几乎完全一致。

- **`charAt(int index)`**：返回指定索引处的字符。
- **`indexOf(String str)`** / **`lastIndexOf(String str)`**：查找子字符串第一次或最后一次出现的索引。
- **`substring(int start, int end)`**：截取并返回一个新的 `String`（注意：此方法返回的是 `String`，**不会**改变原来的 `StringBuilder`）。
- **`length()`**：返回当前字符序列的长度。

------

### 3. 容量管理（进阶必备）

理解容量（Capacity）和长度（Length）的区别能帮你写出性能更优的代码。

- **`capacity()`**：返回当前分配的存储容量（默认为 `str.length + 16`）。
- **`setLength(int newLength)`**：强制设置长度。如果新长度小于原长度，内容会被截断；如果大于原长度，末尾会填充空字符 (`\0`)。
- **`trimToSize()`**：将存储容量收缩至与当前字符长度一致，以节省内存。

------

### 4. 最终转换

- **`toString()`**：这是最重要的一步。当你完成所有修改后，调用此方法将其转换回不可变的 `String` 对象。

------

### 💡 避坑小指南

1. **线程安全**：`StringBuilder` 是**非线程安全**的。如果你在多线程环境下操作同一个字符串缓冲区，请改用 `StringBuffer`（虽然慢一点，但安全）。
2. **不要过度使用**：如果是简单的 `String s = "A" + "B";`，Java 编译器在底层会自动帮你优化成 `StringBuilder`。只有在**循环中**拼凑字符串时，手动创建 `StringBuilder` 才是性能质变的关键。

**举个例子：**

Java

```

sb.append(" 101")           // Rocket 101
  .insert(0, "Big ")        // Big Rocket 101

  .delete(9, 13);           // Big Star

```

这张图片的题目是一道经典的 **C语言 数组与指针** 陷阱题。

你选择 B (输出 "good") 是因为直觉上觉得 `s = "good"` 就是把 "good" 这四个字母放进 `s` 这个盒子里。但实际上，这在 C 语言中是**错误**的操作。

这里有两个核心原因，解释了为什么会有编译错误（选 D）：

### 1. 数组名是常量指针
在 C 语言中，当我们定义 `char s[5];` 时，**`s` 代表的是数组在内存中的首地址**。
最关键的是，这个首地址是 **常量**，不能被修改。
*   **`s` 本质上是 `&s[0]`**，也就是内存里固定的一个位置。
*   试图写 `s = "good";`，就像是试图把“北京”这个城市的名字改成“上海”。城市的地点是固定的（常量），你不能把它的坐标改了。你只能修改这个地方里面的**内容**。

### 2. 赋值操作 vs 初始化
很多人会把**定义时的操作**和**执行代码时的操作**搞混：

*   **正确的写法（初始化）：**
    ```c
    char s[5] = "good"; // 合法！这是在定义的时候直接赋予初值
    ```
    此时编译器会分配内存，并把 'g','o','o','d','\0' 依次拷贝进去。

*   **错误的写法（赋值）：**
    ```c
    char s[5];
    s = "good"; // 错误！这是赋值语句，不能给数组常量名赋值
    ```
    在第二行 `s = "good";` 中，`s` 代表地址（常数），`"good"` 是字符串字面量（也代表地址）。把两个地址直接做赋值运算（`=` 左边必须是左值，通常是变量），在 C 标准里是不允许的。

---

### 如果你想修正这个代码，让它输出 "good"，该怎么做？

如果你是想把字符串复制进 `s` 里，不能直接用 `=`，必须用库函数 **`strcpy`**。

**正确代码：**
```c
#include <stdio.h>
#include <string.h> // 需要包含这个头文件

int main() {
    char s[5];
    strcpy(s, "good"); // 把 "good" 的内容拷贝到 s 所指的内存里
    printf("%s", s);
    return 0;
}
```

### 总结
*   **数组名 `s`** = 地址常量（不能改）。
*   **`s = ...`** = 试图修改常量的值 = **编译报错**。
*   所以正确答案是 **D (编译出错)**。

```
x++ + ++y - --x * y--

```

Java 规定：表达式中的操作数**严格按从左到右的顺序求值**，所以 ①②③④ 依次执行，不会因为 `*` 优先级高就先去求值 `--x * y--`。

------

**优先级 vs 求值顺序 是两回事：**

- **优先级**决定的是运算符的**结合方式**，即 `*` 的结果参与 `-` 而不是 `+`
- **求值顺序**决定的是每个操作数**何时被读取/修改**，Java 这里是严格从左到右

所以实际执行过程是：

1. 先从左到右把所有操作数的值都确定好：`5, 11, 5, 11`
2. 再按优先级做算术：`5 + 11 - (5 * 11) = -39`

### TCP Socket 通信流程

#### 服务器端流程

1. `new ServerSocket(port)` —— 创建服务器监听对象，绑定端口
2. `serverSocket.accept()` —— **阻塞等待**客户端连接，连接成功后返回一个 `Socket` 对象用于通信
3. 通过该 `Socket` 的输入/输出流进行数据收发
4. 关闭 `Socket` 和 `ServerSocket`

#### 客户端流程

1. `new Socket(host, port)` —— 主动发起连接，创建通信用的 `Socket` 对象
2. 通过该 `Socket` 的输入/输出流进行数据收发
3. 关闭 `Socket`

#### 关键区别

|        | 服务器端                   | 客户端                  |
| ------ | -------------------------- | ----------------------- |
| 监听用 | `ServerSocket`             | ❌ 不需要                |
| 通信用 | `accept()` 返回的 `Socket` | `new Socket()` 直接创建 |

------

### 题目解析

- **A 错**：`new ServerSocket()` 是**服务器端**用的，不是客户端
- **B 错**：`accept()` 是**服务器端**调用的，客户端没有这个步骤
- **C ✅ 正确**：客户端通过 `new Socket(host, port)` 发起连接并创建通信对象
- **D 错**：`new ServerSocket()` 创建的是**监听对象**，不是通信的 Socket 对象（通信 Socket 是 `accept()` 返回的）

**答案是 C。**

上面这个演示可以点着看：每点一次「下一步」，就会有一格被搬进数组——你可以盯着"第几行在抄、抄到数组的哪个位置"。下面我们从零开始，把这套逻辑重新铺一遍。

### **第零课：这题不需要任何数学功底**

很多同学一看到矩阵就紧张，以为要算什么。其实这道题的全部内容就是**数格子**：给你一张方格纸，让你把某片区域里的数字按顺序抄到一个单行本上，然后问"某个数字抄在第几格"。你只要能分清"行列、左上右下、顺序"，就能做对。

### **第一课：三个必须先分清的名词**

我们先把这张方格纸的语言统一。

**二维矩阵**就是一张 $n$ 行 $n$ 列的表格，写成 $a_{ij}$ 表示"第 $i$ 行第 $j$ 列"的数字。本题的 $a$ 和 $b$ 都是 4 行 4 列，一共 $4 \times 4 = 16$ 个格子。

**主对角线**是从左上角到右下角的那条斜线，即行号等于列号的位置：$a_{11}, a_{22}, a_{33}, a_{44}$，在题里就是 4、2、5、6 这四个数。

**下三角矩阵**：主对角线**及它左下方**的所有元素构成的部分（形状像一个直角朝左下的三角形）。也就是满足"列号 $\le$ 行号"的格子：第 1 行有 1 个（$a_{11}$），第 2 行有 2 个（$a_{21}, a_{22}$），第 3 行有 3 个，第 4 行有 4 个。

**上三角矩阵**：主对角线**及它右上方**的所有元素（形状像直角朝右上的三角形）。也就是满足"列号 $\ge$ 行号"的格子：第 1 行有 4 个，第 2 行有 3 个，第 3 行有 2 个，第 4 行有 1 个。

注意一个极易混淆的点：**上三角是"右上"那片，下三角是"左下"那片，而两者都包含主对角线**。对角线是公共部分，绝不漏掉。

### **第二课：什么叫"压缩存储"，为什么要压**

矩阵有 16 个格子，但下三角只有 $1+2+3+4 = 10$ 个真正有意义的元素，另外 6 个是"另一半"。

在实际计算里，如果一个矩阵是对称矩阵，那么上三角和下三角的内容是完全一样的，存两遍纯属浪费；如果它是三角矩阵，另一半通常全是 0 或者某个固定常数，根本没有必要占内存。**压缩存储的意思就是：只保留需要的那一片（本题里就是对对角线那一片），把二维表格"拍扁"成一维的单行数组**——用 10 个格子存 10 个数。这也正是为什么题里的数组 $SA$、$SB$ 只有 10 个下标位置（$0\sim 9$）。

### **第三课：压缩时唯一的动作——"行优先，逐行抄"**

这是全题的核心。压缩的规则只有一句话：**一行一行地扫，每行从左到右，遇到该保留的数字就抄进数组，抄完这行再抄下一行**。这种顺序叫"行序为主序"（行优先）。

用生活化的比喻：把矩阵想象成书架，第一层从左到右取书放进箱子，取完再取第二层，箱子里的书自然就按读取顺序排好了。数组的下标就是"这是第几本放进箱子的书"，**而且从 0 开始数**——第 1 本放的位置是下标 0，第 2 本放的是下标 1。

这一点是本题唯一的陷阱来源：**数组下标 = 该元素是第几个被抄进去的，再减 1**。

在下三角里，"该抄的"是每行从第 1 列抄到第 $i$ 列（遇到对角线就停）；在上三角里，"该抄的"是每行从第 $i$ 列抄到第 $n$ 列（从对角线开始，一直抄到行尾）。其余格子直接跳过，不给它分配数组位置。

### **第四课：手把手抄一遍矩阵 a**

按要求，只抄主对角线及左下方的元素，一行一行来：

| 抄到第几行 | 本行要抄的数字 | 它们是箱子里的第几个 | 放进数组的位置 |
|---|---|---|---|
| 第1行 | 4 | 第 1 个 | $SA[0] = 4$ |
| 第2行 | 3, 2 | 第 2、3 个 | $SA[1] = 3$，$SA[2] = 2$ |
| 第3行 | 8, 2, 5 | 第 4、5、6 个 | $SA[3] = 8$，$SA[4] = 2$，$SA[5] = 5$ |
| 第4行 | 7, 2, 1, 6 | 第 7、8、9、10 个 | $SA[6] = 7$，$SA[7] = 2$，$SA[8] = 1$，$SA[9] = 6$ |

于是完整的数组是 $SA = [4, 3, 2, 8, 2, 5, 7, 2, 1, 6]$，一共 10 个元素。要特别注意第 3 行抄完后下标已经用到 5 了，所以第 4 行的第一个数字 7 落位在 $SA[6]$，而不是 $SA[5]$。

看一眼选项：$SA[0]=4$ 完全正确（A 选项说法正确）；$SA[4]=2$，**它不是 5**，所以 B 选项"$SA[4]=5$"是错的。

### **第五课：手把手抄一遍矩阵 b**

上三角要抄的是主对角线及右上方的元素。每行从对角线那个格子开始往右抄，直到行尾：

| 抄到第几行 | 本行要抄的数字 | 它们是箱子里的第几个 | 放进数组的位置 |
|---|---|---|---|
| 第1行 | 7, 2, 1, 6 | 第 1\~4 个 | $SB[0]=7$，$SB[1]=2$，$SB[2]=1$，$SB[3]=6$ |
| 第2行 | 8, 2, 5 | 第 5\~7 个 | $SB[4]=8$，$SB[5]=2$，$SB[6]=5$ |
| 第3行 | 3, 2 | 第 8、9 个 | $SB[7]=3$，$SB[8]=2$ |
| 第4行 | 4 | 第 10 个 | $SB[9]=4$ |

完整数组为 $SB = [7, 2, 1, 6, 8, 2, 5, 3, 2, 4]$。这里的"行头"位置一变，下标就跟着变：第 2 行的第一个数字是 $SB[4]$（因为第 1 行已经占掉了 0\~3 四个位置），所以第 2 行的 8 在 $SB[4]$、2 在 $SB[5]$、5 在 $SB[6]$。

### **第六课：回到原题，逐个选项核对**

| 选项 | 题目给出的说法 | 我们的计算结果 | 判定 |
|---|---|---|---|
| A | $SA[0]=4$ | $SA[0]=4$ | 正确 |
| B | $SA[4]=5$ | $SA[4]=2$ | **错误** |
| C | $SB[3]=6$ | $SB[3]=6$ | 正确 |
| D | $SB[6]=5$ | $SB[6]=5$ | 正确 |

题目问的是"错误的是"，因此答案是 **B**。这里可以顺手做一个全局自检：4 阶矩阵每边 4 个元素，含对角线的三角形共 $\frac{4\times(4+1)}{2}=10$ 个，恰好等于数组长度，说明我们没有多存也没少存，抄得没错。

### **第七课：熟练之后的"地址公式"**

逐格数永远是通用方法，考场上也最稳妥。但如果你想更快，或者在考卷上看到 $n$ 是 100 这种数字，就需要把上面的过程写成公式。这里用中文教材惯用的 1 起始行号列号（$i, j$ 都从 1 开始），$n$ 为矩阵阶数：

**下三角矩阵按行优先**，元素 $a_{ij}$（满足 $j \le i$）在压缩序列中是第几个，由它前面所有行贡献的元素个数（每行 $1,2,\dots,i-1$ 个）加上本行的第 $j$ 个位置得到：

$$
k = \frac{i(i-1)}{2} + j
$$

**上三角矩阵按行优先**，第 $i$ 行之前各行的元素个数依次是 $n, n-1, \dots, n-i+2$，求和后再加上本行内的偏移 $j-i+1$：

$$
k = \frac{(i-1)(2n-i+2)}{2} + (j-i+1)
$$

这两个 $k$ 表示"这是第 $k$ 个元素"，而由于数组下标从 0 开始，真正的下标是 $k-1$。

代入验证一下题目里的关键位置：下三角的 $a_{32}$（第 3 行第 2 列，值为 2），$k=\frac{3\times2}{2}+2=5$，下标 $4$，所以 $SA[4]=2$，与逐格数完全一致；上三角的 $b_{13}$（值为 6），$k = 0 + 3 = 3$，下标 3，所以 $SB[3]=6$；上三角的 $b_{23}$（值为 5），$k=\frac{1\times(8-2+2)}{2}+(3-2+1)=4+2=6$，下标 6，所以 $SB[6]=5$。三处都与选项吻合。

公式的价值不在于背，而在于它其实就是"我前面数过的那些格子，我把它加起来了"这一件事的缩写。理解这一点后，即使公式记混了，重新数一遍也能救回来。

### **第八课：四个最容易踩的坑**

**第一个坑是下标基准。** 题目里的数组下标明确从 0 起算，而人脑习惯从 1 开始数"第几个"。因此永远要记得在最后一步减 1：$a_{32}$ 是第 5 个元素，但它的位置是 $SA[4]$。这个"减一"是本题出错率最高的地方。

**第二个坑是行列优先搞反。** 如果题目改说"列优先存储"，那就要一列一列垂直地抄。本题是行优先，所以横向扫。拿到题先看这两个字。

**第三个坑是漏掉或误算对角线。** 下三角含对角线，上三角也含对角线；对角线会被保存两次（在 $SA$ 和 $SB$ 里各出现一次），这是正常的，因为它属于公共边界。

**第四个坑是数组长度算错。** 4 阶三角矩阵的压缩数组长度是 10 而不是 16；如果按 16 个位置去推下标，后面全错。养成一个习惯：动手前先算出总数 $n(n+1)/2$，用总数给数组划一个合理的范围。

### **第九课：怎么把这类题永久学会**

以后遇到任何"压缩存储"的题，固定走这四步：第一步，判断矩阵类型（下三角、上三角、对称或三对角），由此确定"要抄哪些格子"；第二步，算出一共有多少个待存元素，用 $n(n+1)/2$ 检查数组长度；第三步，严格按"行优先、每行从左到右"的次序逐行抄，一行一行累加计数，边抄边写下标；第四步，把结果代回选项，凡涉及"第几个元素"的位置都必须减 1 得到下标。

想找个更小的例子练手的话，可以拿一个 3 阶矩阵试：设 $c = \begin{bmatrix} 5 & 0 & 0 \\ 7 & 9 & 0 \\ 2 & 4 & 6 \end{bmatrix}$，按行优先压缩存进数组后，$SC = [5, 7, 9, 2, 4, 6]$，共 $3\times4/2 = 6$ 个元素。你可以自己检验一下 $c_{32} = 4$ 应该落在哪个下标（答案：$SC[4]$）。

顺手一提，刚才那个演示页面如果你觉得讲给同学看有用，它可以发布成一个公开链接分享出去——需要的话我帮你发。

### **解题思路小结**

这道题考的是数据结构中"特殊矩阵的压缩存储"，核心操作是把二维的三角区域按行优先顺序拍平成一维数组，难点全在"下标从 0 开始"这一位偏移上。逐行数格子是不需要背公式的通法：$SA$ 的第 3 行抄完后已用到下标 5，故 $SA[4]=2$ 而非 5，选项 B 因此错误。

## 38. Stream API 性能优化（单选题）

**题目：** 以下关于Stream API的性能优化，哪项做法是正确的？

**A.** 对于小数据集（&lt;100个元素），并行流总是比顺序流快  
**B.** 在parallel stream中使用LinkedList作为数据源比ArrayList更高效  
**C.** 使用Stream.toList()（Java 16+）返回的是不可变List，是收集元素的推荐简便方式  
**D.** 在parallel stream中使用forEach的顺序与顺序流一致

**正确答案：C** | **你的答案：D** ❌

---

### 核心知识点

`Stream.toList()` 是 **Java 16** 引入的便捷终端操作，它把流中的元素收集成一个**不可修改的 List**。

#### 关键区分：不可修改 ≠ 不可变

- **不可修改（Unmodifiable）**：列表本身不能增删改（`add`/`remove`/`set` 抛 `UnsupportedOperationException`）
- **不可变（Immutable）**：列表本身 + 列表中的元素都不可变
- `Stream.toList()` 返回的是**不可修改列表**，但如果元素是可变对象，仍可修改对象内部状态

```java
List<String> names = Stream.of(“小明”, “小红”).toList();
// names.add(“小李”);  // ❌ UnsupportedOperationException
// names.get(0) 可访问，但 names 本身不可修改
```

#### Stream.toList() vs Collectors.toList()

| 方法 | 返回类型 | 可修改性 | 推荐场景 |
|------|---------|---------|---------|
| `Stream.toList()` | **不可修改**List（保证） | ❌ | 简洁语法，无需修改列表 |
| `Collectors.toList()` | **不保证**（实现相关） | ⚠️ | 旧版本兼容（Java 16-） |
| `Collectors.toCollection(ArrayList::new)` | **可修改**ArrayList（保证） | ✅ | 明确需要可修改列表 |

```java
// 明确需要可修改的列表
List<String> mutableList = Stream.of(“小明”, “小红”)
    .collect(Collectors.toCollection(ArrayList::new));
mutableList.add(“小李”);  // ✅ 可以修改
```

---

### 错误选项深度分析

#### A. 小数据集并行流更快？❌

**并行流开销来源：**
1. **任务拆分**：将数据源切分成子任务
2. **线程调度**：ForkJoinPool 线程管理
3. **结果合并**：Collector 需要 `combiner()` 合并各线程结果

**经验阈值：**
- 数据集 < 1000 且操作简单（map/filter）→ **顺序流更快**
- 数据集 > 10000 且操作复杂（CPU密集型）→ 并行流才有优势

```java
// 反例：小数据集使用并行流
List<Integer> small = IntStream.range(0, 50).boxed().toList();
small.parallelStream()  // ❌ 线程开销 > 计算收益
     .map(x -> x * 2)
     .toList();
```

---

#### B. LinkedList 在并行流中更高效？❌

**并行流依赖 Spliterator 高效拆分：**

| 数据源 | 拆分方式 | 并行流性能 |
|--------|---------|-----------|
| **ArrayList** | 按索引快速分割子区间 | ⚠️ **高效** |
| **数组** | 直接切分子数组 | ⚠️ **高效** |
| **LinkedList** | 逐个遍历才能定位中点 | ❌ **低效** |
| **HashSet** | 按哈希桶分割 | ⚠️ **中等** |

**原理：**
- `ArrayList` 的 `Spliterator` 实现支持 `SIZED` + `SUBSIZED` 特性，可 O(1) 计算中点并拆分
- `LinkedList` 需要 O(n) 遍历到中点，拆分成本高

```java
// ❌ 反例：LinkedList + 并行流
new LinkedList<>(List.of(1, 2, 3, ...))
    .parallelStream()  // 拆分成本高，性能差
    .map(x -> x * 2)
    .toList();

// ✅ 正例：ArrayList + 并行流
new ArrayList<>(List.of(1, 2, 3, ...))
    .parallelStream()  // 高效拆分
    .map(x -> x * 2)
    .toList();
```

---

#### D. parallel stream 的 forEach 保证顺序？❌

**并行流的顺序保证：**

| 操作 | 顺序保证 | 原因 |
|------|---------|------|
| `forEach` | ❌ **不保证** | 多线程并发执行，顺序随机 |
| `forEachOrdered` | ✅ **保证** | 强制按流原始顺序处理（需同步） |
| `collect(toList())` | ✅ **保证** | Collector 的 `combiner()` 保证顺序 |

**性能权衡：**
```java
// ❌ forEach 在并行流中不保证顺序
List.of(1, 2, 3, 4, 5)
    .parallelStream()
    .forEach(x -> System.out.print(x + “ “));  
// 可能输出：3 1 5 2 4（顺序随机）

// ✅ forEachOrdered 保证顺序，但牺牲并行性能
List.of(1, 2, 3, 4, 5)
    .parallelStream()
    .forEachOrdered(x -> System.out.print(x + “ “));  
// 保证输出：1 2 3 4 5（需要线程间同步协调）
```

### 面试延伸话术

#### 追问1：什么场景适合并行流？

> 三个条件**同时满足**时考虑并行流：
> 
> 1. **数据量足够大**  
>    经验值：数据集 > 1000，且单次操作耗时 > 1ms
> 
> 2. **数据源支持高效拆分**  
>    ✅ ArrayList、数组、IntStream.range  
>    ❌ LinkedList、无限流、文件IO流
> 
> 3. **操作无状态且线程安全**  
>    ✅ map、filter、flatMap  
>    ❌ forEach 修改共享变量、collect 到非线程安全容器

**反例：**
```java
// ❌ 并行流 + 共享可变状态 → 线程安全问题
List<Integer> result = new ArrayList<>();  // 非线程安全
IntStream.range(0, 1000)
    .parallel()
    .forEach(result::add);  // ❌ 并发修改异常

// ✅ 使用线程安全的 Collector
List<Integer> result = IntStream.range(0, 1000)
    .parallel()
    .boxed()
    .collect(Collectors.toList());  // ✅ Collector 保证线程安全
```

#### 追问2：ForkJoinPool 的线程数怎么确定？

> 并行流默认使用 **公共 ForkJoinPool**，核心线程数 = `Runtime.getRuntime().availableProcessors() - 1`。
> 
> **性能陷阱：**
> - CPU 密集型任务在已满载的系统使用并行流 → 线程竞争加剧，性能反降
> - 混用 CPU 密集 + IO 密集任务 → 公共池被阻塞
> 
> **自定义 ForkJoinPool：**
> ```java
> ForkJoinPool customPool = new ForkJoinPool(4);
> customPool.submit(() -> 
>     list.parallelStream()
>         .map(heavyComputation)
>         .toList()
> ).get();
> ```

### **抽象工厂模式的核心，是一次选定一个“产品家族”，并由同一个工厂创建这一家族中的相关对象。**

在这个 UI 框架里，产品家族就是某个平台主题下的一组组件：

- Windows 家族：`WindowsButton`、`WindowsTextField`、`WindowsCheckbox`
- macOS 家族：`MacButton`、`MacTextField`、`MacCheckbox`

抽象工厂为每种组件定义创建接口，再由具体工厂负责创建同一平台的一整套组件。应用只需选择对应的工厂，就能让界面中的组件保持同一风格。

```text
UIFactory
├── createButton()
├── createTextField()
└── createCheckbox()
       ↑
       ├── WindowsUIFactory
       └── MacOSUIFactory
```

例如：

```text
interface UIFactory {
    createButton()
    createTextField()
    createCheckbox()
}

class WindowsUIFactory implements UIFactory {
    createButton()    → WindowsButton
    createTextField() → WindowsTextField
    createCheckbox()  → WindowsCheckbox
}

class MacOSUIFactory implements UIFactory {
    createButton()    → MacButton
    createTextField() → MacTextField
    createCheckbox()  → MacCheckbox
}
```

客户端代码只依赖抽象接口：

```text
factory = choosePlatformFactory()
button = factory.createButton()
field = factory.createTextField()
checkbox = factory.createCheckbox()
```

如果 `factory` 是 `WindowsUIFactory`，创建出的就是一套 Windows 组件；如果是 `MacOSUIFactory`，创建出的就是一套 macOS 组件。客户端不需要在每个组件创建处单独判断平台，从结构上减少了混搭主题的机会。

### **为什么选 C**

题干的关键不是“创建一个按钮”，而是**创建多个类型不同、彼此有关联的对象，并保证它们属于同一套产品家族**。这正是抽象工厂模式的适用场景。

**与其他选项的区别：**

- **A 工厂方法模式**：通常聚焦于创建某一种产品，让子类决定具体创建哪种对象；它不直接负责协调多个不同组件组成的一整套家族。
- **B 建造者模式**：关注按步骤构造一个复杂对象，并控制构造过程；重点不是创建一组同主题的不同对象。
- **D 原型模式**：通过复制已有对象来创建新对象；重点是克隆，不是管理多类相关产品的一致性。

所以这题选择 **C：抽象工厂模式（Abstract Factory）**。




## 40. 中断处理 vs 子程序调用的现场保护（PSW）

**题目：** 中断处理和子程序调用都需要压栈以保护现场，中断处理一定会保存、而子程序调用不需要保存其内容的是（）。

A. 程序计数器　B. 程序状态字寄存器　C. 通用数据寄存器　D. 通用地址寄存器

**正确答案：B** | **你的答案：A** ❌

### 一句话结论

中断和子程序调用都要保存返回地址（PC），也都可能要保存被用到的通用寄存器；唯一"中断必存、调用不存"的差别落在 **PSW（程序状态字寄存器）**——中断由硬件自动把断点连同 PSW 一起压栈，而普通 CALL 指令不做这件事。

### 四个选项逐一辨析

| 寄存器 | 中断处理 | 子程序调用 | 判定 |
|--------|:---:|:---:|------|
| A 程序计数器（PC） | 必须保存 | 也必须保存（返回地址） | A 错：调用同样要存 PC |
| B 程序状态字（PSW） | 硬件自动保存 | 调用机制不自动保存 | ✅ 这就是差别 |
| C 通用数据寄存器 | 谁用谁存 | 谁用谁存 | 两者对称，不构成"必存 vs 不需" |
| D 通用地址寄存器 | 谁用谁存 | 谁用谁存 | 同 C |

C、D 的关键：无论中断还是子程序，通用寄存器都是"用到才需要保存、没用到就不用存"，两边逻辑一样，所以它们不是"中断一定存、调用一定不存"的那个答案。

### 为什么偏偏是 PSW

PSW 装的是**处理器当前状态标志**，典型三类：

- **条件码**（ZF/SF/CF/OF 等）：记录上一条运算的结果特征（是否为零/为负/进位/溢出），供随后的条件跳转使用
- **运行模式/特权级**：当前处于内核态还是用户态
- **中断允许位**：当前是否响应可屏蔽中断

中断是**异步**的——可能砸在程序任意一条指令之间，处理完必须"像什么都没发生一样"回到断点继续。而中断服务过程本身会改变处理器状态（进内核、开关中断、执行自己的运算改掉条件码）。所以硬件在响应中断时**自动把断点 PC + PSW 一起压栈**，返回时（IRET/RTI）再整体恢复。

普通 CALL 只压返回地址、然后跳转；RET 只恢复 PC。它**没有**中断那种"由硬件自动保存整个 PSW"的动作。

### 官方解析的一处不严谨（你提到的点）

官方说"子程序调用通常不会改变处理器状态，因此不需要保存 PSW"——这话太绝对。子程序里做算术、比较照样会改条件码。更准确的表述是：

> 子程序调用机制**本身**没有像中断那样"必须自动保存 PSW"的硬性要求；至于要不要保存，取决于**指令集、调用约定（caller-saved / callee-saved）、以及调用者事后是否还依赖那个条件结果**。

常见调用约定里，条件码不算"调用者必须无条件保留"的状态：若调用后还要用某个比较结果，应在 CALL 前自己存好，或调用后重新比较。所以 B 的本质是**"调用机制层面没有强制保存 PSW 的要求"**，而不是"子程序绝对碰不到 PSW"。

## 41. float 的 IEEE 754 单精度编码（-8.25）

**题目**

float 型数据通常用 IEEE 754 单精度浮点数格式表示。若编译器将 float 型变量 x 分配在一个 32 位浮点寄存器 FR1 中，且 x = −8.25，则 FR1 的内容是（　）。

- A. `C104 0000H`
- B. `C242 0000H`
- C. `C184 0000H`
- D. `C1C2 0000H`

**正确答案：A**

**完整推导**

| 步骤 | 操作 | 本例 |
|------|------|------|
| ① 定符号 | 负数 → `1` | S = **1** |
| ② 转二进制 | 整数除 2 取余、小数乘 2 取整 | `8.25₁₀ = 1000.01₂`（`0.25 = 2⁻²`） |
| ③ 规格化 | 小数点移到第一个 1 之后 | `1.00001₂ × 2³` → 真实指数 **3** |
| ④ 算阶码 + 填尾数 | 阶码 = 真实指数 + **127**；尾数补零到 23 位 | 阶码 `3+127=130=10000010₂`；尾数 `00001000000000000000000` |

拼接后按 4 位一组转十六进制：

```
符号位   阶码        尾数 (23位)
  1     10000010   00001000000000000000000
1100 0001 0000 0100 0000 0000 0000 0000
  C    1    0    4    0    0    0    0        →  C104 0000H
```

**`C104 0000H` 的三段拆解**（"每一部分分别是什么"）

| 部分 | 位数 | 内容 | 含义 |
|------|:---:|------|------|
| 符号位 | 1 | `1` | 负数 |
| 阶码 | 8 | `10000010` | 无符号值 = 130；**减去偏置 127** → 真实指数 = 3 |
| 尾数 | 23 | `00001000000000000000000` | 小数部分；**最前面有一个隐含不存的 1** |

即 `(-1)¹ × 1.00001₂ × 2³ = −1000.01₂ = −8.25`。

**容易错的三处**

- 阶码必须**加偏置 127**（单精度），不能直接填 3；
- 尾数的 23 位里**不含隐含的前导 1**；
- 最后拼接要按 **4 位一组**转十六进制。

## 43. LOOPNZ 循环指令的终止条件

**题目**：循环指令 LOOPNZ 终止循环的条件是（　）。

A. CX=0，且 ZF=0　B. CX=0，或 ZF=1　C. CX≠0，且 ZF=0　D. CX≠0，或 ZF=1

**正确答案：B**

LOOPNZ（等价助记符 LOOPNE）的执行：**先 `CX ← CX − 1`，再在 `CX≠0 且 ZF=0` 时继续循环**。所以**终止**（不满足继续条件）即 **CX=0 或 ZF=1**。选项 C 描述的是"**继续循环**"的条件，是它的取反，别选反了。

**四个循环指令对照：**

| 指令 | 继续循环的条件 | 说明 |
|------|---------------|------|
| LOOP | CX≠0 | 只看 CX，不看标志位 |
| LOOPE / LOOPZ | CX≠0 且 ZF=1 | "相等 / 为零"才继续 |
| LOOPNE / LOOPNZ | CX≠0 且 ZF=0 | "不等 / 非零"才继续 |
| JCXZ | — | CX=0 时**直接跳转**（进入循环前的守卫判断） |

**ZF 是什么**：ZF = **零标志（Zero Flag）**，标志寄存器中的一位，记录**上一条运算结果是否为 0**（结果为 0 → ZF=1，否则 ZF=0）。它是条件跳转 / 循环判断的依据之一。

## 44. Linux 硬链接与软链接（附 inode 图解）

**题目**：Linux 中包括两种链接：硬链接（Hard Link）和软链接（Soft Link），下列说法正确的是（　）。

A. 软连接可以跨文件系统进行连接，硬链接不可以
B. 当删除原文件的时候软连接文件仍然存在，且指向的内容不变
C. 硬链接被删除，磁盘上的数据文件会同时被删除
D. 硬链接会重新建立一个 inode，软链接不会

**正确答案：A**

**核心区别在于"指向什么"：**

| 对比 | 硬链接 | 软链接（符号链接） |
|------|--------|-------------------|
| 指向对象 | 文件的 **inode**（同一份数据） | 一个保存**目标路径**的独立文件 |
| 能否跨文件系统 | ❌ 不能 | ✅ 可以 |
| 删原文件后 | 只要还有链接，数据仍可访问 | 链接仍在，但变**悬空（dangling）**，失效 |
| inode | 与原文件**同一个** | **有自己独立的** inode |
| 能否指向目录 | 通常不允许 | 可以 |

逐项判定：
- **A ✅**：软链接存路径，可跨文件系统；硬链接依赖同一文件系统的 inode，不能跨。
- **B ❌**：删目标后软链接仍存在，但目标路径失效，**访问不到原内容**（并非"内容不变"）。
- **C ❌**：删一个硬链接只是**减少链接计数**；只有计数归零且无进程仍打开该文件，数据才被释放。
- **D ❌**：说反了——硬链接**不**新建 inode，软链接才**有**独立 inode。

**inode 是什么**：文件系统中描述文件**元数据**的结构——大小、权限、所有者、时间戳、数据块位置等；**不含文件名**。文件名保存在**目录项**里，通过 inode 编号关联到 inode。

```
a.txt ─┐
       ├── inode 123 ── 文件数据
b.txt ─┘
```

删除 `a.txt` 只是删掉"名字 → inode"这一条目录记录，`b.txt` 仍指向同一 inode，数据照常可读。

**软链接存的是路径，不是 inode**：访问软链接时，系统按它记录的路径**重新查找**目标；目标被改名 / 移动 / 删除后路径失效，软链接即失效。硬链接则直接与 inode 绑定，删掉某个名字不影响其他名字。

- [[OS八股]] — 「几个易混 Linux 概念」小节（SIGSEGV / `mv` 与 mtime / `ulimit` / `malloc` 与 brk、mmap 等），文件系统相关概念的落点

## 45. 二维数组的列优先（列存储）偏移量

**题目**：二维数组 k[1..7, 1..9]，每元素占 2 字节，使用列存储，a[5,4] 的偏移量为（　）字节。

A. 78　B. 39　C. 25　D. 50

**正确答案：D（50）**

**"列优先 / 列存储"指什么**：**同一列的元素在内存中连续存放**（与"按列读取"是两回事）。该数组 7 行 9 列，列优先的存放顺序是：

```
k[1,1], k[2,1], …, k[7,1],   ← 第 1 列（7 个）
k[1,2], k[2,2], …, k[7,2],   ← 第 2 列
……
```

**算 a[5,4]**（默认以首元素 k[1,1] 为偏移起点），它前面有：

- 前 **3 整列**：3 × 7 = **21** 个元素
- 第 4 列中、第 5 行**之前**：还有 4 个元素

合计 21 + 4 = **25 个元素**，每元素 2 字节 → 25 × 2 = **50 字节**。

**注意区分**：若题目问**元素序号偏移**则是 25；问**字节偏移**才是 50。列优先地址算法：**先数前面完整的列，再数当前列中目标行前面的元素**。

**列优先 vs 行优先**：行优先（C / Java 的 `int[][]`）是"一行一行连续存"；列优先（Fortran / MATLAB）是"一列一列连续存"。同一元素在两种存储下的地址公式互为转置。

**本题关联笔记**

- 与本篇 **#36**（特殊矩阵压缩存储）同属"数组的存储与下标计算"：三角 / 对称矩阵按行 / 列优先压缩成一维数组后，求下标用的正是同一套"先数前面完整行或列，再数本行/列内偏移"的方法。

## 46. 会产生 Belady 现象的页面淘汰算法

**题目**：下述（　）页面淘汰算法会产生 Belady 现象。

A. 先进先出（FIFO）　B. 最近最少使用（LRU）　C. 最不经常使用（LFU）　D. 最佳（OPT）

**正确答案：A（FIFO）**

**Belady 现象**：给进程分配的**页框数增加，缺页次数反而增加**的异常。

| 算法 | 是否产生 Belady | 原因 |
|------|:---:|------|
| FIFO | ✅ 会 | 决策依据（进入顺序）随页框数变化而"抖动"，不满足栈包含性质 |
| LRU（最近最少使用） | ❌ 不会 | 是**栈算法**，页框数越大驻留集一定单调变大 |
| OPT（最佳） | ❌ 不会 | 同样满足栈包含性质 |
| LFU（最不经常使用） | ❌ 非经典考点答案 | 经典题默认答案是 FIFO |

**"栈包含性质"是判据**：若算法满足"n 个页框时的驻留集 ⊇ (n−1) 个页框时的驻留集"，就不会出现 Belady——LRU / OPT 满足，FIFO 不满足。

## 47. 完全二叉树的叶子结点数（n = 2000）

**题目**：一颗完全二叉树的节点总数为 2000，它的叶子节点数为（　）。

A. 977　B. 985　C. 993　D. 1000

**正确答案：D（1000）**

**为什么 2000 − 1023 = 977 不对**：977 是**最后一层的节点数**，不是整棵树叶子数。倒数第二层里没孩子的节点**也是叶子**，被漏掉了。

**分层手算**（前 10 层满，共 2¹⁰ − 1 = 1023 个节点）：

- 第 11 层：2000 − 1023 = **977** 个节点，都是叶子；
- 第 10 层共 2⁹ = 512 个节点；977 = 2 × 488 + 1 → 前 **489** 个节点有孩子，后 512 − 489 = **23** 个节点没孩子，**也是叶子**；
- 叶子总数 = 977 + 23 = **1000**。

**通用结论（层序编号）**：按"从上到下、每层从左到右"编号（根为 1），节点 i 的左右孩子是 2i、2i+1。只要 2i &gt; n，节点 i 就没有左孩子 → 是叶子。因此：

$$\text{非叶节点} = 1 \sim \left\lfloor \frac{n}{2} \right\rfloor, \qquad \text{叶子} = n - \left\lfloor \frac{n}{2} \right\rfloor = \left\lceil \frac{n}{2} \right\rceil$$

代入 n = 2000：叶子 = 2000 − 1000 = **1000**（即编号 1001~2000）。

**⌊·⌋ 是向下取整**：$\lfloor 2000/2 \rfloor = 1000$。

**官方解析的一处不严谨**：它写"每个非叶节点产生 2 个子节点"——完全二叉树可能有**只有左孩子**的节点。结论 D 正确，但用上面的分层法或 ⌈n/2⌉ 公式更稳。
