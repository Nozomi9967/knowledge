### **MySQL InnoDB 通过等待图（wait-for graph）主动检测死锁并回滚代价较小的事务，应用层需按"固定顺序加锁 + 幂等重试 + 指数退避"来兜底。**

下面按面试口述节奏展开。

---

**第一部分：先说 MySQL InnoDB 的死锁检测机制**

InnoDB 处理锁冲突有两条路径：

**一是锁等待超时**，由参数 `innodb_lock_wait_timeout` 控制，默认 50 秒。一个事务等锁超过这个时间，就会被强制回滚并报 `Lock wait timeout exceeded`。这是被动兜底，粒度粗、响应慢。

**二是主动死锁检测**，也就是死锁真正的处理机制，由参数 `innodb_deadlock_detect` 控制（默认开启）。

它的核心数据结构是 **wait-for graph（等待图）**：

- 图中每个节点是一个事务；
- 每条有向边表示"事务 A 在等待事务 B 持有的锁"；
- 每当一个新事务因加锁被阻塞时，InnoDB 就会**从这个事务出发做一次 DFS**，看有没有形成环；
- 一旦发现环，就判定为死锁。

发现死锁后，InnoDB 会选一个 **"回滚代价最小"** 的事务作为牺牲者，把它 rollback、释放锁，让另一个事务继续。选择依据主要是事务修改的行数、undo log 大小，简单说就是**改得少的先死**。牺牲者会收到 `ERROR 1213: Deadlock found when trying to get lock; try restarting transaction`。

对面试题里的场景：两个事务以相反顺序更新同一批订单，比如：

- 事务 A：先锁订单 100，再锁订单 200；
- 事务 B：先锁订单 200，再锁订单 100；

A 拿到 100 等 200，B 拿到 200 等 100，等待图里 A→B→A 形成环，InnoDB 检测到后杀掉其中一个。这就是最典型的**加锁顺序不一致导致的死锁**。

**顺带一提性能坑**：死锁检测的复杂度大约是 O(n²)，n 是等待锁的事务数。在高并发热点行场景下（比如秒杀），检测本身会消耗大量 CPU，甚至比锁等待还严重。这时候可以考虑关闭 `innodb_deadlock_detect`、只靠超时兜底，但要谨慎，通常配合业务改造（分散热点、削峰）一起做。

---

**第二部分：从根源上避免死锁**

死锁最有效的治理不是重试，而是**不让它发生**。针对题目里的场景，几个关键做法：

**1. 统一加锁顺序**：这是最直接的解法。业务代码里凡是要批量更新订单，都先按 `order_id` 排序再逐个加锁，让所有事务的加锁顺序完全一致，等待图就永远不会成环。

```sql
-- 反例：按 List 传入顺序更新
UPDATE orders SET status=1 WHERE id IN (200, 100);

-- 正例：应用层先排序，再逐条或按序范围锁
SELECT * FROM orders WHERE id IN (100, 200) ORDER BY id FOR UPDATE;
```

注意 `IN` 语句的加锁顺序不完全等于 `IN` 里的顺序，InnoDB 是按索引顺序加锁的，所以**依赖索引顺序而不是应用层传参顺序**。真正保险的做法是拆成逐条 `SELECT ... FOR UPDATE` 且应用层排好序。

**2. 缩短事务范围**：事务越大、持锁时间越长，死锁概率指数级上升。把不必要的 RPC、外部调用、日志写入挪出事务，事务里只做必要的 DB 操作。

**3. 用更精确的索引**：确保 `WHERE` 条件能走索引，避免全表扫描导致的范围锁扩大。索引不好会让本来只锁一行的操作变成锁一片，间接增加冲突面。

**4. 降低隔离级别或用乐观锁**：RR 下 Next-Key Lock 更容易产生死锁；如果业务允许，读多写少的场景可以用**版本号乐观锁**（`WHERE version = ? ... SET version = version + 1`）替代悲观锁，冲突时直接更新失败，走应用层重试，比死锁友好得多。

---

**第三部分：应用层重试策略（重点）**

即使做了预防，死锁在高并发下仍然无法 100% 消除，所以**重试是必须的兜底**。核心原则有五点：

**1. 精准捕获错误码，不要一把梭**

只对可重试错误重试，避免把业务异常也当成死锁重试导致数据错乱：

- `1213` — `Deadlock found`，可以立即重试；
- `1205` — `Lock wait timeout`，可以重试但要谨慎（可能是慢事务，重试会加剧压力）；
- 其他业务异常（唯一键冲突、外键错误）**绝对不能重试**。

```java
catch (SQLException e) {
    if (e.getErrorCode() == 1213) {
        // 死锁，重试
    } else {
        throw e;
    }
}
```

**2. 事务级别的重试，不是 SQL 级别**

死锁发生后**整个事务已经被 InnoDB 回滚了**，重试必须从 `BEGIN` 开始重新执行整段业务逻辑，而不是只重跑那一条失败的 SQL。这是很多人踩的坑：如果只重发最后一条 UPDATE，前面已回滚的更新就丢了。

**3. 幂等性是前提**

重试的方法必须幂等，否则重试可能造成"多扣一次库存""重复扣款"。保证幂等的常见手段：

- 用业务唯一键（如订单号）做去重；
- `UPDATE ... WHERE status = 'pending'` 这类带状态判断的更新，天然幂等；
- 借助分布式锁或去重表兜底。

**4. 指数退避 + 随机抖动**

不要立刻死循环重试，两个死锁的事务同时重试，很可能**再次以相同顺序冲突**，形成活锁。标准做法是指数退避加 jitter：

```java
int maxRetry = 3;
for (int i = 0; i < maxRetry; i++) {
    try {
        doTx();
        return;
    } catch (DeadlockException e) {
        if (i == maxRetry - 1) throw e;
        long backoff = (1L << i) * 10 + random.nextInt(20);   // 10~30ms, 20~50ms, 40~90ms
        Thread.sleep(backoff);
    }
}
```

重试次数一般 **3 次以内**，超过就直接抛错让上游处理，避免请求堆积拖垮系统。

**5. 监控与告警**

重试是兜底，不是常态。要把死锁次数、重试次数打点上报，一旦频次异常就报警。生产上排查用：

- `SHOW ENGINE INNODB STATUS\G` — 看最近一次死锁的详情，包含两个事务的 SQL、持有锁、等待锁；
- `information_schema.innodb_trx / innodb_locks / innodb_lock_waits`（8.0 是 `performance_schema.data_locks`）— 实时查看锁情况；
- 开启 `innodb_print_all_deadlocks=ON`，把所有死锁打到 error log 便于事后复盘。

---

**面试收尾一句话：**

MySQL 靠等待图主动检测死锁，代价最小的事务被回滚；但检测本身是被动的、有开销的。**根治靠"统一加锁顺序 + 缩短事务"，兜底靠"捕获 1213 + 事务级重试 + 指数退避 + 幂等保证"**。真正线上稳定的服务，不是没有死锁，而是死锁发生时用户完全无感。
