# Nozomi-Mall 项目深度面试分析报告

---

## 1. 项目概括（简历用）

**一句话描述：** 基于 Spring Cloud Alibaba 微服务架构的 B2C（**Business to Consumer**） 电商平台，涵盖商品搜索、订单交易、秒杀抢购、支付对接及多级缓存一致性等完整电商链路。

**核心价值：** 完整复现工业级电商后端核心业务闭环，验证了微服务架构在电商场景下的高并发、高可用技术方案。

**规模定性：** 生产级微服务项目原型（课程实训项目，14个微服务，完整电商场景），非简单 Demo，但未经历真实线上流量考验。

> [!abstract]- ORM 解析 — Object Relational Mapping（对象关系映射）
> 在**关系型数据库**（MySQL）和**面向对象语言**（Java）之间做数据转换。数据库存"表"，代码用"对象"，ORM 充当翻译层。
>
> | 语言 | ORM 框架 |
> |------|----------|
> | Java（本项目） | **MyBatis-Plus** / JPA |
> | Python | SQLAlchemy |
> | Go | GORM |
>
> **优点**：开发快、代码清晰、切换数据库成本低
> **面试高频坑**：⚠ [[06-其他杂项/N+1查询问题详解\|N+1 查询问题]] · 懒加载 · 复杂查询性能不如手写 SQL
> **本项目**：MyBatis-Plus + MySQL，代码生成器提速 CRUD，Lambda 防注入

> [!summary]- MyBatis-Plus 解析 — MyBatis 增强工具
> 只做增强不做改变，在 MyBatis 基础上提供**自动 CRUD、条件构造器、分页插件**。
>
> | 对比 | MyBatis-Plus ✅ | 原生 MyBatis | JPA |
> |------|----------------|-------------|-----|
> | CRUD 效率 | 零 SQL（BaseMapper） | 写 XML | 零 SQL |
> | 复杂查询 | LambdaWrapper / 手写 XML | 手写 XML | JPQL |
> | 类型安全 | ✅ Lambda 方法引用 | ❌ 字符串拼接 | ⚠ 编译期不检查 |
>
> **三大核心**：① `BaseMapper<T>` 继承即用 CRUD；② `LambdaQueryWrapper` 链式条件构造，防 SQL 注入；③ `PaginationInnerInterceptor` 自动拼分页 SQL
> **面试高频**：⚠ 分页插件版本匹配 · updateById 全字段更新 · 逻辑删除与唯一索引冲突
> **本项目**：MyBatis-Plus + MySQL + Generator 代码生成器 + Lambda 防注入，复杂查询手写 XML
>
> 📖 详细解析：[[06-其他杂项/MyBatis-Plus详解]]

> [!info]- Seata 解析 — Simple Extensible Autonomous Transaction Architecture（分布式事务中间件）
> 阿里巴巴开源的**分布式事务**解决方案，解决微服务跨库/跨服务数据一致性。
>
> | 模式 | 侵入性 | 适用场景 |
> |------|--------|---------|
> | **AT** ✅ 本项目 | 低（`@GlobalTransactional`） | 下单、支付等非极致并发 |
> | **TCC** | 高（三接口） | 秒杀扣减等短事务 |
> | **Saga** | 中（状态机） | 长业务流程 |
> | **XA** | 低 | 数据库原生协议 |
>
> **核心原理（AT）**：一阶段自动拦截 SQL 生成 **undo log**（前/后镜像），二阶段全部成功则清理、任一失败则反向恢复。
> **面试高频**：⚠ 全局锁性能开销 · AT vs TCC 选型 · undo log 清理策略 · Feign 超时配置
> **本项目**：下单 5 步操作（查购物车→扣库存→新增订单明细→新增订单主表→清购物车），`@GlobalTransactional` 零侵入保证 ACID
>
> 📖 详细解析：[[06-其他杂项/Seata详解]]

> [!info]- CDC 解析 — Change Data Capture（变更数据捕获）— Canal 详解
> 通过监听 MySQL **binlog**，实时捕获数据变更并同步到其他系统。
>
> **架构链路**：`MySQL → Canal → Canal Client → Feign → Search 服务 → ES / 静态页`
>
> **为什么用 Canal 而不是双写**：解耦业务代码，零侵入
> **高可用**：Canal 集群 + ZK 选举 + 断点续传
> **容灾**：定期全量重建索引 + 增量同步保证最终一致性
>
> 📖 详细解析：[[06-其他杂项/CDC（Canal）详解]]
>
> *本表中有多个技术点（Sentinel、Seata、RocketMQ 等）可按需展开为独立详解文件。*

> [!example]- OLAP 解析 — Online Analytical Processing（联机分析处理）— Apache Druid
> 面向**分析型**场景，支持对海量数据进行多维聚合、钻取等复杂查询。
>
> | 对比 | OLTP（事务处理） | OLAP（分析处理） |
> |------|----------------|----------------|
> | 典型操作 | 增删改查 | 聚合查询（SUM/GROUP BY） |
> | 数据量 | MB ~ GB | TB ~ PB |
> | 代表系统 | MySQL | **Druid**、ClickHouse |
>
> **Druid 三板斧**：列式存储 · 预聚合（Roll-up） · 时间分区
> **本项目**：通过 Avatica JDBC 查询 Druid，热门商品分析亿级数据秒级返回
>
> 📖 详细解析：[[06-其他杂项/OLAP（Druid）详解]]

> [!summary]- Feign 解析 — 声明式 HTTP 客户端
> 用 **Java 接口 + 注解** 方式调用远程 HTTP 服务，无需手写 HTTP 请求代码。
>
> **解决了什么**：代替 RestTemplate，代码更简洁，URL 集中管理
> **工作流程**：`@FeignClient → 动态代理 → 服务发现（Nacos）→ 负载均衡 → HTTP 调用`
>
> | 对比 | Feign（✅ 本项目） | RestTemplate |
> |------|-------------------|-------------|
> | 编码方式 | 声明式接口 + 注解 | 手写 HTTP 请求 |
> | 可读性 | 好，集中管理 | 差，URL 散落各处 |
> | 负载均衡 | 内置 | 需手动整合 |
>
> **面试高频**：⚠ 超时配置 · 服务名解析 · @RefreshScope 冲突
> **本项目**：Canal Client → Feign → Search/Page 服务
>
> 📖 详细解析：[[06-其他杂项/Feign详解]]

> [!summary]- Elasticsearch 解析 — 分布式搜索引擎
> 基于 **Apache Lucene** 的分布式搜索引擎，倒排索引实现毫秒级全文搜索。
>
> **解决了什么**：替代 MySQL LIKE 模糊查询，百万级数据分词毫秒级检索
> **工作流程**：`MySQL（binlog）→ Canal → Feign → Search 服务 → ES shopsearch 索引`
>
> | 对比 | ES（✅ 本项目） | MySQL LIKE |
> |------|----------------|------------|
> | 查询方式 | 倒排索引 + 分词 | 全表扫描 |
> | 性能（百万级） | < 50ms | 秒级 |
> | 中文分词 | ✅ IK 分词器 | ❌ 不支持 |
> | 多条件组合 | ✅ bool（match + term + range + filter） | ❌ SQL 拼接 |
>
> **面试高频**：⚠ 倒排索引原理 · 深分页问题 · 分词器选型 · Canal 挂掉后 ES 一致性
> **本项目**：Canal 监听 sku 表 → ES shopsearch 索引 → 前端搜索
>
> 📖 详细解析：[[06-其他杂项/ES详解]]

> [!summary]- Redisson 解析 — Redis 客户端 & 分布式解决方案
> 基于 **Redis** 的 Java 内存数据网格，提供分布式锁、布隆过滤器、分布式集合等高级功能，内置看门狗自动续期机制。
>
> **解决了什么**：替代手写 SETNX+Lua 脚本，封装分布式锁、布隆过滤器等高阶数据结构
> **核心功能**：分布式锁（可重入/公平/读写锁）、`RBloomFilter`、`RSemaphore`、`RCountDownLatch`
>
> | 对比 | Redisson（✅ 本项目） | 原生 Jedis SETNX |
> |------|---------------------|-----------------|
> | 原子加锁 | ✅ 内置 Lua 脚本 | ⚠ 需手写 Lua |
> | 自动续期 | ✅ WatchDog 看门狗 | ❌ 需手动续期 |
> | 阻塞等待 | ✅ tryLock 可配置等待时间 | ❌ 一次失败就返回 |
> | 数据结构 | ✅ 锁/布隆过滤器/队列/信号量 | ❌ 仅基础命令 |
>
> **面试高频**：⚠ 看门狗实现原理 · Lua 脚本保证原子性 · 锁粒度设计 · RedLock 算法争议
> **本项目**：秒杀 6 层漏斗终极兜底 + 网关 BloomFilter 防缓存穿透
>
> 📖 详细解析：[[06-其他杂项/Redisson详解]]

## 3. 核心模块拆解

### 3.1 商品搜索模块（ES全文检索）

- **功能**：用户输入关键词，按分类/品牌/价格区间/属性过滤，支持高亮、排序、分页
- **技术实现**：
  - Canal 监听 MySQL `sku` 表 binlog → Feign 调用 Search 服务 → 写入 ES `shopsearch` 索引
  - ES 使用 `bool` 查询组合多条件过滤（`term` + `range` + `match`）
  - 前端通过 `mall-search-web`（Thymeleaf）渲染搜索结果页
  - Canal 同时触发静态页面重新生成（Thymeleaf 模板渲染为 HTML 文件）
- **设计决策**：
  - **为什么用 Canal 而不直接写 ES**：CDC 模式解耦业务写与搜索同步，避免业务代码侵入
  - **传统双写 vs CDC 对比**：

| 维度    | 传统业务双写                    | CDC 模式（Canal）✅                       |
| ----- | ------------------------- | ------------------------------------ |
| 做法    | 写完 MySQL 紧跟着写 ES          | 代码只管 MySQL，Canal 异步监听 binlog 自动同步    |
| 代码耦合  | ❌ 高，商品服务混杂 ES 和静态页逻辑      | ✅ 低，商品服务只关注核心业务                      |
| 数据一致性 | ❌ 差，写完 MySQL 网络闪断就两边不一致   | ✅ 好，MySQL 写入成功就有 binlog，Canal 保证最终同步 |
| 性能影响  | ❌ 大，接口等 MySQL + ES 都写完才返回 | ✅ 小，MySQL 写入后直接返回，异步同步性能极高           |

  - 为什么不直接用 MySQL LIKE：百万级商品 LIKE 效率极低，ES 倒排索引实现分词毫秒级搜索
  - 为什么不用消息队列做同步：Canal 直连 Feign 减少了 RocketMQ 带来的延迟，架构更简洁
- **追问**：Canal 如果挂掉如何处理数据一致性问题？ES 索引重建策略？分词器配置？

### 3.2 订单创建模块（分布式事务）

- **功能**：用户下单 → 查购物车 → 扣库存 → 新增订单明细+主表 → 清购物车
- **技术实现**：
  - `@GlobalTransactional`（Seata AT）包裹 5 步操作（查购物车→扣库存→新增订单明细→新增订单主表→清购物车）
  - 库存扣减用 MySQL 原子 UPDATE：`UPDATE sku SET num=num-#{num} WHERE id=#{id} AND num>=#{num}`（防超卖）
  - 购物车使用 MongoDB 存储，灵活字段，无需 JOIN
- **设计决策**：
  - 为什么用 Seata AT 而非 TCC：AT 对业务侵入小，自动生成反向 SQL，适合非高并发下单场景
  - 为什么购物车用 MongoDB 不用 Redis：购物车数据需要持久化不能丢，Redis 更适合纯缓存
- **追问**：Seata AT 的二阶段回滚原理？全局锁对性能的影响？库存扣减出现负数的兜底机制？

### 3.3 秒杀模块（7 层防护架构）

- **功能**：定时秒杀商品，用户抢购并支付，从网关层到数据库层层过滤保证系统稳定

- **7 层漏斗模型（Funnel Model）**：

  ```
        【所有请求】
            │
            ▼
  ┌──────────────────────────┐
  │ ⓪ Nginx/OpenResty 层     │ ── IP限流、UA黑名单、Lua脚本基础校验
  └──────────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ ① BloomFilter URI 校验   │ ── 拦截非法/不存在的商品ID（缓存穿透防护）
  └──────────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ ② JWT 登录鉴权（IP绑定）   │ ── 拦截未登录、Token过期或异地刷单
  └──────────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ ③ RBAC 权限校验          │ ── 验证用户角色（会员等级限制等）
  └──────────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ ④ Redis 热点库存检测      │ ── DECR 原子减库存，拦截已售罄请求（挡90%+流量）
  └──────────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ ⑤ RocketMQ 异步削峰      │ ── 同步并发转异步排队，削峰填谷
  └──────────────────────────┘
            │
            ▼
  ┌──────────────────────────┐
  │ ⑥ Redisson 分布式锁防超卖 │ ── 终极兜底，数据库层强一致性
  └──────────────────────────┘
            │
            ▼
        【成功下单】
  ```

- **各层防守机理**：

| 层级                  | 防守对象                  | 具体做法                                           |
| ------------------- | --------------------- | ---------------------------------------------- |
| **Nginx/OpenResty** | 恶意刷单/脚本流量、爬虫、DDoS     | IP 令牌桶限流、UA 过滤、Redis 黑名单动态拉黑、连接数限制、静态资源/CDN 分流 |
| ① **BloomFilter**   | 恶意攻击、刷不存在的商品 ID（缓存穿透） | Redisson `RBloomFilter`，位图级别判断，"不存在就是不存在"      |
| ② **JWT + IP 绑定**   | 黑产黄牛盗 Token 异地刷单      | JWT 中封装登录 IP 哈希，请求 IP 对不上直接判 Token 失效          |
| ③ **RBAC**          | 越权访问                  | 基于角色的权限控制，校验会员等级等                              |
| ④ **Redis 热点检测**    | 抢不到商品的"无效流量"          | 库存预热到 Redis，`DECR` 扣减为负数 → "已售罄"               |
| ⑤ **RocketMQ 削峰**   | 瞬时高并发冲垮订单服务           | 秒到资格者发消息排队，订单服务按能力消费                           |
| ⑥ **Redisson 锁**    | 数据库层防超卖               | 加锁 → 查 Redis 库存 → 创建订单 → 原子扣库 → 解锁             |

> 既然由redis进行扣减库存，那怎么同步到数据库

这是秒杀架构里一个很经典的"缓存与数据库一致性"问题。核心思路是:**Redis扣减是"实时的、强一致的"，数据库更新是"异步的、最终一致的"**。具体落地方式跟你⑤层的RocketMQ正好衔接上,流程大致是这样:

```
用户请求
    │
    ▼
④ Redis DECR库存 (原子操作,立即返回成功/失败)
    │ (扣减成功)
    ▼
⑤ 发送MQ消息 (订单创建消息,包含userId、商品ID、数量)
    │
    ▼
消费者异步处理:
    ├─ 创建订单记录(数据库)
    ├─  
    └─ 扣减失败 → 触发补偿(回滚Redis库存 + 取消订单)
```

**为什么这样设计?**

1. **Redis扣减是"快速响应层"**,用户在毫秒级就能知道"抢到了/没抢到",不需要等数据库IO。秒杀的瞬时QPS可能是数据库承受能力的几十上百倍,如果每个请求都同步写数据库,数据库直接被打挂。
    
2. **数据库更新是"持久化兜底层"**,通过MQ异步消费,把瞬时的高并发"削峰"成数据库能承受的稳定写入速率(比如MQ消费者控制并发数为50)。
    

**关键问题:Redis和数据库会不会不一致?**

会有短暂不一致,但最终一致。几种处理方式:

- **方案一(主流):Redis库存为准,数据库异步追平**
    
    - Redis里的库存数量是"权威值",数据库的更新只是为了持久化和后续对账
    - 即使MQ消费者宕机,消息会重新投递(RocketMQ的重试机制),最终数据库一定会被更新
- **方案二:对账补偿任务**
    
    - 定时任务(比如每隔几分钟)对比Redis库存 vs 数据库库存 vs 已创建订单数,如果发现差异就告警或自动修正
    - 这是给"万一MQ消息丢失"上的最后一道保险

**和你⑥层Redisson分布式锁的关系**

注意⑥层"分布式锁防超卖"其实是在**消费者处理订单、写数据库这一步**生效的——虽然Redis DECR已经保证了不会超卖,但如果有"库存预扣 + 后续确认"这种两阶段逻辑(比如用户拍下后还有支付环节,支付超时要释放库存),分布式锁就是用来保护"读取库存→判断→更新"这个非原子操作序列在数据库层面的并发安全。

**给你的nozomi-house的建议**

如果做demo,可以这样组织:

- Redis里维护 `seckill:stock:{productId}` 这个key,用`DECR`
- DECR后值 ≥ 0 → 成功,发送RocketMQ消息(`SeckillOrderMessage`)
- DECR后值 < 0 → 立即返回"已售罄",并执行`INCR`把刚才扣多的加回去(避免库存变成负数越来越大)
- RocketMQ消费者落库:`UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0`,如果`affected rows = 0`说明数据库库存也不够了(理论上不该发生,除非有人绕过Redis直接改库存),记录异常日志触发告警

这套逻辑写出来,面试时讲"为什么用DECR而不是先GET再判断再SET"(避免竞态条件)、"为什么要INCR回滚"(防止库存虚减),都是很好的加分点。

> 我记得有一步将秒杀订单和普通订单的请求分开来，是哪里判断的来着


这个判断通常发生在**网关层(Gateway)**,基于请求的URL路径或者请求参数来做路由分流。具体来说有这几种常见做法:

**1. URL路径区分(最常见)**

- 普通订单:`/api/order/create`
- 秒杀订单:`/api/seckill/order/create`

网关根据路径前缀(比如`/seckill/**`)就能识别出这是秒杀请求,直接路由到专门的秒杀服务(比如你架构里独立的`seckill-service`),走前面说的6层防护漏斗;而普通订单走常规的下单流程,不需要过Redis库存预扣、MQ削峰这些。

**2. 在网关层加标识/打标** 有些设计会在网关层给请求打一个标签(比如在请求头里加`X-Order-Type: SECKILL`),后续的服务、日志、链路追踪都可以根据这个标识做差异化处理(比如秒杀订单走单独的日志通道、单独的监控大盘)。

**3. 商品维度的判断(更细粒度)** 有时候不是看URL,而是看**商品ID**——网关或者第一层服务查一下"这个商品ID是不是当前在秒杀活动中"(可能是查Redis里的一个秒杀商品集合`seckill:active:products`),如果是,就走秒杀链路;如果不是,走普通链路。这种方式适合"同一个商品详情页,但某些时间段内变成秒杀商品"的场景。

**为什么要分开?**

核心原因是**资源隔离**——秒杀订单和普通订单对系统的压力完全不是一个量级:

- 秒杀订单需要走Redis预减库存、MQ异步削峰、独立的限流策略,甚至可以部署在独立的服务实例上(避免秒杀流量打垮普通下单服务)
- 普通订单走传统的"查库存→下单→扣库存"同步流程就够了,没必要给所有订单都套上秒杀的复杂链路,那样反而增加了普通订单的延迟和出错概率

> 代理层nginx的作用

Nginx层主要做这几件事,跟你nozomi-mall里已经搭的OpenResty+Lua+Kafka access log那套是一脉相承的:

**1. 限流(Rate Limiting)** 用`limit_req_zone`基于IP做令牌桶限流,比如每个IP每秒最多5个请求。这是最便宜的防护——在请求还没进入Java应用之前就把恶意刷单/脚本流量挡掉,Lua和Java资源消耗为零。

**2. IP黑名单/UA过滤** 通过Lua脚本读取Redis里的黑名单(比如检测到某IP高频请求就动态拉黑),或者过滤掉明显是爬虫的User-Agent。

**3. 静态资源/CDN分流** 秒杀页面的静态资源(图片、JS、CSS)直接走CDN或Nginx本地缓存返回,不打到后端。这能过滤掉大量"看热闹"但不会真正下单的流量。

**4. 连接数限制** `limit_conn`限制单IP并发连接数,防止单一来源占用过多服务器连接资源。

**5. 简单的本地缓存命中** 比如商品详情页的GET请求,如果数据变化不频繁,可以在Nginx层用`proxy_cache`直接缓存响应,根本不需要到网关。


> 为什么要把这层放最外面、跟网关分开?

- **成本梯度**:Nginx的C代码处理一个被拒绝的请求,开销是微秒级;而到了网关层,哪怕只是布隆过滤器判断,也涉及了应用进程的调度、连接处理等更高成本的操作。秒杀场景下90%以上的流量可能是恶意脚本或者重复刷新,在最便宜的地方挡掉收益最大。
- **职责分离**:Nginx做的是"流量层面"的粗筛(谁在发请求、发了多少),网关做的是"业务层面"的细筛(这个商品ID合不合法、这个用户有没有权限)。两者用不同维度过滤,组合起来漏斗效果更好。

- **技术实现**：
  - Nginx `limit_req_zone` 令牌桶限流 + `limit_conn` 连接数限制
  - OpenResty Lua 脚本读取 Redis 黑名单动态拦截恶意 IP/UA
  - Nginx `proxy_cache` 本地缓存静态资源/API 响应，CDN 分流

  - Redis 预扣库存：`DECR` 原子操作，秒杀成功后在 RocketMQ 中排队

- **设计决策**：
  - 为什么 Nginx 放在最外层、跟网关分开：**成本梯度**——Nginx C 代码处理一个拒绝请求是微秒级，网关 Java 应用进程调度成本更高，在最便宜的地方挡掉 90%+ 恶意流量收益最大；**职责分离**——Nginx 做流量层面粗筛（谁在发、发了多少），网关做业务层面细筛（商品 ID 合法性、用户权限），组合成漏斗效果更好
  - 为什么用 Redisson 而非 Jedis 的 SETNX：Redisson 自带看门狗自动续期，防止锁过期而业务未完成
  - 为什么用 Elastic-Job 而非 @Scheduled：分布式环境下避免多节点重复执行，支持分片与故障转移
  - 为什么 BloomFilter 放在第一层（网关层中的第一层）：位图级别判断极快，不存在直接阻断，避免无效请求浪费后续资源
  - 为什么 Redis 预扣在前、RocketMQ 削峰在后：Redis 挡掉 90%+ 无效流量，确保进 MQ 的都是真正抢到资格的请求

### 3.4 支付模块（事务消息）

- **功能**：微信支付回调 → 更新支付日志 → 通知订单服务 → 发放积分
- **技术实现**：

### 3.5 多级缓存架构

- **功能**：Nginx → Redis → Tomcat 三级缓存，数据库变更通过 Canal 反向更新缓存
- **技术实现**：
  - Lua + Redis：OpenResty 在 rewrite 阶段执行 `aditem.lua` 查询 Redis
  - Nginx Proxy Cache：缓存磁盘存储，`proxy_cache_valid 200 304 60s`
  - Cache Purge 模块：手动清理 Nginx 缓存
  - Spring `@Cacheable` / `@CacheEvict` 注解：Spring Cache 抽象层
- **设计决策**：
  - 为什么需要三级缓存：Tomcat 抗并发极差，Nginx（C 语言事件驱动）可支撑万级并发
  - Lua 查询 Redis vs 直接访问 Tomcat：减少 TCP 连接与线程切换开销
- **追问**：缓存一致性保障（Canal 延迟导致脏读）？缓存穿透/击穿/雪崩的应对策略？布隆过滤器误判率设置依据？

### 3.7 文件存储模块（FastDFS）

- **功能**：商品图片、品牌 Logo 等静态资源的上传、存储与 HTTP 访问
- **技术实现**：
  - **FastDFS 架构**：Tracker Server（调度） + Storage Server（存储），Storage 支持分组（group），每组内可多台互备
  - **Java 客户端**：`mall-file-service` 通过 `fastdfs-client-java` SDK 调用 Tracker 获取 Storage 地址，上传文件后返回 `group/M00/00/00/xxx.jpg` 格式路径
  - **HTTP 访问链**：Nginx 集成 `fastdfs-nginx-module` 模块，收到 `/group1/M00/...` 请求后转发到 Storage 读取文件返回
  - **版本匹配**：libfastcommon V1.0.43 + FastDFS V5.12 + fastdfs-nginx-module V1.20 + Nginx 1.20.1，版本严格对应
- **设计决策**：
  - 为什么用 FastDFS 而非 MinIO/OSS：FastDFS 是传统分布式文件系统，专为中小文件（4KB~500MB）优化，适合电商图片存储场景；相比 OSS 不依赖云厂商，私有化部署
  - 为什么 Tracker 先于 Storage 启动：Tracker 负责集群调度，Storage 启动后要向 Tracker 注册，启动顺序反了会导致 Storage 注册失败
  - 为什么 Nginx 要加 `fastdfs-nginx-module` 而非直接暴露 Storage：Storage 本身无 HTTP 能力；Nginx 模块实现 FastDFS 协议 → HTTP 协议的转换，并提供负载均衡与缓存能力
  - 为什么图片放在 location 规则前：避免被通用静态资源 `\.(png|jpg|jpeg)$` 规则提前拦截
- **追问**：FastDFS 的 group 机制如何实现跨机房互备？Storage 宕机后 Tracker 如何感知和切换？上传性能瓶颈在哪里？

### 3.8 热点发现模块（Druid + ElasticJob）

- **功能**：通过 OLAP 引擎分析用户行为日志，每 30 秒识别热点商品，自动推入秒杀隔离池预热
- **技术实现**：
  - 用户点击行为日志通过异步队列实时灌入 Apache Druid
  - ElasticJob 每 30 秒触发聚合查询：统计过去 1 分钟内访问量 Top 100 且增速最快的商品 ID
  - 超过阈值（如 > 5000 次/秒）的商品自动标记为"热商品"，推入 Redis 秒杀隔离池并预热库存
  - 同步更新网关 BloomFilter 和限流规则，秒杀商品直接走异步 MQ 排队
- **设计决策**：
  - 为什么用 Druid 而非 MySQL/Redis/ZSET 做频次统计：MySQL 扛不住高频 GROUP BY 聚合，Redis ZSET 在超高并发下自己变热点，Druid 列式存储天然适合时序数据实时摄入与毫秒级聚合
  - 为什么用 ElasticJob 而非单机定时任务：分布式协同避免多台机器同时向 Druid 发起聚合查询造成压力翻倍，同时具备故障转移能力

### 3.9 异构数据源（Polyglot Persistence）

根据不同数据类型选择最优存储引擎：

| 数据 | 存储 | 选型理由 |
|------|------|---------|
| 购物车 | **MongoDB** | 灵活 schema，用户加购字段不固定，无需预定义；数据需要持久化不能丢 |
| 订单 | **MySQL** | 强 ACID 事务，保障资金安全与数据一致性 |
| 商品搜索 | **Elasticsearch** | 倒排索引 + 分词，百万级商品毫秒级检索 |
| 用户行为分析 | **Apache Druid** | 列式存储 + Roll-up 预聚合，亿级数据秒级 OLAP 查询 |
| 商品图片/静态资源 | **FastDFS** | 中小文件（4KB~500MB）优化，私有化部署不依赖云厂商 |
| 缓存/分布式锁 | **Redis** | 内存级读写，支撑毫秒级响应与分布式锁（Redisson） |

- **设计决策**：
  - 为什么购物车用 MongoDB 不用 Redis：购物车数据需要持久化不能丢，Redis 更适合纯缓存
  - 为什么订单用 MySQL 不用 NoSQL：订单涉及资金，必须 ACID 事务保证一致性
  - 为什么搜索用 ES 不用 MySQL LIKE：百万级 LIKE 效率极低，ES 倒排索引 + 分词毫秒级检索
  - **多数据源事务解决方案**：跨服务场景用 Seata AT（下单链路 3 个服务 5 步操作）；支付状态同步用 RocketMQ 事务消息（最终一致）

## 4. 技术难点与解决方案（STAR 法则）

### 难点一：秒杀高并发防超卖

| 维度 | 内容 |
|------|------|
| **Situation** | 秒杀活动瞬间数万用户并发抢购，需保证不超卖且性能可接受 |
| **Task** | 设计高可靠、高性能的秒杀库存扣减方案 |
| **Action** | 1. 采用 **Redisson 分布式锁**对商品 ID 粒度加锁，避免 Redis 单 key 热点；2. MySQL 层配合原子 UPDATE 条件 `num>=#{num}` 做兜底；3. 锁过期时间配合看门狗自动续期 |
| **Result** | 单商品秒杀 QPS 可达数千级别（取决于 Redis 性能），库存精确无超卖 |

### 难点二：跨服务分布式事务（下单链路）

| 维度            | 内容                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| **Situation** | 下单涉及 3 个微服务（商品/订单/购物车）的 5 步操作（查购物车→扣库存→新增订单明细→新增订单主表→清购物车），任何一步失败需全部回滚                                                           |
| **Task**      | 实现跨服务 ACID                                                                                          |
| **Action**    | 引入 **Seata AT 模式**，`@GlobalTransactional` 注解声明全局事务；Seata RM 自动解析 SQL 生成 undo log；事务协调者 TC 统一管理提交/回滚 |
| **Result**    | 下单成功率提升至 ~99.9%，业务代码零侵入（仅需加注解）                                                                      |

### 难点三：支付最终一致性

| 维度 | 内容 |
|------|------|
| **Situation** | 微信支付回调可能丢包、重复通知，订单状态与支付状态需最终一致 |
| **Task** | 设计高可靠的支付状态同步机制 |
| **Action** | 采用 **RocketMQ 事务消息**：支付服务发半消息 → 执行本地插入 pay_log → commit；订单服务消费消息更新状态；RocketMQ 回查机制确保事务成功 |
| **Result** | 支付与订单状态最终一致，消息不丢不重（通过幂等性保证） |

### 难点四：数据库变更实时同步到 ES 与缓存

| 维度 | 内容 |
|------|------|
| **Situation** | MySQL 商品数据变更需实时同步到 ES（搜索）和静态页面（展示） |
| **Task** | 实现低延迟、高可靠的数据同步链路 |
| **Action** | 部署 **Canal** 伪装为 MySQL slave，监听 binlog ROW 模式变更；Canal 微服务通过 Feign 直接调用 Search/Page 服务更新 ES 索引和静态 HTML 文件 |
| **Result** | ES 与 MySQL 数据延迟在秒级以内，用户搜索即时反映最新商品状态 |

## 6. 面试高频追问预测

### 架构设计类

**Q1: 为什么用 Seata AT 而不是 TCC 或 Saga？Seata AT 的二阶段回滚原理是什么？**

*A*: AT 模式对业务侵入最小——一阶段自动生成 undo log（记录快照），二阶段通过 undo log 反向 SQL 恢复数据。适合并发不极致但需要强一致性的场景（如下单）。TCC 需要手写 try/confirm/cancel 三接口，开发成本高。Saga 缺乏隔离性。AT 的代价是全局锁会降低并发度，秒杀场景不适合。

**Q2: 你的多级缓存如何保证一致性？Canal 消费失败怎么办？**

*A*: Canal 监听 MySQL binlog 后再调 Feign 写 ES / 清 Nginx 缓存。如果 Canal 挂了，数据会堆积在 binlog 中，恢复后继续消费。更可靠的方案是加 RocketMQ 队列做异步缓冲，或使用 Canal 的高可用模式（HA）。同时缓存设置 TTL（如 60s），最终一致性兜底。

**Q3: Nginx 缓存、Redis 缓存、Tomcat 本地缓存，每层的作用分别是什么？为什么不只用一层？**

*A*: Nginx 缓存（proxy_cache）在磁盘上，容量大，可缓存静态页面/API JSON，请求不进入 JVM。Redis 缓存（内存）读取更快但成本高，适合热点数据。Tomcat 本地缓存（如 Caffeine）速度最快但各节点不一致。三层配合：Nginx 挡 80% 流量，Redis 挡 15%，Tomcat 处理不到 5%，抗压能力最优化。

### 技术原理类

**Q4: Redisson 分布式锁的实现原理？看门狗机制如何工作？**

*A*: Redisson 通过 Lua 脚本保证 SETNX + 过期时间的原子性。看门狗（WatchDog）是一个后台定时任务，默认每 10 秒检查一次锁，如果业务未完成则续期 30 秒。使用 `getLock().lock(10, TimeUnit.SECONDS)` 可以指定过期时间，此时看门狗失效。在秒杀场景应使用可重入锁 + 合理的等待时间。

**Q5: RocketMQ 事务消息的实现流程？回查机制如何处理？**

*A*: 1. 发送 half 消息（投递到 RMQ_SYS_TRANS_HALF_TOPIC）；2. 执行本地事务；3. 返回 commit/rollback。如果步骤 2 未返回，RocketMQ 会回查本地事务状态（通过 `checkLocalTransaction`）。默认回查 15 次，间隔递增。幂等性要求：消费端用唯一键（如订单号）做去重表。

> 📖 详细解析：[[RocketMQ事务消息详解]]

**Q6: Canal 的工作原理？binlog 的三种格式有什么区别？**

*A*: Canal 伪装成 MySQL slave，向 master 发送 dump 协议获取 binlog。ROW 模式记录每行变更前后的值（默认），STATEMENT 模式记录 SQL，MIXED 模式混合。Canal 要求 binlog-format=ROW。ROW 模式可精确知道哪些字段变更，但日志量最大。

### 踩坑经验类

**Q7: 微服务开发中你遇到过哪些常见的坑？如何解决的？**

*A*: ① Feign 调用超时——配置 `connectTimeout` 和 `readTimeout`（下单长事务设 600000ms）；② @RefreshScope 导致 Bean 重新初始化——避免在 @RefreshScope 的类里加 @Scheduled；③ Nacos 配置刷新不生效——确认 `bootstrap.yml` 的优先级和 `file-extension`；④ MyBatis-Plus 分页失效——需要配置 `PaginationInterceptor`；⑤ Seata AT 模式 undo_log 表膨胀——定期清理或配置回收策略。

**Q8: 秒杀场景下 Redis 热点 key 问题如何处理？**

*A*: 单商品 key 会成为热点——对 key 做本地缓存 + 打散（如 `sku:123:0`、`sku:123:1`），读取时随机选一个，写入时写所有。但加锁时只能对原始 key 加锁。也可使用 Redis Cluster 自动分片。终极方案是提前将库存预热到本地内存，Nginx 层用 Lua 直接判断。

### 扩展性/优化类

**Q9: 如果要支撑双十一级别的流量（10万+ QPS），你的架构需要做哪些改进？**

*A*: ① Nginx 层加 LVS + Keepalived 做负载均衡高可用；② Redis 集群扩容（6 节点→更多主从）；③ Elasticsearch 集群（至少 3 节点）；④ Nacos 从单节点改为集群模式（3 节点 + MySQL 持久化）；⑤ RocketMQ 改为多 Broker 集群；⑥ Seata 改为高可用模式（TC 集群 + DB 存储）；⑦ 静态页面推到 CDN；⑧ 限流阈值从 Gateway 下移到 Nginx，降低 Gateway 压力；⑨ 商品详情页全量静态化 + OpenResty Lua 直接返回；⑩ 核心链路（秒杀）与非核心链路（积分）物理隔离。

**Q10: 系统中库存扣减的安全性是如何保证的？如果不小心多卖了怎么办？**

*A*: 三层保障：① 应用层 Redisson 锁；② MySQL 层 `UPDATE ... WHERE num>=#{num}` 原子条件；③ Seata 全局事务回滚。如果因代码 Bug 导致超卖，补偿方案是：后台对账系统（定时扫描 `sku` 表库存与订单量是否一致），发现不一致时人工介入或自动发起退款。分布式系统中做不到绝对不超卖，但可以做到快速发现 + 及时止损。

### 架构设计类（新增）

**Q11: 你的秒杀系统为什么设计成 6 层漏斗？每层之间怎么衔接？**

*A*: "漏斗模型的核心思想是——越上层的校验越轻量，拦截的流量越多；越下层的操作越重，通过的流量越少。BloomFilter 是位图操作，O(1) 时间复杂度，在第一层就拦截了非法商品 ID 的恶意请求；JWT IP 绑定是 Token 解析，挡掉未登录和盗用 Token 的请求；Redis 预扣库存是最关键的一层——库存预热到 Redis，用 DECR 原子减，扣到负数直接返回'已售罄'，这一步能挡掉 90% 以上的无效流量；到了 RocketMQ 削峰，进来的请求已经是真正抢到资格的，消息排队异步处理；最后的 Redisson 锁是终极兜底，走到这的流量基本等于库存量，加锁保证了数据库层不超卖。每层职责单一，互不干扰。"

**Q12: 你的布隆过滤器是静态的还是动态的？商品上架后怎么更新？**

*A*: "布隆过滤器通过 RedisBloom 模块挂在 Redis 上，多台网关共享同一份数据。当运营在后台发布新商品或新秒杀活动时，Canal 监听到这条 INSERT 变更，通过 Feign 调用任务服务，异步将新商品的 URI 加载到 BloomFilter 中。这样商品上架和布隆过滤器更新之间几乎没有延迟，也不需要重启网关。"

**Q13: JWT 绑定 IP，如果用户在地铁上切换了基站 IP 变了怎么办？**

*A*: "这是安全与体验的权衡。对于秒杀这种极高危场景，严格绑定 IP 能大幅提高防刷能力——黑产黄牛即使偷到了 Token，换个 IP 也刷不了。如果正常用户因为切换网络导致鉴权失败，可以让用户进行一次极快的滑块验证或重新获取简易 Token。秒杀场景下，安全优先级高于体验。而非秒杀场景（如普通浏览、加购物车）可以放宽这个限制。"

### 数据驱动类

**Q14: Druid 每 30 秒才统计一次，前 29 秒突发热点怎么办？**

*A*: "这个机制定位是自动闭环兜底，不是唯一的防护手段。① 对于已知的秒杀活动（运营排期好的），我们在活动开始前就通过 Canal 捕获创建事件完成了库存预热；② 对于未知的突发热点（比如某个普通商品突然爆火），30 秒窗口确实存在滞后。但在这 30 秒内，网关层有 Sentinel 局部限流和熔断机制保证系统不被打垮。30 秒后 Druid 自动识别热点并完成隔离池搬迁，限流平稳解除。如果能做到秒级识别，可以用 Flink 实时计算替代 Druid 的批式聚合，但架构复杂度会大幅增加。"

**Q15: 为什么热点发现的 ElasticJob 一定要用分布式？单机跑不行吗？**

*A*: "两个原因。① 高可用：如果单机跑，那台机器挂了热点发现就停了，整个系统暴露在未知突发流量下。ElasticJob 有故障转移能力，一台挂了另一台自动接管。② 避免重复查询：如果多台后台机器不用分布式协同，它们可能在同 1 秒各自向 Druid 发起一次聚合查询，Druid 压力翻倍。ElasticJob 通过 ZooKeeper 协调，保证同一时刻只有一个节点在执行分析任务。"

**Q16: ElasticJob 动态注册定时任务的实现细节？**

*A*: "Canal 监听到秒杀活动 INSERT 后，提取 endTime（如 2026-06-01 18:00:00），通过 `CronExpression` 库转为 Cron 表达式 `0 0 18 1 6 ? 2026`，然后调用 ElasticJob 的 Java API——创建 `JobConfiguration` 对象、设置 cron 和分片参数、通过 `JobScheduler` 动态注册到 ZooKeeper。整个过程代码完成，不需要人工操作。到时间点 ZooKeeper 触发 ElasticJob 的调度，选一台空闲机器执行清理逻辑。如果清理失败，ElasticJob 会按配置的重试策略重新执行。"

> "我用了 Canal 替代传统的业务双写。传统方案在业务代码里既要写 MySQL 又要写 ES，代码耦合高，数据一致性还难保证。Canal 伪装成 MySQL slave 监听 binlog，商品服务只关心核心业务，数据同步完全解耦出去——MySQL 写入成功就有 binlog，Canal 就一定能把数据同步到 ES，不会有遗漏。"

```
           ▼
┌──────────────────────────┐
│ ⑥ Redisson 分布式锁防超卖 │ ── 终级兜底，强一致性
└──────────────────────────┘
           │
           ▼
       【成功下单】
```

**各层防守机理：**

| 层级 | 防守对象 | 为什么快/必要 |
|------|---------|-------------|
| ① **BloomFilter** | 恶意攻击、刷不存在的商品 ID（缓存穿透） | 位图操作，Bit 级判断，绝对精确——不存在就是不存在 |
| ② **JWT + IP 绑定** | 黑产黄牛盗 Token 异地刷单 | JWT 中封装登录 IP 的哈希，请求 IP 对不上直接判失效 |
| ③ **RBAC** | 越权访问（如普通用户调管理员接口） | 标准权限校验，职责单一 |
| ④ **Redis 热点检测** | 抢不到商品的"无效流量"（挡 90%+） | 库存预热到 Redis，`DECR` 扣负数时直接返回"已售罄" |
| ⑤ **RocketMQ 削峰** | 瞬时高并发冲垮下游服务 | 秒杀资格获得者发消息排队，订单服务按能力消费 |
| ⑥ **Redisson 锁** | 终级兜底——数据库层防超卖 | 走到这的流量已极少（约等于库存量），加锁无性能瓶颈 |

**引导话术：**

> "秒杀系统我最得意的是 6 层漏斗防护。从最外层的 BloomFilter 拦截非法请求开始，每层筛掉一批流量——JWT 绑 IP 防 Token 盗用、Redis 预扣库存挡掉 90% 抢不到的无效流量、RocketMQ 削峰把万级并发变成稳定长流。到了最底层的 Redisson 锁，能走到这的流量基本等于库存量，加锁既保证了不超卖，又没有性能瓶颈。层层过滤，每一层职责单一。"

*引导方向→* 漏斗模型设计思想、BloomFilter 误判率与动态更新、JWT IP 绑定取舍、Redis 预扣与最终一致性、MQ 削峰与背压

#### 亮点三：Dynamic ElasticJob 动态定时任务

秒杀活动通过 Canal 捕获活动创建事件，动态计算 `endTime` 对应的 cron 表达式，自动注册 ElasticJob 定时任务，活动结束时自动清理过期静态页面。**无需轮询，事件驱动**。

**解决的传统痛点：**

| 方案 | 缺点 |
|------|------|
| ❌ **轮询**（每 1 分钟扫数据库） | 极度浪费性能，最高延迟 1 分钟 |
| ❌ **JVM ScheduledExecutorService** | 服务器重启后内存中的定时任务全丢，无法分布式协同 |
| ✅ **Canal + ElasticJob 动态注册** | 零浪费、精确到秒、分布式高可用 |

**完整链路：**

```
① 运营创建活动 ──▶ MySQL INSERT
② Canal 监听 binlog ──▶ 提取 endTime
③ 解析 endTime → Cron 表达式 ──▶ ElasticJob API 动态注册
④ ZooKeeper 协调 ──▶ 精确到秒触发
⑤ 清理过期静态页 ──▶ 任务完成
```

**引导话术：**

> "秒杀活动结束后需要清理静态页面。传统做法是写个定时任务每分钟扫一次数据库，99% 的时候都在空扫，浪费性能。我换了一种思路——Canal 监听到活动创建事件后，直接把 endTime 转成 Cron 表达式，通过 ElasticJob 的 Java API 动态注册一个定时任务。这样中间不消耗任何 CPU，到了时间点精确触发。ElasticJob 基于 ZooKeeper 做分布式协调，一台机器挂了另一台自动接管，不存在单点故障。"

*引导方向→* Cron 表达式动态生成、ElasticJob 动态注册 API、ZooKeeper 选举与故障转移、与 @Scheduled 的对比

#### 亮点四：Apache Druid + ElasticJob 热点发现

通过 Druid OLAP 引擎分析用户行为日志，ElasticJob 每 30 秒触发一次聚合查询，自动识别高频访问商品并标记为"热商品"推入秒杀隔离池。**数据驱动的运营闭环。**

**为什么用 Druid 做热点统计？**

| 方案 | 能否扛住高并发日志写入 | 聚合查询性能 |
|------|---------------------|-------------|
| ❌ MySQL | 写日志就瘫痪 | `COUNT(*) GROUP BY` 极慢 |
| ⚠ Redis ZSET | 单节点变热点 | 百万级勉强 |
| ✅ Apache Druid | 列式存储，实时摄入 ROCKETMQ/Kafka | 毫秒级 OLAP 聚合 |

**闭环链路：**

```
用户点击 ──▶ 行为日志 ──▶ Druid 实时摄入
                              │
                    ElasticJob 每 30s 触发
                              │
                    Druid 聚合：过去 1 分钟 Top100
                              │
                    判定热点（>5000次/秒）
                              │
          ┌───────────────────┴───────────────────┐
          ▼                                       ▼
   Redis 秒杀隔离池（预热库存）              Gateway 更新限流规则
```

**引导话术：**

> "这个亮点在于用 OLAP 引擎驱动业务决策。ElasticJob 每 30 秒向 Druid 发起一次聚合查询，统计过去 1 分钟内访问量最高的商品。如果某个商品点击量超过阈值，自动判定为热点，推入 Redis 秒杀隔离池预热库存，同时更新网关的限流规则——整个过程全自动，不需要人工干预。为什么选 Druid？因为 MySQL 扛不住这种高频聚合查询，Redis 的 ZSET 在超高并发下自己就成了热点，而 Druid 是列式存储，天生适合时序数据的实时摄入和高速聚合。"

*引导方向→* 列式存储 vs 行式存储、Druid Roll-up 预聚合、30 秒窗口期的兜底措施、ElasticJob 分布式避免重复查询

#### 亮点五：异构数据源（Polyglot Persistence）

根据数据特点选择不同的存储引擎，发挥各自优势：

| 数据 | 存储 | 为什么选它 |
|------|------|-----------|
| 购物车 | **MongoDB** | 灵活 schema，无需预定义字段，持久化不丢数据 |
| 订单 | **MySQL** | 强 ACID 事务，保障资金安全 |
| 商品搜索 | **Elasticsearch** | 倒排索引，毫秒级全文检索 |
| 用户行为分析 | **Apache Druid** | 列式存储，亿级数据秒级聚合 |
| 商品图片 | **FastDFS** | 中小文件优化，私有化部署 |
| 缓存 | **Redis** | 内存级读写，毫秒级响应 |

**引导话术：**

> "我们没有用统一的数据库存所有东西。购物车用 MongoDB——用户加购的东西千奇百怪，字段不固定，MongoDB 灵活 schema 天然适合；订单用 MySQL——钱的事情不能含糊，必须 ACID 强事务；搜索走 ES——倒排索引分词检索，MySQL LIKE 没法比；用户行为分析走 Druid——列式存储、预聚合，亿级数据秒级返回。这叫 Polyglot Persistence，不同数据用不同的存储，各自发挥最强能力。"

*引导方向→* 选型取舍依据、Polyglot Persistence 概念、多数据源事务（Seata）、跨库查询方案

### 与同类项目的差异化优势

| 对比维度 | 本项目 | 常见课程项目 |
|---------|--------|------------|
| CDC 数据同步 | ✅ Canal + 实时 binlog 同步 | ❌ 手动调用或定时任务 |
| 分布式事务 | ✅ Seata AT + RocketMQ 事务消息 | ❌ 单库或手动回滚 |
| 多级缓存 | ✅ Nginx → Redis → Tomcat | ❌ 仅 Redis |
| 分布式调度 | ✅ Elastic-Job + ZooKeeper（动态注册） | ❌ @Scheduled 单机版 |
| 秒杀防护 | ✅ 6 层漏斗模型（BloomFilter → JWT → RBAC → Redis → MQ → Redisson） | ❌ 仅 Redis 锁 |
| OLAP 分析 | ✅ Apache Druid（热点发现闭环） | ❌ 无 |
| 任务调度 | ✅ 事件驱动（Canal → Cron → ElasticJob） | ❌ 固定轮询 |
| 服务数量 | **14个**（覆盖完整电商链路） | 通常 3~5 个 |
| 中间件覆盖 | Nacos/Sentinel/Seata/RocketMQ/Canal/ES/Redisson/Elastic-Job/Druid/FastDFS | 通常 3~5 种 |

**一句话总结面试策略**：用"**Canal CDC + 6 层秒杀防护**"展现高并发架构能力，用"**Druid 热点发现 + ElasticJob 动态调度**"展现数据驱动思维，用"**14 个服务的完整性**"展现工程能力。
