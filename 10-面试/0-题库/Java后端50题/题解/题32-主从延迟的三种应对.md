### **强制走主库解决"读己之写"、半同步复制降低数据丢失风险、本地缓存兜底跨请求一致性，三者分别对应"读一致性、写可靠性、体验一致性"三个不同层面。**

下面按面试口述节奏展开。

---

**第一部分：先讲清楚主从延迟的根因**

主从延迟 30 秒是个非常大的信号，先得知道它为什么会发生，才知道每种解法在解决什么：

1. **主库写入 QPS 高**、从库单线程 SQL Thread 回放跟不上（MySQL 5.6 之前是单线程回放，5.7+ 有并行复制但依赖库/表/组提交分组）；
2. **大事务**：主库一个 `UPDATE 100 万行` 秒级完成，从库要串行回放同样长时间；
3. **从库硬件差**或**从库还兼顾了大量分析查询**；
4. **网络抖动**或跨机房复制。

而业务层看到的现象是：用户在主库支付成功 → 立刻跳转订单页 → 订单页读从库 → 查不到 → 用户以为支付失败重复下单。这就是典型的**"读己之写不一致 (Read-your-writes inconsistency)"**。

三种方案分别从不同角度解决它。

---

**第二部分：方案一 —— 强制走主库**

**原理**：对"写后立即读"的敏感操作，路由层不走读写分离，直接把 `SELECT` 打到主库。

**实现方式**主要有三种：

**1. Hint 注解式**（最常见）：在代码里显式标注：

```java
@Master  // 或者 /*+ MASTER */ 的 SQL Hint
public Order getOrderAfterPay(Long orderId) { ... }
```

框架层（如 ShardingSphere、MyBatis 拦截器）识别后强制路由主库。

**2. 会话内粘连**：一旦当前会话/事务发生过写操作，接下来一段时间（比如 500ms\~1s）内所有读都走主库。可以用 ThreadLocal 或 Redis 存"写标记 + TTL"实现：

```
用户 A 支付后 → Redis SET user:A:write_mark 1 EX 2
用户 A 查询时 → 有标记走主库，无标记走从库
```

**3. GTID 等待**：拿到主库写完后返回的 GTID，读从库前先 `SELECT WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)`，等从库追上再读。适合对数据实时性要求极高、又不想给主库加压的场景。

**适用边界**：

- ✅ **强一致读**场景：支付回执、订单创建后跳详情、下单后查库存、修改密码后登录；
- ✅ 写后立即读的**短时间窗口**（1\~2 秒内）；
- ❌ 主库承压已经很高时**慎用**，读流量全打回主库会让读写分离形同虚设；
- ❌ 报表、列表、搜索等**允许延迟**的场景没必要走主库。

**风险点**：滥用会让读写分离退化。一定要**精准标注**，只在"读己之写"的入口打标，其他读仍走从库。

---

**第三部分：方案二 —— 半同步复制 (Semi-Sync Replication)**

**原理**：MySQL 默认是**异步复制**——主库写完 binlog 就返回客户端成功，从库何时收到、何时回放都不管。半同步的改进是：主库写完 binlog 后，**必须等至少一个从库确认收到 relay log（不是回放完成）**，才向客户端返回成功。

对应参数：

```
rpl_semi_sync_master_enabled = ON
rpl_semi_sync_master_timeout = 1000       # 超时降级为异步，单位 ms
rpl_semi_sync_master_wait_for_slave_count = 1
```

MySQL 5.7 后引入 **AFTER_SYNC** 模式（Loss-Less 半同步）：主库先写 binlog、等从库 ACK、再提交事务并返回，进一步降低了"主库已提交但从库未收到"的窗口。

**注意关键点**：半同步保证的是 **binlog 已到达从库**，**不保证从库已经回放完成**。也就是说，**它解决的是"数据不丢"，不是"数据可见"**。用户下单后立刻去从库查，从库可能还在回放队列里排队，仍然查不到。

**适用边界**：

- ✅ **数据可靠性优先**场景：金融交易、订单落库、账户变动——即使主库宕机，从库切换后数据不丢；
- ✅ 主从跨机房、需要故障切换的高可用架构；
- ❌ **不能解决"读己之写"延迟问题**，面试题里"支付后看不到订单"如果是回放慢导致的，半同步救不了；
- ❌ 主库写 RT 会增加一个网络 RTT，**写延迟敏感的业务要评估**；
- ❌ 半同步超时会**自动降级为异步**，极端情况下保证会打折。

**所以半同步在这道题里的定位是**：它不是"看不到订单"的直接解药，而是**兜底可靠性**——万一主库挂了，用户支付的数据也不会丢在主库的孤本上。它和方案一是**互补而非替代**关系。

---

**第四部分：方案三 —— 本地缓存 / 写后回填**

**原理**：既然写完立刻查从库查不到，那就**别去查了**——写成功后把结果直接放到应用侧的缓存里，读的时候先查缓存，缓存命中直接返回，缓存未命中再走 DB。

**实现方式**：

**1. 写穿透 (Write-Through)**：主库写成功 → 同步写 Redis / 本地缓存 → 返回客户端。后续读优先查缓存：

```java
Order order = orderMapper.insert(...);   // 主库写
redis.set("order:" + orderId, order, 5, SECONDS);  // 短 TTL 兜底延迟窗口
return order;
```

TTL 一般设置为**略大于主从延迟上限**，比如 5\~10 秒，之后自然过期，读回落到从库时数据已同步。

**2. 前端本地存储**：更轻量，支付成功页直接把订单信息通过接口返回体带出去，前端存一份 sessionStorage，跳转订单页时先展示，异步再拉取最新数据校对。

**3. 消息队列 + 回填**：写成功发 MQ，消费方负责把数据写到缓存 / ES / 搜索索引，读侧优先查这些"最终一致"的镜像。

**适用边界**：

- ✅ **允许最终一致**的展示型场景：订单详情、个人中心、"我的"页面；
- ✅ 主从延迟大且**难以短期治理**的历史系统（改架构成本高，加缓存最快）；
- ✅ 写少读多的场景，缓存命中率高，收益明显；
- ❌ **强一致场景不适用**：库存扣减、余额判断绝不能用缓存兜底，缓存和 DB 不一致会引发资损；
- ❌ 增加了**缓存一致性维护成本**：更新、删除、TTL、雪崩、穿透都要处理；
- ❌ 缓存本身也可能出故障（Redis 宕机），需要有降级到 DB 的路径。

---

**第五部分：三种方案的对比与组合使用**

| 方案 | 解决的问题 | 代价 | 一致性级别 |
|---|---|---|---|
| 强制走主库 | 读己之写不一致 | 主库读压力上升 | 强一致 |
| 半同步复制 | 主库宕机数据丢失 | 写 RT 增加、超时会降级 | 数据可靠但不保证可见 |
| 本地/分布式缓存 | 延迟窗口内的读体验 | 缓存一致性维护复杂 | 最终一致 |

**面试里的关键判断**：这三个方案不是三选一，而是**三层防线组合**——

1. **底层用半同步**保证主从数据不丢、故障切换安全；
2. **中层用强制走主库**解决支付后立刻查订单的强一致读；
3. **上层用缓存/写后回填**兜住跨请求、跨页面的最终一致展示；

同时**根治路径**还是要治延迟本身：**开启并行复制 (`slave_parallel_workers` + `slave_parallel_type=LOGICAL_CLOCK`)、拆大事务、优化从库硬件、监控 `Seconds_Behind_Master` 并告警**。方案是止血，治延迟才是止痛。

---

**面试收尾一句话：**

主从延迟不是单点问题，是"**数据不丢、写后可读、跨请求一致**"三个维度的共同挑战。强制走主库解决 read-your-writes，半同步解决数据可靠性，缓存解决最终一致的用户体验——**三者互补而非替代**。真正稳定的系统，是这三层都做到位，同时把延迟本身压到 1 秒以内，让业务几乎感知不到"主从"这件事。
