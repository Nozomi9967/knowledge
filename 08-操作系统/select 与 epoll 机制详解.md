# select 与 epoll 机制详解

> 一个线程要同时管成千上万个连接，**不能靠"每连接一个线程"，也不能靠"挨个轮询每个 fd"**——前者上下文切换吃光 CPU，后者 N 次系统调用加空转。多路复用的思路是：**把一堆 fd 一次性交给内核，让内核告诉你哪些就绪了。**
>
> 从 `select` 到 `poll` 到 `epoll`，改的不只是 API，而是**内核里"谁去找就绪 fd"这件事的整个模型**。这份笔记讲清三代的实现机制，以及四个面试高频误区。

---

## 一、为什么需要多路复用

一个线程管 N 个连接，不用多路复用只有两条烂路：

| 做法 | 问题 |
|------|------|
| **一连接一线程** | N 个线程，上下文切换成本随 N 涨（见 [[模式切换与上下文切换详解#六、贵的到底在哪：直接开销 vs 间接开销]]） |
| **轮询每个 fd 做非阻塞 read** | N 次系统调用，且大部分时候在空转 |

上面两条烂路各自为什么烂，见 §三 的展开——先垫 socket / accept（一条连接在内核里怎么被管理），再分别拆「每连接一个线程」和「轮询非阻塞 read」。

多路复用 = **一次系统调用，换 N 次等待**。这是 C10K 的基石。

---

## 二、先搞清 fd：后面全靠它

**fd（file descriptor，文件描述符）是一个非负整数，是进程"打开文件表"的数组下标**，指向内核里的一个「打开的文件」对象。用户态永远拿不到内核对象本体，只能拿这个整数当**句柄**。

**关键设计：一切皆文件。** fd 指向的不只是磁盘文件：

| fd 可以指向    | 举例                                            |
| ---------- | --------------------------------------------- |
| 普通文件 / 目录  | `open` / `opendir`                            |
| **socket** | ← **所以 epoll 能管网络连接**                         |
| 管道 / FIFO  | `pipe()`                                      |
| 设备         | `/dev/tty`、`/dev/null`                        |
| **内核造的对象** | **epoll 实例本身**、`eventfd`、`signalfd`、`timerfd` |

**正因为 socket 也是 fd**，网络 IO 和文件 IO 才能共用同一套 `read` / `write` / `close`，epoll 那整套东西才成立。（socket 到底是什么、服务端怎么用它接客，紧接着 §三 展开。）

**0 / 1 / 2 是预分配的**：任何进程一起来就有三个 fd，由 shell 打开——0 = stdin、1 = stdout、2 = stderr。所以新打开的文件从 **3** 开始。

**内核里的三层结构**：

```
进程的 fd 表        系统级打开文件表        inode
  0  ──────▶  ┌──────────────┐  ──────▶  ┌────────────┐
  1  ──────▶  │  struct file │           │ 文件元数据  │
  2  ──────▶  │  · 读写偏移量 │           └────────────┘
  3  ──────▶  │  · 访问模式   │
              │  · 引用计数   │
              └──────────────┘
```

**注意两层的归属不同**：fd 表是**进程私有**的，`struct file` 是**系统级共享**的。这解释了两个常见现象：

- **`fork` 后父子进程的文件偏移是共享的**——fork 复制的是 fd 表，父子俩的 fd 3 指向**同一个 `struct file`**，一个读了，另一个的偏移也跟着走
- **`dup` / `dup2` 出来的新 fd 也共享偏移**，同理

**上限**：单进程 `ulimit -n`（默认常见 1024，服务端会调到几万），系统总 `/proc/sys/fs/file-max`。**忘了 `close` 就会耗尽**，报 `EMFILE: Too many open files`——比内存泄漏更急，因为配额很小，耗尽立刻服务不可用（见 [[未关闭资源泄漏与元空间泄漏详解#一、未关闭资源泄漏的机制]]）。

## 三、服务端怎么接客：socket、accept 与两条"烂路"

§一 说多路复用"不能靠每连接一个线程"——那"每连接一个线程"到底长什么样？要讲清它，得先把 **socket** 和 **accept** 这两个前置概念搞明白。

### 3.1 socket：一条连接的一个端点

> **通俗理解**：socket 英文就是**插座**。两台机器通信像"插头插进插座"，各插一个，中间的线就通了（中文音译"套接字"）。

socket 把「本机 IP + 端口 + 协议 + 对端 IP + 端口」这套通信能力，打包成一个**能被 `read` / `write` 的对象**。它要解决的核心问题是：**怎么把"网络通信"变得像读写文件一样简单**——你只管往里写、从里读，底层 TCP/IP 的拆包、重传、确认全被它藏起来。

**关键一句：socket 就是一个 fd。** 这正是 §二 那句"一切皆文件"的落点：

```
socket() 系统调用  ──►  内核造一个 socket 对象  ──►  返回一个整数 fd
                                                       ↑ 和打开文件拿到的那种一模一样
```

正因为 socket 是 fd：

- 能用 `read` / `write` / `close`，和操作文件是**同一套系统调用**
- 才能被 `select` / `poll` / `epoll` 监听（epoll 管的就是 fd）
- `accept` 返回的"另一个 fd"才说得通——新连接也是一个 socket

**"一切皆文件"让网络 IO 和文件 IO 共用一套接口——这是后面整条多路复用脉络能成立的前提。**

### 3.2 一条连接靠"四元组"唯一标识

内核里，一条 TCP 连接由**四元组**唯一确定（加上协议就是五元组）：

| 要素 | 例子 |
|------|------|
| 本地 IP : 本地端口 | `192.168.1.5:8080` |
| 远端 IP : 远端端口 | `10.0.0.9:52134` |
| 协议 | TCP |

**同一台服务器、同一个端口 8080，能同时服务成千上万个客户端，靠的就是四元组不同**——对端 IP / 端口不一样，内核就能把每条连接区分开。这就是为什么服务端只监听一个端口，却能扛住海量连接。

### 3.3 服务端用了"两种" socket

同样是 socket，服务端其实扮演了两种角色：

| | **监听 socket（`listen_fd`）** | **已连接 socket（`conn_fd`）** |
|---|--------------------------|--------------------------|
| 怎么来 | `socket()` + `bind()` + `listen()` | `accept()` 返回 |
| 数量 | **全程只有一个** | **每接受一个连接就多一个** |
| 职责 | 只听新连接进来，**不传数据** | 和某个客户端**实际收发数据** |
| 四元组 | 只绑了本地 IP:端口，对端未知 | **四元组完整**（对端也确定了） |

`listen_fd` 像店门口的**迎宾**，来一个客人就叫一次 `accept`；`accept` 返回的 `conn_fd` 才是**你和这位客人之间的那根电话线**。一个 `listen_fd` 能 accept 出成千上万个 `conn_fd`。

### 3.4 accept：从内核队列里"摘"一个已建好的连接

完整的服务端流程：

```c
int listen_fd = socket(...);        /* 1. 造一个"迎宾专用" socket */
bind(listen_fd, ...);               /* 2. 绑 IP + 端口 */
listen(listen_fd, backlog);         /* 3. 开监听，内核开始收 SYN（三次握手由内核代劳） */
int conn_fd = accept(listen_fd, …); /* 4. 从【已连接队列】摘一个连接，返回新 fd */
read(conn_fd, ...); write(conn_fd, ...);  /* 5. 在这条连接上收发数据 */
```

**`accept` 不是凭空变出连接**——三次握手是内核在 `listen` 之后**自动完成**的，它用两个队列接力：

```
客户端 ──SYN──►  [半连接队列 SYN queue]    握手未完成（SYN_RCVD）
客户端 ──ACK──►  [全连接队列 accept queue] 握手完成（ESTABLISHED），等 accept 取走
                        │
          accept() ◄────┘  从这里"摘"一个出来
```

- **半连接队列（SYN queue）**：收到 SYN、回了 SYN+ACK、还没等到对方 ACK 的连接——占一个槽位。**SYN Flood 就是拿垃圾 SYN 塞满它**（见 [[计网八股#三次握手没完成：半开连接与 SYN Flood 防护]]）
- **全连接队列（accept queue）**：握手完成、**排队等着你 `accept`** 的连接——就是 `listen(fd, backlog)` 里 `backlog` 控制的东西
- **队列满了会怎样**：全连接队列溢出时默认**静默丢弃**第三次握手的 ACK（假装没收到），客户端表现为"连不上又不报错、卡着"；`tcp_abort_on_overflow=1` 则改发 RST 快速失败

### 3.5 `connect()` 返回 ≠ `accept()` 返回（连接建立 ≠ 应用接受）

`connect()` 默认阻塞，语义是"连上了再告诉我"。它的**返回**意味着：

> **客户端发起的三次握手办完了、控制权交回客户端**——这一刻 TCP 连接已建立，双方内核都进了 `ESTABLISHED`。

**但关键是"两头不同时"**：

```
客户端                                服务端内核              服务端应用
  │ connect() 调用                         │                     │
  ├─── SYN ────────────────────────────►   │                     │
  │ ◄── SYN+ACK ─────────────────────────  │                     │
  ├─── ACK ────────────────────────────►   │ 连接入【全连接队列】 │
  │ ★ connect() 返回 ★（握手完成）          │                     │
  │                                         │     ◄── accept() ───┤ ★ accept() 返回 ★
  │ ◄───────── 双方这才开始真正传数据 ─────────────────────────► │
```

- `connect()` 返回，只说明**客户端 + 服务端内核**这一侧搞定了握手
- 服务端**应用**拿到 `conn_fd`，得等它**自己**下一次 `accept()` 返回
- **连接在 TCP 层已经"通"了，在应用层还没被"接手"**

**两个面试落点**：

1. "客户端 `connect` 成功了，服务端却没打印新连接" → 连接卡在**全连接队列**里还没被 `accept`；队列满还会被丢弃
2. `connect()` 一返回就能立刻 `write()`，**哪怕服务端还没 `accept`**——数据先躺在服务端内核的接收缓冲区，等 `accept` 后 `read` 时再取。**TCP 连接由内核维护，不依赖应用有没有 `accept`**

### 3.6 每连接一个线程：传统 BIO 服务端的形状

有了铺垫，"每连接一个线程"（thread-per-connection）就一句话：

> **每 `accept` 到一个新连接，就专门开一个线程服务它——这个线程从连接建立活到连接断开，只伺候这一个连接。连接数 : 线程数 = 1 : 1。**

```c
while (true) {
    conn_fd = accept(listen_fd);     /* 主线程阻塞在这，没连接就睡着等 */
    new_thread(serve, conn_fd);      /* 来一个连接，就起一个线程 */
}
```

关键在于每个线程**大部分时间阻塞在 `read` 上**（等对端发数据），这段时间它什么也不干，但**内核对象和栈内存一直占着**。它为什么是 §一 要否定的"烂路"：

| 问题 | 机制 |
|------|------|
| **线程数 = 连接数** | 1:1 绑定，没有复用，连接涨线程跟着涨 |
| **线程是内核对象，很重** | 创建要走 `clone()` 系统调用，栈默认 **8MB**（虚拟内存，见 [[OS八股#2.3 协程：把调度权抢回用户态]]） |
| **上下文切换吃光 CPU** | N 个线程来回切，`%sy` 飙高（见 [[模式切换与上下文切换详解#六、贵的到底在哪：直接开销 vs 间接开销]]） |

**算笔账**：扛 10 万并发连接 = **10 万 × 8MB 栈** + 内核调度直接崩。这就是经典的 **C10K 问题**。

所以多路复用换了思路——**不是"每个连接配一个线程"，而是"一个线程管 N 个连接"**。而它接管的入口，恰好就是 **`listen_fd`**：

> epoll 把 **`listen_fd` 本身也注册进去**，当它可读时就代表"有新连接可以 `accept` 了"。这样**一个线程既管着几万条数据连接、又顺便管着新连接进来这件事**，不必再单开一个阻塞在 `accept` 上的主线程。

### 3.7 轮询每个 fd 做非阻塞 read：另一条"烂路"

§一 表格的第二条，思路是"挨个问每个连接：你有没有数据"。长这样：

```c
set_nonblock(fd0); set_nonblock(fd1); …      /* 全部设成非阻塞 */

while (true) {
    for (每个 fd) {
        n = read(fd, buf, size);   /* 有数据就读到；没数据立刻返回 EAGAIN */
        if (n > 0) 处理(buf);
    }
    /* 转完一圈，马上从头再来 */
}
```

它省掉了"每连接一个线程"的线程爆炸，却换来两个更狠的病：

| 病 | 机制 |
|------|------|
| **N 次系统调用** | `read()` 是系统调用，每调一次就是**一趟用户态 ⇄ 内核态的模式切换**（见 [[模式切换与上下文切换详解#一、两个词的定义]]）。1 万连接转一圈 = 1 万次跨态，而这只是**一圈**，一秒能转几万圈 |
| **大部分时候空转** | 1 万连接里通常只有几十个有数据，但你没有"谁有数据"的信息，只能**挨个问**——9990 次得到"没有"，全是白花。CPU 100%、吞吐却上不去，这叫**忙等（busy-waiting）** |

**关键**：这一圈开销 ∝ 连接总数 N，**跟你有几个连接活跃完全无关**——一个都没数据也得转满一整圈。这和 §四 select 的"代价 ∝ 最大 fd 号"是**同一个病根**：每趟都得碰所有 fd。

**为什么必须配"非阻塞"**：若 `read` 是阻塞的，读到某个暂时没数据的 fd 就**卡死在那儿**，后面的 fd 一个都轮不到——退化成串行等待，比每连接一个线程还惨。所以必须非阻塞：没数据立刻返回 `EAGAIN`，好去问下一个。

**多路复用怎么一次治好这两个病**：

| | 轮询（非阻塞 read） | 多路复用（epoll） |
|---|---|---|
| 跨态次数 | **N 次 / 圈** | **1 次 / 次 `epoll_wait`** |
| 谁去找就绪 | 用户态**自己挨个问** | **内核**（回调 → 就绪链表） |
| 没数据时 | **空转烧 CPU** | **睡眠**，有数据才唤醒 |

一句话：把"挨个问"**从用户态搬进内核一次做完**，没数据时**让进程睡着**——这正是 §一 那句"**一次系统调用，换 N 次等待**"。

> ⚠ **术语坑**：这就是 [[OS八股#7.1 五种 I/O 模型（POSIX）]] 里的**「非阻塞 I/O：①轮询轮询轮询」**。而 Java 的 **NIO（New IO）不是它**——Java NIO 底层是 **epoll**，属于**多路复用**。名字撞车，面试别说混。

### 3.8 别混：每连接一个线程 ≠ 每请求一个线程

| 模型 | 粒度 | 典型代表 |
|------|------|----------|
| **每连接一个线程** | 一个连接 ↔ 一个线程，**连接存活期全程独占** | 传统 BIO（手写 `ServerSocket`） |
| **每请求一个线程** | 一个请求 ↔ 一个线程，**线程池复用** | **Tomcat**（keep-alive 下连接可复用池里线程） |

Tomcat 能扛，是因为它把"连接"和"线程"**解绑**了——线程处理完一个请求就还回线程池，而不是被一个连接钉死。三列对比见 [[Java基础面试题#BIO、NIO、AIO 有什么区别？]]（BIO / NIO / AIO 的线程利用）。

## 四、select：位图编码，所以只能"逐位扫"

### 4.1 它怎么表达"我要监听谁"

```c
fd_set readfds;
FD_ZERO(&readfds);      /* 先把 1024 位全清 0 */
FD_SET(3, &readfds);    /* 把第 3 位置 1 —— 表示"要监听 fd 3" */
FD_SET(7, &readfds);    /* 第 7 位也置 1 */

select(8, &readfds, NULL, NULL, NULL);
```

规则就两条：**下标 = fd 号，这一位的值 = 要不要监听它**。

```
bit7  bit6 bit5 bit4 bit3  bit2 bit1 bit0
 1     0    0    0    1     0    0    0     ← 只有第 3、7 位是 1
```

**"要监听谁"是靠"哪几位是 1"告诉内核的**——内核拿到的不是一份 fd 清单，而是**一张按编号铺开、绝大多数位是 0 的稀疏位图**。

### 4.2 `nfds` 是划边界，两个坑都从这儿来

`fd_set` 永远是 1024 位那么长，内核**不知道你填到了哪一位**，所以第一个参数必须传 **最大 fd + 1**。

- **传小了** → 后面的 fd 内核根本不检查，**静默漏掉**，怎么等都等不到（很典型的事故）
- **传对了也慢** → 就算只监听 fd 1000 这一个，`nfds` 也得传 1001，内核得从第 0 位一路扫到第 1000 位

### 4.3 代价模型（这是 select 最值钱的一个认识）

> **select 的开销 ∝ 最大 fd 号，不是 ∝ 监听的个数。**

十个监控项散在 fd 0~1000 之间、和十个挤在连续低位，内核扫描量能差**一百倍**。这也解释了为什么「连接反复开关、fd 号越涨越大」的程序用 select 会**越来越慢**。

⚠ **别拿"一万个连接"举例**：select 连一万个都放不下（位图只有 1024 位），"大量连接"是 **poll / epoll** 的场景。**select 的问题是密而全，不是多。**

### 4.4 为什么它非得逐位扫

因为信息被编码进了**位置**，**解码的唯一办法就是遍历**——内核手上是一张位图，想找出哪些位是 1，除了从头看到尾没有别的办法；它甚至没法只检查你关心的那几个（"0"既表示"不监听"，也和"空位"长得一样）。

**它本可以把"要监听谁"用一张清单表达，但它选了位图**——这就是 select 慢的设计根源。

### 4.5 一次 select 调用内部做了什么

1. **用户态**把 `fd_set` 填好（每一位 = 一个要监听的 fd）
2. `fd_set` **从用户态拷进内核态**（内核看不见你的内存，必须拷）
3. 内核**线性遍历** `nfds` 个 fd，逐个问"你好了吗"——O(n)
4. 没就绪：把当前进程**登记到每一个 fd 的等待队列**上，睡去（任一 fd 就绪 → 中断 → 唤醒）。**n 个 fd 就是 n 次登记**
5. 返回时，内核把 `fd_set` 里**没就绪的位清 0**，只剩就绪的
6. **用户态还得再自己遍历一遍**位图，找出第几位是 1

**四个病**：

| 代价 | 说明 |
|------|------|
| 每次调用**重传全量集合** | 内核不保存你的 fd 集合，每次都得重新拷 |
| 内核 **O(n) 线性遍历** | 一个个问 |
| 返回后**用户再 O(n) 扫**一遍 | 才知道是谁就绪 |
| **上限 1024** | 位图位数定死（`FD_SETSIZE`，改要重编译） |

前三条都是"和 fd 总数成正比"，**跟"到底有几个活了"无关**——这就是它撑不住大并发的根本原因。

## 五、poll：只修了"1024"，其他一个没修

### 5.1 它怎么表达"我要监听谁"

```c
struct pollfd {
    int   fd;        /* 我要监听哪个 fd */
    short events;    /* 我关心什么——输入，我来填 */
    short revents;   /* 实际发生了什么——输出，内核填 */
};

struct pollfd fds[] = {
    { .fd = 3, .events = POLLIN },              /* fd 3：关心"可读" */
    { .fd = 7, .events = POLLIN | POLLOUT },    /* fd 7：读写都关心 */
    { .fd = 9, .events = POLLIN },
};
poll(fds, 3, 1000);   /* 监听这 3 个，最多等 1000 毫秒 */
```

和 select 最根本的不同：**"要监听谁"不再靠"第几位是 1"编码，而是把 fd 号直接写进结构体**。

| | select | poll |
|---|---|---|
| 怎么表达"监听谁" | 位图，**下标 = fd 号**、位值 = 要不要听 | **数组，fd 号直接写在结构体里** |
| 集合容量 | 定长 **1024** 位（`FD_SETSIZE`） | **数组多长就听多少**，无硬上限 |
| 边界参数 `nfds` | **最大 fd + 1**（给位图划边界，传错就静默漏） | **数组元素个数**（数数有几个） |

⚠ **`nfds` 语义变了，这是值钱的一点**：select 的 `nfds` 是"最大 fd + 1"，跟 fd 编号**绑死**；poll 的 `nfds` 只是"数组里有几个元素"，跟 fd 编号**无关**。于是——

> **select 的代价 ∝ 最大 fd 号；poll 的代价 ∝ 监听的个数。**

select 那个"十个监控项散在 fd 0~1000 之间、就慢一百倍"的病（§4.3），**poll 天然没有**。

### 5.2 它修好了什么

| 变化 | 效果 |
|------|------|
| **位图 → 数组** | **去掉 1024 上限**（不再依赖定长位图） |
| `nfds` 语义 | 从"最大 fd + 1" → "元素个数"，**代价不再 ∝ 最大 fd 号** |
| 输入 `events` / 输出 `revents` **分成两个字段** | 不用就地修改、**不用每次调用前重新初始化** |

**最后一条被低估了**：select 每次返回会把没就绪的位清 0，所以下次调用前必须 `FD_ZERO` + 重新 `FD_SET` 一遍；poll 的 `events`（你要的）和 `revents`（实际发生的）是**两个独立字段**，内核只写 `revents`、你的 `events` 原封不动——**下次调用直接复用，不用重建**。

poll 还**天然是水平触发（LT）语义**——每次调用都重新问一遍当前状态，不存在 epoll 那种 ET 模式（见 §七）。

### 5.3 它的返回值，和三个易记混的细节

- **返回值**：`> 0`（就绪的 fd 个数）、`0`（超时）、`-1`（出错）。想知道"到底是谁就绪"，得**自己遍历数组**看哪个 `revents != 0`
- **`timeout` 单位是毫秒**（select 是 `struct timeval`、微秒）——一个高频记混点
- **`POLLERR` / `POLLHUP` / `POLLNVAL`**（出错 / 挂断 / fd 非法）**即使你没在 `events` 里请求，也会出现在 `revents` 里**——这三个是内核强制上报的

### 5.4 没修好什么：四个病，只修了一个

**但**：全量拷贝照旧、O(n) 遍历照旧、用户再扫照旧。

| 病（正对 §4.5 的四个） | poll 的表现 |
|------|------|
| 每次调用**重传全量集合** | pollfd 数组照样整个从用户态**拷进内核** |
| 内核 **O(n) 线性遍历** | 内核还是逐个 pollfd 调它的 `poll` 方法问"你好了吗" |
| 返回后**用户再 O(n) 扫** | 还得自己遍历数组、找哪些 `revents != 0` |
| ~~上限 1024~~ | ✅ **只有这一条修掉了** |

> **一句话：poll 是 select 的"解除 1024 补丁版"，本质没变。**

> **通俗理解**：select 是"在只有 1024 格的花名册上打钩、还得从头翻到尾找钩"；poll 是"把名字写进一张可以无限长的名单"——**不用占固定格位了、名单多长都行，可内核还是得从头把每个名字念一遍，你也还是得自己扫一遍看谁应了**。

### 5.5 那它到底比 select 强在哪、又为什么没笑到最后

抛开"1024"这个数字，poll 唯一**实打实的性能优势**来自 `nfds` 语义的变化：

- 一个"只监听 10 个 fd、但 fd 号已经涨到几千"的服务（连接反复开关、fd 号越涨越大）
  - **select**：每次都得从第 0 位扫到第几千位 → 越来越慢
  - **poll**：只看这 10 个元素 → 开销恒定

**所以 poll 赢的不是"能放下更多连接"，而是"摆脱了 fd 编号"**——高 fd 号稀疏场景下它才明显更划算。

但它也没笑到最后：**大并发实践中都投向了 epoll**。因为连接数上万时，poll 那三个病（全量拷贝 / 内核 O(n) / 用户再扫）会一起爆发。**poll 的价值更像"过渡"**——它证明了"去掉 1024、用数组表达集合"这条路，却没解决"每趟都要碰所有 fd"这个根本问题，真正换掉模型的是下一节。

**面试话术**："poll 相对 select 主要改了两点：一是把位图换成 `pollfd` 数组，去掉了 1024 的硬上限；二是把'监听什么'（`events`）和'发生了什么'（`revents`）拆成两个字段，不用像 select 那样每次调用前重新初始化。还有个容易被忽略的点——select 的 `nfds` 是'最大 fd + 1'、跟 fd 编号绑死，开销跟最大 fd 号成正比；poll 的 `nfds` 只是数组元素个数，开销只跟监听个数成正比，**所以 fd 号稀疏分散时 poll 明显更快**。但它只修了上限这一个病：全量拷贝、内核 O(n) 遍历、返回后用户再 O(n) 扫，三个一个都没动——这也是为什么大并发最终都走 epoll。"

## 六、epoll：换了整个模型

### 6.1 三个接口，把"一次调用"拆成"注册 + 等待"

```c
int epfd = epoll_create1(0);                    /* ① 内核里建一个 epoll 实例 */
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event);    /* ② 注册 / 增删改 fd（一次性） */
epoll_wait(epfd, events, maxevents, timeout);  /* ③ 等就绪（可反复调，不重传） */
```

注意 `epoll_ctl` 直接接收 **fd 本身**（签名的第 3 个参数：`epoll_ctl(epfd, op, fd, event)`）——`fd` 就是一个**普通整数**，一次只操作**一个** fd，直接当参数传进去。而**多次调用累积起来**，内核里的红黑树才装下**所有注册过的 fd**，那才是一个真正的**集合**，不是编码。所以**没有边界参数、不受 fd 编号大小影响**。

**谁调这三个接口？——都是你的程序。** 它们全是**用户态代码主动发起的系统调用**，内核不会自己知道你要盯谁。典型服务端就是一个 `while (1)` 事件循环，三者在里面各司其职：

```c
int epfd = epoll_create1(0);                       /* ← 我雇管家（建 epoll 实例） */

epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);    /* ← 我让管家盯"新连接"（一次性） */

while (1) {
    int conn_fd = accept(listen_fd, ...);          /* ← 我 accept 出新连接 */
    epoll_ctl(epfd, EPOLL_CTL_ADD, conn_fd, &ev);  /* ← 我把新连接登记进管家本子（按需） */

    int n = epoll_wait(epfd, events, MAX, -1);     /* ← 我问管家"谁好了"（每圈都调，没事就睡着） */
    for (int i = 0; i < n; i++)
        handle(events[i].data.fd);                 /*   处理就绪的连接 */
}
```

| | `epoll_ctl` | `epoll_wait` |
|---|---|---|
| **谁调** | **你的程序** | **你的程序** |
| **什么时候** | **按需**——来了新连接 / 断开 / 改事件时才调 | **事件循环每一圈都调** |
| **调完怎样** | 立刻返回（只登记，不等待） | **阻塞**——没事件就睡着，有事件才返回 |
| **干嘛** | 告诉内核"**盯谁**" | 问内核"**谁好了**" |

**这个"阻塞"就是 epoll 省 CPU 的精髓**：一个线程管几万连接，靠的就是它绝大部分时间**睡在 `epoll_wait` 里**——有数据才被内核按门铃叫醒，没数据 CPU 占用接近 0。（对比 §3.7 的轮询非阻塞 read：那个不睡、一直空转烧 CPU。）

**落到 Java**：你调 `selector.register(channel, OP_READ)` → JDK 通过 JNI 调 `epoll_ctl`；你调 `selector.select()` → 底层就是 `epoll_wait`（Netty 的 `NioEventLoop.run()`、Redis 的 `aeApiPoll()` 都是这一句）。**"什么时候登记、什么时候等"始终在你自己手里**——只不过 C 写的服务是程序直接调，你写 Java 时是 JDK 替你调。

### 6.2 内核里的三件套

| 结构 | 装什么 | 作用 |
|------|--------|------|
| **红黑树** | 所有**注册过的** fd | 增删改查 O(log n)；**注册一次就常驻内核**，不用反复拷 |
| **就绪链表** | 已经**就绪**的 fd | `epoll_wait` 只需要看它 |
| **等待队列** | 等在**这个 epfd** 上的进程 | ⚠ **只挂一次**（挂在 epfd 上），不是每个 fd 挂一次 |

### 6.3 关键在"回调"——这是 epoll 快的本质

`epoll_ctl(ADD)` 的时候，**内核顺手给这个 fd 的等待队列注册了一个回调函数**（`ep_poll_callback`）。之后：

```
网卡收到数据
   ↓ 硬中断 → 软中断
内核处理 socket → 该 socket 进入就绪
   ↓ 内核调用它等待队列上的回调
ep_poll_callback()：把这个 fd ★挂进就绪链表★
   ↓
epoll_wait() 醒来 → 看就绪链表非空 → 取出来返回
```

**所以 `epoll_wait` 的代价只和「就绪的 fd 数」成正比，和"总共多少个 fd"完全无关。**

这是个**控制反转**：select 是"我每次来问一遍所有人"，epoll 是"**注册时就把通知方式绑好，你主动来找我**"。和 `SIGCHLD` 是同一个思想（pull → push，见 [[wait 与僵尸进程回收详解#② 标准做法：平时不管，交给 SIGCHLD]]）。

> **通俗理解**：select 像**每次上课点一遍大名**——不管有没有事，全班一百人的名字都得念一遍，谁答到记下来；人越多点得越久。epoll 像**开学时每人发个门铃**——谁有事自己按，你只看"响了哪几个"；**只要没人按，你就不用管有一百个人还是一万个人。**

> ⚠ **这条回路的起点在网卡**：上面说的「内核调用回调」，正是**网卡收包的软中断**里发现 socket 就绪的那一刻——完整链路见 [[网卡收包流程详解#八、和 epoll / 零拷贝的接点]]。

### 6.4 三个对比维度（正对着 select 的三个病）

| 维度 | select / poll | epoll |
|------|--------------|-------|
| fd 集合传递 | 每次调用**全量拷贝** | `epoll_ctl` **注册一次**，永久驻留内核 |
| 谁去找就绪 | 内核**遍历全部** O(n) | **回调**推入就绪链表，取 **O(就绪数)** |
| fd 上限 | 1024（select）/ 无（poll） | 无（受 `file-max`、`ulimit -n` 约束） |

| | select | epoll |
|------|--------|-------|
| 怎么表达"监听谁" | 编码进**位图位置** | fd 作为**参数直接给** |
| 要不要边界参数 | 要（`nfds`，传错就漏） | 不要 |
| 受 fd 编号大小影响吗 | **受**（代价 ∝ 最大 fd 号） | 不受 |
| 怎么找就绪的 | 逐位扫 | 看**就绪链表** |

## 七、LT 与 ET：机制层

|        | **LT（水平触发，默认）**                                  | **ET（边缘触发）**                  |
| ------ | ------------------------------------------------ | ----------------------------- |
| 什么时候报  | **只要缓冲区还有数据，每次都报**                               | **只在"无 → 有"这个状态跳变时报一次**       |
| 内核怎么实现 | `epoll_wait` 返回前检查该 fd 是否**仍然就绪**，是就**重新挂回就绪链表** | 挂出去就不复查                       |
| 编程要求   | 随便读，读不完下次还会通知                                    | **必须配非阻塞 fd + 循环读到 `EAGAIN`** |
| 漏读后果   | 无（下次还报）                                          | **数据永远等不到通知**（状态没再变化），连接卡死    |
| 谁用     | 大多数场景（安全）                                        | **Nginx**，追求更少通知次数            |

**ET 那个坑必须说透**：如果 fd 是**阻塞**的，你循环读到"没数据"时 `read` 会**永久阻塞**；如果不读到 `EAGAIN` 就退出循环，剩下的数据**再也没人通知你**——**两个条件缺一不可**。

另有 **`EPOLLONESHOT`**：报一次后自动把 fd 从就绪链表摘掉，要重新 `epoll_ctl` 注册——**多线程下防止同一个 fd 被两个线程同时处理**。

## 八、四个常见误区（面试高频陷阱）

| ❌ 错误说法 | ✅ 正确 |
|---|---|
| 「epoll 用 **mmap** 共享内核用户内存减少拷贝」 | **错**。`epoll_wait` 是 `copy_to_user` **拷贝**就绪事件；省的是"全量 fd 集合的反复拷贝"。这是 2.4 时代的老传言，从未采用 |
| 「epoll 是 **O(1)**」 | 准确是 **O(就绪数)**。活跃 fd 很多时 ≈ O(n) |
| 「epoll 一定比 select 快」 | **只在"连接多、活跃少"时明显**。若几乎所有 fd 都活跃，epoll 的红黑树维护成本反而可能让它不如 select |
| 「ET 更快所以都用 ET」 | ET 省通知次数，但编程门槛高、易漏读卡死。**LT 更安全**，是默认 |

## 九、两个延伸工程点

- **惊群（thundering herd）**：多个进程 / 线程等同一个 epfd 时，一个事件可能**唤醒全部**，但只有一个能干活。Linux 4.5+ 的 **`EPOLLEXCLUSIVE`** 缓解。
- **kqueue**：BSD / macOS 上的等价物。Netty 的 `EpollEventLoopGroup` / `KqueueEventLoopGroup` 就是包这层。

## 十、下一代：io_uring

epoll 是 **reactor** 模型——它告诉你"这个 fd **可以**读了"，**之后你还得自己 `read`**（又一次系统调用）。

**io_uring** 是 **proactor** 模型——它**替你做完**，你只要读共享内存里的完成队列。它把「提交请求」和「获取结果」都变成了共享内存读写，所以连"取结果"都不需要系统调用。详见 [[模式切换与上下文切换详解#8.1 批量：一次 syscall 搬多块数据]]。

## 十一、落到实战

| 落点 | 在哪 |
|------|------|
| **Redis 单线程 + epoll** | [[Redis IO多路复用详解#架构：Reactor 模式]]（Reactor、文件事件分派器） |
| **Nginx** | 用 **ET** 模式 |
| **Netty** | Linux 走 epoll native transport，macOS 走 kqueue |
| **Java NIO** | `Selector` 在 Linux 上底层就是 **epoll**；`SocketChannel` 就是 fd 的封装 |
| **IO 模型定性** | [[OS热门面试题]] Q19（前四种都算同步 I/O）/ Q20（select/poll/epoll 对比） |
| **系统级底座** | [[OS八股#7.2 IO 多路复用：select → poll → epoll]] |

**为什么 Redis 单线程能扛高并发**：epoll 一次等多连接（**省掉线程上下文切换**）+ 全内存 + 单线程无锁竞争。这三条是因果链，不是并列名词。

## 面试话术

> "select 和 epoll 的差别，本质是**内核里'谁去找就绪 fd'这件事的模型不同**。
>
> select 用**位图**表达要监听谁——下标是 fd 号、这一位是 1 就表示要监听。这带来三个后果：一是每次调用都要把整张位图从用户态拷进内核；二是内核不知道你填到哪一位，必须传 `nfds` 划边界，**传小了会静默漏掉**；三是内核只能**从第 0 位逐位扫**，所以它的开销是跟**最大 fd 号**成正比，不是跟你监听了几个成正比。也正因为位图只有 1024 位，**select 的 fd 上限就是 1024**。
>
> poll 把位图换成了数组，去掉了 1024 上限，但拷贝和 O(n) 遍历一个都没解决——它只是 select 的解绑补丁。
>
> epoll 换了个模型，把一次调用拆成了注册和等待两件事。`epoll_ctl` 注册时，fd 直接当参数传进去插进红黑树，而且**内核顺手在这个 fd 上挂了个回调**。以后数据来了，内核在处理网卡和 socket 的时候就顺手把 fd **丢进一个就绪链表**。所以 `epoll_wait` 只需要看一眼那个链表有没有东西，代价只跟**就绪的个数**成正比，跟总连接数无关。这就是为什么说它赢在'连接多、活跃少'——**如果所有连接都很活跃，epoll 相对 select 的优势就没那么大了**。
>
> 最后有两个坑要说清：第一，**epoll 不是用 mmap 共享内存**，那是老传言，它是把就绪事件拷贝给你的，省的是全量集合的反复拷贝；它的复杂度准确说是 **O(就绪数)**，不是 O(1)。第二，**ET 必须配非阻塞 fd 并循环读到 EAGAIN**，少任何一个条件都可能让连接卡死——用阻塞 fd 会永久阻塞，不读到 EAGAIN 就再也不会收到通知。"
