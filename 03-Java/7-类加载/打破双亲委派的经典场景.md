# 打破双亲委派的经典场景

> 面试高频题「打破双亲委派的经典场景有哪些？」的统一入口。本页汇总两大经典场景（Tomcat / JDBC-SPI）、两种打破方式对比、以及完整面试话术。

---

## 一、先分清：两种"打破"方式

打破双亲委派只有两条路，方向正好相反：

| 方式 | 谁动手 | 方向 | 典型场景 |
|------|--------|------|---------|
| **重写 `loadClass()`** | 子加载器**不委派给父**，优先自己加载 | **下层打破**（子不听话） | Tomcat WebappClassLoader |
| **线程上下文类加载器（TCCL）** | 父加载器**主动调子加载器**去加载 | **上层打破**（父主动伸手） | JDBC SPI、JNDI、JAXB |

> 一句话：**重写 loadClass 是"从下往上打"（子加载器先抢），TCCL 是"从上往下捞"（父加载器够不着，喊子加载器帮忙）。**

---

## 二、场景一：Tomcat —— 重写 loadClass（下层打破）

### 先搞清：为什么一个 JVM 会有多个 webapp？

这是 **Java Web 容器的传统多应用托管模型**（Tomcat 的核心价值之一）：

```
一台服务器
└── Tomcat 进程（一个 JVM）
    ├── webapps/
    │   ├── shop.war   ← WebApp A（自己的 WEB-INF/lib）
    │   ├── admin.war  ← WebApp B（自己的 WEB-INF/lib）
    │   └── api.war    ← WebApp C（自己的 WEB-INF/lib）
    └── 共享一个端口 8080、一份 JVM
```

**好处**：多个应用塞一个 JVM，省内存/进程/端口，运维简单（启动一个 Tomcat 全活）。
**代价**：应用之间**逻辑隔离而非物理隔离**——共享堆、共享 GC、一个应用 OOM 可能拖垮整个 JVM。

> [!warning] 别和微服务混淆
> 「一个 JVM 多个 webapp」是**传统多应用托管**，靠 **ClassLoader 隔离**（逻辑隔离）；微服务是**拆成独立进程/JVM**（物理隔离），反而规避了"多 webapp 争 classpath"的问题，也就不需要 WebappClassLoader 那套隔离。
> 所以答「打破双亲委派」讲的是**传统模型**；微服务里真正常见的是 **SPI/TCCL**（上层打破，见场景二），两者别混。

### 为什么需要

**不同 WebApp 可能依赖同一个 jar 的不同版本**（比如 WebApp-A 用 Spring 4、WebApp-B 用 Spring 5）。如果走双亲委派：

- 父加载器先加载了第一个版本（Spring 4）→ 后面的 WebApp 全被"传染"只能用 Spring 4
- 应用之间**无法隔离**

### 怎么破

Tomcat 的 `WebappClassLoader` **重写 `loadClass()`**，把委派顺序反转：

```
标准双亲委派：          WebappClassLoader（破坏后）：
parent 先尝试           自己先尝试（WEB-INF/classes、WEB-INF/lib）
    ↓                        ↓
parent 失败 → 自己加载      自己失败 → parent 兜底
```

每个 WebApp 一个 `WebappClassLoader`，优先加载自己 `WEB-INF/` 下的类 → **实现应用级依赖隔离**。

### 代价

不同 WebApp 里"同名类"不再是同一个类（破坏"类只加载一次"）——但这正是容器想要的隔离效果。另注意：重写 `loadClass` 有**覆盖核心类**的风险（如果自己加载了 `java.lang.String`），所以 Tomcat 对 `java.*` 开头的类仍然先委派给父（防止破坏 JDK 核心类）。

## 三、场景二：JDBC / SPI —— TCCL（上层打破）

### 为什么需要

```
Bootstrap ClassLoader
    ↑ 只有指向父的 parent 指针，没有指向子的通道
    │
    ├─ java.sql.Driver（接口，在 JDK 里，由 Bootstrap 加载）
    │
    └─ 但 MySQL 驱动实现（com.mysql.cj.jdbc.Driver）在应用 classpath
       Bootstrap 看不到 classpath，加载不到！
```

- `DriverManager` 由 **Bootstrap** 加载（在 `java.base` 里）
- MySQL 驱动实现在应用 classpath，归 **AppClassLoader** 管
- **双亲委派是单向的**：委派只有"子问父"这一根 `parent` 指针。从 Bootstrap 发起加载时，它没有父可问、又没有 children 引用够不到 AppClassLoader，只能自己试（classpath 里没有）→ 失败。**这就是"够不着"的字面含义**（源码级深挖见 [[线程上下文类加载器（TCCL）#核心矛盾]]）

### 怎么破

用**线程上下文类加载器（TCCL）**反向向下加载：

```
DriverManager.init() 运行时
    ↓
获取当前线程的 contextClassLoader（默认是 AppClassLoader）
    ↓
用 contextClassLoader.loadClass("com.mysql.cj.jdbc.Driver") 加载
    ↓ 成功！
```

这就是**从上层调用下层"反向"打破**双亲委派。

### 同类场景（SPI 家族）

| 场景 | 接口（上层） | 实现（下层） |
|------|-------------|-------------|
| **JDBC** | `java.sql.Driver`（JDK） | MySQL / Oracle 驱动（第三方 jar） |
| **JNDI** | `javax.naming.spi.InitialContextFactory` | 容器提供实现 |
| **JAXB** | `javax.xml.bind.JAXBContext` | 各实现 |
| **日志门面** | `org.slf4j.spi` | Logback / Log4j2 绑定 |
| **Dubbo 扩展** | `@SPI` 接口 | 各扩展实现 |

> 面试提一嘴「**JDBC、日志门面、Dubbo 扩展都是同一套 SPI 思想**」——说明你见过不止一个例子，属于加分项。

## 四、为什么"重写 findClass"不算打破

JDK 官方推荐的自定义类加载器方式，**不破坏**双亲委派：

| 维度 | 重写 `findClass()` | 重写 `loadClass()` |
|------|:---:|:---:|
| **是否破坏双亲委派** | ❌ 不破坏 | ✅ 破坏 |
| **典型用途** | 自定义加载来源（网络、加密、指定目录） | 需要优先加载自己的类（容器隔离） |
| **委派顺序** | parent → self（不变） | self → parent（反转） |
| **安全性** | 核心类仍由 Bootstrap 保护 | 可能覆盖核心类（危险） |
| **JDK 推荐** | ✅ 官方推荐 | ⚠ 仅在确实需要破坏时使用 |

> `loadClass()` 默认流程：先查已加载 → 委派父加载器 → 父失败才调 `findClass()`。所以只重写 `findClass()` 只是提供"自己从哪读字节码"的能力，**委派顺序不变**；重写 `loadClass()` 才是把整条链的入口换掉，**真正打破**。

## 五、面试话术（一锤定音版）

**问：打破双亲委派的经典场景有哪些？**

> 主要有两大类，方向正好相反：
>
> **① Tomcat —— 重写 `loadClass()`，下层打破。** 不同 WebApp 可能依赖同一个 jar 的不同版本，双亲委派会让父加载器先加载的版本"传染"所有 WebApp。Tomcat 给每个 WebApp 配一个 `WebappClassLoader`，重写 `loadClass()` **优先加载自己 `WEB-INF/` 下的类**，实现应用级依赖隔离。
>
> **② JDBC/SPI —— 线程上下文类加载器，上层打破。** `DriverManager` 由 Bootstrap 加载，但 MySQL 驱动在应用 classpath，按双亲委派 Bootstrap 够不着。`DriverManager` 通过 `Thread.currentThread().getContextClassLoader()` 拿到当前线程的加载器（AppClassLoader），**反向向下加载**驱动实现。JDBC、JNDI、JAXB、日志门面都是同一套 SPI 思想。
>
> **本质**：打破双亲委派就是**改变"父优先"的加载顺序**——要么子加载器先抢（Tomcat），要么父加载器反手调子加载器（TCCL）。

## 六、补：类的唯一性 = 类加载器 + 全限定名

上文场景一里说 WebappClassLoader「**破坏"类只加载一次"**」——这句要讲精确，否则容易被面试官追着问。

**JVM 判定"是不是同一个类"的规则是：类加载器实例 + 类的全限定名，两者都相同才算同一个类。**

- **同一个类加载器**：不会重复定义同名类——`loadClass()` 第一步 `findLoadedClass()` 命中缓存就直接返回，"只加载一次"对**单个**加载器依然成立。
- **不同类加载器**：可以**各自定义**一个全限定名完全相同的类，这两个 `Class` 对象彼此**不相等**（`clazzA != clazzB`），也不能互相赋值/强转（抛 `ClassCastException`）——JVM 眼里它们是**两个不同的类**。

这正是容器应用隔离的基础：WebApp-A 的 `WebappClassLoader` 和 WebApp-B 的 `WebappClassLoader` 各自加载自己的 `com.example.Foo`，哪怕全限定名一模一样，二者的静态变量、类型强转都不互通，从而做到"你用你的 Spring 4、我用我的 Spring 5"。

> 记忆锚点：**"类只加载一次"是"每个加载器各加载一次"**。同一个类被 N 个加载器加载，就是 N 个互不相同的 `Class` 对象——这既是破坏双亲委派想要的效果（隔离），也是它的代价（同名类不再唯一）。
