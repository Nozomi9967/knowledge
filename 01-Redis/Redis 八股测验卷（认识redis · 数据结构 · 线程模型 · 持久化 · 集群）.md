### 一、认识 Redis（共 2 题）

**第 1 题**

Redis 和 Memcached 有哪些主要区别？为什么选择 Redis 作为 MySQL 的缓存？（请从高性能和高并发两个角度展开）

1. memcached进提供简单的key-value数据结构，而redis提供List Set Hash ZSet等等多种数据结构
2. memcached不支持持久化，redis支持
3. memcached没有原生的集群原型，redis有
4. memcached不支持订阅模型、lua脚本以及事务，redis支持

redis对数据的操作主要是在内存而且redis是单线程，所以它对数据的操作非常快，单机qps轻松过10w

**第 2 题**

Redis 被归类为"基于内存的数据库"，它的读写操作都在内存中完成。请问这种设计带来了哪些优势？又引入了哪些必须解决的问题？（提示：从数据安全、容量、集群等角度思考）

最主要的优势就是非常快
但它的弊端就是数据不安全，如果redis宕机或系统故障，数据就会丢失

### 二、Redis 数据结构（共 3 题）

**第 3 题**

Redis 提供了哪些基本数据类型？请列举出至少 6 种，并分别说明每种类型适合的一个典型应用场景。

1. String：分布式锁、常规计数、存储对象、持久化Session信息
2. List：消息队列
3. Hash：存储对象、购物车
4. Set：共同关注、点赞等交并差运算
5. ZSet：排行榜、手机号/姓名排序
6. GEO：用于提供位置信息
7. HyperLogLog：用于百万UV统计
8. Stream：消息队列，解决了List消息队列的需要自行生成全局唯一ID和消费者组的问题
9. BitMap：用于二值状态统计，例如：用户登录状态以及签到情况

---

**第 4 题**

Redis 的 String、List、Hash、Set、ZSet 五种数据类型，各自在底层使用了什么内部编码实现？请分别说明在什么条件下会触发编码转换（比如从压缩列表转换为其他结构），以及在 Redis 7.0 中有什么变化。

- String：SDS 简单动态字符串
- List：元素个数超过512个且元素大小超过64字节，压缩列表->双向链表
	- 7.0中，只由quicklist实现
- Hash：元素个数超过512个且元素大小超过64字节，压缩列表->哈希表
	- 7.0中，压缩列表被listpack替代
- Set：元素个数超过512个且元素大小超过64字节，整数集合->哈希表
- ZSet：元素个数超过512个且元素大小超过64字节，压缩列表->跳表
	- 7.0中，压缩列表被listpack替代

**第 5 题**

Stream 数据类型解决了 List 作为消息队列时的哪些问题？相比 List，Stream 额外提供了哪些关键能力？

- 解决了List需要自行实现全局唯一ID和无法以消费者组的形式消费数据的问题

- 提供了消息持久化

### 三、Redis 线程模型（共 3 题）

**第 6 题**

我们常说"Redis 是单线程的"，这句话的含义是什么？Redis 启动时真的只有一个线程在工作吗？请说明 Redis 在 2.6 版本和 4.0 版本分别启动了哪些后台线程，各自负责什么任务。

是指进行数据操作的是单线程

redis启动时还会启动三个后台线程，分别用来异步关闭文件、AOF刷盘以及释放内存

---

**第 7 题**

Redis 采用单线程模型为什么还能这么快？请从数据存储位置、数据结构效率、线程竞争开销、IO 处理机制四个角度分别说明。其中 IO 多路复用机制具体是如何工作的？

首先来说，为什么不多线程？
因为redis操作数据主要在内存，而CPU操作内存数据非常快，几乎要不了多少CPU周期
所以性能瓶颈不在于CPU，自然无需多线程
而单线程避免了多线程时线程切换的时间和空间开销，还不用担心死锁的问题
同时，redis还采用了IO多路复用的机制，也就是一个线程可以监听并处理多个socket

---

**第 8 题**

Redis 6.0 为什么引入了多线程？引入的多线程用于处理什么任务？命令的执行是否也变成了多线程？请说明 Redis 6.0 默认的 IO 线程配置方式，以及如何开启对读请求的多线程处理。

因为网络硬件的性能得到了很大的提升，所以性能瓶颈有相当一部分取决于网络IO的处理
引入的多线程就是为了帮助主线程处理网络IO，将客户端发来的数据简单处理后，放入内存，等待主线程去执行操作即可，因此可以看出，命令的执行还是单线程

默认的IO线程只发送响应数据，不处理读数据
io-threads-read yes

### 四、Redis 持久化（共 5 题）

**第 9 题**

Redis 有哪三种数据持久化方式？请简要说明各自的基本原理。

- AOF日志：将操作数据的命令以追加的方式写入到文件中
- RDB快照：将某一时刻的内存数据，以二进制的方式保存下来
- 混合持久化：混合使用AOF和RDB，继承了它们的优点

---

**第 10 题**

AOF 日志是在什么时机记录写操作命令的？Redis 为什么选择"先执行命令，再记录日志"的顺序？这种顺序有没有什么副作用？

主线程执行完写操作后，会将对应的命令写AOF日志

因为如果写入AOF日志的命令有语法错误，会导致复现数据时出现错误

由于写AOF日志是异步的，主线程并不用等待AOF写入成功即可返回响应客户端，所以可能出现数据丢失的现象


---

**第 11 题**

AOF 日志的写入过程分为哪几个步骤？Redis 提供了哪三种写回硬盘的策略（appendfsync 参数）？请分别说明这三种策略的行为和优缺点。

写入aof_buf缓存区->调用write系统调用写入内核缓冲区->由内核决定何时写入到硬盘

- always：每次写AOF日志时，都立刻写回硬盘
	- 优点：数据不易丢失
	- 缺点：性能差
- everysec：每隔一秒，将内核缓冲区的aof日志写回硬盘
	- 优点：数据较完整，不那么容易丢失
	- 缺点：，如果系统宕机的话，也最多只会丢失上一秒的数据
- never：仅由内核决定何时写回硬盘
	- 优点：性能好
	- 缺点：数据非常容易丢失

---

**第 12 题**

什么是 AOF 重写机制？为什么需要 AOF 重写？重写过程是由什么进程来完成的，为什么选择子进程而不是子线程？重写过程中如果主进程修改了已经存在的 key-value，如何保证数据一致性？

由于AOF日志记录的操作命令日志，而一个数据可以经过多个命令的修改，从而会产生非常多的AOF日志，这会导致恢复数据时十分缓慢，AOF重写就是根据当前每一个数据的状态重新生成对应的一个命令

由AOF后台重写子进程完成
子线程的话，如果对共享内存修改会加锁，影响性能
而子进程对父进程的共享内存空间只读，如果对内存修改会发生写时复制

重写时，redis会创建一个aof重写缓冲区，如果主进程修改了已存在的数据，会将该修改命令写入到aof重写缓冲区中，等子进程完成aof重写后，子进程会发送信号给父进程，父进程会将aof重写缓冲区中的aof日志追加到子进程刚刚重写完的新aof日志文件中


---

**第 13 题**

RDB 快照和 AOF 日志在"数据恢复"这个场景下各有什么优缺点？什么是混合持久化？它是如何结合 RDB 和 AOF 两者优点的？混合持久化有什么缺点？

RDB快照因为存的是某一瞬间内存的快照，所以恢复速度很快，但因为每次都是全量RDB快照，快照频率高的话，很影响性能，频率低的话，又容易丢数据
AOF日志因为每次都是追加操作日志，不容易丢数据，但缺点就是恢复速度很慢

混合持久化就是在AOF重写时，子进程先用RDB快照记录父进程共享内存中的数据并写入到AOF日志文件中，结束后再将AOF重写缓冲区中的AOF日志写入到AOF日志文件
好处：恢复速度又快数据又不容易丢
缺点：文件格式乱，前面是RDB快照后面是AOF日志，且对于之前的redis版本来说，不兼容

### 五、Redis 集群（共 3 题）

**第 14 题**

Redis 实现服务高可用有哪三种方案？请分别说明每种方案的核心作用和解决的问题。在主从复制中，主从服务器之间采用的是"读写分离"的方式，请问主服务器将数据同步给从服务器是同步还是异步的？这种设计对数据一致性有什么影响？

- 主从复制：增加redis服务的可用性，解决单点故障导致的业务停滞
- 分片集群：减轻单个节点的内存压力
- 哨兵模式：监视主从节点故障

是异步的，也就是说主服务器完成写命令后会立刻返回响应给客户端，然后发送异步的写命令给从服务器，如果此时从服务器宕机，这个写命令就丢失了，从而导致主从数据不一致

---

**第 15 题**

Redis 的哨兵模式解决了什么问题？哨兵模式具备哪几个核心功能？

解决了主从节点宕机时需要手动更换主节点的操作

- 监听：主从节点会定时ping哨兵，一旦某个节点超过阈值没联系哨兵，就会被判断为下线，如果是主节点，会从从节点中选举新的主节点


---

**第 16 题**

Redis Cluster（切片集群）是如何将数据分布到不同节点上的？请详细说明哈希槽（Hash Slot）的映射过程（从 key 到具体节点的完整链路）。集群中有两种分配哈希槽的方式，分别是什么？


一个集群有16384个哈希槽，哈希槽类似数据分区，当客户端发来一个键值对时，首先会对key进行CRC16计算，得到16bit，再对16bit值进行16383取模，模数在0-16383，也就是对应的哈希槽索引

- 手动分配
- 平均分配

---

**第 17 题**

什么是 Redis 集群脑裂？请描述脑裂产生的完整过程。它会导致什么问题？如何通过 min-slaves-to-write 和 min-slaves-max-lag 这两个参数来防止脑裂导致的数据丢失？请结合一个具体的时间参数配置例子来说明。


如果因为网络故障，主节点和从节点失联，此时主节点还继续处理客户端的请求，而不会同步给从节点，哨兵会判断主节点下线，选举出新的主节点，这时有两个主节点，就是脑裂。如果主节点这时与从节点的通信恢复，但也没用了，它已经变成了从节点，而从节点第一次同步这个新的主节点是要全量同步的，也就是要删除自己的所有数据，之前客户端的操作数据就会丢失

- min-slaves-to-write x：如果与主节点相连的从节点个数少于x，主节点将不再处理客户端请求并直接返回错误
- min-slaves-max-lag y：如果主节点与哨兵的响应延迟大于y，则判断该主节点下线，选举新主节点
