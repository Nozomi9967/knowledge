### **顺序消息的本质是「同一业务键的消息必须进同一个分区、由同一个消费者串行处理」。Kafka 靠「按 key 分区 + 单分区单消费者 + 关闭重试乱序」，RocketMQ 靠 `MessageQueueSelector` 选队列 + `MessageListenerOrderly` 队列锁；所谓"局部有序"才是工程上能用的方案，"全局有序"意味着单分区单线程，吞吐直接掉到最低。**

下面按面试口述节奏展开，先说清楚顺序为什么会乱，再分别讲两个 MQ 的做法。

---

**第一部分：顺序在哪些环节会乱**

一条消息从生产到消费，有四个环节可能乱序：

**发送端并发**。生产者多线程同时发，虽然调用顺序是 1、2、3，但到达 broker 的顺序可能是 3、1、2。

**分区路由**。topic 有多个分区，broker 只保证**分区内有序**，跨分区没有任何顺序保证。

**消费端并发**。一个消费者多线程拉取处理，或者多个消费者分摊同一个 topic 的不同分区，处理完成的顺序就不受控了。

**重试**。Kafka 在 `max.in.flight.requests.per.connection > 1` 且开启重试时，第一批失败重发可能排到第二批后面，造成乱序——这是很多人不知道的坑。

所以"保证顺序"要在这四个环节都做约束，缺一个就白搭。

---

**第二部分：Kafka 的顺序保证**

Kafka 的顺序规则只有一句话：**分区内有序，分区间无序**。

要利用这个规则，做法是：

**生产端按业务键分区**。不指定 partition 时会按 key 的 hash 选分区，所以只要把"需要有序的消息"用同一个 key 发出去，它们必然落进同一个分区：

```java
// 订单状态流转：用 orderId 做 key，同一订单的消息一定在同一分区
ProducerRecord<String, String> record =
    new ProducerRecord<>("order-status", orderId, payload);
producer.send(record);
```

注意：如果生产端手动指定了 partition，key 就不起作用了，顺序保证失效。

**生产端关掉乱序风险**：

```properties
# 要么关掉重试
retries=0
# 要么限制并发请求数为 1（性能损失大）
max.in.flight.requests.per.connection=1
# 最优解：开启幂等，Kafka 会用序号保证重试不乱序
enable.idempotence=true
```

`enable.idempotence=true` 是 0.11 之后的正解：它允许多个在途请求（默认最多 5），同时用 Sequence Number 保证 broker 端按序写入，重试也不会乱。

**消费端只能单线程处理一个分区**。一个分区同一时刻只能被组内一个消费者消费，所以只要消费者内部不开线程池并行处理，就是有序的。开了线程池就必须自己按 key 分发到固定的内存队列。

---

**第三部分：RocketMQ 的顺序保证**

RocketMQ 的模型是 topic → 多个 MessageQueue，顺序规则同样是**队列内有序**。

**生产端：用 `MessageQueueSelector` 手动选队列**

```java
producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> queues, Message msg, Object arg) {
        String orderId = (String) arg;
        int index = Math.abs(orderId.hashCode()) % queues.size();
        return queues.get(index);
    }
}, orderId);
```

同一个 orderId 永远落到同一个队列。

**消费端：用 `MessageListenerOrderly`**

```java
consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ConsumeOrderlyContext ctx) {
        for (MessageExt msg : msgs) {
            handle(msg);
        }
        return ConsumeOrderlyStatus.SUCCESS;
    }
});
```

`MessageListenerOrderly` 和普通的 `MessageListenerConcurrently` 有本质区别：**前者对队列加锁，一个队列同一时刻只允许一个消费线程处理**；后者是多线程并发消费同一个队列。

代价也很直接：顺序消费的吞吐 = 队列数 × 单线程处理速度，队列数固定时无法通过加线程提速。所以 RocketMQ 的顺序消费在队列多的时候才能撑起吞吐。

---

**第四部分：并发消费下怎么不破坏顺序——三个真实坑**

**坑一：失败重试会阻塞整个队列**

`MessageListenerOrderly` 里如果返回 `SUSPEND_CURRENT_QUEUE_A_MOMENT`，这个队列会被挂起一会儿再重试，期间后面的消息全卡住。所以顺序消费的消费逻辑必须"要么快速成功、要么快速失败"，不能有长耗时操作。

**坑二：扩分区 / 扩队列会破坏历史顺序**

Kafka 扩分区后，同一个 key 的新消息可能落到新分区，和历史消息不在一个分区了，顺序断裂。RocketMQ 扩队列同理。所以**有顺序要求的 topic 一开始就要把分区数估够**，后期尽量不扩。

**坑三：全局有序不可取**

想要全局有序只有一条路：单分区 + 单消费者 + 单线程。吞吐直接掉到"一条一条处理"，任何有量的业务都撑不住。所以要跟面试官明确：**我们做的是"按业务键的局部有序"**，比如同一订单的状态流转有序，不同订单之间无所谓。

---

**第五部分：业务层的最后一道保险**

即使 MQ 保证了顺序，消费端处理失败、重试、或者跨系统调用，仍可能让最终状态错乱。所以业务侧通常再加一层"版本号 / 状态机"：

```sql
UPDATE t_order SET status = 'SHIPPED'
WHERE order_no = ? AND status = 'PAID';
-- 影响行数为 0，说明状态已经跳过或回退，直接丢弃这条消息
```

这样即使消息乱序到达（比如"已发货"比"已支付"先到），状态机也能挡住非法流转。**这是比 MQ 顺序更强的保证**，面试里主动提这一点会加分。
