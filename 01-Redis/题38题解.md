### **Redis Cluster 的 `mget` 要求所有 key 落在同一 slot，用 `{}` 包裹 key 的公共部分作为 hash tag 强制同 slot；但生产上更推荐用 pipeline 按 slot 分组并发执行，避免 hash tag 带来的数据倾斜。**

下面按面试口述节奏展开。

---

**第一部分：先讲清楚 `CROSSSLOT` 是怎么来的**

Redis Cluster 把整个 keyspace 分成 **16384 个 slot**，每个 key 通过 **CRC16(key) mod 16384** 计算落到哪个 slot，slot 再分配给具体的 master 节点。

关键规则：**一条命令涉及的所有 key 必须在同一个 slot**，否则集群无法保证原子性和路由效率，直接报错：

```
(error) CROSSSLOT Keys in request don't hash to the same slot
```

受这条规则影响的命令包括：

- **多 key 读**：`MGET`、`MSET`；
- **集合运算**：`SINTER`、`SUNION`、`SDIFF`、`ZUNIONSTORE`、`ZINTERSTORE`；
- **事务**：`MULTI/EXEC` 里的多个 key；
- **Lua 脚本**：`EVAL` 里访问的多个 key（KEYS 数组）；
- **RENAME**、**SMOVE** 这类跨 key 操作。

为什么这么设计？因为 Redis Cluster 是**去中心化架构**，没有全局协调器。一条命令跨多个节点意味着要做分布式事务，代价过高，直接从协议层禁止。

---

**第二部分:hash tag 的用法**

**核心机制**：如果 key 中包含 `{...}`，则**只用 `{}` 内的部分计算 CRC16**，而不是整个 key。

```
user:{1001}:profile
user:{1001}:orders
user:{1001}:cart
```

这三个 key 因为 `{1001}` 相同，CRC16 结果一致，**必然落在同一个 slot**，可以 `MGET` / 事务 / Lua 一起操作。

**几个细节规则**：

1. **只取第一对 `{}` 之间的内容**：`{a}:{b}` 只用 `a` 计算；
2. **空 `{}` 不生效**：`user:{}:1001` 中 `{}` 内为空，回退到用整个 key 计算；
3. **`{` 后必须有对应的 `}`**：`user:{1001:orders` 没有闭合，回退到整个 key；
4. **顺序敏感**：必须 `{` 在前 `}` 在后。

**典型使用场景**：

- **购物车、用户相关的一组 key**：`cart:{uid}`、`profile:{uid}`、`session:{uid}` —— 按用户维度聚合；
- **同一订单的多个字段**：`order:{oid}:items`、`order:{oid}:pay`、`order:{oid}:logistics`；
- **需要事务的一组 key**：转账场景 `account:{txid}:from`、`account:{txid}:to`（虽然这个例子不太合理，实际转账应该是账户间转，需要更谨慎的设计）。

---

**第三部分:hash tag 的坑（面试重点）**

hash tag 用得好是利器，用不好是灾难。核心问题是**破坏了 slot 分布的均匀性**，容易造成数据倾斜。

**坑一：大 tag 导致单节点热点**

如果用 `{shop_id}` 做 tag，某个大商家有几百万个 key，全部集中在一个 slot、一个节点上：

- 这个节点内存爆掉、CPU 打满；
- 迁移 slot 时该节点成为瓶颈；
- 集群扩容也没用，因为 tag 相同的 key **无法拆分到多个节点**。

**规避**：

- 只对**必须同 slot 操作**的 key 加 tag，不要"顺手"加；
- tag 的粒度选 **用户级、订单级**这种基数大的维度，不选**商家级、类目级**这种基数小的维度；
- 单个 tag 下的 key 数量、内存要有监控，超过阈值告警。

**坑二：滥用 hash tag 让 Cluster 退化成单机**

有人为了避免所有 `CROSSSLOT` 报错，把所有 key 都加同一个 tag，比如 `{myapp}:user:1`、`{myapp}:order:1`……结果**所有 key 都落在一个 slot**，整个 Cluster 只有一个节点在干活，白白浪费了 16384 slot 的分片能力。

**坑三:key 迁移**

生产上一开始没用 tag，后来发现需要，改造成本很高——**改 key 名意味着数据要迁移**，所有旧 key 要通过双写、灰度、清理才能安全下线。所以设计初期就要**评估好哪些 key 需要跨 key 操作**。

---

**第四部分:批量操作优化（更推荐的方案）**

大多数场景下，`mget` 报 `CROSSSLOT` **不是必须要求强原子性**，只是想"一次拿多个 key 减少 RTT"。这时候**pipeline 按 slot 分组**才是最佳实践，比 hash tag 更灵活。

**方案一：客户端按 slot 分组 + pipeline**

思路：客户端本地也维护一份 slot → node 映射（Redis Cluster 客户端如 Jedis、Lettuce、redis-py-cluster 都内置了），拿到一批 key 后：

1. 对每个 key 计算 CRC16 → 得到 slot；
2. 按 slot 分组，每组 key 落在同一节点；
3. 对每个节点用 **pipeline 批量发送**；
4. 并发发到多个节点，客户端合并结果返回。

```java
// Redisson 示例：底层自动做分组
RBatch batch = redisson.createBatch();
for (String key : keys) {
    batch.getBucket(key).getAsync();
}
BatchResult result = batch.execute();
```

**优点**：

- 网络 RTT 只从 N 次降到"节点数"次（通常 3\~10 次），性能接近 mget；
- **无需 hash tag**，key 自然分布，不会有热点；
- 客户端库通常已经封装好，业务代码几乎无感。

**缺点**：**非原子**，如果需要事务性/一致性视图，pipeline 满足不了。

**方案二:Redis Cluster Proxy / 集群客户端支持的 `MGET`**

有些客户端（如 Lettuce）或代理层（如 Codis、Twemproxy、Redis Cluster Proxy）会**自动把跨 slot 的 mget 拆成多条子 mget 并行发送**，对业务透明。

**方案三：如果必须原子，才用 hash tag**

只有确实需要**原子读、事务、Lua 脚本**跨多个 key 的场景，才考虑用 hash tag 强制同 slot。

**方案四:合并存储结构**

有时候多个 key 是因为设计不合理才拆开的。比如：

```
user:1001:name
user:1001:age
user:1001:email
```

这三个 key 本质是一个 User 对象的三个字段，应该合并成一个 **Hash**：

```
HGETALL user:1001
```

一次命令拿全，不存在 `CROSSSLOT` 问题，还省内存（Hash 小于 128 字段时用 listpack 编码，比多个 String 省得多）。

---

**第五部分：其他常见问题**

**1. Lua 脚本的 `CROSSSLOT`**

`EVAL script 2 key1 key2 ...` 里 `KEYS` 数组的所有 key 必须同 slot，否则报错。**且 `redis.call('get', 'key_not_in_KEYS')` 里访问的 key 也必须同 slot**——所以 Lua 脚本里通过 `KEYS` 显式声明所有会访问的 key 是最佳实践。

**2. 事务 (`MULTI/EXEC`) 的 `CROSSSLOT`**

事务里所有 key 也必须同 slot。跨 slot 的分布式事务在 Cluster 下不支持，只能用应用层补偿。

**3. `SCAN` 是安全的**

`SCAN` 只扫描单个节点，客户端需要**遍历所有 master 节点**分别 SCAN。集群客户端一般已经封装好 `cluster.scan()` 方法。

**4. 集群模式下慎用 `KEYS *`**

`KEYS *` 只扫当前连接的节点，返回不完整。永远用 `SCAN`。

---

**面试收尾一句话：**

`CROSSSLOT` 是 Redis Cluster 分片模型的必然产物，**hash tag 是"强制同 slot 换原子性"的机制，pipeline 分组是"接受非原子换均匀分布"的机制**。生产上默认用 pipeline，只有真需要事务/Lua 时才用 hash tag，同时警惕 tag 粒度过粗导致的数据倾斜。**记住一个原则：hash tag 是精确制导武器，不是万能开关**——用得多了，Cluster 就退化成一个假装分片的单机 Redis。
