# OS-IO 篇

> 主题：IO 端口（特权指令）· 陷入内核三入口的同步/异步 · 时钟中断 · vDSO · 系统调用优化 / 异常缓解 / 中断不可控。

### **什么是 IO 端口**

x86 架构里，CPU 访问外设有两种方式：

- **端口映射 IO（Port-mapped IO）**：外设的寄存器被编入一个独立的 "IO 地址空间"（共 65536 个端口，0x0000~0xFFFF），用专门的指令 `in`、`out`（以及 `ins`、`outs`）访问。
- **内存映射 IO（MMIO）**：把设备寄存器映射到普通内存地址空间，用 `mov` 等普通指令访问。现代设备（如显卡、NVMe、网卡）多用这种方式。

"操作 IO 端口" 指的是第一种。

### **举例**

- 读写键盘控制器：端口 0x60、0x64
- 老式串口 COM1：端口 0x3F8
- PCI 配置空间：端口 0xCF8、0xCFC
- 可编程中断控制器（PIC）、定时器（PIT）、CMOS/RTC 等

示例（汇编）：

```asm
mov dx, 0x3F8   ; 串口端口号
mov al, 'A'
out dx, al      ; 向串口发送一个字节
```

### **为什么是特权指令**

如果用户程序能随意执行 `in`/`out`，就能直接操控磁盘控制器、网卡、中断控制器等，绕过操作系统的保护与隔离，甚至破坏整个系统。因此 CPU 规定：

- 在 Ring 0（内核态）可以随意执行；
- 在 Ring 3（用户态）执行会触发通用保护异常（#GP），由内核处理（通常杀掉进程）。

用户程序想访问硬件，只能通过系统调用，请内核（驱动）代为操作。

补充：Linux 提供了 `ioperm()` / `iopl()` 系统调用，让有 root 权限的进程获得特定端口的访问许可（内核通过 TSS 里的 IO 权限位图放行），但这是内核授权后的例外，默认用户态不可直接访问。





### **同步（异常、系统调用）**

事件是执行某条指令的直接结果，发生的位置是确定的、可复现的。

- 缺页：执行 `mov rax, [addr]` 时访问了未映射的页，就在这条指令上触发。
- 除零：执行 `div` 指令时除数为 0。
- 系统调用：执行 `syscall` / `int 0x80` 指令时主动陷入内核。

同样的程序、同样的数据再跑一遍，会在同一条指令处再次触发。CPU 处理完后，可以重新执行出错的指令（如缺页）或跳到下一条指令继续（如系统调用）。

### **异步（中断）**

事件来自 CPU 之外的硬件，发生的时刻与当前执行的指令没有因果关系。

- 时钟中断：定时器到时间就发信号，此刻 CPU 可能正在执行任何一条指令。
- 网卡收包：数据包什么时候到达，由外部网络决定。

CPU 通常在**一条指令执行完毕后**检查是否有中断请求，有就暂停当前程序，转去执行中断处理程序，处理完再回到被打断的下一条指令。被打断的程序对此毫无察觉，也无法预测它何时发生。

### **一个直观对比**

| 对比项 | 同步（异常/系统调用） | 异步（中断） |
|---|---|---|
| 触发源 | 当前正在执行的指令 | 外部设备、时钟 |
| 发生时机 | 可预测、可复现 | 不可预测 |
| 与当前进程的关系 | 通常是当前进程自己引起的 | 通常与当前进程无关 |

因此，处理中断时内核不能假设它是"当前进程"造成的，而处理缺页、系统调用时则是在替当前进程服务。这也是中断处理要尽量快速、不能随意睡眠的原因之一。

### **时钟中断：每秒上百次陷入内核，为什么不算系统调用**

"陷入内核"只是描述 CPU 从用户态切到内核态这个动作，系统调用、异常、中断三条路都会造成这种切换；时钟中断属于第三种。

- **谁发起**：硬件定时器到点发信号，不是程序主动请求，程序对此刻在跑什么指令完全不知情。
- **频率**：Linux 内核有时钟节拍（tick），常见 100 / 250 / 1000 Hz，即每秒 100~1000 次陷入内核。
- **它干什么**：更新系统时间（jiffies）；给当前进程的时间片扣减一个 tick、统计 CPU 用时；检查是否有到期的定时器；时间片用完就设置"需要重新调度"标志，中断返回前切换到别的进程。
- **为什么重要**：这是**抢占式调度的基础**——即使某个进程死循环、从不主动让出 CPU，时钟中断也会定期把控制权交回内核，内核据此决定是否换人运行。
- **为什么不算系统调用**：通常说"一次系统调用有开销"，指程序主动调用带来的切换；时钟中断带来的切换是系统后台一直在发生的，程序没调用任何东西也会发生。所以统计一个进程的系统调用次数时，不应把时钟中断算进去——它只是内核在背后计时和调度。



### **知识点**

**vDSO（virtual Dynamic Shared Object，虚拟动态共享对象）：内核在进程启动时映射进用户空间的一小段只读代码和数据，让 `gettimeofday`、`clock_gettime` 等调用在用户态直接完成。**

- 它是什么：内核生成的小型共享库，没有磁盘文件，每个进程自动获得一份，由 glibc 自动找到并使用。
- 包含什么：一段只读代码（实现取时间等函数）和一块内核持续更新、用户态只读的数据页（时间基准）。
- 怎么工作：用户态读取这块数据，再用 `rdtsc` 读 CPU 计数器，自己算出时间，不执行 `syscall`，不切换到内核态。
- 为什么需要：读时间极其频繁，而且只是读数据，用真正的系统调用得不偿失。
- 为什么安全：数据对用户态只读，读时间也不涉及特权资源。

### **知识点场景**

**场景 1：高频取时间**
日志时间戳、性能计时、超时判断等每秒调用成千上万次，vDSO 让每次开销降到几十纳秒。

**场景 2：用 strace 验证**
循环调用 `clock_gettime`，`strace` 里看不到对应的系统调用，说明没有陷入内核。

**场景 3：面试常问**
"哪些系统调用不陷入内核？"答：vDSO 提供的 `gettimeofday`、`clock_gettime`、`time` 等。




### **系统调用可优化,异常与中断只能缓解或无法控制。下面逐点解释。**

### **一、系统调用的优化手段**

系统调用的开销主要来自用户态/内核态切换、参数检查,以及数据在内核与用户空间之间的拷贝。以下四种手段分别针对这几类开销。

**1. 批量:`writev`**
`writev` 属于 scatter/gather I/O(分散/聚集 I/O)。若要发送多段分散在不同内存中的数据(如协议头加正文),逐个调用 `write` 就要多次陷入内核。`writev` 一次传入一个 `iovec` 数组,只触发一次系统调用就把所有片段写出,既省去多次切换,也避免先把片段拼接到一块连续缓冲区里。对应的读操作是 `readv`。`sendmmsg`/`recvmmsg` 和 io_uring 的批量提交也是同一思路。

**scatter/gather 拆开看**:gather(聚集)是写——数据分散在内存多块,一次调用把它们按顺序"聚集"成连续输出;scatter(分散)是读——连续读入的数据按顺序"分散"填进多个缓冲区,对应 `readv`。它解决的问题很具体:发一个"协议头+元数据+正文"的报文,三次 `write` 是三次系统调用(还可能被 TCP 拆成多个小包),先拼进大缓冲区又得多一次内存拷贝;`writev` 一次调用、不拼接。

**四个细节**:① 返回的是**实际传输总字节数**,可能小于请求量(部分写),剩余部分要自己处理;② 单次 `iovec` 数量有上限 `IOV_MAX`(Linux 常为 1024);③ 带偏移的 `preadv`/`pwritev`、网络上的 `sendmsg`/`recvmsg` 同样走 iovec 接口;④ 网卡层面的 **scatter-gather DMA** 能直接从多块内存拼包发送——这正是 `sendfile` 配合它再省一次 CPU 拷贝的硬件基础。

**2. 复用:epoll**
传统多连接服务器要对每个 fd 轮询或调用 `select`/`poll`。这两者每次都要把整个 fd 集合拷进内核,再线性扫描,复杂度为 O(n)。epoll 把关注的 fd 一次性注册到内核的红黑树中,事件就绪时放入就绪链表,`epoll_wait` 只返回就绪的 fd。这样一个线程就能管理成千上万个连接,调用次数和扫描开销都大幅减少,这就是 I/O 多路复用。

**3. 避免拷贝:`sendfile`**
常规的"读文件再发网络"流程是:磁盘 → 内核页缓存 → 用户缓冲区 → 内核 socket 缓冲区 → 网卡,发生两次 CPU 拷贝和多次上下文切换。`sendfile` 让数据直接在内核内部从页缓存送到 socket,不经过用户态,这就是零拷贝。配合支持 scatter-gather 的网卡,还能省掉页缓存到 socket 缓冲区的那次拷贝。类似的还有 `splice`、`mmap`。

**4. vDSO**
vDSO(virtual dynamic shared object)是内核映射到每个进程地址空间的一小段共享库。对 `gettimeofday`、`clock_gettime` 这类只读内核数据、不需要特权操作的调用,用户程序可以直接在用户态读取内核维护的时间数据,完全不用陷入内核,开销从几百纳秒降到几十纳秒。

### **二、异常:只能缓解**

这里的异常主要指缺页异常(page fault)。它由访问未映射或被换出的内存触发,是程序运行中不可完全消除的事件,只能降低发生频率或代价。

- **锁页(`mlock`)**:把关键内存锁定在物理内存中,禁止被换出到磁盘,避免因换入产生的严重缺页(major fault),让延迟更稳定。
- **大页(HugePages)**:用 2MB 或 1GB 页代替 4KB 页。同样的内存需要的页表项和 TLB 条目大幅减少,缺页次数和 TLB miss 都随之降低。
- **预读(readahead / `madvise` / `MAP_POPULATE`)**:提前把数据加载进内存或预先建立映射,把缺页的代价挪到启动阶段或后台完成,运行时就不会被阻塞。

### **三、中断:不可控**

中断由硬件(网卡、磁盘、时钟等)异步触发,发生的时机和频率由外部事件决定,应用程序无法预测,也无法彻底避免。它会打断当前执行的代码,造成抖动。能做的只有间接的系统层面调整,例如中断亲和性(`smp_affinity`)、网卡中断合并、NAPI 或把关键核心隔离出来(`isolcpus`),但这些属于配置层面的缓解,并不是在程序里能"优化"掉的。
