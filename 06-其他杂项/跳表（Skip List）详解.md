# 跳表（Skip List）详解

> 跳表是一种**基于多层有序链表**的概率性数据结构，在 O(log N) 时间内完成查找、插入、删除，且**实现远比红黑树简单**。Redis 的 ZSet、LevelDB/RocksDB 的 MemTable、Java 的 `ConcurrentSkipListMap` 都基于它。

---

## 一、定义与直观理解

**专业定义：** 跳表由 William Pugh 于 1989 年提出。它由若干层链表组成，**每一层都是下一层的"快速通道"**——底层（L1）包含全部元素且有序，越往上元素越稀疏。查找时从最高层开始向右走，走过头就降到下一层，用"空间换时间"把链表的 O(N) 查找加速到 O(log N)。

**通俗理解：** 普通链表查一个元素只能一个个往后数（O(N)）。跳表相当于给链表修了"高架桥"——底层是普通公路（全量元素），上层是只停大站的高速路。查目标时先走高架桥快速跨越中间的小站，接近目标再下到普通公路精确找到。每多一层，跨越能力翻倍，所以层高是 log 级别的。

---

## 二、结构

```
最高层 L3:  head ──→ 1 ────────────────→ 6 ──────→ NIL
L2:        head ──→ 1 ────→ 3 ────────→ 6 ──→ 9 ─→ NIL
L1(底层):  head ──→ 1 ──→ 2 ──→ 3 ──→ 5 ──→ 6 ──→ 9 ──→ 12 ─→ NIL
```

| 组成 | 说明 |
|------|------|
| **节点（Node）** | 每个节点保存一个元素，并有一个**变长 level 数组**，数组第 i 项存放第 i 层的 forward 指针和 span |
| **层（Level）** | 每层是一条有序链表；底层包含全部节点，越往上越稀疏 |
| **头节点（header）** | 拥有最大层数，是每层链表的起点 |
| **NIL** | 每层的尾部哨兵 |
| **跨度（span）** | 某层节点到下一个节点"跳过了多少个底层节点"，Redis 用它实现 O(1) 排名 |

---

## 三、三大操作

### 1. 查找（Search）— O(log N)

从最高层 header 开始：
1. 当前层向右走，只要下一节点 key **≤ 目标**，就继续向右
2. 走不动（下一节点 key > 目标或 NIL）→ 下降到下一层
3. 到底层仍没找到 → 不存在

每往下一层，搜索区间大致减半，所以走的总步数是 **O(log N)**。

### 2. 插入（Insert）— O(log N)

1. 先**查找插入位置**，沿途记录每层的前驱节点（update 数组）
2. **随机决定新节点的层高**：以概率 p（Redis 用 1/4）往上多一层，Redis 最大 **32 层**
3. 从底层到顶层，把新节点插入每层的前驱之后，更新 forward 和 span

> 随机层高是跳表的关键：它保证节点层高服从几何分布，宏观上让链表近似平衡，不需要像红黑树那样做旋转/染色调整。

### 3. 删除（Delete）— O(log N)

1. 查找目标节点，记录每层前驱
2. 从每层链表中摘除该节点，更新 forward 和 span
3. 若最高层空出（只剩头尾），则整体层数 -1

---

## 四、为什么能 O(log N)：概率 vs 强制平衡

| 方案 | 平衡方式 | 代价 |
|------|---------|------|
| 红黑树/AVL | **强制平衡**：每次插入删除后旋转、染色调整 | 实现复杂、调整开销大 |
| 跳表 | **概率平衡**：随机层高，天然近似平衡 | 多耗一部分指针内存 |

跳表不追求严格平衡——它接受"偶尔不均衡"，用概率保证整体层高是 log 级别。`p=1/4` 时，期望每层节点数是上一层的 1/4，层数期望为 `log_{1/p} N`。

## 五、Redis ZSet 中的跳表

### 节点结构

```c
typedef struct zskiplistNode {
    sds ele;                    // member（元素）
    double score;               // 分数
    struct zskiplistNode *backward;   // 后退指针：从尾到头遍历
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针
        unsigned long span;           // 跨度：到下一个节点的距离
    } level[];                  // 每层一组 forward + span
} zskiplistNode;
```

### Redis 的具体设定

- **随机层高概率 p = 1/4**，最大层高 **32**（`ZSKIPLIST_MAXLEVEL`）
- 分数（score）相同时按 member 的**字典序**排序
- **span 字段**是关键设计：记录当前节点到下一节点的底层距离，让 `ZRANK` / `ZREVRANK`（查排名）达到 **O(log N)**，不需要遍历全表数排名

### 为什么跳表 + 哈希表组合

ZSet 实际是「**跳表 + dict 哈希表**」双结构：

| 结构 | 作用 | 支撑的命令 |
|------|------|-----------|
| **哈希表（dict）** | O(1) 定位 member → score | `ZSCORE`、`ZINCRBY` 先查后改 |
| **跳表** | 有序存储，支撑范围查询 | `ZRANGE`、`ZRANGEBYSCORE`、`ZRANK` 排行榜 |

### 为什么不用红黑树 / 平衡树

1. **范围查询更简单**：跳表找到起点后顺着 forward 指针一路向右就能遍历整个区间；红黑树范围查询要先中序遍历收集有序序列，实现复杂
2. **实现简单**：跳表插入/删除只改局部指针，没有旋转、染色、父子指针调整
3. **天然近似平衡**：随机层高免去显式平衡操作
4. **取舍**：跳表比红黑树多耗内存（多层指针），但 Redis 排行榜场景"范围操作 + 排名"是核心，内存换来的实现简洁和区间能力是值得的

## 六、跳表的其他应用

| 场景 | 用途 |
|------|------|
| **LevelDB / RocksDB** | MemTable 的默认实现，写内存后有序落盘 |
| **HBase** | MemStore 内部有序结构 |
| **Kafka** | `ConcurrentSkipListMap` 维护时间戳索引，支持范围查询 |
| **Java 并发库** | `ConcurrentSkipListMap` / `ConcurrentSkipListSet`，跳表天然适合无锁并发读 |

## 面试话术

> "ZSet 底层是 **跳表 + 哈希表**的组合。哈希表负责 O(1) 精确查分数（ZSCORE），跳表负责有序存储和范围查询（ZRANGE、ZRANGEBYSCORE）。跳表比红黑树更适合这里，主要是**范围查询方便**——顺着 forward 指针就能遍历区间，而红黑树范围查询要走中序遍历；而且跳表**实现简单**，随机层高天然近似平衡，不需要旋转调整。Redis 还通过 span 字段让排名查询 ZRANK 达到 O(log N)。"

---

## 通俗理解

跳表就是给有序链表修了几层"高架桥"。底层是普通公路，停靠每一个站（全部元素）；上层高速路只停大站（部分元素）。查询时先在高架桥上快速飞越大部分路程，接近目标再下到普通公路精确定位。**用多修几座桥（指针内存）的代价，把"挨个数"变成"跳着找"，查找从 O(N) 降到 O(log N)。**
