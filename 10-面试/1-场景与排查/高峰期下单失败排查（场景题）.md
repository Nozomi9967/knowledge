# 高峰期下单失败排查（场景题）

> **面试题：** 服务高峰期时用户下单失败，请分析原因（Java 方向）。
>
> **一句话破题：** 高峰期下单失败通常是**资源耗尽或链路阻塞**导致的，原因集中在线程、数据库连接、库存热点、下游超时和事务过长这几方面。

---

## 一、总体思路

下单链路往往同时涉及网关、订单、库存、优惠券、支付、风控等多个服务，流量激增时**任何一个环节出现瓶颈，都会以「下单失败」的形式暴露出来**。所以排查要分层：**先从应用层的线程和连接入手，再看数据库和下游依赖**。

下面按「最可能的顺序」列出七类原因。

---

## 二、七类常见原因

### 1. Web 容器线程池被打满

Spring Boot 默认使用内嵌 Tomcat，**最大线程数默认 200**。如果下单接口内部存在慢调用——比如同步调用远程服务、等待数据库锁——线程会长时间被占用。新请求进来时没有空闲线程可用就会排队，**超过 `accept-count` 后直接被拒绝**，前端表现为超时或 502、503。

**排查：** 用 `jstack` 或 Arthas 的 `thread` 命令，看大量线程是否阻塞在同一处。如果线程大多处于 `TIMED_WAITING` / `WAITING` 且都卡在某个远程调用或锁上，基本可以定位。

### 2. 数据库连接池耗尽

HikariCP **默认最大连接数通常是 10**。高峰期若每个下单请求都要占用连接执行多条 SQL，再加上事务持有连接时间较长，连接很快用完。此时新请求在 `getConnection` 时等待，**超过 `connectionTimeout`（默认 30 秒）后抛异常**。

> [!warning] 连接数要按实例数放大
> 连接池只控制**单个实例**的连接数。多台实例同时部署时，数据库总连接数是**各实例之和**，可能超过数据库的 `max_connections` 上限。

### 3. 热点库存的行锁竞争

秒杀或限时促销时，大量请求同时扣减同一商品库存，会在**同一行记录上竞争行锁**，导致事务排队执行、响应时间迅速拉长。如果「先查询再更新」，还可能出现并发下的**超卖或大量更新失败**。

改进：把扣减改为**条件更新**，判断和扣减合并成一条语句，避免并发读后写：

```java
@Update("UPDATE stock SET available = available - #{qty} " +
        "WHERE sku_id = #{skuId} AND available >= #{qty}")
int deductStock(@Param("skuId") Long skuId, @Param("qty") int qty);
```

返回值为 0 说明库存不足，直接失败即可。极端热点商品还可以把**预扣放到 Redis**（Lua 脚本原子执行、再异步落库），或对库存做**分段拆分**分散锁竞争。

### 4. 下游服务超时与雪崩

下单流程通常会调用优惠券校验、风控、价格计算、支付预下单等服务。若其中某个服务高峰期变慢，而调用方**没有设置合理超时或没有熔断降级**，线程会被持续占用，最终拖垮整个下单服务。

对策：为每次远程调用设置明确的**连接超时和读取超时**（例如 `connectTimeout` 500ms、`readTimeout` 1~2s），并用 Sentinel / Resilience4j 配置熔断和降级。**非核心能力（积分、推荐、营销标签）在高峰期直接降级跳过**，不阻塞主下单流程。

### 5. 事务范围过大

很多项目在 `@Transactional` 方法里同时包含**远程调用、消息发送甚至文件操作**，导致数据库连接和行锁在整个远程调用期间被持有，既放大了锁持有时间，也加剧连接池耗尽。

更合理：**只把数据库写操作放进事务**，远程调用放在事务之外，结合本地消息表或 MQ 实现最终一致性。（类/方法上 `@Transactional` 的覆盖关系见 [[@Transactional 类上 vs 方法上]]）

### 6. 限流与削峰缺失

若系统没有入口限流，突发流量会直接打到后端各服务。即使单请求很快，总量超过承载能力后各项指标都会恶化。常见做法：

- 网关层做**令牌桶 / 漏桶限流**；
- 对同一用户的**重复提交做幂等校验**；
- 用**消息队列把下单请求异步化**，消费者按能力匀速处理，前端返回"排队中"。

### 7. JVM 与基础设施层面

- 堆内存配置偏小或对象创建过多时，高峰期容易**频繁 Full GC**，造成几百毫秒甚至数秒停顿，期间所有请求超时（见 [[Full GC频繁导致CPU 100%的完整排障流程]]）。
- **Redis 连接池耗尽、Redis 大 Key 阻塞、MQ 消息积压、Nginx/网关上游客超时参数过小**等，也会在高峰期集中出现。

## 三、排查建议（落地顺序）

1. **先看监控**：QPS、响应时间分位数（P50/P95/P99）、线程池活跃数、连接池等待数、GC 次数——确认瓶颈在哪一层。
2. **再看链路**：结合链路追踪（SkyWalking / Zipkin）找出耗时最长的环节。
3. **对照异常类型**判断哪类资源先出问题：

| 异常 | 指向 |
|------|------|
| `SQLTimeoutException` | 数据库慢 / 锁等待 |
| `CannotGetJdbcConnectionException` | 连接池耗尽 |
| `SocketTimeoutException` | 下游超时 |
| `RejectedExecutionException` | 线程池拒绝 |

**治理优先级：** 先做**限流和降级保住核心链路** → 再通过**缩短事务、优化库存扣减、调整超时熔断参数**提升吞吐 → 最后再考虑**扩容和架构层面的异步化改造**。

---

## 四、口述版参考答案

> 高峰期下单失败，我一般从「资源耗尽」和「链路阻塞」两个方向找原因。最先怀疑的是**线程和连接**：Tomcat 默认 200 线程，接口里有慢调用就会把线程占满，超过 accept-count 直接拒绝；HikariCP 默认才 10 个连接，事务一长连接池就耗尽，新请求等 30 秒超时。然后是**数据库热点**：秒杀时大家抢同一行库存的行锁，事务排队，得改成条件更新 `available >= qty` 一条语句扣减。再就是**下游雪崩**，优惠券、风控这些调用没设超时和熔断，一个慢就拖垮整条链路，非核心的积分推荐高峰期直接降级。还有**事务范围过大**，把 RPC 包进 `@Transactional` 会让连接和锁一直不释放。最后是**限流削峰缺失**和 **JVM 层面**，比如频繁 Full GC 造成停顿。排查上我先看监控的 QPS、P99、线程池活跃数和连接池等待数定位层级，再用 SkyWalking 拆链路，对照异常类型——`CannotGetJdbcConnectionException` 是连接池、`RejectedExecutionException` 是线程池、`SQLTimeoutException` 是慢 SQL 或锁。治理顺序是先限流降级保核心，再缩短事务优化库存，最后扩容异步化。
