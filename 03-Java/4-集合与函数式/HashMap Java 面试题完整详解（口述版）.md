下面这套题目从基础原理到底层源码、从并发问题到实战场景，覆盖了 HashMap 面试中几乎所有高频考点。回答部分我都尽量用"口语化"的方式来讲，让你在面试现场能够自然地说出来，而不是像背书一样生硬。

---

## **一、基础概念篇**

### **Q1：请你简单介绍一下 HashMap。**

**回答：**
好的。HashMap 是 Java 集合框架里最常用的一个类，它实现了 Map 接口，用来存储键值对。它的特点我可以概括成几点：第一，它是基于哈希表实现的，查询和插入的平均时间复杂度都是 O(1)；第二，它是无序的，也就是说你插入的顺序和遍历出来的顺序是不一致的；第三，它允许 key 和 value 都为 null，但是 key 为 null 的只能有一个；第四，它是**非线程安全**的，如果在多线程环境下使用，可能会出问题，这种情况下我们一般会用 ConcurrentHashMap。

在 JDK 1.7 的时候，HashMap 底层是**数组加链表**的结构；到了 JDK 1.8，为了优化极端情况下链表过长导致查询效率退化的问题，引入了**红黑树**，当链表长度超过 8 并且数组长度大于等于 64 的时候，链表就会转化为红黑树。

---

### **Q2：HashMap 和 HashTable、ConcurrentHashMap 有什么区别？**

**回答：**
这三个都是键值对存储的容器，但用途和特性差别挺大的。

**HashMap** 是非线程安全的，允许 key 和 value 为 null，性能最好，适合单线程或者不需要保证线程安全的场景。

**HashTable** 是早期 JDK 就有的，它是线程安全的，但是它的做法非常粗暴——直接在方法上加 `synchronized`，也就是说整个表都被锁住了，并发性能非常差。而且它不允许 key 或 value 为 null，现在基本已经被淘汰了。

**ConcurrentHashMap** 是并发场景下的首选。JDK 1.7 的时候它用的是**分段锁**（Segment），把整个数组分成若干段，每段独立加锁；JDK 1.8 之后改成了 **CAS + synchronized** 的组合，锁的粒度进一步细化到了数组的每个桶（Node），并发性能大大提升。它同样不允许 null。

## **二、底层原理篇**

### **Q3：HashMap 的底层数据结构是怎样的？**

**回答：**
JDK 1.8 之后，HashMap 底层是**数组 + 链表 + 红黑树**的组合结构。

数组是 HashMap 的主体，我们叫它 `table`，也叫哈希桶数组。当我们 put 一个元素的时候，会先根据 key 的 hash 值计算出它应该落在数组的哪个位置。如果这个位置没有元素，就直接放进去；如果有元素了，说明发生了**哈希冲突**，这时候就用链表把冲突的元素挂在一起，形成一个链表结构。

当链表越来越长的时候，查询效率就会退化，因为链表查找是 O(n) 的。所以 JDK 1.8 做了个优化：当链表长度**超过 8**，并且数组长度**大于等于 64** 的时候，链表就会转成**红黑树**，红黑树的查询是 O(log n)，效率高很多。反过来，如果红黑树节点数减少到**小于等于 6**，它又会退化回链表。

---

### **Q4：为什么链表转红黑树的阈值是 8？为什么退化阈值是 6？**

**回答：**
这个问题其实源码注释里有写。首先，理想情况下，如果 hash 函数分布得足够均匀，一个桶里链表长度达到 8 的概率非常低，大概是**千万分之一**（服从泊松分布）。所以设成 8，是一个非常保守、几乎不会误触发的值。

那为什么退化用 6 不用 7 呢？这是为了**避免频繁抖动**。你想，如果两个阈值都是 8，那么在临界点上稍微增删一个元素，就会来回在链表和红黑树之间转换，代价很高。中间留个 6 到 8 的缓冲区，可以避免这种抖动。

---

### **Q5：HashMap 的 put 方法执行流程是怎样的？**

**回答：**
put 方法的执行流程大概可以分成这几步，我按顺序讲一下：

**第一步**，先判断数组 table 是不是空的，如果是空的，就先调用 `resize()` 进行**初始化**，默认容量是 16。

**第二步**，计算 key 的 hash 值。注意这里的 hash 值不是直接用 `key.hashCode()`，而是做了一个扰动处理——把 hashCode 的**高 16 位和低 16 位做异或**，这样做的目的是让 hash 分布更均匀，减少冲突。

**第三步**，用 `(n - 1) & hash` 计算出这个 key 应该落在数组的哪个下标上。这里用位运算代替取模，效率更高，前提是数组长度必须是 2 的幂。

**第四步**，看这个位置有没有元素。如果**没有**，直接创建一个新节点放进去。如果**有**，就要进一步判断：
- 如果这个节点的 key 和要插入的 key **相等**（equals 判断），那就是更新操作，把 value 覆盖掉。
- 如果这个节点是**红黑树节点**，就走红黑树的插入逻辑。
- 如果是**链表节点**，就遍历链表，找到就更新，没找到就在链表尾部插入。插入之后判断链表长度是不是超过 8，超过的话就尝试转红黑树。

**第五步**，插入完成后，判断当前元素总数是不是超过了阈值（容量 × 负载因子，默认是 16 × 0.75 = 12），超过了就触发**扩容**。

---

### **Q6：HashMap 是怎么计算 hash 值的？为什么要做扰动？**

**回答：**
HashMap 的 hash 方法源码大概是这样：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

它把 key 的 hashCode 拿出来之后，和它自己**右移 16 位**的结果做**异或**。

为什么要这么做呢？因为最终确定下标的公式是 `(n - 1) & hash`，也就是数组长度减一和 hash 做与运算。数组长度一般不大，比如 16，那 `n - 1` 就是 15，二进制是 `1111`，只有低 4 位起作用。这就意味着，如果只用原始 hashCode，那 hashCode 的**高位信息就完全被浪费了**，只要低位相同，就一定冲突。

所以通过高 16 位和低 16 位异或，把高位的特征也"混"到低位里去，让 hash 分布更均匀，冲突就会更少。这个技巧叫**扰动函数**。

---

### **Q6：HashMap 的 get 方法执行流程是怎样的？**

**回答：**
get 方法的逻辑和 put 是镜像关系，我来说一下：

**第一步**，先判断 table 是不是空的或者长度为 0，如果是，直接返回 null。

**第二步**，计算 key 的 hash 值。这里用的 hash 函数和 put 的时候**完全一样**——同样的扰动处理，因为只有 hash 相同，才能定位到同一个桶。

**第三步**，用 `(n - 1) & hash` 算出下标，定位到数组的某个位置。

**第四步**，检查这个位置的第一个节点：
- 如果这个节点的 hash 值和要查找的 hash 相等，并且 key 也相等（equals 判断），那就直接返回 value。
- key 为 null 的情况是单独处理的，因为 null 的 hashCode 固定为 0，也是走同样的比较逻辑。

**第五步**，如果第一个节点不是目标，再看这个节点是不是红黑树节点。如果是，就走红黑树的查找逻辑，O(log n)。

**第六步**，如果不是红黑树，那就是链表，遍历链表逐个比对 hash 值和 key 的 equals，找到就返回 value，遍历完都没找到就返回 null。

**整体来看**，get 的平均时间复杂度是 O(1)，最坏情况（全部冲突形成链表）是 O(n)，但 JDK 1.8 有红黑树兜底，最坏是 O(log n)。

---

### **Q7：HashMap 是怎么计算 hash 值的？为什么要做扰动？**

**回答：**
这个问题主要是为了两个目的：**计算效率**和**分布均匀**。

第一个是效率。计算下标的时候，本来应该用 `hash % n`，但取模运算比较慢。如果 n 是 2 的幂，那么 `hash % n` 就等价于 `hash & (n - 1)`，位运算比取模快得多。

第二个是分布均匀。当 n 是 2 的幂时，`n - 1` 的二进制形式是全 1，比如 16 - 1 = 15 = `01111`，这样做与运算的时候，hash 的每一位都能参与，最终下标的分布就更均匀。反之，如果 n 不是 2 的幂，比如 n = 10，`n - 1 = 9 = 1001`，那中间那两个 0 会让某些位置永远取不到，导致冲突加剧。

所以即使你在构造 HashMap 的时候传入的初始容量不是 2 的幂，HashMap 内部会通过一个 `tableSizeFor` 方法，把它**向上取整到最近的 2 的幂**。

## **三、扩容机制篇**

### **Q8：HashMap 是怎么扩容的？**

**回答：**
HashMap 扩容的核心方法是 `resize()`。触发的条件是：**元素数量超过了阈值**（也就是容量 × 负载因子）。

扩容的时候，会把数组容量**扩大为原来的两倍**，同时阈值也翻倍。然后需要把原数组里的所有元素**重新放到新数组里**，这个过程叫 rehash。

JDK 1.8 在这里做了一个非常巧妙的优化。因为容量是 2 的幂，扩容后是原来的 2 倍，那么某个元素在新数组里的位置只有两种可能：**要么还在原来的位置，要么在"原位置 + 原容量"的位置**。

判断的方法也很巧妙：只要看这个元素 hash 值的那个**新增的高位 bit** 是 0 还是 1。如果是 0，就还在原位置；如果是 1，就在原位置加上旧容量的位置。这样就不用重新计算每个元素的 hash 了，效率高很多。

而且在链表迁移的时候，JDK 1.8 会用两个链表——一个 low 链表放留在原位的，一个 high 链表放要迁移的，遍历一遍就能完成拆分，也**避免了 JDK 1.7 头插法导致的循环链表问题**。

---

### **Q9：JDK 1.7 和 JDK 1.8 的 HashMap 有什么区别？**

**回答：**
主要有这么几个大的区别：

**第一，数据结构不同**。1.7 是数组 + 链表，1.8 增加了红黑树。

**第二，插入方式不同**。1.7 用的是**头插法**，也就是新节点插在链表头部；1.8 改成了**尾插法**。头插法有个问题，在并发扩容的时候可能形成**循环链表**，导致 CPU 100%。尾插法就没这个问题。

**第三，扩容时 rehash 的方式不同**。1.7 需要重新计算每个元素的 hash 值和下标；1.8 通过判断 hash 新增高位是 0 还是 1，直接确定新位置，效率更高。

**第四，hash 函数不同**。1.7 的扰动做了 4 次移位加 5 次异或，比较复杂；1.8 简化成一次高低 16 位异或，性能更好。

---

### **Q10：HashMap 的默认初始容量、负载因子分别是多少？为什么？**

**回答：**
默认初始容量是 **16**，负载因子是 **0.75**。

初始容量选 16，是一个折中——太小容易频繁扩容，太大又浪费内存。16 是个经验值，也刚好是 2 的幂。

负载因子 0.75 是**空间和时间的平衡**。如果设得太小，比如 0.5，那空间利用率就低，浪费内存；如果设得太大，比如 1.0，那哈希冲突就多，链表变长，查询效率下降。0.75 是一个经过实践验证的比较好的平衡点，从统计学上讲也是接近泊松分布最优的。

> [!note] 名词澄清：装填因子 = 负载因子
> **装填因子 = 负载因子 = load factor**，三者是同一个东西，别当成两个概念。默认 **0.75**，扩容阈值 = 容量 × 负载因子（如 16 × 0.75 = 12）；元素数超过阈值就触发 `resize()` 扩容，从而**降低冲突概率**。

### 补充：哈希冲突的四种解决方法

| 方法 | 做法 | 谁在用 |
|:---|:---|:---|
| **① 链地址法（拉链法）** | 冲突元素挂成**链表/树**，存在同一桶里 | **HashMap**（数组 + 链表 + 红黑树） |
| **② 开放地址法（开放定址）** | 冲突时按探测序列在**同一张表**里找空位（线性探测 / 二次探测 / 双重散列） | ThreadLocal、Redis 某些场景 |
| **③ 再哈希法** | 冲突后用**另一个哈希函数**重新算位置 `h2(key)` | 较少单独用 |
| **④ 公共溢出区** | 把冲突元素单独放到**溢出区**存放 | 少用 |

> [!tip] HashMap 用的是哪几种？
> 主体是 **① 链地址法**，长链表时靠**红黑树**兜底（树化阈值：链表长度 > 8 且数组长度 ≥ 64）；**扩容**（元素数超 容量×负载因子）也能降冲突概率。②③④ 是另外三种，笔试爱考区分，但 **HashMap 本体用链地址**。

## **四、并发与线程安全篇**

### **Q11：HashMap 是线程安全的吗？在多线程下会出现什么问题？**

**回答：**
HashMap 是**非线程安全**的，多线程下主要会有这几个问题：

**第一，数据丢失**。两个线程同时 put，如果它们的 key 恰好落在同一个桶，可能会互相覆盖，导致其中一个数据丢失。

**第二，JDK 1.7 下的死循环**。1.7 用头插法扩容，多线程并发扩容的时候可能会把链表构造成环，之后 get 操作就会陷入死循环，CPU 直接飙到 100%。这个问题在 1.8 尾插法之后解决了，但 1.8 依然不是线程安全的。

**第三，size 不准确**。size 字段没有加锁保护，多线程 put 之后 size 的值可能是错的。

如果要在并发场景下用，推荐用 `ConcurrentHashMap`，或者用 `Collections.synchronizedMap()` 包装一下（但性能不如前者）。

---

### **Q12：为什么 HashMap 的 key 一般用 String、Integer 这些不可变类？**

**回答：**
主要有两个原因：

**第一，保证 hashCode 稳定**。如果 key 是可变的，你 put 进去之后，如果外部又修改了它的字段，导致 hashCode 变了，那你再去 get 的时候，算出来的桶位置就不对了，永远也找不到这个元素了。

举个例子：`map.put(key, value)` 时 key.hashCode() 落在 index=5，后来你改了 key 的字段，hashCode 变了再 get 就落到 index=12 去了——index=5 里的数据还在，但再也找不到了。

**第二，避免 equals 判断出错**。同样地，可变对象修改后 equals 结果可能会变，导致 HashMap 的行为异常。

举个例子：key 的 hashCode 没变，数据还在 index=5 里，但你用原来的条件去 get，遍历到那个 entry 时 equals 比对不上了——明明有却找不到。反过来，有人用修改后的条件去 get，equals 对上了，返回了数据，但那并不是他 put 进去的 key，查到了不属于他的数据。

两者都指向同一个原则：**HashMap 内部靠 hashCode 定位桶，靠 equals 匹配节点，key 变了，坐标和身份都变了**。所以 key 必须不可变。

String、Integer 这些类都是 final 的、不可变的，一旦创建 hashCode 就固定了，非常适合做 key。

## **五、进阶与实战篇**

### **Q13：如果让你自定义一个类作为 HashMap 的 key，你需要注意什么？**

**回答：**
必须要做的就是**重写 `hashCode()` 和 `equals()` 方法**，而且这两个方法必须保持一致。

一致性的意思是：如果两个对象 `equals` 返回 true，那它们的 `hashCode` 必须相等。反过来不一定成立，hashCode 相等的两个对象 equals 可以不等，这就是所谓的哈希冲突。

如果不重写会怎样呢？默认继承 Object 的方法，equals 比较的是对象引用（内存地址），hashCode 也是根据内存地址算的。这样即使你两个对象字段完全一样，也会被 HashMap 认为是不同的 key，就会存进去两份，查也查不到。

另外，最好把这个 key 类设计成**不可变的**，就像上一题说的那样。

---

### **Q14：HashMap 的初始容量该怎么设置？**

**回答：**
如果你在创建 HashMap 的时候已经知道大概要存多少个元素，最好在构造函数里指定初始容量，**避免扩容**。

计算公式是：**`初始容量 = 预期元素数 / 负载因子 + 1`**，然后向上取到 2 的幂。

比如你要存 100 个元素，那 `100 / 0.75 ≈ 134`，向上取到 2 的幂就是 256，或者直接传 `(int)(100 / 0.75) + 1 = 134`，HashMap 内部会帮你调整到 256。

Guava 库里有个工具方法 `Maps.newHashMapWithExpectedSize()` 就是干这个的，可以直接用。

预设容量的好处是**避免多次扩容**，因为扩容涉及到整个数组的 rehash，代价比较大。

---

### **Q15：HashMap 遍历有哪些方式？哪种性能最好？**

**回答：**
主要有这几种遍历方式：

**第一种，`entrySet()`**。这是**推荐**的方式，一次遍历同时拿到 key 和 value，性能最好。

**第二种，`keySet()` 然后再通过 key 去 get**。这种方式其实遍历了两次——一次拿 key，一次通过 key 去查 value，性能最差。

**第三种，`values()`**。只需要 value 的时候用这个。

**第四种，Java 8 的 `forEach` 加 Lambda**，或者 `Stream API`。写法简洁，性能和 entrySet 差不多。

**第五种，`Iterator` 迭代器**。这是唯一能在遍历过程中**安全删除**元素的方式（用 `iterator.remove()`），其他方式在遍历中删除会抛 `ConcurrentModificationException`。

---

### **Q16：get 方法找不到元素时返回什么？怎么区分"key 不存在"和"value 就是 null"？**

**回答：**
`get()` 方法在 key 不存在的时候返回 null。但问题是，HashMap 允许 value 为 null，所以你光看返回值是分不清"key 不存在"还是"key 存在但 value 是 null"的。

要区分这两种情况，需要用 `containsKey()` 方法。如果 `containsKey` 返回 true 但 `get` 返回 null，说明 value 本身就是 null；如果 `containsKey` 返回 false，那就是 key 根本不存在。

这也是为什么在**并发场景**下推荐用 ConcurrentHashMap 的原因之一——ConcurrentHashMap 不允许 value 为 null，就是为了避免这种二义性。

---

### **Q17：讲一下红黑树的特点，为什么选红黑树而不是 AVL 树？**

**回答：**
红黑树是一种**自平衡的二叉搜索树**，它有五个特性：节点非红即黑，根节点是黑，叶子节点（NIL）是黑，红节点的子节点必须是黑（不能有两个连续红节点），任意节点到叶子的路径上黑节点数量相同。

这些规则保证了红黑树的最长路径不超过最短路径的 2 倍，也就是**近似平衡**，查询、插入、删除都是 O(log n)。

那为什么不用 AVL 树呢？AVL 树是**严格平衡**的，查询效率略高一点，但每次插入删除都可能需要多次旋转来维持平衡，**写入性能较差**。红黑树是"够用的平衡"，牺牲一点查询效率换来更好的写入性能，对于 HashMap 这种插入删除也很频繁的场景更合适。

## **六、场景题**

### **Q18：如果 HashMap 存了大量数据，性能突然下降，可能是什么原因？**

**回答：**
我会从这几个方向排查：

**第一，hash 冲突严重**。检查一下 key 的 hashCode 实现是不是太差，导致大量 key 落到同一个桶里，形成长链表或大红黑树。这时候查询就会退化。

**第二，频繁扩容**。如果初始容量设得太小，大量数据插入时会不断扩容，每次扩容都要 rehash 所有元素，非常耗时。可以在初始化时就指定合适容量。

**第三，key 用了可变对象**。如果 key 的 hashCode 被外部改动，会导致找不到已存在的元素，性能和正确性都会有问题。

**第四，并发问题**。多线程环境下用 HashMap 可能导致数据结构损坏，比如 1.7 的循环链表。这时候应该换成 ConcurrentHashMap。

**第五，内存不够**。如果堆内存不足，GC 频繁，也会让 HashMap 操作变慢，这个要看 JVM 监控。

### **Q19：一亿条数据放进 HashMap 会怎样？如何优化？**

**回答：**
直接放的话首先是**内存爆炸**。HashMap 每个 Node 除了 key 和 value，还有 hash、next 指针，光对象头和引用就要几十字节。一亿条 Node 大概要几个 GB 内存，很容易 OOM。

其次是**扩容开销巨大**。从 16 一路扩容到能容纳一亿的容量（大概 2 亿多），中间要扩容 20 多次，每次都要 rehash 全部数据，非常耗时。

优化方案：

**第一，预设容量**。直接构造 `new HashMap<>(1 << 28)`，避免频繁扩容。
**第二，如果内存实在放不下**，考虑用堆外存储、分片存储，或者上 Redis、RocksDB 这种外部存储。
**第三，评估是不是真的需要全部放内存**，很多场景其实用 LRU 缓存或者布隆过滤器就够了。
**第四，如果是并发场景**，用 ConcurrentHashMap，并合理设置并发级别。
