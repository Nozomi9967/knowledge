### 1. 驱动表关系

理解这个，先搞清执行顺序：

**`IN` 的执行逻辑：**

```sql
SELECT * FROM A WHERE A.id IN (SELECT B.id FROM B WHERE B.status = 1)
```

MySQL 在执行时，**通常先执行子查询**（`SELECT B.id FROM B WHERE B.status = 1`），把结果集算出来（假设结果是 1, 3, 5），然后外层查询等价变成：

```sql
SELECT * FROM A WHERE A.id IN (1, 3, 5)
```

这里子查询的结果 **B（结果集）** 是驱动表，**A** 是被驱动表。也就是说，**B 结果集的大小决定了外层的循环次数。** 所以当子查询结果集很小时，用 `IN` 性能很好；如果结果集大到几千几万行，驱动表就很大，性能下降。

**`EXISTS` 的执行逻辑：**

```sql
SELECT * FROM A WHERE EXISTS (SELECT 1 FROM B WHERE B.id = A.id)
```

执行时，**逐条遍历外层表 A**，每取一行 A 的数据，就去判断 EXISTS 子查询有没有返回结果。这里是 **A 是驱动表**，子查询是被驱动的（对每一行 A 去 B 里查一次）。

所以一个经典的选型口诀是：**小表驱动大表**。

- 子查询结果集小 → 用 `IN`（让子查询做驱动表）
- 外层表小 → 用 `EXISTS`（让外层表做驱动表）

**为什么不能反过来？** 因为 IN 的子查询结果不能被索引利用（它是物化成内存中的列表），而 EXISTS 的关联条件（`B.id = A.id`）可以利用 B 表上的索引，外层对 A 遍历一次、每次通过索引去 B 查找，效率很高。


### ❌ 反过来错误场景一：外层表小，你却用了 `IN`

假设：外层表 A 只有 10 条数据（极小），子查询 B 表有 1000 万条数据（极大）。

SQL

```
-- 错误示范：在外层表小的时候用了 IN
SELECT * FROM A WHERE A.id IN (SELECT B.id FROM B);
```

- **实际执行流程：** MySQL 会先执行子查询，尝试把 B 表的 1000 万条 `id` 查出来，并在内存中物化（Materialize）成一个巨大的临时表/列表。
    
- **灾难后果：** 为了区区 10 条 A 表的数据，MySQL 却在内存里加载并处理了 1000 万条 B 表的数据。这就叫“大表驱动小表”，内存和 CPU 直接爆满，效率极低。
    

### ❌ 反过来错误场景二：子查询结果小，你却用了 `EXISTS`

假设：外层表 A 有 1000 万条数据（极大），子查询 B 表符合条件的只有 10 条数据（极小）。

SQL

```
-- 错误示范：在子查询小的时候用了 EXISTS
SELECT * FROM A WHERE EXISTS (SELECT 1 FROM B WHERE B.id = A.id);
```

- **实际执行流程：** 根据 `EXISTS` 的原理，外层表 A 是驱动表。MySQL 必须**硬着头皮去遍历 A 表的 1000 万条数据**。每拿出一行 A 的数据，就要去 B 表里利用索引查一下存不存在。
    
- **灾难后果：** 虽然每次去 B 表查索引很快，但**外层循环整整执行了 1000 万次**！哪怕每次索引查找只耗费 0.01 毫秒，重复 1000 万次也是一个巨大的灾难。


### 1. 为什么“A小B大”时，EXISTS 比 IN 快？（索引是主要矛盾）

> - **“能不能用索引”不是主要矛盾：** 因为优化器会兜底，最终两边都能用上索引。
>     
> - **“索引是怎么来的”才是主要矛盾：**
>     
>     - 用 `EXISTS`，使用的是 B 表**原生的、早就随数据一起建好并维护着的静态索引**（零额外成本）。
>         
>     - 用 `IN`，使用的是 **动态生成的、用完就扔的临时表索引**（生成成本与 B 表大小成正比，高达 1000 万级别）。

假设 A 表 10 条（小），B 表 1000 万条（大）。

- **如果用 IN：**
    
    MySQL 尝试把 B 表（1000万条）物化到内存。因为数据量太大，内存放不下，只能转为**磁盘临时表**。而且这个临时表是**没有索引**的。接下来 A 表的 10 条数据要去跟这个没有索引的磁盘大表做比对。
    
    > **结果：** 慢。
    
- **如果用 EXISTS：**
    
    外层 A 表只遍历 10 次。每次拿着 A 的 `id` 去 B 表（1000万条）里找。
    
    这时候**关键来了**：如果 B 表的 `id` 有索引，B 表虽然大，但 B 树索引找一条数据只需要 3~4 次 I/O。10 次循环 $\times$ 4 次 I/O = 40 次操作。
    
    > **结果：** 极快。但**前提是 B 表必须有索引**。如果 B 表没有索引，EXISTS 就会变成外层循环 10 次，每次都对 B 表进行 1000 万次全表扫描，那同样会死得很惨。
    

所以，在“A小B大”**这个特定场景下，“B表能不能利用索引”是决定 EXISTS 飞快还是慢死的**主要矛盾。

### 2. 回到你说的：为什么“反过来”时，索引不是主要矛盾？

正如你所说，如果“A大B小”（A表1000万，B表10条），你还坚持用 EXISTS：

- 外层循环 1000 万次。
    
- 即使 B 表有索引，每次查询只要 0.001 毫秒。
    
- 总时间 = $10,000,000 \times 0.001 \text{ 毫秒} = 10,000 \text{ 毫秒} = 10 \text{ 秒}$。
    

在这个**错误场景**下，主要矛盾已经转移了：**循环基数（A表大小）太大，直接一力降十会，把索引的优势给抹平了。**



### 1. MySQL 面对 `A IN (SELECT B)` 时的真实抉择

当 B 表很大（1000 万），A 表很小（10 条）时，如果我们写了 `A.id IN (SELECT B.id)`，MySQL 的优化器在拿到这个 SQL 时，首先会尝试把它做**物化（Materialization）**。

1. **第一步（生成物化表）：** MySQL 确实会先执行子查询，把 B 表的 1000 万条 `id` 查出来，试图塞进一个内存临时表。
    
2. **第二步（触发内存溢出）：** 因为 1000 万条数据太大了，超出了 `tmp_table_size` 的限制，这个临时表会被**被迫转存到磁盘上**。
    

**关键点来了：** 当这个磁盘临时表生成完毕后，MySQL 并不是傻傻地拿这 1000 万条数据的磁盘表去“驱动” A 表。因为 MySQL 的优化器很聪明，它在物化完成后的下一步，会评估**谁当驱动表代价更小**。

### 2. 为什么最终会变成 “A 表遍历，去比对 B 的磁盘表”？

现在桌面上放着两个东西：

- **表 A：** 10 条数据（有索引，或者全表扫描也只要 10 次）。
    
- **B 的物化临时表：** 1000 万条数据（在磁盘上，**没有索引**）。
    

如果按照你说的“B 驱动 A”：

- 引擎要从磁盘上逐行读取 1000 万条 B 的数据。
    
- 每读出一条，去 A 表（10条）里匹配（虽然 A 有索引，但外层循环了 1000 万次）。
    
- **总代价：** 扫描 1000 万行磁盘数据 + 1000 万次 A 表索引查找。
    

如果反过来，让 “A 驱动 B”：

- 引擎只遍历 A 表 10 次。
    
- 每读出一条，去 B 的 1000 万磁盘临时表里找匹配。
    
- **等等！** 刚才说了 B 的临时表**没有索引**啊，那 A 的每一条数据，去 B 里找的时候，都要对 B 进行一次全表扫描！
    
- **总代价：** 10 次 $\times$ 1000 万次全表扫描 = **1 亿次扫描**。
    

#### 🛠️ MySQL 真正的骚操作：自动补齐索引

MySQL 优化器看到这两个方案都要崩溃了。于是它在把 B 表物化到磁盘的同时，通常会做一件事：**为这个临时表自动创建一个哈希索引（Hash Index）或 B+树索引**。

一旦给 B 的临时表建了索引，优化器评估后就会决定：**依然让 A 充当驱动表**。

它的实际执行变成了：

1. 遍历 A 表（10次）。
    
2. 每次拿着 A 的 `id`，去 B 的磁盘临时表（已自动建好索引）里利用索引查找。



“自动给临时表建索引（Materialization-scan / Materialization-lookup）”的机制，对 MySQL 来说还真不能算“新功能”——它是在 **MySQL 5.6 版本**（2013年发布）中正式引入的，属于优化器子查询重写（Subquery Optimization）的重大升级。

至于我之前为什么没主动提起它，是因为在聊“口诀”的时候，我落入了“经典八股文”的思维定势里。

在绝大多数数据库教程和面试题里，讲到 `IN` 和 `EXISTS` 时，大家还停留在 MySQL 5.5 之前的旧时代逻辑：

- **旧时代的死理：** `IN` 就是老老实实把子查询结果先算出来（物化），然后用子查询驱动外层表。所以只要子查询大，就一定会全表扫描，彻底完蛋。
    

但现实中，现代 MySQL（5.6 / 5.7 / 8.0+）的优化器已经非常聪明了。它看到你写出“A小B大还用IN”这种糟糕的 SQL 时，并不会坐以待毙，而是会通过以下两种“隐藏大招”来帮你擦屁股：

### 🛠️ 现代 MySQL 的两手准备

#### 1. 物化并自动建索引（Materialization）

就是我上面提到的。MySQL 发现 B 表太大了，但它还是先查出 B，塞进磁盘临时表。为了不让后续的比对变成灾难，MySQL 会在磁盘临时表上**临时创建一个 B+树索引或哈希索引**。然后翻转驱动关系，用小表 A 去查这个临时表索引。

> **代价：** 虽然查询变快了，但“把 1000 万数据写入磁盘 + 建索引”的过程依然慢得像乌龟。

#### 2. 直接把 IN 转换成 Join / EXISTS（Semi-Join 优化）

这是更常用的策略。当你写 `WHERE A.id IN (SELECT B.id)` 时，MySQL 优化器在后台一分析，发现 B 表大得离谱，它会**直接把你的 SQL 改写**。 它可能会把它改写成类似 `SELECT A.* FROM A WHERE EXISTS (SELECT 1 FROM B WHERE B.id = A.id)`，或者直接变成一个**半连接（Semi-Join）**。

> **结果：** 此时它会直接让 A 充当驱动表，利用 B 表原有的索引去查，从而绕过了那个“把 1000 万数据物化到磁盘”的恐怖步骤。


而真实的现代数据库：

1. **你遵守口诀（A小B大用EXISTS，A大B小用IN）：** 优化器顺水推舟，执行路径完美，性能最高。
    
2. **你违反了口诀（反过来用）：** 优化器会启动上面说的“补救机制”（改写 SQL 或建临时索引）。虽然优化器尽力了，让查询不至于直接卡死，但因为有改写和建临时表的额外开销，性能依然远不如正确选型。

### 2. NULL 值处理

这个坑比较隐蔽。假设：

**表 t1**: id=1, 2, 3 **表 t2**: id=1, NULL

```sql
SELECT * FROM t1 WHERE t1.id IN (SELECT t2.id FROM t2)
-- 结果：id=1
-- 因为 IN 会把 t2 的结果集算出来 = {1, NULL}，然后 t1.id IN (1, NULL) 对 id=2 和 id=3 返回 NULL（假），不返回
```

```sql
SELECT * FROM t1 WHERE EXISTS (SELECT 1 FROM t2 WHERE t2.id = t1.id)
-- 结果：id=1
-- EXISTS 是逐条判断的
```

表面看结果一样，但如果是反过来的 `NOT IN` vs `NOT EXISTS`：

```sql
SELECT * FROM t1 WHERE t1.id NOT IN (SELECT t2.id FROM t2)
-- 结果：空集合！
```

因为 `t1.id NOT IN (1, NULL)` 等价于 `t1.id != 1 AND t1.id != NULL`。在 SQL 中，任何值与 `NULL` 做比较都返回 `NULL`（未知）。所以 `id=2` 变成 `2 != 1 AND 2 != NULL` --> `TRUE AND UNKNOWN` = `UNKNOWN`，不返回。所有行都被 `NULL` 污染了。

```sql
SELECT * FROM t1 WHERE NOT EXISTS (SELECT 1 FROM t2 WHERE t2.id = t1.id)
-- 结果：id=2, 3
```

NOT EXISTS 走的是一条条判断——`WHERE t2.id = t1.id` 对 id=2 来说匹配不上，就 `NOT EXISTS` 为 TRUE，正常返回。它不参与 NULL 的比较逻辑，所以 NULL 不影响结果。

这是 `IN` 和 `EXISTS` 之间一个非常经典的坑，很多人在 `NOT IN` 上翻过车。

### 3. MySQL 优化器对 IN 和 EXISTS 的重写

这个最容易被忽略——**你写的是 IN，MySQL 不一定会按 IN 执行。**

MySQL 的优化器会把 IN 和 EXISTS **互相转换**，规则大致是：

- **子查询结果集小** → 保持 IN 形式，物化（Materialize）子查询结果
- **子查询结果集大 + 外层表小** → **优化器自动将 IN 重写为 EXISTS**
- **子查询结果集大 + 外层表大** → **优化器自动将 EXISTS 重写为 IN**

MySQL 5.6 开始引入了 **Semi-Join 优化**和 **Materialization 优化**，使得 `IN` 的执行方式不再是简单的"先算子查询再逐条匹配"，而是可以做半连接、物化后用哈希匹配等。从 5.7 开始还有 **Optimizer Trace** 可以查看优化器到底做了什么决策。

所以最终的真相是：**你写 IN 还是 EXISTS，只影响优化器的初始分析路径。优化器会根据实际的表大小、索引、数据分布等因素，最终选择它认为最优的执行计划。** 很多时候你费尽心思把 IN 改成 EXISTS，EXPLAIN 一看执行计划一模一样。

---

**总结一下这三件事的价值：**

|对比维度|IN|EXISTS|
|---|---|---|
|驱动表|子查询结果（物化列表）|外层表|
|适合场景|子查询结果集很小|外层表很小|
|NULL 影响|NOT IN 遇到 NULL 全表失效|NULL 不影响|
|优化器行为|可能被重写为 EXISTS|可能被重写为 IN|

所以更重要的不是死记"IN 和 EXISTS 哪个快"，而是**理解驱动表和 NULL 的坑**，以及**每次写完后都用 EXPLAIN 实际看执行计划**——因为优化器的行为你没法靠直觉猜准。


## 一个反直觉的延伸

如果反过来：t1.id 本身是 NULL，`t1.id IN (SELECT t2.id FROM t2)`，那 `NULL = 1` 也是 UNKNOWN，id 是 NULL 的那行也会被过滤掉——**NULL 的坑在 `IN` 这一侧也会出现**。所以面试话术建议直接说：

> "`IN`/`NOT IN` 对 NULL 敏感，`EXISTS`/`NOT EXISTS` 对 NULL 不敏感"——这是《[IN和EXISTS](app://obsidian.md/IN%E5%92%8CEXISTS)》强调的经典坑。


## 对比：`NOT EXISTS` 为什么抗 NULL

`NOT EXISTS` 的语义是"**去子查询里查一下，看能不能找到匹配行**"：

```sql
SELECT * FROM t1 WHERE NOT EXISTS (
    SELECT 1 FROM t2 WHERE t2.id = t1.id
)
```

sql

对于 t1 的每一行（比如 id=2）：

- 子查询在 t2 里执行 `WHERE t2.id = 2`
- t2 只有 `id=1` 和 `id=NULL` 两行
- t2.id=1 那行：`1 = 2` → FALSE，不匹配
- t2.id=NULL 那行：`NULL = 2` → UNKNOWN，也不算"匹配上"（只有 TRUE 才算存在）
- 子查询一行都没返回 → `EXISTS` 为 FALSE → `NOT EXISTS` 为 TRUE → id=2 正常返回
