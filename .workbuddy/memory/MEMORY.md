## 用户偏好（输出与整理）

- **「知识点整理」输出风格**（2026-10-14 定稿，全文存档 [[知识点整理提示词]]）：
  两段式——「知识点」（一句话定义加粗 + 4~6 条要点：是什么 / 怎么工作 / 为什么需要 / 为什么安全）→「知识点场景」（3 个：使用场景 / 验证方法（命令或现象）/ 面试对照）。
  粒度：300~400 字，只讲主线，不展开历史演进与边缘细节；无 emoji、不加总结段、不写鼓励追问的结尾。
- 该库默认引号风格为 **ASCII 直引号**（写新内容时保持一致）。
- **批卷参考答案必须口述化**（2026-10-23 用户明确要求，细则已并入 `00-元数据/批卷准则.md`「参考答案必须口述化」专节，原提示词来自 `AI/prompt.md` 第二段）：参考答案/追问参考答一律写成**能直接开口说的连贯自然段**——不分点、不加标题、不用列表和表格、不加粗、不用 emoji、代码不加反引号；先结论→再原理→最后补追问坑；单段五六句、一分钟能说完；数字与因果链必须落在句子流里。**只约束此后新批的卷子，已批完的旧卷不返工。**
- **回答风格（2026-10-14 教训）**：用户提具体问题时**先直接给答案**（是/否 + 结论），再补辨析与展开；不要用"纠正提问者概念"式开场。用户理解正确时要**明确肯定**（"你说得对"），不要绕圈子。反例：软链接/目录项连环追问中，先纠正概念再回答导致用户强烈不满（"你到底能不能听懂人话"）；正例：同批 TLS 题答疑先肯定用户逻辑再分析，用户就接受了。

## 编辑与操作教训（该库通用）

- 部分文件含 **NBSP（U+00A0，网页粘贴带入）**：Edit 精确匹配会报 not found——先 `python repr()` 输出目标行定位字符（2026-10-14 两处实证）。
- Edit 报 `EBUSY: resource busy or locked` 是文件被瞬时锁住（Obsidian/同步进程），**重试即可**。
- Markdown 表格单元格里的 `|` 即使在内联代码中也要转义成 `\|`；表格必须顶格独立成块。
- 定位标题前先确认层级（`## 9.x` 还是 `### 9.x`），不要凭记忆写锚点。
- **归类看内容本质，不看文件形态**（2026-10-23 教训）：`Redis 常见数据类型和应用场景` 因为是「大文件 + 剪藏原文」被放进 `1-综合`，但内容整篇是九种数据类型的用法，属数据结构域，被用户当场指出。同类风险：别把「篇幅大」「来源是剪藏」当综合类的理由；判据只看它讲的是哪个知识点域。
- **大段替换 index 前先确认 old_string 的边界**（2026-10-23 / 10-25 三次实证）：一次替换把 4 条相邻条目连带删掉，因为 old_string 跨了多行末尾而 new_string 没包全；另一次把块内后半段留在原地导致 4 条重复出现两遍。**以后改 index 某个区块，一律用脚本按「区块起止锚点」整块重写 + `grep -c "^- \[\["` 断言条目数等于目录内文件数**，不要用 Edit 做多行局部替换。
- **截断式重写必须确认区块是不是最后一个**（2026-10-25 实证）：重写 `06-中间件与技术杂项` 区块时用了 `s[:start] + new`，想当然认为它在文件末尾，结果把后面的「算法题」整段（305 行 / 244 条）截掉了，从 git 历史才取回。**任何 `s[:i] + new` 式重写，先 `grep -n "^## "` 看清该区块后面还有没有别的一级标题**；不是最后一个就用 `s[:start] + new + s[end:]` 两端定位。重写后 `grep -c "^## "` 数一遍区块数，与预期的域数对不上就是丢了。
- 新页面落库五件套：建页面 → 补相关页面回链 → 更新 index.md → 追加 log.md → 写当日 memory。
