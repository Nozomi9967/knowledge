## XREADGROUP 的三种读取模式

```
XREADGROUP GROUP <组名> <消费者名> [COUNT n] [BLOCK ms] STREAMS <stream> <模式>
```

最后一个参数决定了消费者读取哪些消息，行为完全不同：

### `>` — 读取未投递消息（日常消费）

```bash
XREADGROUP GROUP mygroup consumer1 STREAMS mystream >
```

- **含义：** 只读取该消费者组中**从未被任何消费者处理过**的消息
- **使用场景：** 每个消费者启动后，不停地用 `>` 拉取新任务
- **通俗理解：** "给我分配新任务"

### `0` — 读 pending 消息（重启恢复）

```bash
XREADGROUP GROUP mygroup consumer1 STREAMS mystream 0
```

- **含义：** 只读取**已经投递给当前消费者、但还没回复 ACK**的消息（即 pending list）
- **使用场景：** 消费者挂了重启，把之前领了但没干完的任务重新拉回来
- **通俗理解：** "看看我还有哪些没干完的活"

### `$` — 读之后的消息（从最新开始）

```bash
XREADGROUP GROUP mygroup consumer1 STREAMS mystream $
```

- **含义：** 只读取执行这条命令**之后才到达**的新消息，历史消息一概不看
- **使用场景：** 新消费者加入，不想处理旧数据，只从当前开始消费
- **通俗理解：** "以前的活我不管，以后的新活给我"

---

### 核心区别速览

| 模式 | 读什么 | 什么时候用 |
|------|--------|-----------|
| **`>`** | 未被任何消费者处理过的消息 | 日常消费，拉新任务 |
| **`0`** | 已投递给自己但未 ACK 的消息 | 崩了重启，把未完成的任务捡回来 |
| **`$`** | 命令执行之后才来的消息 | 新消费者加入，不回溯历史 |

### 为什么面试官爱问这个？

这三个模式正好对应消息队列的三个核心问题：

1. **正常消费怎么读？** → `>`
2. **挂了重启怎么恢复？** → `0`（配合 pending list + ACK）
3. **新来的消费者要不要处理历史数据？** → `$`（不要）或从头 `>`（要）

# 🎯 面试题 · 2026-07-28 17:55（基于《Stream的XREADGROUP三种模式》）

> [!question]- 面试题 1：请简述 Redis Stream 中 XREADGROUP 命令支持的三种读取模式，以及它们分别读取什么样的消息？
> XREADGROUP 命令通过最后一个参数来决定消费者读取哪些消息，主要有大于号、零和美元符号这三种模式。大于号模式只读取该消费者组中从未被任何消费者处理过的消息，这相当于让消费者去领取新的任务。零模式则专门读取已经投递给当前消费者、但还没有回复 ACK 确认的消息，也就是 pending list 里的那些消息。美元符号模式比较特殊，它只读取执行这条命令之后才到达的新消息，对于之前的历史消息一概不看。

> [!question]- 面试题 2：在实际的项目场景中，我们应该如何根据消费者的运行状态来选择这三种读取模式？
> 选择哪种模式主要看消费者当前的状态和需求。如果是正常的日常消费场景，消费者启动后需要不停地拉取新任务，这时候应该一直使用大于号模式。如果消费者因为故障挂了又重启，需要把之前领了但没干完的任务重新捡回来继续处理，那就必须用零模式来读取那些 pending 消息。还有一种情况是新消费者加入集群，如果我们不想让它处理积压的历史数据，只想让它从当前时间点开始消费，这时就应该选用美元符号模式。

> [!question]- 面试题 3：为什么 Redis Stream 要专门设计这三种不同的读取模式？它们背后解决了消息队列的哪些核心问题？
> 这三个模式的设计其实正好对应了消息队列实现过程中的三个核心问题。第一个是正常消费怎么读，通过大于号模式满足了日常拉取新任务的基本需求。第二个是挂了重启怎么恢复，通过零模式配合 pending list 和 ACK 机制，确保消费者崩溃后能找回未完成的任务，保证可靠性。第三个是新来的消费者要不要处理历史数据，通过美元符号模式让新消费者可以选择只关注未来的新消息，避免了新节点加入时因回溯历史数据带来的性能压力或重复处理问题。

>

> [!question]- 面试题 4：在使用 XREADGROUP 命令时，除了读取模式外，还有哪些关键参数会影响消费行为？请结合命令结构说明。
> 在命令结构中，XREADGROUP 后面紧跟的是 GROUP 组名和消费者名，这两个参数确定了消息归属的组和具体的消费者身份。此外还有 COUNT n 参数用来限制每次拉取的最大消息数量，防止一次拉太多造成阻塞。BLOCK ms 参数则允许设置阻塞等待时间，如果没有新消息时可以等待指定毫秒数再返回，而不是立即返回空结果。这些参数配合最后的读取模式，共同决定了消费者如何高效、稳定地从流中获取数据。
