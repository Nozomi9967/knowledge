# 项目里线程池用在哪（抢座调度池 · 定时任务池）

> 对应面试题：**「讲一下你的实际项目中用到线程池的场景」**。这道题考的不是线程池八股，是**参数是不是真的算出来的**——能不能说清「这个数字凭什么」。

## 一、口述版答案

我在 Nozomi House 里主要在两个地方用了线程池，一处是 Spring 的定时任务调度池，一处是我自己建的抢座任务调度池。前者是为了让多个定时任务不互相拖，后者是要在精确的时间点同时发起多个抢座任务。我拿后者说，因为它最能体现参数是怎么算出来的。这个池用的是 ScheduledThreadPoolExecutor，核心线程数配了四。

这个四不是按 CPU 核数算的，是按同一瞬间的最大并发任务数算的。我们同时服务四个账号，晚上八点整这四个账号的抢座任务是同时发起的，同一瞬间最多就是四个任务要跑，所以核心线程数配四。再多配就是长期闲置，按核数乘二去配八个也没有依据。

之所以不按核数配，是因为这类任务是 IO 型，线程大部分时间在等网络响应、等时间点，不占 CPU，线程数和核数没有直接关系。只有计算密集型的池才需要贴着核数配。

还有一个容易说错的地方，ScheduledThreadPoolExecutor 的 maximumPoolSize 实际上是配不到的。它的队列是 DelayedWorkQueue，无界，而且延迟任务必须先入队才能按触发时间排序，所以 offer 永远返回成功。而 ThreadPoolExecutor 的 execute 方法只有在入队失败的时候才会去扩容到最大线程数，入队成功就直接返回了。所以这个池的线程数永远等于核心线程数，拒绝策略也永远不会触发，配它的时候不用纠结队列容量和拒绝策略，但代价是配小了没有兜底。

另外补一个实际踩过的坑，Spring 的定时任务调度池默认只有一个线程，spring.task.scheduling.pool.size 的默认值是一，所有 Scheduled 任务共用一个线程串行排队。我们之前有个十秒一次的邮件轮询，单次处理超过十秒，就把八点的电费同步堵在后面了，表现是定时任务没按时跑但日志里一个错都没有，后来把这个值调到了四。

## 二、答案拆解（被追问时往下挖）

### 2.1 核心线程数 = 同一瞬间的并发任务数

| 任务类型 | 线程数依据 | 本项目情况 |
|---------|-----------|-----------|
| CPU 密集型 | 贴着核数（核数 + 1） | 不适用 |
| IO 密集型 | 按**并发任务数**或按 IO 等待比估算 | 抢座任务：等时间点 + 等 HTTP 响应 |
| 定时/延迟任务 | 按**同一触发时刻的任务数** | 四个账号八点整同时发起 → 4 |

关键推导：线程在等时间点和等网络响应时不占 CPU，所以「核数 × 2」这种公式在这里没有依据。真正决定线程数的是**同一瞬间要并行跑多少个任务**——四个账号同时抢座，就是 4。

> 注意这里和「IO 密集型可以配很多线程」不矛盾：那是针对「任务数远大于核数、且每个任务都在等 IO」的池（比如 HTTP 调用池，可以配几十上百）；这个池的**任务总量本身就只有 4 个**，配多了纯属闲置。

### 2.2 maximumPoolSize 为什么配不到

这是本题最值钱的一段，因为大多数人答不出机制。

```
ScheduledThreadPoolExecutor.delayedExecute(task)
  → super.getQueue().add(task)      // DelayedWorkQueue，无界
  → ensurePrestart()                // 只在 worker 数 < corePoolSize 时才 addWorker
```

而 ThreadPoolExecutor 的扩容逻辑（execute 方法）是：

```
workerCount < corePoolSize        → 建核心线程
入队成功（offer 返回 true）        → 直接返回，不扩容
入队失败（队列满）                 → 才扩容到 maximumPoolSize
```

`DelayedWorkQueue` 是**无界**的，且延迟任务必须先入队才能按触发时间排序（它的 `offer` 里要做堆调整、可能成为新的队首、要 `available.signal()` 唤醒等待的 worker），所以 `offer` **永远返回 true**。两条一串，结论就是：

- 线程数**永远等于 corePoolSize**，`maximumPoolSize` 是死配置
- 队列永不满 → **拒绝策略永远不会触发**
- 配这个池时不用纠结队列容量和拒绝策略
- **代价：配小了没有兜底**——任务只会在无界队列里排队等待，不报错、不拒绝、不告警

> 这也是 `ScheduledThreadPoolExecutor` 不能简单套用「核心 → 队列 → 最大 → 拒绝」那套流程的原因，它的扩容路径实际是断的。详见 [[ScheduledThreadPoolExecutor详解]]（该页目前仍是 stub，待补源码级推导）。

### 2.3 「没兜底」意味着什么

无界队列 + 线程数固定，意味着**任务堆积是静默的**。所以监控点应该放在「队列长度」和「任务实际执行时间 vs 预期触发时间的偏差」上，而不是放在拒绝策略上——因为这个池根本不会拒绝。

## 三、Spring 定时任务单线程的坑（实际踩过）

`ThreadPoolTaskScheduler` 默认 `poolSize = 1`，也就是 `spring.task.scheduling.pool.size` 默认是 **1**。所有 `@Scheduled` 任务**共用一个线程串行排队**。

本项目的故障现场：

- 有一个十秒一次的邮件轮询（GmailPollService），单次处理超过十秒
- 结果把晚上八点的电费同步任务堵在后面
- 表现：**定时任务没按时跑，但日志里一个错都没有**（因为任务本身没失败，只是没轮到它）
- 处理：把 `spring.task.scheduling.pool.size` 调到 4

这类「静默延迟」比抛异常难查得多，因为没有错误日志、没有堆栈，只能靠「预期触发时间 vs 实际执行时间」的偏差去发现。

## 四、追问预案

| 追问 | 答法要点 |
|------|---------|
| 为什么不用 `@Scheduled(cron)` 抢座？ | cron 精度只到秒级且由 Spring 调度线程触发，多个任务挤同一个调度线程；抢座需要精确到毫秒级的同时发起，且要每个账号独立可控（取消、重排），所以自己管 ScheduledFuture |
| 为什么不用 `Timer`？ | Timer 单线程 + 异常敏感，一个任务抛异常整个 Timer 线程死掉，后续任务全不跑（阿里规约明确禁用） |
| 队列无界会不会 OOM？ | 这个池的任务总量是固定的（四个账号的抢座任务），不会持续生产，所以不会堆积；如果是持续生产任务的池，无界队列才是真风险，那种场景要自己用 ThreadPoolExecutor 配容量 |
| 任务堆了怎么发现？ | 看 ScheduledFuture 的实际执行时间与预期触发时间的偏差、以及线程池活跃线程数；这个池不会拒绝，所以不能靠拒绝策略告警 |
| 为什么核心线程数不按 4 核 CPU 来？ | 见 2.1：IO 型任务线程大部分时间在等，且任务总量就是 4，核数是另一个维度的约束 |
| 和 `@Async` 的线程池是一回事吗？ | 不是。`@Async` 走的是 `TaskExecutionAutoConfiguration` 的 `taskExecutor`（`spring.task.execution`）；`@Scheduled` 走的是 `TaskSchedulingAutoConfiguration` 的 `taskScheduler`（`spring.task.scheduling`），**两个池、两套配置** |

## 五、一句话记忆

> 核心线程数按**同一瞬间的并发任务数**算，不按核数；`ScheduledThreadPoolExecutor` 的 max 和拒绝策略都是死配置（DelayedWorkQueue 无界，offer 永远成功）；Spring 定时任务默认**单线程**，`spring.task.scheduling.pool.size` 记得调。
