## 什么是阻塞队列

**BlockingQueue**（阻塞队列）是 `java.util.concurrent` 包下的接口，扩展自 `Queue`，**当队列满时入队阻塞、当队列空时出队阻塞**——天生适合生产者-消费者场景。

> [!info] BlockingQueue — Blocking Queue（阻塞队列）
> 名字直译：**Blocking**（阻塞）+ **Queue**（队列）。**两个阻塞点** + **一个线程安全** = 生产者消费者的「开箱即用」工具。
>
> 通俗理解：把 BlockingQueue 想象成**快递驿站货架**——货架有容量上限（满员不上架），空了没货可取（空架取件阻塞）。快递员（生产者）put 包裹，顾客（消费者）take 包裹，**货架自动帮你协调生产和消费的速度差**。

### 核心四方法

| 行为 | 抛异常 | 返回特殊值 | 阻塞 | 超时 |
|------|--------|------------|------|------|
| **插入** | `add(e)` → `IllegalStateException` | `offer(e)` → `boolean` | **`put(e)`** | `offer(e, time, unit)` |
| **移除** | `remove()` → `NoSuchElementException` | `poll()` → `null` | **`take()`** | `poll(time, unit)` |
| **检查** | `element()` → `NoSuchElementException` | `peek()` → `null` | — | — |

> **记忆口诀：「抛异常是 add/remove/element；阻塞是 put/take；返回特殊值是 offer/poll/peek」。**

### 一句话总结

> BlockingQueue = **线程安全 + 阻塞 + 超时** = 生产者消费者 / 线程池工作队列的标准实现。

## 一、核心接口与实现类全景

```
BlockingQueue (interface)
├── ArrayBlockingQueue          有界数组，单锁，固定容量
├── LinkedBlockingQueue         链表，双锁（take/put 各一），可无界
├── PriorityBlockingQueue       优先级堆，无界
├── DelayQueue                  延迟队列，无界，元素到期才能取
├── SynchronousQueue            零容量，直接 hand-off
├── LinkedTransferQueue         链表 + transfer
└── LinkedBlockingDeque         双端阻塞队列
```

## 二、ArrayBlockingQueue 详解（最常用）

**底层：** `Object[]` 数组 + `ReentrantLock` + 两个 `Condition`（notFull / notEmpty）

```
        putIdx  ──→  ──→  ──→  ──→  ──→
        ┌─────┬─────┬─────┬─────┬─────┐
items:  │  A  │  B  │  C  │     │     │
        └─────┴─────┴─────┴─────┴─────┘
                                              ↑ takeIdx
```

| 维度 | 详情 |
|------|------|
| **容量** | 构造时指定，**不可变** |
| **锁** | **单锁**（put/take 互斥） |
| **Condition** | **2 个**（notFull 给 put 用 / notEmpty 给 take 用） |
| **公平性** | 可选（`new ArrayBlockingQueue(N, fair)`） |
| **典型场景** | 线程池工作队列（`newFixedThreadPool` / `newSingleThreadExecutor`） |

### 核心源码片段（put）

```java
public void put(E e) throws InterruptedException {
    checkNotNull(e);
    final ReentrantLock lock = this.lock;
    lock.lockInterruptibly();
    try {
        while (count == items.length)        // 满则等
            notFull.await();
        enqueue(e);                          // 入队
    } finally {
        lock.unlock();
    }
}

private void enqueue(E x) {
    items[putIdx] = x;
    if (++putIdx == items.length) putIdx = 0;  // 环形数组
    count++;
    notEmpty.signal();                         // 唤醒一个消费者
}
```

**关键点：**
- **`while` 循环判满**——防虚假唤醒
- **环形数组**——putIdx/takeIdx 走到末尾归 0
- **`signal()` 精确唤醒**——put 完只叫 take 队列的消费者

## 三、LinkedBlockingQueue 详解（最常用）

**底层：** 单向链表 + **双锁**（takeLock + putLock）+ 两个 `Condition`

| 维度 | 详情 |
|------|------|
| **容量** | 构造时指定，默认 `Integer.MAX_VALUE`（**陷阱**） |
| **锁** | **双锁分离**（take 和 put **不互斥**）——**吞吐比 ArrayBlockingQueue 高** |
| **Condition** | 2 个（notFull / notEmpty） |
| **典型场景** | 线程池默认工作队列（**小心无界导致 OOM**） |

### 为什么双锁能提高吞吐？

```
ArrayBlockingQueue:  put 和 take 用同一把锁 → 互斥
LinkedBlockingQueue: put 拿 putLock, take 拿 takeLock → 不互斥
                     ↑
                  并发度提升 ~2 倍
```

### 容量陷阱

```java
new LinkedBlockingQueue()              // 默认 Integer.MAX_VALUE ≈ 21 亿
new LinkedBlockingQueue(1024)          // 显式有界
new LinkedBlockingQueue(100)          // ★ 推荐：永远显式指定容量
```

> [!warning] OOM 风险
> 阿里规约：**线程池不允许使用 `Executors.newFixedThreadPool`**——它默认用 `LinkedBlockingQueue` 无界队列，**任务堆积到 21 亿会导致 OOM**。必须用 `ThreadPoolExecutor` 显式传有界队列。

## 四、SynchronousQueue 详解（零容量）

**底层：** **没有容量**——put 必须等 take 拿走才能返回，take 必须等 put 进来才能拿走。**直接 hand-off（交接）**。

| 维度 | 详情 |
|------|------|
| **容量** | **0**（每个 put 必须配一个 take） |
| **数据结构** | 无（不是真的队列） |
| **公平性** | 默认非公平（栈），可 `new SynchronousQueue(true)`（队列） |
| **典型场景** | `Executors.newCachedThreadPool` 用的就是它 |

### 行为示意

```java
SynchronousQueue<String> sq = new SynchronousQueue<>();

// T1: put 阻塞，直到 T2 来 take
new Thread(() -> {
    sq.put("hello");                       // 阻塞
    System.out.println("T1 put 成功");
}).start();

Thread.sleep(1000);
new Thread(() -> {
    String s = sq.take();                  // 立刻拿走，T1 put 成功
    System.out.println("T2 拿走: " + s);
}).start();
```

**适用场景：** 任务必须**立刻处理**、不能缓冲——cachedThreadPool 把任务直接交给 worker，不排队。

## 五、PriorityBlockingQueue 详解

**底层：** 数组实现的**二叉堆**（默认小顶堆），无界

| 维度 | 详情 |
|------|------|
| **容量** | **无界**（11 → 自动扩容） |
| **排序** | 按元素的 `Comparable` / 构造时传入的 `Comparator` |
| **锁** | 单 `ReentrantLock` |
| **典型场景** | 任务有优先级（VIP 任务先执行） |

### 注意

- **put 不会阻塞**（无界），但 `take` 会按优先级取
- 元素必须实现 `Comparable` 或传 `Comparator`，否则 `ClassCastException`

## 六、DelayQueue 详解

**底层：** `PriorityQueue` + 记录每个元素到期时间的堆

| 维度 | 详情 |
|------|------|
| **容量** | **无界** |
| **元素** | 必须实现 `Delayed` 接口（`getDelay()` 返回剩余时间） |
| **出队** | `take()` 阻塞到**队首元素到期**才能取 |
| **典型场景** | 定时任务调度、订单超时关闭、缓存过期 |

### 元素必须实现 Delayed

```java
public class OrderTask implements Delayed {
    private final String orderId;
    private final long expireTime;          // 到期时间戳

    public OrderTask(String orderId, long delayMs) {
        this.orderId = orderId;
        this.expireTime = System.currentTimeMillis() + delayMs;
    }

    @Override
    public long getDelay(TimeUnit unit) {
        return unit.convert(expireTime - System.currentTimeMillis(), TimeUnit.MILLISECONDS);
    }

    @Override
    public int compareTo(Delayed other) {
        return Long.compare(this.expireTime, ((OrderTask) other).expireTime);
    }
}

// 用法
DelayQueue<OrderTask> queue = new DelayQueue<>();
queue.put(new OrderTask("order-1", 5000));   // 5 秒后到期

// 阻塞直到有元素到期
OrderTask task = queue.take();
```

## 七、四大实现对比表 ⭐

| 维度 | ArrayBlockingQueue | LinkedBlockingQueue | SynchronousQueue | PriorityBlockingQueue | DelayQueue |
|------|--------------------|----------------------|-------------------|------------------------|-------------|
| **底层** | 数组（环形） | 单向链表 | 无（hand-off） | 二叉堆 | 优先级堆 |
| **容量** | 有界（必指定） | 可有可无（默认无界） | **0** | 无界 | 无界 |
| **锁** | 单锁 | **双锁** | 双栈/队列（公平） | 单锁 | 单锁 |
| **Condition** | 2 | 2 | 0 | 0 | 0 |
| **put 阻塞** | ✅ | ✅ | ✅ | ❌ 不阻塞 | ❌ 不阻塞 |
| **take 阻塞** | ✅ | ✅ | ✅ | ✅ | ✅（到期才返） |
| **排序** | FIFO | FIFO | 取决于构造 | 优先级 | 到期时间 |
| **典型场景** | 线程池有界队列 | 线程池（小心 OOM） | cachedThreadPool | 优先级任务 | 定时任务 |
| **性能** | 中 | 较高 | 高（无缓冲） | 中 | 中 |

## 八、线程池工作队列选择

`ThreadPoolExecutor` 的 `workQueue` 选错 = 灾难级 bug。

| 场景 | 推荐队列 | 原因 |
|------|----------|------|
| **CPU 密集型任务** | `ArrayBlockingQueue(2 * nCPU)` | 有界防 OOM |
| **IO 密集型任务** | `LinkedBlockingQueue(容量可控)` | 链表吞吐高 |
| **任务必须立刻处理** | `SynchronousQueue` | 不缓冲，直送 |
| **VIP 优先** | `PriorityBlockingQueue` | 优先级调度 |
| **延迟任务** | `DelayQueue` | 到期才能取 |

### 线程池构造标准范式（避坑）

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8,                                      // corePoolSize
    16,                                     // maximumPoolSize
    60, TimeUnit.SECONDS,                   // keepAliveTime
    new ArrayBlockingQueue<>(1000),         // ★ 显式有界
    new ThreadPoolExecutor.AbortPolicy()    // 拒绝策略
);
```

> [!warning] 阿里规约
> - **禁止** `Executors.newFixedThreadPool()`（无界 LinkedBlockingQueue → OOM）
> - **禁止** `Executors.newSingleThreadExecutor()`（同上）
> - **禁止** `Executors.newCachedThreadPool()`（SynchronousQueue + Integer.MAX_VALUE 线程数 → OOM）
> - **必须**用 `ThreadPoolExecutor` 显式传参

## 九、Condition 在阻塞队列中的应用 ⭐

`ArrayBlockingQueue` 和 `LinkedBlockingQueue` 都用 Condition 实现阻塞——参考 [[Condition 详解]] 的有界队列示例。

### ArrayBlockingQueue 的 Condition 设计

```java
public class ArrayBlockingQueue<E> extends AbstractQueue<E>
        implements BlockingQueue<E> {
    final ReentrantLock lock;
    private final Condition notEmpty;        // take 队列
    private final Condition notFull;         // put 队列

    public ArrayBlockingQueue(int capacity, boolean fair) {
        if (capacity <= 0) throw new IllegalArgumentException();
        items = new Object[capacity];
        lock = new ReentrantLock(fair);
        notEmpty = lock.newCondition();
        notFull = lock.newCondition();
    }
}
```

| Condition | 唤醒谁 | 何时 await |
|-----------|--------|-----------|
| **`notFull`** | put 完成后 | count == items.length 时 |
| **`notEmpty`** | take 完成后 | count == 0 时 |

**收益：避免 `notifyAll` 惊群**——put 完只叫 take 队列的消费者，take 完只叫 put 队列的生产者。

## 十、典型使用场景

### 10.1 生产者-消费者

```java
BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);

// 生产者
new Thread(() -> {
    try {
        for (int i = 0; i < 100; i++) {
            queue.put(i);                       // 满则阻塞
            System.out.println("生产 " + i);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}).start();

// 消费者
new Thread(() -> {
    try {
        while (true) {
            Integer x = queue.take();           // 空则阻塞
            System.out.println("消费 " + x);
            Thread.sleep(50);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}).start();
```

### 10.2 线程池任务队列

```java
// 任务进入队列，worker 自动取
ExecutorService pool = new ThreadPoolExecutor(
    4, 8, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(100)
);
for (int i = 0; i < 1000; i++) {
    pool.submit(() -> processTask());
}
```

### 10.3 消息中间件的基础设施

Kafka / RabbitMQ 客户端底层消费队列都是 BlockingQueue 模式（实际比这复杂得多）。

## 十一、面试高频踩坑

### 11.1 `add()` vs `offer()` vs `put()`

| 方法 | 满时行为 | 选谁 |
|------|----------|------|
| `add(e)` | 抛 `IllegalStateException` | **永远不推荐**——异常开销大 |
| `offer(e)` | 返回 `false` | 想立即知道能不能塞入 |
| **`put(e)`** | **阻塞** | 阻塞队列的精髓 |

### 11.2 `poll()` vs `take()` vs `peek()`

| 方法 | 空时行为 | 选谁 |
|------|----------|------|
| `take()` | **阻塞** | 必须拿到才继续 |
| `poll()` | 返回 `null` | 非阻塞轮询 |
| `peek()` | 返回 `null`（不删除） | 只看不取 |

### 11.3 容量陷阱

```java
// ❌ 错误：无界队列，任务堆积导致 OOM
new LinkedBlockingQueue<>()

// ✅ 正确：显式有界
new LinkedBlockingQueue<>(1000)
```

### 11.4 ArrayBlockingQueue 为什么是单锁？

容量固定 + 数组下标天然互斥——**单锁够用**。LinkedBlockingQueue 用双锁是因为链表操作 put（加尾）和 take（删头）**物理上分开**，可以分两把锁。

### 11.5 SynchronousQueue 是「队列」吗？

**严格说不是**——它没有容量，每个 put 必须配一个 take。**本质是 hand-off（交接）机制**。

### 11.6 DelayQueue 元素必须实现 Delayed

否则编译/运行报错。`Delayed` 接口继承 `Comparable<Delayed>`，所以要实现 `getDelay()` 和 `compareTo()`。

### 11.7 为什么线程池推荐用 ArrayBlockingQueue？

| 维度 | ArrayBlockingQueue | LinkedBlockingQueue |
|------|--------------------|----------------------|
| 内存 | 数组连续，**cache 友好** | 链表节点离散，对 GC 不友好 |
| 容量 | **必须指定**，防 OOM | 默认无界，**易 OOM** |
| 性能 | 双锁稍优，但单锁简单 | 复杂，但并发度高 |

**实际工程：稳定 + 防 OOM > 极限性能**——所以 ArrayBlockingQueue 是更安全的选择。

## 十二、面试话术模板

> "BlockingQueue 是 JUC 提供的线程安全阻塞队列，扩展自 Queue 接口，核心是 put 阻塞（满时）和 take 阻塞（空时）。它把生产者-消费者的「满/空协调」用 Condition 实现，开箱即用。
>
> 五大实现各有侧重：ArrayBlockingQueue 单锁 + 数组 + 有界，适合线程池工作队列；LinkedBlockingQueue 双锁 + 链表 + 可无界，并发度更高但要小心 OOM；SynchronousQueue 零容量 hand-off，适合任务必须立刻处理的场景（cachedThreadPool）；PriorityBlockingQueue 优先级堆，适合 VIP 任务；DelayQueue 延迟队列，适合定时任务调度。
>
> 选型口诀：'要稳定防 OOM → ArrayBlockingQueue；要高吞吐 → LinkedBlockingQueue（限有界）；要立即处理 → SynchronousQueue；要优先级 → Priority；要延迟 → Delay'。
>
> 工程上阿里规约明确禁止 `Executors.newFixedThreadPool` 等，它们默认用无界 LinkedBlockingQueue 会 OOM。必须用 ThreadPoolExecutor 显式传 ArrayBlockingQueue 有界队列 + 明确拒绝策略。"
