#### **2.3 Docker**

**面试官：Docker 是什么？你在实习里怎么用？**

> Docker 是一种容器化技术，可以把应用及其运行环境打包成镜像，再通过镜像启动容器。实习中我主要按照部署手册使用 Docker 相关命令检查镜像和容器状态、启动或查看服务，没有独立设计容器化方案。

**面试官：镜像和容器有什么区别？**

> 镜像是用于创建容器的只读模板，容器是镜像运行起来后的实例。可以把镜像理解为应用运行环境的模板，容器则是基于模板启动的进程环境。同一个镜像可以启动多个容器。

**面试官：你常用哪些 Docker 命令？**

> 我接触的主要是查看容器状态、查看日志和进入容器排查问题，例如 `docker ps`、`docker logs`、`docker exec`。具体部署时也会按手册使用项目规定的启动命令。排查时我会先确认容器是否在运行，再看日志和端口映射。

只说你实际执行过的命令。若没有用过 `docker exec`，就不要说自己用它排查过。

> 完整的命令清单见 [[docker命令]]（状态/日志/启动/排查四类 + `docker run` vs `start`、`exec` vs `attach` 辨析）。

**面试官：容器启动后马上退出，你会怎么查？**

> 我会先用 `docker ps -a` 看容器状态和退出信息，再看 `docker logs` 获取应用输出。然后检查启动命令、环境变量、配置文件、挂载目录和依赖服务是否符合部署要求。定位到具体原因后再按项目流程调整并重新验证。

**面试官：容器里的服务启动了，为什么外部还是访问不到？**

> 我会先确认容器状态和应用监听端口，再检查启动时的端口映射，以及宿主机端口是否可用；如果请求经过 Nginx，还会继续检查反向代理配置和相关日志。容器内部监听地址、端口映射或代理配置不匹配，都可能导致外部无法访问。

不要声称自己排查过具体网络问题，除非确实发生过。

**面试官：Docker 容器和虚拟机有什么区别？**

> 容器通常共享宿主机内核，隔离应用进程和运行环境，启动较轻；虚拟机一般包含独立操作系统，隔离边界更完整，但资源开销通常更大。对我实习中的部署场景来说，Docker 的价值主要是让服务以容器形式运行和管理。

### **三、容器网络：`--net=host` 与 `-p`**

面试官追问"你改的是什么参数、为什么能解决问题"时，需要先把两种网络模式讲清楚。

| 对比项 | `-p 9191:9191`（默认桥接网络） | `--net=host`（host 网络模式） |
|---|---|---|
| 容器的网络空间 | 独立 netns，有自己的 IP（如 172.17.0.2） | 与宿主机共用 netns |
| 流量路径 | 容器 → docker0 网桥 → 宿主机内核 FORWARD 链转发 → 出网卡 | 直接走宿主机网络，不经 docker0 和 FORWARD |
| 端口由谁决定 | 应用在容器内监听某端口，Docker 把宿主机端口转发进去 | 应用监听哪个端口，宿主机上就占用哪个端口，不需要映射 |
| 外部访问容器 | 依靠 `-p` 发布入站端口 | 直接访问宿主机端口 |

**`-p` 的格式**是 `-p 宿主机端口:容器端口`，左边是宿主机，右边是容器。应用实际监听 8080 时要写 `-p 9191:8080`；写 `-p 9191:9191` 意味着容器里的应用也监听 9191。

**两个常见误解需要避开。** 第一，`-p` 只管外部怎么访问容器（入站），不管容器怎么访问外部数据库（出站），所以"`-p` 映射错了导致连不上库"是错误的说法。第二，端口冲突两种模式都会失败：host 模式下应用直接占用宿主机端口，被占用就绑不上；`-p` 模式下宿主机端口被占用，映射就建不起来。换成 `-p` 本身并不能解决宿主机端口占用问题，要避开冲突需要换一个未被占用的宿主机端口，例如 `-p 9291:9191`。

#### **案例一：容器连不上外部数据库（DMException communication error）**

这是部署实习里唯一能讲透的技术排查，值得反复打磨。

**现象**：工单服务启动时报 `DMException communication error`，即连接达梦数据库失败。

**拓扑**：达梦数据库在第一台机器（`xxx.xxx.xxx.1`），工单服务部署在第二台机器（`xxx.xxx.xxx.2`），两者 IP 不同，但处于同一网段且互通。

**改动**：Shell 启动脚本里的 Docker 网络参数由 `-p` 改为 `--net=host`，重启后服务恢复正常。

**可能的根因（推断，需核实）**：第二台机器的防火墙可能拦截了转发路径。桥接网络下容器流量要经宿主机内核的 FORWARD 链转发出去，而 firewalld 或 iptables 的 FORWARD 默认策略常为 DROP，Docker 插入的转发规则可能未生效，或与 firewalld 规则顺序冲突。

这个推断与典型症状吻合：宿主机自己能连数据库，容器里连不上；换成 `--net=host` 后流量不再经过 docker0 和 FORWARD，因此立刻恢复。

**当时可做的验证**：在桥接容器里执行 `telnet 数据库IP 5236`（达梦默认端口），再在宿主机上执行同样命令对比。若宿主机通、容器不通，就查看 `iptables -L FORWARD` 的策略是否为 DROP；也可以临时 `systemctl stop firewalld` 后重试，或 `systemctl restart docker` 让它重建转发规则。

**面试话术**

> 当时工单服务起在第二台机器的容器里，达梦数据库在第一台机器。服务启动报 DMException communication error。我先确认宿主机直接连数据库是通的，说明地址、端口和数据库本身没问题，问题锁定在容器网络路径上。容器在默认桥接网络里，流量要经宿主机 FORWARD 链转发出去，我怀疑是防火墙没有放行 Docker 的转发规则；把启动脚本改成 `--net=host` 后绕开了这条路径，服务立刻连上了。事后我总结过：遇到"容器连不上外部依赖但宿主机能连"，应先对比容器内外分别访问的结果，再查 FORWARD 链和 Docker 的 iptables 规则，而不是直接换网络模式了事。

⚠ 上面的防火墙 FORWARD 是原理上最符合的推断，不是有日志证实的结论。说"我怀疑是……事后我理解是……"比"就是防火墙导致的"稳妥得多。

机制细节见 [[Linux 网络模式详解]]（网络模式与 iptables FORWARD 链）。

### **四、后端实习：告警模块 Bug 排查**

#### **4.1 案例二：监控大屏关键服务重复展示（DashboardStatisticsService）**

后端实习的一两个 Bug 中，这是目前唯一留下代码依据的案例，比泛泛地说"修了个 Bug"更有说服力。

**现象**：关键服务的统计结果重复展示。

**定位**：沿统计数据的组装流程排查，发现结果会合并 Docker 容器指标和进程指标，同一个服务可能同时出现在两类数据里。

**改动**：在合并后增加按服务名去重的处理。

```java
Collectors.toMap(
    c -> c.getServiceName() == null ? "" : c.getServiceName(),  // ① 键
    c -> c,                                                     // ② 值
    (existing, replacement) -> existing,                        // ③ 重复键怎么合并
    LinkedHashMap::new                                          // ④ 用哪种 Map
)
```

**`Collectors.toMap` 四个参数的含义**

| 参数 | 含义 |
|------|------|
| ① 键生成函数 | 用 `serviceName` 作为 Map 的键；为 null 时替换成空串，避免 null 作键 |
| ② 值生成函数 | 值就是容器对象本身，即用服务名找到对应记录 |
| ③ 重复键合并规则 | `(existing, replacement) -> existing`，保留先遇到的，丢弃后来的 |
| ④ Map 工厂 | `LinkedHashMap::new`，保留键的插入顺序，使去重后的展示顺序稳定 |

一句话读法：按服务名建立 Map，值存原容器对象；重复服务名保留第一条，并按首次出现的顺序保存。

**重复时为什么保留 Docker 那条**：合并列表时 Docker 指标在前、进程指标在后，同名时先进入的 Docker 记录被保留。这只有在确认展示需求确实如此时，才能说成设计目的。

**需要主动指出的边界**：`serviceName == null` 被统一映射成空串键，所以所有空名记录会互相去重，只剩一条。业务上如果空名记录不该合并，应先过滤掉，或为每条记录生成不冲突的键。不要只说"防止空指针"，这里主要是避免 null 作键，副作用是空值记录被合并。

**面试话术**

> 我实习时参与过数据中台监控大屏相关逻辑的维护。有一次发现关键服务的统计结果存在重复展示的问题。我沿着统计数据的组装流程排查，发现结果会合并 Docker 容器指标和进程指标，同一个服务可能同时出现在两类数据里。我在合并后增加了按服务名去重的处理，重复时保留先加入的记录，也就是当前合并顺序下优先保留 Docker 指标。修改后我计划用包含重复服务和非重复服务的数据验证结果，经同事验证，线上问题得到解决


#### **4.2 面试官可能顺着代码追问**

| 追问                        | 回答思路                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------ |
| 为什么会有重复服务？                | 这段逻辑把 Docker 容器指标和进程指标合并到同一份列表，同一服务可能被两类指标同时采集到，合并后就出现同名记录                                       |
| 为什么用 `serviceName` 去重？    | 这个场景里展示和业务识别用的是服务名。前提是服务名能唯一标识服务；若存在同名但实际不同的实例，应组合实例等字段作键                                        |
| 重复时为什么保留 `existing`？      | 表示保留先遇到的记录；合并顺序 Docker 在前，所以优先保留 Docker 记录。这个取舍需符合展示需求；若两类数据各有有效字段，应合并字段而不是直接丢一条                 |
| 为什么用 `LinkedHashMap`？     | 保留首次插入顺序，使去重后的展示顺序稳定，不因普通 HashMap 而不确定                                                           |
| `serviceName` 为 null 怎么办？ | 当前把 null 转成空串，所有空名记录被当作同一个键、只留一条。这是否合理要看业务；若空名记录应保留，需先过滤或生成不冲突的键                                 |
| 为什么要传第三个参数？               | 默认遇到重复键会抛出异常，第三个参数定义重复键的合并方式                                                                     |
| 怎么验证这次修改？                 | 准备"同一服务同时出现在两类指标"的数据，检查结果只保留一条；再检查不同服务都被保留，以及只有一类指标的服务正常保留，并特别验证服务名为空时的行为。若当时记录为待验证，就说这是计划中的验证用例 |
| 为什么不直接用 `distinct()`？     | `distinct()` 依赖对象的 equals 和 hashCode；这里要按 `serviceName` 这个特定字段判重，并明确重复时保留哪条，用 Map 更直接            |
| 同名记录的指标字段不同怎么办？           | 当前实现整条保留第一条、丢弃后面的，可能丢失部分字段。应按业务定义合并字段并明确优先级。这是"保留 existing"带来的取舍，很可能被追问                          |

一句话记忆：两类指标合并后按服务名去重，键是服务名、值是记录本身，重复时保留先出现的，LinkedHashMap 保留首次出现顺序；空服务名会映射到同一个空串键，需确认是否符合业务预期。

相关知识可参考 [[StreamAPI]]（`Collectors.toMap` 的重复键异常与合并函数）。

#### **4.3 面试官问"遇到过什么问题、怎么解决的"**

用上面任一案例套用固定结构：现象、排查、定位、修复、验证。职责要限定在真实范围内，协助就不要说成独立解决。

**回答模板**

> 我在【公司】实习时参与【模块】的维护。有一次处理一个【问题类型】，现象是【真实现象】。
>
> 我先根据问题出现的时间和业务场景查看日志，确认异常发生在哪个接口或处理环节；然后沿着调用堆栈定位到相关代码，用断点检查请求参数和关键业务条件。最后发现原因是【真实原因】，我针对这个位置做了【真实修改】，并通过【实际验证方式】确认问题解决，没有影响相关流程。
>
> 这件事让我意识到，排查问题不能只看接口报错，要把日志、调用链和业务条件结合起来定位；修复后也要验证正常场景和相关边界情况。

面试官会继续追问以下五点，提前准备具体答案：问题表现是什么、谁发现的、影响范围多大；日志里看到什么，如何缩小排查范围；断点打在哪个方法或判断附近，检查了哪些参数；最终根因是什么，改了哪段逻辑；怎么验证修复有效，是否回归了相关场景。

编不出根因就不要编。面试官顺着细节追问时，虚构的故事很容易露馅，只讲你真正记得的现象、改动点和验证方式。
