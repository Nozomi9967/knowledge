### 问题背景：RTT 的开销

正常情况下，客户端每发一条命令，都要走一个完整的**请求-响应**往返：

```
客户端                        Redis服务端
  |--- SET key1 val1 ------->|
  |<-- OK ------------------|   ← 等这个 OK 回来，才能发下一条
  |--- SET key2 val2 ------->|
  |<-- OK ------------------|
  |--- SET key3 val3 ------->|
  |<-- OK ------------------|
```

每一次往返的耗时叫 **RTT（Round Trip Time）**。本机回环大概 0.1ms，同城机房大概 1ms，跨城可能 10ms+。

**100 条命令 × 1ms RTT = 100ms**，全在等网络，Redis 本身处理只需要不到 1ms。

---

### Pipeline 的解法

Pipeline 把多条命令**打包成一批**，一次性发过去，服务端处理完**一次性全部返回**：

```
客户端                              Redis服务端
  |--- SET key1 / SET key2 / SET key3 ------->|  ← 一次发出
  |<-- OK / OK / OK --------------------------|  ← 一次收回
```

**100 条命令只需要 1 次 RTT**，无论命令数量增加，等待时间不变。

---

### 关键点：Pipeline ≠ 事务

这是面试常考的区分：

||Pipeline|MULTI/EXEC 事务|
|---|---|---|
|原子性|❌ 无，命令可能穿插执行|✅ 保证原子执行|
|服务端缓冲|客户端打包，网络传输优化|服务端缓冲命令队列|
|错误处理|某条失败不影响其他|运行时错误不回滚|
|适用场景|批量写入、预热缓存|需要隔离的多步操作|

Pipeline 的"批"是在**网络层**做的，服务端还是**逐条顺序执行**，没有原子保证。

---

### 和"高并发"的关系

回到面试题的语境——为什么 Pipeline 属于**高并发**手段：

- Redis 单线程处理命令，瓶颈不在 CPU，在**网络 I/O 的等待时间**
- 大量客户端同时发请求时，每个连接都在等 RTT，连接数堆积
- Pipeline 让单个连接在同样时间内搬运更多命令，**单位时间内的有效吞吐量**大幅提升
- 减少了无效等待占用的连接资源，间接降低了服务端的并发压力

所以追问 _"如何进一步提高吞吐量"_ 时，Pipeline 是比"加机器"更轻量的第一步答案。
