### **核心思路是把三种能力拆成三个独立的 `GlobalFilter`，通过 `Ordered` 接口显式定义执行顺序——黑名单最先拦截（成本最低、命中即断），接口限流其次（保护后端），用户限流最后（精细化控制）——三者都基于 Redis + Lua 保证原子性，链式短路返回 429/403。**

  

## **整体架构**

  

Spring Cloud Gateway 基于 WebFlux，过滤器分两类：`GlobalFilter`（全局，对所有路由生效）和 `GatewayFilter`（局部，通过路由配置绑定）。这个场景三种能力都是横切的，用 `GlobalFilter` 最合适。

  

执行顺序通过实现 `Ordered` 或 `getOrder()` 决定，**数字越小优先级越高**。设计如下：

  

| 过滤器 | Order | 职责 | 短路条件 |
|---|---|---|---|
| `BlacklistFilter` | -100 | 检查用户/IP 是否在黑名单 | 命中直接返回 403 |
| `ApiRateLimitFilter` | -50 | 按接口路径限流 | 超阈值返回 429 |
| `UserRateLimitFilter` | -10 | 按用户 ID 限流 | 超阈值返回 429 |
| Gateway 内置转发 | Integer.MAX_VALUE | 路由转发 | — |

  

**排序的核心哲学：越"便宜"、越"确定性拒绝"的检查放越前，避免为注定要被拒的请求做无谓的下游调用。**

  

- **黑名单第一**：Redis 单次 `SISMEMBER` 或本地缓存查询，成本极低，命中即断，能省下后续所有限流的计算和 Redis 调用。

- **接口限流第二**：粒度粗（按 path），Key 数量少，Redis 命中率高，能第一时间保护"某个爆款接口"被打挂。

- **用户限流第三**：粒度细（按 uid + path），Key 空间大，放在最后能保证前两道已经过滤掉大部分脏流量，减少 Redis 压力。

  

## **黑名单过滤器**

  

```java

@Component

public class BlacklistFilter implements GlobalFilter, Ordered {

  

private final ReactiveStringRedisTemplate redis;

private final Cache<String, Boolean> localCache =

Caffeine.newBuilder().expireAfterWrite(30, SECONDS).maximumSize(10_000).build();

  

@Override

public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {

String userId = extractUserId(exchange); // 从 JWT 或 Header 解析

String ip = extractClientIp(exchange);

  

// 本地缓存兜一层，避免每个请求都打 Redis

Boolean cached = localCache.getIfPresent(userId);

if (Boolean.TRUE.equals(cached)) {

return reject(exchange, HttpStatus.FORBIDDEN, "user in blacklist");

}

  

return redis.opsForSet().isMember("blacklist:user", userId)

.zipWith(redis.opsForSet().isMember("blacklist:ip", ip))

.flatMap(tuple -> {

if (tuple.getT1() || tuple.getT2()) {

localCache.put(userId, true);

return reject(exchange, HttpStatus.FORBIDDEN, "blacklisted");

}

return chain.filter(exchange);

});

}

  

@Override public int getOrder() { return -100; }

}

```

  

**要点**：

- **本地缓存 + Redis 二级结构**：黑名单变更低频，Caffeine 本地缓存 30s，命中率极高。

- **响应式非阻塞**：用 `ReactiveStringRedisTemplate`，别用同步的 `StringRedisTemplate`，会阻塞 Netty 的 EventLoop。

- **短路返回**：命中黑名单直接写 403，不调用 `chain.filter()`。

  

## **接口限流过滤器**

  

按接口的限流，粒度是**路径 + 方法**，比如 `POST /api/order/create`。用**滑动窗口 + Redis Lua** 保证原子性：

  

```java

@Component

public class ApiRateLimitFilter implements GlobalFilter, Ordered {

  

private final ReactiveStringRedisTemplate redis;

private final RateLimitProperties properties; // 前面题目里的 @RefreshScope Bean

private final RedisScript<Long> slidingWindowScript; // Lua 脚本

  

@Override

public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {

String path = exchange.getRequest().getPath().value();

String method = exchange.getRequest().getMethodValue();

String apiKey = method + ":" + path;

  

RuleConfig rule = properties.getApiRules().get(apiKey);

if (rule == null) return chain.filter(exchange); // 未配置则放行

  

String redisKey = "ratelimit:api:" + apiKey;

long now = System.currentTimeMillis();

  

return redis.execute(slidingWindowScript,

List.of(redisKey),

List.of(String.valueOf(now), String.valueOf(rule.getWindowMs()),

String.valueOf(rule.getLimit())))

.single()

.flatMap(allowed -> allowed == 1L

? chain.filter(exchange)

: reject(exchange, HttpStatus.TOO_MANY_REQUESTS, "api rate limit"));

}

  

@Override public int getOrder() { return -50; }

}

```

  

Lua 脚本用**有序集合**实现精确滑动窗口：

  

```lua

-- KEYS[1] = redis key

-- ARGV[1] = now(ms), ARGV[2] = window(ms), ARGV[3] = limit

local key = KEYS[1]

local now = tonumber(ARGV[1])

local window = tonumber(ARGV[2])

local limit = tonumber(ARGV[3])

  

redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

local count = redis.call('ZCARD', key)

if count >= limit then

return 0

end

redis.call('ZADD', key, now, now)

redis.call('PEXPIRE', key, window)

return 1

```

  

**为什么用 Lua**：`ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` 三步必须原子执行，否则并发下会出现"计数不准，放行超额请求"的问题。

  

## **用户限流过滤器**

  

结构和接口限流基本对称，Key 换成 `uid + apiKey` 即可：

  

```java

@Component

public class UserRateLimitFilter implements GlobalFilter, Ordered {

  

@Override

public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {

String userId = extractUserId(exchange);

if (userId == null) return chain.filter(exchange); // 匿名用户不走此限流

  

String path = exchange.getRequest().getPath().value();

String redisKey = "ratelimit:user:" + userId + ":" + path;

  

RuleConfig rule = properties.getUserRules().getOrDefault(path, defaultRule);

// ...同样调用 Lua 脚本

}

  

@Override public int getOrder() { return -10; }

}

```

  

**注意点**：

- **匿名请求怎么办**：如果用户未登录，可以退化为按 IP 限流，或者干脆放到接口限流那一层兜底。

- **热点用户识别**：可以叠加一个"热点探测"，对超频用户临时加入黑名单（复用第一层），实现自适应封禁。

- **Key 空间控制**：`uid + path` 组合会导致 Key 爆炸，务必设置 TTL（比 window 略长即可），别让 Redis 无限膨胀。

  

## **共用的响应工具方法**

  

```java

private Mono<Void> reject(ServerWebExchange exchange, HttpStatus status, String msg) {

ServerHttpResponse response = exchange.getResponse();

response.setStatusCode(status);

response.getHeaders().add("Content-Type", "application/json;charset=UTF-8");

String body = String.format("{\"code\":%d,\"msg\":\"%s\"}", status.value(), msg);

DataBuffer buffer = response.bufferFactory().wrap(body.getBytes(StandardCharsets.UTF_8));

return response.writeWith(Mono.just(buffer));

}

```

  

## **执行顺序的进一步说明**

  

Gateway 内部还有一批预置的 `GlobalFilter`，需要留意和它们的相对顺序：

  

| 内置过滤器 | Order |
|---|---|
| `RemoveCachedBodyFilter` | -2147483648 |
| `AdaptCachedBodyGlobalFilter` | -2147482648 |
| `NettyWriteResponseFilter` | -1 |
| `ForwardPathFilter` | 0 |
| `RouteToRequestUrlFilter` | 10000 |
| `NettyRoutingFilter` | Integer.MAX_VALUE |

  

我们自定义的 -100/-50/-10 处于**路由匹配之后、真正转发之前**，正好是"已知目标路由但还没打到下游"的黄金拦截点。如果需要读取请求体做限流（比如按 body 里的某个字段限流），必须放在 `AdaptCachedBodyGlobalFilter` 之后（order > -2147482648），否则拿不到 body。

  

## **可选增强**

  

- **降级链路**：Redis 挂了怎么办？在每个 Filter 里用 `onErrorResume` 兜底，Redis 异常时**放行而非拒绝**（Fail-Open），避免限流组件反过来变成故障源。真需要严格模式时才 Fail-Close。

- **动态规则**：黑名单和限流阈值都接入 Nacos，按上一题的 `@RefreshScope` + Listener 双通道方案。

- **指标埋点**：每个 Filter 通过 Micrometer 打点，统计"命中率、拒绝率、Redis RT"，方便观测和调参。

- **令牌桶 vs 滑动窗口**：如果需要平滑限流（允许突发），可以把 Lua 换成令牌桶算法，或者直接接入 Sentinel Gateway 适配层，用官方成熟的 `SentinelGatewayFilter`。

- **多维度组合限流**：可以在一个 Filter 里做多维度检查（uid + api + ip），Lua 里一次性判断多个 Key，减少 Redis 往返。

  

## **面试口述要点**

  

口述时按这个骨架讲：**先讲三个 Filter 的职责分离，然后重点讲执行顺序的设计哲学——从"最便宜、最确定拒绝"到"最精细"，即黑名单 → 接口 → 用户；接着展开每一层的实现要点——响应式 Redis、Lua 保证原子性、滑动窗口 vs 令牌桶的取舍；然后强调几个易踩的坑——EventLoop 不能阻塞、Key 要设 TTL、Redis 挂了要 Fail-Open、读 body 要放在 `AdaptCachedBodyGlobalFilter` 之后；最后升华一下：生产上通常还会叠加动态配置（Nacos）、观测（Micrometer）、降级（Sentinel）三驾马车，形成完整的流量治理闭环。** 这样答基本能覆盖 Gateway + 限流的所有考点。
