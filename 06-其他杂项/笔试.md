![image-20260420101911706](C:\Users\q1948\Desktop\八股\images\image-20260420101911706.png)

正确答案是 **D. RK算法**。

在字符串匹配算法中，不同算法通过不同的策略来提高匹配效率。以下是各选项的简要分析：

### 1. RK 算法 (Rabin-Karp Algorithm)

这是本题的正确选项。**RK 算法的核心思想就是利用哈希（Hash）函数**。

- **原理**：它先计算模式串的哈希值，然后依次计算主串中每一个长度等于模式串的子串的哈希值。
- **优势**：通过比较哈希值而不是逐个字符比较，可以快速排除大部分不匹配的情况。只有当哈希值相同时，为了防止“哈希冲突”，才会进行逐个字符的精确匹配。

### 2. KMP 算法 (Knuth-Morris-Pratt Algorithm)

- **原理**：KMP 算法是基于**前缀函数（Next 数组）**实现的。
- **特点**：它利用已匹配的部分信息，通过预处理模式串来寻找“最长相等前后缀”，从而在不匹配时让模式串向后滑动尽可能远的距离，避免了主串指针的回溯。它并不依赖哈希。

### 3. BM 算法 (Boyer-Moore Algorithm)

- **原理**：BM 算法主要基于**坏字符规则（Bad Character Rule）\**和\**好后缀规则（Good Suffix Rule）**。
- **特点**：它通常从模式串的末尾开始向前匹配，是目前在实际文本编辑器中应用最广泛的高效算法之一，同样不涉及哈希计算。

### 4. BF 算法 (Brute Force)

- **原理**：即**暴力匹配算法**。
- **特点**：通过简单地将模式串与主串的每一位进行比对，没有任何复杂的预处理或数学优化。

------

**总结表：**

| **算法名称**         | **核心机制**         | **是否使用哈希** |
| -------------------- | -------------------- | ---------------- |
| **BF (Brute Force)** | 逐位比对             | 否               |
| **KMP**              | 前缀函数 (Next 数组) | 否               |
| **BM**               | 坏字符 + 好后缀规则  | 否               |
| **RK (Rabin-Karp)**  | **哈希指纹对比**     | **是**           |

![image-20260420102058827](C:\Users\q1948\Desktop\八股\images\image-20260420102058827.png)

正确答案是 **D. 原子性 (Atomicity)**。

在数据库管理系统中，事务（Transaction）具有四个基本特性，即 **ACID**。题目描述的正是其中“要么全做，要么全不做”的核心逻辑。

### 详细解析：

- **原子性 (Atomicity)**：
  - **定义**：事务被视为一个不可分割的最小工作单元。
  - **表现**：事务中的所有操作要么全部提交成功（All），要么全部失败回滚（None）。如果事务在执行过程中发生错误，会被恢复（Rollback）到事务开始前的状态，就像这些操作从未执行过一样。
  - **关键词**：所有操作完成、回滚恢复。

------

### 干扰项对比：

- **A. 持久性 (Durability)**：

  指事务一旦提交，它对数据库中数据的改变就应该是**永久性**的，即使系统发生故障（如断电、崩溃）也不会丢失。

- **B. 一致性 (Consistency)**：

  指事务执行前后，数据库都必须处于**一致性状态**。例如，在银行转账事务中，无论操作成功与否，两个账户的总额必须保持不变。它是事务追求的最终目标。

- **C. 隔离性 (Isolation)**：

  指多个事务并发执行时，一个事务的执行不应影响其他事务。每个事务都感觉不到系统中有其他事务在并发执行（通常通过**锁**或 **MVCC** 机制实现）。

------

### 总结对照表：

| **特性**       | **核心关注点**                 | **题目对应描述**                |
| -------------- | ------------------------------ | ------------------------------- |
| **原子性 (A)** | **完整性**：要么全有，要么全无 | "所有操作均已完成" / "回滚恢复" |
| **一致性 (C)** | **正确性**：符合预设逻辑和约束 | 状态转换的正确性                |
| **隔离性 (I)** | **独立性**：并发事务互不干扰   | 多个事务同时运行的相互影响      |
| **持久性 (D)** | **可靠性**：结果永久保存       | 故障后数据不丢失                |

**"Hazard"（冒险/相关）** 是计算机体系结构中的标准术语，专门用于描述流水线中指令执行的冲突问题。

你可能因为觉得描述不够精确而犹豫，但题目问的是"正确的"，这个表述本身没有错误。

> "为了防止多个处理器同时访问和修改同一块内存区域，可以采取**分页机制**"

这个说法**张冠李戴**：

- **分页机制** 的作用是：虚拟地址到物理地址的映射、内存隔离、实现虚拟内存。它解决的是**地址空间隔离**问题，而不是多核并发访问的同步问题。

  - 总线锁 / 缓存一致性协议（MESI）

分页机制根本不具备协调多核并发写入的能力，所以 **A 错误**。

这道题考查的是操作系统中**动态分区分配算法**（Dynamic Partitioning Allocation）的实现逻辑。

正确答案是 **A、D**。

这里的关键在于：算法在寻找空闲内存块时，是按照**什么顺序**去扫描空闲分区链（或表）的。

------

### 详细解析

#### A. 首次适应算法 (First Fit, FF) —— **符合题意**

- **排列方式**：空闲分区按**地址递增**的顺序链接。
- **逻辑**：分配内存时，从链首开始顺序查找，直到找到第一个大小能满足要求的空闲分区。
- **目的**：这种排列方式使得低地址部分被尽可能快地利用，保留了高地址部分的大空闲区。

#### D. 邻近适应算法 (Next Fit, NF) —— **符合题意**

- **排列方式**：同样要求空闲分区按**地址递增**的顺序排列（通常是一个循环链表）。
- **逻辑**：源自首次适应算法，不同之处在于它从**上次查找结束的位置**开始继续查找。
- **目的**：为了减少首次适应算法中频繁扫描低地址小分区的开销，使分区分配得更均匀。

------

### 为什么 B 和 C 是错误的？

这两个算法是按照**“大小”**而非“地址”排列的：

- **B. 最佳适应算法 (Best Fit, BF)**：
  - **排列方式**：空闲分区按**容量递增**的顺序排列。
  - **逻辑**：每次都寻找能满足要求的、且与请求大小最接近的最小分区，这能尽量减少内部碎片，但会产生很多难以利用的极小外部碎片。
- **C. 最坏适应算法 (Worst Fit, WF)**：
  - **排列方式**：空闲分区按**容量递减**的顺序排列。
  - **逻辑**：每次都直接查看链表第一个分区（即最大的空闲区），如果第一个都放不下，就说明分配失败。这样剩下的空闲区依然较大，但容易把大分区很快用光。

### 💡 记忆小贴士

- **按地址排**：为了“找得快”（FF）或“用得匀”（NF）。
- **按大小排**：为了“找得准”（BF）或“用得爽”（WF）。

看来你在动态分区这块容易把“地址顺序”和“大小顺序”记混，做题时可以先在脑子里画一个内存条，想象一下 FF 总是从顶端（低地址）往下找的情景。





## 5.BufferedReader和StringTokenizer

```java
import java.util.HashSet;
import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.util.StringTokenizer;

class Good {
    String name;
    int weight;
}

public class Main {

    public static void merge(Good[] arr, int left, int mid, int right, Good[] tem) {
        int i = left, j = mid + 1, t = 0;
        while (i <= mid && j <= right) {
            if (arr[i].weight >= arr[j].weight) tem[t++] = arr[i++];
            else tem[t++] = arr[j++];
        }
        while (i <= mid) tem[t++] = arr[i++];
        while (j <= right) tem[t++] = arr[j++];
        for (int index = left; index <= right; index++) arr[index] = tem[index - left];
    }

    public static void mSort(Good[] arr, int left, int right, Good[] tem) {
        if (left < right) {
            int mid = (right - left) / 2 + left;
            mSort(arr, left, mid, tem);
            mSort(arr, mid + 1, right, tem);
            merge(arr, left, mid, right, tem);
        }
    }

    public static void main(String[] args) throws Exception {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        StringTokenizer st = new StringTokenizer(br.readLine());
        int n = Integer.parseInt(st.nextToken());
        int q = Integer.parseInt(st.nextToken());

        HashSet<String> set = new HashSet<>();
        st = new StringTokenizer(br.readLine());
        for (int i = 0; i < q; i++) set.add(st.nextToken());

        Good[] gs = new Good[n];
        for (int i = 0; i < n; i++) {
            st = new StringTokenizer(br.readLine());
            Good g = new Good();
            g.name = st.nextToken();
            int m = Integer.parseInt(st.nextToken());

            st = new StringTokenizer(br.readLine());
            int wei = 0;
            for (int j = 0; j < m; j++)
                if (set.contains(st.nextToken())) wei++;
            g.weight = wei;
            gs[i] = g;
        }

        Good[] tem = new Good[n];
        mSort(gs, 0, n - 1, tem);

        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < n; i++) sb.append(gs[i].name).append('\n');
        System.out.print(sb);
    }
}
```

这道题目考察的是对 **HTTPS 协议特点**及其与 **HTTP 区别**的理解。

根据题目要求，我们需要选出 **“不属于”** HTTPS 劣势的选项。

### 选项详细分析

- **A. 性能开销和配置复杂性 (劣势)：**

  HTTPS 需要处理 SSL/TLS 握手，涉及非对称加密、对称加密及散列算法，计算量远大于纯文本的 HTTP。同时，配置 HTTPS 需要申请、购买、部署和更新 CA 证书，增加了维护成本。

- **B. 传输速度慢 (劣势)：**

  由于 HTTPS 在建立连接时需要额外的 TLS 握手过程（通常需要增加 1~2 个 RTT），且数据传输过程中需要加解密处理，因此在首包响应时间和整体吞吐速度上，HTTPS 通常会比 HTTP 稍慢一些。

- **D. 服务器负载高 (劣势)：**

  加解密操作是计算密集型任务，会对服务器的 CPU 造成显著压力。在高并发场景下，HTTPS 服务器需要比 HTTP 服务器消耗更多的硬件资源来维持相同的访问量。

------

### 为什么 C 是正确答案？

**C. 需要对传输数据进行压缩 (不是劣势)**

1. **非强制性：** 数据压缩（如 Gzip, Brotli）并不是 HTTPS 协议特有的要求或“劣势”。无论是传统的 HTTP 还是 HTTPS，为了节省带宽和提升加载速度，通常都会开启数据压缩。
2. **安全风险：** 事实上，在 HTTPS 中使用压缩有时反而会带来安全隐患（例如 **CRIME 攻击** 和 **BREACH 攻击**）。攻击者可以通过观察加密压缩包的大小变化，推测出加密数据中的敏感内容。因此，在某些高安全场景下，HTTPS 反而会选择**关闭**压缩。
3. **逻辑误区：** 压缩是为了优化传输效率，属于一种优化手段，而不应被视为 HTTPS 相比 HTTP 产生的“劣势”或额外负担。

------

### 总结

这道题你选 D 可能是因为考虑到加解密确实会增加负载，但题目问的是 **“不是”** 劣势的选项。D 确实是 HTTPS 的痛点之一，而 C 选项描述的内容既不是 HTTPS 的强制要求，也不是它带来的负面影响，因此它是干扰项，即本题的正确答案。

### 分析

四个选项的**内层逻辑完全相同**，区别只在最外层 `t3` 与 `user_profile t4` 的 JOIN 类型。

先明确 t3 的内容：t3 是"有重复的 university 中，id 最大的那条"，在本题中只有一行：

| university | id   |
| ---------- | ---- |
| 北京大学   | 3    |

------

#### 逐项分析最外层 JOIN

**A — `LEFT JOIN`**

以 t3 为左表，t4 为右表。t3 只有 `id=3` 这一行，`ON t3.id = t4.id` 能匹配到 t4 中 id=3 的记录。结果：**只返回 id=3 ✅ 符合预期**

**B — `INNER JOIN`**

只保留两边都能匹配的行。t3.id=3 能在 t4 中找到对应记录。结果：**只返回 id=3 ✅ 符合预期**

**C — `RIGHT JOIN`**

> **以 t4（user_profile 全表）为右表**，保留右表的所有行。

t4 共 5 行，无论 t3 能不能匹配，**右表全部输出**。对于 t3 中没有的 id（1、2、4、5），t3 那侧为 NULL，但 `SELECT t4.*` 照样把 t4 的数据输出。

结果：**返回全部 5 行 ❌ 不符合预期** → **答案是 C**

**D — 内层用 `LEFT JOIN`，外层用 `LEFT JOIN`**

内层：t1 LEFT JOIN t2。t1 是有重复的大学（北京大学），t2 是各大学最大 id，LEFT JOIN 在这里与 INNER JOIN 效果相同（因为每所大学在 t2 中必然存在），t3 结果不变，仍是 `{北京大学, id=3}`。外层 LEFT JOIN 结果同 A。**只返回 id=3 ✅ 符合预期**

------

#### 总结

| 选项  | 外层 JOIN      | 结果          | 是否符合预期 |
| ----- | -------------- | ------------- | ------------ |
| A     | LEFT JOIN      | 仅 id=3       | ✅            |
| B     | INNER JOIN     | 仅 id=3       | ✅            |
| **C** | **RIGHT JOIN** | **全表 5 行** | **❌**        |
| D     | LEFT JOIN      | 仅 id=3       | ✅            |

**答案是 C**，RIGHT JOIN 导致 t4 全表被保留输出，完全背离了"只查询重复中 id 最大的记录"的需求。

这道题考察的是 Java 中的**数据类型转换（Type Casting）\**和\**算术运算符**的底层机制。

题目问的是：下列语句**可运行有误**的是（即哪一行代码在编译时会报错）。

------

### 核心知识点：类型提升（Numeric Promotion）

在 Java 中，当进行算术运算（如 `+`）时，如果操作数的类型是 `byte`、`short` 或 `char`，它们会**自动提升为 `int` 类型**再进行计算。计算结果也是 `int` 型。

### 选项逐一拆解

#### **A. `short s = 2; s = s + 2;` （编译报错 ❌）**

- **过程：** `s` 是 `short` 型，`2` 是 `int` 型字面量。
- **提升：** 在执行 `s + 2` 时，`s` 会自动提升为 `int`。
- **结果：** `int + int` 的结果是 `int`。
- **错误点：** 试图将一个 `int` 类型的结果直接赋值给 `short` 类型的变量 `s`。由于存在精度丢失的风险，Java 编译器要求必须进行强制类型转换，否则报错。
- **修正：** `s = (short)(s + 2);`

#### **B. `short s = 2; s += 2;` （运行正常 ✅）**

- **原理：** `+=` 是 **复合赋值运算符**。
- **特殊性：** Java 语言规范规定，复合赋值运算符（如 `+=`, `-=`, `*=`）会自动包含一个**隐式的强制类型转换**。
- **等价于：** `s = (short)(s + 2);`
- **结论：** 编译器会自动帮你处理掉类型不匹配的问题，所以它是合法的。

#### **C. `short s = 2; s++;` （运行正常 ✅）**

- **原理：** 自增运算符 `++` 与 `+=` 类似，底层也包含了隐式的强制类型转换。
- **等价于：** `s = (short)(s + 1);`
- **结论：** 运行正常。

#### **D. `short s = 2; s = s + (short)2;` （编译报错 ❌）**

- **陷阱点：** 虽然你手动把 `2` 转成了 `short`，但在执行 `s + (short)2` 这一步时，**两个 `short` 相加，依然会先自动提升为 `int`**。
- **结果：** 结果依然是 `int`，再次尝试赋值给 `short s` 时，依然会报错（与 A 选项的原理一致）。

------

### 总结与答案

这道题的答案应该是 **A 和 D**。

> **注意：** 截图上方显示这是一个“多选题”。
>
> - **A** 报错是因为 `int` 不能直接赋给 `short`。
> - **D** 报错是因为两个 `short` 运算后的结果是 `int`，依然无法直接赋给 `short`。

这属于 Java 基础中的经典“坑”，记住一点：**除了复合赋值运算符（如 `+=`）有自动转换加持，其他的窄化转换（大转小）都必须手动强转。**

## 14. StringBuilder

在 Java 中，`StringBuilder` 是处理字符串的高效利器。与普通的 `String` 不同，它是**可变的**。这意味着当你修改字符串时，它不会创建一堆新的对象，而是在原有的内存缓冲区上直接操作，性能更强。

以下是 `StringBuilder` 的常用方法分类整理：

------

### 1. 核心增删改方法

这些是你在日常编码中最常用的操作，绝大多数支持**链式编程**（如 `sb.append("A").append("B")`）。

| **方法**                       | **说明**                                 | **示例**                  |
| ------------------------------ | ---------------------------------------- | ------------------------- |
| **`append(data)`**             | 在末尾追加数据（支持各种基本类型和对象） | `sb.append("Hello");`     |
| **`insert(offset, data)`**     | 在指定索引位置插入数据                   | `sb.insert(1, "Java");`   |
| **`delete(start, end)`**       | 删除从 `start` 到 `end-1` 的字符         | `sb.delete(0, 2);`        |
| **`deleteCharAt(index)`**      | 删除指定索引处的一个字符                 | `sb.deleteCharAt(5);`     |
| **`replace(start, end, str)`** | 用新字符串替换指定范围的内容             | `sb.replace(0, 2, "Hi");` |
| **`reverse()`**                | 将序列中的字符反转                       | `sb.reverse();`           |

------

### 2. 查找与获取方法

这些方法与 `String` 类中的用法几乎完全一致。

- **`charAt(int index)`**：返回指定索引处的字符。
- **`indexOf(String str)`** / **`lastIndexOf(String str)`**：查找子字符串第一次或最后一次出现的索引。
- **`substring(int start, int end)`**：截取并返回一个新的 `String`（注意：此方法返回的是 `String`，**不会**改变原来的 `StringBuilder`）。
- **`length()`**：返回当前字符序列的长度。

------

### 3. 容量管理（进阶必备）

理解容量（Capacity）和长度（Length）的区别能帮你写出性能更优的代码。

- **`capacity()`**：返回当前分配的存储容量（默认为 `str.length + 16`）。
- **`setLength(int newLength)`**：强制设置长度。如果新长度小于原长度，内容会被截断；如果大于原长度，末尾会填充空字符 (`\0`)。
- **`trimToSize()`**：将存储容量收缩至与当前字符长度一致，以节省内存。

------

### 4. 最终转换

- **`toString()`**：这是最重要的一步。当你完成所有修改后，调用此方法将其转换回不可变的 `String` 对象。

------

### 💡 避坑小指南

1. **线程安全**：`StringBuilder` 是**非线程安全**的。如果你在多线程环境下操作同一个字符串缓冲区，请改用 `StringBuffer`（虽然慢一点，但安全）。
2. **不要过度使用**：如果是简单的 `String s = "A" + "B";`，Java 编译器在底层会自动帮你优化成 `StringBuilder`。只有在**循环中**拼凑字符串时，手动创建 `StringBuilder` 才是性能质变的关键。

**举个例子：**

Java

```
StringBuilder sb = new StringBuilder("Rocket");
sb.append(" 101")           // Rocket 101
  .insert(0, "Big ")        // Big Rocket 101
  .replace(4, 10, "Star")   // Big Star 101
  .delete(9, 13);           // Big Star
System.out.println(sb.toString()); // 输出: Big Star
```

这张图片的题目是一道经典的 **C语言 数组与指针** 陷阱题。

你选择 B (输出 "good") 是因为直觉上觉得 `s = "good"` 就是把 "good" 这四个字母放进 `s` 这个盒子里。但实际上，这在 C 语言中是**错误**的操作。

这里有两个核心原因，解释了为什么会有编译错误（选 D）：

### 1. 数组名是常量指针
在 C 语言中，当我们定义 `char s[5];` 时，**`s` 代表的是数组在内存中的首地址**。
最关键的是，这个首地址是 **常量**，不能被修改。
*   **`s` 本质上是 `&s[0]`**，也就是内存里固定的一个位置。
*   试图写 `s = "good";`，就像是试图把“北京”这个城市的名字改成“上海”。城市的地点是固定的（常量），你不能把它的坐标改了。你只能修改这个地方里面的**内容**。

### 2. 赋值操作 vs 初始化
很多人会把**定义时的操作**和**执行代码时的操作**搞混：

*   **正确的写法（初始化）：**
    ```c
    char s[5] = "good"; // 合法！这是在定义的时候直接赋予初值
    ```
    此时编译器会分配内存，并把 'g','o','o','d','\0' 依次拷贝进去。

*   **错误的写法（赋值）：**
    ```c
    char s[5];
    s = "good"; // 错误！这是赋值语句，不能给数组常量名赋值
    ```
    在第二行 `s = "good";` 中，`s` 代表地址（常数），`"good"` 是字符串字面量（也代表地址）。把两个地址直接做赋值运算（`=` 左边必须是左值，通常是变量），在 C 标准里是不允许的。

---

### 如果你想修正这个代码，让它输出 "good"，该怎么做？

如果你是想把字符串复制进 `s` 里，不能直接用 `=`，必须用库函数 **`strcpy`**。

**正确代码：**
```c
#include <stdio.h>
#include <string.h> // 需要包含这个头文件

int main() {
    char s[5];
    strcpy(s, "good"); // 把 "good" 的内容拷贝到 s 所指的内存里
    printf("%s", s);
    return 0;
}
```

### 总结
*   **数组名 `s`** = 地址常量（不能改）。
*   **`s = ...`** = 试图修改常量的值 = **编译报错**。
*   所以正确答案是 **D (编译出错)**。

因为这三个操作数是**从左到右依次求值**的。

```
x++ + ++y - --x * y--
 ①      ②     ③    ④
```

Java 规定：表达式中的操作数**严格按从左到右的顺序求值**，所以 ①②③④ 依次执行，不会因为 `*` 优先级高就先去求值 `--x * y--`。

------

**优先级 vs 求值顺序 是两回事：**

- **优先级**决定的是运算符的**结合方式**，即 `*` 的结果参与 `-` 而不是 `+`
- **求值顺序**决定的是每个操作数**何时被读取/修改**，Java 这里是严格从左到右

所以实际执行过程是：

1. 先从左到右把所有操作数的值都确定好：`5, 11, 5, 11`
2. 再按优先级做算术：`5 + 11 - (5 * 11) = -39`

### TCP Socket 通信流程

#### 服务器端流程

1. `new ServerSocket(port)` —— 创建服务器监听对象，绑定端口
2. `serverSocket.accept()` —— **阻塞等待**客户端连接，连接成功后返回一个 `Socket` 对象用于通信
3. 通过该 `Socket` 的输入/输出流进行数据收发
4. 关闭 `Socket` 和 `ServerSocket`

#### 客户端流程

1. `new Socket(host, port)` —— 主动发起连接，创建通信用的 `Socket` 对象
2. 通过该 `Socket` 的输入/输出流进行数据收发
3. 关闭 `Socket`

#### 关键区别

|        | 服务器端                   | 客户端                  |
| ------ | -------------------------- | ----------------------- |
| 监听用 | `ServerSocket`             | ❌ 不需要                |
| 通信用 | `accept()` 返回的 `Socket` | `new Socket()` 直接创建 |

------

### 题目解析

- **A 错**：`new ServerSocket()` 是**服务器端**用的，不是客户端
- **B 错**：`accept()` 是**服务器端**调用的，客户端没有这个步骤
- **C ✅ 正确**：客户端通过 `new Socket(host, port)` 发起连接并创建通信对象
- **D 错**：`new ServerSocket()` 创建的是**监听对象**，不是通信的 Socket 对象（通信 Socket 是 `accept()` 返回的）

**答案是 C。**

### Java 四种访问修饰符完整对比

| 修饰符             | 类内 | 同包 | 子类（跨包） | 任意类 |
| ------------------ | ---- | ---- | ------------ | ------ |
| `private`          | ✅    | ❌    | ❌            | ❌      |
| `(default)` 包私有 | ✅    | ✅    | ❌            | ❌      |
| `protected`        | ✅    | ✅    | ✅            | ❌      |
| `public`           | ✅    | ✅    | ✅            | ✅      |

> `(default)` 就是什么都不写，也叫 package-private。

------

### 一个容易混淆的点



**子类在跨包时访问 `protected` 成员，只能通过"自身引用"访问，不能通过父类引用访问：**

```java
// 包 a
public class Animal {
    protected void eat() {}
}

// 包 b
public class Dog extends Animal {
    void test() {
        this.eat();          // ✅ 合法，通过子类自身
        
        Animal a = new Animal();
        a.eat();             // ❌ 编译错误！跨包不能用父类引用访问
    }
}
```

这是面试/考试常考的陷阱，`protected` 的跨包访问权限是绑定在**子类继承关系**上的，不是对父类对象通用的。

ReentrantReadWriteLock不支持从读锁升级到写锁。当一个线程持有读锁时尝试获取写锁，写锁需要等待所有读锁释放，但当前线程持有的读锁不会释放（因为代码在等待写锁），形成死锁。正确做法是先释放读锁再获取写锁，或使用StampedLock的tryConvertToWriteLock()方法尝试锁升级。注意ReentrantReadWriteLock支持写锁降级为读锁（先获取写锁，再获取读锁，再释放写锁）。
