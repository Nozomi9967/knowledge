# N+1 查询问题（ORM 经典陷阱）

## 一句话定义

> 执行 **1 条查询获取 N 条主数据**，再**循环 N 次查询获取每条数据的关联数据**，共执行 **N+1 条 SQL** — 这就是 N+1 查询问题。

---

## 问题场景

假设有两个表：`user`（用户）和 `order`（订单），一个用户有多个订单。

**业务需求**：列出所有用户及其订单列表。

### ❌ 错误写法（N+1 问题）

```java
// 1 条 SQL：查询所有用户
List<User> users = userMapper.selectList(null);

// 循环中 N 条 SQL：每个用户查一次订单
for (User user : users) {
    // 每次都执行一条 SQL
    List<Order> orders = orderMapper.selectByUserId(user.getId());
    user.setOrders(orders);
}
```

**执行 SQL 数量**：`1（查用户） + N（查订单） = N+1 条`

| 用户数 | SQL 条数 | 耗时（估算） |
|--------|---------|------------|
| 10     | 11      | ~10ms     |
| 100    | 101     | ~100ms    |
| 10000  | 10001   | ~10s+     |

数据量越大，性能越差！

---

## 为什么会发生？

### 1. ORM 懒加载（Lazy Loading）

```java
// User 实体中配置懒加载
@OneToMany(fetch = FetchType.LAZY)
private List<Order> orders;

// 遍历时触发 N 次查询
users.forEach(user -> user.getOrders().size()); // 第一次访问时触发 SQL
```

### 2. 循环中查询数据库

```java
// 常见于 MyBatis <collection> 标签 + 循环查询
for (Long id : ids) {
    Order order = orderMapper.selectById(id); // 每次都查 DB
}
```

---

## ✅ 解决方案

### 方案一：JOIN 一次查（推荐）

```sql
SELECT u.*, o.*
FROM user u
LEFT JOIN `order` o ON u.id = o.user_id
WHERE u.id IN (1, 2, 3, ...);
```

```java
// MyBatis-Plus 多表联查
@Select("SELECT u.*, o.* FROM user u LEFT JOIN `order` o ON u.id = o.user_id WHERE u.id IN ${ids}")
List<UserOrderVO> selectUserWithOrders(@Param("ids") String ids);
```

**结果**：1 条 SQL 搞定，无论多少用户。

### 方案二：IN 查询 + IN 聚类（最常用）

```java
// 第 1 步：查所有用户（1 条 SQL）
List<User> users = userMapper.selectList(null);
List<Long> userIds = users.stream().map(User::getId).toList();

// 第 2 步：批量查订单（1 条 SQL）
List<Order> orders = orderMapper.selectByUserIds(userIds);  // WHERE user_id IN (...)

// 第 3 步：内存中组装（0 条 SQL）
Map<Long, List<Order>> orderMap = orders.stream()
    .collect(Collectors.groupingBy(Order::getUserId));

users.forEach(user -> user.setOrders(orderMap.getOrDefault(user.getId(), List.of())));
```

**结果**：**2 条 SQL**，不再 N+1。

### 方案三：MyBatis-Plus 批量查询

```java
// 使用 MyBatis-Plus 的 batch 方法
List<User> users = userService.list();
List<Order> orders = orderService.lambdaQuery()
    .in(Order::getUserId, users.stream().map(User::getId).toList())
    .list();
// 内存组装同上
```

### 方案四：MyBatis `<collection>` 嵌套查询

```xml
<!-- 一次性查出所有用户及其订单 -->
<resultMap id="userOrderMap" type="User">
    <id property="id" column="id"/>
    <collection property="orders" ofType="Order"
                select="selectOrdersByUserId"
                column="id">
        <!-- 注意：这里是嵌套查询，仍然是 N+1！ -->
    </collection>
</resultMap>

<!-- 正确做法：使用 JOIN + 嵌套结果 -->
<resultMap id="userOrderMap" type="User">
    <id property="id" column="id"/>
    <collection property="orders" ofType="Order">
        <id property="id" column="order_id"/>
        <result property="amount" column="amount"/>
    </collection>
</resultMap>

<select id="selectUserWithOrders" resultMap="userOrderMap">
    SELECT u.*, o.id AS order_id, o.amount
    FROM user u
    LEFT JOIN `order` o ON u.id = o.user_id
</select>
```

## 面试话术

> **面试官**：ORM 的 N+1 查询问题是什么？怎么解决？

**回答要点**：
1. **定义**：1 条主查询 + N 条关联查询，共 N+1 条 SQL
2. **原因**：ORM 懒加载机制 / 循环中查数据库
3. **危害**：数据量大时性能急剧下降，1000 条数据就是 1001 条 SQL
4. **解决方案**：
   - JOIN 一次查出（1 条 SQL）
   - IN 批量查询 + 内存组装（2 条 SQL）
   - 使用 `@EntityGraph` / `fetch join` 声明式解决
   - MyBatis 用嵌套结果 `<collection>` 代替嵌套查询
