### **Next-key lock 通过"行锁 + 间隙锁"锁住记录及其前后间隙来防止幻读，但 RR 下快照读与当前读混用、或新插入数据被当前读感知时，仍可能出现幻读。**

面试口述版回答如下，你可以按这个思路展开讲：

---

**第一部分：先讲 InnoDB 在 RR 下怎么防幻读**

MySQL InnoDB 在 RR 隔离级别下解决幻读，主要靠两套机制配合：

一套是 **MVCC(多版本并发控制)**，用于**快照读**，也就是普通的 `SELECT`。事务开启后会生成一个 Read View，之后读到的都是这个一致性视图里的数据，别的事务插入、修改都看不到，所以快照读天然不会有幻读。

另一套是 **Next-Key Lock**，用于**当前读**，比如 `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、`UPDATE`、`DELETE` 这些。它是行锁和间隙锁的组合:

- **Record Lock（行锁）**：锁住索引上的一条具体记录；
- **Gap Lock（间隙锁）**：锁住索引记录之间的"空隙"，不锁记录本身，作用是不让别的事务往这个空隙里插入数据；
- **Next-Key Lock** 就是 "行锁 + 它前面的间隙"，是个左开右闭的区间 `(前一条, 当前记录]`。

举个例子，假设索引上有值 `10, 20, 30`，当我执行 `SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE`，InnoDB 会对 20 这条记录加行锁，同时对 `(10, 20]` 和 `(20, 30]` 这两个区间加间隙锁。这样别的事务想在这个范围内 `INSERT id=18` 或 `id=22` 都会被阻塞，从而避免同一事务两次执行范围查询时出现"多出来的行"，这就是 RR 下防幻读的核心。

另外要提一点：**Next-Key Lock 只在使用索引进行范围扫描时才生效**；如果是唯一索引的等值查询命中一条记录，会退化成 Record Lock，因为不存在幻读风险。

---

**第二部分：讲 RR 下什么场景仍可能出现"幻读"**

虽然官方说 RR 解决了幻读，但在几种场景下依然会看到类似幻读的现象：

**场景一：快照读与当前读混用（最经典）**

事务 A 先执行快照读，比如：

```sql
-- 事务A
BEGIN;
SELECT * FROM t WHERE age > 20;   -- 快照读，返回 3 行
```

这时事务 B 插入了一条 `age = 25` 的数据并提交。然后事务 A 再执行：

```sql
SELECT * FROM t WHERE age > 20 FOR UPDATE;   -- 当前读，返回 4 行
```

两次查询结果不一致，第二次多出一行 —— 这就是幻读。原因是 `FOR UPDATE` 是当前读，读的是最新已提交数据，而不是 Read View 里的快照。

**场景二：事务内自己 UPDATE 了新插入的数据**

事务 A 开启后先做快照读看到 3 行；事务 B 插入一行并提交；事务 A 接着执行 `UPDATE t SET ... WHERE age > 20`，这条 UPDATE 是当前读，会把 B 新插入的那行也更新掉。**并且**更新之后，这行的 `trx_id` 变成了事务 A 自己的，A 再次快照读就能看到它了，感觉上就"幻读"出一行。

**场景三：第一次查询没有加锁**

如果事务开始时先做的是不加锁的 `SELECT`，那时没有 Next-Key Lock，别的事务可以自由插入。等你后面再加锁查询时，新数据已经进来了，也会呈现幻读。

**规避方式**：在事务开始时就用 `SELECT ... FOR UPDATE` 做当前读，让 Next-Key Lock 提前把范围锁住，后续插入被阻塞，就不会有幻读了。

---

**总结一句话收尾（面试时可以说）：**

RR 下 InnoDB 靠 MVCC 让快照读没有幻读，靠 Next-Key Lock 让当前读没有幻读；但一旦在同一事务里**先快照读、后当前读**，或者中途 UPDATE 到了别人新插入的行，快照视图就会被打破，幻读依然会出现。所以严格意义上，RR 只是"大部分场景下"解决了幻读，要彻底避免，要么升级到 Serializable，要么事务一开始就用当前读把范围锁住。
