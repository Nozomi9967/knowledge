# 静态集合内存泄漏与类卸载详解

## 为什么强调"静态"？— GC Roots 视角

面试被问到「内存泄漏常见原因」时，大部分人都能答出"静态集合忘清理"这一条。但面试官追问**"为什么强调静态？"**时，卡住的人就多了。

### 根本原因：static 变量是 GC Root

JVM 在进行可达性分析时，从 **GC Roots** 出发遍历所有存活对象。GC Roots 包括：

| GC Root 类型          | 生命周期         | 回收可能性  |
| ------------------- | ------------ | ------ |
| 栈帧中的局部变量            | 方法执行完即释放     | 高      |
| 活跃线程                | 线程结束即释放      | 高      |
| JNI 全局引用 [^1]       | 手动释放         | 中      |
| **static 变量（类静态域）** | **类卸载前永不释放** | **极低** |

[^1]: **JNI（Java Native Interface）** 是 Java 调用 C/C++ 代码的标准接口。C/C++ 代码可以通过 `NewGlobalRef()` 创建 JNI 全局引用，强引用一个 Java 对象。这个引用必须手动调用 `DeleteGlobalRef()` 释放，否则 GC 无法回收该对象。这就是为什么 JNI 全局引用也算 GC Root 的一种——它连着一块不受 JVM 自动管控的内存生命周期。

> [!important] **static 变量就是天然的 GC Root**
> 一旦一个集合被 `static` 修饰，它就挂在了类上。**只要类没有被卸载，这个集合永远不会被 GC 判定为不可达。**
> 你往里面塞的对象，全被它强引用链拉着，一个都跑不掉。

### 对比：实例变量 vs 静态变量

```java
public class NormalCache {
    // 实例变量：NormalCache 对象可回收时，这个 map 也随之释放
    private Map<Long, User> cache = new HashMap<>();
}

public class StaticCache {
    // 静态变量：只要 StaticCache 类还在方法区（元空间）中，map 就活着
    private static Map<Long, User> cache = new HashMap<>();
}
```

- **实例变量**：所属对象不可达 → 整个对象树被回收 → 集合释放。泄漏范围可控。
- **静态变量**：类不卸载 → 集合永驻内存。泄漏范围 = **整个 JVM 生命周期**。

> 这也是为何 Spring 默认管理的 Bean 是单例而非静态类——Spring 容器持有 Bean 实例的引用，容器销毁时释放，比静态变量可控得多。

## 类卸载（Class Unloading）的条件

这是更深层的问题。上面说了"静态集合在类卸载前永不释放"，那**类什么时候才能被卸载**？

### JVM 规范：三个必要条件

一个类要被卸载，必须同时满足以下三个条件：

1. **该类所有的实例都被回收**（堆中不存在该类的任何实例）
2. **加载该类的 ClassLoader 被回收**（ClassLoader 实例不可达）
3. **该类对应的 `java.lang.Class` 对象没有任何地方被引用**（包括反射、动态代理等）

> 这三条缺一不可。其中第 2 条——**ClassLoader 被回收**——往往是最难满足的。

### 为什么类卸载在实际中很难发生？

#### 情况一：启动类加载器 / 扩展类加载器加载的类

```java
// String、ArrayList 这些 —— 由 Bootstrap ClassLoader 加载
// Bootstrap ClassLoader 由 JVM 实现，本身不是 Java 对象
// 它的生命周期 = JVM 生命周期
// → 这些类永远不可能被卸载
```

`rt.jar`、`java.base` 模块中的核心类——**永不卸载**。

#### 情况二：系统类加载器（App ClassLoader）加载的应用类

```java
// 你自己写的业务类 —— 由 AppClassLoader 加载
// AppClassLoader 是一个 Java 对象，被谁引用？
// 它被 ClassLoader.getSystemClassLoader() 持有
// 只要线程还在跑、还有代码在引用你的类，ClassLoader 就不可回收
// → 在普通 Java 应用中几乎不卸载
```

#### 情况三：自定义 ClassLoader 场景——这才是类卸载真正发生的场景

```java
// 只有自定义 ClassLoader + 明确的作用域控制，类卸载才会成为现实
URLClassLoader loader = new URLClassLoader(new URL[]{new File("ext/").toURL()});
Class<?> clazz = loader.loadClass("com.example.MyPlugin");
Object instance = clazz.newInstance();

// ... 使用完毕后
instance = null;      // 条件 1：实例置空
clazz = null;         // 条件 3：Class 对象引用置空
loader.close();       // 条件 2：ClassLoader 引用置空 + 关闭
loader = null;        // 条件 2 的补充
// 此时 MyPlugin 的类元数据才有可能被回收
```

**典型场景：**

| 场景 | 说明 | 类卸载是否发生 |
|---|---|---|
| Tomcat 热部署 | 每个 WebApp 有独立 WebAppClassLoader，redeploy 时替换 | ✅ 是，旧 ClassLoader 不可达后卸载 |
| CGLIB / ByteBuddy 动态代理 | 每次增强生成新类，加载到特定 ClassLoader | ⚠️ 取决于 ClassLoader 是否复用/泄漏 |
| Spring Boot 重启（DevTools） | 使用 RestartClassLoader 隔离 | ✅ 是 |
| OSGI / 插件系统 | 每个 Bundle 独立 ClassLoader | ✅ 是 |
| **普通 `java -jar` 应用** | AppClassLoader 加载 | ❌ 几乎不卸载 |

### 类卸载与元空间 OOM

类卸载直接关联到**元空间（Metaspace）OOM**：

```java
// 这段代码如果跑在循环里，会撑爆元空间
while (true) {
    // 每次生成一个新的 ClassLoader，加载一个新的类
    URLClassLoader loader = new URLClassLoader(new URL[]{...});
    Class<?> clazz = loader.loadClass("com.example.GeneratedClass");
    // ⚠️ 如果 loader 和 clazz 没有被释放（泄漏），
    //    旧的类元数据堆积 → Metaspace OOM
}
```

这就是典型的 **ClassLoader 泄漏导致元空间 OOM** 的路径。

**JVM 参数调控类卸载：**

```
# CMS 下启用类卸载
-XX:+CMSClassUnloadingEnabled

# G1 下控制类卸载（JDK 8u45+ 默认开启）
-XX:+ClassUnloadingWithConcurrentMark

# 查看类加载/卸载日志
-XX:+TraceClassLoading -XX:+TraceClassUnloading
# JDK 9+ 推荐用 -Xlog:class+load,class+unload
```

> [!tip] 类卸载触发时机
> 类卸载不是在类加载器变得不可达的瞬间发生的，而要等到**下一次 Full GC / Concurrent Class Unloading 周期**才会真正回收元空间中的类元数据。

## 综合：回到面试题

面试官：「内存泄漏有哪些常见原因？」

你：「……静态集合使用 static 的 HashMap、ArrayList 存对象后没清理。」

面试官追问：「**为什么强调静态？**」

### 面试话术（一锤定音版）

> "强调静态是因为 `static` 变量引用的对象属于 **GC Root**，它的生命周期和类的生命周期绑定。在普通 Java 应用中，类几乎不会被卸载——因为 AppClassLoader 本身一直存活，所以类元数据和静态集合都不会被回收。一旦往静态集合里放了对象没清理，这些对象永远可达，等价于常驻堆内存。
>
> 相比之下，实例变量的集合虽然也可能泄漏，但只要外层对象可达范围有限、或者能被 GC 回收，泄漏的"量级"完全不一样。所以面试里提到内存泄漏，**静态集合是必提的第一个例子**。"

面试官：「**那类什么时候才能被卸载？**」（进阶追问）

> "JVM 规定要同时满足三个条件：
> 1. 该类所有实例都已被回收；
> 2. 加载该类的 ClassLoader 已被回收；
> 3. 该类的 Class 对象没有任何引用。
>
> 但在实践中，三大类加载器中——Bootstrap 和 Extension 加载的类永远不会被卸载；AppClassLoader 加载的业务类也几乎不卸载，因为 AppClassLoader 本身一直存活。真正会发生类卸载的场景是 **自定义 ClassLoader**，比如 Tomcat 热部署、OSGI 插件系统、Spring Boot DevTools 等。类卸载的时机也不是即时的，要等到下一次 Full GC 或并发类卸载周期才会真正释放元空间。"
