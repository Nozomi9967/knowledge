## 一、认识 Redis（2 题）

### 1. 什么是 Redis？为什么选择 Redis 作为 MySQL 的缓存？请从「高性能」和「高并发」两个角度展开说明。

> **知识点跳转：** [[redis八股]] · [[解释为何CPU不是redis的瓶颈以及单线程为何还这么快？]]

**参考答案**

Redis 本质上是一个基于内存的键值数据库，读写都在内存里完成，所以它最常被拿来当缓存，也用于分布式锁和消息队列。之所以把它挡在 MySQL 前面，核心就是高性能和高并发这两件事。高性能是因为全内存访问，加上哈希表、跳表这些结构做过极致优化，常用操作基本是 O(1) 或者 O(logN)，一条命令微秒级就返回；而 MySQL 一次查询要解析 SQL、走索引、读磁盘，量级差了好几个。高并发要靠对比才说得清楚：MySQL 受限于线程模型和文件系统，并发上到几千连接，上下文切换和连接池就会成为瓶颈，甚至被打挂；而 Redis 单机 QPS 轻松破十万，靠的是三条环环相扣的设计，全内存让单线程处理也不会阻塞、单线程天然没有上下文切换和锁竞争、再加 epoll 多路复用能同时盯住成千上万个连接。所以它在架构里更像一个蓄水池，把热点请求在内存层消化掉，不让流量直接砸到数据库上。

**追问参考答**

本地缓存活在 JVM 进程里，每个服务实例各存一份，多实例之间不共享，数据必然不一致，进程一重启缓存还全丢了。Redis 是独立的共享中间件，所有实例读的是同一份数据，天然一致，还自带过期时间、持久化和分布式锁这些能力。所以分布式场景下主缓存必须是 Redis，本地缓存只能当二级缓存，用来挡那些极端热点，两道防线配合才合理。

### 2. Redis 与 Memcached 有哪些主要区别？

> **知识点跳转：** [[redis八股]]

**参考答案**

最核心的区别在数据模型，其他的差别都是从这儿延伸出来的。Redis 除了最基础的键值对，还提供 String、Hash、List、Set、ZSet 这五种基础结构，以及在它们之上扩展出来的 BitMap、HyperLogLog、GEO 和 Stream；Memcached 就只有纯粹的 key-value。第二个区别是 Redis 支持持久化，重启能恢复数据，Memcached 一重启数据全没。第三是 Redis 原生支持集群分片，Memcached 得在客户端自己做一致性哈希。第四是 Redis 支持发布订阅、Lua 脚本和事务，Memcached 这三样都没有。选型上就很好判断了，要做排行榜要 ZSet、要去重要 Set、要用 Lua 保证多步操作的原子性、要数据重启不丢，这些都只有 Redis 能给你；如果只是最单纯的 KV 缓存、数据丢了也无所谓，Memcached 也能胜任，它多线程模型在某些纯读场景还有一点优势。

**追问参考答**

讲差异的时候要注意分层，跟 Memcached 比基础数据类型只提五种，BitMap、HyperLogLog、GEO、Stream 是基于基础类型扩展出来的高级数据结构，别混在一起列。否则面试官会顺势追问你说的 BitMap 本质是什么，那时候答不出它底层是 String 的位操作，就显得只会背名词。

## 二、数据结构与底层编码（7 题）

### 3. Redis 有哪些数据类型？请至少列举 9 种，并分别说明一种典型应用场景。

> **知识点跳转：** [[Redis 常见数据类型和应用场景]] · [[redis八股]]

**参考答案**

回答的时候最好分两层说，先说五种基础类型，再说四种在此基础上扩展出来的结构，这样逻辑清楚也不会被追问带偏。五种基础类型是 String、Hash、List、Set、ZSet：String 用来缓存对象、做分布式锁、常规计数和共享 Session；Hash 适合存一个对象的多个字段，购物车是最典型的例子；List 是有序可重复的，最早被拿来做简单消息队列；Set 无序去重，用来做交并差运算、点赞、共同关注和抽奖；ZSet 带 score 可以排序，排行榜就是它的标准场景。高级结构里，BitMap 按位存二值状态，签到和登录状态统计最合适；HyperLogLog 用来做海量 UV 这种基数统计；GEO 存地理位置，底层其实还是 ZSet，score 是 GeoHash 编码后的值；Stream 是可靠消息队列，补上了消费者组、ACK 确认和消息持久化这些 List 缺的东西。

**追问参考答**

HyperLogLog 统计出来的是估算值，标准误差大约百分之零点八一，不是精确数字。但 UV 这类业务本来就不要求精确，几百万的日活差个几千没人关心，换来的是无论数据量多大它都固定只占十几 KB 内存，这个交易很划算。真要求精确只能用 Set 存全量 ID，那内存就爆了。

### 4. String 类型的底层实现是什么（SDS）？相比 C 语言字符串，它解决了哪些问题？

> **知识点跳转：** [[Redis底层编码标准答案]] · [[redis八股]]

**参考答案**

String 的底层不是 C 语言那种以空字符结尾的字符串，而是 SDS，也就是简单动态字符串，它相比 C 字符串解决了三个问题。第一个是取长度，C 字符串得一路遍历到结尾的空字符才知道有多长，复杂度是 O(N)，SDS 专门用一个 len 字段把长度存下来，读字段就是 O(1)。第二个是二进制安全，C 字符串靠空字符判断结尾，存图片、序列化对象这种中间带空字符的数据会被提前截断，SDS 靠 len 来定边界，中间有什么字节都不影响，所以什么二进制都能存。第三个是防止缓冲区溢出，SDS 里还有一个 free 字段记录剩余可用空间，拼接之前先看空间够不够，不够就先扩容再写，不会越界把后面别人的内存覆盖掉。

**追问参考答**

这三件事各对应一个机制，问哪个答哪个就好：O(1) 取长度靠的是专门的 len 字段；二进制安全靠的是用 len 判断边界、不依赖空字符；不溢出靠的是 free 字段加上拼接前的扩容检查。注意别说成"因为 SDS 会检查字符串内容"，那是结果不是机制。

### 5. List 类型的底层编码经历了怎样的演进？每个阶段对应什么条件？

> **知识点跳转：** [[Redis底层编码标准答案]] · [[quicklist的内部节点]]

**参考答案**

List 的底层编码走过了三个阶段。3.0 之前是二选一，元素个数不超过 512 并且每个元素不超过 64 字节，就用 ziplist 压缩列表，任一条件超标就换成 linkedlist 双向链表。3.2 到 6.2 统一用 quicklist，本质是双向链表套 ziplist，每个链表节点里装一个 ziplist，节点多大由 list-max-ziplist-size 控制，默认 8KB。7.0 之后还是 quicklist，但内部节点从 ziplist 换成了 listpack，参数名也跟着改成 list-max-listpack-size，整体逻辑没变。这么演进的理由很直接，纯 ziplist 有连锁更新的风险，纯 linkedlist 每个节点单独 malloc、内存碎片严重，quicklist 是两者的折中，而 7.0 换 listpack 是把连锁更新从根上去掉了。

**追问参考答**

这里最容易翻车的是把 64 字节说成 64KB，差了三个数量级。为什么是这两个阈值也不难理解：元素多了 ziplist 的连锁更新风险会累积，元素大了压缩结构省内存的收益就没了，每个 entry 自己都很大，压不压无所谓，还不如用正经链表。7.0 之后参数名从 list-max-ziplist-size 改成 list-max-listpack-size，逻辑一个字没变。

### 6. Hash 类型的底层编码是什么？什么时候用紧凑结构、什么时候转成 hashtable？转换条件是什么？

> **知识点跳转：** [[Redis底层编码标准答案]] · [[listpack]]

**参考答案**

Hash 的编码是双阈值判断，看字段数和字段值大小两个维度。7.0 之前，字段数不超过 512 并且每个字段值不超过 64 字节，用 ziplist；任一条件超标就转 hashtable。7.0 之后前半段换成 listpack，阈值一个没改。它和 ZSet 的转换逻辑是同构的，都是元素个数加元素大小这两个阈值，小数据用紧凑结构省内存，数据大了换高效结构，根本原因是紧凑结构在数据量上去之后读写性能会下降，ziplist 还带着连锁更新的风险。两者唯一的区别是阈值数值，Hash 是 512，ZSet 是 128，ZSet 只要元素超过 128 个或者有一个元素超过 64 字节，就直接上跳表。

**追问参考答**

这题追问容易答偏。问"相似之处"要答双阈值这套转换机制本身，不是答两者都存键值对——Hash 是 field 对 value，ZSet 是 member 对 score，那是数据形状的差异，答这个等于没答。问"根本原因"要答省内存和性能劣化之间的取舍，顺带说清 512 和 128 这两个数字不一样。

### 7. Set 类型的底层编码有哪些？什么时候用 intset？什么时候转 hashtable？

> **知识点跳转：** [[Redis底层编码标准答案]]

**参考答案**

Set 的判断维度比 Hash 和 ZSet 少一个，它只看两个东西，是不是全整数、元素个数多少，没有元素大小这一维。所有元素都是整数并且个数不超过 512，就用 intset 整数集合，紧凑又省内存；只要有任何一个非整数元素，或者元素个数超过 512，就转成 hashtable。另外它没有 7.0 换 listpack 的那套演进，intset 到 hashtable 一直是这个规则，因为 intset 本身不存在连锁更新问题，没有换的必要。

**追问参考答**

边界要说准，是小于等于 512 用 intset，512 本身还在 intset 里，超过 512 才转。为什么 Set 没有元素大小这一维，是因为它只存成员不存值，成员大小差异对紧凑结构的影响远不如 Hash 的字段值大，所以 Redis 干脆只看整性和个数。

### 8. ZSet 为什么使用「跳表 + 哈希表」的组合？为什么不用红黑树或平衡树？

> **知识点跳转：** [[跳表（Skip List）详解]] · [[Redis底层编码标准答案]]

**参考答案**

这两个结构是分工的。哈希表负责按 member 以 O(1) 查到 score，像 ZSCORE 这种单点查询走它；跳表负责维持有序，ZRANGE、ZRANGEBYSCORE 这类范围查询和排行榜取 TopN 靠它。不用红黑树或者平衡树，主要三条理由。一是范围查询更顺手，跳表定位到起点之后顺着 forward 指针一路走就是区间结果，红黑树得做中序遍历，实现起来绕。二是实现简单，跳表本质就是多层有序链表，插入删除只改几个指针，没有旋转和染色这些平衡调整。三是平衡方式天然，跳表靠概率决定每个节点的层高，不需要维护严格平衡。代价是多花一层指针的内存，但排行榜这种场景范围操作才是核心，这个代价完全值得。

**追问参考答**

如果追问"跳表最坏复杂度不是 O(N) 吗"，要答跳表的层高是随机决定的，期望复杂度是 O(logN)，最坏情况概率极低，工程上可以接受；真要求最坏也保证 O(logN) 才需要严格平衡树，而 Redis 在有序集合这个场景选择了实现简单优先。

### 9. 什么是 ziplist 的「连锁更新」问题？Redis 7.0 的 listpack 是如何解决这个问题的？

> **知识点跳转：** [[ziplist]] · [[listpack]]

**参考答案**

ziplist 每个 entry 的头部有个 prevlen 字段，记录前一个 entry 有多长，而 prevlen 自己的长度是可变的，前一个 entry 小于 254 字节时它占 1 字节，大于等于 254 字节就要占 5 字节。254 就是那个临界点，也正是问题的根源。如果某个 entry 变大跨过了 254，紧跟着它后面那个 entry 的 prevlen 就得从 1 字节扩成 5 字节，于是它自己也跟着变大，又可能让更后面那个也跨过临界点，一路级联下去，这就是连锁更新，最坏情况复杂度会退化到 O(n²)。listpack 的解法是彻底不记录前一个的长度，只记录自己的长度，单个 entry 变长只影响自己，不会传染给后面，从根上把这个问题消掉了。本质区别就是 ziplist 引用前面、listpack 自包含。

**追问参考答**

listpack 的 entry 里放的是自己的 encoding 和长度，读的时候从左往右解析，不需要回头依赖前一个 entry，这就是它免疫连锁更新的原因。顺带说一句，listpack 从右往左遍历要靠每个 entry 末尾的 backlen 字段，所以它并不是完全不记长度，只是记的是自己的。

## 三、线程模型（4 题）

### 10. Redis 是单线程的吗？「单线程」具体指哪一部分？Redis 程序本身启动时会创建哪些后台线程？

> **知识点跳转：** [[redis八股]] · [[Redis IO多路复用详解]]

**参考答案**

严格讲 Redis 是命令执行单线程，不是整个进程单线程。接收客户端请求、解析请求、读写数据、把结果发回去这条完整链路，都由主线程一个人完成。但进程里还有一批后台线程，2.6 就有两个，一个负责异步关闭文件，一个负责 AOF 刷盘；4.0 加了 lazyfree 线程，专门异步释放内存；6.0 又加了 I/O 线程，帮忙分担网络读写。所以更准确的说法是主线程串行执行命令，其余杂活交给后台线程。

**追问参考答**

lazyfree 是 4.0 引入的异步释放内存线程。unlink 的时候主线程只把 key 从全局哈希表里摘掉，这个是微秒级的，真正的内存释放丢给后台 lazyfree 线程去做，所以不阻塞。del 是在主线程同步释放，删一个百万级元素的大 key，光释放内存就能卡住主线程好几百毫秒，所以生产上删大 key 一律用 unlink。

### 11. Redis 为什么采用单线程模型还这么快？为什么说 CPU 不是 Redis 的瓶颈？

> **知识点跳转：** [[解释为何CPU不是redis的瓶颈以及单线程为何还这么快？]] · [[Redis IO多路复用详解]]

**参考答案**

这题要答成一条因果链，而不是并列几个名词。因为是全内存操作，每条命令微秒级就完成了，所以单线程执行也不会阻塞事件循环；正因为是单线程，天然没有多线程上下文切换的 CPU 损耗，也没有锁竞争；再加上核心数据结构都做过优化，常用操作是 O(1) 或 O(logN)；最后靠 epoll 这套 I/O 多路复用，单线程也能同时盯着成千上万个连接。至于为什么 CPU 不是瓶颈，是因为真正的瓶颈在内存容量和网络带宽上，单条命令的 CPU 运算极轻，CPU 远远没跑满，既然算力本来就富余，上多线程只是徒增复杂度。

**追问参考答**

多线程的本职工作其实就两件，一是榨干多核算力跑 CPU 密集型任务，二是掩盖 I/O 阻塞，一个线程在等磁盘的时候另一个继续算。Redis 这两条都不成立：数据全在内存，没有磁盘 I/O 阻塞，第二条用不上；单条命令 CPU 运算极轻，CPU 远未饱和，第一条也没必要。所以它不是因为"不想多线程"，是客观上没有多线程的需求。

### 12. Redis 6.0 之后为什么引入多线程？多线程处理的是什么？命令执行还是单线程吗？

> **知识点跳转：** [[Redis6.0多线程IO的限制]] · [[如何理解随着网络硬件的性能提升，Redis的性能瓶颈有时会出现在网络IO的处理上]]

**参考答案**

引入的原因是网络硬件变快了，瓶颈从 CPU 转移到了网络 I/O 的处理上，读 socket、解析协议、写响应这些活儿单靠主线程开始扛不住，所以 6.0 用多个 I/O 线程来分担。要注意多线程只处理网络 I/O，命令执行依然是单线程，所以并发安全问题一个都没多出来。默认情况下 I/O 多线程只用来发送响应数据，也就是写客户端 socket，读请求默认还是单线程处理，想开读多线程得配 io-threads-do-reads yes。线程数用 io-threads N 设置，这个 N 是包含主线程的，实际起的是 N 减 1 个 I/O 线程，官方建议 4 核配 2 到 3、8 核配 6，而且必须小于机器的核数，配大了反而互相抢 CPU。

**追问参考答**

这里最容易答反的就是默认处理读还是写。默认只处理写，也就是把响应数据发给客户端这一段，读请求还是主线程自己来。因为大多数场景下写响应的数据量比读请求大，收益更明显；读请求多线程需要额外配置开启，而且线程切换的开销未必划算。

### 13. 单线程事件循环的 Redis 就绝对不会阻塞吗？有哪些高危操作会导致主线程阻塞？

> **知识点跳转：** [[redis八股]] · [[Redis 大 Key 对持久化有什么影响？]]

**参考答案**

会阻塞，主动说出这一点是加分的。主要三类高危操作。第一类是耗时命令，KEYS 全库遍历、超大 Hash 的 HGETALL、SMEMBERS 这种 O(N) 命令，主线程在原地数数，后面所有请求排队饿死。第二类是大 key 删除，del 一个百万级元素的 key，释放内存的活儿全压在主线程上。第三类是 AOF 刷盘，appendfsync always 意味着每写一条命令都要等磁盘同步完成，相当于把磁盘的慢速直接引进主线程。所以生产上要禁掉 KEYS、大 key 用 unlink 删、AOF 用 everysec 而不是 always。

**追问参考答**

三种阻塞的机制不一样：大 key 删除是主线程同步释放内存，耗时和数据量成正比；KEYS 是 O(N) 遍历全库，而且它不光是慢，高并发下这段时间所有请求都在等，杀伤力被放大；fsync 是每次写命令都阻塞等磁盘，慢在 I/O 而不是 CPU。对应的解法也不一样，大 key 用 unlink 甩给后台线程，KEYS 用 SCAN 分批扫，fsync 用 everysec 让刷盘变成异步。

## 四、持久化（9 题）

### 14. Redis 如何实现数据不丢失？三种持久化方式分别是什么？各有什么特点？

> **知识点跳转：** [[redis八股]] · [[AOF 持久化是怎么实现的？]] · [[RDB 快照是怎么实现的？]]

**参考答案**

Redis 有三种方式，AOF 日志、RDB 快照，以及 4.0 引入的混合持久化。AOF 是把每条写命令追加到日志文件里，恢复的时候逐条回放，好处是丢数据少，具体丢多少取决于写回策略，坏处是恢复慢，文件越大回放越久。RDB 是把某一时刻的全量内存数据以二进制写成快照，好处是恢复快，直接载入就行，坏处是快照频率不好把握，频率太低丢的数据多，频率太高又影响性能。混合持久化是在 AOF 重写的时候，让子进程先把全量数据以 RDB 格式写进去，再把重写缓冲区里的增量命令以 AOF 格式追加在后面，这样既拿到了 RDB 的恢复速度，又把丢数据的窗口压得很小，算是两者的折中方案。

**追问参考答**

如果被追问"到底会不会丢数据"，要分清三种方式的丢失边界：AOF 的 everysec 最多丢一秒，always 最多丢一条命令，no 可能丢掉所有还没落盘的数据；RDB 丢的是最后一次快照之后的所有写入；混合持久化的丢失边界和 AOF 的 everysec 一样，因为增量部分还是按 AOF 策略刷盘。

### 15. AOF 日志是怎么实现的？为什么 Redis 先执行写命令、再记录日志？这样设计有什么好处？

> **知识点跳转：** [[AOF 持久化是怎么实现的？]]

**参考答案**

AOF 的流程是写命令先执行成功，然后把这条命令追加到 server.aof_buf 这个缓冲区，再由 write 写进 AOF 文件，注意这时候只是进了内核的 page cache，还没有真正落盘，最后才按写回策略决定什么时候 fsync 到磁盘。之所以先执行再记录，有两个好处：一是避免额外的检查开销，如果反过来先记日志再执行，命令语法有错也会被写进日志，恢复的时候就跟着出错；二是命令本身的执行不被打断，执行完顺手记一笔就完事。不过要补一句，客户端视角其实还是阻塞的，它得等 AOF 写完才能收到回复，只是因为追加是顺序写、速度很快，这个等待很短。

**追问参考答**

"真的不阻塞吗"这问要分两个视角答：从服务端看，写命令执行完就返回，不额外校验，所以不阻塞；从客户端看，它必须等到 AOF 写入完成才拿到响应，所以是被阻塞的。不阻塞的是命令的执行，不是客户端的等待，这两件事别混。

### 16. AOF 有三种写回策略（always / everysec / no），它们有什么区别？分别适用于什么场景？

> **知识点跳转：** [[AOF 持久化是怎么实现的？]]

**参考答案**

这三个策略控制的是缓冲区什么时候刷到磁盘。always 是每条写命令执行完立即同步落盘，最多丢一条命令，安全性最高但性能最差，因为它把每次写都变成一次磁盘同步。everysec 是每秒刷一次，最多丢一秒的数据，这是默认值，性能和安全的平衡点，绝大多数业务用这个。no 是写完交给操作系统，什么时候落盘由内核决定，掉电可能把最近所有没落盘的数据全丢掉，风险最大，一般只在能接受大量丢失的场景用。另外要清楚一点，write 之后数据只是进了内核缓冲区，真正的落盘要靠 fsync，这三个策略差的就是 fsync 的时机。

**追问参考答**

"写 AOF 一定会立即落盘吗"，答案是不一定。write 只是把数据从应用缓冲区拷进内核的 page cache，操作系统会自己决定什么时候真正写到磁盘，除非显式调用 fsync。这也是 always 慢的根本原因，它在每次 write 之后都强制 fsync，而 everysec 是攒一秒再 fsync 一次。

### 17. AOF 文件越来越大怎么办？AOF 重写机制是怎么工作的？为什么要使用子进程而不是子线程？

> **知识点跳转：** [[AOF 持久化是怎么实现的？]]

**参考答案**

AOF 是追加日志，同一条 key 反复被写就会留下大量冗余命令，所以文件只会越来越大，超过阈值就触发重写。重写不是去压缩旧日志，而是直接读当前数据库里的所有键值对，每个键值对用一条命令写进新的 AOF 文件，等于重新打一份数据快照，写完之后替换旧文件，所以文件能大幅瘦身。它由后台子进程 bgrewriteaof 来执行。用子进程而不是子线程有两个原因：一是重写期间主进程还能继续处理命令请求，不阻塞线上；二是子进程和父进程共享内存，一方要修改时触发写时复制，父子各持一份副本互不影响，完全不需要加锁；换成线程就得因为共享同一份内存而加锁，性能直接掉下来。

**追问参考答**

补充一个常被忽略的点：重写期间主进程并不是什么都不做，它一边处理客户端命令，一边要把新命令同时写进 AOF 缓冲区和 AOF 重写缓冲区，前者维持旧文件可用，后者给新文件补齐增量，这也是下一个问题要展开的内容。

### 18. AOF 重写期间主进程还在处理写命令，如何保证新旧 AOF 文件数据一致？AOF 重写缓冲区的作用是什么？


> **知识点跳转：** [[AOF 持久化是怎么实现的？]]

**参考答案**

重写期间主进程同时干三件事：执行客户端发来的命令，把写命令追加到 AOF 缓冲区让旧文件继续可用，再额外追加一份到 AOF 重写缓冲区专门给新文件用。子进程把全量数据写完，会向主进程发一个信号，主进程收到后把重写缓冲区里的全部内容追加到新 AOF 文件的末尾，然后改名覆盖旧文件。这样新文件等于子进程 fork 那一刻的全量数据，加上这期间产生的所有增量命令，两边合起来就和当前内存完全一致，而且切换过程里一条命令都不会丢。

**追问参考答**

重写缓冲区的意义就在这儿，它记录的是 fork 之后、重写完成之前这段时间的增量。如果没有它，新文件只有 fork 瞬间的快照，这期间客户端写的数据全丢。两个缓冲区容易混：AOF 缓冲区是给旧文件用的，保证重写失败也能正常持久化；重写缓冲区是给新文件用的，保证切换后数据完整。

### 19. RDB 快照是怎么实现的？save 和 bgsave 有什么区别？RDB 恢复数据为什么比 AOF 快？

> **知识点跳转：** [[RDB 快照是怎么实现的？]]

**参考答案**

RDB 就是把某一时刻的全量内存数据以二进制形式写成文件。save 是在主线程里生成，写盘这段时间主线程没法处理请求，所以线上基本不用；bgsave 是 fork 一个子进程去生成，主线程继续服务，这是实际用的方式。RDB 恢复比 AOF 快，是因为它存的就是全量数据的最终形态，载入即可用，而 AOF 存的是一堆命令，恢复时要一条条回放，文件越大越慢，同量级的数据 AOF 的恢复时间可能是 RDB 的好几倍。

**追问参考答**

自动触发的三个默认配置是 save 900 1、save 300 10、save 60 10000，分别表示 900 秒内至少一次修改、300 秒内至少十次修改、60 秒内至少一万次修改，满足任意一条就触发。这里有个容易搞混的点，配置项虽然叫 save，实际执行的是 bgsave，不会阻塞主线程。

### 20. 执行 bgsave 期间，主进程的数据能被修改吗？写时复制（COW）是怎么保证快照一致性的？

> **知识点跳转：** [[RDB 快照是怎么实现的？]] · [[Redis fork 全量同步优化案例]]

**参考答案**

能修改，而且正是靠写时复制才做到了既让主进程继续写、又保证快照一致。fork 之后父子进程共享同一份物理内存，子进程的视角是只读的；主线程一旦要写某一页，内核就把这一页复制一份出来，主线程在新的页上改，子进程继续用旧的那份写 RDB 文件。所以子进程拿到的永远是 fork 那一瞬间的数据状态，快照的一致性靠的是内存页级别的隔离，而不是靠暂停写入。

**追问参考答**

如果主进程在 bgsave 期间改得特别多，COW 会大量触发，极端情况下内存能涨到原来数据量的两倍，这是实打实的风险，可能触发 OOM。另外如果改的是大 key，复制这一页的耗时本身就长，有阻塞主线程的可能。所以生产上要把 bgsave 安排在低峰期，或者控制单实例的数据量，别让实例大到 fork 一次就抖动。

### 21. 为什么会有混合持久化？它解决了什么问题？有什么缺点？

> **知识点跳转：** [[混合持久化与MP-AOF对比]]

**参考答案**

混合持久化是为了同时解决 RDB 和 AOF 各自的短板：RDB 恢复快但丢数据多、快照频率还不好把握，AOF 丢数据少但恢复慢，文件大了回放要很久。它的做法是在 AOF 重写的时候，让子进程先把共享内存里的全量数据以 RDB 格式写进新的 AOF 文件，然后把重写缓冲区里的增量命令以 AOF 格式追加在后面，所以这个文件前半段是 RDB 格式、后半段是 AOF 格式。优点是启动快加上丢数据少，两部分各管一段；缺点是文件可读性差，混了二进制在里面，而且不兼容 4.0 之前的版本，老版本读不了这种文件。

**追问参考答**

要注意表述准确，AOF 的核心痛点始终是恢复慢，不是重写慢。重写虽然也花时间，但它是后台子进程干的，不影响主线程；真正难受的是故障重启时要逐条回放几十 G 的命令，那才是混合持久化想解决的问题。

### 22. 在持久化场景下，RDB 和 AOF 分别如何处理过期键？（生成 / 加载 / 写入 / 重写四个阶段分别说明）

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

**参考答案**

这题得按阶段一个一个说，混着说一定出错。RDB 生成的时候会检查过期键，已经过期的不写进快照。RDB 加载要分主从，主服务器加载时会检查，过期的键不载入；从服务器不管过没过期都载入，因为后续主从同步会把数据整个清掉重建，加了过滤反而浪费一次判断。AOF 写入的时候不过滤，过期键只要还没被真正删除就照常写进去，等它被删的那一刻再追加一条 DEL 命令；AOF 重写时会检查，过期的键不写进新文件；AOF 加载就按记录老实回放，包括那些 DEL 命令，本来就不需要额外检查。

**追问参考答**

记忆锚点就一句：生成和重写都过滤，写入不过滤靠 DEL 补，加载看主从、主过滤从不过滤。容易错的是 RDB 加载那句，很多人只记住"过期的不载入"，把从服务器的情况漏了，而面试官恰恰爱问从库为什么不删过期键。

## 五、过期删除与内存淘汰（5 题）

### 23. Redis 的过期删除策略是什么？为什么选择「惰性删除 + 定期删除」组合？

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

**参考答案**

Redis 用的是惰性删除加定期删除的组合。惰性删除是不主动清理，只有当某个 key 又被访问时才检查它是否过期，过期就顺手删掉，好处是对 CPU 极其友好，坏处是那些再也没人访问的过期 key 会一直赖在内存里，对内存不友好。定期删除是每隔一段时间随机抽一批 key 检查，把过期的删掉，好处是能主动释放内存，坏处是扫描本身要花 CPU。之所以组合使用，本质就是在 CPU 和内存之间做权衡：只用惰性会烂内存，只用定期会持续占 CPU，两个搭在一起，既不让过期键无限堆积，也不让清理动作拖垮主线程。

**追问参考答**

惰性删除是对 CPU 友好、对内存不友好，定期删除反过来，对内存友好、对 CPU 不友好，两者正好互补。这样的组合保证了两件事：过期数据不会长期滞留，清理开销又被摊薄到很小的批次里。要注意别答"上面已经说过了"，每个追问都要独立组织一遍语言，面试官不会替你翻前面。

### 24. 定期删除的具体流程是怎样的？随机抽取多少个 key？继续下一轮的条件是什么？总时长上限是多少？

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

**参考答案**

流程一共四步。先从过期字典里随机抽 20 个 key，然后检查这 20 个里哪些已经过期，把过期的删掉。接着判断这一轮过期的数量，如果超过 5 个，也就是占比超过百分之二十五，说明过期键还很密集，就继续下一轮循环接着抽；如果占比不到百分之二十五，或者这一轮累计耗时已经超过 25 毫秒，就停下来，等下一个周期再查。三个数字要记死，抽 20 个、阈值百分之二十五也就是 5 个、总时长上限 25 毫秒，这套设计的目的是让每次清理的开销可控，不会因为过期键太多而长时间占住主线程。

**追问参考答**

为什么是 25 毫秒，因为主线程还要处理正常请求，清理占太久就等于阻塞服务，25 毫秒是一个不影响响应时间又能清掉相当一部分的折中值。这也解释了为什么过期键不一定在到期瞬间被删掉，如果它所在的批次一直没被抽到，可能要等好几轮，所以 Redis 的过期是"最终会被删"而不是"准时删"。

### 25. Redis 内存满了会发生什么？8 种内存淘汰策略如何分类？请完整列举。

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

**参考答案**

内存使用达到 maxmemory 之后会触发淘汰机制，但这里有个大坑，默认策略是 noeviction，它压根不淘汰数据，直接返回 OOM 错误拒绝写命令，线上不配这一项很容易踩。八种策略分三类：不淘汰的只有 noeviction 一个；只在设置了过期时间的数据里淘汰的有四个，volatile-random、volatile-ttl、volatile-lru、volatile-lfu；在所有数据里淘汰的有三个，allkeys-random、allkeys-lru、allkeys-lfu。选的时候看业务，纯缓存用 allkeys-lru 或 allkeys-lfu，缓存和持久数据混在一个实例里就只能用 volatile 系列，保证不动的数据不被误删。

**追问参考答**

noeviction 下内存超限返回的错误是 OOM command not allowed when used memory 大于 maxmemory，写命令直接被拒，读命令还能继续。volatile-ttl 的局限在于它并不是全局扫描找最快过期的那个，而是随机抽样，只在抽到的样本里挑 TTL 最小的，样本里没有真正最快到期的那个，结果就不精确。所有 lru、lfu 策略也都是抽样实现的，都不是精确算法。

### 26. LRU 和 LFU 的核心思想分别是什么？传统 LRU 算法存在哪两个问题？Redis 的近似 LRU 是怎么实现的？

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

**参考答案**

LRU 是按最后一次访问时间淘汰，越久没被碰过的越先出局；LFU 是按访问频次淘汰，被访问次数最少的先出局。传统 LRU 有两个问题：一是它要用链表把全部缓存数据管起来，这是实打实的额外空间开销；二是每次访问都要把对应节点移到链表头，访问越频繁这些移动操作就越耗时，性能会被拖下来。Redis 用的是近似 LRU，对象头里有一个 24 bit 的 lru 字段，记录最后一次访问的时间戳，淘汰的时候随机取 5 个 key，比较它们的时间戳，把最旧的淘汰掉。这样既不用维护一条大链表，也不用每次访问都修改链表结构，用很小的代价换到了接近 LRU 的效果。

**追问参考答**

LRU 解决不了缓存污染问题：一次性批量读进来一堆只访问一次的冷数据，它们的时间戳很新，会把真正的热点挤出去，而这些冷数据之后就再也不被访问了。LFU 按频次算，只读一次的冷数据频次低，挤不掉高频热点，所以 Redis 4.0 引入了 LFU。随机采样个数默认是 5，可以通过 maxmemory-samples 调大，调大越接近精确 LRU，但 CPU 开销也越大。

### 27. Redis 的 LFU 是怎么实现的？对象头的 24 bits 字段在 LRU 和 LFU 模式下如何复用？

> **知识点跳转：** [[Redis 过期删除策略和内存淘汰策略有什么区别？]]

**参考答案**

LFU 是把 24 bit 拆开复用：高 16 位存 ldt，也就是最后一次衰减的时间戳，低 8 位存 logc，是对数计数器，记录访问频次。8 位最大才 255，为什么不会溢出？因为 logc 不是每次访问都加一，而是概率性增长：当前计数在 0 到 5 之间，每次访问必涨；6 到 50 之间，大约百分之十的概率涨；超过 50，只有百分之一左右的概率涨。所以一个被访问上百万次的 key，计数可能也就四十多，离 255 还远得很。另外它还会随时间衰减，key 长时间不被访问，每过一个 lfu-decay-time 周期 logc 就减半，这样 LFU 能忘掉过去的热度，跟上访问模式的变化，不至于让一个曾经很热但已经过气的 key 永久霸着位置。

**追问参考答**

这里有个流传很广的错误说法，说 8 bit 溢出后会指向别的内存地址，这是错的，根本不存在溢出这回事。lru 模式下这 24 bit 全部用来存时间戳，lfu 模式下才拆成 16 位时间加 8 位计数，同一个字段两种解释，这是 Redis 省内存的典型手法。
