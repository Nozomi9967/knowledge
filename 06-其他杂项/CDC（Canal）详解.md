# CDC（Change Data Capture）— Canal 详解

## 一句话定义

> **CDC** = **Change Data Capture**（变更数据捕获）  
> 通过监听数据库的变更日志（如 MySQL binlog），实时捕获数据变更事件，同步到其他系统。

**本项目实现**：阿里巴巴 **Canal** — 监听 MySQL binlog，实时同步数据到 Elasticsearch 和静态页面。

---

## 架构图

```
MySQL ──产生 binlog ──▶ Canal ──▶ Canal Client ──▶ Feign ──▶ Search 服务 ──▶ ES
                                                               └─▶ 静态页服务 ──▶ HTML
```

---

## 核心原理

### MySQL 主从复制（Canal 模拟的机制）

```
Master: 写 binlog ──▶ Slave: 读 binlog ──▶ 回放 SQL ──▶ 数据一致
```

Canal **伪装成 MySQL Slave**，向 Master 请求 binlog，解析后推送给客户端。

### binlog 三种格式

| 格式            | 说明         | 优缺点                          |
| ------------- | ---------- | ---------------------------- |
| **STATEMENT** | 记录原始 SQL   | 体积小，但某些函数（NOW()）结果不一致        |
| **ROW**（✅ 推荐） | 记录每行变更前后快照 | 准确，但体积大                      |
| **MIXED**     | 混合模式       | 自动选择，默认用 STATEMENT，不确定时用 ROW |

### Canal 工作流程

```
1. Canal 模拟 Slave 协议向 MySQL 请求 binlog
2. MySQL 推送 binlog 到 Canal
3. Canal 解析 binlog 为 Event 对象（Insert / Update / Delete）
4. Canal Client 轮询拉取 Event
5. Client 通过 Feign 调用下游服务写入 ES / 更新静态页
```

---

## 为什么用 CDC 而不是业务代码直接写 ES？

### 方案对比

| 方式 | 优点 | 缺点 |
|------|------|------|
| **业务代码双写**（写 MySQL + 写 ES） | 实现简单 | 侵入业务代码，耦合高，失败难处理 |
| **Canal CDC**（✅ 本项目方案） | 解耦，无业务侵入 | 多一层组件维护 |
| **消息队列**（RocketMQ 异步同步） | 削峰填谷，可靠 | 增加延迟，架构更重 |

**本项目选择 Canal 的原因**：
- 业务代码零侵入 — 已有服务不需要改一行代码
- 一个 Canal 实例可监听多个表，统一管理
- 配合 Feign 直调，比 MQ 延迟更低

## 面试高频问题

### Q1：Canal 挂掉怎么办？数据一致性如何保证？

**提纲（三层防线）：**

```
方案一：Canal 自身高可用
  └─ Canal Server 集群 + ZooKeeper 选举
  └─ 故障时自动切换，Client 重连新 Server

方案二：全量+增量结合
  └─ 定期全量重建 ES（凌晨低峰期）
  └─ Canal 只负责增量同步
  └─ 即使 Canal 挂了，全量重建后数据最终一致

方案三：Canal 记录位点（position）
  └─ 重启后从断点续传
  └─ 不丢数据（binlog 有保留周期）
```

> [!tip] 口述版（按「位点保不丢 → 集群保不停 → 全量做兜底」的因果顺序讲）
> Canal 挂掉其实会引发两件事：一是下游同步中断、数据延迟；二是中断期间的变更会不会丢。我分三个层次保证一致性。
>
> **第一层，从机制上保证不丢数据。** Canal 本质是伪装成 MySQL 的从库去拉 binlog，它每消费一段就会记录一个位点 position。就算它挂了、重启之后，会拿着这个位点从断点续传，把中断期间的 binlog 重新拉一遍，所以数据不会丢。唯一的约束是 binlog 得有保留周期，只要宕机时间没超过 binlog 的过期时间，补回来就是完整的。
>
> **第二层，是解决单点问题，让服务不中断。** 生产上我会把 Canal Server 部署成集群，挂一个 ZooKeeper 做选举，同一时刻只有一个节点在拉 binlog，避免重复消费。一旦这个节点挂了，ZK 会选出新的节点接管，Client 自动重连到新 Server，同步继续。所以正常情况下，单节点宕机用户是感知不到的。
>
> **第三层，是兜底。** 就算真出现 Canal 长时间不可用、或者下游 ES 数据已经错乱的情况，我还有一个定期全量重建的机制——放在凌晨低峰期把整张表重新灌一遍 ES。日常 Canal 只管增量同步，全量负责最终一致。这样即使增量链路出过问题，也能靠全量把数据修正回来，达到最终一致。
>
> 说白了就是**位点保不丢、集群保不停、全量做兜底**，三层叠起来保证 Canal 同步的高可用和最终一致性。

### Q2：ES 索引如何重建？

**提纲（别名切换，零停机）：**

```bash
# Step 1: 创建新索引
PUT /shopsearch_v2

# Step 2: 全量同步数据（从 MySQL 全部查出写入新索引 v2）

# Step 3: 原子切换别名（零停机）
POST /_aliases
{
  "actions": [
    { "remove": { "index": "shopsearch_v1", "alias": "shopsearch" } },
    { "add":    { "index": "shopsearch_v2", "alias": "shopsearch" } }
  ]
}

# Step 4: 确认无误后删除旧索引 v1
```

> [!tip] 口述版
> 索引重建的核心是**用别名（alias）做一层间接，做到零停机**。业务代码读写 ES 时访问的是别名 `shopsearch`，而不是具体索引名，所以我可以在背后随便换它指向的真实索引。
>
> 步骤是这样的：先创建一个新索引 `shopsearch_v2`；然后把 MySQL 里的全量数据查出来，批量灌进 v2，这时候线上读的还是 v1，完全不受影响；v2 数据写好、校验没问题之后，我调一次 `_aliases` 接口，在**同一个原子操作里**把别名从 v1 摘掉、加到 v2 上。因为 remove 和 add 是一次请求提交的，中间不会出现别名指向空的瞬间，切过去的那一刻用户请求直接打到 v2，感知不到重建。确认稳定后再删掉旧的 v1。
>
> 有个细节要注意：重建期间 Canal 一直在往 v1 写增量，所以要么在切别名前，让 Canal 也把这些变更同步补一份到 v2，要么切完之后让 Canal 从位点重放一遍最近的 binlog 追平，否则全量灌完到切换这几秒的增量会漏掉。说白了就是**别名单点切换保零停机，位点重放保增量不丢**。

### Q3：Canal 同步延迟多大？

**提纲：**

- **局域网内**：毫秒级（通常 < 50ms）
- **高峰写入**：受 binlog 堆积影响，可能秒级延迟
- **优化**：Canal 消费端异步 + 批量写入 ES（攒一批再 flush）

> [!tip] 口述版
> 正常情况下延迟是**毫秒级**的，同机房内 MySQL 产生 binlog 到 Canal 解析推送，通常 50 毫秒以内，业务基本感觉不到。
>
> 但在**写入高峰期**可能会涨到秒级。原因是 Canal 的吞吐跟不上 MySQL 的写入速度时，binlog 会在消费端堆积，延迟就体现在这个积压上——不是链路慢，是消费不过来。
>
> 优化主要做在消费端：一是**异步化**，Canal 拉到变更不直接同步写 ES，而是丢到队列异步处理；二是**批量写**，攒够一批或者到一定时间间隔再 flush 到 ES，用攒批换 ES 的写入吞吐，避免一条一条写把 ES 打爆。这样高峰时延迟能稳在一个可接受的范围。

### Q4：和 Debezium 有什么区别？

**提纲：**

| 对比项 | Canal | Debezium |
|--------|-------|----------|
| 生态 | 阿里开源，Java 生态 | Red Hat，Kafka Connect 生态 |
| 输出 | 自定义 Client / MQ | 主要推 Kafka |
| 部署 | 轻量，单进程 | 需要 Kafka + Connect 集群 |
| 适合场景 | 中小团队，Spring Cloud 架构 | 大型数据平台，已有 Kafka 的团队 |

> [!tip] 口述版
> 这俩本质是同一类东西——都是 CDC，都是伪装成 MySQL 从库去监听 binlog 抓变更，所以原理层面没高下之分，区别主要在**生态和落地成本**。
>
> Canal 是阿里开源的，纯 Java，部署很轻，起一个进程就能用，消费方式灵活，可以自己写 Client 拉、也可以转成 MQ。Debezium 是 Red Hat 的，它是长在 Kafka Connect 生态上的，变更数据默认直接推到 Kafka，下游再从 Kafka 消费。所以 Debezium 的前置依赖更重——你得先有一整套 Kafka + Connect 集群。
>
> 选型上我的判断是：**如果团队本来就是 Spring Cloud 微服务、没有 Kafka**，那 Canal 更契合，Java 生态、部署轻、直接 Feign 调下游就行；反过来，如果公司已经有 Kafka、是个大数据平台，要做多条数据流汇聚，那 Debezium 顺着现成的 Kafka 生态走更自然。我们项目选 Canal，就是因为架构是 Spring Cloud、团队是 Java 栈，没必要为 CDC 再引入一套 Kafka。

## 面试话术

> **面试官**：说说你们项目中的 CDC 是怎么实现的？

**回答要点**：
1. **选型**：使用阿里 Canal 监听 MySQL binlog，实现数据变更捕获
2. **架构**：Canal 伪装成 MySQL Slave → 解析 binlog → Canal Client 拉取 → Feign 调用下游
3. **作用**：搜索同步（MySQL → ES）、静态页面更新
4. **高可用**：Canal 集群 + ZK 选举 + 断点续传
5. **容灾**：定期全量重建，增量同步保证最终一致性
