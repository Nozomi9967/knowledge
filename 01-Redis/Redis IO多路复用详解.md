## Redis IO 多路复用机制详解

### 一句话先说明白

> **IO 多路复用 = 一个线程同时监控多个 socket 连接，哪个连接有数据来了就去处理哪个。**

就好比一个前台（主线程）同时盯着多个电话（socket），哪个电话铃响了就接哪个，不会因为等一个电话而错过其他电话。

---

### 架构：Reactor 模式

Redis 的 IO 多路复用基于 **Reactor（反应器）设计模式**，也叫**文件事件处理器（File Event Handler）**。

```
                    ┌─────────────────────────────┐
                    │       事件处理器              │
                    │  (命令处理器/回复处理器等)      │
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │      文件事件分派器            │
                    │    (分配事件给对应的处理器)     │
                    └─────────────┬───────────────┘
                                  │
                    ┌─────────────▼───────────────┐
                    │      IO 多路复用程序           │
                    │  (select/epoll/kqueue)       │
                    └──┬──────────┬──────────┬────┘
                       │          │          │
                 ┌─────▼──┐ ┌───▼────┐ ┌───▼────┐
                 │socket 1│ │socket 2│ │socket 3│ ...
                 └────────┘ └────────┘ └────────┘
```

四大组件：

| 组件 | 角色 | 做什么 |
|------|------|--------|
| **套接字（Socket）** | 连接通道 | 每个客户端连接对应一个 socket |
| **IO 多路复用程序** | 监控者 | 同时监控所有 socket，谁可读/可写就通知 |
| **文件事件分派器** | 调度员 | 把 IO 多路复用程序上报的事件，分发给对应的处理器 |
| **事件处理器** | 执行者 | 真正干活——处理命令、回复结果 |

---

### 工作流程（完整过程）

```
客户端1连接    客户端2连接    客户端3连接
    │              │              │
    ▼              ▼              ▼
  socket1        socket2        socket3
    │              │              │
    └──────────────┼──────────────┘
                   ▼
    ┌─────────────────────────────┐
    │     IO 多路复用程序           │
    │   (底层用 epoll/select)      │
    │                              │
    │  1. 把所有 socket 注册到 epoll │
    │  2. 调用 epoll_wait() 阻塞等待 │
    │  3. 一旦有 socket 就绪，返回   │
    └─────────────┬───────────────┘
                   │ "socket2 可读了"
                   ▼
    ┌─────────────────────────────┐
    │     文件事件分派器            │
    │  把 socket2 的事件           │
    │  分发给对应的处理器            │
    └─────────────┬───────────────┘
                   │
                   ▼
    ┌─────────────────────────────┐
    │     命令请求处理器            │
    │  从 socket2 读取请求命令      │
    │  执行命令（GET/SET等）        │
    │  把结果写回 socket2           │
    └─────────────────────────────┘
```

### 用时间线看更清楚

```
时间 →  主线程（单线程）
        │
        ├─ 注册 socket1、socket2、socket3 到 epoll
        │
        ├─ epoll_wait() 阻塞等待  ──────────────────┐
        │                                            │
        │（此刻没有请求，线程挂起，不占 CPU）              │
        │                                            │
        │◄── 客户端2 发来 SET key value ─────────────┘
        │
        ├─ IO 多路复用程序发现 socket2 可读
        ├─ 放入就绪队列: [socket2]
        │
        ├─ 文件事件分派器从队列取出 socket2
        ├─ 分发给命令请求处理器
        │
        ├─ 命令请求处理器:
        │    ├─ 从 socket2 读取数据
        │    ├─ 解析命令 "SET key value"
        │    ├─ 执行命令（写内存）
        │    ├─ 将结果 "OK" 写入 socket2 的输出缓冲区
        │    └─ 注册 socket2 为"可写"事件
        │
        ├─ 回到 epoll_wait()
        │
        │◄── epoll 通知 socket2 可写了
        │
        ├─ 文件事件分派器 → 命令回复处理器
        ├─ 命令回复处理器将 "OK" 发送给客户端2
        │
        └─ 回到 epoll_wait()，继续等待下一个事件
```

关键点：**从头到尾只有一个主线程**，但它靠 epoll 同时监控成百上千个 socket，哪个有动静就处理哪个。

---

### 为什么 IO 多路复用比多线程好？

| | 多线程 | IO 多路复用（Redis 的方式） |
|---|---|---|
| **每个连接** | 一个线程 | 不需要额外线程 |
| **10000 连接** | 10000 个线程 → 上下文切换爆炸 | 1 个线程 + epoll，无切换开销 |
| **内存开销** | 每个线程有独立栈（~1MB） | 单线程，极小 |
| **锁竞争** | 需要各种锁保护共享数据 | 无锁，顺序执行 |

### 底层：select / epoll 对比

Redis 会根据操作系统自动选择最优的多路复用实现：

| 系统调用 | 平台 | 特点 | 瓶颈 |
|---------|------|------|------|
| **select** | 通用 | 最老，全平台支持 | 监听上限 1024，每次遍历全部 socket O(n) |
| **poll** | 通用 | 无 1024 限制 | 仍然是遍历 O(n) |
| **epoll** | Linux | **Redis 最常用** | 事件驱动 O(1)，性能最好 |
| **kqueue** | macOS/BSD | Mac 上的 epoll 等价物 | — |

**epoll 为什么快（面试高频）：**
1. 只返回就绪的事件，不需要遍历所有 socket（O(1)）
2. 使用 mmap 共享内核和用户空间的内存，减少数据拷贝
3. 支持边缘触发（ET）和水平触发（LT）两种模式

### 面试话术

> Redis 的 IO 多路复用基于 Reactor 模式实现了文件事件处理器。它由四部分组成：**套接字、IO 多路复用程序、文件事件分派器、事件处理器**。
>
> 工作流程是：IO 多路复用程序（底层用 epoll）同时监控多个 socket 的读写事件；当某个 socket 就绪时，多路复用程序将其放入队列；文件事件分派器从队列中取出事件，按顺序分发给对应的事件处理器（如命令请求处理器、命令回复处理器）；处理器执行具体的命令操作。
>
> 这样就实现了一个主线程同时处理成千上万个客户端连接，既避免了多线程的上下文切换开销，又不会因为某个连接阻塞而影响其他连接。
