# StackOverflowError 与 OutOfMemoryError（虚拟机栈）

## 问题：虚拟机栈什么时候抛什么异常？

JVM 虚拟机栈（Java Virtual Machine Stack）在两种不同场景下会抛出两种截然不同的异常：

- **`StackOverflowError`** — 单个线程的栈深度超限
- **`OutOfMemoryError`** — 整体内存无法为新线程分配栈空间

两者看似都是"栈的问题"，但触发的**原因层次**完全不同。

---

## StackOverflowError（SOF）

### 触发条件

**单个线程**请求的栈帧深度超过了 JVM 允许的最大深度。

### 典型场景

- 递归调用没有终止条件（无限递归）
- 方法调用链特别深（比如深度优先搜索没有显式栈，用递归走大图）
- 每个栈帧特别大（局部变量表里有大数组），导致即使深度不太深也超出限制

### 原理

```
线程 A 的虚拟机栈：
┌──────────────┐
│  方法调用 N   │  ← 新调用试图入栈
├──────────────┤
│  方法调用 3   │
├──────────────┤
│  方法调用 2   │
├──────────────┤
│  方法调用 1   │
└──────────────┘
栈容量上限 ← 到达这里就 SOF
```

每个方法调用创建一个栈帧入栈。当栈帧的总大小超过 **`-Xss`** 设定的阈值时，JVM 抛出 `StackOverflowError`。

### 示例

```java
public void infiniteRecursion() {
    infiniteRecursion(); // 永不终止 → StackOverflowError
}
```

### 关键点

- **只影响一个线程** — 其他线程不受影响，可以继续运行
- 可通过增大 `-Xss` 缓解（但治标不治本，正确做法是修复递归或改用迭代）
- 是**错误（Error）**，不是异常（Exception），一般不捕获

## OutOfMemoryError（OOM）— 无法创建线程

### 触发条件

JVM 尝试**为一个新线程分配栈空间**时，系统内存不足以满足分配需求。

### 典型场景

- 应用创建了大量线程（如无限制的线程池、每个请求新建线程）
- 每个线程栈较大（`-Xss` 设置偏大），可创建的线程数上限降低
- 32 位系统 + 堆占用了大部分进程地址空间，留给栈的虚拟地址不够

### 原理

```
系统物理内存：8 GB
堆（-Xmx）：       4 GB
元空间、Code Cache：~0.5 GB
操作系统保留：     ~1 GB
────────────────────────
剩余可用：         ~2.5 GB

每个线程栈（-Xss = 1MB）：约可创建 2500 个线程
当第 2501 个线程尝试创建时 → OOM
```

每**一个线程**都需要在 JVM 之外向操作系统申请一块内存作为栈空间。当：
```
线程数 × 栈大小 > 剩余系统内存
```
JVM 无法再为新线程分配栈 → `java.lang.OutOfMemoryError: unable to create new native thread`

### 关键点

- **影响整个 JVM 进程** — 新线程创建失败，可能导致服务不可用
- 是系统层面的内存不足，不是堆空间不够（堆 OOM 是 `Java heap space`）
- 典型错误日志：`OutOfMemoryError: unable to create new native thread`
- 排查方向：
  - `thread dump` 看有多少线程
  - 是否线程泄露（线程创建了没销毁）
  - 是否 `-Xss` 设置过大
  - 是否 `-Xmx` 堆太大，挤压了进程地址空间（32 位系统尤其明显）

## 根本区别对比

| 维度 | StackOverflowError | OutOfMemoryError（创建线程） |
|------|-------------------|---------------------------|
| **作用范围** | 单个线程 | 整个 JVM 进程 |
| **触发原因** | 栈帧深度超限 | 线程数量过多，内存耗尽 |
| **错误信息** | `java.lang.StackOverflowError` | `java.lang.OutOfMemoryError: unable to create new native thread` |
| **解决方向** | 改递归为迭代、检查递归终止条件 | 限制线程数、调小 `-Xss`、使用线程池 |
| **可否通过增大 -Xss 缓解** | 可以（延后触发，但可能掩盖 bug） | 适得其反！增大 -Xss 会减少可创建的线程数 |
| **对应区域** | 虚拟机栈内部 | 操作系统级内存分配 |

## 面试话术

> **问：虚拟机栈什么时候抛 StackOverflowError，什么时候抛 OutOfMemoryError？**
>
> 答：当单个线程的方法调用链过深，栈帧总大小超过 JVM 为该线程栈分配的上限时，抛 `StackOverflowError`，典型场景是无限递归。而当创建的线程数过多、每个线程都需要分配栈空间，导致整体系统内存不足以分配新的线程栈时，抛 `OutOfMemoryError`，典型错误信息是 `unable to create new native thread`。两者的区别在于：SOF 是一个线程的"纵向"越界，OOM 是线程数量的"横向"膨胀耗尽内存。

> **为什么不能简单地用增大 -Xss 来解决所有问题？**
>
> 对于 SOF，增大 -Xss 确实能延后触发阈值，但可能掩盖递归 bug。对于线程 OOM，增大 -Xss 反而**恶化问题**，因为每个线程占用更多内存，可创建的线程数更少。正确的做法是减少线程数（用线程池做复用、用异步模型代替同步阻塞）。
