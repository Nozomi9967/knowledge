### **字符编码是把字符和字节互相转换的规则。Java 的 `String` 内部处理的是字符，只有在读写文件、网络或控制台等外部数据时才需要指定编码。**

### **一、为什么需要字符编码**

计算机内部只能存储二进制数据，每个字节是 0 到 255 之间的一个数字。要处理文字，就必须约定"哪个字符对应哪些字节"，这个约定就是字符编码。

这个问题可以拆成两层理解。第一层是字符集（Character Set），它给每个字符分配一个唯一的编号，例如"中"对应 Unicode 编号 U+4E2D。第二层是编码方式（Encoding），它规定这个编号如何存成字节，例如 UTF-8 用 1 到 4 个字节表示一个字符，GBK 用 1 或 2 个字节表示一个汉字。

常见的编码包括：

- **ASCII**：只包含英文字母、数字和符号，每个字符 1 个字节。
- **ISO-8859-1**：西欧语言编码，同样是单字节，不能表示中文。
- **GBK / GB2312**：中文 Windows 常用的编码，汉字通常占 2 个字节。
- **UTF-8**：目前互联网的主流编码，兼容 ASCII，覆盖全世界字符，英文 1 字节，中文一般 3 字节。
- **UTF-16**：Java 内部字符串采用的编码基础，常见字符占 2 字节。

### **二、Java 中的字符与编码**

Java 的 `char` 类型是 16 位的 UTF-16 码元，`String` 则是由一串 `char` 组成的字符序列。因此在 Java 程序内部，你处理的是字符本身，不需要关心它以什么字节形式存放。

编码问题只出现在"字符与字节的转换"时刻，主要有以下几处：

1. **读写文件**：`FileReader`、`FileWriter` 使用的是平台默认编码，而 `InputStreamReader` 和 `OutputStreamWriter` 可以显式指定。
2. **网络通信**：HTTP 请求和响应的 `Content-Type` 中通常会声明编码，程序需要按此解码。
3. **字符串与字节数组**：`String.getBytes()` 把字符串编码成字节，`new String(bytes)` 把字节解码成字符串。
4. **源代码文件**：`.java` 文件本身也有编码，编译时由 `javac` 读取。

### **三、代码示例**

下面的代码演示了编码和解码的过程。推荐始终显式指定 `StandardCharsets.UTF_8`，避免依赖平台默认值。

```java
import java.nio.charset.StandardCharsets;
import java.util.Arrays;

public class EncodingDemo {
    public static void main(String[] args) {
        String text = "中A";

        // 编码：字符串 -> 字节数组
        byte[] utf8Bytes = text.getBytes(StandardCharsets.UTF_8);
        byte[] gbkBytes = text.getBytes(java.nio.charset.Charset.forName("GBK"));

        System.out.println("UTF-8 字节: " + Arrays.toString(utf8Bytes));
        System.out.println("GBK 字节: " + Arrays.toString(gbkBytes));

        // 解码：字节数组 -> 字符串
        String fromUtf8 = new String(utf8Bytes, StandardCharsets.UTF_8);
        System.out.println("正确解码: " + fromUtf8);

        // 错误示范：用 ISO-8859-1 解码 UTF-8 字节，会得到乱码
        String wrong = new String(utf8Bytes, StandardCharsets.ISO_8859_1);
        System.out.println("错误解码: " + wrong);
    }
}
```

运行后可以看到，"中"在 UTF-8 下是 3 个字节，在 GBK 下是 2 个字节。用错误的编码解码时，字节没有变，只是被按照另一套规则解释，于是出现乱码。

### **四、乱码产生的原因**

乱码的本质是**编码和解码使用的规则不一致**。常见场景包括：文件以 UTF-8 保存却按 GBK 读取，网页声明的编码与实际不符，数据库连接字符集与表的字符集不同，或者 `javac` 使用的源码编码与文件实际编码不一致。

排查时可以按照"数据从哪里来、按什么编码产生；数据到哪里去、按什么编码解释"这两个问题逐一检查，通常就能定位问题。

### **五、Java 版本的注意事项**

在 JDK 18 之前，`file.encoding` 默认值取决于操作系统。中文 Windows 上通常是 GBK，因此同一份代码在不同系统上的行为可能不同。从 JDK 18 开始（JEP 400），Java 的默认字符集统一为 UTF-8，但控制台输出（`System.out`）仍可能受系统编码影响。

编译时如果源文件是 UTF-8 而编译器按 GBK 读取，中文字符串就会出错，可以通过 `javac -encoding UTF-8 EncodingDemo.java` 显式指定。

### **六、实践建议**

在新项目中，建议统一使用 UTF-8 作为文件、源码、数据库、网络传输的编码，读写时始终显式传入 `StandardCharsets.UTF_8`，并避免使用已经过时的 `String.getBytes()` 无参写法和依赖平台默认值的 API。这样基本可以避免绝大多数编码问题。

理解了"字符是抽象的，字节是具体的，编码是两者之间的翻译规则"这一点，字符编码相关的问题大多就能迎刃而解。
