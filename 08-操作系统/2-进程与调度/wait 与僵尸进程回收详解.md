# wait 与僵尸进程回收详解

> 子进程 `exit()` 之后，内核**故意不释放它的 PCB**——因为退出码还等着交给父进程。父进程必须调用 `wait()` 家族把它「收走」，内核才能释放。父进程不来收，就留下**僵尸 Z**。
>
> 这个文件回答四个问题：**为什么要 wait、为什么叫 wait、父进程 wait 时能不能干别的、SIGCHLD 和轮询的延迟差在哪。**

---

## 一、问题的起点：内核为什么不自己清理

子进程退出时可能**带着一个退出码**（`exit(0)` / `exit(1)`），或者带着「被哪个信号杀掉的」这个信息。而这份信息**只有父进程有资格知道**。

内核没法替父进程决定「你还要不要这个退出码」，所以它的做法是：**先把 PCB 留着**。于是顺序是——

1. 子进程 `exit()` → 进程实体（地址空间、代码、数据、打开的文件）**全部释放**
2. 内核给父进程发 **SIGCHLD** 信号，**但 PCB 留着**，状态变成 **Z（僵尸）**
3. 父进程调 `wait()` → 读走退出码 → **内核这时才释放 PCB**

**僵尸不是「没清理干净」，是「内核在等父进程签收」。** 这一句是整章的核心。

怎么理解「实体已释放、PCB 还在」？——僵尸进程之所以 `kill -9` 杀不掉，就是因为它**已经没有可执行实体了**（可执行实体 = 程序段 + 数据段这些**能被内核调度上 CPU** 的部分，此时连同地址空间、页表、运行栈一起全部释放，只剩一张 PCB），剩下的只是内核里一张等着被认领的「档案卡」，信号没有送达对象。

→ **通俗理解**：PCB 像医院的**病历本**，内核（医生）从不盯着病人本人、只翻病历本。病人已经走了，但病历本还压在窗口没人取——那就是**僵尸**；病历本取走归档——进程才**真正消亡（X）**。

---

## 二、为什么叫 wait

看 man 手册的标题就明白了：

> **wait, waitpid, waitid — wait for process to change state**

名字取自**调用者的视角**：父进程要做的事就是「**等**子进程变状态」，所以叫 `wait`。收尸是**等价于**这个等待的——你没法「不等就拿退出码」。

**为什么没有单独的 `reap()` 系统调用？** 因为在 Unix 里「等子进程结束」和「取它的退出码」**是同一个动作的两面**：想拿退出码，就必然要等到它死。内核把两件事合成了一个 syscall，名字跟着那个更主动的动作走。

---

## 三、wait 的两个职责，和整个家族

`wait` 家族其实是「**子进程事件等待 + 状态汇报**」接口，收尸只是职责之一：

- **① 等待**——阻塞（或非阻塞）直到子进程状态变化
- **② 回收 + 汇报**——释放僵尸的 PCB，把退出状态交回父进程

而且「状态变化」**不只有「死」**——这点很多人不知道：

- **默认**：只报「终止」
- **`WUNTRACED`**：也报「**停止**」（SIGSTOP / 调试打断）
- **`WCONTINUED`**：也报「**恢复**」（SIGCONT 唤醒）

| 调用 | 等谁 | 特点 |
|------|------|------|
| `wait(&st)` | **任意**一个子进程 | 最简单的阻塞版 |
| `waitpid(pid, &st, opt)` | 指定 pid / 进程组 / `-1`(任意) | 带选项，**主力** |
| `waitpid(..., WNOHANG)` | 同上 | **非阻塞**：没有已退出的就立刻返回 0 |
| `waitid(...)` | 同上 | 信息更全，支持 `WNOWAIT`（**只看不收**，先探再决定） |
| `wait3` / `wait4` | 任意 | BSD 遗留，额外回传资源用量 `rusage` |

常用选项：

| 选项 | 作用 |
|------|------|
| `WNOHANG` | 不阻塞，没结果立刻返回 |
| `WUNTRACED` | 也报告「停止」状态 |
| `WCONTINUED` | 也报告「恢复」状态 |
| `WNOWAIT` | 只查询、**不回收** |

**只能收「亲儿子」**：`wait` 只能收**直接子进程**，收不到孙子。孙子得由你儿子去收，或者把自己设成 **subreaper**。

## 四、父进程 wait 时能干别的吗

**能，看你怎么用。** 默认的 `wait()` 是阻塞的——调用线程进入 **S 状态（可中断睡眠）**，但注意：

> **阻塞的是「调用它的那个线程」，不是「整个进程」。** Linux 上多线程进程里，其他线程照跑。

想不阻塞，有三条路：

### ① `WNOHANG`：非阻塞轮询

```c
pid_t pid = waitpid(-1, &status, WNOHANG);
if (pid == 0) {
    /* 还没有子进程退出，去干别的活，过会儿再来问 */
}
```

父进程可以「干一段 → 来看一眼 → 再干一段」。**代价**：延迟由你设的轮询间隔决定，而且轮询本身有 CPU 空转。

### ② 标准做法：平时不管，交给 SIGCHLD

```
子进程退出 → 内核给父进程发 SIGCHLD
                    ↓
        信号处理函数里一次性排空：
        while (waitpid(-1, &st, WNOHANG) > 0) { /* 收一个 */ }
```

父进程平时该干嘛干嘛、**完全不阻塞**，信号来了才进 handler 收尸。

### ③ 更现代：`pidfd`

Linux 5.3+ 可以 `pidfd_open(pid)` 把子进程变成一个**文件描述符**，然后 `poll`/`epoll` 上去等——「等子进程」从此变成「等一个 fd」，能和你的 IO 多路复用统一调度，**不需要信号**。

---

## 五、关键辨析：SIGCHLD 的延迟 ≠ 轮询延迟

这是最容易绕晕的一点。**SIGCHLD 确实有延迟，但那个延迟不是轮询延迟。**

| | 轮询（`WNOHANG` 定时查） | **SIGCHLD** |
|---|---|---|
| 触发方向 | **你拉**（pull）——自己定时去问 | **内核推**（push）——事件一发生内核主动告诉你 |
| 延迟由谁决定 | **你设的间隔** | **内核的调度时机** |
| 平均延迟 | ≈ 间隔 / 2 | 亚毫秒级 |

**轮询的延迟是你自己拧的旋钮**——间隔设 100ms 就可能晚 100ms，而且和事件何时发生无关（可能刚查完就退了，白等一整个间隔）。**SIGCHLD 的延迟和任何参数无关**，事件一发生内核立刻推，晚的那一点点纯粹来自「信号什么时候能交到你手里」。

那这点投递延迟从哪来？信号要等目标线程**从内核态返回用户态**那一刻才被投递：

| 父进程当时在干嘛 | 投递时机 | 延迟量级 |
|---|---|---|
| **正在用户态跑**（CPU 密集） | 等下一次进内核——一次系统调用、一次缺页、或一次时钟中断 | 通常 **小于 1 个 tick**（tick 是 1~4ms） |
| **在 S 状态睡**（可中断睡眠） | **立刻被信号唤醒** | ≈ 0 |
| **在 D 状态**（不可中断睡眠） | 只能等那个慢 syscall 返回 | 可能很久——这是 D 状态的锅，任何机制都救不了 |

所以最坏情况是「**等一个调度 tick**」（毫秒级），不是「等你设的间隔」（可能是秒级）。

## 六、那个 `while + WNOHANG` 不是轮询，是「排空」

```c
void on_sigchld(int sig) {
    int saved_errno = errno;
    /* 必须循环：SIGCHLD 不排队，只是置一个 pending 标志位 */
    while (waitpid(-1, NULL, WNOHANG) > 0) { }
    errno = saved_errno;
}
```

容易被误读成轮询，但**它不是「过一会儿再来看看」，是「一次性排空」**。为什么必须循环？

> **信号不排队。** 标准信号（非实时信号）只有一个 **pending 标志位**，不做计数。三个子进程同一瞬间退出，内核只会把那个位**置一次**——你最多收到**一个** SIGCHLD。所以 handler 一进来，必须把**所有已经死掉的**子进程一口气全收完，收到 `waitpid` 返回 0 才退出。

- 循环里用 `WNOHANG` 是为了**不阻塞**——已经死掉的是有限个，收完就该走，不能在 handler 里再等下一个（那才是真轮询）。
- 这个循环**不引入延迟**，它是**防漏**的。少了它才会出问题：漏收 → 剩下的变僵尸。

---

## 七、彻底甩掉 handler：self-pipe / signalfd / pidfd

SIGCHLD 的真正麻烦其实不是延迟，是**信号处理函数的约束**——里面只能调 async-signal-safe 的函数（`malloc`、`printf`、大多数库函数都不能碰）。两个办法把它转成普通 fd：

| 方案 | 做法 | 说明 |
|------|------|------|
| **self-pipe trick** | handler 里只 `write` 一个字节到 pipe，主事件循环读这个 pipe 再干正事 | 经典手法，可移植性好 |
| **`signalfd()`** | 把信号直接变成一个**可读 fd**，挂进 epoll | Linux 2.6.22+，信号从此就是一次「fd 就绪」 |
| **`pidfd`** | `pidfd_open(pid)` 把子进程变成 fd，`epoll` 上去等 | Linux 5.3+，**信号完全不需要**，零 handler、无丢失问题，现代推荐 |

**特殊情况**：如果你**根本不在乎退出码**，可以把 SIGCHLD 设成 `SIG_IGN`，或 `sigaction` 带 `SA_NOCLDWAIT`——**内核直接自动收尸**，既不产生僵尸也不发信号。

---

## 八、工程选择表

| 诉求 | 选什么 | 代价 |
|------|--------|------|
| 要退出码、不介意占线程 | 专用线程阻塞 `wait()` | **占一个线程** |
| 要退出码、不占线程、能接受 handler 约束 | **SIGCHLD + drain 循环** | handler 有函数限制；必须排空 |
| 连 handler 都不想写 | **`signalfd` / `pidfd` + epoll** | 需要较新内核（pidfd 要 5.3+） |
| **根本不在乎退出码** | `SIG_IGN` 或 `SA_NOCLDWAIT`（详见 §十） | 拿不到退出码 |

顺带一个坑：**阻塞式 wait 在服务端不可取**——一个子进程占一个线程去 wait，等于把并发能力焊死，所以才要 SIGCHLD 或 pidfd。另外 `wait` 会被信号打断，返回 `-1` 且 `errno == EINTR`；handler 带 `SA_RESTART` 时内核会自动重启这个 wait，你感知不到。

## 九、孤儿进程、re-parent 与 subreaper

- **孤儿进程**：父进程先退出了。它会**被 re-parent 给 init（PID 1）**，由 init 接管并自动 `wait` —— 所以僵尸问题会「自愈」。
- **subreaper**：如果不想让孙子被 PID 1 收养，可以调 `PR_SET_CHILD_SUBREAPER` 把自己设成「子收割者」，后代的孤儿都归你收。
- **容器里的坑**：容器里的 PID 1 是**你自己的主进程**，它通常不 `wait`——所以僵尸会在容器里堆积。Docker 要加 `--init`（tini）兜底。（展开见下一节。）

---

## 十、不想收尸的两种办法：`SIG_IGN` 与两次 fork

前提回顾：默认情况下子进程死了 → 内核留 PCB 等父进程 `wait` → 不收就是僵尸。想让「不产生僵尸」成立，只有两条路：

> **要么让内核别留 PCB，要么让这个进程不归我管。**

| 办法 | 收尸的人 | 依赖 PID 1 吗 |
|------|---------|:---:|
| **① `SIG_IGN`** | **内核**——子进程退出那一刻直接回收 | ❌ 不依赖 |
| **② 两次 fork** | **PID 1**——孤儿过继给它之后由它 `wait` | ✅ **依赖** |

记忆点：**办法一是「内核收」，办法二是「init 收」。** 所以「PID 1 会不会收」这个问题，**只对办法二有意义**。

### 办法一：`SIG_IGN` —— 让内核自己收

最容易搞混的一点：

| SIGCHLD 的处置 | 子进程会变僵尸吗 |
|------|:---:|
| **`SIG_DFL`（默认）** | **会** |
| **`SIG_IGN`（显式设成忽略）** | **不会** |

默认处置对 SIGCHLD 来说**字面上也是「忽略」**——但那个忽略只是「我不做任何处理动作」，**不改变内核留僵尸的行为**。而**显式**设 `SIG_IGN` 是在告诉内核「我彻底不要这个子进程的退出状态」——内核于是在子进程终止时**顺手把它回收**，根本不进僵尸态。

```c
/* 简单写法（Linux 有效，但可移植性差） */
signal(SIGCHLD, SIG_IGN);

/* 可移植的显式写法：语义明写在 flag 上 */
struct sigaction sa;
sa.sa_handler = SIG_IGN;
sa.sa_flags   = SA_NOCLDWAIT;      /* ← 关键：明确告诉内核「别等我收」 */
sigaction(SIGCHLD, &sa, NULL);
```

**代价**：拿不到退出码。之后调 `wait()` 会返回 `-1`、`errno = ECHILD`（没有子进程可等）。所以前提是**你根本不关心子进程怎么死的**。

**为什么它跟 PID 1 无关**：回收是**内核**做的，全程没有经过任何进程、不需要 PID 1 出场——所以容器里和宿主机上效果一样。

### 办法二：两次 fork —— 让这个进程不归我管

思路完全不同：**不是让内核别留 PCB，而是让「需要被收」的那个人不是我的孩子。**

单次 fork 的困境：`P --fork--> C`，C 是 P 的孩子，P 就得负责收尸——不想阻塞、也不想写 handler 就卡住了。

两次 fork：

```
父进程 P
  │ ① fork()
  ├──────────────────────▶ 中间进程 C
  │                          │ ② fork()
  │                          ├──────────────▶ 孙子进程 G   ← 真正干活的
  │◀── ③ C 立刻 exit() ──────┘
  │
  │ wait(C)   ← 一瞬间的事（C 马上就退，不会有僵尸积压）
  │
  └─ ④ 之后 P 彻底自由，该干嘛干嘛

G 的父亲 C 已经死了
      ↓
G 成为孤儿 → 内核把它 re-parent 给 PID 1（见上一节）
      ↓
★ PID 1 成为 G 名义上的父亲，收尸责任转移到它身上 ★
```

三个要点：① 真正干活的孙子 **G 不是 P 的孩子**，责任链断开；② 中间进程 **C 立刻退出**，P 要 `wait` 的只是一个马上要死的进程；③ 孤儿 **G 必定被过继给 PID 1**，而 init 的天职就是不断 `wait` 它的孩子。

这也是 `daemon()` 守护进程化的标准手法。

### 唯一的软肋：容器里 PID 1 不会收

办法二能不能成，**完全取决于「那个 PID 1 是不是一个会 wait 的存在」**。

| 环境 | PID 1 是谁 | 会 wait 吗 | 办法二 |
|------|-----------|:---:|:---:|
| 宿主机 | systemd / init（专职管进程） | ✅ | 成功 |
| **容器** | **你自己的主进程**（如 `java -jar app.jar`） | ❌ | **塌陷** |

容器里根本没有一个「专门的 init」——PID 1 这个身份被业务应用占了，而它**不会去 wait 一个不认识的孙子**（它甚至不知道自己当过爹）。于是 G 变僵尸、一个接一个攒。

**这不是「系统坏了」，是「这条机制依赖的那个人不在场」。**

解法：`docker run --init`

```
docker run --init my-java-app
        ↓
Docker 额外塞一个极小的 init 进程（tini）进容器
        ↓
tini 抢下 PID 1，你的应用退到它下面
        ↓
G 变孤儿 → 过继给 tini → tini 专职收尸 ✅
```

tini 只有两三百 KB，只干两件事：**① 收尸**（`wait` 所有孤儿，消灭僵尸）**② 转发信号**（不转发的话 `docker stop` 的 SIGTERM 到不了你的应用，停止会变慢甚至杀不掉）。

> 注意：办法一 `SIG_IGN` **不受这个影响**——它的回收在内核里做，不依赖 PID 1。

→ **通俗理解**：办法一是「**交给民政局**」——内核当场就办，跟街道办无关；办法二是「**交给街道办**」——孤儿按法律规定归 init 管，可容器里这个职位**被你自己公司占了**，公司不做走访，孩子就没人数；`--init` 就是专门雇一个靠谱的街道办（tini）进驻。

## 十一、Java 侧：你从来不用管这些

| Java API | 等价于 | 是否阻塞 |
|----------|--------|:---:|
| `Process.waitFor()` | 阻塞式 `wait` | 阻塞调用线程 |
| `ProcessHandle.onExit()` | 返回 `CompletableFuture` | **非阻塞**（推送模型，不是轮询） |

**真正收尸的不是你的代码**：JVM 启动时会拉起一个 **process reaper 线程**，在后台替所有 `Runtime.exec` / `ProcessBuilder` 起的子进程 `waitpid`。所以 Java 进程既不攒僵尸，你也不用关心 SIGCHLD 那个 drain 循环——只有用 JNI / 本地库自己 `fork` 时才需要操心。

## 面试话术

> "子进程 exit 之后内核不会立刻释放它的 PCB，因为退出码要交给父进程——所以它先发一个 SIGCHLD，把 PCB 留着、状态置成僵尸 Z，等父进程调 `wait` 来收。这就是为什么僵尸进程 `kill -9` 杀不掉：它已经没有可执行实体了，信号没有送达对象。
>
> 那父进程 wait 的时候会不会被卡住？默认会阻塞调用线程，但有三条路绕开：一是 `WNOHANG` 非阻塞轮询，缺点是延迟你自己拧；二是标准做法，平时不阻塞，挂着 SIGCHLD，信号来了在 handler 里收——这里有个必踩的坑，**信号不排队，只置一个 pending 位**，所以 handler 里必须 `while` 把已经退出的全收完，少收的就会变僵尸；三是 Linux 5.3 之后的 `pidfd`，把子进程变成一个 fd 挂进 epoll，等子进程和等 socket 变成同一件事，连信号都不用了。
>
> 这里要分清一个概念：SIGCHLD 有延迟，但那是**信号投递延迟**，来自内核调度时机，毫秒级、不可调；轮询的延迟是**你设的间隔**，性质完全不同。工程上如果不关心退出码，直接把 SIGCHLD 设成 `SIG_IGN` 或者带 `SA_NOCLDWAIT`，内核自动收尸，最省事；如果是要启动一个长期后台进程、父进程想立刻返回，那就用两次 fork 让孙子进程变孤儿、被 PID 1 收养，收尸责任就转移出去了——不过在容器里得加 `--init`，因为容器的 PID 1 是业务进程自己，它不会 wait。Java 里这些都被包掉了——JVM 有个 process reaper 线程在后台替你 wait，所以你基本不会碰到僵尸。"
