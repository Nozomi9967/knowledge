> **租户（Tenant）**：SaaS 场景中，一套系统服务多个客户（组织/企业），每个客户称为一个租户。租户之间数据必须隔离，这是多租户架构的核心需求。

### **通过 `AbstractRoutingDataSource` + `ThreadLocal` 在请求入口切换数据源即可实现多租户路由**

面试口述的话,我大概会这么讲:

---

首先讲**整体思路**。Spring 的 `AbstractRoutingDataSource` 本质上是一个"代理数据源",内部持有一个 `Map<Object, DataSource> targetDataSources`,每次拿连接的时候会调用它的抽象方法 `determineCurrentLookupKey()`,根据返回的 key 到 map 里找真正的 DataSource。所以多租户切换,核心就是让这个 key 跟着当前请求走。

由于一次 HTTP 请求会绑定到一个线程,自然就想到用 `ThreadLocal` 来传递租户标识——请求进来的时候在拦截器里从 header(比如 `X-Tenant-Id`)拿到租户 ID,塞进 `ThreadLocal`,`determineCurrentLookupKey` 从里面读,请求结束在 `finally` 里 `remove()` 掉,避免线程池复用导致串数据。

---

**代码结构**我会画这几块:

**1. 租户上下文**

```java
public class TenantContext {
    private static final ThreadLocal<String> CTX = new ThreadLocal<>();
    public static void set(String t) { CTX.set(t); }
    public static String get() { return CTX.get(); }
    public static void clear() { CTX.remove(); }
}
```

**2. 路由数据源**

```java
public class DynamicDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TenantContext.get();
    }
}
```

**3. 配置类**里把多个真实 DataSource 注入到 `targetDataSources` map,再设置一个 `defaultTargetDataSource` 兜底:

```java
@Bean
public DataSource dataSource() {
    DynamicDataSource ds = new DynamicDataSource();
    Map<Object, Object> map = new HashMap<>();
    map.put("tenant_a", buildDs(...));
    map.put("tenant_b", buildDs(...));
    ds.setTargetDataSources(map);
    ds.setDefaultTargetDataSource(map.get("tenant_a"));
    return ds;
}
```

**4. 拦截器/Filter** 在 `preHandle` 里 `TenantContext.set(request.getHeader("X-Tenant-Id"))`,`afterCompletion` 里 clear。

---

然后重点讲**几个坑**,这块面试官很爱追问:

**第一,`ThreadLocal` 在异步场景会失效。**比如 `@Async`、`CompletableFuture`、Reactor 线程切换、`parallelStream`,子线程拿不到父线程的值。解决方案是用阿里的 `TransmittableThreadLocal`,或者在提交任务时手动包一层,把上下文透传过去。

**第二,连接池预热问题。**`AbstractRoutingDataSource` 每次获取连接才路由,所以每个租户的底层 DataSource 建议独立配置 HikariCP（Java 连接池组件，连接复用避免频繁创建销毁）,连接池大小要按租户数量做规划,否则连接数会爆炸。租户特别多(比如上千个)的话,不适合每个租户一个池,更常见的做法是"共享库 + schema 隔离（同一数据库内按 schema 区分租户）"或"共享库 + tenant_id 字段隔离"。

**第三,也是最关键的——跨数据源事务问题。**

Spring 默认的 `DataSourceTransactionManager` 是**绑定单个 DataSource 的**,它在事务开始时从 DataSource 拿一个连接、绑定到当前线程,后面整个事务里所有 SQL 都走这个连接。而 `AbstractRoutingDataSource` 只在**第一次获取连接**时决定用哪个真实数据源,一旦事务开启,连接就固定了,即使你中途改了 `ThreadLocal` 也没用——**同一个 `@Transactional` 方法里没法真正操作两个库**。

如果业务上确实要同时写两个租户库,有几种方案,面试时按由简到复杂讲:

1. **不要跨库事务,拆成两个方法,每个方法自己的 `@Transactional`**。这是最推荐的,业务上通过补偿/重试保证最终一致。
2. **JTA + XA 两阶段提交**,比如 Atomikos、Narayana。能强一致,但性能差、依赖数据库 XA 支持、运维复杂,现在互联网项目基本不用。
3. **应用层最终一致性**:本地消息表、事务消息(RocketMQ)、Seata 的 AT/TCC/Saga 模式。Seata AT 模式对业务侵入小,是目前比较主流的选择。
4. **业务上尽量避免**:多租户场景其实很少需要跨租户写,大部分请求就落在一个租户库里,所以问题会被自然规避。

---

最后我会补一句**给面试官看深度的话**:多租户方案要根据租户规模选型——租户少、隔离要求高就 database-per-tenant 配合 `AbstractRoutingDataSource`;租户多就 schema 或行级隔离;而事务尽量控制在单库内,跨库要么拆事务 + 最终一致,要么上 Seata,别轻易上 XA。

这样一套讲下来大概 5\~7 分钟,基本能覆盖考察点。
