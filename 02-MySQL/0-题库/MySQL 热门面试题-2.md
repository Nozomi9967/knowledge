## 四、日志系统（7 题）

### 20. MySQL 有哪几种日志？各自的作用是什么？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

三种核心日志。undo log 是回滚日志，属于 InnoDB 引擎层，两个作用：事务回滚，以及给 MVCC 提供版本链。redo log 是重做日志，也是 InnoDB 层的，作用是崩溃恢复、保证事务的持久性，宕机后重放它就能把已提交的修改补回来。binlog 是归档日志，属于 Server 层，所有存储引擎都能用，作用有两个：主从复制和数据备份。层归属一定要说清，这是被追问最多的地方：undo 和 redo 是 InnoDB 自己的，换引擎就没有；binlog 是 Server 层的，只要用 MySQL 就一直在。

**追问参考答**

undo log 和 redo log 都属于 InnoDB 存储引擎层，binlog 属于 Server 层。这个区别直接决定了几个后果：换 MyISAM 就没有事务和 MVCC，也就没有 undo 和 redo；而 binlog 不管什么引擎都会记，所以主从复制对引擎是透明的。

### 21. undo log 的两大作用？redo log 和 undo log 的区别？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

undo log 的两大作用是事务回滚和 MVCC。回滚靠的是记录修改前的数据，事务失败时逆向执行一遍就回到原状；MVCC 靠的是把旧版本串成版本链，快照读沿着 roll_pointer 往回找可见版本。它跟 redo log 的区别是记录内容正好相反：redo 记的是修改后的状态，用于崩溃恢复，保证已提交的数据不丢；undo 记的是修改前的状态，用于回滚，保证未完成的操作能撤销。

**追问参考答**

再补一个常被追问的细节，三种操作 undo 记的东西不一样。插入操作只需要记这条记录的主键，回滚时按主键删掉就行，所以体积最小；删除操作要把整条记录的完整内容记下来，回滚时原样插回去，所以体积最大；更新操作记的是被修改字段的旧值，回滚时改成旧值即可。记法就是"插入记主键、删除记整行、更新记旧值"。

### 22. 为什么需要 Buffer Pool？什么是脏页？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

Buffer Pool 是 InnoDB 启动时申请的一块内存区域，用来缓存磁盘上的数据页，避免每次读写都走磁盘。读的流程是先查 Buffer Pool，命中就直接返回，没命中才从磁盘读进来、顺手放进池子里。写的流程是先改池子里的数据页，同时把它标记为脏页，后台线程在合适时机批量刷回磁盘。脏页的定义就是内存里已经改过、但还没同步到磁盘的数据页。这里有个高频数字必须记准：InnoDB 的数据页默认是 16KB，不是 512 字节，512 字节是传统机械硬盘的扇区大小，两个概念差 32 倍，说错基本会被当场纠正。

**追问参考答**

为什么要有 Buffer Pool 而不是直接读写磁盘，因为内存和磁盘差几个数量级，缓存命中率高的时候整个数据库的响应时间由内存决定。脏页不能一直不刷，否则崩溃就丢数据，所以有后台线程按 LRU 和脏页比例逐步刷盘，同时 redo log 已经把修改记下来了，即使脏页丢了也能重放恢复。

### 23. 什么是 WAL（预写日志）？为什么事务提交时写 redo log 而不是直接把脏页刷回磁盘？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

WAL 是预写日志，思路是修改数据时先写日志、再改内存页，脏页的落盘往后推。事务提交时只保证 redo log 落盘就返回，脏页由后台慢慢刷。为什么不直接刷脏页，因为两者 IO 模式完全不同：脏页散落在磁盘各处，刷一个页要先寻道定位到那个位置，是随机 IO；redo log 是往文件末尾追加，写指针一直往前推，是顺序 IO。磁盘顺序写比随机写快好几个数量级，所以先写日志这一步的开销可以忽略，整体吞吐反而高得多。

**追问参考答**

为什么 redo log 本身能顺序写，因为它记录的是物理修改，格式是"第几号表空间的第几号页、偏移量多少、写入几个字节"，内容定长，而且写的时候根本不关心原来那页在磁盘的哪个位置，直接往文件尾巴上追加就行。写数据页就不一样，页有固定位置，必须先定位再写，天然随机。

### 24. redo log 什么时候刷盘？innodb_flush_log_at_trx_commit 三个值分别是什么？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

刷盘时机有四个：后台线程每秒轮询刷一次；redo log buffer 写满一半容量时刷；事务提交时按参数决定怎么刷；MySQL 正常关闭时把剩下的全刷掉。参数 innodb_flush_log_at_trx_commit 有三个值。0 是事务提交时什么都不做，数据只留在 redo log buffer 里，等每秒的后台线程刷，崩溃可能丢掉最近一秒的数据，性能最好但最不安全。1 是每次提交都 fsync 到磁盘，不丢任何已提交数据，最安全但每次提交都要等磁盘，IO 开销最大，这是默认值。2 是提交时 write 到操作系统的 page cache 就返回，由操作系统异步刷，MySQL 进程崩了不丢，但操作系统崩了会丢。

**追问参考答**

三个值各丢什么要说得准确：0 丢最近一秒的数据；1 什么都不丢，已经提交的一定在盘上；2 只在操作系统崩溃时丢，MySQL 进程自己崩不影响。这里有个常见错误，说值 1"会丢未提交事务的数据"，但未提交的数据本来就不该持久化，那不是它的缺点，值 1 恰恰是最安全的配置。

### 25. redo log 和 binlog 的区别？

> **知识点跳转：** [[MySQL日志系统与主从复制]] · [[binlog三种格式（statement-row-mixed）]]

**参考答案**

三个角度讲清。层归属上，redo log 是 InnoDB 引擎层的，binlog 是 Server 层的。用途上，redo 做崩溃恢复，binlog 做主从复制和数据备份。写入方式上，redo 是固定大小的文件组循环写，写满就从头覆盖最旧的记录；binlog 是追加写，一个文件写满就新建下一个，历史完整保留。为什么要这样设计，因为 redo 只需要保留"还没刷盘的脏页对应的那份日志"就够恢复了，更早的用过就没用，可以覆盖；binlog 要保留完整历史做复制和按时间点还原，不能覆盖。

**追问参考答**

binlog 的刷盘频率由 sync_binlog 控制，0 是交给操作系统决定，1 是每次事务提交都 fsync，N 是每 N 个事务刷一次。生产一般配 1，配合 redo 的 innodb_flush_log_at_trx_commit 等于 1，也就是常说的"双 1 配置"，能保证崩溃不丢已提交数据。另外 binlog 有三种格式，statement 记 SQL 语句、row 记行变更、mixed 自动切换，8.0 默认改成了 row，细节见 [[binlog三种格式（statement-row-mixed）]]。

### 26. 什么是两阶段提交？为什么需要它？崩溃恢复时怎么判断？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

两阶段提交是在 redo log 的提交过程中插入了 binlog 的写入，把它拆成三步：先把 redo log 写成 prepare 状态，然后写 binlog 并刷盘，最后把 redo log 标记成 commit。之所以要这么绕，是因为 redo 和 binlog 是两份独立的日志，如果不统一提交，就可能出现一个成功一个失败。先写 redo 后写 binlog 中间崩了，主库能靠 redo 恢复，但从库拿到的 binlog 缺这次更新；反过来先写 binlog 后写 redo 中间崩了，主库认为事务无效，从库却已经执行了一次。两种都会造成主从不一致，两阶段提交就是让两边"说好了再一起提交"。

**追问参考答**

崩溃恢复的判断靠 XID。重启后拿 redo log 里这个事务的 XID 去 binlog 里找，找到相同 XID 说明 binlog 已经完整写入了，此时直接提交，因为 binlog 会被从库执行，主库必须跟着提交才能保持一致；找不到或者 binlog 不完整，说明只有 redo 写了，事务回滚。

## 五、主从复制（3 题）

### 27. 主从复制是怎么实现的？IO 线程和 SQL 线程各负责什么？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

主从复制是基于 binlog 的。完整链路是：主库执行写操作记 binlog，从库的 IO 线程连上主库的 log dump 线程，把 binlog 拉过来先落到本地的 relay log 中继日志里，然后从库的 SQL 线程读 relay log，一条条回放执行。两个线程的分工要分清：IO 线程管网络接收，SQL 线程管本地执行，relay log 夹在中间当缓冲，把"收得快"和"放得慢"解耦开，网络抖动或者回放卡顿不会互相拖累。还有一个关键点，复制默认是异步的，主库写完 binlog 立刻返回客户端，不等从库确认，所以只能做到最终一致，主库一崩就可能丢掉还没同步出去的那部分。

**追问参考答**

从库不是直接拿 binlog 执行，中间必须过 relay log。原因很直接：IO 线程只负责把 binlog 完整拉下来落盘，这一步越快越好；SQL 线程按自己的节奏回放，可能因为大事务、锁等待而变慢。有了 relay log，接收和回放解耦，网络不用等执行。理解这个之后，"为什么主从延迟"也就好解释了，延迟主要发生在 SQL 线程回放这一环。

### 28. 主从复制有哪几种模型？它们的区别？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

三种，按"等不等、等多少"来分。同步复制是主库等所有从库都确认收到了才返回客户端，一致性最强但最慢，任何一个从库慢都会拖垮整体写入性能。异步复制是写完 binlog 立刻返回，一个都不等，速度最快但可能丢数据，主库崩了从库还没收到的那部分就没了。半同步复制是折中，等至少一半从库确认收到就返回，延迟和安全性取中间。

**追问参考答**

说"半同步是等一半从库"不准确，正确的是等至少一半，也就是大于等于 N/2。这个措辞差别不是抠字眼：等一半听起来像固定等一半数量，而"至少一半"是达到这个门槛就放行，多一个少一个不影响返回时机。半同步存在的意义也就在这个折中上，异步完全不等太不安全，同步等所有又太慢。

### 29. 从库是不是越多越好？

> **知识点跳转：** [[MySQL日志系统与主从复制]]

**参考答案**

不是，从库越多主库压力越大。每多一个从库，主库就要为它创建一个 log dump 线程专门服务，线程数随从库数量线性增长，多线程调度的开销跟着上涨。多个从库同时拉 binlog，同一份文件被反复读取，主库的磁盘 IO 被放大。网络带宽也是瓶颈，binlog 本身有体积，从库越多总出口流量越大，可能把主库网卡打满，反过来影响正常业务。所以从库数量要按读流量的实际需要来定，同时监控主库的复制负载，不能盲目堆数量。

**追问参考答**

具体消耗分三块：CPU 上是每个从库一个 dump 线程带来的调度开销；IO 上是多份 binlog 并发读取导致寻道增多；带宽上是复制流量挤占业务流量。生产上如果确实需要很多只读副本，更好的做法是级联复制，让从库再往下挂从库分担主库压力，而不是全都直连主库。

## 六、查询执行流程（2 题）

### 30. 一条 SELECT 查询语句的执行流程是怎样的？

> **知识点跳转：** [[MySQL查询执行流程]]

**参考答案**

分几段走。先进连接器，TCP 握手建立连接、校验用户名密码、读取这个用户的权限，之后连接保持住，权限也在这个时刻确定下来。然后查查询缓存，命中就直接返回结果，不过 MySQL 8.0 已经把查询缓存整个组件删掉了，因为表一有更新缓存就全失效，命中率极低还要额外维护。接着是解析器，做两件事：词法分析把 SQL 拆成一个个关键字，语法分析检查是否符合语法规则、构建出语法树。最后是执行器，分三个阶段：prepare 阶段检查表和字段是否存在、把星号展开成具体字段；optimize 阶段由优化器制定执行计划，决定走哪个索引、join 顺序怎么排；execute 阶段按计划调用存储引擎接口读取记录，返回给客户端。

**追问参考答**

MySQL 8.0 删掉的是查询缓存组件，不是 buffer pool，这两个容易混。解析器做的两件事就是词法分析和语法分析。还有一个容易说错的地方：优化器不是解析器和执行器之间独立的一步，它是执行器阶段里的 optimize 子阶段，讲流程时别说成"第五步"。

### 31. EXPLAIN 里的 type 字段有哪些值？执行效率怎么排序？

> **知识点跳转：** [[MySQL索引]]

**参考答案**

type 表示访问类型，一共六档，效率从低到高排。最低是 ALL，全表扫描，逐行读完整张表。往上是 index，全索引扫描，虽然走索引但把整棵索引树都扫一遍。再往上是 range，索引范围扫描，用上了大于、小于、between 这类范围条件。再往上是 ref，非唯一索引的等值扫描，可能命中多行。再往上是 eq_ref，唯一索引扫描，join 的时候每行只匹配一条。最高是 const，主键或者唯一索引的精确等值匹配，优化器能确定最多返回一条记录。

**追问参考答**

const 的准确定义是查询条件是主键或唯一索引的精确等值匹配，比如 where id 等于 123，结果最多一条，属于常数级查找；不能笼统说成"主键索引扫描"，因为主键范围查询就不算 const 了。另外六档里最容易漏的是最底下的 ALL，答题时要从 ALL 开始往上数，别一开口就从 index 说起。

## 七、高级专题（4 题）

### 32. 现代 MySQL（5.6+）里 IN 和 EXISTS 还有明显性能差异吗？NOT IN 和 NOT EXISTS 遇 NULL 时有什么本质区别？

> **知识点跳转：** [[IN和EXISTS]]

**参考答案**

性能差异基本没有了，因为 5.6 之后有半连接优化，优化器会把 IN 和 EXISTS 重写成同一种执行计划。它主要走两个策略：子查询结果集小的时候用物化，把子查询结果建成一张带哈希索引的临时表，再拿外层大表去探测；子查询结果集大的时候用首次匹配，遍历外层小表，在子查询里找到一条就停，不用把子查询全跑完。所以"IN 适合小表、EXISTS 适合大表"是 5.6 之前的老观念，现在只要索引建好，写哪个都差不多。但有一个差异优化器抹不平，就是 NULL 的处理：NOT IN 的子查询结果里只要有 NULL，因为和 NULL 比较的结果是 UNKNOWN，整个排除条件就失效，查询直接返回空集；NOT EXISTS 只看有没有匹配行，完全不受 NULL 影响。

**追问参考答**

所以写排除逻辑优先用 NOT EXISTS，或者确保子查询那个字段是 NOT NULL、加个 where 条件过滤掉 NULL 也行。本质原因是 SQL 的三值逻辑：不等于 NULL 的结果既不是真也不是假，而是未知，而 NOT IN 要把每一行都和集合比一遍，只要碰到 NULL 就整条不成立。

### 33. 为什么 MVCC 无法完全避免幻读？如何做到绝对杜绝幻读？

> **知识点跳转：** [[为什么MVCC无法完全避免幻读现象]] · [[间隙锁防幻读的边缘场景]]

**参考答案**

根子在于 RR 下同时存在两套隔离机制。快照读走 MVCC，Read View 在事务内冻结，看到的永远是那个版本集合；当前读走 Next-key Lock，直接读最新已提交数据。同一个事务里如果先做快照读、再做当前读，中间别的事务插入并提交了，当前读就能看到这些新行，幻读就出现了。要绝对杜绝，办法是让事务内所有范围查询统一用当前读，也就是一开头就用 SELECT FOR UPDATE 把范围锁住，让间隙锁从临界区起点就铺满，挡住所有并发插入。代价是并发度会明显下降，所以实践里更常见的是接受这个极小的缝隙，用唯一约束或者乐观锁版本号在业务层兜底。

**追问参考答**

这道题和第 19 题是同一个知识点的两种问法，19 那道侧重间隙锁"当前读时才加"的时机局限，这道侧重两套机制并存导致的缝隙，答题时侧重点可以不一样。要补的关键一句是：间隙锁只阻止加锁之后的插入，无法撤销加锁之前已经提交的插入，这才是它防不住幻读的真正原因。

### 34. INSERT...SELECT 为什么会持有大范围间隙锁、成为死锁高发场景？

> **知识点跳转：** [[INSERT...SELECT 间隙锁与死锁详解]] · [[间隙锁防幻读的边缘场景]]

**参考答案**

危险点在于它的 SELECT 部分走的是当前读，而且加锁是按扫描路径加的，不是按结果集加的。InnoDB 会对扫描过程中经过的每一条索引记录都加 Next-key Lock，锁的范围等于扫描器走过的整个区间。如果 where 用的是非唯一索引做等值查询，还要往后多扫到第一条不满足的记录，锁范围会被放大；如果压根没有索引，就是全表扫描，每条记录都加 Next-key Lock，等价于加了一把表级排他锁。死锁出在间隙锁和插入意向锁的关系上：两个事务各持一段重叠区间的间隙锁，间隙锁之间是兼容的所以谁都不阻塞；然后各自往对方的间隙里插入，都要申请插入意向锁，而插入意向锁和间隙锁冲突，于是 A 等 B 释放、B 等 A 释放，形成循环等待，InnoDB 只能回滚代价小的一方。

**追问参考答**

间隙锁兼容却还能死锁，靠的就是插入意向锁这一层把兼容关系打破：持有间隙锁的人想插入，会和自己持有的间隙锁兼容，但和别人持有的同区间间隙锁冲突，双方各持一段、又都想进对方的段，环就闭合了。生产上的规避手段是给 INSERT...SELECT 的查询条件建好索引、把大事务拆小、按固定顺序批量写入。

### 35. innodb_autoinc_lock_mode 三种模式分别是什么？为什么模式 2 搭配 statement 格式的 binlog 会导致主从数据不一致？

> **知识点跳转：** [[如何设置 innodb_autoinc_lock_mode]] · [[MySQL锁机制]]

**参考答案**

三种模式控制的是自增锁的粒度。0 是传统模式，每次 INSERT 都要加表级 AUTO-INC 锁，语句结束才释放，并发最差。1 是连续模式，普通 INSERT 用轻量的互斥量，只有批量插入这种事先不知道要分配多少个自增值的语句才退回去用表锁，好处是保证同一语句里的自增值连续，MySQL 8.0 之前它是默认值。2 是交错模式，完全不用表锁，多个语句可以交错分配自增值，并发最好，MySQL 8.0 之后成了默认值。为什么模式 2 配 statement 格式的 binlog 会主从不一致，因为模式 2 下自增值是交错分配的、不连续也不可预测，而 statement 格式只记一条"插入语句加自增起点"，从库重放时按自己的情况算出来的自增值可能和主库不一样，数据就歪了。所以用模式 2 必须配 row 格式的 binlog。

**追问参考答**

MySQL 8.0 默认是模式 2，也就是交错模式。这个参数不支持运行时动态修改，必须改配置文件重启才生效，可以用 SHOW VARIABLES LIKE 'innodb_autoinc_lock_mode' 查看当前值。顺带一个常见追问：为什么模式 2 要配 row，因为 row 格式记的是每一行的实际值，自增值是多少都在 binlog 里写死了，从库照抄就行，不依赖它自己再算一遍。
