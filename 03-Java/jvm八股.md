## JVM的内存模型介绍一下？

根据 JDK 8（Java 1.8）规范，JVM运行时内存包括：虚拟机栈、本地方法栈、堆、元空间、程序计数器**五个部分**

> 还有直接内存，属于操作系统的本地内存，也是可以直接操作的

![img](https://cdn.xiaolincoding.com//picgo/1713516291293-ce6ee4e7-c5a6-4395-9ee7-4ec1c014b206.webp)



## 简单介绍一下程序计数器？

程序计数器存储着当前线程所执行Java方法的字节码指令地址，生命周期与线程一致

如果执行的是native方法，程序计数器为undefined

> 由于 Native 方法由本地代码实现、不对应字节码，因此当线程执行 Native 方法时，程序计数器的值为空

程序计数器也是唯一一块不会发生任何栈溢出和堆溢出的区域





## 简单介绍一下虚拟机栈？

每个线程都有自己独立的虚拟机栈，生命周期与线程一致

每个方法在被调用时都会创建一个栈帧压入当前线程的栈，栈帧用于存储局部变量表、操作数栈、动态链接、方法出口等信息。方法执行完毕后，对应的栈帧出栈销毁

会出现栈溢出和堆溢出



## 简单介绍一下本地方法机栈？

与虚拟机栈类似，主要为native方法服务

在hotspot虚拟机中与虚拟机栈合二为一

会出现栈溢出和堆溢出



## 简单介绍一下堆？

堆是JVM中最大的一块内存区域，被所有线程共享，在虚拟机启动时被创建，用于存放对象实例

从内存回收角度，堆被分为新生代和老年代，新生代又分为Eden区和两个Survivor区
**当堆中没有内存完成实例分配，并且堆也无法扩展时，就会抛出OOM异常**

### 堆分为哪几部分？

Java 堆（Heap）是 JVM 内存管理中最重要的区域，主要用于存放对象实例和数组。从 GC 管理的角度分为以下两部分：

- **新生代（Young Generation）**：分为 Eden Space 和 Survivor Space。Eden 区是新生代中最大的区域（默认 Eden:S0:S1 = 8:1:1），大多数新创建的对象首先存放在这里。当 Eden 区满时，会触发一次 Minor GC。Survivor Spaces 分为两个相等大小的区域（S0 和 S1），在每次 Minor GC 后，存活下来的对象会被移动到其中一个 Survivor 空间，两个区域轮流充当对象的中转站。
- **老年代（Old Generation）**：经过一次或多次 Minor GC 仍存活的对象会被移动到老年代。老年代中的对象生命周期较长，Major / Full GC 发生的频率相对较低，但执行时间通常比 Minor GC 长。

> **注意：** 
> 元空间（Metaspace）从 Java 8 起替代了永久代，但它使用**本地内存**，不属于 Java 堆。
> 大对象（Humongous Objects）在 G1 中虽然占用堆内的 Humongous Region，但在逻辑上归属于老年代，并非独立分区。

### 如果有个大对象一般是在哪个区域？

大对象通常会直接分配到老年代。

新生代主要用于存放生命周期较短的对象，内存空间相对较小。如果将大对象分配到新生代，会很快导致新生代空间不足，频繁触发 Minor GC。每次 Minor GC 都需要进行对象的复制和移动操作，带来额外的性能开销。

大对象通常需要连续的内存空间，如果在新生代中频繁分配和回收大对象，容易产生内存碎片。老年代的空间相对较大，更适合存储大对象，有助于减少内存碎片的产生。



## 简单介绍一下方法区（元空间）？

在 JDK 8（Java 1.8）及以后的版本，方法区被元空间所取代，**使用本地内存**

用于存储已被虚拟机加载的类的元数据信息、常量、静态变量等数据

虽然方法区被描述为堆的逻辑部分，但有**非堆**的别名

方法区可以选择不进行垃圾回收

内存不足时会抛出OOM



## 简单介绍一下运行时常量池？

是方法区的一部分，用于存储编译器生成的各种字面量和符号引用，运行时也可加入新的常量，具有动态性

内存不足时会抛出OOM



## 简单介绍一下直接内存？

不是JVM运行时数据区的一部分，通过NIO类引入，是一种堆外内存，可以显著提高IO性能

直接内存的使用受本机总内存的限制

会抛出OOM





## JVM 堆与栈的区别

### 核心对比

| 维度       | 堆（Heap）            | 栈（Stack）                                                                                                                                                                                       |
| -------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **存储内容** | 对象实例、数组            | **栈帧（Stack Frame）**。<br><br>  <br><br>每个栈帧内部包含：<br><br>  <br><br>1. **局部变量表**（基本数据类型、对象引用）<br><br>  <br><br>2. **操作数栈**（入栈出栈的临时计算）<br><br>  <br><br>3. **动态连接**<br><br>  <br><br>4. **方法返回地址** |
| **线程共享** | ✅ 所有线程共享           | ❌ 每个线程独立一份                                                                                                                                                                                     |
| **生命周期** | 由 GC 管理，对象存活期不定    | 与线程一致（栈帧随方法调用创建，返回销毁）                                                                                                                                                                          |
| **大小**   | 通常较大，可动态扩展         | 较小，固定或有上限                                                                                                                                                                                      |
| **分配速度** | 较慢（需要 GC 参与）       | 极快（移动栈顶指针）                                                                                                                                                                                     |
| **异常**   | `OutOfMemoryError` | `StackOverflowError`                                                                                                                                                                           |

------

### 堆（Heap）

存放所有 `new` 出来的对象，是 GC 的主战场：

```java
// person 对象本身存在堆上
Person person = new Person("Nozomi");
```

堆的内部结构（以 G1 之前的经典分代为例）：

```
┌─────────────────────────────────────────┐
│                  堆                      │
│  ┌──────────────────┐  ┌─────────────┐  │
│  │    新生代         │  │   老年代     │  │
│  │  Eden | S0 | S1  │  │             │  │
│  └──────────────────┘  └─────────────┘  │
└─────────────────────────────────────────┘
```

- **新生代**：新对象先分配在 Eden 区，Minor GC 后存活的晋升到 Survivor
- **老年代**：长期存活的对象，触发 Major GC / Full GC

------

### 栈（JVM Stack）

每个线程私有，由**栈帧（Stack Frame）**组成，每次方法调用压一帧：

```
┌──────────────────────────┐
│   栈帧：methodC()         │  ← 栈顶（当前执行）
├──────────────────────────┤
│   栈帧：methodB()         │
├──────────────────────────┤
│   栈帧：methodA()         │
├──────────────────────────┤
│   栈帧：main()            │  ← 栈底
└──────────────────────────┘
```

每个栈帧包含：

- **局部变量表**：基本类型值 + 对象引用（注意：引用在栈，对象在堆）
- **操作数栈**：执行字节码指令的临时工作区
- **动态链接**：指向运行时常量池的方法引用
- **返回地址**：方法执行完返回到哪里

------

### 一个例子看清两者关系

```java
public void process() {
    int count = 10;              // count 在栈上
    String name = "Nozomi";      // name 引用在栈，"Nozomi" 对象在堆
    Person p = new Person(name); // p 引用在栈，Person 对象在堆
}
栈                        堆
┌───────────────┐         ┌──────────────────┐
│ count = 10    │         │ String "Nozomi"   │
│ name ─────────┼────────▶│                  │
│ p ────────────┼──┐      └──────────────────┘
└───────────────┘  │      ┌──────────────────┐
                   └─────▶│ Person 对象       │
                          └──────────────────┘
```

------

### 常见面试延伸点

- **逃逸分析**：JIT 编译器分析对象是否"逃逸"出方法，若未逃逸可能直接在栈上分配（Stack Allocation），绕过堆，减少 GC 压力
- **-Xmx**（e**X**tended **M**emory **Ma**ximum）：最大堆内存
- **-Xms**（e**X**tended **M**emory **S**tart）：初始堆内存
- **-Xss**（e**X**tended **S**tack **S**ize）：每个线程栈大小
- 除了 JVM Stack，还有**本地方法栈（Native Method Stack）**，服务于 `native` 方法调用





## 栈中存的到底是指针还是对象？

在VM内存模型中，栈（Stack）主要用于管理线程的局部变量和方法调用的上下文，而堆（Heap）则是用于存储所有类的实例和数组。
当我们在栈中讨论"存储"时，实际上指的是存储基本类型的数据（如int，double等）和对象的引用，而不是对象本身。
这里的关键点是，栈中存储的不是对象，而是对象的引用。也就是说，当你在方法中声明一个对象，比如Myobjectobj= newMyobject（）；，这里的obj实际上是一个存储在栈上的引用，指向堆中实际的对象实例。这个引用是一个固定大小的数据（例如在64位系统上是8字节），它指向堆中分配给对象的内存区域。





> [!faq]- Eden:Survivor是8:2，假如Eden满了，然后MinorGC，Survivor也装不下啊?
>
> 你直击了 Java 堆内存管理中**最核心、最经典**的一个矛盾点！
>
> 你的推导完全符合直觉：Eden 是 80%，两个 Survivor 各占 10%。如果 Eden（80%）全满了，而且里面**绝大多数对象都活着**，那哪怕把两个 Survivor 捏在一起（20%）也绝对装不下。
>
> JVM 团队当然也考虑到了这一点。为了解决这个“装不下”的问题，JVM 设计了两个非常核心的机制：**弱代假设（Weak Generational Hypothesis）** 和 **分配担保机制（Handle Promotion Failure）**。
>
> ### 1. 现实残酷但幸运：绝大多数对象“朝生夕死”
>
> JVM 的核心垃圾回收算法是建立在**弱代假设**之上的：**绝大多数对象存活的时间都极短（高达 98% 的对象在第一次 GC 时就会被回收）。**
>
> - **理想情况：** 别看 Eden 有 80%，当触发 Minor GC 时，往往只有不到 1%~2% 的对象还活着。这时候把它们复制到占比 10% 的 Survivor 区（比如 S1），空间是**绰绰有余**的。
> - **设计初衷：** 8:1:1 的比例不是一拍脑门定下来的，而是通过大量实际生产环境的对象生命周期数据测试出的黄金比例，目的是最大化 Eden 的吞吐量，同时不浪费太多内存给 Survivor。
>
> ### 2. 动真格的了：万一真的装不下怎么办？
>
> 你的担心在实际业务中一定会发生（比如突然来了个大并发请求，或者加载了一个大文件，导致 Eden 满的时候，大批对象都死不掉）。
>
> 这时候，JVM 会启动**分配担保机制（Garbage Collection Guarantee）**。
>
> 当 Minor GC 后，Survivor 区真的装不下那些好不容易活下来的对象时，它们**不会被强制挤在 Survivor 区**，而是会发生以下连锁反应：
>
> #### 方案 A：对象直接“跳级”到老年代（空间分配担保）
>
> 这是最常见的处理方式。Survivor 放不下的那部分对象，会直接被送进**老年代（Old Generation）**。老年代就像是一个“后备老大哥”，替新生代兜底。
>
> > **用一个通俗的比喻：**
> >
> > 新生代是**大学宿舍（Eden）**，毕业了（GC）大家都得搬出去。**S1 是租的单身公寓**。
> >
> > - **正常情况：** 毕业时大部分人都回老家了，只有少数几个人需要租房，S1 完全装得下。
> > - **特殊情况：** 今年大家都不想回老家，全想挤进 S1。S1 瞬间爆满，剩下的人没办法，只能直接去投奔已经在社会上立足的**父母家（老年代）**住。
>
> #### 方案 B：触发 Target Survivor Ratio（动态年龄判断）
>
> JVM 还有一个参数叫 `-XX:TargetSurvivorRatio`（默认 50%）。
>
> 如果在某次 GC 后，**同龄的对象**（或者从小到大累加的对象）体积超过了 Survivor 空间的 **50%**，那么为了防止 Survivor 彻底被挤爆，JVM 会把年龄大于或等于该年龄的对象**提前晋升到老年代**，主动给 Survivor 腾地方。
>
> ### 3. 如果连老年代也装不下呢？
>
> 如果新生代发生了 Minor GC，想把装不下的对象送往老年代，结果发现**老年代也满了，或者放不下这么多对象**，那就会触发终极手段：
>
> 1. **触发 Full GC**：JVM 会暂停一切（Stop The World），对整个堆内存（新生代 + 老年代）进行一次彻彻底底的大扫除，尝试释放老年代的空间。
> 2. **抛出 OOM（Out Of Memory Error）**：如果 Full GC 完之后，老年代还是没有足够的空间来接收这些从新生代挤过来的对象，JVM 就会彻底罢工，抛出著名的 `java.lang.OutOfMemoryError: Java heap space`。
>
> ### 总结
>
> - **常态下：** 因为 90% 以上的对象会死掉，10% 的 Survivor 足够用。
> - **极端下（装不下时）：** 触发**分配担保机制**，存活对象绕过 Survivor，直接进入老年代。
> - **老年代也装不下：** 触发 Full GC $\rightarrow$ 失败则 OOM。
>
> 你有遇到过因为这种大对象直接晋升老年代，导致老年代频繁触发 Full GC 的线上问题吗？











## 程序计数器的作用，为什么是私有的？

程序计数器的作用是记录当前线程下一条要执行的字节码指令地址，这样在线程切换后，线程还能从上次暂停的位置继续执行。
因为 Java 支持多线程，每个线程执行的代码位置都可能不同，所以程序计数器必须是线程私有的，避免线程之间互相影响。





## 方法区中的方法的执行过程？

当程序中对象或类直接调用某个方法时
首先，JVM会根据方法的符号引用找到实际的方法地址
接着，JVM会在当前线程的Java虚拟机栈中为该方法分配一个新的栈帧，用于存储局部变量表、操作数栈、动态链接、方法出口等信息

然后，执行方法中的字节码指令，方法执行结束后，可能会返回一个结果给调用者，并清理当前栈帧，恢复调用者的执行环境





## 方法区中有哪些东西？

**方法区用于存储已被虚拟机加载的类型信息、常量、静态变量、运行时常量池、即时编译器编译后的代码缓存等**



## 字符串常量池 vs 运行时常量池

### 关系图

```
方法区（JVM 的逻辑概念）
 ├── JDK 7 之前：PermGen（永久代）
 │    └── 物理上：JVM 内部划出的独立内存（受 MaxPermSize 限制，易 OOM）
 │    └── 包含：运行时常量池、字符串常量池（此时还在里面）
 │
 └── JDK 8 之后：Metaspace（元空间）
      └── 物理上：直接使用操作系统的本地内存（Native Memory，受物理内存限制）
      └── 包含：运行时常量池（每个类一份，包含字面量、符号引用）

字符串常量池（全局共享）
 └── 💡 注意演变：JDK 7 时就已被提前移出 PermGen，放到了【JVM 堆】中；JDK 8 之后依然留在【JVM 堆】中。
```
两者是**包含关系**：字符串常量池是一个独立的全局结构，运行时常量池中的字符串字面量引用会指向它。


### 对比


#### 版本变迁对比

| 区域     | JDK 6 | JDK 7 | JDK 8+     |
| ------ | ----- | ----- | ---------- |
| 运行时常量池 | 永久代   | 永久代   | Metaspace  |
| 字符串常量池 | 永久代   | **堆**  | **堆**      |

|          | 运行时常量池（Runtime Constant Pool）    | 字符串常量池（String Table / String Pool） |
| -------- | -------------------------------- | ---------------------------------- |
| **作用域**  | 每个类一份                            | JVM 全局只有一份                         |
| **存储内容** | 类版本、字段/方法/接口信息、符号引用、字面量（含字符串字面量） | 纯字符串字面量 + `intern()` 存入的对象         |
| **所属关系** | 方法区的一部分（逻辑概念）                    | 运行时常量池中分离出来的区域                     |
| **位置变迁** | JDK6 在 PermGen → JDK8+ 在 Metaspace（本地内存） | JDK7 从 PermGen 迁到堆（独立管理）           |
| **主要用途** | 类加载时解析符号引用                       | 字符串复用，减少内存开销                       |

### 面试话术

> 运行时常量池是按类隔离的，每个类加载后都会生成一份；而字符串常量池是全局共享的，所有类共用一张 String Table。JDK7 之前字符串常量池在 PermGen 里，容易 OOM；JDK7 之后挪到了堆，**JDK8 移除了 PermGen 改为 Metaspace，但字符串常量池仍然留在堆中**，不受元空间大小限制。



---

### 位置变迁补充

- **运行时常量池**：JDK6 在 PermGen → JDK8+ 在 Metaspace（**本地内存**，不在堆）
- **字符串常量池**：JDK6 在 PermGen → JDK7 移到堆（`-XX:StringTableSize` 可调，默认 60013）→ JDK8+ 不变，仍在堆
- **类信息（元数据）**：JDK8+ 存在 Metaspace（本地内存），不再受 JVM 堆大小限制





## String s1="abc"和String s2=new String("abc")的区别

![images\image-20260222192252534](C:\Users\q1948\Desktop\八股\images\image-20260222192252534.png)

### ✅ 面试回答版本

**String s1 = "abc" 和 String s2 = new String("abc") 的主要区别在于对象创建方式和内存位置不同。**

------

### ① 创建方式不同

```
String s1 = "abc";
```

这种方式是**直接使用字符串字面量**创建对象。
 JVM 会先去**字符串常量池（String Constant Pool）**中查找是否已经存在 `"abc"`：

- 如果存在，就直接返回该对象的引用；
- 如果不存在，就在常量池中创建 `"abc"`，然后返回引用。

因此，s1 指向的是**常量池中的对象**。

------

```
String s2 = new String("abc");
```

这种方式会发生两步：

1. 先在字符串常量池中查找 `"abc"`，如果没有则创建；
2. 然后在堆中再创建一个新的 String 对象。

所以，s2 指向的是**堆中的新对象**，而不是常量池中的对象。

------

### ② 对象数量不同

```
String s1 = "abc";
```

👉 只创建 1 个对象（在字符串常量池）。

```
String s2 = new String("abc");
```

👉 通常会创建 2 个对象：

- 常量池中的 `"abc"`
- 堆中的 String 对象

------

### ③ 内存位置不同

| 变量 | 存储位置     |
| ---- | ------------ |
| s1   | 字符串常量池 |
| s2   | 堆           |

------

### ④ 比较结果不同

```
String s1 = "abc";
String s2 = new String("abc");

System.out.println(s1 == s2); // false
System.out.println(s1.equals(s2)); // true
```

原因：

- `==` 比较的是地址；
- `equals()` 比较的是内容。

------

### ⑤ 性能和使用场景

## **弱引用了解吗?举例说明在哪里可以用?**

Java中的弱引用是一种引用类型，它不会阻止一个对象被垃圾回收

 在Java中，弱引用是通过Java.lang.ref.WeakReference类实现的。弱引用的一个主要用途是创建非强制性的对象引用，这些引用可以在内存压力大时被垃圾回收器清理，从而避免内存泄露。 

弱引用的使用场景： 

- 缓存系统：弱引用常用于实现缓存，使用弱引用来维护缓存，可以让JVM在需要更多内存时自动清理这些缓存对象。

- 对象池：在对象池中，弱引用可以用来管理那些暂时不使用的对象。当对象不再被强引用时，它们可以被垃圾回收，释放内存。 

- 避免内存泄露：当一个对象不应该被长期引用时，使用弱引用可以防止该对象被意外地保留，从而避免潜在的内存泄露







## **内存泄漏和内存溢出的理解？ 

**内存泄露：内存泄漏是指程序在运行过程中不再使用的对象仍然被引用，而无法被垃圾收集器回收，从而导致可用内存逐渐减少。**

内存泄露常见原因： 

- 静态集合：使用静态数据结构（如HashMap或ArrayList）存储对象，且未清理。详见 [[静态集合内存泄漏与类卸载详解]]

- 事件监听：未取消对事件源的监听，导致对象持续被引用。 

- 线程：未停止的线程可能持有对象引用，无法被回收。 

**内存溢出：内存溢出是指Java虚拟机（JVM）在申请内存时，无法找到足够的内存，最终引发OutOfMemoryError。这通常发生在堆内存不足以存放新创建的对象时。 

内存溢出常见原因： 

- 大量对象创建：程序中不断创建大量对象，超出JVM堆的限制。 
- 持久引用：大型数据结构（如缓存、集合等）长时间持有对象引用，导致内存累积。 
- 递归调用：深度递归导致栈溢出。详见 [[栈溢出导致OOM的深层机制]]

### ⭐ 元空间溢出（Metaspace OOM）

当 JVM 抛出 **`java.lang.OutOfMemoryError: Metaspace`** 时，说明元空间发生了内存溢出。

元空间主要用于存储类的元数据（如类结构、方法信息、常量池等）。
 如果系统中加载的类过多，或者类无法被回收，就可能导致元空间不断膨胀，最终发生溢出。

常见原因包括：

1. **系统加载的类数量过多**
    例如大型系统、微服务或使用了大量第三方框架，导致类元数据占用空间较大。
2. **动态生成类过多**
    比如使用 CGLIB、JDK 动态代理、ASM、ByteBuddy 等技术频繁生成代理类，如果这些类没有被卸载，就会持续占用元空间。
3. **类加载器泄漏（ClassLoader Leak）**
    某些应用（如 Web 容器热部署）中，如果旧的类加载器没有被正确回收，会导致对应加载的类元数据也无法释放，从而引发元空间 OOM。







## 有具体的内存泄漏和内存溢出的例子么请举例及解决方案?

### 1. 静态属性导致内存泄露

大量使用 static 静态变量会导致内存泄露。静态属性的生命周期通常伴随着应用整个生命周期（除非 ClassLoader 符合垃圾回收的条件）：

```java
public class StaticTest {
    public static List<Double> list = new ArrayList<>();
    public void populateList() {
        for (int i = 0; i < 10000000; i++) {
            list.add(Math.random());
        }
    }
    public static void main(String[] args) {
        new StaticTest().populateList();
        // list 是静态的，方法结束后仍不会被回收
    }
}
```

**解决**：减少静态变量；使用单例时尽量采用懒加载。

### 2. 未关闭的资源

创建数据库连接、输入流等资源后忘记关闭，会阻塞内存导致 GC 无法清理。特别是程序发生异常时没有在 finally 中进行资源关闭。

**解决**：始终在 finally 中关闭资源；Java 7+ 可使用 try-with-resources。

### 3. 使用 ThreadLocal 导致内存泄漏

ThreadLocalMap 使用 ThreadLocal 的弱引用作为 key，当 ThreadLocal 被回收后，key 变为 null，但 value 仍被 `Thread Ref → Thread → ThreadLocalMap → Entry → value` 这条强引用链持有，无法回收。

**解决**：使用 ThreadLocal 的 `remove()` 方法；最好在 finally 块中调用：

```java
try {
    threadLocal.set(value);
    // ... 业务处理
} finally {
    threadLocal.remove();
}
```

### 4. 内存溢出 — 堆溢出（解决思路）

堆溢出（`java.lang.OutOfMemoryError: Java heap space`）的排查与解决：

1. **捕获快照**：通过 JVM 参数 
	`-XX:+HeapDumpOnOutOfMemoryError 
	`-XX:HeapDumpPath=./heapdump.hprof`自动生成堆快照
2. **分析快照**：使用 MAT 或 JProfiler 分析哪些对象占用大量内存
3. **根据原因处理**：
   - 内存泄漏 → 梳理引用链，清理无用引用（如静态集合、未关闭资源）
   - 内存不足 → 调整 `-Xms -Xmx` 扩大堆内存；从代码层面优化（分批处理、设置缓存过期策略）

### 5. 栈溢出的情况

栈溢出（`java.lang.StackOverflowError`）的常见场景：

- **无限递归调用**：没有正确终止条件的递归，栈帧不断累积直至溢出
- **单方法栈帧过大**：方法定义了大量局部变量或大数组

**解决**：
1. 排查递归逻辑，添加终止条件或改为迭代
2. 通过 `-Xss` 参数增大栈内存（注意：栈越大，可创建的线程数越少）
3. 减少方法内局部变量数量


## 类加载机制

### 类加载器有哪些？

- **启动类加载器（Bootstrap Class Loader）**：最顶层，负责加载 Java 核心类库。Java 8 加载 `rt.jar`，Java 9+ 加载 `lib/modules` 模块化镜像。由 C++ 实现，Java 层面没有对应 ClassLoader 对象。
- **扩展类加载器（Extension Class Loader）**（Java 8）/ **平台类加载器（Platform Class Loader）**（Java 9+）：负责加载扩展目录或平台模块中的类。
- **应用程序类加载器（Application Class Loader）**：负责加载 ClassPath 上的类，开发者默认使用的加载器。
- **自定义类加载器（Custom Class Loader）**：开发者可定制类的加载方式（网络、数据库、加密文件等）。

### 双亲委派模型是什么？有什么作用？

**定义**：当一个类加载器收到类加载请求时，先委派给父加载器去尝试加载，只有父加载器加载不了时，自己才会去尝试加载。

**作用**：
1. **保证类的唯一性**：避免同一个类被不同加载器重复加载
2. **保证安全性**：防止恶意代码自定义 `java.lang.String` 等核心类替换 JDK 核心类
3. **支持隔离和层次划分**：不同层级的类加载器服务于不同需求，职责清晰
4. **简化加载流程**：减少每个加载器需要处理的类数量

### 类加载过程（七个阶段）

类从被加载到卸载，生命周期包括以下阶段：

|概念|含义|
|---|---|
|**字节码文件（.class 文件）**|磁盘上的静态二进制文件，是编译产物|
|**class 文件字节流**|加载阶段读取到的二进制数据流，来源不限于文件|

1. **加载（Loading）**：通过类的全限定名获取二进制字节流，将静态存储结构转化为方法区运行时数据结构，生成 `java.lang.Class` 对象
2. **验证（Verification）**：确保 class 文件字节流符合 JVM 规范，不会危害虚拟机安全
3. **准备（Preparation）**：为静态字段分配内存并设置默认初始值（`static final` 且在**编译期可确定的常量** → 直接赋实际值，跳过零值；若值依赖方法调用等运行时计算 → 仍赋零值，留到初始化阶段 `<clinit>()` 中赋值）
4. **解析（Resolution）**：将常量池中的符号引用替换为直接引用
5. **初始化（Initialization）**：JVM 执行编译器自动生成的 `<clinit>()` 方法。该方法由编译器将类中所有**静态变量的赋值语句**和**静态代码块**按照它们在源码中出现的**顺序**依次收集而成，是类生命周期中真正对静态变量赋予程序员指定值的阶段。
6. **使用（Using）**：使用类或创建对象
7. **卸载（Unloading）**：类被卸载需同时满足：所有实例被回收、ClassLoader 被回收、Class 对象无引用

### 创建对象的过程

1. **类加载检查**：检查 new 指令的参数能否在常量池中定位到类的符号引用，并检查该类是否已被加载、解析和初始化
2. **分配内存**：在类加载检查通过后，为新生对象分配内存（大小在类加载完成后即可确定）
3. **初始化零值**：将分配到的内存空间初始化为零值（不包括对象头）
4. **设置对象头**：设置对象是哪个类的实例、指向类元数据的指针、哈希码、GC 分代年龄等信息
5. **执行 init 方法**：执行构造函数，按程序员的意图初始化对象


首先会在常量池中寻找类的符号引用，
然后检查该类是否被加载、链接、初始化
检查通过后会为该对象分配内存，并初始化零值，
接着给对象设置对象头，对象头内容包括：对象所属类名、指向类元数据的指针、哈希码、GC分代年龄，
最后执行构造函数







## 什么是垃圾回收？

垃圾回收是一种自动管理内存的机制，它负责自动释放程序不再引用的对象所占内存




## 什么会触发垃圾回收？

- **内存不足（Allocation Failure）** — 堆内存分配失败时触发，最常见的原因。Eden 区满触发 Minor GC，老年代满触发 Full GC
- **手动请求（System.gc() / Runtime.gc()）** — 只是建议，不保证立即执行；可通过 `-XX:+DisableExplicitGC` 禁用
- **JVM 参数设置** — 如 `-Xms` `-Xmx` 配置的堆大小、`-XX:MetaspaceSize` 元空间阈值等会自动调整 GC 触发时机
- **不同区域的触发条件** — 各代有自己的阈值：Eden 满（Minor GC）、老年代满（Full GC）、元空间达到 `MaxMetaspaceSize`（Full GC）、大对象直接进入老年代
- **晋升失败（Promotion Failure）** — Minor GC 后存活对象无法放入 Survivor 和老年代，会升级为 Full GC

## 什么是垃圾回收算法，解决什么问题？

垃圾回收算法是解决**如何识别不再使用的对象、如何高效回收其占用内存、同时尽量减少对应用程序停顿影响**的一套执行方案。

### 标记清除算法的缺点

标记-清除算法有两个主要缺点：
1. **效率问题**：标记和清除过程的效率都不高
2. **空间问题**：清除之后会产生大量不连续的内存碎片，导致后续分配大对象时可能因没有足够连续空间而提前触发另一次 GC

### Minor GC、Major GC、Full GC 的区别

**Minor GC (Young GC)**
- **作用范围**：只针对年轻代（Eden + Survivor）
- **触发条件**：Eden 区空间不足时触发
- **特点**：发生频繁，回收效率高，暂停时间较短

**Major GC**
- **作用范围**：仅回收老年代（如 CMS 的并发老年代 GC）
- **触发条件**：老年代空间不足，或年轻代对象晋升速度过快

**Full GC**
- **作用范围**：对整个 Java 堆（年轻代 + 老年代）回收，并可能卸载元空间中的无用类
- **触发条件**：
  - **`System.gc()` / `Runtime.getRuntime().gc()` 的显式调用**（仅是向 JVM 发出的**建议**，不保证执行；可被 `-XX:+DisableExplicitGC` 禁用）
  - **空间分配担保失败（Handle Promotion Failure）**：Minor GC 前 JVM 先检查老年代**最大可用连续空间**是否 ≥ 新生代所有对象的**总大小**。若不满足，再检查 `-XX:-HandlePromotionFailure`（JDK 6u24 后默认开启的担保策略）是否允许冒险，以及老年代最大连续空间是否 ≥ **历次晋升到老年代的平均大小**。任一条件不满足 → 触发 Full GC  
  - **元空间（Metaspace）不足**：元空间在本地内存中，Full GC 无法直接回收它。但 Full GC 会遍历堆中对象引用，找出**不再被引用的 ClassLoader** → 卸载其加载的类 → 释放对应类的元数据在 Metaspace 中占用的内存。Full GC 后仍不够 → 才抛 `OutOfMemoryError: Metaspace`
  - **CMS 的 Concurrent Mode Failure**：并发清理速度跟不上分配速度，回退 Full GC
- **特点**：最昂贵的 GC 操作，STW 时间长，应尽量减少触发

---


>遍历对象引用跟classloader有啥关系

核心链条是：

```
ClassLoader 对象 → 活在堆里
    ↓ 持有引用
Class 对象（java.lang.Class）→ 也活在堆里
    ↓ 对应
Metaspace 里的类元数据（方法字节码、常量池等）
```

所以 GC 遍历堆对象引用，本质上是在判断 **ClassLoader 这个堆对象本身是否还可达**。

如果一个 ClassLoader 对象不再被任何 GC Root 引用（比如热部署时旧的 WebAppClassLoader 已经没人持有），它就是垃圾。

然后 JVM 顺着这条链反向推：

- ClassLoader 不可达 → 它加载的所有 Class 对象也不可达 → Metaspace 里对应的类元数据没有存在意义 → 可以卸载释放

所以"遍历对象引用找 ClassLoader"，找的不是 Metaspace 里的东西，找的是**堆里的 ClassLoader 对象是否还活着**，Metaspace 的释放只是连带结果。

一句话总结：**Metaspace 没有独立的 GC，它蹭的是堆 GC 顺带判断 ClassLoader 可达性的结果。**

## 垃圾回收算法哪些阶段会STW？

## 垃圾回收中的 STW（Stop-The-World）阶段

不同 GC 算法的 STW 情况不同，以下以常见实现为例：

------

### 标记-清除 / 标记-整理（传统全停顿）

整个 GC 过程全程 STW，包括标记和清除两个阶段。

------

### CMS（Concurrent Mark Sweep）

| 阶段                         | 是否 STW      |
| ---------------------------- | ------------- |
| 初始标记（Initial Mark）     | ✅ STW（短暂） |
| 并发标记（Concurrent Mark）  | ❌ 并发        |
| 重新标记（Remark）           | ✅ STW（较短） |
| 并发清除（Concurrent Sweep） | ❌ 并发        |

------

### G1（Garbage First）

| 阶段                            | 是否 STW |
| ------------------------------- | -------- |
| 初始标记（Initial Mark）        | ✅ STW    |
| 并发标记（Concurrent Mark）     | ❌ 并发   |
| 最终标记（Final Mark / Remark） | ✅ STW    |
| 筛选回收（Evacuation）          | ✅ STW    |

------

### ZGC / Shenandoah

设计目标是极低 STW，大部分阶段并发执行：

| 阶段            | 是否 STW              |
| --------------- | --------------------- |
| 初始标记根集合  | ✅ STW（极短，毫秒级） |
| 并发标记        | ❌ 并发                |
| 再标记 / 根修复 | ✅ STW（极短）         |
| 并发转移/压缩   | ❌ 并发                |

------

### 总结规律

几乎所有 GC 算法都无法避免以下两类 STW：

1. **初始标记根对象**：==需要一致的GC Roots快照==，必须 STW
2. **重新标记（Remark）**：==修正并发标记期间的漏标==，必须 STW

优化方向就是让这两次 STW 尽可能短，其余阶段与应用线程并发执行。







## 什么情况使用CMS、G1？



CMS：

如果需要一个低延迟的老年代垃圾回收器，可以使用CMS



G1：

G1垃圾回收器适用于 对内存碎片比较敏感、需要比较平衡的性能且大内存堆的场景

> *G1在提供较低停顿时间的同时，也保持了相对较高的吞吐量。*

> [!info]- 为什么 G1 适合大内存堆？
>
> 1. **Region 分块机制**：堆划分为 1~32MB 的等大 Region，每次只收集**部分 Region**，不扫描整个堆；堆越大、Region 越多，选择空间越大，越容易满足停顿时间目标
> 2. **可预测停顿**：`-XX:MaxGCPauseMillis`（默认 200ms）控制每次 GC 时间，通过历史数据计算每个 Region 的回收成本，只选取收益最高的 Region 集合
> 3. **无碎片问题**：G1 用**复制-压缩**（Copy & Compact），避免大堆下 CMS 式的严重碎片化
> 4. **增量式整理**：Mixed GC 将年轻代和老年代中收益高的 Region 一起处理，**分摊全堆整理压力**
>
> > 作为对比：CMS 标记-清除不压缩，大堆极易碎片化 → 晋升失败 → Full GC；Parallel Scavenge 每次 Full GC 全量压缩，大堆 STW 过长





## G1垃圾回收器的特色？



**特点：**

- G1最大的特点是引入分区的思路，弱化了分代的概念。
- 合理利用垃圾收集各个周期的资源，解决了其他收集器、甚至 CMS 的众多缺陷

### GC只会对堆进行GC吗？

JVM 的垃圾回收器不仅仅会对堆进行垃圾回收，它还会对方法区进行垃圾回收。





## 为什么说G1引入分区的思路，弱化了分代的概念

> [!info]- 这句话切中了 G1 垃圾回收器的**灵魂设计**。
>
> 在它之前（比如 CMS、Parallel 垃圾回收器），JVM 的内存就像是**严格划分的“大省”**，而 G1 出来之后，直接打破了省界，把内存变成了“无数个对等的小社区”。
>
> 为了让你秒懂，我们用“圈地”和“乐高积木”来对比：
>
> ## 传统回收器： rigid 的“圈地运动”（强化分代）
>
> 在传统概念里，内存是一整块连续的大硬盘，直接切成三块大蛋糕：
>
> - 这一大块死活不能动，叫 **新生代**。
> - 那一大块死活不能动，叫 **老年代**。
> - 还有一小块叫 **永久代/元空间**
>
> ### 带来的致命问题：
>
> 因为边界是死死固定的，这就导致：
>
> 1. **尾大不掉**：老年代越攒越大。每次老年代满了要清理时（Full GC），垃圾回收器必须把这**一整块几十G的大蛋糕**从头到尾扫描一遍。内存越大，停顿（STW）时间越长。
> 2. **空间死板**：如果新生代满了，哪怕隔壁老年代空着大片地方，新生代也用不了，只能硬着头皮触发 GC。
>
> ## G1 回收器：灵活的“微型社区”（弱化分代）
>
> G1 直接把“大蛋糕”的切法给废了。它把整个堆内存平均分成了几千个大小相等的独立正方形小格子，每个小格子被称为一个 **Region（分区）**。
>
> ### 为什么说它“弱化了分代的概念”？
>
> 因为在 G1 里，**再也没有任何一个 Region 是生来就属于“年轻代”或“老年代”的。它们的身份是动态变化的！**
>
> - 此时此刻，格子 A 里面塞满了刚 new 出来的对象，那它现在就是 **Eden（年轻代）** 属性。
> - 几秒钟后，垃圾回收把格子 A 清空了，格子 A 就变成了 **Available（空闲状态）**。
> - 再过一会儿，程序里产生了一个存活很久的大对象，格子 A 被拿去装这个老对象，它就摇身一变，变成了 **Old（老年代）** 属性。
>
> 这就叫**弱化分代**：分代不再是物理上的“这一大块地归谁”，而仅仅是一个**逻辑上的标签**。格子们不再有固定的编制，哪里需要去哪里。
>
> ## 这样做，最大的好处是什么？
>
> 这就回到了它的名字：**G1（Garbage-First，垃圾优先）**。
>
> 正因为引入了分区，G1 回收内存时，再也不用像以前一样傻乎乎地去扫完整个几十 G 的老年代了。它可以玩“精准打击”。
>
> 想象一下：JVM 现在的内存是由 2000 个格子组成的。
>
> - 到了该回收的时候，G1 去清点了一下。
> - 发现格子 ① 号里面 95% 都是垃圾，回收它只要 1 毫秒。
> - 格子 ② 号里面 80% 都是活对象（垃圾只有 20%），回收它要花 50 毫秒。
>
> G1 就会根据用户设定的**最大停顿时间**（比如：我要求每次 GC 最多卡顿 10 毫秒），掐指一算：“时间有限，我这次**只收性价比最高、垃圾最多的格子 ① 号**，格子 ② 号先放着。”
>
> ### 总结
>
> - **以前的回收器**：要扫就得扫完整个老年代。内存越大，扫得越慢，程序员不敢给 JVM 分配太大的内存。
> - **G1 回收器**：通过**分区**，把大任务化整为零；通过**弱化分代**，让内存动态调配。它不管你是年轻代还是老年代，**谁的垃圾多、回收得快，我就先去薅谁的羊毛**。
>
> 这就是“引入分区思路，弱化分代概念”的真正含义——**化整为零，按需动态治理**。
