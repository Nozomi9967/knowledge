### **Feed 流的核心矛盾是「读时聚合慢、写时扩散贵」，所以工程上几乎都是推拉结合：普通用户（粉丝少）用推模式，发一条就写进所有粉丝的收件箱，读的时候直接取；大 V（粉丝千万）用拉模式，发的时候只写自己的发件箱，读的时候由粉丝端去合并。判断标准是粉丝数阈值，业界一般 10 万到 100 万之间。**

下面按面试口述节奏展开，先对比三种模式，再讲大 V 怎么特殊处理。

---

**第一部分：三种模式的取舍**

**推模式（写扩散 / Fan-out on Write）**

发朋友圈时，把这条动态的 ID 写进每个粉丝的"收件箱"列表。读的时候直接从自己的收件箱取前 N 条，再批量查动态详情。

- 优点：**读极快**，一次 `ZRANGE` 就拿到 ID 列表，O(logN)
- 缺点：**写放大严重**。一个有 1000 万粉丝的大 V 发一条，要写 1000 万次；如果粉丝里有僵尸号，这些写全是浪费
- 适合：粉丝少的普通用户、读多写少的场景

**拉模式（读扩散 / Fan-out on Read）**

发动态只写自己的发件箱。读的时候，去拉所有关注的人的发件箱，按时间归并排序。

- 优点：**写极轻**，发一条只写一次
- 缺点：**读极慢**。关注了 500 个人就要合并 500 个列表，还要排序取前 20，延迟随关注数线性增长
- 适合：关注数少、或者粉丝极多的大 V

**推拉结合（业界主流）**

按粉丝数分流：

- 粉丝数 < 阈值（比如 10 万）：推模式，发一条写进所有粉丝收件箱
- 粉丝数 ≥ 阈值（大 V）：拉模式，只写发件箱
- 读的时候：先取自己的收件箱（推来的），再拉取自己关注的大 V 的发件箱（拉来的），两路归并

这个方案把"写放大"和"读放大"都控制在了可接受范围。

---

**第二部分：存储怎么设计**

**收件箱（推模式）**：用 Redis ZSet，key 是 `inbox:{userId}`，member 是动态 ID，score 是时间戳。

```bash
# 大 V 发动态，给粉丝写收件箱（Lua 脚本或 pipeline 批量）
ZADD inbox:1001 1698300000 post:88888
ZREMRANGEBYRANK inbox:1001 0 -1001   # 只保留最近 1000 条，防止无限增长
```

**为什么要截断到 1000 条**：Feed 流用户最多翻几页就到底了，存 1000 条足够；不截断的话内存会无限膨胀（1 亿用户 × 平均 200 条 × 每个 member 约 50 字节 ≈ 1 TB）。

**发件箱（大 V 用）**：同样用 ZSet，key 是 `outbox:{userId}`，但**不截断**或者保留更长（因为粉丝要拉，历史动态得在）。

**动态详情**：存 MySQL + Redis 缓存，按 postId 查。读 Feed 时拿到 ID 列表后批量 `MGET` 或者用 pipeline 取详情，**不要循环单查**（N+1 问题）。

**持久化备份**：Redis 是内存存储，宕机丢数据。所以收件箱要定期落库（比如每 5 分钟把增量写进 MySQL 的 `t_inbox` 表），恢复时从库里重建。或者更简单——**Redis 只当缓存，丢了就从发件箱重新 fan-out 重建**，但重建一个千万粉大 V 的成本极高，所以要权衡。

---

**第三部分：大 V 的特殊处理（重点）**

**问题一：写扩散的爆炸半径**

一个 5000 万粉的大 V 发一条，推模式要写 5000 万次 Redis。按 Redis 单实例 10 万 QPS 算，要 500 秒——而且这段时间 Redis 被打满，影响其他用户。

所以大 V 必须走拉模式。但拉模式又带来新问题：

**问题二：读时的合并成本**

如果我关注了 500 个大 V，每次刷 Feed 都要拉 500 个发件箱？这不现实。

解法是**缓存合并结果**：给每个用户维护一个"大 V 聚合列表"，后台定时（比如每 5 分钟）把关注的大 V 的新动态拉到一起，写进用户的"大 V 收件箱"；用户读的时候直接取这个聚合结果。

```bash
# 后台任务：为用户 1001 聚合其关注的大 V 动态
ZUNIONSTORE tmp:inbox:1001 2 inbox:1001 outbox:bigv:2001 outbox:bigv:2002
# 按 score（时间戳）合并，再截断
```

**问题三：新粉丝与历史动态**

一个新用户关注了一个大 V，他应该看到大 V 的历史动态吗？通常只看到"关注之后"的。所以拉模式要带时间边界：`ZRANGEBYSCORE outbox:bigv 关注时间戳 +inf`。

**问题四：僵尸粉与无效扩散**

推模式下，给不活跃用户写收件箱是纯浪费。优化是**只给 N 天内登录过的粉丝推**，其余的标为"懒加载"——他下次登录时再补拉。这个优化能把写扩散量降 60% 以上。

---

**第四部分：分页与"不重复不遗漏"**

Feed 流分页不能用 `offset + limit`，因为：

- 翻页期间有新动态插入，会导致**重复**（第 2 页出现第 1 页看过的）
- Redis ZSet 的 `ZRANGE` 用 offset 在大数据量下是 O(N)，越翻越慢

**正解是用游标分页（cursor-based）**：用上一页最后一条的 score（时间戳）做游标，下一页查 `ZREVRANGEBYSCORE key (lastScore -inf LIMIT 0 20`。

这样即使中间有新动态，也不会重复（因为按时间戳过滤），且复杂度是 O(logN + limit)。

**"遗漏"问题**：如果两次翻页之间，某条老动态被删了，游标还能正常工作；但如果是拉模式合并的多个列表在这一刻变化了，可能出现"某条动态这次没出现、下次又出现"。业务上通常可以接受，因为 Feed 流不要求严格的时间线完整——**这是需要主动跟面试官说明的取舍**。

---

**第五部分：其他细节**

**去重**：推拉结合后，同一条动态可能既在收件箱（如果该大 V 曾经粉丝少、走了推模式）又在发件箱里，合并时按 postId 去重。

**权限过滤**：读 Feed 时要过滤掉"已删除、无权限、被拉黑"的动态，所以在批量取详情后还要做一轮过滤，不能直接展示。

**排序**：时间序是最基础的，真实产品会用"时间 + 热度 + 兴趣"加权，但面试先说时间序，被追问再补"可以在 score 里混入权重"。

---

**面试话术收口**

我会这么答：三种模式各有取舍——推模式读快写贵、拉模式写快读贵，所以按粉丝数分流，普通用户推、大 V 拉。存储用 Redis ZSet 存收件箱和发件箱，收件箱截断 1000 条防膨胀，详情批量取避免 N+1。大 V 的读侧用后台定时聚合（ZUNIONSTORE）避免每次拉几百个列表。分页必须用时间戳游标，不能用 offset，否则翻页重复且越翻越慢。最后补一句：推模式只给活跃粉丝推、僵尸粉懒加载，能把写扩散量降一大截。
