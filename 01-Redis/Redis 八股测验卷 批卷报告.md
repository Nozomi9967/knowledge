## 一、认识 Redis（共 2 题）

### 第 1 题 — Redis vs Memcached，为什么做 MySQL 缓存

**评分：7 / 10**

**已答对的部分：**
- ✅ 正确列举了 Memcached 缺失而 Redis 具备的核心能力（多种数据结构、持久化、集群、Lua脚本/事务/订阅）
- ✅ 点出 Redis 基于内存 + 单线程，QPS 轻松过 10w

**硬伤/遗漏（标红）：**
- ❌ **高性能和高并发两个角度的展开不够**—题目明确要求"从高性能和高并发两个角度展开"，回答只提了单机 QPS。高性能还应该包括：Redis 的 IO 多路复用、数据结构高效（如 SDS 的预分配避免频繁扩容）；高并发还应该包括：单线程避免锁竞争、pipeline 批量处理减少 RTT
- ❌ **漏掉 Memcached 的"多线程"优势**—Memcached 本身就是多线程的，天然能利用多核 CPU 来处理 IO，这是一个重要的对称对比点。面试官听到你说 Memcached 没有集群或持久化，但会追问："那 Memcached 有没有什么 Redis 不具备的优点？"
- ❌ **缺少价值上限对比**—Memcached 单个 value 上限 1MB，Redis 是 512MB，这也是选型时的重要差异

**面试追问点（准则1）：**
- "你说 Redis 单机 QPS 过 10w，那如果我想进一步提高吞吐量，有什么手段？" → 应该能答 pipeline、读写分离、Redis Cluster
- "Memcached 本身就是多线程的，为什么 Redis 直到 6.0 才引入多线程？"（跨题追问，和后面第八题联动）

**评分：6 / 10**

**已答对的部分：**
- ✅ 优势：速度快（核心）
- ✅ 问题：宕机数据丢失、内存有限可能 OOM

**硬伤/遗漏（标红）：**

- ❌ **遗漏问题：成本高、容量受限影响缓存命中率设计**
- ❌ **遗漏问题：集群模式下的数据倾斜问题**

- "你说的数据不安全具体指什么？Redis 不是有 RDB 和 AOF 吗？"
- "Redis 内存满了怎么办？有哪些淘汰策略？你项目里用的哪一种？"

### 第 4 题 — 底层编码实现和转换条件

**评分：5 / 10**

**已答对的部分：**
- ✅ String → SDS ✓
- ✅ 7.0 变更：List 由 quicklist 实现，Hash/ZSet 压缩列表被 listpack 替代 ✓
- ✅ ZSet 压缩列表→跳表 ✓

**硬伤（标红）：**
- ❌ **List 编码转换条件错误**—你说"元素个数超过512个且元素大小超过64字节"，这是 Hash 和 ZSet 的压缩列表转换阈值。在旧版本中，List 的压缩列表配置参数是 `list-max-ziplist-size`，默认是每个节点不超过 8KB（不是 512/64）。且 List 压缩列表→双向链表的阈值是 `list-max-ziplist-entries 512`（新版已废弃）。**两者条件不能直接套用**

- ❌ **"7.0中，压缩列表被listpack替代"—只对了一半**：7.0 中 Hash 和 ZSet 的底层确实换成了 listpack，但 Set 的 intset 没有变化

### 第 10 题 — AOF 日志时机及顺序

**评分：4 / 10**

**已答对的部分：**
- ✅ "主线程执行完写操作后，会将对应的命令写AOF日志"—执行后记录 ✓

**硬伤（标红）：**
- ❌ **"先执行命令再记录日志"的原因说错了**—你说"如果写入AOF日志的命令有语法错误，会导致复现数据时出现错误"。但 Redis 的**命令在执行前就已经做了语法校验**，能够执行的命令逻辑上不会有语法错误。真正的正解是：
  1. ==**避免额外的语法检查开销**—让执行时自然验证命令合法==
  2. ==**不会阻塞写操作**—如果先写 AOF 再执行，写 AOF 的 IO 耗时阻塞了命令执行==
  3. ==**记录执行后的结果**—只有执行成功的命令才写入 AOF，确保恢复时状态一致（例如 `INCR` 执行后的具体值已经被改变了，记录的是"自增"命令本身而不是结果值）==
- ❌ **"由于写AOF日志是异步的，主线程并不用等待AOF写入成功即可返回响应"完全错误**—这是混淆了 AOF 的**写回策略**和**记录时机**。写 AOF 日志本身不是异步的：
  - `always` 策略下，主线程**必须等待** AOF 写入成功才返回
  - `everysec` 策略下，主线程写缓冲区就返回，刷盘由后台线程做
  - "主线程不用等待AOF写入成功" 对应的不是"先执行后记录"的副作用，而是**everysec/never 策略的行为**
- ❌ **"先执行后记录"的真正副作用没说—答非所问**：
  - 如果执行完命令后、写 AOF 日志前发生宕机，这条操作就丢了
  - AOF 写回如果采用 always 策略，写日志会阻塞下一个命令的执行（造成性能损耗）

**这道题需要重新理清逻辑，当前理解有严重的因果混淆（准则3—知识缺失，硬伤级别）**

**面试追问点：**
- "如果我用 always 策略，Redis 会怎么处理 AOF 写入？" → 主线程在事件循环中调用 `flushAppendOnlyFile`，根据策略决定是否阻塞

### 第 11 题 — AOF 写盘过程与策略

**评分：6 / 10**

**已答对的部分：**
- ✅ 写入流程：aof_buf → write 系统调用 → 内核决定刷盘 ✓（流程框架正确）
- ✅ always 策略：立刻写回 ✓
- ✅ everysec 策略：每秒写回 ✓
- ✅ never 策略：内核决定 ✓

**硬伤/遗漏（标红）：**
- ⚠️ 流程描述缺少一个关键中间态：write() 是写入 **内核缓冲区（page cache）**，fsync() 才是刷到磁盘。你说"内核决定何时写入到硬盘"过于粗糙，建议明确区分 write（到内核缓冲区）和 fsync（到磁盘）两个阶段，三种策略的本质区别就在**何时调用 fsync**

- ❌ **everysec 优缺点写得很混乱，甚至前后矛盾**：

| 回答原文 | 点评 |
|---|---|
| "优点：数据较完整，不那么容易丢失" | 这勉强可以，但不是标准说法 |
| "缺点：，如果系统宕机的话，也最多只会丢失上一秒的数据" | **这是优点不是缺点！** 缺点应该是：极端场景下丢失 1 秒数据，且刷盘峰值有延迟 |

  正确的优缺点对调了：
  - **优点**：性能好（每秒一次 fsync），最多丢 1 秒数据可接受
  - **缺点**：如果 Redis 或系统崩溃，丢失最后 1 秒的写入数据

- ❌ **never 策略描述"性能好"不严谨**—never 的性能确实好，但要说明"依赖 OS 刷盘策略，通常 30s 一次"，所以**丢数据最多（30s+）**，不能只说"性能好"

**面试追问点：**
- "everysec 是怎么保证每秒刷一次的？" → bio 后台线程每 1 秒执行一次 fsync
- "如果 AOF 写盘很慢（比如磁盘性能差），会发生什么？" → Redis 有 AOF 延迟写回机制、可以调整刷盘策略

### 第 12 题 — AOF 重写机制

**评分：9 / 10**

**已答对的部分：**
- ✅ 重写原因：AOF 日志膨胀，恢复慢，重写本质是"根据当前内存数据重新生成命令"（表述清晰准确）

### 第4题正解：五种类型底层编码完整对照表

| 类型 | 编码（6.x/7.0前） | 转换条件 | 7.0 变化 |
|:---|:---|:---|:---|
| **String** | int / embstr / raw（SDS） | 整数→int, ≤44字节→embstr, >44字节→raw | 不变 |
| **List** | ziplist → linkedlist / quicklist | 旧版：ziplist 默认每节点≤8KB（`list-max-ziplist-size`），超阈值触发升级<br>3.2+：直接由 quicklist 实现（ziplist 节点组成的双向链表） | quicklist 内部节点从 **ziplist → listpack** |
| **Hash** | ziplist → hashtable | **`hash-max-ziplist-entries 512` 且 `hash-max-ziplist-value 64`**（注意：两个条件**同时满足**才用 ziplist，任意一个超阈值就升到 hashtable） | ziplist → **listpack** |
| **Set** | **intset** → hashtable | **所有元素是整数 且 元素个数≤512** → intset<br>**否则** → hashtable<br>没有"元素大小64字节"这个维度 | intset **不变** |
| **ZSet** | ziplist → skiplist | **`zset-max-ziplist-entries 128` 且 `zset-max-ziplist-value 64`**（注意：ZSet 的 entry 阈值是 **128** 不是 512！） | ziplist → **listpack** |

**你答案中的错误来源**：你把 Hash 的条件（512/64）照搬给 List 和 Set 了。而：
- List 旧版阈值是 8KB（不是 512/64），且 3.2+ 已经是 quicklist
- Set 用的是 intset（不是 ziplist），条件只看"是否整数 + 个数≤512"
- ZSet 的 entry 阈值是 **128** 不是 512

### 第7题正解：四个角度完整展开

| 角度 | 要点 |
|:---|:---|
| **① 数据存储位置** | 所有数据在内存（~100ns 访问），无需磁盘 IO（~10ms 寻道），省去了从磁盘加载数据的等待时间 |
| **② 数据结构效率** | SDS（O(1) 获取长度 + 预分配避免频繁扩容）、跳表（O(logN) 查找 + O(logN) 范围遍历）、压缩列表/listpack（内存紧凑、CPU 缓存友好）、哈希表（O(1) 读写） |
| **③ 线程竞争开销** | 单线程无需加锁，无上下文切换开销，无死锁问题；多线程下共享数据结构的并发控制（CAS/互斥锁）会引入显著的性能损耗 |
| **④ IO 多路复用** | 基于 Reactor 模式：文件事件处理器 = 套接字 + IO 多路复用程序 + 事件分派器 + 事件处理器。单线程通过 epoll（Linux）/ kqueue（macOS）同时监听多个 socket 的就绪事件，将就绪事件放入队列，按序分发给对应的命令处理器执行 |

### 第11题正解：三种 appendfsync 策略对照

| 策略 | 行为 | 优点 | 缺点 |
|:---|:---|:---|:---|
| **always** | 每个命令执行完都调用 fsync | 最安全，最多丢一个命令 | 性能最差，频繁 fsync 降低吞吐 |
| **everysec** | 每秒调用一次 fsync（bio 后台线程） | 性能好 + 最多丢 1 秒数据，**最推荐的折中方案** | 宕机时丢 1 秒数据 |
| **never** | 不主动 fsync，由 OS 决定刷盘时机（通常 30s） | 性能最好 | 宕机时可能丢 30s+ 数据，**不推荐** |

你犯的主要错误：everysec 的"最多丢 1 秒数据"写在了**缺点**里，实际上这是 everysec 的优点（相比 always 它性能好很多，相比 never 它只丢 1 秒可以接受）。缺点应该是"宕机时确实会丢最后 1 秒数据"——这是可接受的折中代价，不是严格意义上的缺点。

### 第15题正解：哨兵模式

**哨兵的三项核心职责：**
1. **监控（Monitoring）** — 哨兵 **周期性地向主从节点发送 PING**（注意：是**哨兵 ping 节点**，不是反过来！），检查是否可达
2. **自动故障转移（Automatic Failover）** — 主节点下线时，选举一个从节点升级为新主节点
3. **通知（Notification）** — 将故障转移结果通知客户端（通过发布订阅的 `+switch-master` 频道）

**主观下线（SDOWN）vs 客观下线（ODOWN）的流程：**

```
哨兵A 发现 master 不可达
  → 标记为主观下线（SDOWN）
  → 通过 sentinel is-master-down-by-addr 向其他哨兵询问
  → 如果 ≥quorum 个哨兵都认为 master 不可达
    → 标记为客观下线（ODOWN）
    → 触发故障转移（选举新主节点）
```

| 你的回答 ❌ | 正确答案 ✅ |
|:---|:---|
| "主从节点会定时ping哨兵" | 反向！哨兵定时 PING 主从节点 |
| "一旦某个节点超过阈值没联系哨兵，就会被判断为下线" | 没有区分主客观下线。哨兵单方面判断是 SDOWN，多数哨兵都同意才 ODOWN |

### 第16题正解：Hash Slot 完整映射链路

```
客户端发送: SET user:1001 "Tom"

  Step 1: 计算槽位
    slot = CRC16("user:1001") & 16383    // 本质是 % 16384, 结果 0~16383
    // 注意：16383 是掩码（二进制 0011 1111 1111 1111），不是"对16383取模"
    // 两种等价写法：crc16(key) & 16383 或 crc16(key) % 16384

  Step 2: 客户端查找节点
    客户端本地缓存了 cluster 的槽位-节点映射表（来自 CLUSTER SLOTS 命令）
    如果槽位 A 属于节点 B，直接发请求到节点 B
    
  Step 3: 节点响应 / 重定向
    如果客户端缓存正确 → 节点直接处理
    如果客户端缓存过期（节点迁移了该槽）→ 返回 MOVED 重定向
    如果正在迁移数据 → 返回 ASK 重定向（客户端先发 ASKING，再发操作命令）

  Step 4: 客户端更新缓存
    收到 MOVED 后更新本地槽位映射缓存
```

**两种分配方式（不是"手动/平均"这么简单）：**
- **手动分配**：`CLUSTER ADDSLOTS 0 1 2 ... 5460`（指定槽位范围给某个节点）
- **自动分配**：`redis-cli --cluster create IP:PORT --cluster-replicas 1`（自动均分 16384 个槽）

### 第17题正解：min-slaves-max-lag 的作用

**两个参数配合使用的正确逻辑：**

```conf
# 配置示例：3个从节点，容忍最多10秒复制延迟
min-slaves-to-write 2    # 可用从节点数 < 2 时，主节点拒绝写入
min-slaves-max-lag 10    # 复制延迟 > 10秒的从节点视为"不可用"
```

| 你的回答 ❌ | 正确答案 ✅ |
|:---|:---|
| "如果主节点与哨兵的响应延迟大于y，则判断该主节点下线" | 完全错了。<br>`min-slaves-max-lag` 衡量的是**主节点和它的从节点之间的复制延迟**，不是主节点和哨兵的延迟。<br>哨兵判断主节点下线用的是 `sentinel down-after-milliseconds`，是另一个参数。 |

**完整脑裂防护机制的工作原理：**

1. 网络分区导致原主节点与从节点断开
2. 从节点复制延迟不断增大，超过 `min-slaves-max-lag 10`
3. 这些从节点被标记为"不可用"
4. 如果可用从节点数 < `min-slaves-to-write 2`
5. **原主节点拒绝写入请求**，直接返回错误
6. 即使哨兵选举了新主节点，原主节点上也没有积压的未同步数据 → **数据不会丢**

**代价**：网络抖动时，从节点短暂断开也会触发保护，导致正常写入被拒绝（写入可用性降低）。
